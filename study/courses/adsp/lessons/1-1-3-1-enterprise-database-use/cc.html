01

1. 기업 데이터베이스의 발전

1.1 부서별 파일에서 업무 데이터베이스로

초기의 기업 정보 처리는 회계, 급여, 재고처럼 계산량이 많고 반복적인 업무를 자동화하는 데 집중했다. 부서별 응용 프로그램이 각자의 파일을 관리하면 업무 속도는 빨라지지만 다음 문제가 생긴다.

  • 동일한 고객과 상품을 여러 부서가 중복 입력한다.
  • 코드와 금액 정의가 달라 보고서가 서로 맞지 않는다.
  • 영업의 주문 변경이 생산과 재무에 늦게 전달된다.
  • 파일 구조를 바꾸면 관련 프로그램을 모두 수정해야 한다.
  • 어느 자료가 최신 기준인지 판단하기 어렵다.

DBMS를 이용한 업무 데이터베이스는 공통 구조와 트랜잭션으로 중복·불일치를 줄이고, 여러 응용이 데이터를 공동 이용할 기반을 만들었다. 이 단계의 중심은 일상 거래를 빠르고 정확하게 기록하는 운영 처리다.

1.2 MIS와 전사 관리 정보

거래 데이터가 축적되자 기업은 단순 처리 결과를 관리자에게 제공하는 경영정보시스템을 발전시켰다. 매출 합계, 원가, 재고 회전, 예산 대비 실적처럼 정형화된 보고서를 주기적으로 만들어 관리 통제를 지원했다.

운영 데이터베이스가 “주문 한 건을 정확히 기록”하는 데 강하다면, 관리 정보는 “이번 달 제품군별 이익이 왜 달라졌는가”를 요약한다. 그러나 부서별 시스템이 독립되어 있으면 전사 관점의 원인 분석이 어렵다. 이 한계를 줄이기 위해 프로세스와 데이터를 통합하는 전사 시스템이 중요해졌다.

1.3 ERP를 통한 전사 프로세스 통합

ERP는 재무, 구매, 생산, 판매, 인사 등 기업의 핵심 자원과 업무 프로세스를 통합적으로 관리한다. 주문이 확정되면 재고 예약, 생산 계획, 출고, 매출 인식과 채권 관리로 이어지는 흐름을 공통 데이터와 규칙으로 연결한다.

ERP의 가치는 단순히 여러 프로그램을 한 화면에 넣는 것이 아니다.

  • 전사 기준정보와 코드의 통일
  • 부서 간 업무 사건의 즉시 연결
  • 중복 입력과 수작업 대사의 감소
  • 프로세스 상태와 책임의 가시화
  • 결산·원가·재고 정보의 일관성 향상

반면 기존 업무를 그대로 복제하거나 부서마다 예외 코드를 남발하면 통합 효과가 약해진다. 표준 프로세스, 데이터 소유권, 변경 관리가 함께 필요하다.

1.4 고객과 공급망으로 범위 확장

기업 내부 자원 통합 이후 정보시스템은 고객과 공급자 등 외부 관계까지 연결되었다.

  • CRM: 고객 접점, 상담, 구매, 캠페인, 서비스 이력을 통합해 고객 관계를 관리한다.
  • SCM: 수요, 구매, 조달, 생산, 재고, 물류 정보를 연결해 공급망 전체 흐름을 관리한다.
  • 전자상거래·웹 서비스: 고객이 직접 주문·조회하며 실시간 데이터가 급증한다.
  • 협력사 연계: 발주, 납기, 품질, 정산 정보를 조직 경계 밖과 교환한다.

ERP가 기업 내부 자원의 통합에 중심을 둔다면 CRM은 고객 관계, SCM은 공급망 흐름에 중심을 둔다. 실제 기업에서는 서로 데이터를 교환한다. CRM의 수요 신호가 SCM 계획에 반영되고, SCM의 납기 정보가 CRM 고객 안내에 사용된다.

1.5 데이터 웨어하우스와 분석 중심 발전

운영 시스템은 현재 거래를 신속하고 일관되게 처리하도록 설계된다. 복잡한 전사 분석을 운영 DB에서 직접 수행하면 거래 성능을 떨어뜨리고, 시스템별 과거 정의 차이 때문에 결과가 맞지 않을 수 있다.

데이터 웨어하우스는 여러 운영 시스템의 데이터를 추출·정제·통합해 주제별·시계열 분석에 적합하게 축적한다. 데이터 마트는 특정 부서나 주제의 분석 요구에 맞춘 부분 집합이다. OLAP, BI, 대시보드, 데이터 마이닝은 이를 이용해 패턴과 의사결정 정보를 만든다.

1.6 현대의 데이터 플랫폼

디지털 채널, 센서, 로그, 텍스트와 이미지가 늘면서 관계형 거래 데이터만으로는 모든 요구를 충족하기 어려워졌다. 기업은 데이터 레이크, 클라우드 저장·처리, 스트리밍, 분산 분석, 기계학습 플랫폼을 조합한다. 그러나 기술이 바뀌어도 다음 원칙은 그대로다.

  • 데이터의 의미와 책임자를 정한다.
  • 운영 원본과 분석용 파생 데이터를 추적한다.
  • 품질, 보안, 개인정보와 보존 정책을 적용한다.
  • 분석 결과를 실제 업무 행동과 성과에 연결한다.

“모든 데이터를 한 플랫폼에 모았다”는 것이 통합의 완료를 뜻하지 않는다. 동일 고객의 식별, 매출의 정의, 시간대와 통화 단위가 일치하지 않으면 물리적 중앙화만 이루어진다.

02

2. 경영 기능별 데이터 활용

2.1 생산·운영 관리

생산 기능은 수요를 충족하면서 품질, 원가, 납기와 설비 효율을 관리한다.

MRP는 생산 계획을 바탕으로 필요한 자재의 종류·수량·시점을 계산하고, ERP는 이를 구매·회계·영업과 연결한다. 센서 기반 예지정비는 고장 가능성을 조기에 찾아 계획 정비를 돕지만 오탐 비용과 안전 임계치를 함께 고려해야 한다.

2.2 영업·마케팅과 고객 관리

영업·마케팅은 고객과 시장을 이해해 적절한 상품·가격·채널·관계를 설계한다.

  • 고객 기본정보와 동의 상태
  • 구매 이력과 상품 선호
  • 웹·앱 행동과 캠페인 반응
  • 상담, 불만, 반품, 서비스 이력
  • 고객 생애가치, 이탈 위험, 세그먼트

CRM은 여러 접점의 고객 정보를 연결해 일관된 응대와 관계 관리를 지원한다. 분석을 통해 타깃 캠페인과 추천을 할 수 있지만, 단기 구매확률만 높이면 과도한 메시지나 차별적 혜택으로 장기 신뢰를 해칠 수 있다. 개인정보 이용 목적, 동의, 공정성, 고객 피로도를 함께 관리한다.

2.3 구매·물류와 공급망 관리

SCM은 원재료 공급자부터 생산, 창고, 운송, 고객까지의 흐름을 연결한다.

  • 공급자 가격·납기·품질·위험
  • 발주·입고·검수 상태
  • 창고별 재고와 이동
  • 운송 위치·예상 도착시간
  • 수요 예측과 안전재고

목표는 한 부서의 재고만 최소화하는 것이 아니다. 재고를 지나치게 줄이면 공급 지연 시 품절이 늘고, 안전재고를 과도하게 늘리면 보관·폐기 비용이 증가한다. 공급망 데이터는 서비스 수준, 비용, 위험을 전체 관점에서 균형 있게 판단하도록 돕는다.

2.4 재무·회계

재무·회계는 거래를 화폐 단위로 기록하고 자금, 수익성, 위험과 규정 준수를 관리한다.

  • 매출·매입·채권·채무
  • 원가와 예산 대비 실적
  • 현금 흐름과 자금 계획
  • 세금·결산·공시 자료
  • 이상 거래와 내부 통제 기록

다른 기능의 데이터가 재무 결과와 연결되어야 한다. 출고 수량과 매출 인식, 생산 투입과 제조원가, 직원 정보와 급여가 일치해야 한다. 분석은 현금 부족 위험, 상품별 이익, 예산 편차를 보여 주지만 회계 기준과 기간·통화·조정 규칙이 통일되어야 한다.

2.5 인적자원 관리

인사 기능은 인력 확보, 배치, 성장, 보상과 안전을 지원한다.

  • 인력 구성과 직무·역량
  • 채용 경로와 전형 결과
  • 교육 이력과 역량 개발
  • 근무·보상·성과 정보
  • 이동·퇴직과 조직 건강 지표

인사 분석은 필요한 역량과 교육 수요를 찾는 데 유용하지만 민감정보와 차별 위험이 크다. 과거 채용 결과를 그대로 학습하면 기존 편향을 재생산할 수 있다. 최소 수집, 목적 제한, 접근 통제, 설명 가능한 기준과 사람의 검토가 중요하다.

2.6 연구개발과 제품 관리

아이디어, 실험, 설계 변경, 결함, 고객 피드백, 출시 성과를 연결하면 어떤 기능이 실제 가치를 만드는지 학습할 수 있다. 실험 조건과 실패 결과도 지식 자산이다. 성공한 결과만 남기면 같은 실패를 반복하고 선택 편향이 생긴다.

2.7 기능 최적화와 전사 최적화의 차이

영업이 매출을 늘리기 위해 대규모 할인 주문을 받았지만 생산 능력과 현금 흐름을 고려하지 않으면 납기 지연과 손실이 생길 수 있다. 구매가 단가만 낮추려고 대량 발주하면 재고 비용이 증가한다. 기능별 데이터 활용은 필요하지만, 전사 관점에서는 공통 목표와 교차 영향이 연결되어야 한다.

03

3. 통합 정보시스템과 의사결정

3.1 통합 정보시스템의 의미

통합 정보시스템과 의사결정에서 통합은 화면을 하나로 합치는 것이 아니라 프로세스, 데이터 정의, 책임, 흐름을 연결하는 것이다. 주문 상태가 영업·물류·회계에서 같은 의미를 갖고, 한 단계의 사건이 다음 업무에 일관되게 전달되어야 한다.

통합의 주요 구성은 다음과 같다.

  • 공통 고객·상품·조직·계정 기준정보
  • 프로세스 단계와 상태 전이 규칙
  • 시스템 간 인터페이스와 오류 처리
  • 데이터 소유자와 품질 책임
  • 운영 시스템에서 분석 플랫폼까지의 계보
  • 역할별 권한과 감사 통제

통합은 모든 데이터를 하나의 거대한 테이블에 넣는 것이 아니다. 업무별 자율성을 유지하면서 공통 의미와 연결 계약을 관리한다.

운영 수준에는 빠르고 정확한 현재 상태가 중요하고, 전략 수준에는 내부 데이터뿐 아니라 시장·정책·경쟁·기술 변화와 불확실성 분석이 필요하다. 같은 데이터라도 의사결정 수준에 맞게 집계 범위와 표현이 달라진다.

3.3 OLTP와 분석 환경의 역할

  • OLTP: 많은 개별 거래를 빠르고 정확하게 삽입·수정·조회한다. 현재 업무 상태와 트랜잭션 일관성이 중요하다.
  • OLAP·분석: 여러 기간과 차원을 집계·비교해 패턴과 원인을 탐색한다. 과거 이력과 통합 관점이 중요하다.

주문 등록 화면에서 복잡한 5년 추세 분석을 직접 수행하면 운영 성능이 흔들릴 수 있다. 반대로 분석용 갱신 지연 데이터로 현재 배송 여부를 고객에게 안내하면 잘못된 응답을 줄 수 있다. 목적에 맞는 환경을 사용하고, 원본과 분석 데이터 사이의 갱신 시점과 정의를 표시한다.

3.4 의사결정 지원의 발전

정형 보고서에서 시작해 사용자가 다차원으로 탐색하는 OLAP, 핵심지표를 시각화하는 BI, 미래를 추정하는 예측 분석, 제약 아래 행동안을 찾는 최적화로 발전할 수 있다.

코드 예시 · text

무슨 일이 있었는가?       → 기술·보고
왜 일어났는가?            → 진단·원인 탐색
앞으로 무엇이 일어날까?   → 예측

결과는 실제로 나아졌는가? → 효과 측정과 학습

단계가 높다고 언제나 더 좋은 것은 아니다. 기본 데이터 품질과 업무 정의가 불안정한데 복잡한 예측 모델부터 만들면 신뢰하기 어렵다. 현재 문제에 필요한 가장 단순하고 검증 가능한 방법을 선택한다.

3.5 단일 진실 공급원의 정확한 해석

전사 통합은 흔히 “하나의 진실”을 목표로 표현하지만, 모든 지표가 하나의 값만 가져야 한다는 뜻은 아니다. 매출도 주문 기준, 출고 기준, 회계 인식 기준에 따라 합법적으로 다를 수 있다. 중요한 것은 각 정의, 사용 목적, 계산 규칙과 책임자를 명확히 하여 같은 이름을 다른 뜻으로 쓰지 않는 것이다.

좋은 통합 정보는 다음을 제공한다.

  • 지표의 업무 정의와 계산식
  • 원천 시스템과 갱신 주기
  • 기준 시점·통화·세금 포함 여부
  • 품질 상태와 적용 한계
  • 상세 데이터로의 추적 가능성

3.6 데이터 기반 의사결정의 통제

데이터는 의사결정을 지원하지만 책임을 대신하지 않는다.

  1. 문제와 목표 지표를 정의한다.
  2. 관련 데이터와 품질·대표성을 확인한다.
  3. 가설과 대안을 비교한다.
  4. 분석의 불확실성과 제한을 설명한다.
  5. 이해관계자, 법·윤리, 장기 효과를 검토한다.
  6. 권한 있는 사람이 결정하고 근거를 기록한다.
  7. 실행 결과를 측정해 모델과 규칙을 갱신한다.

대시보드의 숫자가 바뀌었다는 이유만으로 행동하면 지표 조작이나 부분 최적화가 생길 수 있다. 지표가 실제 목표를 잘 대변하는지, 다른 부서와 고객에게 비용을 전가하지 않는지 확인해야 한다.

04

4. 종합 사례: 제조기업의 주문–생산–수익 연결

A사는 영업, 생산, 구매, 회계가 각각 파일을 관리했다. 영업은 고객 주문을 많이 받았지만 생산은 납기를 알지 못했고, 구매는 오래된 생산계획으로 원재료를 발주했다. 회계는 월말에 파일을 수동 대사하느라 결산이 늦었다.

개선 과정은 다음과 같다.

  1. 고객, 상품, 자재, 조직, 거래처 코드를 통일한다.
  2. 주문–생산계획–자재소요–발주–입고–생산–출고–매출의 상태를 연결한다.
  3. ERP에서 핵심 거래와 자원 흐름을 관리한다.
  4. CRM의 캠페인·고객 반응을 수요 신호와 연결한다.
  5. SCM에서 공급자 납기와 물류 위험을 반영한다.
  6. 데이터 웨어하우스에 이력과 외부 시장 데이터를 통합한다.
  7. 주문 수익성, 납기 위험, 설비 능력, 현금 흐름을 함께 제시한다.
  8. 실제 납기 준수율과 이익 개선을 측정해 계획 규칙을 갱신한다.

이제 영업은 매출액만이 아니라 생산 가능성과 기여이익을 보고 주문 조건을 판단하고, 구매는 단가와 함께 재고·납기 위험을 본다. 이것이 기능별 데이터를 통합해 전사 의사결정으로 발전시킨 사례다.

05

5. 시험에서 자주 틀리는 판단

함정 1. ERP는 회계 프로그램만을 뜻한다

재무를 포함하지만 구매, 생산, 판매, 인사 등 전사 자원과 프로세스 통합이 핵심이다.

함정 2. CRM은 신규 판매만 극대화한다

고객 접점과 관계의 전 과정을 관리하며 서비스, 만족, 유지, 불만도 포함한다.

함정 3. SCM은 기업 내부 창고만 관리한다

공급자부터 생산·물류·고객까지 공급망 전체의 흐름과 위험을 연결한다.

함정 4. 데이터 웨어하우스는 실시간 주문 등록용이다

여러 원천의 이력을 통합해 분석하는 데 중심이 있다. 운영 거래 처리는 OLTP 환경의 역할이다.

함정 5. 통합은 모든 데이터를 한 테이블에 넣는 것이다

공통 의미, 기준정보, 프로세스, 인터페이스와 책임을 연결하는 것이 핵심이다.

함정 6. 데이터 기반 의사결정은 사람의 판단을 제거한다

분석은 근거와 대안을 제공한다. 불확실성, 가치, 윤리와 책임을 고려한 최종 판단과 결과 검토가 필요하다.

8. 정답과 해설

  1. 2 — ERP는 여러 기능의 자원과 프로세스를 공통 데이터로 연결하는 전사 통합 시스템이다.
  2. 1 — CRM은 획득뿐 아니라 상담, 서비스, 유지와 장기 고객 관계를 관리한다.
  3. 2 — SCM은 조직 경계를 넘어 공급자부터 고객까지의 물자·정보·자금 흐름을 본다.
  4. 2 — 운영 원천을 통합하고 과거 이력을 분석하기 적합하게 제공하는 것이 핵심이다.
  5. 1 — 구매 단가라는 한 기능의 지표만 최적화해 전사 재고와 폐기 비용을 악화시킨 사례다.
  6. 2 — 단기 반복 업무에는 최신 거래와 작업 상태처럼 상세하고 적시적인 정보가 필요하다.
  7. 2 — 전략 결정은 장기 방향과 투자에 관한 비정형 문제이며 외부 환경과 불확실성이 크다.
  8. 2 — 화면이나 저장 위치보다 데이터 의미, 프로세스, 연계 규칙과 책임의 통합이 중요하다.
  9. 2 — 목적에 따른 여러 기준이 가능하므로 동일 명칭의 정의와 계보를 명확히 해 혼동을 막아야 한다.
  10. 2 — 분석 근거와 함께 불확실성·가치·위험을 검토하고 사후 효과로 학습해야 한다.

9. 핵심 요약

  • 기업 데이터베이스의 발전은 부서별 거래 자동화에서 전사 프로세스 통합, 고객·공급망 연결, 데이터 웨어하우스와 분석·기계학습 활용으로 확장된 흐름이다.
  • ERP는 전사 자원과 내부 프로세스, CRM은 고객 관계, SCM은 공급망 전체 흐름을 중심으로 하며 실제로 서로 데이터를 교환한다.
  • 경영 기능별 데이터 활용은 생산·영업·마케팅·구매·물류·재무·인사·연구개발의 운영과 판단을 지원한다.
  • 한 부서의 지표만 최적화하면 전사 비용과 위험이 악화될 수 있으므로 기능 간 영향을 연결해야 한다.
  • 통합 정보시스템과 의사결정은 공통 의미·기준정보·프로세스·연계·책임을 바탕으로 운영·관리·전략 수준의 결정을 지원한다.
  • OLTP는 현재 거래 처리, 데이터 웨어하우스·OLAP·BI는 통합 이력 분석에 중심이 있으며 목적과 갱신 시점을 구별해야 한다.
  • 데이터 기반 의사결정은 사람의 책임을 없애지 않는다. 불확실성·윤리·장기 효과를 검토하고 실행 결과를 측정해 다시 학습해야 한다.
