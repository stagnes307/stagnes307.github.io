# 2-2-1-3. 분석 실행계획 구체화

> **학습 범위**: 이 레슨은 ADsP `데이터분석 기획 > 분석 마스터플랜 > 마스터플랜 수립` 중 **데이터·기술·조직 조건**, **성과 기준과 이행 계획**, **중장기 계획의 갱신**을 다룬다. 로드맵의 단계와 과제를 실제 착수 가능한 작업·책임·자원·수용 기준으로 구체화하고, 실행 결과를 다시 중장기 계획에 반영하는 것이 목표다.

로드맵이 “고객 이탈 시제품을 1단계에 수행한다”는 방향을 보여 준다면 실행계획은 어떤 데이터가 언제 누구의 승인으로 제공되고, 누가 어떤 산출물을 만들며, 어떤 기준에서 제한 시험으로 넘어갈지 적는다. 일정표만 상세하다고 실행계획이 되는 것이 아니다. 데이터·기술·조직 준비와 업무 성과, 위험 통제, 변경·중단 기준이 연결되어야 한다.

---

## 1. 로드맵과 실행계획 비교

| 구분 | 분석 로드맵 | 분석 실행계획 |
|---|---|---|
| 목적 | 포트폴리오의 단계·순서·능력 방향 | 특정 단계·과제를 실제로 수행·통제 |
| 시간 수준 | 중장기, 가까운 단계만 상세 | 착수 기간의 작업·이정표·책임 상세 |
| 핵심 내용 | 적용 범위, 의존, 관문, 파동 | 데이터·기술·조직 조건, 작업, 자원, 수용 |
| 책임 | 주관 조직·프로그램 수준 | 담당·승인·협의·보고 역할 |
| 변경 | 전략·관문 결과로 순서 조정 | 실행 편차·이슈를 통제하고 로드맵에 환류 |

```text
로드맵의 단계 목표
       ↓
실행 대상 과제·범위 확정
       ↓
데이터·기술·조직 조건과 의존 확인
       ↓
작업·일정·원가·책임·산출물 계획
       ↓
성과·위험·관문·운영 이행 계획
       ↓
실행 결과 → 다음 단계·중장기 로드맵 갱신
```

## 2. 데이터·기술·조직 조건

### 2.1 데이터 조건

**데이터·기술·조직 조건** 중 데이터 계획은 필요한 원천의 이름만 나열하지 않는다.

| 항목 | 명세 내용 |
|---|---|
| 업무 정의 | 대상·관찰 단위·목표값·예측 시점·코드 의미 |
| 범위 | 기간, 대상 집단, 채널, 지역, 최소 건수·사건 |
| 원천·책임 | 원천 시스템, 소유자, 제공·품질 책임 |
| 획득 | 접근 승인, 추출 방법, 주기, 지연, 재처리 |
| 품질 | 정확·완전·일관·유일·적시·대표성 기준 |
| 결합 | 식별자, 시간·공간 정렬, 단위·코드 매핑 |
| 권리·보호 | 목적, 최소 항목, 권한, 보존·삭제, 반출 |
| 계보·버전 | 원천→변환→특징 경로와 스냅샷·변경 통지 |
| 운영 | 입력 장애, 스키마 변화, 대체값·중단 절차 |

데이터 준비 산출물에는 데이터 요구 명세, 사전·계보, 접근 승인, 품질 프로파일·대사, 정제·결합 규칙, 승인 데이터셋과 운영 계약이 포함될 수 있다. 확보 실패 시 대체·범위 축소·수집 과제 전환 조건을 미리 정한다.

### 2.2 기술 조건

기술 계획은 개발·시험·운영의 생애주기를 포함한다.

- 수집·저장·연산 환경과 예상 데이터·부하 규모
- 분석 도구·언어·라이브러리와 재현 가능한 실행 환경
- 코드·데이터·모델·설정 버전 관리와 승인 절차
- 학습·검증·시험 분리, 실험 추적과 자동 검사
- 업무 시스템과의 파일·API·화면·배치 인터페이스
- 인증·권한·암호화·비밀·로그 마스킹과 감사
- 성능·가용성·장애·복구·되돌림과 모니터링
- 확장·유지보수·공급자 종속·종료 이식 계획

시제품 노트북이 실행된다는 사실과 운영 가능성은 다르다. 운영에서는 정해진 시점의 입력, 동시 요청, 실패·재시도, 결과 추적, 모델·데이터 변화, 보안 패치와 책임 교대가 필요하다.

### 2.3 조직 조건

조직 계획에는 후원, 현업, 데이터, 분석, 기술, 운영, 보안·법무의 책임과 투입 시점을 명시한다.

| 역할 | 실행 책임 | 주요 승인·결정 |
|---|---|---|
| 후원자 | 자원·장애 제거·전략 정렬 | 범위·관문·잔여 위험 수용 |
| 과제·현업 책임자 | 문제·업무 규칙·적용·성과 | 사용 절차·업무 수용 |
| 데이터 책임자 | 정의·품질·접근·계보 | 데이터셋·수정·사용 승인 |
| 분석 책임자 | 가설·방법·검증·설명 | 분석 품질·한계 권고 |
| 기술·운영 책임자 | 파이프라인·통합·서비스·감시 | 운영 준비·변경·복구 |
| 보안·법무·윤리 | 보호·권리·영향 검토 | 통제·예외·사용 제한 |

책임표는 모든 사람을 단순히 “협의”로 두지 않는다. 작업 담당, 최종 승인, 의견 제공, 결과 통보를 구분하고 한 결정에 최종 책임자가 누구인지 명확히 한다. 필요한 교육, 현업 작업 시간, 외부 전문성·지식 이전도 계획한다.

### 2.4 준비도와 선행 조건

착수 전에 모든 것이 완벽할 필요는 없지만 어떤 미충족 조건을 어떤 위험으로 수용했는지 기록한다. 데이터 표본·권리, 기준선, 현업 책임자, 시험 환경, 최소 보안 통제가 없으면 분석 결과를 판정하거나 안전하게 실행하기 어렵다.

선행 조건은 다음처럼 구체화한다.

```text
착수 조건
- 과제 정의서·범위·비범위 승인
- 핵심 데이터 표본과 이용 목적 승인
- 현재 업무 기준선과 성과 측정 방법 확정
- 현업·데이터·분석·운영 책임자 및 투입 시간 확인
- 격리된 분석 환경과 접근·반출 통제 준비

운영 시험 진입 조건
- 독립 검증·주요 오류·집단별 결과 검토
- 인터페이스·지연·결측·장애·되돌림 시험
- 사용자 교육·사람 검토·이의 처리 절차
- 모니터링·지원·중단 책임 인계
```

## 3. 성과 기준과 이행 계획

### 3.1 성과 기준의 계층

**성과 기준과 이행 계획**은 산출물 완료와 가치 달성을 분리한다.

| 계층 | 질문 | 지표 예 |
|---|---|---|
| 산출물 | 약속한 문서·데이터·모델·시스템이 수용됐는가 | 검토·시험·인계 완료 |
| 데이터 | 필요한 품질·시점·대표성을 충족하는가 | 누락·대사·지연·연결률 |
| 분석 | 기준 대비 안정적 성능과 오류 통제를 갖는가 | 오차·정밀도·재현율·안정성 |
| 업무 | 의사결정과 현업 과업이 개선되는가 | 처리 시간·손실·유지·품질 |
| 사용 | 사용자가 실제로 이해·채택하는가 | 채택·무시·수정·문의 |
| 운영 | 지속 가능한 성능·가용성·비용인가 | 지연·장애·비용·복구 |
| 책임 | 권리·공정성·보안·설명을 지키는가 | 집단별 오류·사고·이의 |

각 지표에는 정의, 산식, 데이터 원천, 기준선, 목표·최소 수용, 측정 주기, 책임자를 둔다. 목표 수치는 현재 상태와 업무 비용에서 정하며 임의의 보편값을 만들지 않는다.

### 3.2 산출물과 수용 기준

작업마다 산출물과 완료 정의를 연결한다.

| 작업 | 산출물 | 수용 기준 예 |
|---|---|---|
| 데이터 진단 | 품질·계보 보고 | 대상·기간·핵심 라벨의 한계와 대안 승인 |
| 기준 모델 | 재현 가능한 코드·결과 | 시간 누출 없음, 기준선·오류 공개 |
| 후보 모델 | 비교·설명·안정성 보고 | 독립 검증, 중요 위험 기준 충족 |
| 현업 시제품 | 화면·업무 절차 | 대표 사용자의 과업 시험·피드백 반영 |
| 제한 시험 | 비교 결과·부작용 | 순증 업무 효과와 중단 기준 검토 |
| 운영 인계 | 파이프라인·감시·문서 | 장애·되돌림·지원 책임 점검 완료 |

“분석 완료” 같은 모호한 이정표를 쓰지 않는다. 검토자가 같은 근거로 완료를 판정할 수 있어야 한다.

### 3.3 작업·일정·책임 구체화

작업 분해 후 선행·후속 관계, 예상 기간, 역할별 투입, 외부 승인, 이정표를 연결한다. 탐색 작업에는 시간상자와 종료 질문을 둔다. 임계 경로뿐 아니라 데이터 담당·현업 검토자처럼 여러 작업이 공유하는 자원 병목을 확인한다.

```text
W1 과제·기준선 확정 (현업 승인)
  ├ W2 데이터 접근·표본 (데이터·보안 승인)
  │   └ W3 품질·라벨 검토
  │        └ W4 기준 모델·오류 분석
  │             ├ W5 후보 분석
  │             └ W6 시제품 업무 설계
  └─────────────── W7 제한 시험 준비
                         └ W8 시험·관문 결정
```

### 3.4 변화 이행

분석을 업무에 적용하려면 사용자와 프로세스 변화가 필요하다.

- 현재·목표 업무 흐름과 바뀌는 역할·권한을 정의한다.
- 사용자가 결과·오류·한계를 이해하도록 교육한다.
- 낮은 확신·예외·이의·오류 정정과 사람 검토 경로를 둔다.
- 기존 지표와 보상 체계가 새 행동을 방해하지 않는지 본다.
- 일부 대상에서 시험하고 피드백·저항·작업 부담을 측정한다.
- 적용·지원·운영 책임과 의사소통을 단계별로 배치한다.

기술 배포일과 변화 이행 완료일은 다를 수 있다. 사용자가 채택하고 업무 결과가 안정될 때까지 지원과 측정이 필요하다.

### 3.5 위험·이슈·변경 계획

위험 등록부, 품질 관문, 이슈 상향, 변경 승인 절차를 실행계획에 포함한다. 데이터 권리, 핵심 라벨, 성능·공정성, 일정·공급자, 운영 장애의 촉발 조건과 대응을 정한다. 이미 발생한 이슈는 담당·기한·임시 조치·근본 조치·재검증을 추적한다.

범위 변경은 가치, 일정·원가, 품질·위험, 의존 과제와 중장기 로드맵에 미치는 영향을 분석하고 승인한다.

## 4. 중장기 계획의 갱신

### 4.1 갱신이 필요한 이유

**중장기 계획의 갱신**은 계획 실패가 아니라 분석 학습의 정상적인 결과다. 첫 과제에서 데이터 품질과 채택이 예상보다 좋거나 나쁠 수 있고, 전략·규제·기술·예산도 바뀐다. 로드맵을 그대로 지키는 것이 아니라 원래 가치와 새 증거를 비교한다.

### 4.2 갱신 촉발 조건

- 단계 관문에서 계속·축소·전환·중단 결정이 났다.
- 실제 업무 효과와 운영 비용이 예상 범위를 벗어났다.
- 공통 데이터·기술 기반이 준비되거나 지연되었다.
- 새 규제·사고·시장 기회로 시급성이 바뀌었다.
- 데이터 사용 권리·공급자·기술 지원 조건이 변했다.
- 핵심 인력과 조직 구조·현업 프로세스가 바뀌었다.
- 운영 모델 유지 부담이 새 과제 용량을 줄였다.
- 새로운 과제 후보가 기존 과제를 대체·통합한다.

### 4.3 갱신 절차

1. 실행 결과를 원래 가치·비용·위험 가정과 비교한다.
2. 어떤 가정이 틀렸고 어떤 능력·자산을 얻었는지 정리한다.
3. 관련 과제의 가치·실행성·의존성과 자원 용량을 재평가한다.
4. 순서·범위·방식·단계·성과 목표의 대안을 만든다.
5. 즉시 중단·유지해야 할 통제와 계약 영향을 확인한다.
6. 이해관계자와 변경 영향·잔여 위험을 검토해 승인한다.
7. 로드맵, 예산·자원, 실행계획, 성과 기준과 의사소통을 갱신한다.
8. 재평가 날짜와 다음 촉발 조건을 정한다.

### 4.4 학습의 포트폴리오 환류

한 과제의 학습은 다른 과제에 재사용한다. 고객 ID 연결의 오류율, 외부 데이터 계약 기간, 현업 시험에 필요한 시간, 배포 비용의 실제치를 다음 추정에 반영한다. 실패한 모델도 라벨 정의·특징·오류 사례·검증 코드가 공통 자산이 될 수 있다.

단, 과거 한 사례를 모든 영역에 그대로 적용하지 않는다. 데이터·위험·사용자 맥락 차이를 확인한다.

### 4.5 버전과 의사결정 기록

중장기 계획에는 기준일·버전, 변경 내용·이유, 근거, 영향 과제, 승인자를 기록한다. 이전 버전을 보존해 전략 변화와 성과를 추적한다. 변경이 잦아도 가까운 단계의 책임·예산이 모호해져서는 안 된다.

## 5. 구체 사례: 이탈 조기지원 실행계획

### 데이터·기술·조직 조건

고객-계약 단위, 갱신 30일 전 예측, 해지·갱신 라벨과 이용·문의·청구 데이터의 가용 시점을 정의한다. 민감한 문의 원문은 필요한 범주로 최소화한다. 분석 환경과 운영 점수 배치, 결과 설명·상관 ID, 결측 시 기존 상담 목록으로 돌아가는 절차를 준비한다. 현업·데이터·분석·운영·보안 책임자를 배정한다.

예측 시점의 30일은 업무 사례의 합의값이며 보편 기준이 아니다. 상담 용량과 고객에게 유용한 선행 시간을 근거로 정한다.

### 성과와 이행

기준 모델과 중요 이탈 재현, 정상 고객 오접촉, 집단별 오류, 점수 도착 지연을 본다. 제한 시험에서는 실제 순증 유지, 상담 시간, 연락 피로·민원, 상담원의 설명 이해와 무시 이유를 측정한다. 낮은 확신은 사람 검토하고 자동 불이익 결정에는 사용하지 않는다.

### 중장기 갱신

시험에서 예측은 좋지만 상담 용량이 부족하면 대상 범위를 줄이고 업무 자동화·인력 계획을 선행한다. 문의 데이터 권리가 제한되면 해당 특징을 제거하고 가치·성능을 재평가한다. 효과가 확인되면 다른 상품으로 확대하되 상품별 이탈 정의와 집단 성능을 다시 검증한다.

## 6. 실행계획 판단 절차와 완성도 체크리스트

- 과제 정의와 로드맵 단계·범위·관문이 일치하는가?
- 데이터의 정의·기간·원천·권리·품질·계보·운영 계약이 있는가?
- 개발·시험·운영 기술 환경과 보안·복구·이식 조건이 있는가?
- 역할별 작업·승인·협의·투입 시간이 명확한가?
- 작업에 선행 조건·산출물·수용 기준·이정표가 연결되는가?
- 기술·업무·사용·운영·책임 성과와 기준선이 있는가?
- 현업 변화·교육·예외·이의·사람 검토·지원 계획이 있는가?
- 위험 촉발·이슈 상향·변경 영향·중단 기준이 있는가?
- 운영 후 모니터링·재학습·폐기·비용 책임이 있는가?
- 중장기 계획 갱신의 촉발·절차·버전·승인자가 정해졌는가?

## 7. 시험에서 자주 틀리는 포인트

1. 로드맵과 실행계획을 같은 문서라고 본다.
2. 데이터 테이블 이름만 적고 정의·시점·권리·품질을 생략한다.
3. 시제품 실행을 운영 기술 조건 충족으로 본다.
4. 모든 역할을 협의 대상으로 두고 최종 책임자를 정하지 않는다.
5. 산출물 완료와 업무 가치 달성을 혼동한다.
6. 모델 정확도만 성과 기준으로 사용한다.
7. 기술 배포를 변화 이행 완료로 본다.
8. 일정표에 데이터 승인·현업 시험·보안 관문을 누락한다.
9. 중장기 계획 갱신을 초기 기획 실패로 보고 새 증거를 무시한다.
10. 계획을 갱신하면서 변경 이유·영향·이전 버전을 남기지 않는다.

## 정답과 해설

### 정답 1
로드맵은 중장기 과제·능력의 단계·순서·의존을 보여 주고, 실행계획은 가까운 단계의 데이터·기술·조직 조건, 작업·책임·자원·수용 기준을 상세화한다.

### 정답 2
업무 정의, 범위, 원천·책임, 획득 주기·지연, 품질, 결합 키·단위, 권리·보호, 계보·버전, 운영 장애 중 여섯 가지다.

### 정답 3
운영에는 반복 입력, 동시·대규모 부하, 권한, 장애·결측·재시도, 모니터링, 변경·복구·책임 교대가 필요하며 노트북의 일회 실행은 이를 검증하지 않기 때문이다.

### 정답 4
여러 사람이 의견을 주어도 범위·데이터·운영·위험의 최종 결정을 누가 내리고 결과에 책임지는지 불명확하면 지연과 책임 공백이 생기기 때문이다.

### 정답 5
산출물, 데이터, 분석, 업무, 사용, 운영, 책임 성과 중 다섯 가지다.

### 정답 6
“완료”의 해석 차이를 없애고 검토자가 같은 증거로 품질·다음 관문 진입을 판정하며, 일정 진행률이 실질적 결과를 반영하게 하기 위해서다.

### 정답 7
현재·목표 업무와 역할 정의, 사용자 교육, 예외·이의·사람 검토, 지표·보상 정렬, 제한 시험, 지원·운영 책임 배치 중 다섯 가지다.

### 정답 8
관문 결정, 실제 가치·비용 편차, 기반 준비·지연, 전략·규제·시장 변화, 데이터 권리·공급자 변화, 인력·조직 변화, 운영 부담 증가 중 다섯 가지다.

### 정답 9
라벨 오류 유형, 사용할 수 없는 데이터 조건, 재현 가능한 전처리·검증 코드, 실제 데이터 승인 기간을 다음 과제의 정의·추정·품질 기준에 재사용할 수 있다.

### 정답 10
순증 고객 유지, 정상 고객 오접촉·민원, 상담 처리 시간·용량, 현업 채택·무시 이유, 집단별 영향 중 네 가지다.

## 핵심 요약

- **데이터·기술·조직 조건**은 정의·품질·권리·계보, 개발부터 운영까지의 기술 생애주기, 역할·승인·역량과 선행 조건을 구체화한다.
- **성과 기준과 이행 계획**은 산출물·데이터·분석·업무·사용·운영·책임 성과를 기준선과 연결하고 작업별 수용 기준을 둔다.
- 기술 배포뿐 아니라 현업 절차·교육·예외·이의·지원과 운영 책임이 준비되어야 이행이 완료된다.
- **중장기 계획의 갱신**은 관문·가치·비용·기반·전략·자원 변화의 새 증거를 포트폴리오와 로드맵에 환류하는 활동이다.
- 실행계획은 일정표가 아니라 데이터·기술·조직·성과·위험을 누가 어떤 증거로 완수할지 정한 계약이다.
- 계획 변경에는 이유·대안·영향·승인·버전과 다음 재검토 조건을 남겨야 한다.
