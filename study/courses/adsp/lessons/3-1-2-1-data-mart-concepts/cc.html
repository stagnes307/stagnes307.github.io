01

1. 학습 목표와 설계 질문

데이터 마트는 단순히 원천 데이터를 복사한 작은 저장소가 아니다. 특정 주제나 부서, 분석 목적에 필요한 데이터를 일관된 정의와 분석 가능한 입도로 제공하는 구조다. 학습 후에는 마트의 이용자·분석 질문·관측 단위·갱신 시점을 명시하고, 데이터 웨어하우스와 역할을 구분하며, 종속형과 독립형 마트의 장단점을 설명할 수 있어야 한다.

설계는 다음 질문에서 출발한다.

  1. 누가 어떤 의사결정을 위해 사용하는가?
  2. 한 행은 고객, 주문, 상품, 일자 중 무엇을 뜻하는가?
  3. 지표의 기준 시점과 집계 기간은 언제인가?
  4. 식별키와 이력 기준은 무엇인가?
  5. 원천에서 마트까지 변환 규칙과 계보를 추적할 수 있는가?
  6. 갱신 주기, 품질 기준, 접근 권한과 보존 기간은 무엇인가?
02

2. 데이터 마트의 정의와 목적

2.1 정의

데이터 마트는 조직 전체 또는 여러 원천의 데이터를 특정 업무 주제와 분석 사용자에게 맞게 선별·정제·구조화한 분석용 데이터 집합이다. 판매 분석 마트, 고객 행동 마트, 위험 관리 마트처럼 범위가 비교적 명확하다. 저장 방식은 관계형 테이블, 분석 플랫폼의 관리 테이블 등 환경에 따라 달라질 수 있지만 핵심은 분석 목적, 공통 정의, 관리 책임이다.

2. 데이터 마트의 정의와 목적 · 학습 표 1
목적설명확인 지표
접근성 향상반복되는 원천 해석을 줄임분석 준비 시간
정의 일관성동일 지표를 같은 규칙으로 계산지표 대사 차이
성능과 안정성운영 시스템의 부하와 변동을 격리조회 시간, 운영 영향
재사용성검증된 분석 단위를 여러 과제에서 활용중복 가공 감소
통제 가능성권한·품질·이력을 관리오류율, 권한 점검

마트가 있으면 분석가가 매번 운영 테이블의 복잡한 상태 코드와 이력 구조를 해석할 필요가 줄어든다. 그러나 원천 의미를 잘못 정의한 마트는 오류를 빠르고 넓게 재사용하게 만든다. 따라서 편의성보다 데이터 정의서, 책임자, 검증 규칙이 먼저다.

2.2 마트가 해결하려는 문제

운영 데이터는 거래 처리와 현재 상태 관리에 최적화되어 분석 질문과 구조가 다를 수 있다. 주문 취소 이력이 여러 행에 나뉘거나, 고객 상태가 현재 값만 보이거나, 시스템마다 같은 고객 식별자가 다를 수 있다. 마트는 분석 기준 시점에 맞춰 이러한 차이를 해석하고 필요한 관측 단위를 제공한다.

예를 들어 월별 고객 유지 분석에 주문 원장 전체를 그대로 넘기는 대신 고객×기준월 한 행으로 범위를 설계할 수 있다. 단, 고객별 월 합계를 만드는 구체 산식은 집계 레슨의 주범위다. 여기서는 한 행의 의미, 원천 범위, 기준 시점, 포함·제외 정책을 마트 계약으로 정의하는 데 집중한다.

2.3 데이터 마트가 아닌 것

  • 개인 PC에 임시로 복사한 출처 불명 CSV
  • 산식과 갱신 일시가 없는 결과 파일
  • 운영 DB의 모든 열을 목적 없이 복제한 표
  • 같은 지표 이름이 사용자마다 다른 의미를 갖는 저장소
  • 개인정보와 민감정보를 필요 이상으로 담은 분석 사본

마트는 크기가 작다는 이유만으로 성립하지 않는다. 소유자, 목적, 스키마, 품질, 갱신, 보안이 관리되어야 한다.

3. 분석용 데이터 구성

3.1 분석 질문과 관측 단위

한 행이 뜻하는 대상을 관측 단위 또는 입도라고 한다. 같은 고객이 여러 주문을 할 수 있으므로 고객별 마트와 주문별 마트는 행 수와 키가 다르다.

3. 분석용 데이터 구성 · 학습 표 2
분석 질문권장 관측 단위후보 키주의점
주문 처리시간 비교주문 한 건order_id취소·재처리 상태
고객 월별 이용고객×기준월customer_id, month활동월 정의
상품 일별 판매상품×영업일product_id, date반품·휴일
캠페인 반응대상 고객×캠페인customerid, campaignid노출·반응 시점

입도가 흔들리면 수치가 중복된다. 고객 한 행을 기대한 표에 여러 주문 행을 결합하면 고객 속성이 주문 수만큼 반복되고, 단순 합계에서 과대 계산될 수 있다. 설계 문서 첫 줄에 한 행의 의미와 유일키를 적고 실제 중복을 검사해야 한다.

3.2 사실, 차원, 식별키

분석용 데이터는 측정값과 설명 속성을 구분해 생각하면 편리하다.

  • 사실은 매출액, 수량, 처리시간처럼 사건에서 측정되는 값이다.
  • 차원은 고객 등급, 상품 분류, 지역, 시간처럼 사실을 설명하거나 나누는 기준이다.
  • 식별키는 관측 단위를 유일하게 구분하고 원천과 연결하는 값이다.

이 구분은 절대적이지 않다. 나이는 어떤 분석에서는 설명 변수이고 다른 분석에서는 범주로 구간화될 수 있다. 중요한 것은 열 이름, 단위, 값의 정의, 유효 시점이다. 주민등록번호처럼 민감한 원식별자를 분석 편의를 위해 그대로 포함해서는 안 되며, 목적에 맞는 비식별 키와 최소 권한을 사용한다.

3.3 기준 시점과 이력

분석 결과는 언제 알 수 있었던 정보인지가 중요하다. 3월 말 고객 이탈을 예측하는 마트에 4월에 확정된 상담 결과가 들어가면 미래 정보 누출이 발생한다. 기준 시점 이후 정보를 특징에 넣지 않도록 각 열의 발생 시각, 수집 시각, 확정 시각을 구분한다.

스냅샷 마트는 특정 기준일의 상태를 저장한다. 거래 마트는 사건 단위 이력을 유지한다. 어느 방식이든 갱신 일시와 데이터 기준일을 별도 메타데이터로 기록한다. 파일 생성 시각만으로 업무 기준일을 대신하면 지연 수집 자료를 해석할 수 없다.

3.5 품질과 통제

마트 품질은 정확성만이 아니라 완전성, 유일성, 적시성, 일관성, 유효성을 함께 본다.

  1. 행 수와 금액 합계를 원천 통제 총계와 대사한다.
  2. 유일키 중복과 필수 열 결측을 검사한다.
  3. 허용 범위와 코드 집합을 검증한다.
  4. 기준일과 최신 갱신 성공 시각을 확인한다.
  5. 이전 배치 대비 급격한 행 수·분포 변화를 탐지한다.
  6. 오류 시 배포를 중단하고 이전 정상 버전을 식별할 수 있게 한다.

분석가에게 불필요한 민감정보를 제거하고 역할별 권한을 적용한다. 개발·검증 환경에는 최소화·가명화한 자료를 사용한다. 추출 파일의 무제한 보관은 마트 통제가 아니라 새로운 위험이다.

3.6 작은 재현 예시

다음은 고객×기준월 한 행이라는 계약을 표현한 고정 예제다.

customermonth <- data.frame( customerid = c(101L, 102L, 103L), snapshotmonth = as.Date(c('2026-01-01', '2026-01-01', '2026-01-01')), ordercount = c(3L, 1L, 0L), sales_amount = c(87000, 25000, 0), segment = factor(c('일반', '우수', '일반')), stringsAsFactors = FALSE )

key <- paste(customermonth$customerid, customermonth$snapshotmonth) anyDuplicated(key) # 0

이 예제는 외부 파일이나 난수를 사용하지 않는다. ordercount와 salesamount의 구체 계산은 이미 검증된 이전 단계에서 왔다고 가정한다. 여기서는 키 유일성, 기준월, 자료형, 범주, 0의 의미를 확인한다. 주문이 없음을 0으로 표현할지 미수집을 NA로 표현할지는 반드시 정의서에 적는다.

4. 데이터 웨어하우스와 데이터 마트

4.1 역할 비교

데이터 웨어하우스는 기업 전반의 여러 원천을 통합해 장기간 일관된 이력을 제공하는 중심 저장소다. 데이터 마트는 특정 주제나 사용자 집단의 분석 요구에 맞춰 범위를 좁히고 접근성을 높인다.

4. 데이터 웨어하우스와 데이터 마트 · 학습 표 4

둘은 경쟁 관계가 아니다. 웨어하우스의 표준 데이터를 기반으로 마트를 만들면 공통 정의와 계보를 재사용하면서 사용자 친화적인 구조를 제공할 수 있다.

4.2 종속형과 독립형 마트

종속형 데이터 마트는 통합 데이터 웨어하우스를 주요 출처로 삼는다. 정의 일관성과 계보 관리에 유리하지만 웨어하우스 반영 일정과 표준 변경에 영향을 받는다.

독립형 데이터 마트는 특정 부서가 운영 원천 등에서 직접 만든다. 초기 요구에 빠르게 대응할 수 있지만 부서마다 고객, 매출, 기간 정의가 달라지고 중복 추출이 늘어날 수 있다. 독립형 자체가 항상 틀린 것은 아니지만 공통 키·지표·보안·품질 규칙을 중앙 기준과 연결해야 한다.

4.3 계보와 변경 관리

마트 열 하나가 어느 원천 열에서 어떤 규칙으로 왔는지 추적 가능한 데이터 계보가 필요하다. 원천 코드가 바뀌거나 지표 정의가 개정되면 영향받는 마트와 보고서를 찾아야 한다. 스키마 버전, 변경 사유, 적용 일자, 호환성, 재처리 범위를 기록한다.

사용자 요구가 바뀔 때 기존 열의 의미를 몰래 바꾸지 않는다. 새 버전 또는 새 열로 제공하고 전환 기간을 둔다. 동일 열 이름이 과거와 다른 정의를 가지면 시계열 비교가 깨진다.

05

5. 업무 시나리오와 설계 산출물

마케팅팀이 월초에 전월 고객 활동을 분석하려 한다. 원천은 주문, 고객, 캠페인 시스템이다.

  1. 질문을 고객별 전월 구매와 캠페인 노출의 관계로 한정한다.
  2. 한 행을 고객×기준월로 정의한다.
  3. 고객 키와 기준월의 복합 유일성을 선언한다.
  4. 월말까지 발생하고 마감 시점까지 확정된 정보만 포함한다.
  5. 취소 주문, 테스트 고객, 미수집 반응의 처리 규칙을 정한다.
  6. 원천·변환·품질·권한·갱신 책임자를 문서화한다.

필수 산출물은 마트 목적서, 사용자와 이용 사례, 입도·키 명세, 열 정의서, 원천-대상 매핑, 갱신 주기, 품질 규칙, 권한 표, 계보와 변경 이력이다. 테이블을 먼저 만든 뒤 정의를 역으로 적는 방식은 중복과 누출을 놓치기 쉽다.

06

6. 시험 함정과 자주 틀리는 포인트

  1. 마트를 작은 데이터베이스라고만 정의한다. 분석 목적과 관리된 정의가 핵심이다.
  2. 운영 데이터를 모두 복사하면 분석용이라고 본다. 목적·입도·기준 시점에 맞게 구성해야 한다.
  3. 한 행의 의미를 생략한다. 결합과 집계에서 중복 계산이 생긴다.
  4. 0과 결측을 같은 값으로 본다. 업무 의미가 다르다.
  5. 파일 생성 시각을 데이터 기준일로 본다. 기준일과 적재 시각은 구분한다.
  6. 예측 시점 이후 정보를 포함한다. 미래 정보 누출로 평가가 왜곡된다.
  7. 웨어하우스와 마트를 경쟁 대안으로만 본다. 통합 저장소와 목적별 제공 구조로 연계할 수 있다.
  8. 독립형 마트는 언제나 빠르고 좋은 해법이라고 본다. 지표 불일치와 사일로 위험이 있다.
  9. 품질을 정확성 하나로 판단한다. 완전성·유일성·적시성·일관성도 본다.
  10. 분석 편의를 위해 민감정보를 모두 포함한다. 목적 최소화와 권한 통제가 필요하다.

9. 정답과 해설

  1. 정답 2. 데이터 마트는 특정 주제·사용자·분석 목적에 맞춘 관리된 데이터 집합이다.
  2. 정답 3. 같은 고객이 여러 기준월에 나타나므로 두 값을 함께 써야 행을 유일하게 식별할 수 있다.
  3. 정답 2. 관측 단위가 섞이면 같은 사실이 반복되어 합계와 건수가 과대 계산될 수 있다.
  4. 정답 1. 예측 당시 알 수 없던 정보를 포함하면 미래 정보 누출로 모델 평가가 왜곡된다.
  5. 정답 2. 웨어하우스는 전사 여러 원천의 통합 정의와 장기 이력을 제공하는 중심 구조다.
  6. 정답 1. 통합 웨어하우스의 키·코드·지표와 계보를 이용해 일관성을 높일 수 있다.
  7. 정답 1. 부서가 제각각 정의하면 같은 이름의 지표가 달라지고 중복 추출이 늘어난다.
  8. 정답 2. 품질은 값의 정확성뿐 아니라 빠짐, 중복, 시점, 규칙 일치와 허용 범위를 함께 본다.
  9. 정답 3. 0은 관측된 실제 값일 수 있고 결측은 알 수 없음을 뜻하므로 정의가 필요하다.
  10. 정답 2. 분석 질문과 한 행의 의미를 먼저 정해야 필요한 원천·열·검증 규칙을 선택할 수 있다.
10

10. 핵심 요약

  • 데이터 마트는 특정 주제와 분석 목적에 맞춘 관리된 분석용 데이터 집합이다.
  • 한 행의 의미, 유일키, 기준 시점, 포함·제외 규칙이 설계의 중심이다.
  • 열마다 업무 정의, 자료형, 단위, 허용값, 결측 의미와 계보를 기록한다.
  • 품질은 원천 대사, 유일성, 완전성, 적시성, 일관성, 유효성으로 검증한다.
  • 예측 기준 시점 이후의 정보를 넣지 않아 미래 정보 누출을 막는다.
  • 데이터 웨어하우스는 전사 통합과 이력, 데이터 마트는 특정 목적의 접근성에 초점이 있다.
  • 종속형은 표준 일관성, 독립형은 초기 민첩성이 장점이지만 각각 의존성과 사일로 위험이 있다.
  • 최소 권한, 민감정보 최소화, 버전·변경 이력 관리가 마트 운영에 포함되어야 한다.
