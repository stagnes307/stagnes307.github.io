🔄 1. 데이터 변환 — 내용보다 먼저 형태를 맞춘다

사람이 보면 이해되는 데이터도 컴퓨터가 분석하기에는 불편할 수 있어. 날짜 형식이 다르거나, 금액에 쉼표와 통화 단위가 섞이거나, 숫자가 문자열로 저장되는 식이지. 데이터 변환은 이런 원시 데이터를 분석이나 저장에 적합한 일관된 구조와 형식으로 바꾸는 과정이야.

원본
고객A, 2026/08/01, 15,000원
고객B, 2026-08-02, 23000
고객C, 08.03.2026, "17,500"
변환 후
날짜 → YYYY-MM-DD
금액 → 숫자형
문자열 → 분석 가능한 타입

파싱 Parsing

한 덩어리의 원시 데이터를 의미 있는 요소로 분리하고 해석하는 과정이야.

2026-08-26 14:35:20 → 연 / 월 / 일 / 시간

필터링 Filtering

분석 목적에 필요한 데이터만 선택하거나 불필요한 데이터를 제외해.

데이터 유형 변환

"15000" → 15000
"2026-08-26" → 날짜형
"TRUE" → 논리형

표준화된 형식으로의 변환

남 / Male / M → M

같은 의미를 같은 방식으로 표현하게 만드는 것.

🔐 2. 데이터 비식별화 — 데이터는 남기고 개인 식별 가능성은 낮춘다

비식별화의 핵심은 단순히 이름을 지우는 게 아니야. 직접식별자는 물론이고, 다른 정보와 결합했을 때 특정 개인을 알아볼 수 있는 간접 식별 가능성도 함께 봐야 해.

직접식별자

이름, 주민등록번호처럼 그 정보 자체가 개인을 직접 가리킬 수 있는 값.

간접 식별 가능성

나이·지역·직업처럼 여러 정보가 결합될 때 특정 대상이 좁혀질 수 있는 경우.

기법 변화 방식 예시
가명처리 실제 식별값을 다른 값으로 대체 김민수 → 고객 A102
총계처리 개별값 대신 통계량 제공 20·30·40만원 → 평균 30만원
데이터 삭제 식별 위험 정보 자체를 제거 이름 열 삭제
범주화 정확한 값을 더 넓은 범위로 변경 27세 → 20대
마스킹 값 일부를 가림 010-1234-5678 → 010-****-5678

비식별화의 핵심 교환관계

🔍 3. 데이터 품질 검증 — 형식도 맞고 안전한데, 믿을 수 있는가?

표의 모양이 정상이라고 해서 데이터 품질까지 좋은 건 아니야. 값이 틀렸거나, 빠졌거나, 다른 시스템과 충돌하거나, 허용 규칙을 벗어날 수 있어. 데이터 품질 검증은 데이터를 실제 분석이나 업무에 믿고 사용할 수 있는지 확인하는 과정이야.

정확성

실제 사실을 올바르게 반영하는가?

실제 35세 / DB 53세 → 정확성 문제

완전성

필요한 데이터가 빠짐없이 존재하는가?

나이 = NULL → 완전성 문제

일관성

같은 대상의 값이 서로 모순되지 않는가?

DB A: 1995-01-03 / DB B: 1996-01-03

유효성

정의된 범위·형식·규칙을 만족하는가?

나이 허용범위 0~120 / 나이 = -5

정확성 ≠ 유효성

나이 35는 허용 범위 안이므로 유효할 수 있어. 하지만 실제 나이가 42세라면 정확하지는 않아.

유효성: 규칙상 가능한 값인가?
정확성: 현실에서 맞는 값인가?

변환

문자열을 구조화하고 숫자 데이터의 형식을 맞춘다.

목적: 분석 가능한 형태
2

비식별화

이름을 가명으로 바꾸고 전화번호를 마스킹하고 나이를 범주화한다.

목적: 식별 위험 감소
3

품질 검증

범위, 누락, 중복, 시스템 간 값 일치 여부를 확인한다.

목적: 데이터 신뢰성 확보
변환은 형태를 다듬고,
비식별화는 식별 위험을 낮추고,
품질 검증은 데이터의 신뢰성을 확인한다.
