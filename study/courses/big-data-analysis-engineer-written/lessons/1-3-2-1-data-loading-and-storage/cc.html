🚚 데이터 적재 — 저장소 안으로 어떻게 넣을까?

핵심 질문: 언제 · 얼마나 · 어떤 순서로?

데이터를 수집했다고 바로 분석할 수 있는 건 아니야. 주문 DB, 웹 로그, 모바일 앱 이벤트처럼 서로 다른 곳에서 생긴 데이터를 데이터 웨어하우스나 데이터 레이크 같은 분석 저장소로 옮겨 넣는 과정이 필요하고, 이게 데이터 적재야.

배치 적재와 실시간 적재

구분 기준은 “언제 데이터를 넣느냐”야.

배치 적재

데이터를 일정량 모아 한꺼번에 처리해. 일별 매출 집계나 정기 통계처럼 즉시성이 덜 중요한 작업에 잘 맞아.

실시간·스트리밍 적재

데이터가 발생하는 흐름을 지속적으로 처리해. 이상 거래 탐지나 실시간 로그 분석처럼 지연 시간이 중요한 경우에 적합해.

배치는 “하루치 택배를 모아 한 번에”, 실시간은 “택배가 생기는 즉시”라고 생각하면 돼. 중요한 건 어느 방식이 무조건 우수한 게 아니라 업무가 요구하는 처리 속도와 데이터 양이야.

전체 적재와 증분 적재

이번 구분 기준은 “얼마만큼 다시 넣느냐”야.

ALL

전체 적재 Full Load

대상 데이터를 전부 다시 적재해. 구현은 단순하지만 데이터가 많아질수록 시간과 자원을 많이 사용해.

Δ

증분 적재 Incremental Load

이전 적재 이후 새로 추가되거나 변경된 데이터만 적재해. 효율적이지만 무엇이 바뀌었는지 식별할 방법이 필요해.

Order Matters

ETL과 ELT

시험에서는 Transform과 Load의 위치를 보면 돼.

ETL

Extract → Transform → Load

데이터를 추출하고 필요한 형태로 변환한 다음 저장소에 적재해. 전통적인 데이터 웨어하우스와 잘 연결돼.

ELT

Extract → Load → Transform

원본 데이터를 먼저 넣은 다음 저장소 안에서 변환해. 대규모 데이터 레이크나 클라우드 환경과 잘 맞아.

Loading Conditions

🏗️ 적재할 때 무엇을 함께 고려할까?

데이터 크기와 처리 성능

데이터가 TB, PB 규모라면 한 서버의 순차 처리만으로는 한계가 있어. 데이터를 나누거나 여러 노드에서 병렬·분산 처리하는 구조를 활용할 수 있어.

데이터 형식과 스키마

정형 데이터는 테이블처럼 구조가 명확하고, 반정형 데이터는 JSON·XML처럼 일정한 구조를 가지며, 비정형 데이터에는 이미지·영상·자연어 문서 등이 있어.

Schema-on-Write · 저장할 때 구조 정의

Schema-on-Read · 읽을 때 구조 적용

데이터 품질

누락, 중복, 형식 오류를 그대로 두면 분석 과정에서 문제가 돼. 그래서 유효성 검사, 중복 확인, 오류 처리, 적재 결과 검증도 중요해.

Storage

💾 데이터 저장 — 들어온 데이터를 어디에 둘까?

적재가 데이터를 넣는 행위라면, 저장은 데이터를 어떤 시스템과 구조에서 유지할 것인지의 문제야. 데이터의 구조, 규모, 조회 방식, 처리 속도, 확장성에 따라 저장 방식이 달라져.

🗃️ 관계형 데이터베이스 RDBMS

데이터를 행과 열로 이루어진 테이블에 저장하고 테이블 사이의 관계를 이용해 관리해.

정형 데이터 → 테이블 → SQL → 관계

고객, 상품, 주문처럼 구조가 명확하고 데이터 간 관계와 정확성이 중요한 업무에 적합해. 다만 데이터 규모와 형태가 매우 다양해지면 단일 관계형 구조만으로 처리하기 어려울 수 있어.

🧩 NoSQL

고정된 테이블 구조보다 유연하게 데이터를 저장할 수 있도록 설계된 데이터베이스 계열이야.

Key-Value
캐시, 세션
Document
JSON, 상품 정보
Column Family
대규모 분산 데이터
Graph
SNS 관계, 추천

시험에서는 제품 이름보다 대규모 데이터 · 유연한 구조 · 수평적 확장이라는 이유를 먼저 잡아.

Distributed Storage

🌐 분산 파일 시스템과 HDFS

빅데이터에서는 한 서버의 디스크만으로 저장 용량이나 처리 성능을 감당하기 어려워. 그래서 큰 파일을 여러 블록으로 나누고 여러 노드에 분산 저장해.

분할 → 분산 → 복제 → 장애 대응

Analytical Stores

🏞️ 데이터 웨어하우스와 데이터 레이크

데이터 웨어하우스

분석과 의사결정을 위해 데이터를 통합·정제하여 저장하는 시스템이야. 분석하기 좋은 구조로 데이터를 정리해 두기 때문에 보고서, BI, 정형 분석에 강해.

원천 데이터 → 정제·통합 → DW → 분석

데이터 레이크

정형·반정형·비정형 데이터를 포함해 대량의 원본 데이터를 비교적 그대로 저장할 수 있는 구조야. 지금 당장 분석 방법이 정해지지 않은 데이터도 먼저 저장해 둘 수 있어.

정형 반정형 비정형 원본 중심
구분 데이터 웨어하우스 데이터 레이크
데이터 성격 정제·구조화된 데이터 중심 원본·다양한 형태 저장 가능
분석 목적 비교적 명확 다양한 미래 활용 가능
스키마 관점 Schema-on-Write와 연결 Schema-on-Read와 연결
대표 활용 BI·정형 분석 빅데이터·AI 분석

현실에서는 두 구조가 완전히 배타적인 것은 아니고 시스템 설계에 따라 함께 사용되기도 해.

Storage Design

🔧 저장 시스템을 설계할 때 무엇을 따질까?

용량과 확장성

데이터는 계속 증가할 수 있으므로 저장 공간을 늘릴 수 있어야 해.

Scale-up · 한 장비의 성능을 높임
Scale-out · 여러 장비로 수평 확장

가용성과 장애 대응

복제, 백업, 분산 저장 등을 통해 장애에 대비해.

복제 · 서비스 지속성과 가용성
백업 · 손실 발생 시 과거 상태 복구

조회 성능

필요한 데이터를 얼마나 효율적으로 읽는지도 중요해. 인덱스, 파티셔닝, 압축 등을 사용할 수 있어.

예: 10년치 주문을 연도별 파티션으로 나누면 특정 연도의 데이터만 읽을 수 있어.

End-to-End

🔗 적재와 저장을 하나의 흐름으로 연결해 보자

쇼핑몰 클릭 로그를 예로 들어볼게. 사용자가 상품을 클릭하면 로그 데이터가 계속 발생해. 그 데이터가 수집되고, 적재되고, 저장된 뒤 분석에 쓰이는 흐름을 보면 적재와 저장의 위치가 선명해져.

  1. 01

    데이터 발생

    웹·앱에서 클릭 로그 생성

  2. 02

    데이터 수집

    수집 시스템이 로그를 받음

  3. 03

    데이터 적재

    배치 또는 스트리밍으로 저장소에 넣음

  4. 04

    데이터 저장

    분산 파일 시스템·데이터 레이크 등에 보관

  5. 05

    처리·분석

    고객 행동 분석·추천 모델 등에 활용

적재는 ③의 이동·투입 과정, 저장은 ④의 보관·관리 구조라고 위치를 잡으면 돼.

Compression

🧠 마지막으로 한 문장씩 압축

데이터 적재는 수집된 데이터를 목적 저장소에 효율적이고 안정적으로 넣는 과정이야.

배치 적재는 일정량을 모아 처리하고, 실시간 적재는 발생 데이터를 지속적으로 처리해.

전체 적재는 모든 데이터를 다시 넣고, 증분 적재는 새로 추가되거나 변경된 데이터만 넣어.

ETL은 변환 후 적재, ELT는 적재 후 변환이야.

데이터 저장은 데이터를 활용 목적에 맞는 저장 시스템에 보관하고 관리하는 것이야.

RDBMS는 정형·관계 데이터에 강하고, NoSQL은 대규모·유연한 데이터 처리에 유리해.

HDFS 같은 분산 저장 시스템은 데이터를 여러 노드에 분산·복제해 대규모 저장과 장애 대응을 지원해.

데이터 웨어하우스는 정제·통합 분석 데이터, 데이터 레이크는 다양한 원본 데이터의 대규모 저장이라는 방향으로 구별하면 돼.
