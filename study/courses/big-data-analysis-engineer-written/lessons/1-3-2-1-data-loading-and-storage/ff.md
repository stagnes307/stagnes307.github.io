## 🎯 먼저 한 줄로 잡자

이 단원의 핵심은 아주 단순해.

> **데이터 적재**는 데이터를 **목표 시스템으로 옮겨 넣는 과정**이고,
> **데이터 저장**은 들어온 데이터를 **어떤 구조와 저장소에 보관·관리할지 결정하는 것**이야.

시험에서는 둘을 따로 외우기보다 **“어떻게 넣을까?” → 적재 / “어디에 어떻게 둘까?” → 저장**으로 구별하면 돼.

| 구분      | 데이터 적재                   | 데이터 저장                                      |
| ------- | ------------------------ | ------------------------------------------- |
| 핵심 질문   | 데이터를 **어떻게 넣는가?**        | 데이터를 **어디에 보관하는가?**                         |
| 중심      | 이동·입력 과정                 | 저장 구조·저장 기술                                 |
| 주요 고려사항 | 주기, 속도, 전체/증분, 변환        | 용량, 확장성, 가용성, 접근 방식                         |
| 대표 개념   | 일괄, 실시간, 전체, 증분, ETL/ELT | RDBMS, NoSQL, 분산 파일 시스템, 데이터 웨어하우스, 데이터 레이크 |

## 📥 데이터 적재 — 데이터를 목적지에 넣는다

### 적재란 무엇인가?

데이터를 수집했다고 바로 분석할 수 있는 건 아니야.

예를 들어 쇼핑몰에서

**회원 DB → 주문 데이터 수집 → 분석용 데이터 웨어하우스**

라는 흐름이 있다고 해보자.

회원 DB에서 데이터를 가져오는 것은 **수집·추출**에 가깝고, 그 데이터를 데이터 웨어하우스의 테이블에 실제로 넣는 과정이 **적재(Loading)**야.

그래서 보통 큰 흐름은 이렇게 이해하면 좋아.

**원천 데이터 → 추출 → 필요하면 변환 → 적재 → 저장 및 활용**

---

### 적재 방식의 첫 번째 구분: 일괄 vs 실시간

#### 일괄 적재 Batch Loading

일정 기간 동안 데이터를 모아 두었다가 **한꺼번에 적재**하는 방식이야.

예를 들면 매일 새벽 2시에 전날 주문 데이터를 모아서 데이터 웨어하우스에 넣는 거지.

**적합한 경우**

* 즉시 반영할 필요가 없을 때
* 대량의 데이터를 주기적으로 처리할 때
* 처리 효율이 실시간성보다 중요할 때

핵심어는 **“모아서 한 번에”**야.

#### 실시간 적재 Real-time / Streaming Loading

데이터가 발생하면 **즉시 또는 매우 짧은 시간 내에 지속적으로 적재**하는 방식이야.

예를 들어 실시간 금융 거래, IoT 센서, 클릭 로그 같은 경우지.

**적합한 경우**

* 데이터 발생 즉시 분석해야 할 때
* 이상 탐지나 실시간 추천처럼 지연이 중요한 경우
* 데이터가 계속 들어오는 스트림 형태일 때

핵심어는 **“발생하면서 계속”**이야.

### 시험에서는 이렇게 구분

**매일 자정 한 번 처리 → 일괄**

**센서 데이터가 발생할 때마다 처리 → 실시간**

여기서는 데이터의 크기보다 **처리 시점**을 보는 게 중요해.

---

## 🔄 전체 적재와 증분 적재

이 구분도 시험에서 중요해.

### 전체 적재 Full Load

기존 데이터 여부와 관계없이 **전체 데이터를 다시 적재**하는 방식이야.

예를 들어 고객 100만 명의 정보를 매번 처음부터 다시 저장한다고 생각하면 돼.

장점은 구조가 단순하다는 것.

하지만 데이터가 많아질수록

* 처리 시간 증가
* 네트워크 사용량 증가
* 저장·처리 비용 증가

문제가 생길 수 있어.

---

### 증분 적재 Incremental Load

전체를 다시 넣는 게 아니라 **새로 생성되거나 변경된 데이터만 적재**해.

어제까지 데이터가 저장되어 있다면 오늘 새로 발생한 주문이나 수정된 주문만 반영하는 식이지.

그래서 대규모 시스템에서는 효율적이야.

**전체 적재**

`기존 1~100 + 신규 101 → 1~101 전체 재적재`

**증분 적재**

`기존 1~100 + 신규 101 → 101만 추가`

여기서 시험용 핵심 관계가 하나 나와.

> **데이터 규모가 커지고 변경분이 상대적으로 작을수록 증분 적재의 효율성이 커진다.**

---

## 🔍 CDC — 변경된 데이터만 찾아낸다

증분 적재를 하려면 문제가 하나 생겨.

**“그래서 어떤 데이터가 바뀌었는데?”**

이걸 찾아내는 대표적인 방식이 **CDC(Change Data Capture)**야.

CDC는 원천 시스템에서 발생한

* INSERT
* UPDATE
* DELETE

같은 **데이터 변경 사항을 식별해 대상 시스템에 반영**하는 개념이야.

따라서 관계를 이렇게 묶어두면 좋아.

**CDC → 변경 데이터 탐지 → 증분 적재에 활용**

CDC 자체를 그냥 “데이터 저장 기술”이라고 보면 안 돼. 핵심은 **변경 사항 포착**이야.

---

## 🔧 ETL과 ELT는 적재 위치가 다르다

데이터 적재를 공부하면 같이 따라오는 게 **ETL / ELT**야.

### ETL

**Extract → Transform → Load**

즉,

**추출 → 변환 → 적재**

데이터를 목적지에 넣기 **전에 변환**해.

예를 들어 여러 시스템의 날짜 형식을 통일하고 오류 데이터를 정리한 다음 데이터 웨어하우스에 넣는 방식이야.

### ELT

**Extract → Load → Transform**

즉,

**추출 → 적재 → 변환**

먼저 데이터를 저장소에 넣고, **저장된 곳에서 나중에 변환**하는 접근이야.

차이는 딱 하나만 먼저 잡아.

| ETL              | ELT              |
| ---------------- | ---------------- |
| 추출 → **변환** → 적재 | 추출 → **적재** → 변환 |
| 넣기 전에 가공         | 먼저 넣고 나중에 가공     |

시험에서 영어 순서를 그대로 바꿔서 내기 쉬워.

**T가 L보다 앞 → ETL**

**L이 T보다 앞 → ELT**

# 🗄️ 데이터 저장 — 어디에 어떤 구조로 둘 것인가

## 💾 저장은 단순히 디스크에 넣는 게 아니다

빅데이터에서 저장 계획을 세운다는 건 단순히

> “하드디스크 하나 사자.”

가 아니야.

데이터의 특성을 보고 **어떤 저장 기술과 구조를 사용할지 설계하는 것**이 핵심이야.

예를 들어 생각해야 할 게 있어.

### 데이터 규모

데이터가 계속 증가한다면 저장 공간 역시 쉽게 확장되어야 해.

그래서 빅데이터 환경에서는 한 대의 고성능 서버를 계속 키우는 방식뿐 아니라 여러 서버를 추가하는 **수평 확장(Scale-out)**이 중요해져.

### 데이터 형태

데이터가 모두 같은 표 형태인지도 봐야 해.

* 정형 데이터
* 반정형 데이터
* 비정형 데이터

형태에 따라 적절한 저장 기술이 달라질 수 있어.

### 접근 방식

데이터를 어떤 식으로 읽을지도 중요해.

* 잦은 조회와 수정이 필요한가?
* 대규모 분석을 주로 하는가?
* 실시간 응답이 필요한가?
* 큰 파일을 순차적으로 처리하는가?

저장 기술에는 각각 잘하는 일이 달라.

---

## 🧱 RDBMS — 구조와 관계가 중요하다

관계형 데이터베이스는 데이터를 **테이블** 형태로 관리하고, 테이블 사이의 관계를 설정해 사용하는 방식이야.

대표적으로 생각하면 돼.

**행 + 열 + 관계 + SQL**

장점은 데이터 구조와 관계를 명확하게 관리할 수 있고 트랜잭션 처리가 강하다는 점이야.

그래서

* 고객 정보
* 주문 정보
* 결제 정보

처럼 구조가 비교적 명확한 데이터에 잘 맞아.

다만 초대규모·다양한 형태의 데이터를 여러 서버에 분산 처리해야 하는 환경에서는 다른 저장 방식이 함께 사용될 수 있어.

---

## 🧩 NoSQL — 유연성과 분산 확장

NoSQL은 관계형 데이터베이스와 다른 데이터 모델을 사용하며, 빅데이터 환경에서 **유연한 데이터 구조와 분산 확장**을 위해 많이 사용돼.

대표적인 유형은 이렇게 구분해.

| 유형            | 핵심 구조  |
| ------------- | ------ |
| Key-Value     | 키와 값   |
| Document      | 문서 형태  |
| Column Family | 컬럼 계열  |
| Graph         | 노드와 관계 |

시험에서는 유형과 특징을 연결하는 문제가 나올 수 있어.

특히 **Graph Database**는 이름 그대로 사람 관계, 추천 관계, 네트워크처럼 **개체 간 관계 자체가 중요한 데이터**에 적합해.

그리고 한 가지 함정.

> **NoSQL = 무조건 비정형 데이터 전용**은 아니야.

NoSQL의 본질은 “비정형 데이터 저장소” 하나로 끝나는 게 아니라 **관계형 모델과 다른 데이터 모델과 분산·확장 특성을 활용한다**는 쪽으로 이해해야 해.

---

## 🌐 분산 파일 시스템 — 큰 데이터를 여러 장비에 나눈다

빅데이터에서는 데이터 규모가 너무 커서 한 서버에 모두 저장하기 어려울 수 있어.

이때 여러 서버의 저장 공간을 하나의 거대한 시스템처럼 활용하는 **분산 파일 시스템**을 사용할 수 있어.

대표적으로 자주 접하는 개념이 **HDFS(Hadoop Distributed File System)**야.

핵심 관계는 이거야.

**큰 데이터 → 여러 노드에 분산 저장 → 장애에 대비한 복제 → 병렬 처리 기반**

한 서버가 고장 나도 데이터가 다른 노드에 복제되어 있으면 계속 활용할 수 있지.

그래서 분산 저장에서는

* 확장성
* 장애 대응
* 가용성

이 중요한 특성이 돼.

# 🏢 데이터 웨어하우스와 데이터 레이크

둘은 이름이 비슷해서 잘 섞여.

## 데이터 웨어하우스 Data Warehouse

분석을 위해 여러 시스템의 데이터를 **정제·통합하여 구조적으로 저장**하는 저장 환경이야.

보통 정형화된 분석 데이터를 다루기 좋고,

**“분석하기 편하도록 잘 정리해서 저장”**

이라고 이해하면 돼.

대표적인 사고방식은 **Schema-on-Write**야.

즉 데이터를 저장할 때부터 **어떤 구조로 넣을지 미리 정한다**는 뜻이지.

---

## 데이터 레이크 Data Lake

다양한 원천 데이터를 **원본에 가까운 형태로 대규모 저장**하는 접근이야.

정형뿐만 아니라 반정형·비정형 데이터까지 폭넓게 담을 수 있어.

핵심 이미지는

**“일단 넓은 호수에 모아 두고, 사용할 때 필요한 구조를 적용한다.”**

그래서 일반적으로 **Schema-on-Read**와 연결해서 기억해.

| 데이터 웨어하우스       | 데이터 레이크        |
| --------------- | -------------- |
| 정제·구조화된 데이터 중심  | 다양한 원본 데이터 저장  |
| Schema-on-Write | Schema-on-Read |
| 구조를 정하고 저장      | 필요할 때 구조를 해석   |
| 정형 분석에 강함       | 다양한 데이터 활용에 유연 |

### 기억법

**Warehouse = 창고**

물건을 분류해서 선반에 정리해 놓는 느낌.

**Lake = 호수**

여러 곳에서 흘러온 데이터가 일단 모여 있는 느낌.

# ⚙️ 적재부터 저장까지 한 흐름으로 연결하기

이제 각각 따로 외우지 말고 하나의 시스템으로 보자.

온라인 쇼핑몰에서 주문이 발생한다고 해보자.

### ① 데이터 발생

고객이 주문한다.

### ② 데이터 수집

운영 DB, 로그 등에서 주문 관련 데이터를 가져온다.

### ③ 적재 방식 결정

하루 한 번 분석하면 **일괄 적재**를 사용할 수 있어.

실시간 매출 현황이 필요하다면 **실시간 적재**가 필요할 수 있어.

### ④ 적재 범위 결정

매번 모든 주문을 가져오면 **전체 적재**.

새 주문이나 변경 주문만 가져오면 **증분 적재**.

변경 사항을 찾아야 한다면 **CDC**를 활용할 수 있어.

### ⑤ 필요하면 변환

**ETL:** 변환하고 넣는다.

**ELT:** 넣고 변환한다.

### ⑥ 저장소 결정

구조화된 분석 데이터 중심이라면 데이터 웨어하우스가 적합할 수 있고, 원본 로그·이미지·다양한 형식까지 대량 보관한다면 데이터 레이크나 분산 저장 기술을 활용할 수 있어.

이 흐름 하나를 기억하면 용어들이 서로 연결돼.

# 🧠 필기시험에서 자주 헷갈리는 경계

## 🚨 1. 적재와 저장

**적재 = 동작**

데이터를 목적지에 **넣는다.**

**저장 = 상태와 구조**

데이터를 목적지에 **보관·관리한다.**

---

## 🚨 2. 일괄과 전체는 같은 말이 아니다

이거 꽤 중요해.

**일괄/실시간**은 **언제 처리하는지**의 문제야.

**전체/증분**은 **얼마만큼 처리하는지**의 문제고.

따라서 이런 조합도 가능해.

> 매일 새벽 2시에 그날 변경된 데이터만 넣는다.

이건

**일괄 적재 + 증분 적재**

야.

“일괄이니까 전체 적재”라고 연결하면 틀려.

---

## 🚨 3. CDC와 증분 적재

둘도 완전히 같은 용어는 아니야.

**증분 적재**는 변경분만 적재하는 **전략**이고,

**CDC**는 변경된 데이터를 찾아내는 **기술·방식**에 가까워.

즉,

**CDC → 변경분 파악 → 증분 적재**

관계야.

---

## 🚨 4. ETL과 ELT

두 방식 모두 E, T, L이 등장해.

차이는 **변환 시점**.

**ETL:** 변환하고 저장.

**ELT:** 저장하고 변환.

---

## 🚨 5. DW와 Data Lake

**DW = 구조를 먼저**

**Lake = 데이터를 먼저**

그래서

**DW → Schema-on-Write**

**Lake → Schema-on-Read**

연결이 핵심이야.
