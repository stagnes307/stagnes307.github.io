1. 분석 시나리오와 산출물

이 레슨에서는 다음 가상 사례를 사용한다.

A사는 10년간 운영한 주문 시스템을 현대화하려 한다. 웹 화면, 야간 정산 배치, 재고·결제 연계, 관계형 데이터베이스가 있고 월말에 응답 지연이 발생한다. 일부 인터페이스 문서는 실제 운영과 다르며, 운영체제와 DBMS의 지원 종료도 검토해야 한다.

현행 분석이 끝나면 최소한 다음 산출물이 서로 연결되어야 한다.

2. 현행 적용현황 조사

2.1 조사 경계부터 합의한다

“주문 시스템”이라는 이름만으로 범위를 정하면 결제, 재고, 고객, 회계, 인증과 운영 도구가 빠질 수 있다. 다음 경계를 명시한다.

  • 대상 업무 조직과 사용자 집단
  • 사용자 화면, API, 배치, 보고서와 관리 기능
  • 직접 소유한 시스템과 외부 조직·협력사 시스템
  • 운영·개발·시험·재해복구 환경
  • 데이터 생성·변경·조회·보관·폐기 구간
  • 조사 기준일과 분석에서 제외할 항목

범위는 고정 목록이 아니라 새로운 의존성을 발견하면 변경 통제로 갱신한다. 추가 범위가 일정·비용·위험에 미치는 영향을 기록하고 승인받는다.

2.4 인터페이스와 의존성

인터페이스별로 다음을 기록한다.

  • 송신·수신 시스템과 책임 조직
  • 동기/비동기, 실시간/배치, 내부/외부 구분
  • 프로토콜·데이터 형식·문자 인코딩·버전
  • 인증·암호화·접근 경로
  • 정상 처리량, 피크, 최대 메시지 크기
  • 시간 제한, 재시도, 중복 제거, 순서와 실패 보상
  • 변경 가능 시점과 상대 시스템의 호환 기간

“REST 연계”만으로는 부족하다. 요청 계약, 오류 의미, 보안, 처리량과 상대 시스템을 함께 알아야 이행 중 구버전·신버전 공존과 어댑터 필요 여부를 결정할 수 있다.

2.5 데이터와 운영 현황

데이터 조사에는 다음이 필요하다.

  • 데이터 소유자와 업무 정의
  • 테이블·파일·객체 등 저장 위치와 관계
  • 현재 용량, 행 수, 일·월 증가율, 피크 쓰기량
  • 키, 중복, 결측, 코드 불일치와 참조 무결성
  • 개인정보·민감정보 분류와 접근·암호화 요구
  • 보존·파기 기간, 백업과 복구 방식
  • 이력·감사 데이터와 법적 증빙 여부

운영 현황은 배포 빈도, 승인, 모니터링, 온콜, 장애 등급, 평균 탐지·복구 시간, 백업 복원 시험, 정기 작업과 수작업을 조사한다. 운영 자동화가 목표 범위에 포함되지 않으면 새 시스템도 같은 수동 위험을 물려받을 수 있다.

3. 개발범위 도출

3.1 업무 기능을 기준으로 분해한다

기술 모듈 이름만으로 범위를 나누지 않고 다음 계층으로 연결한다.

코드 예시 · text

업무 목표
  └─ 업무 능력: 주문 처리
       ├─ 기능: 주문 등록·가격 계산·승인·취소
       ├─ 응용 모듈: 화면·API·배치
       ├─ 데이터: 주문·품목·상태 이력
       └─ 연계: 재고·결제·회계

이 구조에서 각 기능을 유지·개선·교체·폐기 후보로 분류한다.

  • 유지: 요구를 충족하고 지원·보안·운영 위험이 허용됨
  • 개선: 기본 자산은 재사용하지만 성능·구조·사용성 등을 수정
  • 교체/재개발: 품질·지원·변경 비용 때문에 목표 기술로 전환
  • 폐기: 사용·법적 보존·연계 의존이 없고 승인된 기능
  • 신규: 현행에 없지만 목표 업무에 필요한 기능

폐기는 “최근 호출 0건” 하나로 결정하지 않는다. 월·분기·연말 주기, 비상 절차, 규정과 외부 계약을 확인한다.

4.2 판단 기준

  • 목표 업무 적합성과 필수 기능 차이
  • 변경 빈도, 결합도, 자동 테스트와 코드 품질
  • 데이터 규모·품질·허용 중단 시간
  • 성능·가용성·복구 목표
  • 보안·개인정보·감사·규제 요구
  • 제품 지원 수명, 인력 역량, 공급자 의존
  • 초기비용과 운영비용, 라이선스, 전환 기간
  • 외부 인터페이스의 변경 가능성
  • 되돌리기와 병행 운영 가능성

단순 점수표는 비교를 돕지만 치명적 제약을 평균점수로 가리면 안 된다. 예를 들어 규정상 데이터 위치를 만족하지 못하는 후보는 비용 점수가 높아도 제외 조건이 될 수 있다.

4.3 전환 방식

  • 일괄 전환(big bang): 한 시점에 전부 전환. 기간은 짧지만 실패 영향과 복구 부담이 큼.
  • 단계 전환: 기능·조직·지역·데이터 구간별로 순차 전환. 위험을 나누지만 공존과 연계가 복잡함.
  • 병행 운영: 일정 기간 현행과 목표를 함께 운용·비교. 대사 가능하지만 이중 비용과 데이터 동기화 필요.
  • 파일럿: 제한된 사용자·업무로 검증 후 확대. 대표성 있는 범위와 종료 기준 필요.

선택에는 허용 중단 시간, 거래 원자성, 역방향 데이터 동기화, 사용자 수, 외부 계약과 되돌리기 시간을 반영한다.

4.4 이행 의존성과 순서

코드 예시 · text

공통 인증·관찰 기반
  → 읽기 전용 조회 기능
  → 신규 주문 쓰기 경로
  → 외부 연계 전환
  → 과거 데이터 이관·대사
  → 현행 쓰기 중지
  → 안정화·현행 폐기

실제 순서는 데이터 소유권과 쓰기 원천을 중심으로 정한다. 두 시스템이 같은 레코드를 동시에 수정하면 충돌 규칙이 필요하다. 각 단계에 진입 조건, 성공 지표, 중단 조건, 롤백 절차와 책임자를 둔다.

05

5. 요구사항 작성 원칙

좋은 플랫폼 요구사항은 제품명이 아니라 필요한 결과와 검증 기준을 표현한다.

코드 예시 · text

[ID] INF-OS-001
[요구] 운영체제는 승인된 보안 업데이트를 서비스 중단 목표 안에서 적용할 수 있어야 한다.
[근거] 현행 OS 지원 종료와 분기 감사 지적
[검증] 시험 환경 패치 적용·롤백 결과와 운영 절차 검토
[우선순위] 필수
[추적] RISK-07, NFR-AVAIL-03

다음 품질을 확인한다.

  • 필요성: 업무·위험·규제 근거가 있는가?
  • 명확성: 한 가지 의미로 해석되는가?
  • 완전성: 조건·대상·예외·단위가 있는가?
  • 일관성: 다른 요구와 충돌하지 않는가?
  • 실현 가능성: 기술·기간·비용 안에서 가능한가?
  • 검증 가능성: 시험·검토·분석으로 합격을 판정할 수 있는가?
  • 추적 가능성: 출처와 설계·테스트로 연결되는가?

“빠른 DB”, “최신 OS”, “안정적인 미들웨어”는 측정·판정할 수 없어 요구사항으로 부족하다.

06

6. 운영체제 요구사항 식별

운영체제는 응용·DBMS·미들웨어가 실행되는 기반이므로 호환성과 운영 품질을 함께 식별한다.

6.1 기능·호환성

  • 대상 CPU 아키텍처와 가상화·컨테이너 지원
  • 응용 런타임, DBMS, 미들웨어의 인증된 OS·버전 조합
  • 파일시스템, 문자 인코딩, 경로·권한·시간대 요구
  • 필요한 네트워크·저장장치 드라이버와 프로토콜
  • 기존 스크립트·서비스 관리·배치 도구 호환성

“64비트 OS”만으로 부족하다. 공급자 지원 행렬과 실제 라이브러리·드라이버·설치 자동화를 검증한다.

6.2 용량·성능

  • 예상 CPU 코어, 메모리, 파일·프로세스·소켓 한도
  • 피크 동시 사용자와 배치 병행 시 자원 여유
  • I/O 스케줄링·파일시스템 특성과 저장 요구
  • 시간 동기화와 로그 시각 정확도
  • 자원 격리와 우선순위 요구

평균 사용률만으로 산정하지 않고 피크, 성장률, 장애 시 축소 용량과 정비 작업을 포함한다.

6.3 가용성·운영성

  • 지원 종료일과 보안 업데이트 제공 정책
  • 패치 주기, 재부팅 필요성, 롤링 적용과 롤백
  • 부팅·서비스 자동 복구, 장애 감시, 로그 수집
  • 백업 대상 시스템 설정과 복구 시간
  • 고가용성 구성에서 노드 장애 탐지·전환 조건
  • 표준 이미지, 형상 기준, 관리자 접근과 감사

6.4 보안

  • 최소 설치와 불필요 서비스 비활성화
  • 계정·권한 분리, 관리자 다중 인증과 원격 접근 통제
  • 보안 기준선, 패치, 악성코드·무결성 감시 요구
  • 저장·전송 암호화 지원과 키 보호
  • 감사 로그 항목·보존·위변조 방지

예시 요구사항:

6. 운영체제 요구사항 식별 · 학습 표 6
ID요구검증 기준 예
OS-01승인된 응용 스택과 공급자 지원 조합일 것호환 목록과 설치·회귀시험 통과
OS-02계획 노드 한 대 장애 중 필수 서비스 용량 유지장애 주입 시 오류율·처리량 기준 충족

07

7. DBMS 요구사항 식별

7.1 데이터 모델과 기능

  • 관계형, 문서, 키–값 등 업무 데이터 구조와 질의 패턴
  • 트랜잭션 원자성·일관성, 격리 수준과 동시성 요구
  • 제약조건, 인덱스, 뷰, 프로시저 등 필요한 기능
  • 문자 집합, 정렬, 시간대, 숫자 정밀도
  • 분석·운영 질의 분리와 데이터 수명주기

유행하는 저장소 유형보다 주문·결제처럼 강한 무결성이 필요한지, 유연한 문서 구조와 수평 확장이 중요한지 업무 불변조건으로 판단한다.

7.2 용량·성능

  • 현재 데이터·인덱스·로그 크기와 연도별 증가
  • 초당 읽기·쓰기, 동시 연결, 피크 트랜잭션
  • 핵심 질의의 응답 시간 백분위와 배치 완료 시간
  • 백업·통계·인덱스 정비가 운영 부하에 미치는 영향
  • 복제·스냅샷·임시 공간과 장애 복구 여유

평균 응답 1초만 적으면 긴 꼬리 지연을 숨길 수 있다. 업무별 측정 구간, 데이터량, 동시성, 백분위와 허용 오류율을 함께 쓴다.

7.3 가용성·복구·일관성

  • 목표 복구 시간(RTO)과 허용 데이터 손실 범위(RPO)
  • 동기·비동기 복제와 장애 시 일관성 요구
  • 자동/수동 장애 전환, 오판 방지와 복귀 절차
  • 전체·증분·로그 백업, 보존 위치와 복원 시험
  • 재해복구 사이트 거리·용량·연결과 정기 훈련

복제가 백업을 대체하지 않는다. 실수 삭제나 논리 손상이 사본에 전파될 수 있으므로 시점 복구와 독립 보존이 필요하다.

7.4 보안·운영·호환성

  • 응용·운영·관리 계정 분리와 최소 권한
  • 전송·저장·백업 암호화와 키 관리
  • 접속·권한 변경·중요 데이터 접근 감사
  • 데이터 마스킹과 비운영 환경 반출 통제
  • 기존 SQL, 자료형, 프로시저, 드라이버와 도구 호환
  • 버전 업그레이드, 패치, 라이선스와 공급자 지원

예시 요구사항:

코드 예시 · text

DB-AVAIL-01: 단일 DB 노드 장애 시 주문 쓰기 서비스는 5분 안에 복구되고,
확정 거래의 허용 손실 기준을 충족해야 한다.
검증: 대표 피크 부하에서 장애 전환·정합성 대사·복귀 리허설

수치 자체는 이해관계자 승인과 위험 분석에서 정해야 한다. 근거 없이 짧은 RTO/RPO를 적으면 비용만 늘거나 달성 불가능한 계약이 된다.

08

8. 미들웨어 요구사항 식별

미들웨어는 운영체제와 응용 사이 또는 여러 응용 사이에서 공통 실행·연계 서비스를 제공한다. 웹서버, WAS/응용 서버, 메시지 브로커, API 중계, 트랜잭션·통합 도구 등이 문맥에 따라 포함될 수 있다.

8.1 실행·배포 요구

  • 지원 런타임과 응용 패키지 형식
  • 인스턴스 시작·중지·상태 확인과 무중단/순차 배포
  • 세션 관리, 연결 풀, 스레드·작업 큐와 자원 한도
  • 설정 외부화, 환경별 분리, 비밀 주입
  • 버전 호환과 롤백 가능한 배포물 관리

8.2 연계·메시징 요구

  • 동기 요청인지 비동기 메시지인지
  • 메시지 순서, 전달 보장, 중복 허용과 멱등성
  • 재시도, 지연, 만료, 실패 격리와 재처리
  • 스키마·버전 호환과 생산자·소비자 독립 배포
  • 피크 처리량, 메시지 크기, 보관량과 지연 목표

“exactly once”라는 제품 문구만 믿지 않고 업무 효과까지 한 번인지 확인한다. 브로커 재전달과 소비자 장애가 있어도 주문 반영이 중복되지 않도록 업무 키·트랜잭션 경계를 설계해야 한다.

8.3 품질·보안·운영 요구

  • 부하 분산, 상태 확인, 장애 노드 격리
  • 타임아웃, 회로 차단, 제한 재시도와 과부하 보호
  • 서비스 간 인증·인가와 전송 암호화
  • 관리 포트·콘솔 접근 통제와 감사
  • 요청 ID·추적 ID, 메트릭·로그·분산 추적
  • 구성 백업, 클러스터 복구와 버전 업그레이드
  • 라이선스·지원·운영 인력과 자동화 도구

예시 표:

8. 미들웨어 요구사항 식별 · 학습 표 7
ID요구근거검증
MW-01결제 연계 요청에 종단 추적 ID를 전달장애 원인 추적 지연로그 상관관계 시험
MW-02실패 메시지를 무한 재시도하지 않고 격리장애 시 큐 적체오류 주입과 재처리 시험
MW-03노드 순차 교체 중 읽기 서비스 기준 유지정기 패치 필요롤링 재시작 부하시험
MW-04관리 인터페이스는 승인망·개인 계정만 허용관리자 권한 위험접근·감사 로그 검사
09

9. 세 플랫폼 요구의 조합 검증

운영체제, DBMS, 미들웨어를 각각 좋은 제품으로 골라도 조합이 지원되지 않으면 실패한다.

9.1 호환성 행렬

9. 세 플랫폼 요구의 조합 검증 · 학습 표 8
후보 조합OS 지원DB 드라이버미들웨어 런타임모니터링·백업판정
조합 A공급자 인증지원지원표준 도구 연계후보
조합 B지원 종료 임박지원제한별도 개발제외/보완

문서상 지원뿐 아니라 대표 설치, 연결, 장애 전환, 패치, 백업·복구를 시험한다. 지원 버전의 종료 시점이 프로젝트 수명보다 짧으면 업그레이드 경로와 비용을 요구에 포함한다.

9.2 용량의 공동 검증

DB 연결 수를 2,000으로 잡고 미들웨어 인스턴스마다 풀 500개를 8개 두면 최대 4,000개 요청이 될 수 있다. 실제 동시 쿼리와 대기열, DB 한도, 장애 시 남은 인스턴스의 풀 폭증을 함께 계산한다. 개별 구성 최대값을 모두 크게 하면 전체 시스템이 안정적인 것이 아니다.

9.3 장애 도메인

응용과 DB 이중화 노드를 같은 물리 호스트·전원·스토리지에 두면 공통 장애에 함께 멈출 수 있다. 논리 노드 수뿐 아니라 서버, 랙, 전원, 네트워크, 저장장치, 지역과 관리 계정의 공통 실패 지점을 표시한다.

10. 단계별 수행 절차

  1. 목표·경계 정의: 조사 목적, 기준일, 조직·환경·데이터·연계 범위를 승인한다.
  2. 자료 수집 계획: 담당자, 문서, 로그, 저장소, 관찰과 데이터 접근 권한을 정한다.
  3. 인벤토리 작성: 응용–기능–데이터–인터페이스–인프라를 고유 ID로 연결한다.
  4. 현행 검증: 문서와 실측 차이, 누락 자산, 피크·장애·수작업을 확인한다.
  5. 문제·제약 도출: 지원 종료, 병목, 단일 장애점, 보안·규제, 기술 부채를 근거와 기록한다.
  6. 개발범위 분류: 유지·개선·교체·폐기·신규와 포함·제외 경계를 정한다.
  7. 이행대안 비교: 중단·데이터·호환·비용·복구 기준으로 전략과 단계를 평가한다.
  8. 플랫폼 요구 식별: OS·DBMS·미들웨어 기능과 품질·운영·보안·지원 요구를 쓴다.
  9. 조합 검증: 지원 행렬, 용량, 장애 도메인, 라이선스와 운영 역량을 교차 검토한다.
  10. 검토·승인·추적: 업무·개발·운영·보안·데이터 담당자가 충돌과 누락을 확인하고 기준선으로 관리한다.

10.1 완료 판단 기준

  • 모든 중요 업무 기능이 실행 자산과 연결되어 있는가?
  • 외부 인터페이스와 데이터 소유·보존 책임이 확인됐는가?
  • 현행 문제에 로그·측정·계약 같은 근거가 있는가?
  • 포함·제외와 경계 시스템 책임이 승인됐는가?
  • 이행 단계별 진입·성공·중단·롤백 조건이 있는가?
  • OS·DBMS·미들웨어 요구가 측정·검증 가능한가?
  • 제품 후보보다 요구가 먼저 정의됐는가?
  • 요구 출처에서 설계·시험까지 추적 ID가 연결되는가?

11. 자주 틀리는 포인트

  1. 현행 문서만 읽으면 분석이 끝난다? 운영 로그·설정·소스·관찰·인터뷰를 교차 확인해야 한다.
  2. 범위는 화면 목록과 같다? 배치·API·데이터·운영·보안·이행 활동도 포함한다.
  3. 호출이 적은 기능은 바로 폐기한다? 장주기 업무, 비상 절차, 계약·보존 의무를 확인한다.
  4. 제외 범위는 책임이 없다? 유지·인계·호환·데이터 보존 같은 경계 책임이 남을 수 있다.
  5. 이행 전략은 시스템 전체에 하나만 적용한다? 구성요소별로 유지·재플랫폼·재개발·폐기를 조합할 수 있다.
  6. 제품명을 정하면 요구사항이 완성된다? 기능·품질·제약·검증 기준과 선택 근거가 필요하다.
  7. 평균 사용률로 용량을 정한다? 피크·성장·장애 축소 용량·정비 부하를 포함한다.
  8. DB 복제가 있으니 백업은 필요 없다? 논리 손상·삭제가 복제될 수 있어 독립 복구본과 복원 시험이 필요하다.
  9. RTO와 RPO는 같은 값이다? 각각 복구에 허용되는 시간과 허용 가능한 데이터 손실 시점을 뜻한다.
  10. 미들웨어 재시도는 많을수록 안정적이다? 장애 확대와 중복 처리·큐 적체를 막도록 제한·백오프·멱등성이 필요하다.
  11. OS·DBMS·미들웨어는 개별 요구만 만족하면 된다? 인증 조합·자원 한도·장애 도메인을 함께 검증한다.
  12. 지원 버전이면 프로젝트 수명 동안 안전하다? 지원 종료 시점과 업그레이드 경로를 확인해야 한다.
  13. 현행 문제는 모두 새 시스템 범위다? 목표 가치·위험·비용으로 우선순위를 정하고 제외 근거도 남긴다.
  14. 비기능 요구는 ‘빠르게’, ‘안정적으로’면 충분하다? 부하·측정 구간·수치·검증 절차가 있어야 한다.

12. 확인 문제

문제 1

현행 적용현황을 문서 검토만으로 확정하면 안 되는 이유와 보완 증거 세 가지를 쓰라.

문제 2

개발범위의 유지·개선·교체·폐기를 구분하는 판단 기준을 각각 한 가지 이상 설명하라.

문제 3

제외 범위로 정한 과거 통계 기능에 남을 수 있는 경계 책임 두 가지를 쓰라.

문제 4

일괄 전환과 단계 전환의 장점·위험을 비교하라.

문제 5

“최신 운영체제를 사용한다”를 검증 가능한 운영체제 요구사항으로 고쳐 쓰라.

문제 6

DBMS 요구사항에서 RTO와 RPO가 각각 무엇을 뜻하며 어떤 시험이 필요한지 설명하라.

문제 7

메시지 미들웨어의 재시도 요구를 작성할 때 중복·장애 확대를 막기 위해 포함할 항목 네 가지를 쓰라.

문제 8

OS·DBMS·미들웨어 후보가 개별적으로 지원 제품이어도 조합 검증이 필요한 이유를 두 가지 쓰라.

문제 9

미들웨어 8개 인스턴스가 각각 최대 DB 연결 풀 500개를 가진다. DB 허용 연결이 2,000개라면 어떤 위험이 있고 무엇을 조정해야 하는가?

문제 10

현행 분석 완료 여부를 판단할 추적성과 승인 기준을 설명하라.

13. 정답과 해설

정답 1

문서는 설계 당시 의도이며 운영 변경이 반영되지 않았을 수 있다. 실제 호출·오류·피크를 보여주는 로그, 배포·환경 설정, 소스와 의존성 분석, 담당자 인터뷰, 사용자 업무 관찰, 데이터 프로파일 결과 등을 교차 확인한다.

정답 2

유지는 품질·지원·보안 위험이 허용되고 요구를 충족할 때, 개선은 핵심 자산은 재사용하지만 성능·사용성·구조 수정이 필요할 때다. 교체는 지원 종료·기술 부채·변경 비용 때문에 목표 구조가 유리할 때, 폐기는 사용자·연계·규정상 필요가 없고 보존·인계가 승인됐을 때 선택한다.

정답 3

원본 이력 데이터의 법정 보존·접근 경로를 유지하거나 별도 분석 시스템으로 안전하게 이관해야 할 수 있다. 기존 사용자의 조회 기간, 지원 조직 인계, 외부 보고 형식 호환, 폐기 승인·감사 기록도 경계 책임이 될 수 있다.

정답 4

일괄 전환은 공존 기간이 짧고 구조가 단순하지만 실패 영향이 크고 롤백 부담이 높다. 단계 전환은 위험을 나눠 학습하며 확대할 수 있지만 구·신 시스템 공존, 데이터 동기화, 인터페이스 호환과 전체 기간이 복잡해진다.

정답 5

예: “운영체제는 목표 운영기간 동안 공급자 보안 지원을 받아야 하며, 승인된 중요 보안 패치를 시험–단계 적용–롤백 절차로 정해진 정비 창 안에 적용할 수 있어야 한다. 지원 행렬 검토와 패치 리허설로 검증한다.” 제품 신선도가 아니라 지원·운영 결과를 판정한다.

정답 6

RTO는 장애 후 서비스를 복구하는 데 허용되는 시간, RPO는 복구 시점 기준 허용 가능한 데이터 손실 범위다. 실제 부하·데이터로 장애 전환과 백업 복원, 로그 적용, 정합성 대사, 복귀까지 리허설해 측정한다.

정답 7

재시도 가능한 오류 분류, 최대 횟수, 지수형 백오프와 무작위 지연, 메시지 만료, 실패 격리 큐, 고유 요청 ID와 소비자 멱등성, 재처리 승인·감사, 큐 적체 경보 등을 포함한다.

정답 8

특정 OS 버전과 DB 드라이버·미들웨어 런타임 조합이 공급자 인증 범위를 벗어날 수 있다. 또한 각 구성의 최대 연결·메모리·스레드 설정이 합쳐져 전체 용량을 초과하거나 같은 물리 자원에 배치되어 공통 장애점이 될 수 있다.

정답 9

이론상 최대 요청 연결은 4,000개라 DB 한도 2,000개를 초과해 연결 폭주·시간 초과가 생길 수 있다. 실제 동시 부하를 측정하고 인스턴스별 풀 상한·대기열·시간 제한을 전체 예산 안에서 배분하며, 장애로 인스턴스 수가 줄 때와 관리 연결 여유도 포함한다.

정답 10

중요 업무 기능이 응용·데이터·인터페이스·플랫폼 자산과 연결되고, 각 문제·요구에 출처 ID와 설계·테스트가 추적되어야 한다. 포함·제외, 이행 방향, 품질 수치와 잔여 위험을 업무·개발·운영·보안·데이터 책임자가 검토·승인하고 변경 기준선으로 관리한다.

14. 핵심 요약

  • 현행 분석은 문서·인터뷰·소스·설정·로그·관찰·데이터를 교차 검증해 실제 기준선을 만든다.
  • 업무–기능–응용–데이터–인터페이스–인프라를 연결해야 누락 없는 개발범위를 정할 수 있다.
  • 구성요소를 유지·개선·교체·폐기·신규로 분류하고 포함·제외의 경계 책임까지 기록한다.
  • 이행방향은 재호스팅·재플랫폼·리팩터링·대체·유지·폐기를 구성요소별로 조합한다.
  • 일괄·단계·병행·파일럿 전환은 중단 허용, 데이터 소유권, 공존 복잡성과 롤백 가능성으로 선택한다.
  • 운영체제 요구는 호환성·용량·지원·패치·가용성·보안·운영 자동화를 검증 가능하게 표현한다.
  • DBMS 요구는 데이터 모델·트랜잭션·성능·용량·RTO/RPO·백업·보안·이관 호환을 포함한다.
  • 미들웨어 요구는 실행·배포·세션·연계·재시도·멱등성·과부하 보호·관찰 가능성과 관리 보안을 포함한다.
  • OS·DBMS·미들웨어는 지원 행렬, 전체 자원 예산, 장애 도메인과 운영 역량을 조합으로 검증한다.
  • 모든 요구는 근거·우선순위·검증 기준·책임자와 추적 ID가 있어야 목표 시스템 설계로 안전하게 이어진다.
