# 1-1-1-2. 현행 분석을 바탕으로 목표 시스템 기술 · 현행 시스템 분석하기의 적용 절차와 판단 기준

> **수행 범위 기준**: 이 레슨은 정보처리기사 실기 `요구사항 확인 > 현행 시스템 분석하기`의 **현행 분석을 바탕으로 목표 시스템 기술**, **현행 시스템 분석하기의 적용 절차와 판단 기준**을 다룬다. 앞 레슨에서 수집한 현행 구성·문제·OS·DBMS·미들웨어 요구를 입력으로 받아 목표 상태와 전환 경계를 명확히 기술한다. 다음 레슨의 요구사항 확인·검증 활동과는 구분해, 현행 분석 산출물을 목표 시스템 설명으로 전환하는 데 집중한다.

목표 시스템 기술서는 특정 제품 목록이나 이상적인 그림이 아니다. 현행 근거와 업무 목표에서 출발해 목표 기능, 데이터, 인터페이스, 품질, 운영, 보안, 전환 상태를 이해관계자가 같은 의미로 검토할 수 있게 만든 설계 입력이다. “무엇이 달라지고 무엇이 남는지”, “어떤 조건이면 목표에 도달했다고 판정할지”가 드러나야 한다.

---

## 1. 현행에서 목표로 이어지는 추적 구조

목표 시스템의 모든 주요 결정은 현행 증거나 새로운 업무 목표로 추적되어야 한다.

```text
현행 증거/업무 목표
  → 문제·기회·제약
  → 목표 요구와 품질 시나리오
  → 목표 기능·데이터·인터페이스·플랫폼 구조
  → 전환 단계와 검증 항목
```

예를 들어 “월말 주문 조회 8초”라는 측정에서 바로 “제품 X 도입”으로 건너뛰지 않는다.

```text
EVID-PERF-03: 월말 p95 응답 8초, DB CPU 85%, 조회·정산 경합
  → PROB-04: 핵심 조회가 사용자 허용 기준을 초과
  → NFR-PERF-02: 대표 월말 부하에서 주문 조회 p95 2초 이하
  → TARGET: 읽기 경로 최적화, 정산 작업 시간 분리, 용량 여유 확보
  → VERIFY: 운영 규모 데이터와 동시 부하로 성능 시험
```

이 연결이 있으면 기술 후보가 바뀌어도 목표와 검증 기준은 유지된다. 반대로 근거 없는 목표 기능은 범위 팽창과 과잉 설계를 만든다.

## 2. 목표 시스템 기술의 관점

한 장의 구성도로는 사용자 업무, 데이터 소유, 장애와 운영을 모두 설명할 수 없다. 목적에 맞는 여러 관점을 사용한다.

| 관점 | 답해야 할 질문 | 대표 산출물 |
|---|---|---|
| 업무·기능 | 누가 어떤 목표로 무엇을 수행하는가? | 업무 흐름, 기능 목록, 사용자 여정 |
| 응용 | 기능 책임을 어떤 모듈·서비스가 맡는가? | 응용 구성도, 책임·경계 표 |
| 데이터 | 어떤 데이터가 원본이며 어떻게 생성·보존되는가? | 개념 데이터 모델, 소유·흐름도 |
| 인터페이스 | 시스템들이 어떤 계약으로 연계되는가? | 인터페이스 목록, 시퀀스·오류 흐름 |
| 기술·배포 | 어느 실행 환경과 네트워크 구역에 배치되는가? | 배포 구성도, 플랫폼 요구 |
| 품질 | 성능·가용성·보안 목표를 어떤 조건에서 만족하는가? | 품질 속성 시나리오, SLO·복구 표 |
| 운영 | 배포·감시·장애·백업·변경을 어떻게 수행하는가? | 운영 모델, 책임표, 런북 목록 |
| 전환 | 현행에서 목표로 어떤 순서와 통제로 이동하는가? | 이행 상태도, 데이터·호환 계획 |

각 그림에는 범례, 경계, 기준 시점, 포함·제외와 버전을 표시한다. 같은 상자를 서로 다른 의미로 사용하지 않는다.

## 3. 목표와 설계 원칙 정의

### 3.1 목표는 업무 결과로 쓴다

| 나쁜 표현 | 개선 표현 |
|---|---|
| 최신 기술로 전환 | 지원 종료 위험을 제거하고 승인 패치를 정비 창 안에 적용 가능하게 함 |
| 빠른 시스템 | 월말 대표 부하에서 핵심 주문 조회 p95 2초 이하 |
| 안정적인 서비스 | 단일 노드 장애 시 확정 주문 손실 없이 정해진 시간 안에 복구 |
| MSA 도입 | 독립 변경이 잦은 주문·정산 책임을 분리해 승인된 배포 실패 영향 범위를 제한 |

기술 방식은 목표를 달성할 후보이지 목표 자체가 아니다.

### 3.2 설계 원칙

설계 원칙은 여러 선택에서 일관된 판단 기준을 제공한다.

- 업무 능력과 데이터 소유권을 명확한 책임 단위로 둔다.
- 외부 계약은 버전과 호환 기간을 명시한다.
- 민감 데이터는 최소 수집·최소 권한·전 구간 보호한다.
- 모든 변경은 반복 가능한 배포·롤백과 관찰 수단을 갖는다.
- 장애는 발생할 수 있다고 가정하고 격리·복구·대사 절차를 설계한다.
- 복잡한 분산 구조는 독립 변경·확장·장애 격리의 근거가 있을 때만 도입한다.

원칙끼리 충돌할 때 우선순위와 예외 승인 방식을 적는다. 예를 들어 강한 일관성과 분산 가용성이 충돌하면 주문 확정은 일관성을, 추천 조회는 제한된 지연 복제를 허용하는 식으로 업무별 계약을 둔다.

## 4. 목표 업무·기능 기술

### 4.1 사용자와 업무 시나리오

기능명만 나열하지 않고 시작 조건, 정상 흐름, 대안·예외, 완료 조건을 쓴다.

```text
시나리오: 상담원 주문 취소
사전조건: 주문이 취소 가능 상태이고 상담원에게 해당 채널 권한이 있음
정상흐름:
  1. 상담원이 주문을 조회한다.
  2. 시스템이 취소 가능 수량·환불 예상액을 계산한다.
  3. 상담원이 사유를 선택하고 요청한다.
  4. 시스템이 중복 요청을 확인하고 주문 상태를 원자적으로 변경한다.
  5. 결제·재고 후속 처리를 요청하고 추적 ID를 제공한다.
예외: 이미 취소됨, 출고 완료, 결제 연계 지연, 권한 없음
완료조건: 주문 상태·감사 이력·후속 처리 상태를 조회 가능
```

이 시나리오에서 필요한 화면·API·권한·데이터·이벤트·보상·관찰 항목을 도출한다.

### 4.2 기능 책임과 경계

| 책임 단위 | 소유 기능 | 소유 데이터 | 제공 계약 | 제외 책임 |
|---|---|---|---|---|
| 주문 | 등록·상태 전이·취소 판단 | 주문·품목·상태 이력 | 주문 API·상태 이벤트 | 결제 승인 원장 |
| 결제 연계 | 승인·취소 요청 조정 | 요청·응답·멱등 키 | 결제 어댑터 | 외부 카드 원장 |
| 정산 | 일·월 집계와 회계 전송 | 정산 결과·대사 이력 | 파일/메시지 계약 | 주문 상태 변경 |

한 데이터를 여러 책임 단위가 직접 쓰면 규칙이 충돌한다. 원본 시스템을 정하고 다른 단위는 API·이벤트·승인된 복제본으로 접근한다.

### 4.3 범위 변경 표시

현행 기능별로 목표 변화를 기록한다.

| 현행 항목 | 목표 상태 | 변경 유형 | 근거 | 전환 고려 |
|---|---|---|---|---|
| 주문 화면 | 통합 검색·취소 흐름 | 개선 | 사용자 오류·지연 | 구 URL 안내 기간 |
| 월말 정산 | 독립 실행·재시작 가능 | 재설계 | 조회 경합·수동 복구 | 결과 이중 대사 |
| 미사용 통계 | 분석 플랫폼으로 이관 | 폐기/대체 | 소유 조직 변경 | 이력 보존 |

신규·변경·유지·폐기 표시가 있어야 테스트와 교육 범위를 산정할 수 있다.

## 5. 목표 데이터 기술

### 5.1 데이터 소유와 생명주기

각 핵심 데이터에 다음을 기술한다.

- 업무 정의와 고유 식별자
- 생성·변경 권한을 가진 원본 책임 단위
- 유효 상태와 전이 규칙
- 참조 관계와 무결성 조건
- 민감도, 접근 권한, 암호화·마스킹
- 보존·아카이브·파기 시점
- 다른 시스템에 제공되는 복제·이벤트와 최신성 계약

```text
주문 상태 예:
접수 → 결제대기 → 확정 → 출고준비 → 출고완료
  └──────────── 취소 가능 구간 ───────────┘
```

실제 전이 가능 여부와 보상 규칙은 업무 요구로 승인한다. DB 테이블 상태 값만 복사하지 말고 목표 업무 의미를 기술한다.

### 5.2 이관 대상 분류

- 전량 이관: 운영에 즉시 필요한 활성 데이터
- 기간 이관: 최근 N년 등 업무·규정 기준에 따른 범위
- 요약 이관: 상세는 보관하고 목표에는 집계만 제공
- 보관 접근: 현행 읽기 전용 또는 별도 아카이브
- 정제 후 이관: 중복·코드·참조 오류를 승인 규칙으로 수정
- 폐기: 법적·업무 보존 의무가 없고 승인된 데이터

이관 범위에는 건수와 용량뿐 아니라 원본–목표 키 매핑, 코드 변환, 문자·시간·숫자 정밀도, 첨부 파일과 이력의 처리도 포함한다.

### 5.3 대사 기준

```text
구조 대사: 필수 테이블·열·제약·인덱스 존재
건수 대사: 범위별 원본 건수 = 성공 + 승인 제외 + 오류
금액 대사: 통화·일자·조직별 합계와 허용 오차
관계 대사: 고아 레코드와 참조 불일치 0건 또는 승인 기준
표본 대사: 업무 담당자가 대표·경계·예외 사례 확인
```

전체 건수만 같아도 행이 바뀌거나 중복·누락이 상쇄될 수 있다. 키·합계·해시·관계·업무 표본을 조합한다.

## 6. 목표 인터페이스 기술

인터페이스는 정상 요청 형식만 아니라 실패와 변경 계약을 포함한다.

| 항목 | 기술 내용 |
|---|---|
| 제공자·소비자 | 시스템·책임 조직·지원 연락처 |
| 목적·데이터 | 업무 의미, 필수·선택 필드, 스키마 |
| 방식 | 동기 API, 비동기 메시지, 파일 배치 등 |
| 식별·보안 | 인증 주체, 권한, 암호화, 민감정보 최소화 |
| 시간 특성 | 제한 시간, 주기, 피크 처리량, 최대 크기 |
| 신뢰성 | 재시도, 멱등 키, 순서, 중복, 만료, 보상 |
| 오류 계약 | 오류 코드·재시도 가능성·격리·알림 |
| 버전 | 호환 규칙, 폐기 예고, 계약 시험 |
| 관찰 | 상관관계 ID, 메트릭, 감사·추적 로그 |

### 6.1 시퀀스로 경계를 확인한다

```text
사용자 → 주문 API: 취소 요청(request-id)
주문 API → 주문 DB: 상태 조건부 변경 + 이력
주문 API → 메시지 채널: 주문취소됨(event-id)
결제 연계 ← 메시지 채널: 이벤트 수신·중복 확인
결제 연계 → 외부 결제: 취소 요청
결제 연계 → 상태 저장: 결과 기록
사용자 ← 주문 API: 접수·추적 ID
```

이 그림에서 주문 확정과 외부 결제 취소를 하나의 DB 트랜잭션으로 묶을 수 없는 경계를 확인하고, 비동기 상태·재시도·보상과 사용자 표시 요구를 도출한다.

## 7. 목표 품질을 시나리오로 기술

“고가용성”, “보안 강화” 같은 표어 대신 자극–환경–대상–응답–측정값을 쓴다.

### 7.1 성능

```text
자극: 월말 피크에 상담원 500명이 주문 조회
환경: 정산 배치가 승인된 제한 자원으로 동시 실행
대상: 주문 조회 API와 데이터 저장소
응답: 권한에 맞는 최신 주문 목록 반환
측정: 15분 구간 p95 2초 이하, 오류율 0.1% 이하
```

부하 모델, 데이터 규모, 워밍업, 측정 시작·끝과 제외 조건이 있어야 재현 가능하다.

### 7.2 가용성·복구

- 어떤 장애를 가정하는가: 프로세스, 노드, 저장장치, 구역, 외부 연계
- 어떤 서비스 수준을 유지하는가: 읽기 가능, 쓰기 제한, 큐 보관
- 탐지·전환·복구·복귀의 목표 시간은 얼마인가?
- 확정 데이터의 허용 손실과 대사 기준은 무엇인가?
- 사람이 승인해야 하는 단계와 자동화 범위는 무엇인가?

### 7.3 보안

```text
주체: 상담원, 운영자, 서비스 계정, 외부 제휴사
자원: 주문 개인정보, 결제 참조, 감사 로그, 관리 기능
통제: 강한 인증, 업무 역할 권한, 전송·저장 보호, 최소 노출
검증: 권한 매트릭스 시험, 로그 검사, 위협 모델 검토, 취약점 점검
```

인증에 성공했다고 모든 주문을 조회할 수 있는 것은 아니다. 기능 권한과 데이터 범위 권한을 분리한다.

### 7.4 변경성·운영성

- 독립 배포가 필요한 변경 단위와 허용 중단
- 설정·비밀·스키마 변경의 호환·롤백
- 배포 빈도, 실패율, 복구 시간 목표
- 로그·메트릭·추적과 경보의 책임자·행동 기준
- 표준 장애 절차와 정기 훈련

## 8. 목표 기술·배포 구조

### 8.1 논리 구조와 물리 배포를 구분한다

```text
[논리]
채널 → API 경계 → 주문 책임 → 데이터 접근
                    └→ 비동기 이벤트 → 결제·정산

[배포]
외부 구역: 진입·정책 장비
응용 구역 A/B: 주문 인스턴스와 메시지 소비자
데이터 구역: 주 DB·대기 복제본·백업 경로
관리 구역: 배포·감시·감사 수집
```

논리 서비스 두 개가 같은 서버에 배치될 수도 있고 하나의 논리 서비스가 여러 노드에 복제될 수도 있다. 책임 분리와 물리 장애 격리를 혼동하지 않는다.

### 8.2 플랫폼 요구 반영

앞 레슨에서 식별한 운영체제·DBMS·미들웨어 요구를 목표 배포 구조에 매핑한다.

| 요구 | 목표 구조 반영 | 검증 |
|---|---|---|
| OS 패치 중 서비스 유지 | 장애 구역을 나눈 다중 인스턴스, 순차 교체 | 패치 리허설 |
| DB RTO/RPO | 복제·백업·로그 보존과 전환 절차 | 장애·복원 시험 |
| 메시지 중복 방지 | 이벤트 ID·소비자 처리 이력 | 중복 전달 시험 |
| 관리자 감사 | 개인 계정·권한 분리·중앙 감사 로그 | 권한·로그 검사 |

구조 요소가 어떤 요구를 충족하는지, 충족하지 못하는 잔여 위험은 무엇인지 기록한다.

### 8.3 공통 장애점 검토

- 여러 노드가 같은 물리 호스트·전원·스토리지를 공유하는가?
- 이름·인증·키·시간·배포 시스템 장애가 전체에 미치는 영향은?
- 모니터링과 복구 도구가 대상 시스템과 같은 장애 구역에 있는가?
- 관리 계정 하나가 모든 계층을 변경할 수 있는가?
- 외부 공급자·회선 장애 때 제한 서비스가 가능한가?

상자 수보다 장애 도메인과 복구 증거가 가용성을 결정한다.

## 9. 전환 상태까지 목표에 포함한다

목표 최종 상태만 그리면 이행 중 구·신 시스템의 데이터와 계약이 빠진다.

### 9.1 상태별 기술

| 상태 | 쓰기 원본 | 읽기 경로 | 인터페이스 | 데이터 동기화 | 종료 조건 |
|---|---|---|---|---|---|
| S0 현행 | 현행 | 현행 | 기존 계약 | 없음 | 전환 준비 승인 |
| S1 그림자 검증 | 현행 | 현행, 목표 비교 | 목표는 결과 비노출 | 단방향 복제 | 대사·성능 기준 충족 |
| S2 일부 전환 | 기능별 지정 | 구·신 혼합 | 호환 어댑터 | 충돌 방지 규칙 | 사용자·오류 기준 충족 |
| S3 목표 | 목표 | 목표 | 새 계약 | 아카이브만 | 안정화 승인 |

각 상태에서 누가 쓰기 원본인지 반드시 하나로 정하거나 충돌 해결 규칙을 둔다.

### 9.2 롤백과 롤포워드

- 코드만 되돌리면 되는지 데이터 스키마·신규 거래도 되돌릴 수 있는지
- 목표에서 생성한 데이터를 현행이 해석할 수 있는지
- 외부 시스템이 새 계약으로 전환한 뒤 복귀 가능한지
- 롤백 가능 시점과 이후 롤포워드만 가능한 경계를 어디에 둘지
- 중단 결정권자, 최대 판단 시간, 데이터 대사 절차

“문제 시 롤백”은 절차가 아니다. 명령·책임·데이터 결과·검증 시간까지 리허설한다.

## 10. 현행 시스템 분석하기의 적용 절차와 판단 기준

### 단계 1: 목적·범위·이해관계자 확정

- 왜 분석하는지, 어떤 결정을 내려야 하는지 정의한다.
- 업무·응용·데이터·환경·조사 기준일과 제외 경계를 승인한다.
- 업무·운영·보안·데이터·개발·외부 책임자를 지정한다.

**판단 기준**: 조사 결과를 승인하고 변경 영향에 답할 책임자가 있는가?

### 단계 2: 수집 계획과 증거 확보

- 문서, 인벤토리, 소스, 설정, 로그, 성능·장애·데이터를 수집한다.
- 접근 권한과 개인정보 최소화, 표본 기간과 신뢰도를 기록한다.
- 인터뷰·관찰 결과를 실측과 교차 검증한다.

**판단 기준**: 문서 주장과 실제 운영 차이를 확인할 독립 증거가 있는가?

### 단계 3: 현행 모델과 기준선 작성

- 업무–기능–응용–데이터–인터페이스–플랫폼 관계를 모델링한다.
- 부하·응답·용량·장애·운영 비용 기준선을 측정한다.
- 자산 ID와 소유자, 지원 수명, 기술·보안 위험을 연결한다.

**판단 기준**: 중요한 업무가 고아 자산 없이 추적되고 수치의 측정 조건이 재현 가능한가?

### 단계 4: 문제·기회·제약 분석

- 증상과 원인을 구분하고 근거·영향·빈도·심각도를 기록한다.
- 규제, 계약, 데이터 위치, 중단 시간, 예산·일정·역량 제약을 확인한다.
- 위험을 회피·완화·전가·수용 중 어떤 방식으로 다룰지 정한다.

**판단 기준**: 해결안이 아니라 먼저 검증된 문제와 성공 기준이 정의됐는가?

### 단계 5: 목표·범위·대안 도출

- 유지·개선·교체·폐기·신규를 분류한다.
- 기능·데이터·연계·플랫폼·운영의 목표 관점을 작성한다.
- 여러 대안을 비용·위험·품질·전환·지원성으로 비교한다.

**판단 기준**: 필수 제약을 위반한 대안을 점수 평균으로 선택하지 않았는가?

### 단계 6: 목표 시스템과 품질 시나리오 기술

- 목표 업무 흐름, 책임, 데이터 소유, 인터페이스 계약을 쓴다.
- 성능·가용성·보안·운영성을 부하와 측정값으로 정의한다.
- 기술·배포 구조에 요구 ID를 매핑하고 잔여 위험을 기록한다.

**판단 기준**: 서로 다른 독자가 그림과 용어를 같은 의미로 해석하고 시험 합격을 판정할 수 있는가?

### 단계 7: 전환·검증·운영 설계

- 데이터 이관·대사, 계약 호환, 교육·운영 인수와 폐기를 계획한다.
- 단계별 진입·성공·중단·롤백 조건과 책임자를 둔다.
- 대표 규모로 성능·장애·복구·보안·업무 인수 시험을 정한다.

**판단 기준**: 최종 상태뿐 아니라 모든 중간 상태의 쓰기 원본과 복구 방법이 명확한가?

### 단계 8: 검토·승인·기준선 관리

- 추적표로 현행 근거–목표 요구–구조–시험을 확인한다.
- 충돌·가정·미결사항·예외와 승인 기한을 관리한다.
- 승인 뒤 변경은 영향 분석과 버전으로 통제한다.

**판단 기준**: 승인된 기준선과 이후 변경 이력이 재현 가능한가?

## 12. 실전 예제: 목표 기술 요약서

```text
[목표]
월말 사용자 조회와 정산 작업의 경합을 줄이고, 지원 종료 플랫폼 위험을 제거하며,
단일 노드 장애와 반복 배포를 운영팀이 정해진 절차로 처리할 수 있게 한다.

[핵심 변경]
1. 주문 상태의 쓰기 원본과 책임을 주문 모듈로 명확화
2. 정산을 체크포인트 가능한 독립 작업으로 분리
3. 외부 결제는 버전 계약·멱등 키·추적 ID를 가진 어댑터로 격리
4. 승인된 지원 조합의 OS·DBMS·미들웨어로 단계 전환
5. 중앙 메트릭·로그·추적과 장애·복원 리허설 도입

[유지/제외]
회계 파일 계약은 상대 시스템 전환까지 호환 유지한다.
과거 통계 화면은 제외하되 이력은 승인된 아카이브에서 조회한다.

[성공 기준]
대표 월말 부하의 성능, 장애 전환·복원, 데이터 건수·금액·관계 대사,
권한·감사 시험, 사용자 인수 기준을 모두 충족한다.

[전환]
그림자 비교 → 일부 채널 전환 → 쓰기 원본 전환 → 안정화 → 현행 폐기 순서이며,
각 단계에 진입·중단·복귀 조건을 둔다.
```

이 요약은 상세 모델을 대체하지 않지만 의사결정자에게 목표·변경·성공·전환을 한 흐름으로 보여준다.

## 13. 자주 틀리는 포인트

1. **목표 시스템은 제품 목록이다?** 업무·데이터·인터페이스·품질·운영·전환 상태를 포함한 요구·구조 설명이다.
2. **현행 문제에서 바로 기술을 선택한다?** 문제와 성공 기준을 먼저 정의하고 대안을 비교한다.
3. **구성도 한 장이면 모든 관점이 충분하다?** 업무·데이터·배포·운영·전환은 목적별 관점이 필요하다.
4. **목표는 ‘빠름·안정·최신’처럼 쓰면 된다?** 부하·환경·응답·측정값과 검증 절차가 필요하다.
5. **데이터를 여러 서비스가 직접 갱신해도 편리하다?** 소유권과 불변조건이 분산되어 충돌·추적 문제가 생긴다.
6. **전체 건수가 같으면 데이터 이관은 성공이다?** 키·금액·관계·표본과 승인 제외를 함께 대사한다.
7. **인터페이스 문서는 정상 요청 스키마만 있으면 된다?** 오류·시간 제한·재시도·중복·버전·보안·관찰 계약이 필요하다.
8. **논리 서비스 수가 많으면 고가용성이다?** 물리 장애 도메인과 복구 시험이 중요하다.
9. **최종 목표 상태만 설계하면 된다?** 공존 단계의 쓰기 원본·동기화·호환·롤백을 기술해야 한다.
10. **롤백은 이전 코드를 다시 배포하는 것이다?** 데이터·스키마·외부 계약의 역호환과 대사가 필요하다.
11. **승인된 요구는 바꾸면 안 된다?** 기준선 이후에는 영향 분석·승인·버전으로 통제해 변경할 수 있다.
12. **점수 합이 가장 높은 대안이 항상 정답이다?** 법·보안·호환 같은 필수 제약 위반은 탈락 조건일 수 있다.
13. **모든 품질 목표를 최대로 잡으면 좋다?** 비용·복잡성·상충을 고려해 업무 중요도와 위험으로 수준을 정한다.
14. **목표 구조가 있으면 시험은 나중에 정한다?** 검증 불가능한 구조를 피하려면 목표와 동시에 합격 기준을 정한다.

## 14. 확인 문제

### 문제 1

현행 증거에서 목표 구조로 바로 건너뛰지 않고 문제·요구·검증을 연결해야 하는 이유를 설명하라.

### 문제 2

목표 시스템 기술에 필요한 관점 네 가지를 쓰고 각 관점의 핵심 질문을 설명하라.

### 문제 3

“월말 주문 시스템을 빠르게 한다”를 품질 속성 시나리오로 바꾸어 쓰라.

### 문제 4

목표 데이터 기술에서 원본 책임 단위를 정해야 하는 이유와 복제 데이터에 필요한 계약을 설명하라.

### 문제 5

인터페이스 계약에 정상 데이터 형식 외에 포함해야 할 항목 여섯 가지를 쓰라.

### 문제 6

논리 구조와 물리 배포 구조의 차이를 예로 설명하라.

### 문제 7

단계 전환의 중간 상태마다 반드시 정해야 할 데이터·운영 조건 네 가지를 쓰라.

### 문제 8

코드 롤백만으로 전체 롤백이 되지 않을 수 있는 이유를 데이터와 외부 계약 관점에서 설명하라.

### 문제 9

현행 시스템 분석하기의 적용 절차를 여덟 단계 흐름으로 요약하라.

### 문제 10

목표 시스템 기술서의 완전성·일관성·검증 가능성·추적성을 각각 어떻게 확인하는지 설명하라.

## 15. 정답과 해설

### 정답 1

현행 증상만 보고 특정 기술을 고르면 원인을 해결하지 못하거나 다른 요구를 놓칠 수 있다. 증거–문제–측정 가능한 요구–구조 결정–시험을 연결하면 선택 근거를 검토하고 기술 후보가 바뀌어도 목표와 합격 기준을 유지할 수 있다.

### 정답 2

예를 들어 업무·기능 관점은 누가 어떤 목표로 무엇을 수행하는지, 응용 관점은 어느 모듈이 어떤 책임을 갖는지, 데이터 관점은 원본과 생명주기·무결성이 무엇인지, 인터페이스 관점은 시스템 사이 정상·오류·버전 계약이 무엇인지 묻는다. 배포·품질·운영·전환 관점도 필요에 따라 함께 사용한다.

### 정답 3

예: “월말 정산 배치가 제한 자원으로 동시 실행되고 상담원 500명이 대표 운영 규모의 주문을 조회할 때, 주문 조회 API는 15분 측정 구간 p95 2초 이하와 오류율 0.1% 이하로 권한에 맞는 결과를 반환해야 한다.” 실제 수치는 승인된 업무 기준으로 정한다.

### 정답 4

여러 단위가 같은 데이터를 직접 쓰면 불변조건·충돌 해결·감사 책임이 모호해진다. 원본 소유자를 정하고 복제본에는 전달 방식, 최신성, 순서·중복, 스키마 버전, 재처리와 원본 장애 때의 동작 계약을 둔다.

### 정답 5

제공자·소비자와 책임, 인증·인가·암호화, 시간 제한과 처리량, 오류 코드와 재시도 가능성, 멱등·중복·순서, 버전·호환·폐기, 상관관계 ID와 감사, 최대 크기·만료 등을 포함한다.

### 정답 6

논리 구조는 주문·결제·정산 같은 기능 책임과 호출 관계를 나타낸다. 물리 배포 구조는 그 논리 단위가 어느 서버·구역·노드·저장소에 몇 개 배치되는지 나타낸다. 하나의 논리 주문 서비스가 장애 구역 A와 B의 여러 인스턴스에 배치될 수 있다.

### 정답 7

각 상태의 쓰기 원본, 읽기 경로, 구·신 계약 호환, 데이터 동기화·충돌 규칙, 진입·성공·중단 조건, 모니터링, 책임자, 롤백 후 데이터 처리와 최대 판단 시간을 정한다.

### 정답 8

새 코드가 스키마를 비호환 방식으로 바꾸거나 목표 시스템에서 새 거래를 생성하면 이전 코드가 읽지 못할 수 있다. 외부 소비자가 새 계약으로 전환했으면 구버전 응답을 이해하지 못할 수도 있다. 역방향 이관·호환 어댑터·대사 또는 롤포워드 전략이 필요하다.

### 정답 9

목적·범위·책임자 확정 → 수집 계획과 증거 확보 → 현행 모델·기준선 작성 → 문제·기회·제약 분석 → 목표·범위·대안 도출 → 목표 구조·품질 시나리오 기술 → 전환·검증·운영 설계 → 다자 검토·승인·기준선 관리 순서다. 발견에 따라 반복될 수 있다.

### 정답 10

완전성은 중요 업무·데이터·연계·운영·전환 누락을, 일관성은 용어·데이터 원본·수치·구조의 충돌을 본다. 검증 가능성은 부하·환경·수치·시험 절차로 합격 판정 가능한지 확인한다. 추적성은 현행 증거와 요구, 구조 결정, 이행 작업, 시험 사이에 고아 항목이 없는지 ID로 확인한다.

## 16. 핵심 요약

- 목표 시스템은 현행 증거와 업무 목표에서 추적되는 기능·데이터·인터페이스·품질·운영·전환 설명이다.
- 현행 증거 → 문제·제약 → 측정 가능한 요구 → 목표 구조 → 시험의 연결을 유지한다.
- 업무·응용·데이터·인터페이스·배포·품질·운영·전환 관점을 목적에 맞게 나눠 기술한다.
- 기술 이름보다 업무 결과와 품질 시나리오를 먼저 정의하고 필수 제약을 통과한 대안을 비교한다.
- 데이터 원본 책임과 상태 전이·보존·민감도·복제 최신성·이관 대사 기준을 명확히 한다.
- 인터페이스는 정상 스키마뿐 아니라 보안·오류·시간·재시도·멱등·버전·관찰 계약을 포함한다.
- 목표 논리 구조를 실제 배포·장애 도메인·플랫폼 요구와 매핑하고 복구 시험으로 검증한다.
- 최종 상태뿐 아니라 그림자·부분 전환·공존 상태의 쓰기 원본과 종료·롤백 조건을 기술한다.
- 현행 시스템 분석하기는 범위–증거–기준선–문제–대안–목표–전환–승인의 반복 가능한 절차다.
- 완전성·일관성·실현·검증 가능성·추적성을 체크하고 승인 기준선 이후 변경을 영향 분석으로 관리한다.
