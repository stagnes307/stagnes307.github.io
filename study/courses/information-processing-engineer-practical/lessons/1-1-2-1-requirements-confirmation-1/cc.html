1.2 요구사항의 기본 속성

각 요구에는 본문 외에 다음 메타데이터를 둔다.

  • 고유 ID와 제목
  • 유형·범위·책임자
  • 출처와 업무 근거
  • 우선순위와 미충족 영향
  • 전제·의존·제약
  • 수용 기준과 검증 방법
  • 관련 모델·설계·테스트 링크
  • 상태, 버전, 변경 이력과 승인자

코드 예시 · text

ID: FR-CANCEL-004
조건: 주문이 결제완료이고 출고 전이며 상담원이 해당 채널 권한을 가짐
행동: 시스템은 요청 ID 중복을 확인하고 주문 상태를 취소접수로 변경한다.
결과: 상태 이력과 감사 주체를 저장하고 결제 취소 작업을 생성한다.
예외: 이미 처리된 요청은 기존 결과를 반환하며 중복 작업을 만들지 않는다.
검증: 경계 상태·중복·권한·저장 실패 단위/통합 시험
02

2. 요구사항 분석의 목적

분석은 수집한 자연어 요구를 구조화해 다음 질문에 답한다.

  1. 누가 어떤 업무 목표로 기능을 사용하는가?
  2. 시스템 경계 안팎의 책임은 무엇인가?
  3. 입력·조건·상태에 따라 어떤 결과와 예외가 생기는가?
  4. 어떤 데이터가 생성·변경되고 무결성은 무엇인가?
  5. 기능들이 어떤 순서·병렬·의존 관계를 갖는가?
  6. 품질 요구가 어떤 부하·장애·위협 조건에서 측정되는가?
  7. 요구끼리 중복·모순·누락·모호성이 있는가?
  8. 설계·시험으로 실현하고 검증할 수 있는가?

분석 모델은 요구 자체를 마음대로 바꾸는 도구가 아니다. 자연어에 숨은 가정과 경계를 드러내 이해관계자에게 확인받는 도구다.

03

3. 요구사항 분석 기법

3.1 인터뷰·워크숍 재확인

수집 단계에서 사용한 인터뷰도 분석 결과를 확인하는 데 다시 쓴다.

  • 열린 질문으로 목표와 예외를 듣고, 닫힌 질문으로 수치·선택을 확정한다.
  • 업무 담당자, 운영자, 보안·데이터 책임자와 외부 연계 담당자를 함께 참여시킨다.
  • “현재 그렇게 한다”와 “목표에서도 반드시 그래야 한다”를 구분한다.
  • 회의 뒤 결정·미결·가정·담당·기한을 기록한다.

워크숍에서 목소리가 큰 한 사람의 의견을 전체 요구로 확정하지 않는다. 역할별 승인 권한과 충돌 해결자를 정한다.

3.2 유스케이스와 시나리오

유스케이스는 액터가 목표를 달성하기 위해 시스템과 상호작용하는 흐름을 표현한다.

코드 예시 · text

유스케이스: 주문 취소
주 액터: 상담원
보조 액터: 결제 서비스, 재고 서비스
사전조건: 인증됨, 주문 조회 권한 있음
기본 흐름: 조회 → 취소 가능 검증 → 요청 → 상태·이력 저장 → 후속 처리 접수
대안 흐름: 부분 취소, 후속 처리 지연
예외 흐름: 권한 없음, 출고 완료, 중복 요청, 저장 실패
사후조건: 주문 상태와 후속 처리 추적 상태가 일관됨

정상 흐름만 쓰면 오류·보안·복구 요구가 누락된다. 각 분기에는 시작 조건과 관찰 가능한 결과를 둔다.

3.3 데이터 흐름도

DFD(Data Flow Diagram)는 외부 개체, 처리, 데이터 저장소, 데이터 흐름으로 시스템 경계와 데이터 이동을 표현한다.

코드 예시 · text

[상담원] --취소 요청--> (주문 취소 처리)
   ^                         |      \
   | 결과                    |       \ 취소 이벤트
   |                         v        v
   +------------------- [주문 저장소] [결제 연계]
  • 외부 개체끼리 또는 저장소끼리 데이터가 처리 없이 직접 흐르는 모델을 주의한다.
  • 상위 컨텍스트와 하위 분해의 입력·출력이 균형을 이루는지 본다.
  • 물리 서버나 구현 순서보다 논리적 데이터 변환과 경계를 표현한다.

3.4 데이터 모델링

개체–관계 모델과 데이터 사전을 사용해 핵심 개체, 속성, 식별자, 관계, 카디널리티와 제약을 확인한다.

3. 요구사항 분석 기법 · 학습 표 2
개체핵심 규칙 예
주문한 주문은 하나 이상의 주문 품목을 가진다.
취소 요청요청 ID는 채널 범위에서 유일하며 주문과 연결된다.
상태 이력이전·이후 상태, 시각, 수행 주체를 기록한다.
결제 취소 작업주문 취소와 1:N 가능하며 재시도 상태를 가진다.

화면 필드 목록만으로 데이터 모델을 만들면 업무 식별자와 이력·관계가 누락된다. 동의어·동음어·코드 값·단위·허용 null을 데이터 사전으로 통일한다.

3.5 상태 모델

상태 전이 모델은 객체가 이벤트와 조건에 따라 어떤 상태로 이동할 수 있는지 표현한다.

코드 예시 · text

접수 --결제성공--> 확정 --출고지시--> 출고준비 --출고--> 완료
 |                   |
 +--사용자취소------> 취소접수 --후속성공--> 취소완료
                               --후속실패--> 취소처리중

각 전이에 다음을 확인한다.

  • 이벤트를 발생시킬 권한 주체
  • 전이 조건과 금지 전이
  • 원자적으로 변경할 데이터와 이력
  • 중복·순서 역전 이벤트 처리
  • 외부 작업 실패 때 보상·재시도
  • 시간 초과와 수동 개입

3.6 의사결정표와 의사결정트리

조건 조합이 많을 때 의사결정표로 누락·충돌을 찾는다.

3. 요구사항 분석 기법 · 학습 표 3
규칙출고 전결제 완료취소 권한결과
R1YYY취소 접수·결제 후속
R2YNY주문만 취소
R3N-Y거절–출고 완료
R4--N거절–권한 없음

-는 해당 조건이 결과에 영향을 주지 않음을 뜻한다. 모든 가능한 조합이 한 규칙에만 해당하는지, 우선 적용 규칙이 필요한지 확인한다.

의사결정트리는 조건을 분기 순서로 보여주기 좋다. 표는 조합 완전성과 중복 검사에 유리하다.

3.7 프로세스·활동 모델

업무 흐름도, 활동 다이어그램, BPMN 같은 모델로 순서·병렬·대기·책임 인계를 확인한다.

  • 시작·종료와 업무 완료 의미
  • 사람·시스템·외부 조직의 책임 구역
  • 병렬 작업의 합류 조건
  • 승인·반려·재작업과 시간 제한
  • 보상·수동 복구·에스컬레이션

화살표가 있다고 데이터 일관성과 트랜잭션 경계가 자동 정의되는 것은 아니다. 상태·데이터 모델과 교차 확인한다.

3.8 프로토타이핑

화면, API 예시, 보고서, 처리 흐름을 낮은 비용으로 만들어 사용자가 요구를 구체적으로 확인하게 한다.

  • 탐색용 프로토타입인지 실제 제품으로 발전시킬 진화형인지 명시한다.
  • 디자인 완성도가 기능 완전성으로 오해되지 않게 한다.
  • 접근성, 오류·빈 상태, 권한별 차이, 대량 데이터도 검토한다.
  • 프로토타입에서 발견한 결정을 요구 ID로 반영한다.

“화면이 보이므로 구현도 쉽다”는 결론을 피한다. 데이터·연계·성능·보안은 별도 검증이 필요하다.

3.9 품질 속성 시나리오

비기능 요구를 자극원–자극–환경–대상–응답–측정으로 구조화한다.

코드 예시 · text

자극원: 정상 권한이 없는 인증 사용자
자극: 다른 조직 주문 조회 요청
환경: 정상 운영
대상: 주문 조회 API와 감사 체계
응답: 데이터 미반환, 정책상 오류, 시도 감사
측정: 권한 우회 0건, 감사 필수 필드 누락 0건

보안·성능·가용성·변경성 같은 품질이 실제 시험 가능한 조건으로 바뀐다.

한 모델 안에서 맞아도 다른 관점과 충돌할 수 있다.

교차 확인질문

DFD ↔ 인터페이스외부 데이터 흐름마다 계약·책임자가 있는가?
품질 ↔ 기능성능·감사·복구 기준을 어느 처리와 데이터에 적용하는가?
목표 ↔ 요구모든 하위 요구가 상위 목표에 기여하고 목표가 요구로 완전히 전개됐는가?

예를 들어 유스케이스에는 “부분 취소”가 있지만 데이터 모델에 품목별 취소 수량과 금액 배분이 없으면 분석 결함이다.

5. 요구사항 검증 기준

5.1 정확성

이해관계자의 실제 필요와 업무 규칙을 올바르게 표현하는가? 근거 문서·정책·담당자 승인과 모델 예제로 확인한다.

5.2 완전성

정상·대안·예외, 입력·출력, 상태, 데이터, 권한, 품질과 전환 조건이 필요한 수준으로 포함됐는가? 미정 항목은 숨기지 않고 담당·기한을 둔다.

5.3 일관성

요구끼리 용어·수치·상태·우선순위가 충돌하지 않는가?

코드 예시 · text

REQ-A: 주문 취소는 출고 전까지 가능
REQ-B: 포장 시작 뒤 모든 변경 금지

출고 전과 포장 시작 사이 구간의 우선 규칙을 결정해야 한다.

5.4 명확성·비모호성

“적절한”, “가능하면”, “빠르게”, “사용자 친화적”, “등”처럼 판단자가 달라지는 표현을 조건·수치·목록으로 바꾼다. 한 문장에 여러 독립 요구를 넣지 않는다.

5.5 실현 가능성

기술, 일정, 비용, 법·정책, 인력과 외부 계약 안에서 달성 가능한가? 성능 모형, 기술 검증, 공급자 확인과 추정으로 본다. 어렵다는 이유만으로 삭제하지 않고 목표·제약·대안을 이해관계자와 조정한다.

5.6 필요성

상위 목표·사용자·규제·위험 근거가 있는가? 없어도 좋은 기능과 반드시 필요한 요구를 구분한다.

5.7 검증 가능성

검토, 시험, 분석, 시연 중 하나 이상의 방법으로 합격·불합격을 객관적으로 판정할 수 있는가?

  • “시스템은 안정적이어야 한다” → 불충분
  • “단일 응용 노드 중지 시 진행 중 확정 거래의 중복·손실 없이 60초 안에 새 요청을 처리한다” → 시험 가능

5.8 추적 가능성

출처·상위 목표에서 요구, 설계, 코드, 테스트, 배포와 변경까지 양방향으로 연결되는가? 추적은 문서 링크 수가 아니라 변경 영향과 누락을 찾을 수 있어야 한다.

5.9 우선순위·단일성·수정 가능성

  • 우선순위의 기준과 승인자가 있는가?
  • 한 요구 ID가 하나의 독립 검증 단위를 나타내는가?
  • 중복 없이 구조화되어 변경 시 여러 문장을 동시에 고칠 필요가 적은가?
06

6. 요구사항 검증 방법

6.1 동료 검토와 워크스루

작성자가 모델과 시나리오를 설명하고 관련자가 질문한다. 초기 이해 공유와 빠른 피드백에 유리하다. 설명 능력 때문에 문서 결함이 가려지지 않도록 검토자는 문서를 사전에 읽는다.

6.2 공식 인스펙션

역할과 절차를 정한 체계적 검토다.

  • 작성자: 요구와 근거 설명, 결함 수정
  • 진행자: 범위·시간·규칙 관리
  • 검토자: 업무·기술·시험·운영 관점 결함 탐색
  • 기록자: 결함, 분류, 위치, 담당·기한 기록

회의에서는 해결 설계에 시간을 모두 쓰기보다 결함을 명확히 식별하고, 수정은 별도 수행한 뒤 재확인한다.

6.3 체크리스트 검토

조직의 반복 결함을 질문 목록으로 확인한다.

  • 모든 용어가 데이터 사전에 정의됐는가?
  • 주어·대상·조건·행동·결과가 있는가?
  • 정상·오류·경계·권한 흐름이 있는가?
  • 단위·측정 위치·부하·기간이 명시됐는가?
  • 외부 인터페이스의 시간 제한·중복·버전이 있는가?
  • 개인정보와 로그·보존 요구가 있는가?

체크 표시가 내용의 정확성을 보장하지는 않는다. 도메인 판단과 모델 검토를 함께 한다.

6.4 프로토타입·시뮬레이션·기술 검증

문서만으로 판단하기 어려운 사용성, 복잡한 규칙, 성능·호환 가능성을 실험한다.

  • 프로토타입으로 화면 흐름·오류·접근성을 확인한다.
  • 규칙 표를 실제 사례 데이터에 적용해 결과를 비교한다.
  • 핵심 기술 위험은 제한된 스파이크로 측정한다.
  • 결과·환경·한계와 요구 변경을 기록한다.

기술 검증용 코드를 운영 품질로 오해하지 않는다.

6.5 테스트 케이스 조기 도출

요구를 읽고 테스트를 쓸 수 없다면 모호하거나 누락됐을 가능성이 높다.

7. 검증 절차

단계 1: 검증 계획

  • 검토 대상 버전과 범위를 고정한다.
  • 중요도·위험에 따라 검토 깊이와 참여자를 정한다.
  • 품질 기준, 체크리스트, 결함 심각도와 완료 조건을 합의한다.
  • 참조할 정책·모델·현행 근거와 용어 사전을 준비한다.

단계 2: 개별 사전 검토

검토자는 각자 결함 위치, 유형, 근거와 질문을 기록한다. 회의에서 처음 읽기 시작하지 않는다.

단계 3: 공동 검토

  • 요구 ID와 모델 위치 단위로 결함을 확인한다.
  • 의견 차이는 출처·업무 규칙·측정 결과로 해결한다.
  • 해결되지 않으면 결정권자·기한·의존 작업을 지정한다.
  • 새 기능 제안과 기존 요구 결함을 구분한다.

단계 4: 결함 수정

작성자가 요구 본문, 모델, 용어 사전, 추적표와 수용 기준을 함께 수정한다. 한 파일만 바꾸어 불일치를 남기지 않는다.

단계 5: 재검증

진행자 또는 지정 검토자가 수정이 결함을 해결했고 새 충돌을 만들지 않았는지 확인한다. 치명·중대 결함은 원 참여자와 다시 검토할 수 있다.

단계 6: 승인과 기준선

  • 미해결 결함과 수용 위험을 승인자가 명시적으로 판단한다.
  • 완료 기준을 충족하면 버전과 승인 기록을 남겨 기준선으로 삼는다.
  • 이후 변경은 요청–영향 분석–승인–수정–재검증으로 통제한다.

7.1 완료 기준 예

  • 치명·중대 결함 0건
  • 필수 요구의 출처·수용 기준·검증 방법·책임자 100% 연결
  • 모든 용어 충돌 해결
  • 상위 목표와 연결되지 않은 필수 요구 0건
  • 미결사항은 승인된 담당·기한·영향을 가짐
  • 업무·운영·보안·데이터·시험 책임자의 필수 검토 완료

결함 개수만 낮추려고 문장을 합치거나 미결을 삭제하지 않는다. 중요도와 잔여 위험을 본다.

10. 통합 사례 검증

요구 초안:

상담원은 주문을 빠르게 취소할 수 있다. 시스템은 결제 서비스에 즉시 취소를 요청하고 성공하면 주문을 취소한다.

분석으로 드러난 질문:

  1. 어떤 상담원이 어떤 주문을 취소할 수 있는가?
  2. 전체·부분 취소와 출고 상태별 규칙은 무엇인가?
  3. 결제 응답이 늦거나 성공 응답이 유실되면 주문 상태는 무엇인가?
  4. 같은 버튼을 두 번 누르면 결제 취소가 중복되는가?
  5. “빠르게”, “즉시”의 부하와 수치는 무엇인가?
  6. 주문 변경과 외부 결제를 원자적으로 묶을 수 없는 경계를 어떻게 처리하는가?
  7. 사용자에게 접수·완료·실패 중 무엇을 보여주는가?

개선된 요구 집합:

FR-CAN-02: 시스템은 요청 ID별 취소 접수를 한 번만 생성하고 상태 이력을 저장한다.

11. 자주 틀리는 포인트

  1. 요구사항 확인은 문법·맞춤법 검사다? 업무 의미, 모델, 품질, 실현·검증·추적 가능성을 확인한다.
  2. 인터뷰에서 들은 문장은 바로 확정 요구다? 다른 이해관계자·정책·실측과 분석해 충돌·근거를 확인한다.
  3. 정상 유스케이스만 있으면 충분하다? 대안·예외·권한·중복·복구 흐름이 필요하다.
  4. DFD는 프로그램 호출 순서도다? 데이터의 논리 흐름과 처리·저장·외부 경계를 표현한다.
  5. 화면 필드가 데이터 모델이다? 식별자·관계·카디널리티·상태·이력·제약을 분석해야 한다.
  6. 의사결정표의 모든 조합이 여러 규칙에 걸려도 된다? 우선순위가 없다면 충돌이며 완전성·상호배타성을 확인한다.
  7. 프로토타입이 승인되면 성능·보안도 검증됐다? 주로 흐름·이해 확인이며 다른 품질은 별도 검증한다.
  8. 정확성과 일관성은 같다? 정확성은 실제 필요와 맞는지, 일관성은 요구들끼리 충돌하지 않는지다.
  9. ‘가능하면’, ‘적절히’는 유연한 좋은 요구다? 합격 판단이 달라지는 모호한 표현이다.
  10. 기술적으로 가능하면 실현 가능하다? 일정·비용·법·운영·인력과 외부 제약도 포함한다.
  11. 테스트 케이스는 구현 뒤 만든다? 조기 도출로 요구의 검증 가능성과 경계를 확인할 수 있다.
  12. 검토 회의에서 모든 해결안을 즉시 설계해야 한다? 먼저 결함을 합의·기록하고 수정·재검증한다.
  13. 미결사항을 삭제하면 완료율이 높아진다? 담당·기한·영향과 승인된 위험으로 투명하게 관리한다.
  14. 추적표는 링크를 많이 넣는 문서다? 목표 누락·불필요 구현·변경 영향을 양방향으로 찾는 수단이다.
  15. 기준선은 요구가 영원히 고정된다는 뜻이다? 변경 절차와 영향 분석의 기준 버전이다.
12

12. 확인 문제

문제 1

비즈니스 요구, 사용자 요구, 시스템 기능 요구, 비기능 요구의 차이를 주문 취소 사례로 설명하라.

문제 2

유스케이스의 기본 흐름 외에 사전조건·대안·예외·사후조건을 확인해야 하는 이유를 쓰라.

문제 3

상태 모델과 의사결정표가 각각 찾기 좋은 요구 결함을 설명하라.

문제 4

“시스템은 많은 사용자의 요청을 빠르게 처리한다”의 검증 문제를 지적하고 품질 속성 시나리오로 개선하라.

문제 5

요구사항 검증 기준 중 정확성, 완전성, 일관성, 검증 가능성의 차이를 설명하라.

문제 6

공식 인스펙션의 역할과 개별 사전 검토가 필요한 이유를 쓰라.

문제 7

테스트 케이스 조기 도출이 요구 분석에 주는 이점 세 가지를 쓰라.

문제 8

검증 절차를 계획부터 기준선 승인까지 순서대로 설명하라.

문제 9

정방향 추적과 역방향 추적이 각각 찾는 문제를 설명하라.

문제 10

결제 취소 요청이 중복될 수 있는 요구에서 분석·검증해야 할 항목 다섯 가지를 쓰라.

13

13. 정답과 해설

정답 1

비즈니스 요구는 취소 처리 개선으로 문의·손실을 줄이려는 목표다. 사용자 요구는 상담원이 권한 범위에서 주문을 취소하는 능력이다. 기능 요구는 상태 검증, 중복 방지, 이력 저장과 후속 작업 생성 같은 시스템 행동이다. 비기능 요구는 피크 응답 시간, 감사 누락, 장애 복구 같은 수행 수준과 조건이다.

정답 2

사전조건은 기능이 시작 가능한 상태와 권한을, 대안·예외는 부분 취소·외부 지연·저장 실패 등 정상 밖의 행동을, 사후조건은 성공·실패 뒤 데이터와 관찰 가능한 상태를 정한다. 빠뜨리면 구현마다 다른 해석과 복구 불일치가 생긴다.

정답 3

상태 모델은 허용되지 않은 전이, 도달 불가능·종료되지 않는 상태, 이벤트 순서와 복구 상태 누락을 찾기 좋다. 의사결정표는 여러 조건 조합의 누락, 두 결과가 동시에 적용되는 충돌, 불필요하거나 중복된 조건을 찾기 좋다.

정답 4

“많은”, “빠르게”의 사용자 수·부하·데이터·측정 위치·수치가 없어 판정할 수 없다. 예: “대표 운영 데이터에서 동시 사용자 500명이 15분간 승인된 조회 분포로 요청할 때 주문 조회 p95 2초 이하, 오류율 0.1% 이하”처럼 쓴다.

정답 5

정확성은 실제 업무 필요·규칙과 맞는지, 완전성은 필요한 정상·예외·데이터·품질 조건이 빠지지 않았는지 본다. 일관성은 요구와 모델 사이 용어·수치·행동이 충돌하지 않는지, 검증 가능성은 시험·검토·분석·시연으로 객관적 합격을 판정할 수 있는지 본다.

정답 6

작성자, 진행자, 도메인·기술·시험 검토자와 기록자가 정해진 기준으로 결함을 식별하고 기록한다. 사전 검토를 해야 회의가 문서 낭독에 끝나지 않고 각 관점의 결함을 독립적으로 찾으며 특정 참석자의 설명에 편향되지 않는다.

정답 7

입력·경계·예외와 기대 결과가 없어 테스트를 쓸 수 없는 모호성을 찾는다. 요구가 독립적 검증 단위인지 확인하고, 상태·권한·중복·시간 제한 같은 누락 조건을 발견한다. 수용 기준과 추적 링크를 조기에 만들 수도 있다.

정답 8

대상·참여자·품질 기준과 완료 조건을 계획하고, 검토자가 개별 사전 검토를 한다. 공동 검토로 결함·질문·미결을 합의·기록하고 작성자가 요구·모델·추적을 수정한다. 수정 결과를 재검증하고 잔여 위험을 승인한 뒤 버전·승인 기록을 기준선으로 관리한다.

정답 9

정방향 추적은 업무 목표와 필수 요구가 설계·구현·테스트까지 빠짐없이 반영됐는지 찾는다. 역방향 추적은 구현·테스트·설계 요소가 승인된 요구와 근거를 가지는지 확인해 불필요 기능과 범위 팽창을 찾는다.

정답 10

고유 요청 ID의 범위·수명, 동시·순차 재전송 때 결과, 주문 상태 변경과 후속 작업 생성의 원자성, 외부 성공 응답 유실 시 조회·재시도, 소비자의 멱등성, 최대 재시도·백오프, 감사·추적, 사용자에게 보일 접수·완료 상태를 분석·시험한다.

14. 핵심 요약

  • 요구사항 확인은 자연어 문장의 존재가 아니라 업무 의미·경계·모델·품질·검증·추적 가능성을 확인하는 활동이다.
  • 비즈니스–사용자–시스템 기능–품질–인터페이스–데이터–제약–전환 요구를 수준과 근거로 연결한다.
  • 유스케이스, DFD, 데이터·상태·활동 모델, 의사결정표, 프로토타입과 품질 시나리오를 문제에 맞게 사용한다.
  • 정상 흐름뿐 아니라 대안·예외·권한·중복·시간 제한·복구를 분석한다.
  • 모델끼리 교차 확인해 기능–데이터–상태–권한–인터페이스 불일치를 찾는다.
  • 요구는 정확성·완전성·일관성·명확성·필요성·실현·검증·추적 가능성과 우선순위로 검증한다.
  • 워크스루·인스펙션·체크리스트·프로토타입·기술 검증·조기 테스트 도출을 조합한다.
  • 검증은 계획–사전 검토–공동 검토–수정–재검증–승인·기준선 순서로 수행한다.
  • 결함은 위치·유형·심각도·근거·담당·기한으로 관리하고 미결과 잔여 위험을 숨기지 않는다.
  • 추적성 매트릭스로 목표에서 시험까지 누락과 구현에서 근거까지 범위 팽창을 양방향 확인한다.
