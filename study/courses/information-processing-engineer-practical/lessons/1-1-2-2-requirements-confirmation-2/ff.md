# 1-1-2-2. 요구사항이 응용소프트웨어에 미치는 영향 검토

## 수행 범위와 목표

이 레슨의 정확한 토픽은 **요구사항이 응용소프트웨어에 미치는 영향 검토**와 **요구사항 확인하기의 적용 절차와 판단 기준**이다. 승인된 요구 또는 변경 요청이 기능, 데이터, 인터페이스, 구조, 성능, 보안, 시험, 운영에 어떤 변화를 만드는지 추적하고, 구현 가능성과 우선순위를 판단해 근거 있는 검토 결과를 만드는 실무를 다룬다.

분석모델 자체의 기술적 타당성을 조사하고 추가 의견을 제시하는 일은 다음 레슨 범위다. 여기서는 요구사항 확인 활동 안에서 “이 요구가 응용소프트웨어의 어느 부분에 어떤 영향을 주는가”를 중심으로 수행한다.

학습 목표는 다음과 같다.

1. 요구의 출처와 기준선을 확인하고 영향 대상을 빠짐없이 식별한다.
2. 직접 영향과 전이 영향, 기능 영향과 비기능 영향을 구분한다.
3. 추적표, 영향분석서, 이슈 목록, 변경 요청서 같은 산출물을 작성한다.
4. 가치, 위험, 비용, 일정, 규정, 시험 가능성을 근거로 수용·보완·보류 판단을 제시한다.

## 1. 영향 검토의 의미

요구사항 영향 검토는 문장을 읽고 “개발 가능”이라고 표시하는 일이 아니다. 요구가 바뀌면 연결된 설계, 코드, 데이터, 외부 연계, 시험, 배포, 사용자 문서가 연쇄적으로 달라질 수 있다. 이 연결을 식별하고 영향의 크기와 위험을 설명해야 한다.

예를 들어 “주문 취소는 결제 후 10분 안에만 허용한다”가 “배송 시작 전까지 허용한다”로 바뀌었다고 하자. 화면의 버튼 노출 조건만 고치면 끝나지 않는다. 주문 상태 전이, 결제 취소 연계, 재고 복원, 쿠폰 반환, 감사 이력, 동시 처리, 취소 가능 시간 시험, 고객 안내가 함께 바뀔 수 있다.

    변경 요구 R-17
       ├─ 화면 규칙 UI-04
       ├─ 주문 서비스 SVC-08
       ├─ 상태 모델 DM-03
       ├─ 결제 인터페이스 IF-02
       ├─ 시험 사례 TC-31, TC-32
       └─ 운영·감사 규칙 OP-06

위 도식처럼 요구에서 구현과 검증 산출물까지의 연결을 따라가야 누락을 줄일 수 있다.

## 2. 영향의 주요 관점

### 2.1 기능과 업무 흐름

새 기능, 기존 기능 변경, 삭제 기능을 구분한다. 정상 흐름뿐 아니라 오류, 취소, 재시도, 승인, 권한 부족, 외부 시스템 실패 같은 대체·예외 흐름을 확인한다. 하나의 조건 변경이 다른 상태 전이를 허용하거나 금지하는지도 본다.

### 2.2 데이터

새 속성이나 코드값이 필요한지, 기존 값 의미가 바뀌는지, 널·기본값·유일성·참조 규칙이 달라지는지 확인한다. 과거 데이터에도 새 규칙을 적용할지, 신규 데이터부터 적용할지 결정해야 한다. 스키마 변경뿐 아니라 데이터 이행, 정제, 보존, 삭제, 감사 이력도 영향에 포함한다.

### 2.3 인터페이스

내부 모듈과 외부 시스템 사이 요청·응답 항목, 형식, 코드, 오류, 순서, 제한 시간이 바뀌는지 본다. 기존 소비자가 새 필드를 이해하는지, 필수 필드를 추가하면 하위 호환이 깨지는지, 전환 기간에 구·신 규격을 함께 지원할지 검토한다.

### 2.4 구조와 공통 모듈

변경이 특정 기능 하나에 국한되는지, 인증·알림·결제처럼 여러 기능이 공유하는 모듈에 영향을 주는지 확인한다. 공통 모듈 변경은 편리하지만 영향 범위가 넓다. 임시 조건문을 여러 곳에 복제하면 당장은 빠르더라도 이후 일관성 유지가 어렵다.

### 2.5 성능과 용량

응답 시간, 처리량, 동시 사용자, 배치 시간, 데이터 증가, 네트워크 전송량, 저장 공간에 미치는 영향을 추정한다. “조회 항목 하나 추가”라도 큰 테이블 조인이나 외부 호출을 새로 만들면 영향이 클 수 있다. 평균값만 아니라 최대 부하와 백분위 지연을 고려한다.

### 2.6 보안과 규정

인증·인가, 개인정보 최소 수집, 암호화, 마스킹, 감사, 보존 기간, 동의에 변화가 있는지 확인한다. 민감한 필드를 화면에 추가하면 전송·로그·내보내기·백업까지 노출 경로가 늘어난다. 법적 판단이 필요한 경우 개발자가 임의로 결론 내리지 않고 책임 부서의 확인을 이슈로 남긴다.

### 2.7 시험과 운영

기존 회귀 시험, 새 인수 기준, 시험 데이터, 성능·보안 시험, 배포 순서, 모니터링, 알림, 사용자 교육, 장애 복구 절차를 갱신해야 하는지 확인한다. 구현 코드만 바뀌고 시험·운영 산출물이 그대로면 변경이 완료되었다고 보기 어렵다.

## 3. 요구사항 확인하기의 적용 절차와 판단 기준

### 3.1 1단계: 입력과 기준선 확인

요구사항 명세, 변경 요청, 회의 결정, 계약·규정, 기존 추적표를 수집한다. 검토 대상 버전과 승인 상태를 표시한다. 초안과 승인본을 섞으면 이미 폐기된 문장을 기준으로 분석할 수 있다.

체크 항목:

- 요구에 고유 식별자와 출처가 있는가?
- 현재 기준선과 변경 전·후 문장이 구분되는가?
- 변경 이유와 기대 가치가 설명되어 있는가?
- 결정권자와 검토 기한이 정해져 있는가?

### 3.2 2단계: 요구를 검증 가능한 형태로 정리

행위 주체, 조건, 입력, 처리, 출력, 오류, 품질 기준을 분리한다. “신속하게”, “가능하면”, “사용하기 쉽게” 같은 표현은 판단 기준이 되기 어렵다. 관계자에게 질문해 측정 조건과 예외를 확정하며, 확정되지 않은 내용은 추정으로 숨기지 않고 미결 이슈로 기록한다.

### 3.3 3단계: 직접 영향 추적

요구와 연결된 화면, 기능, 서비스, 데이터, 인터페이스, 시험 사례를 추적표에서 찾는다. 연결이 없다면 산출물 검색, 코드 소유자 인터뷰, 업무 흐름 검토로 보완한다. “추적표에 없으므로 영향 없음”이라고 결론 내리지 않는다.

### 3.4 4단계: 전이 영향 탐색

직접 대상이 의존하거나 이를 사용하는 대상을 한 단계 이상 따라간다. 공통 코드 변경이 여러 기능에 전파되는지, 데이터 코드값 변경이 보고서와 배치에 영향을 주는지 확인한다.

    요구 → 업무 규칙 → 서비스 → 데이터/외부 연계
                   ↓
             화면·배치·보고서
                   ↓
              시험·운영 절차

탐색을 무한히 확장하지 않도록 시스템 경계와 변경 가능한 연결을 기준으로 종료 조건을 정한다.

### 3.5 5단계: 영향도와 위험 평가

각 영향 항목에 규모, 복잡성, 불확실성, 장애 영향, 보안·규정, 되돌리기 난이도를 평가한다. 단순히 상·중·하로 표시하지 말고 근거를 적는다.

| 판단 항목 | 낮은 영향 예 | 높은 영향 예 |
|---|---|---|
| 변경 범위 | 한 화면의 독립 문구 | 공통 상태 모델과 다수 연계 |
| 데이터 | 신규 선택 칼럼 | 대량 이행과 의미 변경 |
| 호환성 | 선택 응답 필드 추가 | 기존 필수 필드 형식 변경 |
| 품질 | 기존 목표 안의 소폭 부하 | 성능·가용성 목표 재설계 |
| 보안 | 공개 정보 표시 | 민감정보 수집·권한 확대 |
| 복구 | 기능 플래그로 즉시 철회 | 비가역 데이터 변환 |

점수 합계만으로 자동 승인하지 않는다. 법규 위반이나 복구 불가처럼 한 가지 치명 요인이 전체 판단을 바꿀 수 있다.

### 3.6 6단계: 대안 비교

요구를 그대로 구현하는 안, 범위를 나누는 안, 기존 기능을 재사용하는 안, 시점을 늦추는 안을 비교한다. 각 대안에 기대 가치, 개발·시험 노력, 위험, 일정, 운영 복잡성, 기술 부채를 기록한다. 불가능하다고만 답하지 말고 어떤 제약 때문에 어려운지와 가능한 대안을 제시한다.

### 3.7 7단계: 검토 결과 합의

결과는 수용, 조건부 수용, 보완 요청, 보류, 반려처럼 조직에서 정의한 상태로 정리할 수 있다. 조건부 수용이면 충족 조건과 확인 책임자를 적는다. 승인자는 비용뿐 아니라 사용자 가치, 위험, 규정과 전체 일정의 균형을 보고 결정한다.

### 3.8 8단계: 산출물과 기준선 갱신

승인된 결과를 요구 명세, 추적표, 영향분석서, 이슈 목록, 일정, 시험 계획에 반영한다. 이전 기준선을 덮어써 변경 이유를 잃지 말고 버전과 결정 이력을 남긴다. 반려된 요청도 이유와 재검토 조건을 기록한다.

## 4. 실무 산출물

### 4.1 영향분석표

| 필드 | 작성 내용 |
|---|---|
| 요구 ID·제목 | 기준선에서 추적 가능한 식별 |
| 변경 전·후 | 의미 차이를 비교 가능한 문장 |
| 변경 이유·가치 | 해결할 문제와 기대 효과 |
| 영향 대상 | 기능, 데이터, 인터페이스, 품질, 시험, 운영 |
| 위험·가정 | 확인된 위험과 검증되지 않은 전제 |
| 대안 | 구현 범위와 장단점 |
| 추정 | 노력·기간 범위와 근거 |
| 결정 | 상태, 승인자, 조건, 일자 |

### 4.2 추적표

요구 ID를 설계 요소, 구현 모듈, 시험 사례, 배포 항목과 연결한다. 양방향으로 살펴보면 요구에 연결되지 않은 구현과 시험되지 않은 요구를 찾을 수 있다.

### 4.3 이슈·결정 기록

미결 질문에는 책임자와 기한을 부여한다. 결정 기록에는 선택지, 선택 이유, 포기한 대안, 재검토 조건을 남긴다. 구두 합의만 있으면 담당자가 바뀔 때 같은 논쟁을 반복한다.

### 4.4 완료 체크리스트

- 모든 exact 요구 문장이 기준선과 일치하는가?
- 기능·데이터·인터페이스·품질·시험·운영 영향을 확인했는가?
- 직접 영향과 전이 영향을 구분했는가?
- 미결 가정에 책임자와 기한이 있는가?
- 비용·일정 추정의 포함 범위가 명확한가?
- 보안·규정 검토가 필요한 항목을 책임 부서가 확인했는가?
- 승인 결과가 추적표와 시험 계획까지 반영되었는가?
- 원복 또는 단계적 전환이 필요한지 판단했는가?

## 5. 구체 업무 시나리오

### 상황

온라인 도서 주문 시스템에서 “회원만 주문할 수 있다”는 요구가 “비회원도 이메일 인증 후 주문할 수 있다”로 변경되었다.

### 영향 분석

1. **기능**: 회원 로그인 외에 비회원 인증, 주문 조회용 검증 흐름이 추가된다.
2. **데이터**: 주문의 고객 식별이 회원번호만 전제로 했는지 확인한다. 이메일을 회원 식별자처럼 재사용하면 중복과 개인정보 문제가 생길 수 있으므로 주문별 비회원 식별 정책을 설계한다.
3. **인터페이스**: 주문·결제·배송 연계가 회원번호 필수인지 확인하고 선택 관계 또는 별도 주문자 식별로 변경한다.
4. **보안**: 인증 코드 유효 기간, 시도 제한, 코드 저장·로그 제외, 주문 조회 권한을 정의한다.
5. **운영**: 인증 메일 지연·실패 지표와 고객 문의 절차가 필요하다.
6. **시험**: 정상 주문, 만료 코드, 반복 시도, 회원 이메일과 동일한 주소, 결제 실패, 주문 조회 권한을 검증한다.

### 판단

기존 주문 테이블의 회원번호를 무리하게 가짜 회원으로 채우는 안은 데이터 의미를 훼손한다. 회원 주문자와 비회원 주문자를 구분하는 명시적 모델, 인증 서비스 재사용 가능성, 외부 연계 호환성을 비교해 조건부 수용안을 제시한다. 개인정보 보존 기간과 조회 인증 방식이 미결이면 책임자와 기한을 정한 뒤 최종 승인한다.

## 6. 안전한 영향 분석 의사코드

다음 의사코드는 자동 승인이 아니라 누락 방지 순서를 표현한다.

    function reviewImpact(requirement):
        assert requirement.id exists
        assert requirement.baselineVersion exists

        direct = trace(requirement.id)
        transitive = expandDependencies(direct, approvedBoundary)
        impacts = classify(direct + transitive,
                           [function, data, interface,
                            quality, security, test, operation])

        issues = findAmbiguities(requirement, impacts)
        risks = assessWithEvidence(impacts)
        alternatives = compareOptions(requirement, risks)

        return reviewReport(impacts, issues, risks, alternatives)

실제 도구로 자동 추적하더라도 결과를 사람이 검토한다. 이름이 같다는 이유만으로 연결하거나, 동적 호출과 외부 운영 절차를 놓칠 수 있기 때문이다.

## 7. 자주 틀리는 함정

1. 변경된 화면만 보고 영향 범위를 끝내지 않는다.
2. 요구 문장이 짧다고 구현 영향도 작다고 단정하지 않는다.
3. 추적표에 연결이 없다는 것을 영향 없음의 증거로 사용하지 않는다.
4. 기능 영향만 보고 성능·보안·운영·시험을 빼먹지 않는다.
5. 데이터 스키마 변경과 데이터 의미 변경을 같은 것으로 보지 않는다.
6. 외부 연계의 선택 필드 추가도 소비자 구현에 따라 영향이 있을 수 있다.
7. 상·중·하 점수만 적고 근거를 생략하지 않는다.
8. 모든 위험을 비용 합계로 상쇄하지 않는다. 규정 위반 같은 중단 조건이 있다.
9. 미결 사항을 개발자 추정으로 확정하지 않는다.
10. 승인 후 요구 명세만 고치고 추적·시험·운영 문서를 그대로 두지 않는다.

## 8. 확인 문제

### 문제 1

요구 영향 검토에서 직접 영향과 전이 영향의 차이는 무엇인가?

**정답과 해설:** 직접 영향은 요구와 바로 연결된 화면·서비스·데이터 같은 대상이고, 전이 영향은 그 대상에 의존하거나 이를 사용하는 보고서·배치·외부 연계 등에 이어지는 영향이다.

### 문제 2

“응답을 빠르게 한다”는 요구를 그대로 영향 분석하기 어려운 이유는 무엇인가?

**정답과 해설:** 대상 기능, 부하, 측정 위치와 목표 시간이 없어 구현·시험 범위를 결정할 수 없기 때문이다. 검증 가능한 기준으로 보완하거나 미결 이슈로 기록한다.

### 문제 3

기존 코드 추적표에 연결된 모듈이 없으면 영향이 없다고 결론 내릴 수 있는가?

**정답과 해설:** 없다. 추적표 자체가 누락되거나 오래되었을 수 있다. 산출물 검색, 의존 관계, 담당자 검토로 보완해야 한다.

### 문제 4

데이터 코드값 추가 시 확인해야 할 영향 세 가지를 쓰시오.

**정답과 해설:** 저장 제약과 기본값, 기존 데이터·보고서의 처리, 외부 인터페이스의 코드 호환성을 확인할 수 있다. 화면 표시와 배치 분기, 시험 데이터도 점검한다.

### 문제 5

조건부 수용 결과에 반드시 기록할 내용은 무엇인가?

**정답과 해설:** 충족해야 할 조건, 확인 책임자, 완료 기한과 검증 방법을 기록한다. 조건이 없으면 사실상 무제한 승인으로 오해될 수 있다.

### 문제 6

보안 영향에서 민감정보 필드 하나를 추가할 때 화면 외에 살펴볼 경로는 무엇인가?

**정답과 해설:** 전송, 로그, 내보내기, 백업, 시험 데이터, 권한과 보존·삭제 경로를 확인한다. 필드가 여러 사본으로 확산되는지도 본다.

### 문제 7

대안 비교에서 개발 노력 외에 확인할 기준 네 가지를 쓰시오.

**정답과 해설:** 사용자 가치, 위험, 일정, 운영 복잡성을 들 수 있다. 규정, 호환성, 복구 가능성, 기술 부채도 중요하다.

### 문제 8

영향 검토가 완료되었다고 판단하기 위한 산출물 갱신 범위는 무엇인가?

**정답과 해설:** 요구 명세뿐 아니라 추적표, 영향분석서, 이슈·결정 기록, 일정, 설계와 시험·운영 계획까지 승인 결과에 맞게 갱신해야 한다.

### 문제 9

점수 합계가 낮으면 어떤 요구든 승인할 수 있는가?

**정답과 해설:** 아니다. 법규 위반, 중대한 보안 위험, 복구 불가능한 데이터 변경처럼 한 가지 치명 요인이 중단 조건이 될 수 있다. 정량 점수와 질적 기준을 함께 본다.

## 9. 핵심 요약

- **요구사항이 응용소프트웨어에 미치는 영향 검토**는 요구에서 기능·데이터·인터페이스·품질·시험·운영으로 이어지는 직접·전이 영향을 찾는 일이다.
- **요구사항 확인하기의 적용 절차와 판단 기준**은 기준선 확인, 검증 가능한 문장 정리, 직접·전이 추적, 위험 평가, 대안 비교, 합의, 산출물 갱신으로 구성한다.
- 추적표는 유용하지만 누락될 수 있으므로 코드·설계·담당자 검토로 보완한다.
- 비용과 일정뿐 아니라 가치, 규정, 보안, 호환성, 복구 가능성을 판단 기준으로 삼는다.
- 영향분석표, 추적표, 이슈·결정 기록, 완료 체크리스트를 남겨 승인 근거와 후속 변경을 추적한다.
- 미결 사항을 숨겨 확정하지 말고 책임자·기한·검증 방법을 부여한다.
