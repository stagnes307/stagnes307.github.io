# 1-1-3-1. 요구사항 도출 기법으로 분석모델 확인 · 분석모델의 기술적 타당성 조사

## 수행 범위와 목표

이 레슨의 정확한 토픽은 **요구사항 도출 기법으로 분석모델 확인**과 **분석모델의 기술적 타당성 조사**이다. 요구 분석 과정에서 만든 업무 흐름, 유스케이스, 도메인·데이터, 상태, 인터페이스 모델이 실제 사용자 업무와 일치하는지 도출 기법으로 확인하고, 목표 환경에서 구현·운영 가능한지 근거를 수집하는 실무를 다룬다.

조사 결과를 바탕으로 개발에 필요한 추가 의견을 공식 제시하고 분석모델 확인 전체 절차를 마감하는 일은 다음 레슨의 주범위다. 여기서는 모델 검증과 기술 타당성 증거 확보에 집중한다.

학습 목표는 다음과 같다.

1. 분석모델의 종류와 모델 사이의 일관성을 확인한다.
2. 인터뷰, 워크숍, 관찰, 문서 분석, 프로토타입을 목적에 맞게 사용한다.
3. 기술, 통합, 데이터, 성능, 보안, 운영, 역량 관점의 타당성을 조사한다.
4. 가정과 사실을 구분하고 실험·측정 결과가 포함된 조사 산출물을 만든다.

## 1. 분석모델이란

분석모델은 구현 기술을 확정하기 전에 업무 요구를 구조화해 표현한 산출물이다. 자연어 요구만으로 드러나지 않는 행위 주체, 상태 변화, 데이터 관계, 경계와 예외를 보여 준다.

| 모델 | 주로 확인하는 내용 | 대표 질문 |
|---|---|---|
| 업무 흐름·활동 모델 | 업무 단계, 분기, 병렬, 책임자 | 누가 어떤 조건에서 다음 단계로 가는가 |
| 유스케이스·사용자 흐름 | 행위자 목표, 정상·대체·예외 흐름 | 실패·취소·권한 부족 흐름이 있는가 |
| 도메인·개념 모델 | 업무 개체, 속성, 관계, 용어 | 같은 용어를 부서마다 다르게 쓰는가 |
| 데이터 모델 | 데이터 단위, 식별, 관계, 생명주기 | 생성·변경·삭제 책임이 명확한가 |
| 상태 모델 | 가능한 상태와 전이 조건 | 금지된 전이나 종료 상태가 누락됐는가 |
| 상호작용·인터페이스 모델 | 시스템·모듈 간 메시지와 순서 | 오류·중복·지연 때 흐름은 무엇인가 |

한 모델만 올바르면 전체가 올바른 것은 아니다. 유스케이스에는 “승인 취소”가 있는데 상태 모델에 승인 상태에서 취소로 가는 전이가 없다면 모델 사이 불일치다. 데이터 모델에 필수 주문자가 있는데 비회원 주문 유스케이스가 있다면 관계와 선택성을 다시 확인해야 한다.

## 2. 분석모델 확인 원칙

### 2.1 요구와 추적 가능해야 한다

각 모델 요소가 어떤 요구를 설명하는지 연결한다. 모델에만 있고 요구 출처가 없는 기능은 불필요 구현일 수 있고, 요구에는 있지만 어떤 모델에도 표현되지 않은 항목은 분석 누락일 수 있다.

### 2.2 이해관계자가 이해할 수 있어야 한다

표기법이 엄밀해도 실제 사용자가 뜻을 이해하지 못하면 확인이 어렵다. 업무 담당자에게는 시나리오, 화면 모형, 용어표처럼 이해하기 쉬운 표현을 함께 제공하고, 기술 모델과의 연결을 유지한다.

### 2.3 정상 흐름만 보지 않는다

입력 오류, 권한 부족, 외부 시스템 시간 초과, 중복 요청, 취소, 재시도, 부분 완료, 복구를 확인한다. 분석모델 결함은 정상 예시보다 경계와 예외에서 잘 드러난다.

### 2.4 관찰 사실과 해석을 구분한다

“현재 담당자는 엑셀에 두 번 입력한다”는 관찰과 “사용자는 이중 입력을 선호한다”는 해석은 다르다. 관찰, 인터뷰 발언, 규정, 분석가 가정을 출처와 함께 구분해야 잘못된 모델을 사실처럼 굳히지 않는다.

## 3. 요구사항 도출 기법으로 분석모델 확인

도출 기법은 새 요구를 찾는 데만 쓰지 않는다. 만들어진 분석모델을 이해관계자와 대조해 누락·오해·충돌을 발견하는 데도 사용한다.

### 3.1 인터뷰

모델의 특정 흐름과 규칙을 업무 전문가에게 질문한다. 일반 질문보다 모델을 짚어 확인한다.

- 이 상태에서 실제 승인자는 누구인가?
- 외부 응답이 오지 않으면 얼마나 기다리고 누가 재처리하는가?
- 주문자와 수령인이 다를 때 어떤 데이터가 필수인가?
- 이 분기는 규정인가, 현재 시스템의 제한인가?

한 명의 답을 조직 전체 규칙으로 일반화하지 않는다. 실제 사용자, 관리자, 운영자, 보안·감사 담당자의 관점을 교차 확인하고 회의 기록과 규정을 대조한다.

### 3.2 워크숍

서로 다른 부서가 같은 모델을 보며 경계와 충돌을 합의하는 데 유용하다. 화면에 모델을 표시하고 시나리오를 처음부터 끝까지 따라가며 각 단계의 책임자, 입력·출력, 예외를 확인한다.

진행자는 강한 발언자가 결론을 독점하지 않도록 역할별 의견을 수집한다. 합의되지 않은 항목은 즉석에서 모호한 문장으로 덮지 말고 이슈, 선택지, 결정권자, 기한으로 남긴다.

### 3.3 관찰

사용자의 실제 업무 수행을 관찰해 모델과 비교한다. 인터뷰에서는 생략한 임시 메모, 대기, 우회 승인, 여러 시스템 사이 복사 같은 암묵 절차가 드러날 수 있다.

관찰 기간에 드물게 발생하는 월말·장애·취소 상황은 보이지 않을 수 있다. 관찰 결과를 표준 절차로 단정하지 말고 문서와 인터뷰로 보완한다. 개인정보가 보이는 업무에서는 관찰 범위와 기록 방식을 승인받고 민감정보를 수집하지 않는다.

### 3.4 문서 분석

업무 규정, 양식, 기존 인터페이스 명세, 장애 기록, 사용자 안내와 모델을 대조한다. 날짜·버전·승인 상태를 확인하지 않으면 폐기된 규정을 근거로 모델을 고칠 수 있다. 문서와 실제 업무가 다르면 어느 쪽이 권위 있는지 책임자에게 확인한다.

### 3.5 설문

많은 사용자에게 역할별 빈도, 불편, 우선순위를 정형적으로 확인할 수 있다. 그러나 선택지에 없는 예외와 이유를 놓칠 수 있으므로 자유 응답이나 후속 인터뷰를 병행한다. 응답 수가 많다고 표본 편향이 사라지는 것은 아니다.

### 3.6 프로토타이핑과 시나리오 워크스루

화면 흐름이나 입력 규칙이 불명확할 때 실행 가능한 모형 또는 저충실도 화면을 보여 주며 모델을 확인한다. 사용자가 “완성된 기능”으로 오해하지 않도록 검증 목적, 구현하지 않은 품질, 폐기 여부를 알린다.

시나리오 워크스루는 구체 사례를 모델에 통과시키는 방식이다.

    사례: 재고 1개인 상품을 두 사용자가 동시에 주문
       1. 두 요청은 어느 상태에서 경쟁하는가?
       2. 재고 확보 시점은 언제인가?
       3. 한 요청이 결제 실패하면 재고는 언제 복원되는가?
       4. 중복 결제 요청을 어떻게 식별하는가?

정상 사례뿐 아니라 경계값, 동시성, 실패 사례를 사용한다.

## 4. 모델별 확인 체크리스트

### 4.1 업무·유스케이스 모델

- 행위자와 목표가 실제 조직 역할과 일치하는가?
- 시작 조건과 종료 조건이 명확한가?
- 정상·대체·예외 흐름이 연결되는가?
- 수동 처리와 외부 시스템 활동이 경계 밖으로 숨겨지지 않았는가?
- 기능 요구와 비기능 제약이 추적되는가?

### 4.2 도메인·데이터 모델

- 용어 정의가 중복되거나 서로 다른 의미로 사용되지 않는가?
- 개체의 식별과 생명주기가 업무 규칙에 맞는가?
- 관계의 수와 선택성이 실제 사례를 표현하는가?
- 계산값, 이력값, 현재값의 의미가 구분되는가?
- 개인정보와 보존·삭제 책임이 표시되는가?

### 4.3 상태 모델

- 모든 상태에 진입·종료 경로가 있는가?
- 같은 사건이 상태에 따라 다른 결과를 내는지 정의했는가?
- 금지 전이와 되돌림·취소 조건이 있는가?
- 외부 실패나 시간 경과로 발생하는 전이가 있는가?
- 최종 상태 이후 허용되는 활동이 명확한가?

### 4.4 인터페이스·상호작용 모델

- 발신자·수신자와 호출 순서가 일치하는가?
- 메시지 식별, 중복, 순서 변경, 시간 초과를 다루는가?
- 오류 코드와 재시도 책임이 명확한가?
- 데이터 항목의 형식, 필수성, 민감도가 정의됐는가?
- 구·신 버전의 호환과 전환 흐름을 고려했는가?

## 5. 분석모델의 기술적 타당성 조사

기술적 타당성은 “사용하려는 기술이 존재한다”는 확인이 아니다. 목표 부하와 품질, 조직 제약 안에서 모델을 구현하고 운영할 수 있는지 증거로 판단하는 활동이다.

### 5.1 기술·플랫폼 적합성

목표 운영체제, 런타임, 데이터 저장소, 브라우저·장치, 배포 환경이 필요한 기능을 지원하는지 확인한다. 지원 버전과 종료 일정, 공급자 의존, 라이선스, 기술 표준을 조사한다. 개인 개발환경에서 동작했다는 사실만으로 운영 지원성을 증명하지 않는다.

### 5.2 연계 가능성

외부 시스템의 실제 인터페이스, 인증, 호출 한도, 응답 시간, 장애 정책, 시험 환경을 확인한다. 문서에 API가 있어도 필요한 데이터와 거래 일관성을 제공하지 않을 수 있다. 외부 담당자와 계약·운영 시간을 확인하고 모의 응답만으로 모든 위험을 닫지 않는다.

### 5.3 데이터 타당성

필요 데이터가 실제로 존재하고 품질과 사용 권한이 있는지 확인한다. 식별자 매핑, 누락률, 중복, 시점, 보존 기간, 데이터량과 증가율을 조사한다. 모델이 가정한 실시간 데이터가 실제로는 하루 한 번만 제공된다면 요구 또는 구조 조정이 필요하다.

### 5.4 성능·확장성

예상 동시 사용자, 초당 요청, 데이터량, 배치 창, 응답 목표를 기준으로 병목 후보를 찾는다. 간단한 프로토타입과 부하 시험으로 핵심 경로를 측정하되 운영과 다른 작은 표본 결과를 과장하지 않는다.

측정에는 입력 조건과 환경을 함께 기록한다.

| 항목 | 기록 예 |
|---|---|
| 데이터 규모 | 행 수, 평균·최대 크기, 분포 |
| 부하 | 동시 사용자, 요청률, 읽기·쓰기 비율 |
| 환경 | CPU, 메모리, 네트워크, 소프트웨어 버전 |
| 결과 | 평균·백분위 응답, 처리량, 오류율, 자원 |
| 한계 | 모의 외부 서비스, 캐시 상태, 미구현 기능 |

### 5.5 보안·규정

인증, 권한, 개인정보, 암호화, 감사, 보존과 삭제 요구를 목표 기술로 충족 가능한지 조사한다. 기능 시제품이 보안 통제를 생략했다면 타당성 결과에 명시한다. 법적 해석은 승인된 책임 부서의 확인을 받는다.

### 5.6 운영·복구 가능성

배포, 설정, 모니터링, 로그, 백업·복원, 장애 전환, 데이터 재처리, 버전 업그레이드를 수행할 수 있는지 확인한다. 운영자가 관찰할 지표와 복구 절차가 없는 기술은 기능이 동작해도 운영 타당성이 낮다.

### 5.7 조직 역량과 일정

팀의 기술 경험, 학습 시간, 전문가 확보, 지원 계약, 개발·시험 환경 준비 기간을 조사한다. 새로운 기술이 나쁘다는 뜻은 아니다. 필요한 학습과 검증 시간을 숨기지 않고 타당성 가정에 반영한다.

## 6. 타당성 조사 절차

1. **검증 질문 정의**: 모델에서 실패 위험이 큰 가정과 품질 목표를 질문으로 바꾼다.
2. **수용 기준 설정**: 응답 시간, 데이터 정확도, 호환 범위처럼 통과·실패를 판단할 기준을 먼저 정한다.
3. **증거 계획**: 공식 문서, 담당자 확인, 데이터 프로파일, 시제품, 부하 시험 중 어떤 증거가 필요한지 정한다.
4. **최소 실험 수행**: 위험을 검증하는 데 필요한 최소 범위만 구현한다. 운영 제품 전체를 시제품으로 만들지 않는다.
5. **결과 기록**: 환경, 입력, 절차, 원시 결과, 한계, 재현 방법을 남긴다.
6. **가정 갱신**: 통과·실패·미확인으로 구분하고 분석모델의 영향을 표시한다.
7. **교차 검토**: 분석가, 개발자, 시험·보안·운영 담당자가 증거와 해석을 검토한다.

## 7. 기술 검증 의사코드

    for each assumption in analysisModel.highRiskAssumptions:
        question = makeTestableQuestion(assumption)
        criterion = defineAcceptanceCriterion(question)
        evidence = collectEvidence(question,
                    [officialDocument, dataProfile,
                     prototype, measurement, ownerConfirmation])

        if evidence satisfies criterion:
            mark(assumption, "확인")
        else if evidence contradicts criterion:
            mark(assumption, "부적합")
        else:
            mark(assumption, "미확인")

        record(environment, inputs, result, limitation)

“미확인”을 “문제없음”으로 처리하지 않는다. 일정상 지금 확인할 수 없다면 남은 위험, 확인 책임자와 결정 기한을 기록한다.

## 8. 구체 업무 시나리오

### 상황

지역 도서관 분석모델은 사용자가 모바일에서 책 표지를 촬영하면 2초 안에 도서를 식별하고 소장·대출 가능 여부를 보여 주도록 설계되었다. 외부 이미지 인식 서비스와 도서관 보유 데이터가 필요하다.

### 모델 확인

1. 사서 인터뷰로 한 책에 여러 판본·ISBN이 있는 경우를 확인한다.
2. 실제 대출 업무를 관찰해 소장 정보가 지점별·권별로 관리됨을 확인한다.
3. 화면 프로토타입으로 인식 실패, 여러 후보, 카메라 권한 거부 흐름을 확인한다.
4. 상태 모델에 검색 중, 후보 선택, 결과 없음, 외부 서비스 실패 상태를 추가로 확인한다.

### 기술 타당성 조사

- 샘플 표지에 대해 인식 정확도와 응답 분포를 측정한다.
- 외부 서비스의 호출 한도, 데이터 사용 조건, 장애·재시도 정책을 확인한다.
- 도서 보유 데이터의 갱신 주기와 ISBN 누락률을 프로파일링한다.
- 모바일 네트워크 지연을 포함해 2초 기준을 측정한다.
- 촬영 이미지 보존 여부, 전송 암호화, 로그 수집 범위를 보안 담당자와 확인한다.

성공한 표지 몇 장만으로 타당하다고 결론 내리지 않는다. 빛 반사, 오래된 책, 여러 언어, 네트워크 지연 등 대표 분포와 실패 조건을 포함한다.

## 9. 산출물과 완료 체크리스트

주요 산출물은 모델 검토표, 요구-모델 추적표, 인터뷰·워크숍 기록, 기술 타당성 조사서, 실험 결과, 가정·이슈 목록이다.

- 모델 요소가 요구 ID와 연결되어 있는가?
- 용어·행위자·상태·데이터가 모델 사이에 일관적인가?
- 정상·예외·동시성·시간 경과 사례를 확인했는가?
- 도출 기법별 참여자와 근거를 기록했는가?
- 기술 검증 질문과 수용 기준을 실험 전에 정했는가?
- 환경·데이터·버전·입력을 기록해 결과를 재현할 수 있는가?
- 성능, 보안, 운영, 역량을 기능 가능성과 함께 조사했는가?
- 사실·가정·미확인 항목을 구분했는가?
- 시제품의 미구현 범위와 결과 한계를 적었는가?
- 분석모델에서 영향받는 요소를 표시했는가?

## 10. 자주 틀리는 함정

1. 요구 도출 기법은 새 요구를 찾을 때만 쓴다고 생각하지 않는다.
2. 모델 표기법이 문법적으로 맞는 것과 업무가 맞는 것을 구분한다.
3. 한 명의 인터뷰 답을 조직 전체 규칙으로 일반화하지 않는다.
4. 현재 업무의 우회 절차를 반드시 유지할 요구로 오해하지 않는다.
5. 화면 프로토타입으로 성능·보안·복구까지 검증되었다고 보지 않는다.
6. API 문서가 있다는 사실만으로 필요한 데이터와 서비스 수준을 보장한다고 단정하지 않는다.
7. 평균 응답 시간만 보고 최대 부하 타당성을 판단하지 않는다.
8. 시험 환경의 작은 데이터 결과를 운영 규모로 단순 확대하지 않는다.
9. 실험에서 확인하지 못한 가정을 통과로 표시하지 않는다.
10. 새 기술의 학습·운영 비용을 기능 시연 성공 뒤에 숨기지 않는다.

## 11. 확인 문제

### 문제 1

분석모델을 요구사항 도출 기법으로 다시 확인하는 이유는 무엇인가?

**정답과 해설:** 자연어 요구를 모델로 변환하며 생긴 누락·오해를 실제 사용자, 업무, 문서와 대조하기 위해서다. 도출 기법은 모델 검증에도 사용할 수 있다.

### 문제 2

유스케이스와 상태 모델 사이 불일치의 예를 하나 드시오.

**정답과 해설:** 유스케이스에는 승인 취소가 있지만 상태 모델에는 승인 상태에서 취소 상태로 가는 전이가 없는 경우다. 두 모델과 원래 요구를 함께 확인한다.

### 문제 3

관찰만으로 드문 장애 업무를 확인하기 어려운 이유와 보완 방법은 무엇인가?

**정답과 해설:** 관찰 기간에 월말·장애 같은 사건이 발생하지 않을 수 있다. 장애 기록, 규정, 인터뷰, 시나리오 워크스루로 보완한다.

### 문제 4

프로토타입의 기술 타당성 결과에 반드시 기록해야 할 한계 두 가지를 쓰시오.

**정답과 해설:** 생략한 기능·품질 통제와 실제 운영과 다른 데이터·환경을 기록한다. 모의 외부 서비스, 작은 부하, 임시 보안도 명시해야 한다.

### 문제 5

기술 타당성에서 데이터 존재 여부 외에 확인할 항목 네 가지는 무엇인가?

**정답과 해설:** 품질, 사용 권한, 갱신 시점, 데이터량을 들 수 있다. 식별자 매핑, 누락·중복, 보존 기간도 확인한다.

### 문제 6

성능 시험 전에 수용 기준을 정해야 하는 이유는 무엇인가?

**정답과 해설:** 결과를 본 뒤 유리한 기준으로 바꾸는 편향을 줄이고, 어떤 부하와 지표가 통과 조건인지 관계자가 같은 뜻으로 판단하기 위해서다.

### 문제 7

기능 시제품이 성공해도 운영 타당성이 없을 수 있는 이유는 무엇인가?

**정답과 해설:** 배포, 관찰, 백업·복원, 장애 대응, 업그레이드 절차와 운영 역량이 없을 수 있기 때문이다. 기능 가능성과 운영 가능성을 구분한다.

### 문제 8

타당성 조사 결과의 세 가지 상태는 어떻게 구분할 수 있는가?

**정답과 해설:** 수용 기준을 충족하면 확인, 증거가 기준과 모순되면 부적합, 증거가 부족하면 미확인으로 구분한다. 미확인에는 책임자와 기한을 둔다.

### 문제 9

분석모델 검토에 실제 사용자 외에 운영·보안 담당자가 필요한 이유는 무엇인가?

**정답과 해설:** 사용자는 배포·복구·감사·권한 같은 운영 제약을 모두 알지 못할 수 있다. 여러 책임자의 관점을 합쳐 전체 생명주기를 확인한다.

## 12. 핵심 요약

- **요구사항 도출 기법으로 분석모델 확인**은 인터뷰, 워크숍, 관찰, 문서 분석, 프로토타입으로 모델을 실제 업무와 대조하는 활동이다.
- 분석모델은 요구와 추적되고, 모델 사이에서 용어·상태·데이터·흐름이 일관되어야 한다.
- 정상 흐름뿐 아니라 예외, 동시성, 시간 경과, 외부 실패 시나리오를 확인한다.
- **분석모델의 기술적 타당성 조사**는 기술·연계·데이터·성능·보안·운영·조직 역량을 증거로 검증한다.
- 검증 질문과 수용 기준을 먼저 정하고 공식 문서, 프로파일, 시제품, 측정, 책임자 확인을 수집한다.
- 실험 환경과 한계를 기록하고 결과를 확인·부적합·미확인으로 구분한다.
