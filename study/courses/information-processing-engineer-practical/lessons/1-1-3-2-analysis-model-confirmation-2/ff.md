# 1-1-3-2. 개발에 필요한 추가 의견 제시

## 수행 범위와 목표

이 레슨의 정확한 토픽은 **개발에 필요한 추가 의견 제시**와 **분석모델 확인하기의 적용 절차와 판단 기준**이다. 검토와 기술 타당성 조사에서 발견된 누락·모순·위험을 개발팀이 실행할 수 있는 의견으로 바꾸고, 관계자 합의와 모델 기준선 반영까지 완료하는 실무를 다룬다.

이전 레슨에서 다룬 도출 기법별 조사와 기술 실험을 반복 설명하지 않는다. 여기서는 이미 수집된 사실과 미확인 항목을 입력으로 받아, 구체적인 선택지·영향·우선순위·수용 기준을 갖춘 의견을 제시하는 데 초점을 둔다.

학습 목표는 다음과 같다.

1. 단순 지적과 실행 가능한 개발 의견을 구분한다.
2. 결함, 누락, 개선, 위험, 질의, 의사결정 항목을 분류한다.
3. 대안별 가치·영향·위험·검증 기준을 비교해 권고안을 작성한다.
4. 모델 검토부터 합의·기준선 갱신까지 분석모델 확인 절차를 수행한다.

## 1. 추가 의견의 의미

**개발에 필요한 추가 의견 제시**는 “모델이 이상하다”라는 감상을 전달하는 일이 아니다. 어떤 근거에서 어떤 문제가 발견되었고, 개발·시험·운영에 어떤 영향이 있으며, 어떤 대안과 판단이 필요한지 구조화하는 활동이다.

좋은 의견은 다음 질문에 답한다.

- 무엇이 발견되었는가?
- 어느 요구·모델 요소와 연결되는가?
- 사실, 가정, 해석 중 무엇인가?
- 그대로 두면 어떤 문제가 생기는가?
- 가능한 대안은 무엇인가?
- 누구의 결정이 언제까지 필요한가?
- 수정되었다고 판단할 수용 기준은 무엇인가?

“예외 처리를 보완하세요”보다 “결제 승인 후 주문 저장이 실패할 때 승인 취소 또는 재처리 책임이 모델에 없다. 중복 결제 방지 키와 보상 흐름을 상태·상호작용 모델에 추가하고, 동일 요청을 두 번 보내도 한 건만 처리되는 시험으로 확인한다”가 실행 가능성이 높다.

## 2. 의견 항목 분류

| 유형 | 의미 | 처리 예 |
|---|---|---|
| 결함 | 모델이 승인 요구 또는 업무 규칙과 모순 | 상태 전이 수정 후 재검토 |
| 누락 | 필요한 흐름·데이터·품질 기준이 없음 | 요구 출처 확인 후 모델 추가 |
| 모호성 | 여러 해석이 가능해 구현 기준이 없음 | 결정 질문과 선택지 제시 |
| 위험 | 아직 실패하지 않았지만 가능성과 영향이 큼 | 검증·완화·수용 계획 지정 |
| 개선 | 현재도 가능하지만 단순화·품질 향상 여지 | 가치와 비용을 비교해 채택 |
| 질의 | 분석자가 결정할 권한이 없는 미확인 사항 | 결정권자·기한 지정 |
| 의사결정 | 대안 중 공식 선택이 필요한 항목 | 결정 기록과 근거 보존 |

모든 의견을 결함으로 표시하면 우선순위가 왜곡되고 관계자의 방어적 반응을 높인다. 반대로 명백한 요구 모순을 “개선 제안”으로 낮추면 필수 수정이 선택 사항처럼 보인다. 분류 기준을 팀이 공유한다.

## 3. 실행 가능한 의견의 구성

### 3.1 식별과 추적

각 항목에 고유 ID를 부여하고 요구 ID, 모델 종류, 요소, 모델 버전을 연결한다. “주문 모델 수정”처럼 넓게 쓰지 않고 “상태 모델 SM-02의 결제완료→취소 전이 조건”처럼 위치를 특정한다.

### 3.2 근거

승인 요구, 업무 규정, 인터뷰 합의, 데이터 프로파일, 기술 시험 결과처럼 확인 가능한 출처를 기록한다. 개인 선호는 근거와 분리한다. 문서 출처는 버전과 날짜를 남긴다.

### 3.3 영향

미수정 시 기능 오류, 데이터 불일치, 보안 노출, 성능 저하, 일정 재작업, 운영 복구 실패 중 어떤 영향이 있는지 설명한다. 막연히 “위험함”이라고 쓰지 않고 발생 조건과 피해 범위를 적는다.

### 3.4 대안과 권고

가능한 대안이 둘 이상이면 장단점을 비교한다. 권고안은 한 대안을 선택한 이유와 포기한 이익을 설명한다. 선택권이 없는 규정 준수 사항은 대안처럼 꾸미지 말고 필수 조건과 가능한 구현 방식을 구분한다.

### 3.5 수용 기준

의견이 해결되었다고 판정할 조건을 적는다. 모델 요소 추가, 관계자 승인, 특정 시험 통과, 성능 기준 충족처럼 관찰 가능한 기준이어야 한다. “적절히 반영”은 수용 기준이 아니다.

### 3.6 소유자와 기한

의견 작성자가 모든 문제의 해결자일 필요는 없다. 업무 결정은 제품 책임자, 보안 판단은 보안 책임자, 외부 규격은 연계 담당자처럼 권한 있는 소유자를 지정한다. 기한은 해당 모델을 사용하는 설계·구현 일정 앞에 둔다.

## 5. 우선순위와 판단 기준

의견 우선순위는 목소리가 큰 사람이나 작성 순서로 정하지 않는다. 다음 요소를 함께 본다.

| 기준 | 질문 |
|---|---|
| 요구 필수성 | 법·계약·핵심 업무 목표에 직접 연결되는가 |
| 영향 크기 | 오류가 발생하면 사용자·데이터·재무에 미치는 피해는 |
| 발생 가능성 | 일반 흐름인가 드문 경계 상황인가 |
| 발견 시점 비용 | 지금 수정하지 않으면 설계·코드·이행 재작업이 커지는가 |
| 확산 범위 | 공통 모델과 여러 모듈에 영향을 주는가 |
| 복구 가능성 | 배포 후 쉽게 되돌리거나 데이터를 재구축할 수 있는가 |
| 불확실성 | 핵심 가정에 증거가 부족한가 |

심각도와 처리 우선순위를 구분한다. 매우 심각하지만 다음 달 외부 결정 전에는 처리할 수 없는 항목이 있을 수 있고, 영향은 낮지만 바로 고칠 수 있어 현재 모델 승인 전에 처리하는 항목도 있다. 미룬 항목에는 임시 통제와 재검토 시점을 둔다.

## 6. 분석모델 확인하기의 적용 절차와 판단 기준

### 6.1 1단계: 검토 계획 수립

검토 대상 모델과 버전, 연결 요구 기준선, 참여자, 완료 조건, 일정, 기록 방식을 정한다. 한 번에 전체 시스템을 검토하기보다 업무 흐름이나 모델 묶음별로 나눠 관계자가 집중할 수 있게 한다.

완료 조건 예:

- 필수 요구가 모델 요소로 추적된다.
- 높은 심각도 결함이 모두 해결되거나 승인된 위험으로 처리된다.
- 미결 항목에 소유자·기한이 있다.
- 모델 사이 모순이 해소된다.
- 승인자가 기준선 사용을 허가한다.

### 6.2 2단계: 입력 건전성 점검

요구 명세와 모델의 최신 승인 버전, 용어집, 규정, 인터페이스 자료, 이전 의견 상태를 확인한다. 파일명이 최신처럼 보여도 승인 이력이 없으면 기준이 될 수 없다. 모델 작성 도구가 달라도 공통 식별자와 버전을 유지한다.

### 6.3 3단계: 요구-모델 추적과 일관성 검토

요구가 업무 흐름, 데이터, 상태, 인터페이스 어디에 표현되는지 확인하고 역방향으로 모델 요소의 요구 출처도 찾는다. 모델 사이에서 같은 용어·식별자·상태·수량 관계가 일치하는지 검토한다.

### 6.4 4단계: 조사 결과 통합

이전 단계에서 얻은 인터뷰, 워크숍, 관찰, 데이터 조사, 기술 검증 결과를 항목별로 통합한다. 같은 문제의 중복 보고를 묶되 서로 다른 원인을 하나로 축약하지 않는다. 사실과 가정, 미확인을 표시한다.

### 6.5 5단계: 의견 작성과 내부 검토

각 발견을 유형, 근거, 영향, 대안, 권고, 수용 기준으로 작성한다. 개발자, 시험, 데이터, 보안, 운영 관점에서 실행 가능성과 누락을 교차 검토한다. 의견 문장이 특정 사람을 비난하지 않고 산출물과 위험에 초점을 두는지도 본다.

### 6.6 6단계: 관계자 협의와 결정

업무 의미는 업무 책임자, 기술 선택은 기술 책임자, 규정은 담당 책임자가 결정한다. 회의에서는 의견별 상태를 해결, 채택, 기각, 위험 수용, 보류로 정하고 근거를 남긴다. 합의가 안 되면 의사결정 경로와 기한을 적용한다.

### 6.7 7단계: 모델 수정과 재확인

승인된 의견을 모델에 반영하고 연결된 모델·추적표·용어집도 갱신한다. 수정된 부분만 보는 국소 재확인과 주변 영향 회귀 검토를 함께 수행한다. 예를 들어 관계의 선택성을 바꾸면 화면 입력과 인터페이스 필수 항목도 다시 본다.

### 6.8 8단계: 기준선 승인과 배포

완료 조건을 만족하면 모델 버전, 승인자, 결정일을 기록하고 읽기 가능한 위치에 배포한다. 이전 버전을 삭제하지 않고 변경 이력을 보존하며, 설계·구현팀이 사용할 기준 버전을 명확히 알린다.

### 6.9 9단계: 미결 위험 추적

기준선이 승인되어도 외부 계약 대기, 대용량 시험 미완료 같은 위험이 남을 수 있다. 소유자, 확인 시점, 임시 가정, 영향받는 모델을 위험 목록에 두고 기한 전에 재검토한다.

상태 이름은 조직에 맞게 정할 수 있지만 누가 다음 행동을 해야 하는지, 언제 닫히는지가 명확해야 한다.

## 8. 구체 업무 시나리오

### 상황

병원 예약 분석모델은 환자가 원하는 의사와 시간을 선택하면 즉시 예약 확정 상태가 된다고 표현한다. 검토 자료에는 일부 진료가 사전 문진 승인 후에만 확정된다는 규칙, 외부 검사 결과가 늦게 도착할 수 있다는 사실이 있다.

### 발견과 의견

1. **누락**: 예약대기 상태와 승인 주체가 상태 모델에 없다.
2. **모호성**: 검사 결과를 얼마나 기다리는지 기준이 없다.
3. **위험**: 즉시 확정 알림을 보내면 승인 전 예약으로 오해할 수 있다.
4. **데이터 영향**: 확정시각과 접수시각을 하나의 필드로 표현해 의미가 섞인다.

### 대안

- A안: 모든 해당 예약을 대기로 만들고 승인 후 확정한다. 의미는 단순하지만 즉시 확정 가능한 환자도 대기한다.
- B안: 진료 유형과 문진 결과에 따라 즉시 확정 또는 승인 대기로 분기한다. 사용자 경험은 좋아지지만 규칙과 시험 조합이 늘어난다.

### 권고와 수용 기준

업무 규칙이 진료 유형별로 명확하고 변경 책임자가 있다면 B안을 권고할 수 있다. 수용 기준은 상태 모델에 대기·확정·반려·만료 전이와 주체가 있고, 알림 시점과 접수·확정 시각이 분리되며, 정상·만료·외부 지연 시나리오가 승인되는 것이다. 의료 규정 해석은 개발팀이 임의로 확정하지 않고 책임 부서의 결정을 받는다.

## 9. 산출물과 완료 체크리스트

주요 산출물:

- 분석모델 확인 계획
- 요구-모델 추적표
- 모델별 검토표
- 통합 의견·이슈 목록
- 대안 비교표와 결정 기록
- 수정 모델과 변경 이력
- 재확인 결과
- 승인된 모델 기준선 및 잔여 위험 목록

완료 체크리스트:

- 의견마다 ID, 대상 모델·버전, 근거가 있는가?
- 결함·누락·위험·질의가 정확히 분류되었는가?
- 영향과 대안, 권고 이유, 수용 기준이 있는가?
- 결정권자와 처리 기한이 지정되었는가?
- 승인 의견이 모든 연결 모델과 추적표에 반영되었는가?
- 수정 후 국소 확인과 주변 회귀 검토를 했는가?
- 높은 심각도 항목이 닫히거나 명시적으로 위험 수용되었는가?
- 미확인 항목을 통과로 처리하지 않았는가?
- 개발·시험팀이 사용할 기준선 버전이 명확한가?

## 10. 안전한 의견 처리 의사코드

    for finding in consolidatedFindings:
        item = classify(finding)
        item.evidence = linkEvidence(finding)
        item.impact = describeImpact(finding)
        item.options = identifyFeasibleOptions(finding)
        item.acceptance = defineObservableAcceptance(finding)
        item.owner = assignDecisionOwner(finding)

        decision = reviewWithAuthorizedStakeholders(item)
        recordDecision(item.id, decision, rationale)

        if decision requires modelChange:
            updateLinkedModels(item)
            recheckChangedAndAdjacentElements(item)

    approveBaselineOnlyIf(completionCriteriaSatisfied)

자동화는 항목 누락을 줄일 수 있지만 권한 있는 사람의 업무·규정 결정을 대신하지 않는다.

## 11. 자주 틀리는 함정

1. 추가 의견을 취향이나 코딩 방식 선호로 작성하지 않는다.
2. “보완 필요”만 쓰고 대상·근거·수용 기준을 생략하지 않는다.
3. 모든 발견을 같은 심각도로 분류하지 않는다.
4. 대안 없이 불가능하다고만 통보하지 않는다.
5. 필수 규정과 선택 가능한 개선안을 같은 방식으로 협상하지 않는다.
6. 회의에서 구두 합의한 뒤 모델과 결정 기록을 갱신하지 않는 실수를 피한다.
7. 모델 한 장 수정 후 연결된 상태·데이터·인터페이스 모델을 놓치지 않는다.
8. 기준선 승인을 모든 위험이 사라졌다는 뜻으로 해석하지 않는다.
9. 기각된 의견도 이유와 재검토 조건을 보존한다.
10. 분석가가 업무·보안 책임자의 결정을 대신하지 않는다.

## 12. 확인 문제

### 문제 1

실행 가능한 추가 의견이 단순 지적과 다른 점은 무엇인가?

**정답과 해설:** 대상과 근거, 미수정 영향, 대안, 소유자, 기한, 수용 기준을 포함해 다음 행동과 완료 조건을 알 수 있다는 점이다.

### 문제 2

명백히 승인 요구와 모순되는 모델 요소를 “개선”으로 분류하면 안 되는 이유는 무엇인가?

**정답과 해설:** 선택 사항처럼 보여 필수 수정의 우선순위가 낮아질 수 있다. 요구 모순은 결함으로 분류하고 해결 또는 공식적인 요구 변경이 필요하다.

### 문제 3

심각도와 처리 우선순위를 구분해야 하는 이유는 무엇인가?

**정답과 해설:** 피해 크기와 실제 처리 순서는 자원, 외부 결정, 선행 조건에 따라 다를 수 있기 때문이다. 미룬 고심각도 항목에는 임시 통제와 기한을 둔다.

### 문제 4

분석모델 확인 완료 조건 네 가지를 쓰시오.

**정답과 해설:** 필수 요구 추적, 높은 심각도 결함 처리, 모델 사이 일관성, 미결 항목의 소유자·기한 지정을 들 수 있다. 승인자의 기준선 승인도 필요하다.

### 문제 5

모델 수정 후 재확인에서 주변 요소까지 봐야 하는 이유는 무엇인가?

**정답과 해설:** 관계 선택성이나 상태 전이 하나의 변경이 화면 필수값, 인터페이스, 시험과 다른 모델에 전파될 수 있기 때문이다.

### 문제 6

의견의 수용 기준으로 “적절히 반영”이 부적절한 이유는 무엇인가?

**정답과 해설:** 사람마다 해석이 달라 해결 여부를 객관적으로 판정할 수 없다. 어떤 모델 요소와 시험·승인이 필요한지 관찰 가능한 조건을 적어야 한다.

### 문제 7

기준선 승인 후에도 잔여 위험 목록이 필요한 이유는 무엇인가?

**정답과 해설:** 외부 결정이나 대규모 시험처럼 승인 시점에 확인할 수 없는 가정이 남을 수 있다. 소유자와 재검토 시점을 두어 후속 설계가 잘못된 전제에 의존하지 않게 한다.

### 문제 8

분석모델 의견의 근거로 사용할 수 있는 자료 세 가지를 쓰시오.

**정답과 해설:** 승인 요구, 업무 규정, 데이터·성능 조사 결과를 들 수 있다. 관계자 합의 기록, 외부 인터페이스 명세도 근거가 된다.

### 문제 9

기각된 의견의 기록을 지우면 안 되는 이유는 무엇인가?

**정답과 해설:** 같은 쟁점을 반복 검토하게 되고, 당시의 가정이 바뀌었을 때 재검토 근거를 잃기 때문이다. 기각 이유와 조건을 보존한다.

## 13. 핵심 요약

- **개발에 필요한 추가 의견 제시**는 발견을 대상·근거·영향·대안·수용 기준·소유자와 연결하는 활동이다.
- 의견은 결함, 누락, 모호성, 위험, 개선, 질의, 의사결정으로 구분해 실제 중요도를 드러낸다.
- **분석모델 확인하기의 적용 절차와 판단 기준**은 계획, 입력 확인, 추적·일관성 검토, 조사 결과 통합, 의견 작성, 협의, 수정·재확인, 기준선 승인, 잔여 위험 추적으로 구성한다.
- 기준선 완료 여부는 필수 요구 추적, 높은 심각도 처리, 모델 일관성, 미결 항목 책임, 공식 승인으로 판단한다.
- 모델 변경은 연결된 모델과 시험에 전파되므로 국소 확인과 주변 회귀 검토를 함께 한다.
- 사실·가정·미확인을 구분하고 권한 있는 책임자의 결정을 기록한다.
