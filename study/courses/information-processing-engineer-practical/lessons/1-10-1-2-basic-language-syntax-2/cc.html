사용자 정의 자료형은 여러 값을 한 묶음으로 담는 편의 기능만이 아니다. 이름, 허용 상태, 생성 규칙, 연산과 불변조건을 함께 정의해 잘못된 값을 만들기 어렵게 하는 설계 도구다. 단순 문자열로 주문 상태·금액·ID를 모두 표현하면 컴파일러와 검증 도구가 의미 차이를 알 수 없지만, 목적이 분명한 타입을 사용하면 오류를 더 이른 시점에 발견할 수 있다.

01

1. 예제 업무와 타입 설계 목표

주문 취소 기능에서 다음 값이 필요하다고 하자.

코드 예시 · text

주문 ID: 빈 값 금지, 다른 ID와 혼용 금지
금액: 통화·소수 자릿수·음수 허용 여부 필요
주문 상태: 정해진 값과 전이만 허용
품목: 상품 ID, 수량, 단가가 함께 움직임
취소 결과: 성공·거절·대기 상태별 데이터가 다름

모든 것을 문자열과 숫자로만 쓰면 다음 오류가 생길 수 있다.

  • 고객 ID를 주문 ID 인자에 잘못 전달
  • 통화가 다른 두 금액을 단순 합산
  • "CONFIRMD" 같은 오타 상태 저장
  • 수량 0·음수인 품목 생성
  • 실패 결과인데 성공 데이터 필드를 읽음

사용자 정의 자료형의 목표는 이 의미와 불변조건을 코드 구조로 표현하는 것이다.

02

2. 사용자 정의 자료형의 주요 형태

언어마다 명칭·문법이 다르지만 공통 개념으로 이해한다.

2.1 열거형

열거형(enum)은 허용된 이름 값 집합을 정의한다.

코드 예시 · text

enum OrderStatus {
    DRAFT,
    CONFIRMED,
    CANCEL_PENDING,
    CANCELLED
}

문자열보다 오타를 줄이고 분기에서 가능한 값을 도구가 확인할 수 있다. 하지만 외부 데이터의 미지 코드와 버전 추가를 어떻게 처리할지 별도 설계가 필요하다.

코드 예시 · text

parseStatus(raw):
    if raw is known code: return corresponding OrderStatus
    else: return validation error or explicit UNKNOWN according to contract

무조건 UNKNOWN으로 받아들이면 금지 상태를 정상 처리할 수 있고, 무조건 실패하면 새 코드 추가 시 구버전 소비자가 중단될 수 있다. 인터페이스 호환 계약에 따라 판단한다.

2.2 구조체·레코드

관련 필드를 하나의 값으로 묶는다.

코드 예시 · text

record OrderLine(
    ProductId productId,
    int quantity,
    Money unitPrice
)

단순 필드 묶음이라도 생성 시 수량·금액을 검증하고 파생 금액 계산을 타입 안에 두면 일관성이 높아진다.

코드 예시 · text

createOrderLine(productId, quantity, unitPrice):
    require productId is valid
    require quantity >= 1
    require unitPrice is non-negative
    return OrderLine(...)

lineAmount(line):
    return line.unitPrice.multiply(line.quantity)

2.3 클래스·객체

상태와 행동을 함께 캡슐화한다. 필드를 외부가 임의 변경하지 못하게 하고 유효한 메서드로만 상태를 바꾸게 할 수 있다.

코드 예시 · text

class Order:
    private id
    private status
    private lines

    addLine(line):
        require status == DRAFT
        require line is valid
        lines.add(line)

    requestCancel():
        require status in [DRAFT, CONFIRMED]
        status = CANCEL_PENDING

모든 getter·setter를 자동 생성하면 필드를 private으로 선언해도 불변조건을 보호하지 못한다. 업무 의미가 있는 연산을 제공한다.

2.4 별칭과 새 이름 타입

일부 언어의 typedef나 type alias는 기존 타입에 새 이름을 붙이지만 컴파일러가 원래 타입과 완전히 구분하지 않을 수 있다.

코드 예시 · c

typedef unsigned long OrderId;
typedef unsigned long CustomerId;

C의 이 별칭들은 대입 호환되어 잘못 섞여도 컴파일될 수 있다. 의미를 엄격히 구분하려면 구조체 래퍼 등 실제 새 타입을 사용한다.

코드 예시 · c

typedef struct { unsigned long value; } OrderId;
typedef struct { unsigned long value; } CustomerId;

2.5 공용체

공용체(union)는 여러 필드가 같은 메모리 공간을 공유한다. 한 시점에 어떤 변형이 유효한지 별도 태그로 관리해야 한다.

코드 예시 · c

typedef enum { RESULT_OK, RESULT_ERROR } ResultKind;

typedef struct {
    ResultKind kind;
    union {
        long order_id;
        int error_code;
    } value;
} SaveResult;

태그와 실제 저장 값을 다르게 해석하면 잘못된 메모리를 읽을 수 있다. 언어가 제공하는 안전한 합 타입이나 패턴 매칭이 있다면 태그–값 일관성을 더 강하게 보장할 수 있다.

2.6 인터페이스·추상 타입

구현이 제공해야 할 연산 계약을 정의한다.

코드 예시 · text

interface PaymentGateway:
    authorize(PaymentRequest) -> PaymentResult
    cancel(CancelRequest) -> CancelResult

구현 세부를 숨기고 호출자가 계약에 의존하게 한다. 인터페이스가 너무 크면 사용하지 않는 메서드까지 구현해야 하므로 역할별로 작고 응집되게 나눈다.

2.7 제네릭·매개변수화 타입

자료형을 매개변수로 받아 반복 구조를 타입 안전하게 재사용한다.

코드 예시 · text

Page<OrderSummary>
Result<OrderId, SaveError>
Repository<Order, OrderId>

무제한 Object나 포인터로 처리하는 것보다 컴파일 시 원소 타입과 반환 상태를 확인할 수 있다. 필요한 연산 제약과 null·오류 의미를 명확히 한다.

03

3. C 언어 예: 구조체·열거형·공용체

코드 예시 · c

#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

typedef struct {
    uint64_t value;
} OrderId;

typedef enum {
    ORDER_DRAFT,
    ORDER_CONFIRMED,
    ORDER_CANCEL_PENDING,
    ORDER_CANCELLED
} OrderStatus;

typedef struct {
    int64_t minor_units;
    char currency[4];
} Money;

typedef struct {
    uint64_t product_id;
    uint32_t quantity;
    Money unit_price;
} OrderLine;

bool order_line_init(
    OrderLine *out,
    uint64_t product_id,
    uint32_t quantity,
    Money unit_price
) {
    if (out == NULL || product_id == 0 || quantity == 0) {
        return false;
    }
    if (unit_price.minor_units < 0) {
        return false;
    }
    *out = (OrderLine){ product_id, quantity, unit_price };
    return true;
}

검토 포인트:

  • 초기화 함수가 실패할 수 있으므로 호출자는 반환값을 확인한다.
  • 출력 포인터와 범위를 먼저 검사한다.
  • 금액은 승인된 최소 통화 단위의 정수로 표현해 부동소수점 오차를 피한다.
  • currency[4]는 3문자 코드와 종료 문자를 위한 크기지만 실제 허용 코드·복사 안전성을 더 검증해야 한다.
  • 곱셈 시 quantity × minor_units 오버플로를 검사한다.

3.1 구조체 복사와 포인터

C 구조체 대입은 필드 값을 복사하지만 필드가 포인터면 가리키는 동적 데이터까지 깊게 복사하지 않는다.

코드 예시 · c

typedef struct {
    char *name;
    size_t length;
} Label;

Label b = a; 뒤 a.name과 b.name은 같은 버퍼를 가리킬 수 있다. 누가 메모리를 해제하는지 소유권 계약, 깊은 복사 함수, 불변 읽기 전용 참조를 명시한다.

3.2 패딩과 직렬화

구조체 메모리에는 정렬을 위한 패딩이 있을 수 있고 플랫폼별 바이트 순서·크기가 다를 수 있다. 구조체 메모리 전체를 그대로 네트워크나 파일에 쓰지 않는다. 필드별 표준 형식과 길이·바이트 순서를 정의해 직렬화한다.

04

4. 객체·값 타입 설계

4.1 엔티티와 값 객체

  • 엔티티: 같은 식별자를 유지하며 시간에 따라 상태가 변한다. 주문은 품목이 바뀌어도 주문 ID로 동일성을 판단할 수 있다.
  • 값 객체: 속성 값 전체로 동일성을 판단하고 가능하면 불변으로 만든다. 금액과 통화가 같은 Money는 같은 값으로 볼 수 있다.

코드 예시 · text

Money(1000, "KRW") == Money(1000, "KRW")
Order(id=10, status=DRAFT)와 Order(id=10, status=CONFIRMED)는 같은 엔티티의 다른 상태

모든 타입에 무조건 ID를 붙이거나 모든 필드로 엔티티 동일성을 비교하지 않는다.

4.2 불변 객체

생성 뒤 상태가 바뀌지 않는 타입은 공유·동시성·해시 키 사용이 안전해진다.

코드 예시 · text

Money.add(other):
    require currency == other.currency
    return new Money(this.amount + other.amount, currency)

원본을 변경하지 않고 새 값을 반환한다. 생성자에서 모든 불변조건을 확인하고 내부 변경 가능한 컬렉션을 그대로 노출하지 않는다.

4.3 생성자와 팩터리

직접 생성자가 단순할 때는 생성자를 쓰고, 이름 있는 생성 경로나 오류 반환이 필요하면 팩터리를 사용한다.

코드 예시 · text

Money.ofMinor(1500, KRW)
Money.parse("15.00", KRW)
OrderId.fromExternal(raw)

파싱·정규화와 이미 유효한 내부 값 생성을 구분하면 입력 경계가 명확해진다.

4.4 동일성·해시·정렬

사용자 정의 타입을 집합·맵 키로 쓰려면 동등성 규칙과 해시 규칙이 일치해야 한다.

코드 예시 · text

if a == b then hash(a) must equal hash(b)

해시 키로 사용 중인 필드를 변경하면 항목을 찾지 못할 수 있다. 키 타입은 불변으로 만들고, 정렬 비교가 동등성과 모순되지 않는지 확인한다.

05

5. 상태와 결과를 타입으로 표현

5.1 잘못된 불리언 조합 피하기

코드 예시 · text

isPaid=true
isCancelled=true
isPending=true

여러 불리언은 동시에 참이 될 수 있어 불가능 상태를 만든다. 상호배타 상태라면 열거형과 상태 전이 메서드를 사용한다.

5.2 선택값

값 없음이 정상 상태라면 null을 무심코 사용하기보다 선택 타입 또는 명시적 결과를 사용한다.

코드 예시 · text

findOrder(id) -> Optional<Order>

호출자가 없음 처리를 강제받는다. 그러나 필수 설정 누락처럼 프로그램 오류인 경우까지 선택값으로 숨기지 않는다.

5.3 성공·실패 합 타입

코드 예시 · text

SaveResult =
    Success(orderId, version)
  | ValidationError(field, reason)
  | VersionConflict(currentVersion)
  | TemporaryFailure(correlationId)

각 변형에 필요한 데이터만 포함하고 패턴 매칭으로 모든 경우를 처리한다. 단일 숫자 오류 코드만 반환할 때보다 의미가 분명하지만 외부 계약으로 직렬화할 때 버전·민감정보 노출을 통제한다.

06

6. 사용자 정의 타입 설계 절차

단계 1: 업무 개념과 불변조건 수집

  • 용어 사전, 데이터 모델, 입력·출력, 상태 규칙을 확인한다.
  • 값 범위, 단위, null, 식별·동일성, 변경 가능성을 정한다.
  • 잘못된 상태가 어떤 업무 오류를 만드는지 평가한다.

판단 기준: 단순 변수 묶음이 아니라 이름 있는 업무 개념인가?

단계 2: 타입 형태 선택

6. 사용자 정의 타입 설계 절차 · 학습 표 1
요구적합 후보
제한된 상태 집합열거형
관련 필드의 값 묶음레코드·구조체·값 객체
식별자와 상태·행동클래스·엔티티
여러 결과 중 하나태그 공용체·합 타입
구현 교체 가능한 계약인터페이스·추상 타입
원소 타입이 다른 반복 구조제네릭

언어 기능을 쓰기 위해 개념을 억지로 복잡하게 만들지 않는다.

단계 3: 생성·유효성 경계 설계

  • 유효하지 않은 인스턴스를 만들 수 없게 생성 경로를 제한한다.
  • 외부 문자열 파싱과 내부 유효 값 생성을 구분한다.
  • 검증 실패의 오류 형식과 필드 위치를 정한다.
  • 객체 역직렬화가 생성자 검증을 우회하지 않는지 확인한다.

단계 4: 연산과 캡슐화

  • 업무 의미가 있는 메서드만 노출한다.
  • 필드 setter보다 상태 전이·계산 메서드로 불변조건을 지킨다.
  • 내부 컬렉션·버퍼의 변경 가능한 참조를 노출하지 않는다.
  • 오류·오버플로·단위 불일치 동작을 정의한다.

단계 5: 값/참조·소유권·수명 결정

  • 복사 비용과 공유 변경 위험을 비교한다.
  • 포인터·참조의 null, 소유자, 해제 시점, 스레드 안전성을 명시한다.
  • 얕은 복사·깊은 복사와 불변 공유 중 하나를 선택한다.

단계 6: 직렬화·저장·호환 설계

  • 내부 필드명과 외부 계약을 직접 결합할지 매핑 계층을 둘지 정한다.
  • 새 필드·열거값 추가와 구버전 처리 규칙을 둔다.
  • 시간·숫자·문자 인코딩·민감정보 표준을 확인한다.
  • DB 키·인덱스·제약과 타입 불변조건을 일치시킨다.

단계 7: 테스트·검토

  • 정상·경계·잘못된 생성과 상태 전이를 시험한다.
  • 동일성·해시·정렬의 수학적 성질을 확인한다.
  • 직렬화 왕복과 구·신 버전 호환을 시험한다.
  • 복사·수명·동시성·오버플로를 언어에 맞게 검사한다.

7. 기본문법 활용하기의 적용 절차와 판단 기준

7.1 문제와 입출력 확인

  1. 입력 출처, 자료형, 단위, 허용 범위와 실패 동작을 정한다.
  2. 출력·상태 변경·부작용과 완료 조건을 정한다.
  3. 업무 규칙을 정상·경계·예외 사례로 만든다.

7.2 타입과 변수 선택

  1. 언어 기본 타입의 범위·정밀도·부호·null 가능성을 확인한다.
  2. 단위·ID·상태처럼 의미가 중요한 값은 사용자 정의 타입 후보로 삼는다.
  3. 변수 범위와 수명을 최소화하고 가능하면 불변으로 둔다.

7.3 연산·제어 구조 작성

  1. 형 변환, 오버플로, 나눗셈·반올림과 평가 순서를 확인한다.
  2. 조건은 긍정적이고 상호배타적으로 작성하며 복잡하면 함수·의사결정표로 분리한다.
  3. 반복은 종료 조건, 빈 입력, 최대 크기와 오류 시 부분 결과를 정의한다.
  4. 자원은 모든 정상·예외 경로에서 정리한다.

7.4 함수·타입 경계 구성

  1. 한 함수·타입은 한 응집된 책임을 갖는다.
  2. 매개변수 순서가 혼동되면 이름 있는 타입·명명 인자·명령 객체를 사용한다.
  3. 반환값·예외·결과 타입으로 성공·실패 계약을 명확히 한다.
  4. 전역 변경 상태보다 명시적 의존성과 입력을 선호한다.

7.5 정적·동적 확인

  • 컴파일러 경고, 타입 검사, 린터와 정적 분석을 활성화한다.
  • 단위 테스트로 경계·상태·오류·동등성·직렬화를 검증한다.
  • 코드 검토로 이름·가독성·중복·불변조건과 언어 관용을 확인한다.
  • 실제 규모·동시성·플랫폼 차이가 중요하면 통합·성능 시험을 추가한다.

7.6 판단 기준

8.2 동등성 성질

  • 반사성: a == a
  • 대칭성: a == b이면 b == a
  • 추이성: a == b, b == c이면 a == c
  • 일관성: 값이 바뀌지 않으면 반복 비교 결과가 같음
  • hash 일치: 동등한 값은 같은 해시

10. 자주 틀리는 포인트

  1. 사용자 정의 타입은 여러 필드를 묶는 구조체뿐이다? 열거형·클래스·공용체·인터페이스·제네릭·합 타입도 포함한다.
  2. type alias면 컴파일러가 원래 타입과 구분한다? 언어에 따라 단순 별칭이라 ID 혼용을 막지 못한다.
  3. 필드를 private으로 하고 setter를 모두 만들면 캡슐화다? 불변조건을 우회하므로 의미 있는 연산을 제공한다.
  4. 열거형이면 외부 새 코드도 자동 호환된다? 미지 값 처리와 버전 계약이 필요하다.
  5. 여러 불리언은 상태를 유연하게 표현한다? 불가능한 조합을 만들 수 있어 상호배타 상태는 열거·합 타입이 낫다.
  6. C 구조체 대입은 포인터가 가리키는 데이터까지 깊게 복사한다? 포인터 값만 복사되어 소유권 문제가 생길 수 있다.
  7. 구조체 메모리를 그대로 네트워크에 보내면 효율적이다? 패딩·정렬·바이트 순서·크기 차이 때문에 표준 직렬화가 필요하다.
  8. 금액은 double이면 모든 소수를 표현한다? 이진 부동소수 오차가 있어 고정 정밀도나 최소 단위 정수를 검토한다.
  9. 엔티티 동등성은 모든 필드가 같아야 한다? 보통 지속되는 식별자를 중심으로 동일성을 판단한다.
  10. 해시 키 객체는 사용 중 필드를 바꿔도 된다? 해시가 달라져 조회가 실패할 수 있으므로 키는 불변이어야 한다.
  11. 생성 뒤 setter에서 검증하면 잠시 잘못된 객체도 괜찮다? 잘못된 인스턴스가 다른 코드로 전달될 수 있어 생성 경계에서 막는다.
  12. 직렬화 도구가 생성자 검증을 항상 호출한다? 우회 가능성을 확인하고 역직렬화 뒤 불변조건을 검증한다.
  13. 타입을 많이 만들수록 설계가 좋다? 의미·오류 감소 효과보다 변환·학습 비용이 큰지 판단한다.
  14. 기본문법 활용은 실행 결과만 맞으면 된다? 타입 범위·수명·오류·가독성·호환·테스트 가능성을 함께 본다.

12. 정답과 해설

정답 1

열거형은 허용 상태만 표현해 오타를 줄이고 분기 누락을 정적 도구가 찾게 한다. 외부 시스템이 새 코드를 보내면 구버전 역직렬화가 실패할 수 있으므로 계약에 따라 미지 값을 거절·보존·UNKNOWN으로 매핑할지 정하고 안전한 기본 동작과 버전 시험을 둔다.

정답 2

단순 typedef는 기존 정수 타입의 별칭일 뿐 별도 대입 불가 타입이 아닐 수 있어 두 ID를 바꿔 전달해도 컴파일된다. 값을 감싼 서로 다른 구조체나 언어의 강한 새 타입·값 객체를 사용하고 생성·변환 함수를 제한한다.

정답 3

구조체 복사는 포인터 주소만 복사해 두 값이 같은 버퍼를 공유할 수 있다. 한쪽 수정이 다른 쪽에 보이고, 두 번 해제하거나 먼저 해제한 메모리를 사용할 위험이 있다. 소유자·대여 기간·해제 책임, 깊은 복사·이동·불변 공유 중 방식을 명시한다.

정답 4

Order는 같은 order ID라면 상태·품목이 바뀌어도 같은 엔티티다. Money는 별도 ID보다 금액과 통화 속성 전체가 같을 때 같은 값이다. 값 객체는 보통 불변으로 만들어 안전하게 공유한다.

정답 5

paid, cancelled, pending이 동시에 참인 불가능 조합을 만들고 전이 규칙이 여러 setter에 흩어진다. 열거형은 한 시점의 허용 상태 하나를, 합 타입은 상태별로 필요한 데이터까지 묶어 잘못된 조합 생성을 줄인다.

정답 6

업무 용어·값 범위·불변조건·동일성·변경성을 수집하고 적합한 열거·레코드·클래스·합·인터페이스 형태를 고른다. 유효한 생성 경계와 오류를 설계하고 의미 있는 연산으로 캡슐화한다. 값/참조·복사·소유권을 정하고 저장·직렬화·버전 매핑을 정의한 뒤 경계·상태·동등성·호환·수명을 시험한다.

정답 7

통화 코드가 허용 목록인지, 금액 정밀도·소수 자릿수가 맞는지, 음수 허용 여부, 덧셈 시 통화 일치, 곱셈·합산 오버플로, 반올림 방식과 적용 시점, 직렬화 단위, 최대값을 정의·검사한다.

정답 8

두 객체가 동등하면 해시도 반드시 같아야 한다. 반사·대칭·추이·일관성도 지킨다. 맵에 넣은 뒤 동등성·해시 계산 필드가 바뀌면 저장 당시 버킷과 조회 버킷이 달라 항목을 찾거나 제거하지 못할 수 있다.

정답 9

값을 직렬화·역직렬화한 왕복 동등성, 구버전 데이터의 신버전 읽기, 신규 선택 필드와 구버전 소비자, 미지 열거값 처리, 시간·정밀도·문자 인코딩, 민감 필드 제외, 잘못된 데이터가 생성자 검증을 우회하지 않는지 시험한다.

정답 10

타입은 범위·정밀도·단위와 업무 의미를 표현하고 변수 범위·수명이 작아야 한다. 조건·반복은 모든 경계에서 올바르게 종료하며 불가능 상태를 만들지 않아야 한다. 오류는 숨기지 않고 호출 계약으로 전달하고 자원은 정리한다. 이름·함수·타입은 읽기 쉽고 과도하지 않으며 정적 검사와 단위·통합 테스트가 불변조건·금지 경로를 검증해야 한다.

13. 핵심 요약

  • 사용자 정의 자료형은 업무 의미·허용 상태·불변조건과 연산을 코드에 표현해 잘못된 값을 줄인다.
  • 열거형은 제한된 값, 구조체·레코드는 관련 값, 클래스는 상태와 행동, 합 타입은 여러 결과 중 하나를 표현한다.
  • 단순 type alias는 강한 타입 구분을 제공하지 않을 수 있어 ID 혼용 위험에는 래퍼 타입을 사용한다.
  • 공용체는 태그와 유효 필드 일관성이 필요하고 구조체의 포인터 복사는 소유권·깊은 복사를 고려한다.
  • 엔티티는 지속 식별자, 값 객체는 속성 전체로 동일성을 판단하며 값 객체는 불변이 유리하다.
  • 생성 경로에서 유효성을 보장하고 무분별한 setter 대신 의미 있는 상태 전이·계산 메서드를 제공한다.
  • 금액·시간·ID·상태는 단위·정밀도·범위·null·버전 의미가 중요한 타입 후보다.
  • 동등성·해시·정렬 규칙을 일치시키고 맵 키와 공유 값은 불변으로 유지한다.
  • 저장·직렬화는 내부 메모리 표현과 분리하고 패딩·바이트 순서·미지 값·구버전 호환을 시험한다.
  • 기본문법 활용은 문제·입출력–타입·변수–연산·제어–함수·타입 경계–정적·동적 검증 순으로 수행하고 단순성 대비 효과를 판단한다.
