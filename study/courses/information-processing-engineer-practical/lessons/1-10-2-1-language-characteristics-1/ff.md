# 1-10-2-1. 언어별 특성 파악과 설명 · 언어 특성을 적용한 애플리케이션 구현

## 수행 범위와 목표

이 레슨의 정확한 토픽은 **언어별 특성 파악과 설명**과 **언어 특성을 적용한 애플리케이션 구현**이다. 프로그래밍 언어의 실행 방식, 타입 체계, 메모리 관리, 패러다임, 오류 처리, 동시성, 모듈 구조를 비교하고, 선택된 언어의 강점과 제약을 실제 코드 구조에 반영하는 실무를 다룬다.

변수·연산자·사용자 정의 자료형의 기본 문법은 앞 레슨 범위이고, 측정 기반 성능 최적화는 다음 레슨에서 다룬다. 여기서는 언어 특성을 이해해 정확하고 유지 가능한 구현을 선택하는 데 집중한다.

학습 목표는 다음과 같다.

1. 정적·동적 타입, 컴파일·해석·가상 머신 실행, 자동·수동 메모리 관리의 차이를 설명한다.
2. 절차형, 객체지향, 함수형, 선언형 특성을 문제 구조와 연결한다.
3. 예외·오류, 값·참조, 변경 가능성, 동시성 모델을 코드에 반영한다.
4. 언어와 런타임의 실제 문서·도구를 이용해 가정을 확인한다.

## 1. 언어 특성을 보는 기준

언어를 “빠르다”, “쉽다”라는 한 단어로 비교하면 실제 선택과 구현에 도움이 되지 않는다. 다음 질문으로 구체화한다.

| 관점 | 확인 질문 |
|---|---|
| 실행 | 원시 코드, 바이트코드, 가상 머신, 인터프리터 중 어떤 경로인가 |
| 타입 | 타입 오류를 언제 발견하며 암시적 변환은 어떻게 작동하는가 |
| 메모리 | 객체 수명과 해제를 누가 관리하는가 |
| 패러다임 | 상태 변경, 객체 협력, 함수 합성 중 무엇을 자연스럽게 표현하는가 |
| 오류 | 예외·오류 값·결과 타입을 어떻게 전달하는가 |
| 동시성 | 스레드, 이벤트 루프, 비동기 작업, 메시지 중 무엇을 제공하는가 |
| 모듈 | 이름 공간, 공개 API, 패키지·빌드 단위는 무엇인가 |
| 생태계 | 표준 라이브러리, 도구, 배포·관찰 지원은 충분한가 |

같은 언어도 구현체와 버전, 실행 옵션에 따라 성능·동시성 세부가 다를 수 있다. 언어 명세와 선택한 런타임 공식 문서를 구분해 확인한다.

## 2. 실행 방식

### 2.1 사전 컴파일

소스 코드를 배포 전에 기계어 등 실행 형식으로 변환한다. 시작과 실행 효율에 이점이 있을 수 있고 배포 대상 운영체제·CPU와 연결될 수 있다. 빌드 도구, 최적화 옵션, 디버그 정보, 플랫폼별 산출물 관리가 필요하다.

### 2.2 인터프리터

실행 시 소스 또는 중간 표현을 해석한다. 빠른 실험과 동적 기능에 유리할 수 있지만 실행 오버헤드와 배포 환경 일치가 중요하다. “인터프리터 언어는 컴파일하지 않는다”라고 절대적으로 구분하지 않는다. 내부적으로 바이트코드나 캐시를 만들 수 있다.

### 2.3 가상 머신과 JIT

소스를 중간 코드로 변환해 가상 머신에서 실행하고, 자주 실행되는 부분을 실행 중 최적화할 수 있다. 준비 시간, 워밍업, 런타임 메모리와 최적화 관찰이 필요하다. 짧게 한 번 실행한 결과와 장시간 운영 성능이 다를 수 있다.

실행 방식은 언어 이름만으로 단순 분류하지 말고 실제 구현체와 배포 형태를 확인한다.

## 3. 타입 체계

### 3.1 정적 타입과 동적 타입

정적 타입 언어는 많은 타입 관계를 컴파일 또는 빌드 시 확인해 인터페이스 계약과 도구 지원을 강화할 수 있다. 동적 타입 언어는 실행 중 값의 타입을 결정해 빠른 표현과 유연한 구조에 유리할 수 있지만 실행하지 않은 경로의 타입 오류를 놓칠 수 있다.

동적 언어도 타입 주석과 정적 분석을 사용할 수 있고, 정적 언어도 반사·동적 변환을 제공할 수 있다. 팀의 시험·분석 도구와 함께 판단한다.

### 3.2 강한 타입과 암시적 변환

서로 다른 타입 사이 연산을 얼마나 엄격히 제한하고 자동 변환하는지 확인한다. 문자열 "10"과 숫자 10을 자동 비교·더하기하면 예상하지 못한 결과가 생길 수 있다. 인터페이스 경계에서 명시적으로 파싱하고 실패를 처리한다.

### 3.3 NULL과 선택값

값 부재를 NULL, null 참조, 선택 타입, 별도 결과 객체로 표현하는 방식이 다르다. 값이 없을 수 있는지 함수 계약에 드러내고 호출자가 처리하게 한다. 의미 없는 빈 문자열·0을 대신 넣지 않는다.

### 3.4 제네릭과 다형성

다양한 타입에 같은 알고리즘을 안전하게 적용하는 제네릭, 인터페이스·프로토콜 기반 다형성을 활용할 수 있다. 모든 것을 최상위 객체나 문자열로 바꾸면 타입 정보와 검증을 잃는다.

## 4. 메모리와 값의 의미

### 4.1 값과 참조

변수 대입이 값을 복사하는지 객체 참조를 공유하는지 이해해야 한다. 공유된 변경 가능한 객체를 한 함수에서 수정하면 다른 코드의 값도 바뀔 수 있다.

    function addItem(order, item):
        newItems = copy(order.items)
        newItems.append(item)
        return order.withItems(newItems)

불변 객체 또는 복사 후 변경을 사용하면 예상하지 못한 별칭 부작용을 줄일 수 있지만 복사 비용을 고려한다. 언어가 제공하는 불변 컬렉션·소유권 모델을 확인한다.

### 4.2 자동 메모리 관리

가비지 컬렉션이 있는 언어도 메모리 누수가 없다는 뜻은 아니다. 전역 컬렉션, 캐시, 이벤트 구독이 참조를 계속 보유하면 회수되지 않는다. 파일·소켓·DB 연결처럼 메모리 외 자원은 명시적 닫기 또는 자동 자원 관리 구문이 필요하다.

### 4.3 수동 관리와 소유권

수동 할당·해제 언어에서는 이중 해제, 사용 후 해제, 경계 초과를 피해야 한다. 일부 언어는 소유권과 수명 규칙을 컴파일 단계에서 강제한다. 어느 방식이든 자원 소유자와 해제 시점을 명확히 한다.

## 5. 프로그래밍 패러다임

### 5.1 절차형

처리 절차와 상태 변화를 순서대로 표현한다. 명확한 계산·배치 흐름에 적합하다. 전역 상태와 긴 함수가 늘면 변경 영향이 커지므로 작은 책임과 명시적 입력·출력을 사용한다.

### 5.2 객체지향

상태와 행위를 객체에 캡슐화하고 책임·협력으로 설계한다. 상속 자체보다 인터페이스, 정보 은닉, 응집도와 결합도가 중요하다. 모든 데이터를 getter·setter만 가진 객체로 만들거나 지나치게 깊은 상속 구조를 사용하지 않는다.

### 5.3 함수형

순수 함수, 불변값, 고차 함수, 함수 합성을 활용해 상태 변화와 부작용을 통제한다. 데이터 변환 파이프라인과 병렬 추론에 유리할 수 있다. 입출력·시간·외부 호출 같은 부작용을 경계로 밀어내면 핵심 로직 시험이 쉬워진다.

### 5.4 선언형

어떻게 순회할지보다 원하는 결과를 표현한다. SQL 질의, 규칙·구성 언어가 예다. 실행기는 최적화할 여지가 있지만 실제 실행 계획과 비용을 이해하지 않으면 비효율이 숨을 수 있다.

실제 애플리케이션은 여러 패러다임을 조합한다. 언어가 지원한다는 이유만으로 한 방식을 모든 문제에 강제하지 않는다.

## 6. 오류 처리 특성

언어는 예외, 오류 코드, 결과 타입, 패닉 등 다른 방식을 제공한다. 복구 가능한 업무 실패와 프로그래밍 결함, 외부 장애를 구분한다.

    result = parseAmount(input)
    if result is invalid:
        return ValidationError(field="amount")

    try:
        receipt = paymentGateway.authorize(result.value)
    catch TemporaryNetworkFailure:
        return DependencyUnavailable()

사용자 입력 오류를 프로그램을 중단시키는 치명 예외로 처리하지 않고, 메모리 불변식 파괴 같은 결함을 조용히 성공값으로 바꾸지 않는다. 예외를 잡고 무시하거나 모든 예외를 하나로 바꾸면 원인과 복구 정책을 잃는다.

자원은 성공·실패 모든 경로에서 해제한다. 언어의 try/finally, with, defer, 자동 자원 관리 같은 관용구를 사용한다.

## 7. 동시성 특성

### 7.1 스레드와 공유 메모리

여러 스레드가 같은 변경 가능한 상태에 접근하면 경쟁 조건이 생긴다. 잠금, 원자 연산, 불변 데이터, 작업 큐로 보호한다. 잠금 순서가 다르면 교착 상태가 생길 수 있다.

### 7.2 이벤트 루프와 비동기

입출력 대기 동안 다른 작업을 처리해 많은 연결을 효율적으로 다룰 수 있다. 그러나 CPU를 오래 점유하거나 동기 블로킹 호출을 이벤트 루프에서 실행하면 전체 요청이 멈출 수 있다. 비동기 함수 호출을 빠뜨리거나 오류를 관찰하지 않는 문제도 주의한다.

### 7.3 메시지·작업자 모델

상태를 공유하기보다 메시지로 작업을 전달한다. 격리를 높일 수 있지만 메시지 순서, 중복, 실패 재처리, 큐 지연을 설계해야 한다.

동시성 모델은 언어 문법뿐 아니라 런타임과 라이브러리에 의존한다. 실제 스케줄링·스레드 안전성 계약을 확인한다.

## 8. 언어 특성을 적용한 애플리케이션 구현 절차

1. **문제 특성 확인**: CPU 계산, 입출력, 동시 요청, 실시간, 메모리·배포 제약을 분류한다.
2. **언어·런타임 기준선 확인**: 버전, 타입·오류·동시성 모델, 지원 플랫폼을 공식 문서로 확인한다.
3. **경계 계약 정의**: 입력 타입, 선택값, 오류, 비동기 반환과 자원 소유를 명시한다.
4. **관용적 구조 선택**: 언어 생태계에서 검증된 모듈·자원 관리·시험 방식을 따른다.
5. **부작용 분리**: 핵심 업무 계산과 DB·네트워크·시간을 분리한다.
6. **오류·자원 경로 구현**: 정상뿐 아니라 실패·취소·시간 초과에서 자원을 해제한다.
7. **정적 분석·시험**: 타입 검사, 린트, 단위·통합·동시성 시험을 수행한다.
8. **실제 런타임 검증**: 지원 환경에서 메모리·스레드·로그와 배포 동작을 확인한다.

## 9. 구체 시나리오

### 상황

대량 파일에서 주문 레코드를 읽어 검증하고 외부 API로 전송한다. 파일은 메모리보다 크고 API 호출은 입출력 대기가 길다.

### 구현 판단

- 파일 전체를 리스트로 읽지 않고 언어의 이터레이터·스트림으로 한 건 또는 제한된 묶음씩 처리한다.
- 파싱·검증은 입력→결과가 명확한 순수 함수로 분리한다.
- 오류 레코드는 행 번호와 안전한 오류코드로 격리하고 전체 파일을 무조건 중단할지 업무 규칙으로 정한다.
- 외부 호출은 런타임의 비동기·작업자 모델에 맞게 제한된 동시성으로 수행한다.
- 무제한 작업 생성으로 메모리와 외부 한도를 초과하지 않도록 큐·세마포어 상한을 둔다.
- 파일과 네트워크 자원은 자동 자원 관리로 닫는다.

특정 언어에서 비동기 호출이 실제로 어떤 스레드를 사용하고 파일 읽기가 블로킹인지 공식 문서와 측정으로 확인한다.

## 10. 산출물과 체크리스트

주요 산출물은 언어 특성 비교표, 런타임·버전 기준, 모듈·오류·동시성 설계, 코딩 규칙, 구현 코드, 정적 분석·시험 결과다.

- 실행 방식과 배포 대상의 호환성을 확인했는가?
- 입력 경계에서 암시적 타입 변환을 통제하는가?
- NULL·선택값과 오류가 함수 계약에 드러나는가?
- 변경 가능한 객체 공유와 복사 의미를 이해했는가?
- 파일·소켓·연결이 모든 경로에서 해제되는가?
- 업무 실패·일시 장애·프로그래밍 결함을 구분하는가?
- 비동기 코드에서 블로킹 작업과 무제한 동시성을 피하는가?
- 핵심 로직과 부작용이 분리되어 시험 가능한가?
- 정적 분석과 실제 런타임 시험을 모두 수행했는가?

## 11. 자주 틀리는 함정

1. 언어를 컴파일형·인터프리터형 하나로만 절대 분류하지 않는다.
2. 동적 타입은 타입 검사가 없고 정적 타입은 런타임 오류가 없다고 보지 않는다.
3. 자동 메모리 관리가 자원 해제와 누수 문제를 모두 해결한다고 생각하지 않는다.
4. 대입이 항상 깊은 복사라고 가정하지 않는다.
5. 객체지향을 상속의 양으로 판단하지 않는다.
6. 함수형 코드를 쓴다고 외부 부작용이 자동으로 사라지지 않는다.
7. 모든 예외를 잡아 성공값으로 바꾸지 않는다.
8. 비동기 함수는 언제나 별도 스레드에서 실행된다고 단정하지 않는다.
9. 동시 작업 수를 무제한으로 늘리지 않는다.
10. 언어 특성의 일반론을 실제 구현체 문서·시험 없이 적용하지 않는다.

## 12. 확인 문제

### 문제 1

정적 타입과 동적 타입의 핵심 차이는 무엇인가?

**정답과 해설:** 많은 타입 관계를 주로 언제 확인하는가의 차이다. 정적은 빌드 전 확인 비중이 높고 동적은 실행 중 값 타입을 판단한다.

### 문제 2

가비지 컬렉션 언어에서도 메모리 누수가 생길 수 있는 이유는 무엇인가?

**정답과 해설:** 캐시·전역 컬렉션·구독이 더 이상 필요 없는 객체 참조를 계속 보유하면 회수 대상이 되지 않기 때문이다.

### 문제 3

파일과 DB 연결을 자동 메모리 관리에만 맡기면 안 되는 이유는 무엇인가?

**정답과 해설:** 외부 자원은 회수 시점이 불확실하면 고갈될 수 있으므로 명시적 닫기나 자동 자원 관리 구문이 필요하다.

### 문제 4

순수 함수가 시험하기 쉬운 이유는 무엇인가?

**정답과 해설:** 같은 입력에 같은 출력을 내고 숨은 외부 상태를 바꾸지 않아 시간·DB·네트워크 대역 없이 결과를 검증하기 쉽다.

### 문제 5

이벤트 루프에서 블로킹 작업을 실행하면 어떤 문제가 생기는가?

**정답과 해설:** 이벤트 루프가 다른 연결과 작업을 처리하지 못해 전체 지연이 커진다.

### 문제 6

공유 변경 상태의 경쟁 조건을 줄이는 방법 세 가지를 쓰시오.

**정답과 해설:** 잠금·원자 연산, 불변 데이터, 메시지·작업 큐를 들 수 있다.

### 문제 7

업무 거절과 프로그래밍 결함을 같은 예외로 숨기면 안 되는 이유는 무엇인가?

**정답과 해설:** 호출자의 복구·사용자 안내와 운영 경보가 달라야 하며 결함을 정상 업무 결과처럼 놓칠 수 있기 때문이다.

### 문제 8

대용량 파일 처리에 이터레이터·스트림이 유리한 이유는 무엇인가?

**정답과 해설:** 전체 파일을 한꺼번에 메모리에 올리지 않고 제한된 데이터만 유지할 수 있기 때문이다.

### 문제 9

언어 특성 적용 전에 확인할 공식 정보 세 가지를 쓰시오.

**정답과 해설:** 언어·런타임 버전, 동시성·스레드 안전성 계약, 지원 플랫폼을 들 수 있다. 오류·자원 관리 관용구도 확인한다.

## 13. 핵심 요약

- **언어별 특성 파악과 설명**은 실행, 타입, 메모리, 패러다임, 오류, 동시성, 모듈과 생태계를 구체적으로 비교하는 활동이다.
- 언어 일반론과 실제 구현체·버전의 동작을 구분한다.
- **언어 특성을 적용한 애플리케이션 구현**은 계약, 자원 소유, 부작용, 오류·동시성 모델을 언어의 관용적 구조로 표현하는 일이다.
- 자동 메모리 관리가 외부 자원 해제와 참조 누수를 없애지는 않는다.
- 정적 분석과 단위 시험뿐 아니라 실제 런타임·배포 환경에서 동시성·자원 동작을 확인한다.
- 대용량·입출력 업무는 스트림, 제한된 동시성, 명시적 오류·자원 관리로 안전하게 구현한다.
- 선택한 언어 특성은 요구사항과 코드·시험 결과가 서로 추적되도록 근거와 함께 기록한다.
