# 1-10-2-2. 언어 특성을 활용한 애플리케이션 최적화

## 수행 범위와 목표

이 레슨의 정확한 토픽은 **언어 특성을 활용한 애플리케이션 최적화**와 **언어특성 활용하기의 적용 절차와 판단 기준**이다. 실제 측정에서 확인한 병목을 대상으로 언어·런타임의 자료구조, 메모리, 호출, 입출력, 동시성, 컴파일·가상 머신 특성을 활용해 성능과 자원 사용을 개선하는 실무를 다룬다.

언어별 실행·타입·메모리·동시성의 기본 특성은 앞 레슨에서 다뤘다. 라이브러리 검색·선택은 다음 레슨 범위다. 여기서는 정확성·가독성·운영성을 보존하며 검증 가능한 최적화를 수행하는 데 집중한다.

학습 목표는 다음과 같다.

1. 응답 시간, 처리량, CPU, 메모리, 입출력, 할당을 기준선으로 측정한다.
2. 알고리즘·자료구조와 언어별 컬렉션·문자열·이터레이터 특성을 활용한다.
3. 동시성·비동기를 자원 상한과 외부 제약에 맞게 적용한다.
4. 같은 조건에서 전후를 비교하고 회귀·부하 시험으로 이익과 부작용을 검증한다.

## 1. 최적화의 원칙

최적화는 코드를 짧게 만들거나 모든 부분을 복잡하게 바꾸는 일이 아니다. 사용자가 체감하거나 운영 한계를 만드는 병목을 측정하고 최소 변경으로 목표를 달성하는 활동이다.

    성능 목표
       ↓
    재현 가능한 기준선
       ↓
    프로파일링으로 병목 식별
       ↓
    후보 변경과 비용 가설
       ↓
    동일 조건 비교
       ↓
    정확성·회귀·운영 검증

측정 없이 “반복문이 느릴 것 같다”라고 추측하면 실제 병목인 DB·네트워크·직렬화는 그대로 두고 가독성만 낮출 수 있다.

## 2. 측정 기준

| 지표 | 의미 | 주의점 |
|---|---|---|
| 응답 시간 | 요청 하나의 완료 시간 | 평균뿐 아니라 백분위·최대 확인 |
| 처리량 | 단위 시간당 완료 작업 | 오류를 성공 처리량에 포함하지 않음 |
| CPU 시간 | 실제 계산에 쓴 프로세서 시간 | 대기 시간이 길면 낮을 수 있음 |
| 메모리 | 상주·힙·최대 사용과 할당량 | 누수와 일시 급증 구분 |
| 입출력 | 파일·네트워크·DB 대기와 바이트 | 캐시 상태를 기록 |
| GC·할당 | 객체 생성·회수 빈도와 정지 | 런타임별 지표 의미 확인 |
| 동시성 | 작업자·큐·연결·대기 | 처리량 증가와 자원 포화 함께 확인 |

운영과 유사한 데이터 분포, 워밍업, 같은 빌드 옵션, 반복 횟수를 기록한다. 짧은 마이크로벤치마크가 전체 요청의 실제 성능을 자동 설명하지 않는다.

## 3. 알고리즘과 자료구조

### 3.1 복잡도

입력 크기 n이 커질 때 연산·공간 증가를 본다. 리스트에서 매번 선형 검색하는 코드를 해시 기반 집합으로 바꾸면 membership 검사를 평균적으로 줄일 수 있다. 그러나 작은 입력에서는 해시 생성 비용과 메모리가 더 클 수 있다.

    느린 후보:
      for order in orders:
          if order.customerId in customerIdList:
              process(order)

    개선 후보:
      customerIdSet = makeSet(customerIdList)
      for order in orders:
          if customerIdSet.contains(order.customerId):
              process(order)

중복 허용, 순서, 해시 가능성, 메모리 요구가 달라지므로 의미를 확인한다.

### 3.2 적합한 컬렉션

- 순서와 인덱스 접근이 필요하면 배열·리스트를 검토한다.
- 빠른 키 조회는 맵·사전을 검토한다.
- 중복 제거와 포함 검사는 집합을 검토한다.
- 앞뒤 삽입·제거, 우선순위 처리에는 해당 큐 구조를 검토한다.

자료구조의 평균 복잡도만 외우지 않고 실제 런타임의 구현, 입력 편향, 메모리와 순회 패턴을 측정한다.

### 3.3 중복 계산 제거

반복문 안에서 변하지 않는 파싱·정규식 준비·설정 조회를 밖으로 이동한다. 동일 함수 결과를 캐시할 때는 입력, 수명, 최대 크기, 무효화와 개인정보를 설계한다. 무제한 캐시는 메모리 누수가 된다.

## 4. 문자열과 데이터 변환

일부 언어에서 문자열은 불변이므로 반복 연결할 때 중간 객체가 많이 생길 수 있다.

    parts = []
    for item in items:
        parts.append(formatItem(item))
    output = join(parts, separator)

언어의 문자열 빌더나 join을 활용할 수 있다. 다만 작은 문자열 몇 개까지 복잡한 최적화를 적용할 필요는 없다. 프로파일러에서 할당·시간 비중을 확인한다.

직렬화와 파싱은 인터페이스에서 큰 비용이 될 수 있다. 필요한 필드만 변환하고 같은 데이터를 여러 번 직렬화하지 않는다. 숫자를 문자열로 바꾸었다가 다시 숫자로 파싱하는 불필요한 왕복을 줄인다.

## 5. 메모리 최적화

### 5.1 스트리밍과 지연 평가

대용량 데이터를 리스트 전체로 만드는 대신 이터레이터·스트림으로 필요한 만큼 처리한다.

    function validRows(file):
        for line in file:
            row = parse(line)
            if row.isValid:
                yield row

    for batch in chunks(validRows(file), boundedBatchSize):
        send(batch)

메모리는 줄지만 스트림을 여러 번 순회할 수 없거나 예외가 늦게 발생할 수 있다. 파일이 열려 있는 수명과 오류·재처리 단위를 명확히 한다.

### 5.2 객체 할당

짧은 시간에 매우 많은 임시 객체를 만들면 GC 부담이 늘 수 있다. 불필요한 래퍼·복사·중간 컬렉션을 줄이고 값 표현을 단순화한다. 객체 풀은 수명 오류와 메모리 보유를 만들 수 있으므로 런타임이 권장하고 측정 이익이 있을 때만 사용한다.

### 5.3 캐시

읽기 비용을 줄일 수 있지만 최신성, 동시성, 최대 크기, 제거 정책, 장애 시 재구축을 정한다. 사용자별 민감 결과를 공용 키로 캐시하지 않는다. 캐시가 없을 때도 원천에서 정확한 결과를 만들 수 있어야 한다.

## 6. 입출력 최적화

### 6.1 묶음 처리

작은 파일·DB·네트워크 호출을 여러 번 하는 대신 승인된 크기로 묶어 왕복을 줄인다. 너무 큰 묶음은 메모리, 제한 시간, 실패 재처리 범위를 키운다. 메시지 크기 한도와 부분 실패 정책을 반영한다.

### 6.2 버퍼링

작은 읽기·쓰기를 버퍼로 모을 수 있다. 완료 전에 flush가 필요한 시점과 프로세스 실패 때 손실 가능성을 이해한다. 감사·금전 기록을 메모리 버퍼에만 둔 채 성공 응답하지 않는다.

### 6.3 비동기 입출력

입출력 대기 동안 작업자를 효율적으로 사용할 수 있다. CPU 작업을 비동기로 감싸기만 하면 빨라지는 것이 아니며 이벤트 루프에서 블로킹 호출을 피한다. 외부 호출 한도와 연결 풀에 맞춰 동시성 상한을 둔다.

## 7. 동시성과 병렬성

동시성은 여러 작업의 진행을 겹치고, 병렬성은 여러 계산을 실제 동시에 수행하는 관점이다. 언어 런타임의 스레드 모델과 CPU 코어, 프로세스 격리, 공유 상태를 확인한다.

    semaphore = new Semaphore(maxConcurrentCalls)
    for request in requests:
        schedule async:
            with semaphore:
                await externalCall(request)

상한은 외부 서비스 호출 제한, 연결 풀, 메모리, 목표 처리량으로 정한다. 작업 수를 늘리면 초기에는 처리량이 오르지만 포화 뒤에는 큐·문맥 전환·잠금이 늘어 지연이 악화될 수 있다.

공유 컬렉션과 카운터의 스레드 안전성을 확인하고, 가능하면 독립 작업·불변 입력·결과 병합 구조를 사용한다. 잠금을 세분화하면 경합은 줄지만 복잡성과 교착 위험이 커질 수 있다.

## 8. 컴파일러·런타임 특성

### 8.1 빌드 최적화

운영 빌드의 최적화·디버그 설정이 실제와 같은지 확인한다. 디버그와 릴리스 성능이 다를 수 있지만 디버그 검사를 무조건 제거하면 진단성이 낮아질 수 있다. 산출물 재현성과 심볼 보관을 함께 관리한다.

### 8.2 워밍업과 JIT

가상 머신의 실행 중 최적화가 있는 경우 초기 요청과 안정 상태를 구분해 측정한다. 테스트가 너무 짧으면 컴파일 비용만 보거나 반대로 운영의 콜드 스타트를 놓칠 수 있다.

### 8.3 GC

힙 크기와 GC 정책을 임의 조정하기 전에 할당률, 살아남는 객체, 정지 시간, 메모리 제한을 측정한다. 코드의 불필요 할당을 줄이는 것이 설정 조정보다 근본 해결일 수 있다. 구체 옵션은 선택 런타임 버전의 공식 지침을 따른다.

## 9. 언어특성 활용하기의 적용 절차와 판단 기준

### 9.1 1단계: 목표 정의

대상 사용자 흐름과 데이터·동시 부하에서 응답 백분위, 처리량, 메모리·CPU 상한을 정한다. “빠르게”가 아니라 측정 가능한 기준을 사용한다.

### 9.2 2단계: 기준선 재현

빌드·런타임·하드웨어·데이터·캐시·워밍업·외부 대역을 기록하고 반복 실행한다. 결과 변동 범위를 확인한다.

### 9.3 3단계: 프로파일링

CPU 샘플, 할당·힙, GC, 입출력 대기, 잠금·큐, 추적을 사용해 큰 비용부터 찾는다. 프로파일링 도구의 오버헤드와 표본 한계를 적는다.

### 9.4 4단계: 가설과 후보

“고객 목록 선형 검색이 전체 CPU의 35%이므로 집합 변환으로 줄일 수 있다”처럼 원인·변경·예상 지표를 연결한다. 한 번에 여러 변경을 섞지 않는다.

### 9.5 5단계: 최소 구현과 정확성 시험

자료구조, 스트림, 묶음, 캐시, 동시성 중 병목에 맞는 최소 변경을 한다. 기존 단위·회귀 시험과 경계·동시성 시험을 통과시킨다.

### 9.6 6단계: 동일 조건 비교

전후를 같은 환경·데이터로 여러 번 측정해 목표 지표와 다른 지표의 악화를 본다. CPU가 줄었지만 메모리와 지연 백분위가 악화될 수 있다.

### 9.7 7단계: 운영 검증과 문서화

점진 배포로 실제 지표와 오류를 관찰하고 원복 조건을 둔다. 선택 이유, 벤치마크, 적용 범위, 재평가 조건을 기록한다.

### 판단 기준

- 실제 병목 비중이 크고 반복 측정된다.
- 최적화 후 업무 결과와 오류 의미가 동일하다.
- 목표 지표 개선이 측정 변동보다 충분히 크다.
- 메모리·쓰기·외부 부하·가독성 악화가 수용 가능하다.
- 변경을 시험·관찰·원복할 수 있다.

## 10. 구체 시나리오

### 상황

한 요청에서 20만 건의 이벤트 중 관심 ID 목록에 속한 항목을 고른다. 프로파일링 결과 리스트 membership이 CPU의 대부분이고 관심 ID는 중복 없이 5천 개다.

### 최적화

1. 관심 ID를 한 번 집합으로 변환한다.
2. 이벤트는 전체 결과 리스트 대신 스트림으로 순회한다.
3. 결과가 매우 클 수 있으므로 제한된 묶음으로 후속 처리한다.
4. 기준·중복·빈 목록·큰 입력 결과가 기존과 같은지 시험한다.
5. 집합 생성 시간과 추가 메모리를 포함해 전후를 측정한다.

입력이 3건뿐인 경로까지 같은 구조가 유리하다고 단정하지 않는다. 입력 크기별 교차점을 기록한다.

## 11. 산출물과 체크리스트

주요 산출물은 성능 목표, 재현 스크립트·데이터, 프로파일, 병목·가설 목록, 변경 코드, 정확성·회귀·부하 결과, 전후 비교와 운영 관찰 계획이다.

- 사용자 영향과 연결된 목표 지표가 있는가?
- 기준선의 환경·데이터·워밍업을 기록했는가?
- 프로파일러로 실제 큰 비용을 찾았는가?
- 알고리즘·자료구조의 의미 차이를 확인했는가?
- 스트림의 수명·한 번 순회·예외 특성을 고려했는가?
- 캐시에 상한·무효화·민감정보 분리가 있는가?
- 동시성이 외부 한도·연결 풀과 맞는가?
- 같은 조건에서 여러 번 전후를 비교했는가?
- 정확성·동시성·회귀 시험이 통과했는가?
- 점진 배포·관찰·원복 조건이 있는가?

## 12. 자주 틀리는 함정

1. 측정 전에 미세 최적화를 시작하지 않는다.
2. 평균 응답만 보고 꼬리 지연과 오류율을 놓치지 않는다.
3. 빅오가 좋다는 이유만으로 작은 입력의 메모리·준비 비용을 무시하지 않는다.
4. 문자열 연결 최적화를 모든 짧은 코드에 적용하지 않는다.
5. 이터레이터를 여러 번 순회할 수 있다고 가정하지 않는다.
6. 무제한 캐시를 성능 해결책으로 쓰지 않는다.
7. 비동기·스레드 수가 많을수록 처리량이 계속 오른다고 보지 않는다.
8. 마이크로벤치마크를 전체 시스템 성능과 동일시하지 않는다.
9. 런타임 옵션을 근거 없이 복사하지 않는다.
10. 성능 이익 때문에 정확성·가독성·복구 가능성을 잃지 않는다.

## 13. 확인 문제

### 문제 1

최적화 전에 기준선을 측정해야 하는 이유는 무엇인가?

**정답과 해설:** 실제 병목과 현재 변동을 알고 변경 효과를 같은 조건에서 비교하기 위해서다.

### 문제 2

목록 membership을 집합으로 바꿀 때 확인할 비용은 무엇인가?

**정답과 해설:** 집합 생성 시간과 메모리, 순서·중복 의미, 값의 해시 가능성을 확인한다.

### 문제 3

스트리밍이 메모리를 줄이면서 만드는 제약 두 가지는 무엇인가?

**정답과 해설:** 한 번만 순회할 수 있고 자원 수명이 순회 동안 유지될 수 있다. 오류도 늦게 발생할 수 있다.

### 문제 4

캐시 설계에 필요한 요소 네 가지를 쓰시오.

**정답과 해설:** 키, 최대 크기, 만료·무효화, 최신성 기준을 들 수 있다. 민감정보와 장애 재구축도 확인한다.

### 문제 5

비동기 처리로 CPU 계산이 자동 빨라지지 않는 이유는 무엇인가?

**정답과 해설:** 비동기는 주로 입출력 대기 중 다른 작업을 진행하게 하며 CPU 연산량 자체를 줄이지 않기 때문이다.

### 문제 6

동시성 상한을 결정할 요소 세 가지는 무엇인가?

**정답과 해설:** 외부 호출 한도, 연결 풀·CPU·메모리, 목표 처리량과 지연을 들 수 있다.

### 문제 7

JIT 런타임에서 워밍업을 기록해야 하는 이유는 무엇인가?

**정답과 해설:** 초기 컴파일·최적화 전 성능과 안정 상태 성능이 달라질 수 있기 때문이다.

### 문제 8

최적화 전후 정확성 시험이 필요한 이유는 무엇인가?

**정답과 해설:** 순서, 중복, NULL, 예외 처리 등 업무 의미가 성능 변경으로 달라질 수 있기 때문이다.

### 문제 9

CPU 사용량이 줄었으면 항상 최적화에 성공한 것인가?

**정답과 해설:** 아니다. 응답·처리량, 메모리, 입출력, 오류, 외부 부하와 가독성까지 목표에 맞는지 확인해야 한다.

## 14. 핵심 요약

- **언어 특성을 활용한 애플리케이션 최적화**는 실제 병목에 자료구조, 스트림, 할당, 입출력, 동시성, 런타임 특성을 적용하는 활동이다.
- 성능은 응답·처리량·CPU·메모리·입출력·GC·큐를 함께 측정한다.
- 알고리즘 이익과 준비·메모리 비용, 스트림·캐시·동시성의 제약을 함께 본다.
- **언어특성 활용하기의 적용 절차와 판단 기준**은 목표, 기준선, 프로파일, 가설, 최소 변경, 동일 조건 비교, 운영 검증으로 구성한다.
- 정확성·회귀 시험과 점진 배포·원복을 성능 측정과 함께 수행한다.
- 복잡한 미세 최적화보다 사용자 병목의 큰 비용을 먼저 줄인다.
