# 1-10-3-1. 필요 라이브러리 검색과 선택 · 언어 특성에 맞는 라이브러리 구성

## 수행 범위와 목표

이 레슨의 정확한 토픽은 **필요 라이브러리 검색과 선택**과 **언어 특성에 맞는 라이브러리 구성**이다. 구현 요구를 재사용 가능한 기능으로 분해해 후보 라이브러리를 찾고, 기능·호환성·보안·라이선스·유지보수·성능·의존성 기준으로 비교하며, 선택한 언어의 패키지·모듈·빌드 체계에 맞는 의존성 구성을 설계하는 실무를 다룬다.

선택 라이브러리를 코드에 실제 적용하고 갱신·제거까지 검증하는 절차는 다음 레슨의 범위다. 여기서는 근거 있는 선택과 재현 가능한 구성 기준선을 만드는 데 집중한다.

학습 목표는 다음과 같다.

1. 요구 기능과 품질·운영 제약을 검색 질문으로 변환한다.
2. 공식 문서·저장소·보안·라이선스·유지 상태를 근거로 후보를 평가한다.
3. 직접·전이 의존성, 버전 범위, 잠금, 개발·운영 의존성을 구분한다.
4. 언어의 모듈·패키지·빌드 관습에 맞춰 충돌과 숨은 전역 의존성을 줄인다.

## 1. 라이브러리의 역할

라이브러리는 응용 프로그램이 호출해 사용하는 재사용 코드 집합이다. 패키지는 라이브러리와 메타데이터를 배포하는 단위일 수 있고, 프레임워크는 실행 흐름과 구조를 더 넓게 제어할 수 있다.

| 용어 | 중심 의미 |
|---|---|
| 모듈 | 특정 책임을 캡슐화한 코드·이름 공간 단위 |
| 라이브러리 | 응용이 호출하는 재사용 기능 집합 |
| 패키지 | 버전·의존성·배포 정보가 있는 설치 단위 |
| 프레임워크 | 규약과 실행 흐름을 제공하고 사용자 코드를 호출 |
| 패키지 관리자 | 검색·설치·해결·갱신·제거 상태 관리 |

한 라이브러리가 여러 패키지로 나뉘거나 한 패키지에 여러 모듈이 포함될 수 있다. 이름을 혼용하지 않고 선택 대상과 배포 단위를 구분한다.

## 2. 필요 기능 정의

검색 전에 무엇이 필요한지 정한다.

    기능: CSV 입력 파싱
    필수 요구:
      - 헤더·따옴표·다국어 처리
      - 스트리밍 읽기
      - 최대 필드·행 크기 제한
      - 잘못된 행의 위치와 오류 반환
    품질 요구:
      - 대상 런타임 버전 지원
      - 상업 배포 가능한 라이선스
      - 알려진 취약점 대응 경로
      - 대용량 표본 성능 기준
    제외:
      - 원격 파일 다운로드
      - 임의 코드 실행 기능

단순히 “CSV 라이브러리”로 검색하면 과도한 기능이나 필요한 제한이 없는 후보를 고를 수 있다. 표준 라이브러리로 요구를 충족하는지도 먼저 확인한다.

## 3. 필요 라이브러리 검색과 선택

### 3.1 신뢰할 출처

언어·런타임 공식 문서, 공식 패키지 저장소, 프로젝트 공식 저장소와 보안 공지를 우선 확인한다. 검색 광고, 이름이 비슷한 패키지, 출처 불명 미러를 바로 설치하지 않는다. 패키지 이름 도용과 오타 유사 이름을 주의한다.

### 3.2 기능 적합성

필수 기능, 입력 제한, 오류 모델, 확장 지점, 플랫폼 지원을 표본 코드와 문서로 확인한다. 기능 목록에 “지원”이라고 써 있어도 필요한 규모·형식·예외까지 지원하는지 작은 기술 검증을 한다.

### 3.3 호환성

언어·런타임, 운영체제·CPU, 프레임워크, 다른 핵심 라이브러리와 지원 범위를 확인한다. 빌드 시 성공해도 실행 시 네이티브 의존성이나 클래스·모듈 충돌이 발생할 수 있다.

### 3.4 유지보수성과 성숙도

최근 릴리스 날짜 하나만 보지 않는다. 이슈 대응, 보안 공지, 변경 기록, 지원 정책, 버스 팩터, 문서·시험, 릴리스 서명과 중단 공지를 본다. 기능이 안정되어 변경이 적은 프로젝트를 무조건 방치로 판단하지 않고 문의·보안 대응 경로를 확인한다.

### 3.5 보안

알려진 취약점, 과거 대응 속도, 설치 스크립트, 네트워크·파일 접근, 파서 한도, 기본 설정을 검토한다. 자동 취약점 스캐너 결과는 출발점이며 실제 사용 버전·호출 경로·노출과 수정 버전을 분석한다.

라이브러리가 입력을 안전하게 처리한다고 가정하지 않는다. 최대 크기·시간 제한·허용 형식과 출력 문맥 인코딩은 응용 경계에서도 적용한다.

### 3.6 라이선스

사용, 수정, 재배포, 소스 공개, 고지, 특허 조항이 조직의 배포 방식과 맞는지 확인한다. 패키지 설명의 짧은 라이선스 이름뿐 아니라 실제 라이선스 파일과 전이 의존성을 검토하고 필요하면 법무·정책 담당자의 승인을 받는다.

### 3.7 성능과 자원

대표 데이터와 환경에서 지연, 처리량, 메모리, 시작 시간, 산출물 크기를 측정한다. 후보가 제공한 벤치마크는 환경·입력·버전이 다를 수 있으므로 재현한다. 가장 빠른 후보가 유지보수·정확성 기준을 충족하지 못하면 적합하지 않다.

### 3.8 API와 오류 모델

API가 업무 코드와 자연스럽게 결합되는지, 비동기·취소·시간 초과, 자원 해제, 스레드 안전성, NULL·오류 반환을 어떻게 표현하는지 본다. 전역 상태와 숨은 부작용이 많으면 시험과 병렬 실행이 어려울 수 있다.

### 3.9 대체·철회 가능성

라이브러리 API가 업무 코드 전반에 퍼지면 교체 비용이 커진다. 핵심 외부 라이브러리는 어댑터 경계로 감쌀 수 있는지, 데이터 형식이 독점적인지, 제거·이행 경로가 있는지 평가한다.

## 4. 후보 비교표

| 기준 | 가중 근거 | 후보 A | 후보 B | 확인 증거 |
|---|---|---|---|---|
| 필수 기능 | 없으면 탈락 | 충족 | 일부 | 표본 시험 |
| 런타임 호환 | 배포 필수 | 지원 | 지원 | 공식 지원표 |
| 보안 대응 | 외부 입력 처리 | 공지·수정 | 불명확 | 보안 정책 |
| 라이선스 | 상업 배포 | 승인 후보 | 검토 필요 | 라이선스 파일 |
| 성능 | 1GB 스트림 | 목표 충족 | 메모리 초과 | 자체 벤치마크 |
| 유지보수 | 3년 운영 | 명확 | 불명확 | 릴리스·이슈 |
| 전이 의존성 | 공격면·충돌 | 3개 | 25개 | 의존성 그래프 |

점수 합계만으로 필수 조건 탈락을 덮지 않는다. 보안 정책 없음이나 라이선스 불일치 같은 중단 조건을 별도로 표시한다.

## 5. 의존성 구조

### 5.1 직접·전이 의존성

프로젝트가 직접 선언한 라이브러리뿐 아니라 그 라이브러리가 필요로 하는 전이 의존성까지 최종 산출물에 포함될 수 있다. 버전 충돌, 취약점, 라이선스, 크기는 전체 그래프에서 확인한다.

    application
      ├─ parser-lib 2.x
      │    └─ text-core 3.x
      └─ report-lib 5.x
           └─ text-core 2.x

두 버전 요구가 동시에 해결되지 않으면 강제 설치보다 후보 버전, 호환 릴리스, 격리 또는 다른 라이브러리를 검토한다.

### 5.2 버전 제약과 잠금

명세의 버전 범위는 어떤 갱신을 허용할지 나타내고, 잠금 정보는 실제 검증한 직접·전이 버전을 기록한다. “최신”은 재현 가능한 버전이 아니다. 지나치게 넓은 범위는 설치 시점 결과를 바꾸고 지나치게 고정하면 보안 수정 반영이 늦을 수 있다.

언어 생태계마다 응용과 라이브러리 배포의 잠금 권장 방식이 다를 수 있으므로 공식 지침을 따른다.

### 5.3 개발·시험·운영 의존성

테스트, 린트, 문서 생성 도구와 운영 실행에 필요한 라이브러리를 분리한다. 개발 도구가 운영 산출물에 포함되면 크기와 공격 표면이 커진다. 반대로 런타임에 필요한 플러그인을 개발 전용으로 잘못 분류하면 운영에서 실패한다.

### 5.4 선택·플랫폼 의존성

특정 운영체제나 기능에서만 필요한 패키지는 조건을 명시하고 모든 지원 환경의 해결 결과를 시험한다. 개발자 장비에서 우연히 설치된 전역 패키지에 의존하지 않는다.

## 6. 언어 특성에 맞는 라이브러리 구성

### 6.1 모듈·이름 공간

언어의 공개·비공개 규칙으로 라이브러리 노출 범위를 제한한다. 외부 타입을 업무 모듈 곳곳에 직접 노출하지 않고 통합 모듈에서 감싼다. 이름 충돌은 별칭보다 명확한 모듈 경계와 의존 방향으로 줄인다.

### 6.2 동기·비동기 API

이벤트 루프 언어에서 동기 블로킹 라이브러리를 핵심 요청 경로에 쓰면 전체 처리가 멈출 수 있다. 비동기 API 지원, 작업자 격리, 취소·제한 시간을 확인한다. 함수가 async라고 내부가 비블로킹이라고 자동 판단하지 않는다.

### 6.3 자원 관리

파일·소켓·네이티브 메모리를 쓰는 라이브러리는 close, dispose, context manager, defer 등 언어의 관용적 해제 방식과 통합한다. 오류 경로와 조기 반환에서도 해제되는지 본다.

### 6.4 타입·오류 통합

동적 언어에서는 타입 힌트·검증 래퍼, 정적 언어에서는 제네릭·결과 타입을 활용해 계약을 드러낸다. 외부 라이브러리의 모든 예외를 삼키지 말고 내부 오류 범주로 변환하면서 원인은 보호된 로깅에 연결한다.

### 6.5 의존성 주입과 설정

업무 코드가 전역 단일 객체를 직접 만들지 않고 인터페이스를 통해 주입받으면 시험 대역과 교체가 쉽다. 엔드포인트·제한 시간·기능 토글은 외부 설정에 두고 비밀은 별도 보안 저장소에서 주입한다.

## 7. 구성 명세 예시

다음은 특정 패키지 관리자 문법이 아닌 논리 예다.

    dependencies:
      runtime:
        csv-parser:
          version-policy: reviewed-compatible-range
          selected-version: locked-version
          reason: streaming + bounded parsing
          source: approved-registry
      development:
        test-runner:
          version-policy: reviewed-range
      platform:
        native-helper:
          condition: supported-platform-only

    controls:
      verify-integrity: true
      allow-unapproved-source: false
      vulnerability-review: required
      license-review: recorded

실제 버전·출처는 프로젝트 승인 자료를 사용하고 비밀 저장소 주소·토큰은 명세에 넣지 않는다.

## 8. 검색·선택·구성 절차

1. **요구·제약 정의**: 기능, 입력 규모, 지원 환경, 보안·라이선스, 성능 기준을 정한다.
2. **표준 기능 확인**: 언어 표준 라이브러리와 기존 승인 사내 구성 요소를 먼저 검토한다.
3. **후보 검색**: 공식 저장소·문서에서 여러 후보와 대체안을 모은다.
4. **필수 조건 선별**: 호환성, 라이선스, 보안, 필수 기능 미충족 후보를 제외한다.
5. **기술 검증**: 대표·경계·악성 입력과 자원·오류 동작을 작은 코드로 시험한다.
6. **전체 그래프 검토**: 전이 의존성, 충돌, 취약점, 라이선스, 산출물 크기를 본다.
7. **구성 기준선**: 직접·개발·플랫폼 의존성과 범위·잠금을 기록한다.
8. **선택 결정**: 증거, 가정, 거절 대안, 재검토 조건과 소유자를 남긴다.

## 9. 구체 시나리오

### 상황

외부 고객이 올린 압축 파일을 검사해야 한다. 후보 라이브러리는 빠른 A와 문서·제한 API가 명확한 B다.

### 선택 판단

- 경로 순회, 압축 폭탄, 중첩 깊이, 파일 개수·총 해제 크기 제한을 지원하는지 시험한다.
- 손상 파일과 암호화 파일의 오류 모델을 확인한다.
- 스트리밍 추출과 취소·시간 제한, 자원 해제를 검증한다.
- 네이티브 코드 포함 여부와 지원 플랫폼을 확인한다.
- 취약점 공지와 라이선스, 전이 의존성을 비교한다.

A가 정상 작은 파일에서 더 빠르더라도 크기 제한과 보안 대응이 불명확하면 외부 입력 경로에 적합하지 않을 수 있다. 직접 압축 형식을 구현하는 대안도 높은 보안·유지 비용이 있으므로 검증된 후보를 우선한다.

## 10. 산출물과 체크리스트

주요 산출물은 기능·품질 요구표, 후보 목록, 비교·탈락 근거, 기술 검증 결과, 보안·라이선스 검토, 의존성 그래프, 구성·잠금 기준선, 선택 결정 기록이다.

- 표준 라이브러리와 기존 승인 구성 요소를 먼저 확인했는가?
- 필수 기능과 제외 범위, 입력 규모를 정의했는가?
- 공식 출처·문서·보안 공지를 확인했는가?
- 지원 런타임·플랫폼과 실제 배포 환경을 시험했는가?
- 전체 전이 의존성의 취약점·라이선스를 검토했는가?
- 대표·경계·악성 입력과 자원 해제를 시험했는가?
- 직접·개발·플랫폼 의존성을 구분했는가?
- 버전 범위와 실제 잠금 결과가 재현 가능한가?
- 외부 API를 격리할 모듈·어댑터 경계가 있는가?
- 선택·탈락 근거와 재검토 조건이 남아 있는가?

## 11. 자주 틀리는 함정

1. 다운로드 수와 별점만으로 신뢰성을 판단하지 않는다.
2. 이름이 비슷한 패키지를 공식 패키지라고 가정하지 않는다.
3. 직접 의존성만 보고 전이 취약점·라이선스를 빼먹지 않는다.
4. 최신 버전이라는 이유만으로 호환·보안 검증을 생략하지 않는다.
5. 자동 취약점 결과 개수만으로 실제 위험을 결정하지 않는다.
6. 점수 합계로 라이선스·필수 기능 탈락을 상쇄하지 않는다.
7. 전역 설치에서 동작한 것을 재현 가능한 구성으로 보지 않는다.
8. 비동기 언어에서 동기 블로킹 라이브러리를 확인 없이 사용하지 않는다.
9. 라이브러리 타입을 업무 전체에 퍼뜨려 교체 비용을 키우지 않는다.
10. 설치 스크립트도 실행 코드라는 사실을 잊지 않는다.

## 12. 확인 문제

### 문제 1

라이브러리 검색 전 정의할 항목 네 가지를 쓰시오.

**정답과 해설:** 필수 기능, 입력 규모, 지원 환경, 보안·라이선스 기준을 들 수 있다. 성능과 제외 범위도 필요하다.

### 문제 2

전이 의존성을 검토해야 하는 이유는 무엇인가?

**정답과 해설:** 최종 산출물에 포함되어 버전 충돌, 취약점, 라이선스와 크기에 영향을 줄 수 있기 때문이다.

### 문제 3

버전 범위와 잠금 정보의 차이는 무엇인가?

**정답과 해설:** 범위는 허용할 해결 정책이고 잠금은 실제 검증·선택된 직접·전이 버전 결과다.

### 문제 4

최근 릴리스가 없다는 이유만으로 방치 프로젝트라고 단정하면 안 되는 이유는 무엇인가?

**정답과 해설:** 기능이 안정되어 변경이 적을 수 있다. 보안·이슈 대응 경로와 지원 정책을 함께 확인한다.

### 문제 5

개발 전용 의존성을 운영에서 분리하는 이유는 무엇인가?

**정답과 해설:** 운영 산출물 크기, 공격 표면, 취약점·라이선스 관리 범위를 줄이기 위해서다.

### 문제 6

외부 라이브러리를 어댑터로 감싸는 이점은 무엇인가?

**정답과 해설:** 업무 코드 결합을 줄이고 시험 대역, 오류 변환, 교체·업그레이드 영향을 한 경계에서 관리할 수 있다.

### 문제 7

비동기 API라는 이름만으로 비블로킹을 보장할 수 없는 이유는 무엇인가?

**정답과 해설:** 내부에서 동기 파일·네트워크 호출이나 CPU 작업을 실행할 수 있으므로 문서와 실제 추적·시험이 필요하다.

### 문제 8

라이브러리 후보 점수와 별도로 중단 조건을 두는 이유는 무엇인가?

**정답과 해설:** 라이선스 불일치, 필수 기능 누락, 치명 취약점은 다른 장점 점수로 상쇄할 수 없기 때문이다.

### 문제 9

압축 처리 라이브러리의 보안 시험 항목 네 가지를 쓰시오.

**정답과 해설:** 경로 순회, 총 해제 크기·파일 수, 중첩 깊이, 손상 파일 처리를 들 수 있다. 제한 시간과 자원 해제도 확인한다.

## 13. 핵심 요약

- **필요 라이브러리 검색과 선택**은 기능·환경·보안·라이선스·성능·유지보수·오류 모델을 증거로 비교하는 활동이다.
- 공식 출처와 표준 기능을 우선 확인하고 대표·경계·악성 입력을 직접 시험한다.
- 직접·전이 의존성 전체의 버전, 취약점, 라이선스와 산출물 크기를 검토한다.
- **언어 특성에 맞는 라이브러리 구성**은 모듈, 동기·비동기, 자원 관리, 타입·오류, 의존성 주입, 패키지 기준선에 맞게 구성하는 일이다.
- 버전 범위와 잠금 결과, 개발·운영·플랫폼 의존성을 구분해 재현성을 확보한다.
- 선택 근거와 거절 대안, 재검토 조건을 기록해 다음 적용 단계의 기준선으로 사용한다.
