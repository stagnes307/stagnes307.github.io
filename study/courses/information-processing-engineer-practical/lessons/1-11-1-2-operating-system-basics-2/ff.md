# 1-11-1-2. 운영체제 기능으로 작업 우선순위 조정

## 수행 범위와 목표

이 레슨의 정확한 토픽은 **운영체제 기능으로 작업 우선순위 조정**과 **운영체제 기초 활용하기의 적용 절차와 판단 기준**이다. 스케줄러의 우선순위, CPU·입출력·메모리·프로세스 자원 제어를 이해하고, 사용자 응답 작업과 배치·백그라운드 작업이 함께 실행될 때 측정과 승인에 따라 안전하게 우선순위를 조정하는 실무를 다룬다.

운영체제 종류와 기본 CLI·GUI 조회는 앞 레슨에서 다뤘다. 여기서는 실제 서비스 영향이 있는 우선순위 변경을 진단·조정·관찰·원복하는 절차에 집중한다.

학습 목표는 다음과 같다.

1. 우선순위, 시간 할당, CPU 친화도, 자원 한도의 차이를 설명한다.
2. CPU 병목과 입출력·잠금·메모리 병목을 지표로 구분한다.
3. 사용자 지연, 처리량, 공정성, 기아·우선순위 역전을 고려해 조정한다.
4. 최소 범위·기간으로 변경하고 전후 측정과 원복 기준을 관리한다.

## 1. 스케줄링과 우선순위

운영체제 스케줄러는 실행 가능한 작업 중 CPU를 사용할 작업을 선택한다. 우선순위는 그 선택에 영향을 주는 하나의 신호이며 절대적인 실행 순서를 보장하는 단순 번호가 아니다.

    실행 가능 작업 큐
      ├─ 대화형 요청
      ├─ 웹 작업자
      ├─ 백업 압축
      └─ 통계 배치
          ↓ 우선순위·공정성·정책
       CPU 스케줄러

작업이 디스크·네트워크·잠금을 기다리면 우선순위를 높여도 CPU에서 할 일이 없어 빨라지지 않는다. 먼저 병목을 구분한다.

## 2. 작업 우선순위 관련 개념

### 2.1 프로세스·스레드 우선순위

운영체제는 프로세스 또는 스레드에 상대 우선순위·nice 값·우선순위 클래스를 제공할 수 있다. 구체 범위와 숫자 방향은 OS마다 다르다. “큰 숫자가 항상 높다”라고 외우지 말고 대상 OS 공식 문서를 확인한다.

일반 사용자가 자기 작업의 우선순위를 낮출 수 있어도 높이려면 추가 권한이 필요할 수 있다. 관리자 권한으로 무리하게 높이면 시스템 서비스와 다른 사용자 작업을 방해할 수 있다.

### 2.2 동적 우선순위

대화형 응답성을 위해 입출력 대기 후 깨어난 작업을 일시 우대하거나 CPU를 오래 쓰는 작업을 조정하는 등 동적 정책이 있을 수 있다. 사용자가 지정한 기본 우선순위와 실제 순간 우선순위가 다를 수 있다.

### 2.3 CPU 친화도

특정 CPU 코어 집합에서만 작업하도록 제한한다. 캐시 지역성이나 라이선스·격리 목적에 도움 될 수 있지만 사용 가능한 코어를 줄여 처리량을 떨어뜨릴 수 있다. 우선순위와 같은 개념이 아니며 NUMA·컨테이너·가상 CPU 환경을 고려한다.

### 2.4 CPU·메모리·입출력 한도

컨테이너·서비스 관리자는 CPU 할당량, 가중치, 메모리 한도, 입출력 우선순위·대역폭을 제공할 수 있다. CPU 우선순위만 바꿔도 디스크를 포화시키는 배치 문제는 해결되지 않는다. 실제 경쟁 자원에 맞는 제어를 사용한다.

### 2.5 전경·배경

전경은 사용자가 즉시 결과를 기다리는 작업, 배경은 지연 허용 작업으로 분류할 수 있다. GUI에서 창이 앞에 있다는 사실과 OS 스케줄링 우선순위는 같은 의미가 아니다. 업무 서비스 수준과 마감시간으로 분류한다.

## 3. 우선순위 조정의 위험

### 3.1 기아

높은 우선순위 작업이 계속 들어오면 낮은 작업이 장기간 실행 기회를 얻지 못할 수 있다. 로그 정리·백업 검증 같은 배경 작업이 계속 밀리면 나중에 장애가 된다. 최대 지연과 완료 기한을 정한다.

### 3.2 우선순위 역전

높은 우선순위 작업이 낮은 작업이 보유한 잠금을 기다리고, 중간 우선순위 작업이 낮은 작업의 실행을 막아 높은 작업이 더 늦어지는 현상이다.

    높은 작업 H ─ 잠금 대기 ─┐
                              │
    낮은 작업 L ─ 잠금 보유 ──┘
          ↑
    중간 작업 M이 CPU 점유 → L의 잠금 해제가 지연

일부 시스템은 우선순위 상속 같은 기법을 제공한다. 응용 잠금 범위를 줄이고 긴 임계구역을 피하는 설계도 중요하다.

### 3.3 시스템 불안정

실시간·최상위 클래스를 잘못 부여하면 관리 셸, 모니터링, 입출력 처리도 실행 기회를 잃어 시스템을 조작하기 어려울 수 있다. 운영에서 최고 우선순위를 시험 없이 사용하지 않는다.

### 3.4 결과 왜곡

배치 우선순위를 낮춰 사용자 응답은 좋아졌지만 마감시간을 넘길 수 있다. 한 지표만 개선하지 말고 사용자 지연과 배치 완료, 오류, 자원, 데이터 최신성을 함께 본다.

## 4. 병목 진단

### 4.1 CPU 병목

CPU 사용이 지속적으로 높고 실행 가능 큐가 길며 대상 작업이 계산 구간에서 시간을 쓴다. 코어별 편향과 가상 환경의 CPU 제한·steal 시간도 확인한다.

### 4.2 입출력 병목

CPU는 여유지만 디스크 지연·큐, 네트워크 대기, 파일시스템 잠금이 높다. CPU 우선순위보다 입출력 양·배치, 저장 구조, 동시성, 네트워크 원인을 본다.

### 4.3 메모리 압박

페이지 폴트·스왑·회수·GC와 프로세스 상주 메모리가 증가한다. 우선순위 상향보다 메모리 누수·한도·작업 크기를 해결해야 한다.

### 4.4 잠금·동기화

CPU가 낮아도 다수 스레드가 잠금·세마포어·DB 연결을 기다릴 수 있다. 프로파일·추적에서 대기 지점을 찾는다. 스레드 우선순위만 올리면 경합이 악화될 수 있다.

## 5. 안전한 조회 예시

우선순위를 바꾸기 전에 상태를 읽는다.

POSIX 계열의 개념적 조회:

    ps -o pid,ppid,user,pri,ni,stat,time,command -p <확인한_PID>

PowerShell의 읽기 전용 조회:

    Get-Process -Id <확인한_PID> |
      Select-Object Id, ProcessName, CPU, WorkingSet, StartTime

실제 옵션과 우선순위 속성은 OS·셸 버전에 따라 확인한다. PID는 재사용될 수 있으므로 이름·시작 시각·소유자·서비스와 함께 대상 프로세스를 확인한다.

GUI 작업 관리자·활동 모니터에서도 우선순위·CPU·메모리·입출력을 확인할 수 있다. 변경 메뉴가 보인다고 승인 없이 조정하지 않는다.

## 6. 운영체제 기능으로 작업 우선순위 조정 절차

### 6.1 1단계: 업무 목표 정의

어떤 사용자·배치의 어떤 목표를 개선할지 정한다.

    사용자 조회 p95: 승인 기준 이내
    야간 배치: 오전 업무 시작 전 완료
    백업 검증: 24시간 안에 완료

목표 사이 충돌을 드러낸다.

### 6.2 2단계: 기준선 수집

조정 전 동일 시간대의 CPU, 실행 큐, 입출력, 메모리, 잠금, 요청 지연, 배치 완료 시간을 기록한다. 일회성 순간값보다 일정 기간과 업무 부하를 본다.

### 6.3 3단계: 정확한 대상 확인

PID, 프로세스·서비스명, 사용자, 시작 시각, 부모, 실행 파일과 컨테이너를 확인한다. 같은 이름의 여러 작업 중 정확한 인스턴스를 고른다.

### 6.4 4단계: 병목·경쟁 자원 판정

CPU 경쟁인지 입출력·메모리·잠금인지 판단한다. CPU 경쟁이 아니면 우선순위 변경을 후보에서 제외한다. 작업 자체의 비효율과 일정 분리 같은 대안도 비교한다.

### 6.5 5단계: 최소 변경 설계

사용자 요청을 극단적으로 높이기보다 배치의 상대 우선순위를 한 단계 낮추거나 CPU 할당량을 제한하는 작은 변경을 검토한다. 적용 시간, 대상, 승인자, 원복값을 정한다.

### 6.6 6단계: 시험

비운영 또는 제한된 운영 범위에서 사용자 응답, 배치 처리량, 다른 서비스, 시스템 관리 응답을 함께 측정한다. 기아와 마감 위반을 확인한다.

### 6.7 7단계: 점진 적용·감시

일부 작업이나 짧은 시간에 적용하고 경보를 본다. CPU 큐, 사용자 백분위, 배치 예상 완료, 입출력, 오류를 비교한다.

### 6.8 8단계: 원복·기록

중단 기준에 도달하거나 이익이 없으면 즉시 원복한다. 변경 전후 설정·지표·결론과 재검토 조건을 기록한다. 재시작 후 우선순위가 유지되는지 서비스 설정도 확인한다.

## 7. 판단 기준표

| 질문 | 조정 적합 신호 | 다른 해결 우선 |
|---|---|---|
| 병목 자원 | CPU 실행 경쟁이 반복 측정됨 | 디스크·DB·네트워크 대기 |
| 업무 우선 | 대화형 지연과 배치 마감이 수치화됨 | “중요해 보임”만 있음 |
| 범위 | 특정 작업·시간대로 제한 가능 | 시스템 전체 최고 우선순위 |
| 공정성 | 낮은 작업 최대 지연을 감시함 | 기아·백업 지연을 모름 |
| 원복 | 이전값과 자동 복구 경로가 있음 | 변경 상태 추적 불가 |
| 권한 | 승인된 운영 절차와 최소 권한 | 임의 관리자 실행 |

## 8. 구체 시나리오

### 상황

오전 9시에 사용자 조회와 전날 통계 집계가 30분 겹친다. CPU가 포화되고 조회 p95가 목표를 넘지만 디스크 지연은 낮다. 통계는 오전 10시까지 완료하면 된다.

### 조정

1. 통계 프로세스와 사용자 서비스의 PID·소유·CPU 시간을 확인한다.
2. 조회 지연과 통계 예상 완료시간 기준선을 기록한다.
3. 통계의 CPU 상대 가중치를 소폭 낮추는 시험을 승인받는다.
4. 10분간 제한 적용해 조회 p95, CPU 큐, 통계 처리율을 측정한다.
5. 통계 예상 완료가 10시를 넘으면 변경 폭을 줄이거나 배치 시작 시간을 앞당기는 대안을 검토한다.
6. 서비스 재시작 때 설정이 사라지거나 영구화되는지 확인한다.

사용자 서비스를 최고 실시간 등급으로 올리는 것은 관리 불능 위험이 있어 첫 선택이 아니다.

### 변경 기록 예시와 중단 판정

운영 변경표에는 대상 서비스와 인스턴스, 변경 전·후 상대 우선순위, 적용 시작·종료 시각, 승인자, 원복 명령 또는 GUI 경로를 함께 적는다. 지표는 평균만 보지 말고 사용자 지연의 상위 백분위, 배치 처리율, 실행 큐, 오류율을 동일한 시간 구간으로 비교한다. 다음처럼 성공·중단 기준을 미리 정하면 결과에 따라 임의로 결론을 바꾸는 일을 줄일 수 있다.

| 판정 | 관찰 결과 | 조치 |
|---|---|---|
| 유지 후보 | 조회 p95 개선, 배치 마감 충족, 오류·기아 없음 | 관찰 시간을 늘린 뒤 승인 |
| 폭 조정 | 조회는 개선됐지만 배치 예상 완료가 마감에 근접 | 변경 폭 축소 또는 일정 분리 |
| 즉시 원복 | 관리 응답 저하, 오류 증가, 낮은 작업 장시간 정지 | 이전값 복원 후 원인 재분석 |
| 효과 없음 | 지연 변화가 없고 입출력 대기만 지속 | 우선순위 변경 종료, 실제 병목 해결 |

조정 뒤 CPU 사용률이 낮아졌다는 사실만으로 성공이라고 하지 않는다. 사용자가 기다리는 시간이 개선됐는지, 낮은 작업도 허용 시간 안에 진척되는지, 효과가 반복 측정되는지를 모두 만족해야 한다. 이는 기술 설정을 업무 서비스 수준과 연결하는 실기 판단이다.

## 9. 산출물과 체크리스트

주요 산출물은 업무 목표, 기준선 지표, 병목 분석, 대상 확인표, 변경·원복 계획, 시험·점진 적용 결과, 최종 설정과 운영 절차다.

- 사용자·배치 목표와 마감이 수치화됐는가?
- CPU·입출력·메모리·잠금 병목을 구분했는가?
- PID·사용자·시작 시각으로 정확한 작업을 확인했는가?
- 우선순위 숫자 의미를 대상 OS 공식 문서로 확인했는가?
- 최소 범위·기간·변경 폭을 선택했는가?
- 낮은 작업의 기아와 최대 지연을 감시하는가?
- 사용자 지연과 배치 완료를 함께 측정하는가?
- 관리자·모니터링 응답에 영향을 시험했는가?
- 원복 값·중단 기준·승인자가 있는가?
- 재시작 후 적용 정책과 변경 기록이 있는가?

## 10. 자주 틀리는 함정

1. 우선순위를 높이면 입출력 대기도 줄어든다고 생각하지 않는다.
2. OS마다 우선순위 숫자 방향이 같다고 외우지 않는다.
3. CPU 친화도와 우선순위를 같은 것으로 보지 않는다.
4. 사용자 프로세스를 최고 실시간 등급으로 올리지 않는다.
5. 순간 CPU 사용만 보고 병목을 결론 내리지 않는다.
6. 낮은 작업의 기아와 배치 마감 실패를 놓치지 않는다.
7. 우선순위 역전을 단순히 높은 작업의 우선순위 부족으로 오해하지 않는다.
8. PID만 보고 오래된 다른 프로세스를 조정하지 않는다.
9. GUI 변경은 기록·원복이 필요 없다고 생각하지 않는다.
10. 효과가 없는 설정을 관성적으로 영구화하지 않는다.

## 11. 확인 문제

### 문제 1

CPU 우선순위를 높여도 네트워크 대기 작업이 빨라지지 않을 수 있는 이유는 무엇인가?

**정답과 해설:** 작업이 CPU 실행이 아니라 외부 입출력 완료를 기다리므로 CPU 선택 우선순위가 병목이 아니기 때문이다.

### 문제 2

기아란 무엇인가?

**정답과 해설:** 높은 우선순위 작업이 계속 실행되어 낮은 작업이 장기간 실행 기회를 얻지 못하는 현상이다.

### 문제 3

우선순위 역전의 핵심 구조는 무엇인가?

**정답과 해설:** 높은 작업이 낮은 작업의 잠금을 기다리는데 중간 작업이 낮은 작업 실행을 막아 잠금 해제가 늦어지는 구조다.

### 문제 4

CPU 친화도와 우선순위의 차이는 무엇인가?

**정답과 해설:** 친화도는 실행 가능한 CPU 집합을 제한하고 우선순위는 실행 가능한 작업 사이 선택에 영향을 준다.

### 문제 5

우선순위 변경 전 대상 프로세스를 확인할 항목 네 가지는 무엇인가?

**정답과 해설:** PID, 프로세스·서비스명, 사용자, 시작 시각을 들 수 있다. 부모·실행 파일도 확인한다.

### 문제 6

배치 우선순위를 낮춘 뒤 함께 측정할 두 업무 지표는 무엇인가?

**정답과 해설:** 사용자 응답 지연과 배치 예상 완료·처리량을 함께 측정한다.

### 문제 7

최소 변경이 중요한 이유는 무엇인가?

**정답과 해설:** 시스템 전체 공정성과 관리 응답에 미치는 피해를 줄이고 원인·효과를 분리하며 쉽게 원복하기 위해서다.

### 문제 8

우선순위 조정 대신 일정 분리를 우선할 수 있는 경우는 무엇인가?

**정답과 해설:** 사용자 부하와 배치가 특정 시간에만 겹치고 배치 시작 시간을 옮겨 목표를 만족할 수 있는 경우다.

### 문제 9

재시작 후 설정을 확인해야 하는 이유는 무엇인가?

**정답과 해설:** 수동 변경이 사라지거나 반대로 서비스 설정에 영구화되어 예상치 못한 시점에도 적용될 수 있기 때문이다.

## 12. 핵심 요약

- **운영체제 기능으로 작업 우선순위 조정**은 CPU 경쟁에서 상대 실행 기회를 바꾸는 활동이며 입출력·메모리·잠금 문제와 구분한다.
- 우선순위, CPU 친화도, 자원 할당량과 전경·배경 업무는 서로 다른 개념이다.
- 기아, 우선순위 역전, 시스템 관리 불능과 배치 마감 실패를 함께 고려한다.
- **운영체제 기초 활용하기의 적용 절차와 판단 기준**은 목표, 기준선, 대상, 병목, 최소 변경, 시험, 점진 적용, 원복·기록으로 구성한다.
- OS별 우선순위 의미를 공식 문서로 확인하고 관리자 권한·최상위 등급을 첫 해결책으로 쓰지 않는다.
- 사용자 지연과 낮은 작업의 완료를 함께 측정해 공정성과 업무 목표를 균형 있게 판단한다.
