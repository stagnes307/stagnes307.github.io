# 1-11-4-1. 선정 운영체제 설치·운용 · 개발도구 설치·운용

## 수행 범위와 학습 목표

이 레슨은 프로젝트 요구와 승인 기준에 따라 **선정 운영체제 설치·운용**을 수행하고, 언어·런타임·편집기·빌드·형상·시험 도구를 일관된 기준으로 구성하는 **개발도구 설치·운용**을 다룬다. 다음 레슨의 웹서버·DB서버 설치와 전체 개발환경 적용 절차는 주범위를 침범하지 않도록, 여기서는 개발자 작업 호스트의 운영체제와 도구체인에 집중한다.

특정 운영체제·도구·버전은 프로젝트마다 달라지고 지원 상태도 변한다. 제품명을 암기하기보다 요구–호환성–지원–보안–재현성–운영성 기준으로 선택하고, 실제 설치는 공식 배포처·지원 문서와 조직 정책을 따른다.

학습 후에는 다음을 할 수 있어야 한다.

- 기능·자원·호환성·지원·라이선스 요구로 운영체제 선정 근거를 설명한다.
- 설치 전 자료 보호·부팅·저장장치·네트워크·계정·복구 계획을 세운다.
- 운영체제를 승인 매체로 설치하고 패치·최소 서비스·권한 기준선을 적용한다.
- 계정, 프로세스, 저장공간, 로그, 시간, 업데이트를 관찰·운용한다.
- 프로젝트 도구체인과 버전 호환표를 만들고 승인 출처에서 설치한다.
- 환경 변수·경로·프로젝트 설정·캐시를 재현 가능하게 관리한다.
- 대표 소스를 빌드·시험해 환경 완료 여부와 문제 원인을 판단한다.

## 입력자료와 선정 기준

운영체제와 도구 설치 전에 다음 입력자료를 확인한다.

- 응용 아키텍처, 대상 언어·프레임워크·런타임
- 개발·시험·운영 배포 대상과 호환 요구
- CPU 구조, 메모리, 저장장치, 그래픽·가상화 장치
- 빌드 시간, 동시 작업, 데이터량, 로컬 서비스 요구
- 조직 보안 기준, 네트워크·계정·패치·암호화 정책
- 지원 기간, 유지보수 채널, 라이선스·비용·조달 조건
- 기존 표준 이미지, 자동 구성, 백업·복구 절차
- 팀 숙련도와 지원 책임, 원격·현장 근무 조건

“개발자가 익숙하다”는 하나의 운영성 요소일 수 있지만 단독 근거는 아니다. 배포 대상과 파일 경로·문자 처리·대소문자·줄바꿈·시스템 라이브러리 차이가 크면 개발–운영 불일치가 결함을 만든다. 동일 계열 환경, 가상화·컨테이너, 자동화된 호환 시험 같은 대안을 비교한다.

| 기준 | 확인 질문 | 증거 |
|---|---|---|
| 기능·호환 | 언어·도구·장치·가상화가 지원되는가? | 지원 행렬·대표 빌드 결과 |
| 성능·자원 | 빌드·시험 동시 실행에 충분한가? | 사용량·빌드 시간 측정 |
| 지원성 | 지원 종료·업데이트·장애 지원 경로는? | 공급자·조직 지원 정책 |
| 보안 | 패치·암호화·계정·감사 기준을 지원하는가? | 기준선 점검 결과 |
| 운영성 | 자동 설치·복구·팀 지원이 가능한가? | 이미지·절차·복구 시험 |
| 비용·법적 | 라이선스·배포·상용 이용 조건이 맞는가? | 승인·계약 기록 |

## 설치 전 계획과 자료 보호

기존 장비라면 설치 방식이 초기화·이중 부팅·별도 디스크·가상 머신 중 무엇인지 확인한다. 파티션 변경과 포맷은 데이터를 잃을 수 있으므로 대상 디스크를 식별하고 필요한 자료를 승인 저장소에 백업한다. 백업 파일 존재만 보지 않고 대표 복원과 암호화 키·복구정보 접근을 확인한다.

설치 계획에는 다음을 포함한다.

- 승인 이미지의 출처·버전·무결성 확인값
- 대상 장비 식별자와 CPU·메모리·디스크·펌웨어 호환
- 부팅 방식과 디스크·파일시스템·암호화·복구키 정책
- 호스트 이름, 네트워크, 이름 해석, 시간대·시간 동기화
- 관리자·일반 사용자, 인증, 원격 접근, 화면 잠금 정책
- 필수 장치 드라이버·관리 에이전트와 불필요 구성 제외
- 설치 후 업데이트·기준선·검증·되돌리기 절차

복구키를 암호화 대상 디스크에만 저장하면 장치 장애 때 사용할 수 없다. 승인된 별도 보관과 접근 이력을 둔다. 설치 매체와 이미지가 공식 출처인지, 전송 중 변조되지 않았는지 조직의 검증 절차로 확인한다.

## 운영체제 설치 절차

1. 변경 승인과 대상 장비·백업·복원 가능성을 확인한다.
2. 승인 이미지·설치 매체·무결성·지원 CPU 구조를 확인한다.
3. 부팅 환경과 저장장치를 확인해 정확한 대상만 선택한다.
4. 계획된 파티션·파일시스템·암호화와 복구정보를 구성한다.
5. 기본 지역·문자·시간대·네트워크를 프로젝트 정책에 맞춘다.
6. 초기 관리자와 일반 개발 계정을 분리하고 강한 인증을 적용한다.
7. 첫 부팅 후 공식 업데이트와 승인 장치 드라이버를 적용한다.
8. 불필요 서비스·공유·원격 접근을 끄고 방화벽·화면 잠금 기준선을 적용한다.
9. 시간 동기화·이름 해석·저장공간·로그·업데이트 상태를 검증한다.
10. 설치 결과·버전·설정·예외·복구 절차를 자산·형상 기록에 남긴다.

설치 화면에서 기본값을 계속 선택하는 것이 표준 설치는 아니다. 표준은 요구와 승인된 기준선이 정의한 값이다. 자동 설치를 사용하면 스크립트·응답 파일의 비밀과 파괴 대상 지정이 안전한지 검토하고, 작은 시험 대상에서 검증한 뒤 적용한다.

## 계정·권한 운용

개발자는 일상 작업에 일반 권한 계정을 사용하고, 시스템 설치·설정 변경 때만 승인된 방식으로 권한을 상승한다. 관리자 계정을 공유하지 않고 개인 행위를 추적한다. 휴면·퇴직·장비 반납 시 계정·키·원격 세션을 회수한다.

서비스가 필요한 경우 사람 계정과 분리된 비대화형 주체를 사용한다. 로그인 금지, 필요한 디렉터리·서비스 권한만 부여하고 비밀 교체 책임을 정한다. 개발 편의를 위해 전체 파일시스템 쓰기나 보안 설정 해제 권한을 상시 부여하지 않는다.

파일·디렉터리 권한은 소스, 빌드 캐시, 비밀, 로그, 공유 작업공간의 소유자를 구분한다. 모든 사용자 쓰기가 가능한 경로를 실행 도구 검색 경로 앞쪽에 두면 의도하지 않은 실행 파일이 선택될 수 있다. 시스템 경로와 프로젝트 도구 경로의 우선순위를 검토한다.

## 업데이트와 소프트웨어 기준선

운영체제 업데이트는 보안·안정성에 필요하지만 개발 도구 호환성에 영향을 줄 수 있다. 업데이트 채널, 검토·시험, 적용 주기, 긴급 처리, 재부팅·되돌리기 조건을 정한다. 지원 종료된 운영체제는 패치가 제공되지 않을 수 있으므로 업그레이드 계획과 기한을 둔다.

기준선은 운영체제 버전만이 아니라 설치 구성요소, 업데이트 수준, 드라이버, 보안 정책, 서비스, 네트워크 설정, 관리 에이전트를 포함한다. 기준선에서 벗어난 변경을 탐지하고 승인·예외·만료를 기록한다.

개발자가 문제 해결을 위해 방화벽·인증서 검증·악성 코드 방어를 임시로 끄는 경우가 있다. 원인 범위를 좁힌 뒤 승인된 대안을 적용하고 즉시 복원·검증한다. 임시 해제를 문서 없이 영구화하지 않는다.

## 운영 관찰과 기본 진단

운영체제 운용에서는 다음을 정기적으로 확인한다.

| 영역 | 관찰 항목 | 판단 예 |
|---|---|---|
| CPU | 사용률, 실행 큐, 상위 프로세스 | 지속 포화인지 짧은 빌드 버스트인지 |
| 메모리 | 사용·가용·스왑, 프로세스별 점유 | 누수·캐시·동시 시험 영향 구분 |
| 저장장치 | 여유, I/O 지연, 오류, inode 등 | 용량만이 아닌 쓰기 지연·파일 수 확인 |
| 네트워크 | 인터페이스, 주소, 손실·오류, 이름 해석 | 링크·IP·DNS·응용 범위 분리 |
| 프로세스·서비스 | 상태, 재시작, 시작 유형 | 필요한 서비스인지 반복 실패인지 |
| 로그·시간 | 오류, 감사, 시간 동기화 | 상관관계와 인증·빌드 시간 정확성 |
| 업데이트 | 누락·실패·재부팅 필요 | 기준선과 지원 정책 일치 |

자원 사용률 하나만 보고 원인을 확정하지 않는다. 빌드가 느리면 CPU, 메모리 압박, 저장장치 작은 파일 I/O, 네트워크 의존성 다운로드, 보안 검사 시간을 구분해 전후 측정한다. 로그 시각이 어긋나면 분산 빌드와 인증·인증서 문제 분석이 어려우므로 시간 동기화를 중요하게 본다.

장애 조치는 관찰→가설→최소 변경→재측정 순으로 수행한다. 여러 설정을 동시에 바꾸면 무엇이 원인이었는지 알 수 없다. 진단 결과와 원복 여부를 작업 기록에 남긴다.

## 개발도구 구성요소

개발도구는 다음 범주에서 프로젝트에 필요한 최소 조합을 선택한다.

- 소스 편집기 또는 통합개발환경과 승인 확장
- 컴파일러·인터프리터·런타임·SDK
- 빌드·패키지·의존성 관리 도구
- 형상관리 클라이언트와 변경 검토 도구
- 단위·통합 시험 실행기, 정적 분석·서식 도구
- 디버거·프로파일러·로그 관찰 도구
- API·데이터베이스 클라이언트와 안전한 로컬 모의 도구
- 문서 생성·모델링·업무 협업 도구

도구가 많을수록 좋은 환경은 아니다. 같은 책임의 도구가 여러 개면 설정과 결과가 달라진다. 팀 기준 도구와 버전·설정·운영 책임을 정하고 개인 선택 가능 범위를 구분한다.

## 버전 호환표와 선정

도구체인은 서로 의존한다. 언어 런타임, 빌드 도구, 프레임워크, 플러그인, 시험 실행기, 대상 운영체제·CPU 구조가 호환되어야 한다.

| 구성 | 기준 버전·범위 | 의존·호환 | 확인 방법 |
|---|---|---|---|
| 언어 런타임 | 프로젝트 기준선 | 프레임워크·빌드와 호환 | 공식 지원표·대표 빌드 |
| 빌드 도구 | 래퍼·잠금 기준 | 런타임과 플러그인 | 깨끗한 빌드·시험 |
| 편집기 확장 | 승인 목록 | 언어 서버·보안 정책 | 권한·출처·기능 시험 |
| DB/API 도구 | 지원 버전 | 서버 계약·인증 | 제한 계정 연결 시험 |
| 정적 분석 | 규칙 기준선 | 언어·생성코드 처리 | 대표 결함·오탐 판정 |

“최신 버전”이라는 움직이는 표현보다 검증된 기준 버전과 허용 범위를 기록한다. 업그레이드는 보안·지원 필요와 호환 위험을 함께 평가하고, 시험 환경에서 빌드·회귀·성능을 확인한다.

## 개발도구 설치

도구는 공식 또는 조직 승인 저장소에서 받고 서명·해시 등 제공되는 무결성 검증 절차를 따른다. 검색 결과의 비공식 배포본과 이름이 비슷한 패키지를 피한다. 설치에 관리자 권한이 필요한지 검토하고 가능한 사용자·프로젝트 범위 설치를 사용한다.

자동 설치 문서는 반복 가능해야 하지만 비밀, 개인 경로, 임시 다운로드 주소를 하드코딩하지 않는다. 설치 순서는 운영체제 전제, 런타임·SDK, 빌드 도구, 프로젝트 의존성, 편집·시험 도구 순으로 의존성을 반영한다. 실패 시 중간 상태와 다시 실행 가능성을 확인한다.

확장·플러그인은 소스·터미널·네트워크에 넓은 권한을 가질 수 있다. 게시자, 권한, 업데이트, 정보 전송, 조직 승인 여부를 확인한다. 프로젝트 파일이 임의 작업 실행을 요청할 수 있는 도구는 신뢰하지 않는 저장소를 열 때 제한 모드를 사용한다.

## 환경 변수·경로·프로젝트 설정

도구 경로는 명확한 우선순위로 구성하고 같은 명령 이름의 다른 버전이 먼저 선택되지 않는지 확인한다. 전역 설치를 최소화하고 프로젝트별 래퍼·잠금·격리 환경을 활용한다. 개인 셸 설정에만 의존하면 동료와 자동 빌드에서 재현되지 않는다.

환경 변수에는 비밀과 일반 설정을 구분한다. 비밀은 승인 저장소에서 주입하며 화면 캡처·진단 출력·프로세스 목록에 노출되지 않게 한다. 프로젝트 설정은 저장 가능한 비민감 기본값과 환경별 외부 설정을 분리한다.

문자 인코딩, 줄바꿈, 지역·시간대, 파일 대소문자 규칙은 운영체제 차이에서 결함을 만든다. 소스·빌드·시험의 명시적 기준을 두고 자동 검사한다. 절대 로컬 경로 대신 프로젝트 상대 경로와 도구가 제공하는 경로 API를 사용한다.

## 설치 검증과 재현성

도구의 버전 명령만 성공한다고 개발환경이 완성된 것은 아니다. 대표 프로젝트로 다음 흐름을 수행한다.

```text
승인 소스 받기
  → 잠금 정보로 의존성 복원
  → 깨끗한 빌드
  → 단위·정적 검사
  → 제한된 통합 시험
  → 산출물 해시·도구 버전 기록
  → 새 작업공간에서 반복
```

온라인 캐시가 없는 깨끗한 작업공간에서도 승인 경로로 복원되는지, 같은 소스에서 의미상 같은 산출물이 나오는지 확인한다. 사용자별 숨은 파일, 전역 패키지, 로컬 서비스가 성공을 우연히 만들지 않게 한다.

허용 시험뿐 아니라 권한 없는 저장소·운영 비밀·배포 경로 접근이 거부되는지도 확인한다. 빌드·시험 로그에 비밀과 개인정보가 없는지 살핀다. 환경 진단 보고서에는 운영체제·도구·설정 버전을 포함하되 자격증명 원문은 제외한다.

## 개발도구 운용과 변경

팀 온보딩 문서는 설치, 검증, 일반 작업, 업데이트, 캐시 정리, 문제 보고, 제거 절차를 제공한다. 특정 개발자만 아는 수동 단계를 줄이고 자동 구성은 형상관리·검토한다.

도구 업데이트는 변경 영향과 되돌리기를 포함한다. 런타임이나 빌드 도구가 바뀌면 잠금 파일·생성물·정적 규칙·산출물 호환이 달라질 수 있다. 변경 전후 깨끗한 빌드·시험·시간·경고를 비교한다. 긴급 보안 업데이트는 빠르게 처리하되 최소 회귀 시험과 기록을 생략하지 않는다.

사용하지 않는 도구·플러그인·자격증명을 제거한다. 캐시는 재현성 문제를 가리거나 저장공간·민감자료를 남길 수 있으므로 목적·경로·보존·정리 정책을 둔다. 라이선스 변경과 지원 종료를 정기 점검한다.

## 구체 실무 시나리오

팀이 서버 응용을 새 노트북에서 개발한다고 하자. 배포 대상과 같은 CPU 구조의 지원 운영체제를 선정하고, 16GB 메모리·충분한 저장공간·가상화 요구를 확인한다. 기존 자료는 승인 저장소에 백업하고 복원을 검증한다. 승인 이미지로 설치한 뒤 디스크 보호, 일반 개발 계정, 방화벽, 시간 동기화, 공식 업데이트 기준선을 적용한다.

도구 호환표에는 런타임, 프로젝트 빌드 래퍼, 시험 실행기, 편집기 확장을 기록한다. 전역 최신 버전에 기대지 않고 저장소의 래퍼와 잠금 파일로 의존성을 복원한다. 대표 프로젝트를 깨끗하게 빌드·시험하고, 다른 신규 계정에서도 같은 흐름이 성공하는지 확인한다.

한 개발자 환경에서만 빌드가 된다면 전역 패키지와 개인 환경 변수를 비교한다. 원인이 전역 코드 생성 도구임을 확인하면 프로젝트 의존성으로 고정하고 문서를 갱신한다. 수정 전후 빌드와 산출물 버전을 기록해 환경 결함이 다시 생기지 않게 한다.

## 산출물과 체크리스트

산출물은 운영체제·도구 요구표, 선정 대안·근거, 설치·복구 계획, 백업·복원 결과, 운영체제·보안 기준선, 자산·계정·서비스 목록, 도구체인·호환표, 자동 설치·프로젝트 설정, 대표 빌드·시험 결과, 운영·업데이트·장애 안내서다.

- [ ] 운영·개발 요구와 공식 지원 근거로 운영체제를 선정했다.
- [ ] 설치 대상과 백업·복원·복구키를 안전하게 확인했다.
- [ ] 일반 계정, 최소 서비스, 방화벽·업데이트·시간 기준선을 적용했다.
- [ ] CPU·메모리·저장공간·로그·네트워크를 관찰할 수 있다.
- [ ] 도구체인 버전·출처·호환성과 운영 책임이 명확하다.
- [ ] 관리자 권한·전역 도구·개인 설정 의존을 최소화했다.
- [ ] 비밀과 운영 데이터가 소스·로그·개발환경에 없다.
- [ ] 대표 프로젝트의 깨끗한 빌드·시험을 반복했다.
- [ ] 허용 접근과 거부 접근, 산출물 추적성을 확인했다.
- [ ] 업데이트·지원 종료·장애·제거·되돌리기 절차가 있다.

## 자주 틀리는 포인트

- 익숙한 운영체제를 호환·지원·보안 검토 없이 선택한다.
- 백업 파일 존재만 확인하고 복원과 복구키 접근을 시험하지 않는다.
- 개발자 일상 계정에 관리자 권한을 상시 부여한다.
- 운영 비밀과 실제 개인정보를 개발 환경에 복사한다.
- 운영체제 업데이트를 무기한 미루거나 검증 없이 즉시 전체 적용한다.
- 최신 개발도구를 개인별 전역 설치해 빌드 결과가 달라진다.
- 비공식 배포처와 과도한 권한의 편집기 확장을 사용한다.
- 개인 셸 환경 변수와 절대 경로에 프로젝트 성공이 의존한다.
- 버전 명령 성공만 보고 대표 빌드·거부 시험을 생략한다.
- 캐시를 항상 신뢰해 깨끗한 환경의 복원·빌드 문제를 놓친다.

## 정답과 해설

1. 기능·호환성, CPU·메모리·저장공간, 지원 기간, 보안 기준, 운영·복구성, 라이선스·비용, 팀 숙련 중 여섯 가지다.
2. 파티션·포맷·암호화 변경은 자료를 잃을 수 있고, 복구키나 백업이 실제로 읽히지 않으면 장애 때 복원할 수 없기 때문이다.
3. 일상 작업의 피해 범위를 줄이고 권한 상승 행위를 승인·추적하기 위해서다. 공유 관리자 계정은 책임과 회수를 불명확하게 한다.
4. OS·업데이트·드라이버, 보안 정책, 계정·권한, 서비스, 네트워크·시간, 관리 에이전트 중 다섯 가지다.
5. CPU·실행 큐, 메모리·스왑, 저장공간·I/O·파일 수, 네트워크·이름 해석, 프로세스·보안 검사·로그를 살핀다.
6. 구성요소, 기준 버전·범위, 의존·호환 관계, 공식 지원 근거, 검증 방법, 소유자·업데이트 정책을 포함한다.
7. 팀·자동 빌드가 같은 버전과 의존성을 사용해 개인 전역 환경의 숨은 차이를 줄이고 재현 가능한 결과를 얻기 위해서다.
8. 공식·승인 출처, 게시자, 요구 권한, 소스·터미널·네트워크 접근, 정보 전송, 업데이트·지원, 신뢰하지 않는 프로젝트 처리 방식을 본다.
9. 승인 소스·잠금·도구만으로 의존성 복원, 빌드, 시험이 가능하며 개인 캐시·전역 패키지에 우연히 의존하지 않음을 보여 준다.
10. 요구에 맞는 기준선이 적용되고 최소 권한·패치·비밀 보호가 확인되며 대표 빌드·시험이 반복 가능하고 관찰·업데이트·복구·추적 절차가 준비된 상태다.

## 핵심 요약

- 운영체제는 호환성·자원·지원·보안·운영·비용 근거로 선정한다.
- 설치 전에 대상·백업·복원·디스크·암호화·계정·네트워크·복구를 계획한다.
- 운용은 최소 권한, 업데이트 기준선, 자원·로그·시간 관찰과 복구를 포함한다.
- 개발도구는 승인 출처·버전 호환표·프로젝트별 고정 설정으로 설치한다.
- 개인 전역 환경과 비밀·운영자료 의존을 줄이고 깨끗한 대표 빌드로 검증한다.
- 완료는 설치 성공이 아니라 재현성·최소 권한·관찰·업데이트·복구·추적 증거로 판단한다.
