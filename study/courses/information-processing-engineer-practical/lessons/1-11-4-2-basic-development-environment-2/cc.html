01

수행 범위와 학습 목표

이 레슨은 개발·통합시험 환경에 필요한 웹서버·DB서버 등 기반 서버 설치·운용을 수행하고, 요구 조사부터 구성·검증·인수까지 기본 개발환경 구축의 적용 절차와 판단 기준을 정리한다. 앞 레슨의 개발자 운영체제·개발도구 설치를 반복하지 않고, 여러 개발자가 공유하는 기반 서비스의 용량·계정·네트워크·데이터·관찰·복구에 집중한다. 다음 레슨의 소프트웨어 패키징·릴리스 노트는 범위에서 제외한다.

특정 서버 제품의 명령과 설정 이름, 지원 버전은 달라질 수 있다. 실제 설치는 승인된 제품의 공식 지원 문서와 조직 표준을 따르고, 예시는 제품 중립적인 구조·의사 설정으로 이해한다.

학습 후에는 다음을 할 수 있어야 한다.

  • 응용 구조·동시 사용자·데이터량·보안·복구 요구로 기반 서버 사양을 정한다.
  • 웹·응용·DB·파일·캐시 등 서비스 책임과 신뢰경계를 배치한다.
  • 승인 출처와 최소 구성으로 서버를 설치하고 서비스 계정·경로·포트를 분리한다.
  • 웹서버의 문서 경로·가상 호스트·프록시·시간·크기·로그 정책을 구성한다.
  • DB서버의 데이터·로그·임시·백업 공간과 접속·권한·문자·시간 기준을 구성한다.
  • 정상·거부·장애·재시작·백업 복원·용량 시험으로 환경을 검증한다.
  • 패치·인증서·계정·용량·로그·백업을 지속 운용하고 완료를 근거로 판단한다.
02

요구사항과 입력자료

기반 서버는 “개발용이므로 아무 설정이나 허용”하는 장비가 아니다. 개발과 시험의 오류를 조기에 찾으려면 운영의 중요한 구조·통제를 합리적으로 재현해야 한다. 입력자료는 다음과 같다.

  • 응용 구성도, 통신 행렬, 인터페이스·포트·프로토콜
  • 동시 사용자·요청량·응답시간·배치·데이터 증가 예상
  • 운영체제·런타임·웹·DB 제품의 호환·지원 행렬
  • 데이터 분류, 인증·권한, 암호화·감사·보존 정책
  • 개발·통합·성능 시험의 격리·가용 시간·재설정 요구
  • 백업 주기, 복구 시점·복구 시간 목표와 복원 책임
  • 네트워크 구역·이름·주소·인증서·시간 동기화 정책
  • 자원·라이선스·장비·가상화·관리 도구 제약

“웹서버 한 대, DB 한 대”라는 수량부터 정하지 않는다. 요청 흐름과 책임, 장애 영역, 데이터 보호를 그린 뒤 필요한 인스턴스·자원을 산정한다. 공유 개발환경이면 프로젝트 간 포트·이름·데이터·계정·자원 한도를 분리한다.

03

논리 구성과 신뢰경계

코드 예시 · text

[개발자·시험 클라이언트]
        │ 허용 네트워크·TLS
        ▼
[웹서버/리버스 프록시]
        │ 내부 응용 포트
        ▼
[응용 서버]
        │ 제한된 DB 포트·서비스 계정
        ▼
[DB서버] ── [분리된 백업 저장소]

[관찰·로그 수집] ← 각 서버의 최소 로그·지표

웹서버는 정적 자원 제공, 보안 통신 종료, 가상 호스트, 요청 전달 같은 경계 역할을 할 수 있다. 응용 서버는 업무 로직, DB서버는 영속 데이터와 무결성을 담당한다. 작은 개발환경에서 한 호스트에 함께 설치하더라도 서비스 계정·포트·디렉터리·자원과 설정 책임은 논리적으로 분리한다.

DB 포트를 모든 개발자 네트워크에 공개하지 않고 응용·승인 관리 경로에 한정한다. 관리 인터페이스는 일반 서비스 경로와 분리하고 개인 인증·최소 권한·접근 기록을 적용한다. 기반 서버가 외부 저장소·시간·이름 서비스에 접근해야 하는 범위도 허용목록으로 정한다.

04

용량과 배치 설계

용량 산정에는 평균보다 최대 동시성과 성장·장애 조건을 포함한다.

용량과 배치 설계 · 학습 표 1
자원산정 입력확인 지표
CPU요청당 연산, 동시 작업, 암호·압축사용률, 실행 큐, 처리량
메모리웹 작업자, DB 버퍼, 연결, 캐시가용·스왑, 프로세스 점유
저장공간데이터·인덱스·로그·임시·백업 증가여유율, 증가율, I/O 지연
네트워크요청·응답 크기, 복제·백업대역, 지연, 손실·재전송
연결웹 동시 연결, 응용 풀, DB 세션활성·대기·거부·시간 초과

각 구성요소의 최대 연결 수를 독립적으로 크게 하면 DB 한도를 초과할 수 있다. 예를 들어 응용 인스턴스 4개가 각 100개 연결 풀을 가지면 최대 400개가 된다. DB 예약 관리자·배치 연결과 장애 시 재연결 폭주를 포함해 종단 전체 예산을 맞춘다.

데이터, 트랜잭션 로그, 임시 영역, 백업을 가능한 별도 용량·성능·보존 기준으로 본다. 한 공간이 가득 찼을 때 모든 기능이 동시에 실패하지 않게 경보와 자동 성장 한도·정리 절차를 둔다. 자동 확장은 물리 용량을 무한히 만들지 않는다.

05

설치 전 계획

설치 계획에는 서버 식별자, 운영체제 기준선, 제품·버전·에디션, CPU 구조, 설치 출처·무결성, 서비스 계정, 디렉터리·볼륨, 포트·방화벽, 이름·인증서, 시간대·문자셋, 시작 순서, 백업·복구와 되돌리기를 포함한다.

기존 서버에 설치한다면 현재 서비스·포트·자원·라이브러리 충돌을 확인한다. 신규 환경이더라도 관리 주체와 비용·삭제 조건을 명시한다. 자동화 스크립트는 대상 환경을 매개변수로 받고, 비밀과 파괴적 초기화가 안전한지 시험한다.

서버 설치 파일과 이미지는 공식 또는 조직 승인 저장소에서 얻고 제공되는 서명·해시 검증을 따른다. 불필요한 예제·관리 콘솔·플러그인·기본 콘텐츠를 제외한다. 기본 계정과 초기 자격증명은 정책에 따라 비활성화·교체한다.

06

공통 설치·운용 기준

서비스마다 비대화형 전용 계정을 사용하고 로그인·홈·파일 권한을 최소화한다. 실행 바이너리·설정은 서비스 계정이 임의 수정하지 못하게 하고, 데이터·로그·임시 경로만 필요한 권한을 준다. 관리자와 서비스 계정을 공유하지 않는다.

서비스 시작·중지·재시작은 운영체제 서비스 관리 기능으로 통제하고, 비정상 종료 후 재시작 횟수와 지연을 제한한다. 무한 재시작은 원인을 숨기고 부하를 키울 수 있다. 의존 서비스가 준비되기 전 단순 프로세스 실행만으로 정상 판정하지 않고 준비 상태 확인을 둔다.

설정은 형상관리 가능한 비민감 기준과 외부 비밀을 분리한다. 환경별 차이는 명시적 변수로 관리하며 개발자가 서버에서 직접 바꾼 설정이 기준선과 어긋나지 않게 한다. 변경 전후 설정 차이와 승인·검증·되돌리기를 기록한다.

07

웹서버 설치·구성

웹서버 설치 후 다음 영역을 구성한다.

  • 수신 주소·포트와 개발망 허용 범위
  • 가상 호스트·서비스 이름과 기본 호스트 처리
  • 문서 루트, 정적 자원, 디렉터리 목록·심볼릭 링크 정책
  • 응용 서버 전달 대상, 헤더·원본 정보 신뢰 범위
  • 연결·읽기·쓰기·전체 요청 시간 제한
  • 요청 본문·헤더·동시 연결·속도·응답 버퍼 한도
  • 안전한 통신, 인증서·개인키 접근·교체·만료 관찰
  • 접근·오류 로그의 필드·마스킹·보존·상관관계 ID
  • 상태 확인·우아한 재시작·오류 응답·정적 점검 페이지

기본 가상 호스트가 알 수 없는 이름의 요청을 실제 응용으로 전달하지 않게 한다. 문서 루트에 소스·설정·백업·임시 파일을 두지 않고 디렉터리 목록을 필요 없이 켜지 않는다. 오류 페이지는 제품·내부 경로·스택을 과도하게 노출하지 않는다.

리버스 프록시가 전달하는 원본 주소·프로토콜 헤더는 승인된 앞단에서 온 요청만 신뢰한다. 외부 사용자가 같은 헤더를 직접 보내도 권한·감사 근거가 되지 않게 한다. 헤더 크기와 전달 시간 제한을 두고 응용·웹서버의 제한이 모순되지 않게 한다.

안전한 통신 설정은 조직의 현재 정책과 공식 지원을 따른다. 개인키는 별도 보호 경로와 최소 읽기 권한을 사용하고 소스·이미지·일반 백업에 넣지 않는다. 갱신은 만료 직전 수동 작업이 아니라 소유자·알림·교체·재적용·검증 절차를 둔다.

08

웹서버 검증

정상 호스트·경로·정적 자원·응용 프록시가 기대 상태와 헤더로 응답하는지 확인한다. 알 수 없는 호스트, 금지 경로, 과도한 요청 크기, 허용되지 않은 메서드, 직접 내부 포트 접근은 정책대로 거부되어야 한다. 오류 응답과 로그에 비밀·내부 경로가 없는지 본다.

응용 서버 중 하나가 느리거나 종료될 때 웹서버의 시간 제한, 연결 회수, 상태 판정이 정상인지 확인한다. 재시작 시 기존 요청 처리 정책과 새 요청 수신 시점을 측정한다. 처리량 시험에서는 CPU뿐 아니라 동시 연결, 큐, 응용·DB 지연을 함께 본다.

09

DB서버 설치·구성

DB서버는 제품·버전과 운영체제·CPU·저장장치 호환을 확인하고 최소 기능으로 설치한다. 데이터, 트랜잭션 로그, 임시, 감사, 백업 경로와 소유권·용량·성능을 계획한다. 문자셋·정렬 규칙·시간대는 생성 후 변경이 어렵거나 데이터 의미에 영향을 줄 수 있으므로 응용 요구와 먼저 합의한다.

코드 예시 · text

DB 저장 구조 예
  /data      : 업무 데이터·인덱스
  /txlog     : 복구용 트랜잭션 로그
  /temp      : 정렬·임시 작업, 크기 한도
  /audit     : 접근 제한된 감사 기록
  backup://  : 서버 장애 영역과 분리된 백업 저장소

관리자, 스키마 배포, 응용 런타임, 읽기 전용 분석, 백업 주체를 분리한다. 응용 계정은 필요한 스키마의 SELECT·INSERT·UPDATE·프로시저 실행만 받고 사용자·권한·서버 설정 변경을 할 수 없어야 한다. 초기·기본 계정과 공개 권한을 검토한다.

DB는 승인 인터페이스·주소에서만 수신하고 방화벽과 DB 접근 정책을 함께 적용한다. 안전한 통신과 상대 인증을 구성하며, 비밀번호·키는 승인 비밀 저장소에서 주입한다. 연결 실패·권한 거부를 기록하되 자격증명과 쿼리 매개변수 민감값을 남기지 않는다.

10

DB 연결·트랜잭션·성능 기준

최대 연결 수는 메모리와 작업 특성을 고려해 정하고 응용 연결 풀 합계와 맞춘다. 연결을 많이 열면 항상 빠른 것이 아니라 문맥·메모리·잠금 경쟁이 늘 수 있다. 유휴·획득·쿼리·트랜잭션 시간 제한과 누수 관찰을 둔다.

개발환경도 자동 커밋·격리 수준·문자·시간대 설정을 운영 의도와 맞춘다. 시험이 끝나지 않은 긴 트랜잭션이 잠금과 로그 증가를 만들 수 있으므로 활성 트랜잭션과 대기 관계를 관찰한다. 느린 쿼리는 단순 시간뿐 아니라 실행 계획, 반환량, 잠금, I/O를 함께 본다.

메모리·캐시·작업 영역을 장비 전체 크기만 보고 최대로 잡지 않는다. 운영체제, 웹·응용 서비스, 백업·검사 작업의 여유를 남긴다. 설정 변경은 대표 부하로 전후를 비교하고 한 번에 여러 값을 바꾸지 않는다.

11

백업과 복구

백업은 복구 요구에서 역으로 설계한다. 어떤 시점까지 데이터를 복구해야 하는지, 얼마 안에 서비스가 돌아와야 하는지, 전체·증분·로그 백업과 보존·암호화·오프사이트 또는 장애영역 분리를 정한다. 개발환경이라도 공유 시험 기준 데이터와 스키마를 잃으면 일정에 영향을 준다.

백업 작업 성공 로그만으로 복구 가능성을 증명하지 못한다. 격리 환경에 정기적으로 복원하고 스키마·행 수·통제합계·응용 연결을 확인한다. 암호화 키, 계정, 도구 버전, 복구 절차가 함께 준비되어야 한다.

시험 데이터 초기화와 백업 복원은 구분한다. 초기화 스크립트가 운영 또는 다른 프로젝트 대상을 선택하지 못하도록 환경 식별·승인·보호 장치를 둔다. 삭제·복원 작업 전 정확한 대상과 최근 백업을 확인한다.

12

로그·지표·경보

웹서버는 요청률, 상태 코드, 지연 분포, 활성 연결, 거부·시간 초과를 관찰한다. DB서버는 연결·대기, 쿼리 시간, 잠금·교착, 캐시·메모리, 데이터·로그·임시 공간, 백업 상태를 본다. 호스트 CPU·메모리·I/O·네트워크와 함께 상관관계로 분석한다.

로그는 서버·환경·서비스·상관관계·결과를 식별하되 인증 헤더, 세션, DB 비밀번호, 민감 쿼리 값은 제외한다. 서버 시간이 맞아야 요청과 DB 기록을 연결할 수 있다. 로그 저장공간이 가득 차서 서비스와 같은 디스크를 고갈시키지 않도록 회전·보존·경보를 둔다.

경보는 임계값뿐 아니라 소유자·조치·상향 기준이 있어야 한다. 저장공간 경보가 울렸을 때 무조건 로그를 삭제하기보다 증가 원인, 보존 의무, 안전한 확장·정리와 서비스 영향을 판단한다.

13

패치·변경·장애 운용

운영체제·웹·DB와 확장 구성요소의 지원·보안 정보를 정기 확인한다. 패치는 시험 환경에서 호환·설정·데이터·성능을 확인하고 백업·되돌리기와 함께 적용한다. 긴급 위험은 신속히 처리하되 승인·최소 검증·결과 기록을 남긴다.

설정 변경은 요구·변경 ID, 영향 서버·포트·데이터, 시험, 작업창, 담당·검토, 되돌리기를 포함한다. 서버에서 직접 바꾼 뒤 나중에 문서화하지 말고 기준 형상으로 적용한다. 변경 후 서비스 프로세스만 보지 않고 실제 건강 확인·대표 업무·로그·지표를 검증한다.

장애 대응은 범위를 분리한다. 호스트 자원, 네트워크·이름, 웹 수신·프록시, 응용 건강, DB 연결·잠금·용량, 외부 의존성 순으로 증거를 모은다. 무작정 재시작하면 증거와 미완료 트랜잭션을 잃을 수 있으므로 상태·영향·복구 절차를 확인한다.

14

기본 개발환경 구축 적용 절차

기본 개발환경 구축의 적용 절차와 판단 기준은 다음과 같다.

  1. 응용 구조·도구·동시성·데이터·보안·복구 요구를 확인한다.
  2. 현재 운영체제·개발도구·기반 서버·네트워크·권한의 차이를 조사한다.
  3. 역할·신뢰경계·용량·제품·버전·배치 대안을 비교해 설계한다.
  4. 주소·이름·포트·계정·디렉터리·비밀·백업·관찰 계획을 작성한다.
  5. 승인 출처와 자동화된 기준선으로 운영체제·도구·서버를 순서대로 설치한다.
  6. 최소 권한, 안전한 통신, 자원·시간 제한, 로그·백업을 구성한다.
  7. 대표 소스를 빌드하고 웹–응용–DB 정상 업무와 거부 흐름을 시험한다.
  8. 동시량·장애·재시작·용량 한계·백업 복원을 검증한다.
  9. 형상·자산·운영·업데이트·장애·되돌리기 문서와 담당자를 인수한다.
  10. 요구–설계–설정–시험 증거와 미해결 예외를 검토해 완료를 승인한다.

완료 판단은 각 제품 설치 성공이 아니다. 팀이 동일한 방식으로 빌드·시험할 수 있고, 서비스 간 통신과 거부가 설계대로이며, 자원·데이터·비밀이 보호되고, 장애·재시작·복원이 요구 시간 안에 가능하며, 설정과 운영 책임이 추적되어야 한다.

15

구체 실무 시나리오

주문 서비스 통합시험 환경을 구축한다고 하자. 요구는 개발자 20명, 동시 자동시험 10개, 합성 주문 데이터 100GB, 야간 초기화, 하루 이내 환경 복구다. 웹서버는 승인 개발망의 안전한 통신만 받고 내부 응용 포트로 전달한다. DB는 응용·제한 관리 경로만 허용하며 데이터·로그·백업 공간을 분리한다.

응용 인스턴스 2개의 연결 풀 합계와 DB 최대 연결, 시험·관리 예약 연결을 계산한다. 알 수 없는 가상 호스트와 직접 응용·DB 접근은 거부한다. 대표 소스 빌드 후 주문 생성·조회, 비인가 역할 거부, 큰 요청 제한, 응용 지연 시 웹 시간 제한, DB 재시작 후 연결 회복을 확인한다.

합성 기준 데이터를 백업하고 별도 환경에 복원해 행 수·금액 통제합계와 응용 연결을 확인한다. 야간 초기화는 환경 ID가 시험일 때만 실행되게 하고 대상·백업을 기록한다. 웹 지연·상태 코드, DB 연결·잠금·공간, 호스트 I/O를 대시보드에서 연결해 관찰한다.

16

산출물과 체크리스트

산출물은 기반환경 요구·통신 행렬, 논리·물리 구성도, 용량 산정표, 제품·버전·호환표, 설치·자동화·설정 형상, 계정·포트·권한표, 웹·DB 검증 결과, 부하·장애·재시작 시험, 백업·복원 증거, 관찰·경보 목록, 운영·패치·장애·되돌리기 안내서다.

  • [ ] 응용 흐름과 웹·응용·DB 책임·신뢰경계가 명확하다.
  • [ ] 동시량·성장·장애를 반영해 CPU·메모리·저장·연결을 산정했다.
  • [ ] 승인 출처·지원 버전·최소 기능으로 설치했다.
  • [ ] 서비스·관리자·응용·배포·백업 계정과 권한이 분리되었다.
  • [ ] 웹 호스트·프록시·시간·크기·로그·인증서 정책이 있다.
  • [ ] DB 데이터·로그·임시·백업 공간과 문자·시간 기준이 명확하다.
  • [ ] 네트워크·포트·비밀·안전한 통신을 최소 범위로 적용했다.
  • [ ] 정상·거부·부하·장애·재시작·복원 시험을 통과했다.
  • [ ] 지연·연결·잠금·용량·로그·백업을 관찰하고 조치할 수 있다.
  • [ ] 형상·자산·패치·복구·담당과 요구 추적이 완료되었다.
17

자주 틀리는 포인트

  • 개발환경이라는 이유로 운영 데이터·비밀과 전체 포트를 개방한다.
  • 각 응용 연결 풀만 보고 전체 DB 연결 합계를 계산하지 않는다.
  • 웹 기본 호스트가 알 수 없는 이름을 실제 응용으로 전달하게 둔다.
  • 프록시 전달 헤더를 모든 외부 요청에서 신뢰한다.
  • DB 응용 계정에 사용자·스키마·서버 관리 권한까지 준다.
  • 데이터·로그·백업을 한 공간에 두고 자동 증가를 무한 용량으로 본다.
  • 문자셋·정렬·시간대를 데이터 생성 뒤에 결정한다.
  • 백업 성공 메시지만 확인하고 격리 복원을 시험하지 않는다.
  • 프로세스 실행 상태만 보고 대표 업무와 거부 흐름을 확인하지 않는다.
  • 여러 설정을 동시에 바꾸고 성능 향상·장애 원인을 단정한다.

확인 문제

  1. 기반 서버 요구사항에서 확인할 입력자료를 여섯 가지 쓰시오.
  2. 웹·응용·DB를 논리적으로 분리해야 하는 이유를 설명하시오.
  3. 여러 응용 인스턴스의 DB 연결 풀을 합산해야 하는 이유는 무엇인가?
  4. 웹서버 가상 호스트와 리버스 프록시에서 검토할 항목을 쓰시오.
  5. DB 데이터·트랜잭션 로그·임시·백업 공간을 구분하는 이유는 무엇인가?
  6. DB 서비스 계정과 관리자·배포 계정을 분리해야 하는 이유를 쓰시오.
  7. 백업 성공과 복구 가능성이 다른 이유를 설명하시오.
  8. 웹서버와 DB서버의 핵심 관찰 지표를 각각 네 가지 쓰시오.
  9. 기반 서버 변경 후 프로세스 상태 외 확인할 사항을 쓰시오.
  10. 기본 개발환경 구축의 적용 절차와 완료 판단 기준을 요약하시오.

정답과 해설

  1. 응용 구조·통신, 동시량·성능, 제품 호환, 데이터·보안, 복구 목표, 네트워크·이름·시간, 자원·라이선스 중 여섯 가지다.
  2. 외부 수신, 업무 처리, 데이터 영속 책임과 권한·장애 범위를 나누어 최소 권한, 독립 변경·진단, 데이터 보호를 가능하게 한다.
  3. DB가 보는 연결은 모든 인스턴스 풀의 합이며 시험·배치·관리 연결도 추가된다. 합계를 보지 않으면 메모리·세션 한도와 재연결 폭주를 초래한다.
  4. 승인 이름·기본 호스트 거부, 문서 루트, 전달 대상, 신뢰할 원본 헤더 범위, 시간·크기·연결 한도, TLS·인증서, 오류·로그를 확인한다.
  5. 공간·I/O·보존·복구 책임이 다르고 한 영역 포화가 전체 서비스를 동시에 멈추는 것을 줄이기 위해서다. 백업은 서버 장애영역 밖에도 있어야 한다.
  6. 런타임 침해나 실수의 피해를 필요한 DML 범위로 줄이고 스키마·권한 변경을 승인된 배포 경로로 추적하기 위해서다.
  7. 백업 파일이 손상되거나 키·도구·절차가 없을 수 있다. 격리 복원 후 스키마·통제합계·응용 연결을 확인해야 실제 복구 능력을 증명한다.
  8. 웹은 요청률·상태 코드·지연·활성 연결·거부·시간 초과, DB는 연결·대기·쿼리 지연·잠금·공간·백업 중 각각 네 가지다.
  9. 실제 건강 확인, 대표 정상·거부 업무, 로그·지표, 데이터·연결 상태, 자원 사용, 설정 형상 일치와 되돌리기 가능성을 확인한다.
  10. 요구·현황 조사, 구조·용량 설계, 설치·최소 권한 구성, 대표 빌드와 정상·거부·장애·복원 시험, 운영 인수 순이다. 재현성·보호·복구·관찰·추적 증거가 있어야 완료다.

핵심 요약

  • 기반 서버는 응용 흐름·동시량·데이터·보안·복구 요구에서 역할과 용량을 설계한다.
