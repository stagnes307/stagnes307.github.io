01

학습 범위와 수행 목표

이 레슨의 정확한 토픽은 소스 빌드와 고객 편의 패키징, 변경·개선사항 릴리즈 노트 작성이다. 개발자가 자신의 환경에서 실행 파일을 만드는 데 그치지 않고, 승인된 소스와 의존성으로 재현 가능한 산출물을 만들고 고객이 설치·실행하기 편한 구조로 묶는 과정을 다룬다. 이어서 해당 버전에서 무엇이 달라졌고 어떤 주의가 필요한지를 검증 가능한 릴리즈 노트로 정리한다.

저작권 보호 도구의 세부 적용은 다음 레슨, 설치·사용자 매뉴얼의 본문 설계는 별도 매뉴얼 레슨의 범위다. 여기서는 패키지 구성과 릴리즈 노트에 필요한 연결 정보만 다룬다.

학습을 마치면 다음을 수행할 수 있어야 한다.

  1. 승인된 기준점에서 깨끗하고 반복 가능한 빌드를 수행한다.
  2. 고객 실행 환경에 맞춰 필수 파일만 포함한 패키지를 구성한다.
  3. 버전·설정·의존성·검증 결과를 추적 가능한 산출물로 남긴다.
  4. 변경·개선·수정·알려진 문제를 사용자 관점의 릴리즈 노트로 작성한다.
  5. 설치·실행·업그레이드·원복 시험을 거쳐 배포 후보를 승인하거나 반려한다.
02

1. 빌드와 패키징을 구분한다

빌드는 소스 코드와 자원을 컴파일·변환·연결해 실행 가능한 결과를 만드는 과정이다. 패키징은 그 결과와 실행에 필요한 설정 예제, 라이선스 고지, 문서 등을 고객이 전달받아 사용할 단위로 구성하는 과정이다.

코드 예시 · text

승인 소스 + 잠긴 의존성 + 빌드 설정
                 │
                 ▼
          깨끗한 환경에서 빌드
                 │
          시험·정적 검사 통과
                 ▼
       실행 산출물과 필수 자원 선별
                 │
        디렉터리·메타정보 구성
                 ▼
       패키지 후보 → 설치·실행 검증

로컬 개발 폴더 전체를 압축하는 것은 패키징이 아니다. 임시 파일, 개인 설정, 비밀키, 테스트 데이터, 빌드 캐시가 섞일 수 있고 고객 환경에서 재현되지 않는다. 반대로 실행에 필요한 런타임이나 데이터 파일을 빼면 설치는 되어도 실행이 실패한다. 따라서 “포함할 것”과 “제외할 것”을 명세로 관리한다.

03

2. 소스 빌드의 입력을 고정한다

재현 가능한 빌드는 같은 승인 입력과 도구 조건에서 기능적으로 동일한 결과를 다시 만들 수 있어야 한다. 바이트 단위 동일성은 타임스탬프·서명 방식 등에 따라 별도 설계가 필요하지만, 최소한 사용한 소스와 의존성·도구를 식별할 수 있어야 한다.

2.1 소스 기준점

브랜치 이름만 기록하면 이후 내용이 바뀔 수 있다. 승인된 커밋, 태그 또는 변경 불가능한 기준점 식별자를 남긴다. 작업 디렉터리에 미반영 변경이 있는지 확인하고, 검토되지 않은 파일이 빌드에 섞이지 않게 한다.

2.2 의존성

직접 의존성뿐 아니라 전이 의존성 버전도 변할 수 있다. 프로젝트가 제공하는 잠금 파일과 공식 패키지 저장소 정책을 사용하고, 패키지 이름·버전·출처·무결성 정보를 보존한다. “항상 최신” 범위는 어느 날 다른 결과를 만들 수 있으므로 릴리즈 빌드에는 적합하지 않다.

2.3 도구와 환경

컴파일러·런타임·빌드 도구 버전, 대상 OS·아키텍처, 로캘, 시간대, 기능 플래그가 결과에 영향을 줄 수 있다. 빌드 컨테이너나 자동화된 실행 환경은 차이를 줄이는 수단이지, 입력 기록을 대체하지 않는다. 캐시를 사용하더라도 깨끗한 빌드와 비교해 오염 여부를 검증한다.

2.4 환경별 설정

코드와 환경 설정을 구분한다. 개발·시험·운영의 주소와 인증정보를 실행 파일 안에 고정하지 않는다. 패키지에는 값이 비어 있거나 안전한 예제 설정을 넣고, 실제 비밀은 승인된 외부 저장소나 설치 단계에서 주입한다.

04

3. 빌드 실행 절차와 판단 기준

단계 1: 빌드 요청 확인

대상 버전, 지원 플랫폼, CPU 아키텍처, 기능 옵션, 마감, 승인 기준을 확인한다. 한 플랫폼용 결과를 다른 플랫폼에서도 동작한다고 추정하지 않는다.

단계 2: 입력 무결성 확인

소스 기준점, 하위 모듈, 의존성 잠금 파일, 빌드 스크립트와 인증된 도구 이미지를 확인한다. 서명키·저장소 토큰은 소스나 로그에 기록하지 않는다.

단계 3: 깨끗한 환경 준비

이전 산출물과 개인 설정이 없는 작업 공간을 사용한다. 네트워크 없이도 가능한 빌드인지, 외부 저장소가 필요하다면 승인된 출처만 사용하는지 정한다. 실패한 의존성 다운로드를 임의 사이트 파일로 대체하지 않는다.

단계 4: 자동 빌드와 검사

사람이 GUI에서 여러 값을 기억해 누르는 절차보다 스크립트·파이프라인으로 반복 가능하게 만든다. 컴파일 경고, 정적 검사, 단위 시험 실패를 숨기지 않는다. 허용 예외가 있다면 사유·승인·만료 조건을 남긴다.

코드 예시 · text

build_request:
  source_ref: release-approved-reference
  target: supported-os-and-architecture
  dependency_lock: verified
  steps: clean -> restore -> compile -> test -> stage
  outputs: artifact, dependency-list, test-report, build-log

위 형식은 특정 도구 문법이 아니라 빌드 기록에 필요한 항목을 나타낸 의사 명세다.

단계 5: 산출물 선별

스테이징 디렉터리를 새로 만들고 명세에 있는 파일만 복사한다. 실행에 필요한 공유 라이브러리, 템플릿, 마이그레이션 자원 등이 빠지지 않았는지 확인한다. 디버그 전용 도구와 비밀이 포함되지 않았는지 자동 탐지와 수동 검토를 병행한다.

단계 6: 검증·승인

산출물 해시, 파일 목록, 빌드 로그, 시험 결과, 소프트웨어 구성 목록을 연결한다. 지원되는 깨끗한 고객 환경에서 설치·시작·핵심 기능·종료·제거 또는 원복을 시험한다. 기준을 만족한 동일 바이트의 패키지만 배포 후보로 승격한다. 시험 뒤 다시 압축하거나 파일을 고치면 새 후보로 재검증해야 한다.

05

4. 고객 편의 패키징 설계

고객 편의는 파일 수를 줄이는 것만 뜻하지 않는다. 사용자가 올바른 패키지를 고르고, 예상 경로에 설치하며, 실패 시 원인을 확인하고, 기존 버전을 안전하게 보존할 수 있어야 한다.

4.1 이름과 구조

파일명에는 제품, 버전, 대상 플랫폼·아키텍처를 일관되게 표시한다. 지나치게 긴 경로, OS에서 허용되지 않는 문자, 대소문자 충돌을 피한다. 최상위에 버전 정보와 시작 문서를 두고 실행 파일·설정·문서·라이선스를 구분한다.

코드 예시 · text

product-3.2.0-os-arch/
  README.txt
  RELEASE-NOTES.md
  LICENSES/
  bin/
  config/example.conf
  resources/
  manifest.json

4.2 기본값과 사용자 데이터

첫 실행이 안전한 기본값으로 시작되게 하되 보안 기능을 꺼 놓지 않는다. 업그레이드가 기존 설정·사용자 데이터를 덮지 않게 백업·마이그레이션 정책을 둔다. 제거 기능도 고객 데이터 삭제 여부를 별도 확인해야 한다.

4.3 플랫폼별 형태

압축 아카이브, OS 설치 패키지, 컨테이너 이미지 등 형태는 배포 환경과 운영 능력에 따라 고른다. 각 형태는 설치 권한, 경로, 자동 업데이트, 무인 설치, 프록시·폐쇄망, 제거 요구가 다르다. 한 형태를 모든 고객에게 강요하기보다 지원 범위를 명시한다.

4.4 완전성과 최소성

패키지 내부 파일 목록과 의존성 목록을 비교한다. 누락 검사는 새 환경 실행으로, 과잉 포함 검사는 비밀·개발 도구·소스·샘플 개인정보 탐지로 수행한다. 압축률이 높다는 이유로 검증 불가능한 독자 형식을 선택하지 않는다.

5. 변경·개선사항 릴리즈 노트 작성

변경·개선사항 릴리즈 노트 작성은 개발 변경 이력을 그대로 복사하는 일이 아니다. 사용자가 업그레이드 여부와 영향, 필요한 조치를 판단할 수 있도록 선별·번역한 배포 문서다.

5.2 사용자 언어로 쓴다

“모듈 X 리팩터링”보다 “대량 검색 시 응답 지연을 줄였다”가 고객 판단에 유용하다. 내부 티켓 번호만 적지 말고 관찰 가능한 증상과 적용 결과를 쓴다. 아직 검증되지 않은 성능 수치를 홍보 문구로 단정하지 않는다.

5.3 변화의 종류를 구분한다

신규 기능, 개선, 결함 수정, 보안, 제거·지원 종료, 알려진 문제를 섞지 않는다. 호환성을 깨는 변경은 눈에 띄게 표시하고 설정·데이터 마이그레이션과 원복 가능 여부를 설명한다. 보안 수정은 위험을 이해할 충분한 정보는 주되 악용 가능한 세부사항이나 비밀값을 노출하지 않는다.

5.4 사실을 추적한다

각 항목은 승인된 변경 요청, 시험 결과, 문서 또는 결함 기록으로 추적되어야 한다. 코드에 병합됐어도 이번 패키지에 포함되지 않았다면 릴리즈 노트에 적지 않는다. 반대로 고객 영향이 있는 기본값·지원 환경 변경을 누락하지 않는다.

07

6. 구체 시나리오: 3.2.0 고객 배포 후보

업무 시스템 3.2.0은 검색 속도 개선, CSV 내보내기 추가, 특정 날짜 조건의 오류 수정을 포함한다. 담당자는 승인 태그와 잠금 파일로 깨끗한 빌드를 수행하고 두 대상 OS용 패키지를 각각 만든다.

  1. 빌드 기록에 소스 기준점·도구 이미지·의존성 목록을 남긴다.
  2. 스테이징에서 개발 설정, 테스트 계정, 로그 샘플을 제외한다.
  3. 파일명에 제품·3.2.0·OS·아키텍처를 표시한다.
  4. 이전 지원 버전에서 업그레이드해 설정과 데이터를 확인한다.
  5. 신규 설치, 핵심 조회, CSV 출력, 제거·원복 시험을 수행한다.
  6. 릴리즈 노트에는 고객 증상과 조치, 알려진 제한을 기록한다.
  7. 해시와 시험이 연결된 패키지만 승인 저장소로 이동한다.

검색 속도가 시험 환경에서만 개선됐다면 “항상 2배 빠름”이라고 쓰지 않는다. 대신 시험 조건과 관찰 범위를 근거 문서에 남기고, 릴리즈 노트에는 검증된 효과만 표현한다.

7. 산출물과 완료 체크리스트

주요 산출물은 빌드 요청서, 소스·도구·의존성 식별 정보, 빌드 로그, 시험 보고서, 패키지 명세·파일 목록, 무결성 값, 릴리즈 노트, 승인 기록이다.

  • [ ] 승인된 소스 기준점과 작업 공간 청결을 확인했다.
  • [ ] 직접·전이 의존성과 빌드 도구 버전을 식별했다.
  • [ ] 대상 OS·아키텍처별 빌드와 실행 시험을 수행했다.
  • [ ] 비밀, 개인 설정, 캐시, 불필요한 개발 파일을 제외했다.
  • [ ] 필수 런타임·자원·라이선스 고지를 포함했다.
  • [ ] 패키지 이름·내부 구조·버전 표기가 일치한다.
  • [ ] 신규 설치·업그레이드·실행·원복 경로를 확인했다.
  • [ ] 릴리즈 노트의 모든 변경이 실제 패키지와 추적된다.
  • [ ] 알려진 문제와 사용자 조치가 검증된 표현으로 작성됐다.
  • [ ] 승인 후 패키지 바이트를 변경하지 않았다.

8. 자주 틀리는 포인트와 실기 함정

  1. 개발 PC에서 성공한 빌드를 재현 가능한 릴리즈 빌드로 간주한다.
  2. 브랜치 이름만 기록하고 실제 소스 기준점을 남기지 않는다.
  3. 잠금 파일을 무시하고 빌드할 때마다 최신 의존성을 받는다.
  4. 개발 폴더 전체를 압축해 비밀·캐시·시험 데이터를 포함한다.
  5. 실행 파일만 전달하고 필수 자원·런타임·라이선스 고지를 뺀다.
  6. 패키지 시험 후 내부 파일을 수동 수정하고 같은 승인 결과를 사용한다.
  7. 커밋 메시지를 그대로 릴리즈 노트로 복사해 고객 영향을 설명하지 않는다.
  8. 포함되지 않은 기능이나 검증되지 않은 성능을 릴리즈 노트에 단정한다.
  9. 알려진 문제를 숨기거나 안전하지 않은 우회 방법을 제시한다.
  10. 버전·플랫폼이 다른 패키지에 같은 모호한 파일명을 사용한다.

10. 정답과 해설

문제 1 정답과 해설

빌드는 소스와 의존성을 실행 가능한 산출물로 변환한다. 패키징은 그 결과와 필수 자원·설정 예제·문서·고지를 고객이 설치·사용할 전달 단위로 구성한다.

문제 2 정답과 해설

브랜치 내용은 이후 변경될 수 있지만 커밋·승인 태그 같은 기준점은 사용한 소스를 정확히 식별한다. 따라서 재현과 감사, 결함 추적이 가능하다.

문제 3 정답과 해설

개인 비밀·운영정보가 유출될 수 있고, 캐시·중간 산출물로 크기와 충돌이 늘며, 개발 환경에만 있는 파일 때문에 고객 환경에서 재현되지 않을 수 있다.

문제 4 정답과 해설

소스 기준점, 의존성 잠금 정보, 컴파일러·런타임·빌드 도구 버전, 대상 OS·아키텍처와 기능 설정을 들 수 있다.

문제 5 정답과 해설

쓸 수 없다. 시험한 바이트와 배포할 바이트가 달라졌으므로 새 후보로 무결성 값과 설치·실행 시험을 다시 연결해야 한다.

문제 6 정답과 해설

제품·버전·플랫폼·아키텍처를 구분할 수 있어야 하고, 내부에는 시작 문서, 실행 파일, 안전한 설정 예제, 필수 자원, 라이선스와 릴리즈 노트가 예측 가능한 위치에 있어야 한다.

문제 7 정답과 해설

커밋 로그는 개발 변경 단위와 내부 용어 중심이다. 릴리즈 노트는 실제 패키지에 포함된 변화 중 고객의 사용·호환성·업그레이드 판단에 필요한 내용을 검증된 언어로 선별한다.

문제 8 정답과 해설

문제가 발생하는 조건, 사용자에게 미치는 영향, 안전하고 검증된 우회 방법, 수정 예정 또는 지원 경로를 적는다. 악용 가능한 보안 세부나 비밀은 공개하지 않는다.

문제 9 정답과 해설

요청·지원 환경 확인 → 승인 소스와 의존성 고정 → 깨끗한 자동 빌드·시험 → 필수 파일 스테이징 → 패키지 구성 → 신규 설치·업그레이드·원복 검증 → 릴리즈 노트와 무결성 값 작성 → 승인 순이다.

11. 핵심 요약

  • 소스 빌드와 고객 편의 패키징은 승인 소스·의존성·도구를 고정하고 깨끗한 환경에서 빌드한 뒤 고객에게 필요한 파일만 안전한 구조로 구성하는 과정이다.
  • 빌드 입력, 로그, 시험, 파일 목록과 무결성 값을 연결해야 같은 후보를 재현하고 감사할 수 있다.
  • 고객 편의는 안전한 기본값, 명확한 플랫폼·버전 식별, 설치·업그레이드·원복 가능성을 포함한다.
  • 변경·개선사항 릴리즈 노트 작성은 실제 패키지에 포함된 고객 영향만 신규·개선·수정·호환성·알려진 문제로 구분해 설명하는 일이다.
  • 검증 후 파일을 바꾸면 새 후보이며, 릴리즈 노트의 모든 사실은 변경·시험·승인 근거로 추적되어야 한다.
