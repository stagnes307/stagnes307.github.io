01

학습 범위와 수행 목표

이 레슨의 정확한 토픽은 형상관리 지침에 따른 버전 등록, 형상관리 지침에 따른 버전관리 도구 사용이다. 조직이 승인한 형상관리 지침에 따라 소스·설정·문서·빌드 정의 등 형상 항목의 변경을 식별하고, 버전관리 도구로 등록·검토·병합·기준선화하며, 필요한 시점의 상태를 재현·복구하는 실기 절차를 다룬다.

특정 도구의 명령 옵션은 버전에 따라 달라질 수 있으므로 개념과 판단 기준을 우선한다. 예시는 분산 버전관리 도구의 일반적인 흐름을 보여 주지만 실제 저장소의 브랜치·리뷰·서명·태그 정책을 먼저 확인해야 한다. 원격 저장소 삭제나 기록 재작성 같은 파괴적 작업은 실습 범위에서 제외한다.

학습 목표는 다음과 같다.

  1. 형상 항목, 버전, 변경 집합, 기준선, 저장소의 관계를 설명한다.
  2. 등록 전 상태·범위·비밀·생성 파일을 점검하고 원자적 변경을 만든다.
  3. 브랜치·검토·병합·태그를 조직 지침에 맞게 사용한다.
  4. 충돌, 긴급 수정, 잘못된 변경을 감사 가능한 방식으로 처리한다.
  5. 권한·백업·보존·추적성·재현성을 기준으로 버전관리 품질을 검증한다.
02

1. 버전관리와 형상관리의 관계

버전관리는 파일과 변경 이력을 저장해 특정 시점의 상태를 조회·비교·복구하는 활동이다. 형상관리는 여기에 형상 항목 식별, 변경 통제, 상태 기록, 감사와 기준선 관리를 포함하는 더 넓은 활동이다. 도구에 파일을 올렸다고 변경 승인과 형상 감사가 자동으로 끝나지는 않는다.

1. 버전관리와 형상관리의 관계 · 학습 표 1
개념의미실기 확인점
형상 항목(CI)독립적으로 식별·통제할 대상소스, 설정 템플릿, 문서, 빌드 정의 등
버전특정 시점 형상 항목의 식별된 상태커밋·리비전·문서 버전
변경 집합하나의 목적을 이루는 변경 묶음요구·결함과 추적, 원자적 범위
기준선검토·승인되어 후속 작업 기준이 된 상태릴리즈 태그, 승인 문서 집합
저장소항목·이력·메타정보를 보관하는 공간권한, 백업, 무결성, 감사
형상 감사실제 상태가 지침·명세·기록과 맞는지 확인누락·무단 변경·버전 불일치

릴리즈 산출물 자체처럼 크거나 도구에 적합하지 않은 파일은 소스 저장소가 아닌 승인 아티팩트 저장소에서 관리할 수 있다. 중요한 것은 각 산출물이 어느 소스 기준점과 빌드에서 나왔는지 연결하는 것이다.

03

2. 형상관리 지침을 먼저 읽는다

조직 지침은 다음을 정한다.

  • 관리 대상과 제외 대상
  • 저장소·프로젝트·디렉터리 구조와 명명 규칙
  • 브랜치 생성·수명·병합 방식
  • 커밋 크기와 메시지 형식
  • 리뷰 인원, 승인자, 자동 검사와 병합 조건
  • 버전 번호·태그·기준선 생성 규칙
  • 긴급 수정, 충돌, 되돌리기와 예외 승인
  • 계정·역할·보호 브랜치·비밀 관리
  • 백업, 보존, 감사 로그, 퇴직·권한 회수

인터넷에서 본 유명 전략을 조직에 그대로 적용하지 않는다. 릴리즈 주기, 팀 규모, 규제, 병렬 유지 버전, 배포 자동화에 따라 적절한 전략이 다르다. 지침과 실제 도구 설정이 다르면 개인이 우회하지 말고 관리자에게 불일치를 보고한다.

04

3. 형상 항목과 제외 항목

3.1 등록할 대상

제품 소스, 스키마 변경, 테스트, 빌드·배포 정의, 안전한 설정 템플릿, API 명세, 설치·사용자 문서, 릴리즈 노트, 라이선스 고지 등 제품을 재현하고 검증하는 데 필요한 텍스트·자원을 관리한다.

3.2 등록하지 않을 대상

비밀번호, 개인키, 액세스 토큰, 실제 고객 데이터, 개인 개발환경 설정, 캐시, 중간 컴파일 결과, 의존성 다운로드 디렉터리, 로그, 임시 파일은 일반적으로 제외한다. 다만 생성 산출물 중 어떤 것을 별도 아티팩트 저장소에 보존할지는 지침으로 정한다.

제외 규칙을 나중에 추가해도 이미 등록된 비밀의 이력은 사라지지 않는다. 비밀이 등록되었다면 값을 즉시 회전·폐기하고 보안 대응 절차를 따른다. 단순히 현재 파일만 삭제하거나 커밋을 덮는 것으로 끝내지 않는다.

3.3 큰 파일과 바이너리

빈번히 바뀌는 큰 바이너리는 저장소 복제와 비교를 어렵게 한다. 전용 큰 파일 관리나 아티팩트 저장소를 검토하고, 출처·버전·해시를 텍스트 명세에 남긴다. “용량이 크다”만으로 필요한 설계 자산을 관리 밖에 두지 않는다.

05

4. 형상관리 지침에 따른 버전 등록

형상관리 지침에 따른 버전 등록은 파일을 무조건 모두 추가하는 행동이 아니라 변경 목적과 실제 차이를 검토해 추적 가능한 단위로 저장하는 과정이다.

단계 1: 작업 기준 확인

올바른 저장소, 기준 브랜치, 최신 승인 상태와 연결된 작업 항목을 확인한다. 다른 프로젝트나 오래된 브랜치에서 시작하지 않는다. 작업 디렉터리의 기존 미등록 변경이 내 작업인지 먼저 구분한다.

읽기 전용 상태 확인 예시:

코드 예시 · bash

git status --short
git branch --show-current
git diff --stat

출력은 현재 브랜치, 수정·추가 파일, 변경 규모를 판단하는 근거다. 아무 출력이 없으면 일반적으로 추적 파일의 작업 변경이 없다는 뜻이지만, 제외 파일과 원격 상태까지 자동 보장하는 것은 아니다.

단계 2: 변경 범위 분리

하나의 요구·결함을 해결하는 데 필요한 파일만 묶는다. 기능 변경, 대규모 서식 변경, 의존성 갱신을 한 커밋에 섞으면 검토·회귀 원인·부분 되돌리기가 어렵다. 반대로 하나의 원자적 변경을 의미 없이 너무 잘게 쪼개 빌드 불가능한 중간 상태를 만들지 않는다.

단계 3: 실제 차이 검토

요약뿐 아니라 줄 단위 변경, 새 파일 내용, 삭제를 확인한다.

코드 예시 · bash

git diff
git diff -- path/to/approved-file

비밀, 디버그 코드, 임시 출력, 예상 밖 대량 삭제, 자동 생성 파일의 불필요한 변동을 찾는다. 줄 끝이나 문자 인코딩만 전체 파일에서 바뀌었다면 의도인지 확인한다.

단계 4: 시험과 추적 정보 확인

관련 정적 검사·단위·통합 시험을 실행하고 결과를 남긴다. 요구·결함 식별자, 설계·문서 변경, 데이터 마이그레이션이 맞게 연결되었는지 확인한다. 시험 실패를 숨기기 위해 테스트를 삭제하거나 건너뛰지 않는다.

단계 5: 선택 등록과 커밋

도구에서 의도한 파일·변경 조각만 스테이징하고 다시 차이를 검토한다. 커밋 메시지는 무엇과 왜를 설명하고 지침의 작업 항목을 참조한다.

코드 예시 · text

제목: 주문 취소 시 재고 복원 누락 수정

본문:
- 취소 트랜잭션에 재고 복원 단계 추가
- 동시 취소 회귀 시험 추가
- 관련 작업: approved-change-id

“수정”, “작업”처럼 의미 없는 제목이나 민감정보를 메시지에 넣지 않는다. 커밋 뒤 식별자를 작업 기록에 연결한다.

단계 6: 원격 등록·리뷰·병합

개인 작업 브랜치를 승인 원격 저장소에 게시하고 변경 요청을 만든다. 자동 검사와 동료 검토를 통과한 뒤 보호된 대상 브랜치에 병합한다. 승인 없이 보호를 해제하거나 실패 검사를 우회하지 않는다.

단계 7: 기준선과 상태 기록

릴리즈 후보가 승인되면 지침에 따른 태그·리비전·기준선을 등록하고 변경 목록, 빌드·시험·패키지와 연결한다. 태그 이름만 믿지 말고 태그가 가리키는 불변 식별자를 기록한다.

06

5. 버전 번호와 기준선 판단

버전 번호는 조직 규칙을 따른다. 주.부.수 형태를 쓰는 곳도 있지만 모든 프로젝트가 같은 의미를 채택하는 것은 아니다. 일반적인 판단 예시는 다음과 같다.

  • 호환되지 않는 공개 인터페이스 변경: 큰 범주의 버전 변경 후보
  • 하위 호환 신규 기능: 기능 범주의 버전 변경 후보
  • 호환 결함 수정: 수정 범주의 버전 변경 후보
  • 시험·내부 빌드: 사전 배포·빌드 식별자 후보

정확한 증분 기준은 제품 계약과 지침이 정답이다. 버전 문자열을 수동으로 여러 파일에서 각각 고치면 불일치가 생긴다. 가능하면 단일 기준에서 생성하고 패키지·릴리즈 노트·문서의 표시와 자동 비교한다.

기준선은 “그 시점에 최신인 코드”가 아니라 검토·시험·승인된 구성이다. 기준선 이후 변경은 새 변경 절차를 거쳐야 하며 기존 태그를 몰래 다른 커밋으로 이동하지 않는다.

07

6. 형상관리 지침에 따른 버전관리 도구 사용

형상관리 지침에 따른 버전관리 도구 사용은 명령 실행 능력뿐 아니라 상태를 읽고 위험을 판단하며 협업 규칙을 지키는 능력이다.

6.1 조회와 비교

작업 상태, 이력, 특정 변경, 두 기준점 차이를 조회해 “어떤 파일을 누가 왜 바꿨는가”를 확인한다. 작성자 정보만으로 책임을 단정하지 않고 리뷰·병합·자동화 계정과 실제 변경 요청을 함께 본다.

코드 예시 · bash

git log --oneline --decorate -n 10
git show --stat <확인한-커밋>
git diff <기준점-A>..<기준점-B> -- path/to/file

식별자는 신뢰된 작업 기록에서 가져오고, 명령 결과가 예상 범위인지 확인한다.

6.2 브랜치

브랜치는 변경을 격리한다. 짧은 작업 브랜치는 통합 지연을 줄이지만 작업이 크면 기능을 안전하게 비활성화하는 전략이 필요할 수 있다. 장기 릴리즈 브랜치는 병렬 유지에 유용하지만 수정 누락과 중복 병합 위험이 커진다.

6.3 병합과 충돌

충돌은 같은 부분의 변경 의도를 도구가 자동 결정할 수 없다는 신호다. 표시만 제거하고 양쪽 내용을 모두 남기는 것이 해결은 아니다.

코드 예시 · text

충돌 처리
  1. 두 변경의 요구·작성자·기준점을 확인한다.
  2. 목표 동작을 결정하고 파일을 의도대로 편집한다.
  3. 충돌 표시와 중복·누락을 검토한다.
  4. 관련 시험을 다시 실행한다.
  5. 리뷰에서 해결 근거를 설명한다.

6.4 되돌리기

공유 이력에서는 잘못된 변경을 상쇄하는 새 변경이 감사와 협업에 유리할 수 있다. 기록 자체를 재작성하면 다른 작업자의 기준이 깨질 수 있다. 어떤 방법을 쓸지는 게시 여부와 지침을 확인하고, 배포된 데이터·스키마·외부 효과는 코드 되돌리기만으로 복구되지 않음을 고려한다.

6.5 태그와 릴리즈

태그는 승인된 기준점을 사람이 읽기 쉬운 이름으로 식별한다. 서명 태그가 필요한지, 누가 생성할 수 있는지, 사전 배포 이름과 공식 릴리즈 이름을 지침으로 정한다. 태그 생성은 빌드·시험·승인 완료 후 수행하고 아티팩트 해시와 연결한다.

08

7. 협업·보안·운영 통제

7.1 최소 권한

읽기, 변경 게시, 리뷰, 병합, 태그, 관리자 권한을 분리한다. 기본 브랜치 직접 쓰기를 제한하고 일정 수의 리뷰·검사 통과를 요구할 수 있다. 퇴직·역할 변경 때 권한과 토큰을 회수한다.

7.2 인증정보

개인 계정과 자동화 계정을 구분하고 토큰 범위·만료를 최소화한다. 원격 주소나 스크립트에 비밀번호를 넣지 않는다. 비밀 유출을 발견하면 저장소에서 보이지 않게 하는 작업보다 먼저 비밀 자체를 회전한다.

7.3 백업과 복구

원격 저장소가 있다고 백업이 자동 보장되는 것은 아니다. 저장소 데이터, 이슈·리뷰·권한·태그·큰 파일 저장소를 포함한 백업 범위와 주기를 정하고 복구 시험을 한다. 복제본이 많아도 모두 같은 삭제·손상을 동기화할 수 있다.

7.4 감사와 보존

누가 언제 어떤 변경을 승인·병합·태그했는지, 보호 설정을 바꿨는지 기록한다. 규정된 보존 기간과 개인정보 최소화를 함께 지킨다. 개인 이메일·토큰 등 불필요한 민감정보를 커밋 메시지에 남기지 않는다.

09

8. 구체 시나리오: 결함 수정 버전 등록

운영 중 “주문 취소 시 일부 재고가 복원되지 않는다”는 결함이 승인되었다.

  1. 작업자는 지침의 유지보수 브랜치와 승인 작업 항목을 확인한다.
  2. 깨끗한 기준점에서 작업 브랜치를 만들고 기존 변경이 없는지 조회한다.
  3. 트랜잭션 처리와 회귀 시험만 수정하고 무관한 서식 변경을 분리한다.
  4. 상태·차이를 검토해 비밀, 로그, 임시 데이터가 없는지 확인한다.
  5. 결함 재현 시험이 수정 전 실패하고 수정 후 통과하는지 확인한다.
  6. 목적·근거가 드러나는 커밋을 등록하고 원격 변경 요청을 만든다.
  7. 자동 검사와 동료 리뷰, 충돌 해결 후 보호 브랜치에 병합한다.
  8. 릴리즈 승인 뒤 지침의 버전·태그를 등록하고 빌드·패키지 해시와 연결한다.
  9. 병렬 지원 브랜치에도 필요한지 변경 관리자가 판단해 별도 적용·시험한다.

다른 브랜치에 같은 수정이 필요하다고 무조건 커밋을 복사하지 않는다. 코드 구조와 의존성이 달라질 수 있으므로 대상 버전에서 충돌·회귀를 다시 검토한다.

10

9. 산출물과 체크리스트

산출물은 형상 항목 목록, 저장소·브랜치 지침, 작업 항목과 커밋 연결, 변경 차이·시험 결과, 리뷰·병합 기록, 버전·태그·기준선 기록, 릴리즈 아티팩트 연결표, 접근 권한표, 백업·복구 시험, 형상 감사 결과다.

  • [ ] 올바른 저장소·브랜치·최신 승인 기준에서 시작했다.
  • [ ] 변경이 승인 요구·결함 하나의 목적에 맞게 구성됐다.
  • [ ] 상태와 전체 차이를 검토하고 비밀·생성 파일을 제외했다.
  • [ ] 코드·시험·문서·스키마 영향이 함께 반영됐다.
  • [ ] 커밋 메시지와 작업 항목이 목적·근거를 추적한다.
  • [ ] 자동 검사·필수 리뷰·보호 브랜치 규칙을 통과했다.
  • [ ] 충돌 해결 후 관련 시험을 다시 실행했다.
  • [ ] 버전·태그가 지침과 승인된 불변 기준점을 가리킨다.
  • [ ] 빌드·패키지·릴리즈 노트가 소스 기준점과 연결된다.
  • [ ] 최소 권한, 감사, 백업과 실제 복구 시험이 운영된다.
11

10. 자주 틀리는 포인트와 실기 함정

  1. 버전관리 도구에 파일을 넣는 것만으로 형상관리가 끝난다고 본다.
  2. 모두 추가 후 차이를 보지 않아 비밀·로그·삭제를 함께 등록한다.
  3. 기능, 서식, 의존성 갱신을 한 변경 집합에 섞는다.
  4. 제외 규칙을 추가하면 과거에 등록된 비밀도 사라진다고 생각한다.
  5. 충돌 표시만 지우고 요구에 맞는 최종 동작을 시험하지 않는다.
  6. 공유 이력을 임의 재작성해 다른 작업자의 기준을 깨뜨린다.
  7. 태그 이름은 기록하면서 실제 불변 커밋과 승인 근거를 남기지 않는다.
  8. 모든 제품에 같은 버전 번호 의미와 브랜치 전략을 강요한다.
  9. 원격 저장소가 있으니 별도 백업·복구 시험이 필요 없다고 본다.
  10. 코드를 되돌리면 이미 변경된 데이터와 외부 효과도 자동 복구된다고 본다.

11. 확인 문제

문제 1

버전관리와 형상관리의 범위 차이를 설명하시오.

문제 2

버전 등록 전에 작업 상태와 전체 차이를 확인하는 이유를 세 가지 쓰시오.

문제 3

좋은 변경 집합과 커밋 메시지가 갖춰야 할 조건은 무엇인가?

문제 4

비밀키가 이미 저장소 이력에 등록된 것을 발견했다. 우선해야 할 대응은 무엇인가?

문제 5

병합 충돌을 올바르게 해결하는 절차를 설명하시오.

문제 6

기준선과 단순 최신 상태의 차이는 무엇인가?

문제 7

공유 저장소에서 기록 재작성이 위험한 이유를 쓰시오.

문제 8

릴리즈 태그를 소스 이외의 어떤 증적과 연결해야 하는가?

문제 9

승인 결함 수정의 시작부터 버전 기준선 등록까지 절차를 순서대로 요약하시오.

13

12. 정답과 해설

문제 1 정답과 해설

버전관리는 파일 변경 이력의 저장·조회·비교·복구를 담당한다. 형상관리는 형상 항목 식별, 변경 통제, 기준선, 상태 기록, 감사와 도구·권한 운영까지 포함한다.

문제 2 정답과 해설

다른 사람의 기존 변경을 섞지 않고, 예상 밖 삭제·대량 서식 변경을 찾으며, 비밀·로그·중간 산출물이 등록되는 일을 막기 위해서다.

문제 3 정답과 해설

하나의 승인 목적을 원자적으로 완성하고 관련 시험·문서를 포함해야 한다. 메시지는 무엇을 왜 바꿨는지와 승인 작업 항목을 설명하되 민감정보를 넣지 않는다.

문제 4 정답과 해설

현재 파일 삭제보다 비밀 자체의 회전·폐기로 더 이상 악용되지 않게 하는 일이 우선이다. 이후 보안 지침에 따라 영향 조사, 이력 정리 필요성, 감사·통지를 처리한다.

문제 5 정답과 해설

양쪽 변경의 요구·기준점을 이해하고 의도한 최종 내용을 편집한다. 충돌 표시와 누락·중복을 확인한 뒤 관련 시험을 다시 실행하고 리뷰에 해결 근거를 남긴다.

문제 6 정답과 해설

최신 상태는 단지 가장 최근 변경일 수 있다. 기준선은 정해진 구성에 대해 검토·시험·승인을 마쳐 후속 빌드·변경의 공식 기준이 된 상태다.

문제 7 정답과 해설

다른 작업자가 이미 사용한 식별자와 조상 관계가 바뀌어 병합·추적이 혼란스러워지고 감사 기록도 손상될 수 있다. 게시 여부와 지침을 확인해 상쇄 변경 등 안전한 방법을 선택한다.

문제 8 정답과 해설

변경·리뷰 승인, 시험 결과, 빌드 식별, 패키지·이미지 해시, 릴리즈 노트·문서 버전과 연결해야 소스에서 배포본까지 추적할 수 있다.

문제 9 정답과 해설

지침·작업·기준 확인 → 격리 브랜치 → 원자적 수정·시험 → 상태·차이 검토 → 커밋·원격 등록 → 자동 검사·리뷰 → 충돌 해결·병합 → 릴리즈 승인 → 버전·태그·아티팩트 연결 순이다.

13. 핵심 요약

  • 형상관리 지침에 따른 버전 등록은 승인 기준에서 변경 범위·차이·시험·비밀을 검토하고 하나의 목적을 가진 변경 집합으로 등록한 뒤 리뷰와 기준선까지 추적하는 일이다.
  • 형상관리는 버전 이력뿐 아니라 항목 식별, 변경 통제, 기준선, 상태 기록, 권한, 감사와 복구를 포함한다.
  • 비밀·고객 데이터·캐시·중간 산출물은 저장소에 넣지 않으며 유출 발견 시 값 회전을 우선한다.
  • 형상관리 지침에 따른 버전관리 도구 사용은 상태·차이·이력을 읽고 브랜치·병합·태그·되돌리기를 조직 규칙과 협업 안전성에 맞게 사용하는 것이다.
  • 승인 태그는 불변 소스 기준점뿐 아니라 시험·빌드·패키지·문서와 연결해야 하며, 최소 권한과 백업·복구 시험으로 저장소 운영을 검증한다.
