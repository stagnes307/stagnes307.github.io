버전관리 도구에 소스가 있다는 사실만으로 제품을 복구할 수 있는 것은 아니다. 배포한 소스 리비전, 의존 패키지, 빌드 도구, 설정 스키마, DB 변경, 매뉴얼과 설치 파일의 조합을 알아야 같은 제품을 다시 만들 수 있다. 백업도 파일을 복사했다는 기록이 아니라 정해진 복구 목표 안에 무결한 자료를 실제로 복원할 수 있는지로 판정한다.

01

1. 버전 현황이 답해야 할 질문

특정 고객 운영환경에서 장애가 발생했다고 하자. 버전 현황만으로 다음에 답할 수 있어야 한다.

  1. 현재 설치된 제품·모듈·플러그인의 정확한 버전은 무엇인가?
  2. 그 설치 파일은 어느 승인 소스와 빌드에서 생성됐는가?
  3. 어떤 라이브러리·런타임·운영체제·DB 스키마와 호환되는가?
  4. 적용된 설정·기능 플래그·데이터 변환 버전은 무엇인가?
  5. 알려진 보안·기능 결함과 지원 종료 상태는 무엇인가?
  6. 직전 안정 버전으로 복구할 자료와 절차가 있는가?
  7. 같은 산출물을 다시 빌드하거나 검증할 증거가 있는가?

v2.4 같은 제품 이름 하나로는 부족하다. 실제 배포 단위와 환경별 차이를 추적하는 버전 현황 기준선이 필요하다.

2. 버전 현황 구성요소

2.1 제품·모듈 버전

2. 버전 현황 구성요소 · 학습 표 1
항목예시
제품 버전2.4.1
빌드 IDbuild-20260828-017
소스 리비전승인 커밋의 변경 불가능 식별자
브랜치/릴리즈 기준release/2.4 기준선
빌드 시각·주체자동 빌드 서비스와 UTC 시각
상태개발, 후보, 승인, 배포, 폐기
대상 환경시험, 운영 A, 운영 B
설치 패키지 해시파일별 SHA-256 등 승인 해시
서명·증명산출물 서명, 빌드 출처 증명

브랜치 이름은 이동할 수 있으므로 정확한 리비전 식별자를 함께 기록한다. 빌드 번호가 같아도 파일을 다시 덮어쓸 수 있는 저장소라면 재현성과 감사가 깨진다. 승인 산출물은 불변으로 보관한다.

2.2 의존 구성

  • 직접·간접 라이브러리 이름과 정확 버전
  • 패키지 잠금 파일과 저장소 출처
  • 런타임·컴파일러·빌드 도구 버전
  • 운영체제·CPU 아키텍처·컨테이너 기본 이미지 식별자
  • 웹서버·DBMS·미들웨어 호환 버전
  • 라이선스·고지·보안 상태

버전 범위만 기록하면 시간이 지나 같은 소스가 다른 의존 버전을 받아 다른 결과를 만들 수 있다. 잠금 파일과 검증된 저장소 스냅샷·캐시 정책을 관리한다.

2.3 데이터·설정 버전

  • DB 스키마 마이그레이션 버전과 적용 순서
  • 기준 코드·초기 데이터·데이터 변환 스크립트 버전
  • 설정 파일 스키마와 기본값 버전
  • 환경별 실제 설정의 승인 이력과 비밀 참조
  • 기능 플래그 정의·상태·만료 책임자
  • 외부 API·메시지·파일 계약 버전

비밀번호·개인 키 같은 비밀값 자체를 일반 버전관리 저장소에 넣지 않는다. 어떤 비밀 참조 버전과 권한 정책이 필요한지는 기록하되 실제 값은 전용 비밀 관리·백업 정책을 따른다.

2.4 문서·운영 자료 버전

  • 설치·사용자·운영·장애 대응 매뉴얼
  • API·데이터·오류 코드 명세
  • 테스트 결과, 승인 기록, 알려진 제약
  • 릴리즈 노트와 변경·보안 고지
  • 라이선스·저작권 고지
  • 배포·롤백·백업·복원 절차

제품 파일과 매뉴얼 버전이 다르면 사용자는 존재하지 않는 기능을 실행하거나 잘못된 복구 절차를 따를 수 있다.

03

3. 버전 식별과 상태 모델

3.1 버전 번호 정책

조직 정책에 따라 의미 기반 버전을 사용할 수 있다.

코드 예시 · text

MAJOR.MINOR.PATCH
  • MAJOR: 호환되지 않는 변경
  • MINOR: 호환되는 기능 추가
  • PATCH: 호환되는 오류 수정

이 의미는 자동으로 생기지 않는다. 공개 API뿐 아니라 설정·DB·파일·운영 절차의 호환 범위를 정의해야 한다. 규제 제품이나 날짜 기반 버전처럼 다른 정책도 가능하며 한 제품 안에서 일관되게 적용한다.

3.2 상태 전이

코드 예시 · text

초안/개발
  → 빌드 완료
  → 검증 후보
  → 승인 릴리즈
  → 환경별 배포
  → 지원/유지보수
  → 지원 종료
  → 폐기·보존

각 전이에 필요한 증거와 권한을 둔다.

3. 버전 식별과 상태 모델 · 학습 표 2
전이필수 조건 예
빌드 완료 → 후보재현 가능한 빌드, 테스트·보안 스캔 기준 충족
후보 → 승인변경 승인, 릴리즈 노트, 설치·롤백 검증
승인 → 배포환경 변경 승인, 백업·복구점, 배포 창
지원 → 종료고객 통지, 대체 경로, 자료 보존·취약점 정책

실패한 후보 버전을 같은 번호로 고쳐 다시 올리지 않는다. 새 빌드 식별자로 이력을 보존한다.

3.3 단일 진실 원천

버전 현황이 스프레드시트, 배포 도구, 저장소 태그, 고객 기록에 따로 존재하면 불일치한다. 권위 있는 시스템을 정하고 자동 수집·연동한다.

코드 예시 · text

소스·태그 → 자동 빌드 → 불변 산출물 저장소
                 ↓
          릴리즈 현황/구성 명세
                 ↓
          환경별 배포 기록·고객 현황

수동 보정은 승인·감사·재동기화 절차를 거친다.

  • DB·설정·API 버전이 해당 제품 호환표 안에 있는가?
  • 설치·릴리즈 문서가 같은 제품 버전을 설명하는가?
  • 환경에서 수집한 실제 버전과 배포 기록이 일치하는가?

5. 백업의 범위

백업은 장애·삭제·손상·보안 사고 뒤 승인 시점의 자료를 독립적으로 복구하기 위한 사본과 절차다.

5.1 백업 대상

5. 백업의 범위 · 학습 표 3
범주대상 예주의점
소스저장소, 태그·브랜치·전체 이력작업 PC 복사만으로 부족
빌드스크립트, 잠금 파일, 도구·이미지 명세외부 저장소 소실 대비
산출물승인 설치 파일, 해시, 서명, SBOM불변성·보존·읽기 권한
데이터 변경스키마·마이그레이션·기준 데이터적용 순서와 롤백·복원 시험
설정비밀 제외 설정, 템플릿, 정책, 환경 명세실제 비밀은 전용 방식
문서매뉴얼, 설계, 승인, 테스트, 라이선스제품 버전과 묶어 보존
운영 자료배포·장애·복원 절차, 대시보드 정의대상 시스템 장애와 분리
관리 메타데이터이슈, 변경 요청, 권한·감사 이력내보내기·복원 API 검증

현재 체크아웃 파일만 백업하면 삭제된 과거 리비전과 태그, 서브모듈, 대용량 객체 저장소가 빠질 수 있다. 저장소 형태에 맞는 전체 백업 방식을 사용한다.

5.2 버전관리와 백업의 차이

5. 백업의 범위 · 학습 표 4
버전관리백업
변경 이력·협업·병합 중심장애·손상·삭제 후 복구 중심
원격 서버도 운영 시스템의 일부별도 장애·권한 도메인의 사본 필요
강제 삭제·계정 탈취·서비스 장애 영향 가능격리·불변·보존 정책으로 영향 제한
소스 중심산출물·설정·문서·메타데이터까지 포함

원격 저장소가 있다는 사실은 중요하지만 단독 백업 전략으로 충분하지 않을 수 있다.

6. 백업 요구 정의

6.1 RPO와 RTO

  • RPO(Recovery Point Objective): 장애 시 어느 시점까지의 변경 손실을 허용하는가?
  • RTO(Recovery Time Objective): 복구에 허용하는 시간은 얼마인가?

소스 저장소 RPO 24시간이라면 그 사이 승인된 보안 수정이 사라질 수 있다. 변경 빈도와 사업 영향을 근거로 대상별 수치를 정한다.

6.2 보존 정책

코드 예시 · text

단기: 빈번한 최근 백업으로 실수 복구
중기: 릴리즈·월별 기준선 보존
장기: 법·계약·감사·제품 지원 기간에 맞춘 보존

백업 세대와 삭제 승인, 법적 보존·소송 보존, 고객 데이터 파기 의무가 충돌하지 않게 한다. “영구 보존”은 비용·개인정보·암호 키 수명 문제를 만든다.

6.3 독립성과 3-2-1 원칙

일반적 출발점으로 데이터 사본 3개, 서로 다른 매체/시스템 2종, 별도 위치 1개를 고려한다. 실제 위험에는 다음을 더 본다.

  • 운영 관리자 계정과 분리된 백업 삭제 권한
  • 일정 기간 변경·삭제할 수 없는 불변 사본
  • 네트워크 격리 또는 오프라인 사본
  • 같은 클라우드 계정·지역·암호 키 의존 여부
  • 백업 관리 시스템 자체의 복구 자료

사본 개수보다 공통 장애와 공통 자격증명을 분리하는 것이 중요하다.

6.4 보안

  • 전송·저장 암호화와 키 수명·복구
  • 최소 권한, 개인별 관리 계정, 다중 승인 삭제
  • 백업 목록·복원·삭제 감사
  • 비밀·개인정보 포함 여부와 마스킹·보존
  • 무결성 해시·서명과 악성 변경 탐지
  • 복원 환경이 운영망을 오염시키지 않도록 격리

암호화 백업의 키를 잃으면 자료가 있어도 복원할 수 없다. 키 백업·회전·폐기와 역할 분리를 함께 시험한다.

07

7. 백업 방식과 주기

7.1 전체·증분·차등

7. 백업 방식과 주기 · 학습 표 5
방식저장 내용장점복구 고려
전체대상 전체복구 경로 단순시간·용량 큼
증분직전 백업 이후 변경빠르고 작음전체+증분 연쇄가 필요, 한 조각 손상 영향
차등마지막 전체 이후 변경증분보다 복구 단순시간이 갈수록 커짐

소스 저장소의 객체 단위 백업과 산출물 저장소 스냅샷은 전통 파일 백업과 동작이 다를 수 있다. 도구 용어보다 어떤 시점과 의존 사본이 필요한지 확인한다.

7.2 이벤트 기반 백업

정기 주기 외에 다음 사건에서 보호 지점을 만든다.

  • 승인 릴리즈 직전·직후
  • 대규모 마이그레이션·저장소 구조 변경 전
  • 보존 정책·권한·암호 키 변경 전
  • 제품 지원 종료·고객 인계 전
  • 중요 보안 사고 대응 중 증거 보존

7.3 일관된 백업

여러 저장소의 상태가 함께 맞아야 하면 백업 시점과 순서를 정한다.

코드 예시 · text

릴리즈 명세
  ↔ 소스 리비전
  ↔ 빌드 산출물·해시
  ↔ DB 마이그레이션
  ↔ 문서·승인

각각 다른 시점의 최신 파일만 모으면 서로 호환되지 않을 수 있다. 릴리즈 ID와 불변 참조로 묶는다.

08

8. 백업 절차

단계 1: 자산·책임·중요도 식별

  • 소스, 산출물, 설정, 데이터 변경, 문서, 메타데이터를 목록화한다.
  • 소유자, 백업 책임자, 복원 승인자와 중요도를 정한다.
  • 외부 서비스가 제공하는 내보내기·보존 한계를 확인한다.

단계 2: 복구 요구와 위험 분석

  • 실수 삭제, 저장소 손상, 계정 탈취, 랜섬웨어, 지역 장애와 공급자 종료를 가정한다.
  • 대상별 RPO·RTO·보존·법적 요구를 승인한다.
  • 공통 장애·계정·키·네트워크 의존을 표시한다.

단계 3: 방식·주기·저장소 설계

  • 전체·증분·스냅샷·복제를 조합한다.
  • 별도 위치·계정·불변·오프라인 계층을 정한다.
  • 용량 증가, 전송 창, 비용과 만료·삭제 정책을 산정한다.

단계 4: 자동화와 보호

  • 백업 시작·완료·실패·누락을 자동 기록한다.
  • 암호화, 최소 권한, 삭제 다중 승인과 감사 설정을 적용한다.
  • 해시·서명으로 전송·보관 무결성을 검증한다.
  • 실패 경보에는 책임자와 재실행·에스컬레이션 행동을 연결한다.

단계 5: 복원 절차 작성

  • 우선순위와 필요한 자격·키·도구를 적는다.
  • 새 격리 환경을 준비하고 백업을 선택하는 기준을 둔다.
  • 복원 순서, 의존 관계, 무결성·기능 확인을 명시한다.
  • 서비스 재개·사용자 통지·사후 대사와 임시 자원 정리를 포함한다.

단계 6: 정기 복원 시험

  • 파일 하나가 아니라 실제 제품 빌드·설치 가능한 범위를 복원한다.
  • 담당자가 바뀌어도 문서만으로 수행 가능한지 본다.
  • RPO·RTO, 누락 자료, 수동 단계와 오류를 기록한다.
  • 실패 원인을 개선하고 다시 시험한다.
09

9. 복원 검증 시나리오

9.1 소스 저장소 전체 복원

검증 항목:

  • 모든 필요한 브랜치·태그·리비전·대용량 객체가 존재
  • 권한·보호 정책을 승인 상태로 재구성 가능
  • 릴리즈 리비전을 체크아웃하고 서브모듈·의존 참조를 해결
  • 이슈·변경 승인과 추적 링크 복구

9.2 승인 릴리즈 재현

코드 예시 · text

1. 격리된 깨끗한 빌드 환경 준비
2. 버전 현황 명세의 소스·도구·의존 버전 복원
3. 네트워크 의존을 승인 저장소로 제한해 빌드
4. 테스트·보안·라이선스 검증 실행
5. 새 산출물 해시와 승인 원본 비교
6. 설치·기동·핵심 기능·DB 호환 시험

완전 재현 빌드가 목표가 아니더라도 기능·서명·구성 검증 기준을 정의한다. 시각·빌드 경로 같은 비결정 요소가 해시에 영향을 주면 원인을 문서화하고 줄인다.

9.3 운영 자료 복원

대상 시스템이 사라진 상태에서 설치 매뉴얼, 배포 설정, 모니터링·경보 정의, 장애 런북과 연락 체계를 복원해 실제 서비스 재구성이 가능한지 확인한다.

9.4 손상·공격 상황

백업 시점이 감염 전인지 판단하고 격리 환경에서 악성 변경과 자격정보 노출을 검사한다. 손상된 운영 설정·비밀을 그대로 복원하지 않고 자격정보를 회전하며 보안 검증 뒤 서비스에 연결한다.

10

10. 제품소프트웨어 버전관리하기의 적용 절차와 판단 기준

10.1 계획

  1. 형상 항목과 제품 구성 단위를 식별한다.
  2. 버전 번호·브랜치·태그·빌드·상태 전이 정책을 정한다.
  3. 역할·승인·접근·변경·감사와 백업 책임을 정한다.

판단: 소스뿐 아니라 의존·설정 스키마·DB·문서·산출물이 범위에 있는가?

10.2 등록·빌드

  1. 승인 변경을 추적 ID와 함께 등록한다.
  2. 자동 빌드가 정확한 리비전·잠금 의존을 사용한다.
  3. 테스트·보안·라이선스 기준을 통과한 산출물에 불변 ID·해시·출처를 부여한다.

판단: 같은 버전 번호를 덮어쓰지 않고 산출물에서 소스로 역추적 가능한가?

10.3 검증·승인·배포

  1. 버전 현황 명세와 릴리즈 노트·매뉴얼을 만든다.
  2. 기능·호환·설치·롤백·보안·데이터 변경을 검증한다.
  3. 승인된 동일 산출물을 환경별로 승격하고 실제 배포 현황을 기록한다.

판단: 시험한 파일과 배포한 파일의 해시가 같고 환경 차이가 승인됐는가?

10.4 유지·변경

  1. 환경·고객별 설치 버전과 지원·취약점 상태를 모니터링한다.
  2. 핫픽스도 원래 변경·빌드·승인 흐름에 역반영한다.
  3. 계약·DB·설정 호환과 지원 종료 일정을 관리한다.

판단: 긴급 변경이 기준선 밖의 숨은 버전으로 남지 않는가?

10.5 백업·복원·폐기

  1. 대상별 RPO·RTO·보존에 맞춰 독립 백업한다.
  2. 자동 무결성 검사와 정기 실제 복원 시험을 수행한다.
  3. 지원 종료 뒤 법·계약·보안에 맞게 자료를 보존·파기한다.

판단: 권한 있는 사람이 목표 시간 안에 지정 버전을 완전하게 복원·검증할 수 있는가?

11. 운영 지표와 점검표

11.1 버전관리 지표

  • 승인 산출물 중 소스·의존·문서 추적 완전율
  • 환경 실제 버전과 배포 기록 불일치 수
  • 지원 종료·알려진 취약 버전 잔존 기간
  • 재현 빌드·설치 검증 성공률
  • 긴급 변경의 정규 기준선 반영 시간

숫자 달성을 위해 실패 기록을 지우지 않고 실제 위험 감소와 연결한다.

11.2 백업 지표

  • 백업 성공률보다 예정 백업 누락과 마지막 성공 시각
  • 대상별 RPO 초과 시간
  • 정기 복원 성공률과 실제 RTO
  • 무결성 오류·손상 사본 수
  • 불변·오프사이트 사본의 최신성
  • 키·자격정보 복구 시험 결과

11.3 일일·릴리즈 점검

  • 자동 백업·복제·내보내기 실패가 없는가?
  • 저장 용량과 보존 만료가 예상대로인가?
  • 새 저장소·문서·산출물이 백업 범위에 등록됐는가?
  • 릴리즈 명세의 리비전·해시·DB·문서 버전이 일치하는가?
  • 실제 배포 인벤토리가 자동 갱신됐는가?
  • 마지막 복원 시험의 미해결 조치가 남아 있는가?

12. 자주 틀리는 포인트

  1. 제품 버전 번호만 알면 전체 현황을 안다? 소스·빌드·의존·DB·설정·계약·문서 조합이 필요하다.
  2. 브랜치 이름은 불변 소스 식별자다? 이동할 수 있으므로 정확한 리비전을 기록한다.
  3. 같은 버전 파일을 고쳐 덮어써도 고객이 받으면 된다? 감사·재현·해시가 깨지므로 새 빌드 식별자를 부여한다.
  4. 패키지 잠금 파일 없이 버전 범위만 있어도 재현된다? 시간이 지나 다른 간접 의존이 선택될 수 있다.
  5. 실제 비밀값을 설정과 함께 저장소에 백업한다? 전용 비밀 관리·키 정책으로 분리한다.
  6. 원격 Git 저장소가 있으니 백업은 필요 없다? 강제 삭제·계정 탈취·서비스 장애와 비소스 자료를 고려해야 한다.
  7. 백업 성공 로그가 있으면 복구 가능하다? 실제 복원·빌드·설치·무결성 시험이 필요하다.
  8. 복제는 백업과 같다? 삭제·손상이 즉시 복제될 수 있어 시점·불변 사본이 필요하다.
  9. 사본을 같은 계정·지역에 여러 개 두면 독립적이다? 공통 자격·지역 장애에 함께 영향받을 수 있다.
  10. 암호화하면 백업이 안전하고 복원도 된다? 키 접근·백업·회전·폐기를 시험해야 한다.
  11. RPO는 복구에 걸리는 시간이다? RPO는 허용 데이터 손실 시점, RTO가 복구 시간 목표다.
  12. 전체 파일 최신본만 모으면 일관된 제품 백업이다? 소스·산출물·DB·문서의 릴리즈 기준 시점을 묶어야 한다.
  13. 핫픽스는 급하므로 나중에 정규 저장소에 반영하지 않아도 된다? 숨은 운영 버전과 재발 위험을 만든다.
  14. 지원 종료면 즉시 모든 자료를 삭제한다? 법·계약·감사·복구·개인정보 파기 요구를 함께 승인한다.
  15. 백업 보존은 길수록 좋다? 비용·비밀·개인정보·취약 자료 노출과 파기 의무를 고려한다.

브랜치 이름과 불변 소스 리비전의 차이, 승인 산출물 해시가 필요한 이유를 설명하라.

DB 스키마·설정·외부 API 버전을 제품 버전과 함께 관리해야 하는 이유를 쓰라.

버전관리 저장소와 독립 백업의 목적 차이를 네 가지 관점에서 비교하라.

14. 정답과 해설

정답 1

빌드 ID, 정확한 소스 리비전, 산출물 파일·해시·서명, 직접·간접 의존과 잠금 파일, 런타임·빌드 도구, OS·아키텍처, DB 스키마, 설정 스키마·기능 플래그, 인터페이스 계약, 설치·릴리즈 문서, 승인·배포·지원 상태와 대상 환경을 포함한다.

정답 2

브랜치는 새 커밋을 가리키며 이동하지만 리비전 식별자는 특정 소스 상태를 가리킨다. 산출물 해시는 저장·전송 중 변경 여부를 확인하고 시험한 파일과 배포·복원한 파일이 같은지 증명해 같은 버전 덮어쓰기를 발견하게 한다.

정답 3

같은 애플리케이션도 스키마·설정 형식·계약 버전이 맞지 않으면 기동 실패, 데이터 손상, 해석 불일치가 생긴다. 호환 행렬과 적용 순서, 롤백 가능성을 알아야 배포·복구할 수 있다.

정답 4

버전관리는 변경 이력·협업·병합과 소스 기준선에 집중한다. 백업은 저장소 자체의 삭제·손상·계정 탈취·서비스 장애 후 복구에 집중하며 별도 장애·권한 도메인을 둔다. 백업은 산출물·설정·문서·메타데이터도 포함하고, 불변 보존과 RPO/RTO·복원 시험을 가진다.

정답 5

RPO는 장애 때 허용할 수 있는 마지막 변경 손실 시점이므로 “최대 몇 시간의 커밋·이슈·승인 이력을 잃어도 되는가?”를 묻는다. RTO는 “새 환경에서 저장소·권한·릴리즈 빌드를 몇 시간 안에 복구해야 하는가?”를 묻는다.

정답 6

전체는 모든 자료를 저장해 복구가 단순하지만 시간·용량이 크다. 증분은 직전 백업 이후만 저장해 작고 빠르나 전체와 이후 모든 증분 연쇄가 필요하다. 차등은 마지막 전체 이후 변경을 저장해 전체+최신 차등으로 복구하지만 시간이 지날수록 차등이 커진다.

정답 7

한 계정 탈취·삭제 권한·지역 장애·공통 암호 키·공급자 장애가 세 사본에 동시에 영향을 줄 수 있다. 별도 계정·지역·매체, 다중 승인 삭제, 일정 기간 불변 사본, 오프라인/격리 사본과 독립 키·관리 역할을 사용한다.

정답 8

격리된 깨끗한 환경을 준비하고 버전 명세의 소스·도구·잠금 의존을 복원한다. 승인 저장소만 사용해 빌드하고 테스트·보안·라이선스 검증을 실행한다. 생성 산출물과 승인 원본의 해시 또는 기능적 재현 기준을 비교하고, 설치·기동·DB·설정·핵심 기능을 시험한 뒤 시간·누락·수동 단계를 기록한다.

정답 9

형상 항목·버전 정책·역할을 계획하고, 승인 변경을 정확한 리비전으로 자동 빌드해 불변 산출물과 출처를 만든다. 기능·보안·호환·설치·롤백을 검증·승인하고 같은 파일을 환경에 승격한다. 환경별 현황·지원·핫픽스를 기준선에 유지하고, 독립 백업·복원 시험을 거쳐 지원 종료 자료를 승인된 보존·파기 정책으로 폐기한다.

정답 10

지정 시점의 모든 소스 이력·산출물·의존·DB·설정·문서가 있고 해시·서명이 유효해야 한다. 필요한 키·자격·도구와 문서로 권한 있는 담당자가 RPO·RTO 안에 격리 환경에 복원해 제품을 빌드·설치·기동하고 핵심 기능·호환·보안을 검증할 수 있어야 한다. 정기 시험의 실패 조치도 닫혀야 한다.

15

15. 핵심 요약

  • 버전 현황은 제품 번호뿐 아니라 소스·빌드·의존·산출물·DB·설정·계약·문서와 환경별 상태를 묶는다.
  • 이동하는 브랜치 이름 대신 정확한 소스 리비전과 불변 산출물 해시·출처로 재현성과 추적성을 확보한다.
  • 의존 잠금, 빌드 도구·런타임, 설정·DB·API 버전이 없으면 같은 제품을 다시 만들 수 없다.
  • 개발–후보–승인–배포–지원–종료 상태 전이에 검증·승인 증거를 두고 같은 버전을 덮어쓰지 않는다.
  • 버전관리는 변경·협업 기준선이고 백업은 저장소 자체와 관련 자료의 삭제·손상·공격 후 복구 수단이다.
  • 백업 범위에는 전체 소스 이력, 빌드·산출물, 데이터 변경, 설정, 문서, 이슈·승인·운영 메타데이터가 포함된다.
  • RPO·RTO·보존·법적 요구로 주기와 방식을 정하고 전체·증분·차등·이벤트 보호 지점을 조합한다.
  • 사본을 별도 계정·지역·매체와 불변·격리 계층에 두어 공통 장애·자격증명 영향을 줄인다.
  • 암호화·최소 권한·삭제 승인·감사·무결성 검증과 키 복구가 함께 작동해야 한다.
  • 백업 완료는 성공 로그가 아니라 정기 실제 복원–빌드–설치–기능·보안 검증이 RPO·RTO 안에 성공하는지로 판정한다.
