01

수행 범위와 목표

이 레슨의 정확한 토픽은 논리 설계에서 데이터 유형 확인·식별과 데이터 논리 단위와 관계 확인이다. 요구사항과 업무 규칙에서 데이터의 의미와 유형을 찾아 데이터 사전에 기록하고, 엔터티·속성·식별자와 엔터티 사이 관계를 논리적으로 확인하는 실무를 다룬다.

널, 유일성, 참조 동작 같은 세부 제약과 논리 저장소 확인 전체 절차는 다음 레슨에서 다룬다. 특정 DBMS의 저장 형식, 인덱스, 파티션 같은 물리 설계도 이후 범위다. 여기서는 구현 제품과 독립적인 업무 의미를 정확히 모델링하는 데 집중한다.

학습 목표는 다음과 같다.

  1. 값의 겉모양이 아니라 업무 의미와 연산에 따라 논리 데이터 유형을 식별한다.
  2. 엔터티, 속성, 식별자의 역할과 데이터 논리 단위를 구분한다.
  3. 일대일, 일대다, 다대다 관계와 선택성을 실제 업무 사례로 확인한다.
  4. 용어집, 데이터 사전, 엔터티 정의서, 관계 검토표를 작성한다.
02

1. 논리 데이터 설계의 관점

논리 데이터 설계는 “어느 DBMS의 어떤 자료형을 쓸까”보다 “업무가 관리해야 하는 사실은 무엇이며 서로 어떻게 연결되는가”를 정한다. 같은 논리 모델을 관계형 데이터베이스, 문서 저장소 등 다른 구현에 옮길 수 있도록 업무 의미를 먼저 확정한다.

예를 들어 고객번호가 숫자 문자로만 구성되어 있어도 더하기나 범위 계산을 하지 않고 앞자리 0을 보존해야 한다면 논리적으로 식별 코드다. 금액은 숫자이지만 통화와 소수 정밀도가 함께 필요하다. 배송일은 “날짜만”인지 “특정 시간대의 순간”인지에 따라 의미가 다르다.

업무 문장 ↓ 명사·사건·규칙 분석 데이터 후보 ├─ 엔터티: 독립적으로 관리할 대상 ├─ 속성: 대상의 성질 ├─ 식별자: 같은 종류의 대상을 구별 └─ 관계: 대상 사이의 업무 연결 ↓ 논리 데이터 모델 + 데이터 사전

03

2. 논리 설계에서 데이터 유형 확인·식별

2.1 문자 유형

이름, 설명, 주소, 코드처럼 문자로 표현하는 값이다. 길이가 고정인지 가변인지보다 먼저 허용 문자, 대소문자 의미, 앞자리 0, 다국어, 검색·정렬 방식을 확인한다.

  • 상품코드는 숫자로만 보여도 계산 대상이 아니라 문자 코드일 수 있다.
  • 전화번호는 국가기호, 구분자, 앞자리 0 때문에 숫자 연산에 적합하지 않다.
  • 긴 설명은 일반 이름과 최대 길이·검색 방식이 다를 수 있다.

논리 사전에는 “문자”라고만 쓰지 않고 형식, 최대 업무 길이, 공백 처리, 대소문자 구분, 예시를 남긴다.

2.2 정수·정확 소수·근사 수치

수량과 횟수는 정수, 금액·세율처럼 정확한 십진 계산이 필요한 값은 정밀도와 소수 자릿수를 가진 정확 수치로 정의한다. 센서 측정처럼 본질적으로 오차가 있고 매우 넓은 범위를 표현하는 값은 근사 수치를 검토할 수 있다.

금액을 근사 부동소수 형태로 처리하면 이진 표현과 반올림으로 합계가 기대와 다를 수 있다. 논리 단계에서 통화, 반올림 시점, 최소 단위, 음수 허용 의미를 정한다. 물리 자료형 이름은 목표 DBMS를 결정한 뒤 매핑한다.

2.4 불리언과 상태 코드

참·거짓만 있는 값은 불리언 의미로 정의할 수 있다. 그러나 “승인 여부”가 미검토, 승인, 반려, 만료를 가진다면 불리언 하나로는 부족하다. 상태 코드와 상태 전이 모델이 필요하다.

코드값에는 코드명, 의미, 유효 기간, 사용 가능 여부, 표시 순서를 정의한다. 코드 목록이 바뀔 수 있고 설명 속성이 있다면 별도 논리 단위로 관리할 수 있다.

2.5 이진·대용량 데이터

문서, 이미지, 서명 파일 같은 이진 데이터는 크기 분포, 콘텐츠 유형, 보존, 검색, 접근 권한을 확인한다. 파일 본문과 메타데이터를 같은 논리 단위로 볼지, 외부 객체 저장소의 위치만 관리할지 요구에 따라 결정한다. 구체 저장 방식은 물리 설계에서 판단한다.

2.6 열거·복합·집합 의미

주소처럼 여러 부분으로 구성된 값은 검색·검증·변경 단위를 기준으로 속성을 나눈다. 한 칼럼에 여러 태그나 전화번호를 쉼표로 넣는 방식은 개별 값의 관계와 검색을 표현하기 어렵다. 반복 가능한 값이 독립 생명주기와 속성을 가지면 별도 논리 단위 후보로 식별한다.

2.7 파생·이력·시점 데이터

생년월일에서 계산되는 현재 나이는 시간에 따라 변하는 파생값이다. 저장할 원천과 계산 규칙을 구분한다. 주문 당시 가격은 현재 상품가격의 단순 복제가 아니라 거래 시점의 사실이다. 현재값, 과거 스냅숏, 계산값을 데이터 사전에 명시한다.

3. 유형 식별 절차

  1. 업무 용어 수집: 화면, 문서, 인터페이스, 보고서에서 데이터 명칭을 모은다.
  2. 정의 통합: 동의어와 동명이의를 찾고 대표 용어와 정의를 합의한다.
  3. 값 표본 확인: 정상값, 최소·최대, 빈 값, 예외 형식, 다국어를 조사한다.
  4. 사용 연산 확인: 계산, 정렬, 검색, 비교, 집계, 기간 연산 여부를 확인한다.
  5. 단위·정밀도 확인: 통화, 측정 단위, 반올림, 시간대, 코드 체계를 정한다.
  6. 논리 유형 지정: 문자, 정수, 정확 소수, 날짜·시각, 불리언, 이진 등으로 분류한다.
  7. 근거와 예시 기록: 유형 선택 이유와 경계값을 데이터 사전에 남긴다.
  8. 관계자 검토: 업무·개발·시험·데이터 담당자가 같은 의미로 이해하는지 확인한다.
05

4. 데이터 논리 단위

4.1 엔터티

엔터티는 업무에서 독립적으로 식별하고 관리해야 하는 대상 또는 사건이다. 고객, 상품 같은 실체뿐 아니라 주문, 결제, 대여처럼 발생 사건도 엔터티가 된다.

좋은 엔터티 후보는 다음 특성을 가진다.

  • 업무상 명확한 정의가 있다.
  • 여러 인스턴스가 존재할 수 있다.
  • 각 인스턴스를 구별할 식별 기준이 있다.
  • 관리할 속성과 생명주기가 있다.
  • 다른 엔터티와 관계를 가진다.

화면 하나나 보고서 한 줄을 그대로 엔터티로 만들지 않는다. 화면은 여러 엔터티의 데이터를 조합해 보여 줄 수 있다.

4.2 속성

속성은 엔터티가 관리하는 성질이다. 고객의 이름, 상품의 현재가격, 주문의 주문시각이 예다. 속성은 하나의 업무 의미를 갖고, 이름만으로 부족하면 정의·단위·값 영역을 데이터 사전에 적는다.

다른 속성에서 항상 계산되는 파생속성, 여러 값이 들어가는 반복속성, 더 나눌 수 있는 복합속성은 저장 여부와 논리 단위를 검토한다. 정규화의 세부 단계보다 여기서는 한 사실의 소유 엔터티가 어디인지에 초점을 둔다.

4.3 식별자

식별자는 같은 엔터티의 인스턴스를 유일하게 구별하는 하나 이상의 속성이다. 업무에서 자연스럽게 생기는 주문번호를 쓸 수도 있고, 시스템이 별도 식별 값을 만들 수도 있다. 후보 식별자는 유일성, 최소성, 안정성, 비널 가능성을 검토한다.

이름이나 전화번호처럼 바뀌거나 중복될 수 있는 값을 편의상 식별자로 쓰지 않는다. 복합 식별자는 업무 의미를 잘 나타낼 수 있지만 관계로 전파될 때 속성 수가 늘어난다는 점을 이후 물리 설계에서 고려한다.

4.4 값 객체와 코드 논리 단위

주소, 금액처럼 여러 속성이 하나의 의미를 이루고 독립 식별이 필요 없는 묶음을 값 객체로 표현할 수 있다. 상태코드처럼 여러 엔터티에서 공유하고 설명·유효기간을 관리한다면 코드 엔터티 후보가 된다. 모델링 표기와 구현 방식은 프로젝트 표준을 따른다.

06

5. 데이터 논리 단위와 관계 확인

관계는 두 엔터티 사이에서 업무상 성립하는 연결이다. 동사형 문장으로 읽어 의미를 확인한다.

고객은 주문을 한다. 주문은 한 명의 주문자에 의해 접수된다. 주문은 하나 이상의 주문항목을 포함한다. 상품은 여러 주문항목에 나타날 수 있다.

5.1 카디널리티

  • 일대일(1:1): 한 인스턴스가 상대 한 인스턴스와 연결된다.
  • 일대다(1:N): 한 부모가 여러 자식과 연결되며 자식은 한 부모에 연결된다.
  • 다대다(M:N): 양쪽 모두 여러 상대와 연결된다.

다대다 관계는 논리적으로 존재할 수 있지만 관계 자체에 수량, 가격, 역할 같은 속성이 있으면 연관 엔터티로 풀어낸다. 주문과 상품 사이 주문항목은 수량과 주문 당시 가격을 가진다.

5.2 선택성

관계가 필수인지 선택인지 확인한다. 신규 고객은 주문이 하나도 없을 수 있으므로 고객에서 주문으로의 최소 수는 0일 수 있다. 주문은 주문자가 반드시 필요할 수도 있지만 비회원 주문을 허용하면 식별 구조가 달라질 수 있다. 현재 데이터에 우연히 모두 값이 있다고 필수 관계라고 단정하지 않는다.

5.3 관계의 이름과 방향

“보유한다”, “관련된다”처럼 모호한 관계명보다 양쪽에서 읽을 수 있는 업무 동사를 사용한다. 조직이 직원을 소속시키고 직원이 조직에 소속된다는 식으로 역할을 명확히 한다. 같은 두 엔터티 사이에 작성자·승인자처럼 관계가 여러 개면 역할명을 구분한다.

5.4 재귀·삼항 관계

조직의 상위 조직처럼 같은 엔터티 사이 재귀 관계가 있을 수 있다. 공급자·부품·프로젝트 세 대상의 조합처럼 세 엔터티가 함께 있어야 의미가 완성되는 관계도 있다. 단순 이항 관계로 나누었을 때 원래 없던 조합이 생기지 않는지 확인한다.

07

6. 관계 확인 절차와 판단 기준

  1. 업무 문장에서 주체·대상·동사를 찾아 관계 후보를 만든다.
  2. 양쪽 방향으로 문장을 읽어 관계 의미와 역할을 확인한다.
  3. 실제 사례와 경계 사례로 최소·최대 수를 검증한다.
  4. 관계에 독립 속성이나 생명주기가 있는지 확인한다.
  5. 다대다 관계를 연관 엔터티로 풀어야 하는지 판단한다.
  6. 재귀, 이력, 시점별 관계가 누락되지 않았는지 살핀다.
  7. 유스케이스·상태·인터페이스 모델의 데이터 사용과 일치하는지 검토한다.
  8. 엔터티·관계 정의서와 용어집을 갱신한다.

판단 기준은 현재 표본의 모양보다 모든 유효 업무 사례다. “한 고객이 지금 한 주문만 있다”는 사실로 1:1을 선택하지 않는다. 앞으로 여러 주문을 할 수 있다는 업무 규칙이면 1:N이다.

08

7. 구체 업무 시나리오

상황

교육 플랫폼에서 학습자가 강좌를 신청하고, 한 신청에는 신청일, 진행상태, 진도율이 있다. 강좌는 여러 강사가 공동 담당할 수 있고 강사마다 주강사·보조강사 역할과 담당 기간이 있다.

논리 단위 도출

  • 학습자: 학습자번호, 이름
  • 강좌: 강좌번호, 제목
  • 수강신청: 학습자와 강좌의 관계를 실체화하며 신청일·상태·진도율을 가짐
  • 강사: 강사번호, 이름
  • 강좌담당: 강좌와 강사의 관계를 실체화하며 역할·담당시작일·담당종료일을 가짐

학습자 1 ─── 0..N 수강신청 N..1 ─── 1 강좌 강좌 1 ─── 1..N 강좌담당 N..1 ─── 1 강사

강좌와 학습자는 다대다지만 수강신청이라는 업무 사건이 있고 속성을 가지므로 연관 엔터티로 표현한다. 강좌와 강사도 역할·기간이 관계에 속하므로 강좌담당을 둔다.

유형 확인

  • 진도율은 정확한 비율이며 허용 범위와 소수 자릿수를 정의한다.
  • 신청일은 날짜인지 신청 순간인지 결정한다. 순서와 감사가 필요하면 시점을 사용한다.
  • 진행상태는 참·거짓이 아니라 신청·진행·수료·취소 등 코드 의미를 가진다.
  • 담당 기간은 종료일이 아직 정해지지 않을 수 있는지 업무에 확인한다.

이 레슨에서는 논리 의미와 관계를 확정하며, NOT NULL·외래 키 같은 실제 제약 표현은 다음 단계에서 결정한다.

10. 산출물과 완료 체크리스트

주요 산출물은 용어집, 데이터 사전, 엔터티 정의서, 속성 정의서, 식별자 목록, 논리 관계도, 관계 검토표다.

  • 모든 엔터티에 명확한 업무 정의와 식별 기준이 있는가?
  • 속성의 논리 유형, 단위, 시점, 값 예가 있는가?
  • 숫자처럼 보이는 코드와 실제 계산 수치를 구분했는가?
  • 날짜, 지역 시각, 절대 시점, 기간을 구분했는가?
  • 현재값, 이력 스냅숏, 파생값의 의미를 적었는가?
  • 관계를 양방향 업무 문장으로 읽을 수 있는가?
  • 최소·최대 카디널리티를 실제·경계 사례로 확인했는가?
  • 다대다 관계의 속성과 생명주기를 확인했는가?
  • 같은 두 엔터티 사이 여러 역할을 구분했는가?
  • 다른 분석모델의 데이터 사용과 일치하는가?
12

11. 자주 틀리는 함정

  1. 값이 숫자로 보인다는 이유만으로 숫자형으로 식별하지 않는다.
  2. 날짜와 시각, 지역 시각과 절대 시점을 섞지 않는다.
  3. 승인 상태를 불리언 하나로 축약해 미검토·반려·만료를 잃지 않는다.
  4. 화면 하나를 엔터티 하나로 그대로 만들지 않는다.
  5. 이름처럼 변경·중복 가능한 속성을 식별자로 쉽게 선택하지 않는다.
  6. 현재 데이터 한 건만 보고 1:1 관계라고 판단하지 않는다.
  7. 다대다 관계에 속성이 있는데 단순 연결로 남기지 않는다.
  8. 주문 당시 가격과 현재 상품가격을 같은 사실로 보지 않는다.
  9. 같은 용어가 부서별로 다른 의미인지 확인하지 않고 합치지 않는다.
  10. 물리 자료형과 인덱스 선택을 논리 의미보다 먼저 확정하지 않는다.

12. 확인 문제

문제 1

숫자로만 이루어진 상품코드를 문자 논리 유형으로 볼 수 있는 이유는 무엇인가?

정답과 해설: 산술 연산 대상이 아니고 앞자리 0과 형식이 업무 의미이기 때문이다. 값의 겉모양보다 사용 연산과 의미로 유형을 선택한다.

문제 2

결제 발생 시간을 단순 지역 시각과 구분해야 하는 이유는 무엇인가?

정답과 해설: 여러 시간대에서 같은 순간을 정렬·감사하려면 시간대가 포함된 절대 시점 기준이 필요하기 때문이다.

문제 3

엔터티 후보의 조건 네 가지를 쓰시오.

정답과 해설: 업무 정의, 여러 인스턴스, 식별 기준, 관리할 속성·생명주기를 들 수 있다. 다른 엔터티와의 관계도 보통 존재한다.

문제 4

다대다 관계를 연관 엔터티로 만드는 대표 판단 기준은 무엇인가?

정답과 해설: 관계 자체에 수량·역할·기간 같은 속성이 있거나 독립 생명주기가 있는 경우다. 주문과 상품 사이의 주문항목이 예다.

문제 5

관계의 선택성을 현재 데이터의 널 비율로만 판단하면 안 되는 이유는 무엇인가?

정답과 해설: 현재 표본에 없는 유효 업무 사례가 있을 수 있다. 관계가 필수인지 선택인지는 업무 규칙과 전체 생명주기로 판단한다.

문제 6

현재 나이를 저장하기보다 생년월일을 원천으로 두는 이유는 무엇인가?

정답과 해설: 나이는 시간에 따라 바뀌는 파생값이어서 저장하면 갱신 누락으로 틀릴 수 있다. 계산 기준일과 규칙으로 필요할 때 계산할 수 있다.

문제 7

같은 두 엔터티 사이 작성자와 승인자 관계를 구분해야 하는 이유는 무엇인가?

정답과 해설: 연결 대상이 같아도 업무 역할, 필수성, 권한과 시점이 다르기 때문이다. 관계명을 역할별로 명확히 한다.

문제 8

데이터 사전에 논리 유형 외에 기록할 내용 네 가지를 쓰시오.

정답과 해설: 정의, 단위·범위, 생성·변경 주체, 시점 의미를 들 수 있다. 예시 값, 형식, 출처도 유용하다.

문제 9

한 칼럼에 여러 전화번호를 쉼표로 저장할 때 논리 모델 문제가 무엇인가?

정답과 해설: 번호별 유형·용도·유효기간과 관계를 표현하기 어렵고 개별 검색·변경이 복잡하다. 반복 값이 독립 속성을 가지면 별도 논리 단위로 식별한다.

14

13. 핵심 요약

  • 논리 설계에서 데이터 유형 확인·식별은 값의 외형보다 의미, 연산, 단위, 정밀도, 시간과 시점 기준을 확인하는 활동이다.
  • 문자, 정수, 정확 소수, 근사 수치, 날짜·시각, 불리언·상태, 이진, 파생·이력 의미를 구분한다.
  • 엔터티는 독립적으로 식별·관리하는 대상이나 사건, 속성은 그 성질, 식별자는 인스턴스를 구별하는 기준이다.
  • 데이터 논리 단위와 관계 확인은 관계 의미, 카디널리티, 선택성, 역할, 관계 속성과 생명주기를 검토한다.
  • 다대다 관계에 자체 속성이나 생명주기가 있으면 연관 엔터티를 고려한다.
  • 용어집·데이터 사전·엔터티 정의서·논리 관계도를 요구와 다른 분석모델에 대조해 확인한다.
