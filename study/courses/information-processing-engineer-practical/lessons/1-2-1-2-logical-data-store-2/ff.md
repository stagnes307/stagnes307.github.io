# 1-2-1-2. 데이터 제약조건과 관계 식별

## 수행 범위와 목표

이 레슨의 정확한 토픽은 **데이터 제약조건과 관계 식별**과 **논리 데이터저장소 확인하기의 적용 절차와 판단 기준**이다. 논리 데이터 모델에서 허용할 값과 금지할 상태, 식별과 참조, 업무 규칙을 명확히 하고 요구·모델·데이터 사전의 일관성을 확인해 승인 가능한 논리 저장소 기준선을 만드는 실무를 다룬다.

앞 레슨에서 데이터 유형과 논리 단위·관계 후보를 도출했다면, 여기서는 그 관계가 지켜야 할 규칙을 식별하고 전체 논리 모델을 확인한다. DBMS별 자료형, 인덱스, 파티션, 실제 파일·공간 배치는 다음 물리 설계 범위다.

학습 목표는 다음과 같다.

1. 도메인, 개체, 참조, 업무·상태 제약을 구분한다.
2. 관계의 카디널리티·선택성·삭제 시 의미를 업무 규칙으로 확인한다.
3. 제약 카탈로그와 관계 검토표를 작성한다.
4. 요구 추적, 시나리오 검증, 정규성 점검, 관계자 승인으로 논리 저장소를 확인한다.

## 1. 데이터 제약조건의 의미

데이터 제약조건은 어떤 데이터 상태가 업무상 유효한지를 정의하는 규칙이다. 자료형만 정해 놓으면 “정수이지만 음수인 주문수량”, “존재하지 않는 고객을 가리키는 주문”, “배송완료인데 배송일이 없는 상태”가 들어올 수 있다. 논리 단계에서 규칙을 명확히 해야 물리 제약, 응용 검증, 시험 기준으로 일관되게 옮길 수 있다.

제약은 구현 구문보다 업무 문장으로 먼저 표현한다.

    규칙 BR-ORD-01
    대상: 주문수량
    조건: 주문항목이 생성·변경될 때
    제약: 1 이상의 정수
    예외: 없음
    위반 처리: 저장 거부
    출처: 주문 정책 4.2

같은 규칙을 화면, 서비스, 데이터베이스가 서로 다른 값으로 구현하지 않도록 식별자와 출처를 관리한다.

## 2. 제약조건의 종류

### 2.1 도메인 제약

속성에 허용되는 유형, 길이, 범위, 형식, 단위, 값 목록을 정한다.

- 주문수량은 1 이상이고 업무 최대 수량 이하이다.
- 할인율은 0 이상 100 이하의 백분율이다.
- 통화코드는 승인된 코드 목록에 속한다.
- 이메일은 조직에서 합의한 형식 검사를 통과한다.
- 종료일은 시작일보다 빠르지 않다.

형식 검사는 값이 실제로 존재하거나 소유자에게 속함을 보장하지 않는다. 이메일 정규식 통과와 이메일 소유 확인은 다른 규칙이다. 복잡한 국제 형식을 지나치게 단순한 패턴으로 제한하지 않도록 요구 목적을 확인한다.

### 2.2 개체 무결성

각 엔터티 인스턴스를 유일하게 식별하고 식별 값이 비어 있지 않도록 하는 규칙이다. 후보 식별자 중 대표 식별자를 정하고 나머지 업무상 유일성도 유지할지 확인한다.

대리 식별자를 추가해도 자연 업무키의 중복 방지가 자동으로 생기지 않는다. 예를 들어 내부 회원ID가 유일해도 같은 조직에서 이메일이 업무상 중복 불가라면 별도 유일성 규칙이 필요하다.

### 2.3 참조 무결성

관계에 참여하는 자식이 유효한 부모를 가리키도록 한다. 주문의 고객ID가 고객을 참조한다면 존재하지 않는 고객ID를 허용하지 않는다. 선택 관계라면 참조 값이 없을 수 있지만, 값이 있다면 유효한 대상을 가리켜야 한다.

부모를 삭제하거나 식별자가 바뀔 때의 의미를 정한다.

| 정책 | 업무 의미 | 주의점 |
|---|---|---|
| 삭제 제한 | 관련 자식이 있으면 부모 삭제 금지 | 보존에는 안전하지만 정리 절차 필요 |
| 연쇄 삭제 | 부모와 생명주기를 같이하는 자식 제거 | 주문·감사처럼 보존할 데이터에 위험 |
| 참조 해제 | 선택 관계로 바꾸고 자식 보존 | 왜 관계가 사라졌는지 이력 필요 가능 |
| 논리 삭제 | 삭제 표시 후 조회에서 제외 | 유일성, 참조, 개인정보 삭제 요구 검토 |

이 표는 논리 정책이며 실제 지원 구문은 DBMS별로 다를 수 있다.

### 2.4 카디널리티와 선택성 제약

“주문은 하나 이상의 주문항목을 가져야 한다”, “직원은 최대 하나의 현재 소속 조직을 가진다”처럼 관계의 최소·최대 참여 수를 정한다. 단순 외래 키 하나로 “최소 한 개의 자식”을 항상 보장하기 어려울 수 있으므로 생성 트랜잭션과 업무 검증 책임을 함께 설계한다.

### 2.5 업무·조건부 제약

여러 속성이나 상태를 함께 보는 규칙이다.

- 주문상태가 배송완료이면 배송완료시각이 존재한다.
- 환불금액은 실제 결제금액을 초과할 수 없다.
- 법인고객이면 사업자 식별 정보가 필요하다.
- 승인자는 신청자와 달라야 한다.

한 행 안의 비교인지, 다른 엔터티·여러 행·과거 상태를 함께 보는지에 따라 구현 위치가 달라진다. 논리 모델에서는 규칙과 책임을 먼저 명시한다.

### 2.6 시간·이력 제약

유효시작과 유효종료 기간이 겹치면 안 되거나, 종료된 계약은 다시 활성 상태가 될 수 없는 규칙이 있다. 현재 상태만 저장할지 모든 변경 이력을 저장할지, 업무 유효시간과 시스템 기록시간을 구분할지 결정한다.

“가장 최근 행”을 시간값 하나로 찾으면 동률이나 지연 입력 문제가 생길 수 있다. 정렬 기준과 식별자를 명확히 한다.

### 2.7 파생값 제약

합계, 잔액, 상태처럼 원천 데이터로 계산되는 값을 저장하면 계산식, 반올림, 갱신 시점, 원천 변경 시 동기화 규칙이 필요하다. 불필요한 중복은 피하되 업무 시점의 확정값과 단순 계산 캐시를 구분한다.

## 3. 관계 식별과 제약 연결

관계를 찾는 데서 끝나지 않고 다음 질문으로 제약을 명확히 한다.

1. 양쪽 엔터티의 역할명은 무엇인가?
2. 각 방향에서 최소와 최대 참여 수는 얼마인가?
3. 관계는 생성 시점부터 필수인가, 나중에 연결될 수 있는가?
4. 관계에 수량·역할·기간 같은 속성이 있는가?
5. 부모와 자식의 생성·변경·종료 생명주기는 같은가?
6. 한쪽 삭제 시 다른 쪽 데이터는 보존·삭제·참조 해제 중 무엇인가?
7. 같은 두 엔터티 사이에 서로 다른 역할의 관계가 있는가?
8. 관계의 유효 기간이나 과거 이력이 필요한가?

### 관계 문장 예

    고객은 0개 이상의 주문을 할 수 있다.
    주문은 정확히 한 주문자 유형과 연결된다.
    주문은 생성 완료 시 1개 이상의 주문항목을 가진다.
    주문항목은 정확히 한 상품 참조를 가진다.
    상품이 판매 종료되어도 과거 주문항목은 보존된다.

이 문장들은 관계 구조와 삭제·보존 정책의 근거가 된다.

## 4. 논리 제약 표현 예시

아래 SQL 유사 표기는 논리 규칙을 이해하기 위한 예이며 특정 제품에서 그대로 실행할 목적이 아니다.

    ENTITY OrderItem
      order_id       : Identifier, required
      line_no        : PositiveInteger, required
      product_id     : Identifier, required
      quantity       : Integer, required, quantity >= 1
      agreed_price   : ExactDecimal, required, agreed_price >= 0

      IDENTIFIER (order_id, line_no)
      RELATION order_id   REFERENCES Order
      RELATION product_id REFERENCES Product
      RULE agreed_price is the price fixed at order time

주문 당시 가격은 현재 상품가격이 바뀌어도 유지해야 하는 거래 사실이다. 이를 상품가격의 단순 중복으로 보고 자동 갱신하면 과거 주문 의미가 깨진다.

## 5. 논리 데이터저장소 확인하기의 적용 절차와 판단 기준

### 5.1 1단계: 입력 기준선 확인

최신 승인 요구, 유스케이스·상태 모델, 용어집, 데이터 사전, 엔터티·관계 모델, 인터페이스 명세를 수집한다. 버전과 승인 상태, 모델 범위를 확인한다.

### 5.2 2단계: 요구-데이터 추적

각 기능이 읽고 생성·변경·삭제하는 논리 단위를 찾는다. 반대로 각 엔터티와 속성이 어떤 요구에서 필요한지 확인한다. 출처가 없는 데이터는 불필요 수집이나 숨은 요구일 수 있다.

### 5.3 3단계: 정의와 유형 정합성 확인

동일 용어가 모델마다 같은 정의·단위·시점으로 쓰이는지 본다. 주문금액이 어떤 곳에서는 세금 포함이고 다른 곳에서는 제외라면 이름이 같아도 같은 속성이 아니다.

### 5.4 4단계: 식별자와 관계 확인

후보 식별자의 유일성·최소성·안정성을 검토하고 관계를 양방향 문장으로 읽는다. 실제 사례와 경계 사례로 카디널리티와 선택성을 검증한다.

### 5.5 5단계: 제약 카탈로그 작성

도메인, 개체, 참조, 조건부, 시간, 파생 규칙을 제약 ID와 출처로 기록한다. 데이터베이스, 응용, 배치 중 어느 계층이 검증할지는 물리 설계에서 구체화하되 논리적 책임과 위반 의미는 현재 단계에서 남긴다.

### 5.6 6단계: 중복과 종속 점검

한 사실이 여러 엔터티에 불필요하게 반복되는지, 속성이 올바른 식별자 전체에 종속하는지 확인한다. 정규화를 기계적으로 가장 높은 단계까지 수행하기보다 삽입·갱신·삭제 이상과 무손실 분해를 고려한다. 성능을 이유로 중복할 필요가 있다면 정규화된 기준과 원천·동기화 정책을 별도 후보로 기록한다.

### 5.7 7단계: 시나리오·표본 검증

정상, 최소·최대, 중복, 누락, 삭제, 상태 전이, 동시 처리 시나리오를 모델에 적용한다. 실데이터 표본은 규칙 발견에 유용하지만 개인정보는 승인된 범위에서 최소화·마스킹하고, 표본에 없다는 이유로 유효 사례를 배제하지 않는다.

### 5.8 8단계: 관계자 검토와 이슈 해결

업무 담당자는 의미와 규칙, 개발자는 구현 가능성, 시험 담당자는 검증 가능성, 데이터·보안 담당자는 품질과 보호를 검토한다. 미결 이슈에는 소유자와 기한을 둔다.

### 5.9 9단계: 기준선 승인

필수 요구가 추적되고, 고심각도 모순이 해결되며, 모든 엔터티·속성·관계·제약에 정의와 출처가 있고, 미결 위험이 관리되면 논리 모델을 기준선으로 승인한다. 변경 이력과 이전 버전을 보존한다.

## 6. 판단 기준표

| 검토 대상 | 통과 판단 |
|---|---|
| 완전성 | 요구에서 필요한 데이터와 정상·예외 상태가 표현됨 |
| 정확성 | 업무 규칙·용어·단위·시점과 모델이 일치함 |
| 일관성 | 모델·인터페이스 사이 정의와 관계가 모순되지 않음 |
| 식별성 | 각 엔터티를 안정적으로 구별할 후보 식별자가 있음 |
| 무결성 | 허용값, 참조, 상태·기간 규칙이 명시됨 |
| 추적성 | 데이터 요소가 요구·인터페이스·시험으로 연결됨 |
| 최소성 | 목적 없는 민감정보와 불필요 중복이 없음 |
| 검증성 | 경계·위반 사례로 규칙을 시험할 수 있음 |

## 7. 구체 업무 시나리오

### 상황

공유 회의실 예약 시스템에는 회의실, 사용자, 예약이 있다. 한 회의실에는 같은 시간대에 승인된 예약이 겹치면 안 되고, 예약 종료시각은 시작시각보다 늦어야 한다. 취소된 예약은 감사 목적으로 보존한다.

### 제약 식별

- 회의실코드는 회의실을 유일하게 식별한다.
- 예약은 정확히 한 회의실과 한 신청자를 참조한다.
- 시작시각 < 종료시각이다.
- 승인 상태의 동일 회의실 예약 기간은 서로 겹치지 않는다.
- 취소 상태는 취소시각과 취소주체를 필요로 한다.
- 회의실이 운영 종료되어도 과거 예약은 삭제하지 않는다.

기간 중복 제약은 한 행의 단순 범위 검사보다 복잡하다. 논리 카탈로그에 규칙, 동시 요청 때의 판정 책임, 위반 결과를 적는다. “먼저 조회하고 없으면 저장”만 하면 두 요청이 동시에 통과할 수 있으므로 구현 단계에서 원자적 보장 방법을 설계해야 한다.

### 위반 사례

| 사례 | 예상 판단 |
|---|---|
| 10:00~09:30 예약 | 종료가 시작보다 빠르므로 거부 |
| 같은 회의실 10:00~11:00과 10:30~11:30 승인 | 기간 중복으로 거부 |
| 다른 회의실 같은 시간 예약 | 업무가 허용하면 가능 |
| 취소된 과거 예약과 시간 겹침 | 새 승인 가능, 취소 이력은 보존 |
| 존재하지 않는 회의실 참조 | 참조 위반 |

## 8. 산출물과 완료 체크리스트

주요 산출물:

- 승인 후보 논리 데이터 모델
- 데이터 사전과 용어집
- 식별자·관계 정의서
- 제약조건 카탈로그
- 요구-데이터-인터페이스 추적표
- 시나리오 검증 결과
- 이슈·결정·잔여 위험 목록

완료 체크리스트:

- 제약마다 ID, 정의, 출처, 위반 의미가 있는가?
- 속성 범위·형식·단위·값 목록이 업무와 일치하는가?
- 기본·대체 식별 규칙과 업무 중복 방지가 명확한가?
- 관계의 최소·최대 수와 선택성이 확인되었는가?
- 부모 삭제·변경 시 자식의 업무 의미를 정했는가?
- 조건부·기간·상태 규칙이 누락되지 않았는가?
- 파생값의 원천·계산·반영 시점이 정의되었는가?
- 요구와 모든 데이터 요소가 양방향 추적되는가?
- 정상·경계·위반 시나리오로 모델을 검증했는가?
- 승인 기준선과 미결 위험이 구분되어 있는가?

## 9. 안전한 제약 검토 의사코드

    for entity in logicalModel.entities:
        assert entity.definition exists
        verifyCandidateIdentifiers(entity)

        for attribute in entity.attributes:
            verifyDomain(attribute.type, attribute.range,
                         attribute.unit, attribute.timeMeaning)
            linkToRequirement(attribute)

    for relation in logicalModel.relations:
        verifyRolesAndCardinality(relation)
        verifyLifecycleAndDeleteMeaning(relation)

    for rule in businessRules:
        addConstraintCatalog(rule.id, rule.source,
                             rule.condition, rule.violation)

    validateWith(normalCases, boundaryCases, violationCases)

이 절차는 논리 검토이며 특정 DBMS 제약 구문을 자동 생성하는 지시가 아니다.

## 10. 자주 틀리는 함정

1. 자료형만 맞으면 도메인 제약이 끝난다고 생각하지 않는다.
2. 기본값이 유효성 검사라고 오해하지 않는다.
3. 대리 식별자를 만들면 자연 업무키 중복이 자동 차단된다고 보지 않는다.
4. 외래 참조 값은 자식에서 반드시 유일해야 한다고 생각하지 않는다.
5. 부모 삭제를 편리하다는 이유로 항상 연쇄 처리하지 않는다.
6. 최소 한 개 자식 규칙이 외래 키 하나로 자동 보장된다고 단정하지 않는다.
7. 주문 당시 가격을 현재 가격 변경에 따라 갱신하지 않는다.
8. 논리 삭제를 하면 개인정보 삭제 의무가 자동 충족된다고 보지 않는다.
9. 실데이터에 위반 사례가 없다는 사실만으로 제약을 생략하지 않는다.
10. 논리 모델 확인 전에 DBMS 구문과 인덱스부터 확정하지 않는다.

## 11. 확인 문제

### 문제 1

도메인 제약과 참조 무결성의 차이는 무엇인가?

**정답과 해설:** 도메인 제약은 한 속성의 유형·범위·형식·허용값을 제한하고, 참조 무결성은 관계 값이 유효한 부모 인스턴스를 가리키게 한다.

### 문제 2

대리 ID가 유일해도 이메일 UNIQUE 규칙이 필요할 수 있는 이유는 무엇인가?

**정답과 해설:** 대리 ID는 행만 구별하며 동일한 업무 사용자가 중복 등록되는 것을 막지 못한다. 이메일이 업무상 후보 식별자라면 별도 유일성 규칙을 유지한다.

### 문제 3

부모 삭제 시 연쇄 삭제를 선택하기 전에 확인할 핵심은 무엇인가?

**정답과 해설:** 부모와 자식의 생명주기가 같은지, 자식에 보존·감사·법적 가치가 있는지 확인한다. 과거 주문처럼 독립 보존할 데이터에는 연쇄 삭제가 위험하다.

### 문제 4

“배송완료이면 배송완료시각 필수”는 어떤 종류의 제약인가?

**정답과 해설:** 상태에 따라 다른 속성의 필수성이 결정되는 조건부 업무 제약이다.

### 문제 5

기간 중복 금지 규칙이 단순 행 CHECK보다 어려운 이유는 무엇인가?

**정답과 해설:** 같은 자원을 참조하는 다른 여러 행과 시간을 비교하고 동시 요청의 경쟁도 처리해야 하기 때문이다.

### 문제 6

논리 저장소 확인에서 요구-데이터 역방향 추적이 필요한 이유는 무엇인가?

**정답과 해설:** 출처가 없는 데이터 수집과 불필요한 민감정보, 요구 없이 추가된 구현을 찾기 위해서다.

### 문제 7

파생 합계를 저장할 때 정의할 항목 네 가지를 쓰시오.

**정답과 해설:** 권위 원천, 계산식, 반올림·널 처리, 갱신 시점을 들 수 있다. 실패 복구와 정합성 검사도 필요하다.

### 문제 8

논리 데이터 모델 기준선 승인 조건 네 가지를 쓰시오.

**정답과 해설:** 필수 요구 추적, 고심각도 모순 해결, 엔터티·관계·제약의 정의와 출처, 미결 위험의 소유자·기한 지정을 들 수 있다.

### 문제 9

현재 데이터에 모든 주문이 회원번호를 가진다는 이유만으로 관계를 필수로 확정해도 되는가?

**정답과 해설:** 안 된다. 비회원 주문 같은 유효 미래·예외 사례와 승인된 업무 규칙을 확인해야 한다. 표본은 규칙의 유일한 근거가 아니다.

## 12. 핵심 요약

- **데이터 제약조건과 관계 식별**은 허용 가능한 데이터 상태와 엔터티 연결 규칙을 업무 문장으로 정의하는 활동이다.
- 도메인, 개체, 참조, 카디널리티·선택성, 조건부·시간·파생 제약을 구분한다.
- 관계에는 역할, 최소·최대 수, 생성 시점, 속성, 생명주기와 삭제 의미가 포함된다.
- **논리 데이터저장소 확인하기의 적용 절차와 판단 기준**은 입력 확인, 추적, 정의 정합성, 식별·관계, 제약 카탈로그, 중복 점검, 시나리오 검증, 관계자 검토, 기준선 승인으로 구성한다.
- 완전성, 정확성, 일관성, 식별성, 무결성, 추적성, 최소성, 검증성을 기준으로 판단한다.
- 논리 규칙을 먼저 확정하고 DBMS별 자료형·제약·인덱스 구현은 물리 설계 단계에서 결정한다.
