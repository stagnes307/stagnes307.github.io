# 1-2-2-1. 저장소 특성을 반영한 물리 설계 · 목표 시스템 데이터 특성을 반영한 최적화 설계

## 수행 범위와 목표

이 레슨의 정확한 토픽은 **저장소 특성을 반영한 물리 설계**와 **목표 시스템 데이터 특성을 반영한 최적화 설계**이다. 승인된 논리 모델을 목표 DBMS의 테이블·칼럼·자료형·키·인덱스·파티션 같은 물리 구조로 변환하고, 데이터량·분포·접근 패턴·변경 빈도·보존 특성을 근거로 최적화 후보를 설계하는 실무를 다룬다.

데이터 파일, 로그, 임시 공간, 테이블스페이스 등 실제 물리 공간을 배치·용량화하는 일과 물리 데이터저장소 설계 전체 절차는 다음 레슨의 주범위다. 여기서는 “어떤 물리 구조가 목표 저장소와 업무 데이터에 맞는가”에 집중한다.

학습 목표는 다음과 같다.

1. 논리 엔터티·속성·관계를 목표 DBMS의 물리 요소로 매핑한다.
2. 자료형, 식별키, 제약, 인덱스를 값의 의미와 저장소 특성에 맞게 결정한다.
3. 데이터량·분포·읽기·쓰기·시간 지역성을 프로파일링한다.
4. 인덱스, 파티셔닝, 클러스터링, 압축, 제한적 반정규화 대안을 측정 근거로 비교한다.

## 1. 논리 설계와 물리 설계의 차이

논리 설계는 업무가 관리할 사실과 관계를 제품 독립적으로 표현한다. 물리 설계는 선택한 DBMS, 운영체제, 저장 장치, 배포 구조에서 이를 실제로 저장하고 접근할 방법을 정한다.

| 논리 요소 | 물리 설계 후보 |
|---|---|
| 엔터티 | 테이블, 문서 컬렉션 등 저장 단위 |
| 속성 | 칼럼과 구체 자료형·길이·정밀도 |
| 식별자 | 기본 키 또는 유일 제약 |
| 관계 | 외래 키, 연결 테이블, 참조 필드 |
| 도메인 규칙 | NOT NULL, CHECK, 코드 참조, 응용 검증 |
| 파생값 | 계산식, 생성 칼럼, 요약 구조 |
| 이력 | 이력 테이블, 유효 기간 칼럼, 변경 로그 |

목표가 관계형 DBMS라면 테이블과 제약으로 매핑할 수 있지만 제품별 자료형과 기능 이름은 다를 수 있다. 논리 의미를 보존하면서 공식 문서와 시험으로 세부 구현을 확인한다.

## 2. 저장소 특성을 반영한 물리 설계

### 2.1 저장 단위와 행 구조

DBMS는 데이터를 페이지나 블록 같은 입출력 단위에 저장하고 메모리 버퍼를 통해 접근한다. 행이 지나치게 넓으면 한 페이지에 적은 행만 들어가 더 많은 입출력이 필요할 수 있다. 반대로 항상 함께 읽는 속성을 무리하게 여러 테이블로 나누면 조인 비용이 커질 수 있다.

자주 사용하는 작은 속성과 드물게 읽는 대용량 본문을 분리하는 수직 분할을 검토할 수 있다. 그러나 분리 후 전체 조회 빈도, 트랜잭션 일관성, 관계 관리 비용을 비교한다.

### 2.2 자료형 매핑

구체 자료형은 값의 범위, 정밀도, 연산, 정렬, 저장 크기와 제품 지원을 기준으로 선택한다.

- 식별 코드는 산술 연산이 없고 앞자리 0을 보존하면 문자형을 검토한다.
- 금액은 정확 십진형과 업무 최대값·소수 자릿수를 사용한다.
- 날짜·시각은 날짜만인지, 지역 시각인지, 절대 시점인지에 맞는 형을 고른다.
- 긴 본문·이진 파일은 크기 분포와 접근 빈도를 확인해 인라인 또는 별도 저장을 판단한다.
- 상태값은 허용 코드와 변경 주체를 제약 또는 코드 테이블로 관리한다.

자료형을 필요 이상으로 크게 잡으면 테이블뿐 아니라 인덱스와 로그, 캐시 공간도 늘 수 있다. 반대로 너무 작게 잡으면 범위 초과와 이행이 발생한다. 실제 최대값, 성장, 법·업무 범위를 근거로 여유를 정한다.

### 2.3 문자 집합과 정렬 규칙

표현할 언어와 기호, 비교·정렬·대소문자·악센트 규칙을 확인한다. 정렬 규칙은 단순 표시뿐 아니라 유일성 판단과 인덱스 검색 결과에 영향을 줄 수 있다. 기존 시스템에서 이행할 때 같은 바이트가 같은 문자와 정렬 의미를 갖는지 표본으로 검증한다.

### 2.4 키와 제약 구현

논리 후보키 중 안정적이고 짧은 대표 키를 선택하고 다른 업무 유일성도 제약으로 유지한다. 외래 키는 참조 무결성을 강화하지만 대량 적재와 삭제 순서, 잠금에 미치는 영향을 계획한다. 복잡한 여러 행 규칙은 데이터베이스 제약, 트랜잭션 로직, 검증 배치 중 어디서 보장할지 책임을 정한다.

제약을 성능 때문에 무조건 생략하면 잘못된 데이터가 여러 입력 경로에서 들어올 수 있다. 비용을 측정하고 필요한 적재 절차를 설계한다.

### 2.5 트랜잭션과 동시성 특성

저장소가 제공하는 트랜잭션, 격리, 잠금 또는 다중 버전 특성을 확인한다. 동일 재고를 여러 사용자가 변경하는 경우 읽고 나서 쓰는 단순 흐름은 갱신 손실을 만들 수 있다. 원자적 조건 갱신, 버전 비교, 적절한 잠금 등 제품이 제공하는 방법을 업무 충돌 정책과 연결한다.

격리 수준은 높을수록 항상 좋은 것이 아니다. 일관성 요구와 동시 처리량, 재시도 가능성을 비교하고 실제 경쟁 시나리오로 시험한다.

### 2.6 제품 기능과 운영 지원

파티셔닝, 압축, 생성 칼럼, 부분 인덱스, 전문 검색, 공간 데이터 같은 기능의 지원 범위와 라이선스·운영 도구를 확인한다. 기능이 존재해도 백업, 복제, 이행, 감시 도구가 같은 방식으로 지원하는지 확인해야 한다.

## 3. 물리 테이블 정의 예시

다음은 표준 개념을 보여 주는 안전한 SQL 예시다. 구체 구문은 사용하는 DBMS 공식 문서에 맞게 조정한다.

    CREATE TABLE order_item (
        order_id       BIGINT         NOT NULL,
        line_no        INTEGER        NOT NULL,
        product_id     BIGINT         NOT NULL,
        quantity       INTEGER        NOT NULL,
        agreed_price   DECIMAL(15, 2) NOT NULL,
        created_at     TIMESTAMP      NOT NULL,
        PRIMARY KEY (order_id, line_no),
        CHECK (quantity >= 1),
        CHECK (agreed_price >= 0)
    );

이 예시의 숫자 범위와 정밀도는 실제 업무 최대값을 확인해 바꿔야 한다. 주문 당시 가격은 현재 상품 가격과 별도 사실이므로 상품 가격 변경 때 갱신하지 않는다. 외래 키 구문은 부모 테이블의 생명주기와 적재 순서를 확인한 뒤 추가한다.

## 4. 목표 시스템 데이터 특성 조사

최적화는 데이터 특성을 모르면 추측이 된다. 다음을 프로파일링한다.

### 4.1 규모와 성장

현재 행 수, 일·월 증가량, 평균·최대 행 크기, 보존 기간, 삭제·아카이브 정책을 확인한다. 평균 증가만 아니라 캠페인, 월말, 법정 신고 같은 최대 증가 구간을 본다.

### 4.2 값 분포와 선택도

칼럼별 고유값 수, 상위 빈도값, 널 비율, 값 범위, 시간별 편향을 확인한다. 성별처럼 종류가 매우 적은 칼럼에 단독 인덱스를 만들면 많은 행을 읽어 이점이 적을 수 있다. 반대로 주문번호처럼 선택도가 높은 조건은 인덱스에 적합할 수 있다.

### 4.3 읽기·쓰기 패턴

주요 질의의 조건, 조인, 정렬, 집계, 반환 행 수와 실행 빈도를 수집한다. 쓰기에서는 삽입, 수정, 삭제 빈도와 동시성을 본다. 인덱스는 읽기를 빠르게 할 수 있지만 쓰기마다 함께 갱신되므로 자주 변경되는 테이블에 과도하면 비용이 크다.

### 4.4 시간·지역성

최근 데이터만 자주 읽는지, 특정 고객·지역의 데이터가 함께 접근되는지, 과거 데이터는 보고서에만 쓰이는지 확인한다. 이 특성은 파티션 키, 클러스터링, 핫·콜드 분리 후보의 근거가 된다.

### 4.5 품질과 이행

중복, 잘못된 형식, 고아 참조, 극단값을 확인한다. 물리 제약을 추가하기 전에 기존 데이터가 통과하는지 정제 계획을 세운다. 표본만 검사해 드문 예외를 놓치지 않는다.

## 5. 목표 시스템 데이터 특성을 반영한 최적화 설계

### 5.1 인덱스

인덱스는 검색 조건, 조인, 정렬을 위한 물리 접근 구조다. 기본 키와 인덱스는 관련될 수 있지만 같은 개념은 아니다.

후보 선정 기준:

- 자주 실행되고 비용이 큰 질의인가?
- 조건·조인에 사용하는 칼럼의 선택도와 순서는 어떠한가?
- 반환 행이 전체의 큰 비율이면 순차 접근이 더 나을 수 있는가?
- 인덱스가 정렬이나 필요한 칼럼 제공까지 도울 수 있는가?
- 쓰기·저장·유지보수 비용보다 읽기 이익이 큰가?

복합 인덱스는 칼럼 순서에 따라 활용 가능한 조건이 달라질 수 있다. 제품의 실행 계획과 실제 데이터로 확인하며 “WHERE에 나온 순서”만 따라 정하지 않는다.

### 5.2 파티셔닝

큰 논리 테이블을 날짜, 지역, 해시 등 기준으로 물리 구역에 나눈다. 질의 조건이 파티션 키를 사용하면 불필요한 구역을 제외할 수 있고, 기간별 보관·삭제를 단순화할 수 있다.

- 범위 파티션: 날짜·금액 범위처럼 연속 구간에 적합하다.
- 목록 파티션: 지역·업무 구분처럼 명시 목록에 적합하다.
- 해시 파티션: 균등 분산이 중요하고 범위 조회가 핵심이 아닐 때 검토한다.
- 복합 파티션: 두 특성을 계층적으로 결합한다.

파티션 수를 지나치게 늘리면 메타데이터와 계획·운영 복잡도가 증가한다. 파티션 키가 질의 조건에 없으면 모든 구역을 읽을 수 있다.

### 5.3 클러스터링과 물리 정렬

같이 읽는 행을 물리적으로 가깝게 배치하면 범위 접근 입출력을 줄일 수 있다. 그러나 삽입과 갱신으로 정렬도가 낮아질 수 있고 한 테이블에 여러 접근 순서를 동시에 만족시키기 어렵다. 제품별 유지 방식과 재구성 비용을 확인한다.

여기서 클러스터링은 데이터 배치 특성이며 고가용성을 위한 서버 클러스터와 구분한다.

### 5.4 압축

중복 패턴이 많은 데이터를 압축하면 저장과 입출력을 줄일 수 있지만 CPU 비용, 수정 비용, 백업·복구, 기능 제한을 확인한다. 읽기 위주의 오래된 데이터와 빈번하게 수정되는 데이터의 효과가 다를 수 있다.

### 5.5 요약·파생 구조와 반정규화

반복 집계가 실제 병목이면 요약 테이블이나 파생 칼럼을 고려할 수 있다. 반복 조인이 주된 비용이면 제한적 중복을 검토한다. 반드시 원천, 갱신 시점, 허용 지연, 실패 재처리, 정합성 검사와 제거 방법을 정한다.

조인이 있다는 이유만으로 반정규화하지 않는다. 질의 수정, 적절한 인덱스, 통계, 캐시 등 중복 없는 대안을 먼저 비교한다.

## 6. 최적화 설계 절차

1. **성능·용량 목표 정의**: 대상 업무, 부하, 응답 시간, 처리량, 저장 목표를 수치화한다.
2. **기준선 측정**: 운영과 유사한 데이터·부하에서 실행 계획, 입출력, CPU, 대기, 잠금을 수집한다.
3. **병목 식별**: 느린 질의, 넓은 행, 잘못된 자료형, 비효율 조인, 데이터 편향 중 원인을 찾는다.
4. **최소 대안 설계**: 인덱스, 질의, 파티션, 압축, 구조 변경 후보를 만든다.
5. **부작용 평가**: 쓰기, 저장, 백업, 복제, 이행, 운영 복잡성을 계산한다.
6. **비교 실험**: 같은 조건에서 전후와 후보를 반복 측정한다.
7. **선택과 문서화**: 목표 달성 여부, 선택 이유, 거절 대안, 적용 조건을 기록한다.
8. **변화 감시 계획**: 데이터 증가와 분포 변화 때 재평가할 지표를 정한다.

## 7. 실행 계획을 이용한 안전한 확인

다음 질의를 자주 사용한다고 하자.

    SELECT order_id, ordered_at, total_amount
      FROM orders
     WHERE customer_id = :customer_id
       AND ordered_at >= :from_time
     ORDER BY ordered_at DESC;

후보 인덱스는 customer_id와 ordered_at을 고려할 수 있다. 그러나 바로 생성하지 말고 다음을 확인한다.

1. 실제 호출 빈도와 반환 행 수
2. 고객별 주문 분포와 기간 선택도
3. 현재 실행 계획과 읽은 페이지 수
4. 기존 인덱스와 중복 여부
5. 주문 삽입·갱신 지연과 저장 증가
6. 같은 조건의 부하 시험 전후 결과

제품마다 인덱스 방향과 포함 칼럼, 실행 계획 표기가 다르므로 개념을 적용한 뒤 공식 문서를 따른다.

## 8. 구체 업무 시나리오

### 상황

센서 이벤트 시스템은 하루 수천만 건까지 증가할 수 있고, 최근 24시간의 장치별 이벤트 조회가 대부분이다. 과거 데이터는 월별 통계와 감사 때만 읽으며 이벤트는 생성 후 거의 수정되지 않는다.

### 설계 판단

- 이벤트시각은 절대 시점으로 저장하고 장치ID와 함께 주요 조회를 지원한다.
- 최근 시간 범위 제거가 쉽도록 날짜 범위 파티션을 후보로 둔다.
- 장치별 최근 조회를 위한 복합 인덱스를 실제 분포로 시험한다.
- 오래된 읽기 전용 파티션에는 압축 효과를 검증한다.
- 이벤트 본문이 크고 드물게 읽히면 기본 목록 속성과 분리하는 방안을 비교한다.
- 월별 통계 반복 계산이 병목이면 원천 이벤트에서 재구축 가능한 요약 구조를 검토한다.

장치가 특정 소수에 집중되면 해시·시간 기준만으로 균등하지 않을 수 있다. 평균 장치당 이벤트 수가 아니라 상위 장치의 편향을 확인한다.

## 9. 산출물과 완료 체크리스트

주요 산출물은 물리 데이터 모델, 테이블·칼럼 정의서, 자료형 매핑표, 키·제약 정의서, 인덱스 후보표, 데이터 프로파일, 성능 기준선, 최적화 비교 결과다.

- 논리 의미가 구체 자료형·길이·정밀도에 보존되었는가?
- 문자 집합·정렬·시간대가 업무 비교 의미와 맞는가?
- 키·제약이 모든 입력 경로에서 무결성을 지키는가?
- 데이터량·성장·분포·읽기·쓰기 패턴을 측정했는가?
- 인덱스마다 대상 질의와 쓰기 비용이 기록되었는가?
- 파티션 키가 주요 질의와 보존 정책에 맞는가?
- 압축·클러스터링의 유지 비용을 시험했는가?
- 반정규화 후보에 원천·동기화·복구 계획이 있는가?
- 운영 유사 데이터와 부하에서 대안을 비교했는가?
- 실제 물리 공간 용량·배치는 다음 단계 입력으로 넘겼는가?

## 10. 자주 틀리는 함정

1. 논리 속성명을 테이블에 옮기기만 하면 물리 설계가 끝난다고 보지 않는다.
2. 자료형은 클수록 안전하다고 생각하지 않는다.
3. 기본 키와 인덱스를 같은 개념으로 보지 않는다.
4. 선택도가 낮은 칼럼의 단독 인덱스가 항상 유리하다고 단정하지 않는다.
5. 인덱스가 많을수록 조회와 쓰기가 모두 빨라진다고 보지 않는다.
6. 파티션을 만들면 모든 질의가 자동으로 빨라진다고 생각하지 않는다.
7. 데이터 클러스터링과 고가용성 서버 클러스터를 혼동하지 않는다.
8. 개발용 소량 데이터의 한 번 실행으로 최적화를 결정하지 않는다.
9. 반정규화의 읽기 이익만 보고 쓰기·정합성 비용을 빼먹지 않는다.
10. 제품의 고급 기능을 라이선스·백업·이행 지원 확인 없이 선택하지 않는다.

## 11. 확인 문제

### 문제 1

논리 자료형을 물리 자료형으로 매핑할 때 확인할 요소 네 가지를 쓰시오.

**정답과 해설:** 값 범위, 정밀도·스케일, 필요한 연산, 저장·인덱스 비용을 들 수 있다. 문자 집합과 시간대도 중요하다.

### 문제 2

인덱스가 읽기를 빠르게 하면서 쓰기를 느리게 할 수 있는 이유는 무엇인가?

**정답과 해설:** 데이터 삽입·수정·삭제 때 관련 인덱스 항목도 함께 갱신하고 로그·저장 공간을 사용하기 때문이다.

### 문제 3

선택도가 낮은 상태 칼럼의 단독 인덱스가 효과가 작을 수 있는 이유는 무엇인가?

**정답과 해설:** 한 값이 전체 행의 큰 비율을 반환하면 인덱스를 거쳐 많은 행을 찾는 것보다 순차 접근이 더 저렴할 수 있다.

### 문제 4

날짜 범위 파티셔닝이 유리한 업무 특성 두 가지는 무엇인가?

**정답과 해설:** 조회가 특정 날짜 범위에 집중되고 기간별 보관·삭제가 필요할 때 유리할 수 있다.

### 문제 5

최적화 전 기준선 측정에 포함할 지표 네 가지를 쓰시오.

**정답과 해설:** 응답 시간, 처리량, 읽은 페이지 또는 입출력, CPU를 들 수 있다. 오류율, 잠금·대기, 저장량도 함께 본다.

### 문제 6

반정규화 요약 테이블에 반드시 필요한 운영 규칙은 무엇인가?

**정답과 해설:** 권위 원천, 계산식, 갱신 시점과 허용 지연, 실패 재처리, 정합성 검사와 재구축 방법이 필요하다.

### 문제 7

물리 클러스터링이 여러 접근 순서를 모두 만족하기 어려운 이유는 무엇인가?

**정답과 해설:** 한 데이터 집합의 물리적 가까움이나 정렬은 보통 한 기준에 맞춰지며 다른 조건은 별도 인덱스나 접근이 필요하기 때문이다.

### 문제 8

센서 이벤트의 평균 분포만으로 파티션을 설계하면 위험한 이유는 무엇인가?

**정답과 해설:** 일부 장치나 시간대에 데이터가 집중되는 편향을 평균이 숨길 수 있다. 상위 빈도와 최대 부하를 조사해야 한다.

### 문제 9

최적화 후보 비교에서 목표 질의 외에 측정할 영향 세 가지를 쓰시오.

**정답과 해설:** 쓰기 지연, 저장·로그 증가, 백업·복구 영향을 들 수 있다. 다른 질의와 운영 복잡성도 확인한다.

## 12. 핵심 요약

- **저장소 특성을 반영한 물리 설계**는 논리 요소를 목표 DBMS의 테이블·칼럼·자료형·키·제약으로 변환하고 저장·트랜잭션 특성을 반영한다.
- 자료형은 범위·정밀도·연산·문자·시간 의미와 저장 비용을 함께 보고 선택한다.
- **목표 시스템 데이터 특성을 반영한 최적화 설계**는 규모·성장·분포·읽기·쓰기·시간 지역성을 측정해 구조를 고른다.
- 인덱스, 파티셔닝, 클러스터링, 압축, 요약·반정규화는 읽기 이익과 쓰기·운영 비용을 비교한다.
- 성능 목표와 기준선을 먼저 정의하고 같은 데이터·부하에서 후보를 반복 측정한다.
- 실제 파일·로그·임시 공간의 배치와 용량은 다음 물리 공간 구성 단계에서 구체화한다.
