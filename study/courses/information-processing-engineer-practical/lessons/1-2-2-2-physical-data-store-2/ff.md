# 1-2-2-2. 실제 데이터가 저장될 물리 공간 구성

## 수행 범위와 목표

이 레슨의 정확한 토픽은 **실제 데이터가 저장될 물리 공간 구성**과 **물리 데이터저장소 설계하기의 적용 절차와 판단 기준**이다. 물리 모델을 실제 운영 환경의 데이터·인덱스·트랜잭션 로그·임시·버전·백업 공간으로 배치하고, 용량·성능·가용성·보안·운영 기준에 맞게 구성·검증하는 실무를 다룬다.

앞 레슨에서 자료형, 키, 인덱스, 파티션 같은 물리 구조와 최적화 후보를 설계했다. 여기서는 그 구조가 차지할 실제 공간과 증가·장애·복구를 관리한다. 데이터 연결·조회 프로시저 작성은 다음 레슨 범위다.

학습 목표는 다음과 같다.

1. 데이터, 인덱스, 로그, 임시, 버전·실행취소, 백업 공간의 용도를 구분한다.
2. 행 수·행 크기·인덱스·성장·보존·여유율을 이용해 용량을 산정한다.
3. 입출력, 장애 영역, 보안, 복구 목표를 고려해 공간을 배치한다.
4. 생성·권한·암호화·자동 증가·감시·복원 시험까지 포함한 설계 절차를 수행한다.

## 1. 물리 공간의 구성 요소

DBMS마다 이름과 구현은 다르지만 다음 역할을 구분하면 설계 판단이 쉬워진다.

| 공간 | 주된 용도 | 주요 위험 |
|---|---|---|
| 데이터 공간 | 테이블 행과 일부 대용량 값 저장 | 증가 예측 실패, 읽기·쓰기 지연 |
| 인덱스 공간 | 검색·조인·정렬 접근 구조 | 과도한 공간과 쓰기 증폭 |
| 트랜잭션 로그 | 변경 순서와 복구 정보 | 가득 차면 쓰기 중단, 지연 시 전체 처리 저하 |
| 임시 공간 | 정렬·해시·중간 결과·임시 객체 | 대형 질의로 급증, 다른 업무와 자원 경쟁 |
| 실행취소·버전 공간 | 롤백·일관된 읽기·행 버전 | 장기 트랜잭션으로 증가 |
| 보관 로그 공간 | 시점 복구 등에 필요한 완료 로그 | 보존 실패 시 복구 구간 손실 |
| 백업 공간 | 전체·증분·로그 백업과 복원 매체 | 원본과 같은 장애 영역, 복원 불가 |

백업 공간은 온라인 데이터 공간과 목적이 다르다. 데이터 디스크의 복제본이 있어도 잘못된 삭제와 논리 손상이 함께 전파될 수 있으므로 복구 가능한 백업을 별도로 관리한다.

## 2. 논리 컨테이너와 물리 파일

많은 관계형 DBMS는 테이블스페이스, 파일그룹 또는 저장 영역 같은 논리 컨테이너를 제공하고 그 아래에 하나 이상의 물리 파일·볼륨을 연결한다. 정확한 명칭과 기능은 제품에 따라 다르다.

    데이터베이스
      ├─ 업무 데이터 영역
      │    ├─ 현재 주문 파티션
      │    └─ 과거 주문 파티션
      ├─ 인덱스 영역
      ├─ 임시 작업 영역
      ├─ 트랜잭션 로그 영역
      └─ 보관 로그·백업 영역(별도 보호)

논리 영역을 나누는 목적은 이름을 많이 만드는 것이 아니라 생명주기, 성능, 백업·복구, 권한, 저장 등급이 다른 데이터를 관리하기 위해서다. 모든 테이블을 각각 다른 영역에 넣으면 운영 복잡도가 커지고, 모든 것을 하나에 넣으면 장애와 증가 영향이 섞일 수 있다.

## 3. 실제 데이터가 저장될 물리 공간 구성 원칙

### 3.1 데이터와 로그의 입출력 특성

데이터 공간은 임의 읽기·쓰기와 범위 읽기가 섞일 수 있고, 트랜잭션 로그는 변경 순서를 지속적으로 기록하는 순차 쓰기 지연이 중요하다. 같은 느린 장치에서 대규모 데이터 읽기와 로그 쓰기가 경쟁하면 트랜잭션 지연이 커질 수 있다.

물리 분리가 항상 별도 디스크 성능을 뜻하지는 않는다. 가상화·공유 스토리지에서 서로 다른 드라이브 문자나 볼륨이 같은 물리 장치와 제어기를 사용할 수 있다. 저장 경로의 실제 장애·성능 영역을 인프라 담당자와 확인한다.

### 3.2 장애 영역

데이터와 백업을 같은 장치, 같은 호스트, 같은 장애 영역에만 두면 장치 손상이나 재해 때 함께 잃는다. 복제, 스냅숏, 백업의 위치와 보호 범위를 구분하고 복구 목표에 맞게 서로 다른 영역에 둔다.

다만 무조건 먼 위치에 복사하면 전송 지연, 일관성, 규정상 데이터 위치 문제가 생길 수 있다. 복구 시점 목표와 복구 시간 목표, 허용 위험, 데이터 위치 규정을 함께 판단한다.

### 3.3 저장 등급

최근 거래처럼 빈번히 접근하는 데이터와 규정상 오래 보관하지만 거의 읽지 않는 데이터를 같은 고성능 등급에 둘 필요는 없을 수 있다. 핫·웜·콜드 분류를 사용해 성능과 비용을 맞춘다. 낮은 등급으로 이동하기 전에 조회 지연, 복원 시간, 지원 기능과 압축 효과를 시험한다.

### 3.4 자동 증가와 사전 할당

자동 증가는 공간 부족으로 즉시 중단되는 위험을 줄이지만 용량 계획을 대체하지 않는다. 아주 작은 증가 단위는 빈번한 확장과 조각화를 만들 수 있고, 지나치게 큰 단위는 장치를 빠르게 소진할 수 있다. 증가 크기·최대치·경보 임계치를 데이터 성장과 확장 시간으로 정한다.

중요 업무는 예상 기간 용량을 사전 할당하고 자동 증가는 예외 완충으로 사용할 수 있다. 제품별 확장 중 잠금과 초기화 비용을 시험한다.

### 3.5 파일시스템과 권한

DB 서비스 전용 계정만 데이터·로그 파일에 접근하게 한다. 일반 사용자와 웹 서비스 계정이 파일을 직접 읽고 수정하지 못하도록 한다. 경로에 소스·로그·백업을 무분별하게 섞지 않고 운영체제 권한, 감사, 악성코드 검사 예외의 위험과 성능을 검토한다.

파일을 운영체제에서 임의 복사한 것이 일관된 데이터베이스 백업이라고 단정하지 않는다. 실행 중인 DB의 캐시와 로그 상태를 고려하는 공식 백업 방식을 사용한다.

### 3.6 암호화와 키

저장장치·파일·데이터베이스 암호화를 적용할 때 위협 모델, 성능, 백업·복구, 키 보관과 교체를 함께 설계한다. 암호화된 백업을 복구하려면 키가 필요하므로 키를 데이터와 같은 위치에만 두지 않는다. 권한 있는 DB 사용자의 조회까지 저장 암호화만으로 차단되지는 않는다.

## 4. 용량 산정

정확한 저장 구조는 DBMS의 페이지·행 오버헤드, 압축, 널 표현, 정렬·버전 정책에 따라 달라진다. 다음 식은 초기 추정의 논리 구조다.

    테이블 원시 용량
      = 예상 행 수 × 평균 물리 행 크기

    테이블 계획 용량
      = 원시 용량
        + 페이지·행 오버헤드
        + 여유 공간
        + 성장분

    전체 온라인 용량
      = 테이블
        + 인덱스
        + 로그·버전 최대 사용
        + 임시 최대 사용
        + 운영 여유

    보호 용량
      = 백업 세대
        + 보관 로그
        + 복원 작업 공간

온라인 용량과 백업·복원 용량을 섞지 않는다. 백업이 압축되더라도 데이터 특성에 따라 비율이 달라지고, 복원 중에는 백업 파일과 복원 대상 공간이 동시에 필요할 수 있다.

### 4.1 행 수 예측

현재 건수, 일평균·최대 증가, 계절성, 보존 기간, 삭제·아카이브를 사용한다.

    1년 예상 건수
      = 현재 건수
        + (평균 일증가 × 일반 일수)
        + 특별 행사 추가량
        - 만료·아카이브 건수

평균만 사용하면 월말이나 이벤트 급증을 놓친다. 기준·낙관·비관 시나리오를 만들고 경보 후 확장에 걸리는 시간을 고려한다.

### 4.2 행 크기

고정 길이 칼럼, 실제 평균·상위 백분위 가변 길이, 행 헤더, 널·버전 정보, 정렬 키를 반영한다. 선언된 최대 길이를 모두 합하면 과대 추정할 수 있고 평균만 쓰면 긴 행을 놓칠 수 있다. 실제 데이터 프로파일과 DBMS 산정 도구를 함께 사용한다.

### 4.3 인덱스

키 크기, 포함 칼럼, 행 수, 포인터·페이지 오버헤드, 채움 비율을 고려한다. 여러 비슷한 인덱스가 중복되지 않는지 확인한다. 파티션마다 로컬 인덱스가 있거나 전역 인덱스가 있으면 유지·복구 특성이 다를 수 있다.

### 4.4 로그·임시·버전 최대치

평균 트랜잭션보다 대량 이행, 인덱스 재구성, 월말 배치, 장기 조회가 로그·임시·버전 공간을 크게 사용할 수 있다. 가장 큰 승인 작업의 동시 실행 시나리오로 산정하고, 로그 보관·백업 실패 때 증가 속도도 고려한다.

## 5. 용량 산정 예시

주문 테이블이 현재 2천만 행이고 하루 평균 10만 행, 행사 최대 30만 행이 추가되며 3년 온라인 보관한다고 하자. 평균 행 크기를 600바이트로 측정했고 행·페이지·여유를 합한 계수를 문제 조건에서 1.3으로 가정한다.

단순 기준 시나리오의 추가 행은 다음과 같다.

    100,000행/일 × 365일 × 3년
      = 109,500,000행

현재를 포함한 기준 행 수는 129,500,000행이다.

    129,500,000 × 600바이트 × 1.3
      ≈ 101,010,000,000바이트

이는 테이블 한 개의 거친 추정이며 약 101GB의 십진 바이트다. 인덱스, 로그, 임시, 다른 테이블, 행사 증가, 백업, 복원 작업 공간은 별도로 더해야 한다. 실제 제품의 단위와 오버헤드를 사용하고 행사 시나리오를 별도 계산한다.

## 6. 물리 데이터저장소 설계하기의 적용 절차와 판단 기준

### 6.1 1단계: 입력과 목표 확인

승인된 물리 모델, 테이블·인덱스 정의, 데이터 프로파일, 보존 정책, 성능 목표, 복구 시점·시간 목표, 보안·감사 요구, 인프라 제약을 수집한다.

### 6.2 2단계: 저장 자원 조사

사용 가능한 장치·볼륨의 용량, 지연, 처리량, 내구성, 장애 영역, 스냅숏·암호화·감시 지원, 확장 소요 시간을 확인한다. 표시된 장치 이름만 보고 물리 분리를 가정하지 않는다.

### 6.3 3단계: 데이터 분류

업무 중요도, 접근 빈도, 변경 빈도, 보존 기간, 민감도, 복구 우선순위로 데이터를 분류한다. 같은 테이블 안에서도 기간 파티션별로 등급이 달라질 수 있다.

### 6.4 4단계: 용량 산정

기준·최대 성장 시나리오에서 테이블, 인덱스, 로그, 임시, 버전, 백업, 복원 공간을 각각 계산한다. 산정식, 단위, 기준일, 가정, 포함·제외 범위를 기록한다.

### 6.5 5단계: 영역과 배치 설계

데이터와 로그의 입출력, 임시 최대 부하, 백업 장애 영역을 고려해 논리 영역과 물리 자원을 매핑한다. 단순 분리보다 실제 장치 경로와 공유 자원을 확인한다.

### 6.6 6단계: 증가·보존·아카이브 설계

초기 크기, 증가 단위, 최대치, 경보 임계치, 확장 책임자와 소요 시간을 정한다. 기간 만료 데이터의 삭제·아카이브·복원 절차와 법적 보존을 연결한다.

### 6.7 7단계: 보안·복구 설계

파일 권한, 저장 암호화, 키 위치, 백업 보존·분리, 복원 우선순위를 정한다. 백업 성공 로그가 아니라 실제 복원 시험으로 복구 가능성을 확인한다.

### 6.8 8단계: 구성과 검증

승인된 자동화 또는 공식 절차로 영역을 생성하고 권한을 적용한다. 예상 데이터와 부하에서 읽기·쓰기·로그·임시 사용량을 측정하고 장치 장애, 공간 임계치, 백업·복원을 시험한다.

### 6.9 9단계: 문서화와 감시

공간-업무 매핑, 경로, 초기·최대 크기, 증가 정책, 경보, 담당자, 복구 순서를 운영 문서에 기록한다. 사용률뿐 아니라 증가 속도와 임계치 도달 예상 시간을 감시한다.

## 7. 안전한 구성 명세 예시

다음은 특정 DBMS에서 실행하는 명령이 아니라 승인용 논리 명세다.

    storage-area: order_current
      purpose: 최근 주문 데이터
      retention: 12개월 온라인
      performance-class: low-latency
      initial-capacity: <산정 결과>
      growth-unit: <확장 시간에 맞춘 값>
      alert-thresholds:
        warning: <운영 합의>
        critical: <운영 합의>
      encryption: required
      backup-policy: <복구 목표에 맞춘 정책>
      owner: database-operations

    storage-area: transaction_log
      purpose: 트랜잭션 복구 로그
      failure-domain: data-area와 독립 여부 확인
      growth-and-archive: <최대 변경량 기준>

비밀 키, 실제 관리자 경로와 계정은 공개 문서에 넣지 않고 권한이 통제된 구성 관리 수단에서 다룬다.

## 8. 구체 업무 시나리오

### 상황

온라인 학습 시스템은 동영상 본문을 객체 저장소에 두고 DB에는 강좌·수강·진도 메타데이터와 객체 식별자를 저장한다. 최근 진도 변경이 많고 월말에는 통계 배치가 임시 공간을 크게 사용한다.

### 구성 판단

- 대용량 동영상과 관계형 메타데이터의 저장·백업 요구를 분리한다.
- 진도 테이블과 인덱스의 성장량을 일별 활성 학습자 기준으로 산정한다.
- 트랜잭션 로그는 진도 이벤트 최대 유입과 대량 이행을 포함해 계산한다.
- 통계 배치의 정렬·집계로 필요한 임시 최대치를 운영과 유사한 데이터에서 측정한다.
- 객체 식별자가 존재하지만 실제 객체가 없거나 접근 권한이 끊긴 고아 상태를 검증하는 운영 절차를 둔다.
- DB 백업과 객체 버전·백업의 복구 시점을 맞출 방법을 설계한다.

DB만 복원해도 객체가 다른 시점이면 메타데이터와 본문이 맞지 않을 수 있다. 여러 저장소의 복구 일관성을 업무 시나리오로 시험한다.

## 9. 판단 기준표

| 관점 | 통과 기준 |
|---|---|
| 용량 | 최대 성장과 확장 소요 시간까지 버틸 여유가 있음 |
| 성능 | 목표 부하에서 데이터·로그·임시 지연이 기준 안에 있음 |
| 가용성 | 단일 장애가 데이터와 모든 복구 사본을 함께 잃게 하지 않음 |
| 복구 | 목표 시점·시간 안에 실제 복원 시험이 성공함 |
| 보안 | 최소 권한, 암호화, 키 분리, 감사가 적용됨 |
| 운영성 | 증가·경보·확장·보존·장애 대응 책임이 명확함 |
| 경제성 | 데이터 등급과 접근 빈도에 맞는 저장 비용임 |
| 추적성 | 물리 영역이 테이블·파티션·업무와 연결됨 |

## 10. 산출물과 완료 체크리스트

주요 산출물은 물리 공간 구성도, 영역·파일 매핑표, 용량 산정서, 성장·보존 계획, 권한·암호화 설계, 백업·복원 계획, 성능·복구 시험 결과, 운영 절차서다.

- 데이터·인덱스·로그·임시·버전·백업 공간을 구분했는가?
- 현재·성장·최대 시나리오와 산정 단위가 명확한가?
- 행·페이지·인덱스 오버헤드를 실제 환경에서 검증했는가?
- 가상 경로의 실제 물리 장애·성능 영역을 확인했는가?
- 초기 크기, 증가 단위, 최대치, 경보와 담당자가 있는가?
- 대량 이행·재구성·월말 작업의 로그·임시 최대치를 포함했는가?
- 파일 접근 권한과 암호화 키 복구를 시험했는가?
- 백업을 원본과 다른 장애 영역에 보존하는가?
- 실제 복원과 여러 저장소 시점 일관성을 검증했는가?
- 사용률과 증가 속도를 감시하고 재산정 시점을 정했는가?

## 11. 자주 틀리는 함정

1. 데이터 크기만 계산하고 인덱스·로그·임시·복원 공간을 빠뜨리지 않는다.
2. 선언된 최대 문자 길이만 모두 더하거나 평균값만 쓰는 단순화를 피한다.
3. 자동 증가를 용량 계획의 대체물로 보지 않는다.
4. 다른 경로 이름을 실제 다른 물리 장치라고 단정하지 않는다.
5. 이중화와 백업을 같은 것으로 보지 않는다.
6. 백업 성공 메시지를 복구 성공의 증거로 보지 않는다.
7. 암호화 키를 데이터·백업과 같은 장애 영역에만 두지 않는다.
8. 임시 공간은 일시적이므로 작아도 된다고 생각하지 않는다.
9. 장기 트랜잭션과 대량 작업의 로그·버전 증가를 무시하지 않는다.
10. 낮은 사용률만 보고 안심하지 말고 증가 속도와 확장 시간을 본다.

## 12. 확인 문제

### 문제 1

데이터 공간과 트랜잭션 로그 공간의 주된 입출력 특성 차이는 무엇인가?

**정답과 해설:** 데이터는 임의·범위 읽기와 쓰기가 섞이고 로그는 변경 순서를 기록하는 지속적 순차 쓰기 지연이 중요하다. 실제 특성은 제품과 부하로 확인한다.

### 문제 2

가상 서버에서 서로 다른 볼륨에 데이터와 로그를 두었어도 물리 분리가 아닐 수 있는 이유는 무엇인가?

**정답과 해설:** 두 볼륨이 같은 실제 장치, 제어기, 네트워크 경로와 장애 영역을 공유할 수 있기 때문이다.

### 문제 3

전체 온라인 용량에 포함할 항목 네 가지를 쓰시오.

**정답과 해설:** 테이블, 인덱스, 트랜잭션 로그·버전 최대 사용량, 임시 공간을 들 수 있다. 운영 여유도 포함한다.

### 문제 4

자동 증가 단위가 지나치게 작거나 클 때의 문제는 무엇인가?

**정답과 해설:** 너무 작으면 빈번한 확장과 조각화·지연이 생길 수 있고, 너무 크면 남은 저장 공간을 급격히 소진할 수 있다.

### 문제 5

백업 용량에 복원 작업 공간까지 고려해야 하는 이유는 무엇인가?

**정답과 해설:** 복원 중 백업 파일과 새 데이터 파일이 동시에 존재하고 검증용 별도 공간이 필요할 수 있기 때문이다.

### 문제 6

저장 암호화를 적용해도 별도 권한 통제가 필요한 이유는 무엇인가?

**정답과 해설:** 저장 암호화는 장치·파일 탈취를 줄이지만 권한 있는 DB 계정의 논리 조회까지 자동 차단하지 않기 때문이다.

### 문제 7

공간 경보에서 현재 사용률 외에 증가 속도가 필요한 이유는 무엇인가?

**정답과 해설:** 같은 사용률이라도 증가 속도에 따라 임계치 도달 시간이 다르며, 확장 작업에 필요한 시간을 확보해야 하기 때문이다.

### 문제 8

물리 데이터저장소 설계 승인 전에 반드시 시험할 복구 항목은 무엇인가?

**정답과 해설:** 실제 백업에서 목표 시점으로 복원하고 목표 시간 안에 서비스 가능한지, 암호화 키와 외부 저장소까지 일관되게 복구되는지 시험한다.

### 문제 9

월말 배치가 임시 공간을 크게 쓰는지 사전에 확인하는 방법은 무엇인가?

**정답과 해설:** 운영과 유사한 데이터량과 동시 부하에서 정렬·해시·집계 작업을 실행해 임시 최대 사용량과 증가 시간을 측정한다.

## 13. 핵심 요약

- **실제 데이터가 저장될 물리 공간 구성**은 데이터, 인덱스, 로그, 임시, 버전·실행취소, 보관 로그, 백업의 용도와 장애 특성을 나누는 활동이다.
- 용량은 행 수·크기뿐 아니라 오버헤드, 성장, 인덱스, 최대 로그·임시·버전, 백업 세대와 복원 공간을 포함한다.
- 다른 논리 경로가 실제 다른 장치인지 확인하고 성능 영역과 장애 영역을 함께 본다.
- **물리 데이터저장소 설계하기의 적용 절차와 판단 기준**은 목표 확인, 자원 조사, 데이터 분류, 용량 산정, 배치, 증가·보존, 보안·복구, 구성·검증, 감시로 구성한다.
- 자동 증가, 이중화, 암호화는 각각 용량 계획, 백업·복원, 권한 통제를 대체하지 않는다.
- 사용률과 증가 속도를 감시하고 실제 부하·공간 장애·복원 시험으로 설계를 검증한다.
