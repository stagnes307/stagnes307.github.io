# 1-2-3-1. 데이터 저장소 연결 프로시저 작성 · 데이터 조회 프로시저 작성

## 수행 범위와 목표

이 레슨의 정확한 토픽은 **데이터 저장소 연결 프로시저 작성**과 **데이터 조회 프로시저 작성**이다. 응용 프로그램이 데이터 저장소에 최소 권한으로 안전하게 연결하고, 입력 검증·매개변수 바인딩·자원 해제·오류 처리를 갖춘 조회 절차를 구현하는 실무를 다룬다.

신규·변경 데이터 저장과 단위 테스트는 다음 레슨 범위다. 여기서는 연결 수명주기와 조회에 집중하며 제품 독립적인 SQL·의사코드를 쓴다.

학습 목표는 다음과 같다.

1. 연결 설정, 인증, 연결 풀, 제한 시간, 자원 해제의 책임을 설명한다.
2. 문자열 결합 대신 매개변수 바인딩을 사용해 조회 프로시저를 작성한다.
3. 조회 목적에 맞게 투영, 조건, 조인, 정렬, 집계, 페이징을 설계한다.
4. 빈 결과, NULL, 시간 초과, 연결 실패를 예측 가능한 결과와 오류로 처리한다.

## 1. 데이터 접근 흐름

응용 프로그램의 데이터 조회는 단순히 SQL 한 줄을 실행하는 일이 아니다.

    [요청 입력]
       ↓ 형식·범위·권한 확인
    [조회 프로시저]
       ↓ 연결 획득
    [데이터 저장소]
       ↓ 매개변수화된 질의 실행
    [결과 집합]
       ↓ 타입·NULL·오류 변환
    [업무 결과]
       ↓
    연결·문장·결과 자원 반환

각 단계의 계약을 정해야 장애와 보안 문제를 줄일 수 있다. 조회 프로시저가 연결 비밀을 하드코딩하거나, 호출자가 임의 SQL을 전달하거나, 결과를 무제한 메모리에 올리면 기능은 동작해도 운영에는 부적합하다.

## 2. 데이터 저장소 연결 프로시저 작성

### 2.1 연결 정보

연결에는 보통 저장소 주소, 포트, 데이터베이스 또는 서비스 이름, 계정·인증 정보, 암호화, 연결·읽기 제한 시간, 문자·시간대 설정이 필요하다. 환경마다 다른 값은 코드에서 분리한다.

비밀번호와 토큰을 소스, 예제 설정, 로그, 오류 메시지에 넣지 않는다. 권한이 통제된 비밀 관리 수단에서 실행 시 주입하고 교체 가능하게 한다. 개발·시험·운영은 별도 계정과 데이터를 사용한다.

### 2.2 드라이버와 프로토콜

검증된 드라이버를 사용하고 런타임·DB·암호화 지원 범위를 확인한다. 연결 옵션과 기본값은 공식 문서를 따른다.

### 2.3 최소 권한

조회 계정에는 필요한 스키마·뷰의 SELECT만 부여하고 삭제·계정 관리 권한을 주지 않는다. 행·열 권한은 응용과 DB의 책임을 정한다.

### 2.4 연결 풀

매 요청마다 물리 연결을 새로 만들면 인증·네트워크 준비 비용이 크다. 연결 풀은 준비된 연결을 빌리고 반환해 재사용한다.

    요청 → 풀에서 연결 대여 → 질의 → 상태 정리 → 풀에 반환
                    │
                    └─ 사용 가능 연결 없음 → 제한 시간 후 실패

풀 상한은 응용 인스턴스 수와 배치·관리 연결을 합해 DB 처리 능력과 비교하고, 획득 제한 시간을 둔다.

### 2.5 연결 유효성

단절 후 풀에 죽은 연결이 남을 수 있다. 유효성·최대 수명·유휴 설정을 적용하고 실패 연결은 폐기한다.

### 2.6 제한 시간과 재시도

연결 획득, 네트워크 연결, 질의 실행에 각각 합리적 제한 시간을 둔다. 제한 시간이 없으면 장애 때 작업자가 장기간 점유될 수 있다.

조회 재시도도 긴 질의를 중복 실행해 부하를 키울 수 있다. 일시 오류와 남은 시간을 판단해 대기·횟수 상한을 두고 무한 재시도하지 않는다.

### 2.7 자원 해제

성공·빈 결과·예외 모든 경로에서 결과, 문장, 연결을 해제한다. 자동 자원 관리를 쓰고 열린 트랜잭션을 풀에 반환하지 않는다.

## 3. 안전한 연결 의사코드

    function withReadConnection(action):
        config = loadRuntimeConfig()
        secret = secretProvider.get(config.credentialReference)

        connection = pool.acquire(timeout=config.acquireTimeout)
        try:
            connection.setReadOnlyHint(true)
            connection.setStatementTimeout(config.queryTimeout)
            return action(connection)
        catch TemporaryConnectionError as error:
            markConnectionBroken(connection)
            raise DataAccessUnavailable(correlationId(), error.category)
        finally:
            pool.releaseOrDiscard(connection)

비밀값, 전체 연결 문자열, 원본 DB 오류를 사용자에게 반환하지 않는다. 내부 로그에도 매개변수의 민감도를 분류하고 필요한 최소 정보만 남긴다. 읽기 전용 힌트는 제품에 따라 강제 제약이 아닐 수 있으므로 계정 권한을 함께 제한한다.

## 4. 데이터 조회 프로시저 작성

조회 프로시저는 업무 입력으로 승인된 질의를 실행해 계약된 결과를 반환하며, 호출자가 임의 SQL 조건을 넘기게 하지 않는다.

### 4.1 입력 계약

입력의 유형, 필수 여부, 범위, 길이, 시간대와 기본값을 정의하고 최대 조회 기간과 객체 권한을 정한다.

형식 검증은 권한 검증을 대체하지 않는다. 유효한 고객ID라도 호출자가 읽을 권한이 있는지 확인한다.

### 4.2 필요한 칼럼만 투영

SELECT * 대신 계약에 필요한 칼럼만 명시해 미래의 민감정보 노출과 전송 비용을 줄이고 결과 매핑을 안정화한다.

### 4.3 매개변수 바인딩

입력값을 SQL에 직접 붙이면 오류와 SQL 주입이 가능하므로 드라이버 매개변수로 바인딩한다.

안전한 형태:

    SELECT order_id, ordered_at, total_amount, status
      FROM orders
     WHERE customer_id = :customer_id
       AND ordered_at >= :from_time
       AND ordered_at <  :to_time
     ORDER BY ordered_at DESC, order_id DESC;

    bind(":customer_id", validatedCustomerId)
    bind(":from_time", normalizedFromTime)
    bind(":to_time", normalizedToTime)

플레이스홀더 문법은 드라이버마다 다르다. 테이블명·정렬 방향은 값처럼 바인딩되지 않을 수 있으므로 허용 목록의 내부 SQL 조각으로 매핑한다.

### 4.4 조건과 NULL

NULL은 0·빈 문자열과 다르며 일반 동등 비교로 찾지 않는다. 선택 조건의 OR가 실행 계획에 미치는 영향도 확인한다.

빈 결과는 오류가 아닐 수 있다. “목록 0건”과 “ID로 단일 대상을 찾았으나 없음”의 업무 의미를 구분해 빈 목록, 찾을 수 없음 오류 등 계약된 결과를 반환한다.

### 4.5 조인

엔터티 관계와 필요한 결과에 맞는 조인 종류를 선택한다.

- 내부 조인은 양쪽에 일치하는 행만 반환한다.
- 왼쪽 외부 조인은 왼쪽 기준 행을 유지하고 상대가 없으면 NULL을 반환한다.
- 다대다 조인은 행 수가 곱처럼 늘 수 있으므로 결과 중복과 집계를 확인한다.

조인 조건을 빠뜨리면 카티션 곱으로 행이 폭증할 수 있다. 외부 조인한 테이블의 필터를 WHERE에 잘못 두면 결과가 사실상 내부 조인처럼 바뀔 수 있으므로 의도를 시험한다.

### 4.6 집계

COUNT, SUM, AVG 같은 집계를 사용할 때 NULL 처리, 중복 조인, 그룹 기준, 통화·반올림을 확인한다. 상세 주문과 여러 결제 행을 동시에 조인해 주문금액을 합하면 주문 행이 결제 수만큼 중복되어 합계가 커질 수 있다. 먼저 올바른 단위로 각각 집계한 뒤 조인하는 방안을 사용한다.

### 4.7 정렬과 페이징

페이지 결과는 정렬이 결정적이어야 한다. ordered_at만 정렬했는데 같은 시각의 행이 여러 개면 페이지 사이 중복·누락이 생길 수 있으므로 order_id 같은 고유한 보조 정렬 키를 둔다.

큰 오프셋은 비용이 커질 수 있어 마지막 정렬 키 이후를 읽는 키셋 페이징을 검토하고 임의 페이지 이동 요구와 비교한다.

### 4.8 결과 크기와 스트리밍

무제한 결과를 메모리에 올리지 말고 최대 기간·건수, 페이징, 스트리밍을 사용한다. 스트리밍의 연결 점유와 실패도 설계한다.

## 5. 조회 프로시저 의사코드

    function findOrders(request, caller):
        customerId = validateIdentifier(request.customerId)
        assert caller.canReadOrdersOf(customerId)

        range = validateAndNormalizeTimeRange(
                    request.from, request.to,
                    maximumAllowedRange)
        limit = clamp(request.limit, 1, maximumPageSize)
        cursor = validateCursor(request.cursor)

        sql = approvedOrderQueryFor(cursor)

        return withReadConnection(connection -> {
            statement = connection.prepare(sql)
            statement.bind("customer_id", customerId)
            statement.bind("from_time", range.start)
            statement.bind("to_time", range.end)
            statement.bind("limit", limit + 1)

            rows = statement.execute()
            return mapPage(rows, limit, redactSensitiveFields)
        })

limit보다 한 건 더 읽어 다음 페이지 존재 여부를 판단할 수 있다. 커서는 클라이언트가 임의 SQL을 넣지 못하도록 구조와 무결성을 검증하고, 민감한 내부 식별 정보 노출 여부를 확인한다.

## 6. 조회 절차의 단계별 작성

1. **조회 목적·사용자 정의**: 누가 어떤 업무 결정을 위해 조회하는지 정한다.
2. **입력·권한 계약**: 필수값, 범위, 시간대, 최대 크기와 객체 수준 권한을 정의한다.
3. **출력 계약**: 반환 필드, 정렬, 빈 결과, NULL, 오류, 페이지 형식을 정한다.
4. **논리 질의 작성**: 필요한 엔터티·관계, 조건, 집계 단위를 확인한다.
5. **매개변수화 구현**: 값 바인딩과 허용 목록 기반 동적 식별자를 사용한다.
6. **연결·자원 관리 적용**: 풀, 제한 시간, 자동 해제, 오류 분류를 적용한다.
7. **정확성 시험**: 정상·경계·빈 결과·NULL·중복·권한·시간대 사례를 시험한다.
8. **성능 시험**: 운영 유사 데이터에서 실행 계획, 반환량, 응답·풀 대기를 측정한다.
9. **관찰과 문서화**: 추적 ID, 지연, 오류 범주, 행 수를 민감정보 없이 기록한다.

## 7. 구체 업무 시나리오

### 상황

고객 상담원이 고객의 최근 90일 배송 이력을 조회한다. 주문이 아직 배송되지 않았어도 주문 행은 보여야 하고, 배송이 여러 번 나뉘면 각 배송의 최근 상태를 표시한다.

### 판단

1. 상담원이 해당 고객을 조회할 권한이 있는지 먼저 확인한다.
2. 주문을 기준으로 유지해야 하므로 배송 관계는 왼쪽 외부 조인을 검토한다.
3. 한 주문에 여러 배송이 있으면 단순 조인 결과가 주문 수보다 늘어난다. “주문별 최근 배송”의 기준 시각과 동률 처리 키를 정한 뒤 부분 질의에서 한 행을 선택한다.
4. 최근 90일은 상담 시스템의 업무 시간대 기준인지 절대 시점 기준인지 정한다.
5. 결과는 주문시각과 주문ID의 결정적 내림차순으로 페이지 처리한다.
6. 주소 전체가 필요 없다면 반환하지 않고 배송 상태와 마스킹된 수령 정보만 제공한다.

### SQL 구조 예

    WITH latest_delivery AS (
        SELECT delivery_id, order_id, delivery_status, changed_at,
               ROW_NUMBER() OVER (
                   PARTITION BY order_id
                   ORDER BY changed_at DESC, delivery_id DESC
               ) AS rn
          FROM delivery
    )
    SELECT o.order_id, o.ordered_at, o.status,
           d.delivery_status, d.changed_at
      FROM orders o
      LEFT JOIN latest_delivery d
        ON d.order_id = o.order_id
       AND d.rn = 1
     WHERE o.customer_id = :customer_id
       AND o.ordered_at >= :from_time
     ORDER BY o.ordered_at DESC, o.order_id DESC;

윈도 함수 지원과 최적 실행 방식은 DBMS에 따라 확인한다. 중요한 것은 최신을 판단하는 정렬이 결정적이고, 주문이 배송 없이도 보존되며, 입력값을 바인딩한다는 점이다.

## 8. 오류 처리와 관찰

오류를 모두 “DB 오류” 하나로 처리하지 않는다.

| 오류 범주 | 호출자 처리 | 내부 기록 |
|---|---|---|
| 입력 오류 | 어떤 필드가 유효하지 않은지 안전하게 반환 | 검증 규칙 ID |
| 권한 오류 | 정보 존재 여부를 과도하게 노출하지 않음 | 호출자·정책·추적 ID |
| 결과 없음 | 계약에 따라 빈 목록 또는 찾을 수 없음 | 필요 시 조회 조건 요약 |
| 일시 연결 오류 | 제한된 재시도 또는 서비스 불가 | DB 대상 식별자, 오류 범주 |
| 제한 시간 | 사용자에게 재시도 가능 여부 안내 | 질의 ID, 시간, 풀·DB 지표 |
| 프로그래밍 오류 | 일반 내부 오류 | 원본 예외는 보호된 로그에 기록 |

SQL 전체와 바인딩 값을 무조건 로그로 남기지 않는다. 질의 템플릿 ID, 처리 시간, 결과 행 수, 추적 ID를 기록하고 개인정보·토큰은 제거한다.

## 9. 산출물과 완료 체크리스트

주요 산출물은 연결 설정 명세, 계정·권한표, 연결 풀·제한 시간 기준, 조회 프로시저 명세, 매개변수·결과 계약, SQL, 단위·통합 시험 결과, 실행 계획·성능 결과다.

- 비밀값이 코드·저장소·로그에 없는가?
- 개발·시험·운영 계정과 데이터가 분리되었는가?
- 조회 계정이 최소 권한을 가지는가?
- 풀 총 연결 수가 DB 용량과 맞는가?
- 모든 경로에서 결과·문장·연결이 해제되는가?
- 값 입력이 매개변수로 바인딩되는가?
- 동적 정렬·식별자는 허용 목록으로 제한되는가?
- SELECT * 없이 필요한 칼럼만 반환하는가?
- NULL·빈 결과·시간대·결정적 정렬을 정의했는가?
- 최대 조회 범위와 결과 크기가 제한되는가?
- 조인 중복과 집계 단위를 시험했는가?
- 운영 유사 데이터에서 정확성과 성능을 검증했는가?

## 10. 자주 틀리는 함정

1. 비밀번호를 환경 변수 이름이 아닌 실제 값으로 예제·로그에 남기지 않는다.
2. 읽기 전용 설정 하나가 최소 권한을 대체한다고 생각하지 않는다.
3. 연결 풀 크기는 클수록 좋다고 보지 않는다.
4. 예외 경로에서 연결 반환을 빠뜨리지 않는다.
5. 사용자 입력을 SQL 문자열에 직접 연결하지 않는다.
6. 테이블명·정렬 방향도 일반 값처럼 바인딩된다고 단정하지 않는다.
7. SELECT *로 미래의 민감 칼럼까지 노출하지 않는다.
8. 외부 조인 후 WHERE 조건으로 상대 없는 행을 제거하는 실수를 주의한다.
9. ordered_at 하나만으로 페이지 정렬이 항상 결정적이라고 보지 않는다.
10. 빈 결과와 저장소 장애를 같은 오류로 처리하지 않는다.
11. 조회이므로 무제한 재시도·무제한 결과가 안전하다고 생각하지 않는다.
12. 평균 데이터만으로 조인과 페이징 성능을 판단하지 않는다.

## 11. 확인 문제

### 문제 1

연결 정보를 코드에서 분리해야 하는 이유 두 가지는 무엇인가?

**정답과 해설:** 환경별 주소·계정을 코드 변경 없이 적용하고 비밀값 노출을 줄이기 위해서다. 비밀은 외부화만 하지 말고 접근·교체 권한도 통제한다.

### 문제 2

연결 풀 상한을 정할 때 고려할 항목 세 가지를 쓰시오.

**정답과 해설:** 응용 인스턴스 수, DB의 동시 처리 능력, 배치·관리용 예약 연결을 고려한다. 질의 평균 시간과 풀 대기도 본다.

### 문제 3

매개변수 바인딩이 SQL 문자열 결합보다 안전한 이유는 무엇인가?

**정답과 해설:** 입력값을 SQL 구조가 아닌 값으로 전달해 따옴표 처리 오류와 SQL 주입을 줄이고 자료형 변환을 드라이버가 일관되게 처리하기 때문이다.

### 문제 4

동적 정렬 방향을 일반 매개변수로 처리하기 어려울 때의 안전한 방법은 무엇인가?

**정답과 해설:** 외부 값이 미리 정한 허용 목록에 있는지 확인하고 각 값에 대응하는 내부 SQL 조각을 선택한다. 임의 문자열을 그대로 붙이지 않는다.

### 문제 5

왼쪽 외부 조인을 사용했는데 상대 테이블 조건을 WHERE에 두면 생길 수 있는 문제는 무엇인가?

**정답과 해설:** 상대가 없어 NULL인 기준 행이 조건에서 제거되어 의도와 달리 내부 조인처럼 동작할 수 있다. 조건 위치와 NULL 의미를 확인한다.

### 문제 6

페이지 정렬에 고유한 보조 키가 필요한 이유는 무엇인가?

**정답과 해설:** 주 정렬값이 같은 행의 순서가 매 실행마다 달라져 페이지 중복·누락이 생기는 것을 막기 위해서다.

### 문제 7

빈 목록과 연결 실패를 구분해야 하는 이유는 무엇인가?

**정답과 해설:** 빈 목록은 정상적인 업무 결과일 수 있지만 연결 실패는 결과의 부재를 확인하지 못한 장애다. 호출자의 표시·재시도 동작이 달라야 한다.

### 문제 8

조인 후 SUM 값이 실제보다 커졌다면 먼저 의심할 원인은 무엇인가?

**정답과 해설:** 일대다 관계를 여러 개 동시에 조인해 기준 행이 중복되었는지 확인한다. 올바른 업무 단위로 먼저 집계한 뒤 조인한다.

### 문제 9

조회 프로시저 로그에 SQL과 바인딩 값을 모두 남기면 위험한 이유는 무엇인가?

**정답과 해설:** 개인정보·토큰이 로그와 백업에 확산되고 로그 열람자가 민감정보에 접근할 수 있다. 질의 ID, 지연, 행 수, 오류 범주를 중심으로 기록한다.

## 12. 핵심 요약

- **데이터 저장소 연결 프로시저 작성**은 외부화된 설정, 안전한 인증, 최소 권한, 연결 풀, 제한 시간, 자원 해제와 오류 처리를 구현하는 일이다.
- 비밀값은 소스·로그에서 제외하고 개발·시험·운영 계정과 데이터를 분리한다.
- **데이터 조회 프로시저 작성**은 입력·권한·출력 계약을 정의하고 매개변수화된 SQL로 필요한 데이터만 조회하는 일이다.
- SELECT *, 문자열 결합, 무제한 결과·재시도를 피하고 NULL·빈 결과·시간대·결정적 정렬을 명시한다.
- 조인과 집계는 업무 단위와 행 증가를 확인하고 페이징은 고유 보조 정렬 키를 사용한다.
- 정확성, 보안, 연결 반환, 운영 유사 데이터 성능을 시험하고 민감정보 없는 관찰 지표를 남긴다.
