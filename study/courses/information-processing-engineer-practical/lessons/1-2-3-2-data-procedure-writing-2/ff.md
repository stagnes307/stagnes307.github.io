# 1-2-3-2. 변경·신규 데이터를 저장하는 프로시저 작성 · 테스트 케이스와 단위 테스트 조건 명세

> **수행 범위 기준**: 이 레슨은 정보처리기사 실기 `데이터 입출력 구현 > 데이터 조작 프로시저 작성하기`의 **변경·신규 데이터를 저장하는 프로시저 작성**, **테스트 케이스와 단위 테스트 조건 명세**를 다룬다. 앞 레슨의 데이터 저장소 연결·조회 프로시저를 전제로 하며, 다음 레슨의 운영환경 기반 성능 예측·측정은 분리한다. 여기서는 쓰기 업무 규칙, 트랜잭션·동시성·오류 계약과 이를 검증할 단위 테스트를 함께 설계한다.

쓰기 프로시저는 SQL 한 문장을 호출하는 얇은 함수로 끝나지 않는다. 입력을 검증하고, 신규와 변경을 구분하며, 업무 불변조건을 지키고, 동시 요청에서 중복·유실을 막고, 성공과 실패의 원자적 경계를 보장해야 한다. 테스트는 정상 한 건만 확인하는 것이 아니라 경계·예외·동시성·롤백 후 데이터 상태를 명세해야 한다.

---

## 1. 예제 업무와 저장 불변조건

가상 주문 품목 저장 기능을 사용한다.

```text
주문(order)
  order_id        고유 주문 ID
  customer_id     고객 ID
  status          DRAFT, CONFIRMED, CANCELLED
  total_amount    품목 합계와 같아야 함
  version_no      낙관적 동시성 버전

주문품목(order_item)
  order_id + line_no  복합 키
  product_id
  quantity            1 이상
  unit_price           0 이상
  line_amount          quantity × unit_price
```

저장 전 합의할 **불변조건(invariant)**은 다음과 같다.

- 주문 ID와 품목 키는 유일하다.
- 고객과 상품은 존재하고 사용할 수 있어야 한다.
- 수량은 1 이상, 단가는 0 이상이며 금액 정밀도 규칙을 따른다.
- `total_amount`는 모든 품목 금액 합계와 일치한다.
- `CONFIRMED` 이후에는 허용된 상태 전이 없이 품목을 임의 변경하지 않는다.
- 같은 요청 ID를 재전송해도 같은 업무 효과를 한 번만 만든다.
- 주문 헤더와 품목은 전부 저장되거나 전부 저장되지 않아야 한다.
- 변경 시 다른 사용자의 갱신을 조용히 덮어쓰지 않는다.

DB 제약조건, 프로시저 검증, 서비스 계층 중 어디에서 지킬지 책임을 정한다. 중요한 무결성은 호출 경로가 달라도 깨지지 않도록 데이터베이스 제약으로도 보호하고, 사용자 친화적 오류는 프로시저에서 미리 검사할 수 있다.

## 2. 프로시저 계약 설계

### 2.1 입력 계약

| 입력 | 형식·범위 | 의미 |
|---|---|---|
| `request_id` | 비어 있지 않은 고유 문자열 | 재시도 중복 방지 키 |
| `order_id` | 신규면 생성 규칙, 변경이면 기존 ID | 대상 주문 |
| `customer_id` | 존재하는 활성 고객 | 주문 소유 고객 |
| `expected_version` | 변경 시 현재 버전 예상값 | 동시 수정 검출 |
| `items` | 1개 이상 품목 목록 | 전체 교체인지 증분 변경인지 계약 필요 |
| `actor_id` | 인증된 수행 주체 ID | 권한·감사 |

빈 값, 생략, `null`, 0은 서로 다른 의미가 될 수 있다. 예를 들어 단가 0은 무료 상품으로 허용할 수 있지만 `null`은 가격 미결정으로 거절할 수 있다.

### 2.2 출력·오류 계약

```text
성공:
  order_id, new_version, stored_total, result_status

업무 오류:
  INVALID_INPUT       입력 형식·범위 오류
  CUSTOMER_NOT_FOUND  고객 없음
  ORDER_NOT_FOUND     변경 대상 없음
  INVALID_STATE       현재 상태에서 변경 불가
  VERSION_CONFLICT    예상 버전과 현재 버전 불일치
  DUPLICATE_REQUEST   같은 요청이 다른 내용으로 재사용됨

시스템 오류:
  TRANSIENT_FAILURE   재시도 가능성이 있는 일시 장애
  INTERNAL_FAILURE    상세 내부정보를 숨긴 비재시도/조사 오류
```

DB 제품의 원시 오류 문구와 테이블 이름을 외부로 그대로 노출하지 않는다. 업무 오류와 일시 시스템 오류를 구분해야 호출자가 재입력·새로고침·제한 재시도 중 올바른 행동을 선택한다.

### 2.3 신규·변경 의미

- `createOrder`: 존재하지 않아야 하며 새 ID 또는 지정 ID를 만든다.
- `updateOrder`: 존재해야 하며 예상 버전과 상태 조건을 만족해야 한다.
- `saveOrder`: 신규/변경을 자동 판정할 수 있으나 존재 확인 시점 경쟁과 호출 의도가 모호해질 수 있다.
- `upsert`: 키가 있으면 변경, 없으면 삽입한다. 기준 키와 동시 실행 의미를 DB 원자 연산으로 명확히 한다.

업무에서 “신규인데 같은 키면 오류”와 “있으면 갱신”은 다른 계약이다. 편의 때문에 무조건 upsert를 사용하지 않는다.

## 3. 변경·신규 데이터를 저장하는 프로시저 작성 절차

### 단계 1: 트랜잭션 경계 결정

한 업무 단위에서 반드시 함께 성공해야 할 데이터 변경을 식별한다.

```text
주문 헤더 삽입/변경
  + 품목 저장
  + 주문 합계 갱신
  + 상태·변경 이력
  + 중복 요청 처리 기록
= 하나의 로컬 트랜잭션 후보
```

외부 결제 API 호출을 DB 트랜잭션 안에서 오래 기다리면 잠금과 장애 결합이 커진다. 로컬 데이터와 후속 작업을 같은 트랜잭션에 기록하고 커밋 후 안전하게 전달하는 패턴을 검토한다.

### 단계 2: 입력·권한 검증

- 필수값, 길이, 자료형, 범위와 허용 코드 확인
- 품목 수와 전체 요청 크기 제한
- actor가 고객·채널·기능 범위에 접근 가능한지 확인
- 금액은 부동소수점이 아닌 승인된 고정 정밀도로 계산
- 클라이언트가 보낸 합계를 신뢰하지 않고 서버에서 다시 계산

검증과 저장 사이에 참조 대상 상태가 바뀔 수 있으므로 중요한 조건은 저장 SQL 조건과 제약으로 다시 보장한다.

### 단계 3: 중복 요청 확인

네트워크 시간 초과 뒤 호출자는 성공 여부를 모른 채 같은 요청을 재전송할 수 있다.

```text
request_log
  request_id       UNIQUE
  payload_hash
  status           PROCESSING/SUCCEEDED/FAILED_FINAL
  result_reference
```

- 같은 `request_id`와 같은 내용이 이미 성공했다면 기존 결과를 반환한다.
- 같은 ID를 다른 내용으로 재사용하면 충돌 오류를 반환한다.
- 진행 중 요청을 동시에 받았을 때 대기·충돌·조회 중 어떤 계약인지 정한다.
- 기록 보존 기간이 재시도 가능 기간보다 짧지 않아야 한다.

메모리 캐시만 사용하면 프로세스 재시작·다중 노드에서 중복을 놓칠 수 있다. 데이터베이스 유일 제약 등 공유 원자성을 사용한다.

### 단계 4: 현재 상태와 동시성 확인

변경 SQL에 예상 버전을 조건으로 포함한다.

```sql
UPDATE orders
   SET customer_id = :customer_id,
       total_amount = :total_amount,
       version_no = version_no + 1,
       updated_by = :actor_id,
       updated_at = CURRENT_TIMESTAMP
 WHERE order_id = :order_id
   AND version_no = :expected_version
   AND status = 'DRAFT';
```

영향 행 수가 0이면 다음을 구분한다.

- 주문 없음
- 버전 충돌
- 변경 불가 상태
- 권한/테넌트 조건 불일치

외부에는 정보 노출을 줄이기 위해 일부 오류를 통합할 수 있지만 내부 감사·운영 진단에는 구분 근거를 남긴다.

### 단계 5: 자식 데이터 저장

품목 목록을 전체 교체하는 계약이라면 단순 삭제 후 삽입이 쉬워도 다음을 고려한다.

- 다른 테이블이 품목 키를 참조하는가?
- 삭제·재삽입으로 감사·생성 시각이 왜곡되는가?
- 대량 품목에서 잠금·로그가 증가하는가?
- 일부 변경만 있는 경우 차이 반영이 더 안전한가?

증분 반영은 입력 키를 기존 키와 비교해 삽입·갱신·삭제 집합을 만든다. 어떤 방식을 쓰든 모든 품목 검증을 먼저 완료하고 트랜잭션 안에서 반영한다.

### 단계 6: 파생값·이력 저장

```text
line_amount = quantity × unit_price
total_amount = 모든 line_amount 합계
```

파생값을 저장하면 조회는 편하지만 원본 변경 때 함께 갱신해 불일치를 막아야 한다. DB 계산 열, 트리거, 프로시저 중 한 책임을 정하고 중복 계산 규칙을 피한다.

감사 이력에는 업무상 필요한 이전·이후 상태, 수행 주체, 시각, 요청 ID, 변경 사유를 저장한다. 비밀번호·토큰·전체 민감정보를 감사 로그에 복사하지 않는다.

### 단계 7: 커밋·롤백과 결과 반환

- 모든 단계 성공 뒤 커밋한다.
- 예상 가능한 업무 오류는 명확한 코드로 롤백한다.
- 예외가 발생하면 열린 자원을 정리하고 원래 원인·상관관계 ID를 내부 로그에 남긴다.
- 커밋 성공 뒤 응답 전 연결이 끊길 수 있음을 고려해 요청 ID로 결과 조회가 가능해야 한다.

커밋 후 발생한 응답 전송 실패 때문에 같은 트랜잭션을 롤백할 수는 없다. 호출자가 재조회·멱등 재요청으로 결과를 확인하게 한다.

## 4. 안전한 의사코드

제품 문법이 아닌 흐름 중심 의사코드다.

```text
function save_order(command):
    validate_shape_and_limits(command)
    authorize(command.actor, command.customer)
    calculated_total = validate_items_and_calculate(command.items)

    begin transaction
    try:
        prior = reserve_request_id(command.request_id, hash(command))
        if prior is SUCCEEDED:
            return prior.result
        if prior has DIFFERENT_HASH:
            fail DUPLICATE_REQUEST

        if command.mode == CREATE:
            insert order header with version 1 and DRAFT state
        else:
            update order where id, expected_version, DRAFT state match
            if affected rows != 1:
                classify and fail NOT_FOUND / VERSION_CONFLICT / INVALID_STATE

        validate referenced products in one bounded query
        apply item insert/update/delete set
        update server-calculated total
        append audit history
        mark request SUCCEEDED with result reference
        commit
        return order id, new version, total
    catch known business error:
        rollback
        return stable business error
    catch database/system error:
        rollback
        log sanitized context and correlation id
        return classified system error
```

동적 SQL 문자열에 입력값을 이어 붙이지 않고 바인딩 매개변수를 사용한다. 테이블·열 이름처럼 바인딩할 수 없는 구조 요소가 동적이면 허용 목록으로만 선택한다.

## 5. 트랜잭션과 동시성 판단

### 5.1 ACID 연결

- **원자성**: 헤더·품목·합계·이력이 전부 반영되거나 전부 취소
- **일관성**: 제약과 업무 불변조건을 만족하는 상태에서 다음 상태로 이동
- **격리성**: 동시 트랜잭션의 중간 결과가 잘못 간섭하지 않도록 제어
- **지속성**: 커밋 완료 데이터가 장애 뒤에도 승인된 내구성 수준으로 보존

격리 수준을 높이면 모든 문제가 자동 해결되는 것은 아니고 동시성·교착·성능 비용이 달라진다. 실제 읽기–판단–쓰기 패턴에서 필요한 잠금 또는 버전 조건을 설계한다.

### 5.2 대표 동시성 문제

**갱신 분실**:

```text
A가 version 3 조회 → 수량 변경
B가 version 3 조회 → 가격 변경
A 저장 version 4
B가 조건 없이 저장 → A 변경을 덮음
```

`WHERE version_no=3` 조건과 영향 행 수 확인으로 B에 충돌을 알려 재조회·병합하게 한다.

**중복 삽입**: 존재 확인 뒤 동시에 두 요청이 삽입하면 둘 다 “없음”을 볼 수 있다. 조회 후 판단만 믿지 말고 유일 제약과 원자적 삽입 결과를 처리한다.

**교착상태**: 두 트랜잭션이 서로 다른 주문·품목을 반대 순서로 잠그면 순환 대기가 생길 수 있다. 접근 순서를 통일하고 트랜잭션을 짧게 유지하며, DB가 한 트랜잭션을 중단하면 멱등성 있는 제한 재시도를 적용한다.

### 5.3 비관적·낙관적 방식

| 방식 | 원리 | 적합 후보 | 주의점 |
|---|---|---|---|
| 비관적 잠금 | 읽을 때부터 변경 대상 잠금 | 충돌이 잦고 짧은 업무 | 대기·교착·긴 사용자 상호작용 금지 |
| 낙관적 동시성 | 저장 시 버전·원본값 비교 | 충돌이 드물고 읽기 비중 큼 | 충돌 사용자 처리·재시도 필요 |

화면을 연 채 사람이 오래 생각하는 동안 DB 잠금을 유지하지 않는다. 낙관적 버전과 충돌 해결 화면이 일반적으로 안전하다.

## 6. 테스트 케이스와 단위 테스트 조건 명세

### 6.1 테스트 케이스 필수 항목

| 항목 | 내용 |
|---|---|
| 테스트 ID | 요구·프로시저와 연결되는 고유 ID |
| 목적 | 검증하려는 규칙 또는 위험 |
| 사전조건 | DB 초기 상태, 사용자 권한, 트랜잭션 설정 |
| 입력 | 모든 인자와 경계값 |
| 실행 | 호출 순서, 동시성·오류 주입 방법 |
| 기대 반환 | 결과 값, 오류 코드, 버전 |
| 기대 DB 상태 | 각 테이블 행, 합계, 이력, 요청 기록 |
| 금지 결과 | 부분 저장, 중복 후속 작업, 민감정보 노출 없음 |
| 정리 | 테스트 데이터 롤백·삭제와 독립성 |
| 추적 | 요구 ID·불변조건·결함 ID |

반환 코드만 보고 데이터 상태를 확인하지 않으면 부분 커밋과 이력 누락을 놓칠 수 있다.

### 6.2 단위 테스트 환경 조건

- 운영과 호환되는 DB 기능·제약·격리 동작을 사용하는가?
- 각 테스트는 독립된 스키마·트랜잭션·고유 키로 실행되는가?
- 고정 시각·ID·외부 응답을 주입할 수 있는가?
- 외부 서비스는 제어 가능한 대역 또는 스텁으로 성공·지연·오류를 재현하는가?
- 테스트 시작 상태를 명시적으로 만들고 실행 순서에 의존하지 않는가?
- 테스트가 끝나면 데이터와 연결·트랜잭션이 정리되는가?

메모리 모형 DB가 운영 DB의 제약, 잠금, SQL 문법과 다르면 빠른 로직 테스트에는 유용해도 통합 DB 테스트를 대체하지 못한다.

## 7. 테스트 설계 기법 적용

### 7.1 동등 분할과 경계값

수량 허용 범위가 1~999라면:

```text
유효 분할: 1~999
무효 분할: 0 이하, 1000 이상, null, 숫자 아님
경계: 0, 1, 2, 998, 999, 1000
```

단가, 품목 수, 문자열 길이, 날짜 범위에도 적용한다.

### 7.2 의사결정표

| 규칙 | 신규/변경 | 주문 존재 | 버전 일치 | 상태 DRAFT | 기대 |
|---|---|---:|---:|---:|---|
| R1 | 신규 | N | - | - | 삽입 성공 |
| R2 | 신규 | Y | - | - | 중복 키 오류 |
| R3 | 변경 | Y | Y | Y | 갱신 성공 |
| R4 | 변경 | N | - | - | 없음 오류 |
| R5 | 변경 | Y | N | - | 버전 충돌 |
| R6 | 변경 | Y | Y | N | 상태 오류 |

각 규칙을 최소 한 테스트와 연결한다.

### 7.3 상태 전이 테스트

- DRAFT → DRAFT 내용 변경: 허용
- DRAFT → CONFIRMED: 별도 확정 규칙에서 허용
- CONFIRMED 상태 품목 직접 변경: 거절
- CANCELLED 주문 변경: 거절
- 정의되지 않은 상태 값: DB 제약 또는 입력 검증으로 거절

### 7.4 오류 추정

경험적으로 자주 생기는 결함을 시험한다.

- 품목 순서만 바뀌었을 때 모두 삭제·재삽입
- 금액 반올림 시 헤더와 품목 합계 불일치
- 커밋 성공 뒤 응답 손실 후 재시도 중복
- 감사 저장 실패인데 업무 데이터만 커밋
- 빈 품목 목록이 전체 삭제로 해석
- 서로 다른 요청 내용에 같은 request ID 재사용
- 교착 재시도 뒤 이력 중복

## 8. 핵심 테스트 케이스 예

### TC-SAVE-001 신규 정상 저장

```text
사전조건: 고객 C1·상품 P1/P2 활성, order O1 없음, request R1 없음
입력: O1, C1, [(P1,2,1000),(P2,1,500)], request R1
기대 반환: 성공, version=1, total=2500
기대 DB:
  orders O1 한 행(total 2500, DRAFT)
  items 두 행(line 2000, 500)
  감사 한 건, request R1 SUCCEEDED
금지: 부분 품목, 중복 이력
```

### TC-SAVE-002 입력 경계 실패와 무변경

수량 0을 넣는다. `INVALID_INPUT`을 반환하고 주문·품목·이력·요청 성공 기록이 하나도 생성되지 않아야 한다.

### TC-SAVE-003 참조 오류 롤백

두 번째 품목의 상품이 존재하지 않는다. 첫 품목까지 일부 저장되지 않고 전체 롤백되어야 한다.

### TC-SAVE-004 변경 성공

기존 버전 3 DRAFT 주문에 `expected_version=3`을 보낸다. 내용·합계가 바뀌고 버전 4, 변경 이력 한 건이 생성된다.

### TC-SAVE-005 버전 충돌

DB는 버전 4인데 입력은 3이다. `VERSION_CONFLICT`이며 기존 주문·품목·이력은 변하지 않는다.

### TC-SAVE-006 상태 오류

CONFIRMED 주문의 품목 변경을 요청한다. `INVALID_STATE`, 무변경이어야 한다.

### TC-SAVE-007 같은 요청 재전송

R1이 성공한 뒤 동일한 입력과 R1을 다시 보낸다. 기존 성공 결과를 반환하며 주문 버전·이력·후속 작업 수가 늘지 않는다.

### TC-SAVE-008 같은 요청 ID, 다른 내용

R1을 다른 수량으로 재사용한다. `DUPLICATE_REQUEST` 또는 정의된 충돌 오류이며 기존 결과를 바꾸지 않는다.

### TC-SAVE-009 동시 버전 갱신

같은 version 5를 읽은 두 트랜잭션을 동시 실행한다. 하나만 version 6으로 성공하고 다른 하나는 충돌해야 한다. 마지막 커밋이 앞 변경을 조용히 덮어쓰면 실패다.

### TC-SAVE-010 감사 저장 실패

감사 테이블 쓰기 오류를 주입한다. 감사가 필수 트랜잭션 요구라면 주문·품목도 전부 롤백되어야 한다.

### TC-SAVE-011 커밋 뒤 응답 손실

첫 호출의 커밋은 성공하지만 응답을 호출자에게 전달하지 못한 상황을 만들고 같은 R1로 재시도한다. 기존 결과를 조회하며 중복 주문이 없어야 한다.

### TC-SAVE-012 SQL 입력 안전성

따옴표·구분 기호를 포함한 허용 문자열이 데이터로 정상 저장되고 SQL 구조로 실행되지 않아야 한다. 바인딩 매개변수와 길이·문자 정책을 확인한다.

## 9. 테스트 구현 구조

의사코드 예:

```text
test "concurrent update detects conflict":
    seed order O1(version=5, DRAFT)
    connection A begin
    connection B begin

    result A = update O1 where version=5
    commit A

    result B = update O1 where version=5
    rollback/commit according to procedure result

    assert exactly one success
    assert failed result is VERSION_CONFLICT
    assert order version == 6
    assert audit count == 1
    assert stored values equal successful command
```

테스트가 프로시저 내부 구현 순서에 지나치게 결합하지 않고 외부 계약과 DB 관찰 상태를 확인한다. 단, 잠금·격리 문제를 재현하려면 두 실제 연결의 단계 동기화가 필요하다.

### 9.1 테스트 데이터 전략

- 테스트별 고유 ID를 사용해 병렬 실행 충돌을 피한다.
- 빌더로 기본 유효 데이터를 만들고 테스트가 바꾸는 필드만 드러낸다.
- 고정된 거대한 공용 덤프에 의존하지 않는다.
- 개인정보를 복사하지 않고 합성·비식별 데이터를 사용한다.
- 경계·다국어·시간대·정밀도·대량 품목 데이터 세트를 둔다.

### 9.2 정리 전략

테스트 전체를 트랜잭션으로 감싸 롤백할 수 있지만, 프로시저 자체 커밋·별도 연결·비동기 작업을 시험할 때는 효과가 제한된다. 격리된 스키마·컨테이너, 고유 키와 명시적 역순 삭제를 환경에 맞게 사용한다.

## 11. 자주 틀리는 포인트

1. **신규와 변경은 존재 여부만 조회해 안전하게 구분한다?** 조회 뒤 경쟁이 있으므로 유일 제약·버전 조건과 원자 연산이 필요하다.
2. **입력 합계는 클라이언트가 계산했으니 저장한다?** 서버가 품목에서 다시 계산하고 정밀도 규칙을 적용한다.
3. **헤더가 저장되고 품목 하나가 실패해도 나머지는 유지한다?** 업무 원자성 계약이 전체 저장이라면 전부 롤백한다.
4. **외부 API를 DB 트랜잭션 중 호출하면 더 원자적이다?** 긴 잠금과 외부 장애 결합이 생기며 로컬 후속 작업 기록·보상 구조를 검토한다.
5. **요청 재시도는 TCP가 막아준다?** 응답 손실 뒤 응용 재시도로 중복될 수 있어 멱등 키가 필요하다.
6. **중복 검사는 먼저 SELECT하면 충분하다?** 동시 요청이 모두 없음을 볼 수 있어 유일 제약과 원자 예약이 필요하다.
7. **UPDATE가 오류 없이 끝나면 한 행이 바뀌었다?** 영향 행 수 0·다수 여부와 이유를 확인한다.
8. **마지막 저장이 이기면 동시성 문제가 해결된다?** 다른 사용자의 변경을 잃을 수 있으므로 버전 충돌을 알린다.
9. **격리 수준을 최대로 하면 무조건 좋다?** 잠금·교착·처리량 비용과 실제 불변조건을 함께 판단한다.
10. **단위 테스트는 반환값만 보면 된다?** DB 최종·부분 상태, 이력, 중복 작업과 롤백을 확인한다.
11. **정상 한 건이 성공하면 프로시저가 완성됐다?** 경계·참조 오류·상태·권한·중복·동시성·장애를 시험한다.
12. **메모리 DB 테스트가 운영 DB 동시성까지 증명한다?** SQL·제약·잠금 차이가 있어 실제 호환 DB 테스트가 필요하다.
13. **모든 테스트를 한 데이터 세트와 순서로 실행하면 편하다?** 순서 의존과 병렬 충돌이 결함을 숨긴다.
14. **SQL 오류 원문을 사용자에게 주면 진단이 쉽다?** 내부 구조·데이터 노출 위험이 있어 안정된 오류 계약과 내부 상관관계 로그를 쓴다.
15. **감사 저장 실패는 부가 기능이므로 무시한다?** 감사가 업무·규제 불변조건이면 전체 트랜잭션 실패로 다뤄야 한다.

## 13. 정답과 해설

### 정답 1

원자성은 헤더·품목·합계·이력이 전부 반영되거나 전부 취소되게 한다. 일관성은 키·합계·상태·감사 불변조건을 보장한다. 격리성은 동시 주문 변경의 중간 상태 간섭을 막고, 지속성은 커밋된 결과를 승인된 내구성 수준으로 보존한다.

### 정답 2

신규는 같은 키가 이미 있으면 오류라는 의도를 가지지만 upsert는 있으면 변경한다. SELECT로 없음 확인 뒤 INSERT 사이에 다른 트랜잭션도 같은 판단을 할 수 있다. 데이터베이스 유일 제약과 원자 삽입/충돌 처리가 최종 중복을 막아야 한다.

### 정답 3

`WHERE order_id=:id AND version_no=:expected AND status=:allowed`처럼 식별자·예상 버전·업무 상태를 조건으로 두고 성공 시 버전을 증가시킨다. 0행이면 대상 없음, 버전 충돌, 상태 변경 불가, 권한·테넌트 불일치를 내부적으로 구분해 계약에 맞는 오류를 반환한다.

### 정답 4

같은 ID에 같은 내용이 재전송됐는지 다른 요청이 잘못 재사용했는지 구분하려면 내용 해시가 필요하다. 성공 결과 참조가 있으면 커밋 뒤 응답 유실 시 새 업무를 만들지 않고 이전 주문 ID·버전을 반환할 수 있다.

### 정답 5

트랜잭션을 되돌릴 수 없으므로 같은 요청 ID를 조회한다. 같은 내용으로 이미 성공했다면 저장·이력·후속 작업을 다시 만들지 않고 기존 결과를 반환한다. 다른 내용이면 충돌로 거절한다.

### 정답 6

유효 분할 1~999, 무효 분할 0 이하·1000 이상·null·비숫자로 나눈다. 경계값으로 0, 1, 2, 998, 999, 1000을 시험하고 각 반환 코드와 DB 무변경/저장을 확인한다.

### 정답 7

두 호출 모두 expected version 5로 시작해 정확히 하나만 성공하고 버전 6이 되어야 한다. 다른 하나는 VERSION_CONFLICT이며 성공 호출의 값만 저장된다. 감사·요청 결과는 성공 한 건에 맞고 조용한 덮어쓰기나 부분 품목이 없어야 한다.

### 정답 8

주문 헤더의 값·버전·상태, 품목 행 수와 금액, 헤더 합계, 감사 이력, 멱등 요청 상태, 후속 작업 수를 확인한다. 실패 테스트에서는 이들이 모두 이전 상태 그대로인지 또는 생성되지 않았는지도 확인한다.

### 정답 9

운영 DB와 SQL 문법·자료형·제약 처리 순서가 다를 수 있다. 격리 수준, 잠금, 교착·동시 연결 동작을 재현하지 못할 수 있다. 프로시저·트리거·오류 코드·정밀도·인덱스 같은 제품 기능 차이도 있어 실제 호환 DB 통합 테스트가 필요하다.

### 정답 10

요청 ID, 주문 ID, 수행 주체 ID, 시각, 변경 사유, 이전·이후 상태, 상관관계 ID와 결과를 기록한다. 비밀번호·접근 토큰·암호 키, 결제 원문, 필요 이상의 개인정보와 SQL 전체 입력은 기록하지 않는다.

## 14. 핵심 요약

- 쓰기 프로시저는 입력·권한·업무 불변조건·신규/변경 의미·동시성·오류 계약을 먼저 정의한다.
- 헤더·품목·파생 합계·감사·멱등 기록의 원자적 경계를 정하고 외부 장기 호출을 DB 트랜잭션 안에 두지 않는다.
- 값은 바인딩하고 클라이언트 합계를 신뢰하지 않으며 DB 제약과 프로시저 검증을 함께 사용한다.
- 신규, 변경, upsert는 서로 다른 존재·충돌 계약이므로 호출 의도를 명확히 한다.
- 유일 제약으로 중복 삽입을 막고 request ID·내용 해시·결과 참조로 응답 유실 재시도를 멱등 처리한다.
- 예상 버전 조건과 영향 행 수 확인으로 갱신 분실을 막고 충돌을 호출자에게 알린다.
- 테스트 케이스는 사전조건·입력·반환·최종 DB 상태·금지 결과·정리·요구 추적을 포함한다.
- 동등 분할·경계값·의사결정표·상태 전이·오류 추정으로 정상 외의 위험을 체계적으로 시험한다.
- 참조 오류·감사 실패·커밋 뒤 응답 유실·동시 갱신·교착 재시도에서 부분 저장과 중복 효과가 없는지 확인한다.
- 빠른 모형 테스트와 실제 호환 DB의 제약·트랜잭션·동시성 통합 테스트를 함께 운영한다.
