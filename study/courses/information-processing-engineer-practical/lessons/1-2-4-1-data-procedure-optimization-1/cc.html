01

수행 범위와 목표

이 레슨의 정확한 수행 범위는 설계와 운영환경을 고려한 프로시저 성능 예측과 성능측정 도구로 프로시저 성능 측정이다. 프로시저를 실행하기 전 설계·데이터·운영 조건으로 성능 위험을 예측하고, 구현 후 동일 조건에서 실행계획·세션 통계·추적·시스템 지표를 수집해 예측과 실제를 비교한다. 실데이터로 병목을 확정하고 해결안을 적용하는 작업은 다음 레슨의 주범위이므로 여기서는 측정 기준선과 증거 확보에 집중한다.

학습 후에는 다음을 수행할 수 있어야 한다.

  • 업무량, 데이터 분포, 접근 경로, 트랜잭션과 운영 자원으로 성능을 예측한다.
  • 응답 시간·처리량·CPU·논리 읽기·물리 읽기·대기와 처리 행 수를 구분한다.
  • 예상 실행계획과 실제 실행 통계를 함께 해석한다.
  • 캐시, 바인드 값, 동시성, 반복 횟수와 측정 오버헤드를 통제한다.
  • 측정 계획서, 결과표, 실행계획과 재현 절차를 산출물로 남긴다.
02

1. 성능 예측의 출발점

프로시저 성능은 SQL 문장 길이나 하드웨어 사양 하나로 결정되지 않는다. 같은 프로시저라도 입력 값의 선택도, 테이블 크기, 데이터 쏠림, 캐시 상태, 동시 사용자와 잠금 경쟁에 따라 결과가 크게 달라진다.

업무 호출 빈도·SLA │ ▼ 입력 범위·데이터 양·분포 │ ▼ SQL 접근·조인·정렬·집계 │ ▼ 트랜잭션·잠금·네트워크 왕복 │ ▼ CPU·메모리·저장장치·DB 설정 │ ▼ 예상 응답·처리량·위험

예측은 “2초가 걸린다”처럼 근거 없는 숫자를 만드는 일이 아니다. 처리 행 수와 자원 사용의 증가 방향, 피크 조건에서 목표를 넘을 가능성, 반드시 측정할 위험 구간을 구체화하는 활동이다.

03

2. 설계 요소로 성능 예측하기

2.1 입력과 결과 규모

  • 호출 1회가 읽는 후보 행 수
  • 조건을 통과하는 결과 행 수
  • 반환 열의 폭과 큰 객체 포함 여부
  • 호출 빈도와 동시 실행 수
  • 일·월·연 단위 데이터 증가량

후보 100만 행에서 10행을 반환한다면 10행이라는 결과 크기만 보지 말고 10행을 찾기 위해 몇 행을 읽는지 예측해야 한다. 화면에서 일부만 표시해도 DB가 전체를 정렬한 뒤 잘라 낸다면 처리 비용은 클 수 있다.

2.2 선택도와 데이터 분포

선택도는 조건이 전체 중 어느 정도를 선택하는지를 나타낸다. 고객번호처럼 거의 한 행을 찾는 조건과 상태값처럼 많은 행이 같은 값을 갖는 조건은 적합한 접근 경로가 다르다.

평균 분포만 사용하면 쏠림을 놓친다. 대부분 조직은 주문이 적지만 특정 조직에 절반이 몰려 있다면 대표값을 여러 구간으로 나누어야 한다.

2.3 접근 경로

인덱스가 존재한다고 반드시 사용되거나 빠른 것은 아니다. 조건과 열 순서, 선택도, 반환 행 수, 정렬 요구와 통계에 따라 넓은 순차 읽기가 더 나을 수 있다.

예측 질문:

  • 검색 조건이 선두 열과 유효한 비교를 이루는가?
  • 조건 열에 함수·형 변환을 적용해 접근 후보를 제한하는가?
  • 인덱스에서 찾은 뒤 테이블의 많은 행을 다시 읽는가?
  • 조회에 필요한 열과 정렬 순서를 지원하는가?
  • 추가 인덱스가 쓰기·저장 공간에 줄 비용은 무엇인가?

특정 DBMS가 어떤 접근을 반드시 고른다고 단정하지 않고 실행계획으로 확인한다.

2.4 조인

조인 비용은 입력 집합 크기, 조인 키, 조인 방식과 순서에 영향을 받는다.

조인 방식의 이름만 보고 우열을 정하지 않는다. 작은 입력, 큰 입력, 정렬 여부와 접근 경로에 따라 적합성이 달라진다.

2.5 정렬·집계와 임시 공간

ORDER BY, GROUP BY, DISTINCT, 집합 연산은 큰 중간 집합을 정렬하거나 해시할 수 있다. 사용 가능한 메모리를 넘으면 임시 저장장치 입출력이 증가할 수 있다. 이미 필요한 순서로 읽을 수 있는지, 업무상 중복 제거가 필요한지 예측한다.

2.6 절차형 처리와 SQL 호출

반복문 안에서 행마다 SQL을 호출하면 SQL 실행·네트워크 왕복이 누적된다. 1건당 5ms라도 10,000회면 순수 호출 시간만 약 50초가 된다. 실제로는 잠금과 로그 비용도 더해질 수 있다.

예측 계산:

총 예상 호출 시간 ≈ 호출 횟수 × 1회 평균 시간

  • 초기화·커밋·네트워크·대기 비용

이는 정확한 성능 보장이 아니라 위험 규모를 찾는 근사식이다.

2.7 트랜잭션과 잠금

큰 트랜잭션은 로그, 잠금 유지 시간과 실패 시 되돌리기 비용을 키울 수 있다. 반대로 지나치게 자주 커밋하면 업무 원자성이 깨지고 커밋 비용이 늘 수 있다. 변경 순서가 다른 동시 프로시저는 교착상태를 만들 수 있다.

2.8 예외와 실패 경로

정상 경로만 예측하지 않는다. 중복 키, 잠금 시간 초과, 재시도, 오류 로그와 되돌리기가 반복되면 피크 부하에서 장애가 증폭될 수 있다. 재시도에는 횟수·간격·멱등 조건이 필요하다.

05

4. 측정 지표

4.1 응답 시간과 처리량

  • 응답 시간: 한 호출의 시작부터 결과 또는 커밋 완료까지 걸린 시간
  • 처리량: 단위 시간당 완료한 호출·거래·행 수

평균 응답만 보면 일부 긴 지연이 가려진다. 중앙값, 상위 백분위, 최대값과 변동 폭을 함께 볼 수 있다. 목표는 업무 중요도와 피크 조건에서 정한다.

4.2 CPU와 경과 시간

CPU 시간은 실제 연산에 쓴 시간이고 경과 시간은 대기와 다른 자원 시간을 포함한다. 경과 시간이 긴데 CPU가 적으면 저장장치, 잠금, 네트워크 같은 대기를 확인한다.

4.3 논리 읽기와 물리 읽기

논리 읽기는 DB 버퍼에서 접근한 블록 양, 물리 읽기는 저장장치에서 실제로 읽은 양을 나타내는 관점이다. 캐시가 따뜻하면 물리 읽기는 줄지만 비효율적으로 너무 많은 블록을 훑는 논리 읽기는 여전히 클 수 있다.

4.4 처리 행 수

실행계획 각 단계의 입력·출력 행을 본다. 한 단계가 수백만 행을 만들고 다음 단계에서 몇 행만 남기면 필터나 조인 순서가 병목 후보다. 예상 행과 실제 행의 큰 차이는 통계·분포·조건 추정 문제의 신호다.

4.5 대기와 경합

잠금, 로그 동기화, 파일 읽기·쓰기, 메모리, 네트워크 등 무엇을 기다렸는지 분류한다. 대기 이벤트 이름은 제품별로 다르므로 시험에서는 “어떤 자원과 원인인가”를 해석한다.

5. 성능측정 도구로 프로시저 성능 측정

성능측정 도구로 프로시저 성능 측정 시 하나의 화면만 신뢰하지 않고 여러 층의 증거를 연결한다.

5.1 예상 실행계획

실행하지 않고 통계와 조건을 바탕으로 선택될 가능성이 있는 접근·조인·정렬 경로를 본다. 안전하게 후보를 검토할 수 있지만 실제 바인드 값, 런타임 행 수와 대기를 반영하지 못할 수 있다.

5.2 실제 실행계획·실행 통계

실제 실행에서 단계별 행 수, 반복 횟수, 시간과 읽기량을 수집한다. 실제 계획 수집 자체가 실행과 측정 오버헤드를 만들 수 있으므로 운영에서는 승인된 범위와 시간을 사용한다.

5.3 세션 통계와 프로파일링

특정 세션·호출의 CPU, 읽기, 쓰기, 정렬, 네트워크, 호출 횟수를 본다. 프로시저 내부 단계별 시간을 계측하면 어느 SQL과 절차가 대부분의 시간을 쓰는지 찾을 수 있다.

5.4 추적

SQL 실행, 바인드 값 범주, 대기, 호출 관계를 시간 순서로 기록한다. 상세 추적은 많은 로그와 부하를 만들고 민감 값이 포함될 수 있으므로 대상·기간·보호를 제한한다.

5.5 시스템 감시

DB만이 아니라 운영체제의 CPU, 메모리, 저장장치, 네트워크와 다른 세션 부하를 같은 시간축으로 본다. DB 대기 증가 시각에 저장장치 지연이 함께 올랐다면 상관관계를 조사할 수 있다.

5.6 응용 추적

사용자 요청이 응용, DB, 외부 서비스 중 어디에서 시간을 쓰는지 구분한다. 전체 API 3초 중 DB 프로시저가 100ms라면 프로시저만 최적화해도 목표를 달성하기 어렵다.

07

6. 재현 가능한 측정 절차

  1. 목표 정의: 대상 프로시저, 입력, 응답·처리량 목표와 실패 조건을 정한다.
  2. 기준선 기록: 코드·스키마·통계·설정 버전과 데이터 기준 시점을 고정한다.
  3. 대표 입력 선정: 선택도가 높은·낮은 값, NULL, 피크 조직과 경계 기간을 포함한다.
  4. 환경 통제: 동시 사용자, 다른 배치, CPU·메모리, 네트워크와 캐시 조건을 기록한다.
  5. 예상 계획 확인: 접근, 조인 순서, 예상 행, 정렬·임시 작업의 위험을 표시한다.
  6. 준비 실행 분리: 컴파일·연결·캐시 준비가 목적이 아니면 준비 호출을 본 측정과 분리한다.
  7. 반복 측정: 동일 조건을 여러 번 실행하고 중앙값·상위 지연과 변동을 기록한다.
  8. 실행 증거 수집: 실제 계획, 단계별 행, 읽기, CPU와 대기를 수집한다.
  9. 시스템 지표 연결: 같은 시간대 OS·DB·응용 지표를 맞춘다.
  10. 예측-실제 비교: 차이가 생긴 단계와 가정을 표시하고 다음 검증 질문을 만든다.
08

7. 측정 조건 통제

7.1 캐시

  • 차가운 캐시: 디스크 읽기와 최초 준비 비용이 크게 나타날 수 있음
  • 따뜻한 캐시: 반복 사용 시 버퍼 적중 상태를 반영

둘 중 하나가 항상 정답은 아니다. 실제 업무가 반복 조회인지 일회성 배치인지에 따라 측정하며 조건을 명시한다. 운영 캐시를 임의로 비우는 행동은 다른 사용자에게 영향을 줄 수 있으므로 허가 없이 하지 않는다.

7.2 바인드 값

상태, 조직, 기간에 따라 선택도가 달라질 수 있다. 한 값만 측정해 전체 성능으로 일반화하지 않는다. 실제 민감 값을 보고서에 그대로 남기지 않고 데이터 범주와 안전한 식별자를 사용한다.

7.3 동시성

단일 실행이 빨라도 동시 호출에서 잠금·CPU·I/O 큐가 늘 수 있다. 목표 사용자 수와 도착 패턴, 같은 키 충돌 여부를 재현한다. 각 가상 사용자 시작을 동시에 몰아 넣는 시험이 실제 분포와 같은지 확인한다.

7.4 측정 오버헤드

상세 추적과 프로파일링은 자체 부하를 만든다. 평상시 저비용 지표로 후보를 좁히고, 상세 수집은 시간·세션을 제한해 사용한다. 도구를 켠 결과와 끈 결과의 차이도 확인한다.

09

8. 구체 업무 시나리오

요구

월말에 고객별 미결 주문 금액을 조회하는 프로시저가 피크 동시 사용자 30명에서 목표 응답 시간을 만족해야 한다.

프로시저 개념

PROCEDURE getopenamount(customerid, fromdate, todate) SELECT customerid, SUM(orderamount) FROM orders WHERE customerid = :customerid AND orderdate >= :fromdate AND orderdate < :todate AND status = :openstatus GROUP BY customer_id;

예측

  • 고객별 주문 수 분포가 크게 쏠리는지 확인한다.
  • 기간이 하루와 1년일 때 후보 행 수를 각각 추정한다.
  • 고객·기간 조건을 지원하는 접근 경로와 상태 선택도를 확인한다.
  • 월말 배치가 같은 주문 테이블을 변경해 잠금·I/O 경합을 만드는지 본다.
  • 결과는 한 행이어도 집계 전 읽는 행 수가 클 수 있음을 기록한다.

측정 결과표 예

8. 구체 업무 시나리오 · 학습 표 3
케이스데이터 범주동시성캐시응답 시간논리 읽기실제 처리 행주요 대기
P1주문 적은 고객·1일1따뜻함측정값측정값측정값측정값
P2주문 많은 고객·1년1따뜻함측정값측정값측정값측정값
P3주문 많은 고객·1개월30실제 유사측정값측정값측정값측정값

수치를 미리 창작하지 않고 동일 환경에서 측정해 채운다. P2와 P3의 차이로 데이터 범위와 동시성 영향을 분리한다.

10. 실기 함정

  1. 한 번 실행한 시간만 기록: 준비 비용과 순간 부하에 왜곡될 수 있어 반복·분포가 필요하다.
  2. 결과 행 수를 읽은 행 수로 착각: 실행계획 단계별 처리 행을 본다.
  3. 평균 데이터만 사용: 쏠린 고객·조직과 긴 기간이 최악 입력일 수 있다.
  4. 예상 실행계획을 실제 결과로 단정: 실제 바인드·행 수·대기를 수집한다.
  5. 실행계획 비용을 초 단위로 해석: 후보 계획 비교를 위한 추정치일 수 있다.
  6. 차가운 캐시와 따뜻한 캐시를 섞어 평균: 목적별로 조건을 분리한다.
  7. 개발 환경 단일 실행을 운영 피크로 일반화: 동시성과 자원 비율을 맞춘다.
  8. DB 시간과 API 시간을 동일시: 응용·네트워크·외부 호출 시간을 분리한다.
  9. 상세 추적을 운영 전체에 상시 적용: 부하·로그·민감정보 위험이 있다.
  10. 인덱스 존재만으로 빠를 것이라 예측: 조건·선택도·읽을 행과 실제 계획을 본다.

12. 정답과 해설

정답 1

입력 선택도, 데이터 분포, 접근 경로, 조인·정렬, 트랜잭션·잠금, 호출 빈도·동시성, CPU·메모리·I/O, 네트워크와 DB 설정 중 다섯 가지다.

정답 2

한 행을 만들기 전에 많은 후보 행을 읽고 조인·정렬·집계할 수 있기 때문이다. 최종 결과가 아니라 단계별 입력 행과 읽기량을 본다.

정답 3

예상 계획은 통계와 조건으로 선택 경로를 추정한다. 실제 계획·통계는 실행된 경로와 실제 행 수, 반복, 시간·읽기·대기를 보여 주지만 수집 오버헤드가 있을 수 있다.

정답 4

응답 시간은 한 호출이 끝나는 데 걸린 시간이고, 처리량은 단위 시간에 완료한 호출이나 거래 수다. 하나가 개선되어도 다른 하나가 반드시 개선되는 것은 아니다.

정답 5

잠금, 저장장치, 로그, 네트워크와 메모리 같은 대기 분류와 같은 시간대 시스템 지표를 확인한다.

정답 6

논리 읽기는 DB 버퍼에서 접근한 블록 양, 물리 읽기는 저장장치에서 가져온 양이다. 따뜻한 캐시에서도 비효율적 논리 읽기는 클 수 있다.

정답 7

데이터 값에 따라 선택도와 분포가 달라져 실행 경로와 처리 행 수가 크게 달라질 수 있기 때문이다. 평균·경계·쏠린 범주를 포함한다.

정답 8

차가운 캐시와 따뜻한 캐시의 물리 읽기와 최초 준비 비용이 달라 비교 결과가 왜곡될 수 있기 때문이다. 실제 업무 조건에 맞게 분리한다.

정답 9

성능 요구·측정 계획, 데이터 분포·대표 입력, 환경 기준선, 예상·실제 실행계획, 원시 측정값·요약표, DB·OS 지표와 재현 절차 중 네 가지다.

14

핵심 요약

  • 설계와 운영환경을 고려한 프로시저 성능 예측은 처리 행, 분포, 접근·조인·정렬, 트랜잭션, 동시성과 자원 조건으로 위험을 구체화하는 활동이다.
  • 결과 행보다 실행 단계가 읽고 만든 행 수를 보고, 평균 분포 외에 쏠림과 경계 입력을 포함한다.
  • 성능측정 도구로 프로시저 성능 측정은 예상·실제 계획, 세션 통계, 추적, OS·DB 지표와 응용 시간을 연결한다.
  • 코드·스키마·통계·설정, 캐시, 바인드, 동시성과 반복 횟수를 고정해야 전후 비교가 가능하다.
  • 응답 시간, 처리량, CPU, 논리·물리 읽기, 처리 행과 대기는 서로 다른 병목 신호다.
  • 성능 측정의 결과는 단일 숫자가 아니라 재현 절차, 실행계획과 원시 증거를 포함한 기준선이다.
