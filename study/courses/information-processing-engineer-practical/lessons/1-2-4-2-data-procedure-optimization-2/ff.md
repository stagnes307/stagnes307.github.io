# 1-2-4-2. 실데이터 테스트로 병목 파악 · 성능 이슈 해결

## 수행 범위와 목표

이 레슨의 정확한 수행 범위는 **실데이터 테스트로 병목 파악**과 **성능 이슈 해결**이다. 운영 특성을 대표하는 데이터의 양·분포·경계값과 동시 부하를 재현하고, 실행계획의 실제 처리 행·대기·자원 지표로 병목을 확정한 뒤 가장 작은 안전한 변경을 적용해 정확성·성능·회귀를 검증한다. 앞 레슨에서 만든 예측·측정 기준선을 입력으로 사용하되 단순 측정 반복보다 원인 격리와 해결 검증에 집중한다.

학습 후에는 다음을 수행할 수 있어야 한다.

- 운영과 유사한 데이터 규모·분포·동시성을 안전하게 준비한다.
- 응용, 네트워크, DB와 DB 내부 CPU·I/O·잠금·로그 병목을 단계적으로 격리한다.
- 실행계획의 예상·실제 행 차이, 반복 횟수, 넓은 읽기와 임시 작업을 해석한다.
- SQL·접근 구조·통계·트랜잭션·절차형 로직 개선안을 위험과 함께 선택한다.
- 변경 전후 결과 동등성, 피크 성능, 다른 입력과 쓰기 작업의 회귀를 검증한다.

## 1. 실데이터 테스트의 의미

**실데이터 테스트로 병목 파악**에서 “실데이터”는 반드시 운영 개인정보 원본을 그대로 복사한다는 뜻이 아니다. 운영의 규모, 값 분포, 상관관계, 중복, NULL, 데이터 쏠림과 동시 변경 패턴을 대표하는 안전한 데이터 집합을 뜻한다.

소량 균등 데이터에서는 드러나지 않는 문제:

- 특정 고객·조직에 행이 집중된 데이터 쏠림
- 오래된 기간과 최신 기간의 분포 차이
- NULL, 인기 코드와 드문 코드의 선택도 차이
- 조인 키 중복으로 중간 결과가 폭증하는 상황
- 큰 정렬·해시가 메모리를 넘어 임시 저장소를 쓰는 상황
- 같은 업무 키를 동시에 갱신하는 잠금 경합
- 로그·백업·다른 배치와 저장장치가 경합하는 피크

## 2. 테스트 데이터 준비

### 2.1 데이터 특성표 작성

| 특성 | 수집·재현 내용 |
|---|---|
| 규모 | 테이블·파티션별 행 수와 증가량 |
| 분포 | 코드·조직·기간별 빈도와 상위 쏠림 |
| 관계 | 부모당 자식 수, 키 중복, NULL 비율 |
| 폭 | 평균·최대 행 길이와 큰 텍스트·파일 참조 |
| 변경 | 삽입·수정·삭제 비율과 피크 시간 |
| 동시성 | 사용자 수, 도착 간격, 같은 키 충돌 |
| 이력 | 오래된 데이터와 최신 활성 데이터 비율 |

평균만 복제하지 않는다. 주문이 많은 상위 고객, 최대 기간, 부모당 자식이 많은 경계 집합을 별도 시나리오로 둔다.

### 2.2 데이터 보호

- 승인된 범위와 환경에서만 사용한다.
- 직접 식별자는 가명·대체 값으로 바꾼다.
- 값 사이 상관관계를 유지해야 하는 키는 일관되게 변환한다.
- 민감 원문과 측정 로그의 접근·보존을 제한한다.
- 테스트 종료 후 승인된 폐기 절차를 따른다.

무작위 치환으로 분포와 관계를 없애면 성능 대표성이 떨어진다. 반대로 분포를 보존하다 재식별 가능성이 생기지 않도록 위험을 검토한다.

### 2.3 반복 가능한 기준선

시험 전 스냅샷 또는 재생성 절차를 준비한다. 변경 프로시저를 반복 실행하면 데이터 상태가 달라져 두 번째 실행이 빨라지거나 느려질 수 있다. 각 후보 변경을 같은 시작 상태에서 비교한다.

## 3. 병목 격리 절차

    사용자 응답 지연
          │
          ▼
    응용 전체 시간 분해
       ┌──┼───────────┐
       │  │           │
      DB  네트워크   외부 서비스/응용
       │
       ▼
    프로시저 내부 단계
       │
       ├─ CPU 연산
       ├─ 데이터 읽기·쓰기
       ├─ 잠금·동시성
       ├─ 로그·커밋
       └─ 임시 정렬·해시
       │
       ▼
    실행계획 단계·SQL·반복 로직

### 단계 1: 현상 고정

어떤 입력, 데이터 기준 시점, 동시 사용자, 캐시와 배치 중첩에서 목표를 넘는지 기록한다. “가끔 느림”을 재현 가능한 시나리오로 바꾼다.

### 단계 2: 응용과 DB 시간 분리

API 전체, 연결 대기, 프로시저 실행, 결과 전송과 후처리 시간을 나눈다. DB 실행이 전체 지연의 작은 부분이면 먼저 다른 구간을 조사한다.

### 단계 3: 자원 포화 확인

같은 시간대 CPU 실행 큐, 메모리, 저장장치 지연·큐, 네트워크와 로그 사용을 확인한다. 높은 사용률만으로 원인을 확정하지 않고 프로시저 실행과 시간 상관을 본다.

### 단계 4: 대기 분류

CPU를 쓰는지, 잠금·I/O·로그·네트워크를 기다리는지 분류한다. 대기 이름 자체보다 기다린 자원, 지속 시간, 발생 SQL과 차단 관계를 확인한다.

### 단계 5: 실행계획 분석

- 예상 행과 실제 행의 차이가 처음 커지는 단계
- 한 번 실행할 것으로 생각한 단계의 실제 반복 횟수
- 반환 행보다 지나치게 많은 입력 행
- 조인 후 중간 결과 폭증
- 정렬·해시의 임시 저장소 사용
- 조건 적용이 늦어지는 위치
- 같은 객체에 대한 반복 접근

가장 비싼 아이콘 하나보다 행이 폭증하기 시작한 최초 지점을 찾는다.

### 단계 6: 절차 내부 분석

행별 반복 SQL, 불필요한 커서, 동일 계산 반복, 잦은 커밋, 예외 기반 정상 흐름, 불필요한 원격 호출을 찾는다. 프로시저 전체 시간 중 각 단계 비율을 계측한다.

### 단계 7: 가설 수립·단일 변경

“통계가 부정확해 조인 순서가 달라졌다”, “행별 호출이 10만 회 반복된다”처럼 증거로 반증 가능한 가설을 세운다. 한 번에 여러 요소를 바꾸면 효과와 부작용 원인을 알기 어렵다.

## 4. 실행계획에서 병목 찾기

### 4.1 예상·실제 행 수 차이

예상 10행인데 실제 100만 행이면 이후 조인과 메모리 산정이 모두 어긋날 수 있다. 원인은 오래되거나 부족한 통계, 열 간 상관관계, 데이터 쏠림, 복잡한 조건식, 바인드 값 민감성일 수 있다.

### 4.2 넓은 범위 읽기

전체 읽기 자체가 오류는 아니다. 많은 행을 반환하거나 대부분을 처리한다면 순차 접근이 효율적일 수 있다. 문제는 몇 행을 얻기 위해 반복해서 큰 집합을 읽는 경우다.

### 4.3 반복 접근

외부 행 100만 건마다 내부 접근을 한 번 수행하면 내부 단계가 빠르더라도 누적 비용이 크다. 실제 반복 횟수와 한 번당 읽기량을 곱해 총 영향을 본다.

### 4.4 정렬·해시 넘침

작업 메모리를 초과해 임시 저장소에 쓰면 I/O가 늘어난다. 무조건 메모리를 올리기 전에 중간 행 수가 불필요하게 큰 이유, 동시 세션 전체 메모리와 정렬 필요성을 확인한다.

### 4.5 계획 민감성

입력 값에 따라 최적 경로가 다를 수 있다. 주문이 거의 없는 고객과 주문 절반을 가진 고객이 같은 계획을 사용할 때 한쪽이 느려질 수 있다. 특정 제품 기능을 가정하기보다 입력 범주별 계획·행 수를 비교하고 안정된 전략을 찾는다.

## 5. 성능 이슈 해결 전략

**성능 이슈 해결**은 원인에 맞는 변경을 선택하고 업무 결과를 보존하는 작업이다.

### 5.1 SQL 구조 개선

- 필요한 열과 행만 반환
- 조인 조건 누락·불필요한 중복 제거
- 큰 집합이 되기 전에 안전하게 필터 적용
- 반복 상관 조회를 집합 기반 조인·집계로 전환
- 같은 계산과 하위 질의의 불필요한 반복 축소
- 업무상 필요 없는 정렬·DISTINCT 제거

외부 조인의 조건 위치나 DISTINCT 제거는 결과를 바꿀 수 있으므로 동등성 검증이 필수다.

### 5.2 접근 구조 개선

검색·조인·정렬 패턴을 지원하는 인덱스를 검토한다. 열 순서, 선택도, 포함 범위와 기존 인덱스 중복을 본다. 추가 인덱스는 조회를 개선해도 삽입·수정·삭제, 저장 공간과 통계 관리 비용을 늘린다.

### 5.3 통계와 추정 개선

실제 데이터 규모·분포를 반영하도록 통계를 관리한다. 통계 갱신 후 모든 중요 입력의 계획을 다시 확인한다. 특정 입력 하나가 빨라져도 다른 입력에서 회귀할 수 있다.

### 5.4 절차형 로직 개선

나쁜 개념:

    FOR each_order IN orders:
        UPDATE customer_total
           SET amount = amount + each_order.amount
         WHERE customer_id = each_order.customer_id

집합 처리 후보:

    MERGE aggregated_order_amount
      INTO customer_total
      USING customer_id

의사코드는 방향을 보여 줄 뿐 실제 문법은 DBMS에 맞춘다. 집합 전환 전 오류 처리, 잠금 순서, 합계 규칙과 트랜잭션 원자성을 확인한다.

### 5.5 트랜잭션·배치 단위

큰 작업을 업무적으로 독립된 배치로 나누면 잠금·로그·복구 범위를 줄일 수 있다. 그러나 중간 커밋이 허용되지 않는 업무를 임의 분할하면 일관성이 깨진다. 재시작 키와 완료 상태, 중복 방지를 설계한다.

### 5.6 파티셔닝·사전 집계

기간·업무 범위가 명확하면 데이터 분할로 읽는 범위를 줄이거나 관리 작업을 분리할 수 있다. 반복 집계는 승인된 사전 집계 결과를 사용할 수 있다. 분할 키가 쿼리 조건과 맞지 않거나 집계 최신성이 업무 요구를 못 맞추면 효과가 없다.

### 5.7 자원·설정 조정

메모리, 병렬성, 연결 수, 로그와 저장 배치를 조정할 수 있다. SQL이 불필요하게 100배의 행을 처리하는데 하드웨어만 늘리는 것은 근본 해결이 아닐 수 있다. 시스템 전체 동시 사용과 장애 영향을 평가한다.

## 6. 해결안 선택 기준

| 기준 | 확인 질문 |
|---|---|
| 원인 적합성 | 측정된 병목을 직접 줄이는가 |
| 정확성 | 행·중복·NULL·정렬·반올림 의미가 같은가 |
| 효과 | 목표 입력·동시성에서 지표가 개선되는가 |
| 회귀 | 다른 바인드, 조회와 쓰기 성능이 나빠지지 않는가 |
| 운영성 | 통계, 인덱스, 집계와 배치를 지속 관리할 수 있는가 |
| 위험 | 잠금, 로그, 복구, 배포·되돌리기 영향은 무엇인가 |
| 비용 | 개발·저장·운영·라이선스·교육 비용은 적절한가 |

## 7. 변경 전후 검증

### 7.1 결과 동등성

- 행 수와 키 집합
- 열별 값과 NULL
- 중복 여부
- 금액·수량 합계
- 날짜·경계값
- 반올림 위치
- 필요한 정렬과 페이지 경계
- 변경 프로시저의 최종 상태와 로그

해시는 큰 결과 비교의 보조 수단이지만 정렬·표현을 같은 방식으로 정규화해야 한다. 해시 일치는 비교 규칙 자체의 타당성을 보장하지 않는다.

### 7.2 동일 성능 조건

같은 스냅샷, 입력, 캐시, 동시성, 다른 부하와 측정 도구를 사용한다. 변경 전은 차가운 캐시, 변경 후는 따뜻한 캐시라면 개선 효과를 과장할 수 있다.

### 7.3 회귀

- 선택도가 높은·낮은 다른 입력
- 작은·큰 기간
- 단일·동시 호출
- 조회와 쓰기 혼합
- 배치·백업 중첩
- 장애·재시도 경로

### 7.4 운영 반영

단계 배포, 지표 임계값, 중단·되돌리기 조건을 정한다. 새 인덱스나 통계 변경이 오래 걸리거나 잠금을 만들 수 있으므로 배포 작업 자체의 영향도 시험한다.

## 8. 구체 업무 시나리오

### 현상

일별 정산 프로시저가 데이터가 많은 지점에서만 목표 시간을 넘고 CPU는 보통인데 임시 저장장치 읽기·쓰기가 급증한다.

### 조사

1. 같은 기준 스냅샷에서 작은 지점과 큰 지점을 실행한다.
2. 응용 시간이 아니라 프로시저 실행이 대부분임을 확인한다.
3. 실행계획에서 지점 조건 적용 전 주문·정산 이력을 결합해 큰 중간 집합을 만드는 지점을 찾는다.
4. 예상 행은 수천인데 실제는 수백만이며 정렬이 임시 저장소로 넘치는 증거를 확인한다.
5. 통계의 지점별 쏠림 반영 여부와 조건·조인 키를 확인한다.

### 해결 후보

- 지점·기간 대상 키를 먼저 제한한 뒤 상세 집합과 결합
- 반복 조회를 한 번의 집계로 변경
- 실제 조건을 지원하는 접근 구조 검토
- 데이터 쏠림을 반영한 통계와 입력 범주별 계획 검증

### 검증

- 정산 대상 키와 금액 합계가 기존과 같은지 확인한다.
- 작은·큰 지점, 월말, 동시 지점 배치로 반복 측정한다.
- 응답 시간뿐 아니라 실제 행, 임시 I/O, CPU와 로그를 비교한다.
- 새 접근 구조가 온라인 주문 쓰기에 주는 영향을 확인한다.
- 기준을 못 맞추거나 회귀가 생기면 준비한 변경을 되돌린다.

## 9. 산출물과 체크리스트

### 산출물

- 실데이터 특성·보호 계획
- 재현 시나리오와 시작 스냅샷
- 병목 증거 묶음: 계획, 실제 행, 대기, 시스템 지표
- 원인 가설·반증 결과표
- 후보 해결안과 영향·위험 비교표
- 변경 전후 결과 동등성·성능 보고서
- 배포·감시·되돌리기 절차

### 체크리스트

- [ ] 운영 규모·분포·관계와 피크를 대표하는가?
- [ ] 민감 데이터 보호와 폐기 계획이 있는가?
- [ ] 같은 시작 상태에서 후보를 비교하는가?
- [ ] DB 밖의 응용·네트워크 시간을 먼저 분리했는가?
- [ ] 실제 행과 반복 횟수로 최초 폭증 지점을 찾았는가?
- [ ] 가설 하나마다 단일 변경으로 효과를 확인했는가?
- [ ] 결과 행·값·중복·NULL·합계를 비교했는가?
- [ ] 다른 입력과 쓰기·동시성 회귀를 확인했는가?
- [ ] 배포 작업 영향과 되돌리기 조건이 있는가?

## 10. 실기 함정

1. **운영 원본을 무단 복제**: 개인정보 보호와 승인, 대표성을 함께 만족해야 한다.
2. **평균 규모만 생성**: 쏠림·최대 부모 자식·기간 경계가 병목을 만든다.
3. **CPU 사용률이 높으면 CPU 증설부터 수행**: 어떤 SQL·행 폭증이 CPU를 쓰는지 찾는다.
4. **실행계획에서 비용 최대 단계만 수정**: 실제 행이 처음 크게 어긋난 단계를 본다.
5. **전체 읽기를 무조건 나쁜 계획으로 판단**: 많은 행이 필요하면 효율적일 수 있다.
6. **인덱스 추가 후 조회만 측정**: 쓰기·저장·통계와 다른 입력의 회귀를 확인한다.
7. **여러 변경을 한꺼번에 적용**: 효과와 부작용 원인을 분리할 수 없다.
8. **빨라졌지만 결과가 달라진 SQL을 성공 처리**: 결과 동등성이 선행 조건이다.
9. **배치 분할을 무조건 권장**: 업무 원자성과 재시작·중복 방지가 필요하다.
10. **하드웨어 증설로 비효율을 숨김**: 처리 행·반복·경합의 근본 원인을 먼저 확인한다.

## 12. 정답과 해설

### 정답 1

테이블 규모, 값 분포와 쏠림, 키 관계·중복·NULL, 행 폭, 변경 패턴, 동시성과 피크를 보존해야 한다. 민감 값은 안전하게 대체한다.

### 정답 2

사용자 요청의 전체 시간을 응용·네트워크·외부·DB로 나눈 뒤 DB 시간이 주원인인지 확인한다. DB에서는 CPU·I/O·잠금·로그·임시 작업 대기를 구분하고 실행계획 단계와 SQL·절차 반복으로 좁힌다.

### 정답 3

그 지점의 잘못된 추정이나 행 폭증이 이후 조인 방식, 메모리와 전체 비용을 연쇄적으로 키울 수 있기 때문이다.

### 정답 4

대부분의 행을 반환·집계하거나 선택도가 낮고 연속 읽기가 효율적일 때 전체 읽기가 적절할 수 있다. 몇 행만 얻기 위해 반복 전체 읽기하는지가 문제다.

### 정답 5

오류 처리 의미, 트랜잭션 원자성, 잠금 순서, 중복·합계 규칙, 행별 실행 순서 의존 중 세 가지다.

### 정답 6

삽입·수정·삭제 비용, 저장 공간, 통계·재구성 관리, 잠금·로그 증가, 다른 계획 선택과 중복 인덱스 복잡성 중 네 가지다.

### 정답 7

행 수, 키 집합, 열 값·NULL, 중복, 합계, 경계 날짜, 반올림, 정렬·페이지, 최종 변경 상태 중 다섯 가지다.

### 정답 8

선택도가 높은·낮은 값, 짧고 긴 기간, 작은·큰 조직, 단일·동시 호출, 조회·쓰기 혼합, 배치 중첩과 재시도 중 네 가지다.

### 정답 9

실데이터 분포와 동시 부하에서 예상하지 못한 회귀나 정확성 문제가 생길 수 있기 때문이다. 중단 지표와 이전 상태 복원 절차를 미리 준비한다.

## 핵심 요약

- **실데이터 테스트로 병목 파악**은 원본 복사가 아니라 운영 규모·분포·관계·경계와 동시성을 안전하게 재현하는 활동이다.
- 전체 응답을 응용·네트워크·DB로 나누고 DB에서는 CPU·I/O·잠금·로그·임시 작업에서 실행계획 단계로 좁힌다.
- 예상·실제 행 차이, 반복 횟수와 최초 중간 행 폭증이 핵심 병목 증거다.
- **성능 이슈 해결**은 SQL, 접근 구조, 통계, 집합 처리, 트랜잭션·분할과 자원을 원인에 맞게 선택한다.
- 변경은 하나씩 적용하고 같은 스냅샷·입력·캐시·동시성에서 결과 동등성과 성능을 비교한다.
- 다른 바인드와 쓰기 작업의 회귀, 배포 영향, 감시와 되돌리기까지 검증해야 해결이 완료된다.
