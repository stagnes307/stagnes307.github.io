# 1-3-1-1. 내외부 모듈 데이터 연계 요구사항 분석 · 연계 대상 데이터 식별

## 수행 범위와 목표

이 레슨의 정확한 수행 범위는 **내외부 모듈 데이터 연계 요구사항 분석**과 **연계 대상 데이터 식별**이다. 업무 사건과 시스템 경계를 기준으로 누가 어떤 데이터를 왜 보내고 받아야 하는지, 데이터의 소유 원천·키·변경 의미·민감도·규모가 무엇인지 정의한다. 메시지 표준의 구체 설계는 다음 레슨, 송수신 방식·주기·실패·보안 구현은 뒤 레슨의 주범위이므로 여기서는 요구와 대상 데이터의 근거를 완성한다.

학습 후에는 다음을 수행할 수 있어야 한다.

- 이해관계자, 송신·수신 모듈과 업무 사건을 식별한다.
- 기능 요구와 성능·가용성·보안·감사 같은 비기능 요구를 분리한다.
- 원천의 권위, 데이터 키, 상태 변화, 코드·단위·시간 의미를 조사한다.
- 신규·변경·삭제·취소와 초기분·변경분의 대상 범위를 정한다.
- 요구사항 명세서, 연계 목록, 데이터 항목 목록과 추적표를 산출한다.

## 1. 연계 요구사항 분석의 의미

**내외부 모듈 데이터 연계 요구사항 분석**은 조직 내부 모듈 또는 외부 시스템 사이에서 필요한 업무 정보의 흐름, 책임과 품질 조건을 명확히 하는 활동이다. “고객 데이터를 연계한다”처럼 넓은 문장은 구현·시험 가능한 요구가 아니다.

분석은 다음 질문에 답해야 한다.

- 어떤 업무 사건에서 연계가 필요한가?
- 송신자와 수신자, 데이터 소유자는 누구인가?
- 어떤 데이터를 어떤 범위로 전달하는가?
- 신규, 변경, 취소와 삭제는 각각 무슨 의미인가?
- 수신 시스템은 데이터를 어떤 업무에 사용하는가?
- 얼마나 빠르고 얼마나 많이 처리해야 하는가?
- 중복, 지연, 누락과 순서 역전에 대한 업무 허용 범위는 무엇인가?
- 민감정보, 감사와 보존 요구는 무엇인가?
- 실패 시 누가 감지하고 어느 상태를 정상으로 판단하는가?

이 단계에서 구현 방식을 먼저 정하면 현재 기술에 요구를 끼워 맞추기 쉽다. 먼저 업무 결과와 제약을 정의하고 이후 메커니즘 단계에서 동기·비동기, 파일·API·메시지 등을 선택한다.

## 2. 분석 대상 경계

### 2.1 내부 모듈

같은 조직이나 시스템 안의 주문, 재고, 결제, 회원 같은 기능 모듈도 데이터 소유와 배포 책임이 다르면 연계 대상이다. 같은 프로세스 안에서 직접 호출된다고 연계 계약이 불필요한 것은 아니다.

### 2.2 외부 시스템

파트너, 공공기관, 결제·배송 제공자처럼 조직 밖 시스템이다. 계약, 네트워크, 보안, 변경 일정과 장애 책임을 독립적으로 합의해야 한다. 외부 시스템 내부 동작을 통제할 수 없으므로 입력·응답의 의미와 책임 경계를 명확히 한다.

### 2.3 사람과 수작업

기존 업무에 파일 업로드, 이메일, 수기 보정이 포함되어 있다면 숨기지 않는다. 자동화 대상인지 승인·예외 처리로 남길지 요구로 결정한다.

### 2.4 기준 경계

    [고객 채널]
         │ 가입·변경 사건
         ▼
    [고객 모듈] ───── 고객 기준정보 ─────> [주문 모듈]
         │                                    │
         │                                    │ 주문 확정 사건
         ▼                                    ▼
    [동의 관리]                         [재고 모듈]
                                              │
                                              └────> [외부 배송사]

도식에는 시스템·모듈, 흐름 방향, 업무 사건과 주요 데이터 묶음을 표시한다. 전송 제품이나 URL은 아직 확정하지 않아도 된다.

## 3. 이해관계자와 책임

| 역할 | 분석 책임 |
|---|---|
| 업무 소유자 | 연계 목적, 상태 의미, 예외와 인수 기준 승인 |
| 데이터 소유자 | 권위 원천, 항목 정의, 민감도와 품질 승인 |
| 송신 모듈 담당 | 생성·변경 사건과 제공 가능 범위 확인 |
| 수신 모듈 담당 | 소비 목적, 필수 항목, 처리 결과와 제약 확인 |
| 아키텍트 | 시스템 경계, 의존성과 비기능 요구 정리 |
| 보안·개인정보 담당 | 최소 제공, 보호·감사·보존 요구 확인 |
| 운영 담당 | 감시, 장애 대응, 작업 창과 지원 책임 확인 |
| 시험 담당 | 요구를 검증 가능한 인수 조건으로 전환 |

송신자와 수신자의 정의가 다르면 데이터 소유자가 의미를 확정한다. 구현팀의 추정으로 상태 코드를 정하지 않는다.

## 4. 요구사항 유형

### 4.1 기능 요구사항

- 고객 생성 시 주문 모듈에 고객 식별·상태 제공
- 주문 확정 시 재고 예약 요청 생성
- 배송 상태 변경 시 주문 상태에 반영
- 취소 요청의 접수·결과를 양쪽에서 추적
- 초기 기준정보와 이후 변경분 제공

### 4.2 데이터 요구사항

- 필수·선택 항목과 조건부 필수
- 키와 상관관계 식별자
- 코드, 날짜·시간대, 단위와 소수 자릿수
- 데이터 범위·기간·제외 조건
- 원본·파생 값과 계산 책임

### 4.3 비기능 요구사항

| 관점 | 요구 질문 |
|---|---|
| 적시성 | 업무 사건 후 언제까지 반영되어야 하는가 |
| 처리량 | 평상·피크 건수와 메시지·파일 최대 크기는 얼마인가 |
| 가용성 | 연계 중단이 허용되는 시간과 업무 대안은 무엇인가 |
| 일관성 | 즉시 일치가 필요한가, 지연 허용 상태가 있는가 |
| 순서·중복 | 순서 역전과 재전달을 수신 업무가 어떻게 인식해야 하는가 |
| 보안 | 데이터 분류, 최소 제공, 보호와 접근 감사 요구는 무엇인가 |
| 추적 | 업무 사건을 송신부터 수신 결과까지 어떻게 식별하는가 |
| 보존 | 원문·처리 기록과 오류 자료를 얼마나 보존하는가 |
| 변경 | 계약 변경 통지, 호환 기간과 승인 책임은 누구인가 |

여기서는 요구를 정의하며 구체적 전송·암호 방식은 이후 설계에서 결정한다.

## 5. 요구사항 도출 절차

1. **업무 범위 확정**: 연계 목적, 시작·종료 업무 사건과 제외 범위를 정한다.
2. **현행 조사**: 화면, 보고서, 수작업 파일, 프로그램·DB 흐름과 장애 이력을 확인한다.
3. **시스템·모듈 목록화**: 소유 조직, 담당자, 운영 시간과 변경 창을 기록한다.
4. **업무 시나리오 작성**: 정상, 취소, 중복, 지연, 부분 실패와 재처리 상황을 서술한다.
5. **데이터 흐름 작성**: 송신·수신·소유 원천과 흐름 방향을 표시한다.
6. **기능·데이터 요구 도출**: 사건별 입력·출력, 키, 상태와 결과를 정한다.
7. **비기능 요구 정량화**: 피크량, 허용 지연, 가용성과 보존 조건을 단위와 함께 적는다.
8. **제약·의존성 확인**: 법·계약, 운영 시간, 기존 인터페이스와 조직 책임을 확인한다.
9. **모호성·충돌 해결**: 용어·상태·시간과 오류 책임 차이를 이슈로 등록하고 승인받는다.
10. **추적·검토**: 업무 목표-요구-데이터-인수 조건을 연결하고 이해관계자가 승인한다.

## 6. 연계 대상 데이터 식별

**연계 대상 데이터 식별**은 요구를 만족하기 위해 실제로 전달할 데이터 집합과 항목을 선정하고 그 출처·의미·변경 책임을 정의하는 작업이다.

### 6.1 업무 개체와 사건

업무 명사만 나열하지 말고 상태 변화 사건을 함께 본다.

- 고객: 등록, 정보 변경, 이용 정지, 탈퇴
- 주문: 생성, 확정, 취소, 완료
- 결제: 승인 요청, 승인, 거절, 취소
- 배송: 접수, 집하, 이동, 완료, 반송

“삭제”가 실제 데이터 제거인지 사용 중지 상태인지 확인한다. 수신자가 이력을 유지해야 할 수 있다.

### 6.2 데이터 권위 원천

같은 고객 주소가 여러 시스템에 있어도 어느 시스템이 기준 값을 결정하는지 정한다. 원천 시스템은 단순히 데이터를 처음 보낸 시스템이 아니라 해당 값의 생성·변경과 품질을 책임지는 권위 원천이다.

파생 값은 계산 책임을 정한다. 송신자가 금액 합계를 보내고 수신자도 재계산하면 반올림·시점 차이로 결과가 달라질 수 있다.

### 6.3 식별 키

- 업무 키: 주문번호처럼 업무에서 대상을 식별
- 기술 키: 내부 저장을 위한 식별자
- 상관관계 ID: 하나의 요청·사건을 시스템 간 추적
- 이벤트 ID: 재전달된 동일 사건을 구분
- 버전·변경 순번: 순서 역전과 최신 상태 판단

내부 기술 키를 외부에 그대로 노출하면 시스템 교체와 보안에 부담이 될 수 있다. 안정된 연계 식별자를 별도로 설계할 필요가 있는지 요구 단계에서 확인한다.

### 6.4 값의 의미

각 항목에서 확인할 것:

- 정확한 업무 정의
- 자료형, 길이, 형식
- 필수·선택과 조건부 필수
- 코드 집합과 유효 기간
- 단위, 통화, 소수 자릿수·반올림
- 날짜·시각, 시간대와 기준 시점
- NULL, 빈 문자열, 0과 “해당 없음”의 차이
- 민감도, 마스킹·보존 요구
- 생성·변경 책임자

### 6.5 범위 식별

- 초기 전체분과 운영 변경분
- 기준일 현재 유효 데이터와 과거 이력
- 신규·수정·취소·논리 삭제
- 특정 조직·상태·기간의 포함·제외
- 큰 첨부·반복 항목의 별도 전송 여부

전체분과 변경분이 같은 항목을 쓰더라도 포함 기준과 추출 시점이 다를 수 있다.

## 7. 데이터 항목 명세

| 항목 | 설명 |
|---|---|
| 연계 ID | 요구·흐름을 식별하는 ID |
| 업무 사건 | 데이터를 보내는 원인이 된 사건 |
| 송신·수신 | 제공·소비 모듈 |
| 논리 항목명 | 업무에서 합의한 이름 |
| 정의 | 포함·제외와 계산 의미 |
| 원천 위치 | 권위 원천 객체·열 또는 사건 |
| 키 여부 | 업무 키·상관관계·버전 |
| 필수 조건 | 항상 또는 특정 상태에서 필수 |
| 형식·범위 | 자료형, 길이, 단위, 코드 |
| 변경 의미 | 생성·수정·취소·삭제의 해석 |
| 민감도 | 보호·감사·보존 요구 |
| 품질 기준 | 허용 NULL, 코드, 시점과 정확성 |

이 단계의 명세는 후보 데이터와 의미를 확정한다. 최종 메시지 필드명·계층·버전 같은 표준 계약은 다음 단계에서 설계한다.

## 8. 대상 선정 판단 기준

### 8.1 필요한 최소 데이터

수신 업무에 필요한 항목만 제공한다. “나중에 쓸 수 있으니 모든 고객 열”을 전달하면 결합도, 개인정보 노출과 변경 영향이 커진다.

### 8.2 안정된 의미

화면 표시용 임시 값보다 업무적으로 정의된 값과 식별자를 사용한다. 표시 문자열만 전달하면 다국어·표현 변경에 취약하므로 코드와 의미를 구분한다.

### 8.3 원천의 신뢰성과 최신성

권위 원천이 아닌 복제본에서 읽을 때 허용 지연과 불일치 위험을 요구로 기록한다. 최신 수정일시만으로 권위 원천을 판단하지 않는다.

### 8.4 변경 감지 가능성

수정·취소·삭제 사건을 신뢰성 있게 찾을 수 있는지, 동일 시각 경계와 지연 입력이 있는지 확인한다. 구체 추출 방식은 메커니즘 설계에서 선택한다.

### 8.5 수신 처리 가능성

수신자가 코드, 단위, 최대 반복 수와 데이터 양을 처리할 수 있는지 본다. 송신 편의로 거대한 중첩 데이터 하나를 보내면 수신 실패·재처리 범위가 커질 수 있다.

## 9. 구체 업무 시나리오

### 주문 확정 → 배송 접수

업무 요구:

- 주문이 결제 완료로 확정되면 배송사에 접수한다.
- 주문 일부가 여러 배송지로 나뉠 수 있다.
- 취소는 집하 전과 후의 업무 의미가 다르다.
- 고객 연락처는 배송 목적으로 필요한 기간만 제공한다.

### 분석

1. 주문 모듈은 주문 상태의 권위 원천, 배송사는 운송 상태의 권위 원천으로 둔다.
2. 사건을 주문 확정, 배송 접수 결과, 배송 상태 변경, 취소 요청·결과로 나눈다.
3. 주문번호만으로 배송 단위를 식별할 수 없으므로 배송지·분할 단위 식별자를 찾는다.
4. 상품명 표시와 실제 배송 상품 식별자를 구분한다.
5. 수량 단위, 주소 구성, 연락처 사용 목적과 보존 요구를 확인한다.
6. 주문 수정 순번 또는 사건 ID가 필요한지 요구로 기록한다.
7. 집하 후 취소를 단순 삭제로 전달하지 않고 반송 등 별도 업무 결과가 필요한지 합의한다.

### 후보 대상 데이터

| 묶음 | 주요 항목 | 선정 근거 |
|---|---|---|
| 사건 | 이벤트 ID, 사건 종류, 발생 시각, 버전 | 중복·순서·추적 요구 |
| 배송 단위 | 주문번호, 배송단위번호 | 분할 배송 식별 |
| 수취 | 수취인, 주소, 연락처 | 배송 수행에 필요한 최소 정보 |
| 품목 | 상품 식별자, 수량, 단위 | 포장·배송 대상 |
| 업무 조건 | 배송 요청일, 특별 취급 코드 | 배송 처리 규칙 |

실제 전송 필드와 표현은 다음 레슨의 표준 설계에서 확정한다.

## 11. 실기 함정

1. **구현 제품부터 선택**: 업무 사건과 요구를 먼저 정의한다.
2. **연계 대상을 테이블 전체로 선정**: 수신 업무에 필요한 최소 항목을 고른다.
3. **같은 이름이면 같은 의미라고 판단**: 정의, 코드, 단위와 기준 시점을 비교한다.
4. **최신 수정 시스템을 권위 원천으로 판단**: 생성·변경 책임과 업무 소유권을 본다.
5. **신규만 분석하고 수정·취소·삭제를 누락**: 상태 변화별 의미를 정의한다.
6. **주문번호 하나로 모든 하위 대상을 식별**: 분할·반복 단위의 키를 확인한다.
7. **NULL, 빈 문자열, 0을 같은 값으로 취급**: 업무 의미를 각각 합의한다.
8. **표시 문자열을 표준 코드 대신 전달**: 코드와 표현 책임을 구분한다.
9. **평균 건수만 비기능 요구에 기록**: 피크, 최대 메시지와 성장량을 포함한다.
10. **개인정보를 나중 사용 가능성으로 과다 제공**: 목적에 필요한 최소 범위와 보존을 정한다.

## 13. 정답과 해설

### 정답 1

연계 업무 사건과 목적, 송신·수신·소유자, 필요한 데이터 범위, 수신 사용 목적, 적시성·처리량, 중복·지연 허용, 민감도와 책임 중 네 가지다.

### 정답 2

기능 요구는 고객 생성 전달, 주문 확정 시 재고 요청, 배송 상태 반영 등이다. 비기능 요구는 허용 지연, 피크 처리량, 가용성, 일관성·보안·추적·보존 등이다.

### 정답 3

복제본이나 화면 캐시가 더 최근 시각을 가질 수 있어도 업무 값의 생성·변경과 품질을 승인할 권한이 없을 수 있기 때문이다. 업무 소유권과 책임으로 정한다.

### 정답 4

업무 키, 상관관계 ID, 이벤트 ID, 버전·변경 순번, 실행·추적 ID 중 네 가지다.

### 정답 5

정의, 자료형·길이, 필수 조건, 코드·유효 기간, 단위·반올림, 날짜·시간대, NULL 의미, 민감도·보존, 생성·변경 책임 중 여섯 가지다.

### 정답 6

초기 전체분은 기준 시점의 유효·이력 범위와 제외 조건을 정의한다. 변경분은 기준 이후 신규·수정·취소·삭제 사건과 경계·지연 입력을 식별해야 한다.

### 정답 7

불필요한 결합과 변경 영향을 줄이고, 개인정보·기밀 노출과 저장·처리 비용을 줄이며, 수신자의 잘못된 사용을 방지하기 위해서다.

### 정답 8

한 주문이 여러 배송지나 묶음으로 분할될 수 있어 주문번호만으로 개별 배송의 상태·취소·재처리 대상을 유일하게 식별할 수 없기 때문이다.

### 정답 9

요구사항 명세, 시스템·담당 목록, 컨텍스트·데이터 흐름도, 인터페이스 후보 목록, 업무 시나리오, 데이터 항목 명세, 권위 원천 표, 추적표와 이슈 기록 중 다섯 가지다.

## 핵심 요약

- **내외부 모듈 데이터 연계 요구사항 분석**은 업무 사건, 송신·수신·데이터 소유 책임과 기능·비기능 조건을 구현 전에 명확히 하는 활동이다.
- 정상뿐 아니라 수정·취소·삭제, 중복·지연·순서와 부분 실패의 업무 의미를 분석한다.
- **연계 대상 데이터 식별**은 권위 원천, 업무·이벤트·버전 키, 코드·단위·시간·NULL, 민감도와 범위를 확정한다.
- 수신 목적에 필요한 최소 데이터만 선정하고 초기분·변경분·이력과 제외 조건을 구분한다.
- 구체 전송 방식보다 업무 목표와 측정 가능한 적시성·처리량·일관성·추적 요구를 먼저 승인한다.
- 요구사항, 데이터 항목과 인수 조건을 추적표로 연결해야 이후 표준·메커니즘·시험의 근거가 된다.
