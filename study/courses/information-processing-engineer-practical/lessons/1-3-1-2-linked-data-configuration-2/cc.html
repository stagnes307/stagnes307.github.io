01

수행 범위와 목표

이 레슨의 정확한 수행 범위는 연계 데이터 표준 설계와 연계 데이터 구성하기의 적용 절차와 판단 기준이다. 앞 단계에서 식별한 업무 사건과 데이터 항목을 송신·수신자가 같은 의미로 해석할 수 있도록 표준 용어, 메시지 구조, 자료형·길이·코드·단위·시간·NULL, 식별자와 버전 규칙으로 구체화한다. 전송 방식과 주기, 실패·보안 처리, 실제 모듈 구현·시험은 뒤 레슨의 주범위이므로 여기서는 데이터 계약의 완전성과 호환성에 집중한다.

학습 후에는 다음을 수행할 수 있어야 한다.

  • 논리 표준 모델과 인터페이스별 물리 메시지 형식을 구분한다.
  • 헤더·본문·반복 구조와 업무 키·이벤트·상관관계 식별자를 설계한다.
  • 문자·숫자·날짜·시간·코드·NULL과 단위·반올림 규칙을 명세한다.
  • 스키마 버전과 하위·상위 호환성을 고려해 변경 규칙을 정한다.
  • 표준 사전, 스키마, 매핑표, 예제와 검증 체크리스트를 산출한다.
02

1. 연계 데이터 표준의 의미

연계 데이터 표준 설계는 서로 다른 모듈이 데이터를 같은 구조와 의미로 생성·해석하도록 공통 규칙과 계약을 만드는 활동이다. 이름과 순서만 맞추는 것이 아니라 값의 업무 의미, 자료형, 코드, 시점과 변경 의미까지 합의해야 한다.

표준이 없을 때의 문제:

  • 송신의 고객상태 A를 수신이 활성으로 볼지 휴면으로 볼지 알 수 없다.
  • 금액의 통화·부가세·반올림 위치가 달라 합계가 맞지 않는다.
  • 시각에 시간대가 없어 사건 순서를 판단하기 어렵다.
  • NULL, 빈 문자열, 0과 필드 누락을 같은 상태로 오해한다.
  • 필드 추가만 해도 수신 파서가 실패한다.
  • 메시지 ID와 업무 키를 혼동해 재전달을 신규 거래로 처리한다.

표준은 형식과 양쪽 책임을 담은 계약이며 예제 밖 입력의 처리까지 명세해야 한다.

03

2. 표준 설계 원칙

2.1 의미 우선

물리 필드명보다 논리 용어와 정의를 먼저 확정한다. 같은 orderAmount라도 상품 합계, 할인 후 금액, 세금 포함 결제액일 수 있다. 계산식과 기준 시점을 명시한다.

2.2 일관성

같은 고객번호, 통화, 상태는 인터페이스마다 임의 자료형·코드를 만들지 않는다. 공통 도메인과 코드 사전을 재사용한다.

2.3 명확성

필수·선택, 최소·최대, 반복 수, 정렬 여부와 조건부 규칙을 검증 가능하게 적는다. “필요하면 입력” 같은 표현을 피한다.

2.4 최소성

수신 목적에 필요 없는 데이터와 내부 구현 세부를 노출하지 않는다. 메시지가 클수록 저장·전송·변경과 개인정보 영향이 커진다.

2.5 확장성과 호환성

필드·코드가 늘어도 수신자가 동작하도록 버전·선택 필드 정책을 정한다. 알 수 없는 값 처리는 계약을 따른다.

2.6 추적성

요구 ID, 업무 사건, 논리 항목, 원천 필드, 표준 필드와 수신 저장 위치를 연결한다. 스키마와 예제, 코드 사전의 버전도 함께 식별한다.

04

3. 논리 표준과 물리 형식

3.1 논리 표준 모델

기술 형식과 독립적으로 업무 개체, 속성, 관계와 도메인을 정의한다.

  • 주문: 주문번호, 주문상태, 주문시각, 통화, 총액
  • 배송단위: 배송단위번호, 수취지, 품목 목록
  • 사건: 이벤트ID, 사건종류, 발생시각, 업무 버전

3.2 물리 메시지

논리 모델을 JSON, XML, 구분자 파일, 고정 길이 레코드 등 실제 표현으로 옮긴다. 이 레슨에서는 특정 방식의 우열보다 어떤 형식에서도 의미를 잃지 않도록 매핑하는 것이 핵심이다.

4. 메시지 구조

4.1 공통 헤더

공통 헤더는 본문과 별개로 메시지 식별·추적 정보를 담는다.

  • 계약 또는 메시지 유형
  • 스키마 버전
  • 메시지·이벤트 ID
  • 상관관계 ID
  • 생성 시스템과 생성 시각
  • 업무 대상 버전 또는 변경 순번

실제 공통 사용 항목만 두고 보안 자격증명을 업무 메시지에 넣지 않는다.

4.2 본문

업무 사건에 필요한 개체와 항목을 담는다. 단일 대상인지 여러 대상을 묶은 배치인지 명확히 하고 반복 구조의 최대 크기와 순서 의미를 정한다.

4.3 메타데이터와 업무 데이터 구분

createdAt이 메시지 생성 시각인지 주문 생성 시각인지 이름만으로 불명확할 수 있다. 전송 메타데이터와 업무 시각을 서로 다른 필드·정의로 분리한다.

4.4 예시 구조

{ "header": { "messageType": "OrderConfirmed", "schemaVersion": "1", "eventId": "EVT-...", "producedAt": "시간대가 포함된 시각" }, "order": { "orderNo": "업무 주문번호", "orderVersion": 3, "currencyCode": "표준 통화 코드", "amount": "정의된 정밀도의 숫자", "deliveryUnits": [ {"deliveryUnitNo": "분할 배송 식별자", "items": ["품목 목록"]} ] } }

실제 코드·길이·정밀도와 시각 표현은 승인된 표준 사전에 따른다.

6. 자료형과 값 표현

6.1 문자열

문자 인코딩, 허용 문자, 앞뒤 공백, 대소문자, 최소·최대 길이를 정한다. 식별자의 선행 0이 의미 있다면 숫자로 정의하지 않는다.

6.2 숫자와 금액

정밀도, 소수 자릿수, 부호, 단위와 반올림 시점을 정한다. 문자열 “1,000원”보다 숫자 1000과 통화·단위 코드를 분리하면 계산과 지역화가 쉽다.

반올림은 행별로 한 뒤 합산할지 합산 후 할지에 따라 값이 달라질 수 있다. 업무 소유자가 식과 순서를 승인한다.

6.3 날짜와 시각

  • 날짜만 필요한 값과 순간을 나타내는 시각을 구분
  • 시간대 또는 기준 시간대
  • 초 이하 정밀도
  • 일광 절약 시간과 모호한 지역 시각 처리
  • 발생 시각, 처리 시각과 반영 시각 구분

문자 정렬을 시간 순서로 가정하지 말고 표준 해석 규칙을 사용한다.

6.4 논리값

true/false와 Y/N, 1/0을 혼합하지 않는다. “미정”이 필요하면 2상 논리값에 억지로 넣지 말고 별도 상태나 nullable 정책을 정의한다.

6.5 NULL·누락·빈 값

  • 필드 누락: 해당 버전에서 제공하지 않았거나 변경하지 않음을 뜻할 수 있음
  • 명시적 null: 알려진 값 없음 또는 값 제거를 뜻할 수 있음
  • 빈 문자열: 길이 0의 알려진 문자열
  • 0: 실제 숫자 값

부분 수정 메시지에서 필드 누락과 null은 특히 다르다. null이 값을 삭제하라는 뜻인지 “모름”인지 계약에 적는다.

6.6 코드

표시명보다 안정된 코드 값을 전달하고 수신자가 표현을 결정할 수 있다. 코드 집합 ID, 버전·유효 기간, 신규 코드가 왔을 때 거부·보류·기본 처리 중 어느 정책인지 정의한다.

알 수 없는 코드를 “기타”로 자동 변환하면 의미 손실을 숨길 수 있다.

08

7. 식별자와 변경 의미

7.1 업무 키

업무 대상을 식별한다. 주문번호, 배송단위번호처럼 수신 업무에서 안정적으로 사용할 수 있어야 한다.

7.2 메시지·이벤트 ID

같은 사건이 재전달되었는지 판단할 수 있는 고유 식별자다. 요청마다 새로 생성하면 재시도의 중복을 판별하기 어렵다. 재전달 정책과 ID 유지 규칙은 뒤 메커니즘 설계에서 구체화한다.

7.3 상관관계 ID

하나의 업무 흐름에서 요청, 응답과 후속 사건을 연결한다. 메시지 하나의 ID와 전체 흐름의 ID를 구분한다.

7.4 버전·순번

같은 업무 대상의 변경 순서를 나타낸다. 네트워크 도착 순서가 업무 발생 순서와 다를 수 있으므로 수신자가 이전 변경을 덮어쓰지 않게 돕는다.

7.5 변경 유형

생성, 전체 교체, 부분 수정, 취소, 논리 삭제와 복구를 구분한다. 부분 수정에서 제공되지 않은 필드를 기존 값 유지로 볼지 null로 볼지 명확히 한다.

09

8. 스키마 버전과 호환성

8.1 호환성 관점

  • 이전 수신자가 새 송신 메시지를 처리할 수 있는가?
  • 새 수신자가 이전 송신 메시지를 처리할 수 있는가?
  • 양쪽이 혼재하는 전환 기간을 지원하는가?

호환 방향 용어는 도구마다 설명 방향이 다를 수 있으므로 “누가 어느 버전을 읽는가”를 문장으로 확인한다.

8.2 상대적으로 안전한 변경

  • 선택 필드 추가
  • 기존 필드의 설명 보완
  • 기존 의미를 바꾸지 않는 새 코드의 합의된 추가

그러나 수신자가 알 수 없는 필드·코드를 엄격히 거부하면 선택 필드 추가도 깨질 수 있다. 실제 파서 정책을 시험한다.

8.3 호환성이 깨지기 쉬운 변경

  • 필수 필드 추가
  • 기존 필드 삭제·이름 변경
  • 자료형·단위·의미 변경
  • 코드 값의 기존 의미 변경
  • 반복 구조나 키 의미 변경

깨지는 변경은 새 주 버전, 병행 운영, 변환 어댑터와 종료 계획을 검토한다. 하나의 버전 문자열만 올리고 소비자 준비를 확인하지 않으면 안 된다.

적용 절차

  1. 승인 요구·대상 확인: 업무 사건, 송수신, 권위 원천과 최소 데이터 범위를 고정한다.
  2. 표준 사전 조사: 조직 용어·단어·도메인·코드와 기존 계약을 재사용한다.
  3. 논리 모델 구성: 업무 개체, 관계, 키와 사건을 기술 형식과 독립적으로 정의한다.
  4. 메시지 경계 결정: 한 메시지의 업무 단위, 반복 구조와 최대 크기를 정한다.
  5. 공통 헤더·본문 설계: 유형·버전·식별·시각과 업무 데이터를 구분한다.
  6. 항목 표준화: 이름, 자료형, 크기, 필수·NULL, 코드, 단위·시간을 명세한다.
  7. 원천-표준-수신 매핑: 변환·계산, 손실 가능성과 책임을 기록한다.
  8. 버전·호환 정책 설계: 필드·코드 변경, 병행 기간과 소비자 대응을 정한다.
  9. 스키마·예제·검증 규칙 작성: 정상·경계·조건부·비정상 예제를 만든다.
  10. 양방향 검토·승인: 송신 생성 가능성과 수신 해석 가능성을 각각 확인한다.
  11. 기준선 배포·변경관리: 스키마, 사전과 매핑 버전을 연결하고 변경 이력을 남긴다.

11. 구체 업무 시나리오

상황

주문 시스템의 확정 사건을 재고 시스템이 받아 예약한다. 원천의 금액은 정수 최소 통화 단위이고, 수신은 소수 금액을 지원한다. 주문 일부는 여러 창고에서 예약될 수 있다.

설계

  1. 업무 사건을 OrderConfirmed로 정의하고 주문 상태 전체 갱신 메시지와 구분한다.
  2. orderNo는 업무 대상, eventId는 동일 사건 재전달 식별, correlationId는 결제부터 예약까지 흐름 추적에 사용한다.
  3. orderVersion을 두어 이전 변경이 나중에 도착했는지 판정할 근거를 제공한다.
  4. amount에 통화 코드, 단위와 반올림 책임을 함께 정의한다.
  5. items는 상품, 수량, 수량 단위를 가진 반복 구조로 정의하고 최대 범위를 합의한다.
  6. 창고 할당은 재고 시스템 책임이면 송신 메시지에 내부 창고 결정을 넣지 않는다.
  7. 취소는 확정 사건의 null 필드가 아니라 별도 사건 또는 명시 변경 유형으로 정의한다.
  8. 새 선택 필드 추가와 필수 의미 변경의 버전 정책을 구분한다.

계약 검토 예

  • 동일 eventId의 업무 내용이 달라질 수 없는가?
  • amount 0이 무료 주문인지 누락인지 명확한가?
  • item quantity의 소수 허용 여부와 단위가 있는가?
  • producedAt과 orderConfirmedAt을 구분했는가?
  • 알 수 없는 상품 코드·주문 버전의 수신 상태가 정의되었는가?

13. 실기 함정

  1. 예제 JSON만 만들고 계약 완료로 판단: 정의, 제약, 버전·변경 규칙이 필요하다.
  2. 물리 필드명부터 정함: 논리 의미와 도메인을 먼저 확정한다.
  3. 메시지 ID와 업무 키를 동일시: 사건 재전달과 업무 대상 식별 역할이 다르다.
  4. 날짜 문자열에 시간대가 필요 없다고 가정: 날짜와 순간 시각을 구분한다.
  5. NULL, 누락, 빈 문자열과 0을 통합: 부분 수정과 값 제거 의미가 달라진다.
  6. 금액 자료형만 정의: 통화, 단위, 정밀도와 반올림 시점을 적는다.
  7. 선택 필드 추가는 항상 호환: 기존 수신자의 알 수 없는 필드 정책을 시험한다.
  8. 코드 표시명을 전송 표준으로 사용: 안정된 코드와 표현을 분리한다.
  9. 내부 기술 키를 무조건 외부 공개: 안정성·종속·노출을 검토한다.
  10. 버전 문자열만 올리면 변경관리 완료: 소비자 준비, 병행·종료와 변환 계획이 필요하다.

15. 정답과 해설

정답 1

논리 표준은 기술 형식과 독립적인 업무 개체·속성·관계·도메인을 정의한다. 물리 표준은 이를 실제 JSON·XML·파일 등의 필드명, 계층, 순서와 인코딩으로 표현한다.

정답 2

메시지 유형, 스키마 버전, 메시지·이벤트 ID, 상관관계 ID, 생성 시스템, 생성 시각, 업무 버전 중 다섯 가지다.

정답 3

통화, 단위, 정밀도·소수 자릿수, 부호·범위, 반올림 방식과 적용 순서 중 네 가지다.

정답 4

누락은 미제공·미변경, null은 값 없음·제거, 빈 문자열은 길이 0의 값, 0은 실제 숫자일 수 있어 수신 상태 변경이 달라지기 때문이다.

정답 5

메시지 ID는 전송 사건 하나, 업무 키는 주문 같은 대상, 상관관계 ID는 여러 메시지의 한 업무 흐름, 업무 버전은 같은 대상 변경 순서를 식별한다.

정답 6

필수 필드 추가, 기존 필드 삭제·이름 변경, 자료형·단위·의미 변경, 코드 기존 의미 변경, 반복·키 구조 변경 중 네 가지다.

정답 7

원천 항목·정의, 표준 필드, 변환·계산식, 수신 항목, 필수·코드·범위 검증, 오류 후보와 책임 중 다섯 가지다.

정답 8

정확성, 완전성, 최소성, 일관성, 명확성, 검증 가능성, 호환성, 추적성, 구현 가능성 중 다섯 가지다.

정답 9

스키마는 형식·자료형·필수성 일부를 확인하지만 금액 계산 의미, 권위 원천, 코드 업무 의미, 시간 기준과 변경 책임의 타당성은 업무 검토가 필요하기 때문이다.

핵심 요약

  • 연계 데이터 표준 설계는 송수신자가 같은 데이터 구조와 업무 의미를 해석하도록 용어·도메인·코드·키·버전 규칙을 계약으로 만드는 활동이다.
  • 논리 업무 모델을 먼저 만들고 메시지 헤더·본문, 자료형·길이·필수·NULL·단위·시간과 반복 구조로 물리화한다.
  • 메시지·이벤트 ID, 업무 키, 상관관계 ID와 업무 버전은 역할이 다르다.
  • 스키마 변경은 누가 어느 버전을 읽는지 기준으로 호환성을 검토하고 병행·종료·변환 계획을 둔다.
  • 연계 데이터 구성하기의 적용 절차와 판단 기준은 요구 확인, 표준 재사용, 논리 모델, 항목·매핑·버전 설계, 양방향 검토와 변경관리로 이어진다.
  • 스키마 자동 검증과 업무 의미 검토를 함께 수행하고 요구-필드-검증의 추적성을 유지한다.
