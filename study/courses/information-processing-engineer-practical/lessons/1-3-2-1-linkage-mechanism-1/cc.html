01

수행 범위와 목표

이 레슨의 정확한 수행 범위는 모듈 특성을 고려한 데이터 송수신 방법 정의와 연계 요구사항을 고려한 연계주기 정의이다. 승인된 연계 데이터 계약을 입력으로 받아 동기 호출, 비동기 메시지, 파일 배치, 변경분 전달 등 송수신 방식을 모듈의 결합도·처리량·가용성에 맞게 선택하고, 실시간·준실시간·주기 배치·요청 시 실행의 주기를 업무 마감과 수용 능력에 맞게 산정한다. 구체적인 실패 처리와 송수신 보안은 다음 레슨에서 다룬다.

학습 후에는 다음을 수행할 수 있어야 한다.

  • 요청-응답, 메시지, 파일·배치, 변경분 연계의 장단점을 비교한다.
  • 송신·수신의 가용성, 응답 필요성, 순서, 양과 크기로 방식을 선택한다.
  • 실시간, 이벤트, 미니 배치, 정기 배치와 온디맨드 주기를 구분한다.
  • 피크 발생량, 처리율, 허용 지연과 작업 겹침으로 주기를 계산한다.
  • 인터페이스 메커니즘 정의서, 흐름도, 주기표와 운영 체크리스트를 만든다.
02

1. 연계 메커니즘의 구성

연계 메커니즘은 송신 모듈에서 데이터가 생성된 뒤 수신 모듈의 업무 상태로 반영될 때까지의 기술·운영 흐름이다.

[업무 사건] │ ▼ 송신 추출·생성 │ ▼ 데이터 계약에 맞춘 변환 │ ▼ 전송 채널·중계 ───── 전달 상태·추적 │ ▼ 수신 검증·변환 │ ▼ 업무 반영·결과

이 레슨에서는 전송 채널과 실행 시점을 정의한다. 데이터 계약의 필드·버전은 앞 레슨의 결과를 사용한다.

03

2. 모듈 특성 분석

모듈 특성을 고려한 데이터 송수신 방법 정의에 앞서 다음 특성을 표로 정리한다.

2. 모듈 특성 분석 · 학습 표 1
특성확인 질문
응답 필요송신 업무가 수신 결과를 즉시 알아야 하는가
가용성 독립수신 중단 중에도 송신 업무가 계속되어야 하는가
처리량평균·피크 사건 수와 데이터 크기는 얼마인가
지연몇 초·분·시간 안에 반영되어야 하는가
순서같은 업무 키의 변경 순서를 지켜야 하는가
거래 경계송신·수신을 하나의 원자 작업으로 묶어야 하는가
데이터 형태단건 요청, 사건 스트림, 대용량 집합 중 무엇인가
변경 감지사건 발생, 수정 시각, 순번, 전체 비교 중 무엇이 가능한가
연결성항상 연결, 간헐 연결, 방화벽·망분리 제약이 있는가
수신 능력동시 요청·배치 크기와 처리 가능한 속도는 얼마인가
운영 역량메시지·스케줄·파일·API를 감시할 인력과 도구가 있는가

“실시간이 가장 좋은 방식”이라는 가정을 버린다. 즉시성이 필요하지 않은 대량 분석 데이터를 단건 API로 보내면 양쪽의 부하와 장애 결합이 커질 수 있다.

04

3. 동기 요청-응답

송신 모듈이 요청을 보내고 수신의 결과를 기다린다.

적합

  • 결과에 따라 현재 업무 흐름을 즉시 결정해야 함
  • 요청 단위가 비교적 작고 응답 시간이 예측 가능함
  • 수신 모듈의 가용성이 업무 요구를 만족함
  • 호출자와 수신자 사이 계약이 명확함

장점

  • 흐름과 결과를 이해하기 쉬움
  • 즉시 성공·업무 거절을 받을 수 있음
  • 단건 조회·검증·승인에 자연스러움

위험

  • 수신 지연·장애가 송신 스레드와 사용자 응답으로 전파
  • 연쇄 호출에서 시간 초과가 누적
  • 재호출 시 이전 요청 처리 여부가 불명확할 수 있음
  • 피크 동시 요청이 수신 모듈을 압박

시간 초과는 “수신이 처리하지 않았다”는 증거가 아니다. 응답만 잃고 업무 반영은 끝났을 수 있으므로 요청 ID와 결과 조회·멱등 요구가 필요하다. 구체 실패 전략은 다음 레슨에서 설계한다.

05

4. 비동기 메시지

송신 모듈이 메시지를 중간 전달 계층에 기록하고 수신 모듈이 자신의 속도로 처리한다.

적합

  • 송신과 수신 가용성을 분리해야 함
  • 사건을 여러 소비자가 받을 수 있음
  • 순간 피크를 대기열로 완충해야 함
  • 즉시 응답보다 최종 반영이 중요함

장점

  • 시간적 결합도 감소
  • 피크 흡수와 독립 확장
  • 사건 구독자를 추가하기 쉬울 수 있음

위험

  • 중복 전달, 순서 역전과 지연
  • 대기열 적체와 오래된 메시지
  • 생산자·중계·소비자 세 구간 추적 필요
  • 최종 일관성과 업무 결과 확인 복잡

메시징 제품이 전달을 보장해도 수신 DB 반영과 확인 사이 장애에서 중복이 생길 수 있다. 이벤트 ID와 업무 키를 이용한 멱등 소비가 필요하다.

06

5. 파일·배치 연계

정해진 시간이나 조건에 데이터를 파일·집합으로 만들어 전달하고 수신이 일괄 처리한다.

적합

  • 대량 데이터와 마감 집계
  • 건별 즉시성이 필요하지 않음
  • 망분리·외부 기관의 정해진 파일 규격
  • 초기 전체분이나 일 단위 변경분

설계 항목

  • 파일명과 실행 ID, 생성 완료 표시
  • 헤더·본문·트레일러와 건수·합계
  • 문자 인코딩, 구분자·고정 길이, 압축
  • 전체분·변경분과 기준 시점
  • 분할 크기와 결합 순서
  • 중복 파일·재전송 식별

파일을 쓰는 동안 수신이 읽지 않도록 임시 이름 또는 완료 표식을 사용한다. 상세 실패·보안 조치는 다음 단계에서 정한다.

07

6. 변경분·데이터 기반 연계

변경 로그, 변경 순번, 수정 시각 또는 원천 비교로 달라진 데이터를 찾아 전달한다.

  • 로그·사건 기반: 업무 변경이 일어난 순서를 파악하기 좋지만 원천 지원과 운영이 필요
  • 수정 시각 기반: 단순하지만 동일 시각 경계, 지연 입력과 삭제 감지에 주의
  • 순번 기반: 단조 증가하는 변경 번호가 신뢰성 있게 부여되어야 함
  • 스냅샷 비교: 삭제·변경을 찾을 수 있지만 데이터가 크면 비교 비용 증가

수정 시각이 마지막 시각보다 큰 행만 추출하면 같은 시각에 늦게 커밋된 행을 놓칠 수 있다. 범위를 겹쳐 읽고 이벤트·업무 키로 중복을 제거하는 등의 요구를 검토한다.

08

7. 직접·간접 연계와 토폴로지

7.1 직접 연계

송신과 수신이 API, 파일 또는 DB 연결 등으로 직접 통신한다. 소수 인터페이스에는 단순하지만 시스템 수가 늘면 연결과 변환이 N:M으로 증가할 수 있다.

7.2 중계·허브 연계

통합 계층이 라우팅, 형식 변환, 대기열과 감시를 제공한다. 공통 통제가 가능하지만 중계 계층의 용량·가용성·변경 책임이 중요하다. 모든 업무 로직을 중계에 넣으면 책임 경계가 모호해질 수 있다.

7.3 공유 데이터베이스

여러 모듈이 같은 테이블을 직접 읽고 쓰면 구현은 빠를 수 있으나 스키마·트랜잭션 결합, 권한 확대와 변경 영향이 커진다. 읽기 전용 공유도 소유자, 시점과 성능 영향을 계약으로 관리한다.

8. 송수신 방식 선택표

8. 송수신 방식 선택표 · 학습 표 2
요구우선 검토 방식확인할 위험
즉시 승인 결과가 현재 업무에 필요동기 요청-응답시간 초과, 연쇄 장애
순간 피크와 수신 중단을 흡수비동기 메시지적체, 중복·순서
하루 수백만 건 마감 전 반영파일·배치처리 창, 부분 실패·재시작
지속 변경 사건을 여러 소비자에게 배포이벤트·메시지계약 진화, 소비자 지연
간헐 연결 지점의 정기 수집파일 또는 누적 메시지중복, 기준 시점, 보관
소수 내부 모듈의 단건 조회직접 API결합도, 호출 폭증

혼합도 가능하다. 주문 승인 결과는 동기, 승인 완료 사건은 비동기로 분석·배송에 배포할 수 있다. 단, 같은 업무 사실의 권위 원천과 중복 반영 책임을 분명히 한다.

10

9. 연계주기 유형

연계 요구사항을 고려한 연계주기 정의는 “매 5분” 같은 숫자를 임의 선택하는 작업이 아니다.

9.1 실시간·동기

업무 요청과 같은 흐름에서 즉시 수행한다. 즉시 결과가 필요하지만 수신 장애와 지연이 사용자 업무에 전달된다.

9.2 사건 기반 비동기

업무 사건이 발생할 때 메시지를 생성하고 수신이 가능한 즉시 처리한다. 개별 지연은 작을 수 있지만 적체 시 지연이 늘어난다.

9.3 준실시간·미니 배치

짧은 간격으로 변경분을 모아 처리한다. 단건 오버헤드를 줄이면서 허용 지연 안에 반영할 수 있다.

9.4 정기 배치

시간·일·월 마감 등 정해진 시점에 집합을 처리한다. 대량 처리에 적합하지만 처리 창, 마감 의존과 실패 시 재실행 시간을 고려한다.

9.5 온디맨드

사용자·운영자 요청이나 특정 조건에 따라 실행한다. 기준 시점, 중복 실행과 권한을 정의한다.

11

10. 주기 산정

10.1 업무 허용 지연

재고 예약은 수초, 분석 통계는 수시간처럼 업무마다 다르다. 가장 엄격한 소비자 하나 때문에 모든 소비자를 같은 실시간 방식으로 묶기보다 별도 흐름을 검토한다.

10.2 발생량과 처리율

주기 동안 쌓이는 건수의 단순 근사:

적체 예상 건수 = 피크 발생률 × 주기

작업 완료 조건:

배치 처리 시간 + 준비·검증·여유 시간 < 다음 실행 간격

발생률이 초당 100건이고 10분마다 처리하면 최대 약 60,000건이 쌓일 수 있다. 이는 균등 발생의 근사이므로 실제 피크·데이터 크기와 재처리 여유를 시험한다.

10.3 수신 수용 능력

송신이 빠르게 보낼 수 있어도 수신 DB와 후속 업무가 감당하지 못하면 적체와 실패가 늘어난다. 최대 동시 요청, 배치 크기와 업무 잠금 영향을 합의한다.

10.4 마감과 의존성

일 마감 파일은 원천 거래가 확정된 뒤 생성하고 수신 집계 전에 끝나야 한다. 선행·후행 작업, 시간대, 휴일과 일광 절약 시간, 지연 데이터의 컷오프를 정의한다.

10.5 겹침 정책

이전 실행이 끝나기 전에 다음 주기가 오면 동시 실행, 건너뜀, 대기 중 어느 정책을 쓸지 정한다. 같은 변경분을 동시에 처리하지 않도록 실행 ID와 구간 소유를 관리한다.

10.6 장애 후 따라잡기

정상 처리율이 발생률과 같으면 장애 후 적체를 줄일 여유가 없다. 따라잡기 용량, 우선순위, 오래된 데이터의 업무 유효성과 최대 복구 시간을 주기 설계에 포함한다.

12

11. 주기 정의 절차

  1. 소비 업무별 허용 지연과 마감 확인
  2. 평균·피크 발생률과 메시지·파일 크기 측정
  3. 수신 처리율과 동시성·잠금 영향 확인
  4. 송수신 방식별 준비·전송·반영 시간을 측정
  5. 선행·후행 배치와 운영 작업 창 배치
  6. 실시간·이벤트·미니 배치·정기·온디맨드 후보 비교
  7. 적체·겹침·장애 후 따라잡기 시뮬레이션
  8. 주기, 컷오프, 시간대, 최대 실행 시간과 우선순위 확정
  9. 대표 부하로 시험하고 지연·적체 임계값 보정
  10. 승인·운영 인계와 정기 재산정

데이터 증가와 소비자 추가로 처리 시간이 변하므로 주기는 고정 숫자가 아니라 감시·재평가 대상이다.

12. 구체 업무 시나리오

요구

  • 온라인 주문 확정 후 재고 예약은 10초 안에 반영되어야 한다.
  • 분석 플랫폼은 주문을 15분 안에 받으면 된다.
  • 회계 시스템은 영업일 마감 후 확정 거래 전체를 받는다.

방식·주기 정의

12. 구체 업무 시나리오 · 학습 표 3
흐름방식주기판단
주문→재고이벤트 메시지사건 발생 시송신과 수신 가용성 분리, 짧은 지연
주문→분석미니 배치 또는 사건 집계5분 후보단건 부하보다 15분 허용 지연 활용

검토:

  1. 재고 소비 속도가 피크 주문률을 넘고 장애 후 따라잡을 여유가 있는지 시험한다.
  2. 분석 5분 작업이 5분을 넘어 겹치지 않는지 본다.
  3. 회계 파일은 마감 확정 전 변경과 늦은 거래의 처리 기준을 정한다.
  4. 세 흐름이 같은 eventId·orderNo와 표준 코드를 사용해 추적되게 한다.
  5. 각 흐름의 실패·재전달·보안 정책은 다음 설계에서 구체화한다.

14. 실기 함정

  1. 실시간을 무조건 최상으로 선택: 결합도·비용과 업무 허용 지연을 본다.
  2. 동기 시간 초과를 미처리로 판단: 수신 반영 후 응답만 유실될 수 있다.
  3. 메시지 큐가 중복을 없앤다고 생각: 소비 반영·확인 사이 장애에서 중복될 수 있다.
  4. 파일 생성 종료와 수신 가능 시점을 구분하지 않음: 완료 표식이 필요하다.
  5. 수정 시각만으로 변경분을 완벽히 식별: 동일 시각·지연 입력·삭제를 고려한다.
  6. 평균 발생률로 주기 산정: 피크와 데이터 크기, 따라잡기 용량을 본다.
  7. 주기와 최대 실행 시간이 같아도 괜찮다고 판단: 지연과 장애 여유가 없어 겹침이 누적된다.
  8. 송신 처리율만 측정: 수신 DB와 후속 업무의 수용 능력이 병목일 수 있다.
  9. 공유 DB가 가장 단순하므로 항상 적합: 스키마·권한·트랜잭션 결합이 커진다.
  10. 시간대·휴일 없는 cron 숫자만 기록: 업무 마감과 컷오프 의미를 명시한다.

16. 정답과 해설

정답 1

동기는 수신 응답을 기다려 수신 지연·장애가 송신 업무에 직접 전파된다. 비동기는 중간 전달 계층에 기록하고 수신이 자기 속도로 처리해 시간적 가용성 결합을 줄이지만 최종 결과 확인이 복잡하다.

정답 2

중복 전달, 순서 역전, 지연·적체, 생산-중계-소비 구간 추적, 최종 일관성, 소비자 장애 중 네 가지다.

정답 3

대량·마감 집계, 낮은 즉시성, 망분리·기관 규격에 적합하다. 파일명·실행 ID, 헤더·트레일러 건수, 인코딩·형식, 기준 시점, 분할·재전송 식별을 설계한다.

정답 4

마지막 시각과 같은 값의 늦은 커밋을 놓치거나 시간대·정밀도 차이로 범위가 겹칠 수 있고, 물리 삭제는 수정 시각으로 찾지 못할 수 있다.

정답 5

실시간은 현재 호출과 함께, 사건 기반은 사건 때 비동기로, 미니 배치는 짧은 간격으로 모아, 정기 배치는 마감·정해진 시각에, 온디맨드는 요청·조건 발생 시 수행한다.

정답 6

업무 허용 지연, 평균·피크 발생률, 데이터 크기, 수신 처리율, 준비·전송·반영 시간, 선후행 작업, 마감·시간대, 장애 여유 중 다섯 가지다.

정답 7

동시 실행, 이전 작업 완료까지 대기, 새 실행 건너뛰기 정책이다. 데이터 구간과 실행 ID의 소유도 명확히 한다.

정답 8

정상 처리율이 발생률과 같으면 장애 중 쌓인 데이터를 영원히 줄일 수 없기 때문이다. 평상시 여유 처리율이나 별도 확장·우선순위가 필요하다.

정답 9

소비 업무의 허용 지연, 응답 필요, 데이터 양과 마감이 다르기 때문이다. 재고는 짧은 지연, 분석은 미니 배치, 회계는 확정 대량 파일이 적합할 수 있다.

18

핵심 요약

  • 모듈 특성을 고려한 데이터 송수신 방법 정의는 응답 필요, 가용성 결합, 처리량, 순서, 데이터 형태와 운영 역량으로 동기·메시지·파일·변경분 방식을 선택한다.
  • 동기는 즉시 결과에, 비동기는 시간적 결합 완화와 피크 흡수에, 파일은 대량·마감 처리에 적합할 수 있다.
  • 전달 도구가 중복·순서·업무 반영을 자동 보장한다고 가정하지 않고 계약 식별자와 멱등 요구를 남긴다.
  • 연계 요구사항을 고려한 연계주기 정의는 업무 허용 지연, 피크 발생률, 수신 처리율, 마감과 장애 후 따라잡기로 산정한다.
  • 작업 시간은 다음 간격보다 충분히 작아야 하며 실행 겹침, 컷오프·시간대와 지연 데이터를 정의한다.
  • 방식과 주기는 한 번 정한 제품 설정이 아니라 실제 적체·지연·성장 지표로 계속 재산정하는 운영 계약이다.
