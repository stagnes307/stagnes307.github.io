01

수행 범위와 목표

이 레슨의 정확한 수행 범위는 연계 실패 처리방안 정의와 송수신 보안 적용이다. 송신 생성부터 수신 업무 반영까지 발생할 수 있는 기술·업무 실패를 분류하고 재시도, 멱등, 격리, 보상, 대사와 수동 복구를 설계한다. 이어서 신원 확인, 최소 권한, 전송·메시지 보호, 재전송 공격 방지, 비밀·키·로그 통제를 연계 경계에 적용한다. 실제 연계 모듈 코딩과 종합 테스트 명세는 다음 레슨의 주범위다.

학습 후에는 다음을 수행할 수 있어야 한다.

  • 송신·전송·중계·수신·업무 단계의 실패를 분류한다.
  • 일시 오류와 영구 오류를 구분해 재시도·격리·수동 조치를 선택한다.
  • 이벤트 ID, 업무 키와 처리 이력으로 멱등 소비를 구현한다.
  • 응답 유실과 부분 반영에서 상태 조회·보상·대사를 설계한다.
  • 기밀성·무결성·인증·권한·재전송 방지와 감사 요구를 적용한다.
02

1. 실패는 한 지점이 아니라 상태 전이에서 발생한다

업무 사건 생성 │ ▼ 송신 데이터 생성 ── 실패 A │ ▼ 중계·전송 저장 ─── 실패 B │ ▼ 수신·형식 검증 ─── 실패 C │ ▼ 업무 반영 ─────── 실패 D │ ▼ 결과·확인 반환 ─── 실패 E

실패 E에서 송신은 시간 초과를 보지만 수신 업무는 이미 완료되었을 수 있다. 단순 재호출은 주문·결제·재고를 중복 반영할 수 있다. 따라서 전송 성공, 수신 접수, 업무 성공을 서로 다른 상태로 기록한다.

2.1 일시 오류와 영구 오류

  • 일시 오류: 짧은 네트워크 단절, 잠금 경합, 일시 자원 부족처럼 같은 요청을 나중에 수행하면 성공할 가능성이 있음
  • 영구 오류: 필수 필드 누락, 알려지지 않은 코드, 계약 버전 불일치처럼 입력이나 규칙을 고치기 전에는 반복해도 실패

모든 오류를 같은 주기로 무한 재시도하면 영구 오류가 큐와 로그를 채우고 정상 처리를 방해한다.

2.2 기술 실패와 업무 거절

수신 서비스가 정상 실행되어 “재고 부족”을 반환했다면 기술 장애가 아니라 업무 결과다. 기술 재시도로 재고 예약을 반복하기보다 상위 업무가 대체·취소·대기 결정을 해야 한다.

연계 계약에는 데이터뿐 아니라 처리 상태의 의미를 포함한다.

실제 상태명은 시스템에 맞게 정하되 서로 배타적인지, 최종 상태인지와 전이 책임을 명시한다.

05

4. 재시도 설계

4.1 재시도 조건

  • 오류 코드가 일시 오류로 분류됨
  • 동일 요청을 다시 처리해도 업무가 중복되지 않음
  • 전체 허용 지연과 만료 시간 안임
  • 수신 보호를 위한 속도·동시성 제한을 지킴

4.2 간격과 횟수

즉시 반복은 장애 난 수신에 더 큰 부하를 준다. 시도할수록 간격을 늘리고 약간의 무작위 분산을 더하면 여러 송신자의 동시 재시도 폭증을 줄일 수 있다. 최대 횟수·전체 시간과 최종 격리 상태를 정의한다. 숫자는 업무 SLA와 복구 시간으로 결정하며 보편 상수로 만들지 않는다.

4.3 재시도 의사코드

process(message): if alreadysucceeded(message.eventId): return storedresult

result = applybusinesschange(message)

if result.success: record_success(message.eventId, result) return result

if result.transient and withinretrywindow: scheduleretry(withbackoffandlimit) else: quarantine(message, result.reason)

DB 반영과 성공 기록 사이가 원자적이지 않으면 반영 후 기록 실패가 생길 수 있다. 가능한 경우 한 로컬 트랜잭션에 묶거나 inbox 같은 처리 기록과 업무 변경을 함께 저장한다.

06

5. 멱등성과 중복 통제

멱등은 같은 업무 요청을 여러 번 적용해도 최종 업무 상태가 한 번 적용한 것과 같도록 하는 성질이다. “전송이 정확히 한 번”이라는 기대만으로 구현하지 않는다. 네트워크와 프로세스 장애에서는 재전달이 발생할 수 있다.

5.1 멱등 키

  • 이벤트 ID: 같은 사건의 재전달 식별
  • 업무 키 + 명령 유형: 특정 주문의 취소 등
  • 업무 버전: 같은 대상 변경 순서와 중복 식별

키의 보존 기간이 재전달 가능 기간보다 짧으면 오래된 중복을 다시 처리할 수 있다.

5.2 inbox

수신이 처리한 메시지 ID와 결과를 저장한다. 업무 변경과 inbox 기록을 한 로컬 트랜잭션으로 반영하면 중복 판단의 공백을 줄인다.

5.3 outbox

업무 DB 변경과 발행할 사건을 같은 로컬 트랜잭션에 기록하고 별도 전달자가 outbox를 전송한다. “업무 커밋은 성공했지만 메시지 발행은 실패”하는 이중 쓰기 공백을 줄인다.

5.4 조건부 상태 전이

“주문 상태가 PAID이고 버전이 3일 때만 SHIPPED 버전 4로 변경”처럼 현재 상태·버전을 조건에 포함한다. 오래된 메시지가 최신 상태를 덮어쓰는 것을 막는다.

07

6. 격리와 재처리

자동 처리할 수 없는 메시지는 별도 격리 영역에 보관한다.

필수 정보:

  • 원본 메시지 식별자와 안전한 참조
  • 업무 키·버전과 발생·수신 시각
  • 실패 단계·오류 코드·원인
  • 시도 횟수와 마지막 시각
  • 계약·프로그램 버전
  • 담당자, 처리 상태와 승인
  • 수정·재처리 실행 ID와 결과

민감 원문을 오류 로그에 그대로 복제하지 않는다. 격리 저장소의 접근과 보존도 업무 데이터 수준으로 통제한다.

재처리 전에 원인을 고치고 이전 반영 여부와 현재 업무 상태를 다시 확인한다. 오래된 메시지가 더 최신 변경 뒤에 적용되지 않도록 버전을 검증한다.

08

7. 보상과 대사

분산된 여러 시스템을 하나의 DB 트랜잭션처럼 되돌리기 어려울 수 있다.

7.1 보상

이미 완료된 업무의 의미를 반대로 만드는 별도 업무 행위다. 결제 승인 후 재고 예약이 불가능하면 결제 취소 요청을 보낼 수 있다. 보상은 기술적 rollback과 다르며 보상 자체도 실패·중복될 수 있다.

7.2 대사

송신 사건, 중계 접수, 수신 처리와 업무 최종 상태를 정기적으로 비교해 누락·중복·불일치를 찾는다.

송신 완료 집합

  • 수신 성공 집합
    = 누락·대기·실패 후보

건수만 같아도 서로 다른 사건이 누락·과다로 상쇄될 수 있으므로 이벤트·업무 키 집합과 중요 합계를 비교한다.

09

8. 감시와 경보

관찰 항목:

  • 성공·재시도·거절·격리 건수
  • 가장 오래된 대기 메시지의 나이
  • 대기열 깊이와 증가 속도
  • 처리 지연의 중앙·상위 값
  • 중복 감지와 순서 역전 건수
  • 인증·권한 실패와 비정상 호출
  • 대사 불일치와 수동 미처리 기간

모든 일시 실패를 알리면 경보 피로가 생긴다. 업무 영향·지속 시간·증가 속도로 계층화한다.

10

9. 송수신 보안의 목표

송수신 보안 적용은 다음 목표를 연계 전체 경로에 적용한다.

  • 기밀성: 권한 없는 주체가 내용을 읽지 못함
  • 무결성: 전송 중 변경을 탐지
  • 인증: 통신 상대와 메시지 출처를 확인
  • 인가: 인증된 주체도 허용된 인터페이스·데이터만 사용
  • 가용성: 과도한 요청과 장애가 서비스 전체를 마비시키지 않게 함
  • 감사·추적: 누가 언제 무엇을 요청·변경했는지 책임 있게 확인

암호화만 적용했다고 송수신 보안이 완성되지 않는다. 잘못된 상대에게 암호화해 보내거나 과도한 권한을 주면 목적을 달성하지 못한다.

11

10. 신원과 권한

10.1 시스템·서비스 인증

사용자 개인뿐 아니라 송신 서비스, 중계와 수신 서비스의 신원을 확인한다. 공유 비밀 하나를 여러 연계에서 재사용하면 유출 시 영향과 책임 추적이 커진다.

10.2 최소 권한

  • 인터페이스·업무 기능별 호출 권한
  • 필요한 데이터 범위만 읽기·쓰기
  • 운영·시험 환경 자격증명 분리
  • 관리·재처리 권한과 일반 처리 권한 분리
  • 정기 권한 검토와 종료 시스템 회수

10.3 비밀·키·인증서 관리

소스 코드, 설정 저장소, 메시지와 로그에 비밀을 평문으로 넣지 않는다. 안전한 보관소에서 필요한 실행 시점에 제공하고 접근 감사, 교체, 만료 감시와 비상 폐기를 마련한다.

12

11. 전송·메시지 보호

11.1 전송 구간 보호

통신 채널의 기밀성과 무결성을 보호하고 상대를 인증한다. 중계에서 암호가 종료된다면 이후 내부 구간과 중계 저장 데이터의 보호 책임을 별도로 확인한다.

11.2 메시지 수준 보호

메시지 자체의 암호화·서명 또는 무결성 검증은 여러 중계·저장을 거쳐도 보호를 유지하는 데 도움을 줄 수 있다. 어떤 필드를 보호하고 어느 구성요소가 복호·검증하는지, 키 교체와 성능을 설계한다.

단순 해시만으로는 비밀 키나 신뢰된 서명이 없을 때 공격자가 내용과 해시를 함께 바꿀 수 있다. 전송 오류 탐지와 공격자 변조 방지를 구분한다.

11.3 파일 연계

  • 파일 내용 암호화 또는 보호된 전송
  • 송신자·파일 무결성 확인
  • 임시·오류·백업 파일의 동일 보호
  • 안전한 파일명과 경로, 최소 권한
  • 완료 파일만 처리하고 처리 후 보존·폐기

파일이 안전한 전송 채널을 지났어도 수신 디스크와 백업에 평문으로 남을 수 있다.

13

12. 재전송 공격과 입력 보호

공격자가 유효한 요청을 복사해 다시 보내는 것을 막으려면 다음을 조합한다.

  • 메시지·요청 고유 ID
  • 생성 시각과 허용 시간 창
  • 한 번 사용하는 난수 값
  • 업무 버전과 처리 이력
  • 메시지 출처·무결성 검증

시각만 사용하면 시계 차이와 같은 시간의 여러 요청 문제가 있다. ID와 처리 이력을 함께 사용한다. 보안 재전송 방지와 업무 멱등은 목적이 겹치지만, 하나가 다른 하나를 완전히 대신하지 않는다.

입력은 계약 스키마, 길이·범위·반복 수와 코드로 검증해 과도한 자원 사용과 주입을 줄인다. 상세 보안 코딩은 별도 범위지만 연계 경계에서 수신 값을 신뢰하지 않는 원칙이 중요하다.

14

13. 로그와 개인정보

로그에는 추적 ID, 인터페이스·단계·상태, 안전한 호출 주체, 시각·지연, 오류와 버전을 남긴다. 토큰·키, 민감정보와 무제한 원문은 제외하고 제어 문자를 안전하게 처리한다. 원문이 필요하면 보호된 참조를 사용하며 로그 접근·무결성·보존도 통제한다.

15

14. 적용 절차

  1. 실패 지점·상태 모델링: 송신부터 수신 업무 결과까지 단계와 책임을 정의한다.
  2. 오류 분류표 작성: 일시·영구·업무 거절, 코드와 다음 행동을 정한다.
  3. 멱등·순서 설계: 이벤트 ID, 업무 키·버전과 처리 이력을 설계한다.
  4. 재시도·격리 설계: 간격, 한도, 만료, 격리·수동 승인과 재처리를 정한다.
  5. 부분 성공 처리: 상태 조회, 보상, 대사와 최종 책임을 정한다.
  6. 자산·위협 분석: 데이터 민감도, 호출 주체, 중계·저장·관리 경계를 식별한다.
  7. 인증·인가 설계: 서비스 신원, 최소 권한과 자격증명 수명주기를 정한다.
  8. 전송·메시지 보호 적용: 구간·저장·파일과 무결성 보호 범위를 정한다.
  9. 재전송·입력·로그 통제: 고유 ID·시간, 계약 검증과 민감 로그 제한을 적용한다.
  10. 장애·보안 시나리오 검토: 응답 유실, 중복, 순서 역전, 키 만료·교체와 권한 오류를 확인한다.
  11. 운영 인계: 지표·경보, 격리 처리, 비상 권한, 대사와 키·인증서 책임을 인계한다.
16

15. 구체 업무 시나리오

주문 확정 → 재고 예약

  1. 주문 시스템은 업무 변경과 outbox 사건을 한 트랜잭션에 기록한다.
  2. 전달자는 eventId를 유지해 메시지를 발행한다.
  3. 재고 시스템은 eventId 처리 이력을 먼저 확인한다.
  4. 미처리 사건이면 주문번호·버전과 현재 상태를 검증하고 예약과 inbox 성공 기록을 한 트랜잭션에 반영한다.
  5. 잠금 시간 초과는 제한 재시도, 알 수 없는 상품 코드는 영구 오류로 격리한다.
  6. 응답이 유실되어도 같은 eventId 재전달은 기존 결과를 반환한다.
  7. 주문과 재고의 성공 집합을 주기적으로 대사한다.
  8. 서비스 상호 인증과 최소 호출 권한을 적용하고 전송·저장 구간을 보호한다.
  9. 로그에는 eventId와 상태만 남기고 고객 개인정보와 자격증명을 제외한다.

보안 공격으로 같은 유효 메시지가 재전송되어도 출처·시간·ID와 처리 이력을 검증하고 업무 멱등으로 중복 예약을 막는다.

17. 실기 함정

  1. 시간 초과를 미처리로 판단: 수신 반영 후 응답만 유실될 수 있다.
  2. 모든 오류를 무한 재시도: 영구 오류가 정상 처리를 방해한다.
  3. 전송 제품의 exactly-once 표현만 믿고 멱등 생략: 업무 DB 반영 경계에서 중복될 수 있다.
  4. 새 이벤트 ID로 재시도: 같은 사건의 중복 판별이 어려워진다.
  5. 중복 테이블 기록과 업무 반영을 별도 커밋: 사이 장애에서 공백이 생긴다.
  6. 격리 후 운영 책임 없음: 원인·승인·재처리·보존을 관리해야 한다.
  7. 보상을 DB rollback과 동일시: 이미 완료된 분산 업무를 반대 의미의 새 업무로 처리한다.
  8. 암호화만 하면 인증·권한도 충족: 상대 신원과 최소 권한은 별도다.
  9. TLS 종료 뒤 내부·저장 구간을 자동 신뢰: 중계와 디스크 보호를 별도 확인한다.
  10. 로그에 원문·토큰을 남겨야 추적 가능: 안전한 ID와 보호된 참조를 사용한다.

19. 정답과 해설

정답 1

요청이 수신 업무에 반영된 뒤 응답만 유실될 수 있기 때문이다. 송신이 시간 초과만 보고 재시도하면 중복 반영이 생길 수 있어 상태 조회와 멱등이 필요하다.

정답 2

일시 오류는 네트워크 단절, 잠금 경합, 일시 자원 부족이다. 영구 오류는 필수 필드 누락, 미등록 코드, 계약 버전 불일치 등이다.

정답 3

동일 업무 사건의 모든 재전달에서 같은 키를 사용하고, 재전달·감사 가능 기간보다 처리 이력 보존이 길어야 한다. 무관한 다른 사건과 충돌하지 않아야 한다.

정답 4

inbox는 수신 업무 반영과 처리 완료 기록 사이의 공백을 줄이고, outbox는 송신 업무 커밋과 사건 발행 사이의 공백을 줄인다.

정답 5

대상 오류 분류, 최대 횟수, 증가 간격·분산, 전체 시간·만료, 동시성 제한, 최종 격리와 경보, 멱등 조건 중 다섯 가지다.

정답 6

기술 실패는 시스템이 요청을 정상 처리하지 못한 상태이고 재시도로 회복될 수 있다. 업무 거절은 시스템은 정상 동작했지만 재고 부족처럼 업무 규칙상 받아들이지 않은 결과다.

정답 7

기밀성, 무결성, 인증, 인가, 가용성, 감사·추적이다.

정답 8

구간 보호는 특정 연결의 양 끝 사이를 보호하며 중계에서 종료될 수 있다. 메시지 수준 보호는 저장·여러 중계를 지나도 내용·출처 보호를 유지할 수 있으나 키·검증 책임이 복잡하다.

정답 9

보안 통제는 유효 요청의 악의적 재전송을 탐지하고, 업무 멱등은 장애·재시도까지 포함한 중복 반영을 막는다. 한 통제의 경계가 다른 실패를 모두 포함하지 않는다.

정답 10

서로 다른 사건의 누락과 과다 처리가 상쇄되어 건수가 같을 수 있기 때문이다. 이벤트·업무 키 집합, 상태와 중요 합계를 비교한다.

21

핵심 요약

  • 연계 실패 처리방안 정의는 송신·전송·수신·업무·응답 상태를 분리하고 일시·영구·업무 거절에 서로 다른 행동을 연결한다.
  • 재시도는 한도·간격·만료가 필요하며 eventId, 업무 키·버전, inbox/outbox와 조건부 전이로 멱등성과 순서를 통제한다.
  • 자동 처리 불가 자료는 격리하고 원인·승인·재처리를 추적하며, 분산 부분 성공은 보상과 키 기반 대사로 관리한다.
  • 송수신 보안 적용은 기밀성·무결성·인증·인가·가용성·감사를 전송, 중계, 저장과 관리 경로 전체에 적용한다.
  • 서비스 신원과 최소 권한, 비밀·키 수명주기, 구간·메시지 보호, 재전송 방지와 민감 로그 제한이 필요하다.
  • 실패·보안 설계는 코드 옵션이 아니라 상태 계약, 운영 지표, 책임과 복구 절차를 포함한 연계 메커니즘이다.
