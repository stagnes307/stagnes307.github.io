01

수행 범위와 목표

이 레슨의 정확한 수행 범위는 연계모듈 구현을 위한 논리·물리 환경 준비와 외부 시스템 연계 모듈 구현이다. 승인된 데이터 계약·송수신 방식·주기·실패·보안 설계를 실행 가능한 환경, 구성과 코드 구조로 구현한다. 다음 레슨에서 작동·무결성과 테스트 케이스를 본격 검증하므로 여기서는 재현 가능한 환경 준비, 경계 어댑터, 변환·검증·멱등·상태 기록과 관측 코드의 완성에 집중한다.

학습 후에는 다음을 수행할 수 있어야 한다.

  • 개발·시험·운영의 논리 구성과 물리 자원·연결·권한을 구분해 준비한다.
  • 인터페이스 계약, 스키마, 코드·인증 자료와 모의 외부 시스템을 기준선으로 만든다.
  • 송신자·수신자·어댑터·변환기·상태 저장소의 책임을 분리한다.
  • API, 메시지, 파일 방식의 외부 연계 모듈을 안전한 의사코드로 구현한다.
  • 구성 외부화, 비밀 보호, 로그·지표·추적과 배포·복구 절차를 산출한다.
02

1. 연계모듈 구현의 입력

구현 전에 다음 승인 산출물이 있어야 한다.

  • 연계 요구사항과 업무 정상·예외 시나리오
  • 논리 데이터 모델, 스키마·파일 레이아웃과 버전
  • 원천-표준-수신 매핑·코드·단위 규칙
  • 송수신 방식, 주기, 컷오프와 용량
  • 실패 분류, 재시도·멱등·격리·대사 정책
  • 인증·인가, 전송·저장 보호와 비밀 정책
  • 인수 기준, 운영 담당과 변경 절차

불명확한 코드·null 의미는 추정하지 말고 계약 이슈로 돌린다.

03

2. 논리 환경과 물리 환경

2.1 논리 환경

소프트웨어가 동작하기 위한 역할과 구성의 논리적 배치다.

  • 송신 추출·사건 생성 구성요소
  • 스키마 검증과 변환기
  • API 클라이언트·서버, 메시지 생산자·소비자, 파일 처리기
  • 멱등·상태·격리 저장소
  • 스케줄러 또는 사건 트리거
  • 인증·권한과 비밀 참조
  • 로그·지표·추적과 경보 연계
  • 외부 시스템 모의체·스텁

2.2 물리 환경

논리 구성요소가 실제로 실행·연결되는 자원이다.

  • 서버, 가상머신, 컨테이너 또는 실행 노드
  • 운영체제·런타임·필수 라이브러리
  • 네트워크 주소, 이름 해석, 방화벽과 프록시
  • 메시지 브로커, 파일 경로, 데이터베이스와 저장 용량
  • 인증서·비밀 보관소와 시간 동기화
  • CPU·메모리·디스크·네트워크 용량과 이중화
  • 배포 파이프라인, 감시·백업·복구 자원

논리적으로 큐가 이중화되어도 두 노드가 같은 물리 전원·저장장치에 의존하면 장애 영역은 하나일 수 있다.

  • 설치·시작·중지·복구 순서

4. 환경 준비 절차

  1. 구현 범위·의존성 확정: 인터페이스별 계약·방식과 외부 구성요소를 목록화한다.
  2. 논리 배치 설계: 송수신, 변환, 상태·격리, 감시 책임을 나눈다.
  3. 물리 자원 산정: 피크 건수·크기, 적체·재처리와 로그·임시 공간을 포함한다.
  4. 네트워크 경로 준비: 이름·포트·방화벽·프록시와 양방향 필요 여부를 확인한다.
  5. 계정·권한·비밀 준비: 환경별 서비스 신원, 최소 권한, 교체와 만료 감시를 구성한다.
  6. 중계·저장 구성: 큐·파일·상태·격리 저장소와 보존·백업을 설정한다.
  7. 시간·추적 기준 준비: 시간 동기화, correlationId와 로그 형식을 적용한다.
  8. 모의 외부 시스템 준비: 정상, 지연, 오류, 중복 응답을 재현하도록 한다.
  9. 연결 확인: 단순 포트 개방뿐 아니라 인증, 송수신, 권한과 로그까지 확인한다.
  10. 기준선 기록·승인: 구성 목록과 실제 값을 안전한 참조로 연결하고 차이를 승인한다.

횡단 책임:

업무 서비스가 외부 URL·파일명·메시지 헤더를 직접 다루지 않도록 포트와 어댑터를 분리하면 계약 변경과 시험 대체가 쉬워진다.

08

7. 공통 구현 원칙

7.1 계약 우선

코드가 생성·수신하는 데이터가 승인 스키마와 코드·단위·시간 규칙을 만족해야 한다. 예제 하나에 맞춰 필드를 추측하지 않는다.

7.2 명령과 조회 분리

상태를 바꾸는 요청과 단순 조회의 재시도·멱등 위험이 다르다. 메서드 이름만이 아니라 업무 효과를 계약에 표시한다.

7.3 구성 외부화

엔드포인트, 시간 제한, 배치 크기, 주기와 기능 전환 값은 승인된 구성으로 관리한다. 비밀은 일반 구성과 분리하고 로그에 출력하지 않는다.

7.4 경계 검증

송신 전 계약을 만족하는지, 수신 직후 스키마·크기·코드·업무 키를 확인한다. 내부에서 생성한 데이터도 다른 버전·결함이 있을 수 있으므로 경계 검증을 생략하지 않는다.

7.5 추적 가능성

eventId, correlationId, 업무 키의 안전한 표현, 계약 버전과 처리 상태를 모든 구간에서 연결한다.

7.6 제한된 자원

연결·스레드·메모리·대기열은 무한하지 않다. 연결 풀, 동시 처리, 메시지·파일 크기와 버퍼에 상한을 두고 과부하 시 무제한 읽기를 멈춘다.

09

8. 외부 API 연계 모듈 구현

8.1 송신 의사코드

sendOrder(order): contract = mapToContract(order) validate(contract)

request = { eventId: stableEventId(order), correlationId: currentTraceId(), body: contract }

response = apiClient.call( endpoint = configuredEndpoint, credential = secretReference, timeout = configuredTimeout, payload = request )

return classifyAndStore(response)

구현 포인트:

  • 연결 시간 제한과 응답 시간 제한을 구분
  • 허용 상태 코드와 업무 결과의 매핑
  • 요청·응답 크기 제한
  • 페이지 조회의 종료 조건과 중복·누락 방지
  • 호출 제한·과부하 응답 존중
  • 상태 변경 호출의 안정된 멱등 키
  • 응답 스키마와 계약 버전 검증

시간 초과 후 무조건 새 eventId로 호출하지 않는다. 설계된 상태 조회·재시도 정책을 적용한다.

8.2 수신 API

receive(request): identifyCallerAndAuthorize() enforceSizeAndSchema(request)

if inbox.has(request.eventId): return inbox.storedResult(request.eventId)

command = mapToDomain(request.body)

transaction: result = domainService.apply(command) inbox.save(request.eventId, result)

return result

인증 상세 기술보다 “인증된 서비스가 해당 업무 명령 권한을 갖는가”를 확인한다. 응답에는 내부 스택·SQL과 비밀을 노출하지 않는다.

10

9. 메시지 연계 모듈 구현

9.1 생산자

업무 변경과 발행 사건의 이중 쓰기 공백을 줄이기 위해 같은 로컬 트랜잭션에 outbox를 기록하고 전달자가 발행할 수 있다.

transaction: updateBusinessState() outbox.insert(eventId, schemaVersion, payload, status="NEW")

전달자는 성공 확인 후 상태를 변경한다. 발행 성공 후 상태 변경 전에 장애가 나면 재발행될 수 있으므로 소비자는 멱등해야 한다.

9.2 소비자

  • 메시지 크기·스키마·버전 검증
  • eventId 중복 확인
  • 업무 버전·현재 상태 확인
  • 업무 변경과 inbox 기록의 원자적 반영
  • 성공 후 전달 확인
  • 일시 실패 재시도, 영구 실패 격리
  • 처리 시간이 길면 소유권·가시성 만료 관리

메시지를 받자마자 성공 확인한 뒤 DB를 반영하면 프로세스 장애 때 메시지를 잃을 수 있다. 반대로 DB 반영 후 확인 전에 장애가 나면 중복 수신될 수 있으므로 멱등이 필요하다.

11

10. 파일 연계 모듈 구현

10.1 송신

  1. 실행 ID와 기준 시점을 고정한다.
  2. 임시 파일에 헤더·본문·트레일러를 쓴다.
  3. 건수·합계와 파일 무결성을 확인한다.
  4. 필요 시 승인된 보호를 적용한다.
  5. 원자적 이름 변경 또는 완료 표식으로 수신 가능 상태를 표시한다.
  6. 생성 결과와 보존·전송 상태를 기록한다.

10.2 수신

  1. 완료된 파일만 선택하고 파일·실행 ID 중복을 확인한다.
  2. 크기, 이름·경로, 인코딩, 헤더·트레일러를 검증한다.
  3. 레코드를 스트리밍하고 오류 위치를 안전하게 기록한다.
  4. 업무적으로 정한 단위로 반영·확인 지점을 저장한다.
  5. 성공·부분 성공·격리 상태와 대사 자료를 남긴다.
  6. 처리 파일을 승인된 보존 영역으로 이동하거나 폐기한다.

파일 전체를 메모리에 올리지 않고 큰 파일은 레코드·블록 단위로 처리한다. 레코드 중간에서 분할하지 않는다.

12

11. 변환기 구현

매핑 규칙은 순수하고 결정적인 함수로 만들면 시험과 재처리가 쉽다.

map(source): require source.orderNo status = codeMap[source.status] if status is missing: reject("UNMAPPED_STATUS")

amount = roundByApprovedRule(source.amount)

return ContractOrder( orderNo = preserveLeadingZeros(source.orderNo), orderStatus = status, amount = amount, changedAt = convertWithExplicitTimezone(source.changedAt) )

주의:

  • 값 손실이 있는 형 변환을 조용히 허용하지 않음
  • 코드 기본값을 임의로 만들지 않음
  • 날짜·시간대와 반올림 순서를 명시
  • null·필드 누락과 삭제 의미 구분
  • 원본 내부 객체를 외부 계약으로 그대로 노출하지 않음

12. 관측 코드

로그

  • 인터페이스·eventId·correlationId
  • 계약·프로그램 버전
  • 단계, 상태, 시각과 소요 시간
  • 오류 코드와 재시도 횟수

지표

  • 요청·성공·실패·격리 처리율
  • 처리 지연과 외부 응답 시간
  • 대기열·파일 적체와 가장 오래된 항목
  • 중복·순서 역전·계약 거절
  • 연결 풀·스레드·메모리 사용

추적

송신 생성, 외부 호출, 수신 처리와 DB 반영 구간을 correlationId로 연결한다. 고객명·토큰·전체 본문은 관측 데이터에 불필요하게 남기지 않는다.

13. 구체 업무 시나리오

외부 배송사 접수 모듈

  1. 주문 확정 사건을 소비하고 주문·배송단위 계약으로 변환한다.
  2. 배송사 시험계 스텁은 성공, 업무 거절, 지연, 잘못된 스키마를 재현한다.
  3. service credential은 비밀 보관소 참조로 주입하고 소스·로그에서 제외한다.
  4. 배송 접수 eventId를 안정적으로 만들고 같은 재시도에서 유지한다.
  5. 배송사 API의 업무 접수번호를 주문의 배송단위와 매핑해 상태 저장소에 기록한다.
  6. 시간 초과 시 접수 상태 조회가 가능하면 먼저 확인한 뒤 정책에 따라 재시도한다.
  7. 정상·재시도·격리 상태와 외부 응답 시간을 지표로 남긴다.
  8. 시험에서 승인된 구성만 운영 배포하며 외부 주소·인증 자료를 환경별로 분리한다.

구현 판단

  • 배송 접수 결과가 현재 주문 흐름에 즉시 필요한지에 따라 동기 대기 또는 outbox 기반 분리를 적용한다.
  • 배송사 호출 제한보다 내부 동시성이 크지 않게 제한한다.
  • 주소·연락처는 계약상 필요한 범위만 전송·로그 제외한다.
  • 배송사 계약 버전 변경은 변환기 어댑터에 격리해 업무 코드 영향을 줄인다.

15. 실기 함정

  1. 포트 연결 성공을 환경 준비 완료로 판단: 인증·권한·업무 계약과 관측까지 확인한다.
  2. 운영 주소·비밀을 소스에 하드코딩: 환경별 안전한 구성으로 분리한다.
  3. 논리 이중화를 물리 이중화로 착각: 공통 전원·저장·네트워크 장애를 추적한다.
  4. 외부 계약 객체를 업무 모델로 그대로 사용: 어댑터·변환 경계가 사라진다.
  5. 시간 초과마다 새 eventId 생성: 동일 요청 중복 처리 위험이 있다.
  6. 메시지 수신 즉시 확인 후 DB 반영: 중간 장애에서 메시지가 유실될 수 있다.
  7. 생산자만 신뢰하고 수신 검증 생략: 버전·결함·잘못된 구성 가능성이 있다.
  8. 파일 생성 중 수신이 읽게 함: 완료 상태를 원자적으로 표시한다.
  9. 큰 파일 전체를 메모리에 적재: 스트리밍·분할과 확인 지점을 사용한다.
  10. 상세 본문을 로그에 남김: 비밀·개인정보와 저장 비용 위험이 커진다.

17. 정답과 해설

정답 1

논리 환경은 송수신 구성요소, 변환·검증기, 상태·격리 저장, 스케줄·감시 역할이다. 물리 환경은 서버·런타임, 네트워크·방화벽, 브로커·DB·파일 경로, CPU·메모리·저장과 비밀 보관소다.

정답 2

환경별 주소·권한·비밀을 안전하게 바꾸고 같은 산출물을 재사용하며, 운영 비밀의 소스 노출과 시험계 오접속을 막기 위해서다.

정답 3

업무 로직은 안정된 포트에 의존하고 외부 계약·프로토콜 차이는 어댑터에 격리된다. 모의 어댑터로 시험하고 외부 버전 변경의 영향을 줄일 수 있다.

정답 4

연결 자체를 못 맺은 상황과 연결 후 수신 처리가 늦는 상황은 원인·재시도 판단이 다르기 때문이다. 전체 업무 허용 시간도 함께 둔다.

정답 5

outbox는 업무 커밋과 사건 발행 사이 이중 쓰기 공백을 줄이고, inbox는 수신 업무 반영과 처리 완료 기록 사이 공백 및 중복 반영을 줄인다.

정답 6

송신이 아직 쓰는 불완전 파일을 수신이 처리하지 않게 하고, 완성된 파일만 원자적으로 발견하도록 하기 위해서다.

정답 7

같은 입력·규칙에서 같은 결과가 나와 단위 시험, 재처리와 오류 재현이 쉬워진다. 외부 상태 의존과 부작용도 줄일 수 있다.

정답 8

로그는 인터페이스·추적 ID, 버전, 단계·상태·시각, 오류 코드·시도 횟수가 필요하다. 지표는 성공·실패율, 지연, 적체·가장 오래된 항목, 중복·거절, 자원 사용 등이 필요하다.

정답 9

정상 응답, 지연·시간 초과, 기술 오류, 업무 거절, 잘못된 스키마·버전, 중복 응답과 연결 단절 중 네 가지다.

핵심 요약

  • 연계모듈 구현을 위한 논리·물리 환경 준비는 역할·구성요소와 실제 서버·네트워크·저장·권한·용량을 구분해 기준선으로 만드는 활동이다.
  • 개발·시험·운영 구성과 비밀을 분리하고 연결, 인증·권한, 시간, 저장, 관측과 복구까지 확인한다.
  • 외부 시스템 연계 모듈 구현은 업무 포트, 계약 변환·검증, API·메시지·파일 어댑터와 상태·멱등 책임을 분리한다.
  • API는 시간 제한·상태·멱등, 메시지는 outbox/inbox와 확인 경계, 파일은 완료 표시·스트리밍·확인 지점이 핵심이다.
  • eventId·correlationId·계약 버전을 유지하고 민감 본문 없이도 오류 위치와 적체를 찾을 관측 코드를 넣는다.
  • 승인된 환경·계약과 구현 산출물을 연결하고 재현 가능한 설치·배포·복구·되돌리기 절차까지 준비해야 구현이 완료된다.
