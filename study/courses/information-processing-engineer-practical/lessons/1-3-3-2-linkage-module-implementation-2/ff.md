# 1-3-3-2. 연계모듈 작동과 데이터 무결성 검증 · 테스트 케이스와 단위 테스트 조건 명세

## 수행 범위와 목표

이 레슨의 정확한 수행 범위는 **연계모듈 작동과 데이터 무결성 검증**과 **테스트 케이스와 단위 테스트 조건 명세**이다. 구현된 API·메시지·파일 연계가 계약대로 작동하고 송신 원천부터 수신 업무 상태까지 누락·중복·변조·순서 오류 없이 반영되는지 증거로 확인한다. 정상 경로뿐 아니라 시간 초과, 응답 유실, 중복·순서 역전, 계약 위반, 권한 실패와 재처리를 테스트 케이스로 만들고, 외부 의존성을 격리한 단위 테스트 조건을 명세한다.

학습 후에는 다음을 수행할 수 있어야 한다.

- 연결 성공과 업무 작동·무결성 성공을 구분한다.
- 스키마·도메인·키·참조·거래·순서·대사 관점의 무결성을 검증한다.
- 테스트 목적, 선행 조건, 데이터, 단계, 예상 결과와 정리 절차를 명세한다.
- mock, stub, fake와 실제 시험계의 사용 경계를 정한다.
- 중복·재시도·응답 유실·부분 실패에서 멱등과 최종 상태를 검증한다.

## 1. 작동 검증의 범위

**연계모듈 작동과 데이터 무결성 검증**은 네트워크 연결이나 HTTP 성공 코드 하나를 확인하는 작업이 아니다.

    원천 업무 상태
          │ ① 사건 생성
          ▼
    송신 계약 데이터
          │ ② 전송·중계
          ▼
    수신 계약 검증
          │ ③ 변환
          ▼
    수신 업무 반영
          │ ④ 결과·상태
          ▼
    송신-수신 대사·추적

각 번호에서 입력, 출력, 상태와 로그를 확인하고 요구 ID와 연결한다.

## 2. 검증 수준

### 2.1 연결성

- 이름 해석과 네트워크 연결
- 상대 서비스 신원과 권한
- 큐·파일·DB 경로 접근
- 시간 동기화와 기본 상태 확인

연결성은 선행 조건이지 업무 검증 완료가 아니다.

### 2.2 계약

- 메시지·파일 스키마와 버전
- 필수·조건부 필드
- 자료형·길이·정밀도
- 코드·단위·시간대와 NULL
- 반복 구조와 최대 크기
- 알 수 없는 필드·코드 정책

### 2.3 업무 기능

- 정상 사건이 올바른 수신 명령으로 변환됨
- 업무 거절이 기술 오류와 구분됨
- 상태 전이와 결과가 요구 시나리오와 일치
- 초기분·변경·취소·삭제의 의미가 보존됨

### 2.4 비기능

- 피크 처리율과 허용 지연
- 적체 후 따라잡기
- 장애·재시도·격리와 복구
- 로그·지표·추적과 경보
- 권한 거절, 비밀·민감 로그 제한

## 3. 데이터 무결성의 관점

| 관점 | 검증 내용 |
|---|---|
| 전송 완전성 | 대상 사건의 누락·과다를 eventId·업무 키 집합으로 비교 |
| 구조·도메인 | 스키마, 필수, 코드, 길이, 범위, 날짜와 단위 확인 |
| 키·유일성 | 같은 eventId의 업무 효과 한 건과 업무 키 유일성 확인 |
| 참조 | 자식의 상품·고객·주문 키가 유효한 부모를 참조하는지 확인 |
| 거래 | 업무 변경과 inbox 기록이 모두 반영되거나 허용 실패 상태인지 확인 |
| 순서·버전 | 버전 3 뒤의 버전 2가 최신 상태를 덮어쓰지 않는지 확인 |
| 수치·의미 | 코드·단위·반올림을 적용한 원천 기대값과 수신 값을 비교 |
| 추적 | eventId·correlationId로 원천부터 업무 결과까지 재구성 |

전체 건수만 같으면 누락과 과다가 상쇄될 수 있고, 형식에 맞는 값도 코드 사전에 없으면 도메인 오류다. 각 관점을 별도 증거로 확인한다.

## 4. 무결성 대사 방법

    송신 대상 건수
      = 수신 성공 건수
      + 승인 거절 건수
      + 격리·처리 대기 건수

    missing = sent_event_ids - received_final_event_ids
    extra   = received_final_event_ids - sent_event_ids

성공·거절·격리 집합은 서로 겹치지 않아야 한다. 재시도 로그가 여러 건이어도 최종 업무 효과는 eventId별 한 건이어야 한다. 통화·조직·일자별 금액, 상품·단위별 수량, 상태·버전별 건수를 대사하여 상쇄 오류를 찾는다. 행 비교는 승인된 코드·단위·시간·반올림 변환 후 수행하며 해시는 같은 정렬·정규화에서만 보조로 쓴다.

SQL 검증 예:

중복 eventId 후보:

    SELECT event_id, COUNT(*) AS cnt
      FROM receive_inbox
     WHERE result_status = 'SUCCESS'
     GROUP BY event_id
    HAVING COUNT(*) > 1;

부모 없는 자식은 외부 조인 후 부모 키가 NULL인 행으로 찾을 수 있다. 실제 테이블과 성공 기록 방식에 맞춰 쿼리를 조정한다.

## 5. 테스트 수준과 대역

| 수준 | 대상 | 외부 의존성 | 목적 |
|---|---|---|---|
| 단위 테스트 | 변환기, 검증기, 재시도 분류, 핸들러 | mock·stub·fake | 분기·경계·결정 규칙 |
| 계약 테스트 | 생산·소비 스키마와 예제 | 계약 검증기·상대 stub | 양쪽 해석 호환 |
| 구성요소 테스트 | 연계 모듈과 로컬 DB·큐 | 시험용 실제 구성 일부 | 트랜잭션·상태·관측 |
| 통합 테스트 | 송신-중계-수신 | 외부 시험계 또는 현실적 대역 | 전체 흐름·실패 경계 |
| 성능·복구 테스트 | 전체 경로 | 운영 유사 자원 | 피크·적체·전환·재처리 |

단위 테스트가 많아도 네트워크·인증서·브로커 확인 경계는 통합 시험이 필요하다. 반대로 모든 경우를 느린 외부 시험계로만 확인하면 원인 격리와 반복성이 떨어진다.

## 6. 테스트 대역 구분

- stub은 준비된 응답, mock은 호출·인수·횟수, fake는 단순 동작 구현, simulator는 외부 프로토콜·상태를 모사한다.
- 대역은 실제 시스템과 다를 수 있으므로 계약을 공유하고 실제 시험계로 교차 확인한다.

## 7. 테스트 케이스 명세

**테스트 케이스와 단위 테스트 조건 명세**에는 다음 항목이 필요하다.

| 항목 | 내용 |
|---|---|
| 테스트 ID·요구 ID | 목적과 요구 추적 |
| 제목·목적 | 검증하려는 한 가지 핵심 |
| 대상 버전 | 모듈·계약·코드 사전·구성 |
| 선행 조건 | DB 상태, 큐, 권한, 시각, 모의 응답 |
| 입력 데이터 | eventId, 업무 키·버전, 경계값 |
| 대역 동작 | 응답·지연·예외·호출 횟수 |
| 수행 단계 | 실행 순서와 장애 주입 시점 |
| 예상 결과 | 반환뿐 아니라 DB·큐·파일 상태 |
| 관측 기대 | 로그·지표·추적·경보 |
| 정리·복원 | 데이터·큐·파일과 설정 원상복구 |
| 판정·증거 | 실제 결과, 증거 위치와 PASS/FAIL |

한 케이스에 너무 많은 목적을 넣으면 실패 원인을 찾기 어렵다. 정상, 중복, 순서, 시간 초과 같은 핵심을 분리한다.

## 8. 단위 테스트 조건

| 조건 | 적용 |
|---|---|
| 결정성 | 시각·난수·네트워크를 주입하여 같은 입력에서 같은 결과를 만든다. |
| 독립성 | 테스트마다 데이터·eventId를 준비·정리해 실행 순서 영향을 없앤다. |
| 단일 관심사 | 변환·멱등·재시도 분류 등 한 행동과 관찰 결과를 확인한다. |

경계값은 길이 바로 초과, 0·음수·최대 수량, 반올림, NULL·누락·빈 값, 날짜·시간대, 반복 수와 미등록 코드를 포함한다. 실패는 연결 전, 요청 후 응답 유실, DB 반영 전·후, 성공 기록 실패, 큐 확인 전 종료, 파일 절단과 권한 거절 지점에 주입한다. 같은 시간 초과도 수신 반영 전후의 기대 결과가 다르다.

## 10. 구체 단위 테스트 의사코드

### 중복 이벤트

    test_same_event_is_idempotent():
      message = validMessage(eventId="E-100", orderVersion=1)
      first  = handler.handle(message)
      second = handler.handle(message)
      assert second == first
      assert businessRepository.countByOrder(message.orderNo) == 1
      assert inbox.countByEventId("E-100") == 1

### 응답 유실 후 재호출

    test_timeout_after_commit_does_not_duplicate():
      externalStub.commitThenDropResponse()
      command = reserveCommand(idempotencyKey="R-200")
      first = client.send(command)       # timeout observed
      externalStub.returnStoredResult()
      retry = client.send(command)
      assert first.isUnknownOutcome
      assert retry.success
      assert externalStub.businessEffectCount("R-200") == 1

### 오래된 버전

    test_older_version_cannot_overwrite_newer():
      handler.handle(msg("O-1", version=3, status="SHIPPED"))
      result = handler.handle(msg("O-1", version=2, status="PAID"))
      assert result.isStaleOrDuplicate
      assert orderRepository.status("O-1") == "SHIPPED"

첫 케이스는 순차·동시 실행으로 나누고, 두 번째는 수신 커밋 전 유실 케이스와 비교한다. 의사코드는 실제 트랜잭션·상태 계약에 맞춘다.

## 11. 업무 시나리오: 재고 예약 연계

### 기준 데이터

- 주문 O-100, 버전 4
- 품목 P-1 수량 2, P-2 수량 1
- 주문 확정 eventId E-400
- 재고 예약 결과 ID R-900

### 정상 예상

1. E-400이 계약 검증을 통과한다.
2. 주문 버전 4와 현재 재고 상태를 확인한다.
3. 두 품목 예약과 inbox E-400 성공을 하나의 거래 단위로 기록한다.
4. 결과 R-900이 송신 측 추적 상태에 연결된다.
5. correlationId로 주문 확정부터 예약까지 조회된다.

### 실패·중복

- P-2 부모 상품이 없으면 전체를 격리할지 P-1만 반영할지는 승인된 거래 계약대로 검증한다.
- 예약 커밋 후 응답 유실을 주입하고 E-400 재전달로 예약이 두 배가 되지 않는지 본다.
- E-400이 동시에 두 소비자 인스턴스에 전달되어도 업무 효과와 inbox가 한 건인지 확인한다.
- 버전 5 취소 후 버전 4 확정이 도착하면 최신 상태를 되돌리지 않는지 확인한다.

### 대사

| 비교 | 기대 |
|---|---|
| 송신 E-400 | 수신 최종 상태 1건 |
| 주문 O-100 버전 | 수신 4 또는 이후 승인 상태 |
| 품목 수량 합계 | P-1=2, P-2=1 |
| 업무 효과 | 예약 R-900 한 건 |
| 추적 | 같은 correlationId로 전 구간 연결 |

## 12. 테스트 실행 절차

1. **범위·요구 추적 확인**: 계약, 멱등, 실패·보안 요구별 케이스를 연결한다.
2. **버전·환경 기준선 고정**: 코드, 스키마, 코드 사전, 구성과 모의체 버전을 기록한다.
3. **데이터·대역 준비**: 독립된 eventId, DB·큐·파일 상태와 외부 응답을 준비한다.
4. **단위·계약 테스트 실행**: 빠른 경계·분기 검증으로 결함을 먼저 찾는다.
5. **구성요소·통합 실행**: 실제 직렬화, DB 거래, 큐 확인과 네트워크 경계를 확인한다.
6. **장애 주입**: 커밋 전후·확인 전후를 나누어 실패시킨다.
7. **무결성·관측 대사**: 키 집합, 합계, 최종 상태와 로그·지표를 비교한다.
8. **성능·복구 확인**: 피크, 적체, 재처리와 따라잡기를 시험한다.
9. **정리·재실행**: 시작 상태로 복원해 동일 결과가 재현되는지 확인한다.
10. **결함 수정·회귀**: 수정 케이스와 연관 정상·실패 케이스를 다시 실행한다.
11. **증거·승인**: 결과, 로그, 쿼리, 버전과 잔여 예외를 기록한다.

## 13. 테스트 판정 기준

- 모든 필수 요구·위협·실패 상태에 케이스가 연결됨
- 정상 결과와 DB·큐·파일 최종 상태가 계약과 일치
- 같은 eventId의 업무 효과가 한 번뿐임
- 오래된 버전이 최신 상태를 덮어쓰지 않음
- 기술 실패·업무 거절·계약 거절 상태가 구분됨
- 격리·재처리 후 원본 처리 이력과 결과가 연결됨
- 송신-수신 키 집합과 통제 합계가 승인 기준 일치
- 피크 처리량·지연과 장애 후 따라잡기가 목표 충족
- 권한 없는 호출·변조·오래된 재전송이 거절됨
- 로그·지표에 필요한 추적은 있고 비밀·민감 원문은 없음

오류 건수만으로 승인하지 않는다. 금액·권리·중복 업무 효과 같은 치명 결함은 한 건이어도 차단 기준일 수 있다.

## 15. 실기 함정

1. **HTTP 성공·파일 존재만으로 작동 성공 판단**: 수신 업무 상태와 무결성을 확인한다.
2. **전체 건수만 대사**: 누락과 과다가 상쇄될 수 있어 키 집합을 본다.
3. **해시 일치만으로 업무 정확성 보장**: 비교 정규화·규칙 자체를 검토한다.
4. **단위 테스트에서 실제 시간·네트워크 사용**: 비결정성과 느린 실패가 생긴다.
5. **mock 호출 횟수만 확인**: 최종 업무 상태와 계약 결과가 핵심이다.
6. **시간 초과를 한 위치에서만 시험**: 커밋 전과 후의 기대 결과가 다르다.
7. **중복을 순차 호출로만 시험**: 동시 소비 경쟁도 확인한다.
8. **재시도마다 새 eventId 사용**: 멱등 테스트 의미가 사라진다.
9. **모든 실패를 기술 오류로 기대**: 업무 거절과 계약 거절을 분리한다.
10. **대역 통과를 실제 외부 호환으로 단정**: 계약·통합 시험계로 교차 확인한다.

## 17. 정답과 해설

### 정답 1

연결성은 경로·신원·권한, 계약은 스키마·도메인, 업무 기능은 상태 전이·결과, 비기능은 성능·장애·보안·관측을 검증한다.

### 정답 2

전송 완전성, 구조·도메인, 키·유일성, 참조, 거래, 순서·버전, 수치·의미, 추적 무결성 중 여섯 가지다.

### 정답 3

송신 사건 A가 누락되고 존재하지 않는 사건 B가 과다 반영되면 양쪽 총건수는 같을 수 있다. 이벤트 ID 집합과 업무 상태를 비교해야 한다.

### 정답 4

단위 테스트는 작은 규칙과 대역, 계약 테스트는 생산·소비 스키마 호환, 통합 테스트는 실제 DB·중계·외부 시험계 경계를 포함한 전체 흐름을 본다.

### 정답 5

stub은 준비된 응답을 반환하고, mock은 예상 호출·인수·횟수를 검증하며, fake는 메모리 저장소처럼 단순하지만 동작하는 대체 구현이다.

### 정답 6

테스트·요구 ID, 목적, 대상 버전, 선행 조건, 입력, 대역 동작, 수행 단계, 예상 반환·상태, 관측 기대, 정리, 판정·증거 중 여덟 가지다.

### 정답 7

첫 호출 결과가 불명이어도 수신 업무 효과는 한 건이고, 같은 멱등 키 재호출이 저장된 같은 결과를 반환하며 중복 상태가 생기지 않는지 확인한다.

### 정답 8

현재 버전보다 낮은 메시지는 stale 또는 중복 상태로 처리되고 최신 업무 상태·버전을 덮어쓰지 않아야 한다. 처리 이력과 지표는 남는다.

### 정답 9

전체·그룹별 건수, 이벤트·업무 키 집합, 금액·수량 통제 합계, 행별 기대값, 버전·최종 상태와 추적 로그 중 네 가지다.

### 정답 10

대역은 실제 외부 시스템의 직렬화, 인증, 네트워크, 시간 제한, 오류·버전 동작을 완전히 재현하지 못할 수 있기 때문이다. 계약 시험과 실제 시험계 통합 검증이 필요하다.

## 핵심 요약

- **연계모듈 작동과 데이터 무결성 검증**은 연결, 계약, 업무 기능, 비기능의 각 수준에서 원천 사건부터 수신 최종 상태까지 확인한다.
