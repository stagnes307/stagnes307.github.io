01

수행 범위와 목표

이 레슨은 서버 프로그램 개발을 시작하기 전에 개발에 필요한 HW·SW 사항 검토와 준비를 수행하고, 검토 결과를 근거로 HW·SW 설치·설정으로 개발환경 구축을 완료하는 실무 절차를 다룬다. 단순히 개발자 PC에 편집기를 설치하는 것이 아니라 소스 작성, 빌드, 실행, 데이터 저장, 단위·통합시험, 외부 연동을 재현 가능한 상태로 만드는 것이 목표다.

학습 후에는 요구사항에서 필요한 자원과 도구를 도출하고, 호환성·라이선스·보안·용량을 평가하며, 설치 순서와 설정 기준을 작성하고, 깨끗한 환경에서 빌드·기동·연동 시험을 수행해 구축 완료 여부를 판단할 수 있어야 한다.

다음 레슨의 형상관리 방침과 저장소 운영은 별도 범위이므로 여기서는 소스 도구가 필요하다는 수준만 언급한다. 공통모듈과 서버 업무 코드 구현도 뒤 레슨에서 다룬다.

02

입력자료와 사전 확인

개발환경 구축 전에 다음 입력자료를 확보한다.

  • 시스템 요구사항 명세서와 서버 프로그램 기능 목록
  • 소프트웨어 아키텍처·배포 구성도와 외부 연계 목록
  • 개발 표준, 지원 언어·런타임·프레임워크 기준
  • 운영 대상의 운영체제, 프로세서 구조, 데이터베이스와 미들웨어 정보
  • 성능·동시 사용자·데이터량·보안·가용성 요구
  • 조직이 허용한 도구, 패키지 저장소, 네트워크·라이선스 정책
  • 개발·시험·운영 환경별 접근권한과 데이터 사용 기준

요구사항이 모호하면 담당자에게 확인하고 가정과 결정 근거를 기록한다. 도구를 먼저 설치한 뒤 시스템 요구에 맞추면 지원되지 않는 런타임이나 데이터베이스 때문에 재구축할 수 있다.

실기에서는 “어떤 제품을 설치했는가”보다 “어떤 요구에서 그 구성요소가 필요했고 설치 후 무엇으로 검증했는가”를 설명해야 한다.

03

개발 장비는 편집기만 실행하는 것이 아니다. 빌드 도구, 데이터베이스, 서버, 시험 도구를 동시에 실행할 수 있어야 한다. 메모리가 부족하면 코드 결함과 무관한 빌드 실패와 지연이 생긴다.

운영과 동일한 규모를 개발환경에 복제할 필요는 없지만 기능·아키텍처·인코딩·시간대처럼 결과 의미에 영향을 주는 차이는 통제한다. 성능 시험에는 별도의 실제 규모 근접 환경을 마련한다.

용량 산정에는 순간 최대값과 증가 여유를 둔다. 로그와 의존 캐시는 정리 정책이 없으면 저장공간을 계속 사용한다. 디스크가 가득 찼을 때 서버와 빌드가 어떻게 실패하는지도 고려한다.

언어와 프레임워크는 팀 숙련도뿐 아니라 운영 지원, 보안 수정, 라이선스, 외부 연계, 배포 형태를 함께 본다. 특정 도구가 유행한다는 이유는 충분한 선정 근거가 아니다.

도구별로 필수 버전 범위, 배포 출처, 설치 위치, 설정 파일, 확인 방법을 구성 명세에 기록한다. “최신”이라는 값은 시점마다 달라 재현 기준이 되지 않는다.

외부 라이브러리는 직접 의존성뿐 아니라 간접 의존성, 라이선스, 지원 상태를 검토한다. 패키지 이름이 비슷한 위조 구성요소를 피하고 승인된 저장소와 무결성 확인 절차를 사용한다.

각 문서가 지원한다고 해도 전체 조합이 검증되었다는 뜻은 아니다. 작은 검증 프로젝트로 컴파일, 서버 기동, DB 연결, 주요 연동을 확인한다.

운영체제의 파일 경로 대소문자, 줄바꿈, 문자 인코딩, 시간대 차이는 개발에서는 지나가고 운영에서 실패하는 원인이 된다. 한국어 파일과 다바이트 문자열, 날짜 경계 데이터를 포함해 시험한다.

06

라이선스와 보안 정책 검토

상용 도구는 개발자 수, 서버 수, 사용 목적에 맞는 라이선스를 확인한다. 오픈소스도 배포·수정·고지 조건이 있으므로 “무료=제약 없음”으로 보지 않는다. 라이선스 목록과 승인 결과를 산출물로 남긴다.

설치 파일은 조직이 승인한 출처에서 받고 서명·해시 등 제공되는 무결성 수단을 확인한다. 관리자 권한은 필요한 설치 단계에만 사용한다. 방화벽을 모두 끄거나 인증서 검증을 무시하는 방식으로 연결 문제를 해결하지 않는다.

개발 데이터에는 운영 개인정보를 그대로 복제하지 않는다. 합성·마스킹 데이터와 최소 권한 계정을 사용한다. 비밀번호·토큰은 소스나 공용 설정 파일에 기록하지 않고 승인된 비밀 주입 방식을 사용한다.

07

환경 구성 설계

설치 전 논리 구성을 그린다.

개발자 워크스테이션 ├─ IDE / 런타임 / 빌드도구 ├─ 로컬 단위시험 └─ 안전한 설정 주입 ↓ 공용 개발 서버 ├─ 응용 실행환경 ├─ 개발 데이터베이스 └─ 외부 시스템 모의 연동 ↓ 통합시험 환경 └─ 운영과 핵심 구성이 유사한 검증

개발·통합시험·운영의 차이를 환경 비교표로 관리한다. 포트, 호스트명, 데이터, 자격 증명, 로그 수준은 다를 수 있지만 업무 로직과 스키마 의미가 달라지지 않게 한다.

도구 설치 순서는 선행 의존성을 따른다. 운영체제 패치와 필수 기반, 런타임, 빌드 도구, IDE, 데이터베이스·미들웨어, 프로젝트 의존성, 시험 도구의 순으로 계획할 수 있다. 실제 환경에서는 제품 지침이 우선한다.

08

단계별 구축 절차

1단계: 기준선 확정

구성 명세서에 하드웨어, 운영체제, 런타임, 빌드·시험도구, DB, 포트, 경로, 환경 변수를 기록하고 담당자의 승인을 받는다. 설치 이전 상태와 복구 방법을 확인한다.

2단계: HW·운영체제 준비

CPU·메모리·디스크 여유와 네트워크 연결을 확인한다. 승인된 운영체제 이미지와 보안 수정, 사용자 계정, 시간 동기화, 문자 인코딩을 설정한다. 개발자가 일상 작업에 최고 권한 계정을 사용하지 않게 한다.

3단계: 언어·도구 설치

승인된 배포본을 검증해 설치한다. 버전 확인 결과와 설치 경로를 기록한다. 시스템 전체 설치와 프로젝트별 격리 환경 중 요구에 맞는 방식을 선택한다. 여러 프로젝트가 다른 버전을 요구하면 격리 도구로 충돌을 줄인다.

4단계: 데이터·미들웨어 구성

개발용 데이터베이스와 스키마를 자동 초기화하고 최소 권한 응용 계정을 만든다. 메시지·외부 API가 필요하면 개발용 인스턴스나 안전한 모의 서버를 구성한다. 운영 자격 증명을 가져오지 않는다.

5단계: 프로젝트 설정

프로젝트가 요구하는 의존성을 선언대로 설치하고 환경별 설정을 주입한다. 견본 설정에는 키 이름과 형식만 두고 비밀값은 제외한다. 포트 충돌과 경로 권한을 확인한다.

6단계: 기능 검증

깨끗한 상태에서 소스 검사, 빌드, 단위시험, 서버 기동, 상태 확인, DB 읽기·쓰기, 외부 연동 모의시험을 수행한다. 성공·실패 결과와 소요 시간을 기록한다.

7단계: 재현성 검증

다른 작업자가 구축서만 보고 새 환경을 만들어 같은 시험을 통과하는지 확인한다. 누락된 수동 설정을 찾아 문서나 자동화에 반영한다.

09

안전한 설정 예시

환경별 설정을 개념적으로 다음처럼 분리한다.

application configuration: databasehost: suppliedbyenvironment databasename: developmentdb loglevel: development externalserviceurl: approvedmockservice secretreference: managedsecret_name

비밀 원문 대신 참조 이름을 사용한다. 시작 시 필수 설정이 없거나 형식이 잘못되면 조기에 실패시키고, 로그에는 민감값을 가린 채 어떤 설정 항목이 문제인지 남긴다.

운영 주소를 기본값으로 두지 않는다. 개발 설정 누락이 운영 시스템 접속으로 이어지지 않게 안전한 로컬·모의값 또는 명시적 실패를 기본으로 한다.

빌드깨끗한 의존 캐시 또는 새 환경 빌드오류 없이 동일 산출물 생성
자동시험단위시험과 기본 정적 분석필수 시험 모두 통과
서버 기동상태 확인과 정상 종료·재기동지정 시간 안에 정상
데이터 연동스키마 생성, 읽기·쓰기, 롤백최소 권한으로 성공
외부 연동승인된 모의 서비스 호출시간 제한·오류 처리 포함
보안비밀·운영 데이터·불필요 포트 점검노출 없음
문서 재현제3자의 신규 구축추가 구두 지시 없이 성공

검증은 설치 프로그램의 성공 메시지로 끝나지 않는다. 실제 프로젝트의 빌드와 기동이 기준이다.

11

산출물

  • HW·SW 요구사항 및 용량 산정표
  • 구성요소 호환성·라이선스·보안 검토표
  • 개발환경 논리 구성도와 환경 차이표
  • 설치·설정 절차서와 자동화 스크립트 또는 선언 파일
  • 환경 변수·포트·경로·계정 목록(비밀 원문 제외)
  • 개발 데이터 초기화·정리 절차
  • 구축 검증 결과서와 실패·조치 이력
  • 재구축 체크리스트와 운영 인계 사항

산출물에는 작성일, 대상 환경, 구성 버전, 작성자·검토자, 변경 이력을 넣는다. 화면 캡처만 나열하지 말고 값과 판단 근거를 기계적으로 비교 가능한 형태로 기록한다.

12

구체 업무 시나리오

“주문 조회 서버” 개발환경을 구축한다고 하자. 요구사항은 서버 런타임, 관계형 데이터베이스, 외부 배송 API 연동, 한국어 상품명 처리다.

  1. 동시 개발 프로세스와 시험 DB를 고려해 장비 자원을 산정한다.
  2. 운영과 호환되는 런타임·DB 버전 조합을 검증한다.
  3. 외부 배송 API 대신 정상·지연·오류 응답을 제공하는 모의 서버를 준비한다.
  4. 개발 DB에는 합성 주문 데이터를 넣고 응용 계정은 주문 스키마의 필요한 연산만 허용한다.
  5. UTF-8 상품명, 시간대 경계 주문, NULL 선택값으로 기본 시험을 한다.
  6. 새 환경에서 빌드–기동–조회–종료를 반복해 재현성을 확인한다.

운영 배송 주소나 고객 개인정보를 가져올 이유가 없다. 실제 외부 호출이 꼭 필요하다면 승인된 시험 계정과 제한된 대상을 사용한다.

13

실무 체크리스트

  • [ ] 요구사항과 아키텍처에서 필요한 구성요소를 모두 도출했다.
  • [ ] HW 용량에 빌드·DB·로그·가상환경과 증가 여유를 반영했다.
  • [ ] SW 버전과 전체 조합의 호환성을 검증했다.
  • [ ] 라이선스와 배포 출처·무결성을 확인했다.
  • [ ] 개발·시험·운영 차이를 문서화했다.
  • [ ] 비밀정보와 운영 개인정보를 개발환경에서 분리했다.
  • [ ] 최소 권한 계정과 필요한 포트만 사용한다.
  • [ ] 깨끗한 빌드, 자동시험, 서버 기동, DB·모의 연동을 통과했다.
  • [ ] 설치·정리·재구축 절차가 문서화되었다.
  • [ ] 다른 작업자가 같은 결과를 재현했다.
14

자주 발생하는 함정

  • IDE 설치만으로 개발환경 구축이 완료되었다고 판단한다.
  • 요구사항 확인 없이 최신 버전을 선택해 프레임워크·운영과 충돌한다.
  • 각 제품이 개별 지원된다는 사실을 전체 조합 호환으로 오해한다.
  • 로그·캐시·시험 데이터의 증가량을 용량 산정에서 빼먹는다.
  • 개발 편의를 위해 운영 DB와 운영 자격 증명을 사용한다.
  • 연결 오류를 해결하려고 방화벽·인증서 검증을 전체 해제한다.
  • 로컬에서 수동 생성한 스키마와 설정을 문서에 남기지 않는다.
  • 설치 성공만 보고 실제 소스 빌드·서버 기동을 시험하지 않는다.
  • 운영과 환경이 다르다는 사실보다 차이를 통제·검증하지 않는 것이 문제임을 놓친다.
  • 비밀값을 가린 화면 캡처 대신 실제 설정 파일을 저장소에 올린다.

확인 문제

  1. 개발환경 구축에 필요한 입력자료를 다섯 가지 이상 쓰라.
  2. CPU·메모리·저장장치·네트워크 요구를 각각 어떤 근거로 산정하는가?
  3. SW 구성요소 호환성 표가 필요한 이유는 무엇인가?
  4. 개발·시험·운영 환경의 차이를 완전히 없애기 어렵다면 어떻게 관리해야 하는가?
  5. 개발 데이터와 비밀정보를 운영과 분리해야 하는 이유를 설명하라.
  6. HW·SW 설치 순서와 선행 의존성의 관계를 설명하라.
  7. 설치 후 수행할 기능 검증을 여섯 가지 쓰라.
  8. 재현성 검증에서 다른 작업자가 구축해야 하는 이유는 무엇인가?
  9. 주문 조회 서버 환경 시나리오의 산출물을 네 가지 쓰라.
  10. 개발환경 구축 완료를 판단할 합격 기준을 설명하라.
16

정답과 해설

  1. 요구사항 명세, 아키텍처·배포 구성도, 개발 표준, 운영 대상 정보, 성능·보안 요구, 외부 연계, 허용 도구·라이선스 정책 등이 필요하다.
  2. CPU는 빌드와 동시 프로세스, 메모리는 IDE·서버·DB 최대 사용, 저장장치는 소스·캐시·로그·데이터와 증가율, 네트워크는 저장소·연계의 대역폭·지연·포트를 근거로 한다.
  3. 운영체제·런타임·프레임워크·DB가 서로 지원하는 조합인지 확인하고, 개별 지원 문서만으로 발견하기 어려운 충돌을 작은 검증으로 찾기 위해서다.
  4. 환경 비교표에 차이와 이유를 기록하고 핵심 기능·인코딩·시간대·스키마 의미를 일치시키며 통합시험에서 운영 근접 구성을 검증한다.
  5. 운영 정보 노출과 오동작을 막고 개발자에게 과도한 권한을 주지 않기 위해서다. 합성 데이터와 안전한 비밀 주입을 사용한다.
  6. 선행 도구가 있어야 후속 도구가 설치·검증되므로 운영체제 기반, 런타임, 빌드, IDE, DB·미들웨어, 프로젝트 의존성과 시험도구 순으로 계획할 수 있다.
  7. 버전 확인, 깨끗한 빌드, 단위시험, 서버 기동·종료, DB 연결·읽기·쓰기, 외부 모의 연동, 로그·포트·비밀 노출 검사를 수행한다.
  8. 작성자가 무의식적으로 수행한 수동 설정과 구두 지식을 찾아 문서와 자동화의 완전성을 확인하기 위해서다.
  9. HW·SW 산정표, 호환성 검토표, 환경 구성도, 설치 절차서, 개발 데이터 초기화, 구축 검증 결과서를 작성한다.
  10. 명세된 구성과 자원을 만족하고 새 환경에서 빌드·시험·기동·연동이 성공하며, 보안 기준과 문서 재현성을 통과해야 한다.
17

핵심 요약

  • 개발에 필요한 HW·SW 사항 검토와 준비는 요구사항에서 자원·도구를 도출하고 호환성·용량·라이선스·보안을 검증하는 과정이다.
  • 개발환경은 IDE뿐 아니라 런타임, 빌드, DB·미들웨어, 시험·분석, 네트워크와 설정을 포함한다.
  • HW·SW 설치·설정으로 개발환경 구축은 기준선 확정–설치–연동–빌드–기동–재현성 검증의 순서로 수행한다.
  • 운영 비밀과 개인정보를 분리하고 최소 권한, 승인된 출처, 안전한 환경별 설정을 적용한다.
  • 산출물은 요구·호환성 표, 구성도, 설치서, 설정 목록, 데이터 초기화, 검증 결과와 재구축 체크리스트다.
  • 구축 완료는 다른 작업자가 깨끗한 환경에서 동일 결과를 재현했을 때 판단한다.
