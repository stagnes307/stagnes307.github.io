# 1-4-1-2. 형상관리 방침과 운영정책에 맞는 환경 구축

## 수행 범위와 목표

이 레슨은 조직의 **형상관리 방침과 운영정책에 맞는 환경 구축**을 수행하고, 그 과정에서 **개발환경 구축하기의 적용 절차와 판단 기준**을 확립하는 실무를 다룬다. 목표는 소스·설정·스키마·문서·빌드 산출물의 변경을 식별하고, 승인된 저장소와 권한, 브랜치·기준선·변경통제·백업 체계를 구성해 누가 어떤 변경을 언제 왜 반영했는지 추적 가능하게 만드는 것이다.

앞 레슨의 HW·SW 설치와 서버 실행환경 구성은 반복하지 않는다. 이 레슨은 이미 준비된 도구 위에 형상관리 정책을 실제 저장소·자동검증·운영절차로 구현하는 범위에 집중한다.

## 형상관리의 목적

형상관리(Configuration Management)는 시스템을 구성하는 항목을 식별하고, 변경을 통제하며, 상태를 기록하고, 기준과 실제가 일치하는지 감사하는 활동이다. 소스 버전관리보다 넓은 개념이다.

핵심 활동은 다음과 같다.

- 형상 식별: 관리할 항목과 이름·버전·소유자를 정한다.
- 형상 통제: 변경 신청, 영향 분석, 승인, 구현, 검증, 반영을 관리한다.
- 형상 상태 기록: 현재 버전, 변경 이력, 배포 상태를 보고한다.
- 형상 감사: 승인 기준선과 실제 산출물이 일치하는지 확인한다.

버전관리 도구를 설치했다고 형상관리가 완성되는 것은 아니다. 무엇을 커밋해야 하는지, 누가 어떤 경로로 병합할 수 있는지, 기준선과 배포 산출물을 어떻게 연결하는지가 운영정책으로 정의되어야 한다.

## 형상 항목 식별

| 분류 | 형상 항목 예 | 관리 기준 |
|---|---|---|
| 소스 | 응용 코드, 공통모듈, 시험 코드 | 변경 이력·검토·빌드 연결 |
| 설정 | 환경별 설정 견본, 정책, 기능 플래그 | 비밀 분리·환경 차이 추적 |
| 데이터 | 스키마 변경, 기준 코드, 초기화 자료 | 적용 순서·롤백·검증 |
| 문서 | 요구·설계·API·운영 절차 | 코드·릴리스 버전과 연결 |
| 빌드 | 빌드 선언, 잠금 정보, 컨테이너 정의 | 재현성·출처·무결성 |
| 산출물 | 실행 패키지, 이미지, 보고서 | 변경 불가 저장·서명·보존 |
| 도구 기준 | 런타임·컴파일러·분석 규칙 | 버전·정책 변경 승인 |

개인 IDE 화면 배치, 임시 로그, 캐시, 비밀 원문, 빌드 중간파일은 보통 소스 저장소에서 제외한다. 그러나 빌드에 필요한 선언, 잠금 정보, 자동시험 설정은 포함해야 재현할 수 있다.

각 항목에는 고유 식별자, 저장 위치, 소유자, 변경 권한, 보존 기간, 기준선 포함 여부를 형상 항목 목록으로 작성한다.

## 형상관리 방침 분석

조직 방침에서 다음을 확인한다.

1. 공식 저장소와 프로젝트 생성 승인 절차
2. 계정·역할과 읽기·쓰기·병합·관리 권한
3. 브랜치·태그·버전 번호와 릴리스 기준
4. 변경 요청, 검토자 수, 승인·분리 원칙
5. 자동 빌드·시험·보안 검사와 실패 기준
6. 비밀정보·개인정보·대용량 파일 처리
7. 백업·복구, 보존·폐기, 감사 로그 정책
8. 긴급 변경과 사후 승인 절차
9. 외부 협력자 접근과 계약 종료 시 회수
10. 산출물 저장소와 운영 배포 권한

방침이 문장으로만 있고 실제 도구 설정과 다르면 통제가 작동하지 않는다. 각 정책 항목을 저장소 보호 규칙, 역할, 자동검사, 감사 증거로 매핑한다.

## 저장소 구조 설계

한 저장소에 모든 시스템을 넣을지 서비스·모듈별로 나눌지는 변경 단위, 권한, 빌드, 배포 주기를 기준으로 정한다. 저장소가 너무 크면 전체 접근과 빌드 비용이 커지고, 지나치게 쪼개면 동일 변경을 여러 저장소에 맞추기 어렵다.

일반적인 구조 예시는 다음과 같다.

    project/
      source/
      tests/
      database-migrations/
      configuration-examples/
      docs/
      build-definition
      dependency-lock
      README

폴더 이름보다 각 디렉터리의 소유와 빌드·시험 연결이 중요하다. 스키마 변경과 이를 사용하는 코드가 같은 변경 묶음으로 검토될 수 있어야 한다.

큰 바이너리와 실행 산출물은 소스 이력에 반복 저장하기보다 전용 산출물 저장소를 사용한다. 산출물은 소스 커밋, 빌드 번호, 의존 버전과 연결한다.

## 권한과 역할

최소 권한으로 역할을 설계한다.

| 역할 | 대표 권한 | 제한 |
|---|---|---|
| 개발자 | 작업 브랜치 읽기·쓰기 | 보호 브랜치 직접 쓰기 금지 |
| 검토자 | 변경 검토·승인 | 자기 변경 단독 승인 제한 |
| 통합 담당 | 승인된 변경 병합 | 자동검증 실패 우회 제한 |
| 릴리스 담당 | 기준선 태그·산출물 승격 | 소스 임의 변경 금지 |
| 저장소 관리자 | 설정·복구·권한 관리 | 일상 개발·단독 배포와 분리 |
| 외부 협력자 | 지정 저장소·기간 접근 | 프로젝트 종료 시 자동 회수 |

계정 공유를 금지하고 개인별 행위가 감사되게 한다. 관리자 권한은 일상 작업에 쓰지 않고 필요 시 승인된 방식으로 상승한다. 퇴직·이동·계약 종료와 연계해 즉시 회수한다.

자동 빌드 계정과 배포 계정도 사람 계정과 분리하고 필요한 저장소·산출물·환경 권한만 준다. 장기 비밀을 설정 파일에 넣지 않고 안전한 자격 증명 저장소와 교체 절차를 사용한다.

## 브랜치 운영

브랜치 전략은 조직의 릴리스 빈도, 동시 버전 유지, 검토 흐름에 맞춘다.

- 주 기준 브랜치는 항상 빌드·시험 가능한 통합 상태를 유지한다.
- 작업 브랜치는 하나의 변경 목적에 집중하고 수명을 짧게 한다.
- 릴리스 브랜치는 안정화가 필요한 경우 제한적으로 사용한다.
- 긴급 수정은 운영 기준에서 시작해 수정 후 주 개발 흐름에도 반영한다.

브랜치 이름보다 병합 규칙이 중요하다. 보호 브랜치에는 직접 푸시를 막고 변경 요청, 동료 검토, 자동시험, 최신 기준과의 충돌 해결을 요구한다.

장기간 분리된 브랜치는 병합 충돌과 기능 차이를 키운다. 작은 변경을 자주 통합하되 완성되지 않은 기능은 안전한 기능 플래그와 테스트로 숨길 수 있다. 기능 플래그 자체도 형상 항목이며 만료·제거 계획이 필요하다.

## 커밋과 변경 단위

좋은 커밋은 하나의 논리적 목적을 갖고 관련 코드·시험·문서를 함께 포함한다. 포맷 변경과 기능 변경을 불필요하게 섞으면 검토가 어렵다.

커밋 메시지는 무엇을 바꾸었는지뿐 아니라 왜 바꾸었는지와 관련 요구·결함 식별자를 남긴다. 생성물과 비밀정보가 포함되지 않았는지 자동 검사한다.

큰 변경을 여러 커밋으로 나눌 수 있지만 각 커밋이 기준 브랜치에 들어갈 때 빌드 가능한지 정책을 정한다. 이력을 보기 좋게 정리하는 방법은 조직 규칙을 따른다.

이력 수정이나 강제 갱신은 공유 브랜치에서 다른 작업자의 기준을 깨뜨릴 수 있으므로 제한한다. 이미 공개된 비밀은 커밋을 삭제하는 것만으로 안전해지지 않으므로 즉시 폐기·교체한다.

## 변경 요청과 검토

변경 요청에는 목적, 관련 요구사항, 변경 파일, 영향 범위, 시험 결과, 데이터·배포 변경, 되돌리기 방법, 보안·성능 영향을 포함한다.

검토자는 다음을 확인한다.

- 요구사항과 상세설계에 맞는가?
- 공통모듈 경계와 의존성이 적절한가?
- 정상·경계·오류 시험이 포함되었는가?
- 비밀·개인정보·위험 설정이 들어가지 않았는가?
- 스키마·인터페이스 호환성과 전환 순서가 안전한가?
- 로그·오류·권한이 운영 기준을 따르는가?
- 되돌리기와 관찰 지표가 준비되었는가?

승인 버튼은 책임 있는 검토의 증거여야 한다. 작성자가 자신의 변경을 유일 검토자로 승인하지 않게 직무를 분리한다. 긴급 변경은 통제를 없애는 것이 아니라 승인자를 줄이거나 순서를 조정하되 사후 검토와 기준선 반영을 필수로 한다.

## 자동 검증 연결

저장소 변경 흐름에 다음 검사를 연결할 수 있다.

    변경 요청
      → 형식·정적 검사
      → 단위시험
      → 빌드·의존성 검증
      → 비밀·정책 위반 검사
      → 검토 승인
      → 보호 브랜치 병합
      → 변경 불가 산출물 생성
      → 기준선·배포 후보 연결

검사 실패를 단순 재실행으로 넘기지 않고 재현 원인을 찾는다. 일시적으로 불안정한 시험은 신뢰를 떨어뜨리므로 격리하고 수정 기한을 둔다.

자동화 정의도 코드와 함께 검토한다. 빌드 작업이 외부의 임의 코드를 높은 권한으로 실행하거나 비밀을 로그에 출력하지 않게 한다. 외부 기여자의 변경에는 비밀 제공과 실행 권한을 제한한다.

## 기준선과 버전

기준선(Baseline)은 공식적으로 검토·승인된 특정 시점의 형상 항목 집합이다. 이후 변경은 통제 절차를 거친다. 단순 최신 브랜치와 다르게 승인 상태와 구성 항목이 식별되어야 한다.

릴리스 기준선에는 소스 커밋, 빌드 정의, 의존 잠금, 스키마 변경, 설정 기준, 시험 결과, 산출물 해시를 연결한다. 태그 이름만 만들고 이동 가능하게 두면 기준선 신뢰가 약해진다.

버전 번호는 호환성 의미와 조직 정책을 따른다. 주·부·수정 버전을 사용하는 체계가 있을 수 있지만 모든 프로젝트에 같은 규칙을 강요하지 않는다. 중요한 것은 버전에서 어떤 소스와 산출물이 만들어졌는지 역추적 가능하다는 점이다.

## 산출물 저장소

빌드 산출물은 같은 버전을 다시 빌드해 운영으로 보내기보다 검증된 동일 산출물을 단계별로 승격하는 방식이 재현성에 유리하다. 산출물에 소스 식별자, 빌드 환경, 의존 정보, 생성 시각과 무결성 정보를 부여한다.

개발용 후보, 시험 승인, 운영 승인 상태를 구분하고 권한을 분리한다. 이미 승인된 산출물을 덮어쓰지 않는다. 보존 기간과 폐기 정책, 취약 산출물 회수 절차를 둔다.

산출물 저장소의 접근 키가 소스 저장소보다 덜 중요하다고 생각하면 안 된다. 공격자가 산출물을 바꾸면 검토된 소스와 다른 코드가 배포될 수 있다.

## 병합 충돌 처리

충돌은 두 변경이 같은 논리 영역을 다르게 바꿨다는 신호다. 문자 단위로 한쪽을 선택하기 전에 각 변경의 요구와 시험을 이해한다.

1. 충돌한 기준과 두 변경의 목적을 확인한다.
2. 관련 담당자와 최종 요구 동작을 합의한다.
3. 결과 코드를 새 변경으로 작성한다.
4. 단위·통합시험을 다시 수행한다.
5. 설계·문서·스키마 영향도 함께 반영한다.
6. 해결 근거와 검토자를 기록한다.

자동 생성 파일의 충돌은 원본 선언에서 해결하고 다시 생성한다. 생성 결과만 수동 수정하면 다음 빌드에서 사라질 수 있다.

## 백업·복구와 감사

원격 저장소가 있다고 백업이 자동 완성되는 것은 아니다. 관리자 실수, 악성 삭제, 계정 손상, 서비스 장애를 고려해 별도 보존과 복구 시험을 수행한다.

백업 범위에는 저장소 데이터뿐 아니라 권한·보호 규칙·웹훅·이슈·변경 요청과 산출물 메타데이터가 포함될 수 있다. 복구 목표 시간과 허용 손실 시점을 정하고 주기적으로 다른 위치에 복원해 검증한다.

감사 로그에는 로그인, 권한 변경, 보호 규칙 변경, 강제 갱신, 기준선 생성·삭제, 산출물 승격을 남긴다. 로그 접근과 보존을 통제하고 시각을 동기화한다.

## 형상관리 환경 구축 절차

### 1단계: 정책–도구 매핑

조직 방침을 역할, 저장소 규칙, 승인, 자동검사, 감사 기능에 매핑한다. 도구가 지원하지 않는 정책은 보완 절차 또는 다른 도구로 구현한다.

### 2단계: 저장소와 항목 등록

공식 저장소를 만들고 구조, 제외 규칙, 소유자, 기본 문서를 설정한다. 기존 파일을 가져오기 전에 비밀·대용량·생성물과 라이선스를 점검한다.

### 3단계: 계정과 권한

중앙 인증을 연계하고 역할별 최소 권한, 다중요소 인증, 외부 협력자 만료를 설정한다. 관리자·자동화 계정을 분리한다.

### 4단계: 브랜치·변경 통제

기준 브랜치 보호, 직접 쓰기 금지, 필수 검토, 자동검사, 서명·커밋 정책을 구성한다. 긴급 변경 절차도 별도로 시험한다.

### 5단계: 빌드·산출물 연계

소스 식별자에서 자동 빌드하고 시험 보고서와 변경 불가 산출물을 연결한다. 승격 권한과 보존을 설정한다.

### 6단계: 백업·감사·복구

백업과 로그 수집을 활성화하고 권한 변경·저장소 복원·산출물 검증 시나리오를 시험한다.

### 7단계: 시범 운영과 교육

작은 프로젝트에서 작업 브랜치–검토–병합–기준선–복구를 수행한다. 사용자 교육과 운영자 대응 절차를 개선한 뒤 정식 적용한다.

## 개발환경 구축하기의 적용 절차와 판단 기준

    방침·대상 확인
       ↓
    형상 항목·소유자 식별
       ↓
    저장소 구조와 역할 설계
       ↓
    브랜치·검토·자동검증 구성
       ↓
    기준선·산출물·배포 추적 연결
       ↓
    백업·감사·긴급변경 시험
       ↓
    시범 운영과 개선

판단 기준은 변경 추적성, 승인된 항목의 완전성, 최소 권한과 직무 분리, 깨끗한 빌드 재현성, 기준선–산출물 연결, 정책 우회 방지, 백업·복구 가능성, 운영자가 지속 관리할 수 있는 단순성이다.

## 구체 업무 시나리오

주문 서버 저장소를 처음 구성한다고 하자.

1. 응용 소스, 시험, DB 마이그레이션, API 문서를 형상 항목으로 등록한다.
2. 비밀은 저장소에서 제외하고 환경별 비밀 참조만 관리한다.
3. 개발자는 작업 브랜치에 쓰고 기준 브랜치는 동료 승인과 자동시험 없이는 병합할 수 없게 한다.
4. 스키마 변경에는 이전·되돌리기와 호환 시험을 필수 항목으로 둔다.
5. 병합된 커밋으로 산출물을 한 번 만들고 시험·운영 후보로 같은 파일을 승격한다.
6. 릴리스 기준선에는 커밋, 스키마 버전, 설정 기준, 시험 보고서, 산출물 해시를 연결한다.
7. 저장소 삭제와 권한 오부여를 가정한 복구·감사 시험을 수행한다.

## 산출물과 체크리스트

산출물은 형상관리 계획서, 형상 항목 목록, 저장소 구조·제외 규칙, 역할·권한표, 브랜치·병합 정책, 변경 요청 양식, 기준선·버전 규칙, 자동검증 흐름, 산출물 관리표, 백업·복구 결과서다.

- [ ] 소스 외 설정·스키마·문서·빌드 정의까지 항목을 식별했다.
- [ ] 비밀·생성물·대용량 바이너리의 처리 규칙이 있다.
- [ ] 개인별 계정과 최소 권한·직무 분리가 적용되었다.
- [ ] 보호 브랜치의 직접 쓰기와 자기 단독 승인이 제한된다.
- [ ] 변경 요청에 영향·시험·되돌리기 정보가 포함된다.
- [ ] 자동검사 실패가 병합을 막고 우회가 감사된다.
- [ ] 기준선에서 소스·의존·설정·시험·산출물을 역추적할 수 있다.
- [ ] 승인 산출물을 덮어쓸 수 없다.
- [ ] 백업에 정책·권한·메타데이터가 포함되고 복구를 시험했다.
- [ ] 긴급 변경은 사후 검토와 주 흐름 반영을 요구한다.

## 자주 발생하는 함정

- 버전관리 도구 설치를 형상관리 전체로 본다.
- 소스만 형상 항목으로 지정하고 스키마·설정·빌드 정의를 놓친다.
- 개인 비밀정보를 실수로 커밋한 뒤 파일 삭제만 하고 비밀을 교체하지 않는다.
- 보호 브랜치를 두었지만 관리자가 일상적으로 우회한다.
- 브랜치를 오래 유지해 통합 시점에 대규모 충돌이 난다.
- 충돌 표시만 없애고 양쪽 업무 요구가 모두 살아 있는지 시험하지 않는다.
- 릴리스마다 다시 빌드해 시험한 파일과 운영 파일이 달라진다.
- 태그가 가리키는 커밋을 변경할 수 있어 기준선이 이동한다.
- 자동화 계정에 소스·산출물·운영 전체 권한을 준다.
- 저장소 원격 복제만 믿고 권한·이슈·규칙의 별도 복구를 시험하지 않는다.

## 확인 문제

1. 형상관리의 식별·통제·상태 기록·감사 활동을 설명하라.
2. 소스 외에 형상 항목으로 관리해야 할 대상을 다섯 가지 쓰라.
3. 개발자·검토자·릴리스·관리자 역할을 분리해야 하는 이유는 무엇인가?
4. 보호 브랜치에 적용할 규칙을 네 가지 이상 쓰라.
5. 좋은 변경 요청과 코드 검토에 포함할 정보를 설명하라.
6. 기준선과 단순 최신 브랜치의 차이는 무엇인가?
7. 검증된 산출물을 재빌드하지 않고 승격하는 이유를 설명하라.
8. 병합 충돌을 안전하게 해결하는 절차를 쓰라.
9. 저장소 백업에 파일 외 어떤 정보를 포함해야 하는가?
10. 형상관리 환경 구축 완료의 판단 기준을 다섯 가지 쓰라.

## 정답과 해설

1. 항목과 버전을 식별하고, 변경을 승인·검증해 통제하며, 현재 상태와 이력을 기록하고, 승인 기준과 실제가 일치하는지 감사한다.
2. 환경 설정 견본, DB 마이그레이션, 요구·설계·API 문서, 빌드 정의와 잠금 정보, 시험 코드·보고, 실행 산출물 메타데이터를 관리한다.
3. 한 사람이 코드 작성부터 승인·배포·감사까지 단독 수행하면 오류·부정과 우회가 발견되기 어렵기 때문이다.
4. 직접 쓰기 금지, 동료 검토, 자동 빌드·시험, 최신 기준과 충돌 해결, 필수 서명·이슈 연결, 관리자 우회 감사를 적용한다.
5. 목적·요구, 영향 범위, 변경 내용, 시험 결과, 스키마·인터페이스·보안 영향, 배포와 되돌리기를 기록하고 검토자는 설계·시험·비밀·호환성을 확인한다.
6. 최신 브랜치는 현재 변경 집합이고, 기준선은 특정 형상 항목 집합이 공식 검토·승인되어 이후 변경이 통제되는 상태다.
7. 같은 소스라도 빌드 시점과 의존·환경이 달라질 수 있다. 시험한 바로 그 변경 불가 파일을 승격해야 검증 결과와 운영 산출물이 일치한다.
8. 두 변경 목적을 확인하고 담당자와 최종 동작을 합의한 뒤 결과 코드를 작성해 관련 시험·문서·스키마를 다시 검증하고 근거를 기록한다.
9. 권한·보호 규칙, 변경 요청·이슈, 웹훅·자동화 설정, 태그·기준선, 감사 기록과 산출물 메타데이터를 포함한다.
10. 항목 완전성, 변경 추적·승인, 최소 권한·직무 분리, 자동검증, 재현 빌드, 기준선–산출물 연결, 정책 우회 감사, 복구 가능성을 본다.

## 핵심 요약

- **형상관리 방침과 운영정책에 맞는 환경 구축**은 정책을 저장소 구조, 역할, 브랜치 보호, 자동검증, 기준선과 감사 기능으로 구현하는 일이다.
- 소스뿐 아니라 설정, 스키마, 문서, 빌드 정의, 시험과 산출물도 형상 항목으로 식별한다.
- 개인별 최소 권한과 작성–검토–릴리스–관리의 직무 분리를 적용한다.
- 작은 작업 브랜치와 변경 요청, 자동시험을 거쳐 보호 기준에 통합하고 이동하지 않는 기준선을 만든다.
- 검증된 동일 산출물을 승격하고 소스·의존·설정·시험·산출물을 역추적한다.
- **개발환경 구축하기의 적용 절차와 판단 기준**은 정책 준수, 재현성, 추적성, 우회 방지와 실제 복구 가능성을 증거로 확인하는 것이다.
