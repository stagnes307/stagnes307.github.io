01

수행 범위와 목표

이 레슨은 승인된 상세설계를 입력으로 상세설계와 언어·도구로 공통모듈 작성을 수행하고, 여러 기능이 안정적으로 재사용할 수 있도록 낮은 결합도와 높은 응집도의 공통모듈 구현을 달성하는 실무를 다룬다. 공통모듈은 단순히 복사된 코드를 한 파일로 모은 것이 아니라 명확한 책임, 안정된 인터페이스, 일관된 오류·로그·설정 계약을 가진 재사용 단위다.

학습 후에는 공통 후보를 판별하고 상세설계에서 인터페이스·자료형·선후조건을 도출하며, 결합도와 응집도를 평가해 모듈 경계를 조정하고, 코드·문서·기본 검증 산출물을 완성할 수 있어야 한다.

다음 레슨은 공통모듈 테스트 케이스와 조건 명세를 집중적으로 다룬다. 여기서는 구현 중 수행하는 기본 단위 확인만 언급하고 시험 설계 상세는 침범하지 않는다.

02

입력자료와 선행조건

  • 요구사항 추적표와 공통 기능 목록
  • 소프트웨어 상세설계서, 클래스·컴포넌트·시퀀스 설계
  • 데이터 모델과 코드·오류·로그 표준
  • 언어·프레임워크·빌드·품질 규칙
  • 기존 모듈·라이브러리 목록과 중복 분석
  • 모듈 소비자, 호출 빈도, 성능·보안·트랜잭션 요구
  • 형상관리 저장소와 변경 승인 상태

상세설계가 모호하면 임의 구현 전에 설계자와 소비자에게 입력·출력·오류·상태 변화의 의미를 확인한다. 구현이 먼저 고정되면 여러 소비자가 잘못된 계약에 의존하게 된다.

공통모듈 후보는 최소 둘 이상의 사용처가 있다는 이유만으로 선정하지 않는다. 업무 의미가 같고 변경 이유가 같으며 안정적인 계약으로 분리할 수 있는지 본다.

03

공통모듈 후보 식별

공통모듈 후보 식별 · 학습 표 1
판단 질문공통화에 긍정적인 신호경계해야 할 신호
의미여러 기능에서 같은 업무 규칙모양만 비슷하고 의미가 다름
변경 이유동일 정책 변경에 함께 바뀜소비자별 변경 주기가 다름
인터페이스작은 안정 입력·출력옵션·분기 매개변수가 계속 증가
의존성표준 타입과 제한된 포트화면·DB·전역 설정에 직접 결합
재사용 범위모듈·서비스 내 명확한 사용자미래 사용을 추측한 과도한 일반화
시험성외부 효과를 분리해 독립 검증시간·네트워크·전역 상태가 숨음

문자열 공백 제거처럼 의미가 분명한 기술 기능은 공통화하기 쉽다. “모든 주문 계산”을 한 공통 함수에 넣고 채널별 조건을 매개변수로 늘리면 거대한 분기 모듈이 될 수 있다.

세 번째 중복이 생길 때 공통화를 고려한다는 경험칙은 판단 보조일 뿐 절대 규칙이 아니다. 보안 검증처럼 한 번만 있어도 중앙 통제가 필요한 기능도 있고, 우연히 세 번 비슷해도 의미가 다른 기능도 있다.

04

상세설계 검토

상세설계에서 다음 항목을 구현 계약으로 변환한다.

  1. 모듈의 책임과 범위, 하지 않는 일
  2. 공개 함수·클래스·인터페이스 이름과 의미
  3. 입력 자료형, 필수·선택, 단위, 길이와 허용 범위
  4. 출력 자료형, 정렬·정밀도, 값 없음 표현
  5. 정상 선조건과 처리 후 보장해야 할 후조건
  6. 오류 분류와 호출자 조치, 재시도 가능성
  7. 외부 상태 변경, 트랜잭션, 자원 소유권
  8. 성능·동시성·보안·감사 요구
  9. 기존 소비자 호환성과 변경 전략

상세설계와 코드가 다르면 둘 중 하나를 조용히 맞추지 않는다. 변경 필요성을 기록하고 승인된 설계를 갱신한 뒤 추적성을 유지한다.

06

응집도

응집도(Cohesion)는 한 모듈 내부 요소들이 하나의 목적을 위해 얼마나 밀접하게 관련되는지를 나타낸다. 일반적으로 높은 응집도를 지향한다.

낮은 쪽에서 높은 쪽으로 흔히 다음 순서를 학습한다.

응집도 · 학습 표 3
응집도의미예
우연적관련 없는 기능을 임의로 모음기타도구 모듈에 날짜·메일·DB 혼재
논리적비슷한 종류를 선택값으로 모음유형 값으로 모든 입력 기능 분기
시간적같은 시점에 수행할 기능을 모음시작 시 로그·캐시·연결 초기화
절차적같은 제어 순서를 따르는 기능순서는 같지만 데이터 목적이 다름
통신적같은 데이터를 사용하는 기능동일 주문을 출력·저장
순차적한 처리 결과가 다음 입력읽기–정규화–검증 변환 파이프
기능적하나의 명확한 기능 수행세금 계산, 전화번호 정규화

교재에 따라 명칭 번역과 단계 설명이 조금 다를 수 있으나 기능적 응집도가 가장 높고 우연적 응집도가 가장 낮다는 기본 판단을 기억한다.

하나의 공통모듈이 사용자 조회, 파일 저장, 메일 발송까지 모두 수행한다면 변경 이유가 많다. 조회 계약, 저장 포트, 알림 포트로 책임을 나누고 상위 사용 사례가 흐름을 조정하게 한다.

07

결합도

결합도(Coupling)는 모듈 사이의 의존 정도다. 일반적으로 낮은 결합도를 지향한다.

강한 쪽에서 약한 쪽으로 흔히 다음처럼 설명한다.

결합도 · 학습 표 4
결합도의미개선 방향
내용 결합다른 모듈 내부 구현·코드를 직접 참조공개 인터페이스 사용
공통 결합전역 데이터를 여러 모듈이 공유명시적 입력·상태 소유자
외부 결합외부 형식·장치·프로토콜에 공동 의존어댑터와 경계 캡슐화
제어 결합플래그로 상대 처리 흐름을 지시역할별 함수·다형성 분리
스탬프 결합큰 구조 전체를 넘기고 일부만 사용필요한 자료만 전달
자료 결합필요한 단순 데이터만 매개변수로 전달유지
메시지 결합공개 메시지·계약으로 상호작용상태 은닉과 계약 강화

분류 체계에 메시지 결합을 별도로 포함하는지 문헌마다 다를 수 있다. 핵심은 상대 내부와 전역 상태를 알수록 강하고, 작은 공개 계약만 알수록 약하다는 것이다.

항상 매개변수를 원시값으로 잘게 쪼개는 것이 최선은 아니다. 서로 함께 의미를 갖는 값은 불변 값 객체로 묶어 잘못된 조합을 막을 수 있다. 스탬프 결합의 문제는 의미 있는 타입 자체가 아니라 필요 없는 거대한 구조와 내부 필드에 의존하는 것이다.

08

의존성 역전과 포트

공통 업무 로직이 특정 데이터베이스나 외부 통신 구현을 직접 생성하면 독립 재사용과 시험이 어렵다. 필요한 기능을 작은 인터페이스 또는 포트로 정의하고 구현을 외부에서 제공한다.

interface Clock: now() -> Instant

class ExpirationPolicy: constructor(clock: Clock) isExpired(expiration): return expiration <= clock.now()

시간을 직접 전역 호출하지 않고 Clock 포트를 받으면 시험에서 고정 시각을 제공할 수 있다. ExpirationPolicy는 특정 시스템 시간 API에 결합되지 않는다.

의존성 주입 도구를 사용한다고 자동으로 결합도가 낮아지는 것은 아니다. 인터페이스가 지나치게 크거나 구현 세부를 그대로 노출하면 결합은 여전히 강하다.

09

공통 오류 계약

공통모듈은 소비자마다 다른 화면 문구를 직접 만들기보다 의미 있는 오류 분류를 제공한다.

Result<NormalizedPhone, ValidationError>

ValidationError: code: stable machine-readable code field: optional field identifier safeMessage: non-sensitive summary

호출자는 웹 응답, 배치 오류 파일, 화면 메시지 등 자신의 문맥으로 변환한다. 공통모듈이 내부 예외와 스택을 외부에 노출하지 않는다.

예상 가능한 검증 실패와 예상 밖 시스템 오류를 구분한다. 오류를 빈 문자열로 바꾸면 정상 빈 값과 실패가 섞인다. 재시도 가능 여부와 원인 소유 계층도 계약에 포함할 수 있다.

10

설정과 로깅 경계

공통모듈이 임의로 환경 변수나 전역 설정을 읽으면 호출 환경에 숨은 의존이 생긴다. 필요한 정책값을 생성 시 주입하거나 명시적 설정 객체로 받는다. 설정 객체에는 필요한 항목만 포함한다.

모듈 내부에서 모든 입력과 출력을 로그로 남기지 않는다. 개인정보와 비밀이 있을 수 있고 호출자 로그와 중복된다. 모듈은 중요한 보안·운영 사건을 구조화해 전달하거나 로그 포트를 사용하며, 상관 식별자와 민감정보 제외 정책을 따른다.

라이브러리 성격의 공통모듈이 자체 프로세스를 종료하거나 전역 로그 수준을 바꾸면 다른 소비자를 방해한다. 오류는 호출자에게 전달하고 자원·정책 소유권을 분명히 한다.

11

언어·도구 적용

언어 기능은 모듈 계약을 강제하는 데 사용한다.

  • 인터페이스와 접근 제한자로 공개·내부 표면을 구분한다.
  • 불변 값과 열거형으로 유효하지 않은 상태를 줄인다.
  • 제네릭·타입 매개변수는 타입 안전한 재사용이 실제 필요할 때 쓴다.
  • 자동 포맷·정적 분석·컴파일러 경고로 표준을 일관되게 적용한다.
  • 빌드 도구로 공통모듈과 소비자의 버전·의존성을 명시한다.
  • 문서 생성 도구로 공개 API와 예제를 동기화한다.

언어의 고급 기능을 많이 쓰는 것이 공통성의 기준은 아니다. 소비자가 이해하기 쉬운 가장 단순한 공개 계약을 선택한다.

12

구현 절차

1단계: 설계 추적

공통 기능 요구와 상세설계 항목을 구현 작업·함수로 연결한다. 불명확한 입력·출력·오류를 확정한다.

2단계: 경계와 계약 정의

모듈의 책임, 공개 인터페이스, 자료형, 선후조건, 부작용과 의존 포트를 먼저 작성한다. 소비자 대표와 계약을 검토한다.

3단계: 핵심 로직 구현

외부 입출력과 프레임워크 세부를 분리하고 순수한 업무 계산을 우선 구현한다. 오류·경계값을 명시적으로 처리한다.

4단계: 어댑터 구현

데이터베이스·시간·파일·외부 서비스 같은 구체 기술은 포트 구현으로 둔다. 최소 권한과 시간 제한, 자원 정리를 적용한다.

5단계: 결합도·응집도 검토

전역 상태, 플래그 분기, 거대한 매개변수, 순환 의존, 여러 변경 이유를 찾는다. 기능적 책임으로 분해하고 필요한 값만 전달한다.

6단계: 기본 검증과 문서화

빌드·정적 검사·대표 단위 확인을 통과하고 공개 API, 예제, 오류표, 버전 호환성을 문서화한다. 상세 테스트 케이스는 다음 레슨에서 확정한다.

7단계: 소비자 통합

대표 소비자에서 적용해 계약이 충분한지 확인한다. 소비자별 예외 처리를 공통모듈에 무리하게 넣지 않는다.

13

구체 업무 시나리오

세 개 서비스가 사용하는 “금액 배분” 규칙을 공통모듈로 만든다고 하자. 총금액을 비율대로 나누고 반올림 잔액을 정해진 우선순위에 배정해야 한다.

  1. 상세설계에서 통화, 최소 단위, 비율 합계, 반올림, 잔액 배정 규칙을 확인한다.
  2. 입력은 Money, AllocationRatio 목록, 정책으로 제한하고 DB 엔티티 전체를 받지 않는다.
  3. 출력은 수신자별 Money 목록이며 총합이 원래 금액과 같다는 후조건을 둔다.
  4. 비율 합계 오류, 음수 금액, 빈 수신자 목록을 분류된 검증 오류로 반환한다.
  5. 계산 모듈은 DB 저장·알림을 하지 않는다. 상위 사용 사례가 결과 저장과 통지를 조정한다.
  6. 통화별 최소 단위 정책이 바뀌어도 외부 DB·화면과 무관하게 모듈만 수정할 수 있게 한다.

allocate(total, shares, roundingPolicy): validate total and shares rawAmounts = calculate each proportional amount rounded = roundingPolicy.round(rawAmounts) remainder = total - sum(rounded) adjusted = roundingPolicy.distribute(remainder, rounded) assert sum(adjusted) == total return adjusted

의사코드는 산술 원리만 보여 주며 실제 금액 타입은 고정 정밀도와 통화 규칙을 사용한다.

자주 발생하는 함정

  • 복사된 코드가 있다는 이유만으로 업무 의미가 다른 기능을 공통화한다.
  • 미래의 모든 경우를 예상해 옵션과 추상 계층을 과도하게 만든다.
  • 공통모듈이 화면, DB, 외부 호출, 로그를 모두 담당해 응집도가 낮아진다.
  • 기능 선택 플래그가 늘어 제어 결합이 강해진다.
  • DB 엔티티 전체를 넘겨 일부 필드만 사용해 스탬프 결합을 만든다.
  • 인터페이스를 만들었지만 구현의 모든 메서드를 그대로 노출한다.
  • 전역 설정과 시스템 시간을 내부에서 읽어 숨은 의존성을 만든다.
  • 검증 실패를 빈 값으로 바꿔 정상과 오류를 구분하지 못한다.
  • 공통모듈 버전을 변경하면서 소비자 호환성과 이전 계획을 만들지 않는다.
  • 기능적 응집도와 자료·메시지 결합의 방향을 반대로 외운다.

확인 문제

  1. 공통모듈 후보를 판단할 기준을 네 가지 쓰라.
  2. 상세설계에서 공개 인터페이스 명세로 옮길 항목을 여섯 가지 쓰라.
  3. 우연적·논리적·시간적·절차적·통신적·순차적·기능적 응집도를 높은 방향으로 설명하라.
  4. 내용·공통·외부·제어·스탬프·자료 결합의 차이를 설명하라.
  5. 큰 DB 엔티티 대신 필요한 값 객체를 전달하면 어떤 결합 문제가 줄어드는가?
  6. 의존성 역전과 포트가 공통모듈 시험성과 재사용성에 도움이 되는 이유는 무엇인가?
  7. 공통 오류 계약에서 안정된 코드와 안전한 메시지가 필요한 이유를 쓰라.
  8. 금액 배분 모듈이 DB 저장과 알림까지 담당하지 않아야 하는 이유는 무엇인가?
  9. 결합도·응집도 검토에서 찾을 코드 징후를 다섯 가지 쓰라.
  10. 공통모듈 구현 산출물을 다섯 가지 이상 쓰라.

정답과 해설

  1. 업무 의미, 변경 이유, 안정된 입력·출력, 소비자 수, 외부 의존성, 독립 시험 가능성을 본다.
  2. 책임, 입력 타입·범위·단위, 출력, 선후조건, 오류, 부작용·트랜잭션, 자원 소유권, 성능·보안 요구를 옮긴다.
  3. 일반적으로 우연적→논리적→시간적→절차적→통신적→순차적→기능적 순으로 응집도가 높아진다. 기능적은 하나의 명확한 목적에 가장 밀접하다.
  4. 내부 구현 직접 참조가 내용, 전역 공유가 공통, 외부 형식 공동 의존이 외부, 플래그로 흐름 지시가 제어, 큰 구조 일부 사용이 스탬프, 필요한 값만 전달하는 것이 자료 결합이다.
  5. 필요 없는 구조와 필드에 의존하는 스탬프 결합을 줄인다. 의미 있는 작은 값 객체는 잘못된 조합도 막을 수 있다.
  6. 핵심 로직이 DB·시간·네트워크 구현을 직접 알지 않고 작은 계약만 의존하여 대체 구현과 시험 대역을 주입할 수 있기 때문이다.
  7. 소비자가 화면·API·배치 문맥에 맞게 오류를 변환하고, 내부 예외·민감정보 노출 없이 안정적으로 분기하기 위해서다.
  8. 금액 계산이라는 한 책임의 기능적 응집도를 유지하고 저장·알림 기술과의 결합을 줄여 독립 시험·재사용하기 위해서다.
  9. 전역 변수, 다수 기능 플래그, 거대한 매개변수, 특정 DB 직접 생성, 순환 의존, 긴 클래스·함수, 여러 변경 이유를 찾는다.
  10. 후보 분석표, 설계–코드 추적표, 책임 정의, API·오류 명세, 구조도, 결합도·응집도 검토표, 코드·빌드 결과, 사용 가이드를 만든다.
19

핵심 요약

  • 상세설계와 언어·도구로 공통모듈 작성은 책임과 입력·출력·오류·부작용을 먼저 계약으로 만들고 추적 가능한 코드로 구현하는 일이다.
  • 공통화는 코드 모양보다 업무 의미와 변경 이유, 안정된 재사용 경계를 기준으로 한다.
  • 낮은 결합도와 높은 응집도의 공통모듈 구현은 하나의 목적을 모으고 전역·내부 구현·거대한 구조 의존을 줄이는 것이다.
  • 기능적 응집도를 지향하고 내용·공통·제어·스탬프 결합을 자료·메시지 계약으로 개선한다.
  • DB·시간·외부 시스템은 작은 포트와 어댑터로 분리하고 오류·설정·로그의 소유권을 명확히 한다.
  • 산출물은 API·오류 명세, 의존 구조, 추적표, 검토 이력, 코드와 소비자 가이드까지 포함한다.
