FF 원문 제목1-4-2-2. 공통모듈 테스트 케이스와 조건 명세

01

수행 범위와 목표

이 레슨은 구현된 공통모듈의 계약과 위험을 근거로 공통모듈 테스트 케이스와 조건 명세를 작성하고, 실행·판정·회귀에 활용할 수 있도록 공통 모듈 구현하기의 적용 절차와 판단 기준을 확립하는 실무를 다룬다. 공통모듈은 여러 소비자가 사용하므로 작은 결함도 넓게 전파된다. 정상 예시뿐 아니라 경계, 오류, 상태, 동시성, 호환성 조건을 명세해야 한다.

앞 레슨의 결합도·응집도와 구현 구조는 입력으로 사용하되 반복하지 않는다. 다음 서버 프로그램 레슨의 전체 업무 흐름·인터페이스 시험과 배치 시험은 별도 범위이며 여기서는 공통모듈 단위와 공개 계약에 집중한다.

02

입력자료

  • 공통모듈 책임·범위와 공개 API 명세
  • 입력·출력 자료형, 선조건·후조건, 불변식
  • 오류 코드·예외·NULL·자원 소유권 계약
  • 요구사항–설계–코드 추적표
  • 소비자 목록과 대표 사용 시나리오
  • 과거 결함, 위험 분석, 성능·보안 기준
  • 구현 코드와 의존 포트·어댑터 구조

코드만 보고 시험을 작성하면 구현과 같은 오해를 복제할 수 있다. 요구와 설계에서 기대 결과를 독립적으로 도출하고 코드 결과와 비교한다.

03

테스트 조건과 테스트 케이스

테스트 조건(Test Condition)은 검증해야 할 기능·규칙·상태·위험의 항목이다. 테스트 케이스(Test Case)는 그 조건을 실행할 구체 입력, 선행조건, 절차, 기대 결과를 명세한다.

예를 들어 “전화번호 최대 길이를 지킨다”는 테스트 조건이고, 길이 최대-1·최대·최대+1 입력과 기대 결과를 정의한 것이 테스트 케이스다.

테스트 조건과 테스트 케이스 · 학습 표 1
필드내용
케이스 ID추적 가능한 고유 식별자
관련 요구·설계요구사항·규칙·API 항목
목적·조건무엇을 검증하는가
선행조건설정, 의존 상태, 입력 준비
입력 데이터값, 단위, 경계, 데이터 출처
수행 절차호출 순서와 관찰 지점
기대 결과반환값, 오류, 상태 변화, 부작용
종료조건자원·데이터 정리 상태
우선순위위험·회귀 중요도

실제 결과와 기대 결과를 한 칸에 섞지 않는다. 실행 전에 기대값을 확정해야 결과에 맞춰 답을 바꾸는 오류를 막는다.

04

테스트 조건 도출

  1. 공개 함수와 사용 사례별 정상 흐름을 나열한다.
  2. 입력 필드마다 자료형, 필수, 범위, 길이, 형식, 조합 규칙을 찾는다.
  3. 출력 정밀도·정렬·중복·NULL·불변식을 확인한다.
  4. 오류 종류와 호출자의 기대 조치를 나열한다.
  5. 상태가 있다면 허용 전이와 금지 전이를 그린다.
  6. 외부 포트 실패, 시간 제한, 부분 성공과 재시도를 확인한다.
  7. 동시 호출·재진입·자원 수명 요구를 찾는다.
  8. 소비자 버전·이전 데이터와 호환 조건을 찾는다.
  9. 과거 결함과 영향이 큰 규칙을 회귀 조건으로 지정한다.

각 조건은 적어도 한 케이스에 연결되고, 각 요구는 테스트 또는 분석·검토 증거에 연결되어야 한다.

05

동등 분할

동등 분할은 입력 영역을 같은 방식으로 처리될 것으로 예상되는 유효·무효 집합으로 나누고 대표값을 선택한다.

나이 입력이 0~120 정수라면 다음 분할이 있다.

  • 유효: 0~120
  • 무효: 음수
  • 무효: 121 이상
  • 무효: 정수가 아닌 값
  • 별도: NULL 또는 미입력(계약에 따라)

각 값 전부를 시험하지 않고 대표값으로 효율을 높인다. 그러나 서로 다른 업무 규칙이 있는 값들을 한 분할로 묶으면 안 된다. 예를 들어 성인 여부가 19에서 바뀐다면 0~120 전체는 하나의 동등 분할이 아니다.

06

경계값 분석

결함은 비교 연산과 배열·길이 경계에서 자주 발생한다. 최솟값, 최솟값 바로 아래·위, 최댓값 바로 아래·값·위, 빈 값과 한 개를 시험한다.

입력 길이 최대 100이라면 99, 100, 101을 포함한다. 배열 크기 n이면 인덱스 -1, 0, n-1, n을 언어와 안전한 시험환경에서 확인한다.

날짜는 월말, 윤년, 자정, 시간대 전환, 계약 시작·종료 포함 여부를 고려한다. 금액은 0, 최소 통화단위, 최대, 반올림 경계를 시험한다.

경계값은 데이터 타입의 물리 범위와 업무 허용 범위를 모두 본다. 타입이 큰 정수를 담을 수 있어도 업무 최대가 더 작을 수 있다.

07

결정 테이블

여러 조건 조합이 결과를 바꾸면 결정 테이블을 사용한다.

할인 적용 예:

결정 테이블 · 학습 표 2
규칙회원쿠폰 유효최소금액 충족기대 결과
R1예예예회원·쿠폰 정책에 따른 허용 할인
R2예아니오예회원 할인만
R3아니오예예쿠폰 할인만
R4무관무관아니오할인 없음

조건이 n개이면 단순 조합은 빠르게 늘어난다. 불가능·무관 조합을 설계 근거로 합치고 규칙 누락·충돌을 확인한다.

보안 권한처럼 “역할, 객체 소유, 자원 상태, 인증 강도”가 함께 영향을 주는 규칙은 대표 허용과 모든 주요 거부 원인을 포함한다.

08

상태 전이 시험

공통모듈이 상태를 가진다면 상태–사건–다음 상태–출력을 표로 만든다.

CREATED --submit--> SUBMITTED SUBMITTED --approve--> APPROVED SUBMITTED --reject--> REJECTED APPROVED --cancel--> CANCELED (정책 허용 시)

정상 전이뿐 아니라 APPROVED에서 approve 재호출, CREATED에서 cancel 같은 금지 전이를 시험한다. 같은 사건 재호출이 멱등인지 오류인지 계약에 따라 기대값을 정한다.

상태 전이 경로 전체가 중요하면 한 단계 케이스 외에 여러 사건 순서를 포함한 시나리오를 만든다. 시험마다 초기 상태를 독립적으로 준비한다.

09

화이트박스 구조 기준

명세 기반 케이스가 중심이지만 구현의 분기와 예외 경로가 빠졌는지 구조 커버리지로 보완할 수 있다.

  • 문장 커버리지는 실행 가능한 문장이 한 번 이상 수행되었는지 본다.
  • 분기 커버리지는 조건의 참·거짓 경로가 수행되었는지 본다.
  • 조건 커버리지는 복합 조건의 각 개별 조건이 참·거짓을 가져보았는지 본다.
  • 경로 커버리지는 가능한 실행 경로를 고려하지만 반복과 분기가 많으면 전체가 현실적으로 불가능할 수 있다.

커버리지 100%가 요구사항 정확성을 보장하지 않는다. 잘못된 코드도 모든 줄을 실행할 수 있다. 위험 기반 테스트와 변이 시험, 코드 검토를 함께 사용한다.

10

테스트 대역

외부 의존을 분리하기 위해 다음 대역을 사용할 수 있다.

테스트 대역 · 학습 표 3
대역역할
Stub미리 정한 값을 반환해 호출 대상 역할
Mock기대한 호출·인수·횟수 상호작용 검증
Fake단순하지만 실제 동작하는 대체 구현
Spy실제 또는 대체 객체의 호출 정보를 기록

용어는 도구마다 조금 다를 수 있다. 중요한 것은 상태 결과를 검증할지 상호작용을 검증할지 목적을 분명히 하는 것이다.

모든 내부 메서드를 mock으로 확인하면 리팩터링만 해도 시험이 깨진다. 공개 동작과 중요한 외부 효과를 중심으로 검증한다. 데이터 저장 fake가 실제 DB의 제약·트랜잭션과 다를 수 있으므로 별도 통합시험으로 보완한다.

11

테스트 구조

Given–When–Then 또는 Arrange–Act–Assert 구조로 한 케이스의 준비, 단일 행동, 검증을 구분한다.

test "합계는 배분 결과 합과 같다": given total = Money(100) and shares = [1, 1, 1] when result = allocator.allocate(total, shares, policy) then sum(result.amounts) == total and result.size == 3

한 시험에서 너무 많은 행동을 순차 수행하면 어디서 실패했는지 알기 어렵다. 단, 상태 전이 시나리오는 의도적으로 여러 사건을 검증할 수 있으며 단계별 기대를 기록한다.

시험 이름은 조건과 기대를 표현한다. test1보다 “최대 길이 초과 시 TOO_LONG을 반환한다”가 실패 의미를 바로 알려 준다.

12

테스트 데이터

테스트 데이터는 코드 안의 작은 값, 빌더·팩터리, 별도 고정 파일 등으로 관리할 수 있다. 개인정보를 복사하지 않고 합성 데이터로 만든다.

시간, 난수, 고유 ID가 결과에 영향을 주면 포트를 통해 고정값을 제공한다. 실행 시각과 순서에 따라 결과가 달라지는 비결정적 시험을 피한다.

공용 DB 상태에 의존하지 않고 각 케이스가 필요한 데이터를 준비·정리한다. 병렬 실행에서도 충돌하지 않도록 고유 키와 독립 트랜잭션을 사용한다.

인코딩·다바이트, 빈 문자열·공백, NULL, 중복, 매우 큰 값, 잘못된 형식과 업무상 경계값을 데이터 세트에 포함한다.

13

오류·보안 조건

공통모듈 오류 케이스는 다음을 포함한다.

  • 필수 입력 누락과 자료형·길이·범위 오류
  • 허용되지 않은 상태와 조합
  • 의존 포트 시간 초과·연결 실패·잘못된 응답
  • 부분 결과와 자원 정리
  • 민감정보가 오류·로그에 포함되지 않음
  • 권한 판단 실패가 허용으로 바뀌지 않음
  • 같은 요청 재호출의 중복 효과

악성 입력을 실제 시스템 공격에 쓸 수 있는 형태로 상세 재현할 필요 없이, 구조화 API와 입력 검증이 명령·경로로 해석되지 않는지 안전한 시험 문자열과 모의 의존으로 확인한다.

로그 검증은 전체 메시지 문자열을 고정하기보다 안정된 사건 코드와 민감 필드 부재를 확인한다. 내부 구현 문구 변경에 불필요하게 결합하지 않는다.

14

비기능 조건

성능 조건은 대표·최대 입력에서 응답 시간, 처리량, 메모리 상한을 명시한다. 개발자 장비의 한 번 측정만 합격 기준으로 쓰지 않고 통제된 환경과 반복 측정을 사용한다.

동시성 조건은 여러 호출이 상태를 공유할 때 결과 정확성, 경쟁, 교착, 자원 누수를 확인한다. 순서가 중요하면 장벽이나 테스트용 동기화 포인트로 재현 가능하게 만든다.

호환성 조건은 이전 소비자, 직렬화 형식, 설정 기본값, 오류 코드가 새 버전에서도 약속대로 동작하는지 본다. 폐기 예정 기능은 경고와 전환 기간을 검증한다.

15

공통 모듈 구현하기의 적용 절차와 판단 기준

1단계: 기준 분석

요구·설계·API·위험을 검토해 테스트 조건 목록과 추적 ID를 만든다.

2단계: 기법 선정

입력 범위에는 동등 분할·경계값, 조건 조합에는 결정 테이블, 상태에는 전이, 구현 누락에는 구조 커버리지를 선택한다.

3단계: 케이스 명세

선행조건, 입력, 절차, 기대 반환·상태·부작용·오류, 정리를 독립적으로 작성한다.

4단계: 자동화 구현

공개 API를 통해 시험하고 외부 의존은 목적에 맞는 대역으로 분리한다. 고정 시간·난수와 독립 데이터를 사용한다.

5단계: 실행과 결함 기록

깨끗한 빌드에서 반복 실행하고 기대와 실제 차이를 결함으로 남긴다. 실패를 무조건 시험 코드 문제로 보지 않는다.

6단계: 충분성 평가

요구 추적, 위험 우선순위, 경계·오류·상태, 커버리지와 변이 결과를 종합한다. 숫자 하나만으로 종료하지 않는다.

7단계: 회귀 묶음 확정

빠른 필수 묶음과 전체 묶음, 비기능 묶음을 분리하고 형상관리·자동 빌드에 연결한다.

판단 기준은 요구·위험 추적성, 기대 결과의 독립성, 경계·오류 완전성, 반복 가능성과 격리, 실패 원인의 명확성, 실행 시간, 소비자 호환성이다.

자주 발생하는 함정

  • 테스트 조건과 구체 테스트 케이스를 같은 개념으로 본다.
  • 구현 코드를 복사해 기대값을 계산하여 같은 오류를 놓친다.
  • 정상 대표값 하나만 시험하고 최대±1 경계를 빠뜨린다.
  • 모든 조건 조합을 무작정 만들거나, 반대로 중요한 조합을 “무관” 처리한다.
  • 커버리지 100%를 요구사항 정확성의 증명으로 본다.
  • 내부 메서드 호출 횟수를 과도하게 mock 검증해 리팩터링에 취약해진다.
  • 현재 시각·실제 네트워크·공용 DB에 의존해 간헐적으로 실패한다.
  • 시험 순서를 바꾸면 실패하는 공유 상태를 방치한다.
  • 오류 코드만 보고 자원·부분 상태·민감 로그를 검증하지 않는다.
  • 실패한 시험을 반복 실행해 우연히 통과하면 해결된 것으로 본다.

  2. 테스트 케이스 명세에 포함할 필드를 여섯 가지 쓰라.
  3. 동등 분할과 경계값 분석을 나이 0~120 입력에 적용하라.
  4. 결정 테이블이 적합한 상황과 조합 축소 시 주의점을 쓰라.
  5. 상태 전이 시험에서 정상 전이 외에 무엇을 확인해야 하는가?
  6. 문장·분기·조건 커버리지의 차이와 한계를 설명하라.
  7. Stub, Mock, Fake, Spy의 역할을 구분하라.
  8. 시간·난수·외부 시스템을 통제해야 하는 이유는 무엇인가?
  9. 공통모듈 테스트 종료를 커버리지 하나로 결정하면 안 되는 이유는 무엇인가?
  10. 공통모듈 시험 산출물과 완료 판단 기준을 다섯 가지 쓰라.

정답과 해설

  1. “최대 길이를 지킨다”는 검증 항목이 조건이고 최대-1·최대·최대+1 입력, 절차, 기대 오류를 적은 것이 케이스다.
  2. ID, 관련 요구, 목적·조건, 선행조건, 입력, 절차, 기대 결과, 종료조건, 우선순위를 포함한다.
  3. 유효 0~120, 무효 음수·121 이상·비정수로 나누고 -1,0,1,119,120,121과 NULL 정책을 시험한다.
  4. 여러 조건 조합이 결과를 바꿀 때 적합하다. 불가능·무관 조합을 근거 없이 제거하지 말고 규칙 누락과 충돌을 확인한다.
  5. 금지 전이, 동일 사건 재호출, 여러 단계 경로, 오류 뒤 상태 불변과 초기 상태 독립성을 확인한다.
  6. 문장은 각 문장, 분기는 참·거짓 경로, 조건은 복합식의 개별 조건 참·거짓을 본다. 모두 명세의 누락과 기대값 오류를 보장하지 않는다.
  7. Stub은 정한 반환, Mock은 기대 상호작용, Fake는 단순 동작 구현, Spy는 호출 기록을 제공한다. 도구별 명칭은 다를 수 있다.
  8. 실행 시점과 환경에 따른 우연한 차이를 제거해 실패를 재현하고 로직 결함인지 외부 장애인지 구분하기 위해서다.
  9. 코드 모든 줄을 실행해도 요구가 빠지거나 기대 결과가 틀릴 수 있다. 요구 추적, 위험, 경계·오류, 변이와 코드 검토를 종합한다.
  10. 조건·추적표, 케이스·데이터, 결정·상태표, 자동화 코드, 결과·결함·커버리지, 회귀 묶음을 만들고 추적성·반복성·격리·위험 충분성으로 판단한다.

핵심 요약

  • 공통모듈 테스트 케이스와 조건 명세는 공개 계약과 위험에서 검증 항목을 도출하고 구체 입력·절차·기대 결과로 만드는 일이다.
  • 동등 분할·경계값·결정 테이블·상태 전이와 구조 커버리지를 목적에 맞게 조합한다.
  • 테스트 대역은 외부 의존을 통제하되 내부 구현보다 공개 동작과 중요한 효과를 검증한다.
  • 시간·난수·데이터·자원을 격리해 반복 가능하고 순서 독립적인 자동시험을 만든다.
  • 반환값뿐 아니라 오류, 상태, 부작용, 자원 정리, 민감정보 부재와 호환성을 확인한다.
  • 공통 모듈 구현하기의 적용 절차와 판단 기준은 요구·위험 추적성, 경계·오류 충분성, 재현성과 유지 가능한 회귀 묶음으로 평가한다.
