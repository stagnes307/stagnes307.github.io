# 1-4-3-1. 업무 프로세스 맵과 세부 프로세스 확인 · 언어·도구로 업무 프로그램 구현

## 수행 범위와 목표

이 레슨은 서버 프로그램 구현 전에 **업무 프로세스 맵과 세부 프로세스 확인**을 통해 행위자·입력·처리·판단·예외·산출물을 정확히 파악하고, 확인된 상세설계와 개발 표준에 따라 **언어·도구로 업무 프로그램 구현**을 수행하는 실무를 다룬다. 목표는 화면이나 데이터베이스 구조를 그대로 코드로 옮기는 것이 아니라 업무 규칙과 상태 전이를 추적 가능한 서버 로직으로 만드는 것이다.

학습 후에는 프로세스 맵의 각 단계를 구현 단위와 트랜잭션 경계로 매핑하고, 표현–응용–업무–데이터 접근 책임을 분리하며, 정상·예외 흐름과 외부 연동을 구현하고 산출물과 자체 점검 결과를 제시할 수 있어야 한다.

다음 레슨은 잠재적 보안 취약성 제거와 내부 기능·인터페이스 테스트를 집중적으로 다룬다. 여기서는 기본 입력·권한·오류 계약은 적용하되 상세 보안·시험 기법을 주범위로 확장하지 않는다.

## 입력자료와 선행조건

- 요구사항 명세와 인수조건
- 업무 프로세스 맵, 세부 프로세스·업무 규칙서
- 화면·API·데이터·인터페이스 상세설계
- 공통모듈 API와 오류·코드 표준
- 데이터 모델, 트랜잭션·동시성 정책
- 개발 언어·프레임워크·코딩·로그 표준
- 외부 시스템 계약과 모의 환경
- 형상관리·빌드·검토 절차

프로세스 맵과 상세설계가 서로 다르면 구현자가 임의로 하나를 선택하지 않는다. 실제 업무 담당자와 설계자에게 차이를 확인하고 승인된 기준을 갱신한다.

## 업무 프로세스 맵 읽기

업무 프로세스 맵은 업무의 시작 사건부터 종료까지 참여자와 활동, 판단, 데이터 이동을 시각화한다.

    [고객 주문 제출]
          ↓
    주문 형식·고객 상태 확인
          ↓
       재고 충분?
       ├─ 아니오 → 품절 안내 → 종료
       └─ 예
          ↓
    가격·할인 확정
          ↓
    주문 저장 및 재고 예약
          ↓
    결제 요청
       ├─ 실패 → 예약 해제·실패 기록
       └─ 성공 → 주문 확정·통지

맵을 읽을 때 상자 이름만 보지 않고 다음을 확인한다.

- 시작 사건과 완료·중단 종료 조건
- 업무 행위자와 시스템·부서별 책임
- 각 활동의 입력·출력과 데이터 소유자
- 판단 조건, 우선순위, 기본 경로
- 반복·병렬·대기·시간 제한
- 예외와 취소·보상 흐름
- 사람 승인과 외부 시스템 인계
- 단계별 기록·통제 합계와 산출물

화살표가 있다고 모두 동기 호출인 것은 아니다. 메시지, 배치, 사람 승인처럼 대기 시간이 긴 흐름은 상태를 저장하고 나중에 이어야 한다.

## 세부 프로세스 확인표

| 단계 | 주체 | 입력 | 처리 규칙 | 출력·상태 | 오류·보상 |
|---|---|---|---|---|---|
| 주문 접수 | 고객/서버 | 주문 항목 | 필수·수량 검증 | 접수 명령 | 형식 오류 반환 |
| 재고 확인 | 주문 서비스 | 상품·수량 | 가용 수량 비교 | 가능/불가 | 품절 종료 |
| 금액 확정 | 가격 정책 | 고객·항목 | 가격·할인 기준일 | 총액 | 정책 오류 |
| 예약 | 재고 서비스 | 주문·수량 | 중복 방지·원자성 | 예약 ID | 실패 시 미진행 |
| 결제 | 외부 결제 | 금액·주문 ID | 중복 방지 키 | 승인/거부 | 시간 초과 확인 |
| 확정 | 주문 서비스 | 승인 결과 | 허용 상태 전이 | 확정 주문 | 실패 시 보상·조사 |

각 단계의 규칙은 자연어 “적절히 처리”가 아니라 입력 범위, 조건, 결과, 책임자를 명시한다. 결정 테이블이나 상태 전이표가 있으면 함께 검토한다.

## 행위자와 권한 확인

업무 행위자는 고객, 상담원, 승인자, 외부 서비스, 배치 작업처럼 서로 다른 신원과 책임을 가진다. 서버 코드에서는 요청자가 누구인지와 어떤 업무 행위를 할 수 있는지 분리해 확인한다.

프로세스 맵의 같은 “승인” 단계라도 작성자와 승인자가 달라야 하는 직무 분리 규칙이 있을 수 있다. 화면에 버튼이 보이는지보다 서버 업무 정책에서 주체·대상·상태를 검사한다.

서비스 간 호출은 사용자 권한을 전달할지 서비스 자체 권한으로 수행할지 계약을 정한다. 서비스 계정에 전체 데이터 권한을 주지 않고 목적별 최소 범위를 사용한다.

## 입력·출력과 데이터 소유

각 데이터가 어느 시스템의 원본인지 정한다. 고객 주소를 주문이 복사해 주문 당시 이력을 보존할 수 있지만, 고객 마스터와 주문 사본은 변경 규칙이 다르다.

클라이언트가 보낸 가격·할인·권한 값을 신뢰하지 않고 서버의 권한 있는 원천에서 다시 계산한다. 외부 시스템 응답도 자료형·필수·업무 상태를 검증한다.

출력에는 소비자에게 필요한 필드만 포함한다. 내부 키, 관리자 메모, 원가, 기술 오류를 전체 객체 자동 직렬화로 내보내지 않는다. API 응답 모델과 내부 데이터 모델을 분리한다.

데이터 단위, 정밀도, 시간대, 코드값, NULL 의미를 명시한다. 금액은 통화와 최소 단위, 시각은 기준 시간대와 저장 표현을 확인한다.

## 업무 규칙 명세

규칙은 조건–행동–결과로 표현한다.

| 규칙 ID | 조건 | 행동 | 결과 |
|---|---|---|---|
| ORD-01 | 항목이 하나 이상이고 수량이 양수 | 접수 계속 | 검증 통과 |
| ORD-02 | 고객 등급과 기준일이 할인 대상 | 할인 정책 적용 | 할인 금액 |
| ORD-03 | 가용 재고가 요청 수량 이상 | 원자적으로 예약 | 예약 ID |
| ORD-04 | 결제 승인 | 주문 상태 확정 | CONFIRMED |
| ORD-05 | 결제 거부 | 예약 해제 요청 | PAYMENT_FAILED |

규칙 충돌 시 우선순위와 승인자를 확인한다. 할인 여러 개를 합산하는지 가장 큰 하나만 적용하는지 같은 조건을 임의로 구현하지 않는다.

규칙값을 코드에 고정할지 설정·데이터로 관리할지는 변경 빈도와 감사 요구를 본다. 외부 설정은 형식·범위·버전을 검증하고 잘못된 값에서 안전하게 실패해야 한다.

## 상태 전이

업무 객체의 상태와 허용 전이를 명시한다.

    RECEIVED
      ├─ reserve success → RESERVED
      └─ invalid/out-of-stock → REJECTED

    RESERVED
      ├─ payment approved → CONFIRMED
      ├─ payment denied → PAYMENT_FAILED
      └─ timeout/cancel → CANCEL_PENDING

    CONFIRMED
      └─ authorized cancel → CANCEL_PENDING → CANCELED

문자열 상태를 아무 곳에서나 대입하지 않고 업무 메서드가 현재 상태와 행위자를 확인해 전이한다. 이미 확정된 주문에 승인 결과가 중복 도착하면 멱등하게 기존 결과를 반환할지 오류로 기록할지 계약을 정한다.

상태 변경과 감사 기록이 함께 성공해야 하는 경우 같은 트랜잭션 또는 신뢰 가능한 사건 기록 방식으로 처리한다.

## 구현 구조

서버 업무 프로그램을 다음 책임으로 나눌 수 있다.

| 영역 | 책임 | 피해야 할 것 |
|---|---|---|
| 표현 계층 | 요청 파싱·형식 검증·응답 변환 | 업무 규칙과 DB 직접 조작 |
| 응용 계층 | 사용 사례 순서·트랜잭션·협력 조정 | 화면·프로토콜 세부 |
| 도메인 영역 | 상태·불변식·업무 계산 | 프레임워크·저장 구현 결합 |
| 데이터 접근 | 저장·조회 계약 구현 | 권한·업무 상태 임의 판단 |
| 외부 어댑터 | 외부 계약 변환·시간 제한 | 외부 모델을 내부 전체로 전파 |

계층 수를 기계적으로 늘리는 것이 목적은 아니다. 서로 다른 변경 이유를 분리하고 의존 방향을 핵심 업무 쪽으로 향하게 한다.

## 사용 사례 구현 의사코드

    function placeOrder(actor, request):
        command = requestMapper.validateAndMap(request)
        customer = customerReader.findActive(actor.customerId)
        pricedOrder = pricingPolicy.price(customer, command.items)

        transaction:
            order = Order.receive(customer.id, pricedOrder)
            reservation = inventory.reserve(
                order.id,
                order.requiredItems,
                idempotencyKey=order.id
            )
            order.markReserved(reservation.id)
            orderRepository.save(order)
            eventStore.append(OrderReserved(order.id))

        paymentRequest = paymentPort.request(
            order.id,
            order.total,
            idempotencyKey=order.id
        )
        return accepted(order.id, paymentRequest.trackingId)

외부 결제를 데이터베이스 트랜잭션 안에서 오래 기다리지 않는다. 결제 결과는 별도 흐름으로 받아 현재 상태와 중복을 검증한 뒤 확정·실패 전이를 수행한다. 실제 설계가 동기 결제를 요구하면 시간 제한과 실패 불확실성을 명시한다.

## 트랜잭션 경계

트랜잭션은 하나의 업무 불변식을 지켜야 하는 변경을 묶는다. 주문과 재고가 서로 다른 시스템이면 단일 DB 트랜잭션으로 묶을 수 없으므로 메시지·상태·보상과 멱등성으로 최종 일관성을 설계한다.

트랜잭션을 사용자 입력 대기나 외부 네트워크 호출까지 유지하면 잠금이 길어진다. DB 안의 읽기–검증–변경은 가능한 짧게 묶고 외부 결과는 상태 기계로 이어 간다.

실패 후 단순 롤백으로 복구되지 않는 외부 효과에는 보상 작업이 필요하다. 보상은 원래 작업의 완전한 시간 역행이 아니라 업무상 상쇄 동작이며 실패·재시도도 관리해야 한다.

## 동시성 판단

두 사용자가 마지막 재고를 동시에 주문할 수 있다. “조회 결과 재고가 1이므로 둘 다 통과”하지 않도록 조건부 원자 갱신, 잠금, 버전 검증 등 데이터 저장소가 제공하는 동시성 수단을 사용한다.

낙관적 방식은 읽은 버전이 바뀌었으면 갱신을 거부하고 재시도·사용자 안내한다. 비관적 방식은 필요한 범위에 잠금을 두지만 대기와 교착 위험을 관리한다. 업무 충돌 빈도와 처리량으로 선택한다.

같은 외부 요청이 재전송될 수 있으므로 요청 식별자와 업무 유일성으로 중복 주문을 막는다. “버튼을 한 번만 누른다”는 전제는 서버 통제가 아니다.

## 외부 인터페이스 구현

외부 시스템 계약의 요청·응답·오류·시간 제한·재시도·중복 의미를 어댑터에서 내부 모델로 변환한다. 외부 코드값과 내부 상태를 직접 동일 열거형으로 공유하면 상대 변경이 핵심 업무에 퍼진다.

시간 초과는 실패 확정과 다를 수 있다. 결제 요청 응답을 못 받았지만 외부에서는 성공했을 수 있으므로 같은 중복 방지 키로 상태 조회·재확인한다. 무조건 새 결제를 생성하지 않는다.

재시도는 일시적 오류에만 제한 횟수와 지연을 두고, 형식 오류·권한 거부에는 반복하지 않는다. 회로 차단과 큐로 외부 장애가 내부 자원을 고갈시키지 않게 한다.

## 오류와 로그

업무 오류, 검증 오류, 외부 일시 오류, 내부 시스템 오류를 구분한다. 표현 계층은 안정된 공개 오류 코드와 안전한 메시지로 변환하고 내부 스택·DB 구조를 노출하지 않는다.

로그에는 주문 ID, 상관 ID, 주체, 상태 전이, 외부 추적 ID, 결과를 구조화해 남긴다. 카드 정보, 비밀번호, 전체 토큰과 개인정보 원문을 기록하지 않는다.

정상 업무 거부와 시스템 실패를 같은 심각도로 대량 경보하지 않는다. 하지만 반복되는 비정상 권한 거부와 상태 충돌은 탐지 대상으로 집계할 수 있다.

## 개발 도구 활용

- IDE의 정적 분석과 리팩터링 기능으로 타입·NULL·중복을 점검한다.
- 빌드 도구로 컴파일, 공통모듈, 시험, 패키징을 동일 정의로 실행한다.
- 데이터베이스 마이그레이션 도구로 스키마 변경 순서를 추적한다.
- API 명세 도구로 요청·응답 모델과 구현의 일치를 확인한다.
- 디버거와 구조화 로그로 상태 흐름을 추적하되 민감값을 노출하지 않는다.
- 코드 생성은 반복 구조를 줄이는 데 쓰되 생성 원본과 결과의 검토 기준을 둔다.

도구 경고를 이유 없이 억제하지 않고 오탐 근거와 범위를 기록한다. 자동 생성 코드라도 빌드 결과에 들어가면 품질·보안 검토 대상이다.

## 단계별 구현 절차

1. 프로세스 맵의 시작·종료·행위자·판단·예외를 확인한다.
2. 세부 프로세스 표로 입력·출력·규칙·상태·책임을 구체화한다.
3. 요구·규칙 ID를 사용 사례와 코드 단위에 매핑한다.
4. 응용 흐름, 도메인 규칙, 저장·외부 포트를 설계한다.
5. 자료형·상태 기계·오류 계약을 먼저 구현한다.
6. 정상 흐름과 업무 거부·보상 흐름을 순차 구현한다.
7. 트랜잭션·동시성·멱등성과 외부 시간 제한을 적용한다.
8. 빌드·정적 검사·기본 단위 확인을 수행한다.
9. 프로세스 담당자와 결과·산출물을 시연해 요구 일치를 확인한다.
10. 형상관리 변경 요청에 영향·시험·배포·되돌리기를 기록한다.

## 구현 판단 기준

- 프로세스의 모든 정상·예외 종료가 코드에 추적되는가?
- 업무 규칙과 상태 전이가 한 책임 안에서 일관되게 강제되는가?
- 화면·DB·외부 모델이 핵심 업무에 과도하게 결합되지 않는가?
- 트랜잭션이 업무 불변식에 맞고 외부 대기까지 길게 잡히지 않는가?
- 동시 요청과 중복 메시지에서도 상태·금액·재고가 정확한가?
- 오류와 로그가 호출자 조치와 운영 진단에 충분한가?
- 요구가 바뀔 때 수정 범위와 영향이 설명 가능한가?

## 구체 업무 시나리오

반품 승인 서버 기능을 구현한다고 하자. 프로세스 맵에서 고객 요청, 주문·배송 상태 확인, 반품 가능 기간과 금액 판단, 승인 상태 변경, 환불 요청 등록, 결과 통지를 차례로 식별한다. 구현자는 `orderId`와 요청 ID를 입력 계약으로 고정하고 반품 가능 여부를 업무 규칙 객체에 둔다. 승인 상태 변경과 환불 요청 저장은 하나의 내부 트랜잭션으로 처리하되, 외부 결제 호출은 확정된 요청을 후속 처리하도록 분리한다. 같은 요청이 반복되면 기존 결과를 반환하고, 상태 버전 충돌이면 최신 상태를 다시 확인한다. 프로세스 단계·규칙 ID·상태 전이·코드·로그가 한 경로로 추적되어야 한다.

## 자주 발생하는 함정

- 프로세스 맵의 상자를 메서드 하나씩으로 기계적으로 바꾸고 데이터·책임을 확인하지 않는다.
- 정상 경로만 구현하고 거부·취소·보상 종료를 빠뜨린다.
- 화면에서 계산한 가격과 역할을 서버가 그대로 저장한다.
- 상태를 문자열 필드에 아무 곳에서나 대입해 금지 전이를 허용한다.
- 외부 호출을 긴 DB 트랜잭션 안에서 기다려 잠금과 장애 전파를 만든다.
- 시간 초과를 외부 작업 실패 확정으로 보고 새 요청을 중복 생성한다.
- 재고 조회 후 갱신을 원자성 없이 나눠 동시 초과 예약이 생긴다.
- DB 엔티티를 API 응답으로 자동 노출해 내부·민감 필드가 공개된다.
- 모든 오류를 하나의 일반 예외로 바꿔 재시도와 사용자 수정 여부를 구분하지 못한다.
- 구현 중 발견한 설계 변경을 문서와 추적표에 반영하지 않는다.

## 정답과 해설

1. 시작·종료, 행위자, 활동, 입력·출력, 판단 조건, 반복·병렬·대기, 예외·보상, 인계와 통제 산출물을 확인한다.
2. 자연어 상자 안의 책임과 계약을 구현 가능한 수준으로 구체화하고 누락·충돌을 업무 담당자와 확인하기 위해서다.
3. 인증된 주체의 역할·조직·소유 관계와 현재 업무 상태를 정책으로 만들고 서버가 각 자원·행위마다 검사한다.
4. 객체가 현재 상태와 행위 조건을 한곳에서 검증해 불가능한 상태를 만들지 않고 모든 호출 경로에서 같은 규칙을 적용하기 위해서다.
5. 표현은 요청·응답, 응용은 사용 사례 순서·트랜잭션, 도메인은 업무 불변식, 데이터 접근은 저장 구현, 외부 어댑터는 외부 계약 변환을 맡는다.
6. 외부 지연 동안 DB 잠금과 연결을 점유하고 장애가 내부 처리에 전파되며 응답 불확실성 때문에 롤백과 외부 효과가 불일치할 수 있다.
7. 조건부 원자 갱신, 잠금 또는 버전 검증으로 읽기–검증–예약을 보호하고 충돌 시 재시도·품절 결과를 명확히 한다.
8. 응답을 못 받았어도 외부 처리는 성공했을 수 있다. 같은 중복 방지 키로 상태를 확인하지 않고 새 요청하면 이중 효과가 생긴다.
9. 프로세스 검토 기록, 세부 규칙·상태표, 추적표, 모듈 구조도, API·오류·트랜잭션 명세, 코드·DB 이력, 어댑터, 빌드 결과를 만든다.
10. 정상·예외 흐름 추적, 규칙·상태 강제, 책임 분리, 동시성·멱등성, 오류·로그, 변경 영향 설명 가능성을 본다.

## 핵심 요약

- **업무 프로세스 맵과 세부 프로세스 확인**은 행위자·입력·규칙·판단·상태·예외·보상을 구현 가능한 계약으로 바꾸는 일이다.
- 프로세스 단계와 요구 ID를 사용 사례, 상태 전이, 코드와 산출물에 추적한다.
- **언어·도구로 업무 프로그램 구현**은 표현–응용–도메인–저장–외부 경계를 나누고 핵심 업무 규칙을 보호한다.
- 서버가 가격·권한·상태를 다시 검증하고 금지 상태 전이와 중복 요청을 막는다.
- 트랜잭션은 업무 불변식에 맞게 짧게 잡고 외부 시스템은 시간 제한·멱등성·상태 확인·보상으로 연계한다.
- 완료는 정상뿐 아니라 거부·취소·장애 흐름이 추적되고 동시 실행에서도 일관성을 지킬 때 판단한다.
