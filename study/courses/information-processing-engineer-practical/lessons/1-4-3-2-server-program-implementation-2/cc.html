01

수행 범위와 목표

이 레슨은 서버 구현 결과를 검토해 잠재적 보안 취약성을 제거한 서버 프로그램 구현을 완성하고, 모듈·계층·데이터 저장·외부 어댑터 사이의 내부 기능과 인터페이스 테스트를 수행하는 실무를 다룬다. 목표는 공격 절차를 재현하는 것이 아니라 신뢰 경계마다 입력·신원·권한·자원·오류를 안전하게 처리하고, 내부 계약이 정상·거부·실패 상황에서 유지되는지 증거로 확인하는 것이다.

앞 레슨의 업무 프로세스 분석과 핵심 코드 구현을 입력으로 사용한다. 공통모듈 단위 테스트 케이스 자체는 앞 레슨 범위이며, 여기서는 완성된 서버의 내부 컴포넌트와 인터페이스 통합에 초점을 둔다.

02

입력자료

  • 서버 프로그램 소스와 업무 프로세스·상태 전이표
  • 내부 모듈·계층·인터페이스 설계서
  • 인증·인가·데이터 분류·오류·로그 보안 요구
  • 입력·출력 스키마와 외부 시스템 계약
  • 데이터베이스 스키마·권한·트랜잭션 정책
  • 안전 코딩 표준과 승인 라이브러리 목록
  • 위협 모델, 과거 결함, 정적 분석 결과
  • 시험환경·합성 데이터·모의 외부 시스템

운영 비밀번호, 실제 개인정보, 파괴적인 검증 방식은 시험에 사용하지 않는다. 권한 있는 범위와 안전한 모의 데이터로 방어 동작을 확인한다.

03

신뢰 경계와 데이터 흐름

외부 요청 ↓ [형식·크기·인증] 표현 계층 ↓ [명령 객체·안전한 주체] 응용 계층 ↓ [자원·행위 인가] 도메인 로직 ↓ [불변식·상태 전이] 저장 포트 / 외부 포트 ↓ [매개변수·최소 권한·시간 제한] DB / 외부 서비스

각 화살표에서 데이터가 신뢰 수준을 바꾸는지 확인한다. 내부 서비스가 보냈다는 이유만으로 자료형·권한을 생략하지 않는다. 외부 응답과 메시지도 입력으로 검증한다.

위협 모델에는 보호 자산, 공격 표면, 가능한 오용 사례, 기존 통제, 잔여 위험과 시험 항목을 연결한다. 단순 취약점 목록보다 실제 업무 흐름에서 어디를 보호하는지 보여 준다.

04

입력 검증

서버는 요청의 자료형, 필수값, 길이, 범위, 형식, 배열 개수·중첩 깊이, 코드값과 필드 조합을 허용 목록 중심으로 검증한다. 클라이언트 화면 제한은 서버 검증을 대신하지 않는다.

검증 순서는 저비용 구조·크기 검사, 인증·권한, 업무 규칙, 비용이 큰 처리 순으로 설계할 수 있다. 그러나 자원 존재 여부를 권한 없는 사용자에게 노출하지 않도록 조회와 오류 응답 순서를 조정한다.

문자열은 사용 문맥에 맞게 처리한다. SQL 값은 매개변수화, 파일 경로는 안전한 결합·정규화 후 허용 루트 확인, 외부 URL은 허용 프로토콜·목적지, 화면 출력은 출력 문맥 인코딩을 사용한다. 한 종류의 이스케이프를 다른 문맥에 재사용하지 않는다.

05

인증과 인가

인증은 주체 확인, 인가는 그 주체가 특정 자원에 특정 행위를 할 수 있는지 판단한다. 로그인한 사용자가 요청 경로의 ID를 바꿔 다른 고객 자료를 볼 수 없도록 객체 단위 정책을 적용한다.

인가 의사코드:

function getOrder(actor, orderId): requireAuthenticated(actor) order = orderRepository.find(orderId) if order is absent: return safeNotFound() if not policy.canRead(actor, order): auditDenied(actor.id, orderId) return safeDeniedOrNotFound() return orderView.fromAuthorized(order)

클라이언트가 보낸 role, ownerId를 신뢰하지 않는다. 서버의 인증 상태와 권한 데이터로 판단한다. 실패 시 정책 정보를 읽지 못하면 허용하지 않는 Fail Secure를 적용한다.

관리 기능과 일반 기능의 경로·역할·감사를 분리한다. 서비스 계정에는 필요한 API와 데이터만 허용한다. 공용 관리자 계정을 사용하지 않는다.

06

질의·명령·경로 안전성

데이터베이스 질의에 외부 값을 문자열로 연결하지 않고 매개변수로 전달한다. 정렬 열·테이블명처럼 구조 요소는 서버가 정의한 허용값에서 내부 표현으로 매핑한다.

운영체제 명령 실행이 필요하면 셸 문자열 조합보다 실행 파일과 인수 배열을 분리하는 API를 사용하고 실행 가능한 명령을 제한한다. 가능하면 전용 라이브러리 API로 대체한다.

파일 업로드는 표시 파일명, 실제 내용 유형, 크기, 개수, 저장 위치와 실행 권한을 검증한다. 서버가 정한 새 이름을 사용하고 웹에서 직접 실행되지 않는 격리 위치에 둔다.

사용자 입력 URL을 서버가 요청한다면 내부 관리 주소로 향하지 않게 승인된 목적지만 사용하고 리다이렉트, 응답 크기·시간을 제한한다.

07

세션·비밀·전송 보호

세션 식별자는 예측하기 어렵게 발급하고 안전한 통신으로만 전달하며 URL·로그에 기록하지 않는다. 로그인과 권한 상승 시 회전하고 미사용·절대 만료, 로그아웃·계정 정지 시 서버 측 폐기를 적용한다.

비밀번호는 전용 검증 방식으로 저장하고 비밀·키·토큰은 소스와 일반 설정에서 분리한다. 비밀 관리 서비스 또는 승인된 주입 방식을 사용하고 목적별 최소 권한과 교체 절차를 둔다.

전송 보호는 상대 인증과 인증서 검증까지 포함한다. 시험 편의로 모든 인증서를 신뢰하는 설정이 운영 프로필에 남지 않게 자동 검사한다.

구체 암호 알고리즘과 매개변수는 조직의 최신 기준과 검증된 고수준 라이브러리를 사용하며 독자 암호를 구현하지 않는다.

08

오류·로그·자원

외부 오류 응답에는 안정된 공개 코드와 상관 ID, 안전한 메시지만 제공한다. 스택, 파일 경로, 질의, 내부 주소와 라이브러리 버전을 노출하지 않는다.

내부 로그에는 사건 시각, 서비스, 상관 ID, 안전한 주체 식별자, 대상, 결과와 오류 분류를 남긴다. 비밀번호, 전체 세션 토큰, 결제·개인정보 원문은 제외한다.

파일·연결·잠금은 정상·실패 모든 경로에서 정리한다. 자동 자원 관리 구문을 사용하고 자원 소유자를 명시한다. 예외를 잡아 빈 결과로 바꿔 실패와 정상 없음이 섞이지 않게 한다.

재시도는 일시 오류만 제한 횟수와 지연으로 수행하고 상태 변경은 중복 방지 키를 사용한다. 권한 거부·입력 오류를 반복하지 않는다.

09

의존성·설정 보안

승인된 저장소에서 검증된 버전의 의존성을 사용하고 실제 배포된 직접·간접 구성요소를 목록화한다. 지원 종료·알려진 문제를 정기 점검하고 변경 시 회귀시험한다.

개발·시험·운영 설정을 분리하되 운영 기본값을 개발 실패의 대체로 두지 않는다. 필수 보안 설정이 없으면 기동을 실패시키고 민감값은 로그에서 가린다.

디버그 기능, 샘플 계정, 기본 비밀번호, 불필요 관리자 API를 운영 산출물에서 제거한다. 기능 플래그의 기본값과 만료를 관리한다.

10

정적·수동 보안 검토

컴파일러 경고와 정적 분석으로 NULL, 자원 누수, 위험 API, 주입 가능 데이터 흐름과 비밀 문자열을 찾는다. 도구 결과는 실제 입력 경로와 통제를 검토해 오탐을 분류한다.

수동 검토에서는 다음을 확인한다.

  • 자원 소유와 객체 단위 인가가 모든 경로에 있는가?
  • 오류 시 자동 허용이나 평문 전환이 있는가?
  • 상태 전이와 금액·재고를 클라이언트가 조작할 수 있는가?
  • 내부 객체 자동 직렬화로 민감 필드가 나가는가?
  • 시간 초과·중복 메시지·동시 요청이 일관성을 깨는가?
  • 로그와 디버그 출력에 비밀이 포함되는가?

발견 항목에는 코드 위치, 원인, 영향, 안전한 수정, 회귀 케이스를 연결한다. 단순 억제 주석으로 닫지 않는다.

12

내부 인터페이스 테스트

내부 인터페이스는 함수 호출뿐 아니라 모듈 간 DTO, 데이터베이스 포트, 메시지·HTTP 어댑터를 포함한다.

검증 항목:

  • 필드 이름·자료형·필수·기본값과 버전
  • 문자 인코딩, 날짜·시간대, 숫자 정밀도
  • 오류 코드와 재시도·멱등 의미
  • 순서·중복·부분 응답과 페이지 처리
  • 인증 주체와 권한 전달
  • 시간 제한, 취소, 자원 정리
  • 새·이전 버전 간 호환성

생산자와 소비자가 같은 클래스 파일을 공유하면 양쪽이 함께 잘못되어 계약 결함을 놓칠 수 있다. 독립 스키마·예제와 소비자 계약시험을 사용한다.

13

테스트 계층과 대역

응용 서비스 시험에서는 저장소·외부 포트를 Stub/Fake로 대체해 분기와 협력 결과를 빠르게 검증한다. 실제 데이터베이스와 직렬화·통신 계층은 컴포넌트 시험에서 확인한다.

test "권한 없는 사용자의 주문 조회를 거부": given order belongs to customer A and actor is customer B when result = orderService.getOrder(actor, order.id) then result is denied and repository did not expose order details and audit contains denial event without sensitive data

대역으로 모든 내부 호출 횟수를 고정하지 않고 공개 결과와 중요한 효과를 검증한다. 실제 DB의 제약과 트랜잭션은 메모리 Fake로 완전히 대신할 수 없다.

외부 시간 초과불확실 상태 기록, 중복 생성 없음
같은 요청 재전송동일 업무 결과, 중복 주문 없음
내부 응답에 추가 필드소비자 호환 정책대로 처리
인증 정책 저장소 오류Fail Secure, 허용하지 않음

실제 공격 문자열이나 우회법을 재현하지 않아도 입력이 구조로 해석되지 않고 정책 거부·상태 불변이 유지되는지 확인할 수 있다.

15

테스트 환경과 데이터

합성 고객·주문·권한 데이터를 사용하고 각 케이스가 독립적으로 준비·정리한다. 관리자·일반·비활성·다른 조직 사용자 역할을 포함한다.

시간과 난수, 외부 응답을 통제해 만료·중복·시간 초과를 재현한다. 시험용 인증서는 승인된 별도 신뢰 체계를 사용하며 검증 자체를 끄지 않는다.

데이터베이스 시험은 실제 제약·트랜잭션을 지원하는 격리 환경에서 수행한다. 케이스 사이 정리 실패를 감지하고 병렬 실행 시 고유 키를 사용한다.

단계별 수행 절차

  1. 위협 모델과 안전 코딩 기준을 서버 흐름에 매핑한다.
  2. 입력·인증·인가·질의·파일·세션·오류·의존성 코드를 검토한다.
  3. 정적 분석 결과를 실제 경로와 함께 판정하고 수정한다.
  4. 보안 요구와 내부 인터페이스 계약에서 테스트 조건을 도출한다.
  5. 응용·도메인 시험과 DB·외부 어댑터 컴포넌트 시험을 구현한다.
  6. 정상·경계·거부·시간 초과·중복·롤백을 실행한다.
  7. 응답·로그·DB 상태·외부 호출을 함께 검증한다.
  8. 결함 수정 뒤 원래 조건과 주변 회귀를 재시험한다.
  9. 미해결 위험과 보완 통제, 승인·기한을 기록한다.
  10. 결과를 형상관리 변경과 빌드 통과 기준에 연결한다.

자주 발생하는 함정

  • 클라이언트 검증이 있으므로 서버 입력 검증을 생략한다.
  • 로그인 성공과 특정 주문 조회 권한을 같은 것으로 본다.
  • HTML 인코딩으로 SQL·경로·명령 주입까지 막았다고 생각한다.
  • 인증서 오류를 시험 편의로 무시한 설정이 운영에 남는다.
  • 오류를 상세 스택으로 반환해 내부 구조를 노출한다.
  • 정적 분석 0건을 취약성 없음의 증명으로 본다.
  • 메모리 Fake 시험만 통과하고 실제 DB 제약·트랜잭션을 확인하지 않는다.
  • 생산자·소비자가 같은 잘못된 모델을 공유해 계약 오류를 함께 놓친다.
  • 반환값만 확인하고 DB 부분 변경, 로그 민감정보, 외부 중복 호출을 확인하지 않는다.
  • 외부 시간 초과에 무조건 재시도해 이중 주문·결제가 생긴다.

정답과 해설

  1. 외부–표현에서 형식·인증, 표현–응용에서 안전한 명령·주체, 응용–도메인에서 자원·행위 인가, 도메인–저장에서 불변식·매개변수, 외부 어댑터에서 상대·응답·시간을 검증한다.
  2. 필수·NULL, 코드 허용값, 배열 개수·깊이, 필드 조합, 인코딩, 단위, 업무 상태와 중복을 확인한다.
  3. 인증은 사용자가 누구인지 확인하고, 인가는 그 사용자가 해당 주문의 소유자·허용 역할이며 현재 상태에서 읽을 수 있는지 확인한다.
  4. SQL은 매개변수화, 명령은 실행 파일·인수 배열과 허용 명령, 경로는 결합·정규화 후 허용 루트, URL은 허용 프로토콜·목적지·리다이렉트 제한을 적용한다.
  5. 외부에는 내부 구조와 비밀을 노출하지 않아야 하지만 운영자는 원인을 조사해야 한다. 안전한 상관 ID로 최소 응답과 제한된 상세 로그를 연결한다.
  6. 기능 시험은 응용 순서·업무 상태·정책 결과를, 인터페이스 시험은 모듈 간 필드·자료형·오류·시간·중복·버전 계약을 검증한다.
  7. Fake는 실제 DB의 제약, 격리, 잠금, 자료형, 질의와 롤백 동작을 정확히 재현하지 못할 수 있기 때문이다.
  8. 한 업무 결과만 생성되는지, 불확실 상태와 외부 추적 ID가 보존되는지, 같은 키로 조회·재확인하는지, 부분 DB 변경이 없는지 본다.
  9. 신뢰 경계·위협표, 안전 코딩 검토표, 정적 분석 조치, 내부 테스트 조건·코드, 시험 데이터·환경, 결과·결함·재시험, 잔여 위험 기록을 만든다.
  10. 모든 경계 검증, 인가·상태 강제, 안전 API·비밀 보호, Fail Secure, 계약 일치, DB·외부 실패 재현, 추적 가능한 수정 증거를 본다.

핵심 요약

  • 잠재적 보안 취약성을 제거한 서버 프로그램 구현은 입력·인증·인가·질의·경로·세션·비밀·오류를 신뢰 경계마다 안전하게 처리하는 일이다.
  • 클라이언트 값을 신뢰하지 않고 객체 단위 권한과 업무 상태를 서버 정책으로 강제한다.
  • 문맥별 구조화 API, 최소 권한, 안전한 세션·비밀 관리, Fail Secure와 민감정보 없는 로그를 적용한다.
  • 내부 기능과 인터페이스 테스트는 응용·도메인 상태와 DTO·저장·외부 계약의 타입·오류·시간·중복 의미를 함께 검증한다.
  • 대역 기반 빠른 시험과 실제 DB·직렬화·외부 실패 컴포넌트 시험을 조합한다.
  • 공격 절차 재현보다 거부·롤백·중복 방지·자원 정리·민감정보 부재가 증거로 확인되는지를 판단한다.
