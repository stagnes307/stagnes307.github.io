# 1-5-1-1. 설계서에서 공통 기능과 데이터 인터페이스 확인 · 연계에 필요한 인터페이스 기능 식별

> **수행 범위 기준**: 이 레슨은 정보처리기사 실기 `인터페이스 구현 > 인터페이스 설계서 확인하기`의 **설계서에서 공통 기능과 데이터 인터페이스 확인**, **연계에 필요한 인터페이스 기능 식별**을 다룬다. 앞 단원의 연계 요구·모듈 구현 내용을 참조할 수 있지만, 이 단원에서는 승인된 설계서를 구현 가능한 인터페이스 기능 목록으로 해석하는 데 초점을 둔다. 다음 레슨의 인터페이스 데이터 표준 확인과 이후 공통 인터페이스 실제 구현은 분리한다.

인터페이스 구현 전에 가장 먼저 할 일은 코드를 쓰는 것이 아니라 설계서 여러 곳에 흩어진 공통 기능, 송수신 데이터, 책임 경계와 실패 계약을 하나의 검토 가능한 목록으로 맞추는 일이다. “A가 B를 호출한다”만 확인하면 인증·검증·변환·중복·시간 제한·감사 같은 필수 기능이 누락되고, 구현자마다 다른 방식으로 공통 기능을 다시 만들게 된다.

## 1. 예제와 확인 산출물

가상 주문 시스템이 결제 시스템에 결제 요청을 보내고 결과를 수신하는 인터페이스를 사용한다.

```text
주문 서비스
  → 결제 요청 생성
  → 공통 인터페이스 처리
  → 결제 게이트웨이
  → 외부 결제 시스템

결과
  → 응답/이벤트 수신
  → 검증·중복 확인·상태 매핑
  → 주문 결제 상태 반영
```

설계서 확인이 끝나면 다음 산출물이 연결되어야 한다.

| 산출물 | 핵심 내용 |
|---|---|
| 설계서 기준 목록 | 문서명, 버전, 승인 상태, 소유자, 기준일 |
| 공통 기능 목록 | 인증, 로깅, 오류, 변환, 트랜잭션 등 재사용 책임 |
| 인터페이스 목록 | ID, 제공자·소비자, 업무 목적, 방식, 주기 |
| 데이터 항목표 | 필드, 의미, 형식, 필수, 코드, 민감도, 검증 |
| 기능 식별표 | 송수신 단계별 필요한 기능, 입력·출력, 오류·품질 |
| 추적 매트릭스 | 요구–설계–인터페이스–기능–테스트 연결 |
| 미결·불일치 목록 | 충돌 내용, 영향, 결정자, 기한과 임시 가정 |

## 2. 확인할 설계서와 우선순위

### 2.1 대표 입력 문서

- 요구사항 명세서와 추적표
- 시스템·소프트웨어 아키텍처 설계서
- 컴포넌트·모듈 상세설계서
- 데이터 모델·테이블 정의서·코드 정의서
- 인터페이스 목록·정의서·메시지/파일 명세
- 시퀀스·활동·상태 전이·데이터 흐름 모델
- 보안 설계서와 권한 매트릭스
- 오류 코드·로그·감사·운영 표준
- 성능·가용성·복구·배포 설계
- 외부 시스템 계약과 버전·지원 일정

문서 이름보다 내용과 승인 상태가 중요하다. 임시 회의 메모와 승인 기준선을 같은 권위로 다루지 않는다.

### 2.2 기준 버전 통제

```text
문서 ID: IF-DESIGN-ORDER-PAY-02
버전: 1.4
상태: 승인
승인일: YYYY-MM-DD
관련 요구 기준선: REQ 2.1
관련 데이터 모델: DM 3.0
소유자: 결제 연계 책임자
```

서로 다른 버전의 필드·오류 코드·URL을 섞으면 구현은 어느 문서도 만족하지 못한다. 불일치가 있으면 임의 선택하지 않고 변경 책임자에게 결정 요청을 남긴다.

### 2.3 문서 신뢰 순서

조직의 형상·승인 규칙을 따르되 일반적으로 승인된 최신 기준선, 공식 변경 요청, 계약 문서, 검토 중 초안, 회의 메모 순으로 권위를 확인한다. 실제 운영 관찰이 문서와 다르면 현재 사실의 증거로 기록하되 목표 설계 변경은 승인 절차를 거친다.

## 3. 설계서에서 공통 기능 확인

**공통 기능**은 여러 업무 모듈이나 인터페이스가 반복 사용하고 일관된 정책이 필요한 기능이다. 많이 호출된다는 이유만으로 공통 모듈이 되는 것은 아니며, 동일한 변화 이유와 계약을 공유해야 한다.

### 3.1 공통 기능 후보

| 범주 | 확인할 기능 | 설계 질문 |
|---|---|---|
| 인증·인가 | 호출 주체 확인, 서비스·기능·데이터 권한 | 어디서 검증하고 실패 시 무엇을 반환하는가? |
| 입력 검증 | 필수·형식·범위·코드·크기 | 공통 형식과 업무 규칙의 책임 경계는? |
| 직렬화·변환 | 객체–메시지, 코드·날짜·단위 변환 | 손실·정밀도·미지 필드 규칙은? |
| 통신 | 연결, 송수신, 시간 제한, 풀 관리 | 동기/비동기와 자원 상한은? |
| 오류 처리 | 오류 분류, 안정된 코드, 예외 변환 | 재시도 가능 여부와 외부 노출 범위는? |
| 재시도·멱등 | 제한 재시도, 중복 요청·이벤트 억제 | 고유 키 범위·수명·결과 재사용은? |
| 로깅·추적 | 상관관계 ID, 메트릭, 감사 | 민감정보 제외·보존·경보 기준은? |
| 보안 | 전송 보호, 서명·무결성, 비밀 관리 | 키 수명·회전·실패 시 안전 동작은? |
| 트랜잭션 | 로컬 원자성, 후속 작업, 보상 | 시스템 경계를 넘는 실패 상태는? |
| 구성·버전 | 엔드포인트·정책 외부화, 계약 버전 | 환경 분리·호환·롤백은? |

### 3.2 공통과 업무 전용의 경계

```text
공통 후보:
  상관관계 ID 생성·전파
  표준 오류 봉투 생성
  시간 제한·연결 자원 정책 적용
  표준 날짜·코드 표현 검증

업무 전용:
  주문 상태가 출고 전인지 판단
  결제 금액이 주문 잔액과 같은지 판단
  부분 취소 금액 배분
```

업무 규칙까지 범용 라이브러리에 넣으면 여러 업무가 한 모듈 변경에 결합된다. 반대로 인증·오류·관찰 정책을 각 모듈이 복사하면 보안과 운영 결과가 달라진다.

### 3.3 공통 기능 계약 기록

| 공통 기능 ID | 입력 | 출력 | 사전·사후 조건 | 오류 | 품질·운영 |
|---|---|---|---|---|---|
| CF-TRACE-01 | 선택적 요청 ID·현재 컨텍스트 | 유효한 상관관계 ID | 기존 ID 검증 후 유지 또는 새 생성 | 형식 오류 | 모든 로그·하위 호출에 전파 |
| CF-ERR-02 | 내부 오류·업무 오류 | 표준 외부 오류 | 민감 상세 제거 | 매핑 없음은 안전한 기본 오류 | 내부 원인은 추적 ID로 기록 |
| CF-RETRY-01 | 오류 분류·시도 수·멱등 가능 여부 | 재시도/중단 결정 | 변경 작업은 멱등 보호 필요 | 정책 초과 | 백오프·최대 시간·메트릭 |

기능 이름만 적지 않고 호출자가 기대할 수 있는 계약과 실패 동작을 쓴다.

## 4. 데이터 인터페이스 확인

### 4.1 인터페이스 수준 정보

| 항목 | 확인 내용 |
|---|---|
| 인터페이스 ID·이름 | 조직 전체에서 유일한 식별자 |
| 업무 목적 | 어떤 업무 결과를 위해 데이터를 교환하는가? |
| 제공자·소비자 | 시스템·모듈·책임 조직과 운영 연락처 |
| 방향 | 단방향/양방향, 요청–응답/발행–구독 |
| 방식 | API, 메시지, 파일, DB 연계 등 |
| 시점·주기 | 실시간, 이벤트, 분·일 배치, 업무 마감 |
| 데이터량 | 평균·피크 건수, 크기, 증가율 |
| 시간 조건 | 연결·처리 제한, 만료, 완료 시한 |
| 신뢰성 | 전달·순서·중복·재처리·대사 계약 |
| 보안 | 인증, 권한, 암호화, 무결성, 감사 |
| 버전 | 호환 규칙, 지원 기간, 변경 통지 |

### 4.2 데이터 항목 수준 정보

```text
필드명: paymentRequestId
업무명: 결제 요청 식별자
형식: 문자열, 최대 36자, 허용 문자 규칙
필수: Y
생성자: 주문 시스템
유일 범위: 채널을 포함한 전체 요청
의미: 재시도와 결과 조회에서 동일 업무를 식별
민감도: 내부 식별 정보
검증: 비어 있지 않음, 형식·중복 검사
변환: 외부 providerReference와 별도 매핑
```

필드명과 자료형만 있으면 다음 문제가 남는다.

- `amount`의 통화와 소수 자릿수는 무엇인가?
- 날짜가 현지 시각인지 UTC인지, 오프셋을 포함하는가?
- 빈 문자열과 null의 차이는 무엇인가?
- 코드값이 추가됐을 때 구버전 수신자는 어떻게 하는가?
- 개인정보가 로그·비운영 환경에 노출돼도 되는가?
- 같은 ID의 재사용 범위와 보존 기간은 얼마인가?

### 4.3 송수신 대칭성

송신 정의와 수신 정의를 나란히 비교한다.

| 비교 | 송신 측 | 수신 측 | 불일치 조치 |
|---|---|---|---|
| 필수 필드 | currency 필수 | 선택 | 계약 승인 필요 |
| 금액 정밀도 | 소수 2자리 | 정수 최소단위 | 변환·반올림 규칙 |
| 시간 | UTC 오프셋 포함 | 현지 시각 | 표준 시각 합의 |
| 성공 의미 | 접수 성공 | 결제 확정 | 상태 분리 |
| 오류 재시도 | 5xx 재시도 | 일부 5xx 영구 | 오류 분류 표 통일 |

“JSON 사용”처럼 물리 형식이 같아도 업무 의미가 다르면 호환되지 않는다.

### 4.4 데이터 생명주기와 소유권

- 원본 데이터는 어느 시스템이 생성·변경하는가?
- 수신자는 복제본을 얼마 동안 얼마나 최신으로 유지하는가?
- 정정·삭제·보존·파기 이벤트는 어떻게 전달되는가?
- 개인정보 열람·정정·삭제 요청을 연계 사본에도 반영하는가?
- 대사 기준과 불일치 책임자는 누구인가?

수신 시스템이 받은 값을 임의 수정한 뒤 원본처럼 재전송하면 소유권이 혼란스러워진다. 변환 결과와 원본 참조를 구분한다.

## 5. 연계에 필요한 인터페이스 기능 식별

설계서의 데이터 흐름을 실제 처리 단계로 나누며 필요한 기능을 식별한다.

### 5.1 송신 기능

1. 업무 이벤트·요청 생성 조건 판단
2. 원본 데이터 조회와 일관된 스냅샷 구성
3. 업무 규칙·필수·범위 검증
4. 내부 모델을 표준 인터페이스 모델로 매핑
5. 요청 ID·상관관계 ID·버전 부여
6. 인증 정보·무결성·전송 보호 적용
7. 직렬화와 크기 제한 확인
8. 전송·응답 제한 시간·연결 자원 관리
9. 결과 분류와 상태 저장
10. 제한 재시도·중복 방지·실패 격리
11. 로그·메트릭·감사와 운영 알림

### 5.2 수신 기능

1. 호출 주체 인증과 인터페이스 권한 확인
2. 메시지 크기·형식·버전·무결성 검증
3. 요청 ID 중복과 재전송 결과 확인
4. 표준 데이터를 내부 모델로 안전하게 변환
5. 업무 상태·참조·불변조건 검증
6. 로컬 트랜잭션 처리와 후속 작업 기록
7. 표준 성공·오류 응답 생성
8. 감사·추적·메트릭 기록
9. 실패 데이터 격리와 승인된 재처리

### 5.3 운영·관리 기능

- 엔드포인트·자격정보·시간 제한·재시도 정책의 환경별 구성
- 비밀 회전과 인증서 만료 감시
- 인터페이스별 성공률·지연·적체·오류 분류 대시보드
- 중단·재개·우회·재처리의 권한과 감사
- 스키마·계약 버전 배포와 소비자 호환 확인
- 데이터 건수·금액·상태 대사와 불일치 처리
- 장애 대응 연락·에스컬레이션·복구 절차

관리 기능이 없으면 정상 구현도 장애 때 안전하게 운영하기 어렵다.

## 6. 기능 식별표 작성

| 기능 ID | 처리 단계 | 입력 | 처리·판단 | 출력 | 오류·복구 | 공통/전용 |
|---|---|---|---|---|---|---|
| IF-PAY-01 | 요청 구성 | 주문 ID | 확정 주문·미결제 금액 확인 | 내부 결제 요청 | 상태 오류 | 업무 전용 |
| IF-PAY-02 | 표준 변환 | 내부 결제 요청 | 통화·금액·시간 매핑 | 표준 메시지 | 매핑 오류 | 공통+설정 |
| IF-PAY-03 | 보호·전송 | 표준 메시지 | 인증·제한 시간·직렬화 | 응답/전송 상태 | 일시 오류 분류 | 공통 |
| IF-PAY-04 | 결과 반영 | 외부 응답 | 요청 ID·무결성·상태 매핑 | 결제 상태·이력 | 중복·늦은 응답 | 업무 전용 |

한 기능에 입력·출력·오류가 너무 많으면 책임을 더 나눌 수 있다. 반대로 네트워크 호출만 기능으로 보고 검증·변환·상태 반영을 누락하지 않는다.

### 6.1 우선순위와 필수성

| 등급 | 판단 예 |
|---|---|
| 필수 | 데이터 무결성, 인증·권한, 법·감사, 업무 완료에 필요 |
| 중요 | 운영 복구·관찰, 피크 품질, 변경 호환에 중요 |

보안·무결성 기능을 일정 때문에 선택으로 낮추지 않는다. 미구현 시 영향과 수용 책임자를 기록한다.

## 7. 단계별 설계서 확인 절차

### 단계 1: 범위와 기준선 확정

### 단계 2: 공통 기능 수집

- 아키텍처·상세·보안·운영 설계에서 반복 기능을 추출한다.
- 기존 공통 모듈의 계약·버전·지원 범위와 재사용 가능성을 확인한다.

**완료 기준**: 공통 기능마다 소유자·입출력·오류·품질 계약이 있다.

### 단계 3: 인터페이스·데이터 추출

- 모든 데이터 흐름을 인터페이스 ID로 식별한다.

**완료 기준**: 송신과 수신 정의가 대칭적으로 검토되고 불일치가 기록된다.

### 단계 4: 처리 시퀀스 분해

- 정상, 대안, 오류, 시간 초과, 중복, 재처리 흐름을 그린다.
- 각 단계의 입력·판단·상태 변경·외부 효과를 식별한다.
- 트랜잭션 경계와 비동기 최종 상태를 표시한다.

**완료 기준**: 실패한 위치별 데이터 상태와 재개 방법을 설명할 수 있다.

### 단계 5: 인터페이스 기능 목록화

- 송신·수신·운영 기능을 고유 ID로 쓴다.
- 공통/전용, 필수성, 의존, 입력·출력·오류와 검증 방법을 기록한다.
- 기존 기능 재사용·확장·신규 구현을 분류한다.

**완료 기준**: 모든 설계 흐름이 하나 이상의 기능과 테스트 후보로 추적된다.

### 단계 6: 다자 검토와 미결 해결

- 업무 의미는 업무 책임자, 필드·코드는 데이터 책임자, 실패·운영은 운영자, 통제는 보안 책임자가 확인한다.
- 충돌은 임의 구현하지 않고 영향·대안·결정자를 기록한다.
- 승인된 결정으로 모든 관련 문서와 추적표를 갱신한다.

**완료 기준**: 치명적 미결이 없고 잔여 가정에 책임자·기한·영향이 있다.

## 9. 통합 사례: 설계 불일치 해결

발견된 설계 내용:

```text
요구사항: 결제 요청은 중복 처리되지 않아야 한다.
API 설계: requestId 선택 필드
데이터 설계: payment_request 테이블에 requestId 유일 제약 없음
오류 설계: 시간 초과 시 3회 재시도
운영 설계: 실패 요청 수동 재처리 가능
```

문제 분석:

- 선택 ID로는 재시도와 수동 재처리를 같은 업무로 식별하기 어렵다.
- 사전 조회만 하면 동시 중복을 막지 못한다.
- 응답 유실 뒤 성공 요청을 재전송할 때 결제가 두 번 생길 수 있다.
- 운영 재처리가 자동 재시도와 겹칠 수 있다.

필요 기능 식별:

1. 필수 `requestId` 생성·형식 검증 기능
2. 요청 ID와 내용 해시의 원자적 예약·유일성 기능
3. 성공 결과 저장·재조회 기능
4. 같은 ID·같은 내용 재전송의 기존 결과 반환 기능
5. 같은 ID·다른 내용 충돌 거절 기능
6. 재시도 소유권·잠금과 수동 재처리 승인 기능
7. 중복·충돌·재시도 메트릭과 감사 기능

설계 변경은 API, 데이터, 오류, 운영 문서와 테스트 추적표에 모두 반영한다.

## 10. 자주 틀리는 포인트

1. **최신 파일 이름이면 승인 기준선이다?** 버전·상태·소유자·변경 승인을 확인한다.
2. **공통 기능은 두 번 이상 사용하면 무조건 공통 모듈이다?** 동일 계약과 변화 이유, 재사용 비용을 판단한다.
3. **업무 규칙을 모두 공통 기능에 넣으면 재사용성이 높다?** 업무 결합이 커져 변경 영향이 확산된다.
4. **인터페이스는 URL·메서드·JSON 필드만 확인한다?** 업무 의미·실패·시간·중복·보안·운영 계약이 필요하다.
5. **송수신 형식이 같으면 의미도 같다?** 단위·정밀도·성공 상태·코드 의미가 다를 수 있다.
6. **빈 문자열, null, 필드 생략은 같다?** 계약에 따라 서로 다른 상태다.
7. **요청–응답 정상 시퀀스만 기능으로 식별한다?** 지연·응답 유실·부분 성공·중복·재처리를 포함한다.
8. **재시도 기능만 있으면 신뢰적이다?** 멱등성·최대 횟수·백오프·만료·오류 분류가 필요하다.
9. **로그 전체 메시지를 남기면 진단이 쉽다?** 민감정보·비밀 노출과 과도한 저장 위험이 있다.
10. **공통 오류 처리는 모든 오류를 한 코드로 바꾼다?** 외부 상세는 제한하되 업무 행동과 재시도 판단에 필요한 안정된 분류를 제공한다.
11. **미결 설계는 구현자가 합리적으로 선택한다?** 문서 간 충돌은 책임자 결정과 변경 통제가 필요하다.
12. **관리·대사·재처리는 구현 뒤 운영팀이 정한다?** 인터페이스의 필수 운영 기능으로 사전에 식별한다.
13. **기능 목록은 이름만 있으면 추정할 수 있다?** 입력·출력·조건·오류·품질·책임·검증을 기록한다.
14. **외부 계약이 바뀌면 한쪽만 수정한다?** 제공자·소비자·데이터·운영·테스트의 호환과 전환 기간을 함께 관리한다.

## 12. 정답과 해설

### 정답 1

요구사항 명세에서 업무 목표·품질·제약을, 아키텍처·상세설계에서 모듈 책임·호출·트랜잭션을, 데이터 모델·사전에서 필드 의미·키·코드·관계를, 인터페이스 정의서에서 제공자·소비자·형식·주기·오류를 얻는다. 보안·운영 설계로 인증·권한·로그·재처리·복구도 확인한다.

### 정답 2

공통 후보는 인증 정보 적용, 표준 오류 변환, 상관관계 ID·로그, 직렬화, 제한 시간·재시도 정책이다. 업무 전용은 주문 결제 가능 상태 판단, 결제 금액과 주문 잔액 검증, 부분 취소 금액 배분과 주문 상태 반영이다.

### 정답 3

업무 의미, 필수·null·빈 값 의미, 길이·정밀도·단위·시간대, 허용 코드, 생성·소유자, 유일 범위, 민감도와 보호, 변환 규칙, 기본값, 버전 추가 시 미지 값 처리, 검증·오류를 확인한다.

### 정답 4

같은 성공 표현의 업무 의미가 다른 계약 불일치다. 접수·처리 중·승인 확정 상태를 별도 코드와 전이로 정의하고 각 상태의 사용자 표시·재조회·시간 제한·후속 처리·대사 기준을 송수신 설계에 함께 반영한다.

### 정답 5

업무 요청 생성 조건 판단, 원본 조회, 입력·상태 검증, 표준 모델 변환, 요청·추적 ID 부여, 인증·무결성·전송 보호, 직렬화·크기 확인, 연결·시간 제한 전송, 응답 검증·상태 매핑, 결과 저장, 오류 분류·제한 재시도·멱등, 로그·메트릭·감사를 포함한다.

### 정답 6

첫 요청이 서버에서 성공했는지 모르는 상태이므로 고유 요청 ID, 내용 해시, 성공 결과 저장·조회, 같은 요청의 기존 결과 반환, 다른 내용 충돌 거절이 필요하다. 일시·영구 오류 분류와 최대 재시도·백오프·만료, 진행 중 소유권과 운영 재처리 중복도 정의한다.

### 정답 7

고유 기능 ID, 처리 단계, 입력·출력, 사전·사후 조건, 처리 판단, 오류·복구, 공통/전용과 소유자, 필수성·우선순위, 성능·보안·운영 조건, 의존 기능, 요구·설계·테스트 추적을 포함한다.

### 정답 8

대상과 승인 설계서 기준선을 확정하고, 여러 문서에서 공통 기능을 추출해 책임·계약을 정한다. 인터페이스와 필드의 송수신 정의를 비교하고 정상·오류·중복·재처리 시퀀스를 분해한다. 필요한 송신·수신·관리 기능을 목록화해 추적하고 업무·데이터·보안·운영 책임자가 불일치와 미결을 검토·승인한다.

### 정답 9

응답 유실·동시 재시도에서 결제가 중복되고 수동 재처리가 자동 재시도와 겹칠 수 있다. 요청 ID를 필수로 하고 범위·수명을 정하며, 공유 저장소의 유일 제약으로 원자 예약한다. 내용 해시·결과 참조, 진행 상태, 재처리 권한·잠금과 감사 기능을 둔다.

### 정답 10

임의 선택은 제공자·소비자가 서로 다른 계약을 구현하고 승인되지 않은 범위·보안·업무 결과를 만들 수 있다. 충돌 위치, 관련 문서·버전, 업무·기술 영향, 가능한 대안, 임시 가정, 결정권자, 담당자·기한, 결정과 반영된 문서·테스트 버전을 기록한다.

## 13. 핵심 요약

- 인터페이스 설계 확인은 승인된 같은 버전의 요구·구조·데이터·보안·운영 문서를 기준으로 수행한다.
- 공통 기능은 반복 횟수보다 동일 계약·정책·변화 이유로 판단하고 업무 전용 규칙과 분리한다.
- 인증·검증·변환·통신·오류·멱등·관찰·보안·트랜잭션·구성 기능의 입출력과 실패 계약을 확인한다.
- 데이터 인터페이스는 필드 형식뿐 아니라 업무 의미·단위·정밀도·시간·코드·민감도·소유·버전을 포함한다.
- 송신과 수신 정의를 나란히 비교해 필수·형식·성공·오류·재시도 의미의 불일치를 찾는다.
- 정상 흐름을 요청 생성–검증–변환–보호–전송–결과 반영–관찰로, 오류 흐름을 시간 초과·중복·부분 성공·재처리까지 분해한다.
- 운영에는 구성·비밀 회전·대시보드·중단·재개·재처리·대사·버전 전환 기능이 필요하다.
- 기능 식별표에는 고유 ID, 입력·출력, 판단, 오류·복구, 공통/전용, 필수성, 품질과 추적을 기록한다.
- 문서 충돌은 구현자가 임의 해석하지 않고 영향·대안·결정자·기한으로 관리해 관련 기준선을 함께 갱신한다.
- 모든 설계 데이터 흐름이 인터페이스 기능과 테스트 후보로 추적될 때 구현 준비가 완료된다.
