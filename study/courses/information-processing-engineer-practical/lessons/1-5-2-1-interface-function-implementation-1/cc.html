01

수행 범위와 목표

이 레슨의 정확한 토픽은 세부설계서로 정형화된 인터페이스 기능 정의와 공통 인터페이스 구현이다. 승인된 상세 설계서를 구현 가능한 입력·출력·처리 계약으로 정리하고, 여러 업무 인터페이스가 공유하는 전송 어댑터, 직렬화, 검증, 추적, 결과 변환 구조를 구현하는 실무를 다룬다.

실패별 재시도·보상 같은 예외처리 방안과 인증·암호화 등 보안 기능은 다음 레슨의 주범위다. 여기서는 정상 처리 중심의 공통 골격을 만들되, 다음 단계에서 예외와 보안을 끼워 넣을 명확한 확장 지점을 둔다.

학습 목표는 다음과 같다.

  1. 설계서의 자연어를 함수 계약과 처리 단계로 정형화한다.
  2. 인터페이스별 업무 로직과 공통 통신 책임을 분리한다.
  3. 메시지 생성·검증·전송·해석·추적을 공통 모듈로 구현한다.
  4. 테스트 가능성, 결합도, 설정 외부화, 자원 관리 기준으로 구현을 검토한다.
02

1. 정형화된 인터페이스 기능

정형화란 “주문 정보를 전송한다” 같은 문장을 개발자마다 다르게 해석하지 않도록 입력, 출력, 선행조건, 처리, 완료조건, 오류 범주, 품질 기준으로 구조화하는 것이다.

기능 ID: IF-ORD-01 목적: 승인 주문을 물류 시스템에 출고 요청 시작 조건: 주문 상태 = 출고요청가능 입력: 주문ID 조회 데이터: 주문자, 배송지, 주문항목 변환: 내부 상태 → 물류 상태코드 전송: 동기 요청, 계약 버전 v2 성공 조건: 물류 요청ID와 접수시각 수신 결과: 주문에 연계 요청ID 기록을 후속 저장 계층에 전달 품질: 설계서의 제한 시간·메시지 크기 준수

이 형식은 구현 코드가 아니라 계약이다. 상태 변경 자체가 어느 트랜잭션에서 이뤄지는지는 업무 서비스와 저장 프로시저의 책임을 별도로 설계한다.

03

2. 세부설계서로 정형화된 인터페이스 기능 정의

2.1 입력 계약

입력 필드, 논리 유형, 필수성, 범위, 최대 크기, 개인정보 등급을 정한다. 호출자가 이미 검증했다고 가정하지 않고 인터페이스 경계에서 계약을 확인한다. 단, 같은 검증을 여러 계층에서 서로 다른 규칙으로 복제하지 않도록 공통 스키마를 사용한다.

2.2 출력 계약

성공 결과의 필드와 의미, 빈 결과, 수신 확인 ID, 처리 시각, 상태를 정의한다. 전송 성공과 업무 처리 성공을 구분한다. HTTP 성공 상태를 받았더라도 본문의 업무 결과가 거절일 수 있고, 메시지 큐에 게시 성공했어도 소비 완료를 뜻하지 않을 수 있다.

2.3 선행·후행 조건

호출 전에 충족할 상태와 성공 후 보장할 상태를 적는다. “요청 전송 전 주문 상태가 유효하다”, “성공 응답의 외부 요청ID가 존재한다”처럼 검증 가능해야 한다. 외부 시스템의 데이터 변경까지 현재 시스템이 보장할 수 있는지 범위를 구분한다.

2.4 변환 규칙

내부 모델과 외부 계약 사이 필드, 코드, 단위, 시간, 배열 구조를 매핑한다. 변환은 순수 함수에 가깝게 분리하면 표본 입력으로 쉽게 시험할 수 있다.

2.5 전송 특성

동기·비동기, 요청-응답·단방향, 최대 메시지 크기, 순서, 중복 가능성, 제한 시간, 처리량을 설계서에서 확인한다. 정상 구현에도 메시지 식별자와 상관관계 ID를 전달할 위치를 둔다.

2.6 완료와 관찰 기준

어떤 결과를 성공으로 볼지, 어떤 메트릭과 로그를 남길지 정의한다. 인터페이스 ID, 계약 버전, 상관관계 ID, 처리 시간, 결과 범주를 기록하되 개인정보·토큰·전체 본문은 기본 로그에서 제외한다.

04

3. 공통 인터페이스 구현의 책임

공통 인터페이스 구현은 업무별 코드에서 반복되는 기술 책임을 재사용 가능한 구성 요소로 제공한다.

[업무 서비스] ↓ 내부 요청 모델 [업무별 매퍼] ↓ 표준 메시지 [공통 인터페이스 계층] ├─ 계약·스키마 검증 ├─ 헤더·추적 정보 생성 ├─ 직렬화/역직렬화 ├─ 전송 어댑터 선택 ├─ 제한 시간·자원 관리 └─ 공통 결과 변환 ↓ [외부 시스템]

공통 계층이 주문 상태나 환불 금액 같은 업무 판단까지 알게 만들지 않는다. 업무별 매퍼와 서비스가 의미를 담당하고 공통 계층은 전송과 계약 실행을 담당한다.

05

4. 공통 구성 요소

4.1 요청·응답 모델

외부 JSON이나 XML을 업무 객체에 바로 섞지 않고 계약별 메시지 모델을 둔다. 버전마다 구조가 다르면 모델과 변환기를 분리한다. 응답의 원본 전체를 상위 계층에 노출하지 않고 필요한 업무 결과로 변환한다.

4.2 헤더 생성기

인터페이스 ID, 메시지 ID, 상관관계 ID, 계약 버전, 송신 시각, 송신 시스템을 일관되게 만든다. 기존 업무 흐름의 상관관계 ID가 있으면 이어받고 없으면 경계에서 새로 생성한다. 사용자 입력을 추적 ID로 그대로 신뢰하지 않는다.

4.3 계약 검증기

필수 필드, 유형, 길이, 패턴, 배열 개수와 코드 매핑을 송신 전·수신 후 검증한다. 기계 스키마와 표현하기 어려운 항목 간 규칙을 분리한다. 검증 오류에는 필드 경로와 규칙 ID를 남기되 민감값은 기록하지 않는다.

4.4 직렬화·역직렬화

객체를 교환 형식으로 바꾸고 되돌린다. 문자 인코딩, 숫자 정밀도, 날짜·시간 형식, 필드명 정책, 알 수 없는 필드 처리, NULL 규칙을 명시한다. 기본 직렬화 설정이 바뀌면 계약이 변할 수 있으므로 설정을 시험과 함께 고정한다.

4.5 전송 어댑터

HTTP, 메시지 브로커, 파일 교환 등 기술별 연결·송수신을 공통 계약 뒤에 캡슐화한다. 업무 코드는 특정 라이브러리의 응답 객체를 직접 다루지 않는다.

interface TransportAdapter: send(endpoint, headers, payload, timeout) -> RawResult

어댑터는 연결과 스트림을 항상 정리하고 설정된 제한 시간을 지킨다. 인증서와 자격증명 주입 지점은 제공하되 실제 보안 정책은 다음 단계에서 적용한다.

4.6 결과 변환기

기술 상태와 외부 업무 결과를 내부 공통 결과로 바꾼다.

InterfaceResult

  • outcome: accepted | rejected | unavailable | invalid_contract
  • externalReference
  • occurredAt
  • errorCategory
  • safeMessage

모든 외부 오류를 문자열 하나로 넘기지 않는다. 구체 예외처리 정책은 다음 레슨에서 outcome과 errorCategory를 사용해 결정할 수 있다.

4.7 설정 공급자

엔드포인트, 계약 버전, 제한 시간, 최대 메시지 크기, 기능 활성화 여부를 코드와 분리한다. 비밀값은 일반 설정과 분리하고 소스·로그에 저장하지 않는다. 시작 시 필수 설정을 검증해 요청 처리 중 뒤늦게 실패하지 않게 한다.

5. 안전한 공통 구현 의사코드

function invokeInterface(interfaceId, businessRequest, context): definition = registry.getApproved(interfaceId) mapper = definition.mapper adapter = adapters.get(definition.transportType)

payloadModel = mapper.toExternal(businessRequest) contractValidator.validate(payloadModel, definition.schema)

envelope = messageFactory.create( interfaceId = interfaceId, version = definition.version, correlationId = context.correlationId, body = payloadModel)

rawResult = adapter.send( endpoint = definition.endpointReference, headers = envelope.safeHeaders, payload = serializer.serialize(envelope), timeout = definition.timeout)

response = serializer.deserialize(rawResult.body, definition.responseSchema) contractValidator.validate(response, definition.responseSchema) return mapper.toBusinessResult(response)

finally: adapter.releaseResources()

endpointReference는 승인된 설정 키이며 호출자가 URL을 임의로 넘기지 않는다. 실제 구현에서는 응답 크기 제한, 콘텐츠 유형, 자원 자동 해제를 적용한다.

07

6. 구현 절차와 판단 기준

6.1 1단계: 설계 기준선 고정

인터페이스 ID, 상세 설계서 버전, 스키마, 코드표, 표본, 비기능 기준을 확정한다. 미결 항목을 개발자 임의값으로 채우지 않고 이슈로 되돌린다.

6.2 2단계: 업무·공통 책임 분리

각 기능에서 반복되는 직렬화·전송·검증·추적과 업무별 매핑·상태 판단을 분류한다. 변경 이유가 다른 코드를 억지로 하나의 거대한 공통 함수에 합치지 않는다.

6.3 3단계: 공통 계약 설계

어댑터, 직렬화기, 검증기, 결과 모델의 인터페이스를 정의한다. 외부 라이브러리 타입이 업무 계층까지 새지 않게 한다. 테스트 대역을 주입할 수 있는 경계를 둔다.

6.4 4단계: 최소 구현

정상 경로의 한 인터페이스를 수직으로 연결해 메시지 생성부터 응답 매핑까지 검증한다. 불필요한 모든 전송 기술을 미리 구현하지 않는다.

6.5 5단계: 계약·단위 시험

매퍼, 날짜·숫자 변환, 필수값, 최대 크기, 헤더 생성, 직렬화 왕복을 시험한다. 고정 표본을 승인 스키마로 검증하고 송신·수신 양쪽 표본과 비교한다.

6.6 6단계: 통합과 관찰 확인

시험 환경 외부 시스템 또는 서비스 가상화 도구와 연결한다. 상관관계 ID가 전 구간에 이어지고 지연·결과 범주가 민감정보 없이 기록되는지 확인한다.

6.7 7단계: 코드·설계 추적

구현 모듈, 설정, 시험 사례를 인터페이스 ID와 연결한다. 계약 버전 변경 시 영향 범위를 찾을 수 있어야 한다.

7. 구체 시나리오

상황

회원 시스템과 알림 시스템 모두 HTTP 방식으로 외부 서비스를 호출한다. 기존 코드는 각 기능이 URL 문자열, JSON 변환, 제한 시간, 로그 형식을 각각 구현해 날짜 형식과 오류 결과가 다르다.

공통화

  1. 업무별 요청 모델과 외부 매퍼는 회원·알림 모듈에 남긴다.
  2. 공통 헤더, 상관관계 ID, JSON 직렬화 설정, 응답 크기 제한, HTTP 자원 관리는 공통 어댑터에 둔다.
  3. 각 계약의 엔드포인트·버전·제한 시간은 승인된 설정 레지스트리에서 가져온다.
  4. 회원 응답의 memberId와 알림 응답의 deliveryId 의미는 업무별 결과 매퍼가 담당한다.
  5. 공통 결과는 accepted·rejected·unavailable 같은 범주를 제공하고 세부 재시도는 다음 예외 정책에서 정한다.

모든 외부 요청을 하나의 거대한 데이터 객체로 만들지 않는다. 공통 헤더와 전송 책임만 재사용하고 계약별 본문 타입은 분리해야 잘못된 필드 조합을 컴파일·검증 단계에서 찾기 쉽다.

09

8. 산출물과 체크리스트

주요 산출물은 정형화 기능 명세, 인터페이스별 입출력 계약, 매핑표, 공통 모듈 설계, 어댑터·검증기·직렬화기 코드, 설정 명세, 단위·계약·통합 시험 결과, 추적표다.

  • 기능 ID, 시작·완료 조건, 입력·출력이 명확한가?
  • 전송 성공과 외부 업무 성공을 구분하는가?
  • 업무 매핑과 공통 기술 책임이 분리되었는가?
  • 날짜·숫자·NULL·코드 변환이 승인 표준과 일치하는가?
  • 호출자가 임의 엔드포인트·SQL·헤더를 전달하지 못하는가?
  • 외부 라이브러리 타입이 업무 계층에 노출되지 않는가?
  • 연결·스트림이 모든 경로에서 해제되는가?
  • 비밀과 민감 본문이 로그·일반 설정에 없는가?
  • 상관관계 ID와 계약 버전이 전 구간 추적되는가?
  • 매퍼와 전송을 독립적으로 시험할 수 있는가?
10

9. 자주 틀리는 함정

  1. 자연어 설계서를 개발자 해석에 맡긴 채 구현하지 않는다.
  2. 전송 성공을 업무 처리 성공과 같은 것으로 보지 않는다.
  3. 공통 모듈에 주문·회원 같은 업무 규칙을 넣지 않는다.
  4. 모든 인터페이스를 하나의 범용 지도 구조로 만들어 타입 검증을 잃지 않는다.
  5. 직렬화 라이브러리 기본값이 계약과 같다고 단정하지 않는다.
  6. 알 수 없는 코드를 임의 기본값으로 바꾸지 않는다.
  7. 엔드포인트와 계약 버전을 코드 여러 곳에 하드코딩하지 않는다.
  8. 추적 로그에 전체 메시지와 개인정보를 남기지 않는다.
  9. 정상 응답만 시험하고 최대 크기·NULL·정밀도 경계를 놓치지 않는다.
  10. 아직 필요 없는 전송 기술까지 추상화해 복잡도를 늘리지 않는다.

10. 확인 문제

문제 1

인터페이스 기능을 정형화할 때 필요한 항목 네 가지를 쓰시오.

정답과 해설: 입력, 출력, 선행조건, 완료조건을 들 수 있다. 변환, 품질 기준, 추적 ID와 오류 범주도 필요하다.

문제 2

전송 성공과 업무 성공을 구분해야 하는 이유는 무엇인가?

정답과 해설: 메시지 전달이나 HTTP 수신은 성공했어도 외부 업무 검증에서 거절될 수 있기 때문이다.

문제 3

공통 인터페이스 모듈에 적합한 책임 세 가지는 무엇인가?

정답과 해설: 직렬화, 계약 검증, 전송·자원 관리를 들 수 있다. 공통 헤더와 추적도 적합하다.

문제 4

업무별 코드 매핑을 공통 전송 어댑터에 넣으면 안 되는 이유는 무엇인가?

정답과 해설: 업무가 바뀔 때 전송 모듈까지 변경되고 다른 인터페이스에 잘못된 규칙이 전파되어 응집도가 낮아지기 때문이다.

문제 5

상관관계 ID의 역할은 무엇인가?

정답과 해설: 여러 서비스와 인터페이스 호출을 거치는 한 업무 흐름의 로그·지표를 연결해 추적하게 한다.

문제 6

직렬화 왕복 시험에서 확인할 항목 네 가지를 쓰시오.

정답과 해설: 숫자 정밀도, 날짜·시간대, NULL·누락, 문자 인코딩을 들 수 있다. 알 수 없는 필드와 배열 순서도 확인한다.

문제 7

전송 어댑터를 인터페이스 뒤에 두면 얻는 이점은 무엇인가?

정답과 해설: 업무 코드가 특정 통신 라이브러리에 결합되지 않고 시험 대역을 주입하거나 기술 구현을 교체하기 쉬워진다.

문제 8

공통 결과 모델에 원본 외부 오류 문자열만 전달하면 부족한 이유는 무엇인가?

정답과 해설: 호출자가 재시도 가능, 업무 거절, 계약 오류를 안정적으로 구분할 수 없고 민감한 내부 정보가 노출될 수 있다.

문제 9

공통화 대상을 판단하는 기준은 무엇인가?

정답과 해설: 여러 기능에서 같은 이유로 변경되는 동일 책임인지 본다. 단지 코드 모양이 비슷하지만 업무 의미가 다르면 분리한다.

12

11. 핵심 요약

  • 세부설계서로 정형화된 인터페이스 기능 정의는 입력·출력·조건·변환·완료·품질을 구현 가능한 계약으로 만드는 일이다.
  • 전송 성공과 외부 업무 성공, 내부 모델과 외부 메시지 모델을 구분한다.
  • 공통 인터페이스 구현은 헤더·추적, 검증, 직렬화, 전송 어댑터, 공통 결과, 설정 공급자를 재사용 구조로 제공한다.
  • 업무별 매핑과 상태 판단은 업무 계층에 남기고 외부 라이브러리 타입을 경계 안에 감춘다.
  • 설정과 비밀을 코드에서 분리하고 자원을 항상 해제하며 민감정보 없는 추적 지표를 남긴다.
  • 정형 명세, 표본·스키마, 단위·계약·통합 시험을 인터페이스 ID와 버전으로 연결한다.
