# 1-5-2-2. 기능 구현 실패 시 예외처리방안 정의 · 인터페이스 보안 기능 적용

## 수행 범위와 목표

이 레슨의 정확한 토픽은 **기능 구현 실패 시 예외처리방안 정의**와 **인터페이스 보안 기능 적용**이다. 인터페이스 실패를 업무 거절·계약 오류·일시 장애·영구 장애로 분류해 제한 시간, 재시도, 중복 방지, 격리, 보상, 수동 복구 방안을 정의하고, 인증·인가·기밀성·무결성·재전송 방지·비밀 관리·감사를 구현하는 실무를 다룬다.

정상 경로의 공통 인터페이스 구현은 앞 레슨에서 다뤘고, 감시 도구 준비와 구현 검증 보고서는 다음 레슨 범위다. 여기서는 실패와 위협이 발생해도 데이터와 업무 상태를 안전하게 유지하는 구현에 집중한다.

학습 목표는 다음과 같다.

1. 실패 원인과 재시도 가능성을 분리해 오류 분류표를 작성한다.
2. 제한 시간·재시도·멱등성·격리·보상 정책을 업무 의미와 연결한다.
3. 인증, 인가, 전송 보호, 메시지 무결성, 입력 검증과 비밀 교체를 적용한다.
4. 오류 응답과 로그에서 민감정보를 제거하고 추적 가능한 안전한 증적을 남긴다.

## 1. 실패를 먼저 분류해야 하는 이유

모든 오류를 같은 예외로 처리하면 잘못된 재시도와 데이터 불일치가 생긴다. 결제 한도 초과라는 업무 거절은 다시 보내도 성공하지 않지만, 짧은 네트워크 단절은 재시도로 복구될 수 있다. 필수 필드 누락은 계약 수정 대상이지 무한 재시도 대상이 아니다.

| 실패 범주 | 예 | 일반적 방향 |
|---|---|---|
| 입력·계약 오류 | 필수 필드 누락, 잘못된 코드 | 즉시 거절, 격리, 생산자 수정 |
| 업무 거절 | 재고 부족, 승인 한도 초과 | 호출자에게 명확한 결과, 임의 재시도 금지 |
| 인증·인가 실패 | 만료 자격증명, 권한 부족 | 보안 사건 분류, 자격 교체·권한 검토 |
| 일시 기술 장애 | 짧은 단절, 일시 과부하 | 상한 있는 지연 재시도 검토 |
| 영구 기술 장애 | 잘못된 주소, 지원 종료 버전 | 설정·배포 수정, 반복 전송 중지 |
| 제한 시간 | 응답 기한 초과 | 결과 미확정 여부 확인, 중복 방지 |
| 부분 처리 | 외부는 성공했으나 내부 기록 실패 | 조회·재조정·보상 절차 |

오류코드 하나를 범주와 직접 같다고 단정하지 않는다. 외부 시스템의 코드 의미와 문서를 확인하고 알려지지 않은 코드는 안전한 미확인 상태로 처리한다.

## 2. 기능 구현 실패 시 예외처리방안 정의

### 2.1 제한 시간

연결, 요청 전송, 응답 대기, 전체 업무 기한을 구분한다. 제한 시간이 없으면 장애 시 작업자·연결이 고갈될 수 있고, 너무 짧으면 정상 처리도 실패한다. 외부 서비스 목표와 내부 남은 기한을 기준으로 설정한다.

시간 초과는 외부 처리가 실패했다는 뜻이 아니다. 응답만 잃고 외부는 성공했을 수 있다. 상태 변경 요청이라면 같은 업무 키로 결과 조회 또는 안전한 재전송을 할 수 있어야 한다.

### 2.2 재시도

재시도 전 다음을 확인한다.

1. 오류가 일시적인가?
2. 요청이 멱등하거나 중복 방지 키가 있는가?
3. 호출 전체 기한 안에 남은 시간이 있는가?
4. 외부가 재시도 지침이나 대기 시간을 제공하는가?
5. 동시에 많은 요청이 재시도해 장애를 키우지 않는가?

즉시 반복보다 지수형 지연과 무작위 분산을 사용해 재시도 폭주를 줄일 수 있다. 최대 횟수와 총시간을 정하고 실패 후 격리 또는 수동 처리로 전환한다.

### 2.3 멱등성과 중복 방지

같은 요청을 여러 번 처리해도 최종 업무 결과가 한 번 처리한 것과 같도록 설계한다. 결제 요청에는 주문ID와 처리 유형으로 만든 고유 업무 키를 사용할 수 있다.

    receive(request):
        validate(request)
        key = request.idempotencyKey

        if resultStore.contains(key):
            return resultStore.get(key)

        result = performExactlyOneBusinessDecision(request)
        resultStore.saveAtomically(key, result)
        return result

“먼저 존재 확인 후 처리”가 원자적이지 않으면 동시 요청 두 개가 모두 통과할 수 있다. 고유 제약, 트랜잭션, 원자적 기록 등 저장소 특성에 맞는 보장이 필요하다.

### 2.4 회로 차단과 역압

외부 서비스가 계속 실패할 때 모든 요청이 제한 시간까지 대기·재시도하면 자원이 고갈된다. 일정 오류율을 넘으면 일시적으로 호출을 빠르게 거절하고 회복 여부를 제한적으로 확인하는 회로 차단을 검토할 수 있다.

큐의 생산 속도가 소비 속도보다 빠르면 큐 지연과 저장량이 증가한다. 최대 큐 크기, 생산 제한, 우선순위, 만료, 격리 기준을 정한다. 단순히 큐가 있으므로 무한히 버틸 수 있다고 생각하지 않는다.

### 2.5 격리와 재처리

계약 오류나 반복 실패 메시지는 정상 큐를 막지 않도록 별도 격리 영역에 둔다. 격리 기록에는 메시지 ID, 인터페이스·버전, 오류 범주, 최초·최근 시각, 재시도 횟수, 안전한 원인 정보를 남긴다.

재처리 전에 원인이 해결되었는지, 이미 외부에서 처리되었는지 확인한다. 원본 민감 메시지를 운영 화면에 그대로 노출하지 않고 권한·마스킹·보존을 적용한다.

### 2.6 보상과 재조정

분산된 두 시스템을 하나의 로컬 트랜잭션으로 묶을 수 없는 경우 부분 성공이 발생할 수 있다. 외부 결제 성공 후 주문 저장 실패라면 결제 취소 보상, 결과 재조회, 수동 조정 중 업무에 맞는 절차가 필요하다.

보상은 과거를 지우는 것이 아니라 새로운 반대 업무를 수행하는 것이므로 실패할 수 있고 감사 이력이 필요하다. 정기 재조정으로 양쪽 업무 키와 상태를 비교해 누락을 찾는다.

### 2.7 안전한 오류 응답

외부에는 계약된 오류코드, 안전한 메시지, 상관관계 ID, 재시도 가능 여부만 제공한다. 스택 추적, 내부 주소, SQL, 토큰, 개인정보를 노출하지 않는다. 내부 원인은 접근 통제된 로그에 오류 범주와 추적 ID로 연결한다.

## 3. 예외처리 정책표

| 범주 | 재시도 | 중복 방지 | 최종 처리 | 알림 |
|---|---|---|---|---|
| 계약 오류 | 하지 않음 | 메시지 ID 기록 | 격리·생산자 수정 | 오류율 임계치 |
| 업무 거절 | 업무 결정에 따름 | 업무 키 | 호출자 결과 반환 | 필요 시 업무 알림 |
| 일시 단절 | 제한적 지연 | 필수 | 성공 또는 격리 | 지속 시 운영 |
| 시간 초과 | 결과 확인 후 | 필수 | 조회·재전송·수동 확인 | 미확정 상태 경보 |
| 권한 실패 | 자동 반복 금지 | 해당 없음 | 자격·권한 점검 | 보안 담당 |
| 부분 성공 | 단순 재시도 금지 | 업무 키 | 보상·재조정 | 즉시 또는 기준 초과 |

정책은 인터페이스별 업무 중요도, 외부 계약, 허용 지연에 맞게 수치화한다.

## 4. 인터페이스 보안 기능 적용

### 4.1 위협과 자산 식별

보호할 데이터, 업무 명령, 자격증명, 가용성을 식별하고 신뢰 경계를 그린다.

    [내부 업무 서비스]
       │ 신뢰 경계
       ▼
    [인터페이스 게이트웨이]
       │ 외부 네트워크
       ▼
    [외부 시스템]

경계마다 도청, 변조, 위장, 재전송, 권한 상승, 서비스 거부, 로그 유출 가능성을 검토한다.

### 4.2 인증

통신 상대의 신원을 확인한다. 인증서 기반 상호 인증, 서명된 토큰, 전용 서비스 자격증명 등 승인된 방식을 사용한다. 공유 비밀번호를 소스에 넣지 않고 비밀 저장소에서 읽으며 만료·교체·폐기 절차를 둔다.

토큰의 서명뿐 아니라 발급자, 대상 서비스, 유효 기간과 사용 시각을 검증한다. 실패 이유를 외부에 지나치게 구체적으로 알려 계정·키 상태를 추측하게 하지 않는다.

### 4.3 인가

인증된 시스템이 어떤 인터페이스와 데이터에 접근할 수 있는지 최소 권한으로 제한한다. “내부 시스템이므로 모든 API 허용”하지 않는다. 서비스 역할, 업무 범위, 고객·조직 경계를 확인하고 관리 인터페이스를 분리한다.

### 4.4 전송 기밀성과 서버 신원

승인된 TLS 정책으로 전송 중 데이터를 보호하고 인증서의 신뢰, 이름, 유효기간을 검증한다. 암호화만 켜고 인증서 검증을 끄면 공격자 서버와 암호화 통신할 수 있다. 인증서 갱신을 감시하고 교체 시 양쪽 신뢰를 시험한다.

### 4.5 메시지 무결성과 서명

중간 전달·저장 과정에서도 변조 여부를 확인해야 하면 메시지 서명 또는 인증 코드를 적용한다. 어떤 필드, 직렬화 순서, 문자 인코딩, 시간과 키 ID가 서명 대상인지 양쪽이 같아야 한다.

비밀번호 해시와 메시지 서명은 목적이 다르다. 서명 검증 키와 암호화 키의 수명·권한도 분리해 관리할 수 있다.

### 4.6 재전송 공격 방지

공격자가 정상 메시지를 복사해 다시 보내는 것을 막으려면 메시지 ID, 생성시각, 짧은 허용 시간, 일회값, 중복 기록을 조합한다. 시계 오차 허용 범위를 정하고 단순 시각 검사만으로 중복 업무 처리를 막았다고 생각하지 않는다.

### 4.7 입력·출력 검증

스키마, 최대 메시지 크기, 중첩 깊이, 배열 수, 허용 콘텐츠 유형을 제한한다. 파서 취약점과 자원 고갈을 줄이고 알 수 없는 필드 처리 규칙을 정한다. 외부에서 받은 텍스트를 로그·HTML·명령·SQL에 사용할 때 각 출력 문맥에 맞게 인코딩하거나 매개변수화한다.

### 4.8 민감정보와 로그

업무 목적에 필요한 필드만 전송한다. 토큰, 비밀번호, 전체 주민식별정보, 카드정보를 일반 로그에 기록하지 않는다. 본문 로깅이 꼭 필요하면 필드별 마스킹, 접근 권한, 짧은 보존, 감사와 비운영 합성 데이터를 사용한다.

## 5. 보안 적용 절차

1. **인터페이스·데이터 분류**: 기밀성·무결성·가용성 영향과 규정 요구를 정한다.
2. **신뢰 경계와 위협 모델**: 송신, 중계, 수신, 저장·로그 경로의 위협을 식별한다.
3. **통제 선택**: 인증, 인가, 전송 보호, 서명, 재전송 방지, 입력 제한을 위험에 매핑한다.
4. **키·비밀 생명주기 설계**: 발급, 배포, 사용, 교체, 폐기, 비상 취소와 복구 책임을 정한다.
5. **공통 계층 적용**: 검증된 보안 라이브러리와 중앙 정책을 사용하되 인터페이스별 권한을 분리한다.
6. **음성·경계 시험**: 만료·위조·권한 부족·변조·재전송·큰 메시지를 시험한다.
7. **관찰과 대응**: 인증 실패, 권한 거절, 서명 실패, 재전송 탐지 지표와 대응 절차를 둔다.

암호 알고리즘을 직접 구현하지 않고 조직이 승인한 라이브러리와 정책을 사용한다. 구체 알고리즘·버전은 당시의 보안 기준과 공식 문서를 따른다.

## 6. 안전한 처리 의사코드

    function receiveInterface(rawRequest):
        enforceTransportSecurity(rawRequest.connection)
        principal = authenticate(rawRequest.credential)
        authorize(principal, rawRequest.interfaceId)

        enforceSizeAndContentType(rawRequest)
        verifySignatureAndFreshness(rawRequest)
        rejectReplay(rawRequest.messageId)

        message = parseWithSafeLimits(rawRequest.body)
        contractValidator.validate(message)

        try:
            return idempotentProcessor.process(
                message.idempotencyKey, message.body)
        catch BusinessRejection as error:
            return safeBusinessResult(error.code)
        catch TemporaryDependencyFailure as error:
            applyBoundedPolicy(error, message)
        finally:
            auditWithoutSecrets(principal, message.messageId)

실제 오류 세부는 보호된 내부 추적 시스템으로 보내고 외부 응답에는 안전한 범주만 포함한다.

## 7. 구체 시나리오

### 상황

주문 시스템이 결제 시스템에 승인 요청을 보낸다. 응답 제한 시간이 지났지만 결제 시스템에는 승인 기록이 생성되었을 수 있다.

### 잘못된 처리

동일 요청을 새 승인 번호로 즉시 재전송하면 이중 승인될 수 있다. 시간 초과를 실패로 단정해 주문만 취소해도 결제와 주문이 어긋난다.

### 안전한 처리

1. 주문ID와 결제 시도 차수를 기반으로 고유 멱등 키를 보낸다.
2. 시간 초과 시 같은 키로 결과 조회 또는 외부가 보장한 멱등 재호출을 수행한다.
3. 결과를 확인할 수 없으면 “결제 결과 미확정” 상태로 격리하고 사용자에게 재결제를 즉시 유도하지 않는다.
4. 일정 시간이 지나도 미확정이면 재조정 작업이 결제·주문 기록을 비교한다.
5. 인증 토큰과 카드 관련 민감값은 로그에서 제외하고 주문ID·외부 거래참조·상관관계 ID만 권한 있게 남긴다.
6. 승인 API는 결제 서비스 역할만 호출하도록 인가한다.

## 8. 산출물과 체크리스트

주요 산출물은 오류 분류표, 예외처리 정책표, 재시도·멱등성 설계, 격리·재처리·보상 절차, 위협 모델, 인증·인가 매트릭스, 키·비밀 관리 계획, 보안 시험 결과다.

- 오류가 계약·업무·일시·영구·권한·부분 실패로 구분되는가?
- 제한 시간 후 외부 결과가 미확정일 수 있음을 처리하는가?
- 재시도 대상·대기·횟수·총시간이 정해졌는가?
- 상태 변경 요청에 원자적인 멱등성 보장이 있는가?
- 격리 메시지의 권한·보존·재처리 책임이 있는가?
- 부분 성공에 보상·재조정 절차가 있는가?
- 상대 인증과 인터페이스별 최소 권한을 적용했는가?
- TLS 인증서 검증과 갱신 시험이 있는가?
- 서명·재전송 방지의 시간·키·직렬화 규칙이 일치하는가?
- 비밀·토큰·개인정보가 오류 응답과 로그에서 제거되는가?

## 9. 자주 틀리는 함정

1. 모든 실패를 즉시 같은 횟수로 재시도하지 않는다.
2. 시간 초과를 외부 처리 실패라고 단정하지 않는다.
3. 멱등 키 존재 확인과 결과 저장을 비원자적으로 구현하지 않는다.
4. 큐와 재시도가 장애를 무한히 흡수한다고 생각하지 않는다.
5. 보상을 원래 거래 삭제와 같은 것으로 보지 않는다.
6. 인증과 인가를 혼동하지 않는다.
7. TLS 사용만 확인하고 인증서 검증을 끄지 않는다.
8. 메시지 암호화가 송신자 신원과 권한을 자동 보장한다고 보지 않는다.
9. 토큰 서명만 보고 발급자·대상·만료를 생략하지 않는다.
10. 전체 요청·응답 본문을 디버그 로그에 남기지 않는다.

## 10. 확인 문제

### 문제 1

업무 거절과 일시 기술 장애를 구분해야 하는 이유는 무엇인가?

**정답과 해설:** 업무 거절은 같은 요청을 반복해도 성공하지 않지만 일시 장애는 제한된 재시도로 복구될 수 있어 처리 정책이 다르기 때문이다.

### 문제 2

시간 초과 후 상태 변경 요청을 바로 새 요청으로 보내면 위험한 이유는 무엇인가?

**정답과 해설:** 외부 처리는 성공하고 응답만 잃었을 수 있어 중복 결제·등록이 발생할 수 있다. 결과 조회나 같은 멱등 키를 사용한다.

### 문제 3

안전한 재시도 조건 네 가지를 쓰시오.

**정답과 해설:** 일시 오류, 멱등성·중복 방지, 남은 기한, 횟수·대기 상한을 들 수 있다. 외부 재시도 지침도 확인한다.

### 문제 4

격리된 실패 메시지를 재처리하기 전에 확인할 것은 무엇인가?

**정답과 해설:** 원인이 해결되었는지, 이미 외부에서 처리되었는지, 계약 버전과 데이터가 여전히 유효한지 확인한다.

### 문제 5

인증과 인가의 차이는 무엇인가?

**정답과 해설:** 인증은 상대가 누구인지 확인하고, 인가는 확인된 상대가 특정 인터페이스와 데이터에 접근할 권한이 있는지 판단한다.

### 문제 6

TLS 인증서 검증을 끄면 생기는 문제는 무엇인가?

**정답과 해설:** 통신은 암호화되어도 공격자의 서버와 연결될 수 있어 상대 신원을 보장하지 못한다.

### 문제 7

재전송 공격 방지에 사용할 요소 네 가지를 쓰시오.

**정답과 해설:** 메시지 ID, 생성시각과 허용 시간, 일회값, 처리된 ID 기록을 들 수 있다. 멱등 업무 키도 함께 사용한다.

### 문제 8

인터페이스 로그에 전체 본문을 남기면 위험한 이유는 무엇인가?

**정답과 해설:** 토큰·개인정보가 로그와 백업에 확산되고 로그 열람자가 업무 데이터에 접근할 수 있기 때문이다.

### 문제 9

부분 성공을 찾기 위한 재조정의 역할은 무엇인가?

**정답과 해설:** 양쪽 시스템의 업무 키와 상태를 주기적으로 비교해 한쪽에만 반영된 거래를 찾고 보상·재처리 대상으로 만드는 것이다.

## 11. 핵심 요약

- **기능 구현 실패 시 예외처리방안 정의**는 오류를 분류하고 제한 시간, 재시도, 멱등성, 회로 차단, 격리, 보상·재조정을 업무에 맞게 선택하는 일이다.
- 시간 초과는 결과 미확정일 수 있으며 상태 변경은 중복 방지와 결과 확인이 필요하다.
- **인터페이스 보안 기능 적용**은 인증·인가, TLS, 메시지 무결성, 재전송 방지, 입력 제한, 비밀·로그 보호를 구현하는 일이다.
- 암호 기능을 직접 만들지 않고 승인된 정책·라이브러리와 키 생명주기를 사용한다.
- 외부 오류 응답에는 안전한 코드와 추적 ID만 제공하고 민감한 원인은 보호된 내부 기록으로 연결한다.
- 정상 기능뿐 아니라 위조·만료·권한 부족·변조·큰 메시지·부분 성공을 시험한다.
