# 1-6-1-1. UI 표준·지침에 따라 요구사항 확인 · UI 요구사항을 반영한 프로토타입 제작

## 수행 범위와 목표

이 레슨의 정확한 토픽은 **UI 표준·지침에 따라 요구사항 확인**과 **UI 요구사항을 반영한 프로토타입 제작**이다. 기능 요구를 화면 요소로 옮기기 전에 조직의 디자인 시스템, 접근성, 반응형·장치, 입력·오류·보안 지침과 대조하고, 핵심 사용자 흐름을 프로토타입으로 만들어 요구의 누락과 오해를 조기에 확인하는 실무를 다룬다.

UI/UX 엔지니어와 적정성을 공식 검토하고 UI 요구사항 확인 전체 절차를 승인하는 일은 다음 레슨의 범위다. 상세 화면·폼 흐름과 메뉴 구조 설계는 그 다음 UI 설계 레슨에서 다룬다. 여기서는 요구 확인과 학습용 프로토타입에 집중한다.

학습 목표는 다음과 같다.

1. 기능·사용성·접근성·장치·보안 요구를 UI 표준에 대조한다.
2. 사용자, 업무 목표, 상태·오류·권한·데이터 조건을 화면 요구로 구체화한다.
3. 검증 질문에 맞는 저·중·고충실도 프로토타입을 선택한다.
4. 시나리오 워크스루와 관찰로 피드백을 수집하고 요구 추적표를 갱신한다.

## 1. UI 요구사항의 구성

UI 요구사항은 “화면을 예쁘게 만든다”는 요청이 아니다. 사용자가 어떤 맥락에서 어떤 목표를 달성하고, 시스템이 어떤 정보와 상태를 제공하며, 입력 오류와 접근 제약을 어떻게 처리할지 정의한다.

| 관점 | 확인 질문 |
|---|---|
| 사용자·역할 | 누가 사용하며 권한·숙련도·보조기술은 무엇인가 |
| 목표·과업 | 사용자가 완료하려는 업무와 빈도·중요도는 |
| 정보 | 판단에 필요한 값, 단위, 시점과 우선순위는 |
| 입력 | 필수·선택, 형식, 범위, 기본값과 민감도는 |
| 상태 | 로딩, 성공, 빈 결과, 오류, 권한 부족을 어떻게 알리는가 |
| 장치·환경 | 화면 크기, 입력 방식, 네트워크, 밝기·소음 제약은 |
| 품질 | 학습성, 효율, 오류 예방, 접근성 목표는 |
| 보안·개인정보 | 노출 최소화, 마스킹, 세션·재인증이 필요한가 |

정상 화면 하나만 정의하면 로딩 중 중복 클릭, 빈 목록, 저장 실패, 세션 만료 같은 실제 사용 상황이 구현자 판단에 남는다.

## 2. UI 표준과 지침

### 2.1 조직 UI 표준

조직의 디자인 시스템에는 색, 타이포그래피, 간격, 아이콘, 버튼, 입력 컨트롤, 표, 알림, 대화상자, 반응형 구간과 컴포넌트 사용 규칙이 포함될 수 있다. 승인된 구성 요소를 재사용하면 일관성과 접근성, 개발·시험 비용을 개선할 수 있다.

표준이 오래되었거나 특정 업무를 지원하지 않는다면 개발자가 임의 변형을 복제하지 않는다. 예외 요청에 사용 목적, 영향, 대안과 디자인 시스템 반영 여부를 남긴다.

### 2.2 접근성 지침

마우스 없이 키보드만으로 핵심 기능을 수행할 수 있는지, 초점 순서와 표시가 명확한지, 텍스트 대체와 레이블이 있는지, 색만으로 상태를 전달하지 않는지 확인한다. 텍스트·배경 대비, 확대, 오류 식별, 동작 시간 제한, 움직임 제어도 고려한다.

특정 접근성 기준의 정확한 수치와 적용 수준은 프로젝트에 적용되는 공식 지침을 확인한다. 프로토타입 단계에서도 키보드 흐름과 화면 읽기 순서를 표시해 후반 재설계를 줄인다.

### 2.3 플랫폼·장치 지침

웹, 모바일, 키오스크는 화면 크기뿐 아니라 입력 방식, 뒤로 가기, 알림, 권한, 네트워크 단절, 안전 영역이 다르다. 지원 브라우저·운영체제·장치, 최소 화면 폭, 터치 대상, 가로·세로 방향을 요구에 포함한다.

“반응형”이라는 한 단어로 끝내지 않고 좁은 화면에서 표와 메뉴가 어떻게 변하며 핵심 행동이 유지되는지 정의한다.

### 2.4 입력과 오류 지침

레이블, 도움말, 필수 표시, 형식 예, 입력 중·제출 후 검증, 오류 위치, 값 보존, 성공 확인을 정한다. 오류 메시지는 무엇이 잘못됐고 어떻게 고칠지 알려야 하며 내부 예외와 보안 정보를 노출하지 않는다.

입력을 무조건 자동 보정하면 사용자가 의도한 값이 바뀔 수 있다. 공백·하이픈·날짜 형식 보정은 원문 보존과 업무 규칙을 확인한다.

### 2.5 콘텐츠·용어 지침

화면 명칭, 버튼 동사, 날짜·금액·단위, 존댓말과 오류 문체를 통일한다. 내부 기술 용어와 코드 대신 사용자의 업무 용어를 쓴다. 동일 행동에 “저장”, “확인”, “등록 완료”를 혼용하지 않는다.

### 2.6 개인정보·보안 지침

필요한 정보만 표시하고 역할별 마스킹, 재인증, 자동 로그아웃, 복사·내보내기, 브라우저 저장 여부를 확인한다. 비밀번호 입력의 표시 전환은 사용자 통제와 주변 노출을 고려하고 비밀번호를 로그·오류에 넣지 않는다.

## 3. UI 표준·지침에 따라 요구사항 확인

### 3.1 요구 출처 수집

업무 요구, 사용자 조사, 화면 목록, 데이터·권한 모델, 조직 표준, 접근성·브랜드·보안 지침, 지원 장치 목록을 최신 버전으로 수집한다. 표준과 요구가 충돌하면 어느 것이 상위 제약인지 결정권자에게 확인한다.

### 3.2 사용자와 과업 구체화

역할별 주요 과업, 빈도, 시간 압박, 오류 영향, 현재 불편을 정리한다. 드문 관리자 기능과 매일 반복하는 상담 업무는 화면 밀도와 단축 흐름 요구가 다르다.

    사용자: 상담원
    목표: 주문 상태 확인 후 고객에게 안내
    빈도: 하루 수십 회
    필요 정보: 주문·결제·배송 최신 상태
    제약: 통화 중 한 손 키보드 사용, 개인정보 최소 노출
    성공 기준: 고객 식별 후 핵심 상태를 짧은 단계로 확인

### 3.3 화면 상태 도출

각 과업에 초기, 입력 중, 로딩, 빈 결과, 성공, 업무 거절, 기술 오류, 권한 부족, 세션 만료 상태를 만든다. 비동기 처리라면 접수·처리 중·완료·실패와 새로고침·알림 방식을 정의한다.

### 3.4 표준 대조표 작성

| 요구 ID | UI 요구 | 적용 표준 | 적합 여부 | 이슈·결정 |
|---|---|---|---|---|
| UR-12 | 주문 검색 | 검색 컴포넌트 표준 | 적합 | 최소 입력 길이 확인 |
| UR-13 | 오류 안내 | 인라인 오류 지침 | 보완 | 필드별 복구 방법 추가 |
| UR-14 | 모바일 표 | 반응형 데이터 표 | 미확인 | 핵심 칼럼 우선순위 결정 |

표준 항목을 단순 체크하지 않고 실제 사용자 과업과 결합해 판단한다.

### 3.5 검증 가능한 수용 기준

“사용하기 쉽다”를 “처음 사용하는 대상 사용자가 도움 없이 핵심 과업을 완료하고 치명 오류가 없다”처럼 관찰 가능한 기준으로 바꾼다. 시간 기준이 필요하면 대상 사용자, 데이터·장치 조건과 근거를 함께 적는다.

## 4. 프로토타입의 역할과 수준

**UI 요구사항을 반영한 프로토타입 제작**은 완성 화면을 미리 꾸미는 일이 아니라 위험한 가정과 흐름을 적은 비용으로 확인하는 활동이다.

### 4.1 저충실도

종이 스케치나 단순 와이어프레임으로 정보 구조, 화면 순서, 핵심 행동을 확인한다. 빠르게 바꾸기 쉽고 시각 장식에 논의가 치우치는 것을 줄인다. 정확한 간격·색·애니메이션 검증에는 부족하다.

### 4.2 중충실도

실제 문구와 주요 컴포넌트, 클릭 흐름, 오류·빈 상태를 포함한다. 업무 워크스루와 기본 사용성 검증에 적합하다. 데이터·서버 동작은 모의일 수 있음을 표시한다.

### 4.3 고충실도

시각 스타일, 반응형, 상호작용을 실제와 가깝게 표현한다. 이해관계자 합의와 세부 사용성 확인에 유용하지만 제작 비용이 크고 완제품으로 오해하기 쉽다. 실제 접근성·성능·보안을 자동으로 보장하지 않는다.

검증 질문에 필요한 최소 충실도를 선택한다. 메뉴 그룹을 확인하는 데 완성 애니메이션을 만들 필요는 없다.

## 5. 프로토타입 제작 절차

1. **검증 질문 선정**: 가장 불확실하거나 실패 비용이 큰 사용자 흐름을 고른다.
2. **대표 시나리오 정의**: 사용자, 목표, 시작 상태, 데이터, 성공·오류 조건을 정한다.
3. **요구 추적**: 각 화면·요소를 요구 ID와 표준 컴포넌트에 연결한다.
4. **정보 우선순위 배치**: 사용자가 판단할 정보와 핵심 행동을 먼저 배치한다.
5. **상태 제작**: 정상뿐 아니라 로딩·빈 결과·오류·권한·모바일 상태를 포함한다.
6. **상호작용 연결**: 클릭, 키보드, 뒤로 가기, 취소, 저장 후 피드백 흐름을 만든다.
7. **내부 점검**: 용어, 표준, 접근성 주석, 개인정보 노출을 확인한다.
8. **사용자 워크스루**: 설명을 최소화하고 사용자의 행동·발언·막힘을 관찰한다.
9. **결과 반영**: 결함·새 요구·선호를 구분해 요구와 프로토타입 버전을 갱신한다.

## 6. 텍스트 와이어프레임 예시

    ┌──────────────── 주문 검색 ────────────────┐
    │ 고객 식별값 [                    ] [검색] │
    │ 도움말: 주문번호 또는 승인된 고객키 사용 │
    ├───────────────────────────────────────────┤
    │ 검색 전: 검색 조건을 입력하세요           │
    │ 로딩 중: 진행 표시, 검색 버튼 비활성       │
    │ 빈 결과: 조건 확인 및 기간 확장 안내       │
    │ 오류: 필드 근처 원인 + 다시 시도 방법      │
    ├───────────────────────────────────────────┤
    │ 결과: 주문시각 | 상태 | 금액 | 상세 이동   │
    └───────────────────────────────────────────┘

프로토타입 주석에는 키보드 초점 순서, 화면 읽기 레이블, 마스킹 규칙, 좁은 화면에서 결과 항목 우선순위를 적는다. 고객 식별값을 예제에 실제 개인정보로 넣지 않는다.

## 7. 프로토타입 검증 방법

### 7.1 시나리오 워크스루

업무 담당자와 설계자가 사례를 따라가며 요구·상태·문구를 확인한다. 정상 성공뿐 아니라 잘못된 입력, 네트워크 중단, 권한 부족, 취소 후 복귀를 포함한다.

### 7.2 과업 기반 사용성 관찰

대상 사용자에게 목표만 설명하고 수행 경로를 관찰한다. 완료 여부, 막힌 지점, 되돌아감, 오류와 발언을 기록한다. 진행자가 버튼 위치를 알려 주면 실제 학습성 문제를 숨기므로 개입 규칙을 정한다.

### 7.3 접근성 초기 검토

키보드 이동 순서, 초점 표시, 레이블·오류 연결, 색 외 상태 표현, 확대 시 재배치를 확인한다. 정적 이미지 프로토타입은 실제 보조기술 시험을 대체하지 못하므로 구현 단계 검증 항목으로 넘긴다.

### 7.4 피드백 분류

| 피드백 | 처리 |
|---|---|
| 요구 누락 | 요구 이슈로 등록, 영향 분석 |
| 표준 위반 | 표준 컴포넌트로 수정 또는 예외 승인 |
| 사용성 결함 | 과업·근거·심각도와 함께 수정 |
| 개인 선호 | 대상 사용자 대표성·목표와 비교 |
| 기술 제약 | 개발·UI/UX와 대안 검토 |

참여자 한 명의 선호를 즉시 전체 요구로 확정하지 않는다.

## 8. 구체 시나리오

### 상황

현장 기사가 휴대전화로 장비 점검 결과를 입력한다. 지하에서는 네트워크가 불안정하고 장갑을 착용하며, 사진과 점검 항목이 많다.

### 요구 확인

- 터치 대상과 간격을 모바일 지침에 대조한다.
- 긴 한 화면 대신 업무 단위 단계 분리를 검토한다.
- 필수·선택 항목과 사진 최대 수·크기를 표시한다.
- 네트워크 중단 시 임시 저장과 전송 대기 상태를 구분한다.
- 중복 제출 방지와 마지막 저장 시각을 보여 준다.
- 장비 식별자는 카메라 스캔과 수동 입력 대안을 제공한다.
- 오류가 난 항목만 찾아 수정할 수 있게 한다.

### 프로토타입 검증

종이·중충실도 프로토타입으로 장갑 사용자의 터치, 한 손 사용, 중간 저장, 네트워크 실패 후 재개 흐름을 관찰한다. 실제 오프라인 저장 안정성과 파일 업로드 성능은 프로토타입만으로 증명되지 않으므로 구현 시험 항목으로 기록한다.

## 9. 산출물과 체크리스트

주요 산출물은 UI 요구 목록, 사용자·과업 시나리오, 표준 대조표, 상태 목록, 수용 기준, 프로토타입, 요구-화면 추적표, 워크스루·사용성 기록, 이슈·변경 이력이다.

- 적용할 조직·접근성·플랫폼·보안 표준 버전이 명확한가?
- 사용자 역할·과업·빈도·환경 제약이 정의됐는가?
- 로딩·빈 결과·오류·권한·세션 상태가 있는가?
- 입력 레이블·필수·형식·오류 복구를 정의했는가?
- 키보드·초점·색 외 표현·확대를 고려했는가?
- 좁은 화면에서 정보·행동 우선순위가 유지되는가?
- 프로토타입 요소가 요구 ID와 표준 컴포넌트에 연결되는가?
- 검증 질문에 맞는 최소 충실도를 선택했는가?
- 합성 데이터만 사용하고 민감정보를 노출하지 않았는가?
- 피드백을 결함·새 요구·선호로 구분해 반영했는가?

## 10. 자주 틀리는 함정

1. UI 요구를 색과 배치 요구로만 보지 않는다.
2. 표준 컴포넌트를 쓰면 접근성 시험이 필요 없다고 생각하지 않는다.
3. 반응형이라는 단어만 쓰고 좁은 화면 동작을 생략하지 않는다.
4. 오류 메시지에 내부 예외와 보안 정보를 노출하지 않는다.
5. 정상·성공 화면만 프로토타입으로 만들지 않는다.
6. 고충실도 프로토타입을 구현 완료나 성능 증거로 보지 않는다.
7. 진행자가 사용법을 알려 주며 사용성 문제를 가리지 않는다.
8. 한 참여자의 개인 선호를 전체 요구로 확정하지 않는다.
9. 실제 개인정보를 프로토타입 표본에 넣지 않는다.
10. 프로토타입 수정 후 요구·수용 기준·추적표를 그대로 두지 않는다.

## 11. 확인 문제

### 문제 1

UI 요구사항에 기능 외에 포함할 관점 네 가지를 쓰시오.

**정답과 해설:** 사용성, 접근성, 장치·환경, 보안·개인정보를 들 수 있다. 상태·오류와 성능도 중요하다.

### 문제 2

색만으로 오류를 표시하면 안 되는 이유는 무엇인가?

**정답과 해설:** 색을 구별하기 어려운 사용자가 상태를 인식하지 못할 수 있다. 텍스트, 아이콘, 레이블 등 다른 단서를 함께 제공한다.

### 문제 3

저충실도 프로토타입이 적합한 검증 질문은 무엇인가?

**정답과 해설:** 정보 구조, 화면 순서, 핵심 행동과 메뉴 그룹처럼 빠른 변경이 필요한 초기 질문에 적합하다.

### 문제 4

프로토타입에 오류·빈 결과 상태가 필요한 이유는 무엇인가?

**정답과 해설:** 실제 사용에서 빈 데이터와 실패가 자주 발생하며 복구·안내 요구를 구현 전에 확인해야 하기 때문이다.

### 문제 5

“사용하기 쉽다”를 검증 가능한 기준으로 바꾸려면 무엇이 필요한가?

**정답과 해설:** 대상 사용자, 대표 과업, 장치·데이터 조건, 완료·오류 기준과 관찰 방법을 정해야 한다.

### 문제 6

고충실도 프로토타입이 실제 접근성과 성능을 보장하지 않는 이유는 무엇인가?

**정답과 해설:** 시각과 클릭 흐름을 모사해도 실제 DOM·보조기술·네트워크·서버 구현이 없거나 다를 수 있기 때문이다.

### 문제 7

사용성 관찰 중 진행자의 개입을 제한해야 하는 이유는 무엇인가?

**정답과 해설:** 사용자가 스스로 찾지 못하는 문제를 설명으로 가리면 실제 학습성과 탐색 결함을 발견할 수 없기 때문이다.

### 문제 8

프로토타입 피드백을 요구로 즉시 확정하지 않는 이유는 무엇인가?

**정답과 해설:** 개인 선호인지 대표 사용자 문제인지, 다른 요구·표준·비용에 미치는 영향이 무엇인지 검토해야 하기 때문이다.

### 문제 9

현장 모바일 UI에서 네트워크 실패 프로토타입이 보여 줘야 할 상태는 무엇인가?

**정답과 해설:** 로컬 임시 저장 여부, 전송 대기, 재시도·취소, 마지막 저장·동기화 시각과 중복 제출 방지 상태를 보여 줘야 한다.

## 12. 핵심 요약

- **UI 표준·지침에 따라 요구사항 확인**은 사용자·과업·상태·장치·접근성·보안 요구를 조직 표준과 대조하는 활동이다.
- UI 요구는 정상 화면뿐 아니라 로딩·빈 결과·오류·권한·세션·반응형 상태를 포함한다.
- **UI 요구사항을 반영한 프로토타입 제작**은 위험한 흐름과 가정을 필요한 최소 충실도로 조기에 검증하는 활동이다.
- 프로토타입 요소를 요구·표준에 추적하고 시나리오·과업 관찰·초기 접근성 검토를 수행한다.
- 고충실도 모형도 실제 구현의 접근성·성능·보안을 자동 증명하지 않는다.
- 피드백을 요구 누락, 표준 위반, 사용성 결함, 선호, 기술 제약으로 분류해 승인 절차로 반영한다.
