# 1-6-1-2. UI/UX 엔지니어와 UI 적정성 검토

## 수행 범위와 목표

이 레슨의 정확한 토픽은 **UI/UX 엔지니어와 UI 적정성 검토**와 **UI 요구사항 확인하기의 적용 절차와 판단 기준**이다. 프로토타입과 UI 요구를 UI/UX, 업무, 개발, 접근성, 보안 관점에서 함께 검토해 사용자의 과업과 표준에 적합한지 판정하고, 이슈 해결과 요구 기준선 승인까지 수행하는 실무를 다룬다.

프로토타입을 처음 제작하는 활동은 앞 레슨에서 다뤘다. 개별 화면·폼 흐름과 메뉴 구조를 상세 설계하는 일은 다음 레슨의 범위다. 여기서는 요구와 프로토타입의 적정성을 증거로 확인하는 데 집중한다.

학습 목표는 다음과 같다.

1. UI/UX 엔지니어와 업무·개발 담당자의 검토 역할을 구분한다.
2. 과업 완결성, 일관성, 피드백, 오류 예방·복구, 접근성, 반응형, 개인정보 기준으로 검토한다.
3. 전문가 검토, 인지적 워크스루, 사용자 관찰 결과를 통합한다.
4. 결함·새 요구·선호를 분류하고 기준선 승인 조건을 판단한다.

## 1. UI 적정성의 의미

UI 적정성은 화면이 보기 좋은지에 대한 취향 판단이 아니다. 대상 사용자가 실제 환경에서 핵심 업무를 정확하고 효율적으로 완료하고, 시스템 상태와 오류를 이해하며, 다양한 입력 방식과 보조기술로 접근할 수 있는지를 보는 종합 판단이다.

    요구·표준·사용자 맥락
              ↓
          프로토타입
              ↓
    ┌─────────┼─────────┐
    │         │         │
    업무 검토  UX 검토   기술·접근성 검토
    │         │         │
    └─────────┼─────────┘
              ↓
       이슈·대안·수용 기준
              ↓
        UI 요구 기준선

한 전문가가 모든 관점을 대표하지 않는다. 업무 담당자는 규칙과 용어를, UI/UX 엔지니어는 정보 구조와 상호작용을, 개발자는 구현 제약을, 접근성·보안 담당자는 해당 통제를 검토한다. 실제 사용자 관찰은 전문가가 예상하지 못한 문제를 보완한다.

## 2. 검토 역할과 준비

### 2.1 역할

| 역할 | 주요 확인 |
|---|---|
| UI/UX 엔지니어 | 과업 흐름, 정보 우선순위, 일관성, 피드백, 오류 예방 |
| 업무 담당자 | 업무 용어, 규칙, 예외, 의사결정 정보 |
| 개발자 | 구현 가능성, 상태·데이터·성능·장치 제약 |
| 시험 담당자 | 요구·수용 기준의 검증 가능성, 경계 상태 |
| 접근성 담당자 | 키보드, 초점, 레이블, 대비, 보조기술 |
| 보안·개인정보 담당자 | 최소 노출, 권한, 마스킹, 세션·감사 |
| 실제 사용자 | 과업 이해, 탐색, 실수, 업무 맥락 |

UI/UX 엔지니어가 업무 정책을 임의로 결정하거나 개발자가 구현 편의만으로 요구를 삭제하지 않는다. 결정 권한과 의견 권한을 구분한다.

### 2.2 입력

최신 UI 요구, 적용 표준·지침, 사용자·과업 시나리오, 프로토타입 버전, 요구-화면 추적표, 데이터·권한 모델, 지원 장치와 이전 검토 이슈를 준비한다. 각 참여자가 다른 프로토타입 버전을 보지 않도록 기준선을 표시한다.

### 2.3 검토 시나리오

대표 빈도·중요도가 높은 정상 과업과 오류 영향이 큰 경계 과업을 선택한다. 시작 상태, 사용자 역할, 데이터, 장치, 성공 조건을 적는다. “전체 화면을 자유롭게 보세요”보다 구체 과업이 적정성 문제를 더 잘 드러낸다.

## 3. UI 적정성 검토 기준

### 3.1 과업 완결성과 효율

사용자가 필요한 정보를 발견하고 목표를 끝낼 수 있는가, 불필요한 단계와 반복 입력이 없는가, 빈번한 과업의 경로가 지나치게 긴지 확인한다. 단계 수만 줄이는 것이 항상 좋은 것은 아니다. 위험한 삭제·결제에는 확인과 검토 단계가 필요할 수 있다.

### 3.2 정보 구조와 우선순위

사용자가 현재 위치와 다음 행동을 이해하고 핵심 정보가 시각·읽기 순서에서 먼저 나타나는지 본다. 관련 정보는 묶고 다른 목적은 구분한다. 전문 용어보다 사용자의 업무 언어를 사용한다.

### 3.3 일관성과 표준

같은 행동은 같은 명칭·위치·모양·결과를 가져야 한다. 버튼 색만이 아니라 키보드 동작, 오류, 날짜·금액, 저장 후 피드백도 일관되어야 한다. 플랫폼 관습과 조직 디자인 시스템을 따르되 사용자의 과업과 충돌하면 근거 있는 예외 절차를 사용한다.

### 3.4 시스템 상태와 피드백

사용자 행동이 접수되었는지, 처리 중인지, 성공·실패·부분 완료인지 적절한 시간 안에 알린다. 오래 걸리는 작업에는 진행 상태, 취소 가능성, 백그라운드 처리 여부를 보여 준다. 버튼을 눌러도 변화가 없으면 사용자는 중복 제출할 수 있다.

### 3.5 사용자 통제와 되돌리기

실수로 이동하거나 입력한 경우 취소·뒤로 가기·초기화·되돌리기의 결과를 예측할 수 있어야 한다. 저장되지 않은 변경을 잃기 전에 알리고, 위험한 작업은 영향과 대상을 명확히 확인한다. 모든 작업을 경고 대화상자로 막으면 사용자가 습관적으로 확인할 수 있으므로 예방·되돌리기 설계를 함께 본다.

### 3.6 오류 예방과 복구

허용할 수 없는 선택을 비활성화하거나 조건을 미리 안내하고, 입력 형식 예를 제공한다. 오류가 나면 해당 위치, 원인, 수정 방법을 알려 주고 가능한 입력을 보존한다. “오류가 발생했습니다”와 내부 코드만으로는 복구할 수 없다.

### 3.7 접근성

키보드만으로 모든 기능에 도달·실행 가능한지, 초점이 논리적으로 이동하고 모달 종료 후 원래 위치로 돌아오는지 확인한다. 레이블과 설명, 오류 메시지가 입력과 연결되고, 색·소리만으로 상태를 전달하지 않는지 본다.

동적 내용이 갱신될 때 보조기술에 적절히 알려야 하지만 모든 변화가 과도하게 읽히면 방해가 된다. 실제 구현에서 보조기술 시험이 필요하다는 항목을 넘긴다.

### 3.8 반응형·장치 적합성

좁은 화면에서 핵심 행동과 정보가 사라지지 않고, 확대·회전·소프트 키보드에서도 입력이 가능한지 본다. 터치 대상 간격, 긴 표의 대체 표현, 마우스 호버에만 있는 정보를 확인한다.

### 3.9 개인정보와 보안

역할에 필요하지 않은 개인정보가 목록·알림·오류·최근 기록에 노출되지 않는지 본다. 마스킹과 상세 보기 권한, 재인증, 자동 로그아웃, 복사·다운로드 경고를 업무 위험에 맞게 적용한다. 보안을 이유로 사용자가 우회 메모를 만들 정도로 과도한 절차인지도 검토한다.

## 4. 검토 방법

### 4.1 전문가 휴리스틱 검토

여러 전문가가 독립적으로 화면을 보고 문제와 근거를 기록한 뒤 통합한다. 일관성, 상태 가시성, 사용자 통제, 오류 예방, 기억 부담, 도움말 등의 원칙을 점검한다. 전문가 검토는 빠르지만 실제 사용자의 업무 지식과 행동을 완전히 대신하지 못한다.

### 4.2 인지적 워크스루

처음 또는 드물게 사용하는 사용자가 각 단계에서 다음을 판단할 수 있는지 묻는다.

1. 사용자는 달성할 목표를 알고 있는가?
2. 올바른 행동이 화면에서 보이는가?
3. 사용자는 그 행동이 목표와 연결됨을 이해하는가?
4. 행동 후 올바른 진행 피드백을 받는가?

학습성과 탐색 문제를 찾는 데 유용하다.

### 4.3 과업 기반 사용자 관찰

대상 사용자에게 시나리오를 수행하게 하고 완료, 오류, 망설임, 되돌아감, 발언을 관찰한다. 표본이 작으면 모든 사용자 집단을 일반화하지 않고 중요한 문제를 발견하는 정성 증거로 사용한다. 정량 지표를 쓸 때는 대상·조건과 표본 한계를 적는다.

### 4.4 접근성 검토

프로토타입 수준에서는 초점 순서·레이블·색 외 표현·확대를 점검하고, 구현 가능한 시제품에서는 키보드와 보조기술을 시험한다. 자동 검사기는 일부 패턴만 찾으므로 수동·사용자 검토를 병행한다.

### 4.5 디자인 비평

제작자를 평가하는 것이 아니라 목표와 근거를 중심으로 대안을 비교한다. “마음에 안 든다” 대신 “빈번한 저장 행동이 접힌 영역 아래 있어 상담원의 핵심 과업 시간이 늘어난다”처럼 관찰 가능한 영향을 말한다.

## 5. 심각도와 처리

| 심각도 | 판단 예 | 처리 |
|---|---|---|
| 치명 | 핵심 과업 완료 불가, 중대한 개인정보 노출 | 기준선 승인 중단 |
| 높음 | 많은 사용자가 큰 오류·재작업 경험 | 구현 전 해결 우선 |
| 중간 | 우회 가능하지만 효율·이해 저하 | 계획에 반영 |
| 낮음 | 제한된 상황의 경미한 불일치 | 일정·비용과 함께 판단 |

발생 빈도, 영향, 지속성, 우회 가능성, 사용자 범위를 근거로 한다. 색상 선호처럼 개인 취향을 치명 결함으로 올리거나 접근 불가 문제를 장식 문제로 낮추지 않는다.

## 6. UI 요구사항 확인하기의 적용 절차와 판단 기준

### 6.1 1단계: 범위·기준선 확정

대상 사용자, 과업, 화면 후보, 표준, 지원 장치, 프로토타입 버전, 완료 기준을 정한다. 필수 업무와 검증하지 못한 범위를 구분한다.

### 6.2 2단계: 요구-표준-프로토타입 추적

각 UI 요구가 어떤 프로토타입 요소와 상태에 표현되는지, 각 요소가 어떤 요구·표준에서 왔는지 양방향으로 확인한다. 출처 없는 개인정보 표시와 구현되지 않은 요구를 찾는다.

### 6.3 3단계: 전문가 교차 검토

UI/UX, 업무, 개발, 시험, 접근성, 보안 관점에서 독립 검토 후 중복·충돌을 통합한다. 미결 업무 규칙은 권한 있는 담당자에게 질문한다.

### 6.4 4단계: 사용자·시나리오 검증

대표 정상·오류 과업을 대상 사용자와 수행한다. 진행자의 개입을 통제하고 행동과 발언, 실패 지점을 기록한다. 실제 개인정보 대신 합성 데이터를 쓴다.

### 6.5 5단계: 이슈 분류와 대안 결정

요구 누락, 표준 위반, 사용성·접근성 결함, 기술 제약, 개인 선호로 분류한다. 각 이슈에 대상, 근거, 영향, 대안, 심각도, 소유자, 수용 기준을 둔다.

### 6.6 6단계: 프로토타입·요구 갱신

승인 대안을 반영하고 관련 상태·문구·추적표·수용 기준을 함께 고친다. 한 화면 수정이 다른 역할·장치·오류 흐름을 깨뜨리지 않는지 재확인한다.

### 6.7 7단계: 기준선 승인

필수 과업이 완료 가능하고 치명·높은 이슈가 해결되며 표준 예외와 잔여 위험이 승인되고 모든 요구가 추적되면 UI 요구 기준선을 승인한다.

### 판단 기준

- 대상 사용자와 핵심 과업·환경이 명확하다.
- 기능·상태·오류·권한·비기능 요구가 완전하다.
- 표준·용어·상호작용이 일관된다.
- 키보드·레이블·색 외 표현·반응형 요구가 확인된다.
- 사용자 관찰에서 핵심 과업을 완료하고 치명 오류가 없다.
- 개인정보 최소 노출과 권한 경계가 명확하다.
- 이슈와 예외에 근거·소유자·수용 기준이 있다.

## 7. 구체 시나리오

### 상황

은행 내부 상담 UI에서 고객 주소 변경을 수행한다. 프로토타입은 새 주소 입력 뒤 즉시 “저장 완료”를 보여 주지만 일부 고객은 추가 본인확인이 필요하다.

### 적정성 검토

1. 업무 담당자는 본인확인 필요 조건과 승인 책임을 제공한다.
2. UI/UX 엔지니어는 저장과 본인확인을 하나의 성공처럼 보이지 않게 상태를 분리한다.
3. 보안 담당자는 고객 정보 마스킹과 재인증 시점을 확인한다.
4. 접근성 검토자는 주소 검색 대화상자의 초점 이동·복귀와 오류 연결을 확인한다.
5. 사용자는 “접수됨”, “확인 필요”, “변경 완료”의 차이를 이해하는지 과업으로 검증한다.
6. 개발자는 외부 주소 서비스 지연·실패 때 수동 입력과 재시도 가능성을 검토한다.

권고 프로토타입은 즉시 완료 대신 “변경 접수”와 다음 단계를 표시하고, 중복 제출을 막으며, 완료 알림의 시점을 업무 결과와 맞춘다.

## 8. 검토 기록 예시

    이슈 ID: UI-RV-021
    화면/상태: 주소 변경 > 외부 검색 실패
    유형: 사용성 + 업무 누락
    근거: 시나리오 S-04, 사용자 3명 중 3명 복구 경로 미발견
    영향: 주소 변경 포기 또는 중복 요청
    대안:
      A. 같은 화면에 수동 입력 제공
      B. 검색 재시도만 제공
    권고: 업무가 허용하면 A, 입력 검증·권한 조건 명시
    소유자: 주소 업무 책임자
    수용 기준: 키보드로 수동 입력 전환 및 원래 값 보존

사용자 수치는 해당 검토의 관찰일 뿐 전체 모집단 통계로 일반화하지 않는다.

## 9. 산출물과 체크리스트

주요 산출물은 적정성 검토 계획, 역할·시나리오, 전문가 검토표, 사용자 관찰 기록, 접근성 점검, 이슈·대안·결정 목록, 수정 프로토타입, 요구-표준-화면 추적표, 승인 기준선이다.

- 모든 참여자가 같은 요구·프로토타입 버전을 검토했는가?
- 핵심·경계 과업에 시작·성공 조건이 있는가?
- UI/UX·업무·개발·접근성·보안 관점이 포함됐는가?
- 과업 완료, 정보 우선순위, 상태 피드백을 확인했는가?
- 오류 예방·복구와 입력값 보존을 확인했는가?
- 키보드·초점·레이블·확대·반응형을 확인했는가?
- 개인정보·권한·세션 요구가 최소 노출 원칙을 지키는가?
- 결함·새 요구·선호·기술 제약을 구분했는가?
- 수정 후 관련 역할·장치·상태를 재검토했는가?
- 기준선 승인 조건과 잔여 위험 승인자가 명확한가?

## 10. 자주 틀리는 함정

1. UI 적정성을 시각 취향 투표로 바꾸지 않는다.
2. UI/UX 엔지니어 한 명이 업무·보안 결정을 대신하지 않는다.
3. 전문가 검토가 실제 사용자 관찰을 완전히 대체한다고 보지 않는다.
4. 단계 수가 적을수록 항상 좋은 UI라고 단정하지 않는다.
5. 경고 대화상자를 많이 띄우면 오류가 예방된다고 생각하지 않는다.
6. 자동 접근성 검사 통과를 전체 접근성 통과로 보지 않는다.
7. 표본이 작은 정성 관찰 결과를 정밀한 전체 통계처럼 쓰지 않는다.
8. 개인 선호와 핵심 과업 실패를 같은 심각도로 다루지 않는다.
9. 프로토타입 수정 후 요구와 수용 기준을 갱신하지 않는 실수를 피한다.
10. 치명 이슈를 일정 이유만으로 근거 없이 위험 수용하지 않는다.

## 11. 확인 문제

### 문제 1

UI 적정성이 단순 미적 평가가 아닌 이유는 무엇인가?

**정답과 해설:** 과업 완료, 정보 이해, 오류 복구, 접근성, 장치·보안 적합성까지 포함하는 사용 결과의 평가이기 때문이다.

### 문제 2

인지적 워크스루가 주로 확인하는 것은 무엇인가?

**정답과 해설:** 처음 또는 드물게 쓰는 사용자가 목표를 알고 올바른 행동을 발견·이해하며 결과 피드백을 받을 수 있는지 확인한다.

### 문제 3

전문가 검토와 사용자 관찰을 함께 해야 하는 이유는 무엇인가?

**정답과 해설:** 전문가는 원칙 위반을 체계적으로 찾지만 실제 업무 행동과 예상 밖의 이해 문제를 놓칠 수 있어 서로 보완하기 때문이다.

### 문제 4

오류 메시지 적정성의 세 요소는 무엇인가?

**정답과 해설:** 오류 위치·원인, 사용자가 취할 수정 방법, 가능한 입력값 보존을 확인한다. 내부 보안정보는 노출하지 않는다.

### 문제 5

시스템 상태 가시성이 부족할 때 발생할 수 있는 문제는 무엇인가?

**정답과 해설:** 사용자가 입력이 접수되지 않았다고 생각해 중복 클릭·제출하거나 처리를 중단할 수 있다.

### 문제 6

접근성 자동 검사만으로 충분하지 않은 이유는 무엇인가?

**정답과 해설:** 자동 도구는 의미 있는 레이블, 실제 키보드 흐름, 보조기술 이해와 업무 완료 같은 문제를 모두 판정하지 못한다.

### 문제 7

UI 이슈 심각도를 정할 요소 네 가지를 쓰시오.

**정답과 해설:** 발생 빈도, 영향 크기, 지속성, 우회 가능성을 들 수 있다. 영향받는 사용자 범위도 중요하다.

### 문제 8

UI 요구 기준선 승인 조건 네 가지를 쓰시오.

**정답과 해설:** 필수 과업 완료 가능, 치명·높은 이슈 해결, 요구 추적, 표준 예외·잔여 위험의 공식 승인을 들 수 있다.

### 문제 9

업무 처리 중간 상태를 모두 “완료”로 표시하면 안 되는 이유는 무엇인가?

**정답과 해설:** 접수, 승인 대기, 실제 완료의 의미가 달라 사용자가 후속 행동과 결과를 잘못 판단할 수 있기 때문이다.

## 12. 핵심 요약

- **UI/UX 엔지니어와 UI 적정성 검토**는 과업, 정보 구조, 일관성, 상태, 오류, 접근성, 장치, 보안을 여러 역할과 함께 검토하는 활동이다.
- 전문가 검토, 인지적 워크스루, 사용자 관찰, 접근성 검토를 서로 보완적으로 사용한다.
- 이슈는 취향이 아니라 대상·근거·영향·대안·심각도·수용 기준으로 기록한다.
- **UI 요구사항 확인하기의 적용 절차와 판단 기준**은 범위, 추적, 교차 검토, 사용자 검증, 이슈 결정, 갱신·재검토, 기준선 승인으로 구성한다.
- 핵심 과업 완료, 치명 이슈 해소, 표준·접근성·개인정보 적합성과 추적성을 승인 기준으로 삼는다.
- 프로토타입 변경을 요구·수용 기준·상태와 함께 갱신해 상세 UI 설계의 신뢰할 입력으로 제공한다.
