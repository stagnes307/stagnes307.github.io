01

수행 범위와 목표

이 레슨의 정확한 토픽은 화면·폼 흐름과 제약사항 설계와 사용자 편의성을 고려한 메뉴 구조 설계이다. 승인된 UI 요구를 바탕으로 화면·폼 사이 이동, 상태·분기·취소·복귀와 입력 제약을 정의하고, 사용자의 업무 관점에서 정보와 기능을 찾기 쉬운 메뉴 계층·명칭·권한·현재 위치 표현을 설계하는 실무를 다룬다.

하위 시스템별 개별 화면과 폼의 상세 레이아웃·필드 설계, UI 설계 전체 승인 절차는 다음 레슨의 주범위다. 여기서는 전체 탐색 구조와 흐름, 제약을 먼저 확정해 상세 화면이 서로 모순되지 않게 한다.

학습 목표는 다음과 같다.

  1. 사용자 과업을 화면 상태와 전이로 바꾸고 정상·예외·복귀 흐름을 설계한다.
  2. 폼의 필수성, 형식, 순서, 권한, 중복 제출, 임시 저장 제약을 정의한다.
  3. 업무 언어와 빈도·중요도에 따라 메뉴를 분류하고 탐색 구조를 만든다.
  4. 흐름도, 화면 전이표, 메뉴 트리, 권한 매트릭스와 점검표를 산출한다.
02

1. 화면·폼 흐름 설계의 의미

화면 흐름은 화면 목록을 화살표로 잇는 것 이상이다. 사용자가 어떤 상태에서 무엇을 보고 행동하며, 성공·실패·취소 후 어디로 가고 데이터가 유지되는지를 정의한다.

[주문 목록] │ 주문 선택 ▼ [주문 상세] ├─ 수정 권한 있음 → [배송지 수정 폼] │ ├─ 저장 성공 → [주문 상세/완료 알림] │ ├─ 검증 실패 → [같은 폼/값 유지] │ └─ 취소 → [변경 폐기 확인] → [주문 상세] └─ 수정 권한 없음 → [읽기 전용 상세]

이 도식에는 권한, 저장 결과, 오류 시 값 유지, 취소 처리가 포함된다. 브라우저 뒤로 가기나 모바일 시스템 뒤로 가기도 상태와 데이터에 어떤 영향을 주는지 정한다.

03

2. 화면 상태와 전이

2.1 시작·종료 상태

과업이 어디에서 시작하고 무엇을 완료로 보는지 정의한다. “신청 화면을 닫음”이 아니라 신청ID가 생성되고 사용자에게 접수 상태가 확인되는 것이 완료일 수 있다. 비동기 처리라면 접수와 최종 완료를 구분한다.

2.2 정상 흐름

빈번하고 기대되는 최단 업무 흐름을 정의한다. 사용자가 이미 제공한 정보를 다시 입력하지 않게 하고, 단계 사이에 문맥과 값이 유지되는지 확인한다.

2.3 대체·예외 흐름

검색 결과 없음, 입력 오류, 중복 데이터, 외부 서비스 실패, 세션 만료, 권한 변경, 네트워크 단절을 설계한다. 오류 후 전체 과업을 처음부터 다시 시작하게 하지 말고 가능한 값과 문맥을 보존한다.

2.4 취소·뒤로·이탈

저장되지 않은 변경이 있을 때 취소와 이동의 결과를 알린다. 단, 단순 조회나 변경 없음에도 매번 경고하면 경고 피로가 생긴다. 실제 데이터 손실 가능성을 기준으로 사용한다.

2.5 새로고침·중복 제출

결제·신청처럼 상태를 바꾸는 제출은 버튼을 잠시 비활성화하는 UI만 믿지 않는다. 요청 식별자와 서버의 멱등 처리도 필요하다. 새로고침 때 같은 요청이 재전송되는지, 완료 화면 URL을 다시 열었을 때 재처리되지 않는지 확인한다.

05

4. 폼 제약사항 설계

4.1 필수·선택·조건부 필수

모든 필드를 필수로 만들지 않는다. 업무에 필요한 최소 입력을 정하고 “배송방법이 택배이면 주소 필수”처럼 조건부 규칙을 명시한다. 필수 표시는 레이블과 프로그램적 정보로 제공한다.

4.2 유형·형식·범위

날짜, 금액, 전화번호, 파일 같은 입력은 허용 형식과 경계, 단위, 예를 보여 준다. 입력 중 검증은 빠른 피드백을 주지만 사용자가 아직 타이핑 중일 때 성급한 오류를 표시하지 않는다. 제출 시 서버에서도 같은 업무 규칙을 검증한다.

4.3 필드 사이·단계 사이 규칙

종료일은 시작일 이후, 환불금액은 결제금액 이하처럼 여러 필드를 비교한다. 여러 단계의 값이 관계되면 검토 화면과 최종 제출에서 전체 규칙을 다시 확인한다.

4.4 기본값과 자동 완성

사용자의 빈번한 선택을 도울 수 있지만 의미가 확정되지 않은 값을 임의 기본으로 선택하면 잘못 제출할 수 있다. 법적 동의, 위험한 공개 범위는 옵트인 원칙과 적용 규정을 확인한다. 자동 완성 결과를 사용자가 검토·수정할 수 있게 한다.

4.5 입력 순서와 키보드

업무 흐름에 따라 논리적 순서로 배치하고 키보드 초점도 같은 순서를 따른다. 비활성·숨김 필드로 초점이 이동하지 않게 한다. Enter가 폼 제출인지 다음 필드인지 컨텍스트와 플랫폼 관습에 맞게 정한다.

4.6 파일과 대용량 입력

허용 유형·크기·개수, 파일명, 악성 콘텐츠 검사, 업로드 진행·취소·실패 후 재개를 정의한다. 클라이언트 확장자만 검사하지 않고 서버에서 실제 콘텐츠와 권한을 검증한다. 표본에는 실제 민감 문서를 사용하지 않는다.

4.7 임시 저장

긴 폼에는 자동·수동 임시 저장을 고려한다. 저장 시각, 저장 범위, 다른 장치에서의 복구, 만료·삭제, 개인정보 보호를 정한다. 자동 저장 실패를 성공처럼 표시하지 않는다.

4.8 오류 표현

폼 상단 요약과 필드 인라인 오류를 연결하고 첫 오류로 초점을 이동할지 정한다. 오류 후 사용자가 입력한 유효값을 보존한다. 내부 코드 대신 수정 방법을 설명하며 색만으로 표현하지 않는다.

5. 흐름 설계 절차

  1. 과업·사용자 선정: 빈도, 중요도, 오류 영향이 높은 과업을 찾는다.
  2. 상태 목록 작성: 시작, 입력, 검토, 처리, 성공, 빈 결과, 오류, 권한 상태를 나열한다.
  3. 전이 정의: 행동·사건, 조건, 다음 상태, 데이터 보존·변경을 표로 만든다.
  4. 제약 연결: 필수·형식·교차 필드·권한·중복·세션 규칙을 전이에 연결한다.
  5. 대체·복구 흐름 추가: 취소, 뒤로, 네트워크 실패, 외부 지연, 재개를 설계한다.
  6. 장치·접근성 확인: 키보드, 모바일 뒤로, 초점, 알림, 확대를 확인한다.
  7. 워크스루: 정상·경계 시나리오를 사용해 막힌 상태와 순환을 찾는다.
  8. 추적·버전 관리: 화면·전이를 요구 ID와 시험 사례에 연결한다.
07

6. 사용자 편의성을 고려한 메뉴 구조 설계

메뉴는 시스템 내부 모듈 구조가 아니라 사용자가 목표를 찾는 정보 구조다. “관리”, “처리”, “기타”처럼 너무 넓은 범주나 개발팀의 서비스 이름은 사용자가 기능을 예측하기 어렵다.

6.1 사용자 언어

메뉴 이름은 행동 또는 업무 대상을 명확히 표현한다. “TRX MGR”보다 “거래 내역”, “등록”보다 “새 주문 등록”이 예측 가능하다. 같은 개념에 화면마다 다른 용어를 쓰지 않는다.

6.2 그룹화

업무 목표, 대상, 생명주기, 사용 빈도에 따라 묶는다. 한 기능이 여러 범주에 자연스럽게 속하면 중복 링크, 바로가기, 검색을 제공하되 권위 있는 위치는 하나로 관리한다.

6.3 깊이와 폭

최상위 항목을 무조건 적게 만들거나 계층을 무조건 얕게 하지 않는다. 한 화면에 너무 많은 동등 항목은 찾기 어렵고, 지나치게 깊으면 클릭과 위치 기억 부담이 늘어난다. 실제 과업으로 탐색 성공과 시간을 검증한다.

6.4 빈도와 개인화

자주 쓰는 기능을 쉽게 도달하게 하고 최근·즐겨찾기를 제공할 수 있다. 개인화가 핵심 메뉴를 숨기거나 다른 장치에서 예측 불가능하게 만들지 않도록 기본 구조를 유지한다.

6.5 현재 위치와 이동

선택 메뉴 표시, 페이지 제목, 경로 표시, 뒤로 가기, 상위 이동을 일관되게 제공한다. 사용자가 깊은 링크로 바로 들어와도 현재 위치와 상위 범주를 이해할 수 있어야 한다.

6.6 권한과 가시성

권한 없는 메뉴를 숨길지 비활성화하고 이유를 알릴지 업무에 따라 정한다. 메뉴 숨김은 보안 통제가 아니므로 서버에서 반드시 권한을 검사한다. 역할 변경 후 캐시된 메뉴가 남지 않게 한다.

6.7 반응형 메뉴

좁은 화면에서 접힌 메뉴, 하단 탐색, 더보기로 바뀔 때 핵심 기능과 현재 위치가 유지되는지 확인한다. 호버에만 의존하지 않고 키보드·터치·화면 읽기 접근을 지원한다.

8. 메뉴 검증 방법

8.1 카드 분류

기능·콘텐츠 카드를 대상 사용자가 의미 있다고 생각하는 그룹으로 묶고 이름을 붙이게 한다. 열린 분류는 사용자의 범주를 발견하고, 닫힌 분류는 제안한 범주의 적합성을 본다. 표본과 참여자 역할을 기록한다.

8.2 트리 테스트

시각 디자인 없이 메뉴 텍스트 트리만 주고 특정 기능을 어디서 찾을지 확인한다. 첫 선택, 성공 경로, 되돌아감과 실패 지점을 관찰해 명칭·그룹 문제를 분리한다.

8.3 과업 워크스루

화면 흐름과 메뉴를 함께 사용해 깊은 링크, 오류 후 복귀, 역할 변경, 모바일 접힘 상태를 확인한다. 메뉴 테스트 성공만으로 화면 내부 과업 흐름이 적절하다고 단정하지 않는다.

10

9. 구체 시나리오

상황

대학 학사 시스템에서 학생이 휴학을 신청한다. 자격 확인, 사유 입력, 증빙 업로드, 등록금 안내 확인, 최종 제출 단계가 있다.

흐름 설계

[학적 서비스 > 휴학 신청] ↓ 자격 조회 ├─ 신청 불가 → 사유·문의 경로 표시 └─ 신청 가능 ↓ 사유·기간 입력 ↓ 증빙 업로드(조건부) ↓ 검토·등록금 안내 확인 ↓ 제출 ├─ 성공 → 접수번호·상태 └─ 결과 미확정 → 조회 상태, 중복 제출 방지

기간 종류에 따라 증빙이 조건부 필수이며, 업로드 실패 시 앞 단계 입력을 보존한다. 학생 메뉴에는 “학적 > 휴학 신청”처럼 업무 언어를 쓰고, 승인 기능은 교직원 역할의 별도 메뉴에 둔다. 학생이 URL을 직접 입력해 승인 기능에 접근해도 서버가 거절해야 한다.

11

10. 산출물과 체크리스트

주요 산출물은 사용자 과업 목록, 화면 흐름도, 상태·전이표, 폼 제약 목록, 메뉴 트리, 메뉴 정의서, 역할-메뉴 매트릭스, 카드 분류·트리 시험 결과, 요구-흐름 추적표다.

  • 과업의 시작·완료·중단 상태가 명확한가?
  • 정상·오류·빈 결과·권한·결과 미확정 흐름이 있는가?
  • 뒤로·취소·새로고침 때 데이터 처리 규칙이 있는가?
  • 필수·조건부·교차 필드·파일 제약이 정의됐는가?
  • 중복 제출을 UI와 서버 양쪽에서 방지하는가?
  • 오류 후 유효 입력과 초점이 보존되는가?
  • 메뉴가 사용자 업무 용어와 목표로 그룹화됐는가?
  • 깊은 링크에서도 현재 위치와 상위 범주를 아는가?
  • 역할별 메뉴와 서버 권한이 일치하는가?
  • 카드 분류·트리 테스트로 명칭과 그룹을 검증했는가?
12

11. 자주 틀리는 함정

  1. 화면 목록만 만들고 상태·전이·데이터 보존을 생략하지 않는다.
  2. 성공 흐름만 설계하고 취소·실패·재개를 구현자에게 맡기지 않는다.
  3. 필수 항목을 많게 하면 데이터 품질이 자동으로 좋아진다고 생각하지 않는다.
  4. 제출 버튼 비활성화만으로 중복 업무 처리가 막힌다고 보지 않는다.
  5. 기본값이 사용자의 동의나 의도를 대신하게 하지 않는다.
  6. 메뉴를 개발 모듈·DB 테이블 이름으로 구성하지 않는다.
  7. 모든 메뉴를 “관리” 아래 넣지 않는다.
  8. 계층은 무조건 얕거나 항목은 무조건 적어야 한다고 단정하지 않는다.
  9. 메뉴를 숨기는 것을 권한 보안으로 보지 않는다.
  10. 카드 분류 한 번의 결과를 모든 사용자 역할에 일반화하지 않는다.

12. 확인 문제

문제 1

화면 흐름에 현재 화면과 다음 화면 외에 기록할 항목 네 가지를 쓰시오.

정답과 해설: 행동·사건, 전이 조건, 데이터 처리, 오류·복귀를 들 수 있다. 사용자 역할과 권한도 필요하다.

문제 2

시간 초과 후 “결과 미확정” 상태가 필요한 이유는 무엇인가?

정답과 해설: 서버에서 처리가 완료되었을 수 있어 실패로 단정하고 다시 제출하면 중복 업무가 생길 수 있기 때문이다.

문제 3

조건부 필수 필드의 예와 필요한 UI 처리를 설명하시오.

정답과 해설: 배송방법이 택배일 때 주소가 필수인 경우다. 조건을 미리 안내하고 택배 선택 시 필수 상태·레이블·검증을 일관되게 바꾼다.

문제 4

폼 오류 후 유효한 입력값을 보존해야 하는 이유는 무엇인가?

정답과 해설: 사용자의 재입력 부담과 오류를 줄이고 어느 필드만 수정할지 명확히 하기 위해서다.

문제 5

메뉴를 내부 시스템 모듈명으로 구성하면 생기는 문제는 무엇인가?

정답과 해설: 사용자는 내부 구조를 모르므로 목표 기능의 위치를 예측하기 어렵다. 업무 대상과 행동 언어로 설계한다.

문제 6

카드 분류와 트리 테스트의 차이는 무엇인가?

정답과 해설: 카드 분류는 사용자가 기능을 어떻게 그룹화·명명하는지 찾고, 트리 테스트는 제안한 텍스트 계층에서 목표를 찾을 수 있는지 검증한다.

문제 7

권한 없는 메뉴를 숨겨도 서버 권한 검사가 필요한 이유는 무엇인가?

정답과 해설: 사용자가 URL이나 요청을 직접 만들 수 있고 오래된 캐시가 남을 수 있어 화면 표시만으로 접근을 막을 수 없기 때문이다.

문제 8

메뉴 깊이와 폭을 결정할 때의 실제 판단 기준은 무엇인가?

정답과 해설: 대상 사용자가 주요 과업을 얼마나 정확하고 빠르게 찾는지, 되돌아감과 기억 부담이 어떤지를 시험해 판단한다.

문제 9

임시 저장 기능에 필요한 규칙 네 가지를 쓰시오.

정답과 해설: 저장 범위·시각, 복구 방법, 만료·삭제, 개인정보 보호를 들 수 있다. 자동 저장 실패 표시와 장치 간 동기화도 정한다.

14

13. 핵심 요약

  • 화면·폼 흐름과 제약사항 설계는 화면 상태, 행동·사건, 조건, 다음 상태, 데이터 보존·변경, 오류·복귀를 정의하는 활동이다.
  • 정상뿐 아니라 빈 결과, 권한, 시간 초과, 취소, 새로고침, 중복 제출과 임시 저장을 설계한다.
  • 폼에는 필수·조건부, 형식·범위, 교차 필드, 파일, 키보드·오류 제약이 필요하다.
  • 사용자 편의성을 고려한 메뉴 구조 설계는 업무 언어, 그룹, 깊이·폭, 빈도, 현재 위치, 권한, 반응형을 사용자 과업에 맞추는 활동이다.
  • 카드 분류로 범주를 탐색하고 트리 테스트로 제안한 계층의 탐색성을 검증한다.
  • 메뉴 숨김은 보안이 아니므로 서버 권한을 강제하고 흐름·메뉴 산출물을 다음 상세 화면 설계의 기준선으로 제공한다.
