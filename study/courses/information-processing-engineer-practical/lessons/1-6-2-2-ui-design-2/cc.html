01

출제 범위와 학습 목표

이 레슨의 공식 수행 범위는 하위 시스템 단위 내외부 화면과 폼 설계이다. 앞 단계에서 정해진 화면 흐름과 메뉴 구조를 입력물로 받아, 하나의 하위 시스템에서 실제로 구현할 화면·입력 폼·상태·검증 규칙을 명세하는 데 집중한다. 화면 이동 구조 자체를 새로 설계하는 것이 아니라, 주문·정산·회원과 같은 하위 시스템별 화면을 구현 가능한 수준으로 구체화하는 작업이다.

두 번째 핵심 주제는 UI 설계하기의 적용 절차와 판단 기준이다. 따라서 시험 답안에서는 “예쁘게 배치한다”보다 어떤 입력물을 확인하고, 어떤 산출물을 만들며, 무엇을 근거로 대안을 선택하고, 어떻게 검토하는지를 보여 주어야 한다. 학습 후에는 다음을 수행할 수 있어야 한다.

  • 외부 고객용 화면과 내부 운영자용 화면의 사용자·업무·보안 차이를 설명한다.
  • 화면 정의서, 폼 항목 명세, 상태·오류 표, 데이터 매핑표를 일관되게 작성한다.
  • 필수 여부, 데이터 형식, 허용 범위, 오류 메시지, 권한을 구현 가능한 규칙으로 표현한다.
  • 접근성·개인정보·중복 제출·복구 가능성을 포함하여 설계안을 검토한다.
  • 요구사항에서 화면 요소와 검증 규칙까지 추적 관계를 유지한다.
02

1. 하위 시스템 단위 설계의 의미

하위 시스템은 전체 서비스를 업무 책임에 따라 나눈 구현·운영 단위이다. 예를 들어 쇼핑 서비스는 상품, 주문, 결제, 배송, 고객 지원으로 나눌 수 있다. 주문 하위 시스템의 외부 화면은 고객이 보는 주문서와 주문 상세이고, 내부 화면은 상담원이 사용하는 주문 검색·상태 변경 화면이다. 두 화면이 같은 주문 데이터를 사용하더라도 목적과 노출 범위가 다르므로 하나의 화면을 그대로 공유해서는 안 된다.

구분외부 화면내부 화면

화면은 단지 입력 상자의 모음이 아니다. 사용자 행동에 따라 달라지는 상태를 가진다. 최초 진입, 로딩, 데이터 없음, 정상 조회, 입력 중, 검증 실패, 저장 중, 저장 성공, 서버 오류, 권한 없음 상태를 설계해야 한다. 정상 상태만 그린 와이어프레임은 구현 중 판단을 개발자에게 떠넘기므로 불완전한 산출물이다.

폼은 정보를 수집하고 업무 명령을 전달하는 인터페이스이다. 각 항목에는 의미, 데이터형, 길이·정밀도, 필수 여부, 기본값, 입력 방식, 값의 범위, 항목 간 관계, 마스킹, 서버 검증, 오류 문구가 필요하다. 화면에 별표만 표시하고 필수 조건을 명세하지 않거나, “올바르게 입력”처럼 판정할 수 없는 문구를 쓰면 테스트 기준도 만들 수 없다.

03

2. 설계 입력물과 산출물

설계자는 요구사항 명세, 업무 규칙, 사용자 역할, 선행 화면 흐름, UI 표준, 데이터 모델, 인터페이스 계약, 개인정보 분류, 접근성 기준을 입력물로 확인한다. 입력물이 서로 충돌하면 임의로 결정하지 말고 쟁점·대안·결정권자를 기록한다.

와이어프레임은 배치와 행동을 검증하는 도구이고, 화면 정의서는 구현 규칙을 전달하는 계약이다. 둘 중 하나로 다른 하나를 완전히 대체할 수 없다. 색상과 여백이 정교한 시안도 검증 규칙이 없으면 설계 명세가 아니며, 표만 가득한 문서도 사용자가 정보를 어떤 순서로 인식하는지 확인하기 어렵다.

04

3. UI 설계하기의 적용 절차와 판단 기준

3.1 입력물 확인과 화면 경계 설정

먼저 하위 시스템의 책임과 외부 연계를 한 문장으로 정의한다. 주문 하위 시스템이라면 “장바구니에서 전달된 상품을 주문으로 확정하고, 결제·배송에 필요한 정보를 전달한다”와 같이 쓴다. 화면이 다른 하위 시스템의 업무를 직접 수정하도록 설계하면 책임 경계가 흐려진다. 연계 데이터는 조회인지 복제인지, 실패 시 사용자가 무엇을 할 수 있는지까지 확인한다.

요구사항마다 화면이 꼭 하나씩 필요한 것은 아니다. 한 화면에서 자연스럽게 완료할 수 있는 짧은 과업은 합치고, 권한·위험·인지 부담·저장 시점이 다른 과업은 분리한다. 외부 고객의 주소 입력과 내부 관리자의 환불 승인은 같은 주문에 속하지만 사용자와 통제 수준이 다르므로 별도 화면이 적절하다.

3.2 사용자와 사용 맥락 분석

역할, 숙련도, 기기, 이용 빈도, 시간 압박, 보조 기술 사용 여부를 기록한다. 반복 업무가 많은 내부 화면은 키보드 이동, 빠른 검색, 선택 유지가 중요하다. 간헐적으로 쓰는 외부 화면은 전문 용어를 풀어 쓰고 단계별 안내를 제공해야 한다. “사용자 편의”라는 추상어 대신 “오류 발생 시 입력값을 보존한다”, “레이블과 입력칸을 프로그램적으로 연결한다”처럼 검증 가능한 기준을 세운다.

3.3 정보와 행동의 우선순위 결정

화면의 주 과업을 하나 정하고, 주요 행동·보조 행동·위험 행동을 구분한다. 주문 확정이 주요 행동이라면 임시 저장은 보조 행동, 주문 취소는 위험 행동이다. 파괴적 행동은 시각적으로 구분하고 영향 범위와 되돌릴 수 있는지 알려 준다. 버튼 이름은 “확인”보다 “주문 확정”, “환불 요청”처럼 결과가 드러나게 쓴다.

정보는 사용자가 판단하는 순서로 묶는다. 배송지, 상품, 금액, 결제 수단처럼 의미 있는 그룹에 제목을 붙인다. 관련 없는 필드를 한 줄에 넣어 공간만 아끼거나, 중요 결과를 접힌 영역에 숨기지 않는다. 모바일에서는 너비만 줄이는 것이 아니라 표의 우선 열, 버튼 순서, 터치 영역, 가상 키보드 유형까지 재검토한다.

3.4 폼 항목과 검증 규칙 명세

각 필드 규칙은 클라이언트와 서버에서 같은 의미로 적용되어야 한다. 클라이언트 검증은 빠른 피드백을 제공하지만 우회될 수 있으므로 보안·무결성의 최종 판단은 서버가 한다. 검증 순서는 보통 존재 여부, 형식, 길이·범위, 항목 간 관계, 업무 규칙 순으로 구성하면 사용자가 가장 직접적인 원인을 먼저 알 수 있다.

예를 들어 수령인 연락처 명세는 다음처럼 작성한다.

구체적인 형식은 프로젝트의 데이터 계약과 정책에 따르며, 익숙한 형식을 임의로 고정하지 않는다. 날짜도 표시 형식, 전송 형식, 시간대, 종료일 포함 여부를 따로 명시한다. 금액은 통화, 소수 자릿수, 반올림 시점, 음수 허용 여부를 기록한다. 선택 항목은 화면 표시명과 전송 코드의 매핑을 남긴다.

3.5 상태·오류·복구 설계

비동기 요청에는 최소한 대기, 성공, 업무 오류, 시스템 오류, 시간 초과가 있다. 저장 버튼을 누른 뒤 진행 표시 없이 다시 누를 수 있으면 중복 요청이 발생한다. 버튼을 일시 비활성화하는 UI 조치와 함께 서버의 중복 방지 키 또는 동일 요청 판정 규칙을 설계한다. 네트워크 실패 후 결과를 알 수 없을 때는 무조건 재시도하게 하지 말고 처리 상태를 조회하는 경로를 제공한다.

오류 메시지는 발생 사실, 원인 범주, 사용자가 할 수 있는 행동을 담는다. “오류 500”만 외부 사용자에게 보여 주거나 내부 예외·경로를 그대로 노출하면 안 된다. 입력 오류는 해당 필드 가까이에 표시하고, 화면 상단 요약과 연결하면 보조 기술 사용자도 오류 위치를 찾기 쉽다. 서버 오류가 나도 사용자가 입력한 비민감 값을 가능한 한 보존한다.

3.6 접근성·보안·일관성 검토

색만으로 필수·성공·실패를 구분하지 않는다. 모든 입력 요소에 식별 가능한 레이블을 제공하고, 오류 설명과 입력 요소의 관계를 전달한다. 키보드만으로 초점 순서가 논리적이어야 하며, 모달을 닫았을 때 초점이 원래 조작 요소로 돌아와야 한다. 확대나 작은 화면에서도 내용과 기능이 잘리거나 겹치지 않는지 확인한다.

화면에서 숨겼다는 이유로 권한이 보장되는 것은 아니다. API에서도 객체 소유권과 역할을 검증한다. 개인·인증 정보는 필요한 만큼만 노출하고, URL·브라우저 저장소·분석 로그에 민감값을 남기지 않는다. 내부 화면의 중요 변경은 변경 전후 값, 수행자, 시각, 사유를 감사 이력으로 남길 요구를 명세한다.

컴포넌트는 같은 의미에 같은 모양과 행동을 사용한다. 단, 일관성은 잘못된 패턴까지 복제하라는 뜻이 아니다. 공통 컴포넌트가 접근성 또는 업무 요구를 충족하지 못하면 예외 근거와 개선 계획을 기록한다.

3.7 프로토타입 검토와 기준선 확정

대표 사용자와 업무 담당자가 정상 경로뿐 아니라 오류·취소·권한 부족·재시도 경로를 수행하게 한다. 관찰자는 사용자가 멈춘 지점, 잘못 해석한 용어, 누락 정보, 되돌리기 요구를 기록한다. 단순 선호와 과업 실패를 구분하고, 빈도·영향·수정 비용으로 우선순위를 정한다.

승인된 설계에는 버전과 기준일을 붙인다. 변경 시 요구사항, 화면 정의, API, 테스트 케이스 중 무엇이 영향을 받는지 추적표로 확인한다. 구두 합의만으로 구현을 바꾸면 디자인과 테스트 기준이 어긋난다.

05

4. 구체 업무 시나리오: 주문 주소 변경

고객용 주문 상세에는 배송 시작 전 주소 변경 버튼이 보인다. 운영자용 상세에는 주문 검색, 본인 확인 결과, 변경 사유, 감사 이력이 추가된다. 같은 기능처럼 보여도 판단 기준이 다르다.

코드 예시 · text

[고객 화면]
주문 조회 → 변경 가능 상태 확인 → 새 주소 입력 → 검증 → 변경 요청
                                └ 오류: 입력 보존 + 수정 위치 안내

[운영자 화면]
주문 검색 → 권한·본인 확인 → 현 주소/새 주소 비교 → 사유 입력 → 승인·기록
                                            └ 변경 불가: 근거와 후속 절차 안내

고객 화면의 필수 필드는 수령인, 주소 구성 값, 연락처이며 주문 상태가 이미 배송 준비 이후라면 변경 버튼 자체의 표시 여부와 별개로 서버에서 거부한다. 운영자 화면은 권한별로 조회와 변경을 나누며, 직접 수정과 승인 요청 중 어느 방식인지를 업무 규칙으로 결정한다. 두 화면 모두 주소 서비스가 실패했을 때 수동 입력 가능 여부, 제출 중 중복 클릭, 처리 결과 확인 방법을 명세한다.

요구사항 ORD-ADDR-03 배송 전 주소 변경을 고객 화면 SCR-ORD-012, 폼 FRM-ADDR-02, API 동작 API-ORD-07, 테스트 TC-ORD-141~148과 연결한다. 이렇게 하면 변경 가능 상태가 바뀔 때 관련 설계와 테스트를 빠르게 찾을 수 있다.

06

5. 설계 완료 체크리스트

  • 화면 ID·목적·주 사용자·진입 조건이 명확한가?
  • 외부와 내부 화면의 노출 정보 및 권한 차이가 정의되었는가?
  • 정상, 빈 결과, 로딩, 오류, 권한 없음, 완료 상태가 설계되었는가?
  • 모든 폼 필드에 레이블·자료형·필수·형식·범위·오류 문구가 있는가?
  • 화면 값과 API·데이터 값의 코드, 널, 날짜, 금액 규칙이 일치하는가?
  • 중복 제출·시간 초과·부분 성공·재시도 시 행동이 정의되었는가?
  • 키보드, 초점, 오류 연결, 색 이외 정보 등 접근성을 검토했는가?
  • 개인정보 최소 노출, 서버 권한, 감사 이력을 반영했는가?
  • 요구사항과 화면·필드·테스트 간 추적이 가능한가?
  • 검토 결과와 미결 쟁점, 승인 버전이 기록되었는가?
07

6. 자주 틀리는 실기 함정

  1. 화면 흐름만 다시 그린다. 이 레슨은 개별 화면과 폼의 구현 규칙이 핵심이다.
  2. 정상 화면만 설계한다. 빈 결과, 대기, 오류, 권한 없음과 복구 행동이 빠지면 불완전하다.
  3. 필수 표시를 검증 규칙으로 착각한다. 조건부 필수, 길이, 형식, 관계 규칙을 판정 가능하게 써야 한다.
  4. 클라이언트 검증만 믿는다. 서버에서도 권한과 무결성을 검증해야 한다.
  5. 내부 화면이면 모든 정보를 보여 준다. 직무에 필요한 최소 정보와 역할별 권한을 적용해야 한다.
  6. 버튼 이름을 모두 ‘확인’으로 쓴다. 행동 결과가 드러나는 동사를 사용한다.
  7. 오류 메시지에 내부 예외를 노출한다. 사용자 행동을 안내하되 민감한 진단 정보는 분리한다.
  8. 반응형을 폭 축소로만 이해한다. 정보 우선순위, 표 표현, 터치와 키보드 입력도 재설계한다.
  9. 와이어프레임만으로 구현이 가능하다고 본다. 데이터·상태·권한·검증 명세가 별도로 필요하다.
  10. 변경 이력을 남기지 않는다. 기준선과 추적 관계가 없으면 요구 변경의 영향을 통제할 수 없다.

확인 문제

문제 1

같은 주문 데이터를 사용하는 고객용 화면과 운영자용 화면을 구분해 설계해야 하는 가장 중요한 이유 두 가지를 쓰시오.

문제 2

화면 정의서에 정상 조회 외에 반드시 고려해야 할 상태 네 가지를 예로 드시오.

문제 3

폼 항목 명세에서 “필수” 여부 외에 구현과 테스트에 필요한 속성 다섯 가지를 쓰시오.

문제 4

클라이언트 측 입력 검증만으로 데이터 무결성과 보안을 보장할 수 없는 이유를 설명하시오.

문제 5

저장 요청 시간이 길어 사용자가 버튼을 반복 클릭하는 상황의 UI와 서버 측 대응을 각각 쓰시오.

문제 6

와이어프레임과 화면 정의서의 역할 차이를 설명하시오.

문제 7

접근성을 고려한 입력 오류 표시 방법 세 가지를 쓰시오.

문제 8

주문 주소 변경 화면에서 화면 버튼이 숨겨져 있어도 서버 권한 검사가 필요한 이유를 쓰시오.

문제 9

UI 설계 변경 시 추적표가 제공하는 실무상 이점을 설명하시오.

문제 10

“사용자 편의성을 높인다”를 검증 가능한 설계 기준 두 개로 바꾸어 쓰시오.

09

정답과 해설

정답 1

사용자의 업무 목적과 숙련·사용 맥락이 다르고, 허용 권한과 정보 노출 범위가 다르기 때문이다. 고객은 본인 과업을 단순하게 완료해야 하지만 운영자는 직무 범위의 조회·변경과 감사 통제가 필요하다.

정답 2

로딩, 데이터 없음, 검증 실패, 서버 오류, 권한 없음, 저장 중, 성공 중 네 가지 이상을 들 수 있다. 중요한 점은 각 상태에서 표시 내용과 사용자의 다음 행동까지 설계하는 것이다.

정답 3

자료형, 길이·정밀도, 입력 형식, 허용 범위, 기본값, 항목 간 관계, 오류 메시지, 마스킹, API 매핑 중 다섯 가지이다. 규칙은 테스트가 판정할 수 있을 만큼 구체적이어야 한다.

정답 4

클라이언트 코드는 조작하거나 우회할 수 있고 다른 호출 경로가 존재할 수 있기 때문이다. 빠른 피드백은 클라이언트가 제공하되 최종 형식·업무 규칙·권한은 서버가 검증한다.

정답 5

UI는 처리 중임을 표시하고 중복 조작을 제한하며 결과 조회·재시도 경로를 제공한다. 서버는 중복 방지 키나 동일 요청 판정 규칙으로 같은 명령이 여러 번 반영되지 않도록 한다.

정답 6

와이어프레임은 정보 계층과 배치·상호작용을 시각적으로 검토하는 도구이고, 화면 정의서는 필드·상태·검증·권한·데이터 대응을 구현 규칙으로 전달하는 계약이다.

정답 7

오류를 해당 입력 가까이에 텍스트로 표시하고, 입력 요소와 오류 설명을 프로그램적으로 연결하며, 화면 상단 오류 요약에서 해당 필드로 이동하게 한다. 색만으로 오류를 구분해서는 안 된다.

정답 8

화면 요소는 조작하거나 API를 직접 호출할 수 있어 접근 통제가 되지 않기 때문이다. 서버가 사용자 역할, 객체 소유권, 현재 업무 상태를 다시 확인해야 한다.

정답 9

요구 변경과 관련된 화면, 필드, 인터페이스, 테스트를 찾아 누락과 불일치를 줄이고 영향 분석·회귀 테스트 범위를 정할 수 있다.

정답 10

예를 들면 “저장 실패 시 비민감 입력값을 보존하고 수정 위치를 안내한다”, “모든 입력 필드에 연결된 레이블을 제공하고 키보드만으로 논리적 순서로 이동할 수 있다”로 표현할 수 있다.

10

핵심 요약

  • 하위 시스템 단위 내외부 화면과 폼 설계는 선행 흐름을 구현 가능한 화면·필드·상태·권한 규칙으로 구체화하는 작업이다.
  • 외부 화면은 단순한 과업 완료와 최소 노출을, 내부 화면은 처리 효율과 역할 통제·감사 추적을 중시한다.
  • 폼 명세에는 자료형·필수·형식·범위·관계·오류·마스킹·데이터 매핑이 포함되어야 한다.
  • 정상뿐 아니라 대기·빈 결과·오류·권한 없음·중복 제출·복구 상태를 설계한다.
  • UI 설계하기의 적용 절차와 판단 기준은 입력물 확인, 경계 설정, 사용자 분석, 정보·행동 설계, 폼·상태 명세, 접근성·보안 검토, 프로토타입 검증, 기준선 확정의 흐름으로 정리한다.
  • 좋은 설계 산출물은 요구사항에서 화면과 테스트까지 추적 가능하며, 개발자와 테스터가 같은 조건으로 판정할 수 있다.
