01

출제 범위와 수행 목표

이 레슨의 첫 번째 주제는 테스트 데이터와 시작·종료 조건 준비이다. 앞 레슨에서 정한 방식·대상·범위와 테스트 케이스가 실제로 반복 실행될 수 있도록 데이터, 환경의 초기 상태, 실행을 시작할 기준, 완료를 판단할 기준을 구체화한다. 두 번째 주제는 애플리케이션 테스트케이스 설계하기의 적용 절차와 판단 기준으로, 요구사항과 위험에서 케이스를 도출하고 검토·기준선화하는 전체 절차를 실기 산출물 관점에서 정리한다.

학습 후에는 다음을 수행할 수 있어야 한다.

  • 정상·오류·경계·상태·권한·규모를 대표하는 테스트 데이터를 설계한다.
  • 개인정보를 보호하면서 재현성과 참조 무결성을 갖춘 데이터를 준비한다.
  • 케이스별 사전 조건과 테스트 단계의 시작 조건을 구분한다.
  • 위험과 목표에 연결된 종료 조건을 판정 가능한 형태로 작성한다.
  • 중단·재개 조건, 데이터 초기화, 결과 증거를 포함한 실행 준비 상태를 검토한다.
  • 요구사항 분석부터 케이스 기준선 확정까지의 적용 절차를 설명한다.
02

1. 테스트 데이터는 입력값보다 넓다

테스트 데이터는 사용자가 폼에 입력하는 값만 뜻하지 않는다. 데이터베이스의 기존 행, 사용자 역할과 권한, 외부 서비스의 응답, 시간·상태, 파일, 메시지 순서, 환경 설정도 실행 결과를 결정한다. 주문 취소 케이스라면 주문 ID 하나만 준비하는 것이 아니라 주문의 현재 상태, 소유 사용자, 결제·배송 연계 상태, 취소 이력 존재 여부까지 통제해야 한다.

좋은 테스트 데이터는 다음 특성을 가진다.

  • 대표성: 요구사항의 유효·무효 분할과 실제 업무 상태를 반영한다.
  • 재현성: 누가 언제 실행해도 같은 초기 상태를 만들 수 있다.
  • 독립성: 다른 케이스의 실행 결과 때문에 의도치 않게 바뀌지 않는다.
  • 추적성: 어떤 케이스와 규칙을 위해 준비했는지 식별할 수 있다.
  • 보안성: 실사용자의 개인정보·인증정보를 불필요하게 포함하지 않는다.
  • 정리 가능성: 실행 후 생성·변경된 데이터를 초기화하거나 격리할 수 있다.
03

경계 데이터는 값 하나를 “극단값”으로 고르는 활동이 아니다. 시작일 ≤ 종료일처럼 항목 간 관계가 있으면 같은 날, 하루 전후, 시간대 경계, 누락 조합을 확인한다. 금액이면 통화와 소수 자릿수, 반올림 시점이 필요하고 문자열이면 문자 수와 저장 바이트의 차이를 데이터 계약에 따라 확인한다.

상태 데이터는 생성 절차가 중요하다. 데이터베이스를 직접 수정해 배송중 문자열만 넣으면 실제로 있어야 할 배송 요청, 변경 이력, 버전 값이 빠져 비현실적인 상태가 될 수 있다. 가능하면 공식 API나 시드 스크립트처럼 도메인 규칙을 지키는 경로로 만들고, 직접 삽입이 필요하면 모든 불변 조건과 참조 관계를 명세한다.

04

3. 생성·선별·마스킹 전략

3.1 합성 데이터

규칙에 맞는 가상 데이터를 생성하면 개인정보 노출을 줄이고 경계·오류 조건을 의도적으로 만들 수 있다. 생성 규칙과 난수 시드를 버전 관리하면 실패를 재현하기 쉽다. 단, 지나치게 깨끗한 합성 데이터만 쓰면 실제의 중복, 누락, 긴 문자열, 다양한 문자 체계, 오래된 상태를 놓칠 수 있으므로 운영 특성을 통계적으로 분석하여 생성 규칙에 반영한다.

3.2 운영 데이터 부분 추출

실제 분포와 복잡한 관계를 얻을 수 있지만, 최소 필요 범위만 선택하고 사용 권한과 보존 기간을 통제해야 한다. 단순히 이름 몇 글자를 가리는 것으로 충분하지 않을 수 있다. 여러 필드를 결합해 개인을 다시 식별할 위험과 자유 서술란·로그·첨부파일에 숨어 있는 민감정보도 검토한다.

3.3 마스킹과 가명화

마스킹 후에도 데이터형, 길이, 유일성, 참조 관계, 도메인 분포가 테스트 목적에 맞게 유지되어야 한다. 고객 ID를 임의 치환했다면 주문·배송 테이블의 같은 고객 ID도 일관되게 바꾼다. 이메일을 모두 같은 값으로 바꾸면 유일 제약을 깨고, 금액을 무작위 치환하면 합계 관계를 잃을 수 있다.

원본 복원이 가능한 방식은 키와 접근 권한을 별도로 관리한다. 테스트 환경에 운영 인증 토큰·비밀번호·비밀키를 복사해서는 안 된다. 외부 전송 기능이 있는 테스트 환경은 가짜 연락처와 차단된 전송 대상을 사용해 실제 사용자에게 알림이 가지 않게 한다.

05

4. 데이터 명세와 초기화

케이스마다 즉석으로 데이터를 만들면 재현성이 떨어진다. 데이터 세트에 ID, 목적, 생성 방법, 소유자, 적용 환경, 관련 케이스, 기준 버전, 초기화 방법을 기록한다.

코드 예시 · text

데이터 세트: DS-ORDER-CANCEL-03
목적: 결제완료·미출고 주문의 취소 및 중복 요청 검증
구성: 사용자 U_TEST_04, 주문 O_TEST_102, 주문항목 2건, 결제 승인 모의 응답
불변 조건: 주문 합계 = 항목 합계 - 할인 + 배송비, 소유자 일치
생성: seed_order_cancel 스크립트의 고정 시드 사용
초기화: 실행 전 전용 네임스페이스 재생성, 실행 후 생성 이벤트 제거
연결 케이스: TC-CANCEL-11~16
금지: 실제 결제·문자 발송 경로 연결

초기화 전략에는 트랜잭션 롤백, 격리된 데이터베이스 재생성, 전용 테넌트, 케이스별 고유 키, 사후 정리 스크립트가 있다. 비동기 메시지나 외부 시스템의 부수 효과는 DB 롤백만으로 사라지지 않을 수 있으므로 별도 격리와 정리가 필요하다. 병렬 실행에서는 같은 사용자·재고를 공유하면 경합이 생기므로 케이스별 식별자와 독립 자원을 사용한다.

테스트 오라클은 실제 결과가 맞는지 판단하는 근거다. 요구사항의 계산식, 승인된 기준 데이터, 독립 계산, 계약 스키마, 이전의 검증된 결과가 될 수 있다. 테스트 대상 프로그램이 계산한 값을 그대로 기대값으로 복사하면 같은 오류를 검출할 수 없다.

06

5. 시작 조건 준비

시작 조건은 테스트 단계나 실행 묶음을 시작해도 되는지 판정하는 기준이다. 개별 케이스의 사전 조건과 구분해야 한다. “주문이 결제완료 상태”는 케이스 사전 조건이고, “검증 대상 빌드가 배포되고 주요 인터페이스 모의 환경이 계약 검증을 통과함”은 실행 시작 조건이다.

“환경 준비 완료”처럼 포괄적으로 쓰면 담당자마다 해석이 다르다. 어떤 서비스, 구성, 버전, 계정, 데이터 검사가 통과해야 하는지 나눈다. 모든 조건을 완벽하게 기다릴 필요는 없지만 충족되지 않은 조건이 결과 신뢰성에 미치는 영향을 평가하고 예외 승인과 제한 범위를 기록해야 한다.

07

6. 종료 조건과 중단·재개 조건

종료 조건은 단순히 일정이 끝났거나 모든 케이스를 한 번 실행했다는 뜻이 아니다. 테스트 목표와 잔여 위험을 바탕으로 “충분히 수행되었다”를 판정하는 기준이다. 수치 기준을 쓸 때는 프로젝트가 승인한 목표를 사용하며 임의의 통과율을 보편 기준처럼 제시하지 않는다.

종료 조건에는 다음 관점이 조합될 수 있다.

  • 범위 내 요구사항과 주요 위험이 케이스에 연결되고 실행되었는가?
  • 필수 플랫폼·역할·인터페이스 조합이 검증되었는가?
  • 승인된 수준을 넘는 미해결 결함이 없는가?
  • 수정 결함의 재테스트와 필요한 회귀 테스트가 끝났는가?
  • 결함 발견 추이와 미검증 영역을 포함한 잔여 위험이 수용되었는가?
  • 결과, 로그, 스크린샷, 데이터 변화 등 필요한 증거가 보관되었는가?
  • 알려진 제한과 운영 인계·우회 절차가 승인되었는가?

통과율은 분모와 우선순위에 따라 의미가 달라진다. 낮은 위험 케이스를 많이 통과해 높은 통과율을 얻어도 핵심 결제 케이스가 실패하면 종료 근거가 약하다. “전체 95%”처럼 임의 수치를 외우기보다 위험 등급별 기준과 차단 결함 정책을 계획에서 정한다.

중단 조건은 환경 장애, 데이터 오염, 주요 의존성 불가, 결과 신뢰성을 훼손하는 도구 오류 등 테스트를 계속해도 유효한 증거를 얻기 어려운 상황이다. 재개 조건은 원인 제거, 환경 재검증, 데이터 초기화, 영향받은 케이스 식별과 재실행 승인처럼 중단 원인과 대응해야 한다.

코드 예시 · text

중단: 결제 모의 서비스가 승인 응답만 반환하여 실패 케이스 판정 불가
조치: 모의 규칙 복구, 계약 응답 샘플 검증, 실행 로그 시간대 확인
재개: 점검 케이스 3종 통과 + 오염된 주문 데이터 재생성 + 담당자 승인
영향: 중단 시점 이후 결제 관련 케이스 전부 무효 처리 후 재실행
08

7. 애플리케이션 테스트케이스 설계하기의 적용 절차와 판단 기준

7.1 요구사항·위험 분석

기능 요구, 품질 요구, 업무 규칙, 인터페이스 계약, 장애 이력, 변경 차이를 수집한다. 모호하거나 상충하는 문장은 질문 목록으로 만들고 결정 전까지 가정을 명시한다. 위험은 실패 가능성과 영향, 탐지 난이도, 변경량을 근거로 우선순위를 정한다.

7.2 테스트 조건 식별

각 요구사항을 검증 가능한 조건으로 분해한다. 정상 처리뿐 아니라 경계, 잘못된 입력, 권한, 상태 전이, 중복, 시간 초과, 데이터 일관성을 식별한다. 조건은 구현 화면에만 묶지 말고 업무 결과와 외부 계약을 포함한다.

7.3 설계 기법과 수준 선택

연속 범위는 경계값, 조합 규칙은 결정 테이블, 상태 의존 기능은 상태 전이, 사용자 목표는 유스케이스 기법이 적합하다. 코드 구조상 중요한 분기는 화이트박스 관점으로 보완한다. 선택 이유를 위험과 연결한다.

7.4 케이스·기대 결과 작성

케이스 ID, 목적, 요구사항 추적, 우선순위, 사전 조건, 입력, 절차, 기대 결과를 쓴다. 기대 결과는 화면 메시지뿐 아니라 저장 상태와 필요한 연계·감사 이력을 포함한다. 테스트 오라클은 테스트 대상과 독립적인 근거를 사용한다.

7.5 데이터와 조건 준비

각 케이스에 필요한 데이터 분할·상태·권한을 연결하고 생성·초기화 방법을 정한다. 실행 묶음의 시작·종료·중단·재개 조건을 판정 가능한 문장으로 작성한다. 실제 알림·결제처럼 외부 피해를 낼 경로는 차단한다.

7.6 검토·기준선·변경 통제

업무 담당자는 규칙과 기대값, 개발자는 기술적 실행 가능성, 테스터는 누락·재현성, 보안·운영 담당자는 권한·환경 위험을 검토한다. 중복 케이스는 줄이되 서로 다른 위험을 무리하게 합치지 않는다. 승인된 케이스·데이터·환경 구성을 기준선화하고 요구 변경 시 추적표로 영향받은 항목을 갱신한다.

판단 기준은 “문서가 작성되었는가”가 아니라 다음과 같다. 요구사항과 위험이 추적되는가, 각 케이스가 독립적으로 판정 가능한가, 데이터가 현실성과 보안을 함께 만족하는가, 실행 조건이 결과 신뢰성을 보장하는가, 남은 위험을 설명할 수 있는가이다.

09

8. 구체 업무 예시: 쿠폰 적용 테스트 준비

요구 규칙이 “사용 기간, 대상 상품, 최소 금액, 회원 등급, 중복 사용 여부를 모두 만족하면 쿠폰 적용”이라고 하자. 결정 테이블로 조건 조합을 줄이고, 날짜와 금액은 경계값을 만든다. 데이터는 활성/만료 쿠폰, 대상/비대상 상품, 기준 금액 바로 아래·같음·위, 등급별 사용자, 이미 사용된 쿠폰을 포함한다.

시작 조건에는 할인 규칙 기준선 승인, 대상 빌드 배포, 시스템 시각 통제 방법, 쿠폰·주문 데이터 시드 검증, 외부 가격 서비스 계약 응답 준비가 포함된다. 종료 조건에는 고위험 규칙 조합 실행, 경계 케이스 판정, 미해결 중요 결함 검토, 수정분 재테스트와 할인 관련 회귀 완료, 증거 보관이 포함된다.

시간 의존 테스트에서 컴퓨터 시계를 임의로 바꾸면 다른 테스트에 영향을 줄 수 있다. 주입 가능한 기준 시각이나 격리 환경을 사용하고, 시간대와 기간 끝점 포함 여부를 명세한다. 할인 기대값은 테스트 대상의 결과를 복사하지 않고 승인된 규칙에 따른 독립 계산표로 산출한다.

10

9. 실기 체크리스트와 자주 틀리는 함정

  • 입력값뿐 아니라 DB 상태·권한·외부 응답·시간도 데이터로 보았는가?
  • 정상·오류·경계·상태·조합 데이터가 위험에 맞게 선택되었는가?
  • 합성·부분 추출·마스킹의 근거와 개인정보 통제가 있는가?
  • 참조 무결성과 유일성, 합계 등 업무 불변 조건을 유지하는가?
  • 데이터 생성·초기화·소유·버전·연결 케이스가 기록되었는가?
  • 시작 조건이 요구·빌드·환경·데이터·의존성별로 판정 가능한가?
  • 종료 조건이 단순 일정이나 전체 통과율 하나에 의존하지 않는가?
  • 중단 원인과 재개 검증, 무효화할 결과 범위가 연결되는가?
  • 기대값이 테스트 대상과 독립된 오라클에서 나오는가?
  • 기준선 이후 변경 영향과 재검토가 추적되는가?

자주 틀리는 함정은 운영 DB를 그대로 복사하면 현실성이 확보된다고 보는 것, 케이스마다 수동으로 데이터를 만들어 재현성을 잃는 것, UI 입력만 준비하고 백엔드 상태를 빠뜨리는 것, 시작 조건과 사전 조건을 혼동하는 것, 통과율 하나로 종료를 선언하는 것, 중단 후 기존 결과를 모두 유효하다고 보는 것이다. 또한 마스킹으로 유일성과 참조 관계가 깨지거나 테스트 환경이 실제 사용자에게 알림을 보내는 사고도 주의해야 한다.

확인 문제

문제 1

테스트 데이터가 화면 입력값보다 넓은 이유를 주문 취소 예로 설명하시오.

문제 2

합성 데이터의 장점 두 가지와 한계 한 가지를 쓰시오.

문제 3

운영 데이터 마스킹 시 값 가리기 외에 유지해야 할 데이터 특성 세 가지를 쓰시오.

문제 4

테스트 오라클의 의미와 테스트 대상 결과를 그대로 기대값으로 쓰면 안 되는 이유를 설명하시오.

문제 5

개별 케이스의 사전 조건과 실행 단계의 시작 조건을 예를 들어 구분하시오.

문제 6

전체 케이스 통과율만으로 종료 여부를 판단하면 안 되는 이유를 쓰시오.

문제 7

중단 조건과 재개 조건이 서로 대응해야 하는 이유를 설명하시오.

문제 8

병렬 테스트에서 같은 사용자와 재고 데이터를 공유할 때 발생할 문제와 대응을 쓰시오.

문제 9

애플리케이션 테스트케이스 설계하기의 주요 절차를 순서대로 여섯 단계 쓰시오.

문제 10

기간 만료 쿠폰 테스트에서 명세해야 할 시간 관련 조건 세 가지를 쓰시오.

12

정답과 해설

정답 1

결과는 입력값뿐 아니라 주문의 현재 상태, 소유권, 결제·배송 상태, 기존 이력에 따라 달라지기 때문이다. 이 초기 상태를 통제하지 않으면 같은 입력도 다른 결과를 낸다.

정답 2

개인정보 노출을 줄이고 원하는 경계·오류 조건을 정확히 만들며 고정 시드로 재현할 수 있다. 한계는 실제 데이터의 복잡한 분포와 오염 특성을 놓칠 수 있다는 점이다.

정답 3

자료형·길이, 유일성, 테이블 간 참조 관계, 합계 등 업무 불변 조건, 의미 있는 분포 중 세 가지이다. 마스킹 후 테스트 목적이 사라지지 않아야 한다.

정답 4

오라클은 실제 결과의 옳고 그름을 판단하는 독립 근거이다. 대상 프로그램의 계산값을 복사하면 대상과 같은 결함이 기대값에도 들어가 오류를 검출하지 못한다.

정답 5

“주문 O가 결제완료 상태”는 특정 케이스의 사전 조건이다. “식별된 빌드가 배포되고 결제 모의 서비스 계약 점검이 통과함”은 테스트 실행을 시작할 조건이다.

정답 6

낮은 위험 케이스를 많이 통과해 수치가 높아도 핵심 기능과 높은 위험 케이스가 실패·미실행일 수 있기 때문이다. 위험별 실행, 중요 결함, 회귀, 증거와 잔여 위험을 함께 본다.

정답 7

중단 원인이 제거되지 않으면 재개 후 결과도 신뢰할 수 없기 때문이다. 원인 제거와 환경·데이터 재검증, 영향 케이스 재실행을 재개 조건으로 연결한다.

정답 8

한 케이스의 변경이 다른 케이스의 사전 상태를 바꾸고 경합·간헐 실패를 만든다. 케이스별 고유 식별자, 전용 테넌트나 독립 자원, 확실한 초기화를 사용한다.

정답 9

요구사항·위험 분석, 테스트 조건 식별, 설계 기법·수준 선택, 케이스·기대 결과 작성, 데이터와 실행 조건 준비, 검토·기준선·변경 통제 순이다.

정답 10

기준 시각과 시간대, 시작·종료 시각의 포함 여부, 실행 중 시각을 통제하는 방법을 명세한다. 날짜만 적고 시간대와 경계를 생략하면 재현성이 떨어진다.

13

핵심 요약

  • 테스트 데이터와 시작·종료 조건 준비는 케이스를 재현 가능하고 안전하게 실행하며 완료 여부를 합리적으로 판단하기 위한 활동이다.
  • 데이터에는 입력값뿐 아니라 저장 상태, 권한, 외부 응답, 시간과 환경 구성이 포함된다.
  • 정상·오류·경계·상태·조합·권한·규모 데이터를 위험에 맞춰 준비하고, 생성·마스킹·초기화 과정에서 개인정보와 무결성을 보호한다.
  • 시작 조건은 실행 준비 상태, 종료 조건은 목표 달성과 잔여 위험 수용을 판정하며, 케이스 사전 조건과 구분한다.
  • 중단과 재개 조건은 원인 제거, 환경·데이터 재검증, 영향 결과 무효화가 서로 대응해야 한다.
  • 애플리케이션 테스트케이스 설계하기의 적용 절차와 판단 기준은 요구·위험 분석에서 조건 식별, 기법 선택, 케이스·데이터 작성, 검토와 기준선 통제로 이어진다.
  • 케이스 수나 통과율 하나보다 추적성, 판정 가능성, 재현성, 데이터 보안, 잔여 위험 설명이 중요하다.
