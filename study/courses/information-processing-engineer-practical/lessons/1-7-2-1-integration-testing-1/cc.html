01

출제 범위와 수행 목표

이 레슨은 독립적으로 확인한 구성 요소를 결합하여 통합 모듈·인터페이스의 요구사항 충족 테스트를 수행하는 방법과, 실행 중 수집한 결함 추이로 잔존 결함 추정을 하는 방법을 다룬다. 단순히 API가 한 번 성공하는지를 보는 것이 아니라 데이터 계약, 호출 순서, 상태 일관성, 실패 전파, 재시도, 권한, 관찰 가능성을 요구사항과 대조한다. 다음 레슨에서 다룰 충분성 최종 판정과 개선조치 문서화보다는 통합 실행과 추이 해석에 초점을 둔다.

학습 후에는 다음을 수행할 수 있어야 한다.

  • 모듈 간 인터페이스 계약과 통합 위험을 테스트 조건으로 바꾼다.
  • 상향식·하향식·샌드위치·빅뱅 통합 전략의 장단점을 설명한다.
  • 스텁과 드라이버를 필요한 경계에 배치하고 한계를 기록한다.
  • 동기 API, 비동기 메시지, 파일, 공유 데이터 연계의 정상·실패 조건을 검증한다.
  • 중복·순서 역전·부분 성공·시간 초과에서 상태 일관성과 멱등성을 확인한다.
  • 발견·해결·재발 결함의 시간 추이를 분석하고 잔존 결함을 단정이 아닌 위험 추정으로 제시한다.
02

1. 통합 테스트의 관찰 경계

모듈 단위 테스트는 각 부품의 내부 규칙을 빠르게 검증하지만, 부품이 맞물릴 때 생기는 계약 오류를 놓칠 수 있다. 주문 모듈이 amount를 소수 둘째 자리 문자열로 보내고 결제 모듈이 정수 최소 단위를 기대하면 각 모듈은 단독 테스트를 통과해도 금액이 잘못 전달된다. 통합 테스트는 이처럼 구성 요소 사이의 연결점과 결합 결과를 검증한다.

인터페이스 요구사항은 다음 관점으로 분해한다.

1. 통합 테스트의 관찰 경계 · 학습 표 1
관점확인 내용대표 결함
구문 계약필드명, 자료형, 길이, 필수, 인코딩, 스키마필드 누락, 형 변환 실패
의미 계약값의 단위·코드·널·날짜·시간대 의미원/최소 통화 단위 혼동, 코드 오해
행위 계약호출 순서, 상태 전이, 응답별 후속 행동승인 전 주문 확정, 잘못된 분기
시간 계약시간 초과, 재시도, 만료, 처리 주기무한 대기, 중복 실행
무결성원자성 경계, 부분 성공, 보상, 일관성결제됐으나 주문 미생성
보안인증, 권한, 무결성, 민감정보 취급타 사용자 데이터 조회, 비밀 로그 노출
운영 관찰상관 식별자, 로그·지표·추적, 알림실패 원인·처리 상태 추적 불가

성공 응답만으로 요구 충족을 판정하지 않는다. 주문 저장, 재고 예약, 결제 상태, 이벤트와 감사 이력이 계약대로 일치하는지 확인한다. 다만 내부 구현 전부를 고정하지 않고 요구와 중요 위험에 필요한 상태만 관찰한다.

03

2. 통합 대상과 의존 관계 파악

먼저 모듈·서비스·데이터 저장소·외부 시스템과 연결 방식을 도식화한다. 각 화살표에 요청자, 제공자, 프로토콜, 계약 버전, 동기/비동기, 인증, 시간 제한, 오류 처리 책임을 붙인다.

코드 예시 · text

[주문 화면]
     │ HTTPS 요청
     v
[주문 서비스] ──동기 API──> [결제 어댑터] ──계약 경계──> [외부 결제]
     │
     ├──이벤트──> [재고 서비스]
     └──이벤트──> [알림 서비스]

이 도식에서 테스트 대상은 선과 끝점만이 아니라 결합 후 업무 상태다. 결제 승인 후 재고 예약 이벤트가 실패했을 때 주문 상태가 무엇인지, 재처리하면 결제가 중복되지 않는지, 알림 실패가 주문 성공을 되돌리는지 요구사항을 확인한다. 책임이 정의되지 않았다면 테스트 기대값을 임의로 만들지 말고 설계 쟁점으로 올린다.

의존성 목록에는 실제 연계·대역 사용 범위, 테스트 계정, 호출 제한, 장애 주입과 데이터 정리 방법을 기록한다. 대역은 실제 인증·네트워크·직렬화 위험을 모두 재현하지 못하므로 계약 검증과 통제된 실제 연계 검증을 층화한다.

04

3. 통합 전략과 선택 기준

3.1 하향식 통합

상위 제어 모듈에서 시작해 하위 모듈을 순차 결합한다. 아직 준비되지 않은 하위 모듈은 스텁으로 대체한다. 주요 업무 흐름과 제어 구조를 일찍 확인할 수 있지만, 하위 공통 모듈의 실제 동작 검증이 늦어지고 많은 스텁이 필요할 수 있다.

3.2 상향식 통합

저수준 모듈을 먼저 묶고 상위 호출자를 드라이버로 대체한다. 데이터 처리와 공통 서비스의 결합을 일찍 안정화할 수 있다. 하지만 사용자 관점의 전체 흐름은 늦게 보이고 드라이버가 실제 상위 모듈의 호출 행동을 정확히 흉내 내야 한다.

3.3 샌드위치 통합

상위와 하위에서 동시에 진행해 중간 계층에서 만난다. 병렬화와 조기 피드백의 장점이 있지만 경계와 책임, 스텁·드라이버 계약을 잘 조정해야 한다. 여러 팀이 독립 배포하는 구조에 유용할 수 있다.

3.4 빅뱅 통합

대부분의 구성 요소를 한꺼번에 결합한다. 작은 시스템이나 이미 안정된 구성 요소에는 단순할 수 있지만, 실패 원인 격리가 어렵고 핵심 계약 오류를 늦게 발견할 위험이 크다. “도구가 자동으로 연결해 준다”는 이유만으로 선택할 전략은 아니다.

3. 통합 전략과 선택 기준 · 학습 표 2
판단 요소질문
아키텍처계층형인가, 이벤트 중심인가, 독립 서비스인가
준비 순서어떤 모듈과 환경을 먼저 사용할 수 있는가
위험금전·데이터 손실 가능성이 큰 경계는 어디인가
격리 가능성실패 원인을 어떤 관찰 정보로 분리할 수 있는가
대역 비용스텁·드라이버가 계약과 상태를 충분히 모사할 수 있는가
실행 속도자동화와 병렬화가 가능한 경계는 무엇인가

스텁은 호출받는 구성 요소를 대신하고, 드라이버는 호출하는 구성 요소를 대신한다. 대역이 실제보다 항상 빠르고 성공만 반환하면 시간 초과·실패 처리 결함을 찾지 못한다. 정상뿐 아니라 계약 오류, 느린 응답, 일시 실패, 중복 응답을 계획적으로 제공하고 어떤 실제 특성을 모사하지 못하는지 한계표를 남긴다.

05

4. 인터페이스 유형별 테스트 포인트

4.1 동기 API

요청 메서드와 경로, 헤더, 본문 스키마, 인증, 응답 상태와 본문을 확인한다. 필수값 누락, 범위 밖 값, 알 수 없는 코드, 권한 부족, 대상 없음, 충돌, 서버 오류, 시간 초과를 구분한다. 재시도 가능 오류와 불가능 오류가 계약대로 표현되는지도 본다.

동일한 생성 요청이 네트워크 오류로 응답만 유실될 수 있다. 호출자가 결과를 모르고 재시도할 때 같은 업무가 두 번 처리되지 않도록 요청 식별자, 멱등 키 또는 자연 업무 키에 따른 정책을 확인한다. 멱등성은 “API를 두 번 호출하지 않는다”가 아니라 같은 의미의 요청을 반복해도 최종 업무 효과가 한 번 적용되도록 하는 성질이다.

4.2 비동기 메시지

생산자와 소비자의 스키마, 메시지 키, 순서 보장 범위, 중복 전달, 재처리, 실패 보관, 소비 완료 시점을 확인한다. 메시지 시스템은 설계에 따라 적어도 한 번 전달되어 중복될 수 있으므로 소비자가 업무 키로 중복 효과를 막는지 검증한다. 서로 다른 키의 전역 순서를 당연하게 가정해서는 안 된다.

코드 예시 · text

사건: PAYMENT_APPROVED(orderId=O-17, eventId=E-901)
1차 수신 → 주문 상태 결제완료, 처리 이력 E-901 저장
동일 사건 재수신 → E-901 확인, 상태·재고 효과 추가 없음
늦은 PAYMENT_FAILED 수신 → 허용 전이 규칙에 따라 거부·격리·알림

처리 실패 시 메시지를 즉시 무한 재시도하면 장애를 확대할 수 있다. 재시도 횟수와 간격의 구체값은 시스템 정책에 따르되, 일시 오류와 영구 오류의 분류, 재처리 기록, 운영자 확인 경로가 있는지 테스트한다.

4.3 파일·배치 연계

파일명 규칙, 문자 인코딩, 구분자, 헤더, 레코드 길이, 날짜·금액 표현, 빈 파일, 중복 파일, 부분 파일, 전송 완료 표식을 확인한다. 처리 건수뿐 아니라 성공·실패·보류 건수 합계와 원본 건수가 일치하는지 대사한다. 파일을 읽는 중 전송이 끝나지 않는 문제를 막기 위해 임시 이름 후 원자적 변경 또는 완료 표식 같은 계약을 확인한다.

4.4 공유 데이터와 저장소

공유 스키마를 통한 결합은 컬럼 의미, 트랜잭션 경계, 잠금, 버전 호환성을 확인한다. 한 모듈이 다른 모듈 소유 테이블을 직접 수정하면 규칙을 우회할 수 있으므로 소유권과 접근 계약을 검토한다. 동시 수정에는 버전 값이나 잠금 정책에 따라 분실 갱신이 방지되는지 검증한다.

06

5. 요구사항 충족 테스트 수행 절차

5.1 요구와 계약 기준선 확보

요구사항 ID, 인터페이스 스키마, 상태 전이, 오류 정책, 보안 요구를 같은 기준 버전으로 맞춘다. 문서와 실제 배포가 다르면 결과를 판정할 수 없으므로 빌드와 계약 버전을 기록한다.

5.2 위험 기반 결합 순서 수립

금전, 개인정보, 데이터 유실처럼 영향이 큰 경계와 변경이 많은 계약을 앞당긴다. 의존 관계와 준비 상태를 고려해 통합 전략을 정하고, 실제 구성 요소와 대역의 사용 범위를 명시한다.

5.3 환경·데이터·관찰 수단 준비

서비스별 빌드 ID, 구성, 계정, 인증서, 테스트 데이터, 시각 설정을 확인한다. 요청부터 후속 메시지까지 이어 볼 수 있는 상관 식별자를 넣고, 로그의 민감정보 마스킹과 시각 동기화를 확인한다. 관찰 수단이 없으면 실패가 아니라 단순 지연인지 판단하기 어렵다.

5.4 정상 흐름부터 계약 확인

먼저 대표 정상 흐름으로 필드·단위·상태와 기본 관찰 경로를 검증한다. 이후 경계·권한·중복·실패를 확대한다. 정상 흐름 실패가 해결되지 않은 상태에서 많은 오류 케이스를 실행하면 원인 중첩으로 결과 해석이 어려울 수 있다.

5.5 실패·복구·동시성 실행

호출 거부, 시간 초과, 응답 유실, 메시지 중복·순서 역전, 부분 성공, 서비스 재시작을 요구 범위에 맞게 주입한다. 사용자에게 보인 결과, 각 저장 상태, 메시지, 감사 이력, 재처리 결과를 함께 확인한다. 실행마다 입력, 시각, 빌드, 상관 ID, 대역 규칙을 증거로 남긴다.

5.6 결함 기록과 재현

결함에는 기대·실제 결과, 최소 재현 절차, 관련 요구·인터페이스, 환경·빌드, 데이터, 로그 상관 ID, 영향과 심각도를 기록한다. “연계 오류”처럼 넓게 쓰지 말고 어느 계약의 어떤 조건에서 어떤 상태 불일치가 생겼는지 명시한다. 동일 원인의 여러 증상을 중복 결함으로 세지 않도록 분류한다.

07

6. 구체 시나리오: 주문·결제·재고 결합

요구는 “결제 승인과 재고 예약이 완료된 주문만 접수 완료로 표시하고, 재시도해도 이중 결제·이중 차감이 없어야 한다”이다.

6. 구체 시나리오: 주문·결제·재고 결합 · 학습 표 3
케이스주입 조건기대 결과
정상승인·예약 모두 성공주문 접수완료, 각 효과 1회, 추적 이력 연결
결제 거부명시적 거부 응답주문 미접수, 재고 효과 없음, 거부 사유 안내
승인 응답 유실결제는 승인했으나 응답 시간 초과상태 조회로 결과 확인, 재시도해도 결제 1건
재고 일시 실패결제 승인 후 예약 실패요구된 보상·보류 상태, 재처리 가능, 상태 불일치 노출
중복 이벤트같은 승인 사건 두 번 전달처리 이력으로 중복 식별, 추가 효과 없음
순서 역전취소 사건 후 늦은 승인 사건허용 전이 정책 적용, 완료 상태로 잘못 복귀하지 않음
타인 주문다른 사용자 토큰 사용권한 거부, 주문·결제·재고 상태 변화 없음

여기서 “트랜잭션이므로 모두 롤백”이라고 단정하면 분산 경계를 무시할 수 있다. 실제 요구가 보상 처리인지, 보류 후 재처리인지, 하나의 원자적 저장 범위인지 확인한 뒤 기대 결과를 쓴다. 외부 결제 승인은 우리 DB 롤백으로 취소되지 않을 수 있다.

08

7. 결함 추이 수집

결함 추이는 시간 또는 테스트 진행량에 따라 발견·해결 상태가 어떻게 변하는지를 본다. 날짜별 새 결함 수만 보면 테스트 투입량 변화에 오해할 수 있으므로 실행 케이스 수, 기능 범위, 빌드 변경, 테스터 투입, 심각도와 함께 해석한다.

7. 결함 추이 수집 · 학습 표 4
지표의미해석 주의
신규 발견 수기간 중 새로 확인된 결함실행량 증가로 함께 늘 수 있음
누적 발견 수지금까지 발견된 고유 결함중복·재분류 정책에 영향 받음
해결·검증 완료 수수정 후 재테스트까지 끝난 결함개발 완료와 검증 완료를 구분
미해결 수현재 남은 열린 결함심각도와 사용 경로를 함께 봄
재오픈 수수정 불충분·회귀 후보요구 오해나 영향 분석 부족 신호
발견율일정 기간/실행량당 발견시간당과 케이스당 의미가 다름
누출 결함이전 단계에서 놓쳐 이후 발견단계 경계와 분류 일관성 필요

결함 상태는 등록, 분석, 수정, 재테스트 대기, 종료 같은 흐름을 일관되게 사용한다. 개발자가 수정했다고 표시한 시점과 테스터가 해결을 확인한 시점을 섞으면 추이가 실제보다 좋아 보일 수 있다. 중복 결함, 환경 문제, 요구 변경을 결함으로 포함할지 분류 정책을 고정한다.

09

8. 결함 추이로 잔존 결함 추정

잔존 결함은 아직 발견되지 않았거나 발견됐지만 해결되지 않은 결함을 넓게 가리킬 수 있다. 추이를 이용한 추정은 정확한 개수를 맞히는 공식이 아니라 남은 위험과 추가 테스트 필요성을 판단하는 근거다.

일반적으로 테스트 범위와 실행량이 안정적인데 신규 결함 발견율이 감소하고, 누적 발견 곡선이 완만해지며, 재오픈과 중요 결함이 줄고, 높은 위험 영역의 실행이 충분하다면 잔존 위험이 낮아지는 신호로 볼 수 있다. 하지만 다음 상황에서는 곡선 하락을 품질 향상으로 해석하면 안 된다.

  • 테스트 인력이나 실행 시간이 줄었다.
  • 쉬운 정상 케이스만 남았거나 반대로 아직 핵심 영역을 시작하지 않았다.
  • 환경 장애로 실제 실행이 적었다.
  • 대규모 변경 빌드가 들어와 과거 추이와 모집단이 달라졌다.
  • 결함 등록 기준이 바뀌거나 여러 증상을 하나로 합쳤다.
  • 관찰 수단이 부족해 결함을 발견하기 어려워졌다.

추정 절차는 다음과 같다.

  1. 동일한 범위·빌드 계열·분류 기준의 데이터를 선택한다.
  2. 시간뿐 아니라 실행 케이스, 요구 커버리지, 위험 영역별 진행률을 함께 정규화한다.
  3. 신규·누적·미해결·재오픈 추이를 심각도와 모듈별로 나눈다.
  4. 발견율이 줄어든 원인이 품질 개선인지 테스트 활동 감소인지 확인한다.
  5. 미실행·변경·결함 밀집 영역을 표시하고 정성적 위험을 보정한다.
  6. “잔존 결함 0”이 아니라 신뢰 범위와 가정, 추가 검증 권고를 보고한다.

예를 들어 전체 신규 결함은 감소하지만 결제 연계 케이스를 이제 시작했고 첫 주에 중요 결함이 집중되었다면 전체 곡선만 보고 종료해서는 안 된다. 반대로 높은 위험 경계까지 안정적으로 반복 실행했고 새로운 결함이 낮은 영향의 표현 문제에 집중되며 재오픈도 감소한다면 위험이 수렴하는 근거가 된다.

10

9. 실기 체크리스트와 함정

  • 인터페이스의 구문·의미·행위·시간·보안 계약을 모두 확인했는가?
  • 통합 전략을 준비 순서와 위험에 근거해 선택했는가?
  • 스텁·드라이버의 정상/실패 행동과 실제 대비 한계를 기록했는가?
  • 정상뿐 아니라 시간 초과·중복·순서 역전·부분 성공을 검증했는가?
  • 멱등성을 호출 횟수가 아닌 최종 업무 효과로 판정했는가?
  • 분산 실패를 무조건 DB 롤백으로 해결된다고 가정하지 않았는가?
  • 빌드·구성·데이터·상관 ID를 포함한 재현 증거가 있는가?
  • 결함 상태와 중복·환경 문제 분류 기준이 기간 내 일관적인가?
  • 추이를 실행량·범위·심각도와 함께 해석했는가?
  • 잔존 결함을 0이라고 단정하지 않고 가정과 미검증 위험을 밝혔는가?

자주 틀리는 답은 API 성공 코드만 확인하는 것, 대역을 실제 시스템과 동일하다고 보는 것, 재시도를 단순 반복 호출로 구현하는 것, 메시지 전역 순서를 가정하는 것, 발견 결함 수가 감소했다는 사실만으로 품질이 좋아졌다고 결론 내리는 것이다. 또한 수정 완료와 검증 완료를 같은 상태로 집계하면 미해결 위험을 축소하게 된다.

11

확인 문제

문제 1

단위 테스트를 통과한 두 모듈 사이에서도 통합 결함이 생기는 이유를 예로 설명하시오.

문제 2

하향식 통합에서 스텁의 역할과 한계를 쓰시오.

문제 3

비동기 메시지 소비자의 멱등성을 어떻게 검증할 수 있는지 설명하시오.

문제 4

동기 API의 응답 유실 상황에서 단순 재시도가 위험한 이유와 확인할 통제를 쓰시오.

문제 5

파일 연계의 처리 무결성을 확인할 대사 항목을 쓰시오.

문제 6

분산된 주문·결제 통합 실패를 로컬 DB 롤백만으로 해결할 수 없는 이유를 쓰시오.

문제 7

결함 추이 해석에서 신규 결함 수와 함께 봐야 할 정보 네 가지를 쓰시오.

문제 8

신규 결함 발견율 감소가 품질 향상을 뜻하지 않을 수 있는 상황 두 가지를 쓰시오.

문제 9

잔존 결함 추정을 보고할 때 함께 명시해야 할 가정과 한계를 설명하시오.

문제 10

통합 결함을 재현 가능한 형태로 기록할 때 필요한 정보 다섯 가지를 쓰시오.

12

정답과 해설

정답 1

각 모듈이 서로 다른 필드명, 자료형, 단위, 코드 의미, 호출 순서를 가정할 수 있기 때문이다. 주문은 원 단위 숫자를 보내는데 결제는 최소 통화 단위 정수를 기대하는 경우가 예다.

정답 2

스텁은 아직 결합하지 않은 하위 피호출 모듈을 대신해 정해진 응답을 반환한다. 실제 성능·네트워크·상태·복잡한 오류를 모두 모사하지 못할 수 있으므로 실제 연계 검증을 완전히 대체하지 않는다.

정답 3

같은 업무 키와 사건 ID를 가진 메시지를 반복 전달한 뒤 최종 상태, 재고·금액 변화, 후속 메시지, 처리 이력이 한 번의 업무 효과만 갖는지 확인한다.

정답 4

외부에서는 이미 승인됐지만 응답만 잃었을 수 있어 재호출이 이중 승인을 만들 수 있다. 멱등 키, 업무 키 조회, 처리 상태 조회 계약으로 기존 결과를 확인해야 한다.

정답 5

원본 레코드 수와 성공·실패·보류 건수 합계가 맞는지, 금액 등 통제 합계가 일치하는지, 중복·부분 파일이 별도로 식별되는지 확인한다.

정답 6

외부 결제 효과는 우리 데이터베이스 트랜잭션 경계 밖에 있어 로컬 롤백으로 취소되지 않기 때문이다. 요구에 따른 보상, 보류·재처리, 상태 대사가 필요하다.

정답 7

실행 케이스 수, 요구·위험 영역 진행률, 빌드 변경, 테스터 투입, 환경 가용성, 심각도, 재오픈 수 중 네 가지를 함께 본다.

정답 8

실행량이나 인력이 줄었거나, 환경 장애로 테스트하지 못했거나, 핵심 영역을 아직 시작하지 않았거나, 등록 기준이 바뀐 경우가 해당한다.

정답 9

분석한 범위·기간·빌드·분류 기준, 미실행 및 최근 변경 영역, 데이터량과 관찰 한계를 밝힌다. 추정은 정확한 잔존 개수가 아니라 조건부 위험 판단임을 명시한다.

정답 10

기대·실제 결과, 최소 재현 절차, 관련 요구·계약, 빌드·환경 구성, 입력 데이터, 상관 ID와 로그, 영향·심각도 중 다섯 가지가 필요하다.

13

핵심 요약

  • 통합 모듈·인터페이스의 요구사항 충족 테스트는 구성 요소 사이의 구문·의미·행위·시간·무결성·보안 계약과 결합 후 업무 상태를 검증한다.
  • 하향식·상향식·샌드위치·빅뱅 전략은 아키텍처, 준비 순서, 위험, 원인 격리와 대역 비용으로 선택한다.
  • 동기 API는 시간 초과와 멱등성, 메시지는 중복·순서·재처리, 파일은 완결성과 대사, 공유 데이터는 트랜잭션·동시성을 중점 확인한다.
  • 성공 응답만 보지 말고 저장 상태, 후속 사건, 감사 이력과 복구 결과를 상관 식별자로 연결한다.
  • 결함 추이로 잔존 결함 추정을 할 때 신규·누적·미해결·재오픈을 실행량·범위·심각도와 함께 해석한다.
  • 결함 발견율 감소는 활동 감소 때문일 수 있으므로 잔존 결함 0을 단정하지 않고 가정·미검증 영역·추가 검증 필요성을 보고한다.
