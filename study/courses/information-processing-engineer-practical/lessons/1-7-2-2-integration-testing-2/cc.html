01

출제 범위와 수행 목표

이 레슨은 통합 테스트 결과가 요구사항과 위험을 충분히 검증했는지 판단하는 충분성 검증과 결함 개선조치 작성을 중심으로 한다. 또한 애플리케이션 통합 테스트하기의 적용 절차와 판단 기준을 계획부터 종료·인계까지 산출물 중심으로 정리한다. 앞 레슨의 인터페이스 실행과 결함 추이 분석을 입력으로 받아, 미검증 영역과 잔여 위험을 드러내고 수정·예방·재검증 조치를 실행 가능한 형태로 만드는 단계다.

학습 후에는 다음을 수행할 수 있어야 한다.

  • 테스트 케이스 개수나 전체 통과율만으로 충분성을 판단하면 안 되는 이유를 설명한다.
  • 요구사항·위험·인터페이스·상태·오류·환경 관점의 충분성 근거를 작성한다.
  • 결함의 증상, 직접 원인, 근본 원인, 영향 범위를 구분한다.
  • 시정조치와 예방조치를 담당자·기한·검증 증거가 있는 계획으로 만든다.
  • 재테스트와 회귀 테스트 범위를 근거로 정하고 종료·인계 여부를 판단한다.
  • 통합 테스트의 전체 적용 절차와 각 단계의 진행 기준을 설명한다.
02

1. 테스트 충분성의 의미

충분성은 “결함이 하나도 없다”는 증명이 아니라 승인된 범위와 위험에 대해 필요한 증거를 확보하여 남은 위험을 의사결정자가 수용할 수 있는 상태인지 판단하는 것이다. 모든 입력과 실행 순서를 시험하는 것은 현실적으로 불가능하므로, 무엇을 어떤 근거로 선택했고 무엇이 남았는지를 투명하게 제시해야 한다.

다음 세 문장은 충분성 근거가 되기 어렵다.

  • “테스트 케이스를 많이 실행했다.” 개수는 요구사항 중요도와 중복 정도를 말해 주지 않는다.
  • “통과율이 높다.” 낮은 위험 케이스가 분모를 크게 만들 수 있고 핵심 실패를 가릴 수 있다.
  • “신규 결함이 줄었다.” 실행량 감소나 미검증 영역 때문일 수 있다.

충분성은 범위 커버리지, 선택한 설계 기법, 실행 결과, 결함 상태, 환경 대표성, 변경 영향, 잔여 위험을 종합한다. 수치 기준은 프로젝트의 테스트 계획과 품질 목표를 따르며 보편적인 단일 임계값을 임의로 만들지 않는다.

2.1 요구사항 추적의 충분성

각 요구사항이 적어도 하나의 케이스에 연결되었는지만 세면 약하다. 케이스가 요구의 모든 조건과 결과를 실제로 검증하는지, 실행 결과와 결함이 다시 연결되는지 확인한다. 예를 들어 “결제 승인 실패 시 주문을 확정하지 않고 사용자에게 재시도 가능 여부를 안내”라는 요구를 성공 케이스 하나와 연결했다면 형식상 커버되지만 의미상 미검증이다.

추적표에는 요구사항 ID, 위험 등급, 관련 인터페이스, 케이스 ID, 실행 환경, 결과, 결함 ID, 잔여 제한을 연결한다. “미적용”은 빈칸으로 두지 말고 제외 근거와 승인자를 기록한다.

2.2 위험 기반 충분성

높은 위험 영역은 더 다양한 기법, 실제에 가까운 연계, 반복·장애·회귀 검증이 필요할 수 있다. 낮은 위험 화면 문구와 금전 이중 처리에 같은 깊이를 요구하지 않는다. 남은 결함의 개수보다 심각도, 사용 빈도, 탐지·복구 가능성, 우회 수단, 데이터 영향과 결함 밀집 영역을 본다.

2.3 인터페이스·상태 충분성

연결별로 정상 응답만 확인하면 부족하다. 계약 오류, 권한, 시간 초과, 중복, 순서 역전, 부분 성공, 재시작 후 재처리를 요구 범위에 맞게 확인한다. 상태 전이 표의 허용·금지 경로와 업무 부수 효과를 매핑해 빈 경로를 찾는다.

코드 예시 · text

요구 상태: 요청 → 처리중 → 완료 | 실패 | 보류
검증 완료: 요청→처리중, 처리중→완료, 처리중→실패
미검증: 처리중 장기 지속, 보류→재처리, 완료 후 중복 사건
판단: 핵심 운영 복구 경로가 비어 있으므로 충분성 미충족

2.4 환경과 대역의 대표성

테스트 환경과 운영 환경의 네트워크 지연, 인증, 구성, 데이터량, 외부 연계가 다르면 결과의 적용 범위를 제한한다. 스텁에서 성공한 계약 테스트가 실제 인증서 갱신이나 프록시 제한을 확인하지는 못한다. 차이를 숨기지 말고 어떤 위험을 별도 검증·모니터링·단계적 배포로 보완할지 기록한다.

04

3. 충분성 검증 절차

3.1 기준과 증거 모으기

승인된 요구·위험 목록, 통합 범위, 환경 구성, 실행 결과, 결함 현황, 변경 목록, 결함 추이, 대역 한계를 같은 기준 시점으로 맞춘다. 오래된 추적표와 최신 빌드 결과를 섞으면 잘못된 판단을 내릴 수 있다.

3.2 미검증 영역 식별

요구사항, 사용자 역할, 인터페이스, 상태, 오류 유형, 데이터 분할, 플랫폼, 비기능 속성을 행과 열로 놓고 공백을 찾는다. 공백이 모두 결함은 아니며, 제외가 승인되고 위험이 수용됐는지 확인한다.

3.3 결과와 결함의 질 평가

통과 결과에 필요한 로그·데이터·메시지 증거가 있는지, 환경 문제로 잘못 통과 처리하지 않았는지, 실패가 결함과 연결됐는지 확인한다. 수정 완료 표시만 있고 재테스트가 없으면 해결 근거가 아니다. 중요 결함이 반복되는 모듈은 주변 미발견 결함 가능성이 높으므로 추가 탐색과 회귀 후보가 된다.

3.4 잔여 위험 평가

미실행 케이스, 대역으로만 확인한 연계, 알려진 결함, 최근 변경, 운영에서만 가능한 조건을 목록화한다. 각 항목에 영향, 발생 가능 조건, 탐지 방법, 우회·복구, 책임자, 수용 여부를 붙인다. “낮음” 한 단어보다 판단 근거를 남긴다.

3.5 결론과 조건부 승인

충분, 조건부 충분, 불충분 같은 프로젝트의 판정 체계에 따라 결정한다. 조건부 승인이라면 남은 조치, 완료 기한, 배포 제한, 관찰 지표, 되돌림 기준을 명시한다. 일정 압박은 위험이 사라졌다는 근거가 아니며, 위험 수용은 권한 있는 의사결정자가 해야 한다.

05

4. 결함에서 개선조치로 전환하기

결함 보고서는 현상을 재현하고 수정 여부를 판단하기 위한 기록이다. 개선조치는 같은 원인으로 다시 발생하거나 다른 영역으로 확산되는 것을 막기 위한 실행 계획이다. 증상을 고치는 시정조치와 원인을 제거하는 예방조치를 구분하면 빠른 복구와 장기 개선을 함께 관리할 수 있다.

코드 예시 · text

증상: 결제 승인 응답이 유실된 뒤 재시도하면 승인 두 건 생성
직접 원인: 재시도 요청에 동일 업무를 식별할 값이 전달되지 않음
근본 원인: 인터페이스 설계 점검표에 멱등·결과 조회 항목이 없고,
           실패 시나리오가 정상 응답 중심으로 작성됨
영향: 고객 중복 청구, 주문-결제 대사 불일치, 상담 비용

여기서 “중복 승인을 삭제한다”는 복구이고, 요청 식별과 결과 조회 계약을 구현하는 것은 시정조치다. 인터페이스 표준과 리뷰·테스트 템플릿에 멱등 항목을 추가하는 것은 예방조치다. 각 조치는 실제 원인과 연결되어야 하며 “주의한다”, “교육한다”만으로 기술·절차 결함을 닫아서는 안 된다.

07

6. 영향 분석과 조치 우선순위

결함 수정은 다른 계약과 상태에 부작용을 낼 수 있다. 변경할 모듈, 호출자·피호출자, 공유 데이터, 메시지 소비자, 배치, 캐시, 화면, 운영 도구, 보안 정책을 추적한다. 인터페이스 필드를 바꾸면 하위 호환, 동시 배포 순서, 이전 메시지 처리도 검토한다.

우선순위 판단 요소는 다음과 같다.

  • 사용자·금전·개인정보·데이터 무결성에 미치는 영향
  • 발생 빈도와 노출 사용자 범위
  • 발견·복구 가능성과 우회 수단
  • 다른 기능으로 확산될 공통 원인인지 여부
  • 규정·계약·운영 중단과 연결되는지 여부
  • 수정 복잡도와 수정 자체의 회귀 위험

심각도가 높다고 무조건 가장 단순한 긴급 패치를 선택하지 않는다. 데이터 복구와 추가 피해 차단을 먼저 하고, 안전한 수정·검증·배포 순서를 정한다. 긴급 조치로 기능을 제한했다면 영구 조치와 제한 해제 조건을 별도로 추적한다.

08

7. 재테스트와 회귀 테스트 설계

재테스트는 원래 결함의 최소 재현 조건과 대표 변형에서 실제 결과가 기대 결과로 바뀌었는지 확인한다. 같은 데이터만 한 번 실행하지 말고 원인 경계의 바로 안팎과 실패·복구 조건을 포함한다. 수정 코드가 배포된 빌드, 환경, 데이터와 증거를 기록한다.

회귀 범위는 변경 파일 목록만으로 정하지 않는다. 호출 그래프, 인터페이스 계약, 데이터 흐름, 공통 모듈 사용처, 업무 상태, 과거 결함 밀집 영역을 기준으로 선정한다.

7. 재테스트와 회귀 테스트 설계 · 학습 표 3
수정직접 재테스트회귀 후보
결제 멱등 처리동일 키 반복·응답 유실·상태 조회주문 생성, 취소, 환불, 대사 배치
날짜 코드 변환각 허용·거부 코드와 시간 경계조회·파일 연계·화면 표시
메시지 재처리중복·순서 역전·재시작후속 소비자, 실패 보관, 운영 재처리
권한 검사역할·소유권별 허용/거부관리자 대행, 배치 계정, 감사 이력

수정 후 원래 케이스만 통과해도 공통 함수가 다른 기능을 깨뜨릴 수 있다. 반대로 전체 시스템을 매번 모두 재검증하면 시간이 낭비된다. 영향과 위험을 근거로 자동화된 빠른 회귀, 인터페이스 회귀, 핵심 업무 시나리오를 층화한다.

09

8. 애플리케이션 통합 테스트하기의 적용 절차와 판단 기준

단계 1: 계획과 범위 확정

통합 대상·요구·위험·제외·환경·역할을 정하고 인터페이스 목록과 의존 그래프를 만든다. 판단 기준은 각 경계의 책임과 테스트 가능성이 설명되는가이다.

단계 2: 전략과 시나리오 설계

상향식·하향식·혼합 등 결합 순서를 정하고 정상·경계·권한·실패·복구 시나리오를 요구에 연결한다. 판단 기준은 높은 위험 경계가 적절히 앞당겨지고, 대역 한계가 밝혀졌는가이다.

단계 3: 환경·데이터·관찰 준비

빌드·구성·계정·인증·대역·시드 데이터를 준비하고 상관 ID, 로그, 지표, 추적을 점검한다. 판단 기준은 결과를 재현·격리하고 민감정보 없이 관찰할 수 있는가이다.

단계 4: 단계적 결합과 실행

기준 정상 흐름을 확인한 후 오류·시간 초과·중복·순서·부분 성공·재시작을 실행한다. 결과는 화면, API, 저장 상태, 메시지, 감사 이력까지 요구 계약에 필요한 범위로 확인한다.

단계 5: 결함 분류와 조치

재현 증거를 갖춰 결함을 기록하고 영향·심각도·원인을 분석한다. 시정·예방조치, 담당자, 완료 기준, 재테스트·회귀 범위를 정한다. 판단 기준은 조치가 증상이 아니라 확인된 원인과 연결되는가이다.

단계 6: 재검증과 충분성 평가

수정 빌드에서 재테스트와 영향 기반 회귀를 수행한다. 추적표, 위험, 미실행, 환경 차이, 결함 추이를 종합해 충분성을 평가한다. 판정 근거와 잔여 위험을 분리해 기록한다.

단계 7: 종료·인계·회고

승인된 종료 기준을 확인하고 테스트 결과, 알려진 제한, 운영 감시, 재처리·복구 절차, 미완료 조치를 인계한다. 반복 원인은 설계 표준, 자동 계약 검사, 코드·문서 리뷰, 관찰성 개선으로 환류한다.

10

9. 구체 업무 시나리오: 재고 예약 누락 개선조치

통합 테스트에서 주문은 접수완료인데 재고 예약 메시지가 발행되지 않는 결함이 발견되었다고 하자. 조사 결과 주문 저장 후 이벤트 발행 사이에 프로세스가 종료되면 데이터와 메시지가 분리되는 창이 있었다.

개선조치는 다음처럼 작성할 수 있다.

코드 예시 · text

결함: INT-247, 접수완료 주문의 재고 예약 사건 누락
영향: 과판매 가능, 주문·재고 대사 불일치
즉시조치: 영향 기간 주문 대사 → 누락 건 보류 → 안전한 재발행
시정조치: 저장과 사건 기록의 일관성을 보장하는 설계로 변경,
          재발행 시 업무 키 중복 방지 및 처리 이력 확인
예방조치: 저장-발행 경계 리뷰 항목과 장애 주입 회귀 케이스 추가
검증: 저장 직후 프로세스 종료, 재시작, 중복 재발행, 소비자 실패 실행
증거: 주문/사건/예약 ID 상관 추적과 대사 합계
잔여위험: 실제 운영 장애 패턴 차이는 단계적 배포와 누락 지표로 관찰

“메시지를 한 번 더 보낸다”는 임시 복구만으로 종료하면 같은 창에서 재발한다. 반대로 특정 구현 패턴을 요구사항 확인 없이 정답으로 단정하지 않는다. 아키텍처 제약 속에서 원자적 기록, 안전한 전달, 중복 방지, 대사가 충족되는 대안을 선택하고 증거로 검증한다.

11

10. 실기 체크리스트와 자주 틀리는 함정

  • 충분성을 케이스 수·통과율·일정 하나로 판정하지 않았는가?
  • 요구와 케이스의 형식 연결이 실제 조건·결과를 검증하는가?
  • 높은 위험 영역의 오류·복구·금지 경로가 포함되었는가?
  • 환경 차이와 대역 한계가 결과 적용 범위에 반영되었는가?
  • 수정 완료와 재테스트 검증 완료를 구분했는가?
  • 증상, 직접 원인, 근본 원인, 영향과 증거를 구분했는가?
  • 즉시 복구·시정·예방조치가 각각 원인과 연결되는가?
  • 담당자·기한·완료 기준·재테스트·회귀·되돌림이 구체적인가?
  • 최근 수정의 계약·데이터·호출자 영향까지 회귀 범위를 정했는가?
  • 잔여 위험의 수용 주체와 운영 관찰·복구 방법을 기록했는가?

자주 틀리는 함정은 결함 개수 0을 충분성으로 보는 것, 미실행을 통과로 간주하는 것, “개발자 주의”를 근본 조치로 쓰는 것, 모든 수정에 같은 회귀 범위를 적용하는 것, 실제 연계와 다른 대역의 결과를 일반화하는 것이다. 일정상 배포한다고 충분성 판정을 바꾸지 말고 조건부 승인과 위험 수용을 명시해야 한다.

12

확인 문제

문제 1

테스트 케이스 수가 많다는 사실만으로 충분성을 판단할 수 없는 이유를 쓰시오.

문제 2

요구사항 추적표에서 단순 연결 여부 외에 확인해야 할 항목 세 가지를 쓰시오.

문제 3

테스트 환경과 운영 환경의 차이를 충분성 판단에 반영하는 방법을 설명하시오.

문제 4

결함의 증상, 직접 원인, 근본 원인을 중복 승인 사례로 구분하시오.

문제 5

즉시 복구, 시정조치, 예방조치의 차이를 쓰시오.

문제 6

재테스트와 회귀 테스트의 범위를 각각 어떤 근거로 정하는지 설명하시오.

문제 7

결함 개선조치서에 담당자와 기한 외에 필요한 검증 관련 항목 네 가지를 쓰시오.

문제 8

중요 결함이 해결되었다고 표시됐지만 재테스트 전인 경우 충분성 판단에서 어떻게 처리해야 하는지 쓰시오.

문제 9

조건부 승인에 반드시 포함해야 할 내용을 네 가지 쓰시오.

문제 10

애플리케이션 통합 테스트하기의 적용 절차를 일곱 단계로 요약하시오.

13

정답과 해설

정답 1

케이스가 낮은 위험에 편중되거나 서로 중복될 수 있고, 핵심 요구·인터페이스·오류 경로가 미검증일 수 있기 때문이다. 요구·위험 추적과 실행 증거를 함께 봐야 한다.

정답 2

케이스가 요구의 모든 조건과 결과를 검증하는지, 실제 실행 결과가 있는지, 연결 결함과 잔여 제한이 무엇인지 확인한다.

정답 3

구성, 네트워크, 인증, 데이터량, 외부 연계의 차이를 목록화하고 각 차이가 만드는 위험을 실제 환경 대표 검증, 모니터링, 단계적 배포, 복구 계획으로 보완한다.

정답 4

증상은 응답 유실 후 승인 두 건이 생성된 것, 직접 원인은 재시도 요청에서 동일 업무를 식별하지 못한 것, 근본 원인은 인터페이스 설계·리뷰·테스트 기준에 멱등과 결과 조회 항목이 빠진 것이다.

정답 5

즉시 복구는 이미 발생한 피해와 데이터를 안전한 상태로 되돌린다. 시정조치는 현재 결함의 원인을 제거하고, 예방조치는 같은 원인이 다른 곳이나 이후 변경에서 재발하지 않도록 표준·자동 검사·리뷰를 개선한다.

정답 6

재테스트는 원래 재현 조건과 원인 경계의 변형을 기준으로 한다. 회귀는 변경 영향, 호출·데이터 흐름, 공통 모듈 사용처, 인터페이스와 업무 위험을 기준으로 한다.

정답 7

완료 기준, 재테스트 케이스·데이터, 회귀 범위, 기대 증거, 배포 순서, 관찰 및 되돌림 조건 중 네 가지가 필요하다.

정답 8

수정 구현 상태와 검증 완료를 구분해 미검증 위험으로 남겨야 한다. 수정 빌드에서 재현 조건과 영향 범위를 확인하기 전에는 해결 근거로 사용할 수 없다.

정답 9

남은 조치와 책임자·기한, 배포 제한, 운영 관찰 지표, 되돌림 기준, 잔여 위험과 승인 주체 중 네 가지를 포함한다.

정답 10

계획·범위 확정, 전략·시나리오 설계, 환경·데이터·관찰 준비, 단계적 결합·실행, 결함 분류·조치, 재검증·충분성 평가, 종료·인계·회고 순이다.

14

핵심 요약

  • 충분성 검증과 결함 개선조치 작성은 통합 테스트 증거를 요구·위험과 대조하고 잔여 위험을 수용 가능한 수준으로 관리하는 활동이다.
  • 충분성은 케이스 수, 통과율, 신규 결함 감소 하나가 아니라 요구·위험·인터페이스·상태·데이터·환경·변경을 종합해 판단한다.
  • 결함은 증상·직접 원인·근본 원인·영향을 증거로 구분하고 즉시 복구, 시정, 예방조치를 연결한다.
  • 개선조치에는 담당자·기한뿐 아니라 완료 기준, 재테스트·회귀, 배포·관찰·되돌림, 잔여 위험이 필요하다.
  • 애플리케이션 통합 테스트하기의 적용 절차와 판단 기준은 계획, 전략, 준비, 결합 실행, 결함 조치, 재검증·충분성, 종료·인계의 흐름이다.
  • 수정 완료 표시는 검증 완료가 아니며, 조건부 승인은 남은 조치와 위험 수용 주체를 명확히 해야 한다.
