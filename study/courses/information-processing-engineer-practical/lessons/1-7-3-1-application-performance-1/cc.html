01

출제 범위와 수행 목표

이 레슨은 재현 가능한 테스트로 성능 분석과 저하요인 발견을 수행하고, 측정 증거에 따라 코드·아키텍처·호출순서 조정으로 성능 개선하는 실무 절차를 다룬다. 특정 도구나 제품의 수치를 외우는 것이 아니라 목표 업무, 부하 모형, 측정 조건, 지표, 병목 가설, 변경 전후 비교를 일관되게 연결하는 것이 핵심이다.

학습 후에는 다음을 수행할 수 있어야 한다.

  • 응답시간·처리량·오류율·자원 사용량의 관계를 설명한다.
  • 부하·스트레스·급증·지속·용량 테스트를 목적에 맞게 선택한다.
  • 대표적인 업무 비율, 동시성, 데이터량, 준비·측정 구간을 명세한다.
  • 지연 분포와 자원·추적 정보를 연결하여 병목 후보를 좁힌다.
  • 코드, 아키텍처, 호출 순서 개선안을 위험과 효과로 비교한다.
  • 동일 조건의 전후 테스트로 개선 효과와 기능·안정성 회귀를 검증한다.
02

1. 성능은 빠르다는 인상이 아니라 계약이다

성능 요구는 “화면이 빠르게 열린다”가 아니라 어떤 사용자가 어떤 업무를 어떤 환경과 부하에서 수행할 때 무엇을 만족해야 하는지를 판정 가능하게 표현해야 한다. 구체 목표값은 프로젝트의 승인된 요구에서 가져오며 임의의 보편값을 만들지 않는다.

1. 성능은 빠르다는 인상이 아니라 계약이다 · 학습 표 1
지표의미해석 시 주의점
응답시간요청 시작부터 결과 수신까지 걸린 시간평균만 보면 긴 꼬리 지연이 숨을 수 있음
백분위 지연요청 중 일정 비율이 그 시간 이내 완료표본 수·구간·오류 포함 여부 명시
처리량단위 시간에 완료한 요청·거래·건수실패 요청을 포함하는지 정의
오류율전체 시도 중 실패한 비율업무 거부와 시스템 오류를 구분
동시성같은 시점에 진행 중인 사용자·작업 수초당 도착률과 같지 않음
자원 사용CPU, 메모리, 디스크, 네트워크, 연결·스레드높은 사용률 자체가 병목의 증거는 아님
포화·대기큐 길이, 잠금 대기, 연결 대기원인 자원과 상류 지연을 구분

평균 응답시간이 짧아도 일부 사용자가 매우 오래 기다리면 품질 문제가 된다. 따라서 중앙값과 상위 백분위, 최대값의 성격을 함께 보고, 타임아웃·실패 요청을 통계에서 제외했는지 명시한다. 실패를 빼면 겉보기 응답시간이 좋아질 수 있다.

처리량과 응답시간은 부하가 증가할 때 함께 관찰한다. 시스템이 포화되면 처리량은 더 늘지 않는데 대기열과 지연만 급격히 커질 수 있다. CPU가 낮다고 여유 있는 것도 아니다. 외부 호출, 잠금, 연결 풀, 디스크 I/O를 기다리는 동안 CPU는 낮을 수 있다.

03

2. 성능 테스트 유형과 선택

2.1 부하 테스트

예상되는 정상·최대 업무 부하에서 성능 요구를 만족하는지 확인한다. 대표 업무 비율과 데이터 상태가 중요하다. 로그인만 반복하면서 주문 처리 성능을 일반화해서는 안 된다.

2.2 스트레스 테스트

계획한 한계를 넘어 부하를 증가시켜 포화 지점, 실패 형태, 보호 장치와 회복성을 본다. 목표는 무조건 큰 숫자가 아니라 어디서 어떻게 성능이 무너지고 부하가 줄면 회복하는지 확인하는 것이다.

2.3 급증 테스트

짧은 시간에 요청이 급격히 늘거나 줄 때 자동 확장, 큐, 캐시, 연결, 제한 정책의 반응을 확인한다. 점진 부하만으로는 초기화 경쟁이나 확장 지연을 놓칠 수 있다.

2.4 지속 테스트

오랜 기간 대표 부하를 유지하여 메모리 누수, 연결 미반환, 로그·디스크 증가, 캐시 열화, 주기 작업 충돌을 찾는다. 짧은 테스트에서 안정적이어도 시간이 지나며 자원이 누적될 수 있다.

2.5 용량·확장성 테스트

데이터 건수, 파일 크기, 동시 작업, 노드 수 등을 변화시켜 처리 한계와 확장 효율을 확인한다. 사용자 수만 늘리는 것이 아니라 운영에서 커질 데이터와 인덱스·배치 처리도 포함한다.

2. 성능 테스트 유형과 선택 · 학습 표 2

3. 신뢰할 수 있는 측정 조건 만들기

성능 결과는 조건이 다르면 직접 비교할 수 없다. 다음 항목을 테스트 계획과 결과에 기록한다.

  • 대상 빌드, 구성, 런타임 설정, 노드 수와 배포 위치
  • 서버·저장소·부하 발생기의 CPU, 메모리, 네트워크 등 자원 조건
  • 업무별 요청 비율, 도착 패턴, 동시성, 사용자 생각 시간
  • 데이터 규모와 분포, 캐시의 초기 상태, 인덱스·통계 상태
  • 외부 시스템을 실제로 쓰는지 대역인지, 대역의 지연·실패 규칙
  • 준비 구간, 안정화 구간, 실제 측정 구간, 종료·회복 관찰 구간
  • 요청 식별자, 서버·DB·외부 호출의 시각 동기화와 추적 방법
  • 백그라운드 작업, 로그 수준, 다른 테스트의 동시 실행 여부

부하 발생기가 먼저 포화되면 대상 시스템이 아니라 측정 도구의 한계를 보게 된다. 발생기의 CPU·네트워크와 연결 수를 함께 관찰하고 필요하면 여러 발생기로 분산한다. 짧은 준비 구간 없이 바로 측정하면 초기 연결, 코드 준비, 캐시 적재 비용이 결과를 지배할 수 있다. 반대로 항상 완전히 데운 캐시만 측정하면 재시작 직후 성능 위험을 놓친다. 차가운 상태와 안정 상태를 목적에 맞게 분리한다.

테스트 데이터도 현실적이어야 한다. 모든 요청이 같은 인기 상품만 조회하면 비정상적으로 높은 캐시 적중이나 한 행의 잠금 경합이 생길 수 있다. 실제 키 분포를 대표하되 개인정보를 제거하고, 쓰기 요청은 케이스별 식별자로 충돌을 통제한다.

05

4. 성능 분석 절차

4.1 목표와 기준선 확정

핵심 사용자 여정과 품질 목표를 정하고 현재 빌드의 기준선을 같은 조건에서 측정한다. 기준선이 없으면 변경 후 수치가 좋아진 것인지 판단하기 어렵다. 기능 오류가 많은 상태의 성능 수치는 무의미할 수 있으므로 성공 결과와 데이터 정합성을 함께 검증한다.

4.2 단계적으로 부하 증가

낮은 부하에서 시작하여 관찰 가능한 단계로 증가시킨다. 각 단계에서 응답시간 분포, 처리량, 오류, 자원, 큐를 함께 수집한다. 갑자기 최대 부하만 주면 포화 시작점과 원인 변화를 놓친다.

4.3 요청 경로를 분해

느린 업무의 전체 시간을 웹·애플리케이션·DB·캐시·외부 호출·큐 대기로 분해한다. 분산 추적이나 상관 로그로 같은 요청을 연결하고, 프로파일링과 실행 계획으로 해당 구간의 내부 비용을 확인한다.

코드 예시 · text

주문 확정 1건의 임계 경로
요청 수신 15ms
  ├─ 회원 조회 20ms
  ├─ 상품 반복 조회 8ms × 12회 = 96ms
  ├─ 할인 계산 7ms
  ├─ 결제 승인 420ms
  └─ 동기 알림 발송 310ms
전체 관찰 약 868ms + 대기/직렬화 비용

이 예에서 CPU 미세 최적화보다 반복 조회 제거와 알림을 임계 경로에서 분리할 가능성을 먼저 검토한다. 단, 결제와 알림의 업무 일관성 요구를 확인하지 않고 비동기로 바꾸면 안 된다.

4.4 자원별 병목 가설 세우기

  • CPU: 특정 함수의 높은 샘플 비중, 불필요한 직렬화, 비효율 알고리즘, 과도한 암호화·압축을 본다.
  • 메모리: 할당 속도, 오래 살아남는 객체, 회수 정지, 캐시 무제한 증가, 누수를 본다.
  • 데이터베이스: 느린 쿼리, 실제·예상 행 수 차이, 전체 스캔, 정렬, 잠금 대기, 반복 질의를 본다.
  • I/O: 디스크 지연, 작은 파일 반복, 동기 로그, 네트워크 왕복을 본다.
  • 동시성: 잠금 경합, 스레드·연결 풀 대기, 공유 자원 임계 구역을 본다.
  • 외부 의존성: 호출 시간 분포, 시간 초과, 재시도 증폭, 연결 설정 비용을 본다.
  • 큐: 생산 속도와 소비 속도 차이, 오래된 메시지, 재처리 폭주를 본다.

상관관계만으로 원인을 확정하지 않는다. CPU 상승과 지연이 함께 발생해도 CPU는 긴 요청의 결과일 수 있다. 한 번에 한 가설을 변경하거나 통제된 실험으로 원인 관계를 검증한다.

4.5 포화와 회복 확인

부하를 낮춘 뒤 큐와 응답시간이 정상으로 돌아오는지, 연결·메모리가 회수되는지 확인한다. 요청 제한이나 빠른 실패 정책이 하류를 보호하는지, 재시도가 동시에 몰려 장애를 연장하지 않는지도 본다. 성능은 최고 처리량뿐 아니라 과부하에서 예측 가능하게 실패하고 회복하는 능력을 포함한다.

5. 코드 조정으로 성능 개선

코드 수준 개선은 프로파일이나 호출 자료로 실제 고비용 구간을 확인한 뒤 시행한다.

5.1 알고리즘과 자료구조

반복문 안에서 전체 목록을 다시 탐색하는 구조는 데이터 증가에 따라 급격히 느려질 수 있다. 키 조회가 많다면 요구 순서와 중복 정책을 확인한 뒤 적합한 색인 구조를 사용한다.

코드 예시 · text

개선 전
for each orderItem:
    scan all products to find matching productId

개선 후보
productById = buildMap(products)
for each orderItem:
    product = productById[orderItem.productId]

메모리를 더 쓰므로 데이터 규모와 수명, 중복 키 처리 기준을 검토한다. 계산 복잡도가 좋아 보여도 작은 데이터에서는 구축 비용이 더 클 수 있으므로 대표 조건에서 측정한다.

5.2 불필요한 작업과 할당 제거

같은 값을 요청 안에서 반복 파싱·직렬화하거나 사용하지 않는 전체 객체를 만드는 작업을 줄인다. 큰 문자열 연결, 불필요한 복사, 과도한 로그도 후보이다. 다만 로그를 제거해 관찰성을 잃거나 객체 재사용으로 동시성 오류를 만들지 않도록 한다.

5.3 일괄 처리와 집합 연산

반복 호출을 묶어 네트워크 왕복과 고정 비용을 줄인다. DB의 행별 조회를 한 번의 집합 조회로 바꾸거나 여러 메시지를 배치 처리할 수 있다. 배치가 너무 크면 메모리, 잠금 시간, 실패 복구 단위가 커지므로 크기와 오류 정책을 측정으로 정한다.

5.4 캐시

변경이 드물고 읽기가 많으며 오래된 값 허용 범위가 명확한 데이터에 유용하다. 키, 유효 기간, 무효화, 용량, 일관성, 장애 시 원본 보호를 설계해야 한다. 캐시는 느린 쿼리를 숨기는 만능책이 아니며 잘못된 값의 장기 노출과 동시 만료 폭주를 만들 수 있다.

07

6. 아키텍처 조정으로 성능 개선

코드 한 곳의 최적화로 해결되지 않거나 경계 자체가 병목이면 아키텍처를 검토한다.

  • 읽기와 쓰기 특성이 크게 다르면 읽기 모델·복제·캐시를 분리할 수 있다.
  • 긴 비핵심 작업은 요구상 허용되는 경우 큐로 분리해 사용자 임계 경로를 줄일 수 있다.
  • 특정 자원만 확장 가능하도록 상태와 책임을 분리할 수 있다.
  • 반복 계산 결과를 사전 계산하거나 배치로 만들 수 있다.
  • 큰 응답은 필요한 필드와 페이지 단위로 제한할 수 있다.
  • 하류 보호를 위해 동시 요청 제한, 제한된 큐, 시간 초과, 차단 정책을 둘 수 있다.

비동기화는 응답이 빨라 보이지만 전체 완료 시간과 일관성 복잡도를 늘릴 수 있다. 작업 수락과 실제 완료를 사용자에게 구분하고, 중복·재처리·보상·관찰을 설계한다. 수평 확장도 공유 DB·잠금·외부 제한이 병목이면 효과가 제한된다. 병목이 이동하는지 전체 경로를 다시 측정한다.

08

7. 호출 순서 조정으로 성능 개선

호출의 의존 관계를 그려 직렬 실행이 꼭 필요한지 판단한다.

코드 예시 · text

개선 전: 회원 조회 → 상품 조회 → 배송비 조회 → 결제 → 알림

의존 분석:
회원 조회 ─┐
상품 조회 ─┼─> 금액 확정 → 결제 → 주문 확정
배송 조회 ─┘                       └─> 알림

서로 독립인 회원·상품·배송 조회를 제한된 동시성으로 병렬 수행하면 임계 경로를 줄일 수 있다. 그러나 공유 자원을 두고 경쟁하거나 하류 호출량을 급증시킬 수 있으므로 연결 풀과 제한을 함께 측정한다. 결제 전에 필요한 검증을 뒤로 미루면 불필요한 승인·취소가 발생하므로 업무 의존성을 성능보다 우선한다.

대표 조정은 다음과 같다.

  • 반복문 안의 원격 호출을 모아서 한 번에 조회한다.
  • 실패 가능성이 높고 값싼 검증을 앞에 두어 비싼 호출을 피한다.
  • 서로 독립인 호출만 제한된 동시성으로 병렬화한다.
  • 사용자 응답에 불필요하고 결과 일관성이 허용하는 작업을 후속 처리로 분리한다.
  • 동일 결과를 여러 하위 모듈이 반복 조회하지 않도록 요청 범위에서 공유한다.

순서를 바꾸면 오류 우선순위, 부수 효과, 보안, 트랜잭션 경계가 바뀔 수 있다. 성능 수치만 좋아지고 실패 시 데이터가 깨지면 개선이 아니다.

09

8. 개선 검증과 산출물

변경 후에는 기준선과 같은 빌드 외 조건, 부하 모형, 데이터, 준비·측정 구간에서 다시 실행한다. 여러 변경을 한꺼번에 넣으면 기여도를 알기 어려우므로 가능한 한 가설 단위로 비교한다.

8. 개선 검증과 산출물 · 학습 표 3
검증 항목질문
목표요구된 업무의 지연·처리량·오류가 개선됐는가
자원병목 자원의 대기·포화가 줄었는가
이동다른 DB·외부 서비스·큐로 병목이 옮겨갔는가
기능계산, 상태, 권한, 메시지 효과가 그대로 맞는가
안정성지속 부하에서 누수·연결 고갈이 없는가
과부하한계에서 안전하게 실패하고 회복하는가
비용자원·운영 복잡도 증가가 효과에 비례하는가

성능 분석 보고서에는 목표, 시나리오, 환경·빌드, 데이터, 부하 단계, 측정 구간, 원시 결과 위치, 지표 그래프, 병목 증거, 가설, 변경, 전후 결과, 기능 회귀, 한계와 다음 조치를 담는다. 화면 캡처 하나보다 재실행할 수 있는 조건과 수치의 정의가 중요하다.

10

9. 구체 업무 시나리오: 주문 상세 지연

주문 상세의 상위 백분위 지연이 목표를 넘었다고 하자. 추적 결과 주문 항목 30개 각각에 대해 상품 API를 호출하고, 모든 호출이 직렬로 실행되었다. CPU는 낮고 외부 호출 시간이 전체의 대부분이었다.

가설은 “상품 ID를 모아 일괄 조회하면 왕복 횟수와 임계 경로가 줄어든다”이다. 일괄 계약이 실제로 지원되는지, 응답 크기와 일부 상품 누락 처리, 권한을 확인한다. 변경 전후에 같은 주문 크기 분포와 외부 지연 조건을 사용한다. 평균뿐 아니라 상위 지연, 외부 호출 수, 응답 크기, 오류율을 비교한다. 작은 주문과 큰 주문, 일부 상품 조회 실패, 반복 실행의 캐시 상태도 분리한다.

만약 일괄 응답이 너무 커 메모리와 네트워크가 증가하면 페이지 또는 필요한 필드만 조회하는 대안을 검토한다. 단순히 호출 수가 줄었다고 성공 판정하지 않고 사용자 응답과 전체 자원·정확성을 함께 본다.

11

10. 실기 체크리스트와 자주 틀리는 함정

  • 목표 업무와 승인된 성능 기준이 판정 가능하게 정의되었는가?
  • 평균뿐 아니라 지연 분포, 처리량, 오류, 자원·대기를 함께 보는가?
  • 대상·발생기·외부 연계·데이터·캐시 조건이 기록되었는가?
  • 준비·측정·회복 구간과 실패 포함 여부가 명확한가?
  • 낮은 부하부터 단계적으로 포화 지점을 찾았는가?
  • 요청 경로를 분해하고 상관관계가 아닌 실험으로 병목을 확인했는가?
  • 프로파일 없이 눈에 띄는 코드를 먼저 고치지 않았는가?
  • 병렬화·캐시·비동기화의 일관성·복구·운영 비용을 검토했는가?
  • 같은 조건에서 전후를 비교하고 병목 이동을 확인했는가?
  • 기능·보안·데이터 정합성과 지속·과부하 회귀를 수행했는가?

자주 틀리는 함정은 평균만 비교하는 것, 부하 발생기 포화를 대상 병목으로 보는 것, CPU가 낮으면 병목이 없다고 판단하는 것, 캐시가 따뜻한 한 번의 결과를 일반화하는 것, 여러 최적화를 동시에 적용해 원인을 잃는 것이다. 또한 비동기화로 사용자 응답만 줄이고 실제 완료 실패를 숨기거나, 호출 병렬화로 하류 서비스를 포화시키는 오류가 흔하다.

12

확인 문제

문제 1

평균 응답시간만으로 성능을 판단하면 안 되는 이유를 쓰시오.

문제 2

부하 테스트와 스트레스 테스트의 목적 차이를 설명하시오.

문제 3

성능 전후 비교에서 반드시 같게 통제하거나 기록해야 할 조건 다섯 가지를 쓰시오.

문제 4

CPU 사용률이 낮은데 응답이 느릴 수 있는 원인 네 가지를 쓰시오.

문제 5

부하 발생기 포화를 어떻게 식별하고 대응하는지 설명하시오.

문제 6

반복 원격 호출을 일괄 호출로 바꿀 때 확인할 부작용 세 가지를 쓰시오.

문제 7

서로 독립적인 호출을 병렬화하기 전에 판단해야 할 조건을 쓰시오.

문제 8

비동기 처리로 사용자 응답을 단축할 때 추가로 설계할 항목 네 가지를 쓰시오.

문제 9

성능 개선 후 병목 이동을 확인해야 하는 이유를 설명하시오.

문제 10

성능 분석 보고서에 포함할 핵심 항목 여섯 가지를 쓰시오.

13

정답과 해설

정답 1

소수의 매우 느린 요청이 평균에 가려질 수 있고 실패 요청 제외 여부에 따라 값이 왜곡되기 때문이다. 중앙값과 상위 백분위, 오류율, 표본과 구간을 함께 본다.

정답 2

부하 테스트는 예상 업무량에서 요구 충족을 확인한다. 스트레스 테스트는 예상 한계를 넘어 포화 지점, 실패 형태, 보호와 회복 행동을 찾는다.

정답 3

대상 빌드·구성, 자원·노드 수, 업무 비율·동시성, 데이터 규모·분포, 캐시 상태, 외부 지연 규칙, 준비·측정 구간 중 다섯 가지이다.

정답 4

외부 API 대기, DB 잠금·연결 풀 대기, 디스크·네트워크 I/O, 큐 대기, 동기화 잠금 중 네 가지이다. CPU가 일을 못 하고 기다리는 상황이다.

정답 5

발생기의 CPU·메모리·네트워크·연결 수와 자체 요청 생성 지연을 함께 관찰한다. 포화되면 발생기를 분산하거나 시나리오 비용을 줄여 대상에 계획한 부하가 실제 도달하게 한다.

정답 6

응답 크기와 메모리 증가, 일부 항목 실패 처리, 하류의 배치 크기 제한·잠금, 권한과 순서 유지 중 세 가지를 확인한다.

정답 7

호출 간 데이터·업무 의존성이 없어야 하고, 공유 자원 경합과 하류 허용 부하를 확인해야 하며, 일부 실패 시 취소·결과 조합 규칙이 정의되어야 한다.

정답 8

작업 수락과 완료 상태 구분, 중복·멱등 처리, 실패 재처리·보상, 진행 상태 관찰·알림, 큐 포화 보호 중 네 가지를 설계한다.

정답 9

한 구간의 비용을 줄이면 DB, 네트워크, 다른 서비스나 큐가 새로운 제한점이 될 수 있기 때문이다. 사용자 목표와 전체 자원 기준으로 다시 측정해야 한다.

정답 10

목표와 시나리오, 환경·빌드, 데이터·부하 모형, 측정 구간·지표 정의, 병목 증거와 가설, 변경 내용, 전후 결과, 기능·안정성 회귀, 한계·다음 조치 중 여섯 가지이다.

14

핵심 요약

  • 테스트로 성능 분석과 저하요인 발견을 하려면 승인된 목표, 대표 부하, 재현 가능한 환경·데이터, 지연 분포·처리량·오류·자원 지표가 필요하다.
  • 부하·스트레스·급증·지속·용량 테스트는 목적이 다르며 낮은 부하에서 포화와 회복까지 단계적으로 관찰한다.
  • 추적, 프로파일, 실행 계획으로 요청 경로를 분해하고 통제된 실험으로 병목 가설을 검증한다.
  • 코드·아키텍처·호출순서 조정으로 성능 개선할 때 알고리즘, 일괄 처리, 캐시, 비동기화, 병렬화의 정확성·복구·운영 비용을 함께 판단한다.
  • 개선 전후는 같은 조건에서 비교하고 평균뿐 아니라 상위 지연, 처리량, 오류, 자원과 병목 이동을 확인한다.
  • 성능 수치가 좋아져도 기능·보안·데이터 일관성·과부하 회복성이 나빠지면 올바른 개선이 아니다.
