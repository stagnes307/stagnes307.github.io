# 1-7-3-2. 소스코드 품질 분석 도구로 성능 개선

## 출제 범위와 수행 목표

이 레슨은 **소스코드 품질 분석 도구로 성능 개선**하는 방법을 다룬다. 정적 분석의 복잡도·중복 후보와 동적 프로파일의 CPU·메모리·잠금·I/O 증거를 연결해 병목을 고친다. **애플리케이션 성능 개선하기의 적용 절차와 판단 기준**에서는 목표, 기준선, 분석, 개선, 재측정과 회귀를 하나의 절차로 정리한다.

제품별 메뉴·임계값보다 도구 유형, 입력·출력, 해석 원리와 판단 기준을 이해해야 한다. 학습 후에는 다음을 수행할 수 있어야 한다.

- 정적 품질 분석과 동적 성능 분석의 차이와 상호 보완 관계를 설명한다.
- 복잡도, 중복, 자원 미반환, 호출 그래프, 핫스팟, 할당, 잠금 정보를 해석한다.
- 코드 냄새와 측정된 성능 병목을 구분하고 우선순위를 정한다.
- 분석 도구의 오탐, 계측 오버헤드, 표본 편향과 민감정보 위험을 통제한다.
- 작은 검증 가능한 변경을 적용하고 같은 조건에서 성능·기능·유지보수성을 재검증한다.
- 성능 개선의 전체 적용 절차와 산출물 체크리스트를 작성한다.

## 1. 품질 분석 결과는 결론이 아니라 단서다

정적 분석 도구는 실행 없이 소스와 의존 관계를 검사해 복잡한 조건, 중복, 자원 미반환, 잠재 오류를 찾는다. 넓은 범위를 반복 검사할 수 있지만 실제 입력 빈도, 외부 지연과 데이터 분포를 알 수 없다.

동적 분석 도구는 실행 중 시간과 자원 사용을 관찰한다. CPU 프로파일러, 메모리·할당 프로파일러, 잠금·스레드 분석, I/O·네트워크 추적, 애플리케이션 요청 추적이 여기에 속한다. 실제 경로의 비용을 보여 주지만 수행하지 않은 경로는 보지 못하고 계측 자체가 결과에 영향을 줄 수 있다.

| 분석 종류 | 대표 입력 | 대표 출력 | 강점 | 한계 |
|---|---|---|---|---|
| 정적 규칙 분석 | 소스·설정 | 규칙 위반 위치·설명 | 실행 전 넓은 검사 | 실제 병목 여부를 확정 못함 |
| 복잡도·중복 분석 | 제어 구조·토큰 | 복잡도, 중복 블록 | 변경·테스트 위험 후보 | 성능 비용과 일대일 대응 아님 |
| CPU 프로파일 | 대표 실행 | 함수별 표본·호출 관계 | 계산 핫스팟 식별 | 대기 원인은 별도 분석 필요 |
| 메모리 분석 | 객체·할당·회수 | 할당률, 보유 객체, 참조 | 누수·회수 압력 후보 | 스냅샷 시점과 부하에 민감 |
| 잠금·동시성 분석 | 스레드·락 사건 | 대기, 경합, 교착 후보 | 동시 처리 지연 원인 | 재현 가능한 동시성 필요 |
| 추적·APM | 요청·DB·외부 호출 | 구간별 시간·오류 | 분산 경로와 대기 파악 | 표본·상관 ID·비용 주의 |

정적 도구의 “복잡도 높음”이 곧 병목은 아니다. 드물게 실행될 수 있고, 짧은 함수도 반복 호출·원격 I/O로 병목이 된다. 정적 결과로 후보를 찾고 대표 부하의 동적 결과로 우선순위를 검증한다.

## 2. 주요 품질 지표와 성능의 관계

### 2.1 복잡도

분기와 경로가 많은 코드는 이해·테스트가 어렵고 비효율 분기가 숨어 있을 가능성이 있다. 그러나 복잡도 수치가 높다고 실행 시간이 반드시 길지는 않는다. 모든 분기가 실행되는지, 빈도가 높은 경로가 무엇인지 프로파일과 결합한다. 복잡한 함수를 작은 함수로 나누면 읽기성은 좋아질 수 있지만 실제 연산량은 같을 수 있다.

### 2.2 중복 코드

같은 변환·조회·검증이 여러 곳에 복제되면 수정 누락과 불필요한 반복 계산 가능성이 높아진다. 공통화하면 캐시나 일괄 처리 같은 개선을 한 곳에 적용하기 쉬워진다. 그러나 우연히 비슷해 보이는 서로 다른 업무 규칙을 억지로 합치면 조건 분기와 결합도가 늘어난다. 변화 이유가 같은지 확인한다.

### 2.3 자원 생명주기

파일, 네트워크 연결, DB 결과, 잠금이 예외 경로에서 반환되지 않으면 시간이 지나 연결 고갈과 지연을 만든다. 정적 분석은 닫힘 누락 후보를 찾고, 지속 테스트와 자원 지표는 실제 누적을 확인한다. 단순한 메모리 사용 증가도 캐시의 정상 적재인지 누수인지 시간에 따른 회수·상한으로 구분한다.

### 2.4 잠재 오류와 방어 코드

반복적인 예외 생성, 실패 후 즉시 무제한 재시도, 루프 내부 로깅, 널 처리 때문에 같은 작업을 다시 하는 코드가 성능에 영향을 줄 수 있다. 보안 검사나 검증을 성능을 이유로 제거해서는 안 된다. 중복 검증을 합리화하되 신뢰 경계마다 필요한 검증을 유지한다.

## 3. 동적 프로파일 결과 읽기

### 3.1 CPU 시간과 벽시계 시간

CPU 시간은 실제 계산에 소비한 시간이고 벽시계 시간은 대기를 포함한 경과 시간이다. 함수의 벽시계 시간은 크지만 CPU 표본이 적다면 DB, 락, 네트워크를 기다릴 가능성이 있다. 반대로 CPU 표본이 집중되면 알고리즘·직렬화·압축 같은 계산 후보를 본다.

호출 트리에서 **포괄 시간**은 하위 호출 시간을 포함하고, **자체 시간**은 함수 내부에 직접 소비된 시간을 뜻한다. 상위 요청 함수의 포괄 시간이 큰 것은 자연스러울 수 있다. 자체 시간이 큰 하위 함수 또는 반복 호출 횟수가 비정상적인 구간을 찾는다.

```text
checkout()              포괄 920ms / 자체 12ms
 ├─ loadItems()         포괄 280ms / 자체 18ms / 호출 1
 │   └─ loadProduct()   포괄 250ms / 자체 20ms / 호출 25
 ├─ calculate()         포괄  35ms / 자체 31ms / 호출 1
 ├─ authorizePayment()  포괄 410ms / 자체  9ms / 호출 1
 └─ sendNotice()        포괄 170ms / 자체  6ms / 호출 1
```

이 자료는 `loadProduct()` 반복과 외부 결제·알림 대기를 후보로 보여 준다. `calculate()` 자체 시간 최적화만으로 전체 개선은 제한적이다. 호출 횟수를 일괄화할 수 있는지, 알림이 임계 경로에 필요한지 요구사항을 확인한다.

### 3.2 표본 방식과 계측 방식

표본 프로파일은 일정 시점의 실행 위치를 수집해 상대적으로 오버헤드가 낮지만 짧고 드문 호출을 놓칠 수 있다. 계측 방식은 함수 진입·종료를 자세히 기록해 호출 횟수와 시간을 얻지만 실행 특성을 더 바꿀 수 있다. 먼저 낮은 오버헤드 방식으로 후보를 찾고 필요한 구간만 상세 계측하는 접근이 유용하다.

### 3.3 메모리·할당

현재 사용량 한 점보다 시간에 따른 할당률, 회수 후 남는 메모리, 객체 유형과 보유 경로를 본다. 높은 할당률은 잦은 회수와 정지 시간을 만들 수 있고, 오래된 객체가 계속 늘면 누수 가능성이 있다. 스냅샷 두 개를 비교할 때 같은 부하 단계와 준비 상태여야 한다.

### 3.4 잠금과 스레드

잠금 보유 시간, 대기 스레드 수, 경쟁 위치, 호출 경로를 본다. 동시성 문제는 단일 사용자 프로파일로 재현되지 않을 수 있다. 공유 임계 구역을 줄이거나 잠금 범위를 바꿀 때는 데이터 경쟁과 순서 보장을 다시 검증한다. 잠금을 제거해 빨라졌지만 값이 유실되면 올바른 개선이 아니다.

### 3.5 I/O와 외부 호출

DB 쿼리 수, 각 지연 분포, 반환 행 수, 실행 계획, 네트워크 왕복, 재시도 수를 연결한다. “DB 시간이 길다”만으로 인덱스를 추가하지 않는다. 잘못된 쿼리 형태, 과도한 호출 횟수, 잠금, 통계, 큰 결과 전송 중 어떤 요인인지 확인한다.

## 4. 도구 선택과 안전한 사용

도구는 다음 판단 기준으로 선택한다.

- 대상 언어·런타임·빌드 방식과 호환되는가?
- CPU, 메모리, 잠금, I/O 중 현재 가설에 필요한 데이터를 주는가?
- 운영과 유사한 환경에서 감당할 수 있는 오버헤드인가?
- 호출 관계와 상관 ID를 유지해 요청 단위 분석이 가능한가?
- 결과를 비교·내보내고 자동화할 수 있는가?
- 개인정보, 쿼리 인자, 헤더, 본문을 수집할 때 마스킹·접근 통제가 가능한가?
- 팀이 결과를 재현하고 해석할 수 있는 문서와 책임자가 있는가?

프로파일에 사용자 토큰, SQL 리터럴, 개인 식별 정보가 들어갈 수 있다. 수집 범위를 최소화하고 비식별화, 접근 권한, 보존 기간을 정한다. 운영 환경에서 상세 계측을 무단으로 켜면 성능과 안정성에 영향을 줄 수 있으므로 통제된 환경에서 먼저 수행하고, 운영 관찰은 승인된 낮은 오버헤드·표본 설정을 사용한다.

정적 분석 규칙에는 기준선과 예외 정책이 필요하다. 신규·변경 코드의 심각한 문제부터 통제하고 기존 부채는 위험 순으로 계획한다. 예외에는 이유, 책임자와 재검토 조건을 남긴다.

## 5. 소스코드 품질 분석 도구로 성능 개선 절차

### 단계 1: 문제와 측정 목표 정의

느린 업무, 영향을 받는 사용자, 승인된 지연·처리량·오류 기준과 측정 조건을 정한다. “코드 품질을 개선한다”보다 “대표 주문 확정 부하에서 상위 지연 원인을 식별하고 목표를 검증한다”처럼 쓴다.

### 단계 2: 재현 가능한 기준선 수집

빌드, 환경, 데이터 분포, 부하, 캐시, 외부 응답, 측정 구간을 고정하고 성능·기능 결과를 저장한다. 분석 도구를 켜기 전과 후의 차이로 오버헤드를 확인한다.

### 단계 3: 정적 분석으로 후보 좁히기

변경 영역과 호출 경로에서 복잡한 반복, 중복 조회, 자원 누락, 과도한 변환, 위험한 동시성 후보를 찾는다. 규칙 설명과 해당 코드의 업무 빈도를 함께 본다. 모든 경고를 성능 결함으로 분류하지 않는다.

### 단계 4: 동적 분석으로 병목 확인

대표 부하에서 요청 추적, CPU·할당·잠금·I/O 프로파일을 수집한다. 호출 횟수, 자체·포괄 시간, 대기, 자원 포화와 사용자 지연을 상관시킨다. 한 번의 느린 요청만이 아니라 분포와 재현성을 본다.

### 단계 5: 원인 가설과 개선 대안 작성

“상품 조회가 반복 호출되어 네트워크 왕복이 지연의 대부분을 차지한다”처럼 관찰→가설→예상 효과를 연결한다. 일괄 조회, 요청 범위 캐시, 데이터 모델 조정 등 대안을 정확성·복잡도·메모리·하류 부하·운영 위험으로 비교한다.

### 단계 6: 최소 변경과 코드 품질 검증

선택한 대안을 작은 단위로 적용한다. 정적 분석과 단위·통합 테스트로 새 오류, 복잡도 증가, 자원 누락, 동시성 위험이 없는지 확인한다. 경고를 없애기 위한 억지 코드보다 의도가 드러나는 구조를 선택한다.

### 단계 7: 동일 조건 재측정

기준선과 같은 조건에서 응답시간 분포, 처리량, 오류, 자원, 호출 횟수를 비교한다. 측정 변동을 고려해 반복하고 원시 자료를 보존한다. 목표 구간만 빨라지고 다른 업무·하류가 느려지지 않았는지 본다.

### 단계 8: 회귀·기준선·지식 환류

기능, 데이터 정합성, 보안, 지속 부하, 과부하 회복을 검증한다. 개선 결과와 한계를 문서화하고 새로운 성능 기준선, 분석 규칙, 회귀 시나리오를 갱신한다. 효과가 없으면 가설을 폐기하거나 조건을 재검토한다.

## 6. 구체 코드 예시 1: 반복 조회

다음 의사코드는 주문 항목마다 저장소를 호출한다.

```text
function enrich(items):
    result = []
    for item in items:
        product = repository.findById(item.productId)
        result.add(merge(item, product))
    return result
```

정적 분석은 반복문 내부의 외부 자원 호출을 후보로 표시할 수 있다. 동적 추적에서 항목 수에 비례해 쿼리 호출이 증가하고 대기가 전체 지연의 큰 비중을 차지한다면 일괄 조회를 검토한다.

```text
function enrich(items):
    ids = distinct(item.productId for item in items)
    productById = repository.findAllByIds(ids).indexById()
    return [merge(item, productById[item.productId]) for item in items]
```

검증 항목은 중복 ID, 없는 상품, 결과 순서, 권한 필터, 허용되는 일괄 크기, 큰 응답의 메모리다. 호출 수 감소만 보지 않고 같은 데이터와 오류 의미가 유지되는지 확인한다.

## 7. 구체 코드 예시 2: 불필요한 객체와 문자열

루프마다 큰 문서를 직렬화해 로그 문자열을 만들지만 해당 로그 수준이 비활성인 경우에도 비용이 발생할 수 있다.

```text
개선 전:
for record in records:
    debug("record=" + serialize(record))

개선 후보:
if debugEnabled:
    for record in records:
        debug("recordId={}, state={}", record.id, record.state)
```

정적 규칙이 비싼 문자열 생성을 알려 줄 수 있고 CPU·할당 프로파일이 반복 비용을 확인한다. 그러나 진단에 필요한 정보를 모두 없애지는 않는다. 개인 정보 원문 대신 식별 가능한 비민감 키와 상태를 남기고, 장애 재현 가능성과 성능의 균형을 잡는다.

## 8. 실기 적용 판단 매트릭스: 무엇을 먼저 고칠 것인가

| 후보 | 실행 빈도 | 사용자 지연 기여 | 위험 | 판단 |
|---|---:|---:|---|---|
| 드문 관리자 함수의 높은 복잡도 | 낮음 | 미측정·낮음 | 유지보수 위험 | 별도 리팩터링 후보, 성능 우선 아님 |
| 주문별 상품 조회 30회 | 높음 | 추적에서 큼 | 계약·메모리 검토 필요 | 성능 우선 실험 |
| 작은 계산 함수의 자체 시간 3ms | 높음 | 전체 대비 작음 | 변경 위험 낮음 | 큰 후보 뒤에 검토 |
| 연결 미반환 후보 | 부하 증가 시 누적 | 지속 시험에서 큼 | 장애 위험 높음 | 즉시 원인 확인·수정 |
| 전역 캐시 도입 | 예상 효과 큼 | 아직 미측정 | 일관성·용량 위험 큼 | 단순 대안 검증 후 판단 |

우선순위는 경고 심각도만이 아니라 실제 실행 빈도, 사용자 지연 기여, 실패 영향, 수정 위험, 검증 가능성으로 정한다. 빠른 작은 개선과 구조적 개선을 나누어 로드맵을 만들 수 있다.

## 9. 분석 결과의 함정과 오류 대응

1. **프로파일러 순위 첫 항목을 바로 고친다.** 상위 포괄 함수일 뿐 자체 비용은 작을 수 있다.
2. **정적 경고를 성능 측정으로 오해한다.** 후보를 동적 증거로 검증해야 한다.
3. **한 번의 실행만 비교한다.** 준비 상태와 잡음 때문에 반복·분포가 필요하다.
4. **계측 오버헤드를 무시한다.** 도구를 켠 조건과 끈 조건의 차이를 확인한다.
5. **대표하지 않는 입력을 사용한다.** 작은 데이터·한 사용자에서 병목이 드러나지 않을 수 있다.
6. **호출 횟수만 줄이면 성공이라 본다.** 응답 크기·메모리·하류 잠금이 증가할 수 있다.
7. **성능을 위해 검증·보안·로그를 제거한다.** 신뢰 경계와 운영 관찰을 유지해야 한다.
8. **코드 냄새를 모두 한 번에 수정한다.** 효과 기여도와 회귀 원인을 잃는다.
9. **오탐을 무기한 무시한다.** 예외 이유·책임자·재검토 조건을 기록한다.
10. **도구 수집 자료에 민감정보를 남긴다.** 최소 수집·마스킹·접근·보존 정책이 필요하다.

도구 결과가 다르면 샘플링 구간, 빌드, 부하, 시계 등 측정 조건을 먼저 비교한다. 간헐 문제는 낮은 오버헤드 추적으로 후보를 찾고 해당 구간만 상세 분석한다. 결과와 설정은 보고서에 연결한다.

## 10. 산출물 체크리스트

- 성능 문제와 목표 업무·지표가 명확한가?
- 기준선의 빌드·환경·데이터·부하·측정 구간이 기록되었는가?
- 정적 분석 규칙과 예외 정책, 도구 버전·설정이 보존되었는가?
- 동적 프로파일이 대표 경로와 충분한 표본을 포함하는가?
- 자체/포괄 시간, 호출 횟수, 대기와 자원 정보를 구분했는가?
- 정적 후보와 동적 병목을 같은 코드·요청 경로로 연결했는가?
- 원인 가설과 대안별 예상 효과·위험이 작성되었는가?
- 변경을 작은 단위로 적용하고 정적·기능 검사를 통과했는가?
- 동일 조건에서 전후 지표와 병목 이동을 비교했는가?
- 개인정보, 계측 오버헤드, 한계, 기준선·회귀 갱신을 기록했는가?

## 확인 문제

### 문제 1
정적 품질 분석만으로 실제 성능 병목을 확정할 수 없는 이유를 쓰시오.

### 문제 2
호출 프로파일의 포괄 시간과 자체 시간의 차이를 설명하시오.

### 문제 3
벽시계 시간은 큰데 CPU 시간이 작은 함수에서 의심할 요인 네 가지를 쓰시오.

### 문제 4
표본 프로파일과 계측 프로파일의 장단점을 각각 쓰시오.

### 문제 5
메모리 사용량 한 번의 스냅샷만으로 누수를 판정하면 안 되는 이유를 쓰시오.

### 문제 6
정적 분석 경고의 개선 우선순위를 정할 판단 요소 네 가지를 쓰시오.

### 문제 7
반복 저장소 조회를 일괄 조회로 바꾼 뒤 기능적으로 확인할 항목 네 가지를 쓰시오.

### 문제 8
상세 프로파일링 도구를 운영 환경에 무단 적용하면 안 되는 이유 두 가지를 쓰시오.

### 문제 9
애플리케이션 성능 개선하기의 적용 절차를 여덟 단계로 요약하시오.

### 문제 10
성능 개선 결과가 목표를 만족해도 기준선과 회귀 시나리오를 갱신해야 하는 이유를 설명하시오.

## 정답과 해설

### 정답 1
정적 분석은 실제 입력 빈도, 데이터 분포, 런타임 최적화, 외부·잠금 대기를 관찰하지 못하기 때문이다. 경고는 후보이며 대표 실행의 프로파일과 성능 지표로 기여도를 확인한다.

### 정답 2
포괄 시간은 해당 함수와 그 하위 호출에 든 시간을 합친 값이고, 자체 시간은 함수 본문에 직접 소비된 시간이다. 상위 함수의 포괄 시간이 크다고 그 본문이 병목인 것은 아니다.

### 정답 3
DB·네트워크 I/O, 잠금, 스레드·연결 풀, 외부 서비스, 큐 대기 중 네 가지를 의심할 수 있다.

### 정답 4
표본 방식은 오버헤드가 비교적 낮고 전체 후보를 찾기 좋지만 짧고 드문 호출을 놓칠 수 있다. 계측 방식은 호출 횟수와 상세 시간을 얻기 좋지만 실행 특성을 더 바꿀 수 있다.

### 정답 5
캐시의 정상 적재와 누수를 구분할 수 없고 부하·회수 시점에 따라 값이 달라지기 때문이다. 동일 조건에서 시간에 따른 할당, 회수 후 잔류, 객체 유형과 보유 경로를 본다.

### 정답 6
실제 실행 빈도, 사용자 지연 기여, 실패 영향, 수정·회귀 위험, 개선 검증 가능성 중 네 가지를 본다. 규칙의 심각도만으로 정하지 않는다.

### 정답 7
중복 ID 처리, 없는 항목 처리, 결과 순서, 권한 필터, 오류 의미, 일괄 크기 경계 중 네 가지를 확인한다.

### 정답 8
계측 오버헤드가 지연과 안정성을 바꿀 수 있고 요청 인자·토큰·SQL 등에 민감정보가 수집될 수 있기 때문이다. 승인된 범위·표본·마스킹과 접근 통제가 필요하다.

### 정답 9
문제·목표 정의, 재현 가능한 기준선, 정적 후보 분석, 동적 병목 확인, 원인 가설·대안 작성, 최소 변경·품질 검증, 동일 조건 재측정, 회귀·기준선·지식 환류 순이다.

### 정답 10
후속 변경이 성능을 다시 악화시키는 것을 자동으로 탐지하고, 새 결과를 비교 기준으로 삼으며, 개선의 조건과 한계를 팀 지식으로 유지하기 위해서다.

## 핵심 요약

- **소스코드 품질 분석 도구로 성능 개선**할 때 정적 분석은 넓은 후보를, 동적 프로파일은 대표 실행의 실제 비용을 제공한다.
- 복잡도·중복·자원 경고는 병목의 확정 증거가 아니며 실행 빈도와 사용자 지연 기여를 연결해야 한다.
- CPU의 자체·포괄 시간, 메모리 할당·보유, 잠금 대기, I/O·외부 호출과 호출 횟수를 구분해 해석한다.
- 오탐, 표본 편향, 계측 오버헤드, 민감정보 수집을 통제하고 도구 설정과 결과를 보존한다.
- **애플리케이션 성능 개선하기의 적용 절차와 판단 기준**은 목표, 기준선, 정적 후보, 동적 확인, 가설·대안, 최소 변경, 재측정, 회귀·환류로 이어진다.
- 같은 조건의 전후 비교와 기능·보안·정합성 검증을 통과해야 성능 개선으로 인정할 수 있다.
