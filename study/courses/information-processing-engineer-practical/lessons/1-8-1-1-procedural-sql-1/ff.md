# 1-8-1-1. 프로시저와 호출문 작성 · 사용자 정의함수와 호출 쿼리 작성

## 출제 범위와 수행 목표

이 레슨은 **프로시저와 호출문 작성**, 그리고 질의식에서 재사용할 **사용자 정의함수와 호출 쿼리 작성**을 다룬다. 다음 범위인 트리거는 제외하고 선언, 매개변수, 제어 흐름, 호출, 반환, 예외·권한·테스트에 집중한다.

DBMS마다 호출·예외·함수 문법이 다르다. 아래는 개념용 의사 SQL이며 실제로는 문제에 제시된 문법을 따른다.

학습 후에는 다음을 수행할 수 있어야 한다.

- 일반 SQL과 절차형 SQL의 역할 차이를 설명한다.
- 프로시저와 사용자 정의함수의 호출 위치, 반환 방식, 부수 효과 차이를 구분한다.
- 입력·출력·입출력 매개변수와 자료형·널·정밀도를 명세한다.
- 조건·반복·변수·예외 처리를 사용하되 집합 연산을 우선하는 코드를 작성한다.
- 호출문의 인자 순서와 출력값, 트랜잭션 책임을 정확히 검증한다.
- 함수 호출 쿼리에서 행별 반복 비용, 결정성, 널 처리와 권한을 점검한다.

## 1. 절차형 SQL의 목적

일반 SQL은 원하는 데이터 집합을 선언하는 데 강하다. 한 번의 `UPDATE`, `SELECT`, `INSERT`로 표현되는 작업은 대체로 집합 연산으로 처리하는 것이 명확하고 효율적이다. 절차형 SQL은 여러 SQL 문과 조건·반복·예외 처리를 하나의 서버 측 실행 단위로 묶어야 할 때 사용한다.

대표 목적은 여러 변경을 업무 단위로 묶고, 서버 측 작업·계산을 재사용하며, 직접 테이블 권한 대신 제한된 실행 인터페이스를 제공하는 것이다. 그러나 원자성과 보안이 자동 보장되지는 않는다. 트랜잭션·실패 복구·실행 권한을 설계하고 행별 반복보다 집합 연산을 우선한다.

## 2. 프로시저와 사용자 정의함수 비교

| 구분 | 프로시저 | 사용자 정의함수 |
|---|---|---|
| 주 목적 | 업무 절차·여러 SQL 수행 | 입력에 대한 값·테이블 결과 계산 |
| 호출 방식 | 독립 호출문 `CALL` 또는 제품별 방식 | `SELECT`, 조건식, 표현식 등에서 호출 |
| 반환 | 출력 매개변수·결과 집합·상태 등 DBMS 방식 | 선언한 스칼라 값 또는 테이블 값 |
| 부수 효과 | 데이터 변경 가능 여부와 트랜잭션은 제품·설계에 따름 | 데이터 변경 제한이 일반적이나 정확한 범위는 제품 규칙 확인 |
| 최적화 영향 | 독립 실행 단위로 계획됨 | 행마다 호출되면 반복 비용이 커질 수 있음 |
| 대표 예 | 재고 조정, 정산 처리, 일괄 상태 변경 | 금액 계산, 코드 변환, 파생 테이블 |

“값을 반환하면 모두 함수”는 틀리다. 프로시저도 출력 매개변수나 결과 집합을 줄 수 있다. 핵심은 함수가 SQL 표현식 안에서 값처럼 사용되도록 선언되는 반면, 프로시저는 호출문으로 업무 절차를 실행한다는 점이다.

함수는 같은 입력에 같은 결과를 주는 계산에 적합하다. 시각·세션·변경 데이터에 따라 결과가 달라지면 최적화와 재현성에 영향을 준다. 결정성 표기와 데이터 접근은 DBMS 규칙을 확인한다.

## 3. 매개변수와 자료형 설계

### 3.1 입력·출력·입출력 매개변수

- `IN`은 호출자가 값을 전달하고 프로시저가 입력으로 사용한다.
- `OUT`은 프로시저가 계산한 값을 호출자에게 돌려준다.
- `INOUT`은 초기값을 받아 변경된 값을 돌려준다.

제품에 따라 기본 모드와 호출 문법이 다르므로 선언을 명확히 쓰는 것이 좋다. 출력 매개변수는 상태 코드와 사용자 메시지를 한 필드에 섞지 않는다. 호출자가 분기할 안정적인 코드와 표시 메시지를 구분하고, 예외와 업무 거부 중 어떤 방식으로 전달할지 계약을 정한다.

### 3.2 자료형 일치

매개변수 자료형은 연결된 테이블 열과 업무 의미에 맞춘다. 금액에는 통화, 정밀도, 소수 자릿수와 반올림 위치를 정한다. ID를 숫자로 보이는 문자열인데 정수로 받으면 선행 0이나 문자 접두사를 잃을 수 있다. 날짜·시간은 시간대와 끝점 포함 여부를 명세한다.

널은 빈 문자열, 0, “없음” 코드와 다르다. 필수 입력은 본문 초기에 명시적으로 검사하고, 선택 입력은 널일 때의 의미를 정한다. SQL의 널 비교는 `= NULL`이 아니라 `IS NULL`/`IS NOT NULL` 의미를 사용해야 한다.

### 3.3 이름과 기본값

매개변수와 열 이름이 같으면 어떤 값을 가리키는지 모호해질 수 있다. `p_product_id`, `v_available_qty`처럼 역할을 나타내고 테이블 별칭으로 열을 한정한다. 기본값은 호출 편의를 주지만 업무 의미가 모호하거나 새 규칙 적용을 숨길 수 있으므로 안전한 경우에만 사용한다.

## 4. 프로시저와 호출문 작성

### 4.1 작성 절차

1. 프로시저가 책임질 한 가지 업무와 호출자를 정의한다.
2. 입력·출력 계약, 자료형, 널·범위·권한을 정한다.
3. 사전 검증과 현재 상태 조회를 설계한다.
4. 가능한 처리는 집합 SQL로 작성하고 필요한 조건만 절차화한다.
5. 변경 건수와 상태를 확인하여 기대하지 않은 결과를 차단한다.
6. 예외와 업무 거부를 분류하고 트랜잭션 책임을 정한다.
7. 호출문과 정상·경계·동시성·권한 테스트를 함께 작성한다.

### 4.2 예시: 조건부 재고 차감 프로시저

다음은 제품별 문법 차이를 줄인 의사 SQL이다. 음수나 0 수량을 거부하고, 충분한 재고가 있을 때만 한 문장으로 차감한다.

```sql
CREATE PROCEDURE adjust_stock (
    IN  p_product_id VARCHAR(30),
    IN  p_quantity   INTEGER,
    OUT p_result_code VARCHAR(20)
)
BEGIN
    IF p_product_id IS NULL OR p_quantity IS NULL OR p_quantity <= 0 THEN
        SET p_result_code = 'INVALID_INPUT';
    ELSE
        UPDATE product_stock AS s
           SET quantity = s.quantity - p_quantity
         WHERE s.product_id = p_product_id
           AND s.quantity >= p_quantity;

        IF ROW_COUNT_VALUE() = 1 THEN
            SET p_result_code = 'SUCCESS';
        ELSE
            SET p_result_code = 'NOT_AVAILABLE';
        END IF;
    END IF;
END;
```

`ROW_COUNT_VALUE()`는 “직전 문장의 영향 행 수를 얻는 DBMS별 기능”을 나타내는 자리표시자다. 실제 시험·환경의 함수명으로 바꾼다. 먼저 수량을 조회한 뒤 별도 `UPDATE`를 수행하면 두 호출 사이에 다른 트랜잭션이 재고를 바꿀 수 있다. 조건부 `UPDATE`는 현재 값 검증과 변경을 한 문장으로 결합해 경쟁 창을 줄인다. 그러나 재고 정책, 격리 수준, 예약 모델에 따라 추가 잠금이나 버전 검사가 필요할 수 있다.

### 4.3 호출문

호출 방식은 DBMS에 따라 다르지만 개념은 다음과 같다.

```sql
-- 출력 변수를 선언하는 문법은 DBMS별로 다르다.
DECLARE v_result_code VARCHAR(20);

CALL adjust_stock('P-1007', 3, v_result_code);

SELECT v_result_code AS result_code;
```

호출 시 인자의 순서와 자료형, 이름 기반 호출 지원 여부, 출력 변수 바인딩을 확인한다. 문자열을 이어 붙여 호출문을 만들면 SQL 주입과 형 변환 오류가 생길 수 있으므로 애플리케이션은 바인드 매개변수를 사용한다. 프로시저 실행 권한과 내부 테이블 접근 권한은 최소 권한 원칙에 따라 부여한다.

### 4.4 트랜잭션과 예외

프로시저와 호출자 중 누가 트랜잭션을 관리할지 명시한다. 내부의 무조건 커밋은 호출자의 전체 롤백을 막고, 예외를 삼킨 성공 응답은 실패를 숨길 수 있다.

예외 처리는 업무 거부와 시스템 오류를 구분하고, 부분 변경의 롤백·저장점 정책과 호출자 오류 계약을 일관되게 적용한다. 로그에는 비민감 업무 키와 오류 범주를 남기되 내부 SQL·개인정보는 외부 메시지에 노출하지 않는다. 구체 구문은 문제의 DBMS 문법을 따른다.

## 5. 절차 제어와 집합 연산 판단

조건문은 업무 규칙에 따른 분기를 표현하고, 반복문은 행마다 다른 외부적 판단이 필요할 때 사용할 수 있다. 그러나 단순한 일괄 갱신을 커서와 반복문으로 작성하면 행별 처리 비용이 커지고 잠금 시간이 늘 수 있다.

```sql
-- 행별 반복보다 집합 연산이 명확한 예
UPDATE membership AS m
   SET grade = 'INACTIVE'
 WHERE m.last_activity_at < p_cutoff_at
   AND m.grade = 'ACTIVE';
```

반복이 필요한 경우 종료 조건, 빈 결과, 예외 시 커서·자원 정리, 처리 건수, 부분 실패 정책을 명세한다. 반복문이 익숙하다는 이유로 SQL의 집합 처리 장점을 버리지 않는다. 동적 SQL은 식별자나 조건을 유연하게 만들지만 바인드할 수 있는 값과 허용 목록으로 제한할 부분을 구분하며, 입력 문자열을 그대로 결합하지 않는다.

## 6. 사용자 정의함수와 호출 쿼리 작성

### 6.1 스칼라 함수 예시

주문 금액과 할인율을 받아 할인액을 계산한다고 하자. 금액·비율의 정밀도와 반올림 시점을 명세해야 한다.

```sql
CREATE FUNCTION calculate_discount (
    p_amount DECIMAL(15, 2),
    p_rate   DECIMAL(7, 4)
)
RETURNS DECIMAL(15, 2)
BEGIN
    IF p_amount IS NULL OR p_rate IS NULL THEN
        RETURN NULL;
    END IF;

    IF p_amount < 0 OR p_rate < 0 OR p_rate > 1 THEN
        RETURN NULL;
    END IF;

    RETURN ROUND(p_amount * p_rate, 2);
END;
```

범위 밖 입력을 널로 돌려줄지 예외로 처리할지는 요구 계약에 따라 선택한다. 여기서는 예시로 널을 사용했으므로 호출 쿼리는 널을 정상 할인액 0으로 오해하지 않도록 해야 한다. 실제 통화별 소수 자릿수와 반올림 규칙도 별도 요구에 맞춘다.

### 6.2 함수 호출 쿼리

```sql
SELECT o.order_id,
       o.total_amount,
       calculate_discount(o.total_amount, o.discount_rate) AS discount_amount
  FROM orders AS o
 WHERE o.order_status = 'PAYMENT_PENDING';
```

함수는 `SELECT` 목록뿐 아니라 DBMS가 허용하는 조건식·정렬·그룹화 등에서 사용될 수 있다. 다만 많은 행마다 함수를 호출하면 비용이 커지고, 열을 함수로 감싼 조건이 기존 인덱스 활용을 방해할 수 있다. 실행 계획과 호출 횟수를 측정하고 단순 표현식, 조인, 사전 계산, 집합형 함수 등 대안을 검토한다.

### 6.3 테이블 반환 함수의 개념

일부 DBMS는 행 집합을 반환하는 사용자 정의함수를 지원한다. 호출자는 테이블처럼 조인할 수 있다. 스칼라 함수와 선언·호출 문법, 최적화 특성이 다르므로 문제에서 유형을 확인한다. 제품이 지원한다는 가정 없이 함수는 항상 단일 값만 반환한다고 단정해서도 안 된다.

## 7. 함수 설계 판단 기준

### 결정성과 부수 효과

같은 입력에 같은 결과를 주는 함수는 테스트와 최적화가 쉽다. 현재 시각·세션·변경 테이블에 숨게 의존하지 말고 필요한 값을 매개변수로 전달할 수 있는지 검토한다. 허용 범위는 DBMS 규칙을 따르되 질의 평가 중 부수 효과에 의존하지 않는다.

### 널과 오류 계약

함수가 널을 받으면 널을 반환하는지, 기본값을 적용하는지, 오류를 내는지 문서화한다. 잘못된 값과 계산 결과 0을 같은 값으로 반환하면 호출자가 구분할 수 없다. 함수 이름과 반환형만으로 알 수 없는 정책은 주석·계약·테스트에 남긴다.

### 성능과 호출 빈도

한 행에서 빠른 함수도 많은 행에서 반복되거나 내부 조회를 하면 큰 비용이 된다. 실행 계획, 호출 행 수와 함수 비용을 측정하되 동일 규칙 복제로 생길 유지보수 위험도 함께 판단한다.

### 보안

권한 실행 맥락은 DBMS 규칙을 확인한다. 입력을 동적 SQL에 결합하지 않고 필요한 루틴에만 실행 권한을 주며 오류에 내부 구조·원문 데이터를 노출하지 않는다.

## 8. 구체 업무 시나리오: 주문 정산

요구는 “정산 대상 주문의 확정 금액을 계산하고 처리 건수와 합계를 반환한다”이다. 프로시저는 대상 기간과 판매자 ID를 입력받고, 승인된 상태만 집합으로 갱신하며 영향 건수·금액을 출력할 수 있다. 할인·수수료 계산은 순수 계산 함수로 분리할 수 있다.

설계 전 다음을 확정한다.

- 기간 시작·종료의 포함 여부와 시간대
- 판매자 ID의 존재·권한, 널의 의미
- 대상 주문 상태와 이미 정산된 주문의 재호출 처리
- 금액 정밀도, 항목별/총합 반올림 시점
- 동시 실행과 중복 정산을 막는 업무 키·상태 조건
- 부분 실패 시 전체 롤백인지 실패 건 분리인지
- 반환할 처리·건너뜀·실패 건수와 대사 합계

```text
호출 전: 대상 12건, 이미 정산 2건, 금액 합계는 독립 대사표로 계산
호출: settle_orders(p_seller, p_from, p_to, OUT count, OUT amount, OUT code)
확인: 대상 상태, 정산 행, 처리 이력, 출력 건수·합계가 일치
재호출: 동일 범위가 중복 정산되지 않고 계약된 결과 반환
오류: 범위 역전·권한 없음·동시 실행에서 부분 효과가 남지 않음
```

계산은 함수로 재사용하고 데이터 변경·업무 상태 관리는 명시적 프로시저 호출에 둘 수 있다. 최종 분리는 함수의 숨은 조회와 애플리케이션 계층 책임까지 보고 결정한다.

## 9. 테스트와 검증 체크리스트

### 프로시저

- 정상, 널, 형식·범위 경계, 존재하지 않는 ID를 실행했는가?
- 호출 인자 순서·이름·자료형과 출력 변수 바인딩이 맞는가?
- 영향 행 수가 0, 1, 다수일 때 결과가 계약과 일치하는가?
- 동시 호출과 동일 요청 재호출에서 중복 효과가 없는가?
- 중간 SQL 실패 시 트랜잭션·저장점 정책대로 복구되는가?
- 업무 거부와 시스템 예외가 호출자에게 구분되어 전달되는가?
- 실행 권한이 없는 역할과 타 사용자 객체 접근을 거부하는가?
- 로그와 오류에 민감정보·내부 구조가 노출되지 않는가?

### 사용자 정의함수

- 정상·경계·널·부적합 입력의 반환 계약이 명확한가?
- 금액·비율의 자료형, 정밀도, 반올림 결과가 맞는가?
- 같은 입력에 요구한 동일 결과가 나오는가?
- 한 행과 다수 행 호출 결과가 독립 계산 오라클과 일치하는가?
- 호출 쿼리의 별칭과 반환형이 후속 계산에 맞는가?
- 많은 행에서 호출 횟수와 실행 계획이 허용 가능한가?
- 함수 내부의 숨은 조회·상태 의존·부수 효과가 없는가?
- 권한과 오류 메시지가 계약에 맞는가?

## 10. 자주 틀리는 실기 함정

1. 프로시저와 함수 모두 “값을 반환하는 프로그램”이라고만 구분한다. 호출 위치와 업무 역할이 핵심이다.
2. DBMS마다 다른 구분자·예외·호출 문법을 하나의 표준처럼 단정한다.
3. 매개변수와 열 이름을 같게 써 비교 대상이 모호해진다.
4. 널을 0·빈 문자열과 같게 처리하거나 `= NULL`로 비교한다.
5. 금액 정밀도와 반올림 시점을 생략한다.
6. 조회 후 갱신을 분리해 동시 변경 경쟁을 만든다.
7. 프로시저 내부에서 무조건 커밋해 호출자의 트랜잭션을 깨뜨린다.
8. 단순 집합 갱신을 행별 커서·반복문으로 작성한다.
9. 함수 호출을 많은 행에 적용하면서 실행 계획과 반복 비용을 확인하지 않는다.
10. 동적 SQL에 입력을 문자열로 이어 붙이거나 실행 권한을 과도하게 준다.

## 정답과 해설

### 정답 1
프로시저는 독립 호출문으로 여러 SQL과 업무 절차를 수행하고 출력 매개변수·결과 등을 줄 수 있다. 함수는 SQL 표현식 안에서 선언된 값 또는 테이블 결과를 계산해 사용된다.

### 정답 2
`IN`은 호출자가 전달하는 입력, `OUT`은 루틴이 호출자에게 채워 주는 출력, `INOUT`은 초기 입력을 받아 변경된 값을 다시 돌려주는 매개변수다.

### 정답 3
통화, 정밀도와 소수 자릿수, 반올림 방식과 시점, 음수·널 허용 여부 중 세 가지를 명세한다.

### 정답 4
조회와 갱신 사이에 다른 트랜잭션이 값을 바꾸면 과도 차감이나 분실 갱신이 생길 수 있다. 현재 수량 조건을 포함한 원자적 갱신, 버전 검사 또는 요구에 맞는 잠금으로 검증과 변경을 연결한다.

### 정답 5
호출자가 프로시저 호출과 다른 변경을 하나의 업무 트랜잭션으로 묶으려 해도 중간 커밋 때문에 전체 롤백할 수 없을 수 있기 때문이다. 경계 책임을 명시한다.

### 정답 6
DBMS가 집합 전체를 최적화할 수 있고 행별 문맥 전환·반복 호출 비용과 긴 잠금을 줄일 수 있기 때문이다. 코드도 더 짧고 판정하기 쉬운 경우가 많다.

### 정답 7
널을 반환하거나, 계약된 기본값을 반환하거나, 업무 오류·예외를 발생시킬 수 있다. 어떤 선택이든 0과 오류처럼 다른 의미를 혼동하지 않게 문서화한다.

### 정답 8
호출 행 수와 함수 호출 횟수, 함수 내부 조회·I/O, 자체·포괄 비용, 인덱스·실행 계획 영향 중 세 가지를 확인한다.

### 정답 9
입력값이 SQL 구조로 해석되어 주입 공격과 형 변환 오류가 생길 수 있다. 바인드 매개변수와 허용 목록, 최소 실행 권한을 사용한다.

### 정답 10
변경된 행과 상태, 영향 건수·합계 대사, 감사·처리 이력, 연계 부수 효과, 롤백 후 잔여 데이터, 권한·민감 로그 중 네 가지를 확인한다.

## 핵심 요약

- **프로시저와 호출문 작성**은 입력·출력 계약, 집합 SQL, 상태·영향 행 수, 트랜잭션·예외·권한을 함께 설계하는 활동이다.
- 프로시저는 독립적으로 업무 절차를 호출하고, 사용자 정의함수는 SQL 표현식에서 값 또는 행 집합을 계산한다.
- 매개변수는 모드, 자료형, 널, 범위, 날짜·금액 의미를 명확히 하고 호출문은 바인드와 최소 권한을 사용한다.
- 단순 일괄 작업은 커서·반복보다 집합 연산을 우선하고, 동시 변경에는 조건부 갱신·버전·잠금 등 요구에 맞는 통제를 적용한다.
- **사용자 정의함수와 호출 쿼리 작성**에서는 반환형, 결정성, 부수 효과, 널·오류, 정밀도와 행별 반복 비용을 검증한다.
- DBMS별 호출·예외·트랜잭션 문법 차이를 확인해야 하며, 코드 결과뿐 아니라 데이터 무결성·대사·권한·운영 이력을 함께 시험한다.
