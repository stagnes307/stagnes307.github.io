# 1-8-1-2. 데이터 삽입·삭제·수정 트리거 작성

## 수행 범위와 학습 목표

이 레슨은 테이블에서 데이터 변경 사건이 발생할 때 데이터베이스가 자동으로 실행하는 **데이터 삽입·삭제·수정 트리거 작성**을 다룬다. 앞 레슨의 프로시저·사용자 정의 함수 작성법을 반복하기보다, 트리거가 필요한 업무 규칙을 식별하고 사건·시점·실행 단위·조건·후속 동작을 안전하게 설계하는 데 집중한다. 제품마다 문법과 지원 기능이 다르므로 예시는 개념 중심 의사 SQL이며 실제 작성 시 대상 DBMS 공식 문서와 조직 표준을 확인한다.

두 번째 목표는 **절차형 SQL 작성하기의 적용 절차와 판단 기준**을 트리거 과제에 적용하는 것이다. 요구사항을 곧바로 코드로 옮기지 않고 입력 자료 확인, 대안 비교, 설계, 작성, 검토, 시험, 배포·복구 준비 순으로 수행하며 정확성·원자성·성능·보안·운영 가능성을 근거로 완료를 판단한다.

학습 후에는 다음을 할 수 있어야 한다.

- INSERT·UPDATE·DELETE 중 필요한 사건과 실행 시점을 선택한다.
- 변경 전후 값과 다중 행 변경을 고려해 행 단위 또는 문장 단위를 결정한다.
- 제약조건·응용 프로그램·프로시저·트리거 중 규칙의 올바른 위치를 판단한다.
- 재귀·연쇄 실행, 잠금 확대, 권한 상승, 감사정보 노출을 예방한다.
- 정상·경계·오류·대량·동시 변경을 확인하고 배포·되돌리기 산출물을 만든다.

## 트리거의 역할과 선택 기준

트리거는 특정 테이블이나 뷰의 변경 사건에 결합된 절차형 데이터베이스 객체다. 호출자가 직접 호출하지 않아도 실행된다는 점이 프로시저와 다르다. 중앙에서 일관되게 지켜야 하고 모든 변경 경로에 적용되어야 하는 규칙에는 유용하지만, 숨은 실행 흐름과 성능 비용을 만들 수 있으므로 필요한 범위만 사용한다.

| 요구 | 우선 검토 수단 | 판단 이유 |
|---|---|---|
| NULL 금지, 값 범위, 참조 무결성 | NOT NULL·CHECK·FOREIGN KEY | 선언적이며 최적화와 오류 의미가 명확하다 |
| 단순 기본값 | DEFAULT | 자동 실행 코드를 만들 필요가 없다 |
| 여러 테이블을 아우르는 변경 이력 | 트리거 또는 승인된 변경 계층 | 모든 변경 경로에서 누락 없이 기록할 필요가 있다 |
| 복잡한 업무 절차와 사용자 피드백 | 서비스·프로시저 | 흐름을 명시하고 시험·오류 처리를 통제하기 쉽다 |
| 읽기 전용 파생값 | 뷰·계산식·조회 | 저장값 동기화 오류를 피할 수 있다 |

시험에서는 “자동 처리이므로 무조건 트리거”라는 답이 위험하다. 선언적 제약으로 표현할 수 있으면 제약을 먼저 쓰고, 응용 계층에서만 의미가 있는 긴 업무 흐름은 그 계층에 둔다. 트리거는 데이터베이스 경계를 통과하는 모든 변경에 강제해야 할 짧고 결정적인 규칙에 적합하다.

## 설계 요소: 사건·시점·단위·조건

첫째, 사건은 INSERT, UPDATE, DELETE로 구분한다. UPDATE라면 어떤 열의 변경에 반응할지와 실제 값이 달라졌는지를 구분한다. 단지 UPDATE 문에 열이 등장했다는 사실과 이전값·새값이 다른 것은 같지 않다.

둘째, 시점은 보통 변경 전(BEFORE), 변경 후(AFTER), 변경 대신(INSTEAD OF)로 생각한다. 변경 전에는 값 검증·정규화가, 변경 후에는 확정된 변경을 이용한 이력 기록이 자연스럽다. 대신 실행은 갱신 가능한 복합 뷰처럼 원래 연산을 대체해야 할 때 검토한다. 트랜잭션 확정 뒤 외부 메시지를 즉시 보낼 수 있다고 가정해서는 안 된다. 일반적인 트리거는 원래 문장과 같은 트랜잭션에 묶이며 커밋 여부가 아직 결정되지 않았기 때문이다.

셋째, 행 단위는 영향받은 각 행마다, 문장 단위는 한 SQL 문장마다 실행된다. 한 번의 UPDATE가 수천 행을 바꿀 수 있으므로 단일 행만 들어온다는 가정은 금물이다. DBMS가 변경 집합을 제공하면 집합 연산으로 처리하고, 행 단위만 지원하면 행별 비용과 잠금 영향을 검토한다.

넷째, 조건은 필요한 변경만 좁혀야 한다. 예를 들어 주문 상태가 `PAID`에서 `CANCELLED`로 실제 전환될 때만 상태 이력을 남긴다. NULL 비교는 일반 등호만으로 기대대로 동작하지 않을 수 있으므로 NULL 안전 비교 또는 명시적 분기를 사용한다.

설계 명세의 최소 필드는 다음과 같다.

| 항목 | 기록 내용 |
|---|---|
| 대상·사건 | 대상 테이블, INSERT/UPDATE/DELETE, 대상 열 |
| 실행 시점·단위 | BEFORE/AFTER/INSTEAD OF, ROW/STATEMENT |
| 변경 참조 | 이전값, 새값, 변경 집합의 별칭과 사용 범위 |
| 실행 조건 | 상태 전이, 값 변화, 제외 조건 |
| 동작 | 검증, 정규화, 이력 기록, 보조 테이블 변경 |
| 오류 정책 | 원문 취소 여부, 오류 코드·메시지, 기록 범위 |
| 비기능 조건 | 예상 건수, 잠금, 실행 시간, 보안 주체 |
| 운영 정보 | 이름, 버전, 배포 순서, 비활성화·복구 방법 |

## INSERT 트리거 작성

삽입 트리거에서는 새 값의 필수성·범위·관계와 생성 주체를 확인한다. 단순 무결성은 제약조건으로 처리하고, 트리거에는 제약만으로 표현하기 어려운 교차 테이블 규칙이나 중앙 감사처럼 분명한 책임만 둔다.

다음은 감사 이력을 남기는 제품 중립 의사 SQL이다. 실제 예약어와 변경 집합 문법은 DBMS에 맞게 바꿔야 한다.

```sql
CREATE TRIGGER order_insert_audit
AFTER INSERT ON orders
REFERENCING NEW TABLE AS inserted_rows
FOR EACH STATEMENT
BEGIN
  INSERT INTO order_audit(order_id, action_type, changed_at, actor_id)
  SELECT order_id, 'INSERT', CURRENT_TIMESTAMP, session_actor()
  FROM inserted_rows;
END;
```

핵심은 삽입 행을 집합으로 다루는 것이다. `SELECT MAX(id)`처럼 방금 삽입한 행을 추정하면 동시 실행에서 다른 세션의 행을 가져올 수 있다. 행 식별자는 새 행 집합에서 직접 얻는다. 감사 주체도 응용 프로그램이 전달한 임의 문자열이 아니라 검증된 세션·요청 문맥에서 가져오며, 개인·비밀 정보 전체를 복사하지 않는다.

## UPDATE 트리거 작성

수정 트리거는 이전값과 새값을 함께 사용해 상태 전이와 변경 내용을 판단한다. 상태를 직접 덮어쓰는 모든 경로에서 전이 규칙을 지켜야 한다면 다음처럼 검증한다.

```text
FOR EACH changed row
    old_state ← OLD.status
    new_state ← NEW.status
    IF old_state = new_state
        CONTINUE
    IF transition_table does not allow (old_state, new_state)
        RAISE domain_error("허용되지 않은 상태 전이")
    APPEND state_history(primary_key, old_state, new_state, trusted_actor, change_time)
END
```

전이표를 코드에 여러 번 하드코딩하면 응용 계층과 트리거의 규칙이 달라질 수 있다. 규칙의 소유 위치를 정하고 한쪽은 방어선인지 핵심 규칙인지 명시한다. 수정일 자동 기록도 무조건 트리거에 넣지 않는다. 해당 열 수정이 다시 같은 UPDATE 트리거를 호출하는지, DBMS가 새 행 값을 직접 설정하는 기능을 제공하는지 확인한다.

금액 합계나 재고 수량을 증감하는 트리거는 특히 주의한다. `새값만 더하기`가 아니라 삽입은 `+NEW`, 삭제는 `-OLD`, 수정은 `NEW-OLD` 차이를 반영해야 한다. 동시에 여러 트랜잭션이 같은 요약 행을 변경하면 잠금 순서와 원자적 갱신을 검토한다. 가능하면 조회 시 집계, 물질화 기능, 검증된 집계 작업 같은 대안도 비교한다.

## DELETE 트리거 작성

삭제 트리거는 이전 행을 이용해 삭제 이력을 기록하거나 참조 관계 외의 규칙을 검사한다. 참조 무결성은 우선 외래키의 제한·연쇄 정책으로 표현한다. 트리거로 수동 연쇄 삭제를 구현하면 누락, 순환, 예상 밖의 대량 삭제가 생기기 쉽다.

감사 이력에는 삭제된 전체 민감 데이터를 그대로 보관하지 않는다. 업무상 필요한 식별자·분류·행위자·시각·사유를 최소화하고 접근권한과 보존기간을 둔다. 논리 삭제가 필요하다면 DELETE를 UPDATE로 조용히 바꾸기 전에 모든 조회가 삭제 표시를 일관되게 제외하는지, 고유키 재사용과 보존·파기 요구가 무엇인지 설계한다.

삭제 방지 규칙은 오류가 호출자에게 명확해야 한다. “하위 데이터가 존재하므로 삭제 불가”처럼 조치 가능한 업무 오류를 반환하고 내부 테이블명이나 SQL 문장을 노출하지 않는다. 오류를 잡아서 원문 삭제는 성공시킨 채 후속 기록만 누락시키는 방식은 원자성을 훼손할 수 있다.

## 트랜잭션·오류·실행 순서

대부분의 트리거는 원래 DML과 동일한 트랜잭션에서 실행된다. 트리거가 예외를 발생시키면 원문 전체가 취소될 수 있고, 트리거가 만든 이력도 함께 롤백된다. 이 특성을 요구와 맞춰야 한다. 실패해도 원문을 살려야 하는 비핵심 알림은 트리거 내부 원격 호출보다 트랜잭션 내 발행함(outbox) 레코드를 기록하고 커밋 뒤 별도 처리하는 구조가 안전하다.

한 대상에 여러 트리거가 있으면 실행 순서가 보장되는지 확인한다. 순서에 의존하는 트리거 여러 개보다는 하나의 명확한 책임 흐름 또는 선언된 순서를 사용한다. A 트리거가 B 테이블을 바꾸고 B 트리거가 다시 A를 바꾸는 순환은 재귀·교착·중복을 일으킨다. 허용 깊이, 종료 조건, 동일 사건 재진입 여부를 설계 단계에서 도식화한다.

```text
orders UPDATE
  ├─ 상태 전이 검증
  ├─ order_history INSERT
  │     └─ history 감사 트리거?  ← 필요성과 재진입 확인
  └─ outbox INSERT
        └─ 커밋 후 전달 작업이 읽음
```

오류 처리에서는 예상 업무 오류와 시스템 오류를 구분한다. 업무 오류는 안정적인 오류 식별자와 조치 메시지를 제공한다. 시스템 오류는 원문 트랜잭션을 안전하게 취소하고 상관관계 ID로 운영 로그를 찾게 한다. 예외를 무조건 삼키거나 성공으로 바꾸지 않는다.

## 성능·동시성·보안 판단

트리거 비용은 숨겨진 DML 비용이다. 대량 적재에서 행마다 조회하거나 로그 한 건씩 기록하면 처리 시간이 급증한다. 실행 계획, 영향 행 수, 추가 읽기·쓰기, 인덱스, 잠금 순서를 측정한다. 변경 집합과 조인하는 집합 연산을 우선하며, 불필요한 전체 테이블 집계와 네트워크 호출을 피한다.

동시성 시험에서는 같은 업무 키의 동시 INSERT, 같은 행의 상태 변경, 교차 순서 갱신을 수행한다. “존재 확인 후 삽입”만으로 유일성을 보장하지 말고 고유 제약과 원자적 연산을 사용한다. 모든 트리거가 관련 테이블을 같은 순서로 접근하면 교착 가능성을 낮출 수 있다.

트리거가 정의자 권한으로 실행될 수 있는 DBMS에서는 호출자가 직접 접근할 수 없는 객체를 간접 변경할 수 있다. 소유자, 실행 보안 문맥, 동적 SQL 사용, 검색 경로, 객체명 고정을 검토한다. 입력값을 SQL 문자열로 연결하지 않고, 트리거 소스와 변경 권한을 형상관리·승인 대상으로 둔다. 로그에는 자격증명·토큰·민감 원문을 남기지 않는다.

## 절차형 SQL 적용 절차

**절차형 SQL 작성하기의 적용 절차와 판단 기준**을 다음과 같이 수행한다.

1. 요구 ID, 데이터 소유자, 정상·예외 규칙, 예상 변경량을 확인한다.
2. 제약조건·응용 로직·프로시저·트리거 대안을 비교하고 선택 근거를 남긴다.
3. 사건·시점·단위·조건·이전값·새값·오류 정책을 트리거 명세로 작성한다.
4. 다중 행과 NULL을 기본 전제로 집합형 의사 SQL을 검토한다.
5. 원문 DML과 후속 변경의 트랜잭션 원자성, 잠금 순서, 연쇄 경로를 검토한다.
6. 최소 권한, 실행 주체, 감사 최소화와 보존정책을 반영한다.
7. 정상·경계·오류·대량·동시·롤백 사례를 독립 환경에서 시험한다.
8. 실행 계획과 전후 처리량을 비교하고 허용 기준을 확인한다.
9. 순서가 포함된 배포, 검증 쿼리, 비활성화·되돌리기 절차를 준비한다.
10. 요구–설계–객체–시험–배포 결과의 추적성을 확인하고 승인한다.

완료 판단은 문법 성공이 아니라 모든 변경 경로에서 규칙이 일관되며, 다중 행·동시 실행에도 정확하고, 실패 시 원자적으로 복구되고, 성능 예산과 최소 권한을 지키며, 운영자가 원인을 추적할 수 있는가로 내린다.

## 구체 실무 시나리오

주문 상태 변경 이력을 모든 입력 경로에서 남겨야 한다고 하자. 요구 분석 결과 상태 이력은 감사와 고객 문의에 필요하며, 주문 상태가 실제 바뀔 때만 기록해야 한다. 구현자는 `orders`의 UPDATE 후 트리거를 선택하고 이전·새 상태가 다른 변경 집합만 `order_status_history`에 넣는다. 허용 전이는 선언된 전이표로 확인하고, 행위자는 검증된 요청 문맥에서 얻는다.

대량 마감 작업이 5만 건을 한 문장으로 갱신할 수 있으므로 단일 행 변수에 의존하지 않고 변경 집합을 사용한다. 이력 테이블에는 업무 키와 조회 인덱스를 준비하되 민감 주문 원문은 복제하지 않는다. 금지 전이 한 건이 포함되면 전체 문장을 취소하는 정책을 업무 담당자와 합의한다. 배포 전에는 단건·다건·NULL·동시 상태 변경·롤백·성능을 확인하고 트리거 활성 여부와 버전을 운영 점검표에 기록한다.

## 산출물과 체크리스트

산출물은 트리거 요구·대안 검토표, 사건–시점–단위 명세, 연쇄 호출도, 객체 소스, 권한표, 시험 케이스·결과, 성능 비교표, 배포·복구 절차, 요구 추적표다.

- [ ] exact 사건과 대상 열, 실행 시점·단위를 명시했다.
- [ ] 선언적 제약이나 명시적 서비스가 더 적합하지 않은지 비교했다.
- [ ] 다중 행 INSERT·UPDATE·DELETE를 집합으로 처리한다.
- [ ] 이전값·새값·NULL·실제 값 변화 조건이 정확하다.
- [ ] 원문 DML과 후속 기록의 원자성 및 오류 정책이 합의되었다.
- [ ] 재귀·연쇄·실행 순서와 잠금 순서를 검토했다.
- [ ] 원격 호출·동적 SQL·비밀 로그를 피하고 최소 권한을 적용했다.
- [ ] 대량·동시 실행의 시간, 잠금, 추가 쓰기를 측정했다.
- [ ] 정상·경계·오류·롤백 시험 결과가 요구와 추적된다.
- [ ] 순서 있는 배포와 검증·비활성화·되돌리기 절차가 있다.

## 자주 틀리는 포인트

- 트리거는 자동 실행되므로 별도 시험이 필요 없다고 생각한다.
- CHECK나 외래키로 충분한 규칙을 복잡한 트리거로 만든다.
- 한 DML은 한 행만 바꾼다고 가정해 변경 집합의 일부만 처리한다.
- UPDATE 문에 열이 포함된 사실을 값이 실제 변경된 것으로 오해한다.
- NULL을 일반 등호로 비교해 변경 조건을 놓친다.
- UPDATE 집계에서 `NEW-OLD`가 아니라 새값 전체를 더한다.
- 외부 시스템 호출을 트리거 안에서 수행해 잠금과 장애를 확산시킨다.
- 감사라는 이유로 민감한 이전·새 행 전체를 무기한 저장한다.
- 트리거 간 실행 순서와 재귀 종료 조건을 확인하지 않는다.
- 트리거 생성 성공만 보고 대량·동시성·롤백 검증을 생략한다.

## 확인 문제

1. 트리거보다 선언적 제약조건을 우선해야 하는 사례 두 가지를 쓰시오.
2. 행 단위 트리거와 문장 단위 트리거의 차이를 설명하시오.
3. UPDATE 트리거가 대상 열의 실제 값 변화를 별도로 확인해야 하는 이유는 무엇인가?
4. 한 문장이 여러 행을 변경할 때 단일 행 가정이 만드는 결함을 쓰시오.
5. 트리거에서 외부 서비스로 직접 통지하는 방식이 위험한 이유와 대안을 쓰시오.
6. 요약 금액을 유지하는 UPDATE 트리거가 반영해야 하는 값은 무엇인가?
7. 연쇄·재귀 트리거 설계 시 확인할 항목 세 가지를 쓰시오.
8. 트리거 보안 검토에서 실행 보안 문맥이 중요한 이유는 무엇인가?
9. 절차형 SQL 적용 절차에서 구현 전에 수행할 대안 검토를 설명하시오.
10. 트리거 작성 완료를 판단하는 품질 기준 다섯 가지를 쓰시오.

## 정답과 해설

1. 필수값은 NOT NULL, 범위는 CHECK, 관계는 FOREIGN KEY가 대표적이다. 선언적 제약은 의도가 명확하고 모든 변경에 일관되며 DBMS 최적화와 오류 처리의 지원을 받는다.
2. 행 단위는 영향받은 각 행마다 실행되고 문장 단위는 SQL 문장당 한 번 실행된다. 대량 변경에서는 호출 횟수와 변경 집합 처리 방식이 크게 달라진다.
3. 열이 SET 절에 있어도 이전값과 같은 값으로 저장될 수 있다. 이를 모두 변경으로 기록하면 불필요한 이력과 연쇄 실행이 생긴다.
4. 첫 행이나 임의 행만 기록하고 나머지를 누락하거나, 잘못된 단일 식별자를 사용해 이력·집계가 어긋날 수 있다. 변경 집합 전체를 처리해야 한다.
5. 원문 트랜잭션의 잠금 시간이 늘고 외부 장애가 내부 DML을 막으며 커밋 전 통지가 전달될 수 있다. 트랜잭션 안에서 발행함을 기록하고 커밋 후 별도 전달한다.
6. 새값 전체가 아니라 `NEW-OLD` 차이를 반영한다. 삽입은 새값, 삭제는 이전값의 반대 부호를 적용한다.
7. 호출 그래프, 최대 깊이와 종료 조건, 동일 사건 재진입, 실행 순서 보장, 잠금 접근 순서 중 세 가지 이상을 확인한다.
8. 정의자 권한 등으로 실행되면 낮은 권한 호출자가 트리거를 통해 보호 객체를 간접 변경할 수 있다. 소유자·객체 권한·동적 SQL·검색 경로를 통제해야 한다.
9. 같은 요구를 제약조건, 응용 로직, 프로시저, 트리거로 해결할 때 일관성·가시성·성능·운영성을 비교하고 선택 근거를 남긴다.
10. 다중 행 정확성, 트랜잭션 원자성, 동시성·성능, 최소 권한·정보 최소화, 추적성과 배포·복구 가능성이 핵심이다.

## 핵심 요약

- 트리거는 모든 데이터 변경 경로에 강제할 짧고 결정적인 규칙에 제한해 사용한다.
- INSERT·UPDATE·DELETE, BEFORE·AFTER, 행·문장 단위와 실제 변경 조건을 명시한다.
- 다중 행·NULL·동시성을 기본 전제로 변경 집합과 선언적 무결성을 활용한다.
- 트리거는 원문 트랜잭션과 잠금을 공유하므로 원격 호출, 재귀, 긴 처리를 피한다.
- 감사 데이터와 실행 권한은 최소화하고 소스·권한·배포를 승인·추적한다.
- 절차형 SQL의 완료는 문법이 아니라 정확성·원자성·성능·보안·운영 증거로 판단한다.
