01

수행 범위와 학습 목표

이 레슨은 데이터베이스의 인증 주체와 역할을 식별하고 최소 권한 원칙에 따라 사용자·그룹·권한 DCL 작성을 수행하는 실무를 다룬다. 또한 업무 요구에서 SQL을 도출하고 정확성·성능·보안·운영성으로 검증하는 응용 SQL 작성하기의 적용 절차와 판단 기준을 정리한다. 특정 DBMS의 계정 생성 문법, 역할 상속, 시스템 권한 이름은 다를 수 있으므로 예시는 제품 중립 개념이며 실제 명령은 공식 문서와 조직 정책을 따른다.

학습 후에는 다음을 할 수 있어야 한다.

  • 사람·서비스·운영 작업의 인증 주체와 수명주기를 구분한다.
  • 직접 권한보다 역할을 중심으로 권한 행렬과 DCL을 설계한다.
  • 객체·행위·범위·위임 가능성을 최소화해 GRANT와 REVOKE를 작성한다.
  • 역할 상속, 소유권, 기본 권한, 뷰·프로시저 실행 권한의 위험을 판단한다.
  • SQL 요구 확인부터 작성·시험·배포·회수까지 적용 절차를 수행한다.
  • 권한 유효성뿐 아니라 과잉 권한 부재와 회수·감사 가능성으로 완료를 판단한다.
02

DCL의 대상과 기본 원칙

DCL(Data Control Language)은 사용자·역할·권한을 생성·부여·회수해 데이터 접근을 통제한다. 제품에 따라 CREATE USER·CREATE ROLE은 DDL로 분류되기도 하지만 실무 과제에서는 인증 주체와 권한 생명주기를 한 흐름으로 관리한다.

권한 설계의 기본 원칙은 다음과 같다.

  • 기본 거부: 필요한 근거가 확인된 접근만 허용한다.
  • 최소 권한: 필요한 객체와 행위, 환경, 기간만 허용한다.
  • 직무 분리: 개발·승인·배포·감사 같은 상충 역할을 분리한다.
  • 역할 기반 부여: 사람마다 직접 부여하기보다 업무 역할을 통해 관리한다.
  • 개별 식별: 공유 사람 계정을 피하고 누가 무엇을 했는지 추적한다.
  • 수명주기 관리: 생성뿐 아니라 변경·휴면·퇴직·만료·회수를 포함한다.
  • 정기 검토: 현재 직무와 실제 사용에 비추어 권한을 재인증한다.

“업무가 막히지 않게 전체 권한을 먼저 주고 나중에 줄인다”는 접근은 권한이 영구 잔존하기 쉽다. 요구된 작업을 세분화해 처음부터 작은 역할을 만들고, 긴급 권한은 승인·만료·사후 검토를 함께 둔다.

03

인증 주체와 역할 모델

사용자는 데이터베이스가 식별하는 로그인 또는 인증 주체다. 그룹이나 역할은 여러 사용자에게 공통 권한을 묶어 부여하는 논리 단위다. 운영체제·디렉터리 그룹과 DB 역할을 연계할 수도 있지만 동기화 지연, 중첩 그룹, 퇴직자 회수 경로를 확인해야 한다.

인증 주체를 다음처럼 분류한다.

인증 주체와 역할 모델 · 학습 표 1
주체예주요 통제
사람 사용자분석가, 운영자개인 식별, 강한 인증, 직무 변경·퇴직 회수
응용 서비스주문 API, 정산 배치비대화형 인증, 최소 객체 권한, 비밀 교체
배포 주체마이그레이션 작업제한 시간·환경, 승인된 변경 권한, 실행 기록
긴급 주체장애 대응 임시 권한사전 승인 또는 통제된 긴급 절차, 자동 만료·사후 감사
감사 주체읽기 전용 감사 역할변경 불가, 필요한 감사 범위만 조회

사람과 서비스 계정을 공유하지 않는다. 응용 서비스에 객체 생성·사용자 관리 권한을 주지 않고 런타임 SELECT·INSERT·UPDATE 등 필요한 행위만 준다. 배포 계정은 런타임 계정과 분리한다. 소유자 계정은 일반 업무 로그인에 사용하지 않고 보호한다.

04

권한 행렬 작성

DCL보다 먼저 주체–객체–행위–조건 행렬을 작성한다.

권한 행렬 작성 · 학습 표 2
역할객체 범위허용 행위제한·근거
order_reader승인된 주문 조회 뷰SELECT고객지원 조회, 민감 열 제외
order_writer주문 입력 프로시저EXECUTE직접 테이블 수정 금지
settlement_job정산 원천 뷰·결과 테이블SELECT, INSERT, UPDATE정산 스키마·서비스 계정만
schema_deployer승인 스키마CREATE, ALTER배포창 동안만 활성화
security_auditor감사 뷰SELECT원본 변경 권한 없음

객체 이름만 적지 말고 스키마·환경을 포함한다. “주문 DB 읽기”는 너무 넓다. 어떤 뷰의 어떤 열과 기간인지, 행 수준 정책이 필요한지 명시한다. 역할 간 상속이 있으면 최종 유효 권한을 펼쳐서 본다. 작은 역할을 조합했더라도 조합 결과가 직무 분리를 깨뜨릴 수 있다.

05

사용자와 역할 작성

제품 중립 의사 DCL은 다음과 같다.

코드 예시 · sql

CREATE ROLE order_reader;
CREATE ROLE order_operator;

GRANT SELECT ON support_order_view TO order_reader;
GRANT EXECUTE ON PROCEDURE cancel_order TO order_operator;

GRANT order_reader TO user_support_01;
GRANT order_operator TO user_order_ops_01;

실제 사용자를 만들 때 비밀번호를 소스나 배포 로그에 평문으로 적지 않는다. 조직의 인증 체계, 비밀 저장소 또는 안전한 초기 자격증명 전달 절차를 사용한다. 만료, 잠금, 로그인 허용, 기본 스키마, 자원 제한을 정책에 맞게 설정한다.

역할 이름은 직무와 책임을 드러내고 환경을 혼동하지 않게 한다. super_user2 같은 이름보다 prod_order_read, prod_order_operate처럼 범위가 드러나는 이름이 낫다. 다만 이름만 믿지 말고 실제 포함 권한을 자동·수동으로 검토한다.

그룹 연계에서는 그룹 소유자, 가입 승인, 중첩 허용, 동기화 주기, 긴급 회수를 명세한다. 외부 디렉터리에서 제거해도 기존 DB 세션이나 캐시된 토큰이 남을 수 있으므로 즉시 회수가 필요한 상황의 세션 종료 절차를 준비한다.

06

GRANT 작성 판단

GRANT는 “누가, 무엇에, 어떤 행위를, 어떤 위임 가능성과 함께” 받는지 명시한다. 필요한 열만 갱신하는 권한이나 제한된 뷰가 지원되면 전체 테이블 권한보다 우선 검토한다. 응용 프로그램이 검증된 프로시저만 호출하면 되는 경우 직접 테이블 DML 대신 EXECUTE 권한을 줄 수 있다.

코드 예시 · sql

GRANT SELECT ON support_order_view TO order_reader;
GRANT UPDATE (status, assigned_agent_id)
ON support_ticket TO support_operator;

열 수준 권한 문법과 지원 여부는 DBMS마다 다르다. 행 범위 제한은 보안 뷰나 행 수준 정책으로 구현할 수 있지만 뷰 우회 원본 권한, 소유권 체인, 정의자/호출자 권한을 확인해야 한다.

WITH GRANT OPTION 또는 관리자 옵션은 받은 주체가 다른 주체에게 다시 권한·역할을 부여하게 한다. 일반 업무 역할에는 거의 필요하지 않다. 위임이 필요하면 승인된 권한 관리자 역할에 한정하고 부여 경로를 감사한다. 소유권 자체가 암묵적 전체 권한을 주는 제품도 있으므로 명시적 GRANT 목록만 보고 판단하지 않는다.

07

REVOKE와 회수 영향

REVOKE는 단순 반대 명령이 아니라 의존성과 잔존 접근을 확인하는 과정이다.

코드 예시 · sql

REVOKE UPDATE ON support_ticket FROM temporary_operator;
REVOKE order_operator FROM transferred_user;

위임받은 주체가 다른 사용자에게 다시 부여했다면 연쇄 회수 또는 제한 동작이 발생할 수 있다. 제품별 CASCADE·RESTRICT 의미를 확인하고 영향 대상을 사전에 조회한다. 역할을 회수해도 다른 역할, 직접 권한, PUBLIC 권한, 소유권, 활성 세션을 통해 접근이 남을 수 있다. 최종 유효 권한으로 검증한다.

업무 이동 시 기존 역할을 먼저 파악하고 새 역할 추가와 기존 역할 회수의 순서를 계획한다. 접근 공백과 과잉 권한 공존 기간을 최소화한다. 임시 권한은 종료일을 티켓 메모로만 남기지 말고 가능한 경우 자동 만료·회수 작업과 검증 알림을 둔다.

08

기본 권한·PUBLIC·객체 수명주기

새 객체가 만들어질 때 자동으로 붙는 기본 권한을 확인한다. 현재 테이블 권한만 바로잡아도 향후 생성 테이블이 넓게 공개되면 통제가 무너진다. 스키마 소유자, 기본 권한 템플릿, PUBLIC 권한, 향후 객체에 대한 부여 정책을 함께 관리한다.

객체 삭제 후 같은 이름으로 다시 생성하면 기존 권한이 유지되는지 사라지는지는 제품과 객체 식별 방식에 따라 다를 수 있다. 배포 절차에서 권한 재적용과 검증을 포함한다. 뷰나 프로시저가 참조하는 기반 객체 권한도 정의자 권한과 호출자 권한 모델에 따라 달라지므로 시험 계정으로 실제 접근을 확인한다.

운영·개발·시험 환경의 역할을 분리하고 운영 자료를 시험에 복제할 때 비식별·접근 통제를 적용한다. 개발 편의를 이유로 운영 읽기 역할을 상시 부여하지 않는다.

09

응용 SQL 적용 절차

응용 SQL 작성하기의 적용 절차와 판단 기준은 조회·DML·DCL 모두에 공통되는 통제 흐름이다.

  1. 요구사항, 업무 규칙, 데이터 분류, 대상 환경과 승인자를 확인한다.
  2. 입력·출력, 결과 한 행의 의미, 영향 객체와 행위를 정의한다.
  3. 스키마·키·제약·권한·데이터량·동시 접근 조건을 확인한다.
  4. 선언적 제약, 정적 SQL, 프로시저, 역할 등 대안을 비교한다.
  5. 바인드·명시적 열·제한된 범위를 적용해 SQL과 예상 결과를 작성한다.
  6. 정상·경계·NULL·중복·오류·권한 거부 사례를 독립 환경에서 시험한다.
  7. 건수·합계·키·변경 전후 상태와 실행 계획을 확인한다.
  8. 최소 권한, 민감정보 노출, 감사·오류 정보, 트랜잭션 영향을 검토한다.
  9. 형상·승인·배포 순서·검증 쿼리·되돌리기 또는 회수 절차를 준비한다.
  10. 요구–SQL–시험–승인–배포 결과를 추적하고 운영 관찰 후 종료한다.

DCL의 완료 기준은 권한 부여 명령 성공이 아니다. 승인된 업무는 가능하고 금지된 업무는 거부되며, 최종 유효 권한이 행렬과 일치하고, 직접·상속·PUBLIC·소유권 우회가 없고, 회수·만료·감사가 동작해야 한다.

일반 응용 SQL의 완료는 요구한 데이터 범위와 결과가 정확하고 트랜잭션·동시성 조건에서 일관되며 실제량 성능 기준과 데이터 최소 접근을 만족하는지로 판단한다. 읽기 쿼리도 민감 열을 과도하게 반환하거나 장시간 잠금을 유발할 수 있으므로 보안·운영 검토 대상이다.

10

권한 검증 방법

관리자 계정에서 권한 목록만 조회하지 말고 대표 시험 주체로 허용·거부를 모두 확인한다.

코드 예시 · text

시험 주체: order_operator_test
  허용: cancel_order 실행                     → 성공해야 함
  거부: orders 테이블 직접 UPDATE             → 거부되어야 함
  거부: 다른 스키마 고객 원문 SELECT           → 거부되어야 함
  거부: 다른 사용자에게 역할 GRANT             → 거부되어야 함
  회수 후: 기존 기능 실행                      → 거부되어야 함

성공 시험만 하면 과잉 권한을 찾지 못한다. 역할 조합별 음성 시험, 새 객체 기본 권한, 역할 회수 후 새 세션, 긴급 권한 만료를 포함한다. 활성 세션에서 회수가 즉시 반영되지 않는 제품이라면 세션·토큰 처리 정책을 확인한다.

감사 기록에는 주체, 역할, 대상, 행위, 결과, 시각, 승인·요청 ID를 남기되 SQL 매개변수의 민감 원문은 최소화한다. 권한 실패가 반복되면 오구성인지 비정상 접근인지 조사할 수 있도록 경보 기준을 둔다.

11

구체 업무 시나리오

고객지원 조직이 주문 상태와 배송 정보를 조회하고 승인된 조건에서만 취소 요청을 등록해야 한다고 하자. 원본 주문 테이블에는 결제 토큰 참조와 내부 위험 점수가 있어 전체 SELECT를 줄 수 없다. 설계자는 필요한 열만 제공하는 support_order_view, 취소 가능 상태와 행위자를 검사하는 cancel_order 프로시저를 준비하고 각각 읽기·운영 역할에 연결한다.

상담원은 읽기 역할, 취소 담당자는 읽기와 운영 역할을 받는다. 역할은 디렉터리 그룹과 연계하되 가입 승인자와 회수 시간을 정한다. 운영 역할에는 원본 테이블 UPDATE와 다른 사용자에게 권한을 주는 옵션이 없다. 시험에서는 승인된 주문 조회·취소가 성공하고, 위험 점수 조회·직접 상태 변경·역할 재부여가 거부되는지 확인한다.

직무 이동 사용자는 기존 운영 역할을 회수하고 새 읽기 역할만 부여한다. 최종 유효 권한 조회와 새 세션 음성 시험으로 잔존 접근이 없음을 확인한다. 이 결과를 요청 ID와 함께 권한 검증표에 기록한다.

12

산출물과 체크리스트

산출물은 사용자·서비스 주체 목록, 역할 정의서, 주체–객체–행위 권한 행렬, 역할 상속도, DCL 스크립트, 승인 기록, 허용·거부 시험 결과, 최종 유효 권한 보고서, 회수·만료 절차, 정기 재인증 일정이다.

  • [ ] 사람·서비스·배포·긴급 주체를 분리했다.
  • [ ] 개인 사람 계정과 비대화형 서비스 계정을 사용한다.
  • [ ] 권한은 객체·행위·환경·기간별 최소 범위다.
  • [ ] 직접 권한보다 승인된 업무 역할을 우선했다.
  • [ ] 역할 상속과 조합 후의 최종 유효 권한을 확인했다.
  • [ ] PUBLIC·기본 권한·소유권·위임 옵션을 검토했다.
  • [ ] 허용 시험과 금지 행위의 음성 시험을 모두 수행했다.
  • [ ] 변경·퇴직·만료·긴급 접근 회수 절차가 있다.
  • [ ] 비밀이 소스·스크립트·로그에 평문으로 남지 않는다.
  • [ ] DCL과 응용 SQL이 요구·시험·승인·배포 기록에 추적된다.
13

자주 틀리는 포인트

  • 직무 대신 개인별 직접 권한을 계속 추가한다.
  • 읽기 전용 요구에 스키마 전체 권한을 부여한다.
  • 서비스 계정에 객체 생성·권한 관리까지 준다.
  • 역할 이름만 확인하고 중첩 상속 후 유효 권한을 보지 않는다.
  • WITH GRANT OPTION을 편의 기능으로 가볍게 부여한다.
  • REVOKE 후 다른 역할·PUBLIC·소유권을 통한 접근을 확인하지 않는다.
  • 신규 객체의 기본 권한과 재생성 시 권한 변화를 놓친다.
  • 허용 기능 성공만 시험하고 금지 기능 거부를 시험하지 않는다.
  • 퇴직·직무 이동 회수를 수동 메모에만 의존한다.
  • DCL 스크립트에 초기 비밀번호나 비밀을 평문으로 넣는다.

확인 문제

  1. 사용자에게 직접 권한보다 역할을 부여하는 이점을 세 가지 쓰시오.
  2. 사람 계정과 서비스 계정을 분리해야 하는 이유는 무엇인가?
  3. 권한 행렬에 포함해야 할 핵심 요소를 쓰시오.
  4. WITH GRANT OPTION 또는 관리자 옵션이 만드는 위험은 무엇인가?
  5. REVOKE 성공 후에도 접근이 남을 수 있는 경로 네 가지를 쓰시오.
  6. PUBLIC 권한과 새 객체 기본 권한을 함께 검토해야 하는 이유는 무엇인가?
  7. 권한 시험에서 음성 시험이 필요한 이유를 설명하시오.
  8. 프로시저 EXECUTE 권한이 직접 테이블 UPDATE보다 적합할 수 있는 사례를 쓰시오.
  9. 응용 SQL 작성하기의 적용 절차를 요구 확인부터 배포까지 순서대로 요약하시오.
  10. DCL 작성 완료 판단 기준 다섯 가지를 쓰시오.
15

정답과 해설

  1. 직무 기준 일관성, 입·퇴사와 이동 시 일괄 회수, 검토 단순화, 직접 권한 누적 방지가 이점이다. 역할 자체의 과잉 권한은 별도로 검토해야 한다.
  2. 사람의 행위와 프로그램 행위를 구분해 추적하고, 인증 방식·권한·교체 주기를 각 용도에 맞게 통제하기 위해서다. 공유하면 책임 소재와 회수가 불명확하다.
  3. 주체 또는 역할, 스키마·객체 범위, SELECT·INSERT·EXECUTE 같은 행위, 환경·기간·조건, 업무 근거와 승인자를 포함한다.
  4. 받은 주체가 다른 주체에게 권한이나 역할을 확산시켜 중앙 승인과 회수를 우회할 수 있다. 제한된 권한 관리자에게만 허용해야 한다.
  5. 다른 역할의 상속, 직접 권한, PUBLIC 권한, 객체 소유권, 남은 활성 세션 중 네 가지를 제시할 수 있다.
  6. 현재 객체 권한을 바로잡아도 PUBLIC 또는 기본 템플릿이 넓으면 새 객체가 자동 공개되어 같은 문제가 반복되기 때문이다.
  7. 성공 시험은 필요한 업무 가능성만 확인한다. 금지 행위가 실제 거부되는지 확인해야 과잉 권한과 우회 경로를 찾을 수 있다.
  8. 취소처럼 상태·권한·감사를 함께 검사해야 하는 업무는 검증된 프로시저만 실행하게 하고 원본 테이블 직접 수정은 막는 편이 책임과 권한을 좁힌다.
  9. 요구·데이터 분류 확인, 영향 범위·결과 정의, 스키마·권한 확인, 대안 비교, 안전한 SQL 작성, 정상·경계·거부 시험, 정확성·성능·보안 검토, 형상·승인·배포·복구 순이다.
  10. 승인 업무 성공, 금지 업무 거부, 최소 최종 권한, 우회 경로 부재, 회수·만료 동작, 감사·추적 가능성 중 다섯 가지 이상이다.
16

핵심 요약

  • 사용자·그룹·권한 DCL은 생성부터 변경·만료·회수·재인증까지 생명주기로 관리한다.
  • 역할 기반 최소 권한과 직무 분리를 적용하고 사람·서비스·배포 주체를 분리한다.
  • GRANT의 객체·행위·환경·기간·위임 범위를 좁히고 REVOKE 뒤 최종 권한을 재검증한다.
  • PUBLIC·기본 권한·소유권·역할 상속은 명시적 권한 밖의 접근 경로가 될 수 있다.
  • 응용 SQL은 요구, grain, 안전한 작성, 정확성·성능·보안 시험, 승인·배포 순으로 적용한다.
  • 완료는 허용된 업무의 성공과 금지된 업무의 거부, 회수·감사 증거가 함께 있을 때 판단한다.
