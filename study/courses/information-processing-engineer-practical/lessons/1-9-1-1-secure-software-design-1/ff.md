# 1-9-1-1. 보안 요구사항 명세 · 보안 요구사항을 만족하는 프로그램 설계

## 수행 범위와 학습 목표

이 레슨은 업무·법규·조직 정책·위험 분석에서 검증 가능한 **보안 요구사항 명세**를 만들고, 그 요구를 구조·데이터·인터페이스·통제·오류 흐름에 반영하여 **보안 요구사항을 만족하는 프로그램 설계**를 완성하는 실무를 다룬다. 구체적인 구현과 결함 시험은 뒤 레슨의 주범위이므로 여기서는 무엇을 보호하고 어떤 조건을 만족해야 하는지, 설계로 어떻게 보장할지를 결정한다.

보안 예시는 방어와 검증에 한정한다. 공격을 재현하는 실행 절차보다 자산·위협·신뢰경계·오용 사례를 식별하고 예방·탐지·대응 통제를 설계하는 데 집중한다.

학습 후에는 다음을 할 수 있어야 한다.

- 보호 자산·이해관계자·데이터 분류·신뢰경계를 식별한다.
- 추상적인 “안전해야 한다”를 측정·시험 가능한 요구로 바꾼다.
- 인증·인가·입력·데이터 보호·감사·가용성 요구를 정상·오용 사례와 연결한다.
- 위협과 위험을 분석해 통제의 우선순위와 잔여 위험을 설명한다.
- 설계 원칙과 신뢰경계별 통제를 구조·데이터 흐름·인터페이스에 반영한다.
- 요구–위협–설계–검증 방법의 양방향 추적성을 산출물로 제시한다.

## 입력자료와 보안 범위

입력자료는 업무 요구사항, 유스케이스·프로세스, 시스템·데이터 흐름도, 인터페이스 명세, 데이터 분류 기준, 사용자·역할 목록, 관련 정책·계약, 가용성·복구 목표, 기존 사고·취약점 교훈이다. 법적 의무나 기술 기준은 적용 여부와 최신 공식 문서를 담당 부서와 확인하고, 버전이나 수치를 근거 없이 고정하지 않는다.

첫 회의에서 범위를 경계로 표현한다.

```text
[사용자 단말]
      │ 공개 네트워크: 신뢰경계 A
      ▼
[접근 계층] ── [인증 서비스]
      │ 내부 서비스 경계 B
      ▼
[업무 서비스] ── [외부 결제 서비스]
      │ 데이터 경계 C
      ▼
[업무 DB]      [감사 저장소]
```

범위에는 코드만이 아니라 설정, 비밀, 빌드 산출물, 로그, 운영 인터페이스, 외부 의존성, 백업·복구 경로를 포함한다. 반대로 조직 전체 보안을 한 프로그램 요구에 무한히 넣지 않는다. 외부 통제는 소유 조직과 인터페이스 계약을 명시한다.

## 자산·주체·데이터 분류

자산은 공격 대상만 뜻하지 않는다. 고객 개인정보, 결제 상태, 주문 승인 권한, 서비스 가용성, 감사 증거, 소스·빌드 산출물, 비밀키, 조직 신뢰도까지 포함한다. 자산마다 소유자, 중요성, 보존·파기, 허용 사용을 기록한다.

| 자산 | 보안 속성 | 손상 영향 | 소유자·근거 |
|---|---|---|---|
| 고객 연락처 | 기밀성·무결성 | 사생활 침해, 오배송 | 고객업무 책임자·데이터 분류 |
| 주문 상태 | 무결성·추적성 | 부정 취소·정산 오류 | 주문업무 책임자 |
| 인증 토큰 | 기밀성·진본성 | 권한 도용 | 인증 서비스 책임자 |
| 감사 기록 | 무결성·가용성 | 조사·책임 추적 실패 | 보안운영 책임자 |
| 주문 서비스 | 가용성 | 판매·고객지원 중단 | 서비스 소유자 |

주체는 고객, 상담원, 관리자, 서비스, 배치, 외부 시스템, 감사자로 나눈다. “내부 사용자”를 하나로 묶으면 직무 분리와 최소 권한이 보이지 않는다. 서비스 간 호출도 주체이며 각 요청의 인증·인가·추적 방법을 정해야 한다.

데이터 흐름마다 생성, 수집, 전송, 처리, 저장, 백업, 파기를 표시한다. 민감 데이터가 로그·캐시·오류 메시지·분석 복제본으로 새어 나가는 2차 경로를 확인한다. 수집하지 않아도 되는 데이터는 통제보다 제거가 우선이다.

## 보안 요구사항의 품질

좋은 요구사항은 고유 ID, 적용 대상, 조건, 기대 동작, 측정 기준, 우선순위, 근거, 책임자, 검증 방법을 가진다. 한 문장에 여러 통제를 묶지 않고 정상과 실패 동작을 함께 적는다.

나쁜 예: “시스템은 강력하게 인증하고 안전하게 로그를 남겨야 한다.”

개선 예:

- `SEC-AUTH-01`: 주문 취소 기능은 인증된 고객 또는 승인된 상담원 주체만 요청할 수 있어야 하며, 서버는 요청 시점마다 주문 소유권 또는 상담원 취소 역할을 확인해야 한다. 검증은 허용 역할 성공과 비소유·비인가 역할 거부 시험으로 한다.
- `SEC-LOG-02`: 주문 상태 변경 결과는 상관관계 ID, 검증된 주체 ID, 주문 ID, 이전·새 상태, 결과 코드, 서버 시각을 감사 기록에 남겨야 한다. 인증정보와 결제 비밀은 기록하지 않으며, 승인되지 않은 주체의 변경·삭제를 거부해야 한다.
- `SEC-AVAIL-03`: 외부 결제 응답 지연 시 주문 서비스는 정의된 시간 제한 뒤 자원을 반환하고, 상태를 불확실로 보존하여 중복 결제를 유발하지 않는 복구 절차를 제공해야 한다. 검증은 지연·중단 모의 시험과 상태 일관성 확인으로 한다.

“적절한”, “가능한 한”, “최신”, “강력한” 같은 표현만 쓰면 완료를 판단하기 어렵다. 기술 선택이 바뀔 수 있으면 특정 제품명을 요구에 고정하기보다 보호 목표와 검증 기준을 적고, 구체 기술은 설계 결정으로 관리한다.

## 요구 영역별 질문

### 식별·인증

어떤 주체를 어떤 신뢰 근거로 식별하는가, 인증 실패·잠금·복구·세션 종료를 어떻게 처리하는가를 정한다. 인증 실패 메시지가 계정 존재 여부를 과도하게 드러내지 않게 하고, 인증정보는 안전한 통신과 저장 경로를 사용하도록 요구한다. 인증 정책의 구체 수치는 조직 표준을 참조하되 근거와 버전을 기록한다.

### 인가와 직무 분리

기능 수준뿐 아니라 대상 자원과 행 수준까지 권한을 확인해야 하는지 정한다. 화면에서 버튼을 숨기는 것은 인가가 아니다. 서버의 신뢰 경계 안에서 매 요청 검증한다. 요청·승인 역할을 분리해야 하는 거래와 긴급 접근의 승인·만료·감사 요구를 적는다.

### 입력·출력·인터페이스

입력의 출처, 형식, 길이, 범위, 상태, 중복을 정의하고 거부 시 동작을 명세한다. 출력은 대상 문맥에 맞는 표현과 민감정보 최소화를 요구한다. 외부 연계는 상대 인증, 시간 제한, 재시도 조건, 중복 방지, 오류 매핑, 계약 버전과 장애 격리를 포함한다.

### 데이터 보호와 비밀

저장·전송·처리 중 보호 수준, 키와 비밀의 생성·접근·교체·폐기 책임, 백업·복구 시 보호를 정한다. 암호 알고리즘을 개발자가 임의 구현하지 않고 승인된 암호 기능과 키 관리 체계를 사용하도록 요구한다. 로그·예외·모니터링에 비밀이 남지 않아야 한다.

### 감사·탐지·대응

보안 관련 사건, 필요한 필드, 시간 동기화, 접근·무결성·보존·파기, 경보와 조사 책임을 정한다. 성공 로그만이 아니라 반복 거부, 권한 변경, 민감 기능 사용 같은 이상 신호를 탐지할 수 있어야 한다. 로그 자체가 민감 데이터가 될 수 있으므로 열람 권한을 제한한다.

### 가용성·복구

자원 제한, 시간 제한, 장애 격리, 중복 요청, 복구 시점과 데이터 복구 목표를 업무 영향과 연결한다. 정상 처리량뿐 아니라 과부하에서 우선 보호할 핵심 기능과 안전한 성능 저하 방식을 정한다. 실패 후 재시작이 중복 업무를 만들지 않아야 한다.

## 오용 사례와 위협 분석

정상 유스케이스만 보면 실패와 악용 조건이 빠진다. 오용 사례는 “비인가 사용자가 다른 고객 주문을 조회하려 한다”, “같은 결제 요청이 반복 전달된다”, “외부 연계가 응답하지 않는다”, “로그에 민감값이 포함된다”처럼 보호 목표를 위반하려는 상황을 기술한다. 구체 공격 페이로드 없이도 전제·대상·예상 방어·탐지·복구를 명세할 수 있다.

위협 분석 절차는 다음과 같다.

1. 최신 구조·데이터 흐름과 신뢰경계를 그린다.
2. 경계별 자산, 진입점, 주체, 특권 변화 지점을 표시한다.
3. 위조, 변조, 정보노출, 서비스 저하, 권한 오용 등 위협 범주로 질문한다.
4. 기존 통제와 통제 실패 시 영향을 기록한다.
5. 발생 가능성과 업무 영향의 조직 기준으로 위험을 평가한다.
6. 회피·감소·이전·수용 중 대응과 소유자·기한을 정한다.
7. 요구 ID와 설계 통제, 검증 방법에 연결한다.

위험 점수는 정밀한 진실이 아니라 우선순위 도구다. 근거 없는 숫자 곱셈만으로 결론 내리지 않고, 안전·법적 의무·대규모 개인정보·특권 경계처럼 영향이 큰 항목은 별도 기준을 적용한다. 수용된 잔여 위험은 권한 있는 책임자가 근거와 만료·재검토 조건을 승인한다.

## 보안 설계 원칙

- **최소 권한**: 구성요소·계정·기능이 필요한 권한만 가진다.
- **완전한 중재**: 캐시된 화면 상태가 아니라 신뢰 경계에서 매 요청을 검증한다.
- **안전한 기본값**: 누락·오류·알 수 없는 상태에서는 보호 쪽으로 동작한다.
- **책임 분리**: 인증, 업무 규칙, 데이터 접근, 감사 책임을 분리한다.
- **심층 방어**: 한 통제 실패가 곧 전체 침해가 되지 않도록 독립 통제를 둔다.
- **공격 표면 최소화**: 불필요한 기능·포트·데이터·권한을 제거한다.
- **단순성과 검증 가능성**: 숨은 흐름과 중복 규칙을 줄여 시험 가능하게 한다.
- **개인정보 최소화**: 목적에 필요한 최소 자료만 수집·노출·보존한다.

원칙은 구호가 아니라 설계 결정으로 나타나야 한다. 예를 들어 관리 기능은 일반 API와 분리된 권한 경계, 명시적 관리자 역할, 강화된 감사, 제한된 네트워크 경로를 가진다. 단순히 URL에 `/admin`을 넣는 것은 경계가 아니다.

## 프로그램 구조에 통제 배치

입력 형식 검증은 외부 경계에서 빠르게 수행하고, 업무 불변식은 도메인 계층에서 모든 호출 경로에 적용한다. 데이터베이스 제약은 마지막 무결성 방어선이 된다. 동일 규칙을 여러 층에 둘 때 각 층의 책임과 오류 의미를 정한다.

```text
요청 수신
  → 인증 문맥 검증
  → 자원 기반 인가
  → 형식·범위 검증
  → 업무 상태·불변식 확인
  → 원자적 상태 변경
  → 최소 감사 기록
  → 민감정보가 제거된 응답
```

외부 시스템 호출은 어댑터 경계로 격리하고 상대 인증, 제한 시간, 제한된 재시도, 중복 방지, 오류 변환을 설계한다. 비밀은 설정 파일이나 소스가 아니라 승인된 저장·주입 경로를 사용한다. 로그는 상관관계 ID로 연결하되 요청·응답 전체를 무조건 기록하지 않는다.

오류 설계는 호출자용 안정적 오류와 내부 진단 정보를 분리한다. 실패가 중간 상태를 남기지 않도록 트랜잭션과 보상 경계를 정하고, 결과가 불확실하면 성공·실패를 추정하지 않고 조회·조정 가능한 상태를 둔다.

## 설계 대안과 판단 기록

보안 통제는 기능·성능·운영성과 함께 비교한다. 다음 형식의 결정 기록을 남긴다.

| 항목 | 내용 |
|---|---|
| 결정 대상 | 주문 취소 인가 위치 |
| 대안 | 화면 제어, API 게이트웨이, 업무 서비스 자원 인가 |
| 선택 | 업무 서비스에서 매 요청 자원 기반 인가, 게이트웨이는 1차 역할 확인 |
| 근거 | 내부 호출·우회 경로에도 주문 소유권 규칙을 일관되게 적용 |
| 부작용·보완 | 조회 비용 증가, 권한 정보 캐시의 만료·무효화 설계 필요 |
| 검증 | 비소유 고객·권한 없는 상담원 거부, 역할 변경 후 재검증 |

선택하지 않은 대안을 남기면 나중에 구조가 바뀔 때 전제를 다시 검토할 수 있다. 설계 검토에는 개발자뿐 아니라 업무·운영·데이터·보안 책임자가 참여하고, 미해결 위험과 가정을 명시한다.

## 구체 업무 시나리오

고객이 주문 배송지를 변경하는 기능을 설계한다고 하자. 자산은 고객 주소, 주문 상태, 변경 감사다. 신뢰경계는 사용자–접근 계층, 접근 계층–주문 서비스, 주문 서비스–배송사 연계다. 주요 오용 사례는 다른 고객 주문 변경, 출고 후 변경, 반복 요청으로 여러 배송 지시 생성, 주소 원문 로그 노출이다.

요구는 “인증된 주문 소유자만 출고 전 주문의 배송지를 변경”, “서버가 소유권과 상태를 매 요청 검증”, “요청 ID로 중복을 판별”, “감사 기록에는 마스킹된 식별 정보와 결과만 기록”, “배송사 지연 시 내부 상태를 불확실로 보존하고 재조정 가능”으로 구체화한다.

설계에서는 인증 문맥을 주문 서비스까지 전달하되 클라이언트가 보낸 고객 ID를 신뢰하지 않는다. 주문 조회와 상태 전이를 하나의 일관성 경계에서 처리하고, 배송사 요청은 중복 방지 키와 발행함을 통해 커밋 뒤 전달한다. 감사 저장소는 응용 변경 권한과 분리한다. 각 통제는 요구 ID와 음성·장애 시험 항목에 연결한다.

## 산출물과 체크리스트

산출물은 보안 범위·가정, 자산·데이터 분류표, 주체·역할표, 데이터 흐름·신뢰경계도, 오용 사례, 위협·위험 등록부, 보안 요구사항 명세, 설계 결정 기록, 보안 구조·인터페이스·오류 설계, 요구–위협–설계–검증 추적표, 잔여 위험 승인 기록이다.

- [ ] 프로그램·데이터·로그·비밀·외부 연계의 범위가 명확하다.
- [ ] 자산의 소유자·보안 속성·손상 영향을 기록했다.
- [ ] 사람·서비스 주체와 신뢰경계를 구분했다.
- [ ] 요구마다 ID·조건·기대 동작·검증 방법·근거가 있다.
- [ ] 정상 사례와 비인가·오류·중복·장애 오용 사례가 있다.
- [ ] 위험 우선순위와 통제·소유자·기한·잔여 위험을 정했다.
- [ ] 인증·인가·입력·데이터·감사·가용성 통제를 설계에 배치했다.
- [ ] 최소 권한·안전한 기본값·심층 방어·정보 최소화를 적용했다.
- [ ] 설계 대안과 선택 근거·부작용을 기록했다.
- [ ] 요구–위협–설계–검증의 양방향 추적이 가능하다.

## 자주 틀리는 포인트

- “보안을 강화한다”처럼 시험할 수 없는 문장만 적는다.
- 시스템 구조와 신뢰경계가 오래된 상태에서 위협을 분석한다.
- 인증 성공을 인가 완료로 오해하고 대상 자원 권한을 확인하지 않는다.
- 화면의 버튼 숨김을 서버 인가 대신 사용한다.
- 외부 연계·로그·백업·빌드 산출물을 보안 범위에서 뺀다.
- 기술 제품명을 먼저 정하고 보호 목표와 검증 기준을 뒤에 맞춘다.
- 정상 유스케이스만 설계하고 거부·장애·중복 흐름을 생략한다.
- 모든 민감 데이터를 암호화하면 수집 최소화가 불필요하다고 생각한다.
- 위험 점수만 계산하고 대응 소유자·기한·잔여 위험 승인을 두지 않는다.
- 요구와 설계 통제·시험 항목의 추적 연결을 만들지 않는다.

## 확인 문제

1. 보안 요구사항을 검증 가능하게 만드는 필드를 여섯 가지 쓰시오.
2. 자산과 신뢰경계를 먼저 식별해야 하는 이유는 무엇인가?
3. 인증과 인가의 차이를 주문 조회 사례로 설명하시오.
4. 오용 사례가 정상 유스케이스를 보완하는 점을 쓰시오.
5. 위험 평가 뒤 선택할 수 있는 대응과 잔여 위험 처리 방법을 설명하시오.
6. 완전한 중재와 안전한 기본값 원칙을 각각 설명하시오.
7. 민감정보 로그 요구를 명세할 때 포함할 통제 네 가지를 쓰시오.
8. 외부 서비스 연계 설계에 필요한 방어 항목 다섯 가지를 쓰시오.
9. 설계 결정 기록에 선택하지 않은 대안과 부작용을 남기는 이유는 무엇인가?
10. 보안 요구사항을 만족하는 프로그램 설계 완료 기준을 쓰시오.

## 정답과 해설

1. 고유 ID, 대상·조건, 기대 동작, 측정 기준, 우선순위, 근거, 책임자, 검증 방법 중 여섯 가지 이상이다. 모호한 형용사 대신 관찰 가능한 결과가 있어야 한다.
2. 무엇을 어떤 경로에서 보호하는지 알아야 위협·통제 범위를 정할 수 있다. 경계가 없으면 내부 호출과 2차 데이터 흐름을 신뢰해 누락하기 쉽다.
3. 인증은 요청 주체가 누구인지 확인하는 것이고 인가는 그 주체가 해당 주문을 볼 수 있는지 확인하는 것이다. 로그인한 고객이라도 다른 고객 주문은 거부해야 한다.
4. 비인가 접근, 잘못된 상태, 중복, 지연, 통제 실패처럼 정상 흐름 밖의 조건과 예상 방어·탐지·복구를 명시하게 한다.
5. 위험 회피·감소·이전·수용을 선택하고 소유자와 기한을 둔다. 남은 위험은 권한 있는 책임자가 근거·만료·재검토 조건과 함께 승인한다.
6. 완전한 중재는 신뢰 경계에서 매 요청을 검증하는 것이고, 안전한 기본값은 정보가 없거나 오류가 날 때 보호되는 상태를 선택하는 것이다.
7. 필요한 사건·필드 정의, 민감값 제외·마스킹, 기록 무결성·접근 제한, 보존·파기, 시간·상관관계, 경보 책임 중 네 가지다.
8. 상대 인증, 안전한 전송, 시간 제한, 제한적 재시도, 중복 방지, 오류 변환, 장애 격리, 계약 버전 중 다섯 가지를 들 수 있다.
9. 구조나 전제가 바뀔 때 결정을 재평가하고, 선택의 비용과 보완 통제가 잊히지 않게 하기 위해서다.
10. 요구가 구조·데이터·인터페이스·오류 흐름의 통제로 구현 가능하게 배치되고, 오용·장애 흐름과 검증 방법이 있으며, 잔여 위험과 양방향 추적성이 승인된 상태다.

## 핵심 요약

- 보안 설계는 자산·주체·데이터 흐름·신뢰경계를 정확히 그리는 데서 시작한다.
- 보안 요구는 대상·조건·기대 동작·근거·검증 방법을 가진 독립적 문장이어야 한다.
- 정상 유스케이스뿐 아니라 비인가·중복·장애·노출 오용 사례를 분석한다.
- 최소 권한, 완전한 중재, 안전한 기본값, 심층 방어, 정보 최소화를 구조에 배치한다.
- 위험 대응과 잔여 위험은 소유자·기한·승인·재검토 조건으로 관리한다.
- 요구–위협–설계–검증의 추적성과 판단 증거가 있어야 설계 완료로 본다.
