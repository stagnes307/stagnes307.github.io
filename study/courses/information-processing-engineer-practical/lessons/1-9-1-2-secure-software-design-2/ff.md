# 1-9-1-2. 보안 강화 구현환경 구축 · 보안 강화 구현 일정계획 수립

## 수행 범위와 학습 목표

이 레슨은 승인된 보안 요구와 프로그램 설계를 실제 개발 작업으로 옮길 수 있도록 **보안 강화 구현환경 구축**을 수행하고, 의존관계·담당자·검증·승인·위험을 포함한 **보안 강화 구현 일정계획 수립**을 완성하는 실무를 다룬다. 앞 레슨의 요구·설계 자체나 다음 레슨의 보안 코드 구현을 대신하지 않고, 구현자가 안전하고 재현 가능한 환경과 현실적인 실행계획을 갖추게 하는 데 집중한다.

특정 도구 이름이나 버전을 정답처럼 고정하지 않는다. 조직이 승인한 개발·빌드·시험 도구와 대상 기술의 공식 지원 정보를 기준으로 선택하며, 지원 종료와 취약점 정보가 바뀔 수 있으므로 선정일·근거·재검토 주기를 기록한다.

학습 후에는 다음을 할 수 있어야 한다.

- 구현 요구에서 필요한 개발·빌드·시험·보안 검증 기능을 도출한다.
- 개발자 단말, 저장소, 빌드, 의존성, 비밀, 시험 데이터의 신뢰경계를 설계한다.
- 최소 권한·분리·고정된 기준선·추적성을 갖춘 환경을 구축하고 검증한다.
- 보안 구현 항목을 작업분해구조로 나누고 선후행·책임·완료 기준을 정한다.
- 검토·시험·수정·재검증·승인 시간을 포함해 일정과 자원을 산정한다.
- 환경 검증표와 일정 기준선으로 착수 가능 여부를 판단한다.

## 환경 요구사항 도출

환경 구축은 도구를 먼저 설치하는 일이 아니다. 보안 요구–설계 추적표에서 구현·검증 활동을 읽어 필요한 기능을 도출한다.

| 구현·검증 요구 | 환경에 필요한 능력 | 확인 증거 |
|---|---|---|
| 서버 자원 인가 구현 | 대표 역할·비인가 역할 시험 주체 | 허용·거부 시험 결과 |
| 비밀 외부 주입 | 승인된 비밀 저장·전달, 로그 마스킹 | 소스·빌드 로그 비밀 검사 |
| 의존성 위험 관리 | 잠금 파일, 출처 통제, 구성요소 목록·검사 | 의존성 명세와 검토 결과 |
| 정적 결함 탐지 | 언어·규칙에 맞는 분석 실행 | 기준선·신규 경고 보고서 |
| 동적·통합 시험 | 격리된 시험 서비스와 관찰 기능 | 시험 실행·로그·결과 |
| 빌드 산출물 추적 | 격리 빌드, 버전·해시·서명 정책 | 산출물 출처·무결성 기록 |

필요 기능을 필수·권장으로 나누고 대상 언어, 프레임워크, 데이터베이스, 운영환경과 호환되는지 확인한다. 도구가 보안 검사를 제공한다는 광고만으로 적합성을 판단하지 않는다. 탐지 범위, 오탐·미탐, 업데이트 방식, 결과 보관, 접근권한, 자동화 인터페이스, 라이선스·운영 책임을 검토한다.

## 환경 구성과 신뢰경계

안전한 구현환경은 다음 구성요소를 연결한다.

```text
[개발자 단말]
   │ 개인 인증·최소 권한
   ▼
[형상 저장소] ── 검토·보호 규칙
   │ 승인된 변경
   ▼
[격리 빌드 실행기] ── [승인 의존성 저장소]
   │ 검증된 산출물
   ├─ [정적·구성요소·비밀 검사]
   ▼
[시험 환경] ── 비운영 시험자료·제한된 외부 모의
   │ 승인·출처 기록
   ▼
[산출물 저장소]
```

각 경계에서 누가 쓰고 읽을 수 있는지, 어떤 자격증명을 쓰는지, 산출물이 어떻게 다음 단계로 전달되는지 정한다. 개발자가 저장소의 보호 규칙을 임의 해제하거나 빌드 산출물을 직접 바꾸어 배포 경로에 넣을 수 없어야 한다. 개발과 시험 편의를 위해 운영망·운영 데이터·운영 비밀을 그대로 연결하지 않는다.

## 개발자 단말과 작업공간

개발자 단말은 승인된 운영체제 기준선, 보안 업데이트, 디스크 보호, 화면 잠금, 악성 코드 방어, 개인 식별 인증을 적용한다. 일상 개발은 관리자 권한 없이 수행하고, 권한 상승은 승인된 설치·지원 작업에 제한한다. 불필요한 서비스와 외부 노출을 줄이며 로컬 방화벽 정책을 따른다.

프로젝트 작업공간에는 소스, 생성물, 설정, 개인 임시파일의 경계를 둔다. 비밀·운영 자료·개인정보가 저장소에 들어가지 않도록 무시 규칙만 믿지 않고 사전 검사와 검토를 둔다. 개발용 예제 비밀도 운영과 혼동되지 않는 명백한 더미여야 한다.

도구 확장과 플러그인도 실행 코드를 포함할 수 있다. 승인 출처, 필요한 권한, 업데이트 정책을 확인한다. 자동 업데이트가 무조건 안전하거나 무조건 위험한 것이 아니라, 검증·배포 속도와 공급망 통제를 조직 정책에 맞춘다.

## 형상 저장소와 변경 통제

저장소 접근은 개인 계정과 역할로 제한하고 기본 브랜치 보호, 검토 승인, 상태 검사, 강제 갱신 제한을 적용한다. 보안 관련 핵심 코드·파이프라인·권한 설정에는 책임자 검토 규칙을 둘 수 있다. 한 사람이 작성·승인·배포를 모두 수행해야 하는 소규모 상황이라면 위험과 보완 검토를 명시한다.

커밋은 요구·결함·변경 요청과 연결하고, 누가 언제 어떤 근거로 바꾸었는지 추적한다. 서명 정책을 사용하는 경우 서명 자체만 보지 말고 서명 주체의 키 수명주기와 검증 실패 처리를 정한다. 삭제된 비밀도 과거 이력에 남을 수 있으므로 노출 발견 시 비밀을 즉시 교체하고 이력 처리 여부를 별도 판단한다.

## 빌드와 의존성 환경

빌드는 가능한 한 깨끗하고 격리된 실행기에서 수행하며 입력 소스·도구체인·의존성·설정을 버전으로 식별한다. 동일 입력이 동일한 의미의 산출물을 만들 수 있도록 임의 네트워크 다운로드, 현재 시각·로컬 경로 의존, 사용자별 설정 차이를 줄인다.

의존성은 승인된 출처와 잠금 정보를 사용한다. 이름이 비슷한 임의 패키지나 검증되지 않은 저장소로 우회하지 않도록 저장소 우선순위와 허용 정책을 둔다. 구성요소 이름·버전·출처·라이선스·무결성 정보를 목록으로 만들고, 위험이 알려졌을 때 영향을 검색할 수 있게 한다.

빌드 실행기에는 필요한 저장소 읽기와 산출물 쓰기 권한만 준다. 장기 비밀을 이미지에 넣지 않고 작업 시점의 제한된 자격증명을 사용한다. 빌드 로그와 실패 덤프에 토큰·환경 변수·인증 헤더가 출력되지 않게 한다. 산출물은 빌드 후 직접 수정하지 않고 해시·출처·검사 결과와 함께 저장한다.

## 비밀과 설정 관리

비밀번호, API 키, 인증서 개인키, 서명키는 소스·일반 설정·명령행·채팅·티켓에 넣지 않는다. 환경별로 분리된 승인 저장소에서 필요한 작업에만 주입하고, 개발자 개인이 운영 비밀을 열람하지 않아도 되게 한다.

비밀마다 소유자, 용도, 접근 주체, 생성·교체·만료·폐기, 노출 대응을 정한다. 시험에는 운영과 다른 제한된 비밀을 쓴다. 로그 마스킹은 값 일부를 숨기는 것에 그치지 않고, 비밀 이름·헤더·예외 객체가 직렬화될 때의 노출도 점검한다.

설정 기준선은 보안 관련 기본값, 허용된 알고리즘·통신, 디버그 기능, 오류 노출, 세션·시간 제한 등을 환경별로 관리한다. 안전하지 않은 개발 설정이 운영에 승격되지 않게 차이를 명시하고 자동 검사를 둔다.

## 시험 환경과 시험 데이터

보안 시험 환경은 운영 구조의 중요한 신뢰경계·권한·설정을 재현하되 운영 시스템과 격리한다. 인증·역할·외부 연계의 허용·거부를 시험할 주체가 필요하다. 외부 시스템은 안전한 모의나 승인된 시험 인스턴스를 사용하고 실거래·실제 통지를 유발하지 않게 한다.

시험 데이터는 합성 자료를 우선한다. 운영 자료가 꼭 필요하면 승인, 최소 추출, 비식별, 접근·보존·파기 절차를 적용하고 재식별 위험을 검토한다. 개인정보를 단순 치환했더라도 희귀 조합이나 자유기술란으로 식별될 수 있다.

시험 환경에서 디버그 로그를 상세히 켰다면 접근과 보존을 제한하고 종료 후 삭제한다. 결함 재현 자료에 민감 원문을 그대로 붙이지 않는다. 시간·동시성·외부 장애 시험은 환경 공유 사용자에게 영향을 주지 않도록 실행창과 자원 한도를 정한다.

## 보안 검증 도구 배치

환경에는 코드 검토, 정적 분석, 구성요소·라이선스 검사, 비밀 탐지, 단위·통합·동적 시험, 설정 검사 등 설계 요구에 맞는 검증 단계를 배치한다. 모든 도구를 무작정 넣는 것이 아니라 어떤 결함 범주를 어느 단계에서 찾는지 검증 전략에 연결한다.

검사 결과는 심각도만으로 자동 실패시키기보다 프로젝트 기준선과 신규 결함 정책, 예외 승인, 재검토 기한을 정한다. 오래된 경고를 숨기기 위해 전체를 기준선 처리하지 않는다. 도구 규칙·엔진·의존성 정보의 업데이트도 변경으로 기록하며, 업데이트 때문에 결과가 달라지면 영향을 평가한다.

도구가 코드를 외부 서비스로 전송하는지, 저장 위치·보존·학습 사용·접근 통제가 무엇인지 확인한다. 비공개 소스와 민감 설정의 처리 조건이 조직 요구와 맞지 않으면 격리형 대안을 검토한다.

## 환경 구축 절차와 완료 판단

1. 보안 요구·설계에서 구현·시험 활동과 필요한 환경 능력을 추출한다.
2. 현재 환경·도구·권한·데이터 흐름을 조사해 차이를 기록한다.
3. 도구·버전·출처·지원성·운영 책임을 평가하고 승인받는다.
4. 단말·저장소·빌드·시험·산출물 저장소의 신뢰경계와 권한을 설계한다.
5. 형상·빌드·의존성·비밀·시험자료 기준선을 구축한다.
6. 보안 검사를 파이프라인과 로컬 검토 흐름에 연결한다.
7. 대표 소스로 빌드·시험·검사·산출물 승격 전 과정을 실행한다.
8. 허용·거부 접근, 비밀 비노출, 출처·해시 추적, 실패 시 중단을 확인한다.
9. 설치·운영·업데이트·장애·복구 절차와 담당자를 문서화한다.
10. 환경 검증표의 미해결 차이와 잔여 위험을 승인하고 기준선을 고정한다.

완료 기준은 도구 설치 성공이 아니라 승인된 소스만 빌드되고, 주체별 최소 권한이 적용되며, 의존성·비밀·시험 데이터가 통제되고, 보안 검사가 반복 실행되며, 산출물 출처와 결과가 추적되고, 실패·복구 절차가 실제로 확인된 상태다.

## 일정계획의 작업분해

**보안 강화 구현 일정계획 수립**에서는 “보안 구현 5일”처럼 한 줄로 잡지 않는다. 요구 ID와 설계 구성요소를 다음 작업으로 분해한다.

- 환경 차이 분석과 접근 승인
- 구현환경 구축·검증·팀 온보딩
- 요구별 보안 코드 작성과 단위 확인
- 코드 검토·정적·구성요소·비밀 검사
- 통합·권한 거부·오류·장애 시험
- 발견 결함 분류·수정·재시험
- 문서·운영 절차·배포 준비
- 잔여 위험·예외·출시 승인

각 작업에는 입력, 산출물, 담당 책임자, 검토자, 예상 공수, 선행 작업, 시작·완료 조건을 둔다. 사람 수를 늘리면 즉시 기간이 줄어든다고 가정하지 않는다. 같은 모듈 충돌, 검토자 병목, 시험 환경 공유, 전문성 학습 시간을 반영한다.

## 의존관계와 마일스톤

환경 접근 승인이 늦으면 구현·시험이 모두 밀릴 수 있다. 위협 분석 미결 항목, 외부 인증 서비스 시험 계정, 시험 데이터 승인, 보안 검토자 일정, 의존성 교체 결정 같은 외부 선행을 일정에 표시한다.

```text
요구·설계 기준선
  ├─ 환경 구축 ─ 검증 ─ 팀 사용 가능
  ├─ 요구별 구현 ─ 동료 검토 ─ 단위 확인
  └─ 시험 설계·데이터 준비
              ↓
       통합 보안 시험
              ↓
       결함 수정·재시험
              ↓
       잔여 위험·출시 승인
```

마일스톤은 날짜만이 아니라 종료 조건을 가진다. “환경 준비 완료”는 대표 빌드·검사 성공과 권한 거부 시험 통과, “구현 완료”는 코드 저장이 아니라 요구 추적·검토·단위 확인 완료, “출시 준비”는 중대한 미해결 결함과 승인 없는 예외가 없는 상태다.

## 산정·여유·변경 관리

산정은 유사 작업 실적, 모듈 복잡도, 변경 규모, 팀 숙련도, 시험 조합, 외부 의존성을 근거로 한다. 보안 작업에는 분석·구현뿐 아니라 검토, 오탐 판정, 결함 수정, 회귀 시험, 증거 정리 시간이 든다. 결함이 하나도 없다는 가정으로 출시일을 잡지 않는다.

위험이 큰 선행 작업에는 일정 여유와 대체 경로를 둔다. 환경 제공 지연, 도구 호환 실패, 중요 의존성 교체, 검토자 부재를 위험 등록부에 연결한다. 일정이 압박받을 때 보안 시험을 조용히 삭제하지 않고 범위·위험·대안을 권한 있는 책임자에게 올린다.

기준선 이후 변경은 요구 ID, 영향 모듈, 추가 시험, 환경·자원·출시 영향으로 평가한다. 일정 변경 이력과 승인자를 남긴다. 완료율은 “코드 90%” 같은 주관값보다 요구별 산출물과 종료 조건으로 측정한다.

## 구체 업무 시나리오

주문 취소 기능의 보안 강화를 4주 내 수행한다고 하자. 환경 차이 분석에서 운영 비밀이 개발 설정 예시에 남아 있고, 빌드가 외부 저장소에서 임의 버전을 받으며, 비인가 역할 시험 계정이 없다는 문제가 발견되었다. 첫 주 작업에 비밀 교체·외부 주입, 승인 의존성 저장소와 잠금, 역할별 시험 계정 마련을 배치한다.

환경 검증은 대표 브랜치가 격리 빌드에서 성공하고 비밀·구성요소·정적 검사가 실행되며, 산출물 해시와 소스 버전이 연결되고, 개발자가 산출물을 직접 덮어쓸 수 없는지 확인하는 것이다. 이 조건을 만족한 뒤 자원 인가와 중복 요청 방어 구현에 착수한다.

둘째 주 구현·단위 확인, 셋째 주 검토와 통합·거부·장애 시험, 넷째 주 결함 수정·재시험·출시 승인을 계획한다. 외부 인증 시험 인스턴스 제공을 선행 위험으로 두고 모의 어댑터 대안을 준비한다. 각 마일스톤은 요구 추적률, 미해결 결함 기준, 검토 승인이라는 종료 조건을 가진다.

## 산출물과 체크리스트

산출물은 환경 요구·차이 분석표, 구조·신뢰경계도, 도구·버전·출처 목록, 접근 권한표, 설정 기준선, 비밀·의존성·시험자료 관리절차, 파이프라인 검증 결과, 환경 운영·복구 안내서, 작업분해구조, 선후행도, 자원·공수 산정, 마일스톤·종료 조건, 위험·변경 등록부다.

- [ ] 보안 요구마다 구현·검증 환경 능력이 연결된다.
- [ ] 단말·저장소·빌드·시험·산출물 경계와 권한이 명확하다.
- [ ] 승인된 도구·의존성 출처와 기준 버전을 추적한다.
- [ ] 운영 비밀·자료가 개발·시험에 직접 복제되지 않는다.
- [ ] 보안 검사가 반복 가능하고 결과·예외가 기록된다.
- [ ] 대표 빌드에서 출처·해시·검사 결과가 산출물과 연결된다.
- [ ] 일정 작업마다 담당자·입력·산출물·선행·종료 조건이 있다.
- [ ] 검토·수정·재시험·승인 공수와 외부 의존성을 반영했다.
- [ ] 일정 위험에 여유·대체 경로·보고 기준이 있다.
- [ ] 환경·일정 기준선 변경의 영향과 승인을 기록한다.

## 자주 틀리는 포인트

- 보안 도구 설치 개수를 환경 구축 완료 기준으로 삼는다.
- 개발자에게 저장소·빌드·배포 전체 관리자 권한을 준다.
- 운영 비밀과 개인정보를 개발·시험 편의상 복사한다.
- 잠금 정보 없이 빌드 때마다 최신 의존성을 내려받는다.
- 빌드 로그·오류 덤프의 토큰과 환경 변수 노출을 놓친다.
- 도구 오탐이 있다는 이유로 모든 경고를 기준선에서 숨긴다.
- 구현 일정에 검토·결함 수정·회귀 시험 시간을 넣지 않는다.
- 외부 승인·시험 환경·전문 검토자의 선행관계를 표시하지 않는다.
- 마일스톤을 날짜로만 정의하고 종료 조건을 두지 않는다.
- 일정 압박을 이유로 보안 활동을 승인 없이 생략한다.

## 확인 문제

1. 보안 강화 구현환경의 주요 구성요소 여섯 가지를 쓰시오.
2. 보안 요구에서 환경 요구를 도출하는 방법을 예로 설명하시오.
3. 격리되고 재현 가능한 빌드가 필요한 이유는 무엇인가?
4. 의존성 관리에서 출처·잠금·구성요소 목록이 각각 제공하는 통제를 쓰시오.
5. 시험 데이터에 운영 개인정보를 그대로 사용하면 안 되는 이유와 대안을 쓰시오.
6. 구현환경 완료 판단이 도구 설치 성공과 다른 점을 설명하시오.
7. 보안 구현 일정의 작업마다 정의해야 할 항목을 쓰시오.
8. 일정에 결함 수정과 재시험 시간을 포함해야 하는 이유는 무엇인가?
9. 마일스톤 종료 조건의 예를 환경 준비와 출시 준비에 각각 쓰시오.
10. 일정 압박으로 보안 활동을 줄여야 할 때 올바른 처리 절차를 쓰시오.

## 정답과 해설

1. 개발자 단말, 형상 저장소, 격리 빌드 실행기, 승인 의존성 저장소, 보안 검사, 시험 환경, 산출물 저장소 중 여섯 가지다.
2. 예를 들어 자원 인가 요구에서 허용·비인가 역할 시험 주체와 음성 시험 기능을, 비밀 보호 요구에서 외부 주입과 로그 비노출 검사를 도출한다.
3. 개발자별 숨은 설정과 임의 다운로드를 줄이고 승인된 입력으로 만들어진 산출물임을 반복 검증·추적하기 위해서다.
4. 출처 통제는 신뢰하지 않은 저장소 사용을 막고, 잠금은 선택 버전을 고정하며, 구성요소 목록은 알려진 위험 발생 시 영향 범위를 찾게 한다.
5. 불필요한 개인정보 노출·재식별·보존 문제가 생긴다. 합성 데이터를 우선하고 꼭 필요하면 승인·최소 추출·비식별·접근·파기 통제를 적용한다.
6. 승인 입력만 빌드되고 최소 권한·비밀·의존성·시험자료가 통제되며 검사 반복성과 산출물 출처·복구가 실제 검증되어야 완료다.
7. 입력, 산출물, 담당자·검토자, 공수, 선행 작업, 시작·종료 조건, 관련 요구와 위험을 정의한다.
8. 보안 검사는 결함과 오탐 판정을 발생시키며 수정 뒤 회귀 확인이 필요하다. 이를 빼면 출시 직전에 일정이 무너지거나 결함을 승인 없이 남기게 된다.
9. 환경 준비는 대표 빌드·검사와 권한 거부 시험 통과, 출시 준비는 중대한 미해결 결함과 무승인 예외가 없고 추적·운영 절차가 승인된 상태다.
10. 생략 범위가 요구·위험·시험·출시에 미치는 영향을 분석하고 대안과 잔여 위험을 권한 있는 책임자에게 보고해 승인·기한·재검토를 기록한다.

## 핵심 요약

- 구현환경은 단말부터 저장소·빌드·의존성·시험·산출물까지 이어지는 신뢰경계다.
- 최소 권한, 승인 출처, 고정된 기준선, 비밀 외부 주입, 시험자료 분리를 적용한다.
- 보안 도구는 탐지 범위·결과 처리·업데이트·정보 전송 조건을 검토해 배치한다.
- 환경 완료는 대표 흐름의 빌드·검사·출처·거부·복구 증거로 판단한다.
- 일정은 요구별 작업, 선후행, 책임, 검토·수정·재시험, 마일스톤 종료 조건을 포함한다.
- 환경과 일정의 위험·변경·잔여 위험은 기준선과 승인 기록으로 통제한다.
