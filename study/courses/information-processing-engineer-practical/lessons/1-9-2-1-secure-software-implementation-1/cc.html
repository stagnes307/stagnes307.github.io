01

수행 범위와 학습 목표

이 레슨은 승인된 보안 요구·설계·일정과 구현환경을 기준으로 계획에 따른 보안 강화 프로그램 구현을 수행하고, 구현 결과에 남은 보안·품질 문제를 찾기 위한 구현 프로그램 결함 테스트를 수행하는 실무를 다룬다. 공격 기술을 재현하는 것이 아니라 신뢰할 수 없는 입력과 실패 조건에서도 프로그램이 안전한 상태를 유지하도록 예방 통제를 구현하고, 정상·경계·거부·오류 시험으로 이를 입증하는 데 집중한다.

결함 생명주기는 다음 레슨에서 다룬다. 여기서는 코드 작성, 검토, 자동·수동 시험과 결함 증거 생성까지가 범위다.

학습 후에는 다음을 할 수 있어야 한다.

  • 요구 ID와 설계 통제를 구현 작업·코드·시험에 연결한다.
  • 입력 검증, 자원 인가, 안전한 데이터 접근, 출력 처리, 비밀·오류·로그 통제를 구현한다.
  • 트랜잭션·동시성·외부 장애에서도 중복·부분 완료를 방지한다.
  • 코드 검토와 정적·구성요소·비밀 검사 결과를 판정한다.
  • 단위·통합·인터페이스·동적 시험에서 허용과 거부를 함께 검증한다.
  • 결함 재현 조건·영향·증거를 민감정보 없이 기록하고 재시험 가능하게 만든다.
02

구현 착수 전 기준선

구현자는 다음 입력을 확인한다.

  • 승인된 보안 요구사항과 우선순위
  • 위협·오용 사례와 보안 설계 결정
  • 데이터·인터페이스·오류·감사 명세
  • 구현환경 기준선과 승인 도구·의존성
  • 작업분해구조, 담당자, 선후행, 완료 조건
  • 코딩 표준, 검토 규칙, 시험 전략과 출시 기준

요구가 모호하거나 설계 전제가 현재 구조와 다르면 임의로 해석해 코드에 숨기지 않는다. 질문·결정 기록으로 기준선을 갱신하고 영향과 승인을 확인한다. 구현 순서는 위험과 의존성을 고려하되, 인증·인가·데이터 경계처럼 여러 기능이 의존하는 통제를 먼저 안정화한다.

03

신뢰경계에서 입력 검증

입력 검증은 “특수문자를 모두 제거”하는 작업이 아니다. 각 필드의 허용 형식·길이·범위·열거값·관계·현재 업무 상태를 정의해 허용목록으로 확인한다. 구문 검증과 업무 의미 검증을 구분한다.

코드 예시 · text

validateCancelRequest(request):
    require request.orderId matches approved identifier format
    require request.reasonCode belongs to allowed reason set
    require normalized note length <= documented limit
    reject unknown fields when contract requires strict schema
    return immutable validated command

식별자 형식이 맞아도 해당 주문이 취소 가능한 상태인지는 업무 계층에서 확인한다. 클라이언트가 계산한 금액·역할·소유자·상태를 신뢰하지 않고 서버의 권위 있는 자료로 재확인한다. 정규화 전후 길이와 의미가 달라질 수 있는 문자 입력은 저장·비교 정책을 명확히 한다.

파일은 크기·형식·구조·저장 위치·자원 한도를 검증하고 서버가 이름을 생성한다. 자원 소비가 큰 처리는 격리하며 거부·관찰 기준을 시험한다.

04

인증 문맥과 자원 기반 인가

인증은 검증된 미들웨어나 플랫폼이 만든 주체 문맥을 사용하고, 클라이언트가 보낸 userId나 역할 문자열을 권한 근거로 쓰지 않는다. 인가는 서버에서 기능과 대상 자원을 함께 검사한다.

코드 예시 · text

cancelOrder(actor, orderId, requestId):
    order ← repository.findForDecision(orderId)
    require actor is authenticated
    require policy.canCancel(actor, order)
    require order.status is cancellable
    return executeIdempotently(requestId, order)

라우트에서 역할을 한 번 확인했더라도 업무 서비스가 다른 내부 경로에서 호출될 수 있으면 핵심 자원 인가를 업무 경계에 둔다. 목록 조회는 반환되는 모든 행에 같은 범위 정책이 적용되는지 확인한다. 관리 기능은 일반 사용자 경로와 권한·감사를 분리하고, 승인 없는 역할 상승을 막는다.

권한 실패는 안전하게 거부하고 내부 정책·대상 존재 여부를 불필요하게 노출하지 않는다. 하지만 운영자는 상관관계 ID와 서버 감사 기록으로 거부 이유를 조사할 수 있어야 한다.

05

안전한 데이터 접근

값 입력은 문자열 연결이 아니라 매개변수화 쿼리나 안전한 데이터 접근 API로 전달한다.

코드 예시 · sql

SELECT order_id, owner_id, status, version_no
FROM orders
WHERE order_id = :order_id;

테이블명·정렬 열처럼 SQL 식별자를 동적으로 선택해야 한다면 사용자가 준 문자열을 직접 붙이지 않고 승인된 열거값을 코드의 고정 식별자로 매핑한다. 필요하지 않은 열을 SELECT *로 가져오지 않고 민감 데이터 접근을 최소화한다.

트랜잭션 경계는 업무 불변식을 보호한다. “권한·상태 확인 후 변경” 사이의 동시 변경을 고려해 버전 열, 조건부 갱신, 적절한 잠금 등 설계된 방법을 사용한다. 오류가 나면 부분 변경을 커밋하지 않는다. 데이터베이스 오류 원문과 구조를 외부 응답에 노출하지 않는다.

코드 예시 · text

updated ← UPDATE orders
          SET status = CANCELLED, version_no = version_no + 1
          WHERE order_id = command.orderId
            AND status = PAID
            AND version_no = command.expectedVersion
IF updated count != 1
    return conflict_or_not_allowed

이 예시는 제품 문법이 아니라 원자적 조건 갱신의 판단 구조다. 실패 이유를 다시 조회할 때도 권한을 유지하고 시간차를 고려한다.

06

출력·직렬화·오류 처리

출력은 HTML·JSON·로그·파일명 등 사용 문맥에 맞게 처리한다. 검증된 기본 이스케이프와 안전한 직렬화를 쓰며, 예외는 좁은 범위와 검토를 둔다.

응답 DTO에는 필요한 필드만 명시한다. 내부 엔터티를 그대로 직렬화하면 비밀번호 해시, 내부 위험 점수, 권한 플래그가 새 필드 추가와 함께 노출될 수 있다. 오류 응답은 안정적인 코드와 사용자 조치 메시지를 제공하고 스택·쿼리·내부 경로는 서버 진단 기록으로 제한한다.

예외를 무조건 잡아 성공으로 반환하거나 빈 목록으로 바꾸면 탐지와 데이터 정확성을 해친다. 예상 업무 오류, 일시 외부 오류, 내부 시스템 오류를 구분해 트랜잭션·재시도·응답·경보 정책을 적용한다.

07

비밀·암호·민감정보

비밀은 승인 저장소에서 실행 시 주입하고 소스·일반 설정·빌드 산출물·로그에 넣지 않는다. 접근은 서비스의 최소 권한으로 제한하고 교체 시 연결·캐시가 갱신되는지 확인한다. 비밀 노출이 의심되면 문자열 삭제만으로 끝내지 않고 비밀을 교체하고 사용 기록과 영향을 조사한다.

암호 기능은 승인된 라이브러리와 키 관리 기능을 사용한다. 자체 알고리즘이나 임의 키 파생을 만들지 않는다. 저장·전송 보호 목적, 키 소유자, 교체·복구·폐기, 실패 동작을 설계와 일치시킨다. 알고리즘과 매개변수는 조직 표준과 대상 플랫폼의 현재 공식 권고를 참조한다.

개인정보는 수집·조회·응답·로그·캐시에서 최소화한다. 마스킹값도 다른 자료와 결합하면 식별될 수 있으므로 접근과 보존을 통제한다. 메모리 덤프·진단 파일·시험 결과에 민감값이 남는지도 확인한다.

08

외부 연계와 가용성 통제

외부 주소는 승인 설정에서 정하고 임의 목적지 선택을 막는다. 상대 인증과 안전한 통신, 연결·응답 시간 제한, 제한 재시도와 호출량 제한을 적용한다.

모든 오류를 재시도하지 않는다. 입력 거부·권한 오류는 반복해도 성공하지 않고, 시간 초과는 상대가 처리했는지 불확실할 수 있다. 같은 업무 요청 ID나 중복 방지 키를 사용하고 상태 조회·조정 절차를 둔다. 재시도 폭주로 장애를 키우지 않도록 회로 차단이나 큐 격리를 설계대로 적용한다.

자원은 성공과 실패 경로 모두에서 해제한다. 요청 본문·페이지 크기·동시 작업·메모리·파일·쿼리 시간에 한도를 둔다. 과부하에서는 무제한 대기보다 제한된 거부와 핵심 기능 보호가 안전할 수 있다.

09

감사와 관찰 구현

감사 사건은 로그인·권한 변경·민감 조회·상태 변경·보안 거부·설정 변경 등 요구에서 정한 항목만 일관된 구조로 기록한다. 필드는 검증된 주체 ID, 사건 유형, 대상 식별자, 결과, 서버 시각, 상관관계 ID, 승인·요청 ID를 포함할 수 있다. 비밀번호·토큰·인증 헤더·전체 개인정보는 제외한다.

로그 문자열 연결보다 구조화 기록 API를 사용하고 로그 실패가 핵심 거래에 미치는 정책을 정한다. 감사 무결성이 필수인 변경에서 기록 실패를 무시해서는 안 된다. 반대로 일반 진단 로그 장애가 모든 요청을 중단시키는 것도 가용성 요구와 비교해야 한다.

운영 지표에는 인증·인가 거부율, 외부 시간 초과, 재시도, 자원 제한 거부, 중요 오류를 포함해 구현 결함과 비정상 상태를 탐지한다. 경보는 소유자와 대응 절차가 있어야 한다.

10

코드 검토

동료 검토는 스타일 확인이 아니라 요구·위협·설계와 코드의 일치를 확인한다.

  • 신뢰할 수 없는 입력이 모두 경계에서 검증되는가?
  • 인증 주체와 대상 자원의 인가를 서버가 확인하는가?
  • 쿼리·출력·파일·외부 호출이 문맥에 맞는 안전한 API를 쓰는가?
  • 트랜잭션·동시성·중복·오류 흐름이 설계와 같은가?
  • 비밀·민감정보가 소스·로그·응답·시험자료에 노출되지 않는가?
  • 기본 실패가 거부·롤백·제한 등 안전한 상태인가?
  • 신규 의존성과 설정 변경의 출처·권한·운영 영향이 검토되었는가?

큰 변경 하나보다 요구 단위의 작은 검토가 이해하기 쉽다. 생성 코드와 설정·마이그레이션·파이프라인도 검토 범위에 포함한다. 의견이 해결되었는지와 승인자를 기록한다.

11

정적·구성요소·비밀 검사

정적 분석은 실행하지 않고 코드 패턴·데이터 흐름·오류를 찾는다. 규칙이 해당 언어·프레임워크와 프로젝트 구조에 맞는지 확인한다. 결과는 위치, 경로, 실제 도달 가능성, 기존 통제를 검토해 참·오탐·추가 확인으로 판정한다.

구성요소 검사는 직접·전이 의존성, 출처, 버전, 알려진 위험, 지원 상태를 확인한다. 단순 심각도뿐 아니라 실제 포함·호출 여부, 배포 환경, 완화 통제, 수정 가능 버전을 본다. 예외는 소유자·근거·만료·재검토를 둔다.

비밀 검사는 현재 소스뿐 아니라 변경 이력과 빌드 로그·산출물을 확인할 수 있다. 발견 값은 결과 보고서에 그대로 복사하지 않는다. 진짜 비밀이면 즉시 교체하고 접근·사용 흔적을 조사한다.

자동 검사에는 미탐이 있고 업무 인가·상태 전이를 이해하기 어려우므로 검토와 실행 시험을 결합한다.

12

단위·통합·인터페이스 결함 테스트

시험은 요구와 오용 사례에서 도출한다.

단위·통합·인터페이스 결함 테스트 · 학습 표 2
시험 범주예기대 결과
정상 허용소유 고객의 취소 가능 주문한 번 취소, 감사 기록
권한 거부인증됐지만 비소유 주문 요청상태 불변, 안정적 거부·감사
경계 입력최대 길이, 최소·최대 금액명세대로 허용 또는 거부
상태 오류이미 배송된 주문 취소변경 없음, 업무 오류
중복·동시같은 요청 반복·동시 상태 변경결과 한 번, 충돌 안전 처리
외부 장애지연·연결 실패·불확실 응답시간 제한, 제한 재시도, 조정 상태
정보 노출오류·로그·응답 필드 점검비밀·내부 정보 없음
자원 한도큰 페이지·많은 동시 요청제한된 거부, 자원 회수

단위 시험은 정책·검증·상태 전이를 빠르게 확인한다. 통합 시험은 실제 직렬화, 데이터베이스 제약·트랜잭션, 인증 문맥과 구성 상호작용을 확인한다. 인터페이스 시험은 계약·상대 인증·시간 제한·오류 매핑을 본다. 동적 시험은 실행 중 노출과 설정 문제를 찾지만 승인된 격리 환경·범위에서 안전하게 수행한다.

각 시험에는 요구 ID, 전제, 입력 범주, 실행 단계, 기대 결과, 실제 결과, 증거, 환경·소스 버전을 둔다. 민감 원문이나 실제 자격증명을 증거에 넣지 않는다. 실패 재현은 최소한의 안전한 데이터로 반복 가능해야 한다.

13

구현·시험 절차와 판단 기준

  1. 요구·설계·일정 기준선과 담당 구현 단위를 확인한다.
  2. 구현 전 음성·오류·동시성 시험을 포함한 기대 결과를 작성한다.
  3. 승인 API·의존성·설정으로 작은 단위의 통제를 구현한다.
  4. 로컬 단위 시험과 정적·비밀 검사를 수행한다.
  5. 동료가 요구 추적과 신뢰경계·오류 흐름을 검토한다.
  6. 격리 환경에서 통합·인터페이스·권한 거부·장애 시험을 실행한다.
  7. 구성요소와 실행 설정, 로그·응답의 민감정보를 확인한다.
  8. 발견 결함을 재현 가능한 증거와 요구 영향으로 등록한다.
  9. 수정 후 직접 시험과 영향 범위 회귀 시험을 반복한다.
  10. 요구별 구현·검토·시험 증거와 미해결 위험을 종합해 완료를 판단한다.

완료는 코드가 컴파일되는 상태가 아니다. 요구 통제가 모든 호출 경로에 적용되고, 허용·거부·경계·오류·중복·동시·장애 시험이 기대대로이며, 중요한 검사 결과가 해결 또는 승인되고, 민감정보 비노출·최소 권한·산출물 추적성이 확인되어야 한다.

14

구체 업무 시나리오

주문 취소 API를 강화한다고 하자. 요구는 주문 소유자 또는 승인 상담원만 출고 전 취소할 수 있고, 반복 요청은 한 번만 처리되며, 외부 환불 결과가 불확실하면 성공으로 단정하지 않는 것이다. 구현자는 검증된 인증 문맥을 사용하고 주문을 조회한 뒤 자원 인가와 상태를 검사한다. 요청 ID 저장과 조건부 상태 갱신으로 중복·동시 실행을 통제한다.

환불 연계에는 승인 주소, 상대 인증, 시간 제한과 제한적 재시도를 적용한다. 거래 커밋 뒤 전달할 요청을 발행함에 기록하고 상태 조회로 결과를 조정한다. 응답에는 내부 결제 식별자와 예외를 노출하지 않고, 감사에는 주체·주문·결과·상관관계만 남긴다.

시험은 소유자 성공, 비소유자·역할 없는 상담원 거부, 배송 상태 거부, 같은 요청 반복, 두 주체의 동시 취소, 환불 지연·불확실 결과, 로그·응답 비밀 비노출을 포함한다. 각 결과가 요구 ID에 추적되고 직접·회귀 시험이 통과할 때 구현 완료로 판단한다.

15

산출물과 체크리스트

산출물은 요구–설계–코드–시험 추적표, 보안 구현 코드·설정, 검토 기록, 단위·통합·인터페이스 시험 명세와 결과, 정적·구성요소·비밀 검사 보고서, 결함 증거, 성능·자원 확인 결과, 잔여 위험·예외 기록이다.

  • [ ] 승인 요구·설계·환경·일정 기준선에서 구현했다.
  • [ ] 입력은 형식·범위·업무 상태까지 신뢰경계에서 검증한다.
  • [ ] 인증 문맥을 검증하고 기능·대상 자원의 인가를 서버에서 수행한다.
  • [ ] 쿼리 매개변수화, 문맥별 출력 처리, 명시적 응답 필드를 사용한다.
  • [ ] 비밀·개인정보가 소스·로그·오류·시험 증거에 없다.
  • [ ] 트랜잭션·동시성·중복·외부 불확실 결과가 안전하게 처리된다.
  • [ ] 정적·구성요소·비밀 검사 결과를 근거로 판정했다.
  • [ ] 정상뿐 아니라 거부·경계·오류·동시·장애 시험을 수행했다.
  • [ ] 결함 수정 뒤 직접 시험과 영향 회귀 시험을 통과했다.
  • [ ] 소스·환경·요구·검토·시험 증거가 양방향 추적된다.
16

자주 틀리는 포인트

  • 클라이언트가 보낸 사용자 ID와 역할을 권한 근거로 신뢰한다.
  • 형식 검증만 하고 현재 업무 상태와 자원 소유권을 확인하지 않는다.
  • 문자열 치환 하나를 SQL·HTML·로그 모든 문맥에 사용한다.
  • 내부 엔터티를 그대로 응답해 새 민감 필드가 자동 노출된다.
  • 시간 초과를 실패 확정으로 보고 외부 업무를 중복 요청한다.
  • 예외를 잡아 빈 결과나 성공으로 바꾸어 결함을 숨긴다.
  • 비밀을 소스에서 삭제한 것으로 노출 대응이 끝났다고 생각한다.
  • 자동 보안 도구 통과를 결함 없음의 증거로 오해한다.
  • 허용 기능만 시험하고 비인가·오류·중복 흐름을 생략한다.
  • 수정한 시험만 재실행하고 영향 범위 회귀 시험을 하지 않는다.
17

확인 문제

  1. 보안 구현 착수 전에 확인할 기준선 다섯 가지를 쓰시오.
  2. 형식 검증과 업무 의미 검증의 차이를 주문 취소로 설명하시오.
  3. 서버 자원 기반 인가가 필요한 이유는 무엇인가?
  4. SQL 식별자를 동적으로 선택해야 할 때 안전하게 처리하는 방법을 쓰시오.
  5. 조건부 갱신이 동시성 결함을 줄이는 원리를 설명하시오.
  6. 외부 호출 시간 초과 결과를 실패로 단정하면 안 되는 이유와 대응을 쓰시오.
  7. 정적·구성요소·비밀 검사가 각각 찾는 문제를 설명하시오.
  8. 보안 결함 테스트에 정상 시험 외 어떤 범주를 포함해야 하는지 다섯 가지 쓰시오.
  9. 결함 증거에 환경·소스 버전과 안전한 재현 조건이 필요한 이유는 무엇인가?
  10. 계획에 따른 보안 강화 프로그램 구현 완료 기준을 쓰시오.
18

정답과 해설

  1. 보안 요구, 위협·설계 결정, 인터페이스·오류·감사 명세, 구현환경 기준선, 일정·담당, 코딩·시험 기준 중 다섯 가지다.
  2. 주문 ID 형식과 사유 길이 확인은 형식 검증이고, 주문이 출고 전인지·요청자가 소유자 또는 승인 역할인지 확인하는 것은 업무 의미 검증이다.
  3. 로그인 사실만으로 모든 자원 접근이 허용되지 않는다. 다른 고객 주문이나 권한 범위 밖 대상의 접근을 매 요청 서버에서 차단해야 한다.
  4. 사용자 문자열을 SQL에 연결하지 않고 허용된 선택값을 코드의 고정된 열·방향 식별자로 매핑한다. 값은 매개변수화한다.
  5. 읽은 버전·상태가 그대로일 때만 원자적으로 변경해 확인과 수정 사이에 다른 트랜잭션이 바꾼 상태를 덮어쓰지 않는다.
  6. 상대가 처리했지만 응답만 늦었을 수 있다. 같은 중복 방지 키를 유지하고 상태 조회·조정으로 확정하며 재시도 횟수와 시간을 제한한다.
  7. 정적 분석은 코드 패턴·흐름, 구성요소 검사는 의존성 출처·알려진 위험·지원 상태, 비밀 검사는 소스·이력·로그의 자격증명 흔적을 찾는다.
  8. 비인가 거부, 경계 입력, 잘못된 상태, 중복·동시성, 외부 장애, 정보 노출, 자원 한도 중 다섯 가지를 포함한다.
  9. 같은 빌드와 설정에서 반복해 원인을 확인하고 수정 전후를 비교해야 하기 때문이다. 실제 비밀·민감 데이터는 증거에서 제거한다.
  10. 요구 통제가 모든 경로에 적용되고 검토와 자동·수동 검사가 완료되며 허용·거부·오류·동시·장애 시험이 통과하고 미해결 위험과 추적성이 승인된 상태다.
19

핵심 요약

  • 구현은 승인된 요구·설계·환경·일정과 시험 기대값을 기준으로 수행한다.
  • 입력 검증, 서버 자원 인가, 매개변수화 데이터 접근, 문맥별 출력 처리를 적용한다.
  • 비밀·민감정보·오류·감사를 최소 권한과 최소 노출 원칙으로 구현한다.
  • 트랜잭션·동시성·중복·외부 불확실 결과에서도 안전한 상태를 유지한다.
  • 코드 검토와 정적·구성요소·비밀 검사, 단위·통합·거부·장애 시험을 결합한다.
  • 완료는 코드 성공이 아니라 요구별 구현·검토·시험·재검증·추적 증거로 판단한다.
