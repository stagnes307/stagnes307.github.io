01

수행 범위와 학습 목표

이 레슨은 코드 검토와 정적·구성요소·비밀·단위·통합·동적 시험에서 나온 문제를 일관되게 접수·분석·수정·재검증·종료하는 테스트에서 발견된 결함 관리를 다룬다. 또한 앞선 보안 요구 명세, 설계, 환경·일정, 구현·시험을 하나의 통제 흐름으로 묶는 SW개발 보안 구현하기의 적용 절차와 판단 기준을 정리한다.

보안 결함 정보는 그 자체로 민감할 수 있다. 재현에 필요한 최소 정보와 방어적 증거를 기록하되, 실제 시스템 침해에 바로 사용할 수 있는 상세 페이로드·운영 자격증명·민감 원문은 제한된 저장소에도 불필요하게 복사하지 않는다.

학습 후에는 다음을 할 수 있어야 한다.

  • 여러 시험 결과를 같은 결함 기준으로 정규화하고 중복을 연결한다.
  • 재현 가능성·영향·악용 전제·기존 통제로 심각도와 우선순위를 판단한다.
  • 소유자·목표 기한·수정안·검증 범위·공개 범위를 정한다.
  • 수정 전후의 직접 시험과 영향 범위 회귀 시험으로 해결을 입증한다.
  • 위험 수용·완화·오탐 결정을 근거·승인·만료와 함께 관리한다.
  • 보안 개발 전 과정의 착수·단계 완료·출시 판단 기준을 설명한다.
02

결함과 관찰사항의 구분

결함은 승인된 요구, 설계, 코딩·설정 기준, 기대 시험 결과에서 벗어난 상태다. 도구 경고는 곧바로 확정 결함이 아니다. 같은 코드 위치라도 실행 경로·입력 통제·배포 설정에 따라 실제 영향이 다르며, 반대로 도구가 경고하지 않아도 업무 인가나 상태 전이 결함은 존재할 수 있다.

초기 분류는 다음처럼 할 수 있다.

“도구 오탐”이나 “재현 안 됨” 한 줄로 종료하지 않는다. 어떤 소스·환경·경로·통제 때문에 결함이 아닌지, 누가 검토했는지, 전제가 바뀌면 언제 재평가할지를 남긴다.

03

결함 기록의 최소 정보

결함 항목에는 다음을 포함한다.

  • 고유 결함 ID, 제목, 발견 일시·발견 방법
  • 관련 요구·위협·설계·시험 ID
  • 영향받는 구성요소, 소스·설정·의존성·환경 버전
  • 안전한 전제조건과 최소 재현 단계
  • 기대 결과와 실제 결과
  • 기밀성·무결성·가용성·추적성·개인정보 영향
  • 필요한 권한·접근 위치·사용자 상호작용 등 악용 전제
  • 기존 예방·탐지·복구 통제와 통제 실패 범위
  • 심각도·우선순위·판단 근거
  • 소유자, 목표 기한, 상태, 수정·검증 계획
  • 증거 접근 등급과 공개 범위

스크린샷·로그·요청 자료에는 실제 토큰, 세션, 개인식별정보, 내부 주소가 포함될 수 있다. 마스킹된 최소 증거와 상관관계 ID를 사용하고 원본이 꼭 필요하면 승인된 제한 저장소와 보존기간을 둔다. 결함 제목에도 고객명·비밀값을 넣지 않는다.

04

접수와 중복 정리

정적 분석, 구성요소 검사, 시험 자동화, 동료 검토, 운영 피드백은 서로 다른 형식을 사용한다. 중앙 결함 저장소에 출처·규칙·신뢰도를 보존하며 정규화한다. 도구 결과를 매 실행마다 새 항목으로 만들면 같은 원인 수백 건이 생길 수 있으므로 구성요소·위치·규칙·데이터 흐름을 비교해 묶는다.

중복은 삭제하지 않고 대표 결함에 연결한다. 같은 취약한 공통 함수가 여러 API에 영향을 주면 원인은 하나라도 영향 경로와 회귀 범위는 여러 개다. 반대로 같은 규칙명이더라도 서로 다른 신뢰경계와 수정 책임을 가지면 별도 결함이 적합할 수 있다.

신규 결함은 자동으로 담당자에게 던지기 전에 기본 정보·민감도·중복 여부를 확인한다. 중요한 보안 결함은 접근 가능한 사람을 업무상 필요한 범위로 제한하고, 소유자·보안 책임자·출시 판단자에게 정해진 경로로 알린다.

05

재현과 원인 분석

재현은 승인된 격리 환경과 합성 데이터에서 수행한다. 운영 시스템에서 확인을 반복하거나 실제 고객 자료로 시험하지 않는다. 소스·빌드·설정·데이터 상태·역할·시간·외부 모의 조건을 고정한다.

코드 예시 · text

결함 재현 카드
  환경: 보안 통합시험 기준선 E-17
  소스: 승인 빌드 식별자 B-204
  주체: 비인가 역할 test_viewer
  전제: 합성 주문 O-100이 다른 합성 고객 소유
  행동: 문서화된 주문 조회 인터페이스 호출
  기대: 접근 거부, 상태 불변, 감사 기록
  실제: 최소 필드 일부가 반환됨
  증거: 마스킹된 결과와 상관관계 ID

원인 분석은 증상 위치에서 멈추지 않는다. 왜 요구가 누락되었는지, 왜 설계·검토·시험이 잡지 못했는지 살핀다. 예를 들어 목록 조회의 인가 누락은 해당 쿼리 수정만으로 막을 수 있지만, 공통 정책을 우회하는 저장소 직접 호출, 추적표 누락, 음성 시험 부재가 체계 원인일 수 있다.

5회 질문, 원인–결과 도식, 변경 이력 비교 같은 기법을 사용할 수 있으나 사람 탓으로 끝내지 않는다. 예방 가능한 프로세스·설계·도구·검토 개선을 찾고 공통 원인이 다른 모듈에 존재하는지 수평 점검한다.

06

심각도와 우선순위

심각도는 결함의 기술·업무 영향을, 우선순위는 언제 어떤 자원으로 처리할지를 나타낸다. 둘은 관련되지만 같지 않다. 심각도가 높아도 영향 기능이 배포되지 않았다면 출시 전 수정으로 통제할 수 있고, 중간 심각도라도 규제 기한이나 광범위 노출 때문에 우선 처리가 필요할 수 있다.

판단 요소는 다음과 같다.

  • 영향 자산과 기밀성·무결성·가용성·안전·개인정보 영향
  • 영향 사용자·자료·거래의 범위와 지속시간
  • 필요한 권한·접근 위치·사용자 상호작용·복잡성
  • 기본 설정에서 도달 가능한지와 실제 배포 여부
  • 기존 탐지·차단·복구 통제의 유효성
  • 알려진 악용 징후나 운영 노출 여부
  • 수정 난이도, 서비스 영향, 외부 의존성, 출시 일정

표준 점수 체계를 사용할 수 있지만 자동 점수만으로 결론 내리지 않는다. 업무 영향과 실제 환경을 근거로 조정하고 이유를 기록한다. 운영 악용 징후가 있거나 비밀 노출이 의심되면 일반 개발 백로그보다 사고 대응 절차를 우선 연결한다.

07

상태 흐름과 책임

권장 상태 흐름은 조직에 맞게 정의하되 의미와 진입·종료 조건을 고정한다.

코드 예시 · text

신규 → 분류 중 → 확인됨 → 수정 중 → 검토 준비
          ├────────→ 오탐/중복
          └────────→ 위험 수용 검토

검토 준비 → 재시험 중 → 해결됨 → 종료
                         └→ 재개방

“수정됨”은 개발자의 코드 제출 상태이고 “해결됨”은 독립 검증으로 기대 결과를 만족한 상태다. “종료”는 관련 문서·추적·배포 상태까지 정리된 상태다. 상태마다 담당 역할, 허용 전이, 필수 증거, 목표 시간을 정한다.

결함 소유자는 수정자와 같을 필요가 없다. 소유자는 영향 분석·일정·협업·종료 증거에 책임진다. 보안 담당자는 판정과 검증을 지원하고, 업무 소유자는 영향·우선순위와 잔여 위험을 판단하며, 출시 책임자는 미해결 항목을 포함한 출시 여부를 승인한다.

08

수정안 검토

수정안은 증상을 숨기는 것이 아니라 원인을 제거하고 설계 원칙을 유지해야 한다. 입력을 무조건 삭제하거나 오류를 성공으로 바꾸는 임시 우회는 업무 정확성과 탐지를 훼손할 수 있다. 다음을 검토한다.

  • 관련 요구와 설계 통제를 실제로 만족하는가?
  • 모든 호출 경로·역할·환경에 적용되는가?
  • 안전한 기본값과 최소 권한을 유지하는가?
  • 기능·성능·데이터·호환성에 새로운 결함을 만들지 않는가?
  • 설정·의존성·배포·데이터 보정이 함께 필요한가?
  • 되돌리기 시 취약 상태로 복귀하는 위험을 어떻게 통제하는가?
  • 공통 원인을 가진 다른 위치도 수정·점검했는가?

긴급 완화는 영구 수정과 구분한다. 기능 제한, 접근 경로 차단, 추가 관찰 같은 완화는 위험을 줄일 수 있지만 소유자·적용 범위·만료·영구 수정 일정을 둔다. 완화 적용 자체도 허용 기능과 운영 영향을 시험한다.

의존성 결함은 단순히 가장 최신 버전으로 올리지 않는다. 수정 가능 버전, 호환성, 전이 의존성, 지원 상태, 변경 기록을 확인하고 회귀 시험한다. 즉시 교체가 어렵다면 실제 도달 경로와 보완 통제를 검토해 기간이 제한된 예외를 승인한다.

09

재시험과 회귀 시험

재시험은 원래 결함의 기대 결과가 충족되는지 확인한다. 같은 환경·자료만 반복하지 않고 수정으로 바뀐 경계와 우회 경로도 포함한다. 인가 결함이라면 한 비인가 역할 거부만이 아니라 허용 역할 성공, 다른 자원·목록·직접 내부 호출, 역할 변경 후 동작을 함께 본다.

회귀 범위는 변경 파일 수가 아니라 영향 분석으로 정한다.

재시험과 회귀 시험 · 학습 표 2
수정직접 재시험회귀 범위
공통 인가 정책해당 비인가 요청 거부모든 사용처의 허용·거부 역할, 캐시 갱신
입력 검증기결함 입력 범주 거부정상 국제문자·경계 길이·다른 사용 필드
의존성 갱신알려진 결함 경로 확인빌드·단위·통합·설정·성능 호환
로그 필터비밀 비노출필수 감사필드·경보·검색 기능 유지

검증자는 가능하면 수정자와 다른 시각을 제공하고, 수정된 소스·빌드·설정 식별자를 기록한다. 자동 시험이 추가되면 이후 재발을 빠르게 탐지할 수 있다. 시험 통과 스크린샷만이 아니라 기대·실제 결과와 로그·데이터 불변식을 확인한다.

10

오탐·위험 수용·예외

오탐 판정에는 도구 규칙, 실제 데이터 흐름, 호출 가능성, 기존 통제, 검토자의 근거가 필요하다. 코드 한 줄에 안전해 보이는 주석만 달아 경고를 억제하지 않는다. 억제는 가능한 좁은 위치·규칙·기간에 적용하고 도구 업데이트나 구조 변경 때 재검토한다.

위험 수용은 “수정하지 않음”이 아니라 남은 위험을 권한 있는 업무 책임자가 알고 선택하는 결정이다. 결함·영향, 현재 통제, 수용 이유, 적용 환경, 승인자, 만료일, 재검토·철회 조건, 관찰 항목을 기록한다. 무기한·소유자 없는 수용은 허용하지 않는다.

수정 기한을 넘기면 자동으로 종료하지 않고 상향 보고, 임시 완화, 범위 제한, 출시 보류 중 적절한 조치를 판단한다. 환경이나 노출이 변하면 기존 심각도와 수용을 다시 평가한다.

11

지표와 품질 개선

결함 수만 목표로 삼으면 신고를 줄이거나 항목을 합쳐 보이게 만들 수 있다. 다음 지표를 맥락과 함께 본다.

  • 심각도별 신규·미해결·기한 초과 결함
  • 발견부터 분류, 수정, 재검증까지 걸린 시간
  • 재개방률과 같은 원인의 반복률
  • 발견 단계: 요구·설계·검토·정적·통합·운영
  • 요구·구성요소별 결함 밀집과 공통 원인
  • 위험 수용의 수·만료·재검토 상태
  • 회귀 자동시험과 예방 통제 추가율

운영에서만 발견되는 인가 결함이 반복된다면 통합시험 숫자만 늘리기보다 요구 추적·자원 기반 음성 시험·공통 정책 사용을 개선한다. 회고 결과는 코딩 표준, 설계 체크리스트, 도구 규칙, 교육, 환경 기준선에 반영하고 담당·기한을 둔다.

12

SW개발 보안 구현 적용 절차

SW개발 보안 구현하기의 적용 절차와 판단 기준은 다음의 닫힌 흐름으로 이해한다.

  1. 업무 범위·자산·데이터·주체·신뢰경계를 확인한다.
  2. 위협·오용 사례와 위험을 분석해 검증 가능한 보안 요구를 명세한다.
  3. 최소 권한·완전한 중재·안전한 기본값·심층 방어를 구조와 인터페이스에 설계한다.
  4. 요구에 맞는 구현·빌드·시험 환경과 비밀·의존성 통제를 구축한다.
  5. 요구별 작업·담당·선후행·검토·수정·재시험을 일정 기준선으로 수립한다.
  6. 승인된 API와 기준선으로 입력·인가·데이터·출력·비밀·오류 통제를 구현한다.
  7. 코드 검토, 정적·구성요소·비밀 검사, 단위·통합·거부·장애 시험을 수행한다.
  8. 발견 결함을 분류·우선순위화하고 원인·영향에 맞게 수정한다.
  9. 직접 재시험과 영향 회귀 시험, 오탐·잔여 위험 승인을 완료한다.
  10. 요구–위협–설계–코드–시험–결함–배포 증거를 검토해 출시하고 운영 관찰·개선으로 환류한다.

단계는 일방향 폭포가 아니다. 구현 중 새 신뢰경계가 발견되면 설계·요구를 갱신하고, 결함 원인이 요구 누락이면 앞 단계로 돌아간다. 다만 기준선 변경의 영향·승인·재시험을 기록한다.

13

14

구체 실무 시나리오

주문 목록 API 시험에서 상담원 역할이 배정되지 않은 계정도 일부 고객의 배송 지역을 조회할 수 있는 결함이 발견되었다고 하자. 결함 담당자는 합성 고객·주문과 비인가 시험 역할로 재현하고, 목록 저장소가 공통 자원 인가 정책을 거치지 않는다는 원인을 확인한다. 요구 ID, 영향 필드, 목록·상세 API 차이, 배포 환경을 기록한다.

영향은 개인정보 기밀성이고 인증은 필요하지만 대상 범위가 넓다. 기존 접근 로그는 탐지에 도움을 주지만 노출을 예방하지 못하므로 높은 우선순위로 출시 전에 수정한다. 수정안은 목록 쿼리에 임시 조건 하나를 붙이는 데 그치지 않고 공통 정책이 조회 범위를 생성하도록 하며, 허용 상담원과 비인가 역할을 모두 시험한다.

직접 재시험은 원 결함 거부와 상태 불변을 확인한다. 회귀 시험은 상세·검색·내보내기, 역할 변경, 페이지 집계, 성능을 포함한다. 자동 음성 시험을 추가하고 같은 저장소 직접 호출을 수평 점검한다. 검증자가 승인 빌드에서 통과를 확인하고 요구·시험·수정 커밋을 연결한 뒤 종료한다.

15

산출물과 체크리스트

산출물은 결함 등록부, 정규화·중복 연결 기록, 안전한 재현 카드, 영향·심각도·우선순위 평가, 원인 분석, 수정·완화 계획, 직접·회귀 시험 결과, 오탐·위험 수용 승인, 기한·상태 보고서, 지표·회고 개선항목, 전 과정 추적표, 출시 판단 기록이다.

  • [ ] 결함이 요구·위협·설계·시험·버전에 연결된다.
  • [ ] 기대·실제 결과와 안전한 최소 재현 조건이 있다.
  • [ ] 민감한 결함 증거의 접근·마스킹·보존을 통제한다.
  • [ ] 심각도와 우선순위를 영향·전제·통제 근거로 구분했다.
  • [ ] 중복은 대표 원인에 연결하되 영향 경로를 잃지 않는다.
  • [ ] 수정안이 모든 호출 경로와 공통 원인을 다룬다.
  • [ ] 직접 재시험과 영향 범위 회귀 시험을 수행했다.
  • [ ] 오탐·완화·위험 수용에 검토자·소유자·만료가 있다.
  • [ ] 기한 초과와 운영 악용 징후의 상향·사고 대응 경로가 있다.
  • [ ] 요구부터 출시·운영 개선까지 양방향 추적된다.
16

자주 틀리는 포인트

  • 자동 도구 경고를 검토 없이 모두 확정 결함 또는 오탐으로 처리한다.
  • 결함 증거에 실제 토큰·개인정보·내부 주소를 그대로 붙인다.
  • 심각도와 수정 우선순위를 같은 값으로만 관리한다.
  • “재현 안 됨”을 환경·버전·전제 확인 없이 종료 근거로 쓴다.
  • 같은 공통 원인의 여러 영향 경로를 중복 삭제로 잃는다.
  • 증상 위치만 수정하고 다른 호출 경로와 체계 원인을 점검하지 않는다.
  • 수정자가 완료했다고 하면 독립 재시험 없이 종료한다.
  • 직접 시험만 통과하고 영향 범위의 회귀·성능 시험을 생략한다.
  • 위험 수용을 무기한·무소유자 예외로 사용한다.
  • 결함 개수를 줄이는 것을 보안 품질 개선으로 오해한다.

  1. 확정 결함, 추가 확인, 중복, 오탐의 차이를 설명하시오.
  2. 보안 결함 기록에 필요한 정보를 여덟 가지 쓰시오.
  3. 결함 증거의 공개와 보존을 제한해야 하는 이유는 무엇인가?
  4. 심각도와 우선순위의 차이를 예로 설명하시오.
  5. 결함 상태에서 “수정됨”과 “해결됨”을 구분해야 하는 이유는 무엇인가?
  6. 원인 분석에서 수평 점검과 체계 원인 확인이 필요한 이유를 쓰시오.
  7. 직접 재시험과 회귀 시험의 차이를 설명하시오.
  8. 위험 수용 기록에 포함해야 할 항목을 쓰시오.
  9. SW개발 보안 구현하기의 적용 절차를 열 단계로 요약하시오.
  10. 보안 결함을 포함한 출시 판단 기준을 쓰시오.

정답과 해설

  1. 확정 결함은 요구 위반이 확인된 상태, 추가 확인은 경로·영향 근거가 부족한 상태, 중복은 기존 원인·영향과 같은 항목, 오탐은 실제 조건에서 요구 위반이 아님이 근거로 확인된 상태다.
  2. 결함 ID·제목, 발견 출처, 관련 요구·시험, 구성요소·버전, 전제·재현, 기대·실제 결과, 영향, 기존 통제, 심각도·우선순위, 소유자·기한, 증거 등급 중 여덟 가지다.
  3. 결함 설명은 취약 위치와 조건을 포함하고 증거에는 비밀·개인정보가 있을 수 있다. 불필요한 확산과 2차 노출을 막기 위해 최소 공개·마스킹·접근·파기를 적용한다.
  4. 심각도는 손상 영향과 악용 조건의 크기이고 우선순위는 처리 순서다. 아직 배포되지 않은 높은 심각도 결함은 출시 전 즉시 수정하고, 광범위 규제 자료에 닿는 중간 심각도도 높은 우선순위가 될 수 있다.
  5. 수정됨은 코드 변경 제출일 뿐이며 해결됨은 승인 빌드에서 원 결함과 회귀 범위가 독립 검증된 상태다. 둘을 합치면 검증되지 않은 수정이 종료된다.
  6. 공통 함수·설계·시험 누락이 다른 모듈에도 같은 결함을 만들 수 있다. 한 증상만 고치면 재발하고 프로세스가 개선되지 않는다.
  7. 직접 재시험은 원래 기대 결과의 회복을 확인하고, 회귀 시험은 수정이 관련 정상 기능·다른 경로·성능에 새 문제를 만들지 않았는지 확인한다.
  8. 결함·영향, 현재 통제, 수용 근거, 적용 범위, 소유자·승인자, 만료일, 재검토·철회 조건, 관찰 항목을 포함한다.
  9. 범위·자산 확인, 요구 명세, 보안 설계, 환경 구축, 일정 수립, 안전한 구현, 검토·다층 시험, 결함 분류·수정, 재시험·위험 승인, 추적 기반 출시·운영 개선 순이다.
  10. 핵심 요구의 구현·시험 추적, 중요한 결함의 수정·재검증, 미해결 위험의 권한 있는 기한부 승인, 재현 빌드, 운영 탐지·복구, 배포 증거를 종합한다.
19

핵심 요약

  • 시험 결과는 정규화·중복 연결·근거 판정을 거쳐 확정 결함과 오탐을 구분한다.
  • 결함에는 안전한 재현, 영향·전제·통제, 심각도·우선순위, 소유자·기한을 기록한다.
  • 수정은 증상뿐 아니라 공통 원인과 모든 호출 경로를 다루고 별도 재검증을 거친다.
  • 직접 재시험과 영향 범위 회귀 시험이 모두 통과해야 해결로 판단한다.
  • 오탐·완화·위험 수용은 근거·검토·만료·재평가 조건이 있는 통제된 결정이다.
  • SW개발 보안은 요구–설계–환경·일정–구현–시험–결함–출시·운영의 닫힌 개선 흐름이다.
