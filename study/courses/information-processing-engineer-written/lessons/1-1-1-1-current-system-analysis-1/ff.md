# 1-1-1-1. 플랫폼 기능 분석 · 플랫폼 성능 특성 분석

> **공식 범위**: 소프트웨어설계 > 요구사항 확인 > 현행 시스템 분석 > `플랫폼 기능 분석`, `플랫폼 성능 특성 분석`

## 0. 학습 목표와 범위

현행 시스템 분석은 새 시스템을 설계하기 전에 지금 운영 중인 기술 환경을 사실에 근거해 파악하는 작업이다. 이 레슨에서는 그중 **플랫폼이 무엇을 제공하는지**와 **그 기능을 어느 수준으로 수행하는지**만 다룬다. 운영체제, 네트워크, DBMS의 세부 분석은 인접 레슨의 범위이므로 여기서는 플랫폼의 의존 요소로 식별하는 수준에 머문다.

학습 후에는 다음을 설명할 수 있어야 한다.

1. 플랫폼의 사용자·연계 시스템·공통 서비스를 기준으로 기능 목록을 만든다.
2. 기능과 구성요소, 인터페이스, 제약조건, 의존관계를 연결한다.
3. 응답시간·처리량·자원사용률·가용성·확장성과 같은 성능 특성을 측정 가능한 값으로 정리한다.
4. 추측이나 평균값 하나가 아니라 로그, 모니터링, 설정 자료와 시간대별 분포로 병목 후보를 판단한다.

---

## 1. 플랫폼의 의미

플랫폼은 응용 소프트웨어가 개발·실행·운영될 수 있도록 기반 기능과 기술 환경을 제공하는 체계다. 서버 실행환경, 공통 인증, 메시지 처리, 배치 실행, 로깅·모니터링, 외부 연계 기능 등이 하나의 운영 기반을 이룰 수 있다. 기업마다 “플랫폼”이라고 부르는 범위는 다르므로 제품명만 보고 단정하지 말고 **현재 시스템에서 실제로 제공하는 역할과 경계**를 확인해야 한다.

플랫폼 분석의 질문은 두 갈래다.

- 기능 관점: 누가 어떤 서비스를 사용하며, 어떤 구성요소와 인터페이스가 이를 실현하는가?
- 성능 관점: 그 서비스가 어느 부하에서 얼마나 빠르고 안정적으로 동작하는가?

기능은 “주문 접수를 처리한다”처럼 무엇을 하는지를 나타내고, 성능은 “동시 사용자 1,000명 조건에서 주문 접수의 95백분위 응답시간이 2초 이하”처럼 어느 수준으로 하는지를 나타낸다.

## 2. 플랫폼 기능 분석

### 2.1 분석 대상과 경계를 먼저 정한다

분석을 시작할 때 시스템 전체를 한꺼번에 보려 하면 누락과 중복이 생긴다. 다음 경계를 기록한다.

| 구분 | 확인 질문 | 예시 |
|---|---|---|
| 사용자 | 누가 플랫폼 기능을 사용하는가? | 고객, 상담원, 운영자 |
| 외부 시스템 | 어떤 서비스와 데이터를 주고받는가? | 결제 서비스, 배송 시스템 |
| 내부 구성요소 | 기능을 담당하는 모듈은 무엇인가? | 인증, 주문, 배치, 알림 모듈 |
| 입력·출력 | 무엇을 받아 무엇을 반환하는가? | 주문 요청 → 접수번호·처리상태 |
| 운영 경계 | 어느 조직과 환경이 책임지는가? | 운영팀, 외부 위탁, 운영·개발 환경 |

이 단계의 산출물은 시스템 컨텍스트, 구성도, 인터페이스 목록, 담당자 목록 등이다. 문서가 오래되었을 수 있으므로 실제 설정과 운영 담당자 인터뷰, 로그를 함께 대조한다.

### 2.2 기능을 계층적으로 분해한다

플랫폼 기능은 상위 업무 기능에서 세부 기능으로 분해한다. 예를 들어 전자상거래 플랫폼을 다음처럼 정리할 수 있다.

```text
주문 서비스
├─ 주문 요청 검증
├─ 주문번호 발급
├─ 결제 연계 요청
├─ 주문 상태 변경
└─ 처리 결과 통지

공통 운영 서비스
├─ 사용자 인증·권한 확인
├─ 오류 기록과 추적
├─ 배치 작업 실행
└─ 상태 모니터링
```

기능 분해의 목적은 구현 코드를 자세히 읽는 것이 아니라, 새 요구사항이 어느 기존 기능과 충돌하거나 재사용될 수 있는지 찾는 것이다. 상위 기능만 적으면 인터페이스와 책임을 놓치고, 함수 단위까지 내려가면 분석 범위가 과도하게 커진다. 요구사항 판단에 필요한 수준에서 분해 깊이를 맞춘다.

### 2.3 기능별 속성을 표로 만든다

기능 이름만 나열하지 말고 다음 속성을 함께 기록한다.

- 기능 ID와 명칭: 중복되지 않는 식별자와 일관된 동사형 이름
- 목적과 사용자: 왜 존재하며 누가 사용하는지
- 입력·출력: 데이터 형식, 필수값, 결과와 오류 응답
- 선행·후행 기능: 실행 순서와 의존관계
- 담당 구성요소: 어떤 모듈이나 서비스가 책임지는지
- 연계 인터페이스: 호출 방식, 동기·비동기 여부, 전달 주기
- 제약조건: 운영시간, 권한, 처리 순서, 외부 계약 조건
- 증거 자료: 설계서, 로그 위치, 설정 버전, 담당자 확인일

예시는 다음과 같다.

| 기능 | 입력 | 출력 | 의존 기능 | 확인할 제약 |
|---|---|---|---|---|
| 주문 접수 | 고객·상품·수량 | 주문번호·상태 | 인증, 상품 확인 | 중복 요청 방지 |
| 결제 연계 | 주문번호·금액 | 승인·거절 결과 | 외부 결제 서비스 | 제한시간, 재시도 |
| 야간 집계 | 당일 거래 | 집계 결과 | 배치 스케줄러 | 마감 후 실행 |

“지원한다”는 문구만으로는 실제 가용 기능인지 판단하기 어렵다. 운영에서 사용 중인지, 특정 버전이나 계약 옵션이 필요한지, 장애 시 대체 절차가 있는지까지 확인한다.

### 2.4 중복·누락·의존성을 찾는다

기능 목록이 만들어지면 다음 관점으로 검토한다.

1. 같은 업무가 여러 모듈에 중복 구현되어 결과가 달라지는가?
2. 사용자 요구에는 있지만 담당 구성요소가 없는 누락 기능이 있는가?
3. 한 기능의 변경이 어떤 선행·후행 기능과 외부 연계를 바꾸는가?
4. 더 이상 사용하지 않지만 호출 관계가 남은 기능이 있는가?
5. 단일 구성요소 장애가 여러 핵심 기능을 동시에 중단시키는가?

이 결과는 향후 변경 영향도와 재사용 가능성을 판단하는 근거다. 그러나 여기서 곧바로 새 아키텍처를 결정하지 않는다. 현행 기능과 사실을 먼저 확정한 뒤 요구사항과 대안을 평가한다.

## 3. 플랫폼 성능 특성 분석

### 3.1 성능 특성은 조건·지표·값으로 표현한다

“느리다”, “트래픽이 많다”, “안정적이다”는 분석 결과가 아니다. 다음 세 요소가 있어야 비교 가능하다.

```text
측정 조건 + 성능 지표 + 관측값 또는 목표값
```

예: “평일 10~11시 동시 사용자 약 800명에서 주문 API의 95백분위 응답시간은 2.4초다.” 조건이 빠지면 다른 시간대나 다른 부하의 값과 잘못 비교할 수 있다.

### 3.2 핵심 성능 지표

| 특성 | 의미 | 대표 측정 |
|---|---|---|
| 응답시간 | 요청부터 응답 완료까지 걸린 시간 | 평균, 중앙값, p95, p99 |
| 처리량 | 단위시간에 완료한 작업 수 | 건/초, 트랜잭션/분 |
| 자원사용률 | 처리에 사용된 자원 수준 | CPU, 메모리, 스레드·연결 사용률 |
| 가용성 | 필요한 시간에 서비스를 사용할 수 있는 비율 | 가동시간/전체 서비스 시간 |
| 용량 | 현재 구성에서 허용 가능한 부하 규모 | 동시 사용자, 큐 길이, 처리 건수 |
| 확장성 | 자원을 늘릴 때 처리능력이 증가하는 특성 | 확장 전후 처리량·응답시간 변화 |

응답시간과 처리량은 같은 개념이 아니다. 요청 하나가 빨리 끝나도 동시에 처리할 수 있는 수가 적으면 처리량은 낮을 수 있다. 반대로 대량 배치가 많은 건을 처리해 처리량이 높아도 개별 작업 완료시간은 길 수 있다.

가용성은 흔히 다음처럼 생각할 수 있다.

```text
가용성 = 실제 서비스 가능 시간 / 계획된 서비스 시간
```

복구 관점에서는 평균고장간격(MTBF)이 길고 평균복구시간(MTTR)이 짧을수록 유리하다. 다만 조직마다 계획정지 포함 여부와 측정 기간이 다르므로 수치 비교 전 산정 기준을 확인한다.

### 3.3 평균 하나보다 분포와 시간대를 본다

응답시간 평균은 일부 매우 느린 요청이나 혼잡 시간대를 가릴 수 있다. 중앙값과 p95·p99, 최대값, 오류율을 함께 본다. p95가 2초라는 말은 관측 요청의 약 95%가 2초 이내에 완료되었다는 의미이며 “모든 요청이 2초 이내”라는 뜻은 아니다.

다음처럼 구간별로 나누어야 병목 후보를 찾기 쉽다.

- 평상시와 업무 마감시간
- 읽기 요청과 쓰기 요청
- 온라인 요청과 배치 작업
- 정상 응답과 오류·재시도 요청
- 기능별·사용자군별·연계 시스템별

성능 로그의 시간 기준이 서로 다르거나 샘플링 간격이 다르면 인과관계를 잘못 추정할 수 있다. 측정 시각, 대상 버전, 부하 조건, 데이터 규모를 함께 보존한다.

### 3.4 증거를 수집하는 절차

1. **핵심 기능 선정**: 업무 중단 영향과 호출 빈도가 큰 기능을 우선한다.
2. **지표 정의**: 기능별 응답시간, 처리량, 오류율, 자원사용률을 정한다.
3. **자료 수집**: 운영 모니터링, 접근 로그, 장애 기록, 용량 보고서, 부하 시험 결과를 모은다.
4. **정상 기준선 작성**: 대표 기간의 평상시 범위와 최고 부하 시간대를 구분한다.
5. **이상 구간 연결**: 성능 저하 시각과 배포, 배치, 외부 연계 지연 등의 사건을 맞춘다.
6. **제약과 위험 기록**: 관측 부족, 오래된 문서, 미측정 구간을 명시한다.
7. **요구사항 영향 정리**: 신규 사용자 수나 거래량 증가가 현재 여유 용량을 넘는지 판단 근거를 제공한다.

관측값만으로 원인을 확정하지 않는다. CPU 사용률과 응답시간이 동시에 올랐다는 사실은 관련성을 시사하지만, CPU가 유일한 원인이라는 증거는 아니다. 추가 로그와 재현 시험으로 가설을 검증한다.

## 4. 기능과 성능을 연결한 분석 예시

신규 할인 이벤트를 앞둔 주문 플랫폼을 분석한다고 하자.

### 기능 분석 결과

- 주문 접수는 인증, 상품 확인, 결제 연계를 순차 호출한다.
- 결제 연계는 동기 응답을 기다리고 제한시간 뒤 한 차례 재시도한다.
- 야간 집계는 주문 데이터에 대량 접근하지만 온라인 시간과 일부 겹친다.

### 성능 분석 결과

- 평상시 주문 접수 p95는 0.9초, 마감시간 p95는 2.7초다.
- 마감시간 처리량은 초당 120건 부근에서 더 늘지 않고 대기열이 증가한다.
- 오류율은 평상시 0.2%지만 외부 결제 지연 구간에 3%까지 상승했다.

### 해석

“플랫폼이 느리다”가 아니라, 주문 기능의 외부 연계 대기와 특정 시간대의 부하가 성능 위험 후보라는 식으로 기록한다. 현재 정보만으로 구체적 해결책을 확정하지는 않는다. 신규 이벤트의 예상 부하와 현행 용량의 차이를 계산하고, 필요한 추가 시험과 연계 조건 확인을 제안한다.

## 5. 비교와 판단 기준

| 잘못된 분석 | 개선된 분석 |
|---|---|
| 제품 소개서의 기능을 그대로 현행 기능으로 간주 | 실제 사용 설정·호출 로그·담당자 확인으로 검증 |
| “응답이 느림”이라고 기록 | 조건, 기능, p95, 오류율과 관측 기간 명시 |
| 평균 응답시간만 비교 | 중앙값·p95·p99와 시간대별 분포 확인 |
| 기능 목록과 성능표를 따로 작성 | 핵심 기능 ID를 기준으로 지표와 병목 후보 연결 |
| 관측 상관관계를 원인으로 확정 | 원인 가설과 추가 검증 필요사항을 구분 |

현행 분석은 완벽한 문서 복원이 아니라 요구사항 판단에 충분한 신뢰도를 확보하는 작업이다. 확인된 사실, 추정, 미확인 항목을 구분하면 후속 설계에서 잘못된 전제를 줄일 수 있다.

---

## 6. 시험 함정

1. **기능과 성능 혼동**: “동시 사용자 1,000명 지원”은 수준·조건을 포함한 성능 또는 용량 특성이지 단순 기능명이 아니다.
2. **응답시간과 처리량 동일시**: 응답시간은 개별 요청의 지연, 처리량은 단위시간 완료 건수다.
3. **평균값 절대화**: 평균이 양호해도 p95·p99가 나쁘면 일부 사용자의 지연이 클 수 있다.
4. **가용성과 신뢰성 혼동**: 고장이 드물어도 복구가 매우 늦으면 가용성이 낮을 수 있다.
5. **확장성과 용량 혼동**: 용량은 현재 처리 한계, 확장성은 자원 추가에 따른 처리능력 변화다.
6. **문서만 신뢰**: 현행 문서는 실제 운영 버전·설정과 다를 수 있어 로그와 담당자 확인이 필요하다.
7. **원인 단정**: 높은 자원사용률과 지연의 동시 발생만으로 인과를 확정하지 않는다.
8. **범위 과잉**: 플랫폼 분석 중 운영체제·네트워크·DBMS의 세부 평가까지 섞으면 분석 책임과 산출물이 흐려진다.

## 7. 확인 문제

### 문제 1

“주문 서비스는 빠르다”를 성능 분석 결과로 쓰기 위해 최소한 무엇을 보완해야 하는가?

**정답과 해설**: 측정 조건, 지표, 관측값을 넣어야 한다. 예를 들어 “평일 마감시간 동시 사용자 800명에서 주문 접수 p95 응답시간 2.4초”처럼 기능·부하·시간대·통계량을 명시한다.

### 문제 2

평균 응답시간은 0.4초인데 p99는 8초다. 무엇을 의미하는가?

**정답과 해설**: 대부분의 요청은 빠르더라도 상위 약 1% 요청에서 긴 지연이 발생할 수 있다는 뜻이다. 평균만 보고 전체 사용 경험이 좋다고 결론 내리면 안 된다.

### 문제 3

서버를 두 배로 늘렸는데 처리량이 거의 늘지 않았다. 이는 어떤 특성을 점검할 근거인가?

**정답과 해설**: 확장성을 점검할 근거다. 자원 증가가 처리능력 향상으로 이어지지 않았으므로 공유 병목, 직렬 처리, 외부 의존 등의 가설을 추가 자료로 검증해야 한다.

### 문제 4

제품 설명서에 메시지 기능이 있다고 적혀 있으면 현행 플랫폼에서 사용 가능하다고 확정해도 되는가?

**정답과 해설**: 아니다. 현재 버전, 라이선스, 설정, 실제 사용 여부를 확인해야 한다. 제품 가능 기능과 현행 활성 기능을 구분한다.

### 문제 5

기능 분석표에 반드시 성능 수치를 모두 넣어야 하는가?

**정답과 해설**: 모든 기능에 같은 깊이의 수치가 필요한 것은 아니다. 업무 중요도와 호출 빈도를 기준으로 핵심 기능을 선정하되, 기능 ID를 성능 자료와 연결해 추적할 수 있어야 한다.

## 8. 최종 요약

- `플랫폼 기능 분석`은 사용자, 기능, 입력·출력, 구성요소, 인터페이스, 제약과 의존관계를 사실에 근거해 정리한다.
- 기능은 요구사항 판단에 필요한 수준으로 계층화하고, 중복·누락·변경 영향도를 확인한다.
- `플랫폼 성능 특성 분석`은 응답시간, 처리량, 자원사용률, 가용성, 용량, 확장성을 조건과 함께 측정한다.
- 평균 하나가 아니라 백분위수, 시간대, 기능별 분포와 오류율을 함께 읽는다.
- 기능과 성능을 같은 기능 ID로 연결하면 어느 서비스가 어느 조건에서 위험한지 설명할 수 있다.
- 문서·로그·모니터링·담당자 확인을 교차 검증하고, 사실·추정·미확인 항목을 분리한다.
- 현행 분석의 결론은 성급한 해결책이 아니라 새 요구사항과 대안을 평가할 신뢰 가능한 기준선이다.
