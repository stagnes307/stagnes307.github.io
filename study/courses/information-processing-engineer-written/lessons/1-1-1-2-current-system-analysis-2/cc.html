01

0. 학습 목표와 분석 원칙

현행 시스템에서 응용 소프트웨어는 운영체제의 프로세스·메모리·파일·권한 관리 기능 위에서 실행되고, 네트워크를 통해 사용자와 다른 시스템에 연결된다. 새 요구사항이 기능적으로 타당해 보여도 운영체제 호환성이나 통신 경로의 제약을 놓치면 실제 이행이 불가능할 수 있다.

이 레슨의 목표는 다음과 같다.

  1. 운영체제의 종류·버전·구성·자원·지원 상태와 응용 프로그램의 의존성을 조사한다.
  2. 네트워크의 물리·논리 구성, 구간, 주소, 프로토콜, 보안 통제와 품질 현황을 정리한다.
  3. 문서와 실제 설정을 대조하고, 변경 요구가 호환성·용량·가용성·보안에 미치는 영향을 식별한다.
  4. 관측 사실과 원인 가설을 구분해 추가 확인 항목을 남긴다.

제품별 명령어나 지원정책은 버전에 따라 달라질 수 있다. 시험에서는 특정 제품의 최신 설정값을 암기하기보다 무엇을 왜 확인하고 어떻게 근거를 남기는지에 초점을 맞춘다.

02

1. 운영체제 분석

1.1 운영체제가 제공하는 기반

운영체제(OS)는 하드웨어 자원을 관리하고 응용 프로그램이 실행될 공통 환경을 제공하는 시스템 소프트웨어다. 주요 역할은 다음과 같다.

  • 프로세스·스레드 생성, 실행 순서와 CPU 시간 관리
  • 가상메모리와 물리메모리 할당·회수
  • 파일시스템, 디렉터리, 장치 입출력 관리
  • 사용자·그룹·권한과 접근통제
  • 서비스 시작·중지와 작업 스케줄링
  • 네트워크 기능과 시스템 로그 제공
  • 오류 탐지, 자원 상태 관찰, 시스템 보호

운영체제 분석은 이러한 기능을 이론적으로 나열하는 것이 아니라 현행 응용 프로그램이 어느 기능과 설정에 의존하는지 찾는 작업이다.

1.2 기본 현황을 식별한다

서버 또는 실행 노드마다 다음 항목을 인벤토리로 만든다.

“Linux 서버” 또는 “Windows 서버”처럼 계열만 적어서는 호환성을 판단하기 어렵다. 같은 계열에서도 버전, 커널, 패치, 설치된 런타임과 라이브러리가 다를 수 있다.

1.3 실행 구성과 의존성을 분석한다

응용 프로그램 단위로 다음 연결을 추적한다.

코드 예시 · text

응용 서비스
→ 실행 계정과 권한
→ 서비스 시작 방식
→ 런타임·공유 라이브러리
→ 환경변수·설정 파일
→ 파일·디렉터리 접근
→ 예약 작업과 로그
→ 장애 시 재시작·복구 절차

예를 들어 배치 프로그램이 특정 디렉터리에 임시 파일을 만들고 전용 계정의 예약 작업으로 실행된다면, 운영체제 변경 시 실행 파일 호환성뿐 아니라 디렉터리 권한, 경로 표기, 스케줄러, 문자 인코딩, 시간대 설정도 확인해야 한다.

설정 파일에 비밀값이 평문으로 들어 있는지 등을 발견할 수 있지만, 민감한 원문을 분석 문서에 복사하지 않는다. 저장 위치와 보호 방식, 개선 필요 여부만 권한 있는 방식으로 기록한다.

1.4 자원과 운영 상태를 분석한다

CPU·메모리·저장공간의 단일 시점 사용률만 보지 않고 대표 기간의 추세와 최고 부하 구간을 확인한다.

  • CPU: 평균·최고 사용률, 실행 큐, 특정 프로세스 집중 여부
  • 메모리: 사용량 추세, 스왑·페이지 활동, 비정상 증가 여부
  • 저장공간: 사용률, 증가속도, 임시·로그 파일 보존정책
  • 프로세스: 필수 서비스, 비정상 종료, 재시작 횟수
  • 계정·권한: 휴면·공용 계정, 과도한 권한, 실행 계정 분리
  • 로그: 시스템 오류, 자원 부족, 시간 동기화 이상
  • 백업·복구: 설정과 파일 백업 범위, 복구 절차의 검증 여부

메모리 사용률이 높다는 사실만으로 메모리 부족을 단정하지 않는다. 운영체제는 남는 메모리를 캐시로 활용할 수 있으므로 가용 메모리, 스왑 활동, 응답 지연과 함께 해석한다. 제품과 버전에 따라 지표 정의가 다를 수 있으므로 수집 도구의 의미도 확인한다.

1.5 운영체제 위험을 요구사항과 연결한다

대표 위험은 다음과 같다.

  • 지원 종료 또는 조직 표준에서 벗어난 버전
  • 새 런타임과 호환되지 않는 라이브러리·아키텍처
  • 특정 절대경로, 계정, 스케줄러에 강하게 결합된 실행 방식
  • 자원 여유 부족과 로그·임시 파일의 지속 증가
  • 수동 시작·복구에 의존하고 절차가 검증되지 않은 서비스
  • 관리자 권한으로 불필요하게 실행되는 응용 프로그램

위험을 발견하면 “즉시 교체”라고 단정하지 않고 영향받는 기능, 증거, 가능성, 영향도, 추가 검증과 대응 대안을 기록한다.

2. 네트워크 분석

2.1 물리 구성과 논리 구성을 구분한다

물리 구성은 장비와 회선이 실제로 어떻게 연결되는지를 나타낸다. 논리 구성은 주소 대역, 서브넷, 보안 구간, 가상 네트워크, 라우팅처럼 통신 관점의 경계를 나타낸다. 물리 장비 하나가 여러 논리 구간을 제공할 수 있고, 가상 네트워크 하나가 여러 장비에 걸칠 수도 있으므로 두 관점을 혼동하지 않는다.

네트워크 분석의 기본 대상은 다음과 같다.

  • 사용자, 서버, 외부 시스템이 위치한 구간과 신뢰 경계
  • 스위치·라우터·방화벽·로드밸런서·게이트웨이의 역할
  • IP 주소 대역, 서브넷, 이름 해석, 기본 경로
  • 시스템 간 출발지·목적지·프로토콜·포트·통신 방향
  • 동기 호출, 비동기 전달, 주기적 파일 전송 등 연계 형태
  • 회선 대역폭, 지연, 손실, 오류와 사용률
  • 이중화 경로, 장애 전환, 단일 장애점
  • 접근통제와 변경 승인·모니터링 방식

2.2 통신 흐름을 행 단위로 정리한다

네트워크 구성도만으로는 실제 허용 규칙과 데이터 흐름을 검증하기 어렵다. 핵심 연계를 다음 표처럼 정리한다.

2. 네트워크 분석 · 학습 표 2
출발지목적지용도프로토콜·포트방향빈도·규모통제
사용자 구간웹 구간화면 요청암호화된 웹 통신단방향 요청·응답상시접근정책
응용 구간외부 결제승인 요청계약된 인터페이스양방향거래별방화벽·인증
관리 구간서버운영 관리승인된 관리 통신제한필요 시관리자 통제

포트가 열려 있다는 사실만으로 통신이 정상이라는 뜻은 아니다. 이름 해석, 라우팅, 방화벽, 인증서, 중간 장비의 제한시간과 주소 변환 등 전체 경로를 확인해야 한다.

2.3 네트워크 품질을 측정한다

2. 네트워크 분석 · 학습 표 3
지표의미혼동하기 쉬운 개념
대역폭이론적 또는 계약상 전송 용량실제 처리량과 같지 않음
처리량실제 단위시간 전송된 데이터프로토콜 오버헤드·혼잡 영향

지터지연시간의 변동실시간 통신 품질에 영향
패킷 손실전송 중 유실된 비율재전송과 지연 증가 유발 가능
오류율손상·실패한 전송 비율장비·회선·설정 문제 단서

응용 응답이 느리다는 이유만으로 네트워크가 원인이라고 단정하지 않는다. 클라이언트 시각, 서버 처리시간, 네트워크 왕복지연을 분리해 관찰한다. 반대로 단순 연결 시험이 성공했다고 업무 트래픽의 처리량과 안정성이 충분하다고 판단해서도 안 된다.

2.4 네트워크 분석 절차

  1. 자료 수집: 최신 구성도, 주소 목록, 방화벽·로드밸런서 정책, 회선 계약, 장애 기록을 모은다.
  2. 현행 검증: 실제 장비·가상 구성·라우팅·허용 규칙과 문서를 대조한다.
  3. 흐름 작성: 핵심 기능별 출발지, 목적지, 프로토콜, 포트, 데이터 규모를 기록한다.
  4. 품질 기준선: 평상시와 최고 부하 시간의 지연, 처리량, 손실, 오류를 수집한다.
  5. 가용성 확인: 경로 이중화, 장애 전환 조건, 상태 점검 방식, 복구 절차를 확인한다.
  6. 보안 경계 확인: 외부·사용자·응용·관리 구간 사이에 최소 허용 원칙이 적용되는지 본다.
  7. 변경 영향 분석: 신규 연계, 사용자 증가, 데이터 규모 증가가 주소·정책·회선·장비 용량에 미치는 영향을 정리한다.

구성도에는 작성 기준일과 버전을 표시한다. 자동 수집 결과도 일시적인 상태일 수 있으므로 변경 기록 및 담당자 확인과 함께 사용한다.

3. 통합 분석 예시

현행 고객 서비스에 새 알림 연계를 추가한다고 하자.

운영체제 관점

  • 알림 에이전트가 요구하는 런타임이 현행 운영체제 버전에서 지원되는가?
  • 실행 계정과 설치 디렉터리 권한은 최소권한으로 구성 가능한가?
  • 서비스 자동 시작, 로그 순환, 장애 시 재시작 방식은 무엇인가?
  • 현행 CPU·메모리·저장공간에 예상 부하를 수용할 여유가 있는가?

네트워크 관점

  • 응용 구간에서 외부 알림 서비스까지 어떤 경로를 사용하는가?
  • 출발지와 목적지, 프로토콜·포트, 이름 해석, 암호화 조건은 무엇인가?
  • 외부 서비스 지연과 연결 제한시간이 현행 요청 처리에 어떤 영향을 주는가?
  • 단절 시 재시도 트래픽이 회선과 응용에 추가 부하를 만들지 않는가?

분석 결과는 “가능/불가능” 한 단어보다 확인된 호환성, 필요한 정책 변경, 용량 여유, 미검증 항목과 시험 계획으로 제시한다.

중심 대상실행 노드와 시스템 소프트웨어통신 구간과 경로
핵심 관계응용 ↔ 프로세스·파일·권한·자원출발지 ↔ 경로 ↔ 목적지
주요 위험호환성, 지원 종료, 자원·권한연결성, 용량, 지연, 단일 경로, 통제
대표 증거버전·설정·프로세스·시스템 로그구성도·정책·흐름·품질 로그

두 분석은 연결된다. 예를 들어 서버의 이름 해석 설정은 운영체제에 존재하지만 서비스 간 통신 경로에도 영향을 준다. 산출물에서는 책임 관점을 구분하면서 상호 의존성을 링크한다.

5. 시험 함정

  1. 제품 계열만 기록: 정확한 버전·패치·아키텍처가 없으면 호환성과 지원 상태를 판단하기 어렵다.
  2. 높은 메모리 사용률 즉시 장애 판단: 캐시 활용 가능성이 있으므로 가용 메모리·스왑·지연을 함께 본다.
  3. 대역폭과 처리량 혼동: 대역폭은 수용 가능한 전송 용량, 처리량은 실제 전송 성과다.
  4. 지연시간과 응답시간 혼동: 응답시간에는 네트워크뿐 아니라 서버 처리와 대기도 포함된다.
  5. 물리·논리 구성 동일시: 하나의 물리 장비에 여러 논리 네트워크가 존재할 수 있다.
  6. 포트 연결 성공으로 품질 확정: 연결성과 용량·지연·안정성은 다른 질문이다.
  7. 구성도 무조건 신뢰: 현행 설정과 변경 기록으로 최신성을 확인해야 한다.
  8. 보안 설정 원문 복사: 비밀값과 민감한 주소·정책은 권한과 취급 기준에 따라 보호한다.
  9. 상관관계를 원인으로 단정: 같은 시각의 CPU 상승과 지연만으로 CPU가 원인이라고 확정하지 않는다.

6. 확인 문제

문제 1

현행 서버가 특정 운영체제 계열이라는 정보만으로 새 실행환경의 호환성을 판단할 수 있는가?

정답과 해설: 부족하다. 정확한 버전과 패치, 아키텍처, 필요한 런타임·라이브러리, 실행 권한과 공급자 지원 범위를 확인해야 한다.

문제 2

1Gbps 회선에서 실제 파일 전송 처리량이 항상 1Gbps가 되는가?

정답과 해설: 아니다. 1Gbps는 명목상 대역폭일 수 있으며 실제 처리량은 프로토콜 오버헤드, 혼잡, 장비 처리능력, 상대 시스템, 손실과 재전송의 영향을 받는다.

문제 3

네트워크 왕복지연은 20ms인데 업무 응답시간은 3초다. 네트워크가 원인이라고 결론 내릴 수 있는가?

정답과 해설: 없다. 서버 처리, 대기, 외부 호출 등 다른 구간을 분리 측정해야 한다. 왕복지연은 전체 응답시간의 한 구성요소다.

문제 4

운영체제 분석에서 서비스 실행 계정을 확인하는 이유는 무엇인가?

정답과 해설: 응용이 실제로 접근할 수 있는 파일·장치·네트워크 자원과 권한 범위를 판단하고, 과도한 권한 및 변경 시 호환 위험을 식별하기 위해서다.

문제 5

네트워크 구성도와 방화벽 정책 목록이 서로 다르다면 무엇을 기준으로 하는가?

정답과 해설: 어느 한 문서를 즉시 정답으로 간주하지 않는다. 실제 구성과 통신 흐름, 변경 기록, 담당자 확인을 대조해 최신 현행을 확정하고 문서 차이를 미확인 위험으로 기록한다.

7. 최종 요약

  • 운영체제 분석은 제품·버전·패치·아키텍처·지원 상태와 응용의 프로세스·파일·권한·런타임 의존성을 조사한다.
  • CPU·메모리·저장공간은 단일 사용률이 아니라 추세, 최고 부하, 오류와 응답 지연을 함께 해석한다.
  • 네트워크 분석은 물리·논리 구성, 통신 흐름, 주소·경로, 프로토콜·포트, 보안 구간, 품질과 가용성을 확인한다.
  • 대역폭과 처리량, 네트워크 지연과 응용 응답시간, 물리와 논리 구성을 구분한다.
  • 문서, 실제 설정, 로그, 변경 기록, 담당자 확인을 교차 검증한다.
  • 변경 영향은 호환성·용량·가용성·보안 통제와 연결해 기록하고, 사실·가설·미확인 항목을 분리한다.
