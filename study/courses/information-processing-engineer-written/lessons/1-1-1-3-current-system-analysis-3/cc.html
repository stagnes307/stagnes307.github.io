01

0. 이번 레슨의 두 관점

현행 시스템을 분석할 때 데이터 관리 기반만 보거나 업무 목적만 보아서는 충분하지 않다. DBMS가 현재 어떤 데이터를 어떤 제약 아래 저장·보호·복구하는지 확인하고, 그 데이터와 정보기술이 업무·산업의 변화와 어떻게 결합되는지도 함께 살펴야 한다.

이 레슨의 학습 목표는 다음과 같다.

  1. DBMS의 제품·버전·구성, 데이터 규모, 가용성, 백업·복구, 보안, 성능과 연계 의존성을 조사한다.
  2. 업무 목표·프로세스·이해관계자·데이터·기술 역량을 연결해 융합 기회와 제약을 분석한다.
  3. 현행 DBMS의 사실과 비즈니스 변화의 가설을 구분하고, 변경 영향과 추가 검증 사항을 근거 있게 기록한다.
  4. 특정 제품이나 유행 기술을 먼저 선택하지 않고 문제·가치·실행 가능성의 순서로 판단한다.

데이터 모델링, SQL, 정규화 같은 상세 설계는 이후 데이터베이스 관련 영역의 범위다. 여기서는 요구사항 확인을 위한 현행 DBMS 환경과 업무 융합 가능성에 집중한다.

02

1. DBMS 분석

1.1 DBMS의 역할

DBMS(Database Management System)는 여러 사용자가 데이터를 정의·저장·조회·변경할 수 있게 하고, 무결성·동시성·보안·복구를 관리하는 소프트웨어다. 단순 파일 저장과 달리 데이터 독립성, 통제된 공유, 트랜잭션 관리, 권한 관리와 복구 기능을 제공한다.

현행 분석에서 중요한 질문은 “어떤 DBMS를 쓰는가?”를 넘어선다.

  • 어떤 업무 데이터와 중요 기능을 담당하는가?
  • 어느 제품·버전·구성으로 운영되는가?
  • 응용 프로그램이 어떤 드라이버·인터페이스·기능에 의존하는가?
  • 데이터 규모와 증가율, 동시 사용자와 작업 패턴은 어떠한가?
  • 장애·손상 시 어디까지, 얼마 만에 복구해야 하는가?
  • 권한, 암호화, 감사와 개인정보 보호는 어떻게 통제되는가?

응용 프로그램과 DBMS의 의존성은 연결 문자열만이 아니다. 특정 데이터 형식, 내장 함수, 저장 프로시저, 트랜잭션 격리 방식, 대소문자·정렬 규칙, 문자 인코딩에 의존할 수 있다. 현행 분석에서는 이러한 의존성이 있다는 사실과 영향 범위를 식별하고, 상세 전환 방안은 별도 검증으로 남긴다.

1.3 데이터 규모와 사용 패턴

데이터베이스 전체 크기 하나보다 업무별 분포와 변화가 중요하다.

  • 핵심 테이블 또는 데이터 영역의 크기와 행 수
  • 일·월별 증가량과 보존·삭제·아카이브 정책
  • 업무시간의 읽기·쓰기 빈도와 최고 동시 연결 수
  • 대량 배치, 보고서, 백업이 온라인 업무와 겹치는 시간
  • 장기 실행 작업, 잠금 대기, 반복 실패와 재시도
  • 불필요한 중복 데이터나 사용되지 않는 영역의 존재

저장공간이 60% 사용 중이라는 사실만으로 여유가 충분하다고 결론 내리지 않는다. 증가속도와 증설 소요시간, 임계값, 로그·임시 영역의 최대 사용량을 함께 본다. 반대로 큰 데이터베이스라고 반드시 느린 것도 아니다. 접근 패턴과 구성, 쿼리, 자원, 동시성의 영향을 추가로 확인해야 한다.

1.4 성능·동시성·가용성 관점

DBMS 성능 분석의 대표 증거는 응답시간, 처리량, 동시 연결, 잠금 대기, 자원사용량, 느린 작업 기록 등이다. 특정 쿼리가 느리다는 결과만으로 DBMS 제품 자체가 원인이라고 단정하지 않는다. 데이터 분포, 실행 계획, 인덱스, 잠금, 응용의 호출 방식, 서버 자원과 네트워크 등 여러 가설을 구분한다.

가용성 분석에서는 다음을 확인한다.

  1. 단일 장애점은 무엇인가?
  2. 장애 감지와 전환은 자동인지 수동인지?
  3. 복제 지연이나 미반영 데이터의 허용 범위는 무엇인지?
  4. 장애 시 응용 연결이 어떻게 복구되는지?
  5. 실제 전환·복구 시험을 언제 어떤 조건에서 했는지?

장비가 이중화되었다고 서비스 가용성이 자동 보장되는 것은 아니다. 동일한 설정 오류가 두 노드에 적용되거나 응용이 예비 노드로 연결하지 못하면 서비스는 중단될 수 있다.

1.5 백업과 복구

백업 파일의 존재와 복구 가능성은 다르다. 다음 항목을 함께 본다.

  • 전체·증분·로그 등 백업 방식과 주기
  • 백업 보관 위치, 기간, 암호화, 접근권한
  • 백업 성공 여부 감시와 실패 통보
  • 복구목표시점(RPO): 어느 시점까지의 데이터 손실을 허용하는가?
  • 복구목표시간(RTO): 서비스 복구까지 얼마를 허용하는가?
  • 복구 절차와 정기 복구 시험 결과

RPO는 허용 가능한 데이터 손실 시점과 관련되고, RTO는 중단 후 복구에 걸리는 허용 시간과 관련된다. “매일 백업”만으로 업무가 요구하는 RPO·RTO를 충족한다고 단정할 수 없다.

1.6 보안과 운영 통제

  • 개인별 계정과 역할 기반 최소권한 적용 여부
  • 공용·휴면 계정과 권한 검토 절차
  • 중요 데이터의 저장·전송 보호 방식
  • 접속·변경·권한 부여에 대한 감사 기록
  • 운영자와 개발자 역할 분리, 승인된 변경 절차
  • 비밀정보의 안전한 보관과 주기적 변경
  • 개발·시험 환경에서 실제 민감정보 사용 여부

분석 문서에 비밀번호, 인증키, 전체 개인정보 표본을 복사하지 않는다. 통제의 존재, 적용 범위, 검증 증거와 개선 필요사항을 적절한 권한으로 기록한다.

03

2. 비즈니스융합분석

2.1 의미와 목적

비즈니스융합분석은 업무·산업의 목표와 프로세스에 데이터, 소프트웨어, 자동화, 연결 기술 등을 결합해 새로운 가치 또는 개선 가능성을 찾고 실행 제약을 평가하는 활동이다. 기술을 도입하는 것 자체가 목적이 아니라 고객 가치, 비용, 품질, 속도, 위험 등 측정 가능한 업무 성과와 연결되어야 한다.

예를 들어 센서를 설치하는 것은 기술 적용이고, 설비 데이터를 이용해 고장 징후를 조기에 발견하여 중단시간을 줄이는 것은 비즈니스 융합의 가치 가설이다.

업무 담당자는 문제와 예외를 잘 알고, 기술 담당자는 시스템 제약과 데이터 상태를 안다. 한 집단의 주장만으로 결론 내리지 않고 여러 이해관계자의 관점을 대조한다.

2.3 분석 절차

  1. 비즈니스 목표 정의: “AI 도입”이 아니라 “반품 판정시간 30% 단축”처럼 결과를 표현한다.
  2. 현행 가치흐름 파악: 고객 요청부터 결과까지 단계, 대기, 인계, 오류와 수작업을 찾는다.
  3. 정보·기술 자산 연결: 이용 가능한 데이터, 시스템 기능, 연계, 인력과 운영역량을 정리한다.
  4. 융합 아이디어 도출: 자동화, 데이터 기반 의사결정, 채널 통합 등 가능한 변화 가설을 만든다.
  5. 가치와 실행 가능성 평가: 효과, 비용, 기간, 기술성, 데이터 준비도, 보안·규제 위험을 비교한다.
  6. 우선순위와 검증계획 설정: 작은 실험으로 핵심 가설을 검증하고 성공 기준을 정한다.
  7. 현행 시스템 영향 연결: 필요한 데이터와 인터페이스가 현재 DBMS·시스템에서 제공 가능한지 확인한다.

아이디어의 매력과 실행 가능성을 분리해 평가한다. 예상 효과가 크지만 필수 데이터가 없거나 품질이 낮다면, 데이터 확보와 품질 개선이 선행 과제가 된다.

2.4 비즈니스 융합 예시

예시 A: 설비 예방정비

  • 현행 문제: 고장 후 수리하여 생산 중단시간이 크다.
  • 융합 가설: 설비 상태 데이터를 모아 이상 징후를 사전에 탐지한다.
  • 필요 자산: 센서 데이터, 정비이력, 설비 식별자, 알림·작업 시스템 연계
  • 성과 기준: 비계획 중단시간, 탐지 정확도, 불필요 정비 건수
  • 위험: 데이터 결측, 잘못된 경보, 현장 수용성, 연결 보안

예시 B: 고객 채널 통합

  • 현행 문제: 온라인·상담·매장 이력이 분리되어 고객이 같은 정보를 반복 제공한다.
  • 융합 가설: 동의와 권한 아래 고객 접점 정보를 연결해 일관된 서비스를 제공한다.
  • 필요 자산: 식별 기준, 데이터 품질, 연계 인터페이스, 개인정보 통제
  • 성과 기준: 처리시간, 재문의율, 고객 만족도
  • 위험: 잘못된 고객 연결, 과도한 정보 노출, 목적 외 이용

예시는 특정 기술을 정답으로 제시하지 않는다. 업무 가치와 데이터·통제 조건이 달라지면 적합한 해법도 달라진다.

04

3. DBMS 분석과 비즈니스 융합을 연결하기

융합 요구가 데이터에 의존한다면 현행 DBMS 분석 결과와 연결해야 한다.

코드 예시 · text

비즈니스 성과 가설
→ 필요한 정보와 시점
→ 현행 데이터 위치·품질·보존기간
→ 접근권한과 법적·조직적 제약
→ 연계·처리 용량과 가용성
→ 부족분과 검증 과제

예를 들어 실시간 고객 추천을 구상했는데 현행 DBMS에는 전날까지의 배치 집계만 있고, 고객 동의 상태를 구분할 수 없다면 “추천 기능 개발”보다 데이터 시점과 동의 통제 문제가 선행된다. 현행 사실을 통해 아이디어의 조건을 구체화하는 것이 분석의 역할이다.

5. 시험 함정

  1. DBMS를 데이터베이스와 동일시: 데이터베이스는 조직화된 데이터 집합, DBMS는 이를 관리하는 소프트웨어다.
  2. 백업 성공과 복구 성공 동일시: 복구 시험 없이는 실제 복구 가능성과 소요시간을 보장하기 어렵다.
  3. RPO와 RTO 혼동: RPO는 허용 데이터 손실 시점, RTO는 허용 복구시간이다.
  4. 이중화만으로 가용성 보장: 전환 경로, 응용 재연결, 공통 장애, 시험 결과까지 확인한다.
  5. 큰 데이터는 곧 느림: 크기만으로 성능을 단정하지 않고 접근 패턴·동시성·구성·작업을 함께 본다.
  6. 기술 도입을 융합 가치로 착각: 기술명보다 해결할 업무 문제와 측정 성과를 먼저 정한다.
  7. 효과만 보고 준비도 무시: 필수 데이터 품질, 권한, 조직 역량과 운영비용을 함께 평가한다.
  8. 민감정보를 분석자료에 복제: 보안·개인정보 원칙에 따라 최소 정보와 통제 증거만 다룬다.
07

6. 확인 문제

문제 1

매일 백업 파일이 생성되면 RPO와 RTO가 충족되었다고 볼 수 있는가?

정답과 해설: 아니다. 백업 간격과 로그 보존이 허용 데이터 손실 범위를 충족하는지, 실제 복구 시험의 소요시간이 RTO를 충족하는지 확인해야 한다.

문제 2

DBMS 서버가 이중화되어 있으면 단일 장애점이 없다고 단정할 수 있는가?

정답과 해설: 없다. 공유 저장장치, 네트워크, 설정, 응용 연결, 운영 절차가 공통 장애점일 수 있다. 실제 전환과 복구를 전체 서비스 관점에서 확인한다.

문제 3

“챗봇을 도입한다”는 비즈니스융합분석의 충분한 목표인가?

정답과 해설: 아니다. 문의 처리시간 감소, 24시간 응대 범위, 상담원 이관 정확도처럼 해결할 문제와 성과 기준을 먼저 정의해야 한다.

문제 4

예상 가치가 큰 융합 아이디어지만 필요한 데이터의 절반이 수집되지 않는다. 어떻게 기록해야 하는가?

정답과 해설: 즉시 채택 또는 폐기보다 데이터 확보 가능성, 비용, 품질 개선과 작은 검증 계획을 선행 과제로 기록해 가치와 실행 가능성을 분리 평가한다.

문제 5

DBMS 사용량 분석에서 전체 용량만 확인하면 부족한 이유는?

정답과 해설: 업무별 크기, 증가율, 로그·임시 영역의 최대치, 보존정책, 최고 부하의 동시 작업이 증설 시점과 성능 위험에 서로 다른 영향을 주기 때문이다.

08

7. 최종 요약

  • DBMS 분석은 제품·버전·구성, 응용 의존성, 데이터 규모·증가율, 작업 패턴, 성능, 가용성, 백업·복구, 보안과 지원 상태를 확인한다.
  • 백업 파일의 존재가 아니라 업무 RPO·RTO와 복구 시험 결과로 복구 가능성을 판단한다.
  • DBMS 이중화는 전체 서비스의 장애 전환·재연결·공통 장애점과 함께 평가한다.
  • 비즈니스융합분석은 업무 목표와 프로세스, 이해관계자, 데이터·기술 자산, 제약을 연결해 가치 가설을 만든다.
  • 기술명보다 측정 가능한 업무 성과를 먼저 정하고 가치, 실행 가능성, 위험과 준비도를 비교한다.
  • 비즈니스 아이디어가 필요로 하는 데이터의 위치·품질·시점·권한을 현행 DBMS 분석 결과와 연결한다.
  • 확인된 현행 사실, 가치 가설, 미검증 항목을 분리해 후속 요구사항과 설계의 근거를 만든다.
