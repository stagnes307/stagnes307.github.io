01

0. 분석모델을 왜 확인하는가

요구사항 문장만으로는 복잡한 업무 흐름, 데이터 관계, 상태 변화와 시스템 경계를 모든 이해관계자가 같은 모습으로 떠올리기 어렵다. 분석모델은 현실의 중요한 부분을 목적에 맞게 추상화하여 구조·행위·정보·상호작용을 이해하도록 돕는다. 그러나 모델이 예쁘게 그려졌다고 정확한 것은 아니다. 원본 요구와 연결되고, 서로 모순이 없으며, 검증과 설계에 사용할 만큼 완전해야 한다.

이 레슨에서는 다음 세 주제를 다룬다.

  1. 모델링 기법: 관점을 선택하고 시스템을 추상화·분해·표현하는 방법
  2. 분석자동화 도구: 모델 작성, 저장, 일관성 검사, 문서 생성을 지원하는 도구
  3. 요구사항 관리 도구: 요구의 속성·버전·기준선·변경·추적관계를 관리하는 도구

목표는 특정 제품 사용법이 아니라, 모델과 도구를 이용해 요구사항의 완전성·일관성·추적 가능성을 확인하는 절차를 이해하는 것이다.

02

1. 모델링 기법

1.1 모델링의 기본 원리

모델은 원본 시스템의 축소 복사본이 아니라 분석 목적에 필요한 특징을 선택한 표현이다. 좋은 모델링은 다음 원리를 따른다.

  • 추상화: 불필요한 세부를 감추고 핵심 개념과 관계를 드러낸다.
  • 분해: 큰 문제를 이해 가능한 하위 영역·프로세스·기능으로 나눈다.
  • 관점 분리: 구조, 행위, 데이터, 상호작용 등 질문별로 표현한다.
  • 계층화: 상위 모델에서 하위 모델로 단계적으로 상세화한다.
  • 일관성: 같은 용어·객체·흐름이 여러 모델에서 모순되지 않는다.
  • 추적성: 모델 요소가 요구사항과 출처, 후속 설계·테스트에 연결된다.

하나의 다이어그램에 모든 정보를 넣으면 복잡해져 이해가 어렵다. 반대로 지나치게 단순하면 예외, 데이터, 책임이 빠진다. 모델의 독자와 검토 질문을 먼저 정한 뒤 필요한 상세 수준을 선택한다.

1.2 구조적 분석 기법

구조적 분석은 시스템을 기능 중심으로 단계적으로 분해하고 데이터의 흐름과 처리를 표현한다. 대표 요소는 다음과 같다.

  • 자료흐름도(DFD): 외부 개체, 프로세스, 자료흐름, 자료저장소의 관계
  • 자료사전(Data Dictionary): 데이터 이름, 의미, 구조, 범위와 별칭 정의
  • 소단위 명세(Mini-spec): 하위 프로세스의 처리 논리를 자세히 설명
  • 상태전이도: 사건에 따른 상태의 변화 표현

DFD의 핵심은 처리 순서도가 아니라 데이터가 어디서 와서 어떤 프로세스를 거쳐 어디로 가는지를 나타내는 것이다. 상위 문맥도에서 시스템 경계를 보이고, 하위 단계로 분해하면서 입·출력 흐름의 균형을 유지한다.

자료흐름도의 일반적인 균형 검토 예는 다음과 같다.

코드 예시 · text

상위 프로세스 입력: 주문 요청
상위 프로세스 출력: 주문 결과

하위 분해 후에도 외부 경계를 통과하는 입력·출력은
상위 모델과 의미상 일치해야 한다.

하위 모델에서 갑자기 외부 입력이 생기거나 상위 출력이 사라지면 요구 누락 또는 모델 불일치 가능성을 점검한다.

1.3 객체지향 분석 기법

객체지향 분석은 업무 영역의 객체를 식별하고 객체의 속성·책임·행위·관계와 상호작용을 모델링한다. 객체는 데이터와 관련 행위를 하나의 책임 단위로 본다.

분석 과정의 일반적인 질문은 다음과 같다.

  1. 업무에서 지속적으로 식별되는 주요 개념과 객체는 무엇인가?
  2. 각 객체가 알아야 할 정보와 수행할 책임은 무엇인가?
  3. 객체 사이에는 어떤 연관·의존·전체-부분 관계가 있는가?
  4. 유스케이스 또는 업무 사건을 수행할 때 객체가 어떻게 협력하는가?
  5. 한 객체에 책임이 과도하게 집중되거나 서로 중복되지는 않는가?

분석 객체를 구현 클래스와 곧바로 동일시하지 않는다. 분석 단계는 문제 영역의 의미와 책임을 설명하고, 구현 언어·프레임워크의 세부 구조는 후속 설계에서 결정한다.

1.4 정보공학과 프로세스·데이터 관점

정보공학적 접근은 조직의 정보 요구와 데이터 구조를 비교적 안정적인 기반으로 보고, 업무 기능·프로세스와 데이터의 관계를 분석한다. 전사 또는 업무 영역 수준에서 기능 분해, 데이터 모델, 프로세스-데이터 대응을 연결하는 데 유용하다.

예를 들어 프로세스와 데이터의 생성·조회·변경·삭제 관계를 표로 만들면 다음을 발견할 수 있다.

  • 어느 프로세스도 생성하지 않는 데이터
  • 생성되지만 사용되지 않는 데이터
  • 권한 없는 프로세스가 변경하는 데이터
  • 동일 데이터를 여러 곳에서 중복 생성하는 흐름

모델링 기법은 상호 배타적 정답이 아니다. 프로젝트의 규모, 업무 성격, 기존 산출물, 이해관계자 역량과 검토 목적에 따라 필요한 관점을 조합할 수 있다.

03

2. 분석모델 확인 절차

2.1 확인 준비

  • 모델의 목적, 범위, 표기 규칙과 버전을 확인한다.
  • 기준이 되는 요구사항 목록과 기준선을 정한다.
  • 업무 담당자, 분석가, 설계·개발·시험·운영 담당 등 검토자를 선정한다.
  • 미확정 용어, 가정, 외부 인터페이스와 제외 범위를 정리한다.

2.2 요구사항과의 추적 확인

요구 ID를 모델 요소와 연결한다.

순방향 추적은 모든 요구가 모델에 반영됐는지 보고, 역방향 추적은 모델 요소가 승인된 요구에 근거하는지 본다. 모델에 출처 없는 기능이 있다면 누락된 요구인지, 불필요한 범위 확장인지 확인한다.

2.3 완전성·일관성·정확성 확인

  • 완전성: 정상·대안·예외 흐름, 데이터, 인터페이스, 상태와 품질 제약이 필요한 수준으로 포함됐는가?
  • 일관성: 용어, 경계, 입·출력, 상태와 책임이 모델 사이에서 모순되지 않는가?
  • 정확성: 업무 규칙과 실제 이해관계자의 의도를 올바르게 반영했는가?
  • 이해 가능성: 표기법과 상세도가 검토자에게 적절한가?
  • 실현 가능성: 알려진 기술·법적·운영 제약과 충돌하지 않는가?
  • 검증 가능성: 모델로부터 수용 시나리오와 테스트 조건을 도출할 수 있는가?

검토 결과는 단순한 “수정 필요”가 아니라 모델 요소, 문제, 영향, 담당자, 기한, 결정 상태로 기록한다.

2.4 이해관계자 확인과 기준선

워크스루 또는 리뷰에서 시나리오를 따라가며 모델을 확인한다. 업무 담당자에게 표기법 설명만 요구하기보다 실제 사례를 제시한다. 예를 들어 “결제 승인 뒤 재고 부족이 확인되면 어떤 상태와 메시지가 필요한가?”처럼 모델의 예외를 구체적으로 검증한다.

합의된 모델과 요구사항은 기준선(baseline)으로 설정할 수 있다. 기준선은 영원히 변경하지 않는다는 뜻이 아니라, 이후 변경을 공식적으로 비교·승인·추적할 기준 버전이다.

3. 분석자동화 도구

3.1 역할

분석자동화 도구는 분석·설계 산출물의 작성, 저장, 연결, 일관성 검사와 문서화를 지원한다. 흔히 CASE(Computer-Aided Software Engineering) 도구 범주로 설명된다.

3. 분석자동화 도구 · 학습 표 2
구분주 지원 단계대표 기능
상위 CASE계획·분석·설계모델링, 요구 연결, 사전·저장소, 문서화
하위 CASE구현·시험·유지보수코드 생성·분석, 테스트 지원, 역공학
통합 CASE생명주기 전반공통 저장소와 단계 간 추적·연계

도구의 세부 분류와 기능은 제품에 따라 다를 수 있으므로 분류명만으로 실제 기능을 단정하지 않는다.

3.2 주요 기능

  • 표준 표기법을 이용한 다이어그램 작성
  • 모델 요소와 용어를 중앙 저장소에서 관리
  • 이름·타입·관계·참조의 일관성 검사
  • 상위·하위 모델 간 연결과 탐색
  • 보고서·사전·산출물 문서 생성
  • 모델 비교, 버전 관리, 변경 이력
  • 모델에서 코드 골격 생성 또는 기존 산출물의 역공학 지원
  • 여러 참여자의 협업, 검토 의견과 승인 흐름

자동화 도구는 형식적 오류와 연결 누락을 줄일 수 있지만 업무 의미의 정확성을 자동으로 보장하지 않는다. 도구가 “검사 통과”를 표시해도 잘못된 업무 규칙을 입력했다면 모델은 여전히 틀리다.

3.3 도구 선택 기준

  • 필요한 모델링 표기법과 산출물을 지원하는가?
  • 기존 개발·문서·형상관리 환경과 연계되는가?
  • 대규모 모델의 성능과 협업·권한 관리가 적절한가?
  • 데이터 내보내기와 장기 보존이 가능한가?
  • 도입·교육·운영·라이선스 비용이 가치에 맞는가?
  • 공급자 종속과 형식 호환 위험을 관리할 수 있는가?

기능이 많은 도구보다 팀이 일관되게 사용할 수 있고 필요한 추적·검토를 지원하는 도구가 적합하다.

05

4. 요구사항 관리 도구

4.1 핵심 역할

요구사항 관리 도구는 요구사항의 생명주기를 통제한다. 요구의 내용뿐 아니라 출처, 책임자, 우선순위, 상태, 버전, 승인, 변경, 추적관계를 구조적으로 관리한다.

주요 기능은 다음과 같다.

  • 요구 ID와 속성, 분류, 우선순위, 상태 관리
  • 버전, 변경 이력, 기준선과 승인 관리
  • 요구 간 상위·하위·의존·충돌 관계 표현
  • 요구 ↔ 분석모델 ↔ 설계 ↔ 코드 ↔ 테스트의 추적
  • 변경 영향분석과 미추적·미검증 항목 보고
  • 리뷰 의견, 협업, 알림, 권한과 감사 기록
  • 범위·상태·품질 지표와 추적성 보고서 생성

4.2 추적성과 변경 통제

요구사항 추적표는 단순 체크 목록이 아니다. 변경이 발생했을 때 영향을 받는 모델·설계·시험과 문서를 찾는 연결망이다.

코드 예시 · text

업무 목표
  ↓
사용자 요구
  ↓
시스템 요구 ─→ 분석모델 요소
  ↓                 ↓
설계 요소 ─────→ 테스트케이스

요구 변경 절차의 예는 다음과 같다.

  1. 변경 요청과 이유, 출처를 등록한다.
  2. 관련 요구·모델·설계·테스트의 영향을 분석한다.
  3. 가치, 비용, 위험, 일정과 충돌을 평가한다.
  4. 권한 있는 담당자가 승인·보류·거절을 결정한다.
  5. 승인된 기준선과 연결 산출물을 갱신한다.
  6. 구현·검증 완료와 문서 일관성을 확인한다.

도구에 저장했다고 변경이 통제되는 것은 아니다. 의사결정 권한, 상태 정의, 기준선 규칙, 갱신 책임이 조직 절차로 정해져야 한다.

5. 통합 적용 예시

주문 취소 요구를 분석한다고 하자.

  1. 요구사항 관리 도구에 FR-CANCEL-01을 등록하고 출처·우선순위·수용 기준을 기록한다.
  2. 모델링 기법으로 정상 취소, 결제 취소 실패, 배송 시작 후 요청 등 흐름과 상태를 표현한다.
  3. 분석자동화 도구의 저장소에서 주문 상태와 메시지 이름을 공통 정의하고 모델 간 참조를 연결한다.
  4. 추적 링크로 요구 ID와 흐름·상태 모델, 테스트 시나리오를 연결한다.
  5. 리뷰에서 “부분 취소”가 범위에서 누락되었음을 발견하면 변경 요청으로 영향과 우선순위를 평가한다.
  6. 합의된 버전을 기준선으로 설정하고 후속 변경 이력을 남긴다.

도구는 이 흐름을 지원하지만 누락을 발견하고 업무 결정을 내리는 책임은 사람에게 있다.

6. 시험 함정

  1. 모델을 현실의 완전한 복사로 오해: 모델은 목적에 따른 추상화다.
  2. DFD와 순서도 혼동: DFD는 데이터 흐름과 처리 관계, 순서도는 제어 절차 중심이다.
  3. 상·하위 모델 균형 무시: 분해 전후 외부 입·출력의 의미가 일치해야 한다.
  4. 분석 객체를 구현 클래스로 즉시 확정: 분석은 문제 영역의 책임, 설계는 구현 구조를 구체화한다.
  5. CASE 도구가 업무 정확성을 보장: 형식 검사는 가능하지만 의미 검증은 이해관계자 리뷰가 필요하다.
  6. 상위·하위 CASE 단계 반대로 기억: 상위는 계획·분석·설계, 하위는 구현·시험·유지보수 중심이다.
  7. 요구사항 저장과 관리 동일시: 기준선, 승인, 변경, 추적과 책임 절차가 있어야 관리다.
  8. 기준선은 변경 금지: 통제되지 않은 변경을 막는 비교 기준이며 승인 절차로 변경할 수 있다.
  9. 추적 링크를 사후 일괄 작성: 변경과 함께 지속적으로 갱신하지 않으면 신뢰도가 낮아진다.

7. 확인 문제

문제 1

상위 DFD의 입력이 하위 DFD에서 이유 없이 사라졌다. 무엇을 확인해야 하는가?

정답과 해설: 상·하위 모델의 균형과 요구 누락을 확인한다. 분해 후에도 외부 경계를 통과하는 입·출력의 의미가 상위 모델과 일치해야 한다.

문제 2

분석자동화 도구의 일관성 검사에 통과하면 업무 규칙도 정확하다고 볼 수 있는가?

정답과 해설: 아니다. 도구는 이름·타입·참조 같은 형식적 일관성을 도울 수 있지만 업무 의미는 원본 요구와 이해관계자 검토로 확인해야 한다.

문제 3

요구사항 기준선을 설정한다는 의미는 이후 변경을 금지한다는 뜻인가?

정답과 해설: 아니다. 승인된 비교 기준을 정해 이후 변경의 이유·영향·승인·반영 이력을 통제한다는 뜻이다.

문제 4

요구사항 관리 도구에서 테스트케이스 연결이 없는 요구를 발견했다. 어떤 위험을 의미하는가?

정답과 해설: 해당 요구가 검증되지 않거나 수용 기준이 누락되었을 수 있다. 요구의 검증 가능성과 테스트 추적 링크를 확인한다.

문제 5

분석자동화 도구와 요구사항 관리 도구는 항상 별도 제품이어야 하는가?

정답과 해설: 아니다. 실제 제품은 기능이 통합되거나 겹칠 수 있다. 모델 작성·일관성 지원과 요구 생명주기·추적 통제라는 역할을 구분해 판단한다.

8. 최종 요약

  • 모델링 기법은 추상화, 분해, 관점 분리, 계층화, 일관성과 추적성을 통해 복잡한 요구를 이해 가능한 모델로 표현한다.
  • 구조적 분석은 기능과 데이터 흐름을, 객체지향 분석은 객체의 책임·관계·협력을, 정보공학은 업무 기능과 데이터의 연계를 강조한다.
  • 분석모델은 요구 추적, 완전성, 일관성, 정확성, 이해 가능성, 실현·검증 가능성으로 확인한다.
  • 분석자동화 도구는 모델 작성·저장·일관성 검사·문서화와 단계 간 연계를 지원하지만 업무 의미를 자동 보장하지 않는다.
  • 요구사항 관리 도구는 요구 속성, 버전, 기준선, 승인, 변경 영향과 양방향 추적을 관리한다.
  • 기준선은 변경 금지가 아니라 통제된 변경의 기준이다.
  • 도구보다 표기 규칙, 검토 책임, 변경 절차와 지속적인 추적 갱신이 분석모델 품질을 좌우한다.
