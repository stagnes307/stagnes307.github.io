# 1-2-1-1. UI 표준 · UI 지침

> **공식 범위**: 소프트웨어설계 > 화면 설계 > UI 요구사항 확인 > `UI 표준`, `UI 지침`

## 0. 학습 목표와 범위

UI(User Interface)는 사용자가 시스템의 상태를 이해하고 목표를 수행하며 결과와 오류를 확인하는 접점이다. 화면이 보기 좋은지만 평가하는 것이 아니라 용어, 정보 구조, 입력 방식, 피드백, 접근성, 일관성과 오류 예방이 사용자의 과업을 지원하는지 확인해야 한다.

이 레슨에서는 조직 또는 제품 전반에 공통으로 적용할 **필수 규칙**과 그 규칙을 상황에 맞게 적용하는 **설명·권고**를 구분한다.

1. `UI 표준`: 화면과 상호작용의 일관성을 위해 반드시 준수하도록 합의한 공통 기준
2. `UI 지침`: UI 원칙, 표준의 적용 방법, 좋은·나쁜 사례, 판단 기준을 설명한 안내

구체적인 화면 흐름이나 스토리보드 작성은 인접 레슨의 범위다. 여기서는 개별 화면을 설계하기 전에 필요한 공통 언어와 품질 기준을 정하는 데 집중한다.

## 1. UI 표준

### 1.1 UI 표준의 목적

UI 표준은 여러 화면과 개발팀이 같은 규칙을 사용하게 해 사용자의 학습 부담과 실수를 줄이고, 개발·시험·유지보수의 중복을 줄인다. 대표 목적은 다음과 같다.

- 동일한 기능은 같은 용어와 동작으로 제공한다.
- 사용자에게 현재 상태와 처리 결과를 예측 가능하게 알린다.
- 반복되는 구성요소를 재사용해 품질과 생산성을 높인다.
- 다양한 장치·브라우저·보조기술에서 필요한 접근성을 확보한다.
- 오류 메시지, 입력 검증, 권한 표시 등 공통 품질을 일관되게 적용한다.
- 변경 시 영향 범위와 예외 승인 기준을 명확히 한다.

표준은 모든 화면을 똑같이 만드는 규칙이 아니다. 업무 맥락이 다른 화면에는 다른 구성이 필요할 수 있지만, 같은 의미의 버튼·상태·피드백은 일관되게 표현해야 한다.

### 1.2 UI 표준의 구성 요소

조직과 제품에 따라 문서 구조는 달라질 수 있지만 일반적으로 다음 범주를 포함한다.

| 범주 | 표준화 대상 | 예시 |
|---|---|---|
| 원칙·정책 | 사용자 경험 목표와 우선 가치 | 명확성, 일관성, 접근성, 오류 예방 |
| 용어·콘텐츠 | 메뉴명, 버튼명, 날짜·금액·단위, 문체 | “저장/등록” 혼용 금지, 날짜 표기 규칙 |
| 레이아웃 | 화면 영역, 정렬, 간격, 반응형 기준 | 제목·본문·작업영역의 계층 |
| 구성요소 | 버튼, 입력, 표, 탭, 알림, 대화상자 | 상태·크기·사용 조건 |
| 상호작용 | 선택, 제출, 취소, 이동, 피드백 | 처리 중 표시, 중복 제출 방지 |
| 시각 표현 | 색, 글꼴, 아이콘, 강조와 상태 | 색만으로 오류 구분 금지 |
| 접근성 | 키보드, 초점, 레이블, 대체정보 | 논리적 초점 순서, 입력 설명 |
| 기술·환경 | 지원 장치·해상도·브라우저 범위 | 테스트 기준과 지원 정책 |

색상 코드나 글꼴 크기만 모은 문서는 UI 표준의 일부일 뿐이다. 상호작용, 콘텐츠, 오류, 접근성과 운영 규칙까지 포함해야 실제 사용자 경험의 일관성을 만들 수 있다.

### 1.3 구성요소 상태를 정의한다

버튼 하나도 기본·호버·초점·누름·비활성·처리 중 상태가 있을 수 있다. 입력 필드는 빈 값, 정상 입력, 오류, 읽기 전용, 비활성 상태를 구분한다. 상태별 시각 표현과 동작, 보조기술에 전달할 의미를 정의하지 않으면 팀마다 다르게 구현된다.

예를 들어 제출 버튼 표준을 다음처럼 정할 수 있다.

```text
명칭: 사용자가 얻는 결과를 동사로 표현한다. 예: 주문하기
위치: 주요 작업영역의 일관된 위치
상태: 기본 / 키보드 초점 / 처리 중 / 완료 / 실패
처리 중: 중복 제출을 막고 진행 상태를 알린다.
완료: 결과와 다음 행동을 명확히 제시한다.
실패: 원인, 수정 방법, 보존된 입력을 설명한다.
```

“비활성 버튼은 회색”만 규정하면 왜 사용할 수 없는지 알기 어렵다. 필요한 조건을 안내하거나 실행 시 구체적 오류를 제공하는 방식 등 사용자 과업 관점의 규칙도 필요하다.

### 1.4 용어와 데이터 표현 표준

같은 개념을 “고객”, “회원”, “사용자”로 섞어 쓰면 사용자는 다른 대상으로 오해할 수 있다. 업무 용어집과 연결해 한 개념의 대표 명칭, 허용 별칭, 금지 표현을 정한다.

날짜·시간·금액·전화번호·단위는 표시 형식뿐 아니라 입력 허용 범위, 시간대, 반올림, 빈 값과 오류 처리까지 결정해야 한다. 예를 들어 날짜 `2026-08-28`과 `28/08/2026`은 사용자 지역에 따라 해석이 달라질 수 있으므로 대상 사용자와 업무 규칙에 맞는 형식을 명시한다.

### 1.5 접근성을 공통 품질로 포함한다

접근성은 별도 화면 몇 개에 추가하는 기능이 아니라 구성요소와 콘텐츠 표준의 일부다.

- 텍스트와 배경은 충분히 구분되고 상태를 색 하나로만 전달하지 않는다.
- 모든 핵심 기능은 키보드만으로도 접근·실행 가능하게 한다.
- 초점 위치가 시각적으로 보이고 이동 순서가 논리적이어야 한다.
- 입력 요소에는 의미 있는 레이블과 오류 설명을 연결한다.
- 이미지·아이콘에는 목적에 맞는 대체정보를 제공한다.
- 제목·목록·표 등 정보 구조를 의미에 맞게 표현한다.
- 동적 변경과 처리 결과가 보조기술 사용자에게도 전달되도록 한다.

구체적인 법적·표준 요구는 적용 지역과 서비스 유형, 유효한 조직 기준을 확인한다. 특정 수치를 무조건 적용한다고 단정하기보다 공식 접근성 기준과 프로젝트 정책을 근거로 삼는다.

## 2. UI 지침

### 2.1 UI 지침의 역할

`UI 지침`은 UI 표준을 왜·언제·어떻게 적용하는지 설명한다. 원칙, 절차, 패턴, 예시, 예외 판단과 검토 체크리스트를 제공한다. 표준이 “같은 기능의 주 버튼은 한 화면에 명확히 구분한다”는 규칙이라면, 지침은 주 버튼을 선정하는 방법, 버튼이 여러 개일 때의 우선순위, 좋은·나쁜 사례를 설명한다.

지침의 대표 원칙은 다음과 같다.

- 명확성: 사용자가 현재 상태와 다음 행동을 이해한다.
- 일관성: 같은 개념과 동작은 같은 방식으로 나타난다.
- 피드백: 사용자 행동 뒤 시스템 반응을 적시에 보여 준다.
- 사용자 통제: 취소·되돌리기·나가기와 결과 예측을 지원한다.
- 오류 예방·회복: 실수를 막고 발생한 오류에서 회복하도록 돕는다.
- 효율성: 자주 쓰는 작업은 불필요한 단계를 줄인다.
- 인지 부담 감소: 기억보다 인식, 적절한 묶음과 정보 계층을 사용한다.
- 접근성과 포용성: 다양한 능력·장치·환경을 고려한다.

### 2.2 오류 예방과 메시지 지침

좋지 않은 메시지:

```text
오류가 발생했습니다. 코드 E103.
```

개선된 메시지의 구조:

```text
무엇이 잘못되었는가: 종료일은 시작일보다 빠를 수 없습니다.
어떻게 고치는가: 종료일을 2026-08-28 이후로 선택하세요.
입력 보존: 다른 입력값은 유지합니다.
필요 시 지원: 반복되면 문의 경로와 추적번호를 제공합니다.
```

오류를 빨간색만으로 표현하지 않고 텍스트·아이콘·필드 연결을 함께 사용한다. 입력 후 모든 오류를 한꺼번에 표시할지, 입력 중 즉시 안내할지는 과업과 오류 유형에 맞게 정한다. 사용자가 입력을 마치기도 전에 과도하게 경고하면 오히려 방해가 될 수 있다.

### 2.3 피드백과 응답 지침

사용자 행동 뒤 아무 변화가 없으면 중복 클릭과 불안을 유발한다.

- 즉시 완료되는 작업: 버튼 상태, 메시지, 화면 변화로 결과를 알린다.
- 시간이 필요한 작업: 처리 중 상태와 중복 실행 방지를 제공한다.
- 장시간 작업: 진행 상황, 예상 단계, 백그라운드 처리 여부를 알린다.
- 실패한 작업: 원인 범위, 재시도 가능성, 보존된 상태를 설명한다.
- 되돌릴 수 없는 작업: 영향과 대상을 명확히 알리고 적절한 확인을 거친다.

모든 작업에 확인 대화상자를 띄우면 사용자는 습관적으로 승인하게 된다. 삭제·전송·결제처럼 영향이 크고 되돌리기 어려운 작업에 집중하고, 가능하면 실행 취소나 복구 기능을 제공한다.

### 2.4 정보 구조와 내비게이션 지침

정보는 사용자의 업무 목표와 중요도에 따라 묶는다. 조직 내부 시스템 구조를 그대로 메뉴에 드러내기보다 사용자가 찾는 용어와 과업 흐름을 사용한다.

- 현재 위치와 상위·하위 관계를 알 수 있게 한다.
- 동일 목적의 기능은 예측 가능한 위치에 배치한다.
- 메뉴 깊이와 한 화면의 선택지를 균형 있게 조절한다.
- 주요 행동과 보조 행동을 시각적 계층으로 구분한다.
- 뒤로 이동, 취소, 저장되지 않은 변경의 처리 규칙을 일관되게 한다.
- 검색·필터 결과에서 적용된 조건과 결과 수를 알린다.

“클릭 수가 적을수록 무조건 좋다”는 규칙은 위험하다. 한 화면에 너무 많은 정보를 넣어 판단을 어렵게 만드는 것보다 의미 있는 단계로 나누는 편이 나을 수 있다. 과업 완료시간, 오류, 이해도와 만족도를 함께 본다.

## 3. UI 표준과 UI 지침의 관계

| 구분 | UI 표준 | UI 지침 |
|---|---|---|
| 핵심 질문 | 반드시 무엇을 일관되게 지켜야 하는가? | 왜·언제·어떻게 적용할 것인가? |
| 성격 | 합의된 필수 규칙과 기준 | 원칙, 설명, 패턴, 사례와 체크리스트 |
| 예 | 오류 상태는 색과 텍스트를 함께 사용 | 오류 문구 작성법과 좋은·나쁜 사례 |
| 변경 통제 | 버전·승인·예외 절차 필요 | 사용 피드백과 사례로 지속 보완 |

두 문서는 분리될 수도 있고 하나의 디자인 시스템 문서에 통합될 수도 있다. 명칭보다 필수 규칙과 적용 안내가 명확한지 확인한다. 디자인 시스템은 구성요소, 설계 자산, 코드, 원칙과 운영체계를 포함할 수 있어 단순 스타일 가이드보다 넓지만 조직마다 범위가 다르다.

## 4. 표준과 지침 수립 절차

### 4.1 현행과 사용자 요구 조사

기존 화면, 고객 문의, 사용성 문제, 오류 로그, 접근성 점검, 지원 환경을 조사한다. 팀별로 다른 버튼명이나 날짜 형식, 반복되는 오류를 목록화한다. 사용자군의 장치, 숙련도, 언어, 사용환경과 핵심 과업을 파악한다.

### 4.2 원칙과 범위 합의

제품의 사용자 경험 목표와 우선 원칙을 정하고 어떤 서비스·장치·조직에 적용할지 명시한다. 법규, 브랜드, 보안, 접근성, 기술환경과 충돌하는 요구를 조정한다.

### 4.3 공통 패턴과 규칙 정의

빈도가 높고 오류 영향이 큰 요소부터 용어, 데이터 형식, 내비게이션, 입력, 표, 상태, 메시지와 접근성 규칙을 정의한다. 구성요소의 상태와 사용·금지 조건, 예외 사례를 함께 작성한다.

### 4.4 시범 적용과 검증

대표 업무 흐름에 적용해 개발 가능성, 사용성, 접근성, 시험 가능성을 확인한다. 디자이너만 검토하지 않고 개발·시험·운영·업무 담당과 실제 사용자 피드백을 포함한다.

### 4.5 배포와 거버넌스

- 표준·지침의 소유자와 승인 책임
- 버전, 변경 이력, 적용 시점
- 예외 요청·심사·만료 절차
- 공통 구성요소 배포와 지원 방식
- 교육, 질문, 결함 신고 경로
- 준수 점검과 사용자 성과 측정

문서를 배포했다고 채택되는 것은 아니다. 구현 자산, 예제, 검토 절차와 지원체계가 함께 있어야 한다. 예외는 무조건 금지하지 않되 이유, 영향, 승인, 유효기간을 기록해 표준의 신뢰도를 유지한다.

---

## 5. 적용 예시: 회원가입 입력 화면

### 표준으로 정할 항목

- 모든 입력에는 지속적으로 확인 가능한 레이블을 제공한다.
- 필수 항목 표시 방식과 설명을 전 화면에서 동일하게 사용한다.
- 오류는 해당 입력과 연결하고 색만으로 구분하지 않는다.
- 제출 중에는 중복 전송을 막고 처리 상태를 알린다.
- 날짜, 전화번호, 비밀번호 규칙의 표현을 일관되게 한다.
- 키보드 초점 순서와 상태가 논리적이고 보이도록 한다.

### 지침으로 설명할 항목

- 레이블은 사용자가 아는 업무 용어로 짧고 명확하게 쓴다.
- 도움말은 입력 전에 필요한 규칙을 제공하고 오류 뒤에만 숨기지 않는다.
- 오류 메시지는 문제와 해결 방법을 함께 제시한다.
- 비밀번호 규칙은 입력 중 확인 가능하게 하고 값을 노출하지 않는다.
- 제출 실패 시 수정과 무관한 입력은 가능한 한 보존한다.

### 확인 지표

과업 완료율, 완료시간, 입력 오류율, 재시도 횟수, 지원 문의, 키보드·보조기술 사용 가능성 등을 본다. “표준을 적용했다”는 사실보다 실제 사용자가 더 쉽게 성공하는지 확인한다.

## 6. 검토 체크리스트

1. 같은 개념과 행동에 같은 용어·구성요소를 사용하는가?
2. 주요 행동과 보조 행동의 우선순위가 명확한가?
3. 사용자의 행동 뒤 상태와 결과를 적시에 알리는가?
4. 오류를 예방하고 발생 시 수정 방법과 복구 경로를 제공하는가?
5. 키보드, 초점, 레이블, 정보 구조와 대체정보가 고려되었는가?
6. 화면 크기·확대·언어 길이 변화에도 핵심 정보와 기능이 유지되는가?
7. 데이터 형식, 단위, 시간대와 빈 값의 의미가 일관적인가?
8. 공통 구성요소를 임의로 변형했을 때 영향과 예외 승인이 기록되는가?
9. 표준의 버전과 적용 대상, 지원 환경이 명확한가?
10. 사용자 시험과 운영 데이터로 지침을 개선할 절차가 있는가?

## 7. 시험 함정

1. **UI를 시각 디자인으로 한정**: 상호작용, 콘텐츠, 피드백, 오류, 접근성과 사용자 과업을 포함한다.
2. **표준과 지침 동일시**: 표준은 필수 공통 기준, 지침은 적용 원칙·방법·사례를 제공한다.
3. **일관성을 모든 화면의 동일화로 오해**: 같은 의미와 동작을 일관되게 하되 업무 맥락 차이는 반영한다.
4. **색만으로 상태 전달**: 텍스트·아이콘·구조 등 다른 단서도 제공한다.
5. **비활성화만으로 설명 완료**: 사용 불가 이유와 필요한 조건을 사용자가 이해할 수 있어야 한다.
6. **확인창을 많을수록 안전하다고 판단**: 중요한 비가역 작업에 집중하고 실행 취소·복구를 고려한다.
7. **클릭 수 최소화 절대화**: 과업 성공, 이해도, 오류와 인지 부담을 함께 평가한다.
8. **접근성을 개발 후 추가**: 구성요소와 콘텐츠 표준 단계부터 포함해야 비용과 누락을 줄인다.
9. **문서 배포만으로 표준 정착**: 소유자, 버전, 예외, 구현 자산, 교육과 점검이 필요하다.

## 8. 확인 문제

### 문제 1

“오류 상태는 색과 텍스트를 함께 사용한다”와 “오류 문구는 문제와 수정 방법을 설명한다” 중 어느 것이 표준과 지침에 더 가까운가?

**정답과 해설**: 첫 문장은 공통으로 준수할 필수 규칙인 UI 표준에 가깝고, 둘째 문장은 문구 작성 방법을 안내하는 UI 지침에 가깝다. 실제 문서에서는 함께 관리될 수 있다.

### 문제 2

모든 화면의 주 버튼을 같은 위치와 색으로 만들면 일관성이 완성되는가?

**정답과 해설**: 아니다. 용어, 동작, 상태, 피드백, 오류 처리와 접근성도 일관되어야 하며 업무 맥락에 필요한 차이도 허용해야 한다.

### 문제 3

삭제 작업마다 확인 대화상자를 두면 오류 예방에 항상 가장 좋은가?

**정답과 해설**: 아니다. 과도한 확인은 습관적 승인을 유발할 수 있다. 영향이 큰 작업을 명확히 설명하고, 가능하면 실행 취소·복구를 제공하며, 대상과 결과를 확인하게 한다.

### 문제 4

버튼의 오류 상태를 빨간색으로만 표시할 때 생기는 문제는?

**정답과 해설**: 색을 구분하기 어렵거나 화면을 보지 못하는 사용자가 상태를 알 수 없다. 텍스트, 아이콘, 의미 구조와 보조기술 전달을 함께 제공한다.

### 문제 5

UI 표준 예외가 필요하면 무조건 금지해야 하는가?

**정답과 해설**: 아니다. 업무·법규·기술상 정당한 예외가 있을 수 있다. 이유와 사용자 영향, 대안, 승인자, 적용 범위와 만료·재검토 조건을 기록한다.

## 9. 최종 요약

- `UI 표준`은 용어, 레이아웃, 구성요소, 상호작용, 콘텐츠, 상태, 접근성, 지원 환경의 필수 공통 기준이다.
- 표준은 화면을 무조건 똑같게 만드는 것이 아니라 같은 의미와 행동을 예측 가능하게 한다.
- `UI 지침`은 명확성, 일관성, 피드백, 사용자 통제, 오류 예방·회복, 효율성과 접근성의 적용 방법과 사례를 제공한다.
- 표준은 “무엇을 지킬지”, 지침은 “왜·언제·어떻게 적용할지”에 더 초점을 둔다.
- 현행 조사, 원칙·범위 합의, 공통 패턴 정의, 시범 검증, 배포·거버넌스 순으로 수립한다.
- 접근성은 사후 추가 기능이 아니라 공통 구성요소와 콘텐츠 규칙에 포함한다.
- 문서뿐 아니라 구현 자산, 버전·예외 절차, 교육, 준수 점검과 사용자 성과 측정이 있어야 표준이 유지된다.
