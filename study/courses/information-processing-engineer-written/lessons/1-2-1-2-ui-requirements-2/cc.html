공식 범위: 2026년 정보처리기사 출제기준의 소프트웨어설계 > 화면 설계 > UI 요구사항 확인 > 3. 스토리보드를 중심으로 학습한다. 이 레슨의 정확한 토픽은 스토리보드, UI 요구사항 확인의 적용 절차와 판단 기준이다. 특정 제작 도구의 버전이나 조직별 문서 양식은 고정하지 않고, 시험에서 변하지 않는 목적·구성·검토 원칙에 집중한다.

스토리보드는 화면을 예쁘게 그리는 산출물이 아니다. 사용자 요구를 화면 단위의 동작, 이동, 입력, 출력, 예외 규칙으로 번역하여 기획자·설계자·개발자·테스터가 같은 시스템을 상상하도록 만드는 명세다. 따라서 그림의 화려함보다 추적 가능하고 검증 가능한 설명이 중요하다.

01

1. 스토리보드의 역할

1.1 정의

스토리보드는 화면 구성, 화면 간 이동, 사용자 조작에 따른 동작, 데이터와 메시지, 예외 상황 등을 화면별로 정리한 설계 문서다. 보통 화면 ID와 화면명, 레이아웃, 항목 설명, 이동 규칙, 처리 조건을 함께 기록한다.

스토리보드가 해결하는 핵심 질문은 네 가지다.

  1. 사용자는 어느 화면에서 무엇을 볼 수 있는가?
  2. 어떤 입력이나 조작을 할 수 있는가?
  3. 조작이 성공·실패했을 때 시스템은 어떻게 반응하는가?
  4. 다음에는 어느 화면 또는 상태로 이동하는가?

화면 한 장만 보여 주고 “버튼을 누르면 처리된다”라고 적으면 충분하지 않다. 처리 조건, 결과 메시지, 중복 조작, 입력 오류, 권한 부족 같은 분기까지 명확해야 구현과 테스트가 가능하다.

1.2 유사 산출물과 비교

1. 스토리보드의 역할 · 학습 표 1
산출물주된 초점표현 수준스토리보드와의 차이
화면 흐름도화면 간 이동 관계전체 흐름 중심개별 화면 항목과 상세 동작은 제한적
와이어프레임화면 배치와 정보 구조저충실도 구조이동·처리·예외 규칙이 충분하지 않을 수 있음
목업색상·모양 등 시각 결과정적 고충실도실제 상호작용이나 처리 규칙은 생략될 수 있음
프로토타입조작 가능한 동작 검증상호작용 중심명세 문서가 없으면 세부 규칙의 근거가 불분명할 수 있음
스토리보드화면·항목·동작·이동의 통합 명세구현·검토 가능한 상세 수준요구사항과 화면 동작을 추적 가능하게 연결

시험에서는 “와이어프레임은 구조”, “스토리보드는 화면 설명과 흐름을 포함한 문서”, “프로토타입은 동작을 시험하는 모형”이라는 중심 차이를 잡는다. 실제 현장에서는 산출물 이름과 경계가 조직마다 조금씩 다를 수 있으므로 명칭보다 목적을 판단한다.

02

2. 스토리보드의 기본 구성

2.1 문서 식별 정보

  • 프로젝트명과 업무 영역
  • 화면 ID, 화면명, 화면 유형
  • 작성자, 작성일, 버전, 변경 이력
  • 관련 요구사항 ID와 상위 업무 ID

화면 ID는 단순 번호가 아니라 추적의 연결점이다. 요구사항, 개발 작업, 테스트 케이스, 결함 기록에서 같은 ID를 참조하면 변경 영향 범위를 찾기 쉽다.

2.2 화면 구성 정보

  • 헤더, 본문, 메뉴, 입력 영역, 결과 영역, 하단 영역
  • 필드, 버튼, 링크, 표, 목록, 메시지의 위치와 이름
  • 필수·선택 여부, 초기값, 표시 형식, 활성·비활성 조건
  • 데이터 출처와 출력 항목

“검색 조건”처럼 묶어서 적기보다 항목마다 이름·자료형·길이·허용 범위·필수 여부를 구체화해야 한다. 다만 이 레슨은 데이터베이스의 물리 칼럼 설계가 아니라 UI 요구를 화면 명세로 옮기는 범위다.

2.3 동작과 이동 정보

  • 화면 진입 조건과 이전 화면
  • 사용자가 수행할 수 있는 조작
  • 버튼·링크·항목 선택 시 처리
  • 성공 시 결과와 다음 화면
  • 실패·취소·시간 초과 시 결과
  • 뒤로 가기, 중복 클릭, 새로 고침 시 처리

화면 이동은 화살표만으로 끝내지 않는다. 로그인 성공 → 대시보드, 인증 실패 → 현재 화면 유지 + 오류 메시지, 비밀번호 재설정 선택 → 재설정 요청 화면처럼 조건-행동-결과로 작성한다.

2.4 정책과 제약

  • 사용자 역할과 접근 권한
  • 입력 검증과 오류 메시지
  • 개인정보 마스킹 여부
  • 응답 시간이나 한 번에 표시할 데이터 범위
  • 키보드 이동, 대체 텍스트, 명도 대비 등 접근성 요구
  • 지원할 화면 크기나 기기 범위

정책을 “적절히 처리”라고 쓰면 판단이 불가능하다. 예를 들어 “전화번호가 형식에 맞지 않으면 저장하지 않고 해당 필드 가까이에 오류 이유를 표시한다”처럼 관찰 가능한 결과로 작성한다.

03

3. 토픽 ① 스토리보드 작성 절차

단계 1: 요구사항과 사용자 작업을 모은다

기능 요구사항, 사용자 역할, 업무 규칙, 기존 화면의 문제점, 법적·접근성 제약을 수집한다. 요구사항마다 ID를 부여하고 사용자 관점의 목표로 다시 읽는다.

예: REQ-SIGN-03 회원은 필수 약관에 동의하고 유효한 정보를 입력하면 가입할 수 있다.

단계 2: 화면과 상태를 식별한다

업무 흐름을 시작·입력·확인·완료·실패 상태로 나누고 필요한 화면을 찾는다. 모달, 빈 결과, 로딩, 오류도 사용자에게 보이는 상태라면 명세 대상이다.

단계 3: 화면 흐름을 연결한다

각 화면의 진입점과 종료점을 연결한다. 정상 경로만 그리지 말고 인증 실패, 권한 부족, 입력 오류, 취소, 데이터 없음 같은 대체 경로를 포함한다.

단계 4: 화면별 항목과 동작을 기술한다

화면 ID, 화면명, 항목 ID, 표시 문구, 입력 규칙, 버튼 동작, 메시지, 이동 화면을 작성한다. 하나의 항목이 여러 조건에서 다르게 동작하면 조건별로 나눈다.

단계 5: 요구사항과 대응시킨다

각 화면·동작이 어느 요구사항을 구현하는지 연결한다. 반대로 모든 UI 요구사항이 최소 한 곳에 반영되었는지 추적표로 확인한다.

단계 6: 이해관계자 검토와 기준선 확정

사용자, 기획, 설계, 개발, 테스트 관점에서 검토한다. 합의된 버전을 기준선으로 정하고 이후 변경은 변경 사유·영향·승인·버전을 기록한다.

04

4. 토픽 ② UI 요구사항 확인의 적용 절차와 판단 기준

4.1 적용 절차

UI 요구사항 확인은 “받은 요구를 그대로 문서에 복사”하는 일이 아니다.

  1. 분류: 기능, 데이터, 사용성, 접근성, 보안, 운영 제약으로 나눈다.
  2. 정제: 모호한 표현과 충돌하는 조건을 질문으로 바꾼다.
  3. 우선순위화: 필수·선택, 위험도, 업무 중요도를 구분한다.
  4. 화면 매핑: 사용자 작업과 화면·상태를 연결한다.
  5. 구체화: 입력·출력·동작·예외를 스토리보드에 기술한다.
  6. 검증: 요구사항과 화면 명세를 양방향으로 추적한다.
  7. 합의·변경 관리: 승인된 기준선과 변경 이력을 유지한다.

4.2 판단 기준

4. 토픽 ② UI 요구사항 확인의 적용 절차와 판단 기준 · 학습 표 2
기준확인 질문불량 예

일관성같은 용어와 규칙이 화면마다 동일한가?한 화면은 고객, 다른 화면은 회원

판단 기준은 따로 떨어져 있지 않다. 예를 들어 “검색 결과는 빨리 나와야 한다”는 요구는 의도는 이해되지만 명확성과 시험 가능성이 부족하다. 허용 응답 기준과 측정 조건을 합의해야 검증 가능해진다.

5. 작성 예시: 회원가입 화면

5.1 화면 기본 정보

코드 예시 · text

화면 ID: SIGN-01
화면명: 회원가입 정보 입력
관련 요구: REQ-SIGN-03, REQ-SIGN-04
진입 조건: 비로그인 사용자가 회원가입을 선택함
정상 종료: 가입 완료 화면 SIGN-02로 이동

5.2 항목 명세 예

5. 작성 예시: 회원가입 화면 · 학습 표 3
항목 ID항목명규칙오류·결과
F-01이메일필수, 이메일 형식, 중복 확인형식 오류는 필드 가까이에 이유 표시
F-02비밀번호필수, 문제에서 정한 정책 충족조건별 충족 여부 안내
C-01필수 약관모두 동의해야 제출 가능미동의 시 해당 항목 강조
B-01가입모든 필수 검증 통과 시 처리성공하면 SIGN-02, 실패하면 현재 화면 유지

5.3 검토 질문

  • 이메일 중복 확인 뒤 값을 바꾸면 확인 상태를 초기화하는가?
  • 가입 버튼을 연속으로 누르면 중복 요청을 방지하는가?
  • 서버 오류가 발생했을 때 사용자가 입력한 값을 유지하는가?
  • 필드 오류를 색상만이 아니라 문구로도 알리는가?
  • 가입 완료 후 뒤로 가기를 했을 때 재제출되지 않는가?

이런 질문은 구현 세부를 대신 결정하려는 것이 아니라 요구사항의 누락과 모호성을 드러내기 위한 것이다.

06

6. 검토 방법과 변경 관리

6.1 역할별 검토

  • 업무 담당자: 실제 업무 규칙과 순서가 맞는가?
  • 사용자 관점: 목표를 불필요한 단계 없이 달성하는가?
  • 개발 관점: 입력·출력·상태·예외가 구현 가능하게 명시됐는가?
  • 테스트 관점: 각 규칙에서 예상 결과와 판정 조건을 만들 수 있는가?
  • 운영·보안 관점: 권한, 개인정보, 장애 시 동작이 누락되지 않았는가?

6.2 변경 처리

요구가 바뀌면 화면 그림만 고치지 않는다. 관련 요구사항 ID, 화면 흐름, 항목 규칙, 메시지, 테스트 케이스의 영향을 확인한다. 변경 전후 차이, 변경 사유, 검토자, 승인일, 버전을 남긴다. 최신본의 식별이 어려우면 서로 다른 부서가 다른 화면을 구현할 수 있다.

07

7. 시험에서 자주 나오는 함정

  1. 스토리보드를 정적 디자인 시안만으로 이해한다.
  2. 와이어프레임·목업·프로토타입의 목적을 뒤바꾼다.
  3. 정상 화면만 그리고 오류·빈 결과·권한 부족 상태를 누락한다.
  4. 버튼 동작을 “처리한다”처럼 관찰 불가능하게 기술한다.
  5. 화면 ID는 있지만 요구사항 ID와 연결하지 않는다.
  6. 완전성과 일관성을 혼동한다. 완전성은 누락 여부, 일관성은 상호 모순 여부다.
  7. 실현 가능성과 시험 가능성을 혼동한다. 구현 가능해도 판정 기준이 모호하면 시험 가능하지 않다.
  8. UI 요구사항 확인을 한 번의 승인으로 끝내고 변경 이력을 무시한다.
08

8. 확인 문제

문제 1

와이어프레임과 스토리보드의 가장 중요한 차이를 설명하라.

문제 2

“검색 결과를 신속하게 제공한다”는 요구가 부족한 판단 기준 두 가지와 보완 방향을 쓰라.

문제 3

스토리보드에서 요구사항 ID와 화면 ID를 연결하는 주된 목적은 무엇인가?

문제 4

다음 중 시험 가능성이 가장 높은 명세는 무엇인가?

  1. 오류를 친절하게 표시한다.
  2. 화면은 세련되게 구성한다.
  3. 필수값이 없으면 저장하지 않고 누락 필드 가까이에 오류 이유를 표시한다.
  4. 사용자가 불편하지 않아야 한다.
09

정답과 해설

  1. 정답: 와이어프레임은 주로 화면의 구조와 배치를 표현하고, 스토리보드는 화면 구성에 더해 항목 설명, 동작 조건, 이동, 예외와 메시지를 통합 명세한다.
  2. 정답: 명확성과 시험 가능성이 부족하다. 측정할 응답 시간, 데이터 규모, 측정 조건과 허용 기준을 합의하여 관찰 가능한 요구로 바꾼다.
  3. 정답: 요구 변경 시 영향을 받는 화면·개발·테스트를 추적하고, 모든 요구가 화면에 반영됐는지 양방향으로 검증하기 위해서다.
  4. 정답: 3번. 조건, 시스템 행동, 사용자에게 보이는 결과가 명시되어 테스트 케이스를 만들 수 있다.
10

9. 최종 요약

  • 스토리보드는 화면 배치뿐 아니라 항목, 동작, 이동, 데이터, 메시지, 예외를 함께 기록하는 UI 명세다.
  • 작성은 요구 수집 → 화면·상태 식별 → 흐름 연결 → 상세 명세 → 요구 대응 → 검토·기준선의 순서로 진행한다.
  • UI 요구사항 확인의 적용 절차와 판단 기준에서는 완전성, 일관성, 명확성, 정확성, 실현 가능성, 시험 가능성, 추적 가능성을 점검한다.
  • 화면 ID와 요구사항 ID를 연결하고 정상·실패·빈 상태를 모두 명세해야 변경과 테스트에 강해진다.
  • 특정 도구나 조직 양식보다 “사용자 조작에 시스템이 어떤 관찰 가능한 결과를 내는가”를 분명히 쓰는 것이 핵심이다.
