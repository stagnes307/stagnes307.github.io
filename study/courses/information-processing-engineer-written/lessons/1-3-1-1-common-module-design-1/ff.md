# 1-3-1-1. 설계 모델링 · 소프트웨어 아키텍처

> **공식 범위**: 2026년 정보처리기사 출제기준의 `소프트웨어설계 > 애플리케이션 설계 > 공통 모듈 설계` 가운데 **설계 모델링**, **소프트웨어 아키텍처**를 다룬다. 다음 레슨의 재사용·모듈화나 결합도·응집도 세부 분류보다, 요구를 설계 모델로 전환하고 시스템의 상위 구조와 품질 결정을 표현하는 데 집중한다.

설계는 “코딩 전에 그림을 그리는 단계”가 아니다. 무엇을 어떤 책임으로 나누고, 서로 어떻게 통신하며, 데이터와 제어가 어떻게 흐르고, 어느 환경에 배치할지를 결정하는 활동이다. **설계 모델링**은 그 결정을 여러 관점의 모델로 표현하는 방법이고, **소프트웨어 아키텍처**는 시스템의 주요 요소·관계·원칙을 결정하는 상위 구조다.

---

## 1. 토픽 ① 설계 모델링

### 1.1 설계 모델링의 목적

분석 모델이 “무엇을 해야 하는가”를 설명한다면 설계 모델은 “그 요구를 어떤 구조와 협력으로 실현할 것인가”를 구체화한다. 두 단계는 완전히 단절되지 않으며 요구사항과 설계 요소가 추적 가능해야 한다.

설계 모델링의 주요 목적은 다음과 같다.

1. 복잡한 시스템을 이해 가능한 관점으로 나눈다.
2. 구현 전에 구조적 충돌과 누락을 발견한다.
3. 개발자·테스터·운영자 사이의 공통 의사소통 수단을 제공한다.
4. 요구사항이 어느 설계 요소에서 실현되는지 추적한다.
5. 성능, 보안, 변경 용이성 같은 품질 요구를 구조에 반영한다.

모델은 실제 시스템 전체를 복제하지 않는다. 특정 판단에 필요한 특성을 남기고 나머지를 생략하는 **추상화**다. 따라서 목적이 다른 모델은 서로 다른 정보를 보여 줄 수 있다.

### 1.2 설계 모델의 주요 관점

| 관점 | 핵심 질문 | 표현 대상 예 |
|---|---|---|
| 구조 관점 | 시스템은 어떤 요소로 구성되는가? | 패키지, 컴포넌트, 클래스, 계층 |
| 동작 관점 | 상태와 처리 순서는 어떻게 변하는가? | 상태 전이, 활동 흐름 |
| 상호작용 관점 | 요소가 어떤 순서로 메시지를 주고받는가? | 요청·응답, 예외 흐름 |
| 데이터 관점 | 정보의 구조·관계·생명주기는 무엇인가? | 데이터 개체, 저장·변환 흐름 |
| 인터페이스 관점 | 외부와 내부의 계약은 무엇인가? | 입력, 출력, 오류, 사전·사후 조건 |
| 배치 관점 | 실행 요소는 어느 환경에 놓이는가? | 노드, 프로세스, 네트워크 연결 |

한 모델로 모든 이해관계자의 질문을 해결하려 하면 지나치게 복잡해진다. 구조를 검토할 때는 구조 관점, 장애와 동시성을 검토할 때는 동작·배치 관점을 함께 본다.

### 1.3 정적 모델과 동적 모델

- **정적 모델**은 시간 변화보다 요소의 구성과 관계를 표현한다. 클래스·컴포넌트·패키지·데이터 구조가 여기에 가깝다.
- **동적 모델**은 시간에 따른 상태 변화, 처리 순서, 메시지 교환을 표현한다. 상태·활동·상호작용 모델이 여기에 가깝다.

정적 모델이 올바르다고 동적 동작까지 자동으로 올바른 것은 아니다. 예를 들어 주문 컴포넌트와 결제 컴포넌트의 관계가 그려져 있어도 결제 성공 뒤 주문 확정 순서, 시간 초과, 중복 요청 처리는 동적 모델에서 확인해야 한다.

## 2. 설계 모델링 절차

### 단계 1: 설계 입력과 제약을 확인한다

기능 요구, 품질 요구, 데이터, 외부 시스템, 기술·운영 제약, 기존 자산을 정리한다. “응답이 빨라야 한다” 같은 품질 요구는 측정 가능한 시나리오로 구체화한다.

### 단계 2: 경계와 책임을 식별한다

시스템의 범위, 외부 행위자, 주요 책임을 정한다. 한 요소가 너무 많은 업무를 맡거나 책임 주체가 없는 요구가 없는지 확인한다.

### 단계 3: 구조를 분해한다

주요 서브시스템, 계층, 컴포넌트, 데이터 저장소를 식별한다. 분해 기준은 업무 능력, 변경 이유, 보안 경계, 실행 특성 등 목적에 맞게 선택한다.

### 단계 4: 인터페이스와 협력을 정의한다

요소 간 요청, 응답, 데이터, 오류, 순서와 의존 관계를 정의한다. 인터페이스는 함수 이름 목록이 아니라 입력·출력·조건·실패 의미를 포함하는 계약이다.

### 단계 5: 동작·데이터·배치를 모델링한다

핵심 시나리오와 예외 흐름을 모델링하고 데이터 소유와 이동을 확인한다. 성능·보안·가용성에 영향을 주는 배치와 통신 경계를 표현한다.

### 단계 6: 일관성과 추적성을 검증한다

구조 모델의 요소가 상호작용 모델에 존재하는지, 인터페이스 이름과 데이터 형식이 일치하는지, 모든 중요 요구가 설계 결정과 연결되는지 확인한다.

### 단계 7: 반복적으로 정제한다

검토, 시뮬레이션, 위험 실험 결과를 반영한다. 모델이 너무 추상적이면 구현 판단을 돕지 못하고, 지나치게 상세하면 변경 비용이 커지므로 목적에 맞는 수준을 유지한다.

## 3. 좋은 설계 모델의 판단 기준

### 완전성

중요 기능, 예외, 외부 연계, 데이터, 품질 요구가 필요한 관점에 표현되어 있는가?

### 일관성

서로 다른 모델에서 요소 이름, 책임, 인터페이스, 메시지 순서가 모순되지 않는가?

### 정확성

요구사항과 업무 규칙을 올바르게 반영하며 잘못된 가정을 포함하지 않는가?

### 추적 가능성

요구사항에서 설계 요소로, 설계 요소에서 구현·테스트로 연결할 수 있는가?

### 이해 가능성

기호와 상세 수준이 독자에게 적절하며 범례, 이름, 설명이 명확한가?

### 실현 가능성

선택한 구조가 기술, 비용, 일정, 운영 환경 안에서 구현 가능한가?

모델의 그림이 정교해도 인터페이스 오류 조건이 빠지거나 요구와 연결되지 않으면 좋은 모델이 아니다.

## 4. 토픽 ② 소프트웨어 아키텍처

### 4.1 정의와 범위

**소프트웨어 아키텍처**는 시스템의 주요 구성 요소, 요소 사이의 관계, 그리고 구조의 설계·진화를 지배하는 원칙과 결정이다. 단순히 디렉터리 구조나 서버 배치만을 뜻하지 않는다.

아키텍처 결정의 예:

- 시스템을 어떤 주요 책임과 계층으로 나눌 것인가?
- 데이터의 권위 있는 소유자는 누구인가?
- 요소는 동기 호출, 비동기 메시지, 공유 저장소 중 무엇으로 통신하는가?
- 장애를 어디에서 격리하고 어떻게 복구하는가?
- 보안 경계와 신뢰 경계는 어디인가?
- 예상 변경이 어느 범위에만 영향을 주도록 할 것인가?

이런 결정은 여러 부분에 광범위한 영향을 주고 나중에 바꾸는 비용이 크기 때문에 일찍 검토한다.

### 4.2 아키텍처와 상세 설계 비교

| 구분 | 아키텍처 | 상세 설계 |
|---|---|---|
| 범위 | 시스템 전체의 주요 구조 | 컴포넌트 내부의 구체 구조와 알고리즘 |
| 관심 | 책임, 관계, 품질 속성, 배치, 원칙 | 클래스, 함수, 자료구조, 세부 처리 |
| 영향 | 광범위하고 변경 비용이 큼 | 주로 국소적 영향 |
| 이해관계자 | 개발·운영·보안·사업 등 다수 | 구현 담당자 중심 |

경계는 절대적이지 않다. 중요한 것은 결정의 영향 범위와 품질 위험이다.

## 5. 아키텍처 뷰와 4+1 관점

하나의 다이어그램으로 모든 관심사를 표현하기 어렵기 때문에 여러 **뷰**를 사용한다. 널리 알려진 4+1 관점은 다음과 같다.

1. **논리 뷰**: 사용자에게 제공할 기능과 주요 추상화·관계를 보여 준다.
2. **프로세스 뷰**: 실행 중 프로세스, 동시성, 통신, 성능과 가용성을 다룬다.
3. **개발 뷰**: 소스 코드·모듈·패키지의 조직과 개발 책임을 보여 준다.
4. **물리 뷰**: 실행 요소가 배치되는 하드웨어·노드·네트워크를 다룬다.
5. **유스케이스 뷰(+1)**: 핵심 시나리오로 다른 뷰의 구조와 협력을 검증한다.

시험 함정은 `+1`을 단순 부록으로 보는 것이다. 핵심 유스케이스는 여러 뷰가 실제 요구를 함께 만족하는지 연결하고 검증한다.

## 6. 대표 아키텍처 스타일

### 계층형

책임을 표현·업무·데이터 등의 계층으로 나누고 정해진 방향으로 의존하게 한다. 관심사 분리와 변경 격리에 유리하지만 계층을 우회하거나 불필요한 전달이 많으면 복잡도와 지연이 증가한다.

### 클라이언트-서버

서비스를 요청하는 클라이언트와 제공하는 서버로 역할을 나눈다. 중앙 관리가 쉬울 수 있지만 서버 병목·장애, 네트워크 의존을 고려해야 한다.

### 저장소 중심

공유 데이터 저장소를 중심으로 여러 요소가 데이터를 읽고 쓴다. 데이터 통합에 유리하지만 저장소 구조와 가용성에 대한 의존이 커질 수 있다.

### 파이프-필터

처리 단계를 필터로 나누고 파이프로 데이터를 전달한다. 단계 조합과 재사용에 유리하지만 상태가 많은 상호작용이나 오류 전파는 별도 설계가 필요하다.

### 이벤트 기반

발행자가 이벤트를 만들고 구독자가 반응한다. 느슨한 시간적 연결과 확장에 유리하지만 처리 순서, 중복, 추적, 최종 일관성을 고려해야 한다.

### 모델-뷰-컨트롤러

데이터·업무 상태, 사용자 표현, 입력 제어의 관심을 나눈다. UI 변경과 업무 로직 분리에 유리하지만 역할 경계가 무너지면 복잡도가 커진다. 이는 구조적 스타일의 설명이며 뒤 레슨의 GoF 디자인패턴 분류와 같은 층위로 단정하지 않는다.

하나의 시스템은 여러 스타일을 조합할 수 있다. “최고의 스타일”이 있는 것이 아니라 품질 요구와 제약에 따른 적합성과 대가가 있다.

## 7. 품질 속성과 트레이드오프

아키텍처는 기능 목록뿐 아니라 품질 속성을 만족해야 한다.

| 품질 속성 | 시나리오 질문 | 구조적 고려 예 |
|---|---|---|
| 성능 | 어떤 부하에서 어느 응답 기준을 만족해야 하는가? | 캐시, 병렬 처리, 통신 횟수 |
| 가용성 | 장애 후 어느 시간 안에 복구해야 하는가? | 중복, 장애 감지, 격리 |
| 보안 | 누가 어떤 자원에 접근하며 침해를 어떻게 제한하는가? | 인증, 권한, 신뢰 경계, 감사 |
| 변경 용이성 | 어떤 변경을 어느 범위에서 수용해야 하는가? | 책임 분리, 안정된 인터페이스 |
| 시험 용이성 | 요소를 독립적으로 관찰·대체할 수 있는가? | 의존 분리, 관찰 지점 |
| 확장성 | 부하 증가 시 어떤 자원을 확장하는가? | 상태 관리, 분산, 분할 |

품질 속성은 충돌할 수 있다. 암호화와 검증을 강화하면 보안은 높아지지만 처리 비용이 늘 수 있고, 강한 데이터 일관성은 일부 분산 상황에서 가용성이나 지연과 대가 관계가 생길 수 있다. 따라서 “모두 최대화”가 아니라 우선순위와 측정 조건을 합의한다.

## 8. 적용 예시: 주문 처리 시스템

### 요구

- 주문 접수, 결제 승인, 재고 예약, 알림을 처리한다.
- 결제 중복과 재고 초과 예약을 방지한다.
- 알림 장애가 주문 확정을 막지 않아야 한다.
- 결제 사업자 변경의 영향을 제한해야 한다.

### 상위 구조

```text
주문 인터페이스 → 주문 서비스 → 결제 인터페이스
                         ├→ 재고 인터페이스
                         └→ 주문 이벤트 → 알림 처리
```

### 설계 모델로 확인할 것

- 구조 모델: 주문·결제·재고·알림의 책임과 관계
- 상호작용 모델: 정상 승인, 결제 거절, 시간 초과, 재시도 순서
- 데이터 모델: 주문 상태와 결제 식별자의 소유
- 배치 모델: 외부 결제 경계와 장애 격리 지점

### 아키텍처 판단

알림을 주문 확정의 동기 호출로 묶으면 단순하지만 알림 장애가 주문을 실패시킬 수 있다. 주문 확정 이벤트에 비동기로 반응하게 하면 장애 격리는 쉬워지지만 중복 이벤트와 지연 처리에 대비해야 한다. 정답은 요구 우선순위와 실패 의미에 따라 결정한다.

---

## 9. 시험 함정

1. 분석 모델과 설계 모델을 완전히 같은 것으로 본다.
2. 설계 모델을 코드 자동 생성용 그림으로만 이해한다.
3. 정적 구조가 맞으면 동적 순서와 예외도 맞다고 가정한다.
4. 소프트웨어 아키텍처를 서버 배치나 폴더 구조 하나로 축소한다.
5. 4+1 뷰의 논리·프로세스·개발·물리·유스케이스 관심사를 뒤바꾼다.
6. 아키텍처 스타일은 하나만 선택해야 한다고 생각한다.
7. 품질 요구를 “빠르게, 안전하게”처럼 측정 조건 없이 둔다.
8. 장점만 외우고 병목·복잡성·일관성 같은 대가를 무시한다.

## 10. 확인 문제

### 문제 1

정적 설계 모델과 동적 설계 모델의 차이를 주문 처리 예로 설명하라.

### 문제 2

4+1 뷰에서 동시성·프로세스 통신·성능을 주로 다루는 뷰와 실행 노드 배치를 다루는 뷰는 각각 무엇인가?

### 문제 3

이벤트 기반 아키텍처의 장점 한 가지와 주의점 두 가지를 쓰라.

### 문제 4

“모든 요청은 매우 빠르게 처리한다”가 좋은 아키텍처 품질 요구가 아닌 이유는 무엇인가?

## 정답과 해설

1. **정답**: 정적 모델은 주문·결제·재고 요소와 관계를 보여 주고, 동적 모델은 주문 요청 뒤 결제 승인·재고 예약·실패 보상 메시지가 어떤 순서로 일어나는지 보여 준다.
2. **정답**: 프로세스 뷰와 물리 뷰다. 프로세스 뷰는 실행 중 동시성과 통신, 물리 뷰는 노드와 배치를 중심으로 한다.
3. **정답 예**: 장점은 발행자와 구독자의 시간적 결합을 낮추고 확장하기 쉽다는 점이다. 주의점은 처리 순서, 중복 이벤트, 추적 어려움, 최종 일관성 중 두 가지다.
4. **정답**: 부하, 요청 종류, 측정 구간, 허용 응답 시간과 비율이 없어 설계 판단과 검증을 할 수 없기 때문이다.

## 11. 최종 요약

- **설계 모델링**은 요구를 구조·동작·상호작용·데이터·인터페이스·배치 관점의 구현 가능한 청사진으로 전환한다.
- 설계 입력 확인 → 책임·경계 식별 → 구조 분해 → 인터페이스·협력 정의 → 동작·배치 모델링 → 일관성·추적성 검증의 순서로 정제한다.
- **소프트웨어 아키텍처**는 주요 요소, 관계, 설계·진화 원칙과 광범위한 품질 결정을 다룬다.
- 4+1 뷰와 여러 아키텍처 스타일을 목적에 맞게 사용하며 하나의 시스템에서 조합할 수 있다.
- 성능·가용성·보안·변경 용이성 등은 측정 가능한 시나리오와 트레이드오프로 검토해야 한다.
