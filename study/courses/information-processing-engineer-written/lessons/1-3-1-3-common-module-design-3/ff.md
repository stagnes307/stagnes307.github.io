# 1-3-1-3. 결합도 · 응집도

> **공식 범위**: 2026년 정보처리기사 출제기준의 `소프트웨어설계 > 애플리케이션 설계 > 공통 모듈 설계` 가운데 **결합도**, **응집도**를 다룬다. 두 개념의 정의, 강도 순서, 코드·설계 사례 판별과 개선 원칙에 집중한다.

모듈을 나누었다고 독립성이 자동으로 생기지는 않는다. 모듈 사이 의존이 과도하면 작은 변경도 전체에 퍼지고, 한 모듈 내부의 기능이 서로 무관하면 이해와 재사용이 어렵다. 이때 외부 관계를 보는 척도가 결합도, 내부 관련성을 보는 척도가 응집도다.

핵심 목표는 한 문장으로 정리된다.

> **결합도는 낮게, 응집도는 높게 설계한다.**

---

## 1. 두 척도의 방향

### 결합도

**결합도**는 모듈 사이의 상호 의존 정도다. 한 모듈이 다른 모듈의 내부 구현, 전역 상태, 제어 흐름에 많이 의존할수록 결합도가 높다. 결합도가 높으면 변경 파급, 독립 시험의 어려움, 재사용 제약이 커진다.

### 응집도

**응집도**는 한 모듈 내부의 요소들이 하나의 목적을 위해 관련되어 있는 정도다. 모든 처리와 데이터가 명확한 하나의 기능에 기여할수록 응집도가 높다. 응집도가 낮으면 모듈의 존재 이유를 설명하기 어렵고 여러 변경 이유가 섞인다.

### 비교

| 구분 | 결합도 | 응집도 |
|---|---|---|
| 관찰 범위 | 모듈과 모듈 사이 | 모듈 내부 |
| 바람직한 방향 | 낮을수록 좋음 | 높을수록 좋음 |
| 핵심 질문 | 다른 모듈을 얼마나 많이 아는가? | 내부 요소가 같은 목적에 기여하는가? |
| 문제 영향 | 변경 전파, 대체·시험 어려움 | 책임 혼합, 이해·재사용 어려움 |

결합도와 응집도는 연관되지만 완전한 반대말은 아니다. 외부 의존이 적어도 내부가 무관한 기능의 모음이면 응집도는 낮을 수 있다.

---

## 2. 토픽 ① 결합도 유형

결합도는 일반적으로 약한 것부터 강한 것까지 다음 순서로 학습한다.

> **자료 → 스탬프 → 제어 → 외부 → 공통 → 내용**

뒤로 갈수록 의존이 강하고 바람직하지 않다.

### 2.1 자료 결합도(Data Coupling)

모듈이 필요한 단순 데이터 값만 매개변수로 주고받는다. 상대 모듈의 내부 구조를 알 필요가 없어 가장 약한 결합으로 본다.

```text
calculateTax(amount, rate)
```

호출자는 금액과 세율이라는 필요한 값만 전달한다. 단, 매개변수가 지나치게 많으면 인터페이스가 복잡해질 수 있으므로 값만 전달한다고 무조건 완벽한 설계는 아니다.

### 2.2 스탬프 결합도(Stamp Coupling)

레코드, 구조체, 객체 등 복합 자료구조를 전달하지만 수신 모듈은 그중 일부만 사용한다.

```text
printAddress(customerRecord)
```

주소만 필요하지만 고객 전체 레코드를 전달하면 고객 구조의 불필요한 변경에도 영향을 받을 수 있다. `address`에 필요한 데이터만 전달하면 자료 결합도로 낮출 수 있다.

### 2.3 제어 결합도(Control Coupling)

한 모듈이 플래그나 제어값을 전달하여 다른 모듈의 내부 처리 경로를 지시한다.

```text
renderReport(data, mode="SUMMARY")
```

`mode` 값이 수신 모듈 안에서 어느 로직을 실행할지 통제한다. 단순 업무 데이터와 제어 신호를 구분해야 한다. 모든 불리언 인수가 제어 결합도인 것은 아니며, 값이 업무 의미인지 상대의 내부 흐름 선택인지 문맥을 본다.

### 2.4 외부 결합도(External Coupling)

여러 모듈이 외부에서 정한 데이터 형식, 통신 프로토콜, 장치 인터페이스 등에 함께 의존한다.

```text
여러 모듈이 특정 장치의 고정 명령 형식과 파일 레코드 규격에 직접 의존
```

외부 표준 자체가 나쁘다는 뜻은 아니다. 외부 형식 변경이 여러 내부 모듈로 전파되는 의존을 가리킨다. 변환 경계를 두어 외부 의존을 한 곳에 모을 수 있다.

### 2.5 공통 결합도(Common Coupling)

여러 모듈이 전역 변수나 공통 데이터 영역을 공유한다.

```text
global currentUser, taxRate, errorCode
```

어느 모듈이 언제 값을 바꿨는지 추적하기 어렵고 실행 순서에 따라 결과가 달라질 수 있다. 읽기 전용 상수와 변경 가능한 전역 상태는 위험이 다르므로 문맥을 구분한다.

### 2.6 내용 결합도(Content Coupling)

한 모듈이 다른 모듈의 내부 데이터나 코드에 직접 접근하거나 내부 실행 위치로 분기하는 등 구현 내용을 침범한다. 가장 강하고 바람직하지 않은 결합이다.

```text
모듈 A가 모듈 B의 내부 지역 자료를 직접 변경하거나
B의 정상 인터페이스를 거치지 않고 내부 로직으로 진입
```

내용 결합도에서는 상대의 캡슐화가 사실상 깨지므로 작은 내부 변경도 호출 모듈을 망가뜨릴 수 있다.

## 3. 결합도 판별 방법

사례를 읽을 때 “데이터를 주고받는다”는 표면만 보지 말고 의존 대상을 찾는다.

1. 단순한 필요한 값만 전달하는가? → 자료
2. 복합 구조 전체를 넘기고 일부만 쓰는가? → 스탬프
3. 상대 모듈의 처리 경로를 지시하는가? → 제어
4. 공통 외부 규격·장치·프로토콜에 의존하는가? → 외부
5. 변경 가능한 전역 영역을 함께 쓰는가? → 공통
6. 상대 내부 구현을 직접 읽거나 바꾸는가? → 내용

한 사례에 여러 의존이 섞이면 가장 직접적으로 묘사한 관계를 판별한다. 예를 들어 전역 구조체를 공유하면서 내부 필드를 직접 수정한다면 공통 공유와 내용 침범의 특징이 모두 보일 수 있다. 문제의 강조 문구를 확인한다.

---

## 4. 결합도를 낮추는 방법

- 필요한 최소 데이터만 명시적 매개변수로 전달한다.
- 큰 레코드 대신 목적에 맞는 작은 입력·출력 모델을 만든다.
- 제어 플래그로 내부 분기를 지시하기보다 목적별 명확한 연산을 제공한다.
- 외부 형식은 변환 모듈이나 어댑터 경계에서 내부 형식으로 바꾼다.
- 변경 가능한 전역 상태를 제거하고 소유자와 변경 경로를 명확히 한다.
- 다른 모듈의 내부 데이터에 접근하지 않고 공개 인터페이스를 사용한다.
- 인터페이스의 사전 조건, 사후 조건, 오류 의미를 문서화한다.

결합도를 낮추려고 모든 호출 사이에 의미 없는 전달 계층을 추가하면 복잡성만 증가할 수 있다. 목표는 의존을 숨기는 것이 아니라 안정되고 필요한 의존만 남기는 것이다.

---

## 5. 토픽 ② 응집도 유형

응집도는 일반적으로 약한 것부터 강한 것까지 다음 순서로 학습한다.

> **우연적 → 논리적 → 시간적 → 절차적 → 통신적 → 순차적 → 기능적**

뒤로 갈수록 내부 관련성이 높고 바람직하다.

### 5.1 우연적 응집도(Coincidental Cohesion)

서로 관련 없는 기능을 우연히 한 모듈에 모은다.

```text
Utility 모듈 안에 세금 계산, 이미지 크기 변경, 로그 삭제가 함께 존재
```

공통 목적과 변경 이유가 없어 가장 낮은 응집도다. `기타`, `도우미`라는 이름 아래 무관한 기능이 계속 쌓이는 경우가 흔하다.

### 5.2 논리적 응집도(Logical Cohesion)

논리적으로 비슷한 범주의 기능을 한 모듈에 묶고 제어값으로 하나를 선택한다.

```text
InputHandler(type)이 키보드·파일·네트워크 입력 중 하나를 처리
```

모두 입력이라는 범주로 묶였지만 실제 처리와 변경 이유는 다르다. 제어 플래그와 함께 나타날 수 있으나, 응집도는 모듈 내부 관계를 판정한다.

### 5.3 시간적 응집도(Temporal Cohesion)

같은 시점에 수행된다는 이유로 기능을 묶는다.

```text
initialize()가 설정 읽기, 로그 열기, 임시파일 정리를 수행
```

시작 시 실행된다는 시간 관계는 있지만 기능 자체의 목적은 다르다.

### 5.4 절차적 응집도(Procedural Cohesion)

특정 절차의 순서에 따라 수행된다는 이유로 기능을 묶는다. 요소가 같은 데이터를 다루지 않아도 순서상 함께 있다.

```text
사용자 확인 → 파일 열기 → 화면 메시지 표시가 정해진 순서로 실행
```

시간적 응집도는 같은 시점, 절차적 응집도는 정해진 제어 순서가 핵심이다.

### 5.5 통신적 응집도(Communicational Cohesion)

같은 입력 데이터나 출력 데이터를 사용한다는 이유로 기능을 묶는다.

```text
고객 레코드를 읽어 주소 라벨을 출력하고 고객 통계를 기록
```

동일 데이터를 다루므로 절차적 응집도보다 관련성이 높지만 기능 목적은 여러 개일 수 있다. 통신적은 통신 프로토콜이 아니라 **공통 데이터**가 핵심이다.

### 5.6 순차적 응집도(Sequential Cohesion)

한 요소의 출력이 다음 요소의 입력이 되는 연속 처리로 묶인다.

```text
원문 읽기 → 토큰 분리 → 정규화 → 색인 생성
```

단순히 순서대로 실행하는 절차적 응집도보다 데이터 흐름의 연결이 강하다.

### 5.7 기능적 응집도(Functional Cohesion)

모든 내부 요소가 하나의 명확한 기능 수행에 기여한다. 가장 높은 응집도다.

```text
calculateShippingFee가 배송비 계산에 필요한 검증·구간 판정·금액 계산만 수행
```

모듈 이름을 하나의 동사구로 명확히 설명할 수 있고 불필요한 기능이 없다.

## 6. 응집도 판별 비교

| 유형 | 묶인 이유 | 판별 단어 |
|---|---|---|
| 우연적 | 특별한 관계 없음 | 무관한 기능의 모음 |
| 논리적 | 비슷한 범주 | 플래그로 기능 선택 |
| 시간적 | 같은 시점 | 초기화, 종료 시 수행 |
| 절차적 | 정해진 순서 | 제어 흐름 순서 |
| 통신적 | 같은 데이터 | 동일 입력·출력 사용 |
| 순차적 | 출력이 다음 입력 | 데이터가 단계별 전달 |
| 기능적 | 하나의 기능 | 모든 요소가 단일 목적 기여 |

`통신적`과 `순차적`을 자주 혼동한다. 같은 데이터를 각자 사용하면 통신적, 앞 처리의 결과가 다음 처리의 입력으로 이어지면 순차적이다.

---

## 7. 응집도를 높이는 방법

- 모듈의 책임을 한 문장으로 작성하고 맞지 않는 기능을 분리한다.
- 플래그로 전혀 다른 동작을 선택하는 큰 모듈을 목적별 연산으로 나눈다.
- 초기화·종료라는 시점만 같은 기능은 실제 소유 책임으로 이동한다.
- 공통 데이터 전체보다 각 기능에 필요한 책임과 처리를 함께 둔다.
- 연속 변환이 하나의 분명한 목적을 이룬다면 파이프라인의 경계를 명확히 한다.
- 이름과 실제 기능이 일치하도록 하고 `Manager`, `Utility` 같은 넓은 이름을 검토한다.

기능을 분리한 뒤 생기는 모듈 간 인터페이스 비용도 함께 본다. 응집도를 높이려는 분해가 과도한 원격 호출과 데이터 복사를 만들면 전체 품질은 나빠질 수 있다.

## 8. 결합도와 응집도를 함께 보는 사례

### 나쁜 설계

```text
GlobalContext에 사용자, 주문, 결제, 화면 상태를 모두 저장한다.
OrderUtility(mode, GlobalContext)는 mode에 따라
주문 계산, 결제 호출, 화면 메시지, 로그 정리를 수행한다.
```

- 여러 모듈이 `GlobalContext`를 공유하므로 공통 결합의 위험이 있다.
- `mode`가 내부 처리 경로를 지시하면 제어 결합의 특징이 있다.
- 무관한 기능이 한 모듈에 모여 논리적 또는 우연적 응집의 문제가 있다.

### 개선 방향

```text
OrderCalculator.calculate(orderItems)
PaymentPort.authorize(paymentRequest)
OrderMessageFormatter.format(orderResult)
```

각 모듈은 한 책임에 집중하고 필요한 데이터만 계약으로 주고받는다. 전역 상태를 소유자 내부로 옮기고 외부 결제 형식은 경계에서 변환한다.

### 검토 질문

- 한 모듈의 내부 필드가 바뀌면 몇 개 모듈이 수정되는가?
- 테스트할 때 다른 모듈이나 전역 상태를 반드시 준비해야 하는가?
- 모듈 이름을 하나의 기능으로 설명할 수 있는가?
- 내부 처리들이 같은 데이터만 쓰는가, 서로 출력·입력으로 이어지는가, 하나의 목적에 기여하는가?

## 9. 암기와 이해를 함께 하는 방법

### 결합도 약 → 강

`자료-스탬프-제어-외부-공통-내용`

- 필요한 값
- 구조 일부 사용
- 흐름 지시
- 외부 규격 공유
- 전역 영역 공유
- 내부 침범

### 응집도 약 → 강

`우연-논리-시간-절차-통신-순차-기능`

- 관계 없음
- 범주만 같음
- 시점이 같음
- 순서만 같음
- 데이터가 같음
- 출력이 다음 입력
- 하나의 목적

순서만 외우지 말고 각 단계에서 관계가 무엇 때문에 한 단계 강해지는지 연결한다.

---

## 10. 시험 함정

1. 결합도와 응집도 모두 낮을수록 좋다고 생각한다.
2. 결합도의 약→강 순서와 응집도의 약→강 순서를 반대로 외운다.
3. 스탬프 결합을 단순 값 전달과 혼동한다.
4. 모든 플래그를 제어 결합으로 판단하고 업무 데이터인지 보지 않는다.
5. 외부 결합을 외부 모듈 호출 전체와 같은 뜻으로 본다.
6. 공통 결합의 전역 공유와 내용 결합의 내부 침범을 혼동한다.
7. 시간적 응집의 같은 시점과 절차적 응집의 같은 순서를 혼동한다.
8. 통신적의 같은 데이터와 순차적의 출력→입력 관계를 혼동한다.
9. 모듈을 작게 나누기만 하면 결합도가 자동으로 낮아진다고 생각한다.

## 11. 확인 문제

### 문제 1

결합도를 약한 것부터 강한 것까지 순서대로 쓰라.

### 문제 2

고객 전체 레코드를 전달하지만 수신 모듈은 우편번호만 사용한다. 어떤 결합도이며 어떻게 낮출 수 있는가?

### 문제 3

같은 데이터로 보고서를 출력하고 통계 로그도 기록하는 모듈과, 한 처리 결과가 다음 처리 입력으로 이어지는 모듈의 응집도는 각각 무엇인가?

### 문제 4

`startup()`이 로그 열기, 캐시 초기화, 임시파일 정리를 수행한다. 가장 잘 맞는 응집도는 무엇이며 이유는 무엇인가?

## 정답과 해설

1. **정답**: 자료 → 스탬프 → 제어 → 외부 → 공통 → 내용이다.
2. **정답**: 스탬프 결합도다. 우편번호나 목적에 맞는 작은 값·구조만 전달하면 자료 결합에 가깝게 낮출 수 있다.
3. **정답**: 같은 데이터를 사용하는 것은 통신적 응집도, 출력이 다음 입력이 되는 것은 순차적 응집도다.
4. **정답**: 시간적 응집도다. 서로 다른 기능이 시스템 시작이라는 같은 시점에 실행된다는 이유로 묶여 있다.

## 12. 최종 요약

- **결합도**는 모듈 사이 의존 정도이며 낮을수록 바람직하다: `자료 → 스탬프 → 제어 → 외부 → 공통 → 내용`.
- **응집도**는 모듈 내부 요소의 관련성이며 높을수록 바람직하다: `우연적 → 논리적 → 시간적 → 절차적 → 통신적 → 순차적 → 기능적`.
- 자료 결합은 필요한 값만, 스탬프는 복합 구조 일부, 제어는 처리 경로 지시, 공통은 전역 공유, 내용은 내부 침범이 핵심이다.
- 통신적 응집은 같은 데이터, 순차적 응집은 앞 출력이 다음 입력, 기능적 응집은 하나의 기능 기여가 핵심이다.
- 좋은 모듈은 필요한 안정된 계약만 외부에 보이고 내부는 하나의 명확한 책임에 집중한다.
