# 1-3-2-1. 객체지향 설계

> **공식 범위**: 2026년 정보처리기사 출제기준의 `소프트웨어설계 > 애플리케이션 설계 > 객체지향 설계`에서 제시한 **객체지향(OOP)**, **디자인패턴**을 학습한다. 특정 프로그래밍 언어 문법이나 프레임워크 버전에 의존하지 않고, 객체의 책임·협력과 GoF 패턴의 의도·분류·비교를 중심으로 다룬다.

객체지향 설계는 현실의 명사를 클래스 이름으로 바꾸는 작업이 아니다. 변화하는 요구를 여러 객체의 책임으로 나누고, 객체가 공개 계약을 통해 협력하도록 만드는 활동이다. 디자인패턴은 이 과정에서 반복적으로 나타나는 설계 문제에 대한 검증된 해결 구조와 대가를 공유하는 어휘다.

---

## 1. 토픽 ① 객체지향(OOP)

### 1.1 기본 구성 요소

**객체(Object)**는 식별 가능한 상태와 행동을 가지며 다른 객체와 메시지를 주고받는 실행 단위다.

**클래스(Class)**는 유사한 객체가 가질 속성, 행동, 계약을 정의한 추상적 틀이다. 클래스가 설계 정의라면 객체는 실행 중 생성된 구체적 인스턴스다.

**속성(Attribute)**은 객체의 상태를, **메서드(Method)**는 객체가 제공하는 행동을 나타낸다. 외부는 내부 필드를 임의로 바꾸기보다 메서드가 제공하는 계약으로 상태를 변경해야 불변 조건을 지킬 수 있다.

```text
BankAccount
  상태: accountId, balance, status
  행동: deposit(amount), withdraw(amount), close()
```

`balance`를 누구나 직접 수정할 수 있게 하면 음수 제한, 거래 기록, 권한 같은 규칙을 우회할 수 있다. `withdraw()`가 검증과 상태 변경을 책임지면 객체가 자신의 일관성을 보호한다.

### 1.2 객체와 클래스의 차이

| 구분 | 클래스 | 객체 |
|---|---|---|
| 의미 | 공통 구조와 행동의 정의 | 실행 중 존재하는 구체적 실체 |
| 예 | `BankAccount` 설계 | 계좌 A, 계좌 B 인스턴스 |
| 상태 | 속성 종류를 정의 | 각 인스턴스가 실제 값을 가짐 |
| 생성 | 객체 생성을 위한 틀 | 클래스에 따라 생성됨 |

“클래스는 객체의 인스턴스”가 아니라 일반적으로 **객체가 클래스의 인스턴스**다.

## 2. 객체지향의 핵심 특성

### 2.1 추상화(Abstraction)

대상의 모든 세부를 표현하지 않고 현재 문제에 필요한 본질적 특성만 모델링한다. 지도 앱의 `Vehicle`은 색상보다 위치·속도·이동 가능 여부가 중요할 수 있다. 추상화 수준은 목적에 따라 달라진다.

추상화는 인터페이스나 추상 클래스 같은 구현 수단으로 나타날 수 있지만 특정 문법 자체가 목적은 아니다. 핵심은 불필요한 세부를 숨기고 안정된 개념을 드러내는 것이다.

### 2.2 캡슐화(Encapsulation)

관련 상태와 행동을 한 단위에 묶고 내부 구현을 감추며 필요한 인터페이스만 공개한다. 캡슐화는 단순히 모든 필드를 `private`로 선언하는 것이 아니다. 공개된 setter가 어떤 값이든 허용한다면 객체 규칙을 보호하지 못한다.

효과:

- 내부 구현 변경의 파급을 제한한다.
- 상태의 유효 조건을 객체가 지킨다.
- 사용자는 안정된 계약에 의존한다.
- 오용 가능한 조작을 줄인다.

### 2.3 상속(Inheritance)

기존 클래스의 특성과 행동을 기반으로 새로운 클래스를 정의하는 관계다. 공통 특성 표현과 다형성에 사용할 수 있지만 단순 코드 복사를 줄이기 위해 남용하면 부모 변경이 자식에 강하게 전파된다.

상속이 적절하려면 자식 객체를 부모가 기대되는 곳에 넣어도 계약이 깨지지 않는 **대체 가능성**을 확인한다. `Bird`의 모든 하위 타입에 `fly()`를 강제하면 날지 못하는 새가 부모 계약을 위반할 수 있다.

### 2.4 다형성(Polymorphism)

같은 메시지나 인터페이스에 대해 객체의 실제 타입에 따라 다른 행동을 수행할 수 있는 성질이다.

```text
PaymentMethod.pay(amount)
  ├─ CardPayment.pay(amount)
  ├─ AccountTransfer.pay(amount)
  └─ PointPayment.pay(amount)
```

호출자는 구체 결제 방식의 조건문을 늘어놓지 않고 `pay()` 계약에 의존한다. 새 방식이 추가되어도 호출 흐름의 변경을 줄일 수 있다.

다형성의 구현 방식에는 오버라이딩, 오버로딩, 제네릭 등 여러 형태가 있지만 언어마다 지원 범위와 용어가 다를 수 있다. 설계 핵심은 구체 타입 대신 안정된 추상 계약으로 협력하는 것이다.

## 3. 객체 관계

### 연관(Association)

객체가 다른 객체를 알고 사용하는 일반적 관계다. `Customer`가 여러 `Order`를 조회하는 관계처럼 방향과 다중성을 표현할 수 있다.

### 집합(Aggregation)

전체-부분 관계지만 부분이 전체와 독립적으로 존재할 수 있다. 팀이 해체되어도 구성원 객체가 존재할 수 있는 관계가 예가 될 수 있다.

### 합성(Composition)

더 강한 전체-부분 관계로, 부분의 생명주기가 전체에 종속된다. 주문의 주문항목처럼 주문이 사라지면 해당 구성도 함께 사라지는 모델이 예다. 실제 업무의 소유와 생명주기를 확인해야 하며 명사 관계만 보고 판단하지 않는다.

### 일반화(Generalization)

상위 개념과 하위 개념의 `is-a` 관계다. 하위 타입은 상위 타입의 계약을 지켜야 한다.

### 의존(Dependency)

한 요소가 다른 요소를 일시적으로 사용하여 변경의 영향을 받을 수 있는 관계다. 매개변수, 반환형, 지역 사용 등으로 나타날 수 있다.

시험에서는 집합과 합성을 특히 혼동한다. 핵심은 부분 객체의 독립 존재와 생명주기 소유다.

## 4. 책임 중심 객체 설계 절차

### 단계 1: 사용자 목표와 시나리오를 정리한다

시스템이 제공할 결과와 정상·예외 흐름을 확인한다. 데이터 테이블부터 클래스로 옮기면 행동 없는 데이터 객체만 늘어날 수 있다.

### 단계 2: 책임을 식별한다

알아야 할 것, 해야 할 것, 협력해야 할 것을 찾는다. 책임은 “주문 관리”처럼 너무 넓지 않게 `주문 총액 계산`, `결제 승인 요청`, `주문 상태 전이`처럼 관찰 가능한 행동으로 쓴다.

### 단계 3: 책임을 객체에 할당한다

필요한 정보를 가진 객체가 그 정보를 이용한 행동을 담당하도록 검토한다. 하나의 객체에 모든 조정과 규칙을 몰지 않는다.

### 단계 4: 협력과 인터페이스를 정의한다

객체가 주고받는 메시지, 입력·출력, 사전 조건, 오류를 정한다. 구체 구현보다 역할과 계약을 먼저 생각한다.

### 단계 5: 관계와 생명주기를 검토한다

연관·집합·합성·일반화 중 업무 의미에 맞는 관계를 선택한다. 객체 생성·공유·소멸의 소유자를 확인한다.

### 단계 6: 변경 시나리오로 평가한다

새 결제 방식, 정책 변경, 외부 서비스 교체 같은 예상 변경에서 어느 객체가 수정되는지 본다. 변경이 여러 무관한 객체로 퍼지면 책임이나 추상화 경계를 다시 검토한다.

## 5. 객체지향 설계 원칙

널리 알려진 SOLID 원칙은 객체 설계 판단에 도움을 준다.

- **단일 책임 원칙**: 한 요소가 여러 무관한 변경 이유를 갖지 않도록 한다.
- **개방-폐쇄 원칙**: 기존 안정된 코드를 계속 고치기보다 확장 지점을 통해 새 행동을 추가하도록 한다.
- **리스코프 치환 원칙**: 하위 타입이 상위 타입의 계약을 깨지 않고 대체 가능해야 한다.
- **인터페이스 분리 원칙**: 사용하지 않는 큰 인터페이스에 의존하도록 강요하지 않는다.
- **의존 역전 원칙**: 상위 정책과 하위 구현이 구체 클래스보다 추상 계약에 의존하도록 한다.

원칙은 무조건 적용하는 규칙이 아니다. 작은 변화 가능성까지 모두 추상화하면 이해와 구현 비용이 증가한다. 실제 변경 축과 위험을 근거로 적용한다.

## 6. 토픽 ② 디자인패턴

### 6.1 정의

**디자인패턴**은 반복적으로 등장하는 객체지향 설계 문제의 맥락, 핵심 해결 구조, 참여자 협력과 결과를 이름 붙여 정리한 재사용 가능한 설계 지식이다. 완성된 코드나 복사할 템플릿이 아니라 문제를 풀기 위한 구조적 아이디어다.

패턴을 이해할 때 네 요소를 본다.

1. **이름**: 해결책을 짧게 공유하는 공통 어휘
2. **문제·맥락**: 어떤 상황과 제약에서 필요한가?
3. **해결 구조**: 참여 객체와 책임·협력은 무엇인가?
4. **결과·대가**: 무엇이 유연해지고 어떤 복잡성이 늘어나는가?

패턴 이름만 보고 적용하면 불필요한 클래스와 간접 호출이 늘 수 있다. 먼저 실제 문제가 있는지 확인한다.

## 7. GoF 디자인패턴 분류

GoF 패턴은 목적에 따라 생성, 구조, 행위 패턴으로 나뉜다.

### 7.1 생성 패턴 5개

객체 생성 과정의 결합과 변화를 다룬다.

| 패턴 | 핵심 의도 |
|---|---|
| 추상 팩토리(Abstract Factory) | 관련 객체 제품군을 구체 클래스 지정 없이 생성 |
| 빌더(Builder) | 복잡한 객체의 생성 절차와 표현을 분리 |
| 팩토리 메서드(Factory Method) | 생성할 구체 타입 결정을 하위 클래스나 확장 지점에 위임 |
| 프로토타입(Prototype) | 기존 객체를 복제하여 새 객체 생성 |
| 싱글턴(Singleton) | 인스턴스를 하나로 제한하고 접근 지점 제공 |

싱글턴은 전역 상태와 비슷한 문제를 만들 수 있으므로 “항상 좋은 유일 객체”가 아니다. 생명주기, 동시성, 시험 격리 비용을 고려한다.

### 7.2 구조 패턴 7개

클래스와 객체를 더 큰 구조로 조합하는 방법을 다룬다.

| 패턴 | 핵심 의도 |
|---|---|
| 어댑터(Adapter) | 호환되지 않는 인터페이스를 기대하는 인터페이스로 변환 |
| 브리지(Bridge) | 추상과 구현을 분리하여 독립적으로 변화 |
| 컴포지트(Composite) | 개별 객체와 객체 집합을 같은 방식으로 다루는 트리 구조 |
| 데코레이터(Decorator) | 객체를 감싸 런타임에 책임을 유연하게 추가 |
| 퍼사드(Facade) | 복잡한 서브시스템에 단순한 통합 인터페이스 제공 |
| 플라이웨이트(Flyweight) | 공유 가능한 상태를 재사용해 많은 객체의 메모리 절약 |
| 프록시(Proxy) | 실제 객체의 대리자를 두어 접근 제어·지연 로딩 등 수행 |

### 7.3 행위 패턴 11개

객체의 책임 배분과 메시지 협력 방식을 다룬다.

| 패턴 | 핵심 의도 |
|---|---|
| 책임 연쇄(Chain of Responsibility) | 요청을 처리자 사슬에 전달해 결합을 낮춤 |
| 커맨드(Command) | 요청을 객체로 캡슐화하여 저장·취소·큐잉 가능 |
| 인터프리터(Interpreter) | 간단한 언어 문법과 해석 규칙 표현 |
| 이터레이터(Iterator) | 집합의 내부 표현을 노출하지 않고 순회 |
| 미디에이터(Mediator) | 객체 간 복잡한 상호작용을 중재자에 모음 |
| 메멘토(Memento) | 캡슐화를 깨지 않고 객체 상태를 저장·복원 |
| 옵서버(Observer) | 한 객체 변화 시 구독 객체에 통지 |
| 상태(State) | 내부 상태에 따라 행동이 바뀌는 것을 상태 객체로 분리 |
| 전략(Strategy) | 교환 가능한 알고리즘·정책을 객체로 캡슐화 |
| 템플릿 메서드(Template Method) | 알고리즘 골격은 상위에서, 일부 단계는 하위에서 정의 |
| 비지터(Visitor) | 객체 구조를 바꾸지 않고 새로운 연산 추가 |

분류는 패턴의 주된 의도에 따른다. 실제 구현에서는 생성·구조·행위 관심이 함께 나타날 수 있다.

## 8. 혼동하기 쉬운 패턴 비교

### 어댑터 vs 데코레이터 vs 프록시

- **어댑터**: 인터페이스를 바꿔 호환시킨다.
- **데코레이터**: 같은 인터페이스를 유지하며 책임을 덧붙인다.
- **프록시**: 같은 대상의 대리자로 접근을 제어하거나 지연한다.

### 전략 vs 상태

- **전략**: 호출자나 설정이 교환 가능한 알고리즘을 선택한다.
- **상태**: 객체 내부 상태 전이에 따라 행동이 달라진다.

구조가 비슷해 보여도 의도가 다르다.

### 팩토리 메서드 vs 추상 팩토리

- **팩토리 메서드**는 하나의 제품 생성 결정을 확장 지점에 위임하는 데 초점이 있다.
- **추상 팩토리**는 서로 관련된 여러 제품의 일관된 제품군을 생성하는 데 초점이 있다.

### 전략 vs 템플릿 메서드

- 전략은 조합을 통해 전체 알고리즘을 교체한다.
- 템플릿 메서드는 상속을 통해 고정된 골격의 일부 단계를 바꾼다.

---

## 9. 적용 예시: 알림 발송

### 요구

이메일, 문자, 앱 알림을 지원하고 사용자 정책에 따라 채널을 선택한다. 발송 전 로깅과 재시도 정책도 선택적으로 적용한다.

### 객체지향 설계

```text
NotificationSender.send(message)
  ├─ EmailSender
  ├─ SmsSender
  └─ PushSender
```

호출자는 구체 채널 대신 `NotificationSender` 계약에 의존한다. 채널 선택 정책을 **전략 패턴**으로 분리할 수 있고, 기존 발송 객체를 감싸 로깅 책임을 추가한다면 **데코레이터 패턴**의 의도와 맞을 수 있다. 외부 발송사의 인터페이스가 내부 계약과 다르면 **어댑터 패턴**으로 변환할 수 있다.

### 패턴을 쓰지 않아야 할 때

채널이 하나뿐이고 변경 가능성이 거의 없는데 팩토리, 전략, 데코레이터 계층을 모두 만들면 구조가 요구보다 복잡해진다. 패턴 적용 비용보다 실제 변화 위험이 큰지 판단한다.

## 10. 시험 함정

1. 클래스와 객체의 관계를 반대로 설명한다.
2. 캡슐화를 단순 접근 제한자나 데이터 은닉만으로 축소한다.
3. 상속을 코드 재사용을 위한 최우선 수단으로 본다.
4. 집합과 합성에서 부분의 생명주기 차이를 놓친다.
5. 다형성을 같은 이름의 함수가 있다는 사실만으로 판단한다.
6. 디자인패턴을 완성 코드나 알고리즘 모음으로 이해한다.
7. GoF 생성 5개, 구조 7개, 행위 11개 분류를 뒤바꾼다.
8. 어댑터·데코레이터·프록시가 모두 감싸는 구조라는 이유로 같은 의도로 본다.
9. 전략과 상태의 구조만 보고 선택 주체와 문제 의도를 보지 않는다.
10. 패턴을 많이 사용할수록 객체지향 설계가 우수하다고 생각한다.

## 11. 확인 문제

### 문제 1

추상화와 캡슐화의 차이를 계좌 객체 예로 설명하라.

### 문제 2

전체 객체가 사라질 때 부분 객체의 생명주기도 함께 끝나는 관계는 무엇인가?

### 문제 3

호환되지 않는 외부 인터페이스를 내부 기대 인터페이스로 바꾸는 패턴과 기존 객체에 책임을 동적으로 추가하는 패턴은 각각 무엇인가?

### 문제 4

전략 패턴과 상태 패턴의 핵심 의도 차이는 무엇인가?

### 문제 5

GoF 패턴의 생성·구조·행위 패턴 수와 각 분류의 관심을 쓰라.

## 정답과 해설

1. **정답**: 추상화는 계좌에서 현재 문제에 필요한 잔액·입출금 같은 본질을 선택하는 것이고, 캡슐화는 잔액 상태와 변경 행동을 묶어 내부 수정은 숨기고 `deposit`, `withdraw` 계약만 공개하는 것이다.
2. **정답**: 합성 관계다. 집합은 부분이 전체와 독립적으로 존재할 수 있다.
3. **정답**: 어댑터와 데코레이터다. 프록시는 같은 대상의 대리자로 접근을 통제하는 의도가 중심이다.
4. **정답**: 전략은 교환 가능한 알고리즘·정책을 선택하는 문제이고, 상태는 객체 내부 상태 전이에 따라 행동이 변하는 문제다.
5. **정답**: 생성 5개는 객체 생성, 구조 7개는 클래스·객체 조합, 행위 11개는 책임과 메시지 협력을 다룬다.

## 12. 최종 요약

- **객체지향(OOP)**은 객체에 상태와 행동의 책임을 배치하고 안정된 메시지·인터페이스로 협력하게 하는 설계 접근이다.
- 추상화, 캡슐화, 상속, 다형성의 목적과 대가를 구분하고 상속 관계에서는 대체 가능성을 확인한다.
- 연관·집합·합성·일반화·의존은 관계의 의미와 생명주기를 근거로 선택한다.
- **디자인패턴**은 반복 설계 문제의 맥락, 해결 구조, 참여자와 결과를 이름 붙인 지식이며 복사할 코드가 아니다.
- GoF 패턴은 생성 5개, 구조 7개, 행위 11개이며 구조가 비슷해도 문제 의도로 구분한다.
- 패턴은 실제 변화와 복잡성 문제가 있을 때 적용하고, 패턴 자체가 목적이 되지 않게 한다.
