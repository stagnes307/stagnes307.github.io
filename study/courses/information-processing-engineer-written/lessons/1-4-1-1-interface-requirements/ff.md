# 1-4-1-1. 인터페이스 요구사항 확인

> **공식 학습 범위**: 소프트웨어설계의 인터페이스 설계 영역에서 `내외부 인터페이스 요구사항`을 확인하고, `요구공학`의 관점으로 요구를 수집·분석·명세·검증·관리하는 방법을 학습한다.

## 0. 이번 레슨의 도착점

인터페이스는 서로 다른 구성 요소가 데이터나 서비스를 주고받는 접점이다. 인터페이스 요구사항 확인의 핵심은 “어떤 기술을 쓸 것인가”를 성급히 정하는 일이 아니라, **누가 무엇을 왜 주고받아야 하며 어떤 조건을 만족해야 하는가**를 검증 가능한 문장으로 만드는 일이다. 이 레슨을 마치면 다음을 할 수 있어야 한다.

1. 시스템 내부와 외부의 접점을 구분하고 각 접점에서 필요한 기능·데이터·품질·제약 요구를 찾아낸다.
2. 이해관계자의 표현을 요구공학 절차에 따라 분석하고 모호함, 누락, 충돌을 줄인다.
3. 요구사항을 식별자, 근거, 우선순위, 수용 기준, 추적 관계와 함께 기록한다.
4. 구현 방식이나 특정 제품을 요구사항으로 오해하는 시험 함정을 판별한다.

이 레슨에서는 요구를 확인하는 단계까지만 다룬다. 구체적인 시스템 아키텍처와 연계 대상의 식별은 다음 레슨, 송수신 항목과 데이터 형식의 상세 명세는 그다음 레슨의 범위다.

## 1. 인터페이스 요구사항의 의미와 경계

### 1.1 인터페이스 요구사항이 답해야 하는 질문

인터페이스 요구사항은 접점에서 기대하는 행위와 조건을 기술한다. 좋은 요구는 다음 질문에 답한다.

- **주체**: 데이터를 보내거나 서비스를 요청하는 쪽은 누구인가?
- **상대**: 받거나 응답하는 쪽은 누구인가?
- **목적**: 교환으로 달성하려는 업무 목적은 무엇인가?
- **내용**: 어떤 업무 정보 또는 사건을 주고받는가?
- **시점과 빈도**: 언제, 어떤 사건을 계기로, 어느 정도 빈도로 교환하는가?
- **품질**: 허용 지연, 정확성, 가용성, 보안, 감사 가능성은 어느 수준이어야 하는가?
- **예외**: 상대가 응답하지 않거나 입력이 유효하지 않을 때 업무적으로 어떤 결과를 기대하는가?

“결제 시스템과 연동한다”는 대상만 언급했을 뿐 충분한 요구가 아니다. “주문 승인 후 결제 승인 요청을 전달하고, 사용자가 기다리는 흐름에서 정해진 시간 안에 승인 또는 거절 결과를 받아 주문 상태에 반영한다”처럼 목적·입력·결과·시간 조건이 드러나야 검증할 수 있다. 다만 이 단계에서 특정 통신 제품이나 세부 필드 길이까지 확정할 필요는 없다.

### 1.2 요구사항과 설계 결정의 구분

요구사항은 필요한 결과와 제약을 말하고, 설계는 그 결과를 달성하는 방법을 선택한다.

| 구분 | 중심 질문 | 예시 | 검토 기준 |
| --- | --- | --- | --- |
| 기능 요구 | 접점에서 무엇을 해야 하는가? | 회원 상태 조회 요청에 상태 결과를 제공한다 | 업무 시나리오로 확인 가능한가 |
| 비기능 요구 | 어느 수준으로 수행해야 하는가? | 정상 운영 시 응답 지연의 허용 기준을 만족한다 | 측정 기준이 있는가 |
| 제약 요구 | 반드시 지켜야 할 제한은 무엇인가? | 개인정보는 승인된 범위에서만 전달한다 | 법·정책·환경 근거가 있는가 |
| 설계 결정 | 어떻게 구현할 것인가? | 특정 메시지 형식이나 제품을 사용한다 | 대안 비교와 요구 추적이 가능한가 |

“빠르게 처리한다”, “안전하게 연동한다”는 방향은 맞지만 측정하거나 판정할 수 없다. 반대로 “반드시 특정 제품을 사용한다”는 문장은 계약이나 표준 같은 근거가 없다면 요구가 아니라 성급한 구현 선택일 수 있다.

## 2. 내외부 인터페이스 요구사항

`내외부 인터페이스 요구사항`은 시스템 경계 안의 구성 요소 사이 접점과 경계 밖의 조직·시스템·사용자·장비와의 접점에서 필요한 조건을 함께 본다는 뜻이다.

### 2.1 내부 인터페이스 요구

내부 인터페이스는 한 시스템을 이루는 모듈, 계층, 서비스, 저장 영역 등 내부 구성 요소 사이의 상호작용에 관한 요구다. 내부라고 해서 중요도가 낮지 않다. 내부 접점의 계약이 불명확하면 한 모듈의 변경이 다른 모듈의 장애로 이어질 수 있다.

- 어느 업무 기능이 다른 내부 기능의 결과를 필요로 하는가?
- 호출 전후에 유지되어야 하는 상태와 순서는 무엇인가?
- 동일 데이터의 책임 주체와 변경 권한은 어디에 있는가?
- 실패가 발생했을 때 호출한 기능과 호출된 기능이 각각 무엇을 보장해야 하는가?
- 성능, 동시성, 트랜잭션 경계처럼 내부 연결에도 필요한 품질 조건은 무엇인가?

예를 들어 주문 기능이 재고 기능에 예약을 요청한다면 “재고를 확인한다”에서 끝나지 않는다. 예약 성공 여부가 주문 상태에 어떤 의미를 주는지, 같은 요청이 반복될 때 중복 예약을 막아야 하는지, 예약 실패가 전체 업무에 어떤 결과를 만드는지를 요구 수준에서 확인해야 한다.

### 2.2 외부 인터페이스 요구

외부 인터페이스는 조직 밖의 시스템뿐 아니라 현재 개발 범위 밖에서 독립적으로 관리되는 시스템, 사용자, 장비, 기관과의 접점을 포함한다. 외부 접점에는 통제할 수 없는 변경과 운영 조건이 있으므로 책임 경계가 특히 중요하다.

- 외부 제공자와 소비자의 업무 책임은 어디에서 나뉘는가?
- 운영 시간, 점검 시간, 호출 한도처럼 상대가 정한 조건이 있는가?
- 교환 가능한 데이터의 법적·정책적 범위는 무엇인가?
- 외부 장애나 지연이 발생했을 때 사용자의 업무를 어떻게 보호해야 하는가?
- 버전 변경과 종료 통지는 누가 어떤 절차로 관리하는가?

### 2.3 공통 분류 축

내부와 외부 모두 다음 축으로 요구를 분류하면 누락을 줄일 수 있다.

1. **업무 이벤트**: 어떤 사건이 교환을 시작하는가.
2. **기능**: 요청, 통지, 조회, 등록, 변경, 취소 중 무엇인가.
3. **정보**: 업무적으로 반드시 전달되어야 할 정보는 무엇인가.
4. **품질**: 시간, 처리량, 정확성, 가용성, 복구 가능성은 어떠해야 하는가.
5. **보안과 개인정보**: 인증, 권한, 기밀성, 무결성, 기록 요구가 있는가.
6. **운영과 변경**: 감시, 장애 통지, 버전, 담당자, 변경 승인 조건은 무엇인가.

이 분류는 데이터 필드의 상세 형식을 미리 정하려는 것이 아니다. 상세 설계에 넘겨야 할 요구의 근거와 판정 기준을 빠짐없이 만드는 틀이다.

## 3. 요구공학으로 확인하는 절차

`요구공학`은 이해관계자의 필요를 체계적으로 도출하고 분석하여 명세하고, 그것이 올바른지 검증하며, 변경을 지속해서 관리하는 활동이다. 교재마다 단계 명칭이나 묶는 방식은 조금 다를 수 있지만 핵심 흐름은 동일하다.

### 3.1 도출: 숨어 있는 요구를 끌어내기

도출에서는 인터뷰, 워크숍, 관찰, 설문, 기존 문서 분석, 업무 시나리오 검토, 프로토타입 등으로 정보를 모은다. 인터페이스 요구에서는 한쪽 담당자만 만나면 안 된다. 송신 측, 수신 측, 업무 담당, 운영, 보안, 데이터 책임자처럼 접점에 영향을 주는 관점을 함께 확인한다.

질문은 “무엇이 필요합니까?”보다 구체적이어야 한다.

- 현재 어떤 사건에서 수작업 전달이 발생하는가?
- 결과가 늦거나 누락되면 어떤 업무 피해가 생기는가?
- 같은 요청이 두 번 도착하면 어떻게 판단하는가?
- 어느 정보는 보내면 안 되며, 어느 정보는 감사 목적으로 남겨야 하는가?
- 상대 시스템이 점검 중일 때 현재 업무는 중단되는가, 대기하는가, 나중에 재처리하는가?

### 3.2 분석: 모호함·충돌·누락을 찾기

분석에서는 후보 요구를 분류하고 모델링하며 실현 가능성과 우선순위를 검토한다. 같은 단어를 서로 다른 뜻으로 쓰는지, 두 요구가 양립할 수 있는지, 정상 흐름만 있고 예외 흐름이 빠졌는지를 본다.

업무 부서는 “항상 최신 고객 정보를 즉시 받아야 한다”고 하고 외부 제공자는 “정기 배치로만 제공한다”고 할 수 있다. 이를 그대로 두지 않고 최신성의 업무 이유, 허용 가능한 지연, 대체 절차, 비용을 비교하여 합의 가능한 요구로 조정한다. 분석의 목적은 한쪽 의견을 지우는 것이 아니라 **충돌을 보이게 하고 결정 근거를 남기는 것**이다.

### 3.3 명세: 검증 가능한 문장으로 고정하기

명세에는 요구 식별자, 설명, 근거, 출처, 우선순위, 전제, 입력과 결과, 예외, 수용 기준, 관련 요구를 기록한다. 문장은 한 요구에 한 핵심 행위를 담고 능동형으로 쓰는 편이 좋다.

나쁜 예:

> 시스템은 적절하고 신속하게 외부 정보를 처리한다.

개선 예:

> 승인된 사용자 요청에 대해 외부 고객 상태 조회를 수행하고, 정상 응답이면 상태와 기준 시각을 표시하며, 허용 시간을 넘기면 지연 상태와 재시도 가능 여부를 사용자에게 알린다.

개선 문장은 아직 세부 프로토콜을 고정하지 않지만 정상 결과와 시간 초과 결과를 시험할 수 있다.

### 3.4 검증과 확인: 제대로 썼는가, 필요한 것을 썼는가

검증에서는 요구가 완전성, 일관성, 명확성, 실현 가능성, 검증 가능성, 추적 가능성을 갖추었는지 검토한다. 보통 검토 회의, 시나리오 워크스루, 체크리스트, 시험 사례 초안, 프로토타입 등을 활용한다.

- **완전성**: 정상·예외·운영·보안 관점이 빠지지 않았는가?
- **일관성**: 같은 데이터의 의미나 시점이 요구마다 충돌하지 않는가?
- **명확성**: “신속히”, “가능하면”처럼 해석이 갈리는 표현은 없는가?
- **실현 가능성**: 기술·비용·일정·외부 계약 안에서 달성 가능한가?
- **검증 가능성**: 관찰하거나 측정해 통과 여부를 결정할 수 있는가?
- **추적 가능성**: 상위 업무 목적과 이후 설계·시험으로 이어지는가?

### 3.5 관리: 변경과 기준선을 통제하기

요구는 프로젝트 중 변한다. 요구사항 관리는 변경 요청을 접수하고 영향도를 분석하여 승인 여부를 결정하고, 기준선과 버전, 추적 관계를 갱신하는 활동이다. 인터페이스 요구 하나의 변경은 송신 기능, 수신 기능, 운영 절차, 보안 검토, 시험 자료에 동시에 영향을 줄 수 있다.

변경 기록에는 변경 이유, 요청자, 영향 대상, 승인 결과, 적용 버전을 남기고 관련 산출물의 기준선도 함께 갱신한다.

## 4. 요구사항 확인 산출물과 추적성

### 4.1 요구사항 목록의 기본 항목

| 항목 | 의미 | 확인 질문 |
| --- | --- | --- |
| 요구 ID | 변경되어도 추적할 수 있는 고유 식별자 | 중복되거나 재사용되지 않는가 |
| 요구 문장 | 필요한 행위와 조건 | 하나의 핵심 요구로 읽히는가 |
| 근거·출처 | 왜 필요한지, 누가 요청했는지 | 충돌 시 판단 근거가 되는가 |
| 우선순위 | 필수성과 구현 순서 판단 | 단순 희망과 필수를 구분했는가 |
| 전제·제약 | 성립 조건과 제한 | 외부 계약·정책을 반영했는가 |
| 수용 기준 | 완료를 판정할 관찰 기준 | 시험 사례로 바꿀 수 있는가 |
| 추적 관계 | 상위 목적과 후속 산출물 연결 | 변경 영향 분석이 가능한가 |

추적 행렬은 요구와 업무 목적, 설계 요소, 시험 항목 사이 연결을 보여준다. 모든 행을 기계적으로 많이 만드는 것이 목적은 아니다. 요구 누락과 불필요한 설계를 찾고 변경 영향을 설명할 수 있어야 한다.

### 4.2 검토 회의의 진행 순서

1. 검토 범위와 기준선, 요구의 출처와 업무 목적을 확인한다.
2. 정상 시나리오를 송신·수신 관점에서 따라간다.
3. 오류, 지연, 중복, 권한 부족 같은 예외를 질문한다.
4. 품질 조건과 측정 방법을 확인한다.
5. 미결 사항에 담당자·기한을 배정하고 승인 결과를 기준선으로 남긴다.

검토에서 “구현자가 알아서 처리한다”는 답이 반복되면 요구가 충분히 분석되지 않았다는 신호다.

## 5. 사례: 주문과 결제 접점의 요구 확인

상황은 주문 서비스가 외부 결제 서비스의 승인을 받아야 하는 경우다. 이 단계에서는 구체적인 API 경로나 필드 크기를 설계하지 않는다.

### 5.1 후보 요구 도출

- 사용자는 주문 확정 과정에서 결제 승인 결과를 알아야 한다.
- 같은 주문에 대한 승인 요청이 반복되어도 이중 결제가 발생해서는 안 된다.
- 결제 사업자가 응답하지 않으면 주문을 성공으로 확정하면 안 된다.
- 승인·거절·시간 초과 결과는 고객 문의와 정산 확인에 필요한 범위에서 추적 가능해야 한다.
- 개인정보와 결제 관련 정보는 업무에 필요한 최소 범위로 교환해야 한다.

### 5.2 분석과 명세

“결제가 실패하면 다시 시도한다”는 후보 요구에는 실패 유형과 재시도 주체가 모호하다. 업무 담당자와 운영 담당자는 사용자가 즉시 수정할 수 있는 거절과 일시적인 통신 지연을 구분해야 한다고 합의할 수 있다. 명세에는 두 결과에서 사용자 안내와 주문 상태가 어떻게 달라지는지 기록한다.

수용 기준은 “정상 승인 결과가 오면 해당 주문이 결제 완료 상태가 된다”, “시간 초과인 동안에는 결제 성공으로 확정하지 않는다”, “동일 업무 식별자의 중복 요청에서도 승인 건수가 임의로 늘지 않는다”처럼 관찰 가능한 문장으로 만든다.

### 5.3 경계 확인

여기서 특정 메시지 브로커, 통신 규격, 데이터 형식을 선택하지 않는다. 또한 어느 서버가 실제 송신·수신을 담당하는지 확정하지 않는다. 이 레슨의 결과는 다음 설계 활동이 판단할 수 있는 **검증된 요구와 근거**다.

## 6. 비교와 시험 판별 기준

| 활동 | 대표 행위 | 시험에서의 판별 신호 |
| --- | --- | --- |
| 도출 | 인터뷰, 관찰, 워크숍으로 후보 요구 수집 | 이해관계자의 필요를 발견 |
| 분석 | 분류, 모델링, 충돌 해결, 우선순위 협의 | 모호함과 상충 관계 조정 |
| 명세 | 요구를 문서와 모델로 표현 | 검증 가능한 문장과 수용 기준 |
| 검증 | 완전성·일관성·실현 가능성 등 검토 | 명세 품질과 필요 충족 확인 |
| 관리 | 기준선, 변경 통제, 추적성 유지 | 변경 영향과 버전 관리 |

단계는 현실에서 반복될 수 있다. 검증 중 누락을 발견해 다시 도출하거나 분석할 수 있으므로 “항상 한 번씩 직선으로 끝난다”는 해석은 틀리다.

같은 조직 안의 시스템도 별도 범위와 운영 주체를 가지면 외부 접점일 수 있다. 내부 접점에도 요구 문서와 오류 조건이 필요하다.

## 7. 시험 함정

1. **요구와 구현을 뒤바꾸는 함정**: 특정 제품 사용을 언제나 기능 요구로 고르면 안 된다. 계약상 제약인지 설계 대안인지 근거를 확인한다.
2. **기능 요구만 찾는 함정**: 지연, 보안, 장애 통지, 변경 관리 같은 비기능·운영 요구도 중요하다.
3. **한쪽 관점만 확인하는 함정**: 송신자는 성공으로 보았지만 수신자는 처리하지 못할 수 있다.
4. **요구공학 단계를 고정 순서로만 보는 함정**: 단계의 목적은 구분하되 실제 수행은 반복·피드백될 수 있다.
5. **검증 가능성을 상세함과 동일시하는 함정**: 문장이 길어도 통과 기준이 없으면 검증하기 어렵다.
6. **추적성을 문서 링크 수로 판단하는 함정**: 요구의 근거와 영향 대상을 찾을 수 있어야 한다.

## 8. 확인 문제

### 문제 1

다음 중 인터페이스 요구사항에 가장 가까운 문장을 고르시오.

A. 모든 연계는 특정 상용 제품으로 구현한다.
B. 고객 상태 조회가 허용 시간을 넘기면 지연 상태와 재시도 가능 여부를 사용자에게 알린다.
C. 개발자는 편한 데이터 형식을 선택한다.
D. 연계 모듈의 클래스 이름은 `ExternalConnector`로 한다.

### 문제 2

요구공학 활동과 설명을 연결하시오.

1. 도출  2. 분석  3. 명세  4. 검증  5. 관리

가. 변경 영향과 기준선을 통제한다.
나. 이해관계자로부터 후보 요구를 찾는다.
다. 모호함과 충돌을 조정한다.
라. 검증 가능한 문장과 수용 기준으로 기록한다.
마. 완전성·일관성·실현 가능성을 검토한다.

### 문제 3

외부 제공자가 “고객 정보는 하루 한 번만 제공한다”고 하고 업무 담당자가 “항상 즉시 최신 정보가 필요하다”고 주장한다. 요구 분석에서 먼저 해야 할 일을 두 가지 쓰시오.

### 문제 4

인터페이스 요구 목록에 요구 ID와 문장은 있지만 근거, 수용 기준, 추적 관계가 없다. 각각이 빠졌을 때 생기는 위험을 설명하시오.

## 9. 정답과 해설

### 문제 1 정답: B

B는 조건, 기대 결과, 사용자 관점의 관찰 가능성이 있어 요구로 검증할 수 있다. A는 계약상 근거가 없다면 설계 결정이고, C와 D도 구현자 선택에 가깝다.

### 문제 2 정답

1-나, 2-다, 3-라, 4-마, 5-가이다. 도출은 발견, 분석은 정리와 충돌 해결, 명세는 표현, 검증은 품질 확인, 관리는 변경과 추적 유지라는 핵심 동사로 구분한다.

### 문제 3 예시 해설

첫째, “즉시 최신”이 필요한 업무 이유와 허용 가능한 지연을 측정 가능한 수준으로 구체화한다. 둘째, 외부 제공 조건과 대안의 비용·업무 영향을 비교하여 충돌을 기록하고 권한 있는 이해관계자의 합의를 이끈다. 한쪽 주장을 임의로 삭제하면 안 된다.

### 문제 4 예시 해설

근거가 없으면 충돌이나 변경 시 왜 필요한 요구인지 판단하기 어렵다. 수용 기준이 없으면 구현 완료와 시험 통과를 객관적으로 판정하기 어렵다. 추적 관계가 없으면 변경이 설계·시험·운영에 미치는 영향을 찾거나 상위 목적과 무관한 기능을 발견하기 어렵다.

## 10. 최종 요약

- `내외부 인터페이스 요구사항`은 내부 구성 요소와 외부 범위 사이 접점에서 필요한 기능, 정보, 품질, 보안, 운영 조건을 확인하는 것이다.
- 요구는 **무엇과 왜, 어떤 조건**을 말하고 설계는 **어떻게**를 선택한다.
- `요구공학`의 핵심 활동은 도출, 분석, 명세, 검증, 관리이며 실제로는 반복될 수 있다.
- 좋은 요구는 명확하고 완전하며 일관되고 실현 가능하고 검증·추적할 수 있어야 한다.
- 정상 흐름만 보지 말고 지연, 중복, 오류, 권한, 변경과 같은 예외·운영 관점을 함께 확인한다.
- 이 단계의 산출물은 검증된 요구와 근거다. 시스템 대상, 송수신 항목, 데이터 형식의 상세 결정은 후속 설계에서 수행한다.
