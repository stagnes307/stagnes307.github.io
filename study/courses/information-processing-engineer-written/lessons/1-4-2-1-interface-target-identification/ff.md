# 1-4-2-1. 인터페이스 대상 식별

> **공식 학습 범위**: 인터페이스 요구사항을 바탕으로 `시스템 아키텍처`를 해석하고, 송신·수신 및 중계 역할을 수행할 `인터페이스 시스템`을 식별하는 방법을 학습한다.

## 0. 이번 레슨의 도착점

인터페이스 대상 식별은 연계할 시스템 이름을 목록에 적는 일보다 넓다. 업무 흐름을 실제로 수행하는 구성 요소가 어디에 배치되어 있고, 어느 경계를 넘어 어떤 역할로 상호작용하는지를 찾아야 한다. 이 레슨을 마치면 다음을 할 수 있어야 한다.

1. 시스템 아키텍처의 구성 요소, 계층, 배치, 데이터 흐름을 인터페이스 관점으로 읽는다.
2. 업무 이벤트별 송신 시스템, 수신 시스템, 필요한 경우 중계 시스템을 식별한다.
3. 직접 연계와 중계 연계, 동기적 상호작용과 비동기적 상호작용의 판단 관점을 비교한다.
4. 인터페이스 대상 목록과 관계 행렬을 만들어 누락·중복·책임 불명을 발견한다.

앞 레슨에서 확인한 요구를 입력으로 사용하지만 요구공학 절차 자체를 다시 깊게 다루지 않는다. 또한 이 레슨에서는 구체적인 송수신 필드, 데이터 길이, 오류 코드 같은 상세 명세를 확정하지 않는다.

## 1. 시스템 아키텍처를 인터페이스 관점으로 읽기

`시스템 아키텍처`는 시스템의 주요 구성 요소, 구성 요소 사이 관계, 배치와 제약을 설명하는 상위 구조다. 인터페이스 대상을 찾을 때는 아키텍처 그림의 모양보다 **업무 책임과 경계**를 읽어야 한다.

### 1.1 확인할 네 가지 관점

| 관점 | 확인 내용 | 인터페이스 식별에 주는 정보 |
| --- | --- | --- |
| 논리 관점 | 업무 기능, 서비스, 모듈의 책임 | 어떤 기능이 다른 기능의 결과를 필요로 하는가 |
| 데이터 관점 | 데이터의 생성·소유·조회·변경 책임 | 원천과 소비자, 정합성 책임이 어디에 있는가 |
| 배치 관점 | 실행 노드, 네트워크 구간, 보안 영역 | 실제 경계를 넘는 통신과 제약은 무엇인가 |
| 운영 관점 | 가용 시간, 배치 주기, 감시·장애 책임 | 실시간·예약·재처리 필요와 담당자는 누구인가 |

하나의 구성 요소가 논리적으로 분리되어도 같은 프로세스 안에서 직접 호출될 수 있고, 반대로 같은 업무 이름을 쓰더라도 서로 다른 보안 영역과 운영 주체에 배치될 수 있다. 따라서 “상자 수 = 인터페이스 수”로 단순 계산하면 안 된다.

### 1.2 경계의 종류

대상 식별에서 경계는 물리 네트워크만 의미하지 않는다.

- **업무 책임 경계**: 주문과 결제처럼 상태와 규칙의 책임 주체가 달라지는 지점
- **애플리케이션 경계**: 별도 배포·버전·장애 단위를 갖는 지점
- **데이터 소유 경계**: 원천 데이터를 생성·변경할 권한이 달라지는 지점
- **보안 경계**: 인증 수준, 접근 통제, 신뢰 영역이 달라지는 지점
- **조직·운영 경계**: 담당 부서, 협력사, 기관, 서비스 수준이 달라지는 지점

경계를 넘는 모든 흐름이 반드시 별도 시스템 간 인터페이스는 아니다. 그러나 변경과 실패를 독립적으로 관리해야 한다면 명시적 접점 후보로 기록하는 편이 안전하다.

### 1.3 아키텍처 자료의 교차 확인

대상 식별에는 한 종류의 그림만 믿지 않는다. 시스템 구성도, 배치도, 업무 흐름도, 데이터 흐름도, 현행 연계 목록, 운영 절차, 보안 영역도를 함께 본다.

업무 흐름도에는 “회원 확인”이라는 활동만 있지만 배치도에서는 회원 서비스가 별도 보안 구역에 있을 수 있다. 반대로 구성도에 여러 내부 모듈이 그려져 있어도 같은 애플리케이션 안에서 단일 배포 단위로 처리되어 별도 외부 접점 관리가 필요하지 않을 수 있다. 자료가 충돌하면 최신 기준선과 담당자를 확인하고 미결 사항으로 남긴다.

## 2. 인터페이스 시스템의 역할

`인터페이스 시스템`은 업무 정보나 서비스를 보내고 받거나 전달하는 데 참여하는 시스템이다. 일반적으로 송신, 수신, 중계 역할로 설명할 수 있지만 한 시스템이 상황에 따라 둘 이상의 역할을 맡을 수 있다.

### 2.1 송신 시스템

송신 시스템은 업무 이벤트를 감지해 필요한 정보를 내보내거나 서비스를 요청하는 쪽이다.

- 어떤 사건이 송신을 시작하는가?
- 송신할 정보의 원천과 책임자는 누구인가?
- 송신 전 업무 조건이 충족되었는가?
- 동일 사건을 다시 보낼 가능성과 식별 방법은 무엇인가?
- 송신 성공을 어느 시점에 판단하는가?

단순히 연결을 먼저 시작한 쪽만 송신이라고 보지 않는다. 업무 정보의 흐름과 책임을 기준으로 판단해야 한다.

### 2.2 수신 시스템

수신 시스템은 정보를 받아 검증하고 업무에 반영하거나 요청에 응답하는 쪽이다.

- 받은 정보로 어떤 업무 상태가 변하는가?
- 처리 가능 여부를 어떤 조건으로 판단하는가?
- 성공, 거절, 보류 결과를 누구에게 알려야 하는가?
- 수신한 데이터의 보관·폐기·감사 책임은 어디에 있는가?
- 중복이나 순서 변경이 업무에 어떤 영향을 미치는가?

수신은 네트워크에서 데이터를 받은 순간 끝나지 않는다. 업무적으로 반영되었는지, 아니면 접수만 되었는지 상태 의미를 구분해야 한다.

### 2.3 중계 시스템

중계 시스템은 송신과 수신 사이에서 전달, 변환, 라우팅, 임시 저장 같은 공통 기능을 수행할 수 있다. 중계가 있으면 송신자와 수신자의 결합을 낮추거나 운영을 일원화할 수 있지만 장애 지점과 책임 경계가 하나 더 생긴다.

- 단순 전달인지, 업무 규칙을 적용하는지
- 데이터 형식이나 코드 값을 변환하는지
- 임시 저장과 재전송 책임을 갖는지
- 여러 수신자로 분배하거나 여러 송신자를 통합하는지
- 중계 장애의 감시·복구·추적 담당자가 누구인지

중계 시스템이 모든 경우에 필수라는 해석도, 중계가 있으면 언제나 비효율적이라는 해석도 틀리다. 요구와 운영 조건을 근거로 판단한다.

## 3. 대상 식별 절차

### 3.1 1단계: 기준 자료와 범위 확정

승인된 인터페이스 요구 목록, 시스템 범위, 최신 아키텍처 자료, 현행 연계 목록의 기준선을 확인한다. 개발 대상 시스템의 경계가 불명확하면 같은 흐름을 내부 기능으로 볼지 외부 연계로 볼지 팀마다 달라진다.

식별 단위도 정한다. 조직 전체 시스템 수준인지, 애플리케이션·서비스 수준인지, 배치 작업 수준인지 목적에 맞춰야 한다. 지나치게 큰 단위는 실제 책임을 숨기고, 지나치게 작은 단위는 관리할 접점 수를 불필요하게 늘린다.

### 3.2 2단계: 업무 이벤트와 정보 흐름 추출

요구와 업무 시나리오에서 “누가 무엇을 필요로 하는가”를 뽑는다.

| 항목 | 질문 |
| --- | --- |
| 업무 이벤트 | 어떤 사건이 흐름을 시작하는가 |
| 원천 정보 | 누가 신뢰 가능한 원본을 보유하는가 |
| 소비 목적 | 받는 쪽은 어떤 결정을 위해 사용하는가 |
| 방향 | 단방향 통지인가, 요청과 응답인가 |
| 시점 | 즉시 필요한가, 정해진 시각에 모아도 되는가 |
| 실패 영향 | 누락·지연 시 어느 업무가 멈추거나 잘못되는가 |

이 단계에서는 데이터 항목 하나하나를 확정하지 않는다. “주문 승인 결과”, “회원 상태”, “재고 예약 요청”처럼 업무 정보 묶음과 목적을 중심으로 본다.

### 3.3 3단계: 후보 구성 요소 매핑

각 정보의 원천 기능과 소비 기능을 아키텍처의 실제 구성 요소에 매핑한다. 이름이 비슷하다는 이유만으로 연결하지 말고 책임, 데이터 소유권, 배치 위치를 확인한다.

“고객 관리”라는 이름이 업무 포털, 고객 원장 서비스, 분석 저장소에 모두 나타날 수 있다. 고객 상태의 권위 있는 원천이 고객 원장 서비스라면 포털 화면을 원천 시스템으로 잘못 식별하면 안 된다.

### 3.4 4단계: 송신·수신·중계 역할과 방향 확정

후보마다 해당 업무 이벤트에서 맡는 역할을 기록한다. 요청과 응답이 있는 경우 한 연결 안에서도 요청 방향과 응답 방향의 정보 책임이 다를 수 있다.

- A가 B에 조회를 요청하면 요청 시점에는 A가 요청 송신, B가 요청 수신이다.
- B가 결과를 반환하면 결과 정보 관점에서는 B가 송신, A가 수신이다.
- 인터페이스 목록을 업무 접점 하나로 관리할지 방향별로 나눌지는 조직 기준과 추적 목적에 따라 정한다.

문제에서 “송신 시스템”을 물으면 단순한 연결 방향이 아니라 주어진 업무 데이터의 송신자를 찾아야 한다.

### 3.5 5단계: 경로와 연계 방식 후보 검토

대상 사이에 직접 연결이 가능한지, 공통 중계가 필요한지, 즉시 응답이 필요한지, 비동기 전달이 적합한지를 상위 수준에서 검토한다.

| 구분 | 적합할 수 있는 상황 | 주의할 점 |
| --- | --- | --- |
| 직접 연계 | 대상이 적고 단순하며 즉시 상호작용이 중요 | 대상 증가 시 연결과 변경 관리가 복잡해질 수 있음 |
| 중계 연계 | 다수 시스템의 라우팅·변환·감시를 공통화 | 중계 책임과 장애 영향, 추가 지연을 확인 |
| 동기적 상호작용 | 결과가 있어야 다음 업무를 진행 가능 | 상대 지연이 호출자 대기와 장애 전파로 이어질 수 있음 |
| 비동기적 상호작용 | 시간 분리, 완충, 재처리가 중요 | 최종 처리 상태와 중복·순서 관리가 필요 |

이 표는 특정 기술을 바로 결정하는 표가 아니다. 대상과 책임을 명확히 한 뒤 상세 설계에서 검토할 후보를 정리하는 것이다.

### 3.6 6단계: 누락·중복·책임 검증

식별 결과를 요구사항과 역추적한다.

- 모든 인터페이스 요구가 하나 이상의 대상 관계에 매핑되었는가?
- 근거 요구가 없는 연결이 추가되지 않았는가?
- 같은 업무 흐름을 이름만 다르게 중복 등록하지 않았는가?
- 송신 원천과 수신 반영 책임이 명확한가?
- 중계가 있다면 최종 성공을 누가 판단하는가?
- 시스템 종료·변경 시 영향을 받을 관계를 찾을 수 있는가?

검토자는 시스템별 담당자와 업무 시나리오를 따라가며 확인한다. 그림만 보고 승인하지 않는다.

## 4. 식별 산출물

### 4.1 인터페이스 대상 목록

대상 목록에는 인터페이스 후보 ID와 업무 명칭, 근거 요구 ID, 업무 이벤트와 목적, 송신·수신 시스템의 책임 기능, 중계 책임, 정보 흐름 방향, 예상 시점, 운영·보안 경계, 미결 사항과 담당자를 기록할 수 있다.

세부 데이터 필드와 상세 오류 코드는 후속 명세에서 보완한다. 이 단계의 핵심은 누가 참여하고 왜 연결되는지다.

### 4.2 관계 행렬

시스템을 행과 열에 놓고 정보 흐름을 표시하면 다대다 관계와 고립된 시스템을 찾기 쉽다.

| 송신 \ 수신 | 주문 서비스 | 재고 서비스 | 알림 서비스 | 분석 영역 |
| --- | --- | --- | --- | --- |
| 주문 서비스 | 해당 없음 | 예약 요청 | 주문 결과 통지 | 주문 사건 전달 |
| 재고 서비스 | 예약 결과 | 해당 없음 | 해당 없음 | 재고 변동 전달 |
| 알림 서비스 | 발송 결과 | 해당 없음 | 해당 없음 | 발송 통계 전달 |

행렬의 칸이 많다고 좋은 설계는 아니다. 근거 요구 없이 연결이 과도하면 결합과 운영 부담이 커질 수 있다. 반대로 빈칸이 많다는 이유만으로 누락이라고 단정하지 않고 업무 흐름과 대조한다.

### 4.3 컨텍스트 관점

개발 대상 시스템을 중심에 두고 외부 참여자와 주요 정보 흐름을 표시하면 범위 합의에 유용하다. 컨텍스트 표현은 상위 수준이어야 하며 내부 모듈의 모든 호출을 한 그림에 넣지 않는다. 화살표에는 “데이터”보다 “결제 승인 결과”, “재고 예약 요청”처럼 업무 의미를 붙인다.

## 5. 사례: 온라인 주문의 대상 식별

요구는 주문 확정 전 재고 예약 결과가 필요하고, 결제 승인 결과에 따라 주문 상태가 결정되며, 주문 결과를 고객과 분석 영역에 전달해야 한다고 가정한다. 아키텍처에는 주문 서비스, 재고 서비스, 결제 연계 서비스, 알림 서비스, 사건 중계 영역, 분석 저장 영역이 있다.

1. 주문 서비스는 주문 흐름을 시작하고 재고 예약을 요청한다.
2. 재고 서비스는 재고 원천을 책임지고 예약 결과를 반환한다.
3. 주문 서비스는 결제 연계 서비스에 승인 요청을 전달하고 결과를 받는다.
4. 주문 완료 후 알림 서비스가 통지에 필요한 주문 결과를 받는다.
5. 분석용 사건은 업무 응답과 분리되어 사건 중계를 거쳐 분석 영역으로 전달될 수 있다.

결제 연계 서비스와 외부 결제 제공자를 하나의 이름으로 합치면 책임 경계가 흐려질 수 있다. 내부에서 외부 계약과 호출을 책임지는 구성 요소와 실제 외부 제공자를 구분해 기록한다. 재고 예약 결과가 없을 때 주문이 어떻게 되는지는 요구 검토 대상이지만, 예약 요청의 필드 이름이나 결제 오류 코드 표는 아직 상세 명세의 범위다.

## 6. 판별 비교

### 6.1 시스템·기능·인터페이스

- **시스템**은 독립적인 책임과 운영 경계를 가진 실행 대상이다.
- **기능**은 시스템이 수행하는 업무 능력이다.
- **인터페이스**는 서로 다른 책임 주체가 상호작용하는 계약된 접점이다.

하나의 시스템에 여러 기능과 인터페이스가 있을 수 있다. 기능 하나가 여러 시스템의 협력으로 구현될 수도 있다. 구성 요소 이름과 기능 이름을 같은 수준으로 혼동하지 않는다.

### 6.2 원천과 복제본

데이터를 보유하고 있다는 사실만으로 송신 원천이라고 단정할 수 없다. 분석 저장소에 고객 정보 복제본이 있어도 고객 상태의 변경 책임은 고객 원장 시스템에 있을 수 있다. 최신성, 권한, 업무 책임을 확인해 권위 있는 원천을 식별한다.

### 6.3 요청자와 데이터 송신자

조회 요청에서는 요청자가 요청 메시지를 보내지만, 조회 결과 데이터의 송신자는 응답 시스템이다. 문제 문장이 어느 정보 흐름을 기준으로 송신·수신을 묻는지 확인해야 한다.

## 7. 시험 함정

1. **아키텍처 상자마다 인터페이스가 하나씩 있다고 보는 함정**: 구성 요소 사이에 여러 업무 흐름이 있거나 같은 배포 단위의 내부 호출일 수 있다.
2. **조직 이름으로 대상을 식별하는 함정**: 실제 실행과 데이터 책임을 가진 시스템·서비스를 찾아야 한다.
3. **연결을 시작한 쪽을 언제나 송신으로 보는 함정**: 요청 정보와 응답 정보의 방향을 구분한다.
4. **중계 시스템을 최종 업무 책임자로 보는 함정**: 중계 성공과 최종 수신 업무 반영 성공은 다를 수 있다.
5. **대상 식별 단계에서 필드와 오류 코드를 확정하는 함정**: 이 단계는 참여 대상, 역할, 관계를 확인한다.
6. **현재 그림 하나를 절대 기준으로 보는 함정**: 업무, 데이터, 배치, 운영 자료를 교차 확인한다.
7. **모든 연결에 같은 방식을 적용하는 함정**: 즉시 결과 필요성, 장애 격리, 처리량, 재처리 요구가 다를 수 있다.

## 8. 확인 문제

### 문제 1

인터페이스 대상 식별을 위해 시스템 아키텍처를 검토할 때 함께 보아야 할 관점 네 가지를 쓰고, 각각 무엇을 알려 주는지 설명하시오.

### 문제 2

주문 시스템 A가 고객 시스템 B에 고객 상태 조회를 요청하고 B가 상태 결과를 반환한다. “고객 상태 결과”를 기준으로 송신 시스템과 수신 시스템을 쓰시오.

### 문제 3

여러 업무 시스템이 서로 다른 형식으로 같은 기관의 정보를 받아야 하고 실패한 전달을 한곳에서 추적하려 한다. 중계 시스템을 검토할 이유 두 가지와 추가 위험 두 가지를 쓰시오.

### 문제 4

대상 목록에 업무 명칭과 송수신 시스템 이름은 있지만 근거 요구, 업무 이벤트, 원천 데이터 책임, 미결 사항이 없다. 상세 설계에 넘길 때 생길 문제를 설명하시오.

### 문제 5

대상 식별 단계와 후속 상세 설계에서 해야 할 일을 각각 두 가지씩 구분하시오.

## 9. 정답과 해설

### 문제 1 예시 정답

논리 관점은 기능과 서비스 책임을, 데이터 관점은 생성·소유·소비 책임을, 배치 관점은 실행 노드와 네트워크·보안 경계를, 운영 관점은 가용 시간·주기·장애 담당을 알려 준다.

### 문제 2 정답

고객 상태 결과의 송신 시스템은 B, 수신 시스템은 A이다. 조회 요청 메시지를 기준으로 보면 방향이 반대이므로 문제에서 기준으로 제시한 정보를 먼저 읽어야 한다.

### 문제 3 예시 정답

형식 변환과 다수 대상 라우팅을 공통화할 수 있고 실패 전달의 저장·재전송·감시를 한곳에서 운영할 수 있다. 반면 중계 장애가 여러 흐름에 미치는 영향, 추가 지연, 중계 성공과 최종 성공의 구분, 운영 책임 증가를 확인해야 한다.

### 문제 4 예시 해설

근거가 없으면 불필요한 연결인지 누락인지 판단하기 어렵다. 이벤트가 없으면 송신 시점과 방향이 모호하다. 원천 책임이 없으면 복제본을 권위 있는 데이터로 잘못 선택할 수 있다. 미결 사항을 숨기면 상세 설계자가 임의로 가정해 재작업이 생긴다.

### 문제 5 예시 정답

대상 식별에서는 업무 정보 흐름을 아키텍처 구성 요소에 매핑하고 송신·수신·중계 역할과 경계를 확인한다. 후속 상세 설계에서는 실제 송수신 데이터 항목·형식과 오류 코드·처리 규칙 같은 세부 계약을 정한다.

## 10. 최종 요약

- `시스템 아키텍처`는 구성 요소 이름만 보는 그림이 아니라 업무·데이터·배치·운영 책임과 경계를 읽는 자료다.
- `인터페이스 시스템`은 업무 정보의 송신, 수신, 필요한 경우 중계 역할에 참여한다.
- 대상 식별은 기준선 확정 → 이벤트·정보 흐름 추출 → 구성 요소 매핑 → 역할·방향 확인 → 경로 후보 검토 → 요구 역추적 순으로 수행할 수 있다.
- 송신과 수신은 연결을 시작한 방향이 아니라 문제에서 다루는 업무 정보의 방향으로 판단한다.
- 중계는 결합 완화와 공통 운영에 도움을 줄 수 있지만 장애 지점, 지연, 최종 성공 책임을 함께 검토해야 한다.
- 대상 목록과 관계 행렬에는 근거 요구와 책임을 남겨야 하며, 데이터 필드와 오류 처리의 상세 명세는 후속 레슨의 범위다.
