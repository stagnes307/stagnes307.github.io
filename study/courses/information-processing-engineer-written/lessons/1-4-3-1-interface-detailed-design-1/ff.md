# 1-4-3-1. 내외부 송수신 · 데이터 명세화

> **공식 학습 범위**: 인터페이스 상세 설계에서 `내외부 송수신`의 업무 흐름과 조건을 구체화하고, 교환할 정보를 `데이터 명세화`하여 양쪽 시스템이 같은 의미로 처리하도록 만드는 방법을 학습한다.

## 0. 이번 레슨의 도착점

인터페이스 대상이 정해졌다고 곧바로 구현할 수 있는 것은 아니다. 송신자는 어떤 사건에서 무엇을 보내고, 수신자는 어떤 조건으로 받아 어느 업무에 반영할지 합의해야 한다. 같은 “고객번호”라도 한쪽은 숫자, 다른 쪽은 앞자리 0을 포함한 문자열로 이해하면 오류가 발생한다. 이 레슨을 마치면 다음을 할 수 있어야 한다.

1. 송신·수신의 업무 흐름, 방향, 시점, 주기, 선행·후행 조건을 명세한다.
2. 데이터 항목의 이름, 정의, 형식, 길이, 필수 여부, 값 범위, 코드, 원천을 기술한다.
3. 송신 데이터와 수신 데이터의 대응 관계와 변환 규칙을 매핑 표로 작성한다.
4. 예시 메시지와 경계값을 이용해 명세의 완전성·일관성·검증 가능성을 점검한다.

앞 레슨의 시스템 대상 식별을 입력으로 삼되 아키텍처 구성 요소를 다시 선정하지 않는다. 오류 코드와 재시도 정책의 상세 설계는 다음 레슨에서 다룬다.

## 1. 내외부 송수신의 기본 개념

`내외부 송수신`은 시스템 내부 구성 요소 또는 외부 시스템 사이에서 업무 정보가 이동하는 과정이다. 단순 전송만 보는 것이 아니라 **업무 사건 발생 → 송신 데이터 생성 → 전달 → 수신 검증 → 업무 반영 → 결과 확인**의 전체 흐름을 본다.

### 1.1 송신 명세가 답할 질문

- 어떤 업무 이벤트가 송신을 시작하는가?
- 송신 데이터는 어느 원천에서 어떤 기준 시각으로 생성되는가?
- 한 건씩 보내는가, 여러 건을 묶는가?
- 즉시 전송하는가, 일정 시각이나 주기로 전송하는가?
- 송신 전에 승인, 상태 확인, 중복 확인 같은 선행 조건이 있는가?
- 전달 완료와 업무 처리 완료를 어떻게 구분하는가?

송신 시스템이 파일이나 메시지를 만들었다는 사실과 상대 시스템이 업무에 반영했다는 사실은 다르다. 명세에서 어느 상태를 “성공”으로 부르는지 명확히 해야 한다.

### 1.2 수신 명세가 답할 질문

- 수신 가능한 시간과 조건은 무엇인가?
- 구조, 필수값, 값 범위, 권한을 어느 단계에서 검증하는가?
- 유효한 데이터는 어느 업무와 저장 영역에 반영되는가?
- 동일한 업무 식별자가 다시 오면 신규, 중복, 변경 중 무엇으로 해석하는가?
- 일부 항목이나 일부 건만 유효할 때 전체를 거절할지 유효한 부분을 처리할지 결정되어 있는가?
- 처리 결과를 송신자나 운영자에게 어떤 수준으로 알려야 하는가?

수신 명세는 “받아서 저장한다”로 끝나면 안 된다. 접수, 검증, 반영, 완료의 상태가 다를 수 있음을 고려한다.

### 1.3 송수신 유형 비교

| 구분 | 특징 | 확인할 핵심 |
| --- | --- | --- |
| 요청·응답 | 요청 후 결과를 기다려 다음 업무 수행 | 허용 대기 시간, 응답 의미, 시간 초과 상태 |
| 단방향 통지 | 송신자가 사건을 알리고 즉시 업무 응답을 요구하지 않음 | 최종 수신 확인, 유실 감지, 중복 처리 |
| 실시간 처리 | 사건 발생과 가깝게 건별 전달 | 순간 부하, 상대 장애 영향, 순서 |
| 배치 처리 | 일정 시점에 여러 건을 묶어 전달 | 기준 시각, 건수·합계, 부분 실패, 재처리 단위 |

어느 방식이 항상 우월한 것은 아니다. 업무가 결과를 즉시 필요로 하는지, 지연을 허용하는지, 양과 운영 조건이 어떤지에 따라 판단한다. 구체 기술 이름보다 업무 시간성과 완료 기준이 먼저다.

## 2. 송수신 상세 항목

### 2.1 인터페이스 기본 정보

각 인터페이스에는 고유 ID, 업무명, 목적, 근거 요구, 송신 시스템, 수신 시스템, 담당 조직, 방향, 시점·주기, 예상 건수, 보안 등급, 관련 문서 버전을 기록한다. 고유 ID는 이름이 바뀌어도 추적할 수 있어야 한다.

“회원 연계”, “주문 전송”처럼 넓은 이름만 있으면 서로 다른 흐름이 섞일 수 있다. “회원 상태 조회”, “주문 완료 사건 통지”처럼 행위와 업무 정보가 드러나는 이름이 유리하다.

### 2.2 업무 흐름과 상태

송수신 흐름은 정상 흐름과 예외 후보를 순서로 표현한다.

1. 선행 업무 조건을 확인한다.
2. 송신 대상과 기준 시각을 확정한다.
3. 송신 데이터를 생성하고 업무 식별자를 부여한다.
4. 정해진 전달 경로로 보낸다.
5. 수신 측이 구조와 업무 유효성을 확인한다.
6. 수신 업무 상태에 반영한다.
7. 필요한 경우 접수 또는 처리 결과를 돌려준다.
8. 양쪽이 추적 가능한 기록을 남긴다.

여기서 “결과를 돌려준다”는 존재만 기록하고 오류 분류·재시도 횟수 같은 정책은 다음 단계에서 상세화할 수 있다.

### 2.3 건수와 제어 정보

배치나 복수 건 전송에서는 본문 외에 제어 정보가 중요하다. 파일·묶음 식별자, 생성 시각, 기준 일자, 전체 건수, 필요 시 합계나 검증값을 두면 누락과 중복을 발견하는 데 도움이 된다. 다만 어떤 제어 정보를 쓸지는 업무 위험과 환경에 맞춰야 하며 모든 항목이 언제나 필수라는 식으로 암기하지 않는다.

## 3. 데이터 명세화

`데이터 명세화`는 송신자와 수신자가 교환 데이터의 구조와 의미를 동일하게 이해하도록 항목별 계약을 기록하는 활동이다. 단순히 데이터형과 길이만 적는 것이 아니라 업무 의미, 원천, 허용값, 조건, 변환 관계를 포함한다.

### 3.1 항목 정의서의 핵심

| 명세 항목 | 설명 | 예시 질문 |
| --- | --- | --- |
| 항목명·표준명 | 양쪽이 식별할 이름 | 같은 개념에 다른 이름을 쓰지 않는가 |
| 업무 정의 | 값이 의미하는 사실 | “처리일”은 요청일인가 완료일인가 |
| 자료형·표현 | 문자, 수, 날짜 등 논리 형식 | 앞자리 0과 소수점은 보존되는가 |
| 길이·정밀도 | 최대 길이, 자릿수, 소수 자릿수 | 초과값과 반올림 기준은 무엇인가 |
| 필수 여부 | 항상 필수인지 조건부인지 | 조건부라면 어떤 조건인가 |
| 허용값·범위 | 코드, 최소·최대, 패턴 | 정의되지 않은 코드가 올 수 있는가 |
| 원천·기준 시각 | 값의 책임 시스템과 시점 | 복제본과 원천을 구분했는가 |
| 변환 규칙 | 단위, 코드, 날짜, 기본값 변환 | 정보 손실이나 의미 변경은 없는가 |
| 개인정보·보안 | 민감도와 마스킹·권한 조건 | 불필요한 정보가 포함되지 않는가 |

“숫자”라는 표현만으로는 부족할 수 있다. 금액인지 수량인지, 음수를 허용하는지, 소수 자릿수와 반올림이 무엇인지가 업무 의미에 영향을 준다.

### 3.2 필수값, 선택값, 조건부 필수값

- **필수값**은 모든 유효한 송수신에서 존재해야 한다.
- **선택값**은 없어도 전체 데이터가 유효할 수 있다.
- **조건부 필수값**은 특정 상태나 업무 유형에서 반드시 필요하다.

예를 들어 배송 주문에서는 배송지 식별자가 필수지만 매장 수령 주문에서는 필요하지 않을 수 있다. 이를 단순 선택값으로 적으면 배송 주문에서도 누락을 허용할 위험이 있다. “주문 유형이 배송이면 필수”처럼 조건을 명세한다.

### 3.3 빈 값의 의미

값이 없다는 표현도 합의해야 한다. 미입력, 알 수 없음, 해당 없음, 삭제됨은 서로 다른 업무 의미다. 빈 문자열, 공백, 특정 코드, 항목 생략을 임의로 혼용하면 안 된다. 특정 표현 방식은 환경에 따라 달라질 수 있으므로 명세에서는 **업무 의미와 허용 표현**을 함께 기록한다.

### 3.4 날짜·시간과 단위

날짜·시간은 형식뿐 아니라 기준 시간대, 정밀도, 의미를 확인한다. “주문일시”가 사용자가 주문한 시각인지 서버가 접수한 시각인지 다를 수 있다. 수량·거리·온도·통화처럼 단위가 있는 값은 단위를 데이터에 포함할지 인터페이스 전체 규칙으로 고정할지 결정하고 변환 과정의 반올림·손실을 검토한다.

### 3.5 코드와 식별자

코드는 값과 의미, 유효 기간, 관리 주체를 기록한다. 같은 “01”이 시스템마다 다른 의미일 수 있으므로 코드 매핑이 필요하다. 식별자는 화면 표시용 번호와 내부 업무 식별자를 구분한다. 문자열 식별자를 수로 처리하면 앞자리 0이 사라질 수 있으며, 서로 다른 업무 객체의 식별자를 이름이 비슷하다고 섞으면 안 된다.

## 4. 데이터 매핑과 변환 규칙

### 4.1 매핑 표

| 송신 항목 | 수신 항목 | 대응 | 변환 | 확인 사항 |
| --- | --- | --- | --- | --- |
| customer_id | member_key | 1:1 | 표현 형식 정규화 | 앞자리 문자·0 보존 |
| order_amount | total_price | 1:1 | 단위와 소수 자릿수 일치 | 반올림 기준 |
| order_status | receive_state | 코드 매핑 | 송신 코드→수신 코드 | 미정의 코드 처리 |
| address parts | delivery_address | 여러 항목→한 항목 | 결합 규칙 | 구분자와 길이 초과 |

대응은 항상 1:1이 아니다. 여러 항목을 합치거나 하나를 나누고, 조건에 따라 다른 값을 만들 수 있다. 변환 후 원래 의미가 손실되는지, 역추적이 가능한지 확인한다.

### 4.2 매핑 절차

1. 양쪽 데이터 정의서의 기준 버전을 맞춘다.
2. 이름이 아니라 업무 정의로 같은 개념인지 확인한다.
3. 자료형, 길이, 정밀도, 필수 조건, 코드 범위를 비교한다.
4. 직접 대응, 결합, 분리, 계산, 코드 변환 여부를 기록한다.
5. 대응되지 않는 송신 항목과 수신 필수 항목을 찾는다.
6. 경계값과 대표값으로 변환 예를 만든다.
7. 업무·데이터 책임자의 검토와 승인을 받는다.

자동 변환이 가능하다는 사실과 업무 의미가 같다는 사실은 다르다. 문자열을 날짜로 바꿀 수 있어도 그 값이 같은 기준 시각을 뜻하는지 확인해야 한다.

## 5. 사례: 주문 완료 정보 송수신

주문 시스템이 분석 시스템에 완료 주문을 전달한다고 가정한다. 분석 시스템은 업무 거래를 변경하지 않고 집계에 사용한다.

### 5.1 흐름 명세

- 이벤트: 주문이 업무적으로 완료 상태가 됨
- 송신: 주문 시스템
- 수신: 분석 수집 영역
- 방향: 단방향 사건 전달
- 시점: 완료 사건 발생 후 허용 지연 안에서 전달
- 완료 구분: 송신 기록, 수신 접수, 분석 반영은 서로 다른 상태
- 기준 시각: 주문 완료 시각과 데이터 생성 시각을 구분

### 5.2 데이터 예

| 항목 | 업무 정의 | 조건 | 주의 |
| --- | --- | --- | --- |
| order_id | 주문을 유일하게 식별 | 필수 | 표시 번호와 구분 |
| completed_at | 주문이 완료로 확정된 시각 | 필수 | 기준 시간대 명시 |
| amount | 완료 주문의 합의된 금액 | 필수 | 통화·소수 기준 |
| channel_code | 주문이 접수된 경로 | 필수 | 코드 버전 관리 |
| coupon_id | 적용 쿠폰 식별자 | 쿠폰 사용 시 필수 | 미사용과 알 수 없음 구분 |

“분석용이므로 대충 보내도 된다”는 판단은 틀리다. 원천 의미와 기준 시각이 불명확하면 지표가 달라진다. 반대로 분석에 필요하지 않은 개인정보를 함께 보내는 것도 피해야 한다.

### 5.3 경계값 검토

최소·최대 금액, 소수 금액, 가장 긴 식별자, 코드 변경 시점, 쿠폰 미사용, 완료 시각의 날짜 경계를 예로 만든다. 예시 한 건만 정상이라고 명세가 완전한 것은 아니다. 대표값과 경계값, 조건부 필수 상황을 함께 본다.

## 6. 명세 검토 체크리스트

### 6.1 완전성

- 모든 근거 요구가 송수신 흐름과 데이터 항목에 반영되었는가?
- 수신 필수 항목에 값을 제공할 원천이 있는가?
- 정상값뿐 아니라 빈 값, 경계값, 미정의 코드 후보를 검토했는가?
- 기준 시각, 단위, 코드 관리 주체가 기록되어 있는가?

### 6.2 일관성

- 같은 항목이 문서마다 다른 이름·정의·길이를 갖지 않는가?
- 송신의 완료 의미와 수신의 완료 의미를 혼동하지 않는가?
- 본문 건수와 제어 정보의 건수 기준이 같은가?
- 데이터 매핑과 예시 데이터가 서로 일치하는가?

### 6.3 검증 가능성

- 각 필수·조건부 필수 조건을 시험 사례로 만들 수 있는가?
- 길이, 범위, 정밀도, 코드 규칙의 통과 여부를 판정할 수 있는가?
- 송수신 시점과 주기를 관찰할 수 있는가?
- 요구 ID에서 항목·흐름·시험으로 추적할 수 있는가?

## 7. 시험 함정

1. **송신 완료와 수신 업무 완료를 같은 것으로 보는 함정**: 전달, 접수, 반영 상태를 구분한다.
2. **자료형과 길이만 있으면 데이터 명세가 완성된다는 함정**: 업무 정의, 원천, 조건, 코드, 단위도 필요하다.
3. **이름이 같은 항목을 자동으로 매핑하는 함정**: 정의와 기준 시각이 다를 수 있다.
4. **빈 값은 모두 같은 의미라는 함정**: 미입력, 알 수 없음, 해당 없음은 구분될 수 있다.
5. **식별자를 무조건 수로 처리하는 함정**: 앞자리 0, 문자 혼합, 계산 불필요성을 고려한다.
6. **배치에서 본문만 확인하는 함정**: 기준 일자, 전체 건수, 묶음 식별 같은 제어 정보가 누락 탐지에 필요할 수 있다.
7. **상세 명세 단계에서 특정 제품을 당연한 전제로 두는 함정**: 공식 범위의 핵심은 업무 계약과 데이터 의미다.

## 8. 확인 문제

### 문제 1

“회원 정보를 매일 전송한다”는 문장을 송수신 명세로 보완하기 위해 확인할 항목을 다섯 가지 이상 쓰시오.

### 문제 2

다음 항목 명세의 문제를 찾고 개선 방향을 설명하시오.

> 항목명: amount, 자료형: 숫자, 필수 여부: 선택

### 문제 3

배송 주문에서는 배송지 식별자가 반드시 필요하고 매장 수령에서는 필요하지 않다. 이를 단순 선택값으로 명세하면 어떤 문제가 생기며 어떻게 표현해야 하는가?

### 문제 4

송신 시스템의 `customer_id`는 10자리 문자열이고 수신 시스템의 `member_no`는 수형으로 정의되어 있다. 직접 변환하기 전에 확인할 사항을 세 가지 쓰시오.

### 문제 5

주문 완료 사건을 보냈다는 송신 기록은 있지만 수신 시스템에 집계 결과가 없다. 어떤 상태들을 구분해 조사해야 하는가?

## 9. 정답과 해설

### 문제 1 예시 정답

업무 이벤트, 송신·수신 시스템, 원천 데이터의 기준 시각, 전송 시각·주기, 대상 선정 조건, 건수·묶음 기준, 수신 반영 업무, 완료 판단, 보안 조건을 확인할 수 있다. 단순히 “매일”만으로는 어느 시각의 어떤 대상을 어떤 완료 기준으로 보낼지 알 수 없다.

### 문제 2 예시 해설

금액의 업무 정의, 통화 단위, 음수 허용 여부, 최대 자릿수, 소수 자릿수, 반올림 기준, 필수·조건부 조건, 원천을 알 수 없다. 자료형을 더 구체화하고 업무 의미와 범위, 단위, 필수 조건을 추가해야 한다.

### 문제 3 정답

단순 선택으로 두면 배송 주문에서도 누락을 유효하게 볼 수 있다. “주문 유형이 배송이면 필수, 매장 수령이면 해당 없음”처럼 조건부 필수와 해당 없음의 의미를 기록한다.

### 문제 4 예시 정답

앞자리 0이 업무 식별에 필요한지, 문자 가능성이 있는지, 양쪽 길이 범위가 맞는지, 동일한 업무 객체를 뜻하는지, 수형 변환 후 원복·추적이 가능한지를 확인한다. 계산하지 않는 식별자는 문자열이 더 적절할 수 있다.

### 문제 5 예시 해설

데이터 생성, 전달 시도, 중계 또는 수신 접수, 구조·업무 검증, 저장·업무 반영, 후속 집계 상태를 구분한다. 한 단계의 성공을 최종 업무 성공으로 오해하면 원인을 찾기 어렵다.

## 10. 최종 요약

- `내외부 송수신` 명세는 이벤트, 방향, 시점, 선행 조건, 전달, 수신 검증, 업무 반영, 완료 기준을 연결한다.
- 송신 완료·수신 접수·업무 반영 완료는 서로 다른 상태일 수 있다.
- `데이터 명세화`에는 항목명과 자료형뿐 아니라 업무 정의, 길이·정밀도, 필수 조건, 허용값, 원천, 기준 시각, 단위, 코드, 보안 조건이 필요하다.
- 데이터 매핑은 이름이 아니라 업무 의미를 기준으로 하며 직접 대응, 결합, 분리, 계산, 코드 변환과 손실 여부를 기록한다.
- 대표값만 보지 말고 빈 값, 조건부 필수, 최대·최소, 코드 변경, 시간 경계 같은 사례로 명세를 검토한다.
- 이 레슨은 송수신과 데이터 계약의 범위이며 오류 처리 정책과 전체 인터페이스 설계 판단은 다음 레슨에서 이어진다.
