# 2-1-2-1. 프로시저

> **출제 범위 기준**: 이 레슨은 정보처리기사 필기 출제기준의 `소프트웨어개발 > 데이터 입출력 구현 > 데이터 조작 프로시저 작성 > 1. 프로시저`를 다룬다. 정확한 학습 토픽은 **프로시저**, **데이터 조작 프로시저 작성의 적용 절차와 판단 기준**이다. DBMS 제품마다 문법과 지원 기능이 다르므로 특정 제품의 예약어를 공통 표준처럼 외우기보다 목적, 실행 흐름, 트랜잭션 경계와 검증 기준을 중심으로 학습한다.

프로시저는 여러 SQL 문과 제어 로직을 이름이 있는 실행 단위로 묶어 DBMS에 저장한 프로그램이다. 시험에서는 단순히 “SQL을 모아 둔 것”이라는 정의보다, 입력값을 받아 데이터 조작을 수행하고 결과나 상태를 돌려주는 과정, 함수·트리거와의 경계, 예외와 트랜잭션을 어떻게 통제하는지를 함께 판단해야 한다.

---

## 1. 프로시저의 역할과 구조

### 1.1 왜 프로시저를 사용하는가

응용 프로그램이 주문 확정, 재고 차감, 이력 기록처럼 서로 연결된 데이터 조작을 수행한다고 하자. 각 SQL을 클라이언트가 따로 전송하면 호출 횟수가 늘고, 중간 단계 실패 시 일부 변경만 남을 수 있으며, 여러 프로그램이 서로 다른 규칙을 구현할 가능성도 생긴다. 프로시저는 이런 규칙을 데이터베이스 쪽의 하나의 호출 단위로 모을 수 있다.

주요 목적은 다음과 같다.

- **업무 규칙의 일관성**: 동일한 검증·변경 순서를 여러 호출자가 공유한다.
- **호출 단위 단순화**: 여러 SQL과 분기 로직을 하나의 이름으로 호출한다.
- **권한 경계 설정**: 테이블 직접 변경 권한 대신 승인된 프로시저 실행 권한만 줄 수 있다.
- **네트워크 왕복 감소 가능성**: 다수의 개별 요청을 한 호출로 묶을 수 있다.
- **재사용과 유지보수**: 반복되는 데이터 조작을 중앙에서 변경할 수 있다.

그러나 모든 로직을 프로시저로 옮기는 것이 정답은 아니다. DBMS 종속성이 커질 수 있고, 버전 관리·테스트·배포 체계를 갖추지 않으면 변경 추적이 어려워진다. 응용 계층과 DB 계층 중 어디에 규칙을 둘지는 데이터 일관성, 변경 빈도, 호출 범위, 운영 역량을 함께 보고 결정한다.

### 1.2 논리적 구성 요소

제품별 표기 차이는 있지만 프로시저는 대체로 다음 요소를 가진다.

| 구성 요소 | 역할 | 검토 질문 |
|---|---|---|
| 이름과 스키마 | 호출 대상을 식별 | 이름 충돌과 소유 스키마가 명확한가 |
| 매개변수 | 입력·출력 계약을 표현 | 자료형, 필수 여부, 방향이 요구사항과 맞는가 |
| 선언부 | 지역 변수·상수·커서 등을 준비 | 초기값과 범위가 분명한가 |
| 실행부 | 조회·삽입·수정·삭제와 분기·반복 수행 | 연산 순서와 대상 행이 정확한가 |
| 예외 처리부 | 오류를 분류하고 기록·전파 | 실패를 성공처럼 숨기지 않는가 |
| 트랜잭션 정책 | 커밋·롤백 책임과 원자성 결정 | 중간 결과가 남지 않는가 |
| 결과 계약 | OUT 값, 결과 집합, 상태 코드 등 반환 | 호출자가 성공과 실패를 구분할 수 있는가 |

매개변수 방향은 보통 `IN`, `OUT`, `INOUT` 개념으로 구분한다. `IN`은 호출자가 값을 전달하고, `OUT`은 프로시저가 결과를 채우며, `INOUT`은 입력받은 값을 실행 중 변경해 돌려준다. 모든 DBMS가 같은 키워드와 호출 방식을 쓰는 것은 아니지만 “누가 값을 제공하고 누가 최종값을 책임지는가”라는 계약은 같다.

### 1.3 실행 흐름

프로시저 호출은 보통 다음 순서로 이해할 수 있다.

1. DBMS가 호출자의 실행 권한과 대상 프로시저를 확인한다.
2. 입력 매개변수의 개수·자료형·허용 범위를 확인한다.
3. 지역 변수와 실행 문맥을 준비한다.
4. 조건문, 반복문, SQL 문을 정의된 순서로 수행한다.
5. 오류가 발생하면 예외 처리와 트랜잭션 정책을 적용한다.
6. 출력 매개변수, 결과 집합 또는 상태를 호출자에게 반환한다.

“저장되어 있으므로 항상 빠르다”는 단정은 틀리다. 실행 계획 재사용이나 왕복 감소가 도움이 될 수 있지만, 비효율적인 SQL·잘못된 인덱스 사용·과도한 잠금이 있으면 프로시저도 느리다. 이 레슨에서는 작성 판단과 정확성에 집중하고 구체적인 쿼리 성능 측정은 뒤의 별도 레슨 범위로 남긴다.

## 2. 프로시저와 인접 개념 구분

### 2.1 함수와의 구분

함수는 일반적으로 값을 계산해 반환하며 표현식 안에서 사용할 수 있도록 설계되는 경우가 많다. 프로시저는 하나 이상의 데이터 조작과 업무 절차를 수행하고, OUT 매개변수나 결과 집합 등 다양한 방식으로 결과를 전달할 수 있다. 다만 반환 가능 여부, 함수 내부의 데이터 변경 허용 범위는 제품마다 다르다.

따라서 시험 문제에서 “반드시 값을 하나 반환하면 함수, 아니면 프로시저”처럼 지나치게 단순화하지 않는다. 핵심은 다음과 같다.

- 계산 결과를 표현식의 일부로 재사용하는가?
- 여러 단계의 데이터 조작 절차를 하나의 명령처럼 실행하는가?
- 부수 효과와 트랜잭션을 포함하는가?
- 해당 DBMS가 함수와 프로시저에 어떤 제약을 두는가?

### 2.2 트리거와의 구분

트리거는 특정 테이블 변경이나 DB 이벤트가 발생하면 자동으로 실행되는 객체다. 프로시저는 일반적으로 호출자가 이름을 지정해 명시적으로 실행한다. 자동 실행이 필요한 무결성 보조 로직과 명시적 업무 절차를 구분하지 않으면, 호출 흐름을 찾기 어렵고 예상치 못한 연쇄 변경이 생길 수 있다.

| 비교 | 프로시저 | 트리거 |
|---|---|---|
| 실행 시작 | 명시적 호출 | 지정 이벤트에 반응해 자동 실행 |
| 입력 계약 | 매개변수로 비교적 명확히 표현 | 이벤트의 이전·이후 행 문맥을 사용 |
| 호출 흐름 가시성 | 호출 코드에서 찾기 쉬움 | 숨은 부수 효과가 될 수 있음 |
| 대표 용도 | 주문 처리, 정산, 일괄 변경 | 감사 이력, 제한된 무결성 보조 |

### 2.3 일반 SQL과의 구분

한 번의 단순 조회나 변경을 위해 무조건 프로시저를 만들 필요는 없다. 반복 호출되는 복합 절차, 공통 업무 규칙, 일관된 권한 경계가 필요할 때 이점이 커진다. 반대로 화면마다 자주 바뀌는 표시 로직까지 DB 프로시저에 넣으면 변경 비용과 종속성이 커질 수 있다.

## 3. 데이터 조작 프로시저 작성의 적용 절차와 판단 기준

### 3.1 1단계: 요구사항과 데이터 계약 확정

먼저 자연어 요구사항을 입력, 선행조건, 변경 대상, 결과, 실패 조건으로 나눈다. 예를 들어 “회원 간 포인트를 이체한다”면 다음을 확인한다.

- 보내는 회원과 받는 회원 ID는 서로 다른가?
- 이체 금액은 0보다 큰가?
- 보내는 회원의 잔액이 충분한가?
- 두 잔액 변경과 이력 삽입이 모두 성공해야 하는가?
- 동시 이체 시 잔액 검증과 차감 사이의 경쟁을 어떻게 막는가?
- 실패 원인을 호출자에게 어떤 값이나 오류로 전달하는가?

입력 자료형만 맞는다고 유효한 값은 아니다. 금액 범위, 존재 여부, 상태, 상호 관계 같은 업무 제약도 명세해야 한다. 결과 계약에는 정상 결과뿐 아니라 “대상 없음”, “잔액 부족”, “중복 요청”, “시스템 오류”를 구분할 방법이 있어야 한다.

### 3.2 2단계: 원자성과 트랜잭션 경계 결정

여러 변경이 하나의 업무 단위라면 전부 반영되거나 전부 취소되어야 한다. 포인트 차감은 성공했지만 적립이 실패한 상태를 허용하면 안 된다. 이때 다음을 판단한다.

1. 트랜잭션을 프로시저가 시작·종료하는가, 호출자가 더 큰 트랜잭션을 관리하는가?
2. 중첩 호출에서 내부 프로시저가 임의로 커밋해도 되는가?
3. 예외 발생 시 어느 범위까지 롤백하는가?
4. 잠금 순서를 일정하게 하여 교착 가능성을 줄였는가?

내부에서 무조건 `COMMIT`하는 설계는 재사용성을 해칠 수 있다. 호출자가 여러 업무를 한 트랜잭션으로 묶어야 하는데 내부 커밋이 먼저 실행되면 전체 취소가 불가능해질 수 있기 때문이다. 제품과 프로젝트의 트랜잭션 책임 규약을 먼저 따른다.

### 3.3 3단계: 명확한 의사 SQL로 흐름 설계

다음은 제품 종속 문법을 피한 의사 코드다. 실제 구현 시 해당 DBMS의 프로시저 생성, 오류 발생, 행 잠금 문법으로 바꾼다.

```sql
PROCEDURE transfer_point(
    IN from_member_id INTEGER,
    IN to_member_id INTEGER,
    IN amount DECIMAL,
    OUT result_code VARCHAR
)
BEGIN
    VALIDATE from_member_id <> to_member_id;
    VALIDATE amount > 0;

    BEGIN TRANSACTION ACCORDING TO PROJECT POLICY;

    SELECT balance
      INTO current_balance
      FROM member_point
     WHERE member_id = from_member_id
       FOR UPDATE;

    IF current_balance < amount THEN
        SIGNAL business_error('INSUFFICIENT_BALANCE');
    END IF;

    UPDATE member_point
       SET balance = balance - amount
     WHERE member_id = from_member_id;

    UPDATE member_point
       SET balance = balance + amount
     WHERE member_id = to_member_id;

    INSERT INTO point_history(from_id, to_id, amount, created_at)
    VALUES(from_member_id, to_member_id, amount, CURRENT_TIMESTAMP);

    SET result_code = 'OK';
EXCEPTION
    WHEN business_error THEN
        ROLLBACK ACCORDING TO PROJECT POLICY;
        PROPAGATE A DOCUMENTED BUSINESS FAILURE;
    WHEN OTHERS THEN
        ROLLBACK ACCORDING TO PROJECT POLICY;
        RECORD SAFE DIAGNOSTIC INFORMATION;
        RE-RAISE THE ERROR;
END;
```

이 예시는 개념 흐름을 보여 줄 뿐 그대로 실행되는 표준 SQL이 아니다. `FOR UPDATE`, 예외 선언, 트랜잭션 제어의 위치는 DBMS마다 다르다. 중요한 판단 기준은 검증과 변경 순서, 동시성 보호, 세 변경의 원자성, 오류 은폐 방지다.

### 3.4 4단계: 데이터 조작의 영향을 제한

`UPDATE`나 `DELETE`에서 조건절이 빠지면 전체 행이 바뀔 수 있다. 작성 단계에서 다음 방어를 적용한다.

- 키 또는 명확한 조건으로 대상 행을 제한한다.
- 실행 전 기대 대상 건수를 정의한다.
- 실행 후 영향받은 행 수가 기대와 맞는지 확인한다.
- 0건과 여러 건을 정상으로 볼지 오류로 볼지 명세한다.
- 문자열 연결식 동적 SQL 대신 매개변수 바인딩을 사용한다.
- 호출자에게 필요한 최소 실행 권한만 부여한다.

영향 행 수가 0이라고 항상 실패는 아니다. “없으면 변경하지 않음”이 정상인 요구도 있다. 반대로 회원 한 명을 갱신해야 하는데 0건이나 2건이 바뀌면 무결성 문제다. 판단은 요구사항의 기수성과 사후조건에서 나온다.

### 3.5 5단계: 예외 처리와 반환 계약 구현

예외 처리의 목적은 오류를 없던 일로 만드는 것이 아니다. 복구 가능한 업무 오류와 복구 불가능한 시스템 오류를 구분하고, 트랜잭션을 일관된 상태로 만든 뒤 호출자가 대응할 정보를 제공하는 것이다.

- 업무 오류: 잔액 부족, 허용되지 않은 상태, 중복 요청 등
- 데이터 오류: 필수 행 없음, 유일성 위반, 자료형·범위 위반 등
- 시스템 오류: 연결, 저장공간, 내부 장애 등

모든 예외를 잡아 `result_code='OK'`로 반환하면 장애가 숨는다. 반대로 내부 테이블명, SQL 전문, 개인정보를 그대로 사용자 메시지에 노출해도 안 된다. 외부에는 문서화된 오류 코드와 안전한 메시지를, 운영 로그에는 추적 ID와 필요한 진단 정보를 남기는 식으로 경계를 둔다.

### 3.6 6단계: 테스트와 배포 판단

정상 사례 하나만 실행해서는 충분하지 않다. 최소한 다음을 시험한다.

| 시험 범주 | 예시 | 기대 결과 |
|---|---|---|
| 정상 경계 | 잔액과 이체액이 정확히 같음 | 정책대로 잔액 0, 이력 1건 |
| 입력 오류 | 금액 0·음수, 동일 회원 | 변경 없이 명시적 실패 |
| 존재 오류 | 보내는 회원 또는 받는 회원 없음 | 부분 변경 없이 실패 |
| 업무 오류 | 잔액 부족 | 두 잔액·이력 모두 불변 |
| 동시성 | 같은 계정에서 동시 이체 | 음수 잔액이나 유실 갱신 없음 |
| 중간 실패 | 두 번째 갱신 또는 이력 삽입 실패 | 전체 업무 단위 롤백 |
| 권한 | 승인되지 않은 호출자 | 테이블 우회 변경과 실행 거부 |

배포할 때는 생성 스크립트, 변경 스크립트, 권한 부여, 되돌리기 방법을 버전 관리한다. 매개변수 제거·자료형 변경·결과 형식 변경은 호출자 호환성을 깨뜨릴 수 있으므로 영향 분석이 필요하다. 운영 반영 전에 기존 호출 코드와 새 프로시저 버전의 계약을 대조한다.

---

## 4. 적용 여부를 고르는 판단표

다음 조건이 많을수록 프로시저 적용을 검토할 가치가 크다.

- 여러 데이터 변경이 하나의 원자적 업무 단위다.
- 여러 응용 프로그램이 동일한 데이터 규칙을 공유한다.
- 테이블 직접 권한을 숨기고 승인된 연산만 공개해야 한다.
- 데이터 가까이에서 일괄 처리해야 네트워크 왕복을 줄일 수 있다.
- 조직에 DB 객체의 테스트·형상관리·배포·모니터링 체계가 있다.

다음 조건이 강하면 응용 계층 구현이나 단순 SQL이 더 적합할 수 있다.

- 데이터 조작이 한 번의 단순하고 명확한 SQL로 끝난다.
- 규칙이 화면·서비스 요구에 따라 매우 자주 변한다.
- 여러 종류의 DBMS로 이식해야 하며 제품 종속 비용이 크다.
- DB 프로시저를 자동 테스트하고 배포할 운영 기반이 없다.
- 외부 서비스 호출처럼 DB 트랜잭션 안에 오래 묶기 부적절한 작업이 중심이다.

선택 문제에서는 “프로시저는 항상 성능이 좋다”, “보안이 자동으로 해결된다” 같은 절대 표현을 경계한다. 효과는 올바른 설계, 권한, SQL 품질, 운영 체계가 있을 때 얻어진다.

---

## 5. 시험 함정 정리

1. **프로시저와 트리거를 혼동**: 명시적 호출과 이벤트 기반 자동 실행을 구분한다.
2. **매개변수 방향을 반대로 해석**: 호출자 기준 입력인지 프로시저 기준 출력인지 확인한다.
3. **예외를 잡으면 정상 종료라고 판단**: 롤백, 반환 상태, 재발생 여부까지 봐야 한다.
4. **커밋을 많이 할수록 안전하다고 판단**: 업무 원자성을 쪼개고 호출자 트랜잭션을 방해할 수 있다.
5. **저장 객체이므로 무조건 빠르다고 판단**: SQL과 실행 계획이 비효율적이면 느리다.
6. **동적 SQL 문자열 결합을 편의로만 판단**: 주입 위험, 자료형 오류, 계획 재사용 저하를 함께 본다.
7. **영향 행 0건을 항상 정상으로 처리**: 요구한 기수와 사후조건을 기준으로 판단한다.
8. **제품 문법을 표준 개념으로 암기**: 생성·호출·예외·결과 반환 방식은 DBMS마다 다를 수 있다.

## 6. 확인 문제

### 문제 1

재고 차감, 주문 상태 변경, 이력 삽입이 모두 성공해야 하는 업무를 프로시저로 구현했다. 이력 삽입이 실패했는데 앞의 두 변경만 커밋되었다. 가장 먼저 점검할 설계 요소는 무엇인가?

1. 프로시저 이름 길이
2. 트랜잭션 경계와 예외 시 롤백 정책
3. OUT 매개변수의 화면 색상
4. 주석의 줄 수

### 문제 2

프로시저와 트리거의 실행 시작 방식 차이를 설명하라.

### 문제 3

회원 한 명만 수정해야 하는 `UPDATE` 뒤 영향 행 수가 0으로 나왔다. 이를 무조건 성공으로 처리하면 안 되는 이유는 무엇인가?

### 문제 4

내부 프로시저가 매 호출마다 무조건 `COMMIT`하는 설계가 상위 업무 트랜잭션을 방해할 수 있는 이유를 설명하라.

### 문제 5

다음 주장 중 옳지 않은 것은 무엇인가?

1. 프로시저는 반복되는 복합 데이터 조작을 하나의 호출 계약으로 묶을 수 있다.
2. 테이블 직접 권한 대신 제한된 실행 권한을 제공하는 데 활용할 수 있다.
3. DBMS에 저장된 프로시저는 SQL 내용과 무관하게 항상 최적 성능을 보장한다.
4. 매개변수·결과·오류 계약을 문서화하고 경계값을 테스트해야 한다.

## 정답과 해설

1. **정답: 2번.** 세 변경은 하나의 업무 단위이므로 중간 실패 때 전부 롤백되어야 한다. 부분 커밋은 원자성과 데이터 일관성을 깨뜨린다.
2. **정답:** 프로시저는 보통 호출자가 이름과 매개변수를 지정해 명시적으로 실행한다. 트리거는 지정된 데이터 변경이나 DB 이벤트가 발생할 때 자동 실행된다.
3. **정답:** 대상 키가 없거나 조건이 틀렸을 수 있기 때문이다. 요구사항이 정확히 한 행 변경이라면 0건은 사후조건 위반이며, 변경 없이 성공했다고 반환하면 오류를 숨긴다.
4. **정답:** 상위 호출자가 여러 작업을 하나로 묶어 나중에 전체 롤백하려 해도 내부 변경이 이미 확정될 수 있기 때문이다. 트랜잭션 책임은 프로젝트 규약에 따라 한 경계에서 일관되게 관리한다.
5. **정답: 3번.** 저장 위치만으로 성능이 보장되지 않는다. SQL 구조, 통계, 인덱스, 데이터 분포, 잠금과 실행 계획의 영향을 받는다.

## 7. 최종 요약

- **프로시저**는 SQL과 제어 로직을 이름 있는 실행 단위로 DBMS에 저장하여 복합 데이터 조작과 업무 규칙을 수행하는 객체다.
- 매개변수, 선언부, 실행부, 예외 처리, 트랜잭션 정책, 결과 계약을 하나의 흐름으로 이해한다.
- 함수는 주로 값 계산과 표현식 재사용, 트리거는 이벤트 기반 자동 실행, 프로시저는 명시적 업무 절차 호출이라는 중심 차이를 구분한다.
- **데이터 조작 프로시저 작성의 적용 절차와 판단 기준**은 요구사항·계약 확정 → 원자성·트랜잭션 경계 결정 → 흐름 구현 → 대상 행·권한 제한 → 예외·반환 설계 → 정상·경계·실패·동시성 테스트 순으로 정리한다.
- 프로시저 적용은 일관성·권한·호출 단순화의 이점과 DBMS 종속성·배포·테스트 비용을 함께 평가한다.
- 제품별 문법보다 대상 행, 영향 행 수, 부분 실패, 커밋 책임, 오류 은폐 같은 판단 지점을 우선 학습한다.
