# 2-1-3-1. 데이터 조작 프로시저 최적화

> **출제 범위 기준**: 이 레슨은 정보처리기사 필기 `소프트웨어개발 > 데이터 입출력 구현 > 데이터 조작 프로시저 최적화`에 해당하며, 정확한 토픽은 **쿼리(Query) 성능 측정**, **소스코드 인스펙션**이다. 특정 DBMS의 실행 계획 명칭이나 IDE 화면은 달라질 수 있으므로 측정–분석–변경–재측정의 원칙과 정적 검토 절차를 중심으로 학습한다.

최적화는 코드를 짧게 만드는 작업이 아니다. 동일한 업무 결과와 데이터 일관성을 유지하면서 응답 시간, 처리량, 자원 사용, 동시성 문제를 개선하는 과정이다. 먼저 쿼리를 실제 조건에서 측정하고, 소스코드 인스펙션으로 잘못된 SQL 구성·불필요한 호출·예외와 트랜잭션 결함을 찾아야 한다. 근거 없는 인덱스 추가나 전면 재작성은 최적화가 아니라 새로운 가설일 뿐이다.

---

## 1. 성능 문제를 정확히 정의한다

“느리다”는 측정 가능한 요구사항이 아니다. 다음 질문으로 문제를 수치와 조건으로 바꾼다.

- 어떤 사용자·업무·쿼리가 느린가?
- 입력 데이터 크기와 선택 조건은 무엇인가?
- 단일 실행인가, 동시 요청이 많은 상황인가?
- 평균뿐 아니라 상위 지연 시간은 얼마인가?
- 응답 시간 목표와 처리량 목표는 무엇인가?
- CPU, 메모리, 디스크 입출력, 네트워크, 잠금 대기 중 무엇이 포화되었는가?
- 변경 전후 결과 행과 트랜잭션 의미가 같은가?

대표 지표는 다음과 같다.

| 지표 | 의미 | 해석할 때 주의점 |
|---|---|---|
| 응답 시간(latency) | 요청 시작부터 결과 완료까지 시간 | 평균만 보면 일부 매우 느린 요청이 가려질 수 있음 |
| 처리량(throughput) | 단위 시간에 완료한 작업 수 | 동시성을 높여도 자원 포화 후에는 감소할 수 있음 |
| CPU 시간 | 연산에 사용한 프로세서 시간 | 경과 시간과 같지 않으며 대기 시간은 별도 |
| 논리적 읽기 | 버퍼 등에서 읽은 데이터 블록 양 | 디스크 읽기가 없어도 과도한 접근을 드러냄 |
| 물리적 읽기 | 저장장치에서 실제로 읽은 양 | 캐시 상태에 따라 반복 측정값이 달라짐 |
| 잠금 대기 | 다른 트랜잭션 때문에 기다린 시간 | 쿼리 자체보다 트랜잭션 범위가 원인일 수 있음 |
| 반환·영향 행 수 | 읽거나 변경한 결과 규모 | 같은 시간이라도 처리량 자체가 다르면 직접 비교 곤란 |

성능 목표는 예를 들어 “대표 데이터 100만 건, 동시 사용자 30명에서 조회 응답 시간 p95가 500ms 이하”처럼 조건과 백분위수를 포함해야 비교 가능하다. 숫자는 시스템마다 다르며 문제에서 제시된 기준을 따른다.

## 2. 쿼리(Query) 성능 측정 절차

### 2.1 기준선을 먼저 기록한다

**쿼리(Query) 성능 측정**은 변경 전 기준선(baseline)을 남기는 것에서 시작한다. 동일한 SQL이라도 데이터 분포, 통계 정보, 인덱스, 매개변수, 캐시, 동시 부하에 따라 결과가 달라진다.

1. 운영과 유사한 스키마·인덱스·데이터 분포를 준비한다.
2. 실제로 자주 쓰이거나 느린 매개변수 조합을 선정한다.
3. 결과 행 수와 정확성을 먼저 확인한다.
4. 준비 실행과 측정 실행을 구분한다.
5. 여러 번 반복하여 중앙값, p95 등 분포를 기록한다.
6. 응답 시간과 함께 읽기량·CPU·잠금·실행 계획을 수집한다.
7. 동시성 문제가 의심되면 단일 실행과 부하 실행을 따로 측정한다.

한 번 실행한 시간을 절대값으로 비교하면 백그라운드 작업이나 캐시 우연에 좌우된다. 반대로 캐시를 무조건 비우는 것도 실제 운영이 대부분 웜 캐시라면 대표성이 떨어질 수 있다. 콜드·웜 조건 중 무엇을 시험했는지 명시한다.

### 2.2 전체 구간과 DB 구간을 분리한다

응용 프로그램에서 본 응답 시간에는 연결 획득, 네트워크, SQL 실행, 결과 전송, 객체 변환, 화면 처리 시간이 모두 포함될 수 있다. DB 실행 시간만 빨라도 전체 사용 경험은 느릴 수 있다.

```text
전체 응답 시간
  = 연결·대기 시간
  + SQL 파싱·계획·실행 시간
  + 결과 전송 시간
  + 응용 계층 처리 시간
```

따라서 계층별 관찰 지점을 두되 시간을 중복 합산하지 않는다. 분산 추적이나 타이머를 사용할 때 동일한 시계 기준과 요청 ID로 구간을 연결한다. 측정 자체가 성능에 영향을 주는 오버헤드도 고려한다.

### 2.3 실행 계획을 읽는다

실행 계획은 DBMS가 테이블 접근, 조인, 정렬, 집계를 어떤 순서와 방법으로 수행할지 나타낸다. 계획을 볼 때 다음을 대조한다.

- 예상 행 수와 실제 행 수의 차이
- 전체 스캔과 인덱스 접근의 선택
- 조인 순서와 조인 방법
- 정렬·해시·임시 공간 사용
- 조건이 어느 단계에서 적용되는지
- 반복 수행 횟수와 각 단계의 누적 비용
- 병렬 실행과 데이터 이동 여부

계획의 “비용(cost)”은 DBMS 최적화기가 후보 계획을 비교하기 위한 상대값인 경우가 많다. 밀리초와 같은 실제 경과 시간으로 곧바로 읽지 않는다. 또한 전체 테이블 스캔이 항상 나쁜 것은 아니다. 대부분의 행을 읽는 쿼리나 작은 테이블에서는 연속 스캔이 더 효율적일 수 있다.

다음은 개념적인 측정 기록 예다. 실제 명령은 제품 문서를 따른다.

```sql
-- 1. 결과 정확성과 규모 확인
SELECT customer_grade, COUNT(*)
  FROM orders
 WHERE ordered_at >= :from_time
 GROUP BY customer_grade;

-- 2. 해당 DBMS가 제공하는 실행 계획/실측 통계 기능으로
--    예상 행, 실제 행, 읽기량, 실행 시간을 확인한다.
```

매개변수를 문자열로 이어 붙이기보다 바인딩하면 주입 위험을 줄이고 자료형 계약과 계획 관리에 유리하다. 다만 특정 값의 데이터 편향 때문에 하나의 계획이 모든 매개변수에 적합하지 않을 수 있으므로 대표적인 값 범위를 나누어 측정한다.

### 2.4 결과 집합을 줄이고 필요한 일만 한다

성능 개선 후보를 찾을 때 다음 패턴을 확인한다.

- 필요 없는 열까지 `SELECT *`로 전송한다.
- 필터 없이 많은 행을 가져온 뒤 응용 프로그램에서 버린다.
- 같은 쿼리를 반복 호출하는 N+1 패턴이 있다.
- 반복문 안에서 한 행씩 변경해 왕복 횟수가 커진다.
- 인덱스 열에 불필요한 함수·형 변환을 적용해 탐색이 어려워진다.
- 조인 조건 누락으로 행이 곱집합처럼 증가한다.
- 중복 제거가 필요 없는데 `DISTINCT`로 정렬·해시 비용을 만든다.
- 정렬 기준이 없는데 전체 정렬을 수행한다.

각 패턴은 무조건 삭제할 규칙이 아니다. `DISTINCT`가 업무상 필요한 중복을 제거하거나, 함수 기반 인덱스를 의도적으로 사용하는 설계도 있다. 결과 의미와 계획을 확인한 후 바꾼다.

### 2.5 인덱스는 쓰기 비용과 함께 본다

인덱스는 조건 검색과 조인을 빠르게 할 수 있지만 저장공간, 삽입·수정·삭제 비용, 유지보수 부담을 늘린다. 후보를 평가할 때 다음을 본다.

- 조건·조인·정렬에 실제로 사용되는 열인가?
- 선택도가 충분한가, 값이 심하게 편향되어 있는가?
- 복합 인덱스의 열 순서가 대표 조건과 맞는가?
- 기존 인덱스와 중복되지 않는가?
- 조회 개선이 쓰기 지연과 공간 증가보다 중요한가?
- 변경 후 통계와 실행 계획이 의도대로 갱신되는가?

인덱스를 추가한 뒤에도 같은 측정 세트로 재시험한다. 계획에 인덱스 이름이 보인다는 사실만으로 성공이라 판단하지 않는다. 전체 응답 시간, 읽기량, 처리량과 쓰기 영향이 실제로 개선되었는지 확인한다.

### 2.6 트랜잭션과 잠금 범위를 측정한다

단독 실행이 빠른데 동시 부하에서 느리다면 잠금 경합, 긴 트랜잭션, 교착 재시도, 연결 풀 대기를 확인한다. 사용자 입력이나 외부 API 응답을 기다리는 동안 트랜잭션을 열린 채 유지하면 잠금 시간이 길어진다.

- 트랜잭션 시작과 종료 지점을 기록한다.
- 같은 자원을 갱신하는 경로의 잠금 순서를 비교한다.
- 읽기·쓰기 격리 수준이 요구사항보다 과도하지 않은지 본다.
- 실패 재시도 시 동일 작업이 중복 반영되지 않는지 확인한다.
- 일괄 변경은 한 번에 너무 많은 행을 잠그지 않는지 평가한다.

격리 수준을 낮추면 무조건 빨라진다는 주장도 틀리다. 더티 리드, 비반복 읽기, 팬텀과 같은 현상을 허용할 수 있으므로 정확성 요구와 함께 판단해야 한다.

## 3. 변경 전후 비교를 공정하게 한다

최적화 A와 B를 비교할 때는 다음 조건을 고정한다.

| 고정할 항목 | 이유 |
|---|---|
| 데이터와 통계 | 행 수·분포가 다르면 계획과 작업량이 달라짐 |
| SQL 결과 의미 | 더 적은 행을 잘못 반환해 빨라진 것은 개선이 아님 |
| 매개변수 집합 | 유리한 값 하나만 고르면 편향됨 |
| 서버·설정·부하 | 자원과 동시성 차이를 쿼리 차이로 오해할 수 있음 |
| 측정 도구·구간 | 서로 다른 타이머와 범위를 직접 비교할 수 없음 |
| 반복·요약 방식 | 단일 우연값 대신 분포를 비교해야 함 |

성능 개선률은 같은 단위로 계산한다. 시간이 작을수록 좋은 지표라면 다음처럼 해석할 수 있다.

```text
개선률(%) = (변경 전 시간 - 변경 후 시간) / 변경 전 시간 × 100
```

변경 전 200ms, 변경 후 150ms라면 25% 감소다. “1.33배 빠르다”와 “25% 감소했다”는 기준이 달라 혼동하기 쉬우므로 원자료를 함께 제시한다. 처리량처럼 클수록 좋은 지표에는 같은 공식을 그대로 적용하지 않는다.

## 4. 소스코드 인스펙션의 개념

**소스코드 인스펙션**은 프로그램을 실행하지 않고 코드와 관련 산출물을 체계적으로 검토하여 결함을 찾는 정적 검증 활동이다. 단순히 작성자가 코드를 다시 읽는 것보다 역할, 진입 기준, 체크리스트, 결함 기록, 재작업과 후속 확인이 명확하다.

### 4.1 목적

- 실행 전에 논리·자료형·경계·보안 결함을 조기에 발견한다.
- 코딩 표준과 데이터 접근 규칙 준수를 확인한다.
- 테스트로 드러내기 어려운 예외 누락·자원 해제·권한 문제를 찾는다.
- 팀이 코드와 업무 규칙을 공유한다.
- 반복 결함 유형을 수집해 예방 체크리스트를 개선한다.

인스펙션의 중심은 결함 탐지이며 작성자 평가가 아니다. 회의에서 즉시 모든 해결책을 설계하려 하면 시간이 길어지고 결함 기록이 흐려질 수 있다. 발견과 수정은 분리하고, 수정 결과는 후속 확인한다.

### 4.2 대표 역할

정형 인스펙션에서는 다음 역할을 둘 수 있다. 조직 규모에 따라 한 사람이 일부 역할을 겸할 수 있지만 책임은 구분한다.

| 역할 | 책임 |
|---|---|
| 작성자(author) | 검토 대상과 배경 설명, 결함 수정 |
| 진행자·중재자(moderator) | 범위·진입 기준·일정 관리, 회의 통제 |
| 낭독자(reader) | 코드 흐름을 논리 단위로 설명하여 검토를 이끔 |
| 기록자(recorder) | 위치, 유형, 심각도, 조치 상태 기록 |
| 검토자(inspector) | 사전 준비와 체크리스트로 결함 탐색 |

작성자가 진행을 독점하면 방어적으로 설명하거나 중요한 의문이 지나갈 수 있다. 진행자는 사람에 대한 비난을 막고 코드와 요구사항에 집중시킨다.

### 4.3 절차

1. **계획**: 대상 규모, 목표, 참여자, 체크리스트, 진입 기준을 정한다.
2. **개요 설명**: 작성자가 업무 배경, 인터페이스, 위험 구간을 공유한다.
3. **개별 준비**: 각 검토자가 코드를 읽고 결함 후보를 기록한다.
4. **인스펙션 회의**: 논리 흐름을 따라 결함을 확인·분류·기록한다.
5. **재작업**: 작성자가 합의된 결함을 수정한다.
6. **후속 조치**: 진행자가 수정과 재검증 결과를 확인해 종료 여부를 결정한다.

진입 기준에는 코드 빌드 성공, 관련 요구사항·설계·테스트 존재, 검토 가능한 크기 등이 포함될 수 있다. 너무 큰 변경을 한 번에 검토하면 집중력이 떨어지고 중요한 결함을 놓친다.

## 5. 데이터 조작 코드 인스펙션 체크리스트

### 5.1 정확성과 경계

- SQL의 대상 테이블·열·조인 키가 요구사항과 같은가?
- `NULL`과 빈 문자열, 0을 혼동하지 않는가?
- 날짜·시간대·경계 포함 여부가 명확한가?
- `UPDATE`·`DELETE` 조건이 대상 행을 충분히 제한하는가?
- 영향 행 수 0건·복수 건을 올바르게 처리하는가?
- 정렬 없는 “첫 행”에 업무 의미를 부여하지 않는가?

### 5.2 보안과 권한

- 외부 입력을 SQL 문자열에 직접 연결하지 않는가?
- 매개변수 바인딩과 허용 목록 검증을 사용하는가?
- DB 계정과 프로시저에 최소 권한을 부여했는가?
- 로그와 오류 메시지에 개인정보·비밀값이 노출되지 않는가?
- 동적 식별자(열·정렬 방향)를 매개변수처럼 처리할 수 없을 때 허용 목록을 쓰는가?

### 5.3 트랜잭션과 자원

- 커밋·롤백 책임이 호출자와 충돌하지 않는가?
- 예외 경로에서도 연결, 커서, 파일 등의 자원이 정리되는가?
- 반복문 안에서 불필요한 개별 쿼리를 호출하지 않는가?
- 긴 계산이나 외부 대기 동안 잠금을 유지하지 않는가?
- 재시도 시 중복 삽입·중복 지급이 발생하지 않는가?

### 5.4 성능과 관찰 가능성

- 필요한 열과 행만 조회하는가?
- 동일 데이터를 반복 조회하지 않는가?
- 실제 매개변수와 데이터 분포로 기준선을 측정했는가?
- 실행 계획의 예상 행과 실제 행 차이를 확인했는가?
- 오류·지연을 요청 ID와 안전한 지표로 추적할 수 있는가?

체크리스트는 기계적으로 “예/아니오”만 표시하는 문서가 아니다. 프로젝트에서 실제 발생한 결함 유형을 반영해 계속 다듬어야 한다.

## 6. 워크스루·동료 검토·인스펙션 구분

| 검토 방식 | 일반적 특징 | 중심 목적 |
|---|---|---|
| 자기 검토 | 작성자가 제출 전 스스로 확인 | 빠른 기본 결함 제거 |
| 동료 코드 리뷰 | 변경 제안과 토론, 비동기 도구 활용 가능 | 품질·지식 공유·변경 승인 |
| 워크스루 | 작성자가 흐름을 설명하며 의견 수렴 | 이해 공유와 결함 발견 |
| 정형 인스펙션 | 역할·절차·체크리스트·기록·후속 확인이 명확 | 체계적 결함 탐지와 예방 데이터 수집 |

모든 조직이 가장 정형적인 인스펙션을 모든 줄에 적용할 필요는 없다. 결제, 권한, 대량 데이터 변경처럼 위험도가 높은 코드에는 엄격한 절차를, 작은 저위험 변경에는 간결한 리뷰를 적용할 수 있다. 중요한 것은 위험도에 맞는 검증 강도와 추적 가능성이다.

## 7. 측정과 인스펙션을 결합한 최적화 흐름

1. 느린 업무와 목표 지표를 정의한다.
2. 대표 입력·데이터·동시성에서 기준선을 측정한다.
3. 실행 계획과 계층별 시간을 보고 병목 후보를 세운다.
4. 소스코드 인스펙션으로 반복 호출, 잘못된 조건, 트랜잭션·권한·예외 문제를 찾는다.
5. 결과 의미를 유지하는 최소 변경을 선택한다.
6. 단위·통합 테스트로 정확성을 확인한다.
7. 같은 조건과 지표로 재측정한다.
8. 쓰기 성능, 동시성, 다른 쿼리와 운영 영향까지 회귀 확인한다.
9. 측정값, 계획, 변경 이유, 검토 결함과 후속 조치를 기록한다.

측정 없이 인스펙션만 하면 실제 병목이 아닌 코드를 다듬을 수 있고, 인스펙션 없이 수치만 보면 빠르지만 위험한 동적 SQL이나 잘못된 결과를 놓칠 수 있다. 두 활동은 서로 대체하지 않는다.

## 8. 시험 함정

- 실행 계획의 비용을 실제 밀리초로 단정한다.
- 전체 스캔은 언제나 나쁘고 인덱스 접근은 언제나 좋다고 판단한다.
- 평균 응답 시간만 보고 느린 상위 요청과 변동성을 무시한다.
- 반환 행 수가 달라졌는데 변경 전후 시간을 직접 비교한다.
- 측정할 때마다 데이터·캐시·매개변수·부하가 달라진다.
- 인덱스 추가의 쓰기·공간·유지 비용을 보지 않는다.
- 단독 실행 결과만으로 동시 사용자 환경을 보장한다.
- 인스펙션 회의를 작성자 비판이나 즉석 해결책 회의로 운영한다.
- 재작업 후 후속 확인 없이 결함을 종료 처리한다.
- 코드가 빨라졌다는 이유로 결과 정확성·권한·트랜잭션 회귀를 생략한다.

## 9. 확인 문제

### 문제 1

쿼리 변경 전 200ms, 변경 후 150ms로 같은 조건에서 측정되었다. 응답 시간 감소율은 얼마인가?

### 문제 2

실행 계획에 전체 테이블 스캔이 보이면 즉시 인덱스를 추가해야 한다는 주장이 틀린 이유를 두 가지 적어라.

### 문제 3

인스펙션에서 결함을 기록하고 수정안을 긴 토론으로 확정하느라 다른 코드 검토를 끝내지 못했다. 절차상 무엇을 개선해야 하는가?

### 문제 4

개선 쿼리가 변경 전보다 두 배 빠르지만 결과 행이 10% 누락되었다. 이를 성공적인 최적화로 볼 수 없는 이유는 무엇인가?

### 문제 5

다음 중 공정한 쿼리 성능 비교에 가장 부적절한 것은 무엇인가?

1. 같은 데이터와 매개변수 집합을 사용한다.
2. 여러 번 실행해 분포를 기록한다.
3. 변경 후에는 결과 행을 줄이되 정확성 비교는 생략한다.
4. 응답 시간과 읽기량·잠금 같은 원인 지표를 함께 본다.

## 정답과 해설

1. **정답: 25%.** `(200-150)/200×100=25`이다. 변경 후 시간이 변경 전의 75%가 되었다.
2. **정답 예:** 대부분의 행을 읽거나 테이블이 작으면 전체 스캔이 더 효율적일 수 있다. 또한 인덱스는 쓰기·공간 비용을 만들며 실제 데이터 분포와 측정 결과 없이 효과를 보장할 수 없다.
3. **정답:** 인스펙션 회의는 결함 발견·분류·기록에 집중하고 상세 해결과 수정은 재작업 단계로 분리한다. 진행자가 시간과 범위를 통제해야 한다.
4. **정답:** 최적화는 동일한 업무 결과와 정확성을 유지해야 한다. 누락으로 작업량만 줄어 빨라진 것은 요구사항 위반이지 개선이 아니다.
5. **정답: 3번.** 결과 의미와 행 수가 다르면 같은 작업의 성능을 비교한 것이 아니다. 정확성 검증이 성능 측정보다 먼저다.

## 10. 최종 요약

- **쿼리(Query) 성능 측정**은 문제·목표 정의 → 대표 조건과 기준선 확보 → 응답 시간·처리량·자원·잠금·실행 계획 수집 → 가설 기반 변경 → 동일 조건 재측정 순으로 진행한다.
- 실행 계획 비용은 상대 추정치일 수 있으며, 전체 스캔이나 인덱스 접근을 이름만으로 좋고 나쁘다고 판단하지 않는다.
- 인덱스, 결과 축소, 호출 횟수, 조인, 트랜잭션을 변경할 때 정확성·쓰기 비용·동시성 영향을 함께 검증한다.
- **소스코드 인스펙션**은 실행 없이 역할, 체크리스트, 결함 기록, 재작업, 후속 확인을 통해 코드를 체계적으로 검토하는 정적 활동이다.
- 데이터 조작 코드는 조건·NULL·영향 행 수, SQL 주입·최소 권한, 커밋·롤백, 반복 쿼리, 자원 정리와 관찰 가능성을 중점 확인한다.
- 측정은 실제 병목을 찾고, 인스펙션은 숫자만으로 놓치기 쉬운 정확성·보안·유지보수 결함을 찾는다. 두 결과를 결합해야 안전한 데이터 조작 프로시저 최적화가 된다.
