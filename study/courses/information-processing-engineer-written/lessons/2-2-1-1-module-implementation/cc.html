01

0. 모듈 구현의 목표

모듈은 시스템의 특정 책임을 수행하도록 논리적으로 구분한 프로그램 단위다. 함수, 클래스, 라이브러리, 서비스처럼 구현 형태는 다양하지만 핵심은 명확한 책임과 인터페이스를 가지며 다른 부분과 약속에 따라 협력한다는 점이다. 모듈 구현은 코드를 작성하는 데서 끝나지 않는다. 명세에 맞게 동작하고, 독립적으로 확인할 수 있으며, 이후 통합에서 예측 가능한 결과를 제공해야 한다.

이 레슨은 두 주제를 연결한다.

  1. 단위모듈 구현: 상세 명세와 인터페이스 계약에 맞춰 한 책임 단위를 코드로 구현한다.
  2. 단위모듈 테스트: 해당 단위를 가능한 한 격리해 정상·경계·예외 동작을 검증한다.

여러 모듈 사이의 본격적인 통합 시험이나 전체 시스템 시험은 인접한 테스트 영역에서 다룬다. 여기서는 한 단위의 구현 품질과 빠른 피드백에 집중한다.

02

1. 단위모듈 구현

1.1 구현 전에 계약을 확인한다

모듈의 입·출력과 책임이 모호한 상태에서 코딩을 시작하면 내부 구현보다 경계에서 결함이 많이 발생한다. 다음을 먼저 확인한다.

1. 단위모듈 구현 · 학습 표 1
계약 항목확인 질문예시
목적·책임이 모듈이 반드시 해야 할 한 가지 핵심 역할은?할인금액 계산
입력형식, 단위, 필수값, 허용 범위는?금액은 0 이상의 정수
출력결과 형식과 의미는?최종금액과 적용 할인액
선행조건호출 전 만족해야 할 조건은?인증된 요청, 유효한 정책
후행조건정상 종료 뒤 보장할 상태는?최종금액은 0 미만이 아님
오류 계약잘못된 입력·의존 실패를 어떻게 알리는가?정의된 오류 유형·결과코드
부수효과상태·파일·외부 시스템을 바꾸는가?사용 이력 저장
품질 제약성능·보안·동시성 요구는?민감값을 로그에 기록하지 않음

호출자와 구현자가 같은 용어를 사용해야 한다. “금액”이 세전인지 세후인지, “날짜”가 어느 시간대를 기준으로 하는지처럼 형식만으로 드러나지 않는 의미를 문서화한다.

1.2 책임을 작게 유지한다

한 모듈이 입력 검증, 업무 계산, 데이터 저장, 외부 통신, 화면 문구까지 모두 담당하면 변경 이유가 많아지고 독립 시험이 어려워진다. 다음 원칙으로 책임을 조정한다.

  • 함께 변하는 규칙은 가깝게 둔다.
  • 서로 다른 변경 이유와 외부 의존은 경계를 분리한다.
  • 외부 자원 접근은 인터페이스 뒤에 감춰 대체 가능하게 한다.
  • 모듈이 필요한 최소 정보만 전달하고 내부 표현을 노출하지 않는다.
  • 공개 인터페이스는 작고 명확하게 유지한다.

모듈을 무조건 잘게 나누는 것도 정답은 아니다. 지나친 분해는 호출과 추적을 복잡하게 한다. 업무 책임, 변경 단위, 재사용, 시험 가능성과 실행 비용을 함께 고려한다.

1.3 구현 절차

  1. 상세 명세 검토: 기능, 데이터, 인터페이스, 예외, 품질 요구를 확인한다.
  2. 내부 구조 설계: 책임을 함수·클래스 등으로 나누고 의존 방향을 정한다.
  3. 입력·출력 모델 정의: 타입, 범위, 단위, 불변조건을 명시한다.
  4. 정상 흐름 구현: 가장 일반적인 업무 규칙을 작은 단계로 작성한다.
  5. 경계·예외 처리: 빈 값, 한계값, 중복, 의존 실패, 재시도 가능성을 다룬다.
  6. 관찰 가능성 확보: 진단에 필요한 로그·상태를 남기되 민감정보는 보호한다.
  7. 코드 검토와 정적 점검: 명명, 복잡도, 중복, 오류 처리와 보안 규칙을 확인한다.
  8. 단위 시험 실행: 계약과 주요 분기, 오류 동작을 자동 또는 반복 가능한 방식으로 검증한다.
  9. 산출물 연결: 요구·설계 ID, 소스, 시험과 변경 이력을 추적한다.

1.4 구현 예시

다음은 주문금액에서 등급 할인을 계산하는 단순한 Python 예다. 예시의 목적은 언어 기능보다 계약과 시험 가능한 경계를 보여 주는 것이다.

코드 예시 · python

from dataclasses import dataclass

@dataclass(frozen=True)
class PriceResult:
    original: int
    discount: int
    final: int


def calculate_price(amount: int, grade: str) -> PriceResult:
    """0원 이상의 정수 금액과 등급을 받아 최종금액을 계산한다."""
    if not isinstance(amount, int) or amount < 0:
        raise ValueError("amount must be a non-negative integer")

    rates = {"BASIC": 0, "SILVER": 5, "GOLD": 10}
    if grade not in rates:
        raise ValueError("unsupported grade")

    discount = amount * rates[grade] // 100
    return PriceResult(amount, discount, amount - discount)

이 구현의 계약은 다음과 같다.

  • 금액은 0 이상의 정수이며 소수 처리 규칙은 범위 밖이다.
  • 지원 등급은 세 종류로 제한한다.
  • 할인은 정수 연산으로 계산하고 결과는 원금, 할인액, 최종금액을 함께 반환한다.
  • 입력 객체를 변경하지 않고 불변 결과를 만든다.

실제 시스템에서는 세금, 통화, 반올림, 정책 유효기간 등이 추가될 수 있다. 명세에 없는 규칙을 임의로 추측해 구현하지 않고 담당자에게 확인한다.

1.5 오류 처리와 로그

오류를 모두 잡아 정상값처럼 반환하면 호출자는 실패를 알기 어렵고 데이터가 오염될 수 있다. 반대로 내부 예외를 그대로 외부에 노출하면 구현정보와 민감값이 유출될 수 있다. 모듈 경계에서 다음을 정한다.

  • 호출자가 복구할 수 있는 오류와 시스템 오류를 구분한다.
  • 오류 유형·코드·메시지는 인터페이스 계약에 맞춘다.
  • 한 번 기록된 오류를 여러 계층에서 중복 기록하지 않도록 책임을 정한다.
  • 로그에는 추적 ID, 시각, 작업, 결과처럼 진단에 필요한 정보를 남긴다.
  • 비밀번호, 인증키, 전체 개인정보와 결제정보를 기록하지 않는다.
  • 실패 시 일부 상태만 반영되지 않도록 원자성 또는 보상 절차를 고려한다.

2. 단위모듈 테스트

2.1 목적과 특징

단위모듈 테스트는 구현한 가장 작은 실용적 단위를 다른 부분과 가능한 한 분리하여 확인한다. 목적은 결함을 일찍 찾고, 요구된 동작을 문서화하며, 이후 변경이 기존 기능을 깨뜨렸는지 빠르게 알려 주는 것이다.

좋은 단위 시험은 다음 특성을 가진다.

  • 반복 가능: 같은 조건에서 같은 결과를 낸다.
  • 독립적: 실행 순서와 다른 시험의 상태에 의존하지 않는다.
  • 빠름: 개발 중 자주 실행할 수 있다.
  • 명확함: 실패 이유와 검증하려는 동작을 이해할 수 있다.
  • 격리됨: 외부 데이터베이스·네트워크·시간 같은 불안정한 의존을 통제한다.
  • 자동 판정: 사람이 출력을 눈으로 비교하지 않아도 성공·실패를 판단한다.

2.2 Arrange–Act–Assert 구조

단위 시험을 준비–실행–검증의 세 단계로 정리하면 의도가 분명해진다.

코드 예시 · python

def test_gold_customer_gets_ten_percent_discount():
    # Arrange: 입력과 기대값 준비
    amount = 10_000

    # Act: 시험 대상 실행
    result = calculate_price(amount, "GOLD")

    # Assert: 계약된 결과 확인
    assert result.discount == 1_000
    assert result.final == 9_000

한 시험에서 너무 많은 시나리오를 반복하면 어느 조건이 실패했는지 찾기 어렵다. 공통 준비 코드는 재사용할 수 있지만 시험의 의도는 한눈에 읽히게 한다.

2.3 정상·경계·예외를 나눈다

앞의 모듈에는 다음 시험이 필요하다.

코드 예시 · python

import pytest

def test_zero_amount_is_allowed():
    assert calculate_price(0, "SILVER").final == 0

def test_basic_customer_has_no_discount():
    assert calculate_price(5_000, "BASIC").discount == 0

def test_negative_amount_is_rejected():
    with pytest.raises(ValueError):
        calculate_price(-1, "GOLD")

def test_unknown_grade_is_rejected():
    with pytest.raises(ValueError):
        calculate_price(5_000, "VIP")

시험 데이터는 정상 대표값뿐 아니라 0, 최소·최대 경계, 경계 바로 안팎, 빈 값, 잘못된 타입과 지원하지 않는 상태를 포함한다. 다만 가능한 모든 입력을 시험할 수는 없으므로 위험과 동등한 동작을 기준으로 대표값을 선택한다.

2.4 스텁·목·드라이버의 역할

시험 대상이 다른 모듈을 호출하면 의존 대역(test double)을 사용할 수 있다.

  • 스텁(stub): 시험에 필요한 정해진 응답을 돌려주는 대체물
  • 목(mock): 호출 횟수·순서·인자 같은 상호작용 기대까지 검증하는 대체물
  • 페이크(fake): 실제와 유사하지만 단순화된 동작을 하는 구현, 예: 메모리 저장소
  • 드라이버(driver): 상위 호출자가 준비되지 않았을 때 시험 대상을 호출하는 역할

스텁은 보통 하위 모듈을 대체하고, 드라이버는 상위 모듈의 호출 역할을 대신한다고 이해할 수 있다. 도구에 따라 용어와 기능 경계가 다를 수 있으므로 이름보다 대체 목적을 본다.

대역을 너무 많이 사용하면 실제 협력과 다른 시험이 될 수 있다. 순수 계산은 직접 시험하고, 느리거나 비결정적이거나 아직 구현되지 않은 외부 경계에 대역을 집중한다.

2.5 커버리지와 품질 판단

문장·분기·조건 커버리지는 어떤 코드가 실행되었는지 보여 주지만 정답을 올바르게 검증했는지는 알려 주지 않는다. 100% 문장 커버리지라도 잘못된 기대값, 누락된 경계, 잘못된 요구를 발견하지 못할 수 있다.

시험 품질은 다음을 함께 본다.

  • 중요 업무 규칙과 실패 경로가 포함됐는가?
  • 요구·설계와 시험이 추적되는가?
  • 경계와 예외가 적절히 선택됐는가?
  • 실패 시 원인을 빠르게 알 수 있는가?
  • 변경된 코드와 위험에 비례해 회귀시험이 보완됐는가?
04

3. 구현과 단위 시험의 반복

구현을 모두 끝낸 뒤 시험을 몰아서 작성하면 시험하기 어려운 구조를 늦게 발견한다. 작은 계약을 정하고 구현·시험·개선을 반복한다.

코드 예시 · text

작은 동작과 계약 선택
→ 시험 또는 예시로 기대 결과 명확화
→ 최소 구현
→ 시험 실행
→ 중복·복잡도 개선
→ 전체 단위 회귀시험

시험 주도 개발을 사용하지 않더라도 구현과 단위 시험을 가까운 시간에 수행하면 결함 원인 범위가 작고 피드백이 빠르다.

05

4. 비교와 경계

4. 비교와 경계 · 학습 표 2
구분단위모듈 테스트통합·시스템 수준 확인
중심한 모듈의 계약과 내부 분기모듈 간 연결 또는 전체 요구
의존대역으로 격리 가능실제 인터페이스·환경 비중 증가
속도대체로 빠르고 자주 실행상대적으로 준비·실행 비용 큼
결함 위치실패 원인이 비교적 좁음여러 구성요소의 상호작용 가능

단위 시험이 많아도 모듈 간 데이터 형식이나 실제 환경 설정 결함은 남는다. 각 시험 수준은 서로 대체하는 것이 아니라 다른 위험을 보완한다.

06

5. 시험 함정

  1. 모듈을 파일과 동일시: 모듈은 책임과 인터페이스로 구분되는 논리 단위이며 물리 형태는 다양하다.
  2. 작을수록 무조건 좋은 모듈: 지나친 분해는 호출과 이해 비용을 늘릴 수 있다.
  3. 명세 없는 예외를 임의 처리: 오류 계약과 업무 규칙을 먼저 확인한다.
  4. 모든 예외를 삼킴: 실패를 정상 결과처럼 숨기면 호출자가 복구·기록할 수 없다.
  5. 단위 시험이 실제 외부 자원에 의존: 느리고 비결정적이 되어 반복성이 낮아진다.
  6. 스텁과 드라이버 혼동: 스텁은 호출되는 하위 역할, 드라이버는 호출하는 상위 역할을 주로 대신한다.
  7. 커버리지 100%면 무결함: 실행 여부와 요구 검증의 정확성은 다르다.
  8. 시험 간 상태 공유: 실행 순서에 따라 결과가 달라져 결함 재현이 어려워진다.
  9. 단위 시험이 모든 시험을 대체: 실제 연계·환경·전체 업무 흐름은 다른 수준에서 확인한다.
07

6. 확인 문제

문제 1

단위모듈 구현 전에 입력·출력뿐 아니라 오류 계약을 확인해야 하는 이유는?

정답과 해설: 호출자가 실패를 구분하고 복구·기록할 수 있는 일관된 방법이 필요하기 때문이다. 내부 예외를 무조건 숨기거나 그대로 노출하는 문제도 줄인다.

문제 2

시험 대상이 아직 구현되지 않은 하위 모듈을 호출한다. 정해진 응답을 반환하도록 대체할 수 있는 것은?

정답과 해설: 스텁이다. 호출되는 하위 모듈을 대신해 시험에 필요한 응답을 제공한다.

문제 3

문장 커버리지가 100%이면 모든 요구사항을 올바르게 검증했다고 볼 수 있는가?

정답과 해설: 아니다. 모든 문장이 실행되었다는 뜻일 뿐 기대 결과, 경계값, 누락 요구와 업무 정확성을 보장하지 않는다.

문제 4

단위 시험이 실행 순서에 따라 성공하거나 실패한다면 어떤 특성이 부족한가?

정답과 해설: 독립성과 반복 가능성이 부족하다. 시험이 공유 상태를 정리하지 않거나 다른 시험의 결과에 의존하는지 확인한다.

문제 5

외부 저장소를 모두 목으로 대체한 시험만 통과하면 실제 연계도 정상이라고 결론 내릴 수 있는가?

정답과 해설: 없다. 단위 계약은 확인했지만 실제 데이터 형식, 연결, 권한과 환경 문제는 통합 수준에서 별도로 검증해야 한다.

08

7. 최종 요약

  • 단위모듈 구현은 한 책임과 명확한 인터페이스 계약을 기준으로 입력·출력·선행·후행조건·오류·품질 제약을 코드로 실현한다.
  • 책임, 변경 이유와 외부 의존을 고려해 모듈 경계를 정하고 지나친 결합이나 분해를 피한다.
  • 오류는 호출자가 처리할 수 있게 계약화하고 로그에는 진단정보를 남기되 민감정보를 보호한다.
  • 단위모듈 테스트는 한 단위를 격리해 정상·경계·예외 동작을 빠르고 반복 가능하게 검증한다.
  • Arrange–Act–Assert 구조와 스텁·목·페이크·드라이버를 목적에 맞게 사용한다.
  • 커버리지는 보조 지표일 뿐 요구 충족과 결함 부재를 보장하지 않는다.
  • 단위 시험은 통합·시스템 시험을 대체하지 않으며 구현과 가까운 주기로 반복해 빠른 피드백을 얻는다.
