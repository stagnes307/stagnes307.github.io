# 2-3-1-1. 애플리케이션 패키징 · 애플리케이션 배포 도구

> **공식 범위**: 소프트웨어개발 > 제품소프트웨어 패키징 > 제품소프트웨어 패키징 > `애플리케이션 패키징`, `애플리케이션 배포 도구`

## 0. 실행 가능한 제품으로 전달하기

소스 코드가 완성되었다고 사용자가 설치·운영할 수 있는 제품이 된 것은 아니다. 실행 파일, 라이브러리, 설정 템플릿, 정적 자원, 데이터 변경, 라이선스와 버전 정보 등을 일관된 단위로 묶고, 목표 환경에 안전하게 전달·설치·검증·복구할 수 있어야 한다.

이 레슨에서는 다음을 다룬다.

1. `애플리케이션 패키징`: 검증된 구성요소를 식별 가능한 배포 단위와 부속 정보로 묶는다.
2. `애플리케이션 배포 도구`: 패키지를 목표 환경에 전달하고 설치·설정·기동·검증·복구하는 과정을 지원·자동화한다.

모니터링 도구와 DRM은 다음 레슨, 상세 버전관리와 빌드 자동화는 별도 레슨의 범위다. 여기서는 패키지의 완전성·재현성·무결성과 배포의 안전성에 집중한다.

## 1. 애플리케이션 패키징

### 1.1 패키지의 의미

애플리케이션 패키지는 특정 버전의 제품을 설치하거나 실행하는 데 필요한 산출물을 정의된 구조와 형식으로 묶은 배포 단위다. 제품 형태에 따라 압축 파일, 설치 프로그램, 라이브러리 패키지, 컨테이너 이미지, 모바일 패키지 등이 될 수 있다.

중요한 것은 확장자가 아니라 다음 질문에 답할 수 있는가이다.

- 어떤 소스 버전과 빌드로 만들었는가?
- 어떤 파일·의존성·설정이 포함되었는가?
- 어느 환경과 플랫폼에서 실행 가능한가?
- 누가 언제 어떤 절차로 생성·검증했는가?
- 전송 중 변조·손상을 어떻게 확인하는가?
- 설치·업그레이드·제거·복구 방법은 무엇인가?

### 1.2 패키지 구성 요소

| 구성 | 내용 | 주의점 |
|---|---|---|
| 실행 산출물 | 실행 파일, 라이브러리, 정적 자원 | 소스가 아닌 검증된 빌드 결과 사용 |
| 메타데이터 | 이름, 버전, 빌드 ID, 생성시각 | 제품·소스·배포를 추적 가능하게 함 |
| 의존성 정보 | 필요한 런타임·라이브러리·서비스 | 버전 범위와 충돌 조건 명시 |
| 설정 템플릿 | 환경별로 채울 설정의 구조·기본값 | 비밀값은 포함하지 않음 |
| 데이터 변경 | 스키마·초기 데이터 변경 절차 | 순서, 반복 실행, 복구 고려 |
| 설치·제거 정보 | 경로, 권한, 서비스 등록과 정리 | 기존 사용자 데이터 보존 기준 |
| 문서·고지 | 사용권, 변경사항, 알려진 제한 | 배포 대상과 버전에 일치 |
| 무결성 정보 | 체크섬·서명 등 검증 정보 | 생성·검증 주체와 키 보호 |

환경별 비밀번호·인증키를 패키지에 넣으면 유출 위험이 있고 동일 산출물을 여러 환경에 승격하기 어렵다. 패키지는 가능한 한 환경 중립적으로 만들고 비밀과 환경값은 배포 시 승인된 관리체계에서 주입한다.

### 1.3 패키징 절차

1. **대상과 버전 확정**: 승인된 소스 기준선, 의존성과 목표 플랫폼을 정한다.
2. **깨끗한 환경에서 빌드**: 개인 작업공간의 우연한 파일이 섞이지 않게 한다.
3. **시험·품질 점검**: 단위 시험, 정적 점검, 필요한 보안·라이선스 확인을 통과한다.
4. **필수 산출물 수집**: 실행물, 설정 템플릿, 데이터 변경, 문서와 메타데이터를 모은다.
5. **불필요·민감 항목 제외**: 개발 로그, 임시 파일, 시험 계정, 비밀, 개인 경로를 제거한다.
6. **패키지 생성**: 정의된 구조와 명명 규칙으로 한 번만 생성한다.
7. **무결성·출처 기록**: 체크섬, 서명, 빌드 정보와 소스 버전을 연결한다.
8. **설치 시험**: 깨끗한 대표 환경에서 설치·업그레이드·제거·복구를 검증한다.
9. **보관·승격**: 변경 불가능한 산출물 저장소에 보관하고 같은 패키지를 단계별 환경으로 승격한다.

개발·시험·운영 환경마다 다시 빌드하면 서로 다른 바이너리가 되어 시험한 것과 운영한 것이 달라질 수 있다. 한 번 검증한 불변 패키지를 동일하게 승격하고 설정만 환경에 맞게 적용하는 흐름이 추적에 유리하다.

### 1.4 재현 가능성과 무결성

재현 가능한 패키징은 같은 소스·의존성·도구·설정으로 같은 의미의 산출물을 다시 만들 수 있는 능력이다. 생성시각, 파일 순서 등 비기능 메타데이터 때문에 바이트가 달라질 수 있으므로 조직이 요구하는 재현 수준을 정의한다.

체크섬은 전송 중 우연한 손상이나 값의 차이를 탐지하는 데 유용하지만, 공격자가 파일과 체크섬을 모두 바꿀 수 있는 환경에서는 출처를 보장하지 못한다. 신뢰된 서명과 키 관리, 저장소 권한, 전송보호를 함께 사용한다.

소프트웨어 구성요소 명세(SBOM)는 포함된 구성요소와 의존성의 식별을 도와 취약점·라이선스 영향 분석에 활용할 수 있다. 구체 형식은 조직과 도구에 따라 달라질 수 있으며 정확한 생성과 갱신 절차가 필요하다.

## 2. 애플리케이션 배포 도구

### 2.1 배포의 의미와 도구 역할

배포는 패키지를 목표 환경에 전달하고 실행 가능한 상태로 전환하는 일련의 활동이다. `애플리케이션 배포 도구`는 다음을 자동화하거나 통제한다.

- 산출물 저장소에서 승인된 패키지 선택
- 대상 환경과 노드 식별, 권한 확인
- 파일 전송과 무결성 검증
- 환경 설정·비밀값 주입
- 설치, 데이터 변경, 서비스 시작·중지
- 배포 전후 상태 점검과 스모크 테스트
- 단계적 전개, 진행 상태, 로그와 감사 기록
- 실패 시 중단·재시도·이전 버전 복구

자동화 도구를 사용해도 승인, 역할 분리, 변경 창구와 책임이 필요하다. 빠르게 실행되는 잘못된 자동화는 수동 오류보다 더 넓은 피해를 만들 수 있다.

### 2.2 배포 파이프라인의 단계

```text
승인된 패키지 선택
→ 대상·권한·사전조건 확인
→ 무결성·정책 검증
→ 단계적 설치·설정
→ 데이터 변경
→ 서비스 기동
→ 상태 점검·스모크 테스트
→ 트래픽 전환 또는 배포 확정
→ 결과·버전·로그 기록
```

각 단계는 입력, 성공조건, 시간제한, 실패 처리와 재실행 가능성을 가져야 한다. 중간 실패 후 처음부터 다시 실행할 때 동일 작업이 중복 적용되지 않도록 멱등성을 고려한다.

### 2.3 대표 배포 방식

| 방식 | 개념 | 장점 | 주의점 |
|---|---|---|---|
| 일괄 교체 | 기존 버전을 중지하고 새 버전으로 교체 | 단순한 절차 | 서비스 중단 가능성 |
| 롤링 | 일부 인스턴스씩 순차 교체 | 전체 중단 감소 | 구·신 버전 공존 호환성 |
| 블루-그린 | 두 환경 중 새 환경 검증 후 트래픽 전환 | 빠른 전환·복구 | 자원 비용, 데이터 호환 |
| 카나리 | 일부 사용자·트래픽에 먼저 새 버전 적용 | 실제 위험을 제한해 관찰 | 대상 선정·지표·복잡한 라우팅 |

명칭만으로 무중단이 보장되지 않는다. 상태 저장 방식, 데이터 스키마 호환성, 외부 시스템, 세션, 캐시와 트래픽 전환 능력을 확인해야 한다.

### 2.4 데이터 변경과 호환성

응용 코드와 데이터 구조가 동시에 바뀌면 복구가 어려워질 수 있다. 배포 중 구·신 버전이 함께 동작할 가능성이 있다면 양쪽이 같은 데이터 구조를 안전하게 사용할 수 있도록 단계적 변경을 고려한다.

예를 들어 새 필드를 먼저 추가하고 기존 버전이 무시할 수 있게 한 뒤, 새 코드가 값을 쓰도록 전개하고, 데이터 보완이 끝난 후 오래된 필드를 제거하는 방식이 있을 수 있다. 실제 절차는 DBMS와 업무 제약에 따라 달라지므로 사전 시험과 복구 계획을 세운다.

데이터 변경 스크립트는 실행 버전, 순서, 완료 여부, 반복 실행 결과와 복구 가능성을 관리한다. 대규모 변경은 잠금과 처리시간, 백업·복구 목표에 미치는 영향도 확인한다.

### 2.5 배포 검증과 복구

배포가 “명령 성공”으로 끝나서는 안 된다.

- 올바른 버전과 체크섬이 대상에 설치됐는가?
- 프로세스가 실행 중일 뿐 아니라 핵심 의존과 연결되는가?
- 대표 사용자 흐름의 스모크 테스트가 성공하는가?
- 오류율·응답시간·자원사용이 허용 범위인가?
- 데이터 변경이 예상 건수와 상태로 완료됐는가?
- 감사 로그에 대상, 실행자, 승인, 시작·종료와 결과가 남았는가?

롤백은 이전 파일을 복사하는 것보다 넓다. 데이터 변경, 메시지, 외부 부수효과와 사용자 요청을 되돌릴 수 있는지 확인해야 한다. 완전한 되돌리기가 불가능하면 앞으로 수정(roll forward), 기능 비활성화, 데이터 복구 등 대안을 준비한다.

## 3. 패키징·빌드·배포·릴리스 구분

| 활동 | 핵심 질문 | 결과 |
|---|---|---|
| 빌드 | 소스를 실행 산출물로 어떻게 변환할까? | 컴파일 결과·실행물 |
| 패키징 | 실행·설치에 필요한 것을 어떻게 묶을까? | 식별 가능한 불변 패키지 |
| 배포 | 패키지를 환경에 어떻게 설치·기동할까? | 실행 가능한 환경 상태 |
| 릴리스 | 어느 버전을 누구에게 언제 제공할까? | 승인된 사용자 제공·공지 |

배포되었지만 기능을 아직 사용자에게 노출하지 않을 수 있고, 릴리스 승인 뒤 배포가 실행될 수도 있다. 조직 절차에 따라 순서는 달라질 수 있으므로 용어 정의를 합의한다.

## 4. 예시: 주문 서비스 배포

패키지에는 주문 서비스 실행물, 설정 스키마, 데이터 변경 스크립트, 버전·빌드 메타데이터, 사용권 고지와 체크섬을 포함한다. 운영 비밀번호와 실제 접속주소는 넣지 않는다.

배포 도구는 다음을 수행한다.

1. 승인된 `order-service` 버전의 무결성을 확인한다.
2. 카나리 대상 일부에 패키지를 설치하고 환경 설정을 주입한다.
3. 서비스 상태, 주문 조회·접수 스모크 테스트와 오류율을 확인한다.
4. 기준을 충족하면 롤링 방식으로 대상을 확대한다.
5. 오류율이 임계값을 넘으면 자동 확대를 중지하고 승인된 복구 절차를 실행한다.
6. 최종 대상 버전과 결과를 기록한다.

중요한 것은 도구 이름이 아니라 승인된 동일 패키지, 측정 가능한 성공조건, 단계적 노출과 복구 가능성이다.

## 5. 시험 함정

1. **소스 코드 압축을 완전한 패키지로 간주**: 실행물·의존성·설정·메타데이터·설치정보가 필요하다.
2. **환경별 재빌드**: 시험한 산출물과 운영 산출물이 달라져 추적성이 낮아진다.
3. **패키지에 비밀값 포함**: 환경 설정과 비밀은 승인된 방식으로 배포 시 주입한다.
4. **체크섬이 출처까지 보장**: 손상 탐지에는 유용하지만 신뢰된 출처 보장은 서명·권한과 함께 본다.
5. **빌드와 배포 동일시**: 빌드는 소스를 산출물로 변환, 배포는 패키지를 환경에 설치·기동한다.
6. **배포 성공을 프로세스 실행으로만 판단**: 의존 연결, 핵심 기능, 오류·성능과 데이터 상태를 검증한다.
7. **롤링이면 무조건 무중단**: 구·신 버전, 데이터, 세션과 인터페이스 호환이 필요하다.
8. **롤백은 파일 복사**: 데이터와 외부 부수효과가 되돌릴 수 있는지 확인한다.
9. **자동화면 승인 불필요**: 권한·승인·감사와 실패 통제가 여전히 필요하다.

## 6. 확인 문제

### 문제 1

개발·시험·운영 환경마다 같은 소스를 다시 빌드하는 방식의 주요 위험은?

**정답과 해설**: 도구·의존성·설정 차이로 서로 다른 산출물이 만들어져 시험한 것과 운영한 것이 달라질 수 있다. 한 번 만든 불변 패키지를 검증 후 승격하는 편이 추적에 유리하다.

### 문제 2

패키지에 운영 데이터베이스 비밀번호를 포함하면 안 되는 이유는?

**정답과 해설**: 패키지 복제·보관·전송 과정에서 비밀이 노출되고 환경별 재사용이 어려워진다. 비밀은 별도 보호체계에서 권한에 따라 배포 시 주입한다.

### 문제 3

배포 도구가 “완료”를 반환했지만 핵심 외부 연계가 실패한다. 배포 성공인가?

**정답과 해설**: 아니다. 설치 명령 완료뿐 아니라 의존 연결, 핵심 흐름의 스모크 테스트와 운영 지표가 성공조건을 만족해야 한다.

### 문제 4

블루-그린 배포의 장점과 주의점 한 가지씩은?

**정답과 해설**: 새 환경을 미리 검증하고 트래픽을 빠르게 전환·복구할 수 있다. 대신 두 환경의 자원 비용과 데이터·세션 호환성을 관리해야 한다.

### 문제 5

체크섬이 일치하면 신뢰된 개발팀이 만든 패키지라고 확정할 수 있는가?

**정답과 해설**: 체크섬 출처 자체가 신뢰되지 않으면 확정할 수 없다. 신뢰된 서명, 저장소 권한, 키 관리와 배포 경로를 함께 확인한다.

## 7. 최종 요약

- `애플리케이션 패키징`은 실행물, 의존성, 설정 템플릿, 데이터 변경, 문서, 버전과 무결성 정보를 식별 가능한 배포 단위로 묶는다.

- 깨끗한 빌드, 품질검사, 구성 확인, 무결성 기록과 설치·업그레이드·제거 시험이 필요하다.
- `애플리케이션 배포 도구`는 패키지 선택·전송·설치·설정·기동·검증·복구와 감사 기록을 지원한다.
- 롤링, 블루-그린, 카나리는 위험·비용·호환성 조건이 다르며 명칭만으로 무중단을 보장하지 않는다.
- 배포 성공은 올바른 버전뿐 아니라 핵심 기능·의존·데이터·운영 지표로 확인한다.
- 빌드, 패키징, 배포, 릴리스의 목적을 구분하고 데이터와 외부 부수효과를 포함한 복구를 준비한다.
