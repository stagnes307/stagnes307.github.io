# 2-3-3-1. 제품소프트웨어 버전관리

> **공식 범위**: 소프트웨어개발 > 제품소프트웨어 패키징 > 제품소프트웨어 버전관리 > `소프트웨어 버전관리 도구`, `빌드 자동화 도구`

## 0. 같은 소스에서 같은 제품을 만들기

제품소프트웨어의 버전을 관리하려면 “어떤 변경이 들어간 소스인가?”와 “그 소스를 어떤 절차로 산출물로 만들었는가?”에 답할 수 있어야 한다. 소스 이력만 있어도 빌드 방법과 의존성이 불명확하면 제품을 재현하기 어렵고, 자동 빌드만 있어도 입력 버전과 변경 승인이 불명확하면 산출물의 출처를 신뢰하기 어렵다.

이 레슨은 두 주제를 다룬다.

1. `소프트웨어 버전관리 도구`: 소스와 관련 형상항목의 변경 이력, 분기, 병합, 태그와 공동 작업을 관리한다.
2. `빌드 자동화 도구`: 소스·의존성·설정에서 컴파일, 시험, 패키징 등 반복 가능한 빌드 절차를 실행한다.

애플리케이션을 환경에 설치·전개하는 배포 도구는 이전 레슨의 범위다. 여기서는 버전 식별과 빌드 재현성, 실패 피드백에 집중한다.

---

## 1. 소프트웨어 버전관리 도구

### 1.1 버전관리의 목적

버전관리 도구는 파일의 시간순 복사본을 저장하는 것보다 넓은 기능을 제공한다.

- 누가 언제 무엇을 왜 변경했는지 기록한다.
- 특정 시점의 제품 소스를 정확히 복원한다.
- 여러 개발자의 병렬 작업과 병합을 지원한다.
- 결함 수정이 어느 버전에 포함되었는지 추적한다.
- 실험·기능·릴리스 흐름을 분리하고 승인 후 통합한다.
- 기준 버전과 제품 산출물을 연결한다.
- 차이 비교, 코드 리뷰, 자동검사와 감사의 근거를 제공한다.

### 1.2 주요 개념

| 개념 | 의미 | 주의점 |
|---|---|---|
| 저장소 | 버전 이력과 파일을 보관 | 권한·가용성·백업 필요 |
| 작업복사본 | 특정 버전을 꺼내 수정하는 공간 | 생성 파일·비밀 혼입 방지 |
| 커밋 | 논리적 변경 단위와 설명을 기록 | 한 목적, 추적 ID, 시험 가능 |
| 브랜치 | 독립적인 변경 계열 | 장기 분리 시 병합 위험 증가 |
| 병합 | 여러 변경 계열을 결합 | 문법뿐 아니라 의미 충돌 확인 |
| 충돌 | 자동 결합이 결정을 못 하는 상태 | 변경 의도 이해 후 해결 |
| 태그 | 특정 버전에 의미 있는 식별자 부여 | 릴리스·기준점과 연결 |
| 원격 저장소 | 협업을 위한 공유 저장소 | 보호 규칙과 리뷰 정책 적용 |

제품의 표시 버전과 저장소의 커밋 식별자는 역할이 다르다. 제품 버전은 사용자·운영자에게 호환성과 변경 범위를 전달하고, 커밋 식별자는 정확한 소스 상태를 가리킨다. 빌드 메타데이터로 둘을 연결한다.

### 1.3 중앙집중형과 분산형

중앙집중형은 중앙 저장소가 주 이력을 관리하고 작업자가 필요한 파일을 받아 작업한다. 중앙 통제와 단순한 모델이 장점일 수 있지만 연결 장애와 중앙 가용성에 의존한다.

분산형은 각 작업자가 전체 이력을 가진 저장소를 복제하고 로컬에서 커밋·분기한 뒤 원격과 교환한다. 오프라인 작업과 유연한 분기가 가능하지만 공유 저장소, 리뷰, 보호 브랜치와 동기화 규칙이 필요하다.

조직의 네트워크, 보안·감사, 저장소 규모, 작업 방식에 따라 선택한다. 분산형이라고 중앙 협업 지점이 전혀 필요 없다는 뜻은 아니다.

### 1.4 버전 흐름과 정책

버전관리 흐름의 일반 예:

```text
승인된 기준 브랜치
→ 작업 이슈별 짧은 변경 브랜치
→ 작은 커밋 + 로컬 시험
→ 원격 검토 요청
→ 자동 빌드·시험 + 코드 리뷰
→ 승인 후 기준 브랜치 병합
→ 제품 버전·태그·빌드 산출물 연결
```

브랜치 전략은 팀 규모, 릴리스 빈도, 긴급수정, 규제와 제품 지원 방식에 따라 달라진다. 특정 전략을 모든 조직의 정답으로 단정하지 않는다. 중요한 것은 작업 흐름, 병합 기준, 릴리스와 긴급수정 절차가 합의되고 자동 검증되는 것이다.

### 1.5 좋은 변경 이력

좋은 커밋은 다음 특성을 가진다.

- 하나의 논리적 목적을 가진다.
- 빌드·기본 시험이 가능한 상태다.
- 변경 이유와 관련 이슈가 드러난다.
- 불필요한 형식 변경과 생성 파일을 섞지 않는다.
- 비밀번호, 인증키, 개인정보를 포함하지 않는다.
- 큰 바이너리는 관리 정책과 적합한 저장방식을 따른다.

커밋이 너무 크면 리뷰와 원인 추적이 어렵고, “수정”처럼 의미 없는 메시지는 미래의 유지보수자가 의도를 파악하기 어렵다. 반대로 한 줄마다 커밋을 나누는 것도 논리적 변경을 이해하기 어렵게 할 수 있다.

### 1.6 버전 식별

제품 버전 체계는 사용자와 운영자에게 변경의 호환성·위험을 전달해야 한다. 주·부·수정 번호를 사용하는 의미 기반 체계가 널리 쓰이지만 실제 증가 규칙과 사전 릴리스 표기는 조직 정책에 따라 다르다.

어떤 체계든 다음 연결이 중요하다.

```text
제품 표시 버전
↔ 저장소 커밋·태그
↔ 빌드 실행 ID와 도구·의존성
↔ 패키지 체크섬
↔ 릴리스 노트·배포 기록
```

버전 번호만 올리고 실제 산출물과 소스 연결을 남기지 않으면 재현과 감사가 어렵다.

## 2. 빌드 자동화 도구

### 2.1 빌드의 의미

빌드는 소스와 자원, 의존성을 실행·배포 가능한 산출물로 변환하고 필요한 검증을 수행하는 과정이다. `빌드 자동화 도구`는 사람이 순서대로 명령을 반복하는 대신 선언된 절차와 의존관계에 따라 작업을 일관되게 실행한다.

일반적인 단계는 다음과 같다.

1. 소스 버전과 빌드 환경 확인
2. 의존성 해석·복원과 무결성 확인
3. 소스 생성·컴파일 또는 변환
4. 정적 분석·형식·정책 검사
5. 단위 시험과 결과·커버리지 수집
6. 실행물·문서·자원 조립
7. 패키지 생성, 체크섬과 메타데이터 기록
8. 산출물 저장소 게시

모든 프로젝트가 컴파일을 필요로 하는 것은 아니지만 시험·패키징·검증의 반복 절차는 자동화할 수 있다.

### 2.2 빌드 스크립트의 원칙

빌드 절차는 텍스트로 선언하고 소스와 함께 버전관리한다.

```text
target clean:
    이전 생성물을 제거한다

target test depends on compile:
    단위 시험을 실행한다

target package depends on test:
    검증된 실행물과 메타데이터로 패키지를 만든다
```

실제 문법은 도구마다 다르지만 핵심은 작업의 입력·출력·의존관계와 실패조건을 명시하는 것이다. 시험이 실패했는데도 패키징이 계속되면 자동화의 신뢰성이 무너진다.

### 2.3 재현 가능한 빌드

재현성을 높이려면 다음을 통제한다.

- 정확한 소스 커밋과 하위 모듈·생성기 버전
- 빌드 도구, 컴파일러·런타임과 플러그인 버전
- 직접·간접 의존성과 무결성 정보
- 문자 인코딩, 로캘, 시간대, 파일 정렬 등 환경 차이
- 네트워크에서 사라질 수 있는 외부 자원
- 빌드에 영향을 주는 환경변수와 설정
- 생성시각·경로처럼 결과를 불필요하게 바꾸는 메타데이터

“내 컴퓨터에서 성공”을 피하려면 깨끗하고 격리된 빌드 환경에서 공통 명령으로 수행한다. 의존성 버전을 무조건 최신으로 가져오면 같은 소스에서 다른 산출물이 생길 수 있어 잠금·승인·갱신 절차가 필요하다.

### 2.4 전체·증분 빌드와 캐시

전체 빌드는 모든 산출물을 처음부터 생성해 오래 걸리지만 숨은 의존성과 오래된 파일의 영향을 줄인다. 증분 빌드는 변경된 부분과 의존 대상만 다시 처리해 빠르지만 입력·출력 관계가 잘못 정의되면 오래된 산출물을 재사용할 수 있다.

캐시는 반복 계산을 줄이지만 캐시 키에 소스, 도구, 의존성, 설정이 충분히 반영되어야 한다. 이상한 빌드 결과가 생기면 깨끗한 전체 빌드로 비교하고 캐시 오염 가능성을 점검한다.

### 2.5 실패를 빠르고 명확하게

자동화의 가치는 버튼 하나가 아니라 일관된 판정과 빠른 피드백에 있다.

- 첫 원인 오류를 가리지 않도록 로그를 구조화한다.
- 경고를 무한히 허용하지 않고 정책에 따라 품질 기준을 정한다.
- 시험 결과와 실패한 테스트 이름을 보존한다.
- 실패 산출물을 운영 가능한 정상 패키지로 게시하지 않는다.
- 실행 ID, 소스 버전, 환경, 도구 버전과 시간을 기록한다.
- 동일 입력으로 재실행할 수 있는 정보를 남긴다.

### 2.6 빌드 자동화와 지속적 통합

빌드 자동화는 반복 가능한 빌드 절차다. 지속적 통합(CI)은 개발자의 변경을 공유 흐름에 자주 통합하고 자동 빌드·시험으로 빠르게 검증하는 개발 실천과 운영체계다. 자동 빌드 도구는 CI의 핵심 수단이지만 둘은 완전히 같은 개념은 아니다.

## 3. 두 도구의 연결

```text
버전관리 도구가 정확한 소스와 빌드 정의를 제공
→ 빌드 자동화 도구가 깨끗한 환경에서 검증·산출물 생성
→ 빌드 결과에 커밋·제품 버전·도구 정보를 기록
→ 패키지 저장소와 릴리스 기록으로 연결
```

예를 들어 결함 수정 커밋이 병합되면 자동 빌드가 소스를 받아 의존성을 복원하고 시험·패키징을 수행한다. 산출물에는 제품 버전과 커밋 ID가 기록되며 체크섬과 시험 결과가 함께 보관된다. 운영에서 결함이 발생하면 패키지에서 정확한 소스와 빌드 실행을 역추적할 수 있다.

---

## 4. 비교와 경계

| 구분 | 소프트웨어 버전관리 도구 | 빌드 자동화 도구 |
|---|---|---|
| 중심 | 변경 이력과 여러 작업 흐름 | 소스에서 검증된 산출물 생성 |
| 입력 | 파일·변경·커밋·브랜치 | 소스 버전·의존성·빌드 정의 |
| 결과 | 추적 가능한 버전과 기준점 | 실행물·시험 결과·패키지·메타데이터 |
| 실패 예 | 잘못된 병합, 비밀 커밋 | 환경 의존, 숨은 의존, 실패 무시 |

빌드 성공은 기능 요구 전체가 충족되었다는 뜻이 아니고, 버전관리 이력이 있다는 사실만으로 빌드 재현성이 보장되지 않는다.

## 5. 시험 함정

1. **버전관리와 파일 백업 동일시**: 변경 이력·분기·병합·기준선과 협업을 지원한다.
2. **브랜치와 태그 혼동**: 브랜치는 변경 계열, 태그는 특정 버전 식별이 중심이다.
3. **병합 성공이면 의미도 정상**: 자동 병합 후에도 업무 충돌과 회귀시험을 확인한다.
4. **분산형에는 공유 저장소 불필요**: 협업을 위한 원격 저장소와 정책을 운영할 수 있다.
5. **제품 버전과 커밋 ID 동일시**: 사용자용 호환성 표기와 정확한 소스 식별 역할이 다르며 연결해야 한다.
6. **빌드는 컴파일만**: 의존성, 시험, 정적 점검, 패키징과 메타데이터 생성 등을 포함할 수 있다.
7. **자동 빌드는 항상 재현 가능**: 도구·의존성·환경과 외부 자원을 통제해야 한다.
8. **증분 빌드는 항상 안전**: 숨은 의존과 오래된 산출물로 잘못된 결과가 날 수 있다.
9. **빌드 자동화와 배포 동일시**: 빌드는 산출물 생성, 배포는 환경 설치·기동이다.
10. **CI와 빌드 도구 동일시**: 도구는 수단이고 CI는 자주 통합·검증하는 실천이다.

## 6. 확인 문제

### 문제 1

제품 버전 `2.4.1`만 알면 정확한 소스와 빌드 환경을 복원할 수 있는가?

**정답과 해설**: 버전과 커밋·태그, 빌드 실행 ID, 도구·의존성 정보, 패키지 체크섬이 연결되어 있어야 정확히 추적할 수 있다.

### 문제 2

버전관리 병합이 충돌 없이 완료되면 시험을 생략해도 되는가?

**정답과 해설**: 아니다. 텍스트 충돌이 없어도 두 변경의 업무 의미와 실행 동작이 충돌할 수 있어 빌드·회귀시험·리뷰가 필요하다.

### 문제 3

같은 소스에서 매번 최신 의존성을 내려받으면 재현 가능한가?

**정답과 해설**: 최신 버전이 바뀌면 결과도 달라질 수 있다. 승인된 버전과 무결성 정보를 잠그고 통제된 갱신 절차를 둔다.

### 문제 4

증분 빌드 결과가 이상할 때 깨끗한 전체 빌드와 비교하는 이유는?

**정답과 해설**: 잘못된 의존성 정의, 캐시 또는 이전 생성물이 결과에 섞였는지 구분하기 위해서다.

### 문제 5

빌드 자동화 도구를 설치하면 지속적 통합이 완성되는가?

**정답과 해설**: 아니다. 변경을 자주 공유하고 자동 검사 실패를 빠르게 고치며 기준 브랜치를 건강하게 유지하는 팀 절차가 함께 필요하다.

---

## 7. 최종 요약

- `소프트웨어 버전관리 도구`는 커밋, 브랜치, 병합, 충돌, 태그와 원격 저장소로 변경 이력과 병렬 작업을 관리한다.
- 논리적인 작은 커밋, 의미 있는 메시지, 코드 리뷰와 보호 규칙으로 검토·추적 가능성을 높인다.
- 제품 표시 버전, 커밋·태그, 빌드 실행, 패키지 체크섬과 릴리스 기록을 연결한다.
- `빌드 자동화 도구`는 의존성 복원, 컴파일·변환, 정적 점검, 단위 시험, 패키징과 메타데이터 생성을 반복 가능하게 실행한다.
- 깨끗한 환경에서 소스·도구·직간접 의존성·설정을 고정해 재현성을 높인다.
- 전체·증분 빌드와 캐시는 속도와 신뢰성의 장단점이 있으며 깨끗한 빌드로 검증한다.
- 버전관리와 빌드 자동화가 연결되어야 어떤 소스에서 어떤 검증을 거쳐 제품이 만들어졌는지 추적할 수 있다.
