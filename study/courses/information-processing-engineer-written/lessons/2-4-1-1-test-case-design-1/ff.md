# 2-4-1-1. 테스트 케이스 · 테스트 레벨

> **공식 범위**: 소프트웨어개발 > 애플리케이션 테스트 관리 > 애플리케이션 테스트케이스 설계 > `테스트 케이스`, `테스트 레벨`

## 0. 무엇을 어떤 수준에서 확인할 것인가

소프트웨어 테스트는 프로그램을 실행해 보는 행위만이 아니다. 요구와 위험에서 시험조건을 도출하고, 입력·절차·기대 결과를 재현 가능하게 만들며, 구성요소부터 전체 사용자 수용까지 서로 다른 수준에서 결함을 찾는 체계적인 활동이다.

이 레슨의 두 주제는 다음과 같다.

1. `테스트 케이스`: 특정 시험목적을 확인하기 위한 사전조건, 입력, 절차, 기대 결과와 판정정보의 집합
2. `테스트 레벨`: 개발 산출물과 시험대상의 범위에 따라 구분한 컴포넌트, 통합, 시스템, 인수 수준

여러 테스트 케이스를 업무 흐름으로 조직하는 테스트 시나리오와 전체 테스트 지식 체계는 다음 레슨에서 다룬다. 여기서는 한 케이스의 품질과 레벨별 목적 구분에 집중한다.

---

## 1. 테스트 케이스

### 1.1 테스트 케이스의 구성

좋은 테스트 케이스는 다른 시험자가 같은 환경에서 실행해 같은 기준으로 판정할 수 있어야 한다.

| 항목 | 내용 |
|---|---|
| 식별자·제목 | 중복 없는 ID와 검증 동작을 드러내는 이름 |
| 관련 요구·위험 | 시험 근거와 우선순위 |
| 목적 | 무엇을 확인하려는가 |
| 사전조건 | 계정, 데이터, 상태, 환경과 설정 |
| 입력 데이터 | 값, 형식, 경계, 데이터 출처 |
| 실행 절차 | 순서가 있는 구체적 행동 |
| 기대 결과 | 단계·최종 상태의 검증 가능한 결과 |
| 사후조건 | 시험 뒤 남아야 할 상태·정리 방법 |
| 환경 | 버전, 장치, 구성과 의존 서비스 |
| 실제 결과·판정 | 실행 결과, 성공·실패·차단과 증거 |
| 결함·비고 | 관련 결함 ID, 로그, 재실행 정보 |

기대 결과는 실행 전에 요구·설계에서 도출해야 한다. 실제 결과를 본 뒤 기대 결과를 맞춰 쓰면 결함을 정상으로 승인할 위험이 있다.

### 1.2 테스트 케이스 설계 절차

1. **테스트 베이시스 확인**: 요구사항, 설계, 인터페이스, 위험과 규정을 읽는다.
2. **테스트 조건 도출**: 검증할 기능·품질·업무 규칙과 실패 조건을 목록화한다.
3. **우선순위 설정**: 업무 영향, 변경, 복잡도, 결함 이력과 사용 빈도를 반영한다.
4. **설계 기법 적용**: 입력 영역, 경계, 규칙 조합, 상태와 구조를 이용해 대표값을 고른다.
5. **사전조건·데이터 작성**: 독립적이고 반복 가능한 상태를 준비한다.
6. **절차·기대 결과 작성**: 한 단계 한 행동과 관찰 가능한 결과를 명시한다.
7. **추적·검토**: 요구·위험과 양방향 연결하고 누락·중복·모호성을 리뷰한다.
8. **실행 가능성 확인**: 환경, 권한, 도구, 데이터와 정리 절차를 시험한다.

### 1.3 명확한 기대 결과

나쁜 예:

```text
절차: 올바른 정보로 로그인한다.
기대 결과: 정상적으로 처리된다.
```

개선 예:

```text
사전조건: 활성 계정이 존재하고 로그인 화면이 표시됨
입력: 등록된 이메일과 올바른 비밀번호
절차: 이메일·비밀번호를 입력하고 로그인 실행
기대 결과:
1) 인증된 사용자 홈으로 이동
2) 화면에 해당 사용자 이름 표시
3) 새로운 인증 세션 생성
4) 비밀번호 원문이 화면·로그에 노출되지 않음
```

“정상”이라는 단어 대신 화면, 데이터, 메시지, 상태와 부수효과를 관찰 가능한 방식으로 적는다. 내부 구현을 과도하게 고정하면 리팩터링만으로 시험이 깨질 수 있으므로 요구된 외부 동작과 필요한 내부 품질의 균형을 잡는다.

### 1.4 대표 테스트 설계 기법

#### 동등분할

같은 방식으로 처리될 것으로 예상되는 입력 영역을 유효·무효 집합으로 나누고 대표값을 선택한다. 나이 허용범위가 19~65라면 19~65의 유효 집합, 19 미만과 65 초과의 무효 집합을 나눌 수 있다.

#### 경계값 분석

결함이 자주 발생하는 경계와 바로 안팎 값을 선택한다. 위 범위에서는 18, 19, 20, 64, 65, 66이 대표 후보다. 정확한 선택 수는 위험과 조직 기준에 따라 달라질 수 있다.

#### 결정 테이블

여러 조건 조합에 따라 결과가 달라질 때 조건과 행동을 표로 정리한다.

| 회원 | 재고 있음 | 결제 승인 | 결과 |
|---|---|---|---|
| 예 | 예 | 예 | 주문 확정 |
| 예 | 예 | 아니오 | 결제 실패 안내 |
| 예 | 아니오 | - | 품절 안내 |
| 아니오 | - | - | 인증 요청 |

불가능하거나 무관한 조합을 구분하고 업무 규칙이 모든 조합을 정의하는지 확인한다.

#### 상태전이 시험

현재 상태와 사건에 따라 다음 상태가 달라지는 대상에 사용한다. 주문의 `접수→결제완료→배송중→완료`와 취소 가능한 전이를 확인하고 금지된 전이도 시험한다.

#### 구조 기반 기법

구현 구조를 바탕으로 문장, 분기, 조건과 경로가 실행되는지 본다. 커버리지는 실행 범위를 보여 주지만 기대 결과와 누락 요구를 자동 보장하지 않는다.

### 1.5 테스트 데이터와 독립성

- 개인정보를 그대로 복사하지 않고 합성·비식별·승인된 데이터를 사용한다.
- 시간, 난수, 외부 서비스 등 비결정 요소를 통제한다.
- 케이스마다 필요한 상태를 명시하고 실행 순서 의존을 줄인다.
- 실행 후 생성·변경한 데이터를 정리하거나 고립된 환경을 사용한다.
- 실패 시 재현할 수 있도록 데이터 버전과 환경을 기록한다.
- 유효·무효·경계·중복·누락·권한 데이터의 목적을 구분한다.

시험 데이터가 우연히 다른 케이스에서 생성되어야만 성공하면 독립성이 낮고 자동화·병렬 실행이 어렵다.

### 1.6 테스트 케이스 품질 검토

좋은 케이스는 정확하고 명확하며 반복·추적 가능하고, 한 목적에 집중하며, 적절한 우선순위와 정리 절차를 가진다. 다음을 묻는다.

- 모든 중요 요구·위험에 케이스가 연결되었는가?
- 같은 동작을 의미 없이 중복 시험하고 있지 않은가?
- 정상뿐 아니라 경계·오류·권한·복구를 포함하는가?
- 기대 결과가 실행 전에 결정되고 관찰 가능한가?
- 특정 시험자의 암묵지나 실행 순서에 의존하지 않는가?
- 환경과 데이터 준비 비용이 위험에 비례하는가?

## 2. 테스트 레벨

테스트 레벨은 시험대상의 범위와 개발 산출물에 따라 구분한다. 각 레벨은 다른 결함을 찾으며 상위 레벨이 하위 레벨을 대체하지 않는다.

### 2.1 컴포넌트 테스트

함수, 클래스, 모듈 등 개별 컴포넌트를 가능한 한 격리해 내부 로직과 단위 계약을 확인한다. 개발자 또는 해당 코드에 가까운 역할이 수행할 수 있으며 스텁·목·드라이버를 사용해 의존을 통제한다.

대표 결함: 계산 오류, 경계 처리, 잘못된 분기, 지역 오류 처리, 내부 상태 변화.

### 2.2 통합 테스트

컴포넌트·서브시스템·외부 시스템 사이의 인터페이스와 상호작용을 확인한다. 데이터 형식, 호출 순서, 제한시간, 오류 전달, 트랜잭션과 설정 등 연결 결함을 찾는다.

대표 결함: 매개변수 불일치, 프로토콜·스키마 차이, 호출 순서, 상태 동기화, 오류·재시도 처리.

통합 전략과 상세 절차는 별도 통합 테스트 범위에서 더 깊게 다룰 수 있다.

### 2.3 시스템 테스트

완성된 통합 시스템이 전체 기능·비기능 요구를 만족하는지 대표 운영환경과 유사한 조건에서 확인한다. 기능 흐름뿐 아니라 성능, 보안, 사용성, 복구, 호환성 등 시스템 전체 특성을 평가한다.

대표 결함: 전체 업무 흐름 누락, 환경 설정, 요구 불일치, 시스템 품질 목표 미달.

### 2.4 인수 테스트

사용자·고객·운영 관점에서 시스템이 합의된 인수 기준과 업무 목적을 충족하여 사용할 준비가 되었는지 확인한다. 사용자 인수, 운영 인수, 계약·규제 인수 등 목적에 따라 형태가 달라질 수 있다.

대표 결함: 실제 업무 적합성, 운영 준비, 계약·규정 미충족, 사용자 수용 기준 불일치.

인수 테스트는 단순히 고객이 시스템 테스트를 반복하는 단계가 아니다. 업무 가치와 배포·운영 준비의 최종 판단 근거를 제공한다.

### 2.5 V 모델의 대응 관계

V 모델은 개발 산출물과 테스트 레벨의 대응을 이해하는 데 도움이 된다.

| 개발 관점 | 대응 테스트 관점 |
|---|---|
| 사용자·업무 요구 | 인수 테스트 |
| 시스템 요구·명세 | 시스템 테스트 |
| 아키텍처·인터페이스 설계 | 통합 테스트 |
| 상세 설계·코드 | 컴포넌트 테스트 |

이는 시험 준비와 조기 설계를 강조하는 개념적 대응이다. 모든 프로젝트가 단계별로 한 번씩만 수행한다는 뜻은 아니며 반복·점진 개발에서도 레벨별 검증을 수행할 수 있다.

### 2.6 테스트 레벨과 테스트 유형 구분

테스트 레벨은 **어느 범위의 대상을 시험하는가**, 테스트 유형은 **어떤 품질 특성이나 변화 목적을 시험하는가**에 가깝다. 기능, 성능, 보안, 사용성, 회귀 같은 유형은 여러 레벨에서 수행할 수 있다.

예를 들어 성능은 한 함수의 처리시간을 보는 컴포넌트 수준과 전체 시스템의 동시 사용자 처리량을 보는 시스템 수준 모두에 적용할 수 있다.

## 3. 레벨별 케이스 예시

주문 취소 기능을 각 레벨에서 본다.

| 레벨 | 테스트 케이스 예 |
|---|---|
| 컴포넌트 | 주문 상태별 취소 가능 여부 함수의 경계·예외 확인 |
| 통합 | 주문 서비스와 결제 서비스의 취소 요청·오류 전달 확인 |
| 시스템 | 로그인부터 취소·환불상태 표시까지 전체 흐름과 성능 확인 |
| 인수 | 실제 업무 규칙, 운영 복구와 고객 수용 기준 충족 확인 |

같은 “취소”라도 시험대상, 기반 문서, 데이터, 기대 결과와 발견할 결함이 다르다.

## 4. 시험 함정

1. **테스트 케이스를 입력값만으로 정의**: 사전조건, 절차, 기대 결과와 판정이 필요하다.
2. **실행 후 기대 결과 작성**: 실제 결함에 기대를 맞추는 확증 편향이 생긴다.
3. **정상값만 시험**: 경계, 무효값, 예외·권한과 상태 전이를 포함한다.
4. **경계값과 동등분할 동일시**: 동등분할은 처리 집합, 경계값은 경계와 바로 안팎을 본다.
5. **커버리지가 요구 검증을 보장**: 코드 실행 범위와 요구 정확성은 다르다.
6. **컴포넌트 시험이 통합 시험을 대체**: 실제 인터페이스 결함은 남을 수 있다.
7. **시스템 테스트와 인수 테스트 동일시**: 전체 요구 확인과 업무·수용·운영 준비 판단의 관점이 다르다.
8. **테스트 레벨과 유형 혼동**: 범위와 품질 관점을 구분한다.
9. **V 모델은 테스트를 끝에만 수행**: 각 개발 산출물과 대응 시험을 일찍 설계하는 관점을 제공한다.

## 5. 확인 문제

### 문제 1

테스트 케이스의 기대 결과는 언제, 어떤 근거로 작성해야 하는가?

**정답과 해설**: 실행 전에 요구·설계·업무 규칙에서 도출해야 한다. 실제 결과를 보고 맞추면 결함을 정상으로 인정할 수 있다.

### 문제 2

허용 나이가 19~65일 때 경계값 후보는?

**정답과 해설**: 대표적으로 18, 19, 20, 64, 65, 66을 선택할 수 있다. 경계와 바로 안팎의 처리를 확인한다.

### 문제 3

두 서비스의 데이터 형식과 오류 전달을 확인하는 주된 테스트 레벨은?

**정답과 해설**: 통합 테스트다. 구성요소 사이 인터페이스와 상호작용 결함을 확인한다.

### 문제 4

완성된 시스템이 계약된 업무 수용 기준과 운영 준비를 만족하는지 확인하는 레벨은?

**정답과 해설**: 인수 테스트다. 사용자·고객·운영·계약 관점의 사용할 준비 여부를 판단한다.

### 문제 5

보안 테스트는 시스템 테스트 레벨에서만 수행하는가?

**정답과 해설**: 아니다. 보안은 테스트 유형이며 컴포넌트의 입력 검증, 통합의 인증 전달, 시스템 전체의 접근통제 등 여러 레벨에서 수행할 수 있다.

## 6. 최종 요약

- `테스트 케이스`는 시험목적, 근거, 사전조건, 데이터, 절차, 기대 결과, 사후조건, 환경과 판정정보를 포함한다.
- 기대 결과는 실행 전에 요구에서 도출하고 “정상”이 아니라 관찰 가능한 상태·메시지·데이터로 쓴다.
- 동등분할, 경계값, 결정 테이블, 상태전이와 구조 기반 기법으로 위험을 대표하는 데이터를 선택한다.
- 케이스는 독립·반복·추적 가능해야 하며 민감한 운영 데이터를 안전하게 다룬다.
- `테스트 레벨`은 컴포넌트, 통합, 시스템, 인수로 구분되며 각기 다른 범위와 결함을 다룬다.
- V 모델은 개발 산출물과 대응 시험을 연결하지만 반복 개발에서도 레벨별 검증을 적용할 수 있다.
- 테스트 레벨은 대상 범위, 테스트 유형은 기능·성능·보안·회귀 같은 품질·목적 관점이며 서로 대체하지 않는다.
