# 2-4-1-2. 테스트 시나리오 · 테스트 지식 체계

> **공식 범위**: 소프트웨어개발 > 애플리케이션 테스트 관리 > 애플리케이션 테스트케이스 설계 > `테스트 시나리오`, `테스트 지식 체계`

## 0. 개별 검증을 업무 흐름과 지식 체계로 연결하기

테스트 케이스가 한 조건과 기대 결과를 구체적으로 확인한다면 테스트 시나리오는 여러 케이스를 사용자·업무의 흐름과 위험에 따라 조직한다. 테스트 지식 체계는 이러한 설계·실행·관리 활동을 원칙, 프로세스, 기법, 역할과 산출물의 관점에서 구조화한다.

이 레슨의 목표는 다음과 같다.

1. `테스트 시나리오`를 정상·대안·예외 흐름과 상태·데이터 변화가 연결된 형태로 작성한다.
2. 시나리오와 테스트 케이스, 유스케이스·사용자 스토리의 차이를 구분한다.
3. `테스트 지식 체계`의 기본 원칙, 정적·동적 시험, 프로세스, 결함관리와 독립성 개념을 설명한다.
4. 위험 기반으로 시험 범위와 깊이를 선택하고, 완전 시험이 불가능하다는 사실을 계획에 반영한다.

특정 자격·기관의 용어 체계나 도구 버전은 달라질 수 있다. 여기서는 소프트웨어 시험 분야에서 널리 공유되는 핵심 개념과 판단 원리를 중심으로 학습한다.

## 1. 테스트 시나리오

### 1.1 정의

테스트 시나리오는 사용자의 목표 또는 업무 사건이 시작되어 결과에 도달하는 흐름을 고수준으로 표현하고, 이를 검증할 테스트 조건과 케이스를 조직한 것이다. “어떤 상황과 흐름을 시험할 것인가”에 답하며 세부 입력과 단계는 연결된 테스트 케이스에서 구체화할 수 있다.

예를 들어 “회원이 상품을 주문하고 결제를 완료한다”는 정상 시나리오 외에도 다음이 필요하다.

- 결제 승인이 거절되는 대안 흐름
- 주문 중 재고가 소진되는 예외 흐름
- 중복 제출이나 시간초과 뒤 재시도 흐름
- 결제 완료 뒤 알림만 실패하는 부분 실패 흐름
- 취소·복구·보상 처리가 필요한 흐름

정상 흐름 하나만 시험하면 구성요소가 실패하거나 상태가 바뀌는 실제 운영 위험을 놓친다.

### 1.2 구성 요소

| 항목 | 내용 |
|---|---|
| 시나리오 ID·제목 | 목표와 시작 사건이 드러나는 식별 |
| 업무 목적·위험 | 왜 중요한지와 실패 영향 |
| 관련 요구·유스케이스 | 시험 근거와 추적 링크 |
| 참여자·시스템 | 사용자, 내부·외부 시스템의 역할 |
| 시작·사전조건 | 초기 데이터·상태·권한·환경 |
| 기본 흐름 | 가장 일반적인 성공 경로 |
| 대안·예외 흐름 | 선택 조건, 오류, 제한시간, 복구 |
| 종료·사후조건 | 성공·실패 뒤 데이터와 시스템 상태 |
| 연결 테스트 케이스 | 상세 입력·절차·기대 결과 |
| 우선순위·적용 범위 | 위험, 빈도, 버전, 환경 |

시나리오가 너무 추상적이면 실행할 수 없고, 모든 클릭과 데이터 값을 넣으면 테스트 케이스와 중복되어 유지보수가 어렵다. 업무 흐름과 분기·상태를 시나리오에, 구체 데이터와 판정 단계를 케이스에 두는 식으로 수준을 합의한다.

### 1.3 작성 절차

1. **업무 목표와 시작 사건 선정**: 사용자 가치와 실패 영향이 큰 흐름을 고른다.
2. **시스템 경계와 참여자 식별**: 외부 서비스와 책임 범위를 명확히 한다.
3. **기본 흐름 작성**: 시작부터 성공 종료까지 중요한 상태 변화를 순서대로 쓴다.
4. **분기·예외 도출**: 조건, 권한, 데이터 부재, 중복, 시간초과와 의존 실패를 찾는다.
5. **사후조건 정의**: 성공·실패·취소 뒤 데이터와 외부 부수효과를 확인한다.
6. **위험·우선순위 반영**: 발생 가능성과 영향, 사용 빈도, 최근 변경을 고려한다.
7. **케이스로 구체화**: 각 경로의 대표 데이터, 단계와 기대 결과를 연결한다.
8. **추적·검토**: 요구·업무 규칙·상태와 시나리오·케이스의 누락·중복을 확인한다.
9. **실행 결과 반영**: 결함과 변경으로 새 흐름이 발견되면 갱신한다.

### 1.4 예시: 주문 취소 시나리오

```text
시나리오 ID: SC-CANCEL-01
목적: 배송 시작 전 주문을 취소하고 결제를 되돌린다.
사전조건: 인증된 고객, 결제 완료 상태의 본인 주문

기본 흐름:
1. 고객이 주문 상세에서 취소를 요청한다.
2. 시스템이 소유권과 취소 가능 상태를 확인한다.
3. 결제 서비스에 취소를 요청한다.
4. 승인 후 주문 상태를 '취소 완료'로 변경한다.
5. 고객에게 결과와 환불 정보를 표시한다.

대안·예외:
A. 배송 시작 상태 → 취소 불가 이유와 가능한 절차 안내
B. 결제 취소 시간초과 → 중복 취소 방지 후 처리 중 상태와 재확인
C. 알림 실패 → 주문 취소는 유지하고 알림 재처리 기록

사후조건:
성공 시 주문·결제 상태 일치, 감사 이력 생성
실패 시 부분 반영 여부와 복구·보상 상태 확인
```

이 시나리오에서 “시간초과 후 다시 요청할 때 결제가 두 번 취소되지 않는가?”, “주문 상태와 결제 상태가 달라지면 어떻게 복구하는가?” 같은 케이스를 도출할 수 있다.

### 1.5 시나리오 설계 관점

- 사용자 여정: 처음 진입부터 목표 완료·이탈까지
- 업무 규칙: 금액, 기간, 자격, 상태와 권한 조건
- 데이터 생명주기: 생성·조회·변경·취소·보존
- 시스템 상태: 정상, 저하, 단절, 복구와 재시작
- 외부 의존: 지연, 거절, 중복·순서 변경과 부분 실패
- 채널·환경: 장치, 언어, 권한, 연결 품질과 지원 환경
- 변경 영향: 최근 수정과 연관된 상·하류 흐름

가능한 모든 조합을 시나리오로 만들 수 없으므로 위험, 업무 빈도와 대표성으로 선택한다.

### 1.6 시나리오와 케이스 비교

| 구분 | 테스트 시나리오 | 테스트 케이스 |
|---|---|---|
| 중심 | 업무 목표와 흐름·분기 | 한 조건의 구체 입력·절차·기대 결과 |
| 수준 | 비교적 고수준 | 실행·판정 가능한 상세 수준 |
| 관계 | 여러 케이스를 묶거나 도출 근거 제공 | 시나리오의 특정 경로를 검증 |
| 변경 | 업무 흐름 변경에 영향 | 입력·UI·규칙 세부 변경에 영향 |

조직에 따라 두 용어를 다르게 사용할 수 있으므로 템플릿과 상세 수준을 합의한다.

## 2. 테스트 지식 체계

### 2.1 테스트의 목적

`테스트 지식 체계`는 테스트를 결함 찾기, 품질정보 제공, 위험 감소, 요구·규정 준수 확인과 의사결정 지원의 활동으로 본다. 테스트는 품질을 대신 만들어 주지 않는다. 개발 전 과정에서 예방·리뷰·자동화·설계 개선과 함께 품질을 형성하고, 테스트는 현재 품질과 남은 위험에 대한 증거를 제공한다.

### 2.2 널리 알려진 테스트 원칙

1. **테스트는 결함의 존재를 보여 줄 수 있지만 부재를 증명할 수 없다.** 통과한 범위 밖의 결함은 남을 수 있다.
2. **완전 테스트는 불가능하다.** 입력, 상태, 경로와 환경 조합이 방대하므로 위험 기반으로 선택한다.
3. **조기 테스트가 비용을 줄인다.** 요구·설계 리뷰와 시험 설계를 일찍 시작하면 결함을 싼 단계에서 발견한다.
4. **결함은 특정 영역에 집중되는 경향이 있다.** 복잡도, 변경, 의존과 과거 결함이 큰 영역을 우선한다.
5. **같은 시험만 반복하면 새 결함 발견력이 낮아질 수 있다.** 결함과 변경에 맞춰 데이터와 시나리오를 보완한다.
6. **테스트는 상황에 의존한다.** 안전·금융·게임·내부 도구의 위험과 방법은 다르다.
7. **요구와 사용자 가치를 충족하지 못하면 결함이 적어도 성공이 아니다.** 잘못된 제품을 완벽히 구현하는 오류를 경계한다.

이 원칙들은 “테스트를 적게 하라”가 아니라 제한된 자원을 가장 중요한 위험에 집중하라는 뜻이다.

### 2.3 정적 테스트와 동적 테스트

정적 테스트는 소프트웨어를 실행하지 않고 요구·설계·코드·문서 등을 검토·분석한다. 리뷰, 워크스루, 인스펙션, 정적 분석이 대표적이다. 모호한 요구, 표준 위반, 도달 불가 코드, 보안 위험을 조기에 발견할 수 있다.

동적 테스트는 소프트웨어를 실행해 실제 결과와 기대 결과를 비교한다. 기능·성능·보안·사용성 등 여러 품질을 다양한 레벨에서 검증한다.

두 방식은 대체 관계가 아니다. 정적 분석이 찾기 어려운 실행 상태 결함이 있고, 동적 시험이 모든 문서 모순과 경로를 찾는 것도 아니다.

### 2.4 검증과 확인

- 검증(verification): 개발 산출물이 명세와 절차에 맞게 만들어졌는가? “제품을 올바르게 만들고 있는가?”
- 확인(validation): 완성된 결과가 사용자의 실제 필요와 목적을 충족하는가? “올바른 제품을 만들고 있는가?”

용어 번역과 사용은 조직마다 다를 수 있으나 **명세 준수**와 **사용 목적 적합성**의 관점을 구분한다.

### 2.5 일반 테스트 프로세스

테스트 활동은 선형으로 한 번만 진행되지 않고 반복된다.

1. **계획**: 범위, 목표, 위험, 전략, 자원, 일정, 환경, 종료 기준을 정한다.
2. **모니터링·제어**: 실제 진행과 품질을 계획과 비교하고 우선순위·자원을 조정한다.
3. **분석**: 테스트 베이시스에서 테스트 조건과 위험을 도출한다.
4. **설계**: 케이스, 데이터, 환경과 기대 결과를 구체화한다.
5. **구현**: 절차·자동화·묶음과 추적을 준비하고 실행 가능성을 확인한다.
6. **실행**: 시험을 수행해 실제와 기대를 비교하고 결과·증거·결함을 기록한다.
7. **완료**: 종료 기준, 남은 위험, 결함, 산출물과 교훈을 정리한다.

실행 건수만으로 진행을 평가하지 않는다. 요구·위험 커버리지, 중요 결함, 차단된 시험, 환경 안정성과 남은 위험을 함께 본다.

### 2.6 테스트 기법의 지식 영역

- 명세 기반(블랙박스): 내부 구조와 무관하게 요구·입출력·업무 규칙으로 설계
- 구조 기반(화이트박스): 코드·제어·데이터 구조의 실행 범위를 기반으로 설계
- 경험 기반: 오류 추정, 탐색적 테스트, 체크리스트로 지식과 직관 활용

명세 기반이라고 내부를 절대 보지 않는다는 뜻보다 시험조건의 주 근거가 외부 명세라는 뜻이다. 경험 기반도 무계획한 임의 클릭이 아니라 목표, 시간, 기록과 학습을 가진 구조적인 탐색이어야 한다.

### 2.7 위험 기반 테스트

제품 위험은 기능이 실패할 가능성과 그 영향의 조합으로 생각할 수 있다.

```text
위험 우선순위 ≈ 발생 가능성 × 영향
```

정확한 계산식보다 일관된 평가 기준이 중요하다. 업무 중단, 안전·금전·개인정보, 사용 빈도, 복잡도, 최근 변경, 결함 이력을 고려한다. 높은 위험에는 더 이른 리뷰, 깊은 케이스, 다양한 환경과 재시험을 배정한다. 낮은 위험을 전혀 시험하지 않는다는 뜻은 아니다.

### 2.8 결함관리

결함 보고에는 다음이 필요하다.

- 요약과 발견 버전·환경
- 사전조건·입력·재현 절차
- 기대 결과와 실제 결과
- 로그·화면·추적 ID 등 증거
- 심각도와 업무 영향, 우선순위 제안
- 재현 빈도와 우회 방법
- 관련 요구·시나리오·케이스

심각도는 결함의 기술·업무 영향, 우선순위는 언제 수정할지를 결정하는 사업·일정 판단이다. 심각도가 높아도 발생 조건과 릴리스 상황에 따라 우선순위 결정은 별도일 수 있다.

결함은 등록→분석→할당→수정→재시험→종료 같은 상태를 거칠 수 있다. 조직별 흐름은 다르지만 상태 정의와 재개방 기준, 중복·재현 불가 처리와 책임을 합의한다.

### 2.9 테스트 독립성

작성자와 다른 관점의 검토자는 익숙함 때문에 놓친 결함을 발견할 수 있다. 독립성은 동료 검토, 별도 시험 담당, 외부 시험 등 여러 수준이 가능하다. 높은 독립성이 항상 최선은 아니다. 의사소통 비용과 제품 지식 부족이 생길 수 있어 위험과 조직 규모에 맞춘다. 개발자 시험과 독립 시험은 상호 보완한다.

## 3. 통합 적용 예시

신규 회원가입 기능을 시험한다고 하자.

1. 위험 분석에서 개인정보 동의 누락과 중복 계정 생성을 높은 위험으로 정한다.
2. 요구·정책을 정적으로 검토해 동의 철회와 보존기간의 모호성을 발견한다.
3. 정상 가입, 이미 존재하는 이메일, 인증 시간초과, 동의 미선택, 네트워크 재시도 시나리오를 만든다.
4. 각 경로를 경계값·결정 테이블과 상태전이 케이스로 구체화한다.
5. 실행 결과와 결함을 요구·시나리오·케이스에 추적한다.
6. 수정 뒤 결함 재시험과 관련 회귀시험을 수행한다.
7. 종료 시 미해결 결함, 차단 환경과 남은 위험을 보고한다.

이 흐름은 시나리오 설계가 전체 테스트 프로세스와 분리된 문서 작업이 아니라 위험·요구·실행·결함을 연결하는 활동임을 보여 준다.

## 4. 시험 함정

1. **시나리오와 케이스 동일시**: 시나리오는 업무 흐름, 케이스는 구체 입력·절차·기대 결과에 더 가깝다.
2. **정상 흐름만 작성**: 대안·예외·시간초과·부분 실패와 복구를 포함한다.
3. **모든 조합 시험 가능 가정**: 완전 시험은 불가능하므로 위험과 대표성으로 선택한다.
4. **테스트 통과가 무결함 증명**: 시험한 조건에서 발견되지 않았다는 증거다.
5. **정적 테스트는 코드 실행**: 산출물을 실행하지 않고 검토·분석한다.
6. **검증과 확인 혼동**: 명세대로 만들었는지와 실제 필요를 충족하는지의 관점을 구분한다.
7. **경험 기반 테스트는 무계획 클릭**: 목표·시간·기록과 학습을 가진 탐색이어야 한다.
8. **심각도와 우선순위 동일시**: 영향과 수정 시점의 사업 판단은 관련되지만 다른 속성이다.
9. **독립 시험이면 개발자 시험 불필요**: 빠른 단위 피드백과 독립 관점은 상호 보완한다.
10. **실행 건수만으로 완료 판단**: 위험 커버리지, 미해결 결함과 차단·남은 위험을 본다.

## 5. 확인 문제

### 문제 1

테스트 시나리오와 테스트 케이스의 핵심 차이는?

**정답과 해설**: 시나리오는 사용자·업무 목표의 흐름과 분기·상태를 고수준으로 조직하고, 케이스는 특정 조건의 입력·절차·기대 결과를 실행·판정 가능하게 구체화한다.

### 문제 2

모든 가능한 입력 조합을 시험할 수 없는 상황에서 무엇을 기준으로 선택하는가?

**정답과 해설**: 발생 가능성과 영향, 사용 빈도, 복잡도, 최근 변경과 결함 이력 등 위험과 대표성을 기준으로 우선순위를 정한다.

### 문제 3

요구사항 문서를 실행하지 않고 리뷰해 모순을 찾는 활동은?

**정답과 해설**: 정적 테스트다. 코드·문서·모델을 실행하지 않고 검토·정적 분석한다.

### 문제 4

결함의 심각도가 높으면 항상 수정 우선순위도 가장 높은가?

**정답과 해설**: 반드시 그렇지 않다. 심각도는 영향, 우선순위는 릴리스 일정·발생 가능성·우회책·사업 판단을 포함한 수정 시점 결정이다.

### 문제 5

결함 수정 확인만 하고 관련 기능의 시험을 생략해도 되는가?

**정답과 해설**: 수정 자체의 재시험과 함께 변경이 기존 기능을 깨뜨리지 않았는지 위험에 따른 회귀시험이 필요하다.

## 6. 최종 요약

- `테스트 시나리오`는 사용자·업무 목표의 기본·대안·예외 흐름, 참여자, 상태와 사후조건을 조직하고 상세 케이스를 연결한다.
- 정상 흐름뿐 아니라 시간초과, 부분 실패, 재시도, 보상과 복구를 위험에 따라 포함한다.
- 시나리오는 비교적 고수준의 흐름, 테스트 케이스는 구체 입력·절차·기대 결과라는 상세 수준에 초점이 있다.
- `테스트 지식 체계`는 테스트 목적·원칙, 정적·동적 시험, 프로세스, 기법, 위험·결함관리와 독립성을 구조화한다.
- 결함 부재와 완전 시험은 증명하기 어려우므로 조기 시험과 위험 기반 선택이 필요하다.
- 명세 기반, 구조 기반, 경험 기반 기법은 서로 다른 근거를 사용하며 상호 보완한다.
- 테스트 결과는 실행 건수보다 요구·위험 커버리지, 중요 결함, 차단 항목과 남은 위험을 포함해 의사결정에 제공해야 한다.
