# 2-4-2-1. 결함관리 도구 · 테스트 자동화 도구

> **공식 범위**: 2026년 정보처리기사 출제기준의 `소프트웨어개발 > 애플리케이션 테스트 관리 > 애플리케이션 통합 테스트` 가운데 **결함관리 도구**, **테스트 자동화 도구**를 학습한다. 특정 제품명·버전·화면 사용법은 고정하지 않고, 도구가 지원해야 할 업무 흐름과 선택·운영 기준을 중심으로 다룬다. 통합 테스트의 결합 전략과 절차 자체는 다음 레슨 범위다.

테스트에서 발견한 문제는 기록만 한다고 해결되지 않는다. 재현 가능한 정보로 등록하고 영향과 긴급도를 판단하며, 수정·재시험·종료까지 상태를 추적해야 한다. 반복 검사는 자동화할 수 있지만, 자동화 도구가 테스트 목적이나 판정을 대신하는 것은 아니다.

---

## 1. 결함의 의미와 관리 목적

**결함**은 요구사항, 설계, 코드, 데이터, 환경 또는 문서가 기대한 결과와 달라 실패를 일으킬 수 있는 문제다. 테스트 실행 중 관찰된 실패 현상과 그 원인인 결함은 구분해야 한다. 같은 실패가 환경 설정 때문에 발생할 수도 있고 여러 실패가 하나의 결함에서 파생될 수도 있다.

결함관리의 목적은 다음과 같다.

1. 문제를 재현하고 동일한 대상을 논의할 수 있게 한다.
2. 업무 영향과 수정 긴급도를 근거로 처리 순서를 정한다.
3. 담당자, 상태, 변경 이력과 의사결정을 추적한다.
4. 수정 결과를 원래 실패 조건에서 재시험한다.
5. 반복 결함과 누출 원인을 분석해 개발·테스트 과정을 개선한다.

결함 수를 줄여 보이기 위해 등록 기준을 느슨하게 하면 품질이 좋아지는 것이 아니다. 도구는 사실과 흐름을 투명하게 만드는 수단이어야 한다.

---

## 2. 토픽 ① 결함관리 도구

### 2.1 핵심 기능

**결함관리 도구**는 결함의 등록, 분류, 배정, 상태 전이, 의사소통, 이력, 보고와 추적을 지원한다.

| 기능 | 지원 내용 | 확인 포인트 |
|---|---|---|
| 등록 | 제목, 환경, 재현 절차, 기대·실제 결과, 증거 | 다른 사람이 재현 가능한가? |
| 분류 | 유형, 모듈, 원인 후보, 심각도, 우선순위 | 용어와 기준이 일관적인가? |
| 배정 | 책임 팀·담당자·기한 지정 | 미배정 결함이 방치되지 않는가? |
| 상태 관리 | 신규, 분석, 수정, 재시험, 종료, 재오픈 등 | 전이 조건과 책임이 명확한가? |
| 추적 | 요구사항, 테스트 케이스, 변경, 릴리스 연결 | 영향과 회귀 범위를 찾을 수 있는가? |
| 협업 | 의견, 첨부, 알림, 승인 기록 | 결정 근거가 이력에 남는가? |
| 분석 | 추세, 누적, 재오픈, 모듈별 분포 | 수치를 맥락 없이 목표화하지 않는가? |

조직에 따라 상태 이름은 달라질 수 있다. 시험에서는 이름을 암기하기보다 `발견 → 등록 → 분석·분류 → 배정 → 수정 → 재시험 → 종료 또는 재오픈`의 흐름을 이해한다.

### 2.2 좋은 결함 보고서

필수 정보는 다음과 같다.

- 고유 결함 ID와 간결한 제목
- 발견한 빌드·환경·데이터·사용자 권한
- 재현 전제조건과 단계
- 기대 결과와 실제 결과
- 재현 빈도와 영향 범위
- 화면, 로그, 입력·출력 등 필요한 증거
- 관련 요구사항과 테스트 케이스
- 심각도, 우선순위, 담당자와 상태

나쁜 제목: `로그인 안 됨`

개선 제목: `[모바일/일반회원] 올바른 인증정보 입력 후 로그인 버튼을 누르면 응답 없이 로딩 상태가 유지됨`

재현 절차는 “로그인해 본다”가 아니라 시작 상태, 입력값 범주, 조작 순서, 관찰 결과를 번호로 쓴다. 실제 개인정보나 비밀키를 증거에 첨부하지 않는다.

### 2.3 심각도와 우선순위

**심각도(Severity)**는 결함이 시스템과 사용자에게 미치는 기술·업무 영향의 크기다. **우선순위(Priority)**는 언제 얼마나 먼저 수정할지를 나타내는 처리 순서다.

둘은 관련 있지만 같지 않다.

- 심각도 높음·우선순위 높음: 결제가 이중 청구됨
- 심각도 낮음·우선순위 높음: 공개 직전 첫 화면의 회사명 오탈자
- 심각도 높음·우선순위 상대적 낮음: 사용하지 않는 실험 기능의 데이터 손상

우선순위는 출시 일정, 노출 빈도, 우회 방법, 규제, 수정 위험 등을 함께 고려한다. “심각도가 높으면 반드시 같은 단계의 우선순위”라고 기계적으로 대응시키지 않는다.

### 2.4 결함 생명주기

```text
발견
  ↓
등록·중복 확인
  ↓
분석·심각도/우선순위 결정
  ↓
담당 배정
  ↓
수정 및 자체 확인
  ↓
재시험 ─ 실패 → 재오픈
  ↓ 성공
회귀 영향 확인
  ↓
종료
```

`수정 완료`와 `결함 종료`는 다르다. 수정자는 변경을 완료할 수 있지만, 원래 실패가 해소됐고 관련 기능에 부작용이 없는지 독립적으로 재시험한 뒤 종료한다.

### 2.5 결함 지표 해석

- 기간별 신규·종료·미해결 추세
- 모듈·원인·심각도별 분포
- 결함 재오픈 비율
- 테스트 단계별 발견과 운영 누출
- 발견부터 해결까지 걸린 시간

수치가 높거나 낮다는 사실만으로 품질을 단정하지 않는다. 테스트 강도, 변경량, 시스템 규모, 분류 기준이 함께 필요하다. 결함이 0개라는 결과는 완벽한 품질이 아니라 테스트가 부족하다는 신호일 수도 있다.

## 3. 결함관리 도구 선정 기준

1. 조직의 상태 흐름과 필수 필드를 표현할 수 있는가?
2. 요구·테스트·코드 변경·릴리스와 연결할 수 있는가?
3. 권한, 감사 이력, 민감정보 보호가 가능한가?
4. 검색, 중복 탐지, 대시보드와 보고 기능이 충분한가?
5. 개발·배포 도구와 필요한 범위에서 연동 가능한가?
6. 사용자 수와 프로젝트 증가를 감당하는가?
7. 데이터 내보내기·이관과 장기 보존이 가능한가?
8. 지나친 입력 부담 없이 필요한 품질 정보를 확보하는가?

기능이 많은 도구보다 실제 업무 흐름을 일관되게 운영할 수 있는 도구가 적합하다. 도구를 도입하면서 결함 분류 기준과 상태 전이 책임도 함께 정의해야 한다.

## 4. 토픽 ② 테스트 자동화 도구

### 4.1 정의

**테스트 자동화 도구**는 테스트 준비, 실행, 결과 비교, 보고, 반복 수행의 일부를 소프트웨어로 지원한다. 자동화의 대상은 단순 클릭만이 아니다.

| 유형 | 자동화 대상 | 주의점 |
|---|---|---|
| 정적 검사 | 실행 없이 코드·규칙·구조 분석 | 실제 실행 실패를 모두 찾지는 못함 |
| 단위 테스트 | 함수·클래스의 빠른 반복 검증 | 외부 의존을 격리하고 경계를 명확히 함 |
| API 테스트 | 요청·응답·오류 계약 검증 | 인증·데이터·비동기 결과를 고려 |
| UI 테스트 | 사용자 흐름과 화면 상호작용 | 화면 변경에 취약하고 실행 비용이 큼 |
| 성능 테스트 | 부하·응답·자원 사용 측정 | 현실적인 시나리오와 환경 필요 |
| 커버리지 측정 | 실행된 코드 범위 확인 | 높은 비율이 좋은 판정을 보장하지 않음 |
| 테스트 데이터·가상화 | 반복 가능한 데이터와 대체 서비스 제공 | 실제 시스템과 차이를 관리 |
| 실행·보고 | 일정·변경에 따른 실행과 결과 수집 | 불안정 테스트와 오탐을 관리 |

### 4.2 자동화에 적합한 테스트

- 반복 실행 빈도가 높다.
- 기대 결과가 명확하고 기계적으로 비교 가능하다.
- 입력 조합이 많고 데이터 기반 실행이 유리하다.
- 회귀 검사가 자주 필요하다.
- 사람이 반복하면 시간과 오류가 많이 든다.
- 환경과 테스트 데이터가 안정적으로 준비된다.

반대로 탐색적 평가, 새 기능의 사용성, 시각적 인상, 요구가 급변하는 초기 화면은 사람의 판단이 더 중요할 수 있다. 모든 테스트를 자동화하는 것이 목표가 아니다.

### 4.3 자동화 접근 방식

**기록·재생 방식**은 빠르게 시작할 수 있지만 화면 위치와 순서 변경에 취약할 수 있다.

**스크립트 방식**은 코드로 절차와 검증을 작성한다. 유연하지만 프로그래밍 능력과 유지보수가 필요하다.

**데이터 주도 방식**은 테스트 절차와 입력·기대 데이터를 분리하여 같은 흐름을 여러 데이터로 반복한다.

**키워드 주도 방식**은 `로그인`, `검색`, `확인` 같은 업무 동작을 키워드로 정의하여 조합한다. 비개발자와 공유하기 쉬울 수 있지만 키워드 계층을 관리해야 한다.

**혼합 방식**은 목적에 맞춰 여러 방식을 조합한다. 이름보다 변경에 강하고 실패 원인을 진단하기 쉬운 구조인지가 중요하다.

## 5. 자동화 구축 절차

### 단계 1: 목표와 범위를 정한다

회귀 시간 단축, 결함 조기 발견, 반복 데이터 검증 등 자동화 목적을 정한다. 자동화 비율 자체를 목표로 삼지 않는다.

### 단계 2: 후보를 평가한다

실행 빈도, 업무 위험, 안정성, 판정 가능성, 수동 비용, 데이터·환경 준비도를 평가하여 우선순위를 정한다.

### 단계 3: 도구와 계층을 선택한다

같은 결과를 더 낮은 계층에서 빠르고 안정적으로 확인할 수 있다면 과도한 UI 자동화를 피한다. 단위·API·UI 검사는 서로 다른 위험을 다루므로 균형을 잡는다.

### 단계 4: 재사용 가능한 구조를 설계한다

테스트 데이터, 화면·API 접근, 검증, 보고를 분리한다. 한 화면 문구가 바뀔 때 수십 테스트를 직접 수정하지 않도록 변경 지점을 모은다.

### 단계 5: 환경과 데이터를 통제한다

테스트 시작 상태, 계정, 시간, 외부 서비스, 데이터 정리 규칙을 명확히 한다. 테스트 순서에 의존하지 않게 만든다.

### 단계 6: 실행·판정·보고를 연결한다

코드 변경이나 일정에 따라 실행하고, 실패 증거와 관련 결함을 연결한다. 실패가 제품 결함인지 자동화 코드·환경 결함인지 분류한다.

### 단계 7: 유지보수한다

중복 테스트, 오래된 시나리오, 불안정 테스트를 정리한다. 반복적으로 성공·실패가 바뀌는 테스트를 방치하면 경고를 무시하게 된다.

## 6. 결함관리와 테스트 자동화의 연결

```text
자동 테스트 실패
  ↓
재실행·환경 확인
  ↓
제품 결함이면 결함관리 도구에 등록
  ↓
테스트 실행, 로그, 데이터, 빌드와 연결
  ↓
수정 후 해당 자동 테스트 재실행
  ↓
관련 회귀 테스트 통과 후 종료 판단
```

자동 실패마다 곧바로 결함을 생성하면 환경 오류와 일시적 네트워크 문제로 중복 결함이 쌓일 수 있다. 반대로 실패를 자동화 문제로만 치부하면 실제 결함이 누락된다. 분류 기준과 사람이 확인할 경계를 정한다.

## 7. 적용 예시: 주문 결제

### 자동화 후보

- 정상 주문의 금액·상태 검증
- 재고 부족, 결제 거절, 중복 요청의 API 결과
- 다양한 할인·세금 입력의 계산 결과
- 핵심 구매 흐름의 제한된 UI 회귀 검사

### 결함 보고 예

```text
제목: 동일 결제 요청을 재전송하면 주문 금액이 두 번 승인됨
환경: 통합 시험 환경, 빌드 식별자 기록
전제: 결제 가능한 주문 1건
절차: 동일 요청 식별자로 결제 요청을 2회 전송
기대: 두 번째 요청은 기존 결과 반환, 추가 승인 없음
실제: 승인 기록 2건 생성
영향: 중복 청구 가능
증거: 요청 식별자, 응답, 관련 로그의 비밀값 제거본
```

자동화 테스트는 같은 요청 식별자로 재전송하고 승인 기록 수를 검증한다. 수정 후 원 테스트와 주문 취소·환불·정상 결제 회귀 검사를 함께 실행한다.

---

## 8. 시험 함정

1. 테스트 실패 현상과 원인 결함을 항상 1:1로 본다.
2. 심각도와 우선순위를 같은 개념으로 본다.
3. 수정 완료 상태를 결함 종료와 동일시한다.
4. 결함 수가 적으면 무조건 품질이 높다고 판단한다.
5. 테스트 자동화를 사람의 판단이 전혀 필요 없는 활동으로 본다.
6. UI 기록·재생이 모든 자동화에 가장 적합하다고 생각한다.
7. 커버리지 100%면 모든 요구가 검증됐다고 판단한다.
8. 불안정한 자동 테스트를 제품 결함으로 자동 등록해 중복을 늘린다.
9. 자동화 작성 비용만 보고 데이터·환경·유지보수 비용을 무시한다.

## 9. 확인 문제

### 문제 1

심각도와 우선순위의 차이를 예와 함께 설명하라.

### 문제 2

결함을 수정한 개발자가 상태를 `수정 완료`로 바꾸었다. 바로 종료하면 안 되는 이유는 무엇인가?

### 문제 3

데이터 주도 자동화와 키워드 주도 자동화의 중심 분리 대상은 각각 무엇인가?

### 문제 4

자동화에 적합한 테스트의 특성을 세 가지 쓰라.

## 정답과 해설

1. **정답**: 심각도는 결함의 기술·업무 영향, 우선순위는 수정 처리 순서다. 데이터 손상은 심각도가 높고, 공개 직전 첫 화면 오탈자는 영향은 낮아도 우선 처리될 수 있다.
2. **정답**: 원래 실패 조건에서 수정 효과를 재시험하고 관련 기능의 회귀 영향이 없는지 확인해야 하기 때문이다. 실패하면 재오픈한다.
3. **정답**: 데이터 주도는 테스트 절차와 입력·기대 데이터를 분리하고, 키워드 주도는 업무 동작을 키워드로 정의해 테스트 시나리오와 구현을 분리한다.
4. **정답 예**: 반복 빈도가 높음, 기대 결과가 명확함, 입력 조합이 많음, 회귀 위험이 큼, 환경과 데이터가 안정적임 중 세 가지다.

## 10. 최종 요약

- **결함관리 도구**는 결함의 재현 가능한 등록, 분류, 배정, 상태, 추적, 이력과 분석을 지원한다.
- 심각도는 영향, 우선순위는 처리 순서이며 수정 후 재시험과 회귀 확인을 거쳐 종료한다.
- **테스트 자동화 도구**는 준비·실행·비교·보고를 반복 가능하게 하지만 테스트 목적과 사람의 판단을 대신하지 않는다.
- 자동화는 반복성, 위험, 판정 가능성, 안정성, 유지비를 평가하고 단위·API·UI 등 적절한 계층을 선택한다.
- 자동 실패와 결함관리 흐름을 연결하되 제품 결함, 자동화 코드, 환경 오류를 구분해야 한다.
