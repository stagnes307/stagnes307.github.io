# 2-4-2-2. 통합 테스트

> **공식 범위**: 2026년 정보처리기사 출제기준의 `소프트웨어개발 > 애플리케이션 테스트 관리 > 애플리케이션 통합 테스트 > 3. 통합 테스트`를 바탕으로 **통합 테스트**, **애플리케이션 통합 테스트의 적용 절차와 판단 기준**을 학습한다. 특정 시험 도구의 사용법은 이전 레슨 범위이므로, 결합 순서·대역 구성·인터페이스 위험·수행 및 종료 판단에 집중한다.

각 모듈이 단독으로 정상이어도 함께 연결하면 실패할 수 있다. 데이터 형식, 호출 순서, 상태 공유, 오류 해석, 시간 조건이 다르기 때문이다. 통합 테스트는 이런 **모듈 사이의 관계와 협력**을 검증한다.

---

## 1. 토픽 ① 통합 테스트

### 1.1 정의

**통합 테스트**는 단위 테스트를 마친 모듈, 컴포넌트, 서브시스템 또는 외부 시스템을 결합하여 인터페이스와 상호작용이 설계대로 동작하는지 확인하는 테스트 단계다.

주요 검증 대상:

- 호출 인터페이스와 매개변수 순서
- 데이터 형식, 단위, 문자 인코딩, 필수값
- 메시지 순서, 동기·비동기 처리, 시간 제한
- 상태 전이와 트랜잭션 경계
- 오류 코드, 예외, 재시도, 취소와 보상
- 공유 자원, 동시성, 중복 요청
- 외부 서비스 장애와 지연

통합 테스트의 목적은 개별 함수의 모든 분기를 다시 검사하는 것이 아니다. **연결 때문에 새로 생기는 위험**을 우선한다.

### 1.2 테스트 단계 비교

| 단계 | 주된 대상 | 중심 질문 |
|---|---|---|
| 단위 테스트 | 함수·클래스·모듈 내부 | 개별 단위가 명세대로 계산하는가? |
| 통합 테스트 | 단위 사이 인터페이스·협력 | 연결 시 데이터와 제어가 올바르게 흐르는가? |
| 시스템 테스트 | 완성 시스템 전체 | 전체 기능·품질 요구를 만족하는가? |
| 인수 테스트 | 사용자·발주 관점의 업무 수용 | 실제 목적과 인수 기준을 만족하는가? |

같은 시나리오가 여러 단계에 나타날 수 있지만 관찰 범위와 실패 원인 탐색 수준이 다르다.

## 2. 통합 전략

### 2.1 빅뱅 통합(Big Bang Integration)

모든 또는 대부분의 모듈을 한 번에 결합한 뒤 테스트한다.

장점:

- 작은 시스템에서는 별도 대역 작성이 적을 수 있다.
- 전체 연결 모습을 빠르게 구성할 수 있다.

단점:

- 실패 원인이 어느 인터페이스인지 격리하기 어렵다.
- 결함이 누적된 뒤 발견될 수 있다.
- 일부 모듈이 늦으면 전체 시험이 지연된다.
- 중간 상태를 관찰하기 어렵다.

“한 번에 통합하므로 가장 빠르다”라고 단정하면 안 된다. 원인 분석과 재시험 비용이 크게 늘 수 있다.

### 2.2 점진적 통합(Incremental Integration)

모듈을 정한 순서로 조금씩 결합하며 각 단계에서 테스트한다. 실패 원인 범위를 좁히고 조기 결함 발견에 유리하다. 대신 결합 순서와 테스트 대역을 계획해야 한다.

#### 하향식 통합(Top-Down)

상위 제어 모듈부터 하위 모듈 방향으로 통합한다. 아직 준비되지 않은 하위 모듈은 **스텁(Stub)**으로 대체한다.

- 장점: 주요 제어 흐름과 사용자 관점의 상위 구조를 일찍 검증할 수 있다.
- 단점: 하위 기능을 단순화한 스텁이 많이 필요할 수 있고 상세 처리 검증이 늦어진다.

스텁은 상위 모듈이 호출할 하위 모듈의 인터페이스를 흉내 내어 정해진 응답을 반환한다.

#### 상향식 통합(Bottom-Up)

하위 기능 모듈부터 결합하여 상위 방향으로 진행한다. 아직 준비되지 않은 상위 호출자는 **드라이버(Driver)**로 대체한다.

- 장점: 하위 유틸리티와 데이터 처리 기능을 조기에 충분히 검증할 수 있다.
- 단점: 전체 제어 흐름과 사용자 기능은 상대적으로 늦게 확인된다.

드라이버는 상위 모듈처럼 하위 모듈을 호출하고 입력을 제공하며 결과를 관찰한다.

#### 샌드위치·혼합 통합

상위와 하위에서 동시에 진행해 중간 계층에서 합친다. 병렬 진행이 가능하지만 계획과 대역 관리가 복잡해지고 중간 계층의 책임이 불명확하면 결합 위험이 집중될 수 있다.

---

## 3. 스텁과 드라이버 비교

| 구분 | 스텁 | 드라이버 |
|---|---|---|
| 대신하는 대상 | 아직 없는 하위 호출 대상 | 아직 없는 상위 호출자 |
| 주로 사용 | 하향식 통합 | 상향식 통합 |
| 역할 | 호출을 받아 가짜 응답 제공 | 시험 대상을 호출하고 입력 제공 |
| 주의 | 실제 하위 시스템의 지연·오류를 충분히 재현해야 함 | 실제 상위 흐름의 호출 조건을 충분히 재현해야 함 |

암기 요령은 “상위에서 아래로 내려갈 때 아래가 없으므로 스텁, 아래에서 위로 올라갈 때 위가 없으므로 드라이버”다.

대역은 실제 구현과 계약이 달라질 수 있다. 대역 테스트가 성공해도 실제 시스템 연결에서 실패할 수 있으므로 최종적으로 실제 구성 요소와의 시험이 필요하다.

---

## 4. 통합 순서 선정 기준

결합 순서는 단순 개발 완료 순서만으로 정하지 않는다.

1. **업무 위험**: 실패 영향이 큰 결제·권한·데이터 변경 경로를 우선한다.
2. **기술 위험**: 새 기술, 복잡한 프로토콜, 비동기·외부 연계를 우선 확인한다.
3. **의존 관계**: 공통 하위 모듈과 핵심 인터페이스의 준비 상태를 본다.
4. **사용 빈도**: 핵심 사용자 흐름과 빈번한 경로를 먼저 연결한다.
5. **변경 가능성**: 자주 바뀌거나 불안정한 계약을 조기에 검증한다.
6. **관찰 가능성**: 실패를 추적할 로그·상태·식별자를 준비할 수 있는가?

위험 기반 순서와 아키텍처의 계층 구조를 조합한다. 모든 인터페이스를 같은 깊이로 테스트하지 않고 영향과 실패 가능성에 따라 우선순위를 둔다.

## 5. 토픽 ② 애플리케이션 통합 테스트의 적용 절차와 판단 기준

### 5.1 진입 조건 확인

통합을 시작하기 전에 다음을 확인한다.

- 대상 모듈의 단위 테스트가 합의 기준을 통과했는가?
- 인터페이스 명세와 버전이 식별됐는가?
- 중대한 미해결 결함과 제한사항을 알고 있는가?
- 필요한 스텁·드라이버·가상 서비스가 준비됐는가?
- 테스트 환경, 계정, 데이터, 관찰 수단이 준비됐는가?

진입 조건은 완벽한 무결함을 뜻하지 않는다. 알려진 위험을 받아들일지 명시적으로 판단하기 위한 기준이다.

### 5.2 계획과 시나리오 설계

1. 통합 대상과 범위를 확정한다.
2. 인터페이스 목록과 의존 관계를 정리한다.
3. 결합 전략과 단계별 순서를 정한다.
4. 정상·경계·오류·장애 시나리오를 설계한다.
5. 입력 데이터와 기대 결과, 관찰 지점을 정한다.
6. 환경, 역할, 일정, 진입·종료 기준을 기록한다.

시나리오는 단순한 화면 단계보다 컴포넌트 사이의 데이터와 상태를 드러내야 한다.

### 5.3 환경과 데이터 준비

운영과 유사한 통신 경계, 설정, 시간 조건을 준비하되 실제 비밀정보와 개인정보를 사용하지 않는다. 테스트 데이터는 시작 상태와 정리 규칙이 있어야 반복 결과가 같다.

비동기 흐름에서는 요청 식별자, 메시지 ID, 상태 변경 시간을 기록해 하나의 거래를 끝까지 추적할 수 있게 한다.

### 5.4 단계별 실행

정해진 순서로 모듈을 추가하고 각 단계에서 다음을 확인한다.

- 요청과 응답 구조
- 데이터 변환 전후 값과 단위
- 호출·메시지 순서
- 상태 전이와 저장 결과
- 오류 전파와 복구
- 시간 초과, 재시도, 중복 처리
- 이미 통합된 기능의 회귀

새 모듈을 추가한 직후 실패하면 직전 성공 기준과 새 연결을 비교해 원인 범위를 좁힌다.

### 5.5 결함 처리와 재시험

실패를 재현 가능한 정보로 기록하고 제품 결함, 환경·데이터 문제, 테스트 대역 차이를 구분한다. 수정 후 실패한 시나리오를 재시험하고 관련 인터페이스의 회귀 시험을 수행한다.

### 5.6 종료 판단과 보고

통합이 끝났다고 달력 날짜만으로 선언하지 않는다. 합의한 종료 기준과 잔여 위험을 보고 승인한다.

## 6. 판단 기준

### 기능 정확성

결합된 흐름이 요구한 업무 결과와 상태를 만드는가?

### 인터페이스 일치성

요청·응답 필드, 필수값, 자료형, 단위, 순서와 오류 코드가 명세와 같은가?

### 데이터 무결성

변환·저장·전송 과정에서 데이터가 누락·중복·왜곡되지 않는가? 트랜잭션의 전부 또는 일부 실패 의미가 분명한가?

### 오류·장애 처리

시간 초과, 외부 실패, 부분 성공, 재시도, 중복 요청에서 일관된 결과를 내고 복구 가능한가?

### 관찰·추적 가능성

요청 식별자, 로그, 상태를 통해 모듈 사이 흐름과 실패 지점을 찾을 수 있는가?

### 품질 요구

통합 환경에서 응답, 처리량, 보안, 가용성 등 합의한 품질 기준을 만족하는가? 이 레슨에서는 개별 성능 알고리즘보다 통합 경계의 품질 판정을 본다.

### 회귀 안정성

새 연결이나 수정이 이미 통과한 기능을 깨뜨리지 않았는가?

---

## 7. 종료 기준 예시

- 계획한 필수 인터페이스와 핵심 시나리오가 실행됨
- 업무 치명적 결함이 없거나 승인된 예외만 남음
- 미해결 결함의 영향·우회·계획이 기록됨
- 핵심 오류·복구·중복 시나리오가 기준을 만족함
- 요구사항과 테스트 결과의 추적이 완성됨
- 회귀 테스트가 합의 기준을 통과함
- 잔여 위험을 이해관계자가 검토하고 승인함

단순 통과율 하나만으로 종료하지 않는다. 실행하지 못한 테스트와 테스트하지 않은 환경이 무엇인지 함께 보고한다.

## 8. 적용 예시: 주문-결제-재고 통합

### 인터페이스

```text
주문 서비스 → 결제 서비스: 결제 요청 / 승인·거절·시간 초과
주문 서비스 → 재고 서비스: 예약 요청 / 예약·부족·중복
주문 서비스 → 알림: 주문 확정 이벤트
```

### 핵심 시나리오

1. 결제 승인과 재고 예약 성공 → 주문 확정
2. 결제 거절 → 재고 예약 없음, 주문 거절
3. 결제 승인 후 재고 부족 → 결제 취소 또는 보상 정책 실행
4. 동일 요청 재전송 → 중복 승인·예약 없음
5. 알림 실패 → 주문 확정 상태는 유지하고 재처리 가능

### 점진 통합

먼저 주문과 결제 대역을 연결해 승인·거절·시간 초과를 검증하고, 실제 결제 인터페이스로 교체한다. 다음으로 재고를 추가해 부분 성공과 보상 흐름을 시험한다. 마지막으로 비동기 알림을 연결하고 지연·중복 이벤트를 검증한다.

### 판단

화면에 “주문 완료”가 표시됐다는 사실만 보지 않는다. 주문 상태, 승인 기록, 재고 예약, 이벤트 발행이 같은 거래 식별자와 기대 순서로 일치하는지 확인한다.

---

## 9. 시험 함정

1. 통합 테스트를 단위 테스트를 모두 다시 실행하는 단계로 본다.
2. 빅뱅 통합은 대역이 적으므로 항상 가장 빠르고 좋다고 판단한다.
3. 하향식의 스텁과 상향식의 드라이버를 뒤바꾼다.
4. 스텁·드라이버 성공을 실제 시스템 연결 성공과 동일시한다.
5. 정상 요청·응답만 검사하고 시간 초과·부분 성공·중복을 누락한다.
6. 테스트 순서를 개발 완료 순서로만 정하고 위험을 고려하지 않는다.
7. 결합 후 화면 결과만 확인하고 데이터·상태·로그를 보지 않는다.
8. 통과율만으로 종료하고 미실행·잔여 위험을 숨긴다.

## 10. 확인 문제

### 문제 1

하향식 통합과 상향식 통합에서 각각 필요한 테스트 대역과 그 역할을 설명하라.

### 문제 2

빅뱅 통합의 가장 큰 진단상 단점은 무엇인가?

### 문제 3

주문 서비스가 결제 성공 후 재고 부족을 받았다. 통합 테스트에서 반드시 확인할 항목을 두 가지 쓰라.

### 문제 4

통합 테스트 종료를 통과율 하나로 판단하면 안 되는 이유는 무엇인가?

## 정답과 해설

1. **정답**: 하향식에서는 아직 없는 하위 모듈을 스텁이 대신해 응답한다. 상향식에서는 아직 없는 상위 호출자를 드라이버가 대신해 하위 모듈을 호출하고 결과를 관찰한다.
2. **정답**: 여러 모듈을 한꺼번에 연결하므로 실패가 어느 인터페이스와 변경에서 발생했는지 격리하기 어렵다.
3. **정답 예**: 결제 취소·보상 정책이 실행되는지, 주문 상태가 일관되는지, 중복 보상이 없는지, 동일 식별자로 거래를 추적할 수 있는지 중 두 가지다.
4. **정답**: 미실행 시나리오, 결함의 심각도, 핵심 오류·복구 경로, 잔여 위험과 회귀 결과를 반영하지 못하기 때문이다.

## 11. 최종 요약

- **통합 테스트**는 모듈 사이 인터페이스, 데이터·제어 흐름, 상태, 오류와 장애 처리를 검증한다.
- 빅뱅은 한 번에 결합하고, 점진 통합은 단계별로 결합하여 원인 격리와 조기 발견에 유리하다.
- 하향식은 스텁, 상향식은 드라이버를 사용하며 최종적으로 실제 구성 요소와 연결해야 한다.
- **애플리케이션 통합 테스트의 적용 절차와 판단 기준**은 진입 조건 → 계획·순서 → 환경·데이터 → 단계 실행 → 결함·회귀 → 종료·위험 보고로 구성한다.
- 종료는 기능 정확성, 인터페이스·데이터 일치, 오류 처리, 추적성, 품질 요구, 회귀와 잔여 위험을 함께 판단한다.
