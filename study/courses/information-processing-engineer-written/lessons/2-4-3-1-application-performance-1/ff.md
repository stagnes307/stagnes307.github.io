# 2-4-3-1. 알고리즘

> **공식 범위**: 2026년 정보처리기사 출제기준의 `소프트웨어개발 > 애플리케이션 테스트 관리 > 애플리케이션 성능 개선 > 1. 알고리즘`을 바탕으로 **알고리즘**, **애플리케이션 성능 개선의 적용 절차와 판단 기준**을 학습한다. 특정 소스코드 분석 제품이나 언어별 최적화 기능은 다음 레슨 범위이므로, 문제 해결 절차·복잡도·측정 기반 개선 원칙에 집중한다.

성능이 느리다고 코드를 짧게 바꾸는 것이 곧 최적화는 아니다. 먼저 정확한 입력·출력과 성능 목표를 정하고, 실제 병목을 측정하며, 더 적절한 알고리즘과 자료구조를 선택한 뒤 정확성과 회귀를 검증해야 한다.

---

## 1. 토픽 ① 알고리즘

### 1.1 정의

**알고리즘**은 주어진 문제를 해결하기 위해 입력을 받아 유한한 단계의 명확한 연산을 수행하고 결과를 내는 절차다. 프로그램은 알고리즘을 특정 언어와 실행환경으로 구현한 것이다.

알고리즘의 일반적 특성:

1. **입력**: 0개 이상의 입력을 받을 수 있다.
2. **출력**: 1개 이상의 결과를 만든다.
3. **명확성**: 각 단계의 의미와 실행 순서가 모호하지 않다.
4. **유한성**: 유한한 단계 뒤에 종료한다.
5. **유효성**: 각 연산이 실제 수행 가능한 기본 작업이다.

같은 문제를 해결하는 알고리즘이 여러 개일 수 있으며, 입력 크기·분포·메모리·실시간성·구현 난이도에 따라 적합성이 달라진다.

### 1.2 표현 방법

- **자연어**: 이해하기 쉽지만 모호성이 생길 수 있다.
- **의사코드**: 언어 문법에 덜 의존하면서 제어와 자료 처리를 명확히 표현한다.
- **순서도**: 시작·종료, 처리, 판단, 입력·출력과 흐름을 도형으로 표현한다.
- **프로그램 코드**: 실제 실행 가능하지만 언어와 환경의 세부에 영향을 받는다.

시험에서 의사코드를 읽을 때는 변수 초기값, 반복 범위, 조건 경계, 종료 조건, 자료구조 연산 비용을 표시한다.

---

## 2. 알고리즘 정확성

빠르더라도 잘못된 결과를 내면 좋은 알고리즘이 아니다. 정확성은 다음 관점으로 확인한다.

### 사전 조건과 사후 조건

- 사전 조건: 알고리즘 실행 전에 입력이 만족해야 할 조건
- 사후 조건: 종료 후 결과가 만족해야 할 조건

예: 이진 탐색의 사전 조건은 탐색 대상 배열이 비교 기준에 따라 정렬되어 있다는 것이다. 정렬되지 않은 배열에 적용하면 빠르게 실행돼도 결과를 보장하지 못한다.

### 불변식

반복 중에도 계속 참이어야 하는 성질이다. 이진 탐색에서는 “찾는 값이 존재한다면 현재 탐색 구간 안에 있다”는 성질을 유지해야 한다.

### 경계값

빈 입력, 원소 1개, 첫·마지막 위치, 중복값, 최솟값·최댓값, 매우 큰 입력을 확인한다. `&lt;`와 `&lt;=` 차이로 마지막 원소를 누락하거나 무한 반복이 생길 수 있다.

## 3. 시간 복잡도와 공간 복잡도

### 3.1 복잡도의 의미

**시간 복잡도**는 입력 크기 증가에 따라 기본 연산 횟수가 어떻게 증가하는지 나타낸다. **공간 복잡도**는 입력 외에 필요한 추가 메모리가 어떻게 증가하는지 나타낸다.

실제 초 단위 실행 시간은 하드웨어, 언어, 데이터, 캐시, 네트워크 등에 영향을 받는다. 복잡도는 이런 환경을 모두 무시한다는 뜻이 아니라 입력 규모에 따른 증가 경향을 비교하는 추상적 도구다.

### 3.2 Big-O 표기

Big-O는 보통 입력이 커질 때 증가율의 상한을 표현한다. 상수 계수와 낮은 차수 항을 생략해 성장 형태에 집중한다.

```text
3n² + 5n + 20  →  O(n²)
7n + 10        →  O(n)
```

그러나 같은 O(n) 알고리즘도 상수 비용과 데이터 접근 방식 때문에 실제 시간은 다를 수 있다. 복잡도와 측정은 보완 관계다.

### 3.3 자주 비교하는 증가율

| 복잡도 | 대표적 의미 | 입력이 커질 때 |
|---|---|---|
| O(1) | 입력 크기와 무관한 일정 연산 | 가장 완만함 |
| O(log n) | 탐색 범위를 일정 비율로 축소 | 매우 완만함 |
| O(n) | 입력을 한 번 순회 | 선형 증가 |
| O(n log n) | 효율적 비교 정렬 등 | 선형보다 조금 빠르게 증가 |
| O(n²) | 모든 쌍 비교, 중첩 순회 | 큰 입력에서 급증 |
| O(2ⁿ) | 부분집합 조합 탐색 등 | 작은 증가에도 폭발적 |
| O(n!) | 모든 순열 탐색 등 | 매우 빠르게 폭발 |

일반적으로 `O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2ⁿ) < O(n!)` 순으로 증가한다.

### 3.4 최선·평균·최악의 경우

- **최선의 경우**: 가장 유리한 입력에서 필요한 연산
- **평균의 경우**: 가정한 입력 분포에서 기대되는 연산
- **최악의 경우**: 가장 불리한 입력에서 필요한 연산

실시간·안전 중요 시스템은 최악 지연의 상한이 중요할 수 있고, 일반 서비스는 평균과 상위 백분위 응답을 함께 볼 수 있다. 어떤 경우를 분석했는지 명시한다.

## 4. 대표 알고리즘 비교

### 4.1 선형 탐색과 이진 탐색

**선형 탐색**은 처음부터 순서대로 비교한다. 정렬이 필요 없고 O(n)이다.

**이진 탐색**은 정렬된 자료의 중간값과 비교하여 탐색 구간을 절반씩 줄인다. 탐색은 O(log n)이지만 정렬 유지 비용과 무작위 접근 가능성을 고려해야 한다.

```text
binarySearch(sortedValues, target):
    left ← 0
    right ← length(sortedValues) - 1
    while left ≤ right:
        middle ← left + (right - left) / 2의 정수 부분
        if sortedValues[middle] = target: return middle
        if sortedValues[middle] < target: left ← middle + 1
        else: right ← middle - 1
    return NOT_FOUND
```

데이터를 한 번만 탐색하는데 정렬 비용이 더 크다면 선형 탐색이 실용적일 수 있다. 반복 탐색과 정렬 유지 여부를 함께 본다.

### 4.2 정렬 알고리즘의 선택 관점

정렬에서는 비교 횟수만 보지 않는다.

- 최선·평균·최악 시간 복잡도
- 추가 메모리 사용
- 같은 키의 상대 순서를 유지하는 안정성
- 입력이 거의 정렬됐는지 여부
- 외부 저장장치에 있는 대용량 데이터인지 여부
- 구현 복잡성과 표준 라이브러리의 검증 수준

버블 정렬은 이해하기 쉽지만 일반적으로 O(n²) 비교가 커진다. 병합 정렬은 O(n log n) 시간과 안정성을 제공할 수 있지만 추가 공간이 필요하다. 퀵 정렬은 평균적으로 효율적일 수 있으나 피벗과 입력에 따라 최악 O(n²)이 가능하다. 특정 정렬이 모든 상황에서 최고라고 단정하지 않는다.

### 4.3 해시 기반 조회

해시 구조는 평균적으로 빠른 키 조회를 제공할 수 있지만 충돌, 해시 품질, 메모리 사용, 순서 보장, 최악의 경우를 고려한다. 범위 검색이나 정렬 순회가 중요하면 트리 계열 구조가 더 적합할 수 있다.

## 5. 재귀·반복과 동적 계획법

### 재귀

문제를 같은 형태의 더 작은 문제로 정의한다. 종료 조건이 없거나 입력이 충분히 줄지 않으면 무한 재귀가 발생한다. 호출 스택 비용과 깊이 제한을 고려한다.

### 분할 정복

문제를 독립적인 작은 문제로 나누어 해결하고 결과를 합친다. 병합 정렬, 이진 탐색 등이 관련 예다.

### 동적 계획법

겹치는 부분 문제의 결과를 저장하여 중복 계산을 줄인다. 메모이제이션은 필요할 때 위에서 아래로 저장하고, 테이블 방식은 작은 상태부터 아래에서 위로 계산할 수 있다.

### 탐욕법

각 단계에서 현재 가장 좋아 보이는 선택을 한다. 문제에 탐욕 선택 성질과 최적 부분 구조가 있을 때 전체 최적해를 보장한다. 단순히 빠르다는 이유로 모든 최적화 문제에 적용하면 안 된다.

## 6. 토픽 ② 애플리케이션 성능 개선의 적용 절차와 판단 기준

### 단계 1: 성능 목표를 정의한다

“빠르게”가 아니라 업무 시나리오, 입력 규모, 동시 사용자, 응답 기준, 처리량, 자원 한도를 정한다. 평균만 보면 일부 사용자의 긴 지연을 놓칠 수 있으므로 필요한 분포 기준도 합의한다.

### 단계 2: 기준선을 측정한다

현재 버전의 동일 환경·데이터에서 실행 시간, 처리량, CPU, 메모리, 입출력, 오류를 기록한다. 기준선이 없으면 변경이 개선인지 판단할 수 없다.

### 단계 3: 병목을 식별한다

전체 시간에서 가장 큰 비중과 증가 원인을 찾는다. 추측으로 모든 반복문을 수정하지 않는다. 알고리즘 복잡도, 불필요한 중복 계산, 자료구조, 데이터 접근, 외부 통신, 잠금 대기 등을 구분한다.

### 단계 4: 개선 가설을 세운다

예:

- 이중 순회를 해시 집합 조회로 바꾸면 중복 검사가 O(n²)에서 평균 O(n)에 가까워질 것이다.
- 반복 계산 결과를 재사용하면 동일 입력의 계산 횟수가 줄 것이다.
- 전체 자료 정렬 대신 필요한 상위 일부만 선택하면 비용이 줄 것이다.

가설에는 예상 효과와 메모리·복잡성·정확성 대가를 함께 적는다.

### 단계 5: 작은 범위로 변경한다

한 번에 여러 변수를 바꾸지 않고 병목과 직접 관련된 변경을 적용한다. 읽기 어려운 미세 최적화보다 알고리즘과 자료구조 개선을 우선 검토한다.

### 단계 6: 동일 조건에서 재측정한다

워밍업, 데이터, 부하, 환경과 측정 구간을 일치시킨다. 한 번의 가장 빠른 값이 아니라 반복 결과와 변동을 본다.

### 단계 7: 정확성·회귀·운영성을 검증한다

기능 결과, 경계값, 메모리, 오류 처리, 동시성, 가독성과 유지보수성을 확인한다. 성능이 향상돼도 잘못된 결과나 불안정성이 생기면 채택할 수 없다.

## 7. 성능 개선 판단 기준

| 기준 | 판단 질문 |
|---|---|
| 정확성 | 같은 계약과 결과를 유지하는가? |
| 목표 달성 | 합의한 입력·부하에서 기준을 만족하는가? |
| 확장성 | 입력·사용자 증가 시 증가율이 감당 가능한가? |
| 자원 균형 | 시간 개선 때문에 메모리·네트워크가 과도하게 늘지 않는가? |
| 재현성 | 같은 조건에서 반복 측정해도 효과가 나타나는가? |
| 회귀 안전 | 다른 기능과 경계 입력을 깨뜨리지 않는가? |
| 유지보수성 | 코드가 이해·시험·변경 가능한가? |
| 전체 효과 | 한 구간을 빠르게 해 다른 구간 병목을 악화시키지 않는가? |

최적화는 국소 코드 속도가 아니라 사용자 시나리오와 전체 처리의 개선으로 판단한다.

## 8. 적용 예시: 중복 사용자 찾기

### 기존 알고리즘

```text
for i = 0 to n-1:
    for j = i+1 to n-1:
        if users[i].email = users[j].email:
            중복 기록
```

모든 쌍을 비교하므로 O(n²)이다. 입력이 두 배가 되면 비교 횟수는 약 네 배로 늘 수 있다.

### 개선 알고리즘

```text
seen ← 빈 해시 집합
for user in users:
    normalized ← 이메일 정규화 규칙 적용
    if normalized in seen: 중복 기록
    else: seen에 normalized 추가
```

평균적으로 한 번 순회하므로 O(n)에 가까울 수 있지만 O(n) 추가 공간을 사용한다. 해시 충돌과 정규화 규칙도 정확성에 영향을 준다.

### 검증

- 빈 입력, 한 명, 모든 이메일 동일, 대소문자·공백, 매우 큰 입력
- 기존과 개선 결과 집합의 일치
- 동일 환경에서 입력 크기별 시간과 메모리
- 중복 출력 순서가 계약에 포함되는지 여부

이 예는 시간과 공간의 트레이드오프를 보여 준다. 메모리가 매우 제한되거나 입력이 이미 정렬돼 있다면 다른 선택이 적합할 수 있다.

## 9. 시험 함정

1. 알고리즘과 프로그램을 완전히 같은 개념으로 본다.
2. Big-O를 실제 실행 초 단위와 동일시한다.
3. 상수와 입력 규모를 무시하고 낮은 차수면 항상 빠르다고 단정한다.
4. 이진 탐색의 정렬 사전 조건을 누락한다.
5. 평균 시간만 보고 최악 시간과 지연 분포를 보지 않는다.
6. 시간 복잡도만 개선하고 공간 복잡도와 정확성을 무시한다.
7. 측정 전에 코드를 추측으로 최적화한다.
8. 서로 다른 환경·데이터의 측정값을 직접 비교한다.
9. 성능 향상을 위해 가독성·오류 처리·회귀 검증을 포기한다.

## 10. 확인 문제

### 문제 1

알고리즘의 다섯 가지 일반적 특성을 쓰라.

### 문제 2

`4n² + 100n + 7`의 Big-O와 그 이유를 설명하라.

### 문제 3

이진 탐색이 선형 탐색보다 항상 좋은 선택이 아닌 이유를 두 가지 쓰라.

### 문제 4

성능 개선 전에 기준선과 병목을 측정해야 하는 이유는 무엇인가?

### 문제 5

O(n²) 중복 검사를 해시 집합을 이용한 평균 O(n) 방식으로 바꿀 때 생기는 대표 대가는 무엇인가?

## 정답과 해설

1. **정답**: 입력, 출력, 명확성, 유한성, 유효성이다.
2. **정답**: O(n²)이다. 입력이 커질 때 최고차항 n²이 증가율을 지배하며 상수 계수와 낮은 차수 항은 성장 비교에서 생략한다.
3. **정답 예**: 정렬된 데이터라는 사전 조건이 필요하고, 한 번만 탐색할 때는 정렬 비용이 선형 탐색보다 클 수 있다. 연결 구조처럼 무작위 접근이 어려운 자료에도 부적합할 수 있다.
4. **정답**: 현재 성능과 목표 차이를 알아야 개선 여부를 비교할 수 있고, 전체 시간에 영향이 작은 코드를 최적화하는 낭비를 피하기 위해서다.
5. **정답**: 입력 크기에 비례하는 추가 메모리와 해시 충돌·키 정규화 관리 비용이다.

## 11. 최종 요약

- **알고리즘**은 입력을 받아 유한하고 명확한 유효 단계로 결과를 만드는 문제 해결 절차다.
- 정확성의 사전·사후 조건과 경계값을 먼저 확인하고 시간·공간 복잡도로 입력 증가 경향을 비교한다.
- Big-O와 실제 측정은 보완 관계이며 알고리즘·자료구조 선택은 입력, 메모리, 최악 위험과 함께 판단한다.
- **애플리케이션 성능 개선의 적용 절차와 판단 기준**은 목표 정의 → 기준선 → 병목 → 가설 → 작은 변경 → 동일 조건 재측정 → 정확성·회귀 검증이다.
- 성능 개선은 속도 하나가 아니라 정확성, 자원 균형, 확장성, 재현성, 유지보수성과 전체 사용자 흐름으로 판단한다.
