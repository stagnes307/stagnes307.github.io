# 2-4-3-2. 소스코드 품질분석 도구 · 코드 최적화

> **공식 범위**: 2026년 정보처리기사 출제기준의 `소프트웨어개발 > 애플리케이션 테스트 관리 > 애플리케이션 성능 개선` 가운데 **소스코드 품질분석 도구**, **코드 최적화**를 학습한다. 특정 제품명·버전·규칙 번호는 고정하지 않고, 정적·동적 분석의 차이, 지표 해석, 측정 기반 최적화와 회귀 검증 원칙을 중심으로 다룬다.

분석 도구가 경고를 0개로 만들었다고 좋은 코드가 되는 것은 아니며, 실행 시간이 짧아졌다고 좋은 최적화가 되는 것도 아니다. 도구는 위험 후보를 찾고 증거를 제공한다. 사람은 요구·맥락·영향을 판단하고, 변경 후 기능과 성능을 다시 검증해야 한다.

---

## 1. 소스코드 품질의 관점

소스코드 품질은 문법 오류가 없다는 뜻보다 넓다.

| 관점 | 확인 질문 | 문제 예 |
|---|---|---|
| 정확성 | 요구한 결과와 오류 의미를 지키는가? | 경계값에서 잘못된 계산 |
| 신뢰성 | 예외·자원·동시성을 안정적으로 처리하는가? | 파일 미닫힘, 경쟁 상태 |
| 유지보수성 | 이해·수정·시험하기 쉬운가? | 지나치게 긴 함수, 복잡한 분기 |
| 가독성 | 이름·구조·의도가 명확한가? | 의미 없는 이름, 중첩 과다 |
| 재사용성 | 특정 환경과 불필요하게 얽히지 않는가? | 전역 상태와 하드코딩 |
| 효율성 | 필요한 시간·메모리·입출력 자원을 쓰는가? | 중복 조회, 불필요한 복사 |
| 보안성 | 입력·권한·비밀·오류를 안전하게 다루는가? | 검증 없는 입력, 비밀 로그 |
| 시험 용이성 | 동작을 독립적으로 관찰·대체할 수 있는가? | 숨은 외부 의존과 시간 의존 |

한 지표가 모든 관점을 대표하지 않는다. 복잡도는 낮지만 업무 결과가 틀릴 수 있고, 중복을 줄이려 만든 공통 함수가 오히려 서로 다른 업무를 강하게 묶을 수 있다.

## 2. 토픽 ① 소스코드 품질분석 도구

### 2.1 정적 분석 도구

소스코드를 실행하지 않고 구문, 제어·데이터 흐름, 규칙, 의존 관계를 분석한다.

찾을 수 있는 후보:

- 초기화되지 않은 값, 도달 불가능 코드
- 사용하지 않는 변수·반환값
- 자원 해제 누락과 일부 널 참조 가능성
- 복잡한 조건과 과도한 중첩
- 중복 코드와 순환 의존
- 코딩 표준 위반
- 알려진 위험한 API 사용과 입력 검증 누락 후보
- 하드코딩된 비밀값 후보

장점은 실행 경로를 준비하지 않아도 넓은 코드를 반복 검사할 수 있다는 점이다. 한계는 실제 실행환경과 업무 의미를 모두 알 수 없어 오탐과 미탐이 발생한다는 점이다.

### 2.2 동적 분석 도구

프로그램을 실행하면서 시간, 메모리, 호출, 자원, 오류와 동시성 현상을 관찰한다.

예:

- 함수·구간별 실행 시간과 호출 횟수
- 메모리 할당과 해제, 누수 후보
- CPU, 입출력, 잠금 대기
- 실행 중 예외와 실제 호출 경로
- 부하에 따른 응답과 처리량

실제 실행 증거를 얻지만 실행한 입력과 경로만 관찰한다. 테스트하지 않은 경로의 문제를 자동으로 보장하지 않는다.

### 2.3 정적 분석과 동적 분석 비교

| 구분 | 정적 분석 | 동적 분석 |
|---|---|---|
| 프로그램 실행 | 필요 없음 | 필요함 |
| 분석 범위 | 규칙에 따라 넓은 코드 검사 | 실제 실행된 경로 |
| 강점 | 조기 반복 검사, 표준·구조·흐름 위험 | 실제 시간·메모리·호출 관찰 |
| 한계 | 오탐·실행환경 차이 | 입력·환경에 따라 경로 누락 |
| 활용 시점 | 작성·검토·빌드 과정 | 테스트·성능 검증·운영 진단 |

둘 중 하나가 다른 하나를 대체하지 않는다. 정적 경고로 위험 후보를 찾고 동적 측정과 테스트로 실제 영향을 검증할 수 있다.

## 3. 대표 코드 지표

### 코드 복잡도

분기와 독립 경로가 많을수록 이해와 테스트 부담이 커진다. 순환 복잡도는 제어 흐름의 독립 경로 수를 나타내는 대표 지표다. 수치가 높으면 함수 분리와 조건 구조를 검토할 신호지만, 낮추기 위해 의미 없는 작은 함수로 쪼개면 전체 흐름이 더 어려워질 수 있다.

### 중복

동일·유사 코드가 여러 곳에 존재하면 정책 변경과 결함 수정이 누락될 수 있다. 그러나 우연히 모양만 같은 서로 다른 업무를 하나로 합치면 잘못된 공통화가 된다. 함께 변해야 하는 지식인지 확인한다.

### 크기

파일, 클래스, 함수의 줄 수는 이해 부담의 한 단서다. 주석과 빈 줄을 포함하는 방식이 도구마다 다를 수 있고, 짧다고 자동으로 단순한 것은 아니다.

### 의존성

순환 의존, 불안정한 외부 요소에 대한 의존, 계층 방향 위반을 확인한다. 의존 개수만 줄이는 것보다 의존의 성격과 변경 전파가 중요하다.

### 테스트 커버리지

문장·분기·조건 등이 테스트 중 실행된 정도를 나타낼 수 있다. 높은 커버리지는 미실행 영역을 줄였다는 증거지만 올바른 입력과 판정을 사용했다는 증거는 아니다. 커버리지 수치만 맞추기 위한 무의미한 테스트를 피한다.

## 4. 품질분석 도구 적용 절차

### 단계 1: 품질 정책과 범위를 정한다

적용 언어·모듈, 필수 규칙, 위험 등급, 예외 승인, 기존 코드 처리 방법을 정한다. 모든 규칙을 한꺼번에 적용해 수천 경고를 만들면 중요한 문제를 놓칠 수 있다.

### 단계 2: 기준선을 만든다

기존 경고와 새 경고를 구분한다. 기존 문제를 숨기기 위한 기준선이 아니라 신규 악화를 막고 점진적으로 개선하기 위한 출발점으로 사용한다.

### 단계 3: 자동 분석을 실행한다

개발 중 빠른 검사와 통합 시 전체 검사를 조합한다. 재현 가능한 설정을 공유하고 개인 환경에서만 다른 결과가 나오지 않게 한다.

### 단계 4: 경고를 분류한다

실제 결함·보안 위험, 유지보수 문제, 맥락상 허용, 오탐으로 분류한다. 심각도, 노출 가능성, 영향, 수정 비용을 함께 본다.

### 단계 5: 수정 또는 예외를 결정한다

수정할 때 동작을 바꾸지 않는지 테스트한다. 예외는 이유, 범위, 승인과 재검토 시점을 기록한다. 규칙을 전역으로 꺼서 한 사례를 해결하지 않는다.

### 단계 6: 추세와 효과를 검토한다

신규 경고, 반복 원인, 복잡도 변화, 결함과의 연관을 본다. 경고 수를 개발자 평가 목표로 직접 사용하면 경고 숨기기와 무분별한 억제가 생길 수 있다.

## 5. 도구 선정 기준

1. 사용하는 언어와 빌드 방식을 정확히 분석하는가?
2. 필요한 결함·보안·품질 규칙과 데이터 흐름 분석을 제공하는가?
3. 오탐을 검토하고 예외 근거를 관리할 수 있는가?
4. 결과가 재현 가능하고 변경된 코드에 빠른 피드백을 주는가?
5. 심각도·위치·수정 근거가 이해 가능한가?
6. 기존 개발·검토·통합 흐름과 연계 가능한가?
7. 대규모 코드에서 시간과 자원 비용을 감당하는가?
8. 규칙·결과·이력을 조직이 장기 관리할 수 있는가?

도구마다 지표 계산과 규칙 정의가 다를 수 있다. 서로 다른 도구의 숫자를 직접 순위처럼 비교하지 않는다.

## 6. 토픽 ② 코드 최적화

### 6.1 정의와 우선순위

**코드 최적화**는 요구한 기능과 품질을 유지하면서 실행 시간, 메모리, 입출력, 네트워크, 에너지 등 자원 사용을 개선하는 활동이다.

기본 우선순위:

1. 정확하고 명확하게 동작한다.
2. 성능 목표와 현재 기준선을 측정한다.
3. 실제 병목을 찾는다.
4. 가장 큰 병목부터 안전하게 개선한다.
5. 동일 조건에서 재측정하고 회귀를 검사한다.

“최적화한 것처럼 보이는 코드”와 “측정된 최적화”를 구분한다.

### 6.2 최적화 대상

#### 중복 계산 제거

반복문 안에서 변하지 않는 값을 매번 계산하거나 같은 외부 조회를 반복하는지 확인한다. 결과 재사용은 메모리와 유효기간·일관성 대가가 있다.

#### 자료 변환과 복사 감소

큰 자료를 여러 형식으로 반복 변환하거나 전체 복사하는지 확인한다. 참조 공유는 빠를 수 있지만 변경 가능 자료의 예상치 못한 부작용을 주의한다.

#### 입출력 묶기

작은 파일·네트워크·데이터베이스 요청을 매우 자주 보내면 고정 비용이 커질 수 있다. 묶음 처리는 효율을 높일 수 있지만 지연, 메모리, 실패 단위가 커진다.

#### 캐시

비싼 계산이나 조회 결과를 재사용한다. 적중률, 메모리, 만료, 무효화, 데이터 일관성을 설계해야 한다. 오래된 값이 허용되지 않는 업무에는 신중하다.

#### 객체·자원 생명주기

불필요한 생성과 해제를 줄이고 파일·연결·스레드 등 자원을 적절히 재사용한다. 자원 풀을 너무 크게 만들면 오히려 경쟁과 고갈이 생길 수 있다.

#### 동시성

독립 작업을 병렬화할 수 있지만 잠금, 순서, 공유 상태, 스케줄링 비용과 경쟁 상태를 고려한다. 스레드 수를 늘리는 것이 무조건 빠른 것은 아니다.

## 7. 코드 최적화 절차

### 7.1 목표와 측정 시나리오 정의

입력 크기, 부하, 환경, 워밍업, 측정 구간과 성공 기준을 정한다. 기능별로 목표가 다를 수 있다.

### 7.2 정적·동적 증거 수집

정적 분석의 복잡도·중복·자원 경고와 동적 분석의 시간·호출·메모리·입출력 결과를 함께 본다. 실행 시간이 큰 구간이면서 개선 가능한 원인을 우선한다.

### 7.3 개선 가설 작성

```text
관찰: 사용자 1명 조회에 같은 권한 쿼리가 30회 반복됨
가설: 요청 범위에서 권한 결과를 재사용하면 조회 횟수가 감소함
대가: 요청 중 권한 변경의 반영 시점과 메모리 사용을 확인해야 함
```

### 7.4 작은 변경과 기능 검증

한 번에 하나의 주요 원인을 바꾸고 기존 테스트를 통과시킨다. 경계값, 오류, 동시성 결과가 유지되는지 확인한다.

### 7.5 재측정과 비교

기준선과 같은 조건에서 반복 측정한다. 평균뿐 아니라 변동과 긴 지연을 보고 CPU 감소 대신 메모리나 데이터베이스 부하가 늘지 않았는지 확인한다.

### 7.6 문서화와 회귀 방지

왜 변경했는지, 측정 조건과 효과, 대가, 되돌리는 기준을 기록한다. 이후 변경에서 성능 회귀를 감지할 기준을 유지한다.

## 8. 적용 예시: 보고서 생성

### 기존 코드의 현상

```text
for each order:
    customer = loadCustomer(order.customerId)
    policy = loadPolicy(customer.grade)
    appendRow(order, customer, policy)
```

주문 1,000건에서 같은 고객과 정책을 반복 조회한다. 정적 분석은 반복문 안의 외부 의존 호출과 복잡한 함수 경고를 줄 수 있고, 동적 분석은 조회 호출 횟수와 대기 시간이 전체의 큰 비중임을 보여 줄 수 있다.

### 개선 가설

- 필요한 고객을 한 번에 조회해 ID로 매핑한다.
- 정책은 요청 범위에서 등급별로 재사용한다.
- 보고서 행 생성은 순수 변환으로 분리한다.

### 판단

- 조회 횟수와 전체 시간이 실제로 감소했는가?
- 고객·정책 데이터의 최신성 요구를 지키는가?
- 누락 ID와 부분 조회 실패를 올바르게 처리하는가?
- 메모리 사용이 허용 범위인가?
- 생성된 보고서가 기존과 같은가?

단순히 반복문을 짧게 바꾸는 것이 아니라 시스템 경계의 중복 입출력을 줄이는 개선이다.

## 9. 최적화 금지 신호

- 병목 측정 없이 “이 연산은 느릴 것”이라고 추측한다.
- 표준적이고 명확한 코드를 복잡한 비트 연산으로 바꾼다.
- 작은 테스트의 한 번 결과만 보고 개선이라 선언한다.
- 캐시 무효화와 오류 처리를 생략한다.
- 기능 테스트를 통과하지 않은 성능 변경을 채택한다.
- 읽기 어려운 코드를 만들고 이유와 측정 자료를 남기지 않는다.
- 한 서버의 CPU를 줄이기 위해 데이터베이스·네트워크 부하를 크게 늘린다.

최적화하지 않는 결정도 합리적일 수 있다. 이미 목표를 충분히 만족하고 변경 위험이 효과보다 크다면 명확한 코드를 유지한다.

## 10. 시험 함정

1. 정적 분석은 프로그램을 실행해야 한다고 생각한다.
2. 동적 분석 결과가 실행하지 않은 경로까지 보장한다고 생각한다.
3. 도구 경고를 모두 실제 결함 또는 모두 오탐으로 단정한다.
4. 순환 복잡도가 낮으면 기능 정확성도 높다고 본다.
5. 커버리지 100%를 좋은 테스트와 동일시한다.
6. 경고 수를 줄이기 위해 규칙 전체를 비활성화한다.
7. 코드 최적화를 줄 수와 문법 축약으로 이해한다.
8. 캐시·병렬화·자원 풀은 항상 성능을 높인다고 생각한다.
9. 최적화 전후의 환경·입력·측정 조건을 다르게 한다.

### 문제 4

### 문제 5

코드 최적화의 안전한 절차를 순서대로 요약하라.

## 정답과 해설

1. **정답**: 정적 분석은 실행 없이 넓은 코드의 규칙·흐름·구조 위험을 찾지만 오탐과 실행환경 차이가 있다. 동적 분석은 실행 중 실제 시간·메모리·호출을 관찰하지만 실행한 입력과 경로에 한정된다.
2. **정답**: 복잡도는 이해·시험 부담의 단서이고 커버리지는 실행 범위의 단서일 뿐 요구 정확성, 판정 품질, 보안, 유지보수성 전체를 대표하지 않기 때문이다.
3. **정답**: 맥락과 증거를 검토해 예외 이유, 범위, 승인과 재검토 시점을 기록한다. 한 사례 때문에 규칙 전체를 끄지 않는다.
4. **정답 예**: 메모리, 만료, 무효화, 데이터 최신성·일관성, 적중률, 동시 접근 중 세 가지다.
5. **정답**: 목표·기준선 정의 → 정적·동적 증거로 병목 확인 → 개선 가설 → 작은 변경 → 기능·회귀 검사 → 동일 조건 재측정 → 효과·대가 문서화다.

## 12. 최종 요약

- **소스코드 품질분석 도구**는 정적·동적 분석과 지표를 통해 결함·유지보수·성능 위험 후보를 찾는다.
- 정적 분석은 실행 없이 넓게, 동적 분석은 실제 실행 경로를 깊게 관찰하며 서로 보완한다.
- 복잡도·중복·크기·의존성·커버리지 수치는 맥락과 추세로 해석하고 오탐·예외 근거를 관리한다.
- **코드 최적화**는 정확성을 유지하며 측정된 병목의 시간·메모리·입출력 자원 사용을 개선하는 활동이다.
- 목표와 기준선 → 병목 증거 → 개선 가설 → 작은 변경 → 기능·회귀 검증 → 동일 조건 재측정 순서를 지키며 유지보수성과 전체 시스템 대가를 함께 본다.
