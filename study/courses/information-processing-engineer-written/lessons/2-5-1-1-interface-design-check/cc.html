공식 범위: 2026년 정보처리기사 출제기준의 소프트웨어개발 > 인터페이스 구현 > 인터페이스 설계 확인에서 제시한 인터페이스 기능 확인, 데이터 표준 확인을 학습한다. 다음 레슨의 인터페이스 보안·소프트웨어 연계 테스트나 이후 레슨의 설계 산출물·인터페이스 명세서 검증과 경계를 두고, 구현 전에 기능 계약과 교환 데이터 표준을 확인하는 활동에 집중한다.

인터페이스는 두 시스템이 연결되는 선이 아니라 서로 기대하는 행동과 데이터의 계약이다. 송신 시스템은 성공했다고 생각하지만 수신 시스템은 필수값 누락으로 거절할 수 있고, 같은 amount라도 한쪽은 원 단위 정수, 다른 쪽은 소수 통화 단위로 해석할 수 있다. 구현 전에 기능과 데이터 의미를 맞추는 이유다.

01

1. 인터페이스 설계 확인의 목적

인터페이스 설계 확인은 다음 질문에 합의된 답이 있는지 검토하는 활동이다.

  1. 누가 누구에게 어떤 업무 기능을 요청하는가?
  2. 언제, 어떤 조건에서 요청하는가?
  3. 입력과 결과, 실패의 의미는 무엇인가?
  4. 데이터 필드의 이름·형식·코드·단위는 같은가?
  5. 중복, 지연, 순서 변경, 부분 실패를 어떻게 해석하는가?
  6. 요구사항에서 인터페이스와 구현·테스트까지 추적할 수 있는가?

화면이나 네트워크 연결이 가능하다는 사실만으로 업무 인터페이스가 올바르다고 판단하지 않는다.

03

3. 토픽 ① 인터페이스 기능 확인

3.1 기능 목록과 경계

먼저 인터페이스가 제공할 기능을 업무 동작으로 식별한다.

나쁜 표현:

코드 예시 · text

고객 API
데이터 전송
연동 처리

개선 표현:

코드 예시 · text

고객 등록 요청
고객 연락처 변경 통지
고객 상태 조회
회원 탈퇴 완료 통지

기능 이름은 요청자의 목적과 관찰 가능한 결과가 드러나야 한다. 등록과 수정, 조회와 통지처럼 의미가 다른 동작을 하나로 합치지 않는다.

3.2 기능별 계약

각 기능에서 다음을 확인한다.

  • 기능 ID와 이름
  • 송신·수신 시스템과 책임
  • 호출 또는 발생 조건
  • 사전 조건과 권한 전제
  • 입력과 필수값
  • 정상 결과와 상태 변화
  • 오류 종류와 호출자의 대응
  • 동기·비동기 응답 의미
  • 시간 제한과 재시도 조건
  • 중복 요청과 순서 처리
  • 처리량·건수·파일 크기 같은 용량 조건

성공을 응답 수신으로만 정의하면 안 된다. 요청 접수 성공인지, 실제 업무 처리 완료인지 구분한다. 비동기 처리에서는 접수 응답과 최종 완료 통지가 서로 다른 상태일 수 있다.

3.3 정상·대체·예외 흐름

기능 확인은 정상 경로만 읽지 않는다.

코드 예시 · text

정상: 유효한 고객 등록 → 고객 ID 생성 → 완료 응답
대체: 이미 존재하는 외부 고객 ID → 기존 결과 반환 또는 중복 오류
예외: 필수값 누락 → 거절, 잘못된 필드와 이유 반환
장애: 처리 중 저장소 시간 초과 → 결과 불명 상태를 구분하고 재확인

호출자가 재시도해도 중복 생성이 없어야 하는 기능이라면 요청 식별과 중복 처리 규칙이 필요하다. 모든 인터페이스에 같은 재시도 정책을 적용하지 않는다. 업무 동작의 반복 가능성과 부작용을 판단한다.

3.4 상태와 오류 의미

오류는 기술 메시지 하나가 아니라 호출자가 결정할 수 있는 계약이어야 한다.

04

4. 기능 확인 절차

단계 1: 인터페이스 대상을 식별한다

업무 흐름, 외부 시스템, 컴포넌트 의존 관계에서 필요한 연결을 찾는다. 송신·수신과 데이터 소유 책임을 표시한다.

단계 2: 요구사항과 기능을 대응시킨다

각 요구사항이 어느 인터페이스 기능에서 실현되는지 연결하고, 근거 요구가 없는 기능과 반영되지 않은 요구를 찾는다.

단계 3: 기능 계약을 검토한다

호출 조건, 입력, 결과, 상태 변화, 오류, 시간, 중복을 정상·대체·예외 시나리오로 읽는다.

단계 4: 시퀀스를 따라간다

한 업무가 여러 인터페이스를 거치면 요청 식별자와 상태가 끝까지 이어지는지 확인한다. 부분 성공과 보상 책임을 찾는다.

단계 5: 예제로 명세를 실행해 본다

정상·경계·오류 데이터 예를 만들어 송신자가 생성할 수 있고 수신자가 해석할 수 있는지 검토한다. 이 단계는 실제 연계 테스트가 아니라 설계의 모호성을 찾는 정적 검토다.

단계 6: 불일치를 해결하고 기준선을 정한다

이름, 상태, 데이터 의미, 책임의 불일치를 소유자와 합의한다. 미결 사항, 가정, 결정 사유와 변경 이력을 남긴다.

05

5. 토픽 ② 데이터 표준 확인

5.1 데이터 표준의 목적

데이터 표준은 여러 시스템이 같은 데이터를 같은 의미와 형식으로 이해하도록 이름, 정의, 형식, 코드, 품질 규칙을 통일한 기준이다.

표준이 없으면 다음 문제가 생긴다.

  • customerId, custNo, memberKey가 같은지 다른지 알기 어렵다.
  • 한쪽의 status=1이 활성, 다른 쪽에서는 탈퇴를 뜻할 수 있다.
  • 날짜·시간의 시간대가 달라 처리 순서가 바뀐다.
  • 금액의 단위와 소수 자릿수 차이로 값이 왜곡된다.
  • 빈 문자열, null, 0의 의미가 섞인다.

5.2 확인할 표준 항목

5.3 코드 데이터

코드는 값·표시명·정의·유효기간·관리 주체를 확인한다.

코드 예시 · text

고객상태
A = 활성
S = 정지
W = 탈퇴처리중
C = 탈퇴완료

수신 시스템에 없는 새 코드가 추가될 때 처리 방법을 정한다. 알 수 없는 코드를 활성로 간주하는 식의 임의 기본값은 위험하다. 코드 변경의 배포 순서와 호환 기간을 고려한다.

5.4 날짜·시간과 숫자

날짜·시간은 형식뿐 아니라 시간대와 의미를 명시한다. 2026-03-01 09:00이 어느 지역 시간인지, 발생 시각인지 저장 시각인지 구분한다.

숫자는 단위, 부호, 정밀도, 반올림 규칙, 범위를 확인한다. 통화는 부동소수 오차와 최소 단위를 고려하고, 식별번호는 계산하지 않으므로 문자열이 더 적합할 수 있다.

06

6. 데이터 표준 확인 절차

  1. 송신·수신의 데이터 항목 목록을 수집한다.
  2. 조직 표준 용어·도메인·코드와 대응시킨다.
  3. 필드 이름뿐 아니라 업무 정의를 비교한다.
  4. 자료형, 길이, 정밀도, 필수성, 기본값을 비교한다.
  5. 코드·단위·날짜·시간대·결측 표현을 확인한다.
  6. 변환이 필요하면 방향, 규칙, 오류와 책임을 정한다.
  7. 정상·경계·오류 예제 데이터로 상호 해석을 검토한다.
  8. 표준 예외와 미결 사항을 승인·기록한다.

변환 규칙은 A를 1로 변환만 쓰지 않는다. 알 수 없는 코드, 폐기 코드, null, 변환 실패에서 무엇을 하는지 함께 정한다.

발견 가능한 문제

  • CRM의 customerKey가 회원 ID가 아니라 내부 고객 키일 수 있다.
  • changedAt을 현지 시각으로 보내고 수신자가 표준시로 해석할 수 있다.
  • 탈퇴 고객의 연락처 변경을 수신자가 허용하지 않을 수 있다.
  • 같은 메시지 재전송 시 중복 이력이 쌓일 수 있다.

9. 시험 함정

  1. 인터페이스를 네트워크 연결 규격 하나로만 본다.
  2. 응답 수신을 업무 처리 완료와 동일시한다.
  3. 정상 흐름만 확인하고 시간 초과·중복·부분 실패를 누락한다.
  4. 필드명이 같으면 의미도 같다고 판단한다.
  5. 자료형이 같으면 단위·코드·시간대도 같다고 생각한다.
  6. null, 빈 문자열, 0을 모두 같은 결측으로 처리한다.
  7. 코드 매핑에서 알 수 없는 새 코드 처리 규칙을 누락한다.
  8. 모든 일시 장애를 무제한 재시도로 해결한다.
  9. 기능·데이터의 소유자와 변경 책임을 정하지 않는다.

10. 확인 문제

문제 1

비동기 인터페이스에서 접수 성공과 업무 처리 완료를 구분해야 하는 이유는 무엇인가?

문제 2

송신과 수신 필드가 모두 정수형 amount다. 표준 일치로 바로 판단할 수 없는 이유를 두 가지 쓰라.

문제 3

인터페이스 기능 확인에서 중복 요청 규칙이 필요한 대표 상황을 설명하라.

문제 4

데이터 표준 확인 항목을 다섯 가지 쓰라.

11

정답과 해설

  1. 정답: 접수는 요청을 받았다는 뜻일 뿐 실제 업무가 성공했다는 뜻이 아닐 수 있다. 최종 성공·실패 상태와 통지·조회 방법을 별도로 정의해야 한다.
  2. 정답 예: 통화 단위가 원과 천원으로 다를 수 있고, 소수·반올림·부호·허용 범위나 세금 포함 의미가 다를 수 있다.
  3. 정답: 시간 초과 후 같은 결제·등록 요청을 재전송할 때 첫 요청이 이미 처리됐을 수 있다. 요청 식별과 중복 처리 규칙이 없으면 이중 처리될 수 있다.
  4. 정답 예: 용어·항목명, 자료형, 길이·정밀도, 필수성, 코드, 단위, 날짜·시간대, 결측 표현, 문자·인코딩 중 다섯 가지다.

11. 최종 요약

  • 인터페이스 기능 확인은 송신·수신, 발생 조건, 입력·결과, 상태, 오류, 시간, 중복과 책임을 업무 계약으로 검토한다.
  • 정상뿐 아니라 대체·예외·장애 흐름과 비동기 접수·완료 상태를 구분한다.
  • 데이터 표준 확인은 용어, 이름, 의미, 자료형, 길이, 코드, 단위, 시간대, 결측과 인코딩을 송수신 양쪽에서 맞춘다.
  • 기능은 요구사항과, 데이터는 표준 사전·코드와 추적하며 예제 데이터로 상호 해석을 검토한다.
  • 좋은 인터페이스 설계는 완전성, 일관성, 명확성, 정확성, 추적·시험 가능성과 변경 호환성을 갖는다.
