인터페이스는 신뢰 경계를 통과한다. 올바른 데이터를 보내는 것만으로 충분하지 않고 누가 보냈는지, 전송 중 바뀌지 않았는지, 권한이 있는지, 재전송이 중복 처리되지 않는지를 보장해야 한다. 구현 뒤에는 실제 연계 경로에서 정상·오류·장애·보안 조건을 시험한다.

01

1. 토픽 ① 인터페이스 보안

1.1 보호 목표

1. 토픽 ① 인터페이스 보안 · 학습 표 1
목표의미인터페이스 위험 예
기밀성허가되지 않은 주체가 내용을 읽지 못함전송 중 개인정보 노출
무결성데이터가 무단 변경되지 않았음을 확인금액·계좌 필드 변조
인증통신 상대의 신원을 확인위조된 송신 시스템
인가인증된 주체의 기능·데이터 권한 확인조회 권한으로 삭제 호출
가용성필요한 때 서비스를 사용할 수 있음과도한 요청으로 자원 고갈
추적성누가 언제 무엇을 했는지 확인거래 식별자·감사 기록 부재
부인 방지수행 사실을 부정하기 어렵게 증거 확보승인 요청 주체 분쟁

모든 인터페이스에 같은 강도의 통제를 적용하지 않는다. 데이터 민감도, 업무 영향, 외부 노출, 규제, 위협 가능성을 평가해 통제를 선택한다.

1.2 주요 위협

  • 도청과 중간자 공격
  • 송신자 위장과 탈취된 자격정보 사용
  • 요청·응답 데이터 변조
  • 유효한 요청의 캡처 후 재전송
  • 입력을 이용한 명령·쿼리 삽입
  • 권한 없는 기능·다른 사용자의 데이터 접근
  • 과도한 요청·큰 본문·느린 연결에 의한 자원 고갈
  • 오류·로그·응답을 통한 비밀정보 노출
  • 오래되거나 폐기된 인터페이스의 방치

위협과 통제를 연결해야 한다. 암호화를 적용해도 탈취된 관리자 자격으로 보내는 요청의 권한 남용은 막지 못한다.

02

2. 인터페이스 보안 통제

2.1 통신 구간 보호

전송 중 내용을 암호화하고 통신 상대를 확인한다. 신뢰할 수 있는 인증서·키와 프로토콜 설정, 유효기간, 이름 일치, 폐기 절차를 관리한다. 단순히 포트가 열려 연결된다는 사실은 안전한 통신의 증거가 아니다.

내부 네트워크라고 자동으로 신뢰하지 않는다. 중요 데이터는 구간별로 어디에서 평문이 되는지와 중간 장비·로그 노출을 확인한다.

2.2 인증과 인가

인증은 호출 주체가 누구인지 확인하고, 인가는 그 주체가 요청한 기능과 자원에 접근할 수 있는지 판단한다.

확인 사항:

  • 사람, 시스템, 서비스 계정을 구분한다.
  • 최소 권한으로 기능·데이터 범위를 제한한다.
  • 자격정보를 코드·설정 파일·로그에 평문으로 두지 않는다.
  • 자격정보의 발급, 보관, 회전, 폐기와 사고 대응을 관리한다.
  • 인증 후에도 요청한 자원의 소유·업무 권한을 매번 검증한다.

인증 성공이 모든 기능 허용을 의미하지 않는다.

2.3 무결성과 재전송 방지

메시지 인증 코드나 전자서명 등으로 내용과 송신 주체의 무결성을 검증할 수 있다. 실제 방식은 보안 정책과 환경에 따른다.

재전송 공격과 중복 업무 처리를 줄이기 위해 다음을 조합한다.

  • 요청 고유 식별자
  • 허용 시간 범위와 시각 정보
  • 한 번만 사용하는 임의값
  • 처리된 요청 식별자의 기록
  • 같은 요청의 반복 처리 결과를 정의하는 멱등성 규칙

시간 정보만 사용하면 시스템 시계 차이와 재전송 창을 고려해야 하고, 식별자만 사용하면 보관 기간과 저장 용량을 정해야 한다.

2.4 입력 검증과 안전한 처리

인터페이스 경계에서 다음을 확인한다.

  • 필수 필드, 자료형, 길이, 범위, 허용 문자
  • 중첩 깊이, 배열 건수, 파일 크기
  • 코드값과 상태 전이
  • 예상하지 않은 필드의 처리
  • 구조와 업무 규칙의 검증 순서

허용 목록 방식으로 기대한 형식을 검증하고, 데이터가 명령이나 쿼리로 해석되지 않게 안전한 API를 사용한다. 클라이언트 검증만 믿지 않고 수신 시스템 경계에서 다시 확인한다.

2.5 오류와 로그

외부 응답에는 호출자가 판단할 수 있는 오류 분류와 추적 식별자를 제공하되 내부 경로, 쿼리, 스택, 비밀값을 노출하지 않는다.

로그에는 다음을 기록할 수 있다.

  • 요청 식별자, 호출 주체, 기능, 시각, 결과
  • 보안 정책에 필요한 변경 전후 상태와 승인
  • 실패 분류와 처리 시간

비밀번호, 인증 토큰, 비밀키, 전체 개인정보와 결제정보는 기록하지 않거나 정책에 따라 마스킹한다. 로그 자체의 접근권한, 무결성, 보존과 삭제도 관리한다.

2.6 자원과 가용성 보호

  • 요청 크기와 처리 시간 제한
  • 주체·기능별 요청 빈도 제한
  • 연결·스레드·큐·메모리 상한
  • 느린 외부 호출의 시간 초과와 격리
  • 재시도 횟수·간격·중단 조건
  • 과부하 시 명확한 거절과 회복

무제한 재시도는 장애 중 부하를 더 키울 수 있다. 지수적 간격, 임의 지연, 회로 차단 등 일반 원리를 상황에 맞게 적용하되 특정 설정값을 고정하지 않는다.

03

3. 혼동하기 쉬운 보안 개념

인코딩 vs 암호화

인코딩은 데이터를 전송·표현 가능한 형식으로 바꾸며 비밀 키 없이 되돌릴 수 있는 경우가 많다. 기밀성 보호가 목적이 아니다. 암호화는 권한 있는 주체만 복호화하도록 기밀성을 제공한다.

해시 vs 암호화

해시는 입력에서 고정 길이 값을 계산하는 단방향 성질을 이용해 무결성 확인 등에 사용한다. 암호화처럼 원문 복구를 목적으로 하지 않는다. 단순 해시만으로 송신자 인증이 자동으로 되는 것은 아니다.

인증 vs 인가

인증은 신원 확인, 인가는 기능·자원 접근 허용 판단이다. 순서상 인증 후 인가가 흔하지만 두 질문은 다르다.

전송 보호 vs 저장 보호

전송 구간 암호화는 이동 중 데이터를 보호하지만 데이터베이스·파일·백업·로그에 저장된 데이터 보호를 대신하지 않는다.

04

4. 인터페이스 보안 구현 절차

  1. 인터페이스 자산, 데이터 민감도, 신뢰 경계를 식별한다.
  2. 위장·변조·도청·재전송·권한 남용·가용성 위협을 분석한다.
  3. 조직 정책에 맞는 인증, 인가, 암호, 무결성, 입력 제한을 선택한다.
  4. 비밀과 키의 발급·저장·회전·폐기 절차를 정의한다.
  5. 오류 응답, 감사 로그, 추적 식별자를 설계한다.
  6. 정상 기능과 보안 실패를 모두 구현한다.
  7. 연계 테스트와 보안 검토로 통제의 실제 동작을 확인한다.
  8. 운영 중 권한, 자격정보, 로그, 폐기 인터페이스를 지속 관리한다.

보안은 마지막에 필터 하나를 붙이는 단계가 아니라 인터페이스 생명주기 전체의 책임이다.

05

5. 토픽 ② 소프트웨어 연계 테스트

5.1 정의

소프트웨어 연계 테스트는 구현된 시스템·컴포넌트 사이의 연결에서 기능, 데이터, 상태, 오류와 보안 통제가 설계한 계약대로 동작하는지 확인하는 시험이다. 일반 통합 전략 전체보다 여기서는 실제 인터페이스 기능 구현의 검증에 초점을 둔다.

5.2 시험 범위

5. 토픽 ② 소프트웨어 연계 테스트 · 학습 표 2
시험 영역확인 내용
연결주소·경로·대상 식별과 통신 성립

데이터필드, 형식, 코드, 단위, 필수값, 인코딩
상태접수·처리·완료·실패·취소의 전이

연결 성공 시험만 통과하고 업무 데이터와 상태를 확인하지 않으면 연계 테스트가 완전하지 않다.

06

6. 소프트웨어 연계 테스트 절차

단계 1: 대상과 계약 확인

송신·수신, 기능, 데이터 매핑, 오류, 시간, 중복, 보안 요구를 확인한다. 서로 다른 버전이나 환경을 시험하지 않도록 대상 식별자를 기록한다.

단계 2: 환경과 관찰 수단 준비

시험 계정·권한, 키와 자격정보, 네트워크, 데이터, 시간 조건, 로그와 거래 식별자를 준비한다. 운영 비밀·개인정보를 시험 데이터로 복사하지 않는다.

단계 3: 테스트 케이스 설계

  • 정상값, 최솟값·최댓값, 선택·필수값
  • 형식 오류, 미지원 코드, 추가·누락 필드
  • 권한별 허용·거절
  • 시간 초과, 연결 단절, 수신 지연
  • 같은 요청 반복과 메시지 순서 변경
  • 부분 성공과 보상·재처리
  • 민감정보가 오류·로그에 나타나는지 여부

각 케이스에 사전 상태, 입력, 실행, 기대 응답, 기대 데이터·상태·로그를 정의한다.

단계 4: 단방향 기능부터 전체 흐름으로 실행

연결과 단순 요청을 먼저 확인한 뒤 상태 변경과 여러 시스템을 지나는 전체 업무로 확대한다. 실패하면 송신 전, 전송, 수신 검증, 업무 처리, 응답 중 어느 구간인지 식별한다.

단계 5: 결과 대조

화면이나 응답 코드만 보지 않는다. 송신 기록, 수신 데이터, 상태, 중복 여부, 후속 이벤트와 감사 로그가 같은 요청 식별자로 일치하는지 확인한다.

단계 6: 결함·재시험·회귀

재현 조건과 양쪽 증거를 함께 기록한다. 수정 후 원 실패와 연관된 정상·오류·보안 흐름을 재시험한다.

단계 7: 종료와 잔여 위험 보고

핵심 인터페이스와 위험 시나리오의 통과, 중대한 결함, 미실행 항목, 대역과 실제 환경 차이, 운영 준비 상태를 보고한다.

7. 보안 테스트의 판정 예

인증 실패

  • 잘못되거나 만료된 자격정보는 거절되는가?
  • 응답이 자격정보의 존재 여부를 과도하게 알려 주지 않는가?
  • 실패가 감사 가능하되 비밀값이 로그에 남지 않는가?

권한 부족

  • 읽기 권한만 가진 주체가 변경 기능을 호출하면 거절되는가?
  • 다른 사용자의 식별자를 바꾸어 접근해도 자원 권한을 검사하는가?

변조·재전송

  • 보호된 필드를 바꾸면 무결성 검증이 실패하는가?
  • 같은 요청을 반복해도 업무 규칙에 맞게 한 번만 반영되거나 정의된 결과를 내는가?

입력 공격

  • 길이·중첩·건수 제한을 초과하면 안전하게 거절하는가?
  • 입력이 명령으로 실행되지 않고 오류 응답에 내부 정보가 노출되지 않는가?

보안 시험은 운영 시스템에 무단으로 수행하지 않는다. 승인된 범위와 격리된 환경, 복구 계획에서 진행한다.

08

8. 적용 예시: 결제 승인 인터페이스

계약

코드 예시 · text

호출자: 주문 서비스
기능: 결제 승인 요청
핵심 입력: 요청 ID, 주문 ID, 금액, 통화, 결제 수단 참조값
결과: 승인, 업무 거절, 입력 오류, 처리 상태 불명
중복: 같은 요청 ID는 추가 승인 없이 기존 결과 제공

보안 설계

  • 승인된 주문 서비스의 신원을 확인한다.
  • 해당 기능만 수행하도록 최소 권한을 부여한다.
  • 전송 구간과 메시지 무결성을 보호한다.
  • 금액·통화·식별자·본문 크기를 검증한다.
  • 결제 수단 비밀정보를 응답·로그에 노출하지 않는다.
  • 요청 ID와 시각으로 중복·재전송을 통제한다.

연계 테스트

  1. 정상 승인 후 주문·결제 상태와 거래 식별자 일치
  2. 잘못된 금액·통화 형식 거절, 데이터 미변경
  3. 권한 없는 서비스 호출 거절
  4. 응답 유실 후 동일 요청 재전송, 이중 승인 없음
  5. 수신 시간 초과에서 상태 불명과 조회·복구 절차 확인
  6. 오류와 로그에 비밀 결제정보가 남지 않음

판정

성공 응답만으로 승인 완료를 판단하지 않는다. 승인 기록, 주문 상태, 중복 여부와 추적 로그를 함께 대조한다.

09

9. 시험 함정

  1. 인코딩을 암호화와 같은 기밀성 통제로 본다.
  2. 인증에 성공하면 모든 자원 접근이 허용된다고 생각한다.
  3. 전송 구간 암호화가 입력 검증·권한·저장 보호를 대신한다고 본다.
  4. 단순 해시만으로 송신자 인증과 재전송 방지가 모두 된다고 생각한다.
  5. 비밀값을 로그에 남긴 뒤 접근권한만 제한하면 충분하다고 본다.
  6. 일시 장애에 무제한 재시도를 적용한다.
  7. 연계 테스트를 연결 성공·응답 코드 확인으로 끝낸다.
  8. 대역 시스템 성공을 실제 외부 시스템 성공과 동일시한다.
  9. 보안 실패 시나리오를 승인 없이 운영 환경에서 시험한다.

10. 확인 문제

문제 1

인증과 인가의 차이를 인터페이스 호출 예로 설명하라.

문제 2

유효한 결제 승인 요청이 재전송되어 이중 승인되는 것을 막기 위한 요소를 세 가지 쓰라.

문제 3

전송 암호화를 적용했는데도 입력 검증이 필요한 이유는 무엇인가?

문제 4

소프트웨어 연계 테스트에서 응답 코드 외에 확인할 결과를 네 가지 쓰라.

문제 5

오류 로그에 남겨도 되는 정보와 남기면 안 되는 정보의 예를 각각 쓰라.

11

정답과 해설

  1. 정답: 인증은 호출자가 주문 서비스인지 신원을 확인하는 것이고, 인가는 인증된 주문 서비스가 결제 승인 기능과 해당 주문에 접근할 권한이 있는지 판단하는 것이다.
  2. 정답 예: 요청 고유 ID, 처리 ID 기록, 허용 시간과 시각, 한 번 쓰는 값, 멱등 처리 계약 중 세 가지다.
  3. 정답: 암호화는 이동 중 기밀성을 보호하지만 인증된 호출자가 보낸 악성·오류 입력이나 업무 범위 위반을 자동으로 막지 못하기 때문이다.
  4. 정답 예: 수신 데이터, 업무 상태, 저장 결과, 중복 처리 여부, 후속 이벤트, 양쪽 로그와 거래 식별자, 감사 기록 중 네 가지다.
  5. 정답: 요청 식별자, 호출 주체, 기능, 시각, 결과 분류는 정책에 따라 기록할 수 있다. 비밀번호, 토큰, 비밀키, 전체 개인정보·결제정보는 기록하지 않거나 필요한 최소 부분만 마스킹한다.
12

11. 최종 요약

  • 인터페이스 보안은 기밀성, 무결성, 인증, 인가, 가용성, 추적성을 위협과 데이터 위험에 맞게 구현한다.
  • 전송 보호, 최소 권한, 입력 검증, 무결성·재전송 통제, 비밀 관리, 안전한 오류·로그와 자원 제한을 함께 적용한다.
  • 인코딩·암호화·해시, 인증·인가, 전송·저장 보호의 목적을 구분한다.
  • 소프트웨어 연계 테스트는 실제 연결에서 기능·데이터·상태·오류·재처리·보안·운영 조건을 계약과 대조한다.
  • 응답만 보지 말고 송수신 데이터, 상태, 중복, 후속 처리와 로그를 같은 식별자로 추적하며 수정 후 보안·회귀 흐름을 재시험한다.
