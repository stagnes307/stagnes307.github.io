FF 원문 제목3-1-1-1. 트리거 · 이벤트

공식 범위: 2026년 정보처리기사 출제기준의 데이터베이스구축 > SQL 응용 > 절차형 SQL 작성 가운데 트리거, 이벤트를 학습한다. DBMS마다 지원하는 발생 시점, 문법, 예약어, 스케줄 기능과 트랜잭션 제약이 다를 수 있으므로 특정 제품 문법을 고정하지 않고 개념·분류·설계·시험 원칙을 중심으로 설명한다. 사용자 정의 함수와 일반 SQL 문법은 다음 레슨 범위다.

트리거와 이벤트는 사람이 직접 호출하지 않아도 정해진 조건이나 시점에 데이터베이스 동작을 실행하게 한다. 반복 규칙을 중앙에서 지킬 수 있지만 실행 흐름이 숨겨지고 연쇄 동작이 생길 수 있으므로 목적, 범위, 실패 의미와 운영 책임을 명확히 해야 한다.

01

1. 절차형 SQL과 자동 실행

일반 SQL 문은 “무엇을 조회·변경할지”를 선언한다. 절차형 SQL은 변수, 조건, 반복, 예외와 여러 SQL 문을 묶어 처리 흐름을 표현한다. 트리거와 이벤트는 이런 처리 블록을 특정 발생 조건과 연결한다.

자동 실행 구조는 흔히 ECA(Event-Condition-Action)로 이해할 수 있다.

  1. Event: 무엇이 발생했는가?
  2. Condition: 어떤 조건일 때 실행하는가?
  3. Action: 조건이 참이면 무엇을 수행하는가?

코드 예시 · text

이벤트: 주문 상태 UPDATE
조건: 이전 상태는 PAID, 새 상태는 CANCELLED
동작: 취소 감사 이력 기록

이 구조를 명확히 쓰면 트리거의 발생 범위와 숨은 부작용을 검토하기 쉽다.

02

2. 토픽 ① 트리거

2.1 정의

트리거(Trigger)는 테이블·뷰·스키마·데이터베이스 등에서 지정한 데이터 변경이나 시스템 사건이 발생할 때 DBMS가 자동으로 실행하는 절차형 데이터베이스 객체다.

핵심 특징:

  • 애플리케이션이 일반 함수처럼 명시적으로 호출하지 않는다.
  • 특정 사건과 대상에 연결된다.
  • 실행 시점과 행·문장 범위를 정의할 수 있다.
  • 발생한 변경의 이전값·새값을 참조할 수 있는 경우가 많다.
  • 원래 SQL과 같은 트랜잭션에 참여하는 경우가 많지만 구체 동작은 DBMS 규칙을 확인한다.

2.2 트리거 구성 요소

2. 토픽 ① 트리거 · 학습 표 1
구성질문예
이름어떤 규칙을 수행하는가?주문 상태 감사
대상어느 테이블·뷰·사건인가?orders
사건어떤 변경에 반응하는가?INSERT, UPDATE, DELETE
시점변경 전·후·대신 중 언제인가?AFTER UPDATE
수준문장 한 번인가, 영향받은 각 행인가?FOR EACH ROW
조건언제 동작을 수행하는가?상태가 실제 변경됨

문법은 DBMS별로 다르므로 구성의 의미를 먼저 이해한다.

03

3. 트리거 분류

3.1 사건에 따른 분류

DML 트리거

테이블·뷰의 INSERT, UPDATE, DELETE 같은 데이터 조작에 반응한다. 데이터 검증, 감사, 파생 정보 유지 등에 쓰일 수 있다.

DDL 트리거

테이블 생성·변경·삭제 같은 스키마 사건에 반응한다. 변경 감사나 제한에 사용할 수 있으나 지원 범위가 DBMS마다 다르다.

데이터베이스·시스템 트리거

로그인, 시작, 종료 같은 사건에 반응하는 기능을 제공하는 DBMS도 있다. 제품별 차이가 크므로 개념만 구분한다.

3.2 실행 시점에 따른 분류

BEFORE 트리거

원래 변경이 반영되기 전에 실행한다. 입력값 검증이나 허용되는 값의 정규화에 사용할 수 있다. 원래 변경을 취소하거나 새값을 수정할 수 있는지는 제품별 규칙을 확인한다.

AFTER 트리거

원래 변경이 수행된 뒤 실행한다. 확정된 변경을 바탕으로 감사나 후속 처리를 할 때 사용한다. 트랜잭션이 최종 커밋됐다는 뜻과 동일하지 않을 수 있다.

INSTEAD OF 트리거

원래 연산을 대신 실행한다. 복잡한 뷰에 대한 변경을 실제 테이블 연산으로 변환하는 데 사용할 수 있다. 지원 대상과 의미는 DBMS별로 다르다.

AFTER를 “항상 커밋 이후”라고 외우면 안 된다. 많은 DBMS에서 트리거는 원 문장과 같은 트랜잭션 안에서 실행되며 이후 전체가 롤백될 수 있다.

3.3 실행 수준에 따른 분류

행 수준 트리거(Row-level Trigger)

영향받은 각 행마다 실행된다. 10,000행을 한 문장으로 변경하면 10,000번 실행될 수 있어 성능과 연쇄 동작을 주의한다.

문장 수준 트리거(Statement-level Trigger)

한 SQL 문장당 한 번 실행된다. 영향 행 전체를 다루는 방법은 DBMS별 기능에 따라 다르다.

시험에서 “UPDATE 문 한 번”과 “변경된 행 수”를 구분한다.

04

4. 이전값과 새값

행 변경 트리거에서는 일반적으로 이전 상태와 새 상태를 구분한다. 표현 이름은 DBMS마다 다르지만 흔히 OLD, NEW 개념으로 설명한다.

4. 이전값과 새값 · 학습 표 2
사건이전값새값
INSERT보통 없음삽입할 값
UPDATE변경 전 값변경 후 값
DELETE삭제 전 값보통 없음

예를 들어 상태 변경 감사에서는 단순히 현재값을 기록하지 않고 이전 상태와 새 상태, 변경 주체, 시각, 업무 식별자를 함께 기록한다.

코드 예시 · sql

-- 제품 중립적 의사 SQL: 실제 문법으로 그대로 실행하는 코드가 아님
TRIGGER order_status_audit
AFTER UPDATE OF status ON orders
FOR EACH ROW
WHEN OLD.status IS DISTINCT FROM NEW.status
BEGIN
    INSERT INTO order_status_history(
        order_id, old_status, new_status, changed_at
    ) VALUES (
        NEW.order_id, OLD.status, NEW.status, CURRENT_TIME
    );
END;

NULL 비교, 현재 시각 함수, 변경 사용자 취득 방법은 제품에 따라 다르다. 의도는 “상태가 실제로 바뀐 행만 감사한다”는 것이다.

05

5. 트리거 사용 사례와 주의점

적합할 수 있는 사례

  • 여러 애플리케이션 경로에서 반드시 남겨야 하는 데이터 변경 감사
  • 데이터베이스 경계에서 지켜야 할 간단한 무결성 보조
  • 이전·새값을 이용한 변경 이력
  • 제한된 파생값이나 요약값의 일관성 유지
  • 변경 가능한 뷰의 연산 변환

가능하면 기본키, 외래키, 고유, 검사 제약처럼 선언적 제약으로 표현할 수 있는 규칙은 제약조건을 먼저 검토한다. 선언적 규칙이 더 명확하고 최적화·검증하기 쉬울 수 있다.

위험

숨은 실행

애플리케이션 코드에는 한 번의 UPDATE만 보이지만 여러 트리거가 추가 SQL을 실행할 수 있다. 성능과 오류 원인을 추적하기 어려워진다.

연쇄·재귀

트리거 A가 테이블 B를 바꾸고 B의 트리거가 다시 A의 대상을 바꾸면 순환·무한 실행 위험이 있다. DBMS의 재귀 제한에만 의존하지 말고 구조를 단순화한다.

대량 처리 성능

행 수준 트리거가 각 행마다 조회·수정을 수행하면 대량 변경에서 비용이 급증한다. 집합 단위 처리 가능성과 실행 계획을 검토한다.

트랜잭션 확대

트리거 내부의 긴 작업과 외부 연계는 원 트랜잭션의 잠금 시간과 실패 범위를 키울 수 있다. 외부 시스템 호출을 트리거에 직접 넣는 설계는 장애·재시도·일관성 문제를 특히 주의한다.

배포 순서

테이블·트리거·감사 테이블·코드가 호환되는 순서로 배포돼야 한다. 트리거가 존재한다는 사실과 변경 이력을 애플리케이션·운영 담당자가 알아야 한다.

06

6. 트리거 설계 절차

  1. 자동화할 업무 규칙과 데이터 소유자를 확인한다.
  2. 선언적 제약이나 명시적 애플리케이션 로직이 더 적합한지 비교한다.
  3. 사건, 대상, 시점, 행·문장 수준을 정한다.
  4. 이전값·새값과 실행 조건을 정의한다.
  5. 수행 SQL, 오류, 롤백, 재귀·연쇄 영향을 분석한다.
  6. 단일행·다중행·대량 변경, null, 실패, 동시성을 시험한다.
  7. 성능, 실행 권한, 감사, 배포·비활성화·복구 절차를 문서화한다.

트리거를 만들 때는 삭제 방법만이 아니라 일시 비활성화 시 데이터 일관성을 어떻게 유지할지도 계획한다.

07

7. 토픽 ② 이벤트

7.1 이벤트의 의미

이벤트(Event)는 데이터베이스가 감지하여 정해진 동작의 계기가 되는 사건이다. 데이터 변경, 스키마 변경, 시스템 상태, 특정 시각·주기 등이 이벤트가 될 수 있다.

절차형 SQL 맥락에서 이벤트는 두 관점으로 볼 수 있다.

  1. 트리거를 발생시키는 사건: INSERT·UPDATE·DELETE 등
  2. 예약된 데이터베이스 이벤트: 특정 시각이나 주기에 SQL 블록·프로시저를 실행하는 기능

두 번째 기능의 이름과 지원 범위는 DBMS마다 다르며 별도 작업 스케줄러로 제공될 수도 있다.

7.2 예약 이벤트의 구성

7. 토픽 ② 이벤트 · 학습 표 3

실패재시도, 알림, 부분 처리와 복구
기록시작·종료·건수·결과·오류 이력

7.3 제품 중립적 의사 구조

코드 예시 · sql

-- 개념 설명용 의사 SQL
EVENT expire_pending_orders
SCHEDULE EVERY 1 INTERVAL
START AT configured_start_time
DO
BEGIN
    UPDATE orders
       SET status = 'EXPIRED'
     WHERE status = 'PENDING'
       AND expires_at < CURRENT_TIME;
END;

INTERVAL, 일정, 시간 함수와 활성화 문법은 DBMS마다 다르다. 실제 구현에서는 한 시간에 한 번이라는 고정값보다 업무 지연 허용, 처리량, 시간대와 겹침을 먼저 결정한다.

“자동 실행”이라는 공통점 때문에 같은 개념으로 보지 않는다. 사건 반응과 시간 기반 실행의 차이가 핵심이다.

09

9. 이벤트 설계와 운영

멱등성

실행이 중복되어도 결과가 한 번 실행한 것과 같은지 검토한다. 작업 재시작과 스케줄러 장애 복구에서 중요하다.

겹침 방지

이전 실행이 끝나기 전에 다음 일정이 시작될 수 있다. 잠금, 작업 상태, 실행 식별자를 이용해 동시 실행 정책을 정한다.

시간대와 달력

일광절약시간, 지역 시간, 월말·공휴일, 윤년과 시스템 시계 차이를 고려한다. 업무 시각과 저장 시각의 기준을 명시한다.

처리 범위와 재시작

대량 데이터를 한 트랜잭션으로 처리하면 잠금과 롤백 비용이 커질 수 있다. 구간·배치 단위, 진행 위치, 실패 후 재개와 중복 방지를 설계한다.

관찰과 알림

실행 예정만 있고 실제 시작·종료·건수·실패 기록이 없으면 누락을 알기 어렵다. 장시간 실행, 실패, 처리 건수 이상을 감지한다.

10

10. 적용 예시: 주문 상태 자동화

요구 A: 상태 변경 감사

주문 상태가 바뀔 때마다 이전·새 상태와 변경 시각을 기록한다.

적합 후보: AFTER UPDATE 행 수준 트리거. 실제 상태가 달라진 경우에만 감사한다. 대량 업데이트 성능과 감사 테이블 실패 시 원 거래를 롤백할지 정책을 정한다.

요구 B: 장기 미결 주문 만료

만료 시각이 지난 PENDING 주문을 주기적으로 EXPIRED로 바꾼다.

적합 후보: 예약 이벤트 또는 외부 스케줄 작업. 시간대, 겹침, 처리 구간, 재시작을 설계한다.

연쇄 영향

예약 이벤트가 주문 상태를 바꾸면 상태 감사 트리거도 실행될 수 있다. 실행 건수, 잠금, 감사 데이터 증가와 실패 관계를 함께 시험한다.

시험 케이스

  • 실제 상태 변경과 같은 값 UPDATE
  • 단일행·다중행·0행 변경
  • null과 허용하지 않는 상태 전이
  • 이벤트 중복 실행과 실행 도중 실패
  • 월말·시간대 경계
  • 감사 기록 실패 시 주문 변경의 결과
  • 대량 만료에서 처리 시간과 잠금 영향
11

11. 시험 함정

  1. 트리거를 애플리케이션이 명시적으로 호출하는 함수로 본다.
  2. AFTER 트리거를 항상 트랜잭션 커밋 이후 실행으로 이해한다.
  3. UPDATE 문 한 번과 행 수준 트리거 한 번을 동일시한다.
  4. INSERT에서 이전값, DELETE에서 새값이 항상 존재한다고 생각한다.
  5. 선언적 제약으로 충분한 규칙도 무조건 트리거로 구현한다.
  6. 트리거 내부 외부 호출이 원 트랜잭션과 장애에 미치는 영향을 무시한다.
  7. 예약 이벤트와 데이터 변경 트리거를 모두 같은 시간 기반 작업으로 본다.
  8. 주기 작업의 중복 실행·시간대·재시작을 누락한다.
  9. 트리거와 이벤트가 연쇄 실행되는 관계를 시험하지 않는다.
12

12. 확인 문제

문제 1

ECA에서 E, C, A가 각각 무엇을 뜻하는지 주문 상태 감사 예로 설명하라.

문제 2

행 수준 트리거와 문장 수준 트리거의 실행 횟수 차이를 100행 UPDATE 예로 설명하라.

문제 3

BEFORE, AFTER, INSTEAD OF 트리거의 중심 차이를 설명하라.

문제 4

트리거와 예약 이벤트의 발생 원인과 적합 사용 사례를 각각 쓰라.

문제 5

예약 이벤트에서 멱등성과 겹침 방지가 필요한 이유는 무엇인가?

13

정답과 해설

  1. 정답: E는 상태 UPDATE 사건, C는 이전과 새 상태가 실제로 다르다는 조건, A는 감사 이력을 기록하는 동작이다.
  2. 정답: 행 수준은 영향받은 각 행마다 실행되어 최대 100회가 될 수 있고, 문장 수준은 UPDATE 문 한 번에 대해 한 번 실행된다. 구체 지원은 DBMS를 확인한다.
  3. 정답: BEFORE는 원 변경 전, AFTER는 원 변경 수행 후, INSTEAD OF는 원 연산을 대신해 실행한다. AFTER가 반드시 커밋 후라는 뜻은 아니다.
  4. 정답: 트리거는 데이터·스키마 등 사건에 반응하며 변경 감사에 적합하다. 예약 이벤트는 시각·주기에 따라 실행하며 만료 처리·정기 집계에 적합하다.
  5. 정답: 장애 복구·재시도로 같은 작업이 반복되거나 이전 실행이 끝나기 전에 다음 실행이 시작될 수 있어 중복 변경, 경쟁, 데이터 왜곡을 막아야 하기 때문이다.
14

13. 최종 요약

  • 트리거는 지정한 데이터·스키마·시스템 사건에 DBMS가 자동 반응하는 절차형 객체이며 사건·시점·수준·조건·동작으로 설계한다.
  • DML·DDL 트리거, BEFORE·AFTER·INSTEAD OF, 행·문장 수준을 구분하고 이전값·새값의 사건별 존재를 이해한다.
  • 선언적 제약을 우선 검토하고 숨은 실행, 연쇄·재귀, 대량 처리, 트랜잭션과 배포 위험을 관리한다.
  • 이벤트는 동작의 계기가 되는 사건이며, 예약 이벤트는 시각·주기에 따라 데이터베이스 작업을 자동 실행한다.
  • 예약 작업은 멱등성, 겹침, 시간대, 재시작, 대량 처리와 관찰을 설계하고 트리거와의 연쇄 영향까지 시험한다.
