01

학습 목표와 범위

이 레슨은 절차형 SQL에서 값을 계산해 돌려주는 사용자 정의 함수와, 그러한 프로그램 단위를 읽고 작성할 때 필요한 SQL 문법을 함께 다룬다. 학습을 마치면 함수의 입력·처리·반환 구조를 설명하고, 프로시저와 함수의 차이를 구분하며, 선언부와 실행부에서 변수·조건·반복·예외 처리를 올바르게 배치할 수 있어야 한다. 또한 SQL 문장과 절차 제어문이 섞인 코드를 순서대로 추적하여 반환값과 오류 원인을 판단할 수 있어야 한다.

제품마다 함수 생성 키워드, 매개변수 표기, 블록 구분자, 예외 이름에는 차이가 있다. 시험에서는 특정 제품의 사소한 철자보다 입력을 받아 처리하고 하나의 결과를 반환한다는 공통 원리, 매개변수 방향, 실행 흐름, 부작용과 호출 위치를 중심으로 판단한다. 이 레슨에서는 트리거와 이벤트의 상세 동작, DML·DCL 명령 자체의 분류는 인접 레슨의 범위이므로 필요한 비교만 한다.

02

사용자 정의 함수의 개념

사용자 정의 함수(User-Defined Function, UDF)는 데이터베이스 사용자가 업무 규칙이나 반복 계산을 이름 있는 프로그램 단위로 정의해 두고 호출하는 객체다. DBMS가 기본 제공하는 문자열·숫자·날짜 함수만으로 표현하기 어려운 계산을 캡슐화할 때 유용하다. 예를 들어 공급가액과 세율을 받아 세액을 계산하거나, 점수를 받아 등급 문자를 반환하거나, 여러 열을 정규화된 표시 문자열로 바꾸는 규칙을 함수로 만들 수 있다.

함수의 핵심 계약은 “정해진 입력을 받고 정해진 자료형의 결과를 반환한다”는 것이다. 일반적인 구성 요소는 다음과 같다.

  • 함수 이름: 스키마 안에서 객체를 식별하고 호출할 때 사용한다.
  • 매개변수: 호출자가 넘기는 입력의 이름과 자료형을 선언한다.
  • 반환 자료형: 함수 결과가 어떤 형식인지 미리 약속한다.
  • 지역 선언: 계산 중 사용할 변수, 상수, 커서 등을 준비한다.
  • 실행문: 대입, 조회, 조건 분기, 반복 등 실제 로직을 수행한다.
  • 반환문: 계산 결과를 호출자에게 돌려주며 해당 실행 경로를 끝낸다.
  • 예외 처리: 예상 가능한 오류를 다른 결과로 바꾸거나 호출자에게 전파한다.

함수는 하나의 스칼라 값을 반환하는 형태가 대표적이지만, DBMS에 따라 행 집합이나 테이블 형태를 반환하는 함수도 있다. 필기 문제에서는 반환 형식이 명시되면 그 조건을 그대로 읽어야 한다. “함수는 언제나 숫자 하나만 반환한다”거나 “모든 DBMS에서 테이블 반환 함수 문법이 같다”는 식의 일반화는 옳지 않다.

03

함수와 프로시저 비교

함수와 프로시저는 모두 SQL 문장과 절차 제어를 묶어 재사용하는 저장 프로그램이라는 공통점이 있다. 그러나 호출 목적과 결과 전달 방식이 다르다.

표의 내용은 공통 경향이다. 실제로 SQL 문장 안에서 호출 가능한지, 함수 내부에서 데이터를 변경할 수 있는지, 트랜잭션 명령을 허용하는지는 DBMS 규칙을 따른다. 시험 지문에 제품이나 조건이 제시되면 그 조건이 우선한다.

함수를 선택하기 좋은 경우는 계산 결과가 다른 질의의 일부로 필요하고, 동일 규칙이 여러 곳에서 반복되며, 입력과 출력 관계를 명확히 표현할 수 있을 때다. 여러 테이블을 갱신하고 로그를 남기며 성공 여부를 여러 값으로 전달해야 한다면 프로시저가 더 자연스럽다. 함수로 만들 수 있다는 사실과 함수로 만드는 것이 좋은 설계라는 판단은 구분해야 한다.

04

함수 정의와 호출 절차

제품 중립적인 의사 문법으로 등급 계산 함수를 나타내면 다음과 같다.

CREATE FUNCTION 점수등급(점수 INTEGER) RETURNS CHAR(1) BEGIN DECLARE 결과 CHAR(1); IF 점수 >= 90 THEN SET 결과 = 'A'; ELSEIF 점수 >= 80 THEN SET 결과 = 'B'; ELSE SET 결과 = 'C'; END IF; RETURN 결과; END;

이 코드를 읽는 순서는 다음과 같다.

  1. 함수 이름, 매개변수 수와 자료형을 확인한다.
  2. 반환 자료형을 확인해 모든 실행 경로가 호환되는 값을 반환하는지 본다.
  3. 지역 변수의 선언 위치와 초기값을 확인한다.
  4. 조건식을 위에서 아래로 평가하며 실제로 선택되는 경로를 찾는다.
  5. 반환문에 도달할 때 변수의 최종 값을 계산한다.
  6. NULL 입력, 범위를 벗어난 입력, 조회 결과 부재와 같은 경계 조건을 점검한다.

호출은 개념적으로 “점수등급(85)”처럼 인수를 전달하는 표현이다. SQL 문장 안에서 허용된다면 SELECT 목록, 조건식, 정렬식 등에 나타날 수 있다. 그러나 열마다 함수를 반복 호출하면 대상 행 수만큼 실행되어 비용이 커질 수 있다. 특히 함수 내부에서 다시 테이블을 조회한다면 단순한 표기와 달리 실행 비용은 작지 않을 수 있다.

함수의 변경은 보통 기존 정의를 교체하거나 삭제 후 재생성하는 방식으로 수행한다. 함수가 다른 뷰나 프로그램에서 참조되고 있다면 매개변수 또는 반환 자료형 변경이 연쇄 영향을 일으킬 수 있다. 따라서 정의 변경 전에는 의존 객체, 권한, 호출부, NULL 처리 규칙을 확인해야 한다.

05

매개변수와 반환값

매개변수는 외부 값과 함수 내부 이름을 연결한다. 호출 시에는 위치에 따라 대응시키는 방식과 이름을 지정하는 방식이 있을 수 있다. 매개변수 자료형은 호출 인수와 변환 가능해야 하며, 암시적 형 변환에 의존하면 성능 저하나 뜻밖의 비교가 생길 수 있다. 문자열 '10'을 숫자 10으로 자동 변환해 주는지는 제품과 설정에 따라 달라지므로 명시적 변환이 안전하다.

절차형 SQL의 매개변수 방향은 보통 IN, OUT, INOUT 개념으로 설명한다. IN은 호출자의 값을 내부로 전달하고, OUT은 내부 결과를 호출자에게 전달하며, INOUT은 두 방향을 겸한다. 다만 함수는 반환값이 주된 결과이므로 제품에 따라 입력 매개변수만 허용하거나 출력 매개변수 사용을 제한한다. 프로시저의 OUT 매개변수와 함수의 RETURN을 같은 것으로 착각하지 않아야 한다.

반환값에서는 세 가지를 확인한다.

  • 자료형 일치: 반환식이 선언된 반환 자료형과 호환되어야 한다.
  • 경로 완전성: 조건의 어느 분기로 가더라도 필요한 반환이 이루어져야 한다.
  • NULL 의미: 입력이 NULL이거나 조회 결과가 없을 때 NULL을 반환할지, 기본값을 반환할지 정해야 한다.

NULL은 0이나 빈 문자열이 아니라 “알 수 없음 또는 값 없음”을 나타낸다. 따라서 “매개변수 = NULL” 같은 일반 비교로 참을 얻는다고 가정하면 안 된다. NULL 여부는 전용 조건을 사용하며, 계산식에 NULL이 섞일 때 결과가 어떻게 전파되는지도 살펴야 한다.

06

절차형 SQL 문법의 골격

SQL 문법을 절차형 프로그램 관점에서 보면 선언부, 실행부, 예외 처리부라는 골격으로 정리할 수 있다. 정확한 키워드와 구분 기호는 제품마다 다르지만 역할은 비교적 일정하다.

선언부에서는 변수·상수·커서·사용자 정의 예외를 선언한다. 변수에는 이름과 자료형을 부여하고 필요하면 초깃값을 설정한다. 테이블 열과 같은 자료형을 따르도록 참조형 선언을 지원하는 제품도 있는데, 열 자료형 변경에 대응하기 쉽다는 장점이 있다.

실행부에서는 SQL 문장과 절차 제어문을 순서대로 실행한다. 대입문은 계산 결과를 변수에 저장한다. 한 행 조회 결과를 변수에 담는 문법은 결과가 없거나 여러 행이면 예외가 될 수 있으므로 조회 건수 가정을 분명히 해야 한다. 여러 행을 처리하려면 커서나 집합 처리 방식을 고려한다.

예외 처리부에서는 실행 중 발생한 오류를 분류해 대응한다. 특정 오류만 처리하고 나머지는 상위 호출자에게 전파할 수 있으며, 모든 오류를 무조건 정상 결과로 바꾸면 원인을 숨길 수 있다. 예외를 잡은 뒤 적절한 반환, 기록, 정리 또는 재발생 중 무엇이 필요한지 설계한다.

07

조건문과 반복문

조건문은 논리식의 결과에 따라 실행 경로를 나눈다. 대표 형태는 IF–THEN–ELSIF–ELSE와 CASE다. IF는 복합 조건과 절차 흐름에 적합하고, CASE는 하나의 식을 여러 값과 비교하거나 조건별 결과를 간결하게 표현하는 데 적합하다. SQL의 검색 CASE는 첫 번째 참인 WHEN의 결과를 선택하고 뒤 조건은 선택하지 않는다는 점을 기억한다.

조건을 설계할 때는 경계값 순서가 중요하다. 점수 90 이상을 먼저 검사한 뒤 80 이상을 검사해야 한다. 80 이상을 먼저 검사하면 95도 그 분기에 들어가 A 경로에 도달하지 않는다. 범위가 겹치는지, 빠지는 값이 있는지, NULL일 때 조건 결과가 어떻게 되는지 표로 점검하면 좋다.

반복문은 조건이 참인 동안 반복하는 방식, 본문 실행 후 조건을 검사하는 방식, 정해진 범위를 순회하는 방식 등으로 구분한다. 종료 조건이 갱신되지 않으면 무한 반복이 된다. 반복 중 특정 조건에서 빠져나가는 종료문과 현재 회차만 건너뛰는 제어문의 차이도 알아야 한다.

SQL은 원래 행 집합을 한 번에 처리하는 데 강하다. 모든 행을 커서로 한 줄씩 순회하는 절차형 코드는 이해하기 쉬울 수 있지만 대량 데이터에서는 집합 기반 SQL보다 느릴 수 있다. 반복이 필요하다는 이유만으로 커서를 먼저 선택하지 말고, 하나의 집합 연산으로 바꿀 수 있는지 확인한다.

08

커서와 한 행씩 처리하는 흐름

커서는 질의 결과의 현재 위치를 가리키며 여러 행을 순차적으로 처리하게 한다. 일반 흐름은 선언, 열기, 인출 반복, 종료 조건 확인, 닫기다.

  1. 처리할 SELECT 문을 커서로 선언한다.
  2. 커서를 열어 결과 집합을 준비한다.
  3. 현재 행을 변수로 인출한다.
  4. 더 이상 행이 없는지 확인한다.
  5. 행 단위 로직을 수행하고 다음 행으로 이동한다.
  6. 반복이 끝나면 커서를 닫아 자원을 해제한다.

인출보다 종료 여부 확인을 잘못 배치하면 마지막 행을 두 번 처리하거나 존재하지 않는 값을 처리할 수 있다. 오류가 발생해도 커서를 닫아야 하는지 고려해야 한다. 일부 제품은 반복문이 커서의 열기·인출·닫기를 자동 관리하지만, 시험에서는 명시적 단계가 제시되면 순서를 정확히 판단한다.

09

예외 처리와 안정성

함수에서 흔한 오류는 0으로 나누기, 자료형 변환 실패, 조회 결과 없음, 한 행을 기대했는데 여러 행 반환, 제약조건 위반 등이다. 입력값 검사는 예외가 발생하기 전에 의미 없는 계산을 막는다. 예를 들어 분모가 0이면 NULL을 반환할지 업무상 오류로 처리할지 먼저 정해야 한다.

예외 처리의 목적은 오류를 없었던 일로 만드는 것이 아니라 일관된 계약을 유지하는 것이다. 함수가 실패했는데 무조건 0을 반환하면 실제 0과 오류를 구분할 수 없다. NULL, 오류 코드, 예외 재발생 중 무엇이 호출자에게 가장 분명한지 판단한다. 보안상 내부 테이블명이나 상세 시스템 정보를 최종 사용자에게 그대로 노출하지 않는 것도 중요하다.

함수 내부 질의가 읽는 데이터가 바뀌면 같은 인수라도 결과가 달라질 수 있다. 이 경우 함수를 순수 계산으로 생각해 결과를 임의로 캐시하면 안 된다. 결정성 여부를 선언하거나 최적화에 활용하는 기능이 있더라도 실제 성질과 맞게 지정해야 한다.

10

적용 예시: 배송비 계산

주문금액과 회원등급을 받아 배송비를 반환한다고 하자. 규칙은 “주문금액이 50,000 이상이면 0, 아니면서 회원등급이 VIP이면 1,000, 그 밖에는 3,000”이다.

FUNCTION 배송비(주문금액 DECIMAL, 회원등급 VARCHAR) RETURNS INTEGER BEGIN IF 주문금액 IS NULL THEN RETURN NULL; ELSEIF 주문금액 >= 50000 THEN RETURN 0; ELSEIF 회원등급 = 'VIP' THEN RETURN 1000; ELSE RETURN 3000; END IF; END;

입력이 (70000, '일반')이면 첫 금액 조건이 참이므로 0이다. (30000, 'VIP')이면 두 번째 유효 조건이 참이므로 1000이다. 주문금액이 NULL이면 업무 규칙상 계산 불가를 나타내도록 NULL을 반환한다. 회원등급이 NULL이고 금액이 30000이면 VIP 비교는 참이 아니므로 ELSE의 3000으로 간다. 문제에서 NULL 정책이 다르게 주어지면 그 정책을 따른다.

이 예시는 반환 경로가 짧고 명확하다는 장점이 있다. 반면 세율표나 등급 규칙이 자주 바뀐다면 값을 코드에 고정하기보다 정책 테이블을 조회하는 설계를 검토한다. 다만 조회형 함수는 행마다 반복 호출될 때 비용이 커질 수 있으므로 호출 규모도 함께 본다.

11

시험 함정

  • “함수와 프로시저는 모두 저장 프로그램이므로 호출 방식과 결과 전달 방식도 같다”는 설명은 틀리다.
  • RETURN은 함수의 결과를 돌려주고 실행 경로를 끝내는 핵심 문장이다. 단순 변수 대입만으로 호출자에게 반환되는 것은 아니다.
  • NULL은 0이나 공백이 아니며 일반 등호 비교로 NULL 여부를 판정하지 않는다.
  • 모든 분기에서 반환값이 정해지는지 확인한다. 조건이 거짓일 때 반환 없이 끝나는 경로가 함정으로 자주 나온다.
  • 조건은 위에서부터 평가하므로 넓은 범위를 먼저 쓰면 뒤의 좁은 범위가 도달 불가능해질 수 있다.
  • 커서의 일반 순서는 선언–열기–인출–종료 확인과 처리–닫기다. 열지 않은 커서에서 인출하거나 종료 후 닫지 않는 선택지를 경계한다.
  • 절차형 반복이 언제나 빠른 것은 아니다. 대량 행 처리는 집합 기반 SQL이 더 적합할 수 있다.
  • 함수가 SQL 표현식에 사용될 수 있는지와 내부에서 변경 SQL을 실행할 수 있는지는 DBMS별 제한이 있으므로 무조건 가능하다고 단정하지 않는다.
  • 예외를 모두 잡아 0을 반환하면 안정적인 것이 아니다. 정상값 0과 실패를 구별하지 못할 수 있다.
  • 암시적 자료형 변환은 편리하지만 변환 오류와 인덱스 활용 저하를 일으킬 수 있다.
12

확인 문제

  1. 사용자 정의 함수의 가장 핵심적인 입출력 계약을 한 문장으로 설명하라.
  2. 함수와 프로시저를 목적, 결과 전달, 일반적인 호출 방식의 세 기준으로 비교하라.
  3. 점수 조건을 “80 이상 B, 90 이상 A” 순서로 작성했을 때 95점이 B가 되는 이유는 무엇인가?
  4. 함수의 모든 실행 경로에서 RETURN을 점검해야 하는 이유는 무엇인가?
  5. 커서 처리의 일반적인 다섯 단계를 순서대로 쓰라.
  6. NULL 입력을 “입력 = NULL”로 검사하면 안 되는 이유를 설명하라.
  7. 행마다 사용자 정의 함수를 호출할 때 성능을 검토해야 하는 이유 두 가지를 쓰라.
  8. 함수 내부 예외를 무조건 0으로 바꾸는 설계의 문제점은 무엇인가?
13

정답과 해설

  1. 정해진 매개변수로 입력을 받고 선언된 자료형과 의미를 갖는 결과를 반환한다는 계약이다. 호출자는 이 계약을 전제로 함수를 표현식처럼 사용한다.
  2. 함수는 값 계산과 반환이 중심이고, 프로시저는 일련의 업무 작업 수행이 중심이다. 함수는 RETURN으로 선언된 결과를 제공하며 SQL 표현식에 허용되는 경우가 많고, 프로시저는 출력 매개변수나 결과 집합 등을 사용하며 독립 호출이 일반적이다. 세부 허용 범위는 DBMS에 따라 다르다.
  3. 조건을 위에서부터 검사하므로 95는 먼저 나온 “80 이상”을 만족한다. 이미 그 분기가 선택되어 뒤의 90 이상 조건에 도달하지 않는다. 좁고 높은 범위를 먼저 둬야 한다.
  4. 어떤 입력에서는 반환값 없이 끝나거나 선언 자료형과 맞지 않는 값을 반환할 수 있기 때문이다. 조건의 참·거짓, 예외 경로, NULL 경로를 모두 추적해야 한다.
  5. 선언, 열기, 인출, 종료 조건 확인과 행 처리 반복, 닫기다. 제품별 자동화 문법이 있어도 이 논리 순서는 유지된다.
  6. NULL은 알 수 없는 값을 나타내므로 일반 비교 결과도 미정이 된다. NULL 전용 판정 조건을 사용해야 한다.
  7. 대상 행 수만큼 함수 본문이 반복되고, 함수 내부에 테이블 조회나 복잡한 계산이 있으면 그 비용도 반복되기 때문이다. 집합 연산으로 대체 가능한지 살핀다.
  8. 실제 계산 결과 0과 오류로 인한 0을 구별할 수 없고 원인을 숨긴다. 호출자가 실패를 정상으로 오해할 수 있으므로 명확한 오류 계약이 필요하다.
14

최종 요약

  • 사용자 정의 함수는 반복되는 업무 계산을 이름 있는 데이터베이스 객체로 만들고 선언된 결과를 반환한다.
  • 함수의 기본 구조는 매개변수, 반환 자료형, 지역 선언, 실행문, RETURN, 필요 시 예외 처리로 이뤄진다.
  • 함수는 값 계산이 중심이고 프로시저는 작업 수행이 중심이지만, 구체적인 호출·변경 허용 범위는 DBMS마다 다르다.
  • SQL 문법에서는 선언부·실행부·예외 처리부, 조건문, 반복문, 커서의 역할과 실행 순서를 구분해야 한다.
  • NULL, 경계값, 모든 반환 경로, 자료형 변환, 예외 의미를 함께 점검해야 정확하고 안전한 함수를 설계할 수 있다.
  • 대량 데이터에서는 행 단위 반복이나 함수 반복 호출보다 집합 기반 처리 가능성을 먼저 검토한다.
