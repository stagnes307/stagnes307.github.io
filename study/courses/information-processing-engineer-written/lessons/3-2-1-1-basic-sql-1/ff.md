# 3-2-1-1. DDL · 관계형 데이터 모델 · 트랜잭션

## 학습 목표와 범위

이 레슨은 데이터 구조를 정의하는 **DDL**, 데이터를 릴레이션으로 표현하는 **관계형 데이터 모델**, 논리적인 작업 단위를 안전하게 처리하는 **트랜잭션**을 연결해 이해한다. 학습 후 CREATE·ALTER·DROP 등 정의 명령의 효과를 구분하고, 릴레이션의 속성·튜플·도메인·키와 무결성 제약을 설명하며, ACID 특성과 COMMIT·ROLLBACK·SAVEPOINT의 의미를 사례에 적용할 수 있어야 한다.

다음 레슨은 테이블 구현 요소와 데이터 사전을 더 자세히 다루고, 이후 레슨은 뷰·인덱스·집합 연산자를 다룬다. 여기서는 그 항목을 DDL과 관계 모델을 설명하는 데 필요한 수준으로만 언급한다. DDL의 자동 확정 여부, ALTER가 지원하는 세부 동작, 격리 수준의 기본값은 DBMS마다 다르므로 조건 없는 제품 종속 단정은 피한다.

## DDL의 개념

DDL(Data Definition Language)은 데이터베이스의 논리적·물리적 객체 구조를 정의하고 변경하며 제거하는 언어다. 대표 명령은 CREATE, ALTER, DROP이며, 테이블의 모든 행을 빠르게 제거하는 TRUNCATE를 DDL 범주로 설명하는 경우가 많다. 스키마, 테이블, 뷰, 인덱스, 제약조건 등 어떤 객체를 다루는지는 명령 뒤의 객체 종류로 판단한다.

| 명령 | 목적 | 결과를 읽는 핵심 |
|---|---|---|
| CREATE | 새 객체 정의 | 이름, 열·자료형, 제약조건, 옵션 |
| ALTER | 기존 객체 구조 변경 | 추가·변경·삭제 대상과 기존 데이터 영향 |
| DROP | 객체 자체 제거 | 데이터와 정의, 의존 객체 영향 |
| TRUNCATE | 테이블의 전체 행 제거 | 구조 보존 여부, 로그·롤백·제약의 제품별 특성 |

DDL은 저장된 행을 한 건씩 업무 조건으로 수정하는 DML과 목적이 다르다. DELETE는 조건에 맞는 행을 지우고 구조는 유지하지만, DROP TABLE은 테이블 정의 자체를 제거한다. TRUNCATE는 일반적으로 WHERE 조건 없이 전체 행을 대상으로 하며 구조는 남긴다. 세 명령의 저장 공간 처리와 롤백 가능성은 DBMS에 따라 달라질 수 있으므로 “항상”이라는 표현을 경계한다.

## CREATE와 자료 구조 정의

테이블 생성에서는 열 이름, 자료형, NULL 허용 여부, 기본값, 제약조건을 정한다.

    CREATE TABLE 수강 (
        학번       VARCHAR(20) NOT NULL,
        과목코드   VARCHAR(20) NOT NULL,
        수강연도   INTEGER     NOT NULL,
        성적       DECIMAL(5,2),
        CONSTRAINT 수강_pk
            PRIMARY KEY (학번, 과목코드, 수강연도)
    );

복합 기본키는 세 열의 조합이 각 행을 유일하게 식별한다는 뜻이다. 각 열 하나가 반드시 유일하다는 뜻은 아니다. 성적은 아직 확정되지 않을 수 있어 NULL을 허용했다고 볼 수 있다. 자료형의 크기와 정밀도는 실제 값의 범위, 비교·계산, 저장 효율을 함께 고려한다.

DEFAULT는 값을 생략했을 때 적용할 기본값이며, 명시적으로 NULL을 넣는 것과 같은지는 DBMS와 열 제약에 따라 살핀다. 자동 생성값이나 현재 시각을 기본값으로 쓸 때도 평가 시점과 변경 정책을 명확히 한다.

## ALTER와 변경 관리

ALTER는 열 추가, 자료형·기본값·NULL 허용 변경, 열 삭제, 제약조건 추가·삭제 등에 사용된다. 정확한 하위 문법은 제품마다 다르지만 변경 전 질문은 공통적이다.

1. 기존 행이 새 제약조건을 모두 만족하는가?
2. 자료형 변환 과정에서 손실이나 실패가 없는가?
3. 열 삭제 시 응용 프로그램·뷰·인덱스·제약이 참조하지 않는가?
4. 큰 테이블 변경이 잠금, 저장 공간, 서비스 시간에 어떤 영향을 주는가?
5. 실패 시 원래 구조와 데이터를 어떻게 복구할 것인가?

NULL이 있는 열을 NOT NULL로 바꾸려면 기존 NULL을 먼저 처리해야 한다. 문자열 열의 길이를 줄이면 기존 값이 새 범위보다 길 수 있다. 외래키를 추가하면 기존 자식 값 중 부모에 없는 값이 검증을 막을 수 있다. 문법이 맞는 것과 운영상 안전한 것은 별개다.

## DROP, TRUNCATE, DELETE 비교

| 기준 | DELETE | TRUNCATE | DROP TABLE |
|---|---|---|---|
| 주목적 | 조건에 따른 행 삭제 | 전체 행 제거 | 테이블 객체 제거 |
| WHERE | 사용 가능 | 일반적으로 사용하지 않음 | 해당 없음 |
| 구조 | 유지 | 유지 | 제거 |
| 행 단위 처리 | DML 성격 | 일괄 구조 명령 성격 | 객체 정의 제거 |
| 롤백·로그 | 트랜잭션 설정을 따름 | 제품별 차이가 큼 | 제품별 DDL 특성을 따름 |

시험에서는 가장 분명한 목적과 구조 보존 여부를 먼저 본다. “TRUNCATE는 모든 제품에서 절대로 롤백할 수 없다” 같은 문장은 제품 조건이 없으면 지나치게 단정적이다. 참조 제약이 있는 테이블에 TRUNCATE가 허용되는지, 자동 증가 값이 어떻게 되는지도 제품에 따라 다르다.

DROP은 의존 관계에 영향을 준다. 다른 객체가 참조하면 제거를 거부하거나, 명시적인 연쇄 옵션을 요구하거나, 의존 객체를 무효화할 수 있다. 편의를 위해 연쇄 제거를 사용하기 전 정확한 영향 범위를 확인한다.

## 관계형 데이터 모델의 기본 용어

**관계형 데이터 모델**은 데이터를 릴레이션이라는 2차원 표 형태의 논리 구조로 표현하고, 키와 무결성 제약을 통해 관계를 유지한다.

- 릴레이션 스키마: 릴레이션 이름과 속성들의 구조적 정의
- 릴레이션 인스턴스: 특정 시점에 릴레이션에 들어 있는 튜플 집합
- 속성(Attribute): 열에 해당하며 데이터의 의미 있는 특성
- 튜플(Tuple): 행에 해당하며 하나의 사실이나 개체 발생을 표현
- 도메인(Domain): 한 속성이 취할 수 있는 원자값의 집합과 의미 범위
- 차수(Degree): 릴레이션을 구성하는 속성 수
- 카디널리티(Cardinality): 특정 시점의 튜플 수

차수는 열 수이고 카디널리티는 행 수다. 데이터를 추가·삭제하면 카디널리티는 바뀌지만 스키마가 그대로라면 차수는 바뀌지 않는다. 열을 추가하는 DDL은 차수를 바꾼다.

관계 모델의 릴레이션은 수학적 집합에 바탕을 두므로 같은 튜플의 중복이 없고 튜플 순서에 의미가 없다는 이론적 성질을 가진다. 실제 SQL 테이블은 키 제약이 없으면 중복 행을 허용할 수 있고, ORDER BY 없이는 표시 순서가 보장되지 않는다. 이론적 관계와 SQL 구현의 차이를 구분한다.

각 속성값은 해당 도메인에 속해야 하며 개념적으로 원자값이어야 한다. 하나의 셀에 여러 전화번호를 구분자로 이어 넣으면 검색·제약·갱신이 어려워진다. 반복 값은 별도 릴레이션으로 분리하는 것이 관계 설계 원리에 더 맞다.

## 키의 종류

키는 튜플을 식별하거나 릴레이션 사이를 연결한다.

- 슈퍼키: 튜플을 유일하게 식별할 수 있는 속성 집합. 불필요한 속성을 포함할 수 있다.
- 후보키: 유일성과 최소성을 함께 만족하는 최소 슈퍼키.
- 기본키: 후보키 중 대표 식별자로 선택한 키.
- 대체키: 후보키 중 기본키로 선택되지 않은 키.
- 외래키: 다른 릴레이션의 후보키 또는 기본키를 참조하여 관계를 표현하는 속성 집합.
- 복합키: 둘 이상의 속성 조합으로 된 키.

유일성은 같은 키 값의 튜플이 둘 없다는 성질이고, 최소성은 키에서 어느 속성 하나를 빼면 유일성을 잃는다는 성질이다. 학번이 이미 유일한데 {학번, 이름}을 식별자로 사용하면 슈퍼키이지만 최소성이 없어 후보키는 아니다.

기본키는 개체 무결성에 따라 NULL일 수 없고 유일해야 한다. 외래키는 참조 무결성에 따라 참조 대상 키 값과 일치하거나, 설계상 허용된다면 NULL일 수 있다. 외래키 값이 반드시 자식 테이블 안에서 유일해야 하는 것은 아니다. 여러 주문이 같은 고객을 참조할 수 있다.

## 무결성 제약

관계형 데이터의 정확성과 일관성을 지키는 대표 무결성은 다음과 같다.

| 무결성 | 의미 | 대표 구현 |
|---|---|---|
| 도메인 무결성 | 속성값이 허용된 자료형·범위·형식에 속함 | 자료형, NOT NULL, CHECK |
| 개체 무결성 | 기본키가 각 튜플을 유일하게 식별하고 NULL이 아님 | PRIMARY KEY |
| 참조 무결성 | 외래키가 존재하는 부모 키를 참조하거나 허용된 NULL임 | FOREIGN KEY |
| 사용자 정의 무결성 | 업무 고유 규칙을 만족함 | CHECK, UNIQUE, 프로그램 규칙 등 |

부모 행을 삭제·변경할 때 외래키 동작은 제한, 연쇄 변경·삭제, NULL 설정 등으로 설계할 수 있다. 연쇄 동작은 자동으로 일관성을 유지하지만 영향 범위가 커질 수 있다. 업무 의미와 생명주기를 고려한다.

제약조건은 오류를 귀찮게 만드는 장애물이 아니라 잘못된 상태가 저장되는 것을 막는 선언적 규칙이다. 응용 프로그램 검증과 데이터베이스 제약을 함께 사용하되, 여러 경로로 데이터가 들어와도 지켜야 할 규칙은 데이터베이스에 두는 것이 안전하다.

## 트랜잭션의 개념

**트랜잭션**은 데이터베이스에서 하나의 논리적 업무 단위로 취급되는 연산들의 집합이다. 계좌 이체는 출금과 입금이 함께 성공해야 한다. 출금만 저장되고 입금이 실패하면 업무적으로 잘못된 상태가 된다.

트랜잭션 상태는 일반적으로 활동(실행 중), 부분 완료(마지막 연산 수행), 완료 또는 확정, 실패, 철회 또는 중단 같은 흐름으로 설명한다. 부분 완료는 아직 영구 반영이 보장된 최종 완료와 다르다. 실패하면 지금까지의 영향을 되돌려 일관된 이전 상태로 복귀하고, 필요하면 다시 시작한다.

트랜잭션 경계는 너무 넓으면 잠금과 자원 점유가 길어지고, 너무 좁으면 하나의 업무가 중간 상태로 쪼개질 수 있다. 사용자 입력을 기다리는 동안 트랜잭션을 오래 유지하지 않도록 하고, 실제로 원자성이 필요한 연산을 한 단위로 묶는다.

## ACID 특성

| 특성 | 의미 | 계좌 이체 예시 |
|---|---|---|
| 원자성(Atomicity) | 전부 수행되거나 전부 수행되지 않음 | 출금과 입금 모두 반영 또는 모두 취소 |
| 일관성(Consistency) | 트랜잭션 전후 정의된 제약과 규칙 유지 | 잔액·키·참조 규칙을 만족 |
| 격리성(Isolation) | 동시 실행이 서로의 미완료 중간 상태를 함부로 보지 않음 | 다른 거래가 이체 중간 잔액을 오해하지 않음 |
| 지속성(Durability) | 확정된 결과가 장애 후에도 보존됨 | 성공 응답한 이체가 재시작 후에도 남음 |

일관성은 “모든 값이 현실적으로 옳다”를 DBMS가 자동 보장한다는 뜻이 아니다. 정의된 제약, 트랜잭션 로직, 동시성 제어가 올바르게 설계되어야 한다. 잘못된 금액을 정상 문법으로 입력하면 자료형 제약만으로 업무 오류를 알아낼 수 없다.

격리성은 동시 실행을 완전히 직렬로 만드는 것과 같은 효과를 목표로 설명되지만, 실제 DBMS는 성능과 일관성 사이에서 여러 격리 수준과 동시성 제어를 제공한다. 낮은 격리에서는 다른 트랜잭션과의 상호작용으로 비반복 읽기나 유령 행 같은 현상이 나타날 수 있다. 구체적인 보장 범위는 선택한 격리 수준과 DBMS 구현을 따른다.

## COMMIT, ROLLBACK, SAVEPOINT

COMMIT은 트랜잭션의 성공적인 변경을 확정한다. ROLLBACK은 아직 확정되지 않은 변경을 취소하고 이전 일관된 상태로 되돌린다. SAVEPOINT는 트랜잭션 내부에 이름 있는 중간 지점을 만들어 전체가 아닌 일부 작업을 그 지점까지 되돌릴 수 있게 한다.

    트랜잭션 시작
    주문 헤더 추가
    SAVEPOINT 헤더완료
    주문 항목 추가
    재고 차감
    모든 검증 성공 시 COMMIT
    항목 오류이며 헤더를 유지할 이유가 있을 때 정책에 따라 저장점 복귀
    업무 전체가 실패하면 ROLLBACK

저장점으로 일부를 되돌릴 수 있다고 해서 항상 부분 성공이 허용되는 것은 아니다. 주문 헤더만 남는 것이 업무상 무의미하다면 전체 롤백해야 한다. 트랜잭션 제어는 기술 기능보다 업무 원자성 경계를 먼저 따른다.

일부 환경의 자동 커밋은 각 문장을 자동으로 확정할 수 있다. 여러 문장을 하나의 업무 단위로 묶어야 한다면 연결과 트랜잭션 설정을 확인한다. 이미 확정된 변경은 일반적인 ROLLBACK만으로 취소되지 않으므로 보상 트랜잭션이나 복구 절차가 필요할 수 있다.

## 동시성과 이상 현상

동시 실행에서는 미확정 값을 읽는 오손 읽기, 같은 행을 다시 읽을 때 값이 달라지는 비반복 읽기, 같은 조건의 행 집합이 달라지는 유령 읽기, 한쪽 변경이 덮이는 갱신 손실을 고려한다. 격리 수준은 이런 현상의 허용 범위를 정하지만 구현은 잠금·다중 버전 등 다양하다. 높은 격리는 이상 현상을 줄이는 대신 대기나 재시도를 늘릴 수 있다.

## 통합 예시: 수강 신청

관계 모델에서 학생과 과목은 각각 기본키를 가지고, 수강 릴레이션은 학번과 과목코드를 외래키로 참조한다. 같은 학생이 같은 연도에 같은 과목을 중복 신청하지 못하게 복합 기본키 또는 유일성 제약을 둔다. 성적 범위가 0부터 100이라면 CHECK 같은 도메인 규칙을 적용할 수 있다.

DDL로 구조를 생성한 뒤 수강 신청 트랜잭션은 정원 확인, 중복 확인, 수강 행 삽입, 현재 인원 반영을 하나의 업무 단위로 처리한다. 두 사용자가 마지막 한 자리를 동시에 신청할 수 있으므로 단순 조회 후 삽입만으로는 충분하지 않을 수 있다. 적절한 동시성 제어와 제약을 사용하고, 한 단계라도 실패하면 전체 결과가 업무 규칙을 만족하도록 롤백한다.

구조를 바꾸어 학기 열을 추가한다면 기존 행에 어떤 값을 채울지, 복합키에 학기를 포함할지, 참조하는 프로그램을 어떻게 전환할지 검토한다. ALTER 문법 한 줄보다 데이터 이행과 제약 검증이 더 큰 작업일 수 있다.

## 시험 함정

- CREATE는 생성, ALTER는 구조 변경, DROP은 객체 제거다.
- DELETE·TRUNCATE·DROP은 모두 “삭제”처럼 보이지만 조건 사용과 구조 보존 여부가 다르다.
- 차수는 속성 수, 카디널리티는 튜플 수다.
- 후보키는 유일성뿐 아니라 최소성도 만족해야 한다.
- 복합키는 각 구성 열이 각각 유일하다는 뜻이 아니라 조합이 유일하다는 뜻이다.
- 기본키는 NULL이 될 수 없고, 외래키는 설계상 허용되면 NULL일 수 있다.
- 외래키가 자식 릴레이션에서 유일해야 하는 것은 아니다.
- 원자성은 모두 실행 또는 모두 취소, 지속성은 확정 결과의 보존이다.
- 부분 완료 상태를 최종 확정 상태와 혼동하지 않는다.
- SAVEPOINT는 기술적으로 부분 복귀를 지원하지만 업무가 부분 성공을 허용한다는 뜻은 아니다.
- DDL의 자동 확정과 TRUNCATE의 롤백 가능성을 모든 DBMS에 동일하게 단정하지 않는다.
- 높은 격리 수준이 언제나 최선은 아니다. 정확성 요구와 동시 처리 비용의 균형이 필요하다.

## 확인 문제

1. CREATE, ALTER, DROP의 목적을 각각 설명하라.
2. DELETE, TRUNCATE, DROP TABLE을 WHERE 사용 가능성과 구조 보존 기준으로 비교하라.
3. 릴레이션의 차수와 카디널리티는 무엇이며 어떤 변경으로 각각 달라지는가?
4. 슈퍼키와 후보키의 차이를 유일성과 최소성으로 설명하라.
5. 개체 무결성과 참조 무결성의 핵심 규칙을 쓰라.
6. 트랜잭션의 ACID 네 특성을 계좌 이체 예와 연결해 설명하라.
7. COMMIT, ROLLBACK, SAVEPOINT의 역할을 구분하라.
8. 수강 신청에서 단순히 정원을 조회한 뒤 삽입하는 방식만으로 동시 초과 신청을 막기 어려운 이유는 무엇인가?

## 정답과 해설

1. CREATE는 새 객체를 정의하고, ALTER는 기존 객체 구조를 변경하며, DROP은 객체 정의 자체를 제거한다.
2. DELETE는 WHERE로 일부 행을 지울 수 있고 구조를 유지한다. TRUNCATE는 일반적으로 조건 없이 전체 행을 제거하고 구조를 유지한다. DROP TABLE은 WHERE 대상이 아니며 구조 자체를 제거한다. 세부 트랜잭션 동작은 제품별로 확인한다.
3. 차수는 속성 즉 열의 수이고, 카디널리티는 특정 시점의 튜플 즉 행의 수다. 열을 추가·삭제하면 차수가, 행을 추가·삭제하면 카디널리티가 달라진다.
4. 슈퍼키는 유일하게 식별하면 되지만, 후보키는 그중 불필요한 속성이 없는 최소 슈퍼키다. 즉 유일성과 최소성을 모두 만족한다.
5. 개체 무결성은 기본키가 유일하고 NULL이 아니어야 한다는 규칙이다. 참조 무결성은 외래키가 존재하는 참조 대상 키와 일치하거나 허용된 NULL이어야 한다는 규칙이다.
6. 원자성은 출금·입금 전부 성공 또는 전부 취소, 일관성은 이체 전후 제약 유지, 격리성은 다른 거래가 미완료 중간 상태를 오해하지 않음, 지속성은 확정된 이체가 장애 후에도 보존됨이다.
7. COMMIT은 변경 확정, ROLLBACK은 미확정 변경 취소, SAVEPOINT는 트랜잭션 내부의 부분 복귀 지점이다.
8. 조회와 삽입 사이에 다른 트랜잭션도 같은 남은 자리를 보고 신청할 수 있기 때문이다. 적절한 잠금·격리·원자적 조건 갱신이나 제약 및 실패 처리가 필요하다.

## 최종 요약

- **DDL**은 CREATE·ALTER·DROP을 중심으로 데이터베이스 객체의 구조를 정의·변경·제거한다.
- 구조 변경 전에는 기존 데이터, 제약, 의존 객체, 잠금과 복구 가능성을 함께 점검해야 한다.
- **관계형 데이터 모델**은 릴레이션, 속성, 튜플, 도메인, 키, 무결성 제약으로 데이터를 표현한다.
- 후보키는 유일성과 최소성, 기본키는 개체 무결성, 외래키는 참조 무결성과 연결된다.
- **트랜잭션**은 논리적 업무 단위이며 원자성·일관성·격리성·지속성의 ACID 특성을 지향한다.
- COMMIT·ROLLBACK·SAVEPOINT와 동시성 제어는 제품 기능 이전에 업무의 원자성 경계를 정확히 정의한 뒤 사용해야 한다.
