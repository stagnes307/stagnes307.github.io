FF 원문 제목3-2-1-2. 테이블 · 데이터 사전

01

학습 목표와 범위

이 레슨은 관계형 데이터베이스에서 실제 데이터를 저장하는 테이블의 구성과 관리 원칙, 데이터베이스 객체의 정의 정보를 관리하는 데이터 사전의 역할을 다룬다. 학습 후에는 열·행·자료형·기본값·제약조건을 업무 규칙과 연결하고, 테이블 생성 및 변경 시 기존 데이터와 의존성을 점검하며, 데이터 사전에서 객체·열·제약·권한 같은 메타데이터를 찾아 활용할 수 있어야 한다.

앞 레슨의 DDL 명령·관계형 모델·트랜잭션 이론과 뒤 레슨의 뷰·인덱스는 필요한 연결만 설명한다. 데이터 사전의 실제 뷰 이름, 시스템 스키마, 조회 권한 범위는 DBMS마다 다르므로 공통 개념을 중심으로 학습한다.

02

테이블의 의미와 구성

테이블은 관계형 데이터베이스에서 동일한 구조를 따르는 행들의 집합을 저장하는 기본 객체다. 하나의 행은 한 건의 사실이나 개체 발생을 표현하고, 하나의 열은 모든 행에 공통으로 적용되는 속성의 의미와 값 범위를 정의한다.

예를 들어 상품 테이블은 상품번호, 상품명, 단가, 판매상태 열을 가진다. 각 행은 상품 한 건이다. 상품번호는 행을 식별하고, 단가는 숫자 범위와 통화 의미를 가지며, 판매상태는 허용된 코드만 저장해야 한다. 열 이름과 자료형만 정하는 것으로 충분하지 않고 식별·필수·범위·참조 규칙을 제약조건으로 표현해야 한다.

테이블의 논리 구조와 물리 저장은 구분한다. 사용자는 행과 열의 논리 구조를 대상으로 SQL을 작성하지만, DBMS는 페이지, 파일, 파티션 등 내부 구조에 저장할 수 있다. 제품별 물리 옵션이 달라도 관계형 SQL이 보는 기본 구조는 테이블이다.

03

열 설계 원칙

열을 설계할 때는 이름, 자료형, 길이 또는 정밀도, NULL 허용, 기본값, 제약조건, 의미 설명을 함께 결정한다.

  • 이름은 업무 의미를 명확히 드러내고 일관된 규칙을 따른다.
  • 자료형은 값의 성질과 연산을 반영한다. 수량은 숫자, 날짜는 날짜 계열로 저장하는 것이 문자열보다 검증과 계산에 유리하다.
  • 문자열 길이와 숫자 정밀도는 현재 예시 하나가 아니라 허용 가능한 업무 범위를 기준으로 정한다.
  • NULL은 “알 수 없음 또는 값 없음”이 허용될 때 사용한다. 0, 공백, 특정 마법값으로 대신하면 의미가 섞인다.
  • 기본값은 입력 생략 시 합리적인 값이 분명할 때 둔다. 잘못된 누락을 숨기는 기본값은 피한다.
  • 단위가 있는 값은 통화, 길이, 시간대 같은 의미가 혼동되지 않도록 이름이나 별도 열로 표현한다.

전화번호·우편번호·사번처럼 숫자로만 보이더라도 산술 연산 대상이 아니고 앞의 0이 의미 있으면 문자열이 적합할 수 있다. 반대로 날짜를 '20260828' 같은 문자열로 저장하면 유효성 검증, 기간 계산, 정렬 규칙을 응용 프로그램마다 다시 구현해야 한다.

정확한 금액은 이진 부동소수점보다 고정 정밀도 숫자형이 적합한 경우가 많다. 평균·비율처럼 계산 결과의 자릿수도 고려한다. 자료형 선택은 저장 크기만의 문제가 아니라 비교 의미, 정렬, 인덱스 사용, 변환 오류와 연결된다.

04

행 식별과 키

각 행은 안정적인 키로 식별되어야 한다. 업무에서 이미 유일하고 변하지 않는 값이 있다면 자연키 후보가 된다. 별도의 순번 같은 대리키를 사용할 수도 있다. 대리키를 쓴다고 주민등록번호나 상품코드 같은 업무상 유일 규칙이 사라지는 것은 아니므로 필요한 UNIQUE 제약을 별도로 둔다.

복합키는 여러 열의 조합으로 행을 식별한다. 주문항목에서 주문번호와 항목순번 조합이 기본키라면 항목순번 1은 여러 주문에 있을 수 있지만 같은 주문 안에서는 한 번만 나타나야 한다.

키 선택 시 다음을 검토한다.

  1. 모든 정상 행에서 값이 존재하는가?
  2. 중복되지 않는가?
  3. 값이 자주 변경되지 않는가?
  4. 지나치게 길어 참조 테이블과 인덱스 비용을 키우지 않는가?
  5. 업무상 유일성과 기술적 식별을 각각 어떻게 보장하는가?
05

제약조건으로 규칙 선언하기

NOT NULL은 필수값, UNIQUE는 열 또는 열 조합의 중복 금지, PRIMARY KEY는 대표 식별, FOREIGN KEY는 테이블 사이 참조, CHECK는 행 값의 조건을 선언한다.

CREATE TABLE 상품 ( 상품번호 VARCHAR(20) NOT NULL, 상품명 VARCHAR(200) NOT NULL, 단가 DECIMAL(12,2) NOT NULL, 판매상태 VARCHAR(10) DEFAULT '판매' NOT NULL, CONSTRAINT 상품pk PRIMARY KEY (상품번호), CONSTRAINT 상품단가ck CHECK (단가 >= 0), CONSTRAINT 상품상태_ck CHECK (판매상태 IN ('판매', '중지')) );

단가 제약은 음수를 막고 상태 제약은 허용 코드를 제한한다. 그러나 통화 단위나 할인 정책 전체까지 이 한 테이블이 자동으로 보장하는 것은 아니다. 행 하나만으로 판정 가능한 규칙과 여러 행·테이블·시간 흐름을 함께 봐야 하는 규칙을 구분한다.

외래키는 부모 테이블에 존재하는 키를 참조하게 한다. 부모 삭제 시 제한, 연쇄 삭제, NULL 설정 등 참조 동작을 선택할 수 있지만 업무 생명주기에 맞아야 한다. 고객을 삭제했다고 과거 거래까지 자동 삭제하는 설계는 감사·정산 요구와 충돌할 수 있다.

제약조건 이름을 명시하면 오류 메시지와 변경 작업에서 대상을 식별하기 쉽다. 이름을 자동 생성하게 둘 수 있어도 운영과 이행을 고려하면 일관된 명명 규칙이 도움이 된다.

06

테이블 생성·변경·삭제 절차

테이블 생성 전에는 요구사항에서 개체, 속성, 식별자, 관계, 값 범위를 도출한다. 논리 모델을 검토한 뒤 DBMS 자료형과 제약으로 구현하고 샘플과 경계값으로 검증한다.

  1. 테이블이 표현할 한 가지 중심 사실을 정한다.
  2. 각 열의 의미와 원자성을 확인한다.
  3. 기본키와 업무상 후보키를 정한다.
  4. 필수값, 범위, 참조 규칙을 제약으로 선언한다.
  5. 예상 조회·변경 패턴과 데이터 규모를 검토한다.
  6. 정상, 경계, 오류 데이터를 넣어 제약 동작을 시험한다.
  7. 객체와 열의 의미를 문서화한다.

ALTER로 열을 추가할 때 기존 행에 적용할 기본값과 NULL 허용을 확인한다. NOT NULL 열을 기본값 없이 추가하면 기존 행을 채울 수 없어 실패할 수 있다. 자료형을 줄이거나 바꿀 때는 변환 불가 값과 잘림을 검사한다. 열 삭제 전에는 코드, 보고서, 뷰, 제약, 인덱스 등 의존 대상을 찾아야 한다.

DROP은 객체와 데이터를 제거하므로 백업·보존 정책과 의존성을 확인한다. 이름이 비슷한 개발·운영 스키마를 혼동하지 않도록 완전한 대상과 현재 연결 환경을 검증한다. 실제 운영에서는 승인, 점검, 복구 계획 같은 변경 관리 절차가 필요하다.

07

임시 테이블과 파생 저장 구조

작업 중간 결과를 저장하는 임시 테이블 기능을 제공하는 DBMS가 있다. 임시 테이블은 세션이나 트랜잭션 범위에서만 보이도록 설계될 수 있고, 종료 시 데이터 또는 객체가 정리될 수 있다. 정확한 가시성과 수명은 제품 규칙을 따른다.

임시 테이블은 복잡한 단계를 나누거나 반복 사용하는 중간 결과에 유용하지만, 무조건 성능을 높이는 것은 아니다. 생성·입력·인덱싱 비용이 있고 동시 세션과 저장 공간을 사용한다. 한 질의로 명확하게 표현 가능한 작업을 필요 없이 여러 임시 단계로 나누면 일관성 관리가 어려워질 수 있다.

파티션 테이블처럼 큰 데이터를 특정 기준으로 나누어 관리하는 기능도 있다. 논리적으로 하나의 테이블처럼 사용하면서 물리 관리 단위를 나눌 수 있지만, 분할 키·가지치기·유지보수 방식은 제품별이다. 이 레슨에서는 그러한 객체도 데이터 사전에 정의 정보가 기록된다는 연결만 이해한다.

08

데이터 사전의 개념

데이터 사전(data dictionary)은 데이터베이스가 관리하는 데이터에 관한 데이터, 즉 메타데이터의 집합이다. 사용자가 만든 테이블의 실제 업무 행을 보관하는 곳이 아니라 그 테이블의 이름, 소유자, 열, 자료형, 제약조건, 권한, 생성 상태 같은 정의 정보를 제공한다.

데이터 사전이 관리하거나 보여 줄 수 있는 정보는 다음과 같다.

  • 스키마와 객체의 이름·종류·소유자·생성 및 변경 상태
  • 테이블과 열의 이름, 순서, 자료형, 길이, NULL 허용, 기본값
  • 기본키·유일키·외래키·검사 제약과 연결 열
  • 뷰 정의와 객체 간 의존 관계
  • 인덱스의 대상 테이블과 구성 열
  • 사용자·역할과 객체 권한
  • 저장 구조, 통계 정보, 파티션 등 제품이 제공하는 관리 메타데이터

DBMS 자체가 일관성을 유지해야 하므로 사용자가 일반 테이블처럼 시스템 내부 기초 사전 행을 임의로 변경하지 못하게 하는 것이 보통이다. 제공된 DDL과 관리 명령을 실행하면 DBMS가 데이터 사전을 갱신한다.

09

시스템 카탈로그와 정보 스키마

데이터 사전, 시스템 카탈로그, 메타데이터 뷰는 문맥에 따라 비슷한 뜻으로 쓰인다. 내부의 기초 시스템 테이블을 직접 노출하기보다 사용자가 조회할 수 있는 카탈로그 뷰나 표준화된 정보 스키마를 제공하는 DBMS가 많다.

실제 이름은 다르지만 메타데이터 조회 질문은 다음 형태로 바꿀 수 있다.

  • 현재 사용자가 볼 수 있는 테이블 목록은 무엇인가?
  • 특정 테이블의 열 이름과 자료형은 무엇인가?
  • 이 외래키가 어느 부모 키를 참조하는가?
  • 특정 사용자에게 어떤 객체 권한이 있는가?
  • 한 열을 삭제하면 영향을 받을 객체는 무엇인가?

조회 결과는 현재 사용자의 권한에 따라 달라질 수 있다. 객체가 존재해도 메타데이터를 볼 권한이 없으면 목록에 나타나지 않을 수 있다. “사전에 없으므로 객체가 물리적으로 없다”고 곧바로 단정하기 전에 연결한 데이터베이스, 스키마, 이름 대소문자 규칙, 권한을 확인한다.

10

데이터 사전 활용 절차

스키마 변경 전 열 하나를 조사한다고 하자.

  1. 현재 연결 환경과 대상 스키마를 확인한다.
  2. 객체 목록에서 정확한 테이블 소유자와 종류를 찾는다.
  3. 열 메타데이터에서 자료형, 길이, NULL, 기본값을 확인한다.
  4. 제약 메타데이터에서 키·검사·참조 관계를 찾는다.
  5. 의존성 정보에서 뷰와 프로그램 객체의 참조를 확인한다.
  6. 권한 정보에서 변경 주체와 이용자 영향을 확인한다.
  7. 통계나 사용량 정보가 필요하면 그 정보의 수집 시점과 신뢰도를 확인한다.
  8. 변경 후 다시 조회하여 예상 정의와 일치하는지 검증한다.

데이터 사전 조회 결과는 자동 문서화, 스키마 비교, 배포 검증, 영향 분석, 보안 감사에 활용할 수 있다. 다만 열 이름만으로 업무 의미를 완전히 알 수 없으므로 주석, 논리 모델, 데이터 표준 문서와 함께 본다.

11

데이터 사전과 데이터 디렉터리 구분

시험에서 용어를 혼동하기 쉬운 부분이다. 데이터 사전은 메타데이터를 관리하는 논리적 저장소다. 데이터 디렉터리라는 표현은 시스템에 따라 파일 위치나 데이터 파일 목록 같은 다른 의미로 쓰일 수 있다. 지문이 “데이터에 관한 데이터”, “객체 정의와 제약”, “시스템이 유지”라고 설명하면 데이터 사전 또는 시스템 카탈로그를 가리킨다.

또한 통계 정보는 메타데이터의 일부로 사전에 보일 수 있지만 언제나 실시간 정확한 행 수를 뜻하지 않는다. 최적화 통계는 수집 시점의 추정이나 표본에 기반할 수 있다. 카탈로그의 행 수 열과 SELECT COUNT(*)의 실제 결과가 반드시 같다고 가정하지 않는다.

12

보안과 데이터 사전

메타데이터에는 민감한 구조 정보가 들어 있다. 사용자 목록, 권한, 테이블명, 열 이름은 공격자에게 시스템 구조를 알려 줄 수 있으므로 최소 권한으로 접근을 제한한다. 반대로 관리자는 사전을 이용해 과도한 권한, 소유자 불명 객체, 유효하지 않은 의존성, 표준에 맞지 않는 자료형을 점검한다.

권한 감사에서는 직접 부여 권한과 역할을 통한 권한을 구분하고, 중첩된 역할이나 공개 범위 권한이 있는지 본다. 단순히 한 권한 행이 없다고 실제 유효 권한이 없다고 결론 내리면 안 된다. 제품의 권한 계산 규칙을 따른다.

13

적용 예시: 열 변경 영향 분석

상품코드 열을 10자리에서 20자리로 늘린다고 하자. 데이터 사전에서 상품 테이블의 열 정의만 확인하는 것으로 끝나지 않는다. 상품코드를 기본키로 쓰는지, 주문항목 등 다른 테이블이 외래키로 참조하는지, 뷰와 프로그램이 고정 길이를 가정하는지, 관련 인덱스가 무엇인지 확인한다.

길이를 늘리는 변경은 줄이는 것보다 데이터 손실 위험이 작아 보이지만 참조 열의 자료형 불일치, 응용 화면 길이, 외부 인터페이스 규격에 영향을 줄 수 있다. 변경 전후 메타데이터를 비교하고 참조 제약을 검증하며 실제 경계값을 시험한다.

14

시험 함정

  • 테이블은 행과 열로 된 논리 객체이며 물리 파일과 같은 개념이 아니다.
  • 숫자로 보이는 모든 값이 숫자형에 적합한 것은 아니다. 산술 의미와 선행 0 보존을 본다.
  • DEFAULT와 NULL은 같은 뜻이 아니다.
  • 대리키가 있더라도 업무상 유일성 제약이 필요할 수 있다.
  • 복합 기본키는 구성 열 각각이 아니라 조합이 유일하다.
  • 외래키는 부모 키를 참조하며 자식 쪽에서 같은 값이 여러 번 나타날 수 있다.
  • ALTER 문법이 가능해도 기존 데이터가 새 제약을 위반하면 실패할 수 있다.
  • 데이터 사전은 업무 데이터가 아니라 객체 정의 등의 메타데이터를 관리한다.
  • 사용자는 일반적으로 시스템 사전의 기초 정보를 직접 DML로 고치지 않고 DDL을 통해 변경한다.
  • 메타데이터 목록은 권한과 현재 스키마에 따라 다르게 보일 수 있다.
  • 카탈로그의 통계 행 수를 항상 실시간 정확한 COUNT 결과로 보지 않는다.
  • 임시 테이블의 수명과 가시성은 모든 DBMS에서 같지 않다.
15

확인 문제

  1. 테이블의 행과 열은 각각 무엇을 표현하는가?
  2. 전화번호를 숫자형보다 문자열로 저장하는 것이 적합할 수 있는 이유를 쓰라.
  3. 대리키를 기본키로 정했어도 업무상 상품코드에 UNIQUE가 필요할 수 있는 이유는 무엇인가?
  4. 열을 NOT NULL로 변경하기 전에 확인할 사항을 두 가지 쓰라.
  5. 데이터 사전이 제공하는 메타데이터를 네 종류 이상 쓰라.
  6. 객체가 메타데이터 목록에 보이지 않을 때 존재하지 않는다고 즉시 단정하면 안 되는 이유는 무엇인가?
  7. 데이터 사전을 이용한 열 삭제 영향 분석 절차를 설명하라.
  8. 카탈로그 통계의 행 수와 실제 COUNT 결과가 다를 수 있는 이유는 무엇인가?
16

정답과 해설

  1. 행은 한 건의 사실이나 개체 발생을, 열은 모든 행에 공통인 속성과 값의 의미를 표현한다.
  2. 전화번호는 산술 대상이 아니고 선행 0, 구분 기호, 국가 코드처럼 표시 의미가 있기 때문이다. 숫자형 변환은 선행 0을 잃을 수 있다.
  3. 대리키는 기술적으로 행을 식별하지만 서로 다른 대리키를 가진 동일 상품코드 입력을 막지 못한다. 업무상 중복 금지는 별도의 유일 제약으로 선언해야 한다.
  4. 기존 행에 NULL이 있는지, 이후 모든 입력 경로가 값을 제공하는지 확인한다. 기본값과 응용 프로그램 영향도 함께 본다.
  5. 객체 이름·종류·소유자, 열 자료형과 NULL 여부, 키와 검사 제약, 외래키 참조, 인덱스, 뷰 의존성, 사용자·역할 권한 등이 있다.
  6. 현재 사용자의 조회 권한, 연결한 데이터베이스와 스키마, 이름 규칙 때문에 보이지 않을 수 있기 때문이다.
  7. 대상 열 정의를 찾고 키·제약·인덱스와 외래키를 확인한 뒤, 뷰와 프로그램 객체의 의존성 및 권한 사용자를 조사하고 변경 후 메타데이터를 재검증한다.
  8. 최적화 통계가 과거 수집 시점이나 표본·추정에 기반할 수 있고 그 뒤 데이터가 변경될 수 있기 때문이다.
17

최종 요약

  • 테이블은 같은 구조의 행을 저장하며 열의 자료형·NULL·기본값·제약조건이 업무 의미를 구체화한다.
  • 안정적인 키, 업무상 유일성, 도메인·개체·참조 규칙을 선언적으로 설계해야 한다.
  • 구조 변경에서는 기존 데이터, 의존 객체, 잠금과 복구를 함께 검토한다.
  • 데이터 사전은 객체·열·제약·인덱스·권한·의존성 같은 메타데이터를 DBMS가 관리하는 저장소다.
  • 데이터 사전은 스키마 조사, 변경 영향 분석, 배포 검증, 문서화, 권한 감사에 활용된다.
  • 사전 조회 결과는 현재 환경과 권한, 통계 수집 시점의 영향을 받으므로 업무 문서 및 실제 검증과 함께 해석한다.
