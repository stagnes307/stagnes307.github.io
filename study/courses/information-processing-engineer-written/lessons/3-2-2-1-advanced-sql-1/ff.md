# 3-2-2-1. 뷰 · 인덱스 · 집합 연산자

## 학습 목표와 범위

이 레슨은 질의를 이름 있는 가상 구조로 제공하는 **뷰**, 데이터 탐색 경로를 만들어 조회를 돕는 **인덱스**, 여러 질의 결과를 행 방향으로 결합하는 **집합 연산자**를 다룬다. 학습 후에는 뷰의 논리적 독립성과 보안 효과, 인덱스의 탐색 이점과 변경 비용, UNION·UNION ALL·INTERSECT·차집합 연산의 중복 처리와 합집합 호환 조건을 설명할 수 있어야 한다.

뒤 레슨의 조인과 서브쿼리는 필요한 비교만 한다. 뷰 갱신 가능성, 인덱스 종류와 사용 여부, 차집합 연산자의 실제 키워드는 DBMS마다 차이가 있으므로 시험 지문의 제품 조건을 우선한다.

## 뷰의 개념

뷰(View)는 하나 이상의 테이블이나 다른 뷰를 대상으로 작성한 SELECT 질의에 이름을 부여한 데이터베이스 객체다. 일반 뷰는 질의 결과를 별도 행 집합으로 항상 저장하기보다 정의된 질의를 통해 논리적인 테이블처럼 보여 준다. 사용자는 허용된 범위에서 뷰를 SELECT의 FROM 대상으로 사용할 수 있다.

    CREATE VIEW 재직사원_공개
        (사원번호, 사원명, 부서코드)
    AS
    SELECT 사원번호, 사원명, 부서코드
      FROM 사원
     WHERE 재직여부 = 'Y';

이 뷰는 재직 행과 세 열만 노출한다. 급여나 개인 연락처 같은 민감 열을 숨기는 인터페이스가 될 수 있다. 그러나 뷰가 있다고 자동으로 보안이 완성되는 것은 아니다. 원본 테이블 권한, 뷰 소유권과 실행 권한, 우회 경로를 함께 통제해야 한다.

## 뷰의 장점과 한계

뷰의 대표 장점은 다음과 같다.

- 논리적 데이터 독립성: 원본 구조 일부가 바뀌어도 뷰 인터페이스를 유지하면 이용자 변경을 줄일 수 있다.
- 보안: 필요한 행과 열만 보여 주고 원본 테이블 직접 접근을 제한할 수 있다.
- 단순화: 복잡한 조인·계산·필터를 이름 있는 재사용 질의로 감춘다.
- 일관성: 여러 보고서가 같은 업무 조건과 계산식을 공유한다.
- 사용자별 관점: 같은 데이터를 직무와 목적에 맞는 형태로 제공한다.

한계도 있다. 뷰를 겹겹이 중첩하면 실제 실행 질의를 이해하기 어렵고 성능 문제 원인을 추적하기 힘들다. 원본 열 이름이나 자료형 변경은 뷰를 무효화하거나 결과 의미를 바꿀 수 있다. 모든 뷰가 갱신 가능한 것도 아니다.

일반적으로 하나의 기본 테이블에서 행과 열을 단순 선택한 뷰는 갱신 가능성이 높다. 집계, GROUP BY, DISTINCT, 집합 연산, 계산으로만 만든 열, 여러 테이블 결합 등이 포함되면 원본의 어느 행을 어떻게 변경해야 하는지 모호해져 제한될 수 있다. 구체적인 갱신 규칙은 DBMS에 따라 다르다.

## CHECK OPTION과 구체화된 뷰

필터 조건이 있는 갱신 가능 뷰에서 WITH CHECK OPTION과 같은 기능은 뷰를 통해 삽입·변경한 행이 계속 뷰 조건을 만족하도록 제한한다. 예를 들어 D10 부서만 보이는 뷰에서 부서코드를 D20으로 바꾸면 변경 후 행이 뷰에서 사라진다. CHECK OPTION은 이런 변경을 막아 뷰의 행 범위를 유지한다.

일반 뷰와 달리 결과를 물리적으로 저장하고 필요 시 새로 고치는 구체화된 뷰 기능을 제공하는 DBMS도 있다. 복잡한 집계 조회를 빠르게 할 수 있지만 저장 공간이 들고 원본 변경과 결과 사이에 시차가 생길 수 있다. 갱신 시점과 일관성 수준은 구현·설정에 따라 다르다. 시험에서 단순히 “뷰”라고 하면 결과를 항상 물리 저장한다고 가정하지 않는다.

## 인덱스의 개념

인덱스(Index)는 테이블의 특정 열 값과 행 위치를 연결하는 보조 탐색 구조다. 책의 찾아보기처럼 모든 행을 처음부터 확인하지 않고 조건에 맞는 위치를 빠르게 찾는 데 도움을 준다. 인덱스는 원본 테이블과 별도 저장 공간을 사용하며 INSERT·UPDATE·DELETE 때 함께 유지되어야 한다.

인덱스가 유리할 가능성이 큰 상황은 선택도가 높은 동등 조건, 범위 검색, 조인 키 탐색, 정렬 순서 활용 등이다. 반대로 테이블 대부분을 읽어야 하거나 테이블이 매우 작고, 조건식이 인덱스 열을 효과적으로 사용할 수 없거나, 유지 비용이 이점보다 크면 전체 읽기가 더 나을 수 있다. 인덱스가 존재한다고 최적화기가 반드시 선택하는 것은 아니다.

선택도는 조건으로 선택되는 비율과 관련된다. 전체에서 매우 적은 행만 찾는 값은 일반적으로 인덱스 이점이 크다. 성별처럼 값 종류가 적은 열도 다른 열과 결합하거나 특정 값의 분포가 치우쳐 있으면 유용할 수 있으므로 단일 기준으로 단정하지 않는다. 통계와 실제 질의 패턴이 중요하다.

## 대표 인덱스 구조와 특성

B-트리 계열 인덱스는 키를 정렬된 트리 구조로 관리해 동등 검색과 범위 검색에 널리 쓰인다. 루트에서 중간 노드를 거쳐 리프의 키 범위를 찾으며, 균형을 유지해 탐색 깊이가 급격히 치우치지 않도록 한다.

해시 계열 인덱스는 해시 함수로 버킷을 찾아 동등 비교에 적합할 수 있지만 일반적인 범위 검색이나 정렬 순서 활용에는 제한이 있다. 비트맵 계열 구조는 값 종류가 적고 읽기 중심인 분석 환경에서 장점이 있을 수 있으나 동시 변경이 많은 환경에서는 특성을 검토해야 한다. 실제 지원 여부와 동작은 제품마다 다르다.

클러스터드와 비클러스터드라는 분류는 인덱스 키 순서와 실제 행 저장의 관계를 설명할 때 사용되지만 DBMS별 구현과 용어가 다르다. 일반적으로 한 테이블의 행 물리 배열을 여러 독립 순서로 동시에 유지하기는 어렵다는 원리를 이해한다. “기본키는 언제나 특정 유형 인덱스가 된다”는 제품 조건 없는 단정은 피한다.

## 복합 인덱스와 열 순서

복합 인덱스가 (부서코드, 입사일) 순서라면 부서코드만 또는 부서코드와 입사일을 함께 제한하는 조건에서 탐색 경로가 되기 쉽다. 입사일만 조건으로 사용할 때 같은 방식으로 효율적인지는 인덱스 구조와 최적화 기능에 따라 달라진다. 선두 열 원칙은 대표적인 설계 기준이다.

열 순서는 다음을 함께 고려한다.

1. 실제 WHERE와 JOIN에서 자주 함께 쓰는가?
2. 동등 조건과 범위 조건의 배치는 어떤가?
3. ORDER BY나 GROUP BY 순서를 활용할 수 있는가?
4. 값 분포와 NULL, 데이터 규모는 어떠한가?
5. 조회 이득과 변경 유지 비용이 균형을 이루는가?

함수나 계산을 인덱스 열에 적용하면 일반 인덱스와 조건식이 직접 대응하지 않아 사용이 어려울 수 있다. DBMS가 표현식 인덱스나 함수 기반 인덱스를 지원하기도 하지만, 조건식을 고치는 것과 별도 인덱스를 추가하는 것 중 무엇이 적절한지 검토한다.

## 인덱스의 비용과 관리

인덱스가 많으면 읽기 경로 선택지는 늘지만 데이터 변경 때 모든 관련 인덱스를 갱신해야 한다. 저장 공간, 캐시, 통계 수집, 재구성 비용도 든다. 중복되거나 거의 사용되지 않는 인덱스는 오히려 부담이다.

인덱스 설계 절차는 질의 패턴 수집, 실행 계획과 처리 행 수 확인, 후보 열·순서 선정, 생성 전후 측정, 변경 부하 확인, 지속 모니터링 순으로 진행한다. 느린 질의가 보인다고 무조건 인덱스를 하나 추가하는 방식은 중복 인덱스를 만든다.

유일 인덱스는 중복 키를 막는 기능을 제공할 수 있지만 업무 무결성을 표현할 때는 PRIMARY KEY나 UNIQUE 제약의 의미를 우선한다. DBMS가 제약 구현을 위해 인덱스를 사용할 수 있어도 “제약”이라는 논리 규칙과 “인덱스”라는 접근 구조는 개념적으로 구분한다.

## 집합 연산자의 전제

**집합 연산자**는 둘 이상의 SELECT 결과를 위아래로 결합한다. 조인이 열 방향으로 관련 행을 붙이는 것과 대조된다. 집합 연산을 하려면 양쪽 결과가 합집합 호환 조건을 만족해야 한다.

- 대응하는 열의 개수가 같아야 한다.
- 같은 위치 열의 자료형이 같거나 서로 호환 가능해야 한다.
- 결과 열 이름은 일반적으로 첫 번째 질의의 이름이나 별칭을 기준으로 정해진다.
- 각 열의 의미와 단위도 논리적으로 같아야 한다.

문법상 숫자 열끼리 호환되어도 한쪽이 금액이고 다른 쪽이 수량이면 결합 결과는 의미가 없다. 구조적 호환성과 의미적 호환성을 함께 본다.

## UNION과 UNION ALL

UNION은 양쪽 결과를 합치고 중복 행을 제거한다. UNION ALL은 중복을 유지한다.

    SELECT 고객번호 FROM 온라인주문
    UNION
    SELECT 고객번호 FROM 매장주문;

이 결과는 두 채널 중 하나 이상에서 주문한 서로 다른 고객번호 목록이다.

    SELECT 고객번호, 주문금액 FROM 온라인주문
    UNION ALL
    SELECT 고객번호, 주문금액 FROM 매장주문;

두 채널의 모든 주문 행을 보존한다. 같은 고객번호와 주문금액 조합이 양쪽에 있어도 둘 다 남는다. 중복 제거가 필요 없다면 UNION ALL이 중복 판단 작업을 피할 수 있고 각 발생 행을 보존한다. UNION의 중복 판단은 선택한 전체 열 조합을 기준으로 한다.

## INTERSECT와 차집합

INTERSECT는 양쪽 결과에 공통으로 존재하는 행을 반환하고 중복을 제거하는 집합 교집합에 해당한다. 차집합 연산자는 첫 번째 결과에는 있고 두 번째 결과에는 없는 행을 반환한다. 표준 계열 키워드와 일부 제품의 대체 키워드가 다를 수 있으므로 의미를 중심으로 이해한다.

연산 방향은 차집합에서 중요하다. A 차집합 B와 B 차집합 A는 일반적으로 다르다. “온라인 구매 고객 중 매장 구매 이력이 없는 고객”은 온라인 목록이 왼쪽이어야 한다.

ALL 변형을 지원하는 범위와 중복 개수 처리 방식은 제품마다 다를 수 있다. 기본 집합 연산은 수학적 집합처럼 중복을 제거한다는 점을 먼저 기억한다.

## 연산 순서와 ORDER BY

여러 집합 연산자를 섞으면 연산자 우선순위가 표준이나 DBMS에서 다르게 해석될 여지를 줄이기 위해 괄호나 파생 질의로 의도를 명확히 한다. 단순히 왼쪽에서 오른쪽으로만 계산한다고 가정하지 않는다.

ORDER BY는 보통 결합된 최종 결과 전체에 한 번 적용한다. 각 SELECT 내부의 정렬이 최종 결합 순서를 보장하지 않는다. 최종 출력 열 이름이나 위치를 사용하되 제품 문법을 확인한다. 관계형 결과는 ORDER BY가 없으면 표시 순서를 보장하지 않는다.

NULL을 포함한 행의 중복 판정은 일반 WHERE의 “NULL = NULL” 비교와 동일하게만 생각하면 혼동할 수 있다. DISTINCT나 집합 연산의 중복 제거는 같은 위치의 NULL들을 중복 판정에서 같은 것으로 취급하는 동작이 일반적이다.

## 통합 적용 예시

직원에게 공개할 고객 요약 뷰를 만들되 개인정보 열은 제외한다. 자주 사용하는 고객번호와 상태 조건을 조사해 적절한 인덱스 후보를 검토한다. 온라인과 오프라인 활동을 모두 보여 줄 때는 두 결과의 열을 채널, 고객번호, 활동일, 활동종류 순으로 맞춰 UNION ALL로 결합한다.

채널을 나타내는 상수 열을 추가하면 같은 고객과 날짜가 있어도 발생 출처를 구분할 수 있다. 서로 다른 사건을 보존해야 하므로 UNION보다 UNION ALL이 자연스럽다. 반대로 두 채널에서 한 번이라도 활동한 고유 고객 목록만 원하면 고객번호 하나를 선택해 UNION을 사용한다.

뷰 뒤에 인덱스가 있다고 표현할 때 실제로는 원본 테이블의 인덱스를 이용하는 일반 뷰인지, 결과를 저장하는 별도 기능인지 구분한다. 이름만으로 성능이 보장되는 것은 아니므로 실행 계획과 측정으로 확인한다.

## 시험 함정

- 일반 뷰는 질의 정의를 저장하는 논리 객체이며 결과 행을 항상 별도 저장한다고 단정하지 않는다.
- 모든 뷰가 갱신 가능한 것은 아니다. 집계·DISTINCT·집합 연산 등이 있으면 제한될 가능성이 크다.
- 뷰가 민감 열을 숨겨도 원본 테이블 직접 권한이 남아 있으면 보안 목적이 무너질 수 있다.
- 인덱스가 많을수록 언제나 빠른 것은 아니다. 변경·저장·관리 비용이 늘어난다.
- 인덱스가 존재해도 조건 선택도와 비용에 따라 전체 읽기가 선택될 수 있다.
- 복합 인덱스의 열 순서는 중요하며 임의의 구성 열 조건에 똑같이 유리하지 않다.
- UNIQUE 제약과 유일 인덱스는 관련되지만 논리적 무결성과 물리적 접근 구조라는 관점이 다르다.
- UNION은 중복 제거, UNION ALL은 중복 유지다.
- 집합 연산의 대응 열은 개수·자료형뿐 아니라 의미도 맞아야 한다.
- UNION의 중복은 첫 열만이 아니라 전체 결과 열 조합을 기준으로 판단한다.
- 차집합은 좌우 방향을 바꾸면 결과가 달라진다.
- 각 부분 질의의 정렬이 최종 결과 순서를 보장하지 않는다.

## 확인 문제

1. 일반 뷰의 정의와 대표 장점 세 가지를 쓰라.
2. 단순 뷰보다 집계 뷰의 갱신이 어려운 이유는 무엇인가?
3. 인덱스가 조회에는 도움을 주지만 변경에는 비용이 되는 이유를 설명하라.
4. (부서코드, 입사일) 복합 인덱스에서 열 순서가 중요한 이유는 무엇인가?
5. UNION과 UNION ALL의 중복 처리 차이를 쓰라.
6. 집합 연산의 합집합 호환 조건을 설명하라.
7. INTERSECT와 차집합의 의미를 비교하고 차집합에서 순서가 중요한 이유를 쓰라.
8. 집합 연산 뒤 결과 순서를 보장하려면 어떻게 해야 하는가?

## 정답과 해설

1. 뷰는 SELECT 질의에 이름을 부여해 논리적 테이블처럼 제공하는 객체다. 행·열 보안, 복잡한 질의 단순화, 논리적 독립성, 규칙 재사용 등의 장점이 있다.
2. 한 뷰 행이 여러 원본 행의 집계 결과이면 변경값을 어느 원본 행에 어떻게 나누어 반영할지 유일하게 결정하기 어렵기 때문이다.
3. 조회 시 키를 통해 대상 위치를 좁힐 수 있지만, 행을 추가·삭제하거나 인덱스 열을 바꿀 때 별도 인덱스 구조도 갱신해야 하기 때문이다.
4. 정렬된 탐색 구조에서 선두 열이 탐색 범위를 먼저 나누기 때문이다. 입사일만 조건인 경우 부서코드별 범위를 넓게 살펴야 할 수 있다. 실제 사용은 최적화기와 DBMS 기능을 따른다.
5. UNION은 결합 후 같은 전체 행을 하나로 줄이고 UNION ALL은 모든 발생 행을 유지한다.
6. 양쪽 SELECT의 열 개수가 같고 같은 위치 자료형이 호환되어야 하며, 업무 의미와 단위도 대응해야 한다.
7. INTERSECT는 양쪽 공통 행, 차집합은 왼쪽에만 있는 행이다. A에만 있는 행과 B에만 있는 행이 다르므로 좌우 순서가 중요하다.
8. 결합된 전체 결과에 최종 ORDER BY를 적용한다. 부분 질의의 내부 순서만으로는 최종 표시 순서를 보장하지 않는다.

## 최종 요약

- **뷰**는 질의를 논리적 테이블로 제공해 보안, 단순화, 독립성, 일관된 관점을 지원한다.
- 뷰의 갱신 가능성과 결과 저장 여부는 정의 및 DBMS 기능에 따라 다르다.
- **인덱스**는 탐색을 돕는 별도 구조이며 선택도·질의 패턴·복합 열 순서와 변경 비용을 함께 평가해야 한다.
- 인덱스와 키 제약은 관련될 수 있지만 접근 성능 구조와 데이터 무결성 규칙으로 구분한다.
- **집합 연산자**는 행 방향으로 결과를 결합하며 UNION, UNION ALL, INTERSECT, 차집합의 중복·방향 차이를 이해해야 한다.
- 대응 열의 개수·자료형·의미를 맞추고 최종 ORDER BY로 표시 순서를 명시한다.
