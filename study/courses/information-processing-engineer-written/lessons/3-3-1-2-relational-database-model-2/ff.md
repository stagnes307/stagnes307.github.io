# 3-3-1-2. 시스템카탈로그와 뷰

> **출제 범위 기준**: 이 레슨은 정보처리기사 필기 `데이터베이스구축 > 논리 데이터베이스 설계 > 관계데이터베이스 모델 > 3. 시스템카탈로그와 뷰`를 다룬다. 정확한 토픽은 **시스템카탈로그와 뷰**, **관계데이터베이스 모델의 적용 절차와 판단 기준**이다. 제품마다 카탈로그 테이블명과 뷰 갱신 규칙이 다르므로 공통 개념, 판단 순서, SQL 의미를 중심으로 학습한다.

관계 데이터베이스에는 업무 데이터만 있는 것이 아니다. 어떤 테이블과 열이 존재하는지, 자료형·제약조건·권한·뷰 정의가 무엇인지 설명하는 메타데이터도 필요하다. DBMS는 이 정보를 시스템카탈로그로 관리한다. 뷰는 하나 이상의 기본 테이블에서 필요한 논리적 모습을 정의해 사용자에게 제공한다. 둘을 함께 이해하면 실제 스키마를 검증하고, 사용자별 데이터 표현과 권한 경계를 설계할 수 있다.

---

## 1. 시스템카탈로그의 개념

### 1.1 데이터에 관한 데이터

**시스템카탈로그(system catalog)**는 데이터베이스 객체와 운영 상태를 설명하는 메타데이터의 집합이다. 데이터 사전(data dictionary)이라는 표현과 겹쳐 쓰이는 경우가 많다. 엄밀한 이름과 공개 범위는 제품마다 다르지만 다음 정보가 대표적이다.

- 스키마, 테이블, 뷰, 열의 이름과 소유자
- 열의 자료형, 길이, 기본값, NULL 허용 여부
- 기본키, 외래키, 고유·검사 제약조건
- 인덱스와 구성 열
- 사용자, 역할, 객체 권한
- 프로시저·함수·트리거 같은 객체 정의
- 통계 정보와 저장 구조에 대한 일부 메타데이터

업무 테이블의 주문 금액이 **데이터**라면, 그 열의 이름이 `order_amount`이고 숫자형이며 NULL을 허용하지 않는다는 설명은 **메타데이터**다.

### 1.2 DBMS가 유지한다

카탈로그의 핵심 특성은 DBMS가 데이터 정의문과 권한 변경에 맞추어 일관되게 유지한다는 것이다. 사용자가 테이블을 생성하면 관련 메타데이터가 반영되고, 열을 삭제하면 해당 정의도 바뀐다. 일반 사용자가 내부 카탈로그 행을 임의로 직접 수정하는 방식은 무결성을 깨뜨릴 수 있으므로, 객체 변경은 DDL이나 DBMS가 제공하는 관리 인터페이스로 수행한다.

카탈로그를 조회하는 것은 가능하지만 모든 사용자가 모든 메타데이터를 볼 수 있는 것은 아니다. 자신에게 권한이 있는 객체만 보이거나, 민감한 정의가 마스킹될 수 있다. “시스템카탈로그는 누구나 수정할 수 있는 일반 업무 테이블”이라는 설명은 틀리다.

### 1.3 시스템카탈로그와 사용자 데이터 구분

| 구분 | 시스템카탈로그 | 사용자 업무 테이블 |
|---|---|---|
| 저장 내용 | 객체 정의·권한·제약·통계 등 메타데이터 | 주문·회원·상품 등 업무 데이터 |
| 주된 관리 주체 | DBMS | 승인된 응용 프로그램과 사용자 |
| 변경 방식 | DDL·권한 명령·관리 기능에 따라 DBMS가 반영 | DML과 업무 절차로 변경 |
| 대표 용도 | 스키마 탐색, 영향 분석, 관리·최적화 지원 | 업무 처리와 분석 |
| 접근 범위 | 권한과 제품 정책에 따라 제한 | 업무 권한에 따라 제한 |

카탈로그도 관계형 표나 뷰의 형태로 조회되는 경우가 많지만, 이것이 내부 구현까지 항상 일반 테이블과 동일하다는 뜻은 아니다.

### 1.4 표준 정보 스키마와 제품별 카탈로그

여러 관계형 DBMS는 표준화된 정보 스키마 계열 뷰 또는 제품 고유의 시스템 뷰를 제공한다. 표준 인터페이스는 이식성에 도움이 되지만 모든 제품 기능을 표현하지 못할 수 있다. 제품 고유 뷰는 세부 정보를 제공하는 대신 종속성이 커진다.

다음은 개념적인 조회 예다. 실제 열 이름과 지원 범위는 사용하는 DBMS 문서를 확인한다.

```sql
SELECT table_schema, table_name, column_name, data_type
  FROM information_schema.columns
 WHERE table_schema = :target_schema
 ORDER BY table_name, ordinal_position;
```

이 조회는 업무 데이터를 바꾸는 것이 아니라 현재 스키마 정의를 관찰한다. 문자열 연결로 스키마 이름을 넣기보다 지원되는 경우 바인딩이나 안전한 관리 API를 사용한다.

## 2. 시스템카탈로그의 활용

### 2.1 스키마 검증과 문서화

배포 전에 기대 스키마와 실제 카탈로그를 비교하면 누락된 열, 다른 자료형, 제약조건 차이를 찾을 수 있다. 문서를 사람이 수동으로 갱신하는 데만 의존하지 않고, 카탈로그에서 객체 목록을 추출해 기준 정의와 대조한다.

검증 순서는 다음과 같다.

1. 대상 환경과 스키마를 확정한다.
2. 필요한 테이블·열·제약조건의 기대 목록을 준비한다.
3. 권한 있는 계정으로 카탈로그를 조회한다.
4. 이름, 자료형, NULL, 기본값, 키와 참조 관계를 비교한다.
5. 차이를 승인된 변경인지 배포 누락인지 분류한다.
6. 변경 스크립트와 검증 결과를 버전·환경과 함께 기록한다.

객체 이름만 있다고 배포가 맞는 것은 아니다. 같은 열이라도 길이, 정밀도, NULL 허용, 기본값이 다르면 응용 동작이 달라질 수 있다.

### 2.2 영향 분석

열이나 테이블을 변경하기 전에 그것을 참조하는 뷰, 제약조건, 인덱스, 프로시저 등을 찾아야 한다. 카탈로그 의존성 정보는 영향 분석의 출발점이다. 다만 응용 프로그램 문자열 안의 동적 SQL처럼 DBMS가 의존성을 완전히 알 수 없는 참조도 있다. 카탈로그 결과만으로 영향이 0이라고 단정하지 말고 소스 검색, 실행 추적, 테스트 결과를 결합한다.

### 2.3 권한 감사와 운영 진단

- 어떤 역할이 어떤 테이블·뷰에 권한을 가졌는지 확인한다.
- 사용하지 않는 과도한 권한을 찾는다.
- 객체 생성자와 변경 상태를 조사한다.
- 통계·인덱스 메타데이터를 성능 분석의 보조 자료로 쓴다.

카탈로그 조회 결과에는 객체명, 사용자명, 정의문처럼 민감할 수 있는 정보가 포함된다. 관리 화면이나 로그에 무제한 노출하지 않고 최소 권한과 감사 정책을 적용한다.

## 3. 뷰의 개념과 동작

### 3.1 논리적 테이블

**뷰(view)**는 저장된 질의 정의에 이름을 붙여 테이블처럼 조회할 수 있게 한 논리적 객체다. 일반 뷰는 기본 테이블의 데이터를 별도로 복제해 보관하는 것이 아니라 조회 시 정의를 바탕으로 결과를 구성한다. 따라서 기본 테이블 데이터가 바뀌면 같은 조건에서 본 뷰 결과도 달라진다.

```sql
CREATE VIEW active_customer_summary AS
SELECT customer_id,
       customer_name,
       customer_grade
  FROM customer
 WHERE status = 'ACTIVE';
```

이 뷰는 필요한 열과 활성 고객만 공개하는 논리적 창이다. `CREATE VIEW` 문법과 갱신 가능 조건은 제품별 차이가 있으므로 시험에서는 정의와 목적을 먼저 본다.

### 3.2 뷰의 장점

1. **논리적 데이터 독립성 보조**: 기본 구조 변경의 일부를 뷰가 흡수하여 사용자 인터페이스를 유지할 수 있다.
2. **보안 경계**: 민감 열이나 허용되지 않은 행을 제외한 뷰에만 권한을 줄 수 있다.
3. **질의 단순화**: 복잡한 조인·계산·필터를 이름 있는 논리 객체로 재사용한다.
4. **사용자별 표현**: 같은 데이터를 부서·역할·업무 관점에 맞게 제공한다.
5. **일관된 정의**: 공통 계산과 필터의 기준을 중앙에서 관리한다.

뷰만 만들면 보안이 자동으로 완성되는 것은 아니다. 사용자가 기본 테이블을 직접 조회할 권한을 함께 갖고 있다면 뷰의 열·행 제한을 우회할 수 있다. 실행자/정의자 권한 정책과 간접 추론 가능성도 검토해야 한다.

### 3.3 뷰의 제약과 단점

- 복잡한 중첩 뷰는 실제 실행 SQL과 성능 문제를 파악하기 어렵게 한다.
- 기본 객체 변경이 뷰를 무효화하거나 결과 계약을 바꿀 수 있다.
- 모든 뷰가 삽입·수정·삭제 가능한 것은 아니다.
- 집계·그룹화·중복 제거·집합 연산·여러 테이블 조인 등이 있으면 한 변경을 기본 행에 모호하지 않게 대응하기 어렵다.
- 이름이 비슷한 뷰가 늘면 소유권과 정의 관리가 복잡해질 수 있다.

“뷰는 항상 물리 저장공간을 사용하지 않는다”도 주의해야 한다. 일반 뷰의 결과는 별도 저장하지 않는 것이 보통이지만, **물리화 뷰(materialized view)** 또는 이에 해당하는 제품 기능은 결과를 저장하고 갱신한다. 일반 뷰와 물리화 뷰를 구분한다.

## 4. 갱신 가능한 뷰 판단

뷰를 통한 DML이 가능한지는 DBMS 규칙과 뷰 정의에 따라 달라진다. 공통 판단은 “변경할 뷰 행을 하나의 기본 테이블 행으로 명확히 대응할 수 있는가?”이다.

### 4.1 갱신 가능성이 높은 형태

- 하나의 기본 테이블을 대상으로 한다.
- 행과 열을 단순 선택한다.
- 기본키 등 행 식별에 필요한 정보가 유지된다.
- 집계, 그룹화, 중복 제거, 집합 연산이 없다.
- 계산 열이 아닌 기본 열에 변경을 대응할 수 있다.

### 4.2 갱신이 제한되기 쉬운 형태

| 뷰 정의 요소 | 제한 이유 |
|---|---|
| `GROUP BY`, 집계 함수 | 하나의 결과 행이 여러 기본 행을 대표 |
| `DISTINCT` | 어떤 기본 중복 행을 변경할지 모호할 수 있음 |
| 여러 테이블 조인 | 변경 대상을 어느 테이블·행으로 보낼지 모호 |
| 집합 연산 | 결과 행의 원본 관계가 복잡 |
| 계산식 열 | 값을 어떤 기본 열 조합으로 역변환할지 불명확 |

실제 DBMS는 조인 뷰의 일부 열 갱신, 대신 실행되는 트리거 등 추가 기능을 지원할 수 있다. 따라서 위 표는 공통 원칙이며 제품 문서의 규칙을 확인한다.

### 4.3 CHECK OPTION

필터가 있는 갱신 가능 뷰에서 변경 후 행이 뷰 조건 밖으로 사라지는 상황이 생길 수 있다. 개념적으로 `WITH CHECK OPTION`은 뷰를 통해 삽입·수정한 행이 뷰의 조건을 계속 만족하도록 제한한다.

```sql
CREATE VIEW active_customer AS
SELECT customer_id, customer_name, status
  FROM customer
 WHERE status = 'ACTIVE'
WITH CHECK OPTION;
```

이 뷰를 통해 `status`를 비활성 값으로 바꾸려 하면 뷰 조건을 위반하므로 거부될 수 있다. 정확한 지원 문법과 중첩 뷰에서의 적용 범위는 제품별로 확인한다.

## 5. 관계데이터베이스 모델의 적용 절차와 판단 기준

**관계데이터베이스 모델의 적용 절차와 판단 기준**은 업무 개념을 무작정 테이블로 옮기는 것이 아니라, 관계·키·제약·사용자 표현을 검증 가능한 구조로 만드는 흐름이다. 이 레슨에서는 카탈로그와 뷰를 이용한 적용·확인 단계에 초점을 둔다.

### 5.1 1단계: 업무 사실과 사용 관점 분리

영속적으로 보존해야 할 핵심 사실과, 특정 사용자에게 보여 줄 표현을 구분한다. 회원의 식별자·상태·등급은 기본 관계의 속성이 될 수 있고, 상담원에게 보여 줄 “활성 회원 요약”은 뷰가 될 수 있다.

판단 질문은 다음과 같다.

- 이 값은 독립적으로 저장해야 하는 원천 사실인가?
- 다른 값에서 결정적으로 계산할 수 있는가?
- 어떤 키로 한 행을 식별하는가?
- 어떤 사용자가 어떤 열·행을 볼 수 있어야 하는가?
- 표현은 자주 바뀌지만 기본 데이터 계약은 안정적인가?

### 5.2 2단계: 관계·키·제약 정의

각 관계의 후보키와 기본키를 고르고, 참조 관계와 도메인 제약을 정의한다. 이름만 같은 열을 자동으로 외래키로 가정하지 않는다. 참조 대상의 유일성, NULL 허용, 삭제·수정 시 정책을 명확히 한다.

이 단계의 결과가 실제 DDL로 반영되었는지는 시스템카탈로그에서 확인할 수 있다. 설계 문서에는 외래키가 있는데 카탈로그에는 없다면 배포 누락인지, 응용 계층 검증으로 의도적으로 대체했는지 근거를 확인한다.

### 5.3 3단계: 사용자별 뷰 설계

뷰가 필요한 경우 다음을 정한다.

1. 공개할 기본 관계와 열
2. 허용할 행 필터
3. 조인·계산의 의미와 NULL 처리
4. 결과 열 이름과 자료형 계약
5. 읽기 전용인지 갱신을 허용할지
6. 뷰 권한과 기본 테이블 직접 권한
7. 성능과 의존성 관리 방법

뷰에 `SELECT *`를 사용하면 기본 테이블 열 추가가 예상치 못한 정보 노출이나 인터페이스 변경으로 이어질 수 있다. 공개 계약에서는 필요한 열을 명시하는 편이 안전하다.

### 5.4 4단계: 카탈로그로 구현 검증

설계와 실제 구현을 다음처럼 대조한다.

| 설계 항목 | 카탈로그에서 확인할 대상 |
|---|---|
| 관계와 속성 | 테이블·열·자료형·NULL·기본값 |
| 식별 규칙 | 기본키·고유 제약 |
| 참조 무결성 | 외래키와 참조 대상·동작 |
| 허용값 | 검사 제약과 도메인 표현 |
| 사용자 표현 | 뷰 이름·열·정의·의존 객체 |
| 접근 정책 | 사용자·역할·테이블/뷰 권한 |

카탈로그 조회 계정의 권한 때문에 일부 객체가 보이지 않을 수 있다. “조회 결과 없음”을 곧바로 “객체 없음”으로 결론 내리기 전에 현재 데이터베이스, 스키마, 대소문자 규칙과 조회 권한을 확인한다.

### 5.5 5단계: 질의·갱신·권한 검증

- 대표 조회가 정확한 행과 열을 반환하는지 시험한다.
- NULL, 빈 결과, 중복, 경계값을 포함한다.
- 갱신 가능 뷰는 허용·거부해야 할 DML을 각각 시험한다.
- 뷰 권한만 가진 사용자가 기본 테이블을 우회할 수 없는지 확인한다.
- 기본 객체 변경 시 의존 뷰와 응용 계약이 깨지지 않는지 회귀 검증한다.

### 5.6 선택 판단

| 상황 | 적합한 선택 | 이유 |
|---|---|---|
| 민감 열을 제외한 안정적 조회 계약 | 필요한 열을 명시한 뷰 | 노출 범위와 인터페이스를 고정 |
| 사용자마다 다른 행 범위 | 권한 정책과 결합한 제한 뷰 검토 | 역할별 논리 표현 제공 |
| 대규모 집계의 반복 조회 | 일반 뷰만 고집하지 말고 물리화·요약 구조 검토 | 일반 뷰는 결과를 매번 계산할 수 있음 |
| 단순 일회성 내부 조회 | 직접 SQL도 가능 | 불필요한 객체 증가 방지 |
| 실제 스키마 차이 점검 | 시스템카탈로그 조회 | 기억이나 문서가 아닌 DBMS의 현재 정의 확인 |

## 6. 오류 대응과 시험 함정

### 6.1 카탈로그 조회에서 자주 생기는 오류

- 잘못된 데이터베이스나 스키마에 연결했다.
- 객체 이름의 대소문자·인용 규칙을 혼동했다.
- 조회 계정 권한 때문에 객체가 보이지 않는다.
- 표준 정보 스키마에 제품 고유 속성이 없는데 “설정 없음”으로 판단했다.
- 설계 문서와 실제 카탈로그의 기준 버전·환경이 다르다.

### 6.2 뷰 문제에서 자주 생기는 함정

- 일반 뷰가 결과 데이터를 항상 별도 저장한다고 설명한다.
- 모든 뷰가 자유롭게 삽입·수정·삭제 가능하다고 설명한다.
- 뷰 권한을 주면 기본 테이블 권한과 무관하게 보안이 자동 완성된다고 본다.
- 기본 테이블 변경이 뷰에 영향을 주지 않는다고 본다.
- 집계 뷰의 한 행을 하나의 기본 행으로 착각한다.
- `CHECK OPTION`을 단순 조회 필터 기능으로만 이해한다.
- 시스템카탈로그를 사용자가 직접 DML로 유지하는 업무 테이블로 본다.

설계 문서에는 외래키가 있지만 카탈로그 조회 결과에는 없다. 즉시 “외래키가 존재하지 않는다”고 확정하기 전에 확인할 사항 세 가지를 적어라.

### 문제 5

일반 뷰와 물리화 뷰의 핵심 차이를 설명하라.

## 정답과 해설

1. **정답: 3번.** 시스템카탈로그는 데이터베이스 구조와 운영 객체에 관한 메타데이터 집합이며 DDL·권한 변경에 따라 DBMS가 일관되게 유지한다.
2. **정답:** 결과 한 행이 여러 기본 행을 집계한 값이라 어느 한 기본 행의 어떤 값으로 변경을 대응해야 하는지 모호하기 때문이다.
3. **정답:** 뷰를 통해 삽입·수정된 행이 변경 후에도 뷰의 필터 조건을 만족하도록 제한하여, 뷰 범위 밖으로 사라지는 변경을 막기 위한 것이다.
4. **정답 예:** 현재 연결한 데이터베이스·스키마와 환경, 객체명 대소문자·인용 규칙, 카탈로그 조회 권한을 확인한다. 설계 문서와 실제 배포 버전이 같은지도 대조한다.
5. **정답:** 일반 뷰는 저장된 질의 정의를 통해 조회 시 결과를 구성하는 논리 객체이고, 물리화 뷰는 질의 결과를 물리적으로 저장한 뒤 정책에 따라 갱신한다.

## 8. 최종 요약

- **시스템카탈로그와 뷰**에서 시스템카탈로그는 스키마·테이블·열·제약·권한·뷰 등 데이터베이스 메타데이터를 DBMS가 관리하는 집합이다.
- 카탈로그는 스키마 검증, 영향 분석, 권한 감사, 관리·성능 진단의 근거가 되지만 조회 권한과 제품별 공개 범위를 고려한다.
- 일반 뷰는 저장된 질의 정의로 만든 논리적 테이블이며 보안 경계, 논리적 독립성, 질의 단순화와 사용자별 표현에 활용한다.
- 집계·그룹화·중복 제거·복잡한 조인은 기본 행 대응이 모호하여 뷰 갱신을 제한할 수 있다. 실제 규칙은 DBMS 문서를 확인한다.
- `WITH CHECK OPTION`은 갱신 후 행이 뷰 조건을 벗어나는 것을 제한하는 개념이다.
- **관계데이터베이스 모델의 적용 절차와 판단 기준**은 업무 사실·사용 관점 분리 → 관계·키·제약 정의 → 뷰 설계 → 카탈로그 구현 대조 → 질의·갱신·권한 검증 순으로 정리한다.
- 뷰를 적용할 때 공개 열·행, 읽기/갱신 계약, 기본 테이블 권한, 의존성과 성능을 함께 판단하며, 카탈로그 결과는 올바른 환경·스키마·권한에서 해석한다.
