# 3-3-2-1. 데이터모델 개념 · 개체-관계(E-R)모델 · 논리적 데이터모델링

> **출제 범위 기준**: 이 레슨은 정보처리기사 필기 `데이터베이스구축 > 논리 데이터베이스 설계 > 데이터모델링 및 설계`의 **데이터모델 개념**, **개체-관계(E-R)모델**, **논리적 데이터모델링**을 다룬다. 다음 레슨의 데이터베이스 정규화와 논리 모델 품질검증, 뒤의 물리 설계 세부 기법은 여기서 원리만 연결하고 중복해 확장하지 않는다.

데이터 모델링은 화면에 보이는 입력 칸을 그대로 테이블로 옮기는 작업이 아니다. 조직이 보존해야 할 업무 사실, 그 사실을 식별하는 기준, 사실 사이의 관계와 반드시 지켜야 할 규칙을 구조적으로 표현하는 일이다. 좋은 논리 모델은 특정 DBMS 저장 옵션에 묶이지 않으면서도 실제 관계형 스키마로 변환할 수 있고, 요구사항의 각 규칙을 추적할 수 있어야 한다.

---

## 1. 데이터모델 개념

### 1.1 데이터 모델의 세 요소

**데이터 모델**은 현실 세계의 데이터를 추상화하여 구조, 연산, 제약조건으로 표현하는 체계다.

| 요소 | 질문 | 예시 |
|---|---|---|
| 구조(structure) | 어떤 데이터와 관계가 존재하는가? | 회원, 주문, 상품과 주문–상품 관계 |
| 연산(operation) | 데이터를 어떻게 조회·변경하는가? | 주문 생성, 상태 변경, 회원별 주문 조회 |
| 제약조건(constraint) | 어떤 상태와 변경을 허용하는가? | 주문은 정확히 한 회원에 속함, 수량은 양수 |

구조만 그린 그림은 업무 규칙 전체를 담지 못한다. 예를 들어 주문과 상품이 연결되어 있다는 사실 외에도 한 주문에 여러 상품이 포함될 수 있는지, 같은 상품이 여러 주문에 들어갈 수 있는지, 주문 없이 주문항목이 존재할 수 있는지를 제약으로 표현해야 한다.

### 1.2 추상화의 목적

현실의 모든 세부 정보를 저장하면 모델이 좋아지는 것이 아니다. 시스템 목적에 필요한 사실을 선택하고 일관된 의미를 부여해야 한다.

- **분류**: 비슷한 객체를 회원, 상품 같은 유형으로 묶는다.
- **추상화**: 목적과 무관한 세부를 제외하고 핵심 속성만 표현한다.
- **일반화·특수화**: 공통 특징을 상위 유형으로, 차이를 하위 유형으로 표현한다.
- **집합화**: 여러 구성 요소를 하나의 더 큰 개념으로 바라본다.

같은 사람도 병원 모델에서는 환자·의사, 쇼핑 모델에서는 회원·판매자처럼 업무 역할이 다르다. 현실 객체의 이름만으로 개체를 정하지 말고 시스템이 관리할 사건과 규칙을 기준으로 한다.

### 1.3 개념·논리·물리 모델

| 단계 | 중심 질문 | 대표 산출물 | 기술 종속성 |
|---|---|---|---|
| 개념 모델 | 업무에 어떤 핵심 개체와 관계가 있는가? | 핵심 E-R 모델, 주요 규칙 | 낮음 |
| 논리 모델 | 속성·식별자·관계·도메인을 어떻게 일관되게 표현할까? | 상세 논리 ERD, 관계 스키마 | 특정 DBMS와 독립적 |
| 물리 모델 | 선택한 DBMS에서 어떻게 저장·접근할까? | 테이블·열 자료형, 인덱스, 파티션 등 | 높음 |

논리 모델에서도 관계형 구조를 생각할 수 있지만 저장장치, 제품별 자료형, 인덱스 옵션은 물리 단계의 판단이다. 반대로 물리 설계에서 성능 때문에 구조를 조정하더라도 논리 모델의 업무 의미와 추적 관계를 잃어서는 안 된다.

### 1.4 스키마와 인스턴스

**스키마(schema)**는 데이터베이스의 구조와 제약에 대한 정의이고, **인스턴스(instance)**는 특정 시점에 실제로 저장된 데이터 상태다. `회원(회원번호, 이름, 등급)`이라는 정의는 스키마이며, 오늘 저장된 회원 행들의 집합은 인스턴스다.

한두 개 예시 행에 우연히 중복이 없다고 그 열이 키가 되는 것은 아니다. 키와 기수성은 현재 인스턴스가 아니라 모든 유효한 상태에서 지켜야 할 업무 규칙을 근거로 정한다.

## 2. 개체-관계(E-R)모델의 구성 요소

### 2.1 개체와 개체 집합

**개체(entity)**는 업무에서 독립적으로 식별하고 정보를 관리할 대상이다. 같은 유형의 개체 모음을 개체 집합 또는 개체 유형이라 한다. 회원 한 명은 개체 인스턴스이고 `회원`은 개체 유형이다.

개체 후보는 다음 기준으로 확인한다.

- 업무상 이름과 정의가 명확한가?
- 여러 인스턴스가 존재할 수 있는가?
- 각 인스턴스를 구분할 수 있는가?
- 관리할 속성이나 다른 개체와의 관계가 있는가?
- 단순 화면 항목이나 계산 결과가 아닌 지속할 업무 사실인가?

“회원주소”가 독립 개체인지 회원의 속성인지는 요구사항에 따라 다르다. 주소 이력, 배송지 여러 개, 주소별 검증과 관계를 관리한다면 개체가 될 수 있고, 단순 문자열 하나만 필요하면 속성일 수 있다.

### 2.2 속성과 식별자

**속성(attribute)**은 개체나 관계의 특성을 나타낸다.

| 속성 유형 | 의미 | 예시 |
|---|---|---|
| 단순 속성 | 더 나누지 않고 사용하는 값 | 등급 코드 |
| 복합 속성 | 의미 있는 하위 요소로 나뉨 | 주소 → 시·구·도로명 |
| 단일값 속성 | 한 개체에 한 값 | 생년월일 |
| 다중값 속성 | 한 개체에 여러 값 | 여러 연락처 |
| 유도 속성 | 다른 값으로 계산 가능 | 생년월일에서 계산한 나이 |
| 저장 속성 | 원천 사실로 보존 | 생년월일 |

**후보키**는 각 개체를 유일하게 식별할 수 있는 최소 속성 집합이고, 그중 선택한 것이 주 식별자 또는 기본키가 된다. 식별자 판단 기준은 유일성, 최소성, 안정성, NULL 불허 가능성이다. 바뀔 수 있는 이름·전화번호를 편리하다는 이유로 식별자로 선택하면 참조와 이력 관리가 어려워질 수 있다.

파생 가능한 값도 조회 비용이나 당시 값 보존 때문에 저장할 수 있지만, 원천 값과 불일치할 위험을 통제해야 한다. “유도 속성은 절대로 저장할 수 없다”는 절대 규칙으로 외우지 않는다.

### 2.3 관계와 관계 차수

**관계(relationship)**는 개체 사이의 업무 연관이다. 회원이 주문을 `한다`, 주문이 상품을 `포함한다`처럼 동사로 읽어 의미를 검증한다. 관계 자체에도 수량, 계약일, 역할 같은 속성이 있을 수 있다.

관계에 참여하는 개체 유형 수를 관계 차수(degree)라 한다.

- 단항 관계: 직원이 다른 직원을 관리하는 재귀 관계
- 이항 관계: 회원–주문
- 삼항 관계: 공급자가 특정 프로젝트에 특정 부품을 공급

삼항 관계를 세 개의 이항 관계로 무조건 분해하면 “어느 공급자가 어느 프로젝트에 어떤 부품을 공급했는가”라는 세 요소의 결합 의미를 잃을 수 있다.

### 2.4 기수성과 참여 제약

**기수성(cardinality)**은 한쪽 개체 인스턴스가 반대쪽 몇 개와 연결될 수 있는지를 나타낸다.

- 1:1 — 사람과 현재 유효한 단일 여권처럼 양쪽 최대 하나
- 1:N — 한 회원이 여러 주문을 하고 각 주문은 한 회원에 속함
- M:N — 한 주문에 여러 상품, 한 상품이 여러 주문에 포함됨

최소 참여 수까지 함께 표현하면 선택/필수 관계를 알 수 있다. `(0, N)`은 참여하지 않을 수도 있고 여러 개일 수도 있으며, `(1, 1)`은 정확히 하나에 반드시 참여한다는 의미다. 최대 기수만 보고 필수 여부를 추측하지 않는다.

**전체 참여(total participation)**는 해당 개체의 모든 인스턴스가 관계에 반드시 참여하고, **부분 참여(partial participation)**는 참여하지 않는 인스턴스도 허용한다. 표기법에 따라 이중선, 원·막대, 최소·최대 숫자 등 표현이 다르므로 기호 모양보다 의미를 읽는다.

### 2.5 강한 개체와 약한 개체

**강한 개체**는 자신의 속성만으로 식별 가능하다. **약한 개체(weak entity)**는 단독으로 완전한 식별자가 없고 소유 개체의 식별자와 부분키를 함께 사용해 식별한다.

예를 들어 `주문항목`을 `(주문번호, 항목순번)`으로 식별한다면 항목순번은 주문 안에서만 유일한 부분키이고, 주문항목은 주문에 존재 의존적일 수 있다. 주문이 없는데 주문항목만 남아 있으면 업무 의미가 깨진다.

약한 개체를 단순히 “속성이 적은 개체”나 “중요하지 않은 개체”로 이해하지 않는다. 핵심은 식별 의존성과 존재 의존성이다.

## 3. E-R 표기와 읽는 법

전통적인 Chen 표기에서는 개체를 사각형, 관계를 마름모, 속성을 타원으로 나타내는 방식이 널리 알려져 있다. Crow's Foot 계열 표기는 관계 끝의 기호로 최소·최대 기수성을 표현한다. 도구와 조직마다 표기법이 다르므로 모델에는 범례와 규칙을 명시해야 한다.

그림을 읽을 때는 각 관계를 양방향 문장으로 만든다.

```text
회원 한 명은 0개 이상의 주문을 할 수 있다.
주문 하나는 정확히 한 회원에 속해야 한다.

주문 하나는 1개 이상의 주문항목을 가진다.
주문항목 하나는 정확히 한 주문에 속한다.
```

이 문장이 요구사항과 맞는지 업무 담당자에게 확인한다. “회원이 주문을 한다”만으로는 주문 없는 회원을 허용하는지, 비회원 주문을 허용하는지 알 수 없다.

### 3.1 예시 E-R 구조

온라인 주문의 간단한 개념 모델을 글로 표현하면 다음과 같다.

```text
회원(회원번호, 이름, 등급)
주문(주문번호, 주문일시, 상태)
상품(상품번호, 상품명, 현재가격)
주문항목(주문번호, 항목순번, 상품번호, 주문수량, 주문단가)

회원 1 ── 0..N 주문
주문 1 ── 1..N 주문항목
상품 1 ── 0..N 주문항목
```

`주문단가`는 현재 상품 가격과 같아 보이지만 주문 당시 거래 사실을 보존하기 위해 주문항목에 저장할 수 있다. 현재가격이 바뀌어도 과거 주문 금액이 바뀌면 안 되기 때문이다. 속성 배치는 “중복처럼 보이는가”만으로 판단하지 않고 그 값이 설명하는 업무 사실과 시간 기준을 본다.

## 4. E-R 모델을 관계 모델로 변환하는 원칙

### 4.1 강한 개체

강한 개체 유형은 보통 하나의 관계(테이블)로 변환하고, 단순 속성을 열로, 주 식별자를 기본키로 옮긴다. 복합 속성은 필요한 단순 구성 요소로 나눈다.

### 4.2 다중값 속성

한 회원이 여러 전화번호를 가진다면 한 열에 쉼표로 연결하기보다 별도 관계로 분리한다.

```text
회원(회원번호, 이름, ...)
회원전화(회원번호, 전화번호, 전화유형, ...)
```

회원전화의 키는 업무 규칙에 따라 `(회원번호, 전화번호)` 또는 별도 식별자가 될 수 있다. 전화번호 변경 이력과 중복 허용 규칙을 먼저 확인한다.

### 4.3 약한 개체

약한 개체 관계에는 소유 개체의 기본키를 외래키이자 식별자의 일부로 포함하고, 부분키를 결합한다. 주문항목의 `(주문번호, 항목순번)`이 대표 예다.

### 4.4 1:1 관계

한쪽 테이블에 다른 쪽 키를 외래키로 두고 유일 제약을 적용하는 방식이 일반적이다. 어느 쪽에 둘지는 전체 참여, NULL 최소화, 접근 방향, 생명주기를 본다. 두 개체가 항상 함께 생성·삭제되고 의미도 하나라면 통합 가능성도 검토하지만, 보안·선택 속성·수명 차이가 있으면 분리가 적합할 수 있다.

### 4.5 1:N 관계

일반적으로 N쪽 관계에 1쪽 기본키를 외래키로 둔다. 회원–주문이라면 주문에 회원번호를 둔다. 주문이 반드시 회원에 속해야 하면 외래키의 NULL 불허와 참조 무결성을 함께 표현한다.

### 4.6 M:N 관계

M:N 관계는 두 개체의 키를 참조하는 교차·연결 관계로 변환한다. 관계 속성도 이 관계에 둔다.

```text
주문항목(
    주문번호  FK → 주문,
    항목순번,
    상품번호  FK → 상품,
    주문수량,
    주문단가,
    PK(주문번호, 항목순번)
)
```

상품번호까지 복합 기본키에 포함할지는 “한 주문에 같은 상품이 여러 항목으로 나올 수 있는가?” 같은 규칙에 따라 달라진다. 그림의 M:N을 기계적으로 두 키의 조합만으로 정하지 않는다.

### 4.7 재귀·삼항 관계

재귀 1:N 관계는 같은 테이블의 키를 참조하는 외래키로 표현할 수 있다. 직원의 관리자번호가 직원번호를 참조하는 예가 있다. 삼항 관계는 참여한 세 개체 키와 관계 속성을 가진 별도 관계로 변환하되, 후보키는 기수성 규칙을 분석해 정한다.

## 5. 논리적 데이터모델링 절차

**논리적 데이터모델링**은 개념 모델을 상세화하여 속성, 식별자, 관계, 도메인과 제약을 특정 DBMS 저장 방식과 독립적으로 정의하는 활동이다.

### 5.1 요구사항에서 업무 사실 추출

명사만 모아 개체를 만들지 않는다. 문장의 행위와 규칙을 함께 분석한다.

```text
“회원은 여러 배송지를 등록할 수 있고, 주문할 때 등록 배송지 중 하나의
당시 주소를 배송 주소로 확정한다.”
```

이 요구에서는 회원, 등록배송지, 주문이라는 후보 외에 “주문 당시 주소를 보존한다”는 시간 규칙이 중요하다. 등록배송지가 나중에 수정되어도 과거 주문의 배송 주소가 변하지 않도록 모델링해야 한다.

### 5.2 개체 정의와 명명

각 개체에 다음을 기록한다.

- 고유하고 일관된 업무 명칭
- 한 문장 정의
- 포함·제외 범위
- 대표 사례와 반례
- 생명주기와 생성·종료 조건
- 소유 업무 영역

동음이의어는 이름을 구분하고, 같은 의미를 여러 이름으로 쓰는 이음동의어는 표준 용어로 통합한다. `사용자`가 고객인지 운영자인지 모호하면 모델 전체 관계가 흔들린다.

### 5.3 속성·도메인 정의

각 속성에 의미, 값의 단위, 허용 범위, NULL 의미, 기본값, 유도 여부를 정의한다. 논리 도메인은 “금액”, “회원상태코드”, “일시”처럼 업무 의미를 표현하며 제품별 `VARCHAR(20)` 같은 물리 자료형과 구분한다.

NULL이 `알 수 없음`, `해당 없음`, `아직 미정` 중 무엇을 뜻하는지 구분하지 않으면 조회 조건과 통계 해석이 달라진다. 서로 다른 의미를 하나의 NULL로 합쳐도 되는지 판단한다.

### 5.4 식별자 선정

후보 식별자를 모두 찾고 다음을 비교한다.

- 모든 유효 인스턴스에서 유일한가?
- 불필요한 속성을 빼면 유일성이 깨지는 최소 집합인가?
- 생명주기 동안 값이 안정적인가?
- 반드시 값이 존재하는가?
- 외부 개인정보나 업무 변화에 지나치게 종속되지 않는가?

대리키를 쓰더라도 원래 업무상 유일 규칙을 고유 제약 등으로 보존해야 한다. 단순 일련번호가 있다고 이메일 중복 허용 여부 같은 업무 규칙이 사라지는 것은 아니다.

### 5.5 관계·기수성·선택성 정의

각 관계를 양방향 문장으로 읽고 최소·최대 참여를 기록한다. 기수성 근거가 현재 데이터 건수가 아니라 업무 규칙인지 확인한다. 부모 없는 자식, 삭제 시 자식 처리, 관계의 시작·종료 시점을 정한다.

### 5.6 관계 스키마로 변환

E-R 변환 원칙으로 관계와 키·외래키 후보를 만든다. M:N과 다중값 속성을 해소하고, 관계 속성을 올바른 위치에 둔다. 이 단계에서는 아직 특정 저장장치나 인덱스 옵션을 결정하지 않는다.

### 5.7 요구사항 추적과 검토

모델의 각 개체·속성·관계·제약이 어떤 요구사항을 구현하는지 연결한다. 반대로 요구사항의 모든 데이터 규칙이 모델 어딘가에 표현되었는지 확인한다.

| 검토 관점 | 질문 |
|---|---|
| 완전성 | 필요한 업무 사실과 규칙이 빠지지 않았는가 |
| 정확성 | 기수성·선택성·식별자가 실제 규칙과 맞는가 |
| 일관성 | 같은 용어·도메인·규칙을 서로 다르게 표현하지 않는가 |
| 최소성 | 같은 사실을 근거 없이 여러 곳에 중복 저장하지 않는가 |
| 추적성 | 모델 요소를 요구사항과 연결할 수 있는가 |
| 이해 가능성 | 업무 담당자와 개발자가 같은 문장으로 읽을 수 있는가 |

정규화를 통한 세부 이상 현상 제거와 공식적인 품질검증은 다음 레슨에서 이어진다.

## 6. 모델링 판단 사례

### 6.1 주문의 회원번호는 어디에 두는가

회원 1명은 0개 이상의 주문을 할 수 있고 주문은 정확히 한 회원에 속한다면 1:N 관계다. N쪽인 주문에 회원번호 외래키를 둔다. 비회원 주문이 가능하다면 “정확히 한 회원”이라는 규칙부터 수정하고 게스트 식별 방식과 NULL 의미를 정의해야 한다.

### 6.2 현재 나이를 저장할 것인가

나이는 시간에 따라 변하고 생년월일에서 계산된다. 일반적으로 생년월일을 원천 속성으로 저장하고 기준일에 따라 나이를 계산한다. 특정 계약 체결 당시 나이가 법적 사실로 필요하다면 “계약 당시 나이” 또는 판단 근거 일시를 별도 사실로 보존할 수 있다.

### 6.3 한 열에 여러 상품번호를 저장할 것인가

쉼표로 연결한 상품번호는 개별 참조 무결성, 검색, 수량·단가 관계 표현이 어렵다. 주문–상품 M:N 관계를 주문항목 개체로 풀어 각 상품과 주문수량·주문단가를 행 단위로 관리한다.

### 6.4 코드명을 매 행에 반복 저장할 것인가

코드 값과 코드 설명의 변경 주기, 다국어, 유효 기간을 관리한다면 코드 개체와 참조 관계를 둔다. 값이 고정된 작은 도메인이고 DB 제약으로 충분한 경우 별도 코드 테이블이 항상 필수인 것은 아니다. 운영·확장 요구를 보고 결정한다.

## 7. 시험 함정

- 현재 예시 데이터에 중복이 없다는 이유로 후보키라고 판단한다.
- 개체를 단순 명사, 관계를 단순 동사로만 기계적으로 추출한다.
- 1:N 관계의 외래키를 일반적으로 1쪽에 둔다고 잘못 외운다.
- M:N 관계를 관계 속성 없이 두 테이블만으로 바로 구현한다.
- 약한 개체를 중요도가 낮거나 속성이 적은 개체로 정의한다.
- 최대 기수성만 보고 관계 참여가 필수인지 선택인지 판단한다.
- 유도 속성은 어떤 상황에서도 저장할 수 없다고 단정한다.
- 대리키를 추가하면 업무상 유일 제약이 자동으로 보장된다고 본다.
- 논리 모델에 제품별 인덱스·파티션·저장공간 결정을 섞는다.
- 삼항 관계를 의미 검토 없이 세 이항 관계로 나눈다.

## 8. 확인 문제

### 문제 1

회원 한 명이 여러 주문을 할 수 있고 각 주문은 반드시 한 회원에 속한다. 관계 모델로 변환할 때 외래키의 일반적인 위치는 어디인가?

1. 회원 테이블에 주문번호
2. 주문 테이블에 회원번호
3. 두 테이블 모두 외래키 없음
4. 상품 테이블에 회원번호

### 문제 2

약한 개체의 핵심 특성을 설명하고 주문항목 예시에서 식별자를 적어라.

### 문제 3

문장 커뮤니케이션 관점에서 관계의 최소·최대 기수성을 양방향으로 읽어야 하는 이유는 무엇인가?

### 문제 4

대리키 `member_id`를 회원 테이블에 추가했지만 업무상 이메일 중복을 허용하지 않는다. 대리키만 기본키로 두면 충분하지 않은 이유는 무엇인가?

### 문제 5

다음 중 논리적 데이터모델링 단계의 중심 작업과 가장 거리가 먼 것은 무엇인가?

1. 개체 정의와 식별자 선정
2. 관계의 기수성과 선택성 정의
3. 업무 도메인과 NULL 의미 정의
4. 특정 저장장치의 파일 배치 결정

## 정답과 해설

1. **정답: 2번.** 1:N 관계는 일반적으로 N쪽인 주문에 1쪽 회원의 기본키를 외래키로 둔다. 필수 관계라면 NULL 불허도 함께 검토한다.
2. **정답:** 약한 개체는 자신의 속성만으로 완전히 식별되지 않고 소유 개체의 식별자에 의존한다. 주문항목이 주문 안의 항목순번으로 식별된다면 `(주문번호, 항목순번)`이 결합 식별자가 된다.
3. **정답:** 한쪽의 “여러 개” 정보만으로 반대쪽의 필수 참여 여부와 최대 연결 수를 알 수 없기 때문이다. 양방향 문장으로 읽어야 0 허용, 정확히 1, 여러 개라는 규칙을 모두 확인할 수 있다.
4. **정답:** 대리키는 행을 기술적으로 식별하지만 이메일이 중복되면 안 된다는 별도의 업무 규칙을 표현하지 않는다. 이메일에 고유 제약 등 적합한 논리 제약이 필요하다.
5. **정답: 4번.** 저장장치 파일 배치는 특정 환경에 종속된 물리 설계 판단이다. 논리 모델은 개체·속성·식별자·관계·도메인과 제약을 중심으로 한다.

## 9. 최종 요약

- **데이터모델 개념**은 현실의 업무 사실을 구조, 연산, 제약조건으로 추상화하는 체계다. 개념·논리·물리 모델의 목적과 기술 종속성을 구분한다.
- 스키마는 구조와 제약의 정의이고 인스턴스는 특정 시점의 실제 데이터 상태다. 현재 데이터의 우연한 패턴을 영구 규칙으로 착각하지 않는다.
- **개체-관계(E-R)모델**은 개체, 속성, 식별자, 관계, 기수성, 참여 제약을 표현한다. 약한 개체는 소유 개체의 식별자에 의존한다.
- 1:N은 일반적으로 N쪽에 외래키를 두고, M:N은 관계 속성을 포함한 연결 관계로 변환한다. 다중값 속성도 별도 관계로 분리한다.
- **논리적 데이터모델링**은 요구사항의 업무 사실 추출 → 개체 정의 → 속성·도메인 → 식별자 → 관계·기수성 → 관계 스키마 변환 → 요구사항 추적·검토 순으로 진행한다.
- 모델의 올바름은 예시 데이터가 아니라 모든 유효 상태에 적용될 업무 규칙에서 판단한다. 물리 저장 옵션보다 의미, 키, NULL, 시간 기준, 생명주기와 추적성을 먼저 확정한다.
