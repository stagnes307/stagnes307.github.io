# 3-3-2-2. 데이터베이스 정규화 · 논리 데이터모델 품질검증

> **출제 범위 기준**: 이 레슨은 정보처리기사 필기 `데이터베이스구축 > 논리 데이터베이스 설계 > 데이터모델링 및 설계`에서 **데이터베이스 정규화**, **논리 데이터모델 품질검증**을 다룬다. 정규형 이름만 암기하지 않고 함수 종속, 이상 현상, 무손실 분해와 종속성 보존을 판단하는 과정을 익힌다. 물리적 성능을 위한 반정규화는 논리 모델의 의미와 품질을 검증한 뒤 별도 근거로 결정한다.

정규화는 테이블 수를 무조건 늘리는 기술이 아니다. 하나의 관계에 서로 다른 사실이 뒤섞여 같은 값이 반복될 때 삽입·수정·삭제가 다른 사실에 뜻밖의 영향을 주는 문제를 줄이는 과정이다. 품질검증은 정규형만 확인하는 작업도 아니다. 요구사항의 완전성, 식별자와 관계의 정확성, 도메인·명명·추적성까지 함께 검토해야 한다.

---

## 1. 정규화가 필요한 이유

### 1.1 반복 데이터와 이상 현상

다음 관계를 생각해 보자.

```text
수강(학생번호, 학생명, 과목번호, 과목명, 담당교수번호, 담당교수명, 성적)
기본키 후보: (학생번호, 과목번호)
```

학생 한 명이 여러 과목을 들으면 학생명이 반복되고, 한 과목을 여러 학생이 들으면 과목명·교수 정보가 반복된다. 이때 다음 이상(anomaly)이 생길 수 있다.

| 이상 | 의미 | 예시 |
|---|---|---|
| 삽입 이상 | 한 사실을 넣기 위해 무관한 사실까지 필요 | 수강생이 없는 새 과목을 등록하기 어려움 |
| 수정 이상 | 중복된 같은 사실을 모두 바꾸지 않아 불일치 | 교수명을 일부 수강 행에서만 변경 |
| 삭제 이상 | 한 사실 삭제가 다른 독립 사실까지 제거 | 마지막 수강 취소로 과목 정보도 사라짐 |

이상 현상의 원인은 단순히 행이 많아서가 아니라 서로 다른 결정 규칙을 가진 사실을 한 관계에 저장한 데 있다.

### 1.2 정규화의 목적

- 데이터 중복과 갱신 이상을 줄인다.
- 속성 간 종속 관계를 명확히 한다.
- 한 관계가 한 주제의 사실을 표현하도록 돕는다.
- 무결성 제약을 더 직접적으로 구현할 수 있게 한다.
- 변경 시 영향을 받는 행과 규칙을 예측하기 쉽게 한다.

정규화가 저장 중복을 줄일 수는 있지만, 조회가 항상 빨라진다는 보장은 없다. 분해된 관계를 다시 결합하는 비용이 생길 수 있다. 정확한 논리 모델을 만든 뒤 실제 측정과 일관성 요구를 근거로 물리 최적화를 판단한다.

## 2. 함수 종속을 읽는 법

### 2.1 함수 종속

관계 R에서 속성 집합 X의 값이 같으면 속성 집합 Y의 값도 항상 같을 때 `X → Y`라고 쓰고 “X가 Y를 함수적으로 결정한다”고 한다. X는 결정자, Y는 종속자다.

```text
학생번호 → 학생명
과목번호 → 과목명, 담당교수번호
담당교수번호 → 담당교수명
(학생번호, 과목번호) → 성적
```

현재 표본 데이터에서 우연히 같은 값이 없다는 이유로 함수 종속을 정하지 않는다. 업무 규칙상 모든 유효 인스턴스에서 성립해야 한다. 담당교수번호 하나가 여러 교수명을 가질 수 있다면 위 종속은 잘못된 것이다.

### 2.2 완전·부분 함수 종속

복합 결정자 X의 모든 속성이 있어야 Y를 결정하고, 어떤 진부분집합으로도 Y를 결정할 수 없으면 **완전 함수 종속**이다. 반대로 복합키 일부만으로 Y를 결정할 수 있으면 **부분 함수 종속**이다.

수강 관계에서 `(학생번호, 과목번호) → 성적`은 성적이 두 값의 조합에 달려 있다면 완전 함수 종속이다. 그러나 `학생번호 → 학생명`은 복합키의 일부만으로 결정되므로 학생명은 기본키에 부분 종속한다.

기본키가 단일 속성이라면 그 키의 일부라는 것이 없으므로 기본키에 대한 부분 함수 종속 문제는 발생하지 않는다.

### 2.3 이행 함수 종속

`X → Y`, `Y → Z`가 성립하고 Y가 X에 종속하며 Z가 키에 직접 의존하는 것이 아니라 Y를 거쳐 결정될 때 X에서 Z로 **이행 함수 종속**이 생긴다.

```text
과목번호 → 담당교수번호
담당교수번호 → 담당교수명
따라서 과목번호 → 담당교수명
```

교수명은 과목번호에 직접 속한 사실이 아니라 교수번호가 설명하는 사실이다. 교수 정보를 별도 관계로 분리하면 교수명 수정 이상을 줄일 수 있다.

### 2.4 함수 종속 추론의 기본

시험에서는 함수 종속 집합에서 다른 종속을 추론하거나 키를 찾는 문제가 나올 수 있다. 대표적인 Armstrong 공리는 다음과 같다.

- **반사성**: Y가 X의 부분집합이면 `X → Y`
- **증가성**: `X → Y`이면 `XZ → YZ`
- **이행성**: `X → Y`, `Y → Z`이면 `X → Z`

여기서 합집합, 분해, 의사이행 규칙 등을 유도할 수 있다. 속성 폐쇄 `X+`는 함수 종속을 반복 적용하여 X가 결정할 수 있는 모든 속성 집합이다. X의 폐쇄가 관계의 모든 속성을 포함하면 X는 슈퍼키이고, 더 줄일 수 없다면 후보키다.

## 3. 정규형별 판단

정규화는 이전 단계 조건을 만족한 상태에서 다음 조건을 확인하는 누적 과정이다.

### 3.1 제1정규형(1NF)

각 속성값이 관계 모델에서 취급하는 원자값이고 한 칸에 반복 그룹이나 여러 값을 묶지 않은 상태다.

```text
잘못된 예: 회원(회원번호, 전화번호목록="010...,02...")

분리 예:
회원(회원번호, 이름)
회원전화(회원번호, 전화번호, 전화유형)
```

원자성은 절대적인 문자열 길이가 아니라 시스템이 값을 더 나누어 독립적으로 질의·제약할 필요가 있는지에 따라 정해진다. 주소 전체를 하나의 값으로 취급할 업무와 시·구별 검색이 필요한 업무의 원자성 판단은 다를 수 있다.

### 3.2 제2정규형(2NF)

1NF를 만족하고, 모든 비주요 속성이 모든 후보키에 완전 함수 종속한 상태다. 복합키 일부에만 종속하는 속성을 분리한다.

수강 예에서 다음처럼 나눌 수 있다.

```text
학생(학생번호, 학생명)
과목(과목번호, 과목명, 담당교수번호, 담당교수명)
수강(학생번호, 과목번호, 성적)
```

학생명과 과목 정보가 복합키 일부에 부분 종속하던 문제가 제거된다. 다만 과목 관계에는 아직 `담당교수번호 → 담당교수명`이라는 이행 종속이 남아 있다.

### 3.3 제3정규형(3NF)

2NF를 만족하고, 비주요 속성이 후보키에 이행적으로 종속하지 않도록 한 상태다. 일반적으로 “비키 속성은 키 전체에, 그리고 키에만 의존한다”는 기억법을 쓰지만 여러 후보키가 있을 때는 정식 조건을 확인해야 한다.

```text
과목(과목번호, 과목명, 담당교수번호)
교수(담당교수번호, 담당교수명)
```

교수명을 교수번호가 결정하므로 교수 관계로 분리한다. 이제 교수명 변경은 교수 한 행에만 적용된다.

3NF의 정식 조건은 모든 비자명 함수 종속 `X → A`에 대해 X가 슈퍼키이거나 A가 주요 속성, 즉 어떤 후보키에 속하는 속성인 것이다.

### 3.4 BCNF(Boyce-Codd Normal Form)

모든 비자명 함수 종속 `X → Y`에서 X가 슈퍼키인 상태다. BCNF는 결정자가 반드시 후보키 또는 슈퍼키여야 하므로 3NF보다 엄격하다.

3NF는 종속자의 속성이 후보키 일부인 경우 일부 비슈퍼키 결정자를 허용할 수 있지만 BCNF는 허용하지 않는다. 후보키가 여러 개이고 서로 겹치는 관계에서 차이가 나타날 수 있다.

예를 들어 특정 업무 규칙에서 `(학생, 과목) → 교수`와 `교수 → 과목`이 성립한다고 하자. 교수 한 명이 한 과목만 담당하지만 한 과목은 여러 교수가 담당할 수 있고, 학생은 과목별 한 교수에게 배정된다. 후보키가 `(학생, 과목)`, `(학생, 교수)`가 될 수 있으며 `교수 → 과목`의 결정자 교수는 슈퍼키가 아니어서 BCNF를 위반한다.

BCNF 분해는 이상을 줄이지만 모든 원래 함수 종속을 개별 분해 관계에서 직접 검사할 수 있는 종속성 보존이 깨질 수 있다. 무손실성과 종속성 보존을 함께 판단한다.

### 3.5 제4정규형(4NF)

BCNF를 만족하고 비자명한 다치 종속(multivalued dependency)에서 결정자가 슈퍼키인 상태다. 한 개체에 대해 서로 독립적인 다중값 사실을 한 관계에 함께 두면 불필요한 조합이 생긴다.

```text
강사(강사번호, 자격증, 사용언어)
```

자격증 목록과 사용언어 목록이 서로 독립이라면 한 강사의 모든 자격증×언어 조합이 반복된다. 다음처럼 분리할 수 있다.

```text
강사자격(강사번호, 자격증)
강사언어(강사번호, 사용언어)
```

단순히 값이 여러 개라는 사실만으로 다치 종속을 판단하지 않는다. 두 다중값 집합이 서로 독립적으로 결정되는지가 핵심이다.

### 3.6 제5정규형(5NF)

모든 비자명한 조인 종속이 후보키에 의해 함의되는 상태다. 관계를 셋 이상으로 분해했다가 자연 조인했을 때 원래 관계를 정확히 복원해야 하는 복잡한 제약을 다룬다. 공급자–부품–프로젝트처럼 세 요소의 허용 조합이 쌍별 관계만으로 결정되는지 여부를 분석한다.

5NF는 실무의 일반 업무 모델에서 자주 직접 적용되는 단계는 아니지만, “무조건 더 많이 분해하면 좋다”가 아니라 무손실 복원과 업무 조인 규칙을 확인해야 한다는 점이 중요하다.

### 3.7 정규형 비교표

| 정규형 | 제거하려는 중심 문제 | 핵심 판단 |
|---|---|---|
| 1NF | 반복 그룹·비원자값 | 한 속성값을 업무상 하나의 값으로 다루는가 |
| 2NF | 복합키 일부에 대한 부분 종속 | 비주요 속성이 후보키 전체에 의존하는가 |
| 3NF | 비키 속성을 거치는 이행 종속 | 비주요 속성이 키가 아닌 속성에 의존하는가 |
| BCNF | 슈퍼키가 아닌 결정자 | 모든 결정자가 슈퍼키인가 |
| 4NF | 독립적인 다치 종속 | 다치 종속의 결정자가 슈퍼키인가 |
| 5NF | 비키에서 생기는 조인 종속 | 더 분해·조인해도 허위 튜플 없이 복원되는가 |

## 4. 분해 품질: 무손실과 종속성 보존

### 4.1 무손실 분해

관계 R을 R1, R2로 분해한 뒤 자연 조인하여 정확히 원래 R을 복원할 수 있으면 **무손실 조인 분해(lossless-join decomposition)**다. 누락되거나 원래 없던 허위 튜플이 생기면 손실 분해다.

이항 분해에서는 공통 속성이 R1 또는 R2를 함수적으로 결정하는지 보는 조건이 중요한 판단 근거가 된다. 분해 전 데이터 일부만으로 시험하지 않고 함수 종속을 근거로 보장해야 한다.

### 4.2 종속성 보존

분해 후 각 관계에 투영된 제약만 검사하여 원래 함수 종속을 모두 보장할 수 있으면 **종속성 보존(dependency preservation)**이다. 보존되지 않으면 제약 하나를 확인하기 위해 여러 관계를 조인해야 할 수 있다.

무손실 분해와 종속성 보존은 다른 특성이다. 무손실이라고 모든 종속이 보존되는 것은 아니고, 종속을 보존한다고 원래 관계가 허위 튜플 없이 복원된다는 뜻도 아니다. 정규화 선택에서는 둘을 별도로 확인한다.

## 5. 데이터베이스 정규화 적용 절차

1. 관계의 의미와 후보키를 확정한다.
2. 업무 규칙에서 함수 종속을 도출한다.
3. 속성 폐쇄로 후보키와 결정자를 검증한다.
4. 반복 그룹과 다중값 표현을 제거해 1NF를 확인한다.
5. 복합 후보키 일부에 종속한 비주요 속성을 찾아 2NF로 분해한다.
6. 비키 속성 사이의 이행 종속을 찾아 3NF로 분해한다.
7. 모든 결정자가 슈퍼키인지 확인해 BCNF 필요성을 판단한다.
8. 독립 다중값·조인 종속이 있으면 4NF·5NF를 검토한다.
9. 각 분해의 무손실성과 종속성 보존을 확인한다.
10. 요구사항 사례로 삽입·수정·삭제와 조회 결과를 재검증한다.

관계 이름과 열을 먼저 잘라 놓고 나중에 종속을 맞추지 않는다. 어떤 업무 규칙 때문에 분해했는지 기록해야 모델 품질검증과 유지보수가 가능하다.

## 6. 논리 데이터모델 품질검증

**논리 데이터모델 품질검증**은 모델이 요구사항을 빠짐없이 정확하고 일관되게 표현하며 실제 구현으로 전환 가능한지 확인하는 활동이다.

### 6.1 완전성

- 요구사항의 모든 핵심 업무 사실이 개체·속성·관계에 반영되었는가?
- 생성·변경·종료와 이력 규칙이 빠지지 않았는가?
- 필수 데이터와 선택 데이터가 구분되었는가?
- 오류·취소·예외 상태도 표현했는가?

CRUD 매트릭스나 요구사항 추적표를 이용해 어떤 기능이 어떤 개체를 생성·조회·변경·삭제하는지 대조할 수 있다. CRUD가 전혀 없는 개체는 불필요하거나 기능 요구가 누락되었을 수 있고, 사용하는 데이터가 모델에 없으면 모델 누락일 수 있다.

### 6.2 정확성

- 식별자가 실제로 유일·최소·안정적인가?
- 관계의 최소·최대 기수성과 존재 의존성이 맞는가?
- 속성이 올바른 개체의 사실을 설명하는가?
- 도메인, 단위, 시간 기준, 코드 의미가 정확한가?
- 유도값과 저장값의 원천·갱신 책임이 분명한가?

샘플 행을 만들어 정상·경계·예외 업무 문장을 모델에 넣어 본다. 모델이 허용하면 안 되는 상태를 허용하거나 유효한 상태를 표현하지 못하면 제약이 잘못되었다.

### 6.3 일관성

- 같은 업무 용어가 모델마다 같은 정의와 이름을 쓰는가?
- 같은 도메인의 자료 의미와 NULL 정책이 일치하는가?
- 부모·자식 관계의 식별자와 참조가 양쪽에서 맞는가?
- 중복 속성의 원천과 동기화 규칙이 충돌하지 않는가?

`고객`, `회원`, `사용자`가 같은 대상을 뜻하는지 다른 역할인지 용어 사전으로 명확히 한다. 이름만 통일하고 의미가 다르면 더 위험하다.

### 6.4 준거성·표준 준수

조직의 명명 규칙, 표준 도메인, 코드 체계, 개인정보 분류, 데이터 소유권 정책을 따르는지 확인한다. 표준은 일관성을 돕지만 잘못된 업무 의미를 표준 이름으로 포장하지 않도록 요구사항 정확성을 먼저 본다.

### 6.5 최소성·비중복성

같은 원천 사실을 여러 개체에 이유 없이 중복 저장하지 않는지 함수 종속과 정규형으로 확인한다. 의도적 중복이 필요하면 원본, 갱신 시점, 불일치 탐지·복구 방법을 기록한다. 논리 모델에서 근거 없는 반정규화를 성능 개선이라고 미리 단정하지 않는다.

### 6.6 추적성

각 모델 요소가 어떤 요구사항·업무 규칙에서 왔고, 어떤 기능·인터페이스에서 사용되는지 연결한다. 요구사항 변경 시 영향을 받는 개체·관계·제약을 찾을 수 있어야 한다.

### 6.7 이해 가능성과 명확성

- 개체·속성 정의가 한 문장으로 명확한가?
- 관계를 양방향 업무 문장으로 읽을 수 있는가?
- 약어와 코드가 용어 사전에 설명되어 있는가?
- 표기법 범례와 선택/필수 기호가 일관적인가?
- 모델 규모를 업무 영역별로 나누되 연결 관계를 잃지 않았는가?

## 7. 품질검증 실행 흐름

### 7.1 자동 점검과 사람 검토를 결합한다

모델링 도구로 중복 이름, 키 없는 개체, 고아 관계, 도메인 불일치, 참조 오류를 자동 탐지할 수 있다. 그러나 “한 회원이 여러 활성 계약을 가질 수 있는가?” 같은 업무 의미는 담당자 검토가 필요하다.

1. 모델 버전과 검토 범위를 고정한다.
2. 자동 규칙으로 구조 오류와 표준 위반 후보를 찾는다.
3. 모델러가 후보키, 함수 종속, 정규형과 분해 근거를 준비한다.
4. 업무 담당자와 관계·기수성·상태·시간 규칙을 시나리오로 확인한다.
5. 개발·DB 담당자가 구현 가능성, 제약 표현, 인터페이스 영향을 검토한다.
6. 결함 위치, 근거, 심각도, 담당자와 상태를 기록한다.
7. 수정 후 영향 영역과 요구사항 추적표를 다시 확인한다.

### 7.2 검증 사례표

| 사례 | 모델에서 확인할 내용 |
|---|---|
| 회원 탈퇴 후 주문 보존 | 주문의 회원 참조와 삭제 정책, 익명화 규칙 |
| 상품 가격 변경 | 주문 당시 단가와 현재 가격의 사실 분리 |
| 동일 이메일 재가입 | 회원 식별자, 이메일 유일성·유효 기간 |
| 주문 전체 취소 | 주문·항목 상태와 이력 표현 |
| 하나의 강의에 복수 강사 | 기수성과 연결 개체 필요 여부 |
| 주소 여러 개 등록 | 다중값 속성 분리, 기본 배송지 제약 |

정상 시나리오만 확인하면 삭제·이력·동시 유효성 같은 문제를 놓친다.

## 8. 반정규화 판단의 경계

반정규화는 정규화된 구조를 성능·가용성 등의 구체적 목표 때문에 의도적으로 중복·통합하는 물리적 선택이다. 다음 조건을 갖춘 뒤 검토한다.

- 실제 쿼리와 부하에서 병목이 측정되었다.
- 인덱스·쿼리 개선·캐시 등 대안을 평가했다.
- 중복 원천과 갱신 책임이 하나로 정해졌다.
- 불일치 탐지와 복구 방법이 있다.
- 쓰기 비용, 잠금, 저장공간과 운영 복잡성을 평가했다.
- 논리 모델과 물리 차이를 문서화했다.

정규화가 “좋음”, 반정규화가 “나쁨”이라는 가치 판단이 아니다. 논리 정확성과 물리 성능은 다른 단계의 목표이며, 반정규화에는 측정 가능한 근거와 일관성 통제가 필요하다.

## 9. 시험 함정

- 2NF를 “모든 비키 속성이 기본키 일부에 종속”이라고 반대로 설명한다.
- 기본키가 단일 속성인데 기본키 부분 종속을 찾는다.
- 3NF와 BCNF를 동일하다고 본다.
- BCNF 분해는 언제나 종속성까지 보존한다고 단정한다.
- 무손실 분해와 종속성 보존을 같은 개념으로 본다.
- 현재 데이터에서 우연히 성립한 패턴을 함수 종속으로 확정한다.
- 1NF의 원자성을 단순히 “문자열을 더는 자를 수 없음”으로 이해한다.
- 정규형 숫자가 높을수록 모든 시스템 성능이 자동으로 좋아진다고 본다.
- 품질검증을 명명 규칙 검사나 자동 도구 실행만으로 끝낸다.
- 대리키를 추가하면 후보키·업무상 유일 규칙 분석이 필요 없다고 본다.

## 10. 확인 문제

### 문제 1

관계 `수강(학생번호, 과목번호, 학생명, 성적)`의 후보키가 `(학생번호, 과목번호)`이고 `학생번호 → 학생명`이 성립한다. 학생명과 관련된 정규화 문제는 무엇인가?

1. 다치 종속
2. 복합키 일부에 대한 부분 함수 종속
3. 조인 종속
4. 함수 종속이 없음

### 문제 2

3NF와 BCNF의 결정자 조건 차이를 설명하라.

### 문제 3

무손실 분해와 종속성 보존이 서로 다른 이유를 설명하라.

### 문제 4

논리 데이터모델 품질검증에서 CRUD 매트릭스가 완전성 점검에 어떻게 도움이 되는가?

### 문제 5

정규화된 모델의 열을 두 테이블에 중복 저장하려 한다. 이를 승인하기 전에 확인해야 할 조건 세 가지를 적어라.

## 정답과 해설

1. **정답: 2번.** 학생명은 복합 후보키 전체가 아니라 학생번호 하나만으로 결정되므로 부분 함수 종속이며 2NF 분해 대상이 된다.
2. **정답:** 3NF는 모든 비자명 종속 `X → A`에서 X가 슈퍼키이거나 A가 후보키에 속하는 주요 속성이면 허용한다. BCNF는 더 엄격하게 모든 비자명 종속의 결정자 X가 슈퍼키여야 한다.
3. **정답:** 무손실은 분해 관계를 조인해 원래 튜플을 정확히 복원할 수 있는지에 관한 특성이다. 종속성 보존은 원래 제약을 분해 관계별 검사만으로 보장할 수 있는지에 관한 특성이다. 하나가 성립해도 다른 하나가 자동으로 성립하지 않는다.
4. **정답:** 기능별 생성·조회·변경·삭제 대상과 모델 개체를 대조하여 기능이 쓰는 데이터가 모델에 없는지, 아무 기능도 사용하지 않는 개체가 있는지 찾아 요구와 모델의 누락 후보를 드러낸다.
5. **정답 예:** 실제 성능 병목의 측정 근거, 중복 데이터의 단일 원천과 갱신 책임, 불일치 탐지·복구 방법을 확인한다. 쓰기·잠금·저장공간 영향과 다른 대안 평가도 필요하다.

## 11. 최종 요약

- **데이터베이스 정규화**는 함수 종속과 업무 규칙을 바탕으로 서로 다른 사실을 분리하여 삽입·수정·삭제 이상과 불필요한 중복을 줄이는 과정이다.
- 1NF는 원자값, 2NF는 복합 후보키에 대한 부분 종속 제거, 3NF는 비키 속성 사이의 이행 종속 제거, BCNF는 모든 결정자가 슈퍼키인지를 중심으로 판단한다.
- 4NF는 독립적인 다치 종속, 5NF는 조인 종속을 다룬다. 높은 정규형으로의 분해도 업무 규칙과 필요성을 근거로 한다.
- 분해할 때 원래 관계를 정확히 복원하는 무손실성과 원래 함수 종속을 분해 관계에서 검사 가능한 종속성 보존을 각각 확인한다.
- **논리 데이터모델 품질검증**은 완전성, 정확성, 일관성, 표준 준수, 최소성·비중복성, 추적성, 이해 가능성을 자동 점검과 업무 시나리오 검토로 확인한다.
- 모델의 함수 종속·키·관계는 현재 샘플의 우연이 아니라 모든 유효 상태에 적용되는 업무 규칙에서 도출한다.
- 반정규화는 정규화 오류를 숨기는 지름길이 아니라 실제 측정, 대안 비교, 갱신 책임과 불일치 통제를 갖춘 별도 물리 설계 결정이다.
