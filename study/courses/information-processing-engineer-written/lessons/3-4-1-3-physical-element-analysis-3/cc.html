01

0. 허가된 주체에게 필요한 범위만

데이터베이스 접근제어는 사용자·프로그램·관리자 같은 주체가 데이터와 관리 기능에 접근할 때 신원을 확인하고, 허가된 작업만 수행하게 하며, 그 결과를 추적하는 통제다. 계정과 비밀번호만 설정하거나 방화벽으로 포트를 제한하는 것으로 끝나지 않는다. 인증, 권한 결정, 정책 집행, 감사와 정기 검토가 함께 작동해야 한다.

이 레슨의 목표는 다음과 같다.

  1. 접근제어의 인증·인가·감사와 최소권한·직무분리 원리를 설명한다.
  2. 임의적·강제적·역할 기반 접근통제 모델의 차이를 구분한다.
  3. 계정·역할·권한·뷰·행·열 통제와 운영 절차를 데이터 민감도와 업무 책임에 맞춰 설계한다.
  4. 물리요소 조사 분석의 적용 절차와 판단 기준에 따라 스토리지·분산·이중화·암호화·접근제어를 통합적으로 조사하고 근거를 남긴다.

제품별 권한 이름과 지원 범위는 다를 수 있으므로 실제 적용에서는 공식 문서와 현행 설정을 확인한다.

02

1. 접근제어의 구성

1.1 식별·인증·인가·감사

1. 접근제어의 구성 · 학습 표 1
단계질문예시
식별누구라고 주장하는가?사용자 ID, 서비스 계정 ID
인증그 주장이 맞음을 어떻게 확인하는가?비밀번호, 인증서, 다요소 인증
인가무엇에 어떤 작업을 허용하는가?특정 뷰 SELECT, 프로시저 EXECUTE
감사누가 언제 무엇을 했는지 남는가?로그인·권한변경·민감조회 로그

인증에 성공했다고 모든 데이터 접근이 허용되는 것은 아니다. 인증은 신원 확인, 인가는 자원별 작업 허용이다. 감사는 사후 추적뿐 아니라 이상 접근 탐지와 책임성 확보에 사용한다.

1.2 접근 주체와 객체

  • 주체(subject): 사용자, 응용 서비스, 배치, 관리자, 외부 연계
  • 객체(object): 데이터베이스, 스키마, 테이블, 뷰, 칼럼, 행, 프로시저, 백업과 관리기능
  • 작업(action): 조회, 삽입, 변경, 삭제, 실행, 구조 변경, 권한 부여
  • 조건(context): 시간, 접속경로, 장치, 데이터 민감도, 업무 상태

권한 요구는 “시스템 접근”처럼 넓게 쓰지 않고 상담원 역할은 본인 담당 고객의 연락처를 조회하되 변경할 수 없다처럼 주체·객체·작업·조건으로 명확히 한다.

03

2. 접근통제 모델

2.1 임의적 접근통제(DAC)

객체 소유자 또는 권한을 가진 주체가 다른 사용자에게 접근권한을 부여·회수하는 방식이다. 유연한 공유가 가능하지만 권한이 연쇄적으로 퍼지거나 소유자의 판단에 따라 과도하게 부여될 위험이 있다.

2.2 강제적 접근통제(MAC)

주체의 인가 등급과 객체의 보안 등급처럼 중앙 정책에 따라 접근을 강제한다. 사용자가 임의로 등급 정책을 바꾸기 어렵고 엄격한 기밀성 통제가 필요한 환경에 적합할 수 있으나 운영과 분류가 복잡하다.

2.3 역할 기반 접근통제(RBAC)

사용자에게 개별 권한을 직접 많이 부여하지 않고 업무 역할에 권한을 묶어 사용자를 역할에 배정한다.

코드 예시 · text

사용자 → 역할 → 권한 → 데이터 객체·작업

입사·이동·퇴직 때 역할 배정만 변경해 관리 일관성을 높일 수 있다. 하지만 역할이 계속 늘어나는 역할 폭증, 이름만 다르고 권한이 같은 중복 역할, 개인 예외 권한이 쌓이는 문제를 주기적으로 정리해야 한다.

2.4 속성·규칙 기반 조건

현대 시스템은 역할뿐 아니라 부서, 데이터 소유자, 접속시간, 위치, 위험도 같은 속성과 규칙을 함께 적용할 수 있다. 제품·표준에 따라 명칭과 구현은 다르며, 복잡한 조건은 설명·시험·감사가 어려워질 수 있다.

2.5 모델 비교

2. 접근통제 모델 · 학습 표 2
모델권한 결정 중심강점주의점
DAC소유자의 재량유연한 공유권한 확산·일관성
MAC중앙 보안등급 정책강한 중앙 통제분류·운영 복잡도

현실에서는 여러 방식을 조합할 수 있다. 모델 명칭보다 실제 누가 권한을 결정·변경할 수 있고 어떤 정책이 강제되는지 확인한다.

04

3. 데이터베이스 접근제어 설계

3.1 최소권한과 기본 거부

업무 수행에 필요한 최소한의 객체와 작업만 허용하고, 명시적으로 허가되지 않은 접근은 거부한다. “나중에 필요할 수 있으니 전체 권한”은 위험하다. 조회·변경·구조 관리·권한 관리·백업 역할을 분리한다.

3.2 직무분리

한 사람이 개발, 운영 배포, 데이터 변경, 권한 부여와 감사로그 삭제를 모두 할 수 있으면 오류·부정행위를 예방·탐지하기 어렵다. 위험한 작업은 요청·승인·실행·검증 책임을 나누고 비상 권한은 시간 제한, 사유, 승인과 사후 검토를 둔다.

3.3 계정 유형 관리

  • 개인 계정: 사용자별 식별, 강한 인증, 역할 배정과 추적
  • 서비스 계정: 응용별 분리, 비대화형 사용, 비밀 회전과 최소권한
  • 관리자 계정: 일반 업무 계정과 분리, 강화 인증·감사
  • 비상 계정: 엄격한 보관·승인·사용 통보와 사후 검토

공용 계정은 책임 추적이 어렵다. 불가피한 시스템 계정도 사용 주체, 목적, 소유자, 만료·검토일과 비밀 관리 책임을 지정한다.

3.4 객체·행·열 수준 통제

  • 객체 권한: 테이블·뷰·프로시저에 조회·변경·실행 권한 부여
  • 뷰: 필요한 행·열만 노출하는 논리 인터페이스 제공
  • 저장 프로시저·API: 직접 테이블 변경 대신 검증된 작업만 허용
  • 행 수준 정책: 사용자·조직·소유 관계에 따라 보이는 행 제한
  • 열 수준 정책: 민감 칼럼 조회·변경을 별도 제한
  • 마스킹: 권한에 따라 값 일부를 가려 표시

뷰나 마스킹만으로 모든 우회 경로가 차단된다고 단정하지 않는다. 직접 객체 권한, 내보내기, 백업, 로그, 관리자 경로와 추론 가능성을 함께 점검한다.

3.5 권한 생명주기

  1. 업무 역할·데이터 분류에 따른 권한 요청
  2. 데이터 소유자와 책임자의 승인
  3. 최소권한으로 부여하고 시작·종료일 기록
  4. 권한 적용 결과 검증과 감사로그 확인
  5. 조직 이동·휴직·퇴직·계약 종료 시 즉시 변경·회수
  6. 정기 재인증으로 과도·미사용·충돌 권한 검토
  7. 예외·비상 권한의 만료와 사후 분석

권한을 한번 부여한 뒤 방치하면 직무 변경이 누적되어 권한 과잉이 발생한다. 역할과 실제 사용, 데이터 소유자의 재승인을 주기적으로 확인한다.

3.6 감사와 모니터링

감사 대상은 인증 성공·실패, 권한 부여·회수, 구조 변경, 민감 데이터 조회·변경, 대량 내보내기, 관리자·비상 작업 등 위험에 따라 정한다.

감사로그는 다음 조건을 고려한다.

  • 사용자·서비스 ID, 시각, 출발지, 객체, 작업, 결과와 추적 ID
  • 로그 자체의 무결성, 접근권한과 보존기간
  • DB 관리자도 임의 삭제·변조하기 어려운 분리 저장
  • 시간 동기화와 다른 시스템 로그의 상관분석
  • 이상 패턴 경보와 담당자 대응 절차
  • 개인정보 최소수집과 합법적 보존

모든 쿼리 전문을 무제한 기록하면 민감정보 유출과 성능·저장 비용이 커질 수 있다. 위험과 규정에 맞는 범위를 선택한다.

05

4. 물리요소 조사 분석의 적용 절차와 판단 기준

물리요소 조사 분석의 적용 절차와 판단 기준은 특정 장비 목록을 만드는 데 그치지 않고, 업무 요구와 현재 구성의 차이를 근거로 물리 설계 요소를 평가하는 것이다.

4.1 적용 절차

  1. 업무·품질 요구 수집: 데이터 중요도, 처리량, RPO·RTO, 보안·규제와 성장 전망을 확인한다.
  2. 범위·자산 식별: 데이터베이스, 스토리지, 복제·분산 노드, 네트워크, 키·계정과 백업을 목록화한다.
  3. 현행 구성 수집: 구성도, 용량, 성능, 장애·복구, 권한, 암호화와 운영 절차를 확인한다.
  4. 증거 교차검증: 문서와 실제 설정·로그·담당자 인터뷰·시험 결과를 대조한다.
  5. 요소별 적합성 분석: 용량, 성능, 가용성, 정합성, 보안, 운영·비용과 확장성을 평가한다.
  6. 단일 장애점·위험 식별: 공통 전원·네트워크·키 저장소·관리 계정과 수동 절차를 찾는다.
  7. 변경 영향·대안 비교: 요구 증가와 설계 후보의 효과·비용·위험·전환성을 비교한다.
  8. 검증계획 제시: 부하, 장애 전환, 복구, 암호화 성능, 권한 우회 시험을 정한다.
  9. 결론과 미확인 기록: 사실·가정·제약·의사결정과 책임자를 남긴다.

5. 적용 예시

상담 데이터베이스에서 상담원은 담당 고객의 연락처를 조회해야 하지만 주민 식별정보 전체는 볼 필요가 없다고 하자.

  • 상담원 역할에는 담당 고객 뷰의 조회와 승인된 프로시저 실행만 부여한다.
  • 민감 칼럼은 마스킹하고 업무상 전체값이 필요한 별도 역할은 추가 승인과 기간 제한을 둔다.
  • 응용 서비스 계정은 테이블 소유권과 권한 부여 권한을 갖지 않는다.
  • 대량 조회, 관리자 권한 변경과 마스킹 해제는 감사·경보한다.
  • 조직 이동 시 역할을 회수하고 분기별로 데이터 소유자가 권한을 재확인한다.

접근정책은 기능시험뿐 아니라 직접 객체 접근, 우회 뷰, 백업·내보내기와 비상권한 경로까지 시험한다.

07

6. 시험 함정

  1. 인증과 인가 혼동: 신원 확인과 작업 허용은 다른 단계다.
  2. 방화벽을 DB 접근제어로 충분하다고 판단: 접속 후 객체·행·열·작업 권한이 필요하다.
  3. DAC·MAC·RBAC 혼동: 소유자 재량, 중앙 등급정책, 업무 역할이 중심이다.
  4. 역할을 많이 만들수록 세밀함: 중복·예외가 늘면 역할 폭증과 관리 실패가 생긴다.
  5. 관리자에게 모든 권한 상시 부여: 일반·관리·비상 계정을 분리하고 감사한다.
  6. 뷰·마스킹만으로 우회 차단: 직접 권한, 내보내기, 백업과 관리자 경로를 확인한다.
  7. 감사로그에 모든 데이터 기록: 민감정보·성능·저장 위험을 고려해 범위를 정한다.
  8. 권한 부여 후 영구 유지: 이동·퇴직과 정기 재인증으로 회수한다.
  9. 물리요소를 제품 기능표로만 비교: 실제 부하·장애·복구·운영 시험과 필수조건으로 판단한다.

7. 확인 문제

문제 1

사용자 로그인 성공과 특정 테이블 조회 허용은 각각 무엇인가?

정답과 해설: 로그인으로 신원을 확인하는 것은 인증, 해당 테이블의 조회 권한을 결정하는 것은 인가다.

문제 2

업무 역할에 권한을 묶고 사용자를 역할에 배정하는 모델은?

정답과 해설: RBAC, 역할 기반 접근통제다. 역할 폭증과 개인 예외권한은 정기적으로 정리해야 한다.

문제 3

응용 서비스 계정에 테이블 소유권과 권한 부여 권한까지 주는 것이 위험한 이유는?

정답과 해설: 침해 또는 오류 시 피해 범위가 커지고 최소권한·직무분리가 무너진다. 필요한 조회·변경·실행 권한만 부여한다.

문제 4

문서상 이중화가 구성되어 있으면 RTO 충족으로 판단할 수 있는가?

정답과 해설: 없다. 실제 장애범위와 부하에서 감지·전환·재연결·데이터 검증까지 시험한 결과가 필요하다.

문제 5

물리요소 대안의 총점이 높지만 필수 보안 규정을 충족하지 못한다. 선택 가능한가?

정답과 해설: 필수조건이면 부적합하다. 가중 총점보다 규제·RPO·RTO 같은 통과 필수 기준을 먼저 적용해야 한다.

09

8. 최종 요약

  • 접근제어는 식별·인증·인가·감사로 주체의 데이터 작업을 정책에 따라 통제한다.
  • DAC는 소유자 재량, MAC은 중앙 등급정책, RBAC는 업무 역할을 중심으로 권한을 부여한다.
  • 최소권한, 기본 거부, 직무분리와 개인·서비스·관리·비상 계정의 생명주기를 관리한다.
  • 객체·뷰·프로시저·행·열 통제를 조합하고 우회 경로와 감사로그 자체도 보호한다.
  • 물리요소 조사 분석의 적용 절차와 판단 기준은 요구·자산·현행증거를 수집해 성능·용량·가용성·정합성·보안·운영·비용을 통합 평가한다.
  • 제품 기능표와 총점만 믿지 않고 필수조건, 실제 부하·장애·복구·보안 시험과 미확인 위험을 근거로 판단한다.
