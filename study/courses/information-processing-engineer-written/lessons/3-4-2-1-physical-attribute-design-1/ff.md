# 3-4-2-1. 파티셔닝 · 클러스터링

> **공식 범위**: 데이터베이스구축 > 물리 데이터베이스 설계 > 데이터베이스 물리속성 설계 > `파티셔닝`, `클러스터링`

## 0. 데이터의 물리 배치를 접근 패턴에 맞추기

데이터가 커질수록 모든 행을 한 물리 단위에 저장하고 전부 읽는 방식은 조회·유지보수·백업에 부담을 줄 수 있다. 물리 설계에서는 데이터를 규칙에 따라 나누거나 함께 자주 접근하는 행을 가깝게 배치해 불필요한 입출력을 줄인다.

이 레슨의 두 주제는 다음과 같다.

1. `파티셔닝`: 큰 테이블·인덱스를 파티션 키와 규칙에 따라 여러 물리 단위로 분할하되 논리적으로 하나처럼 사용한다.
2. `클러스터링`: 특정 키나 접근관계가 비슷한 행을 물리적으로 가깝게 배치하여 관련 데이터 접근의 지역성을 높인다.

여기서 클러스터링은 물리 데이터 배치 관점이다. 고가용성을 위한 서버 클러스터나 데이터베이스 이중화와 혼동하지 않는다. 제품별 구현·제약이 크게 다르므로 원리와 판단 기준을 먼저 이해한다.

---

## 1. 파티셔닝

### 1.1 목적과 효과

파티셔닝은 큰 객체를 관리 가능한 단위로 나누어 다음 효과를 기대한다.

- 조건에 맞는 파티션만 읽는 파티션 가지치기(pruning)
- 기간별 적재·삭제·보관과 유지보수 단위 축소
- 파티션별 병렬 처리와 저장장치 분산 가능성
- 장애·복구·백업 대상의 세분화
- 자주 쓰는 데이터와 오래된 데이터의 저장정책 분리

파티션 수가 많다고 자동으로 빨라지는 것은 아니다. 쿼리가 파티션 키 조건을 사용하지 않으면 여러 파티션을 모두 읽을 수 있고, 작은 파티션이 지나치게 많으면 메타데이터·계획·운영 비용이 증가한다.

### 1.2 수평·수직 분할 관점

- 수평 분할: 같은 칼럼 구조의 행을 조건에 따라 나눈다. 일반적인 테이블 파티셔닝은 이 관점이 중심이다.
- 수직 분할: 한 행의 칼럼들을 사용 패턴·보안·크기에 따라 나눈다. 원래 행을 재구성할 키와 조인이 필요하다.

수직 분할은 넓은 행에서 거의 사용하지 않는 대용량 칼럼을 분리할 수 있지만 조인이 늘고 원자적 변경이 복잡해질 수 있다. 이 레슨에서는 파티션 방식의 중심인 수평 분할을 자세히 본다.

### 1.3 대표 파티션 방식

| 방식 | 분할 기준 | 적합한 상황 | 주의점 |
|---|---|---|---|
| 범위(range) | 날짜·번호 구간 | 기간 조회·보관·삭제 | 경계 누락, 최신 구간 집중 |
| 목록(list) | 지역·상태 등 명시 값 집합 | 값 집합별 운영정책 | 새 값의 기본 처리 |
| 해시(hash) | 해시 함수 결과 | 데이터를 비교적 균등 분산 | 범위 조회와 위치 예측 어려움 |
| 복합(composite) | 범위+해시 등 단계 결합 | 기간 관리와 부하 분산 동시 요구 | 설계·운영 복잡도 증가 |

#### 범위 파티션 예

```text
orders_2026_q1: 2026-01-01 이상, 2026-04-01 미만
orders_2026_q2: 2026-04-01 이상, 2026-07-01 미만
```

상한을 미만으로 일관되게 정의하면 날짜·시간의 마지막 순간을 별도로 계산하는 오류를 줄일 수 있다. 새 기간 파티션 준비와 범위를 벗어난 값의 처리도 정한다.

#### 목록 파티션 예

지역 코드 `SEOUL`, `BUSAN`처럼 유한 값 집합을 나눌 수 있다. 값이 자주 추가되거나 잘못된 코드가 많으면 유지보수 부담과 데이터 라우팅 실패가 생길 수 있다.

#### 해시 파티션 예

고객 ID를 해시해 여러 파티션에 분산하면 특정 순번 범위에 쓰기가 몰리는 현상을 완화할 수 있다. 그러나 고객 ID 범위로 여러 파티션을 제거하기 어렵고 파티션 수 변경 시 데이터 재배치가 필요할 수 있다.

### 1.4 파티션 키 선정

좋은 파티션 키는 다음을 균형 있게 만족한다.

- 주요 쿼리의 필터 조건과 일치하여 가지치기가 가능한가?
- 값 분포가 한 파티션에 과도하게 치우치지 않는가?
- 데이터 적재·보관·삭제 단위와 맞는가?
- 키 값이 자주 변경되지 않는가?
- 조인 상대 테이블의 분할과 정렬할 수 있는가?
- 미래 데이터 증가와 파티션 수를 예측 가능한가?

날짜는 관리에 편리하지만 최신 파티션으로 쓰기가 몰릴 수 있다. 고객 ID는 분산에 유리할 수 있지만 기간 삭제가 어렵다. 복합 방식은 두 요구를 조합하지만 복잡도를 정당화할 근거가 필요하다.

### 1.5 인덱스와 제약

파티션별로 독립적으로 관리되는 인덱스와 전체 파티션을 포괄하는 인덱스는 유지보수·고유성·조회 범위의 장단점이 다를 수 있다. 구체 지원 명칭과 제약은 DBMS마다 다르므로 다음을 확인한다.

- 파티션 추가·교환·삭제 시 인덱스 유효성
- 고유키에 파티션 키 포함 요구 여부
- 통계정보 수집 범위와 실행계획
- 파티션 간 조인·집계와 병렬 처리
- 백업·복구·데이터 이동 중 가용성

## 2. 클러스터링

### 2.1 의미

`클러스터링`은 동일하거나 연관된 클러스터 키 값을 가진 행을 물리적으로 가까운 위치에 저장하여 함께 조회할 때 입출력 횟수를 줄이는 배치 기법이다. 한 테이블의 행 순서를 특정 키에 가깝게 유지하거나, 자주 조인하는 여러 테이블의 관련 행을 가까이 둘 수 있다. 실제 지원 형태와 유지방식은 DBMS마다 다르다.

예를 들어 주문 상세를 항상 주문 ID 단위로 조회한다면 같은 주문의 상세 행이 가까이 있을 때 적은 블록으로 읽을 가능성이 높다.

### 2.2 적합한 접근 패턴

- 같은 키 범위나 동일 키의 여러 행을 자주 함께 조회
- 읽기 비중이 높고 클러스터 키 값 변경이 드묾
- 관련 테이블을 같은 키로 반복 조인
- 반환 행이 충분히 많아 물리적 근접의 이득이 있음
- 데이터 분포와 키당 행 수가 비교적 예측 가능

단일 행을 고유키로만 조회한다면 일반 인덱스가 더 단순할 수 있다. 클러스터 키에 무관한 다양한 조건으로 조회하면 이득이 제한된다.

### 2.3 비용과 위험

- 삽입 위치를 맞추기 위한 탐색·페이지 분할과 이동 비용
- 클러스터 키 변경 시 행 재배치 비용
- 키 분포가 치우칠 때 일부 블록·영역 집중
- 시간이 지나 물리 순서가 흐트러지는 재구성 필요
- 다른 조회 순서에는 최적화되지 않는 단일 물리 배치
- 대량 적재·삭제·갱신과 동시성 영향

물리적 순서를 한번 만들었다고 영구 유지된다고 가정하지 않는다. 갱신 패턴과 재구성·통계 관리 비용을 운영 계획에 포함한다.

### 2.4 클러스터 키 선정

클러스터 키는 자주 함께 조회되는 행을 결정하면서 값이 안정적이고 분포가 과도하게 치우치지 않아야 한다. 키당 평균·최대 행 수, 블록 크기, 행 크기와 접근 빈도를 조사한다.

예:

```text
customer_id별 최근 주문 조회가 매우 빈번
→ customer_id를 기준으로 주문 행의 근접 배치 후보 검토

단, 특정 대형 고객에 주문이 집중
→ 키 편향과 블록 수, 대량 삽입 비용을 별도 측정
```

### 2.5 파티셔닝·클러스터링·인덱스 비교

| 기법 | 주 목적 | 선택 단위 | 대표 효과 |
|---|---|---|---|
| 파티셔닝 | 큰 객체의 분할·관리·가지치기 | 행 집합을 여러 파티션으로 | 읽을 파티션 축소, 관리 단위 분리 |
| 클러스터링 | 관련 행의 물리적 근접 | 클러스터 키 | 범위·동일키 접근의 블록 감소 |
| 인덱스 | 검색 경로 제공 | 키→행 위치 구조 | 전체 스캔 없이 대상 위치 탐색 |

세 기법은 함께 사용할 수 있지만 각각 저장공간, 쓰기·유지보수와 통계 비용을 추가한다. 읽기 성능만 보고 중복 적용하지 않는다.

## 3. 적용 절차

1. 업무 쿼리, 필터·조인·정렬, 데이터 증가와 보존정책을 수집한다.
2. 데이터 분포, 키별 행 수, 동시 읽기·쓰기와 시간대 부하를 측정한다.
3. 전체 스캔, 대량 유지보수, 랜덤 입출력 등 현재 병목을 확인한다.
4. 파티션·클러스터 후보 키와 대안을 만든다.
5. 데이터 균등성, 가지치기 가능성, 관리 주기와 변경 안정성을 평가한다.
6. 대표 데이터와 실제 쿼리로 실행계획·입출력·응답시간·처리량을 비교한다.
7. 삽입·갱신·삭제, 인덱스, 통계, 백업과 장애복구 비용을 시험한다.
8. 마이그레이션, 롤백, 신규 파티션과 재구성 운영절차를 수립한다.
9. 적용 후 데이터 편향, 파티션 크기와 계획 변화를 모니터링한다.

소량 시험 데이터에서 균등해 보이는 해시나 클러스터 키가 운영 데이터에서는 심하게 치우칠 수 있으므로 실제 분포를 반영한다.

## 4. 적용 예시

5년치 주문 20억 건을 보유하고 최근 3개월 조회와 월별 보관·삭제가 많다고 하자.

- 주문일 기준 월별 범위 파티션을 후보로 삼아 최근 기간 조회의 가지치기와 월 단위 보관을 지원한다.
- 최신 월의 쓰기 집중이 병목이면 범위 안에서 추가 분산이 필요한지 복합 파티션을 시험한다.
- 주문 상세는 주문 ID로 묶어 자주 조회하므로 같은 주문의 행을 근접 배치하는 클러스터링 후보를 검토한다.
- 적용 전후 핵심 조회의 읽은 블록, p95 응답시간, 적재 처리량, 파티션 유지보수 시간을 비교한다.

조회 한 건만 빨라졌다고 채택하지 않고 대량 적재, 마감 배치, 인덱스와 복구의 전체 비용을 평가한다.

## 5. 시험 함정

1. **파티션 수와 성능 비례**: 키 조건이 없으면 여러 파티션을 모두 읽고 관리비용만 늘 수 있다.
2. **범위·목록·해시 혼동**: 구간, 명시값 집합, 해시 결과를 기준으로 나눈다.
3. **해시 파티션이 범위 조회에 최적**: 균등 분산은 유리하지만 범위 가지치기는 제한될 수 있다.
4. **파티션 키를 자주 변경**: 행 이동과 인덱스·유지보수 비용이 커진다.
5. **클러스터링을 서버 이중화로 해석**: 이 레슨에서는 관련 행의 물리적 근접 배치다.
6. **클러스터링은 모든 조회에 유리**: 한 물리 순서는 다른 접근 패턴에 불리할 수 있다.
7. **클러스터링과 인덱스 동일시**: 근접 배치와 검색 경로라는 목적이 다르다.
8. **읽기 성능만 평가**: 쓰기, 재구성, 통계, 백업·복구와 운영 복잡도를 포함한다.
9. **시험 데이터 분포 무시**: 실제 키 편향과 증가 패턴을 반영해야 한다.

## 6. 확인 문제

### 문제 1

기간별 조회·삭제가 많은 테이블에 가장 먼저 검토할 파티션 방식은?

**정답과 해설**: 날짜를 기준으로 한 범위 파티션이 후보가 될 수 있다. 실제 필터 조건, 쓰기 집중과 데이터 분포를 시험해 결정한다.

### 문제 2

해시 파티셔닝의 주요 장점과 약점은?

**정답과 해설**: 데이터를 비교적 균등하게 분산할 수 있지만 키 범위 조회의 파티션 가지치기와 값의 물리 위치 예측은 어려울 수 있다.

### 문제 3

파티션 키 조건이 없는 쿼리는 항상 빨라지는가?

**정답과 해설**: 아니다. 여러 파티션을 모두 접근할 수 있어 가지치기 이득이 없고 계획·병렬·관리 오버헤드가 생길 수 있다.

### 문제 4

클러스터링이 적합한 데이터 접근은?

**정답과 해설**: 같은 키 또는 인접 범위의 여러 행을 자주 함께 읽고 키 변경이 드문 접근이다. 단일 고유행 조회나 다양한 무관 조건에는 이득이 작을 수 있다.

### 문제 5

클러스터링 적용 후 반드시 함께 측정할 쓰기 관점은?

**정답과 해설**: 삽입 위치 탐색, 페이지 분할·행 이동, 키 변경, 대량 적재와 재구성 비용을 확인한다.

## 7. 최종 요약

- `파티셔닝`은 큰 테이블·인덱스를 규칙에 따라 물리 단위로 나누어 가지치기, 관리·보관·병렬 처리 범위를 줄인다.
- 범위는 구간, 목록은 값 집합, 해시는 분산, 복합은 여러 목적 결합에 적합하지만 각각 비용이 있다.
- 파티션 키는 주요 필터, 데이터 균등성, 관리주기, 변경 안정성과 조인 관계를 기준으로 선택한다.
- `클러스터링`은 같은 키나 관련된 행을 물리적으로 가까이 배치해 동일키·범위 접근의 입출력을 줄인다.
- 클러스터링은 서버 고가용성 클러스터가 아니며 인덱스의 검색 경로와도 역할이 다르다.
- 읽기 성능뿐 아니라 쓰기, 인덱스, 통계, 재구성, 백업·복구와 운영비용을 대표 부하에서 비교한다.
