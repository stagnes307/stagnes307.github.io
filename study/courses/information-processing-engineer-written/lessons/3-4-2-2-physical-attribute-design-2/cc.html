01

0. 복구할 수 있고 성장할 수 있는 물리 설계

데이터베이스 물리속성 설계는 현재 데이터를 저장하는 것뿐 아니라 장애·오류 후 필요한 시점으로 복구하고, 보존기간 동안 증가할 데이터를 안정적으로 수용해야 한다. 백업이 존재해도 복구 목표와 시험이 없으면 사용할 수 없을 수 있고, 현재 크기만으로 공간을 잡으면 인덱스·로그·임시공간과 증가량 때문에 운영 중 부족해질 수 있다.

이 레슨의 목표는 다음과 같다.

  1. 데이터베이스 백업의 전체·차등·증분·로그, 물리·논리, 온라인·오프라인 방식의 목적과 복구 흐름을 구분한다.
  2. RPO·RTO, 보존, 장애범위, 정합성과 복구시험을 기준으로 백업전략을 설계한다.
  3. 테이블 저장 사이징에서 행 크기, 행 수·증가율, 인덱스, 저장 오버헤드, 여유공간과 보존정책을 계산한다.
  4. 추정치의 가정과 단위를 명시하고 운영 관측값으로 주기적으로 보정한다.

구체적인 백업 명령, 압축률과 블록 오버헤드는 DBMS 제품·버전·데이터에 따라 달라질 수 있으므로 실제 환경에서 검증한다.

02

1. 데이터베이스 백업

1.1 백업의 목적

데이터베이스 백업은 장애, 손상, 잘못된 변경, 재해 등이 발생했을 때 데이터를 합의된 시점과 시간 안에 복원하기 위해 독립된 복구본과 관련 정보를 만드는 활동이다.

백업전략의 핵심 질문:

  • 무엇을 보호하는가? 데이터, 로그, 설정, 키, 사용자 정의와 메타데이터
  • 어떤 사고에서 복구하는가? 장비 장애, 논리 오류, 삭제, 랜섬웨어, 센터 손실
  • 어느 시점까지 복구해야 하는가? RPO
  • 얼마나 빨리 복구해야 하는가? RTO
  • 어디에 얼마나 오래 보관하는가?
  • 누가 백업·복구에 접근하고 변경할 수 있는가?
  • 실제 복구에 필요한 순서와 의존성이 검증되었는가?

1.2 전체·차등·증분 백업

1. 데이터베이스 백업 · 학습 표 1
방식포함 범위장점복구·운영 고려
전체(full)대상 전체복구 기준이 단순시간·공간·부하 큼
차등(differential)마지막 전체 백업 이후 변경증분보다 복구 세트가 단순할 수 있음다음 전체 전까지 크기 증가
증분(incremental)마지막 백업 이후 변경각 백업량과 시간이 작음여러 증분 순서·무결성 필요

복구 예:

코드 예시 · text

차등: 일요일 전체 + 가장 최근 차등
증분: 일요일 전체 + 이후 필요한 증분들을 순서대로

정확한 구현은 제품에 따라 다를 수 있다. “차등은 누적, 증분은 직전 이후”라는 기본 차이와 복구 체인의 길이를 이해한다.

1.3 로그 백업과 시점 복구

트랜잭션 로그 또는 변경 기록을 연속 보존하면 전체·증분 백업 사이의 특정 시점으로 복구할 수 있다. 일반 흐름은 기준 백업 복원→후속 백업 적용→로그를 목표 시점 직전까지 적용하는 방식이다.

다음이 필요하다.

  • 로그 체인이 끊기지 않는 수집·보관
  • 백업과 로그의 시작·종료 위치·순서 식별
  • 목표 시점, 시간대와 장애 시각의 정확한 판단
  • 잘못된 변경 이후 로그를 적용하지 않는 기준
  • 복구 중 쓰기 차단과 최종 일관성 확인

로그가 있다고 모든 업무 부수효과까지 되돌리는 것은 아니다. 데이터베이스 밖으로 전송된 결제·알림·파일 등은 별도 보상과 대조가 필요하다.

1.4 물리 백업과 논리 백업

  • 물리 백업: 데이터 파일·로그·제어정보 등 저장 구조를 복제한다. 대용량 전체 복구에 효율적일 수 있으나 제품·버전·플랫폼 의존성이 있을 수 있다.
  • 논리 백업: 테이블·스키마·행·정의 같은 논리 객체를 내보낸다. 선택적 이관·복원과 확인에 유용할 수 있으나 대용량 복구시간과 객체 순서·권한을 고려한다.

둘은 목적이 다르며 함께 사용할 수 있다. 논리 내보내기 파일 한 개를 전체 재해복구 전략으로 간주하지 않는다.

1.5 온라인·오프라인 백업

오프라인(콜드) 백업은 데이터베이스를 정지하거나 쓰기를 중단해 일관된 상태를 복사하기 쉬울 수 있지만 서비스 중단이 필요하다. 온라인(핫) 백업은 서비스를 운영하며 수행하지만 백업 중 변경을 일관되게 복구하기 위한 로그와 제품 기능이 필요하다.

온라인 백업이라는 이유로 업무 부하 영향이 없는 것은 아니다. 저장 I/O, 네트워크, CPU와 로그 증가를 대표 부하에서 측정하고 일정·속도 제한을 조정한다.

1.6 백업 보관과 보안

  • 운영 데이터와 다른 장애영역에 복사본을 둔다.
  • 최소 하나의 복구본은 운영 계정 침해와 동시 삭제에 견디도록 격리·불변성을 고려한다.
  • 전송·저장 암호화와 키 분리·복구를 관리한다.
  • 백업 접근·삭제·복원 권한을 분리하고 감사한다.
  • 보존기간, 법적 보류, 만료와 안전한 폐기를 정의한다.
  • 개인정보가 든 백업의 사용·복제·시험 환경 반입을 통제한다.
  • 체크섬과 카탈로그로 손상·누락을 확인한다.

“3-2-1 규칙”처럼 여러 매체·위치에 복사본을 두는 원칙이 활용되기도 하지만 조직의 재해·위협·규제와 클라우드 구조에 맞게 구체화해야 한다.

1.7 복구시험

백업 작업 성공 메시지는 복구 성공의 증거가 아니다. 정기적으로 다음을 시험한다.

  1. 실제 권한과 문서만으로 담당자가 복구할 수 있는가?
  2. 전체·차등·증분·로그 체인이 모두 존재하고 순서가 맞는가?
  3. 암호화 키, 설정, 사용자·권한과 외부 의존을 복구할 수 있는가?
  4. 목표 시점과 RTO 안에 복구되는가?
  5. 행 수·합계·무결성, 핵심 트랜잭션과 응용 연결이 정상인가?
  6. 운영 복구 중 기존 데이터와 충돌·덮어쓰기 위험은 통제되는가?

복구시험 결과의 실제 소요시간과 병목을 다음 사이징·전략에 반영한다.

2. 테이블 저장 사이징

2.1 사이징의 구성

테이블 저장 사이징은 예상 행 수와 행당 저장크기를 바탕으로 테이블, 인덱스, 저장 오버헤드, 성장과 운영 여유를 추정하는 작업이다.

코드 예시 · text

테이블 공간
≈ 평균 행 크기 × 예상 행 수
  + 블록·행·가변길이 오버헤드
  + 갱신·공간 재사용 여유

전체 데이터 영역
≈ 테이블 + 인덱스 + 대형객체 + 여유·성장

로그, 임시공간, 백업, 복제본과 아카이브는 테이블 영역과 별도로 산정한 뒤 전체 저장계획에 합친다.

2.2 평균 행 크기 추정

  • 고정길이 타입의 저장바이트
  • 가변길이 칼럼의 평균·상위 크기와 길이표시 오버헤드
  • NULL 비율과 NULL 비트맵·행 헤더
  • 문자 인코딩에 따른 문자당 바이트 변화
  • 숫자의 정밀도, 날짜·시간과 식별자 저장형식
  • 행 외부에 저장되는 대형객체 포인터와 실제 영역
  • 압축 가능성과 사전·메타데이터 비용

문자 VARCHAR(100)의 최대 길이를 모든 행에 곱하면 과대 추정할 수 있고, 현재 평균만 사용하면 긴 값이 늘어날 때 부족할 수 있다. 실제 분포와 상위 백분위, 업무 최대를 함께 본다.

2.3 행 수와 성장

코드 예시 · text

예상 행 수
= 현재 행 수
+ 기간별 신규 행
− 보존기간 내 삭제·아카이브 행
+ 실패 재처리·이력·중복 허용분

월평균 증가만 보지 않고 성수기, 사업 성장, 정책 변경과 데이터 보존연장을 고려한다. 삭제한다고 파일이 즉시 줄어드는지, 공간이 내부에서 재사용되는지는 DBMS와 운영 방식에 따라 확인한다.

2.4 간단한 계산 예

평균 행 크기를 헤더·가변 오버헤드 포함 220바이트, 현재 1억 행, 연 4천만 행 증가, 3년 보존 계획이라고 하자.

코드 예시 · text

3년 후 예상 행 수 = 1억 + (4천만 × 3) = 2억 2천만 행
테이블 원시 추정 = 220 × 220,000,000
                  = 48.4GB (10진 단위 단순 계산)
인덱스 추정 40% = 약 19.4GB
소계             = 약 67.8GB
운영·성장 여유 30%를 단순 적용하면 약 88GB

이는 예시일 뿐이다. 실제로는 블록 채움률, 삭제·갱신, 압축, 파티션, 인덱스 종류·키 폭, 문자집합과 제품 오버헤드를 측정해야 한다. 임시·로그·백업 공간은 별도다.

2.5 인덱스·대형객체·로그

  • 인덱스: 키 길이, 행 식별자, 엔트리 수, 트리·페이지 오버헤드, 채움률과 여러 인덱스 합계
  • 대형객체: 본문과 메타데이터, 행 내부·외부 저장, 압축·중복제거
  • 트랜잭션 로그: 변경량, 최대 트랜잭션, 백업주기, 복제지연과 체크포인트
  • 임시공간: 정렬·해시·인덱스 생성·대량 작업의 최고 동시 사용량
  • 아카이브: 보존 위치, 검색 요구, 압축과 복구 시간
  • 백업: 전체·증분 크기, 보존 세트, 압축률과 복사본 수

운영 용량은 데이터 파일만 더한 값보다 훨씬 클 수 있다.

2.6 사이징 절차와 보정

  1. 업무량, 보존기간, 성장 시나리오와 목표기간을 확정한다.
  2. 테이블별 현재 행 수, 증가·삭제율과 데이터 분포를 수집한다.
  3. 칼럼 타입·평균 길이·NULL·대형객체로 평균 행 크기를 측정한다.
  4. 인덱스, 파티션, 압축과 저장 오버헤드를 반영한다.
  5. 로그·임시·백업·복제·아카이브 공간을 별도 산정한다.
  6. 성수기·사업 확장·정책 변경의 기준·상·하 시나리오를 만든다.
  7. 실제 시험 적재로 예상값과 물리 사용량을 비교한다.
  8. 경보 임계값, 증설 조달시간과 운영 여유를 정한다.
  9. 매월·분기 관측값으로 증가율과 압축률을 보정한다.

가정, 단위(GB/GiB), 기준일과 포함·제외 항목을 문서화해야 추정치를 해석할 수 있다.

04

3. 백업과 사이징의 연결

데이터 증가가 두 배가 되면 운영 저장공간뿐 아니라 전체 백업시간, 네트워크 전송, 보존공간과 복구시간도 늘 수 있다. 저장 사이징 결과를 RTO와 비교한다.

예를 들어 전체 백업 복원 처리량이 시간당 2TB이고 데이터 세트가 10TB라면 파일 복원만 최소 5시간 수준이다. 로그 적용, 검증, 응용 연결을 더하면 RTO 4시간을 충족하기 어렵다. 파티션 단위 복구, 병렬 처리, 백업 방식과 시스템 구성을 재검토해야 한다.

4. 시험 함정

  1. 백업 성공과 복구 가능 동일시: 실제 복원·검증 시험이 필요하다.
  2. 차등·증분 혼동: 차등은 마지막 전체 이후 누적, 증분은 마지막 백업 이후 변경이 기본이다.
  3. 이중화로 백업 대체: 논리 오류·삭제·악성 변경도 복제될 수 있다.
  4. 온라인 백업은 무부하: I/O·CPU·로그와 업무 성능에 영향을 줄 수 있다.
  5. RPO와 RTO 혼동: 허용 데이터 손실 시점과 허용 복구시간이다.
  6. 백업 파일만 보호: 키·카탈로그·설정·권한과 복구 절차도 필요하다.
  7. 최대 문자열 길이를 평균으로 계산: 실제 분포와 상위값을 사용하되 업무 최대도 확인한다.
  8. 테이블 데이터만 사이징: 인덱스·로그·임시·백업·복제·여유공간을 포함한다.
  9. 평균 성장률만 사용: 성수기·정책·보존 변경과 증설 소요시간을 반영한다.

5. 확인 문제

문제 1

마지막 전체 백업 이후 모든 변경을 누적하는 백업은?

정답과 해설: 차등 백업이다. 복구에는 보통 전체 백업과 가장 최근 차등 백업을 사용한다.

문제 2

RPO 10분은 무엇을 뜻하는가?

정답과 해설: 장애 시 업무가 허용하는 데이터 손실 시점의 최대 범위가 약 10분이라는 의미다. 실제 정의와 산정 기준은 업무 합의로 명확히 한다.

문제 3

백업 작업이 매일 성공했지만 복구시험을 한 적이 없다. 주요 위험은?

정답과 해설: 파일 손상, 로그 체인 누락, 키·설정 부재와 절차 오류로 실제 복구가 불가능하거나 RTO를 넘을 수 있다.

문제 4

테이블 원시 데이터가 100GB라면 저장장치 100GB면 충분한가?

정답과 해설: 아니다. 행·블록 오버헤드, 인덱스, 증가·갱신 여유, 로그·임시공간, 백업·복제와 증설시간을 포함해야 한다.

문제 5

사이징 문서에 GB만 적고 10진·2진 단위를 명시하지 않으면 어떤 문제가 있는가?

정답과 해설: 도구·공급자마다 GB와 GiB 해석이 달라 용량 차이가 생길 수 있다. 단위, 기준일, 가정과 포함 범위를 기록한다.

6. 최종 요약

  • 데이터베이스 백업은 RPO·RTO와 장애범위에 맞춰 전체·차등·증분·로그, 물리·논리, 온라인·오프라인 방식을 조합한다.
  • 차등은 마지막 전체 이후 누적, 증분은 마지막 백업 이후 변경이며 복구 체인의 차이를 이해한다.
  • 운영과 다른 장애영역의 보호된 복구본, 키·카탈로그·설정과 정기 복구시험이 필요하다.
  • 테이블 저장 사이징은 평균 행 크기×예상 행 수에 저장 오버헤드, 인덱스, 성장과 운영 여유를 더한다.
  • 로그·임시·대형객체·백업·복제·아카이브 공간은 별도로 산정해 전체 계획에 반영한다.
  • 가정·단위·보존·성장 시나리오를 명시하고 실제 적재·운영 관측으로 지속 보정한다.
  • 데이터 증가가 백업·복구시간에도 미치는 영향을 계산해 용량과 RTO를 함께 설계한다.
