# 3-4-3-1. 데이터베이스 무결성 · 칼럼 속성

## 학습 범위

이 레슨의 핵심 토픽은 **데이터베이스 무결성**과 **칼럼 속성**이다. 논리 데이터 모델에서 정의한 업무 규칙을 실제 테이블의 칼럼, 자료형, 널 허용 여부, 기본값, 제약조건으로 옮기는 방법을 다룬다. 키의 세부 종류와 반정규화 설계는 다음 레슨의 범위이므로, 여기서는 무결성을 구현하는 데 필요한 기본 키·외래 키 제약의 역할까지만 살펴본다.

학습 목표는 다음과 같다.

1. 무결성이 무엇이며 왜 애플리케이션 코드만으로 보장하기 어려운지 설명한다.
2. 개체, 참조, 도메인, 사용자 정의 무결성을 구분한다.
3. 칼럼의 자료형, 길이, 정밀도, 널 허용 여부, 기본값 같은 물리 속성을 업무 의미에 맞게 결정한다.
4. 데이터 프로파일링 결과를 바탕으로 논리 속성을 물리 칼럼으로 변환하고 검증한다.

## 1. 데이터베이스 무결성의 뜻과 원리

데이터베이스 무결성은 저장된 데이터가 정해진 규칙에 맞아 정확성, 일관성, 유효성을 유지하는 성질이다. 단순히 “오류가 없는 값”만을 뜻하지 않는다. 주문 번호가 중복되지 않아야 한다는 규칙, 존재하지 않는 고객을 주문이 참조해서는 안 된다는 규칙, 주문 수량은 1 이상이어야 한다는 규칙처럼 데이터 사이의 관계와 업무 의미까지 포함한다.

무결성 규칙은 가능한 한 데이터가 저장되는 지점에 선언하는 것이 중요하다. 여러 화면, 배치 프로그램, 외부 연계가 같은 테이블을 갱신할 때 각 프로그램의 검사 로직이 조금씩 다르면 우회 경로가 생긴다. 데이터베이스 제약조건은 어느 경로에서 입력하더라도 공통 규칙을 적용한다. 다만 복잡한 승인 절차나 여러 시점의 상태를 비교해야 하는 규칙은 제약조건만으로 표현하기 어려울 수 있다. 이때도 데이터베이스 제약조건과 트랜잭션, 애플리케이션 검증을 상호 보완적으로 사용해야 한다.

무결성은 트랜잭션과도 연결된다. 하나의 업무가 여러 테이블을 바꿀 때 일부만 반영되면 각각의 칼럼 값은 유효해 보여도 전체 업무 상태는 불일치한다. 원자성을 갖춘 트랜잭션으로 관련 변경을 한 묶음으로 처리하고, 동시 갱신에서는 적절한 격리와 충돌 처리를 사용해야 한다. 즉 제약조건은 값과 관계의 규칙을, 트랜잭션은 변경 단위의 일관성을 지킨다.

## 2. 무결성의 주요 유형

### 2.1 개체 무결성

개체 무결성은 테이블의 각 행을 다른 행과 구별할 수 있어야 한다는 원칙이다. 기본 키 값은 행을 유일하게 식별해야 하므로 중복될 수 없고 널이 될 수 없다. 예를 들어 고객 테이블의 고객번호가 기본 키라면 두 고객이 같은 고객번호를 가져서는 안 되며, 고객번호를 알 수 없는 행도 저장해서는 안 된다.

UNIQUE 제약도 값의 중복을 제한하지만 기본 키와 완전히 같다고 단정하면 안 된다. 기본 키는 테이블의 대표 식별자이고 널을 허용하지 않는다. UNIQUE의 널 처리 방식과 허용 개수는 데이터베이스 제품별 세부 동작을 확인해야 한다. 시험에서는 “기본 키는 유일성과 최소 식별성을 갖고 널이 아니다”라는 핵심을 먼저 잡는다.

### 2.2 참조 무결성

참조 무결성은 외래 키 값이 참조 대상의 유효한 키 값과 일치하거나, 업무 규칙상 허용될 때 널이어야 한다는 원칙이다. 주문의 고객번호가 고객 테이블을 참조한다면 존재하지 않는 고객번호로 주문을 만들 수 없다. 부모 행을 삭제하거나 식별 값을 바꾸면 자식 행에 미치는 영향도 설계해야 한다.

삭제·갱신 시 동작에는 일반적으로 제한, 연쇄 처리, 널 설정 같은 선택지가 있다. 어떤 선택이 항상 옳은 것은 아니다. 결제 이력이 있는 주문 고객을 함께 삭제하는 연쇄 처리는 감사와 보존 규칙을 위반할 수 있다. 반대로 임시 상세 행처럼 부모 없이 의미가 없는 데이터는 부모 삭제와 함께 제거하는 것이 자연스러울 수 있다. 제품이 지원하는 구문보다 먼저 업무 생명주기를 판단해야 한다.

### 2.3 도메인 무결성

도메인 무결성은 한 칼럼에 들어갈 수 있는 값의 범위와 형식을 제한한다. 자료형, 길이, 정밀도, 널 허용 여부, CHECK 제약 등이 이에 해당한다. 주문수량이 양의 정수여야 하고, 주문상태가 준비·결제·배송·취소 중 하나여야 하며, 할인율이 정해진 범위 안에 있어야 한다는 규칙이 예다.

자료형만 맞는다고 도메인 무결성이 완성되지는 않는다. 정수형 칼럼은 음수도 저장할 수 있으므로 수량이 1 이상이라는 조건은 별도의 제약이 필요하다. 반대로 값 목록이 자주 변경되고 설명, 사용 기간 등 속성을 가진다면 긴 CHECK 식보다 코드 테이블과 참조 제약이 더 관리하기 쉬울 수 있다.

### 2.4 사용자 정의 무결성

사용자 정의 무결성은 특정 조직과 업무에서만 성립하는 규칙이다. “배송 완료 시 배송완료일은 반드시 존재한다”, “대출 종료일은 시작일보다 빠를 수 없다”, “승인 금액은 신청 금액을 초과할 수 없다” 같은 조건이 해당한다. 한 행 안의 단순 비교는 CHECK로 표현할 수 있지만 여러 행의 합계, 다른 시점의 상태, 외부 시스템 값까지 포함하면 트랜잭션 로직이나 별도의 검증 절차가 필요할 수 있다.

무결성 유형은 배타적인 상자가 아니다. 외래 키는 참조 무결성을 구현하면서 해당 칼럼의 값 영역도 제한한다. 시험 문제에서는 규칙이 무엇을 보호하는지에 초점을 맞춘다. 행의 식별이면 개체, 테이블 사이의 참조이면 참조, 값 자체의 형식·범위이면 도메인, 업무 고유 조건이면 사용자 정의 무결성이다.

## 3. 무결성을 구현하는 제약조건

- NOT NULL은 값의 부재를 허용하지 않는다. 필수 업무 속성에 적용하되, 아직 알 수 없는 값을 빈 문자열이나 0으로 대신 넣게 만들면 의미가 왜곡될 수 있다.
- PRIMARY KEY는 행을 대표해 식별하며 유일성과 비널 조건을 함께 요구한다.
- UNIQUE는 후보 값의 중복을 제한한다. 널 처리 세부 규칙은 제품에 따라 확인한다.
- FOREIGN KEY는 자식 값이 부모의 참조 가능한 키에 대응하도록 한다. 자식 쪽에 같은 외래 키 값이 여러 번 나타나는 것은 보통 허용된다.
- CHECK는 한 값 또는 같은 행의 값 사이 조건을 선언한다. 지원 가능한 표현 범위는 제품마다 다를 수 있다.
- DEFAULT는 입력값이 생략될 때 사용할 값을 제공한다. DEFAULT 자체는 입력된 값의 유효성을 검사하는 제약이 아니다.

제약조건에는 사람이 이해할 수 있는 이름을 부여하는 편이 좋다. 오류가 발생했을 때 어느 규칙이 위반되었는지 찾기 쉽고, 변경·배포 이력을 관리하기도 편하다. 대량 적재를 위해 제약을 임시로 해제했다면 적재 후 기존 행까지 검증해야 한다. 제약을 다시 활성화했다는 사실만으로 과거에 들어온 모든 행이 검증되었다고 가정해서는 안 된다.

## 4. 칼럼 속성의 구성 요소

칼럼 속성은 논리 속성을 물리적으로 저장하고 해석하기 위한 세부 정의다. 핵심 요소는 이름, 자료형, 길이 또는 정밀도, 널 허용 여부, 기본값, 제약조건이다. 문자 데이터에서는 문자 집합과 정렬 규칙, 시간 데이터에서는 시간대 처리 원칙, 자동 생성 값에서는 생성 주체와 변경 규칙도 검토한다.

### 4.1 자료형과 길이

자료형은 표현할 값과 수행할 연산을 기준으로 고른다. 숫자처럼 보이는 값이라도 계산하지 않고 앞자리 0을 보존해야 하는 우편번호·상품코드는 문자형이 적합하다. 금액처럼 정확한 십진 연산이 필요한 값은 고정 정밀 숫자형을 우선 검토하고, 측정치처럼 근삿값을 다루는 경우 부동소수점형을 검토한다. 날짜를 문자열로 저장하면 달력 연산, 정렬, 유효성 검사가 어려우므로 날짜·시간 의미에 맞는 형을 사용한다.

고정 길이 문자형은 값의 길이가 거의 일정할 때 단순한 구조를 제공하고, 가변 길이 문자형은 길이 편차가 큰 값의 불필요한 공간을 줄일 수 있다. 그러나 실제 저장 오버헤드와 비교 방식은 제품별로 다르다. “항상 CHAR가 빠르다” 또는 “항상 VARCHAR가 작다” 같은 절대적인 결론보다 데이터 분포와 사용 제품을 확인하는 것이 안전하다.

정밀도와 스케일은 소수 값을 설계할 때 중요하다. 정밀도는 표현 가능한 전체 유효 자릿수, 스케일은 소수점 이하 자릿수를 의미하는 방식으로 쓰인다. 세율, 환율, 금액을 같은 규칙으로 정의하면 반올림 위치가 흔들리지 않는다. 예상 최대값과 법적·업무상 필요한 소수 자릿수를 계산한 뒤 여유 범위를 정한다.

### 4.2 NULL, 빈 값, 기본값

NULL은 값이 0이라는 뜻도, 빈 문자열이라는 뜻도 아니다. 값이 없거나 알 수 없음을 나타내는 표지다. SQL의 비교에서는 미확정 논리가 적용되므로 “칼럼 = NULL” 같은 일반 비교가 아니라 널 여부를 검사하는 표현을 사용한다. 집계 함수가 널을 처리하는 방식도 함수별로 확인해야 한다.

필수 속성에는 NOT NULL을 적용할 수 있지만, 현실에서 아직 수집되지 않은 값을 억지 기본값으로 채우면 품질이 오히려 나빠진다. 예를 들어 미정인 탈퇴일을 특정 과거 날짜로 채우면 실제 날짜와 구별할 수 없다. 기본값은 “생략 시에도 업무 의미가 확정되는 값”일 때 사용한다. 생성 시각, 초기 상태처럼 명확한 경우가 대표적이며, 기본값의 생성 위치가 데이터베이스인지 애플리케이션인지도 일관되게 정한다.

### 4.3 문자 집합, 정렬, 시간

문자 집합은 표현 가능한 문자와 저장 크기에 영향을 준다. 다국어 이름과 기호를 저장해야 한다면 실제 입력 범위를 포함하는 문자 집합을 선택한다. 정렬 규칙은 대소문자, 악센트, 언어별 순서의 비교 결과에 영향을 줄 수 있으므로 유일성 판단에도 연결된다. 시간 값은 단순한 지역 시각인지, 전 세계에서 동일한 순간인지, 날짜만 필요한지 구분하고 변환 기준을 문서화한다. 세부 형식과 지원 기능은 데이터베이스 제품 버전에 의존할 수 있으므로 공식 문서를 확인한다.

## 5. 논리 속성을 물리 칼럼으로 옮기는 절차

1. **업무 의미 확인**: 속성의 정의, 필수 여부, 값의 단위, 생성·변경 주체, 보존 기간을 확인한다.
2. **실데이터 프로파일링**: 최소·최대값, 최대 길이, 널 비율, 고유값 수, 형식 위반, 이상치를 조사한다. 표본만 보면 드문 긴 값이나 과거 예외를 놓칠 수 있다.
3. **자료형 매핑**: 값 영역과 필요한 연산에 맞는 자료형, 길이, 정밀도, 스케일을 정한다.
4. **무결성 규칙 선언**: 필수값, 유일성, 참조 관계, 허용 범위를 제약조건으로 변환한다. 표현하기 어려운 규칙은 적용 계층과 검증 책임을 기록한다.
5. **기본값과 생성 규칙 결정**: 값이 생략되었을 때의 의미와 데이터베이스·응용 프로그램 중 생성 책임을 정한다.
6. **이행 가능성 검증**: 기존 데이터가 새 속성과 제약을 통과하는지 검사하고 정제 또는 예외 처리 계획을 세운다.
7. **성능과 운영 검증**: 예상 행 수와 인덱스, 조인, 정렬, 변경 빈도를 고려해 저장량과 실행 계획을 확인한다.
8. **문서화와 테스트**: 칼럼 사전, 제약 이름, 단위, 예시 값을 남기고 경계값·널·중복·잘못된 참조를 시험한다.

## 6. 적용 예시

주문 테이블에 주문번호, 고객번호, 주문수량, 단가, 주문상태, 주문일시를 정의한다고 하자.

- 주문번호는 행의 대표 식별자이므로 기본 키와 비널 조건을 갖는다.
- 고객번호는 고객 테이블의 유효한 고객을 참조한다. 비회원 주문을 허용하는 업무라면 널 허용 또는 별도 비회원 식별 정책을 먼저 정해야 한다.
- 주문수량은 정수형으로 정의하되 1 이상이라는 CHECK 규칙을 추가한다.
- 단가는 정확한 십진 계산이 가능한 형과 필요한 정밀도·스케일을 사용하고 음수 허용 여부를 규정한다.
- 주문상태는 허용 목록이 작고 고정적이면 CHECK를, 설명과 전이 규칙을 가진 관리 대상이면 코드 테이블을 검토한다.
- 주문일시는 주문이 발생한 순간을 표현할 형과 시간대 기준을 정하고, 생성 주체가 중복되지 않게 한다.

이 설계에서 애플리케이션 화면의 입력 제한은 사용자 편의를 높이지만 데이터베이스 제약을 대체하지 않는다. 배치 적재나 다른 API는 화면 검사를 통과하지 않을 수 있기 때문이다. 반대로 제약조건 오류만 사용자에게 그대로 노출하면 어떤 값을 고쳐야 하는지 알기 어려우므로 애플리케이션에서도 친절한 사전 검증과 오류 해석이 필요하다.

## 7. 절차와 선택지 비교

| 판단 대상 | 선택 기준 | 잘못된 단순화 |
|---|---|---|
| 제약조건과 프로그램 검사 | 공통·항상 성립하는 규칙은 DB에 선언하고, 복합 업무 흐름은 트랜잭션 로직과 병행 | 프로그램에서 검사하므로 DB 제약은 불필요하다 |
| 숫자형과 문자형 | 계산·범위 연산 여부, 앞자리 0 보존, 형식 의미 | 숫자로만 보이면 모두 숫자형이다 |
| 정확 숫자와 근사 숫자 | 금액·비율의 정확성 요구와 측정 오차 허용 여부 | 저장 공간만 보고 결정한다 |
| NULL과 기본값 | 실제로 값이 없거나 모르는지, 생략 시 의미가 확정되는지 | 미정 값을 0이나 빈 문자열로 채운다 |
| CHECK와 코드 테이블 | 값 목록의 변경 빈도, 추가 속성·관계·운영 관리 필요성 | 허용값은 언제나 CHECK 하나로 해결한다 |
| 삭제 제한과 연쇄 삭제 | 부모·자식의 생명주기, 감사·보존·복구 요구 | 편의를 위해 무조건 연쇄 삭제한다 |

## 8. 시험 함정

1. 개체 무결성과 참조 무결성을 바꾸어 외우기 쉽다. 행 자체의 식별은 개체, 테이블 사이의 올바른 연결은 참조 무결성이다.
2. 외래 키 값은 유일해야 한다는 설명은 틀리다. 여러 주문이 한 고객을 참조할 수 있다.
3. DEFAULT는 유효성 검사 규칙이 아니다. 생략된 값의 초기값을 제공할 뿐, 명시적으로 잘못 입력한 값을 막지는 않는다.
4. NULL을 0 또는 빈 문자열과 같다고 보면 안 된다. 의미와 비교 규칙이 다르다.
5. 자료형이 정수라고 해서 양수만 허용되는 것은 아니다. 업무 범위는 별도의 제약으로 표현한다.
6. 기본 키는 널을 허용하지 않는다. UNIQUE 제약의 널 세부 동작을 기본 키와 혼동하지 않는다.
7. 제약조건을 잠시 해제한 뒤 다시 켰다고 해서 과거 데이터가 자동으로 모두 검증되었다고 단정하지 않는다.
8. 논리 모델의 속성명을 그대로 옮기는 것만이 물리 설계가 아니다. 실제 값 분포, 자료형, 길이, 널, 기본값, 운영 영향을 결정해야 한다.

## 9. 확인 문제

### 문제 1

주문 테이블의 고객번호가 존재하지 않는 고객을 가리키지 못하게 하는 무결성 유형과 대표 구현 수단은 무엇인가?

**정답과 해설:** 참조 무결성이며 대표 구현 수단은 외래 키 제약이다. 외래 키는 자식의 고객번호가 부모 고객 테이블의 참조 가능한 키와 대응하도록 한다. 삭제·갱신 시 동작은 고객과 주문의 생명주기 및 보존 규칙에 맞게 따로 결정한다.

### 문제 2

상품수량을 정수형으로 정의하면 “1 이상이어야 한다”는 규칙까지 자동으로 보장되는가?

**정답과 해설:** 보장되지 않는다. 정수형은 정수 표현을 보장하지만 음수와 0도 표현할 수 있다. 수량의 업무 범위는 CHECK 같은 추가 제약으로 선언해야 한다.

### 문제 3

NULL, 숫자 0, 빈 문자열을 같은 값으로 다뤄도 되는가?

**정답과 해설:** 안 된다. NULL은 값의 부재 또는 미확정을 나타내고, 0은 확정된 숫자 값이며, 빈 문자열은 길이가 0인 문자 값이다. 저장 의미와 비교·집계 동작을 구분해야 한다.

### 문제 4

금액 칼럼의 물리 속성을 결정할 때 최소한 확인할 항목 네 가지를 쓰시오.

**정답과 해설:** 예상 최소·최대 금액, 전체 정밀도, 소수점 이하 자릿수, 음수·널 허용 여부를 확인할 수 있다. 여기에 통화 단위, 반올림 규칙, 계산 방식, 기존 데이터 분포까지 확인하면 안전하다.

### 문제 5

모든 데이터 입력이 한 화면에서 이루어지고 그 화면에 검사가 있으므로 데이터베이스 제약조건을 생략해도 된다는 주장에 문제가 있는 이유는 무엇인가?

**정답과 해설:** 배치, 외부 연계, 관리 도구, 향후 새 애플리케이션이 화면을 거치지 않을 수 있고, 검사 로직이 경로마다 달라질 수 있다. 공통으로 항상 성립해야 하는 규칙은 데이터베이스에 선언하고 화면 검사는 사용자 편의와 빠른 오류 안내를 위해 병행하는 것이 좋다.

## 10. 최종 요약

- **데이터베이스 무결성**은 데이터의 정확성, 일관성, 유효성을 유지하는 성질이다.
- 개체 무결성은 행 식별, 참조 무결성은 테이블 사이 연결, 도메인 무결성은 값의 범위와 형식, 사용자 정의 무결성은 업무 고유 규칙을 보호한다.
- PRIMARY KEY, FOREIGN KEY, UNIQUE, NOT NULL, CHECK는 규칙을 데이터 저장 지점에 선언하며, DEFAULT는 생략된 값의 초기값을 제공한다.
- **칼럼 속성**에는 이름, 자료형, 길이·정밀도, 널 허용 여부, 기본값, 제약조건 등이 포함된다.
- 자료형은 겉모양이 아니라 값의 의미와 필요한 연산을 기준으로 정한다. NULL을 0이나 빈 문자열로 대체해서는 안 된다.
- 물리 칼럼 설계는 업무 의미 확인, 데이터 프로파일링, 자료형 매핑, 제약 선언, 이행·성능 검증, 문서화 순으로 수행한다.
- 제품별 세부 구문과 널·정렬 처리에는 차이가 있을 수 있으므로 원칙을 먼저 적용하고 실제 환경의 공식 문서와 테스트로 확인한다.
