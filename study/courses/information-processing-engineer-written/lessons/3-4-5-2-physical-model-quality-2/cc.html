01

학습 범위와 목표

이 레슨은 물리데이터 모델 품질 검토의 후반 주제인 CRUD 분석과 SQL 성능 튜닝을 다룬다. CRUD 매트릭스로 업무 프로세스와 데이터의 상호작용을 검증하고, 측정 자료와 실행 계획을 근거로 느린 SQL의 원인을 찾아 개선하는 흐름을 익힌다. 앞 레슨의 물리 E-R 다이어그램 작성법이나 다음 단원의 데이터 전환 기술로 범위를 넓히지 않는다.

학습 후에는 다음을 할 수 있어야 한다.

  • 프로세스와 데이터 개체로 CRUD 매트릭스를 작성하고 해석한다.
  • 누락된 프로세스, 사용되지 않는 데이터, 생성·사용 순서의 이상을 찾는다.
  • SQL 성능을 응답 시간, 처리량, 자원 사용량 등으로 측정한다.
  • 실행 계획과 실제 처리량을 비교해 병목 원인을 좁힌다.
  • 변경 전후 결과의 정확성과 성능을 함께 검증한다.
02

1. CRUD 분석의 기본 개념

CRUD는 데이터에 수행하는 네 가지 기본 연산을 뜻한다.

  • Create: 새로운 데이터를 생성한다.
  • Read: 기존 데이터를 조회한다.
  • Update: 기존 데이터의 값을 변경한다.
  • Delete: 기존 데이터를 삭제한다.

CRUD 분석은 업무 프로세스가 어떤 데이터 개체에 어떤 연산을 수행하는지 행렬 형태로 정리하여 프로세스 모델과 데이터 모델의 완전성·일관성을 검토하는 기법이다. 보통 행에는 업무 프로세스, 열에는 엔터티나 테이블을 배치하고 교차 셀에 C, R, U, D를 표시한다. 한 셀에 CR 또는 RU처럼 여러 연산이 들어갈 수도 있다.

CRUD 매트릭스는 실제 프로그램 코드를 대신하는 상세 설계서가 아니다. 어떤 업무가 어떤 데이터에 책임을 갖는지를 빠르게 조망하고 누락과 이상을 발견하는 검토 도구다.

03

2. CRUD 매트릭스 작성 절차

2.1 분석 범위 확정

업무 프로세스 목록, 데이터 개체 목록, 기준 버전을 확정한다. 프로세스의 수준이 섞이면 “주문 관리” 같은 큰 기능과 “주문 승인” 같은 세부 기능이 한 행에 놓여 해석하기 어렵다. 같은 분해 수준을 유지하는 것이 중요하다.

2.2 프로세스와 데이터 배치

일반적으로 프로세스를 행, 데이터 개체를 열에 둔다. 반대로 배치해도 원리는 같지만 표의 방향을 명시해야 한다. 데이터 개체는 같은 의미를 중복해 열로 만들지 말고, 프로세스 이름은 행위가 드러나게 적는다.

2.3 연산 표시

각 프로세스가 데이터에 하는 일을 근거 문서와 함께 표시한다.

“주문 취소”가 주문을 실제 삭제하지 않고 상태만 변경한다면 D가 아니라 U다. 업무 용어의 “삭제”, “취소”, “폐기”를 곧바로 물리적 Delete로 해석해서는 안 된다. 이력 보존 정책과 실제 데이터 처리 의미를 확인한다.

2.4 행과 열 검토

행 방향으로는 프로세스가 필요한 데이터를 빠짐없이 사용하고 결과를 남기는지 본다. 열 방향으로는 데이터가 어디서 생성되고 누가 조회·수정·삭제하는지 본다.

2.5 이상 사항 확인과 보정

누락 셀은 요구사항 누락, 프로세스 누락, 데이터 개체 누락 중 무엇인지 원인을 확인한다. 매트릭스를 억지로 채우기보다 근거 문서를 수정하고 연관 산출물을 함께 갱신한다.

04

3. CRUD 매트릭스 해석 기준

3.1 생성 없는 데이터

어떤 열에 R, U, D만 있고 C가 없으면 데이터 생성 프로세스가 누락되었을 가능성이 있다. 다만 외부 시스템에서 전달받는 기준정보나 이미 존재하는 초기 데이터라면 현재 분석 범위 밖에서 생성될 수 있다. 따라서 “C가 없으면 무조건 오류”가 아니라 생성 책임과 유입 경로가 설명되는지 확인한다.

3.2 사용되지 않는 데이터

열 전체가 비어 있으면 어느 프로세스도 해당 데이터를 사용하지 않는다는 뜻이다. 불필요한 데이터 개체인지, 업무 프로세스가 누락되었는지 검토한다. 이 역시 감사·법적 보존처럼 별도 목적이 있을 수 있으므로 근거를 확인한다.

3.3 데이터에 접근하지 않는 프로세스

행 전체가 비어 있다면 데이터 처리가 없는 순수 제어·안내 프로세스일 수 있지만, 보통은 분석 누락을 의심한다. 프로세스 결과가 어디에 기록되는지, 입력 데이터가 무엇인지 확인한다.

3.4 생성과 사용 순서

논리적으로 C가 R·U·D보다 먼저 일어나야 한다. 실제 실행 순서는 프로세스 흐름도와 함께 검토한다. 매트릭스 자체에는 시간 순서가 충분히 표현되지 않으므로 행 배치만 보고 단정하지 않는다.

3.5 과도한 생성·수정 책임

서로 무관한 여러 프로세스가 같은 데이터를 생성하거나 핵심 값을 수정한다면 책임 중복과 무결성 위험을 검토한다. 여러 생성 경로가 업무상 정당할 수 있으나 동일 규칙이 모든 경로에서 보장되는지 확인해야 한다.

3.6 클러스터와 경계

특정 프로세스 묶음이 특정 데이터 묶음에 집중적으로 접근하면 기능 응집도와 업무 경계를 파악하는 단서가 된다. 반대로 한 프로세스가 지나치게 많은 데이터에 CUD를 수행하면 역할이 과도하게 넓거나 트랜잭션 경계가 복잡할 수 있다. CRUD 매트릭스만으로 구조를 확정하지 말고 추가 분석의 출발점으로 사용한다.

05

4. SQL 성능의 의미

SQL 성능 튜닝은 SQL이 같은 업무 결과를 유지하면서 목표한 응답 시간과 처리량을 달성하고 자원을 효율적으로 사용하도록 분석·개선하는 활동이다. 단순히 문장을 짧게 바꾸거나 인덱스를 무조건 추가하는 작업이 아니다.

주요 관찰 지표는 다음과 같다.

  • 응답 시간: 요청 시작부터 결과 반환까지 걸린 시간
  • 처리량: 단위 시간에 처리한 요청 또는 행의 수
  • CPU 사용량: 연산과 비교에 소비한 처리 자원
  • 논리적·물리적 읽기: 버퍼나 저장장치에서 읽은 데이터 블록의 양
  • 처리 행 수: 단계별 입력 행과 출력 행의 차이
  • 대기 시간: 잠금, 입출력, 메모리, 네트워크 등으로 기다린 시간

평균만 보면 일부 사용자의 긴 지연이 가려질 수 있다. 문제에서 백분위 지연, 최대 시간, 동시 사용자 조건을 주면 그 조건을 기준으로 판단한다.

06

5. SQL 처리와 실행 계획

데이터베이스는 SQL을 해석하고, 가능한 접근 경로와 조인 순서를 비교해 실행 계획을 선택한 뒤 실행한다. 세부 단계와 명칭은 제품에 따라 다를 수 있으나 다음 원리는 공통적이다.

  1. SQL 문장의 구문과 객체를 확인한다.
  2. 조건, 통계, 사용 가능한 접근 구조를 고려해 실행 방법을 선택한다.
  3. 선택한 계획에 따라 데이터를 읽고 필터링하고 결합한다.
  4. 정렬, 집계, 결과 반환을 수행한다.

실행 계획은 테이블 접근 방식, 조인 순서와 방식, 예상 행 수, 정렬·집계 같은 연산을 보여 준다. 예상 행 수와 실제 처리 행 수의 차이가 크면 데이터 분포나 조건의 선택도 추정이 부정확한 원인일 수 있다. 계획의 비용 숫자는 같은 환경에서 후보를 비교하는 단서이지, 서로 다른 제품과 환경에서 절대 성능을 보장하는 시간 단위가 아니다.

07

6. SQL 성능 튜닝 절차

6.1 목표와 재현 조건 정의

“느리다”를 “동시 사용자 50명에서 주문 조회의 응답 시간이 목표를 초과한다”처럼 측정 가능하게 바꾼다. 데이터 규모, 입력 값, 캐시 상태, 동시 부하, 실행 횟수를 기록한다. 조건이 다르면 변경 전후 수치를 공정하게 비교할 수 없다.

6.2 기준값 수집

SQL 원문, 입력 매개변수, 실행 시간, 처리 행 수, 읽기량, 실행 계획을 수집한다. 전체 시스템 병목인지 특정 SQL 병목인지 먼저 구분한다. 애플리케이션 대기 시간을 전부 SQL 실행 시간으로 오해하지 않는다.

6.3 병목 지점 식별

다음 신호를 살핀다.

  • 필요한 결과보다 지나치게 많은 행을 읽은 뒤 버림
  • 선택도가 높은 조건이 늦게 적용됨
  • 큰 집합의 불필요한 정렬이나 중복 제거
  • 조인 조건 누락으로 행 수가 급증함
  • 반복문 안에서 같은 형태의 SQL이 과도하게 호출됨
  • 필요한 열보다 훨씬 넓은 데이터를 반환함
  • 예상 행 수와 실제 행 수가 크게 다름

6.4 개선안 설계

가능한 개선은 조건식과 조인식 정리, 불필요한 열과 행 제거, 적절한 접근 구조 검토, 반복 호출을 집합 처리로 변경, 중복 연산 축소 등이다. 함수나 형 변환을 조건 열에 적용하면 일부 환경에서 효율적인 접근 경로를 쓰기 어려울 수 있으므로 동일 의미의 비교 방식으로 바꿀 수 있는지 살핀다. 단, 옵티마이저 동작은 제품과 통계에 따라 달라지므로 실제 계획으로 검증한다.

6.5 결과 정확성 검증

튜닝 전후 SQL의 결과 행, 중복, NULL 처리, 정렬 요구, 경계값이 동일한지 확인한다. 빠르지만 결과가 달라진 SQL은 개선이 아니다. 특히 외부 조인 조건을 옮기거나 집계 전에 필터를 적용할 때 의미가 달라질 수 있다.

6.6 성능 재측정과 회귀 확인

같은 조건에서 여러 번 측정하고 대표값과 변동 폭을 비교한다. 특정 입력에서는 빨라졌지만 다른 입력에서 급격히 느려지지 않는지 확인한다. 변경한 접근 구조가 쓰기 비용과 저장 공간에 미치는 영향도 고려한다.

6.7 반영과 모니터링

변경 근거, 전후 계획, 시험 결과, 되돌리기 조건을 기록한 뒤 통제된 절차로 반영한다. 운영 데이터 분포와 부하는 계속 변하므로 반영 후에도 목표 지표를 관찰한다.

8. 실전 예시

요구사항은 “특정 기간 동안 특정 상태인 고객의 주문번호, 주문일시, 총액을 최신순으로 조회”하는 것이다. 기존 SQL이 모든 주문과 고객을 결합한 뒤 고객 상태와 날짜를 거르고, 화면에서 쓰지 않는 고객의 상세 설명까지 반환한다고 하자.

분석 절차는 다음과 같다.

  1. 대표 기간과 고객 상태, 실제 데이터 규모로 기준 시간을 측정한다.
  2. 실행 계획에서 주문과 고객 각각의 입력·출력 행 수를 본다.
  3. 조인 조건이 고객 식별자로 정확히 연결되는지 확인한다.
  4. 날짜와 상태 조건이 가능한 단계에서 적용되는지 확인한다.
  5. 화면 계약상 필요한 열만 반환하도록 후보 SQL을 만든다.
  6. 필요한 정렬이 한 번만 수행되는지 확인한다.
  7. 기존과 후보 결과의 행 수, 주문번호 집합, 총액, NULL을 비교한다.
  8. 같은 부하 조건에서 반복 측정하고 읽기량과 응답 시간을 함께 비교한다.

조건 열을 임의 문자열로 변환해 비교하는 기존 표현이 있다면 원래 자료형의 범위 조건으로 표현할 수 있는지 검토한다. 그러나 “함수가 있으면 항상 인덱스를 못 쓴다”처럼 단정하지 않는다. 제품 기능과 실제 실행 계획이 최종 판단 근거다.

9. 시험 함정

  1. CRUD의 C를 조회로 착각: C는 Create, R이 Read다.
  2. 업무상 취소를 D로 단정: 상태 변경과 물리 삭제는 다르다.
  3. C가 없는 열을 무조건 오류 처리: 외부 유입이나 분석 범위 밖 생성인지 확인한다.
  4. 매트릭스 행 순서를 실행 순서로 단정: 시간 흐름은 프로세스 모델과 함께 확인한다.
  5. 인덱스 추가를 유일한 튜닝 방법으로 생각: SQL 의미, 읽는 행, 조인, 호출 횟수, 정렬 등도 분석한다.
  6. 비용 값을 초 단위로 해석: 실행 계획 비용은 보통 후보 계획 비교를 위한 추정 지표다.
  7. 응답 시간만 줄면 성공이라고 판단: 결과 정확성, 처리량, 자원, 쓰기 부하와 회귀를 함께 본다.
  8. 외부 조인의 조건 위치를 무심코 변경: NULL 확장 행의 포함 여부가 달라질 수 있다.
  9. 개발용 소량 데이터 결과를 운영 성능으로 일반화: 데이터 규모와 분포, 동시성을 맞춰 측정한다.

10. 확인 문제

문제 1

CRUD 매트릭스의 행과 열에는 보통 무엇을 배치하며 셀에는 무엇을 기록하는가?

문제 2

한 데이터 열에 R과 U만 있고 C가 없을 때 바로 결함으로 확정하면 안 되는 이유는 무엇인가?

문제 3

업무 용어 “주문 취소”가 CRUD의 D가 아닐 수 있는 사례를 설명하시오.

문제 4

SQL 튜닝 전 기준값으로 수집할 항목을 네 가지 쓰시오.

문제 5

실행 계획의 예상 행 수와 실제 행 수 차이가 크면 무엇을 의심할 수 있는가?

문제 6

튜닝한 SQL의 결과 정확성을 검증해야 하는 이유는 무엇인가?

문제 7

접근 구조를 추가할 때 조회 성능 외에 고려할 비용 두 가지를 쓰시오.

문제 8

반복문에서 행마다 SQL을 호출하는 상황의 개선 방향을 쓰시오.

11. 정답과 해설

정답 1

보통 행에는 업무 프로세스, 열에는 데이터 엔터티나 테이블을 배치하고 교차 셀에는 C, R, U, D 연산을 표시한다. 방향을 반대로 써도 범례가 명확하면 분석 원리는 같다.

정답 2

해당 데이터가 외부 시스템이나 초기 구축 과정에서 생성되어 현재 분석 범위 안에 C가 없을 수 있기 때문이다. 생성 책임과 유입 경로가 설명되는지 확인한 뒤 판정한다.

정답 3

주문 행을 삭제하지 않고 주문상태를 “취소”로 바꾸고 취소일시를 기록한다면 실제 연산은 Update다. 업무 표현과 물리 연산을 구분해야 한다.

정답 4

예: SQL 원문과 매개변수, 실행 시간, 실행 계획, 처리 행 수, 논리적·물리적 읽기량, 동시 부하 조건 중 네 가지다. 비교 가능하도록 데이터 규모와 측정 조건도 기록한다.

정답 5

조건의 선택도나 데이터 분포 추정, 통계 정보, 연산 단계의 추정이 실제와 맞지 않을 가능성을 의심한다. 차이가 생긴 지점을 따라 병목 원인을 좁힌다.

정답 6

조건식, 조인, 집계 방식을 바꾸면 행 수, 중복, NULL 포함 여부가 달라질 수 있기 때문이다. 업무 결과가 같아야 성능 개선으로 인정할 수 있다.

정답 7

데이터 변경 시 유지 비용과 저장 공간 비용을 고려한다. 잠금, 메모리, 관리 복잡성도 환경에 따라 영향을 준다.

정답 8

가능하면 여러 행을 한 번에 처리하는 집합 기반 SQL이나 일괄 요청으로 바꾸어 호출 왕복과 반복 해석 비용을 줄인다. 단, 트랜잭션과 오류 처리 의미를 보존해야 한다.

최종 요약

  • CRUD 분석은 프로세스와 데이터의 C·R·U·D 상호작용을 행렬로 정리해 누락과 책임 이상을 찾는 기법이다.
  • 빈 행·열, 생성 없는 데이터, 과도한 CUD 책임은 결함 후보이며 범위와 업무 근거를 확인한 뒤 판정한다.
  • SQL 성능 튜닝은 측정 가능한 목표, 기준값, 실행 계획과 실제 처리량을 근거로 수행한다.
  • 튜닝은 목표 정의, 재현, 병목 식별, 개선안 적용, 결과 정확성 검증, 재측정, 반영 후 모니터링 순으로 진행한다.
  • 응답 시간뿐 아니라 처리량, 읽기량, CPU, 대기, 쓰기 비용과 회귀 영향을 함께 본다.
  • 시험에서는 업무 용어와 CRUD 연산, 예상 비용과 실제 시간, 빠른 SQL과 올바른 SQL을 구분해야 한다.
