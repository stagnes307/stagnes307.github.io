01

학습 범위와 목표

이 레슨은 데이터 전환 기술 가운데 초기데이터 구축과 ETL(Extraction, Transformation, Loading)을 다룬다. 새 시스템이 업무를 시작할 수 있도록 기준 시점의 데이터를 준비하는 과정과, 원천에서 데이터를 추출하여 목표 형식으로 변환한 뒤 적재하는 흐름을 연결해 이해하는 것이 목표다. 파일 형식별 처리 기법, 전환 수행 계획서, 상세 검증과 정제 규칙은 뒤 레슨의 범위이므로 여기서는 핵심 원리와 기술 흐름에 집중한다.

학습 후에는 다음을 할 수 있어야 한다.

  • 초기데이터의 목적과 범위를 운영 중 발생하는 데이터와 구분한다.
  • 원천·목표 매핑을 기준으로 추출, 변환, 적재 단계를 설계한다.
  • 전체 추출과 증분 추출, 일괄 처리와 단계 처리의 선택 근거를 설명한다.
  • 키, 코드, 날짜, NULL, 참조 순서를 고려한 전환 절차를 제시한다.
  • 재실행 가능성, 추적성, 오류 격리의 중요성을 설명한다.
02

1. 데이터 전환과 초기데이터의 의미

데이터 전환은 기존 시스템이나 외부 원천의 데이터를 새 시스템에서 사용할 수 있는 구조와 값으로 옮기는 활동이다. 단순 복사는 원천과 목표의 구조·코드·업무 의미가 같을 때만 가능하다. 실제로는 열 이름, 자료형, 코드 체계, 식별자, 날짜 표현, NULL 의미가 달라서 변환 규칙이 필요하다.

초기데이터 구축은 새 시스템을 최초로 가동할 때 필요한 기준 데이터와 업무 데이터를 준비하여 목표 데이터베이스에 적재하는 일이다. 시스템 설치 직후 비어 있는 데이터베이스만으로 업무를 시작할 수 없다. 공통 코드, 조직·사용자·상품 같은 기준정보, 전환 기준일 현재의 유효 계약과 잔액, 필요한 이력 등을 정해진 범위에 맞추어 구축해야 한다.

초기데이터는 다음 질문으로 범위를 정한다.

  • 새 시스템의 첫 업무일에 반드시 존재해야 하는 데이터는 무엇인가?
  • 과거 이력은 어느 시점부터 얼마만큼 옮기는가?
  • 종료되었거나 폐기된 데이터도 법적·업무상 보존해야 하는가?
  • 원천 시스템의 어느 시점 값을 기준으로 삼는가?
  • 전환 후 새로 들어온 변경분은 어떻게 반영하는가?

“가능한 모든 데이터를 옮긴다”는 답은 안전해 보이지만 비용과 위험을 키운다. 사용할 필요가 없는 오래된 데이터, 의미가 불명확한 값, 중복 데이터까지 옮기면 새 시스템의 품질이 나빠질 수 있다. 업무·보존·감사 요구에 근거해 범위를 확정해야 한다.

03

2. 초기데이터의 유형

2.1 기준정보

여러 업무가 공통으로 참조하는 조직, 사용자, 거래처, 상품, 계정과목 같은 데이터다. 다른 업무 데이터가 이를 외래키로 참조할 수 있으므로 일반적으로 먼저 준비한다. 기준정보의 식별자와 사용 상태가 바뀌면 광범위한 데이터에 영향을 줄 수 있다.

2.2 코드와 분류 체계

상태, 유형, 지역, 등급처럼 값을 분류하는 데이터다. 기존 코드와 새 코드가 같지 않으면 매핑표가 필요하다. 예를 들어 원천의 A, B, C가 목표의 10, 20, 30에 대응하는지, 폐기 코드가 어느 값으로 가는지 정한다. 매핑되지 않은 코드를 임의로 기본값에 넣으면 의미가 왜곡된다.

2.3 업무 기준 시점 데이터

전환 기준일 현재 유효한 주문, 계약, 재고, 잔액처럼 새 시스템에서 업무를 이어가기 위한 데이터다. 기준 시점을 명확히 하지 않으면 추출 중 계속 변하는 값 때문에 테이블마다 서로 다른 시점의 상태가 섞일 수 있다.

2.4 필요한 이력

조회, 고객 응대, 분석, 감사와 보존을 위해 옮길 과거 기록이다. 모든 이력을 운영 테이블에 넣는 방식만 있는 것은 아니다. 목표 시스템의 사용 방식과 보존 정책에 따라 범위와 저장 위치를 결정한다.

2.5 시스템 운영용 초기값

번호 채번의 시작점, 업무 달력, 권한 기준, 환경별 설정처럼 시스템 실행에 필요한 값이다. 설정값은 개발·시험·운영 환경마다 달라질 수 있으므로 업무 데이터와 같은 방식으로 무조건 복사하지 않는다.

3. 초기데이터 구축의 준비 산출물

3.1 원천·목표 매핑 정의

매핑 정의에는 보통 다음 항목이 들어간다.

3. 초기데이터 구축의 준비 산출물 · 학습 표 1
항목설명
원천 객체·열데이터를 읽을 위치와 열
목표 테이블·열적재할 위치와 열
변환 규칙코드 변환, 계산식, 형식 변경

같은 이름이라고 같은 의미는 아니고, 다른 이름이라고 다른 의미인 것도 아니다. 열명보다 업무 정의와 값의 도메인을 기준으로 매핑한다.

3.2 전환 기준 시점

추출이 시작된 뒤 원천 데이터가 변경되면 원천 테이블끼리 시점이 어긋날 수 있다. 업무 중단 구간을 두거나, 일관된 시점의 스냅샷을 사용하거나, 최초 전체분 이후 변경분을 별도로 반영하는 등의 방식을 선택한다. 중요한 것은 어느 시점의 상태를 옮겼는지 설명할 수 있는 것이다.

3.3 키 대응표

새 시스템이 새로운 식별자를 부여한다면 기존 키와 새 키의 대응표를 유지해야 자식 데이터의 외래키를 올바르게 변환할 수 있다. 대응표에는 원천 시스템 식별자도 함께 두어 서로 다른 원천의 같은 번호가 충돌하지 않게 한다.

05

4. ETL(Extraction, Transformation, Loading)

ETL(Extraction, Transformation, Loading)은 원천에서 필요한 데이터를 추출하고, 목표 구조와 업무 규칙에 맞게 변환한 다음, 목표 저장소에 적재하는 과정이다. 세 단계는 개념적으로 구분되지만 실제 구현에서는 일부가 연속되거나 병렬로 진행될 수 있다.

4.1 Extraction: 추출

추출은 원천에서 전환 대상 데이터를 읽어 오는 단계다.

  • 전체 추출: 대상 범위 전체를 가져온다. 최초 전환이나 작은 데이터에 단순하지만 양이 크면 시간과 부하가 증가한다.
  • 증분 추출: 마지막 처리 이후 변경된 데이터만 가져온다. 반복 전환과 짧은 중단 시간에 유리하지만 변경 누락과 중복을 막을 기준이 필요하다.

증분 기준으로 수정일시를 사용할 때 동일 시각의 경계값, 시간대, 지연 입력을 고려해야 한다. 마지막 시각보다 “큰 값”만 읽으면 같은 시각에 뒤늦게 기록된 행을 놓칠 수 있다. 변경 번호나 범위 중첩 후 중복 제거 같은 대안을 환경에 맞게 선택한다.

추출 단계에서는 원천 시스템에 과도한 부하를 주지 않아야 한다. 필요한 열과 행만 읽고, 작업 시간대와 배치 크기를 조정하며, 추출 건수와 기준 시점을 기록한다.

4.2 Transformation: 변환

변환은 원천 값을 목표의 의미·형식·구조에 맞게 바꾸는 단계다.

  • 자료형과 형식 변환: 문자 날짜를 목표 날짜 의미로 바꾸기
  • 코드 변환: 원천 상태 코드를 목표 코드로 매핑하기
  • 단위 변환: 금액이나 수량 단위를 목표 기준에 맞추기
  • 파생값 계산: 여러 원천 값으로 목표 값을 산출하기
  • 분할·결합: 한 열을 여러 열로 나누거나 여러 열을 결합하기
  • 키 변환: 기존 식별자를 새 식별자로 대응하기
  • 값 표준화: 공백, 대소문자, 표현 형식을 정해진 원칙으로 맞추기

변환 규칙은 결정적이어야 한다. 같은 입력을 같은 규칙으로 처리하면 같은 결과가 나와야 재실행과 문제 분석이 쉽다. 규칙에 없는 값은 조용히 버리기보다 오류 또는 보류 대상으로 분리하고 원인을 남긴다.

4.3 Loading: 적재

적재는 변환된 데이터를 목표 저장소에 반영하는 단계다.

  • 초기 일괄 적재: 비어 있거나 준비된 목표에 큰 범위를 한 번에 넣는다.
  • 단계 적재: 기준정보, 부모, 자식 순으로 나누어 넣는다.
  • 변경 반영: 새 행 삽입과 기존 행 갱신을 규칙에 따라 구분한다.

부모 데이터가 있어야 자식의 외래키를 확인할 수 있으므로 참조 의존 순서를 고려한다. 무결성 제약을 임시로 해제하는 접근은 위험과 복구 방식을 통제한 경우에만 고려하며, 적재 뒤 반드시 관계의 유효성을 확인해야 한다.

적재 단위를 너무 크게 잡으면 한 건의 오류로 전체 작업을 다시 해야 할 수 있고, 너무 작게 잡으면 관리·반영 비용이 커질 수 있다. 데이터 양, 트랜잭션 시간, 재시작 요구를 기준으로 적절한 단위를 정한다.

5. ETL 설계의 핵심 원리

5.1 재실행 가능성과 멱등성

작업이 중간에 실패했을 때 처음부터 또는 확인 지점부터 안전하게 다시 실행할 수 있어야 한다. 같은 입력을 재처리했을 때 중복 행이 생기지 않도록 업무 키나 처리 식별자, 적재 상태를 이용한다. 모든 작업이 완전한 멱등성을 갖기 어렵다면 어느 단계까지 반영되었고 어떻게 되돌리거나 이어갈지를 명확히 한다.

5.2 추적성

목표 행이 어느 원천의 어떤 행과 규칙에서 왔는지 추적할 수 있어야 한다. 실행 ID, 원천 식별자, 규칙 버전, 처리 시각, 결과 상태를 기록하면 오류 분석과 재처리가 쉬워진다. 로그에 개인정보나 비밀 값을 불필요하게 남기지 않는 것도 중요하다.

5.3 오류 격리

오류 한 건 때문에 정상 데이터 전체가 처리되지 못하게 할지, 오류만 격리하고 나머지를 진행할지는 업무 중요도에 따라 정한다. 금액 합계처럼 전체 일관성이 중요한 집합은 일부 성공이 위험할 수 있다. 독립된 기준정보는 오류 행을 보류하고 정상분을 진행할 수 있다. 격리된 데이터에는 원천 키, 실패 단계, 원인, 재처리 상태를 남긴다.

5.4 데이터 일관성

서로 관련된 테이블이 같은 기준 시점과 규칙을 사용해야 한다. 주문은 전환 기준일 상태인데 결제는 하루 뒤 상태라면 합계와 상태가 맞지 않을 수 있다. 추출 시점, 변환 규칙, 적재 차수의 일관성을 함께 관리한다.

5.5 보안과 최소 권한

ETL 계정은 필요한 원천 읽기와 목표 쓰기 권한만 갖도록 한다. 임시 저장 영역과 로그에도 민감 데이터가 남을 수 있으므로 접근 통제와 보존 기간을 적용한다. 실데이터를 시험 환경에서 사용할 때는 승인된 보호 조치를 따른다.

07

6. 초기데이터 구축 절차

  1. 범위 정의: 대상 업무, 기준일, 이력 기간, 제외 조건을 확정한다.
  2. 원천 조사: 소유자, 데이터 양, 변경 방식, 품질 위험과 접근 시간을 파악한다.
  3. 목표 구조 확인: 필수 열, 키, 코드, 관계와 업무 규칙을 확인한다.
  4. 매핑·변환 규칙 작성: 원천과 목표 열, 코드표, 기본값, 오류 처리를 명시한다.
  5. 추출 방식 선택: 전체 또는 증분, 기준 시점과 부하 통제 방식을 정한다.
  6. 변환·적재 흐름 구현: 단계별 입력·출력과 재시작 지점을 만든다.
  7. 시험 실행: 실제와 유사한 양과 경계값으로 반복 가능성을 확인한다.
  8. 초기 적재 수행: 의존 순서에 따라 적재하고 실행 기록을 남긴다.
  9. 기본 인수 확인: 대상 건수, 핵심 합계, 필수 데이터 존재 여부가 승인 기준에 맞는지 확인한다.
  10. 운영 전환: 변경분 반영과 업무 개시 시점을 연결하고 책임자에게 결과를 인계한다.

여기서 인수 확인은 ETL 흐름이 계획대로 끝났는지 판단하는 최소 확인이다. 검증 유형과 상세 대사 기법은 별도의 데이터 검증 범위에서 더 깊게 다룬다.

7. 실전 예시: 회원과 주문 초기 구축

원천 회원의 회원번호는 문자 8자리이고, 목표에서는 새 내부 식별자를 사용한다고 하자. 원천 회원등급은 G, S, V이고 목표 코드는 10, 20, 30이다. 주문은 원천 회원번호를 참조한다.

추출

  • 전환 기준일 현재 활성 회원을 추출한다.
  • 보존 범위에 포함되는 주문만 추출한다.
  • 회원과 주문이 동일한 기준 시점을 사용하도록 한다.

변환

  • 원천 회원번호별 새 회원 식별자를 만들고 키 대응표에 기록한다.
  • G→10, S→20, V→30 코드 매핑을 적용한다.
  • 정의되지 않은 등급은 임의로 10에 넣지 않고 보류한다.
  • 주문의 회원번호를 대응표의 새 회원 식별자로 바꾼다.

적재

  • 코드 기준정보를 먼저 넣는다.
  • 회원을 적재한 다음 주문을 적재한다.
  • 작업 실행 ID별 추출 건수, 변환 성공·보류 건수, 적재 건수를 기록한다.

실패 후 다시 실행할 때 회원이 중복 생성되지 않도록 원천 시스템과 원천 회원번호의 조합을 재처리 기준으로 사용할 수 있다. 새 식별자를 매번 다시 만들면 주문이 다른 회원을 참조할 위험이 있으므로 키 대응표를 안정적으로 보존한다.

9. 시험 함정

  1. ETL을 단순 복사로 정의: 목표 의미에 맞춘 변환이 핵심 단계다.
  2. 초기데이터를 공통 코드만으로 한정: 기준정보, 업무 기준 시점 데이터, 필요한 이력과 운영 초기값도 포함될 수 있다.
  3. 전체 추출이 항상 더 정확하다고 단정: 실행 중 데이터가 바뀌면 전체 추출도 시점 불일치가 생길 수 있다.
  4. 증분 기준을 수정일시 하나로만 처리: 동일 시각, 지연 입력, 시간대와 재처리 경계를 고려한다.
  5. NULL을 빈 문자열이나 0으로 무조건 변경: 값 없음, 미정, 해당 없음의 업무 의미를 확인한다.
  6. 부모와 자식 적재 순서를 무시: 키 대응과 참조 의존성을 고려한다.
  7. 오류 값을 기본값으로 조용히 대체: 의미 왜곡을 막기 위해 규칙과 승인 근거가 필요하다.
  8. 재실행하면 처음 실행과 자동으로 같은 결과가 난다고 생각: 중복 방지 키, 실행 상태, 규칙 버전이 필요하다.
  9. 특정 도구의 단계 이름을 보편 표준으로 암기: 추출·변환·적재의 역할과 데이터 흐름을 중심으로 판단한다.

11. 정답과 해설

정답 1

초기데이터는 새 시스템 최초 가동 시 업무 시작에 필요한 기준 시점의 데이터이며, 운영 데이터는 가동 후 업무 처리로 계속 생성·변경되는 데이터다. 초기 구축에는 기준일과 이력 범위를 명확히 정해야 한다.

정답 2

예: 원천 객체·열, 목표 테이블·열, 변환 규칙, NULL·기본값 규칙, 키 대응, 필터 조건, 의존 순서, 오류 처리 중 네 가지다.

정답 3

전체 추출은 대상 전체를 읽어 흐름이 단순하지만 큰 부하와 긴 시간이 위험이다. 증분 추출은 변경분만 읽어 효율적이지만 경계값에서 누락이나 중복이 생길 수 있다.

정답 4

자식 데이터의 기존 외래키를 새 부모 키로 바꾸고, 목표 행이 어느 원천 행에서 왔는지 추적하며, 재실행 때 같은 대응을 재사용하기 위해서다.

정답 5

예: 코드 매핑, 자료형·날짜 형식 변환, 단위 변환, 파생값 계산, 열 분할·결합, 키 변환, 값 표준화 중 세 가지다.

정답 6

자식의 외래키가 참조할 부모 키가 먼저 존재해야 참조 무결성을 지키고 키 대응을 적용할 수 있기 때문이다.

정답 7

실행 ID와 단계별 상태를 기록하고, 안정적인 업무 키로 중복을 방지하며, 확인 지점과 오류 격리 영역을 두는 방법 등이 있다.

정답 8

코드의 업무 의미가 다른 값으로 왜곡되어 집계와 후속 업무가 잘못될 수 있기 때문이다. 오류로 보류하고 매핑 규칙을 승인받은 뒤 재처리해야 한다.

13

최종 요약

  • 초기데이터 구축은 새 시스템의 최초 업무 수행에 필요한 기준정보, 코드, 기준 시점 업무 데이터, 필요한 이력과 운영 초기값을 준비하는 활동이다.
  • 범위, 기준 시점, 원천·목표 매핑, 키 대응, 적재 의존 순서를 먼저 정의한다.
  • ETL(Extraction, Transformation, Loading)은 추출, 변환, 적재의 역할을 구분해 데이터 전환을 수행하는 흐름이다.
  • 전체 추출은 단순하지만 부하가 크고, 증분 추출은 효율적이지만 누락·중복 경계 관리가 필요하다.
  • 변환은 코드·형식·단위·키와 구조를 목표 의미에 맞추며, 규칙 없는 값은 격리하고 근거를 남긴다.
  • 재실행 가능성, 추적성, 오류 격리, 기준 시점 일관성, 최소 권한이 안정적인 초기 구축의 핵심이다.
