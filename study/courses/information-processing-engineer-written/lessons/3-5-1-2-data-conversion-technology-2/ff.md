# 3-5-1-2. 파일 처리 기술

## 학습 범위와 목표

이 레슨은 데이터 전환 기술 중 **파일 처리 기술**을 중심으로, **데이터 전환 기술의 적용 절차와 판단 기준**을 함께 익힌다. 파일의 레코드 구조와 접근 방식, 문자 인코딩, 구분자, 정렬·병합, 대용량 분할 처리와 재시작 설계를 이해하고 전환 상황에 맞는 방식을 선택하는 것이 목표다. 앞 레슨의 ETL 전체 구조나 뒤 레슨의 수행 계획서·상세 검증 항목을 반복하지 않고 파일 입력과 출력의 기술적 처리에 집중한다.

학습 후에는 다음을 할 수 있어야 한다.

- 텍스트 파일과 이진 파일, 고정 길이와 가변 길이 레코드를 구분한다.
- 순차, 직접, 색인 순차 접근의 원리와 적합한 사용 상황을 설명한다.
- 인코딩·구분자·따옴표·줄바꿈 때문에 생기는 오류를 예방한다.
- 대용량 파일을 스트리밍, 분할, 정렬·병합 방식으로 처리한다.
- 데이터 양, 접근 패턴, 상호운용성, 복구 요구를 근거로 처리 방식을 선택한다.

## 1. 파일 처리의 기본 단위

파일은 저장 매체에 기록된 데이터의 모음이며, 전환 작업에서는 시스템 사이의 중간 전달 수단으로 자주 사용된다. 파일 처리를 이해하려면 값 하나보다 레코드와 필드의 경계를 먼저 알아야 한다.

- 필드: 고객번호, 이름, 금액처럼 한 항목의 값
- 레코드: 한 고객이나 한 주문처럼 관련 필드의 묶음
- 파일: 같은 목적의 레코드가 모인 집합
- 헤더: 파일 버전, 생성 시각, 열 이름, 기준일 같은 설명 정보
- 트레일러: 전체 레코드 수나 합계처럼 파일 완결성을 확인하는 정보

헤더와 트레일러는 업무 데이터와 구분하여 처리해야 한다. 첫 행을 무조건 열 이름으로 간주하거나 마지막 행을 일반 레코드로 읽으면 건수와 값이 틀어질 수 있다. 파일 사양서에 존재 여부와 형식을 명시한다.

## 2. 텍스트 파일과 이진 파일

### 2.1 텍스트 파일

문자를 특정 인코딩으로 표현한 파일이다. 사람이 비교적 쉽게 읽고 여러 환경에서 교환하기 좋다. 구분자로 필드를 나누는 형식, 고정된 문자 폭으로 항목을 배치하는 형식, 계층 구조를 표현하는 형식 등이 있다.

장점은 확인과 교환이 쉽다는 점이고, 단점은 구분자·따옴표·인코딩 해석 규칙이 다르면 같은 바이트를 다르게 읽을 수 있다는 점이다. 숫자와 날짜도 문자로 저장되므로 의미 있는 자료형으로 변환할 때 형식 검사가 필요하다.

### 2.2 이진 파일

값을 사람이 읽는 문자 그대로가 아니라 정해진 이진 구조로 기록한다. 같은 정보를 더 작은 크기로 표현하거나 빠르게 읽을 수 있지만, 구조 정의와 읽기 도구가 맞지 않으면 해석하기 어렵다. 바이트 순서, 자료형 크기, 압축, 버전 호환 같은 사양이 중요하다.

텍스트가 항상 느리고 이진이 항상 빠르다는 단정은 피한다. 데이터 양, 압축, 파서, 저장장치, 네트워크, 처리 방식에 따라 결과가 달라지므로 대표 자료로 측정한다.

## 3. 레코드 구성 방식

### 3.1 고정 길이 레코드

각 필드가 정해진 시작 위치와 길이를 차지한다. 예를 들어 1~8번째 문자는 고객번호, 9~28번째는 이름처럼 위치로 값을 구분한다.

장점:

- 구분자를 탐색하지 않고 위치로 필드를 찾을 수 있다.
- 임의 위치의 레코드 계산이 비교적 단순하다.
- 값에 구분자가 포함되어도 경계가 흔들리지 않는다.

주의점:

- 짧은 값에도 정해진 폭을 사용하므로 공간이 낭비될 수 있다.
- 다국어 문자의 “문자 수”와 “바이트 수”를 혼동하면 열 위치가 어긋난다.
- 길이를 초과한 값을 자를지 오류로 처리할지 규칙이 필요하다.
- 왼쪽·오른쪽 채움 문자와 공백 제거 규칙을 정해야 한다.

### 3.2 구분자 기반 가변 길이 레코드

쉼표, 탭, 파이프 같은 문자를 필드 경계로 사용한다. 값 길이에 따라 레코드 크기가 달라져 공간을 효율적으로 쓸 수 있다.

값 자체에 구분자나 줄바꿈, 따옴표가 들어갈 때 이스케이프 또는 인용 규칙이 필요하다. “쉼표로 문자열을 단순 분리”하면 따옴표 안의 쉼표까지 경계로 오인할 수 있다. 사양에 맞는 파서를 사용하고 인용 문자의 중복 표현, 빈 값, 마지막 빈 필드를 확인한다.

### 3.3 길이 표시 방식

레코드나 필드 앞에 길이 정보를 두고 그 길이만큼 읽는 방식이다. 구분자가 값에 포함되는 문제를 줄일 수 있지만 길이 단위가 문자 수인지 바이트 수인지, 길이 자체의 크기와 바이트 순서가 무엇인지 합의해야 한다.

## 4. 파일 접근 방식

### 4.1 순차 파일과 순차 접근

레코드를 처음부터 차례대로 읽거나 쓴다. 전체 데이터를 한 번씩 변환하는 일괄 작업에 적합하다. 구현이 단순하고 연속 읽기의 효율이 좋지만 뒤쪽 특정 레코드 하나를 찾기 위해 앞에서부터 읽어야 할 수 있다.

정렬된 두 파일을 키 순서대로 읽으며 결합하는 병합 처리도 순차 접근의 대표 활용이다. 두 입력이 같은 정렬 기준과 비교 규칙을 사용해야 한다.

### 4.2 직접 파일과 직접 접근

키를 주소나 위치와 연결하여 필요한 레코드에 바로 접근하는 방식이다. 해시 함수를 이용하면 키로 저장 위치를 계산할 수 있다. 특정 키 조회가 많을 때 유리하지만 충돌 처리, 공간 사용, 범위 순서 조회를 고려해야 한다.

해시는 서로 다른 키가 같은 위치를 가리키는 충돌이 발생할 수 있다. 충돌이 없다고 가정하거나 해시값 자체를 유일한 업무 식별자로 사용해서는 안 된다.

### 4.3 색인 순차 접근

데이터를 일정 순서로 저장하면서 별도의 색인을 이용해 특정 구간에 빠르게 접근하는 방식이다. 순차 처리와 키 검색을 함께 지원하는 것이 목적이다. 색인을 유지할 추가 공간과 갱신 비용이 든다.

시험에서는 세 방식을 다음처럼 구분한다.

| 방식 | 강점 | 약점 | 대표 적합 상황 |
|---|---|---|---|
| 순차 | 전체 일괄 읽기, 단순성 | 개별 키 탐색이 느릴 수 있음 | 전체 전환, 정렬 병합 |
| 직접 | 특정 키에 빠른 접근 | 충돌·공간·순서 조회 고려 | 키 기반 조회·갱신 |
| 색인 순차 | 순차 처리와 키 접근 결합 | 색인 유지 비용 | 범위 처리와 개별 조회 병행 |

## 5. 문자 인코딩과 줄바꿈

문자는 인코딩 규칙에 따라 바이트로 저장된다. 보내는 쪽과 받는 쪽의 인코딩이 다르면 한글이 깨지거나 바이트 길이가 달라진다. 파일 사양에는 인코딩 이름, 파일 시작 표식의 처리 여부, 허용 문자 범위를 명시한다.

특히 고정 길이 파일에서는 글자 수와 바이트 수가 다를 수 있다. “이름 20자리”가 문자 20개인지 바이트 20개인지 분명해야 한다. 한 문자의 중간 바이트에서 자르면 복구할 수 없는 문자열이 생길 수 있다.

운영체제나 생성 도구에 따라 줄바꿈 표현이 달라질 수 있다. 읽기 로직은 합의된 형식을 사용하고, 인용된 필드 안의 줄바꿈을 레코드 끝으로 오인하지 않아야 한다. 파일 끝의 마지막 줄바꿈 유무도 빈 레코드 생성 여부에 영향을 줄 수 있다.

## 6. 숫자·날짜·NULL 표현

파일 안의 값은 문자로 전달되는 경우가 많으므로 표현 규칙이 필요하다.

- 숫자: 천 단위 구분자, 소수점 기호, 부호 위치, 소수 자릿수
- 날짜·시각: 연월일 순서, 시간대, 초 이하 정밀도
- 논리값: Y/N, 1/0 등 허용 값
- NULL: 값 없음과 빈 문자열, 숫자 0, 공백의 구분

빈 필드가 NULL인지 빈 문자열인지 사양 없이 추정하지 않는다. 날짜 “00000000”처럼 원천에서 미정 값을 나타내는 특수 값도 실제 날짜로 변환하려 하지 말고 업무 규칙에 따라 보류하거나 NULL로 대응한다.

## 7. 대용량 파일 처리 기술

### 7.1 스트리밍

파일 전체를 메모리에 올리지 않고 레코드나 일정 블록 단위로 읽고 처리한다. 메모리 사용을 제한할 수 있고 첫 결과를 빠르게 만들 수 있다. 다만 전체 집합이 필요한 정렬이나 중복 비교는 추가 구조가 필요하다.

### 7.2 버퍼링과 블로킹

작은 입출력을 매번 저장장치에 요청하면 호출 비용이 커진다. 여러 레코드를 버퍼에 모아 블록 단위로 읽고 쓰면 효율을 높일 수 있다. 버퍼가 너무 크면 메모리와 실패 시 재처리 범위가 커질 수 있으므로 측정하여 정한다.

### 7.3 분할 처리

파일을 크기, 키 범위, 날짜 등으로 나누어 처리한다. 병렬화와 재시작에 유리하지만 레코드 중간에서 자르지 않아야 하고, 각 조각의 범위가 겹치거나 빠지지 않아야 한다. 조각을 다시 합칠 때 순서 요구와 중복 여부를 확인한다.

### 7.4 외부 정렬

메모리에 들어가지 않는 큰 파일은 일부씩 읽어 정렬된 작은 구간을 만들고, 이를 여러 단계로 병합할 수 있다. 정렬 키, 오름·내림차순, NULL 위치, 문자 비교 규칙이 모든 단계에서 같아야 한다.

### 7.5 정렬 병합

같은 키로 정렬된 두 파일을 앞에서부터 읽으며 같은 키를 결합한다. 전체 파일을 순차적으로 처리하므로 큰 자료에 유용하다. 키 중복이 있을 때 1:1인지 1:N인지 규칙을 정하지 않으면 예상보다 많은 출력 행이 생길 수 있다.

### 7.6 확인 지점과 재시작

처리한 파일, 레코드 위치, 마지막 완료 키, 출력 조각, 오류 수를 확인 지점으로 남긴다. 단순 바이트 위치만 저장하면 가변 길이 문자나 압축 파일에서 안전하게 재개하기 어려울 수 있다. 재시작 시 이미 출력된 레코드를 다시 쓰지 않도록 출력 커밋 단위와 상태를 함께 관리한다.

## 8. 오류 처리와 안전성

파일 처리 오류는 크게 형식 오류, 값 오류, 구조 오류, 입출력 오류로 나눌 수 있다.

- 형식 오류: 열 수가 다름, 따옴표가 닫히지 않음, 고정 길이 부족
- 값 오류: 숫자 열에 문자, 허용하지 않은 날짜
- 구조 오류: 헤더 버전 불일치, 트레일러 건수 불일치
- 입출력 오류: 파일 미존재, 권한 부족, 저장 공간 부족, 전송 중 손상

오류 레코드에는 파일 식별자, 논리적 레코드 번호, 업무 키, 오류 코드와 원인을 남긴다. 민감한 전체 레코드를 로그에 그대로 복제하지 않는다. 출력 파일은 완성 전 임시 이름으로 쓰고, 정상 종료 후 최종 이름으로 전환하면 소비자가 미완성 파일을 읽는 위험을 줄일 수 있다.

파일 수신 전후의 무결성 값이나 크기를 비교하면 전송 중 손상 여부를 확인하는 데 도움이 된다. 그러나 해시가 같다는 사실은 업무 내용이 올바르다는 뜻이 아니라 바이트가 같다는 뜻이다.

## 9. 데이터 전환 기술의 적용 절차와 판단 기준

**데이터 전환 기술의 적용 절차와 판단 기준**은 도구 이름보다 요구와 데이터 특성에서 시작한다.

### 9.1 적용 절차

1. **입출력 계약 확인**: 파일 형식, 인코딩, 레코드 구조, 생성 주기, 보안 등급을 확인한다.
2. **데이터 특성 분석**: 파일 크기, 레코드 수, 평균·최대 길이, 정렬 여부, 키 중복을 파악한다.
3. **접근 패턴 정의**: 전체 순차 처리인지, 개별 키 조회인지, 범위 검색인지 정한다.
4. **표현 방식 선택**: 고정 길이, 구분자 기반, 이진 구조 중 상호운용성과 성능에 맞는 방식을 선택한다.
5. **처리 전략 선택**: 스트리밍, 버퍼, 분할, 정렬·병합, 직접 또는 색인 접근을 조합한다.
6. **오류·복구 설계**: 오류 격리, 확인 지점, 재시작, 중복 출력 방지를 설계한다.
7. **대표 자료 시험**: 한글, 구분자 포함 값, 빈 값, 최대 길이, 대용량 경계를 시험한다.
8. **측정 후 보정**: 처리 시간, 메모리, 입출력량, 오류율을 측정해 블록과 분할 크기를 조정한다.

### 9.2 판단 기준

| 판단 기준 | 확인 질문 |
|---|---|
| 데이터 양 | 메모리에 전체 적재 가능한가, 분할이 필요한가 |
| 접근 패턴 | 전체 순차인가, 키 직접 조회인가, 둘 다 필요한가 |
| 상호운용성 | 송신·수신 환경이 같은 구조와 인코딩을 해석하는가 |
| 레코드 특성 | 길이가 일정한가, 구분자가 값에 포함되는가 |
| 변경 빈도 | 색인이나 직접 구조 유지 비용을 감당할 수 있는가 |
| 순서 요구 | 원래 순서나 키 정렬을 보존해야 하는가 |
| 복구 요구 | 어느 단위에서 재시작해야 중복과 손실이 없는가 |
| 보안 | 암호화, 접근 통제, 임시 파일 보호가 필요한가 |
| 처리 창 | 허용 시간 안에 읽기·변환·쓰기를 끝낼 수 있는가 |

## 10. 실전 예시

매일 고객 변경분을 전달하는 파일 사양을 정한다고 하자.

- 첫 행은 헤더이며 파일 버전과 기준일을 가진다.
- 이후 레코드는 구분자 기반이고 고객번호, 이름, 상태, 수정일시를 가진다.
- 마지막 행은 트레일러이며 데이터 레코드 수를 가진다.
- 이름에는 구분자나 줄바꿈이 포함될 수 있다.
- 파일 크기는 메모리보다 클 수 있다.

적용 판단은 다음과 같다.

1. 이름의 구분자와 줄바꿈을 처리할 수 있는 인용 규칙을 명시한다.
2. 송수신 인코딩과 수정일시 표현, NULL 표현을 확정한다.
3. 파일 전체를 메모리에 넣지 않고 레코드 스트리밍으로 읽는다.
4. 헤더의 버전이 지원 범위인지 먼저 확인한다.
5. 데이터 레코드 수와 트레일러 수를 비교한다.
6. 오류 행은 레코드 번호와 원인만 안전하게 격리한다.
7. 일정 레코드 단위로 확인 지점을 남기되 출력 중복을 막을 커밋 상태를 함께 기록한다.
8. 정상 완료 후 임시 출력 파일을 최종 파일로 전환한다.

이 사례에서 단순 문자열 분리는 적절하지 않다. 이름 안의 구분자와 줄바꿈을 제대로 처리할 파서가 필요하다. 반면 특정 키를 반복적으로 임의 조회할 요구가 없다면 직접 파일 구조를 추가할 이유는 약하다.

## 11. 시험 함정

1. **고정 길이의 길이를 항상 문자 수로 해석**: 사양이 바이트 수인지 문자 수인지 확인한다.
2. **구분자만 기준으로 단순 분리**: 인용된 값 안의 구분자와 줄바꿈을 고려한다.
3. **빈 문자열, 공백, NULL, 0을 같은 값으로 취급**: 업무 의미와 파일 사양을 따른다.
4. **직접 파일은 충돌이 없다고 생각**: 해시 기반 접근에는 충돌 처리 전략이 필요하다.
5. **순차 파일은 언제나 느리다고 단정**: 전체 일괄 읽기에는 효율적일 수 있다.
6. **파일 전체를 메모리에 올려야 처리 가능하다고 생각**: 스트리밍과 외부 정렬을 사용할 수 있다.
7. **분할하면 자동으로 병렬 안전하다고 생각**: 경계 중복·누락, 순서, 출력 결합을 통제해야 한다.
8. **해시 일치가 업무 데이터 정확성을 증명한다고 생각**: 바이트 무결성과 업무 의미 검증은 다르다.
9. **특정 파일 확장자만 보고 내부 형식을 단정**: 실제 사양과 헤더를 확인한다.

### 문제 2

순차 접근, 직접 접근, 색인 순차 접근이 적합한 상황을 하나씩 쓰시오.

## 13. 정답과 해설

### 정답 1

고정 길이는 위치와 폭으로 필드를 나누므로 길이 초과와 문자·바이트 단위를 주의한다. 구분자 기반은 특정 문자로 경계를 나누므로 값 안의 구분자, 따옴표, 줄바꿈과 빈 필드 규칙을 주의한다.

### 정답 2

순차 접근은 전체 일괄 변환, 직접 접근은 특정 키의 반복 조회, 색인 순차 접근은 순차 처리와 키 또는 범위 검색을 함께 요구하는 상황에 적합하다.

### 정답 3

한 문자가 인코딩에 따라 여러 바이트가 될 수 있어 바이트 기준 위치를 문자 수로 자르면 뒤 필드가 밀리거나 문자 중간이 잘릴 수 있기 때문이다.

### 정답 4

필드 값 안의 구분자를 실제 필드 경계로 오인하여 열 수와 값이 달라질 수 있기 때문이다. 합의된 인용·이스케이프 규칙을 이해하는 파서를 사용한다.

### 정답 5

레코드 스트리밍, 블록 버퍼링, 파일 분할, 외부 정렬 중 두 가지다. 전체 집합이 필요한지에 따라 조합한다.

### 정답 6

레코드 중간 절단 여부, 키 범위의 중복·누락, 조각 결합 순서와 중복 출력 여부 등을 확인한다.

### 정답 7

입력 파일 식별자, 마지막 완료 레코드나 키, 출력 조각, 커밋 완료 여부, 실행 ID를 함께 기록해야 한다. 위치만 기록하면 이미 쓴 결과를 다시 쓸 수 있다.

### 정답 8

예: 데이터 양, 접근 패턴, 상호운용성, 레코드 길이 특성, 변경 빈도, 순서 요구, 복구 요구, 보안, 허용 처리 시간 중 네 가지다.

## 최종 요약

- **파일 처리 기술**은 레코드 구조, 인코딩, 접근 방식, 대용량 입출력과 오류 복구를 함께 다룬다.
- 고정 길이는 위치와 길이 단위, 구분자 기반 형식은 인용·이스케이프와 빈 값 규칙이 핵심이다.
- 순차 접근은 전체 처리, 직접 접근은 키 조회, 색인 순차 접근은 순차와 검색의 결합에 적합하다.
- 대용량 파일은 스트리밍, 버퍼링, 분할, 외부 정렬과 병합으로 제한된 메모리에서 처리할 수 있다.
- **데이터 전환 기술의 적용 절차와 판단 기준**은 계약 확인, 특성 분석, 방식 선택, 복구 설계, 대표 자료 시험, 측정 순으로 적용한다.
- 확장자나 도구 이름이 아니라 데이터 양, 접근 패턴, 상호운용성, 복구·보안·처리 시간 요구를 근거로 선택한다.
