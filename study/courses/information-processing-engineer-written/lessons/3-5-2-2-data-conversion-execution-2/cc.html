FF 원문 제목3-5-2-2. 데이터 검증

01

학습 범위와 목표

이 레슨은 데이터 전환 수행의 마지막 핵심 주제인 데이터 검증과 데이터 전환 수행의 적용 절차와 판단 기준을 다룬다. 원천과 목표의 건수만 맞추는 데서 끝나지 않고 구조, 값, 키, 관계, 집계, 업무 의미가 전환 규칙에 따라 보존되었는지 확인하는 능력이 목표다. 오류 값을 실제로 정제하는 기법과 오류율을 측정하는 상세 방법은 다음 단원의 범위이므로 여기서는 검증 규칙, 증거, 판정과 인수에 집중한다.

학습 후에는 다음을 할 수 있어야 한다.

  • 검증 목표와 통과 기준을 전환 전에 정의한다.
  • 구조·완전성·도메인·무결성·업무 규칙·대사 검증을 구분한다.
  • 건수, 합계, 키 집합, 표본과 전수 검사의 장단점을 설명한다.
  • 원천과 목표의 차이를 허용된 변환과 결함으로 분류한다.
  • 오류 영향과 검증 증거를 근거로 승인·재처리·중단을 판단한다.
02

1. 데이터 검증의 의미

데이터 검증은 전환된 데이터가 사전에 정한 매핑과 업무 규칙을 충족하고 새 시스템에서 사용할 수 있는지 객관적인 증거로 확인하는 활동이다. 전환 프로그램이 정상 종료되었다는 메시지는 검증 결과가 아니다. 프로그램은 기술적으로 성공했어도 일부 행을 누락하거나 잘못된 코드로 바꾸거나 부모와 자식의 연결을 훼손할 수 있다.

검증의 핵심 질문은 다음과 같다.

  • 옮겨야 할 대상이 빠짐없이 옮겨졌는가?
  • 옮기지 말아야 할 대상이 들어오지 않았는가?
  • 값과 자료형이 목표 정의를 만족하는가?
  • 키와 관계가 보존되었는가?
  • 허용된 변환을 제외하면 업무 의미가 같은가?
  • 차이와 예외가 승인된 기준 안에 있는가?

검증은 결함을 발견하는 활동이고, 발견된 값을 수정하는 데이터 정제와는 목적이 다르다. 같은 과정에서 연계될 수 있지만 발견, 원인 분석, 수정, 재검증의 상태를 구분해야 한다.

03

2. 검증 기준은 언제 정하는가

검증 기준은 전환이 끝난 뒤 결과에 맞춰 만드는 것이 아니라 매핑과 수행 계획을 확정할 때 함께 정한다. 사후에 기준을 정하면 발견된 차이를 정당화하는 방향으로 기준이 흔들릴 수 있다.

검증 정의에는 다음을 포함한다.

  • 검증 대상과 제외 범위
  • 원천 기준 시점과 목표 실행 ID
  • 검증 규칙과 계산식
  • 전수 또는 표본 여부와 표본 선정 방식
  • 허용 오차와 예외 승인자
  • 실패 시 재처리·중단 기준
  • 실행 담당자와 업무 승인자
  • 결과 로그와 증거의 보관 위치

허용 오차는 임의의 보편 숫자가 아니다. 금액 잔액은 한 건의 차이도 허용하지 않을 수 있고, 비핵심 설명 데이터는 승인된 예외를 둘 수 있다. 업무 영향과 규정, 복구 가능성을 근거로 정한다.

04

3. 데이터 검증의 유형

3.1 구조 검증

목표 테이블과 열, 자료형, 길이, 필수 여부가 설계와 일치하는지 확인한다. 전환 결과를 넣을 열이 누락되었거나 자료형이 좁아 값이 잘렸다면 값 비교 전에 구조부터 수정해야 한다.

확인 예:

  • 필수 테이블과 열의 존재
  • 자료형과 길이
  • 기본키·외래키·유일성 정의
  • NULL 허용 여부와 기본값
  • 파일이나 테이블의 열 순서가 계약과 일치하는지

3.2 완전성 검증

대상 데이터가 빠짐없이 반영되었는지 확인한다. 전체 건수뿐 아니라 의미 있는 그룹별 건수를 비교해야 한다.

예를 들어 원천 주문 100만 건과 목표 주문 100만 건이 같아도, 정상 주문 1천 건이 빠지고 제외 대상 주문 1천 건이 잘못 들어오면 전체 건수는 같다. 상태별, 기준일별, 조직별 건수와 대상 키 집합을 함께 확인하면 이런 상쇄 오류를 찾을 수 있다.

3.3 유일성 검증

기본키나 업무상 유일해야 하는 식별자가 중복되지 않는지 확인한다. 원천마다 같은 번호 체계를 사용할 때 원천 시스템 식별자를 빼고 결합하면 충돌할 수 있다. 목표의 새 키뿐 아니라 원천·목표 키 대응도 한 원천 행이 여러 목표 행에 잘못 연결되지 않았는지 본다.

3.4 도메인 검증

값이 허용된 형식과 범위를 만족하는지 확인한다.

  • 코드 값이 목표 코드 목록에 존재하는가?
  • 날짜가 유효하고 허용 기간 안에 있는가?
  • 수량과 금액의 부호·범위가 업무 규칙과 맞는가?
  • 필수 값이 NULL이 아닌가?
  • 문자 길이와 형식이 목표 정의를 만족하는가?

자료형 변환에 성공했다는 사실만으로 도메인이 맞는 것은 아니다. 숫자 99가 저장 가능해도 상태 코드의 허용 값이 10, 20, 30뿐이라면 도메인 오류다.

3.5 참조 무결성 검증

자식의 외래키가 존재하는 부모를 참조하는지 확인한다. 부모가 없는 자식, 키 대응 실패, 잘못된 부모 연결을 찾는다. 외래키 열이 NULL을 허용하는 경우에는 NULL이 업무상 선택 관계를 뜻하는지, 변환 실패를 숨긴 값인지 구분한다.

3.6 업무 규칙 검증

여러 열과 테이블을 함께 보아야 하는 의미 규칙을 확인한다.

  • 종료일은 시작일보다 빠를 수 없다.
  • 취소 상태이면 취소일시가 필요하다.
  • 주문 총액은 승인된 계산 규칙에 따른 항목 금액과 일치한다.
  • 활성 계약은 유효한 고객과 상품을 참조해야 한다.

이 규칙은 목표 자료형만으로는 확인할 수 없다. 업무 담당자가 정의와 예외를 승인해야 한다.

3.7 대사 검증

건수, 금액, 수량 같은 통제 합계를 원천과 목표에서 같은 기준으로 계산하여 비교한다. 전환 중 코드 통합이나 단위 변환이 있다면 단순 원본 합계가 아니라 승인된 변환을 적용한 기대값과 비교해야 한다.

대표 대사 항목:

  • 전체 및 그룹별 건수
  • 금액·수량 합계
  • 최솟값·최댓값과 NULL 건수
  • 키 집합의 차집합
  • 상태별 분포
  • 부모별 자식 건수

3.8 기능 연계 검증

전환 데이터가 새 시스템의 핵심 업무 기능에서 올바르게 조회·처리되는지 확인한다. 데이터베이스 값이 맞아도 응용 프로그램이 기대하는 코드나 상태 전이가 다르면 업무가 실패할 수 있다. 검증 시나리오는 조회만이 아니라 승인, 취소, 후속 배치처럼 전환 데이터가 참여하는 핵심 경로를 포함할 수 있다.

05

4. 원천과 목표를 공정하게 비교하기

원천과 목표는 구조와 값이 달라질 수 있으므로 같은 의미로 정규화한 비교 집합을 만든다.

예를 들어 원천 상태 A, B, C를 목표 10, 20, 30으로 변환한다면 목표와 원천 원문을 직접 비교하면 전부 다른 값으로 나온다. 검증용 기대값은 승인된 매핑을 원천에 적용해 만든다.

비교 시 고정할 조건:

  • 같은 기준 시점
  • 같은 포함·제외 범위
  • 같은 코드와 단위 변환 규칙
  • 같은 NULL 해석
  • 같은 소수점 처리와 반올림 위치
  • 같은 시간대와 날짜 경계
  • 같은 중복 처리 기준

금액을 각 행에서 반올림한 뒤 합산하는 것과 합산 후 반올림하는 것은 결과가 다를 수 있다. 문제에 제시된 업무 규칙의 순서를 따른다.

06

5. 전수 검증과 표본 검증

5.1 전수 검증

모든 대상 행이나 규칙을 확인한다. 자동화 가능한 키 중복, 참조 무결성, 코드 유효성, 건수·합계에는 전수 검증이 적합하다. 데이터가 커도 집합 연산으로 수행할 수 있지만 처리 시간과 시스템 부하를 고려해야 한다.

5.2 표본 검증

일부 데이터를 선정하여 상세하게 확인한다. 복잡한 화면 표시, 사람이 판단해야 하는 문서 내용, 모든 경우를 자동화하기 어려운 항목에 유용하다. 무작위 표본만 쓰면 드문 오류를 놓칠 수 있으므로 다음을 함께 고려한다.

  • 경계값과 최대·최소값
  • NULL과 특수 문자
  • 각 코드·상태와 조직
  • 오래된 데이터와 최신 데이터
  • 오류가 많았던 원천
  • 큰 금액이나 업무 중요 고객

표본에서 오류가 없다고 전체에 오류가 없다고 증명되는 것은 아니다. 표본은 전수 검사를 대체하는 만능 방법이 아니라 위험 기반 보완 수단이다.

07

6. 비교 기법

6.1 건수 비교

가장 빠른 기본 확인이지만 단독으로 충분하지 않다. 전체, 필터 범위, 업무 그룹별로 나누고 제외·보류 건수를 식에 포함한다.

예:

원천 대상 건수 = 목표 성공 건수 + 승인된 제외 건수 + 미처리 보류 건수

각 항목의 집합이 겹치지 않는지 확인해야 한다. 같은 행이 성공과 보류에 동시에 집계되면 식만 맞아도 상태가 잘못될 수 있다.

6.2 통제 합계

금액, 수량, 잔액 같은 핵심 수치를 비교한다. 단위와 반올림, 환율 기준, 부호 규칙을 동일하게 적용한다. 서로 다른 오류가 더하고 빼져 전체 합계가 같아지는 상쇄 오류를 막기 위해 그룹별 합계와 건수도 본다.

6.3 키 집합 비교

원천 대상 키를 목표 키 대응표로 변환한 집합과 실제 목표 집합의 차집합을 구한다. 원천에만 있으면 누락 후보, 목표에만 있으면 과다 적재 후보가 된다. 중복 키는 집합 비교에서 사라질 수 있으므로 중복 건수도 별도로 확인한다.

6.4 행 단위 비교

업무 키로 연결한 뒤 열별 기대값과 실제값을 비교한다. 큰 텍스트나 다수 열은 정규화한 값의 해시를 보조 지표로 사용할 수 있다. 해시가 같으면 같은 입력 규칙 아래 바이트 표현이 같을 가능성을 확인할 수 있지만, 검증 규칙 자체가 잘못되었는지는 알 수 없다.

6.5 분포 비교

코드별 빈도, 날짜별 건수, 금액 구간별 건수처럼 분포를 비교하면 전체 건수와 합계가 가리는 구조적 차이를 찾을 수 있다. 원천과 목표 코드 체계가 다르면 매핑 후 같은 범주로 비교한다.

08

7. 데이터 전환 수행의 적용 절차와 판단 기준

7.1 적용 절차

  1. 검증 범위·기준 확정: 대상, 기준 시점, 규칙, 허용 예외와 승인자를 정한다.
  2. 기대 결과 준비: 원천에 승인된 변환 규칙을 적용해 비교 가능한 기대값을 만든다.
  3. 기본 구조 확인: 목표 구조와 실행 버전이 기준선과 같은지 본다.
  4. 자동 검증 수행: 건수, 키, 도메인, 참조, 합계, 업무 규칙을 실행한다.
  5. 표본·기능 확인: 위험 기반 표본과 핵심 업무 시나리오를 확인한다.
  6. 차이 분류: 허용된 변환, 승인된 예외, 전환 결함, 원천 결함, 검증 규칙 오류로 나눈다.
  7. 영향 평가와 조치: 치명도, 범위, 복구 가능성을 보고 재처리·보류·중단을 결정한다.
  8. 재검증: 수정된 범위와 연관 집합을 같은 기준으로 다시 검사한다.
  9. 결과 승인·인계: 통과 증거, 잔여 예외, 책임과 후속 일정을 기록한다.

7.2 판단 기준

7. 데이터 전환 수행의 적용 절차와 판단 기준 · 학습 표 1
판단 관점질문
업무 중요도오류가 금액, 권리, 규제, 핵심 업무에 영향을 주는가
오류 범위한 행인가, 특정 원천인가, 전체 규칙 오류인가
완전성누락·과다 적재가 있는가
정확성승인된 변환 기대값과 일치하는가
무결성키와 관계, 도메인이 유효한가
복구 가능성원인을 고쳐 안전하게 재처리할 수 있는가
시간 제약전환 창 안에 수정·재검증 가능한가
증거 수준결과를 재현할 로그와 기준 버전이 있는가

오류 건수만으로 승인 여부를 정하지 않는다. 고객 잔액 한 건의 오류가 설명 열 수천 건의 공백보다 더 큰 영향을 줄 수 있다. 건수, 치명도, 업무 영향과 확산 범위를 함께 판단한다.

09

8. 검증 결과 기록

검증 보고에는 다음을 포함한다.

  • 실행 ID와 원천·목표 기준 시점
  • 프로그램·규칙·매핑 버전
  • 검증 규칙 ID와 대상 범위
  • 기대값, 실제값, 차이
  • 성공·실패·보류 건수
  • 차이의 분류와 원인
  • 조치, 재처리 실행 ID, 재검증 결과
  • 승인자, 승인 시각, 잔여 위험

“차이 0”만 남기면 어떤 규칙으로 무엇을 비교했는지 재현할 수 없다. 쿼리나 규칙 식별자, 입력 기준과 결과 파일 위치를 남긴다. 민감한 원문 값을 보고서에 불필요하게 노출하지 않는다.

10

9. 실전 예시: 계약 데이터 검증

전환 규칙:

  • 기준일 현재 유효하거나 보존 대상인 계약만 옮긴다.
  • 원천 상태 A, C, E는 목표 상태 10, 20, 30으로 바꾼다.
  • 금액은 행 단위로 정해진 소수 자릿수에 반올림한다.
  • 고객 키는 승인된 키 대응표로 변환한다.

검증 흐름:

  1. 원천에서 포함 조건을 적용한 계약 건수를 계산한다.
  2. 코드 매핑과 반올림을 적용한 검증용 기대 집합을 만든다.
  3. 목표 계약의 실행 ID 범위를 고정한다.
  4. 전체·상태별·월별 건수와 금액 합계를 비교한다.
  5. 원천 계약번호와 목표 키 대응 집합의 누락·과다를 찾는다.
  6. 목표 상태가 허용 코드인지, 고객 외래키가 존재하는지 전수 확인한다.
  7. 시작일·종료일 관계와 취소 상태의 필수 값을 확인한다.
  8. 경계일, 큰 금액, NULL, 각 상태를 포함한 표본을 업무 화면에서 확인한다.
  9. 차이를 규칙 오류, 전환 오류, 승인 예외로 분류한다.
  10. 수정 후 같은 검증 규칙을 다시 실행하고 결과를 연결한다.

전체 건수와 총액이 같더라도 특정 계약의 고객 연결이 바뀌었다면 검증 실패다. 반대로 원천 코드와 목표 코드가 다르더라도 승인된 매핑의 결과라면 정상 차이다.

11

10. 시험 함정

  1. 프로그램 정상 종료를 검증 성공으로 판단: 결과 데이터의 구조와 의미를 별도로 확인한다.
  2. 전체 건수만 같으면 완전하다고 판단: 누락과 과다 적재가 상쇄될 수 있다.
  3. 원천 값과 목표 값을 무조건 직접 비교: 코드·단위·키 변환을 적용한 기대값과 비교한다.
  4. 표본 무오류를 전체 무오류로 일반화: 자동화 가능한 핵심 규칙은 전수 검증하고 표본은 보완한다.
  5. 합계가 같으면 행도 같다고 판단: 상쇄 오류를 막기 위해 키와 그룹별 분포를 확인한다.
  6. 해시 일치를 업무 규칙의 타당성으로 해석: 같은 비교 입력임을 돕는 지표일 뿐 규칙의 정확성을 보장하지 않는다.
  7. NULL 외래키를 전부 정상 선택 관계로 처리: 키 변환 실패가 NULL로 숨겨졌는지 확인한다.
  8. 오류 건수만으로 치명도 판단: 금액·권리·규제·핵심 업무 영향을 함께 본다.
  9. 수정 후 실패 규칙 하나만 확인: 연결된 집합과 전체 회귀 검증이 필요하다.

11. 확인 문제

데이터 전환 프로그램의 정상 종료가 데이터 검증 성공을 뜻하지 않는 이유는 무엇인가?

문제 2

데이터 검증 유형을 다섯 가지 쓰고 각각 한 문장으로 설명하시오.

문제 3

전체 건수 비교만으로 누락을 찾지 못할 수 있는 사례를 설명하시오.

문제 4

원천 코드 A가 목표 코드 10으로 변환되는 경우 어떤 값끼리 비교해야 하는가?

문제 5

전수 검증과 표본 검증의 적합한 사용 상황을 설명하시오.

문제 6

통제 합계에서 반올림 순서를 고정해야 하는 이유는 무엇인가?

문제 7

문제 8

12. 정답과 해설

정답 1

프로그램은 예외 없이 끝나도 대상 누락, 잘못된 코드 변환, 키 중복, 부모 연결 오류가 있을 수 있기 때문이다. 실행 상태와 결과의 업무 적합성은 별개다.

정답 2

예: 구조 검증은 테이블·열·자료형을, 완전성 검증은 대상 누락·과다를, 유일성 검증은 키 중복을, 도메인 검증은 값의 허용 범위를, 참조 무결성 검증은 부모·자식 연결을 확인한다. 업무 규칙·대사·기능 연계 검증도 가능하다.

정답 3

옮겨야 할 정상 주문 100건이 빠지고 제외해야 할 주문 100건이 잘못 들어오면 전체 건수는 같지만 구성은 틀리다. 그룹별 건수와 키 집합을 비교해야 한다.

정답 4

원천 A를 그대로 목표 10과 비교하지 않고, 승인된 매핑을 원천에 적용해 만든 기대값 10과 실제 목표값 10을 비교한다.

정답 5

키·도메인·참조·건수처럼 자동화 가능한 핵심 규칙은 전수 검증에 적합하다. 사람이 해석해야 하는 화면이나 복잡한 사례는 위험 기반 표본으로 상세 확인한다.

정답 6

각 행을 반올림한 뒤 합산한 값과 합산 후 반올림한 값이 다를 수 있기 때문이다. 원천과 기대값, 목표가 같은 업무 규칙 순서를 사용해야 한다.

정답 7

허용된 변환, 승인된 예외, 전환 결함, 원천 데이터 결함, 검증 규칙 오류 중 네 가지다. 분류에 따라 수정 책임과 재처리 대상이 달라진다.

정답 8

오류의 수보다 업무 영향이 중요하기 때문이다. 잔액이나 권리 상태 한 건의 오류는 비핵심 설명 값 다수의 오류보다 재무·법적 영향이 클 수 있다.

14

최종 요약

  • 데이터 검증은 전환 결과가 구조, 완전성, 유일성, 도메인, 참조, 업무 규칙과 대사 기준을 만족하는지 증거로 확인하는 활동이다.
  • 검증 기준, 기대값 계산, 허용 오차와 실패 행동은 전환 전에 확정한다.
  • 전체 건수만 보지 말고 그룹별 건수, 통제 합계, 키 집합, 행 값, 분포와 업무 기능을 함께 확인한다.
  • 전수 검증은 자동화 가능한 핵심 규칙에, 표본 검증은 복잡하고 사람 판단이 필요한 위험 영역에 사용한다.
  • 데이터 전환 수행의 적용 절차와 판단 기준은 기준 확정, 기대 결과 준비, 자동·표본 검증, 차이 분류, 영향 평가, 재검증, 승인 순으로 적용한다.
  • 승인 판단은 오류 건수뿐 아니라 업무 중요도, 범위, 복구 가능성, 시간과 증거 수준을 함께 고려한다.
