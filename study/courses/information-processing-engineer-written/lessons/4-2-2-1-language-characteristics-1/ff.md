# 4-2-2-1. 절차적 프로그래밍 언어 · 객체지향 프로그래밍 언어

## 학습 목표와 범위

이 레슨은 명령과 처리 절차를 중심으로 문제를 푸는 **절차적 프로그래밍 언어**와 객체의 책임과 협력으로 시스템을 구성하는 **객체지향 프로그래밍 언어**의 특성을 비교한다. 학습 후에는 절차적 언어의 순차·선택·반복과 함수 분해, 객체지향의 추상화·캡슐화·상속·다형성·동적 바인딩을 설명하고, 같은 요구를 두 관점으로 모델링하며 결합도·응집도·변경 영향을 판단할 수 있어야 한다.

다음 레슨의 스크립트 언어와 선언형 언어는 다루지 않는다. 특정 언어를 하나의 패러다임으로만 고정하지 않는다. 많은 현대 언어는 절차적 코드와 객체지향 기능을 함께 지원하므로, 이름보다 실제로 사용하는 구조와 설계 원리를 본다.

## 프로그래밍 패러다임

프로그래밍 패러다임은 문제와 해결 과정을 바라보고 표현하는 대표 관점이다. 절차적 관점은 데이터를 어떤 순서의 명령으로 처리할지를 중심으로 보고, 객체지향 관점은 상태와 행동을 가진 객체들이 어떤 책임을 나누고 협력할지를 중심으로 본다.

두 관점은 우열이 단순히 정해진 대체 관계가 아니다. 계산 절차가 명확한 작은 변환은 절차적 함수로 간결하게 표현할 수 있고, 여러 업무 개념의 상태와 행위가 함께 변하는 큰 시스템은 객체 모델이 변경을 국소화하는 데 도움을 줄 수 있다. 객체지향 프로그램의 메서드 내부도 순차·조건·반복이라는 절차를 사용한다.

## 절차적 프로그래밍 언어의 개념

절차적 프로그래밍 언어(Procedural Programming Language)는 문제 해결 절차를 명령문의 순서와 함수·프로시저 단위로 표현한다. 프로그램 상태를 변수와 자료 구조로 두고, 문장이 그 상태를 읽고 변경한다.

대표 구조는 순차, 선택, 반복이다.

- 순차 구조는 문장을 위에서 아래로 차례대로 실행한다.
- 선택 구조는 조건에 따라 실행할 경로를 고른다.
- 반복 구조는 조건이나 범위에 따라 문장 집합을 되풀이한다.

이 세 구조와 적절한 함수 분해로 임의의 계산 절차를 명확하게 구성할 수 있다는 것이 구조적 프로그래밍의 핵심 생각이다. 무조건 분기처럼 흐름을 임의 위치로 이동시키면 진입·종료 경로를 추적하기 어려워지므로 블록 구조와 단일한 제어 구성을 선호한다.

## 함수와 프로시저 분해

큰 절차를 여러 함수나 프로시저로 분해하면 이름을 통해 의도를 드러내고 반복 로직을 재사용하며 독립 시험할 수 있다. 하향식 설계는 전체 작업을 큰 단계로 나눈 뒤 각 단계를 더 작은 절차로 세분한다.

예를 들어 주문 합계 계산을 다음 단계로 나눌 수 있다.

1. 주문 항목을 읽는다.
2. 각 항목의 수량과 단가를 검증한다.
3. 항목 금액을 합산한다.
4. 할인 규칙을 적용한다.
5. 세금과 최종 금액을 계산한다.

각 단계를 함수로 만들 때 입력, 출력, 변경하는 외부 상태를 분명히 한다. 전역 변수를 여러 함수가 암묵적으로 변경하면 호출 순서에 의존하고 시험이 어려워진다. 필요한 값은 매개변수로 받고 결과를 반환하는 방식이 의존성을 드러낸다.

함수가 한 가지 이유로 변경되도록 책임을 모으고, 세부 구현이 다른 함수에 누출되지 않게 한다. 함수가 지나치게 길거나 매개변수가 너무 많다면 절차 분해 또는 데이터 구조 자체를 다시 살핀다.

## 절차적 방식의 장점과 한계

장점은 실행 순서가 명시적이고 알고리즘을 그대로 옮기기 쉽다는 점이다. 작은 프로그램, 수치 계산, 시스템 수준 처리, 데이터 변환처럼 단계가 중심인 문제에서 효율적이고 예측 가능한 구현이 가능하다. 함수 단위로 모듈화하면 재사용과 시험도 충분히 할 수 있다.

한계는 데이터와 그 데이터를 다루는 함수가 떨어져 있어 규칙이 여러 위치로 퍼질 수 있다는 점이다. 큰 시스템에서 공용 상태를 많은 절차가 변경하면 어떤 함수가 불변식을 깨뜨렸는지 찾기 어렵다. 새로운 데이터 종류가 추가될 때 여러 조건문을 곳곳에서 고쳐야 할 수도 있다.

그러나 이런 문제는 절차적 언어 자체만의 필연은 아니다. 모듈, 추상 자료형, 정보 은닉과 순수 함수로 잘 설계할 수 있다. “절차적 언어는 재사용이 불가능하다”는 설명은 틀리다.

## 객체지향 프로그래밍 언어의 개념

객체지향 프로그래밍 언어(Object-Oriented Programming Language)는 시스템을 상태와 행동을 함께 가진 객체들의 협력으로 표현한다. 객체는 고유 정체성과 상태를 가지며 메시지 또는 메서드 호출에 따라 행동한다.

클래스 기반 언어에서 클래스는 객체가 가질 필드와 메서드의 공통 정의이고, 객체는 그 정의에 따른 구체 인스턴스다. 클래스와 객체를 설계도와 건물에 비유할 수 있지만, 클래스 자체도 실행 시 객체일 수 있는 언어가 있어 비유를 절대 규칙으로 확대하지 않는다.

객체는 내부 상태를 직접 노출하기보다 의미 있는 행위를 제공한다. 계좌 객체에 잔액 필드를 누구나 대입하게 두는 대신 출금 메서드가 금액과 잔액 규칙을 확인하도록 하면 불변식을 한곳에서 유지할 수 있다.

## 추상화

추상화(Abstraction)는 대상의 목적에 중요한 특성과 행동에 집중하고 불필요한 세부를 감추는 것이다. 결제수단이라는 추상 개념은 결제 승인이라는 공통 행동을 제공하되 카드나 계좌의 내부 처리 세부는 각각 다를 수 있다.

추상화는 단순히 코드를 줄이는 것이 아니다. 이용자가 알아야 할 안정적인 계약과 구현자가 바꿀 수 있는 세부의 경계를 만든다. 지나치게 일반적인 추상화는 실제 차이를 숨기고 복잡한 조건을 만들 수 있으므로 실제 변경 축과 대체 가능성을 기준으로 도출한다.

인터페이스나 추상 타입은 “무엇을 할 수 있는가”를 계약으로 표현하고 구현 클래스는 “어떻게 하는가”를 제공할 수 있다. 구체 문법은 언어마다 다르다.

## 캡슐화와 정보 은닉

캡슐화(Encapsulation)는 관련 데이터와 행동을 하나의 단위로 묶고 내부 상태에 대한 접근을 통제한다. 정보 은닉은 변경 가능성이 큰 구현 세부를 외부에서 보이지 않게 하여 영향을 줄이는 설계 원리다.

필드를 비공개로 하고 모든 필드에 단순 읽기·쓰기 메서드를 자동 제공하는 것만으로 충분하지 않다. 쓰기 메서드가 어떤 값이든 허용하면 외부가 여전히 내부 상태를 직접 조립한다. “출금한다”, “주소를 변경한다”처럼 업무 의미를 가진 메서드에서 규칙을 지킨다.

접근 제한자는 공개, 보호, 비공개 등 가시성을 표현할 수 있다. 실제 규칙은 언어에 따라 다르지만 필요한 최소 인터페이스만 공개한다는 원칙이 중요하다.

## 상속

상속(Inheritance)은 기존 타입의 속성과 행동을 바탕으로 더 구체적인 타입을 정의하는 방식이다. 일반화–특수화 관계와 코드 재사용을 지원할 수 있다.

정사각형이 직사각형의 수학적 하위 개념처럼 보여도 폭과 높이를 독립 변경하는 직사각형 인터페이스를 그대로 상속하면 대체 가능성을 깨뜨릴 수 있다. “A는 B이다”라는 말뿐 아니라 B를 기대하는 모든 코드에서 A를 문제없이 사용할 수 있는지 확인한다.

상속 계층이 깊어지면 행동이 어느 상위 클래스에서 왔는지 찾기 어렵고 한 변경이 많은 하위 클래스에 영향을 줄 수 있다. 단순 코드 재사용 목적이라면 객체를 필드로 포함하고 역할을 위임하는 합성을 우선 검토한다.

다중 상속을 지원하는 언어도 있고 인터페이스 구현만 여러 개 허용하는 언어도 있다. 같은 이름 구현이 여러 경로에서 들어오는 모호성 해결 규칙은 언어마다 다르다.

## 다형성과 바인딩

다형성(Polymorphism)은 같은 인터페이스나 메시지에 서로 다른 객체가 각자의 방식으로 응답하는 성질이다. 결제수단의 pay 요청에 카드결제와 계좌이체 객체가 다른 구현을 수행하는 예가 있다.

하위 타입 다형성에서는 상위 계약 변수로 여러 구체 객체를 다룬다. 매개변수 다형성은 타입 매개변수로 여러 타입에 공통인 알고리즘을 표현하고, 오버로딩은 같은 이름을 매개변수 형태에 따라 선택하는 방식이다. 교재 문맥에 따라 다형성 분류가 다를 수 있으므로 어떤 메커니즘을 가리키는지 본다.

바인딩은 호출할 코드와 이름을 연결하는 것이다. 정적 바인딩은 실행 전에 대상을 결정하고, 동적 바인딩은 실행 시 실제 객체 타입에 따라 재정의된 메서드를 선택한다. 객체지향의 실행 시간 다형성은 동적 바인딩과 연결된다.

오버로딩과 오버라이딩을 구분한다.

- 오버로딩은 같은 범위에서 같은 이름을 서로 다른 매개변수 목록으로 여러 개 정의하는 개념이다.
- 오버라이딩은 하위 타입이 상위 타입의 메서드 계약에 맞춰 구현을 재정의하는 개념이다.

정확한 허용 조건과 반환 타입 규칙은 언어마다 다르다.

## 객체 사이 관계

연관은 객체들이 업무상 연결되어 상호작용하는 일반 관계다. 집약과 합성은 전체–부분 관계를 설명한다.

- 집약은 부분이 전체와 독립된 생명주기를 가질 수 있는 느슨한 전체–부분 관계로 설명한다.
- 합성은 부분의 생명주기와 소유가 전체에 강하게 묶인 관계로 설명한다.

팀과 선수는 선수가 팀을 옮겨도 존재할 수 있어 집약으로 볼 수 있고, 주문과 외부에 독립 의미가 없는 주문항목은 합성으로 모델링할 수 있다. 실제 업무 규칙에 따라 달라진다.

의존은 한 객체가 매개변수나 지역 사용처럼 일시적으로 다른 객체의 기능을 사용하는 관계다. 모든 관계를 상속으로 표현하면 결합이 강해진다. “상속보다 합성”은 재사용 대상의 행동을 포함 객체에 위임해 변경 영향을 줄이려는 판단 기준이다.

## 책임과 협력 설계

객체지향 설계에서는 먼저 사용 사례에서 필요한 책임을 찾는다. 책임은 아는 것과 하는 것으로 생각할 수 있다. 주문은 자신의 항목과 상태를 알고 총액 계산·취소 규칙을 수행하고, 저장이나 외부 알림은 별도 협력자에게 요청할 수 있다.

좋은 객체는 관련된 책임이 모인 높은 응집도를 갖고 다른 객체의 내부 표현에 대한 의존은 낮다. 한 객체가 다른 객체의 필드를 연쇄적으로 탐색해 판단하면 내부 구조 변경이 전파된다. 필요한 행동을 그 책임을 가진 객체에게 요청한다.

메시지 계약은 입력, 결과, 오류, 상태 변화와 불변식을 명확히 한다. 객체를 많이 만든다고 자동으로 객체지향적인 것은 아니다. 데이터만 가진 객체와 모든 로직을 가진 거대한 서비스 하나로 나뉘면 캡슐화 이점을 얻기 어렵다.

## 절차적 방식과 객체지향 방식 비교

| 기준 | 절차적 관점 | 객체지향 관점 |
|---|---|---|
| 중심 단위 | 함수·프로시저와 실행 절차 | 객체·클래스의 책임과 협력 |
| 데이터와 행동 | 자료 구조와 처리 함수가 분리될 수 있음 | 상태와 관련 행동을 객체에 묶음 |
| 분해 방식 | 큰 절차를 작은 단계로 하향 분해 | 업무 개념과 역할별 책임 분해 |
| 재사용 | 함수·모듈·라이브러리 | 합성·인터페이스·다형성·상속 |
| 변경 대응 | 처리 단계 추가가 자연스러울 수 있음 | 새로운 구현 타입 추가에 유연할 수 있음 |
| 대표 위험 | 전역 상태와 긴 절차 | 깊은 상속과 과도한 객체·결합 |

데이터 종류는 고정되어 있고 새로운 연산을 자주 추가한다면 절차 또는 함수 중심 구조가 단순할 수 있다. 연산 계약은 안정적이고 새로운 종류가 자주 추가된다면 다형성으로 조건 분기를 줄일 수 있다. 실제 시스템은 두 방식을 조합한다.

## 적용 예시: 배송비 계산

절차적 방식에서는 주문 자료와 배송 유형 코드를 함수에 전달하고 조건문으로 일반·빠른·해외 유형을 나누어 금액을 계산할 수 있다. 알고리즘이 한곳에 보여 작은 유형 집합에서는 명확하다. 유형이 늘면 여러 함수의 조건문을 함께 고쳐야 할 수 있다.

객체지향 방식에서는 ShippingPolicy 인터페이스에 calculate 계약을 두고 각 정책 객체가 계산을 구현할 수 있다. 주문은 구체 타입을 검사하지 않고 정책에 계산을 요청한다. 새 정책을 추가할 때 기존 조건문 변경을 줄일 수 있다.

하지만 정책이 두 종류뿐이고 변화가 거의 없다면 여러 클래스가 불필요한 복잡성이 될 수 있다. 변경 가능성, 규칙 독립성, 시험 필요를 근거로 선택한다.

## 언어 특성 판단 절차

1. 프로그램의 중심 변화가 처리 단계인지 업무 종류인지 파악한다.
2. 데이터 상태와 그 불변식을 누가 책임져야 하는지 정한다.
3. 공통 절차는 함수로, 교체 가능한 행동은 명확한 계약으로 분리한다.
4. 전역 상태와 객체 내부 노출을 최소화한다.
5. 상속 전 실제 대체 가능성을 검증하고 합성을 비교한다.
6. 다형성이 조건 분기를 실제로 줄이는지 확인한다.
7. 작은 단위 시험에서 입력·결과·상태 변화를 검증한다.
8. 언어가 여러 패러다임을 지원하면 문제에 가장 단순한 조합을 사용한다.

## 시험 함정

- 절차적 프로그래밍은 무조건 분기를 많이 쓰는 비구조적 방식과 같은 뜻이 아니다.
- 절차적 언어도 함수와 모듈로 캡슐화·재사용할 수 있다.
- 객체는 데이터만 담는 레코드와 항상 같은 개념이 아니다. 상태와 책임 있는 행동을 가진다.
- 클래스는 정의, 객체는 인스턴스라는 구분이 기본이다.
- 캡슐화는 필드와 메서드를 묶고 접근을 통제하는 것이며 단순 공개 접근자 생성만 뜻하지 않는다.
- 추상화는 중요한 계약에 집중하는 것이지 모든 차이를 제거하는 것이 아니다.
- 상속은 코드 복사 편의만으로 선택하지 않고 대체 가능성을 확인한다.
- 오버로딩은 매개변수 형태가 다른 같은 이름, 오버라이딩은 상위 메서드의 재정의다.
- 다형성은 같은 요청에 객체별 다른 구현이 응답할 수 있는 성질이다.
- 동적 바인딩은 실행 시 실제 객체에 맞는 재정의 구현을 선택하는 것과 연결된다.
- 객체지향 언어의 메서드 내부에도 절차적 제어 구조가 사용된다.
- 특정 언어를 오직 한 패러다임으로만 분류하지 않는다.

## 확인 문제

1. 절차적 프로그래밍의 순차·선택·반복 구조를 설명하라.
2. 하향식 함수 분해의 장점과 전역 상태의 문제점을 쓰라.
3. 객체와 클래스의 차이를 설명하라.
4. 추상화와 캡슐화의 목적을 각각 설명하라.
5. 상속보다 합성을 검토해야 하는 상황을 쓰라.
6. 오버로딩과 오버라이딩을 비교하라.
7. 다형성과 동적 바인딩의 관계를 설명하라.
8. 같은 배송비 계산 요구에서 절차적 조건문과 객체지향 정책 객체 중 무엇을 선택할지 판단 기준을 쓰라.

## 정답과 해설

1. 순차는 문장을 정해진 순서로 실행하고, 선택은 조건에 따라 경로를 고르며, 반복은 조건이나 범위에 따라 문장 집합을 되풀이한다.
2. 큰 절차를 이름 있는 작은 단위로 나눠 이해·재사용·시험하기 쉽다. 전역 상태는 어떤 함수가 언제 값을 바꾸는지 숨겨 호출 순서 의존과 동시성 문제를 만든다.
3. 클래스는 공통 상태와 행동의 정의이고 객체는 실행 중 그 정의에 따라 생성된 구체 인스턴스다. 클래스 기반이 아닌 객체 모델도 있을 수 있다.
4. 추상화는 중요한 계약에 집중해 세부를 감추고, 캡슐화는 관련 상태와 행동을 묶어 내부 접근과 불변식을 통제한다.
5. 단순 코드 재사용만 필요하거나 하위 타입이 상위 계약을 완전히 대체하기 어렵고, 행동을 실행 중 교체해야 할 때 포함과 위임을 이용한 합성을 검토한다.
6. 오버로딩은 같은 이름을 다른 매개변수 목록으로 여러 정의하는 것이고, 오버라이딩은 하위 타입이 상위 메서드 구현을 계약에 맞게 바꾸는 것이다.
7. 다형적 상위 계약 호출에서 동적 바인딩이 실행 시 실제 객체 타입의 오버라이딩 구현을 선택해 객체별 다른 행동을 만든다.
8. 유형 수와 변경 빈도, 규칙의 독립성, 조건 분기의 반복, 팀의 복잡성 비용을 본다. 작고 고정된 규칙이면 함수가, 교체 가능한 유형이 자주 늘면 정책 객체가 유리할 수 있다.

## 최종 요약

- **절차적 프로그래밍 언어**는 순차·선택·반복과 함수·프로시저 분해로 처리 절차를 명시한다.
- 함수 입력·출력과 상태 변경을 분명히 하고 전역 상태를 줄이면 모듈성과 시험 가능성을 높일 수 있다.
- **객체지향 프로그래밍 언어**는 상태와 행동을 객체에 묶고 책임과 협력으로 시스템을 구성한다.
- 추상화·캡슐화·상속·다형성은 각각 계약 집중, 정보 통제, 일반화, 동일 요청의 다양한 구현을 지원한다.
- 상속은 대체 가능성을 확인하고 단순 재사용에는 합성을 비교하며, 오버로딩과 오버라이딩을 구분한다.
- 실제 언어와 시스템은 두 관점을 함께 사용할 수 있으므로 문제의 변화 축과 복잡성에 가장 단순한 구조를 선택한다.
