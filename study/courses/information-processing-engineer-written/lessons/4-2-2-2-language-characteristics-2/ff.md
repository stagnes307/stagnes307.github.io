# 4-2-2-2. 스크립트 언어 · 선언형 언어

## 학습 목표와 범위

이 레슨은 기존 시스템을 연결하고 작업을 빠르게 자동화하는 데 널리 쓰이는 **스크립트 언어**와, 처리 순서보다 원하는 결과나 규칙을 기술하는 **선언형 언어**의 특성을 이해한다. 학습 후에는 스크립트 언어의 실행·배포·동적 특성을 장단점과 함께 설명하고, 선언형 언어의 질의·함수·논리 방식이 절차형 표현과 어떻게 다른지 비교하며, 문제 성격에 맞는 언어 관점을 선택할 수 있어야 한다.

앞 레슨의 절차적·객체지향 언어와 비교하되 그 개념을 반복하지 않는다. 다음 레슨의 라이브러리 및 데이터 입출력, 그다음 레슨의 예외 처리와 프로토타입은 범위를 침범하지 않는다. 현대 언어 구현은 해석·컴파일을 혼합하고 여러 패러다임을 함께 지원하므로 특정 언어 이름만으로 절대적인 분류를 하지 않는다.

## 스크립트 언어의 개념

스크립트 언어(Scripting Language)는 원래 운영체제 셸, 응용 프로그램, 웹 실행환경 같은 호스트 환경의 기능을 제어하거나 여러 도구를 연결해 작업을 자동화하는 데 널리 사용된 언어를 가리킨다. 짧은 코드로 파일 처리, 명령 실행, 시스템 관리, 빌드 보조, 웹 페이지 동작, 데이터 변환 등을 표현하기 좋다.

스크립트는 보통 소스 형태로 배포되어 실행환경이 직접 해석하거나 실행 시 중간 형태로 변환한다. 수정–실행 주기가 짧고 대화형 실행을 지원하는 경우가 많다. 그러나 현대 실행환경은 바이트코드 컴파일이나 실행 중 컴파일을 사용하기도 하므로 “스크립트 언어는 절대로 컴파일되지 않는다”는 설명은 부정확하다.

스크립트 언어와 일반 프로그래밍 언어의 경계는 사용 문맥과 구현에 따라 달라졌다. 같은 언어가 작은 자동화 스크립트부터 대규모 서버 프로그램까지 사용될 수 있다. 코드 길이나 확장자만으로 분류하지 않는다.

## 스크립트 언어의 일반 특성

모든 스크립트 언어에 예외 없이 적용되는 규칙은 아니지만 다음 경향이 있다.

- 별도 빌드 단계를 적게 요구해 작성과 실행 전환이 빠르다.
- 문자열, 목록, 사전 등 자동화에 유용한 고수준 자료 처리를 쉽게 제공한다.
- 운영체제 명령, 파일, 네트워크, 다른 프로그램 API를 연결하는 기능이 풍부하다.
- 대화형 실행이나 즉각적인 결과 확인을 지원하는 경우가 많다.
- 실행 시 타입을 검사하는 동적 타입 방식을 채택한 언어가 많다.
- 메모리 관리를 실행환경이 맡고 풍부한 표준 모듈을 제공하는 경우가 많다.

동적 타입은 스크립트 언어의 필수 정의가 아니다. 정적 검사를 지원하거나 선택적인 타입 표기를 제공할 수 있다. 반대로 컴파일 언어도 동적 타입일 수 있다. “해석 실행”, “동적 타입”, “스크립트 용도”는 서로 관련될 수 있지만 같은 분류 축은 아니다.

## 실행 방식과 이식성

전통적인 인터프리터 방식은 소스 또는 중간 표현을 실행환경이 읽어 명령을 수행한다. 컴파일–실행을 사용자가 별도 단계로 느끼지 않아 빠르게 시험할 수 있다. 오류 중 일부는 해당 실행 경로에 도달했을 때 발견될 수 있다.

소스가 같아도 실행환경 버전, 설치 모듈, 운영체제 명령과 경로가 다르면 결과가 달라진다. “인터프리터만 있으면 항상 이식 가능하다”는 말은 지나치다. 언어 표준 기능만 사용하는지, 외부 명령과 플랫폼 API에 의존하는지, 문자 인코딩과 줄바꿈을 가정하는지 확인한다.

스크립트 첫 줄이나 파일 연결 설정으로 실행환경을 지정하는 체계가 있을 수 있다. 절대 경로를 고정하면 다른 시스템에서 실패하고, 환경 검색에만 맡기면 의도하지 않은 버전이 선택될 수 있다. 조직의 실행 규약과 의존 환경을 명시적으로 관리한다.

## 스크립트 언어의 활용 분야

운영 자동화에서는 파일 정리, 사용자·서비스 상태 점검, 로그 분석, 정기 작업을 스크립트로 묶을 수 있다. 빌드와 시험에서는 여러 도구를 순서대로 호출하고 결과 코드를 검사한다. 데이터 처리에서는 텍스트를 읽어 변환·집계하고 다른 형식으로 출력한다.

웹 환경에서는 클라이언트의 사용자 상호작용이나 서버의 요청 처리를 스크립트 언어로 구현할 수 있다. 응용 프로그램 내장 스크립트는 사용자가 규칙이나 확장 기능을 작성하게 한다. 이 경우 호스트 기능에 접근할 권한을 제한해야 한다.

“접착 언어(glue language)”라는 표현은 서로 다른 프로그램과 구성요소를 연결하는 역할을 강조한다. 표준 입력·출력, 파일, 프로세스, 네트워크 API를 통해 기존 도구를 조합하면 새 프로그램 전체를 다시 만들지 않고 업무 흐름을 자동화할 수 있다.

## 장점과 한계

장점은 짧은 개발 주기, 간결한 표현, 풍부한 모듈, 대화형 시험, 기존 도구 연동이다. 요구가 자주 바뀌는 자동화와 시제품에 유리하다. 소스가 바로 보이므로 운영자가 필요 시 흐름을 조사하기 쉽다는 장점도 있을 수 있다.

한계는 실행환경과 외부 모듈 의존, 일부 오류의 늦은 발견, 대규모 코드의 구조 관리, 소스 노출, 성능·자원 예측 문제다. 그러나 이는 절대적이지 않다. 정적 분석, 타입 주석, 자동 시험, 모듈화, 실행 중 컴파일 등으로 개선할 수 있다.

같은 작업을 매번 빠르게 작성한다는 이유로 입력 검증, 오류 상태, 로그, 권한을 생략하면 운영 스크립트가 큰 장애를 만들 수 있다. 한 번 쓰고 버리는 코드인지 정기 운영 코드인지에 따라 품질 기준을 달리하되, 데이터 삭제나 권한 변경처럼 위험한 작업은 특히 검증과 안전장치가 필요하다.

## 스크립트 보안

외부 입력을 셸 명령 문자열에 그대로 연결하면 명령 주입이 발생할 수 있다. 가능하면 인수 배열을 받는 구조화된 실행 API를 사용하고 허용된 명령과 값을 제한한다. 파일 이름에 공백이나 제어문자가 있다는 사실도 고려한다.

검색 경로가 조작되면 같은 이름의 악성 실행 파일이나 모듈이 먼저 선택될 수 있다. 실행할 도구와 모듈의 출처, 경로, 버전을 관리한다. 관리자 권한으로 스크립트 전체를 실행하기보다 필요한 최소 작업에만 권한을 부여한다.

비밀번호와 토큰을 소스, 명령행 인수, 로그에 남기지 않는다. 스크립트 파일의 쓰기 권한도 제한해야 한다. 실행 권한만 보호하고 파일을 누구나 수정할 수 있다면 공격자가 내용을 바꿔 높은 권한으로 실행시킬 수 있다.

## 선언형 언어의 개념

선언형 언어(Declarative Language)는 원하는 결과가 만족해야 할 조건이나 규칙을 기술하고, 그 결과를 얻는 구체 실행 순서와 제어 흐름의 상당 부분을 처리계에 맡기는 언어 또는 표현 방식이다.

SQL에서 “재직 사원의 부서별 인원수”를 요청하면 사용자는 어떤 인덱스를 먼저 읽고 어떤 조인 알고리즘을 쓸지 일일이 명령하지 않는다. 질의 처리기가 통계와 규칙을 바탕으로 실행 계획을 선택한다. 스타일 규칙 언어에서는 어떤 요소가 어떤 모양을 가져야 하는지 기술하고 적용 순서는 엔진이 결정한다.

선언형은 “아무 절차도 없다”는 뜻이 아니다. 내부 실행기는 반드시 어떤 절차를 수행한다. 사용자가 절차를 직접 명시하는 정도가 낮고 결과의 속성에 집중한다는 뜻이다.

## 절차형 표현과 비교

“숫자 목록에서 짝수의 제곱 합”을 구한다고 하자.

절차형 표현은 합계 변수를 0으로 초기화하고 목록을 반복하며, 값이 짝수이면 제곱을 더하는 순서를 명시한다. 선언형 표현은 목록에서 짝수를 선택하고 제곱으로 변환해 합산한다는 연산 관계를 기술한다. 실제 반복과 병렬화는 실행환경이 정할 수 있다.

| 기준 | 절차형 표현 | 선언형 표현 |
|---|---|---|
| 중심 질문 | 어떻게 순서대로 처리할 것인가 | 어떤 결과·조건을 원하는가 |
| 제어 흐름 | 반복·분기·대입을 직접 명시 | 처리계가 실행 전략을 선택 |
| 상태 변경 | 단계별 가변 상태가 흔함 | 불변 값·규칙·관계 표현이 두드러짐 |
| 최적화 | 개발자가 순서를 많이 결정 | 처리계가 동등한 실행 계획을 선택하기 쉬움 |
| 대표 위험 | 복잡한 상태와 순서 | 숨은 실행 비용과 처리계 의존 |

한 프로그램 안에서도 데이터베이스 질의는 선언적으로 작성하고 응용 흐름은 절차적으로 작성할 수 있다. 분류는 언어 전체보다 코드 부분의 표현 방식에 적용되기도 한다.

## 함수형 언어

함수형 프로그래밍은 계산을 수학적 함수의 평가와 조합으로 표현하는 선언형 계열로 설명되는 경우가 많다. 순수 함수는 같은 입력에 같은 결과를 내고 외부 상태를 변경하지 않는다. 불변 데이터와 고차 함수, 재귀, 함수 합성을 활용한다.

함수를 값처럼 변수에 담거나 인수로 전달하고 결과로 반환할 수 있다. map은 각 원소 변환, filter는 조건에 맞는 원소 선택, reduce 또는 fold는 값을 누적해 하나의 결과로 만드는 고차 연산의 예다.

부작용을 완전히 없애야 실제 프로그램을 만들 수 있는 것은 아니다. 입출력과 상태 변화는 경계를 분리하거나 언어가 제공하는 방식으로 명시한다. 순수한 핵심 계산은 병렬 실행·시험·추론이 쉬워질 수 있다.

함수형 언어라고 실행 순서가 전혀 없거나 항상 느리다는 단정은 틀리다. 엄격 평가와 지연 평가, 최적화 방식은 언어마다 다르다.

## 논리형 언어

논리형 프로그래밍은 사실과 규칙을 선언하고 질의에 맞는 해를 추론하도록 한다. 예를 들어 “가람은 나래의 부모다”, “X가 Y의 부모이면 X는 Y의 조상이다” 같은 사실과 규칙을 정의하고 조상 관계를 질의한다.

개발자가 해를 찾는 반복 순서를 직접 쓰기보다 추론기가 변수에 값을 대입해 조건을 만족하는 해를 탐색한다. 통일, 역추적 같은 메커니즘이 사용될 수 있다. 규칙의 순서와 탐색 전략이 성능이나 종료에 영향을 줄 수 있으므로 선언적이라고 실행 특성을 무시할 수는 없다.

논리형 언어는 규칙 기반 시스템, 제약 만족, 지식 표현에 적합할 수 있다. 수치 반복 처리나 상태가 많은 입출력 업무에서는 다른 패러다임과 조합하기도 한다.

## 질의 언어와 규칙 언어

관계형 질의 언어는 원하는 열, 행 조건, 관계, 그룹 결과를 선언한다. 처리계는 접근 경로와 결합 순서를 선택한다. 사용자가 명시한 결과 의미를 유지하면서 더 효율적인 계획으로 변환할 수 있다는 점이 장점이다.

구성 파일이나 정책 언어도 목표 상태와 규칙을 선언할 수 있다. “서비스 인스턴스가 세 개 존재해야 한다”는 목표를 주면 실행기가 현재 상태와 비교해 필요한 작업을 수행하는 방식이다. 그러나 모든 구성 문법이 순수 선언형인 것은 아니며 템플릿과 명령형 확장을 섞을 수 있다.

마크업 언어는 문서 구조를 기술하고 스타일 규칙은 표현을 선언하지만 일반 목적의 계산 언어와 같은 의미의 프로그래밍 언어인지 문맥을 구분한다. 시험 지문이 HTML을 선언형 언어 사례로 제시한다면 처리 절차보다 구조를 기술한다는 관점에서 판단한다.

## 선언형 방식의 장점

- 구현 절차보다 업무 조건과 결과를 간결하게 표현한다.
- 처리계가 실행 순서, 병렬화, 접근 경로를 최적화할 여지가 크다.
- 가변 상태와 제어 흐름이 줄어 코드 추론과 검증이 쉬워질 수 있다.
- 같은 선언을 다른 실행환경에서 적용할 수 있는 추상화가 생긴다.
- 규칙을 조합해 복잡한 결과를 표현할 수 있다.

선언의 의미가 명확하면 “어떻게”보다 “무엇”을 검토하므로 요구사항과 코드의 거리가 짧아진다. SQL 질의는 원하는 결과 집합을 직접 표현하고, 최적화기는 데이터 규모가 바뀌면 다른 계획을 선택할 수 있다.

## 선언형 방식의 한계

실행 전략을 엔진에 맡기므로 성능 비용이 겉으로 드러나지 않을 수 있다. 작은 선언 한 줄이 매우 큰 탐색 공간이나 전체 데이터 처리를 만들 수 있다. 실행 계획, 평가 전략, 규칙 충돌을 이해해야 한다.

특수한 절차 순서와 세밀한 자원 제어가 핵심이면 선언만으로 표현하기 어렵거나 비직관적인 우회가 필요할 수 있다. 디버깅 때 어느 규칙이 결과를 만들었는지 추적 도구가 필요하다.

처리계마다 지원 기능과 의미가 다르면 이식성이 제한된다. 선언적 문법이라는 사실만으로 성능·정확성·보안이 자동 보장되지 않는다.

## 언어 선택과 조합 기준

1. 문제의 중심이 단계 제어인지 결과 조건·규칙인지 본다.
2. 실행환경과 기존 시스템을 연결하는 자동화인지 판단한다.
3. 성능·자원·응답 시간과 배포 환경 제약을 확인한다.
4. 팀의 경험, 시험·분석 도구, 유지보수 기간을 고려한다.
5. 외부 모듈과 실행환경 버전을 재현할 수 있는지 본다.
6. 안전한 권한과 입력 검증, 오류 추적을 구현할 수 있는지 확인한다.
7. 한 패러다임에 모든 문제를 억지로 맞추지 않고 경계를 정해 조합한다.

예를 들어 데이터 선택과 집계는 질의 언어에 맡기고, 파일 도착 확인과 여러 도구 호출은 스크립트로 조정하며, 복잡한 업무 상태 전이는 일반 프로그램 모듈로 구현할 수 있다. 각 층의 계약과 실패 전달을 분명히 한다.

## 적용 예시: 보고서 자동 생성

매일 판매 보고서를 만든다고 하자. 스크립트는 실행 기준일을 받고 원천 파일 존재 여부를 확인한 뒤 데이터베이스 질의를 호출하고 결과 파일 생성 도구를 실행한다. 각 도구의 종료 상태를 확인하고 로그와 산출물을 정해진 위치에 둔다.

질의는 기준일의 판매를 지역별로 그룹화하고 합계를 구한다는 결과를 선언한다. 어떤 인덱스와 결합 순서를 사용할지는 질의 처리기가 선택한다. 계산 후 파일 이름과 보관 정책을 적용하는 흐름은 스크립트가 조정한다.

사용자 입력을 명령 문자열로 직접 연결하지 않고 구조화된 인수로 전달한다. 실행환경과 모듈 버전을 고정하며 실패 시 불완전 파일을 최종 결과로 공개하지 않는다. 이 사례는 스크립트와 선언형 질의가 경쟁하지 않고 역할을 나눌 수 있음을 보여 준다.

## 시험 함정

- 스크립트 언어는 절대로 컴파일되지 않는다는 설명은 현대 구현에 일반화할 수 없다.
- 스크립트 언어와 동적 타입 언어는 같은 분류가 아니다.
- 인터프리터가 있으면 운영체제·모듈 차이와 무관하게 항상 이식된다고 보지 않는다.
- 짧은 운영 스크립트라도 권한, 입력 검증, 오류 상태와 로그가 필요하다.
- 선언형 언어는 내부 실행 절차가 없다는 뜻이 아니라 사용자가 결과 조건에 집중한다는 뜻이다.
- 선언형은 항상 빠른 것이 아니다. 실행 비용이 감춰질 수 있어 계획과 규모를 본다.
- 함수형의 순수 함수는 같은 입력에 같은 결과를 내고 외부 상태 변경을 피한다.
- 논리형은 사실과 규칙을 선언하고 질의를 만족하는 해를 추론한다.
- 객체지향·절차형·스크립트·선언형을 서로 완전히 배타적인 언어 목록으로만 외우지 않는다.
- HTML 같은 구조 기술 언어를 일반 목적 계산 언어와 같은 의미로 단정하지 않고 지문 문맥을 본다.
- 선언형 규칙의 순서가 코드에 덜 드러나도 실행기의 탐색·평가 전략은 성능과 종료에 영향을 줄 수 있다.

## 확인 문제

1. 스크립트 언어가 기존 시스템의 접착 언어라고 불리는 이유를 설명하라.
2. “스크립트 언어는 컴파일되지 않는다”는 설명이 부정확한 이유는 무엇인가?
3. 스크립트의 이식성을 판단할 때 실행환경 외에 확인할 요소를 세 가지 쓰라.
4. 선언형 언어와 절차형 언어를 중심 질문과 제어 흐름 기준으로 비교하라.
5. 함수형 프로그래밍의 순수 함수와 고차 함수 개념을 설명하라.
6. 논리형 프로그래밍에서 사실·규칙·질의가 어떤 역할을 하는가?
7. 선언형 방식의 장점과 숨은 실행 비용이라는 한계를 설명하라.
8. 일일 보고서 자동화에서 스크립트와 선언형 질의의 역할을 어떻게 나눌 수 있는가?

## 정답과 해설

1. 운영체제 명령, 파일, 데이터베이스, 다른 프로그램 API를 짧은 코드로 호출하고 결과를 연결해 전체 작업을 자동화하기 때문이다.
2. 현대 실행환경은 소스를 바이트코드로 바꾸거나 실행 중 컴파일할 수 있고, 사용자가 별도 빌드 단계를 느끼지 않는 것과 내부 컴파일 여부는 다르기 때문이다.
3. 외부 모듈 버전, 운영체제 명령과 경로, 문자 인코딩, 권한, 환경 변수와 셸 차이 등을 확인한다.
4. 절차형은 어떻게 순서대로 처리할지를 반복·분기·대입으로 명시하고, 선언형은 어떤 결과나 조건을 원하는지 기술해 실행 전략을 처리계에 더 많이 맡긴다.
5. 순수 함수는 같은 입력에 같은 결과를 내고 외부 상태를 바꾸지 않는다. 고차 함수는 함수를 인수로 받거나 결과로 반환해 변환·선택·누적을 조합한다.
6. 사실은 알려진 관계, 규칙은 관계를 도출하는 조건, 질의는 만족하는 값이나 관계를 요청한다. 추론기가 해를 탐색한다.
7. 결과 의미가 간결하고 엔진 최적화 여지가 크지만, 선언 한 줄이 큰 탐색이나 전체 처리를 유발할 수 있어 실행 계획과 평가 전략을 확인해야 한다.
8. 스크립트는 시각·파일·도구 실행과 실패 흐름을 조정하고, 질의는 필요한 행·그룹·합계 조건을 선언한다. 입력·출력과 오류 계약으로 두 영역을 연결한다.

## 최종 요약

- **스크립트 언어**는 짧은 작성–실행 주기와 풍부한 연동 기능으로 자동화·접착 작업에 적합하다.
- 해석 실행과 동적 타입은 흔한 경향일 뿐 절대 정의가 아니며 실행환경·모듈·플랫폼 의존성을 관리해야 한다.
- 운영 스크립트도 최소 권한, 안전한 명령 호출, 비밀 관리, 오류와 로그가 필요하다.
- **선언형 언어**는 처리 순서보다 원하는 결과·조건·규칙을 표현하고 실행 전략을 처리계에 맡긴다.
- 함수형은 함수 평가와 불변성, 논리형은 사실·규칙과 추론, 질의 언어는 결과 관계의 선언을 강조한다.
- 실제 시스템에서는 스크립트로 작업을 조정하고 선언형 질의로 데이터를 처리하는 등 문제에 맞게 패러다임을 조합한다.
