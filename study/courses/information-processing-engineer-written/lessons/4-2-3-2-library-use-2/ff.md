# 4-2-3-2. 예외 처리 · 프로토타입

> **출제 범위 기준**: 이 레슨은 정보처리기사 필기 `프로그래밍언어활용 > 프로그래밍 언어 활용 > 라이브러리 활용`에서 **예외 처리**, **프로토타입**을 다룬다. 여기서 프로토타입은 함수의 이름·매개변수·반환형을 호출 전에 선언하는 함수 원형을 중심으로 설명한다. 프로토타입 기반 객체 모델처럼 다른 문맥에서 쓰이는 동음 용어와 구분하고, 언어별 문법 차이는 공통 원리와 함께 본다.

실행 중 예상 가능한 실패를 모두 `if`문 하나로 숨기거나, 함수 선언 없이 호출 결과를 추측하면 결함을 찾기 어렵다. 예외 처리는 정상 흐름과 실패 흐름을 구조화하고 자원을 안전하게 정리하는 기법이며, 함수 프로토타입은 호출자와 구현 사이의 자료형 계약을 컴파일·분석 단계에서 확인하게 한다.

---

## 1. 오류와 예외의 경계

### 1.1 예외란 무엇인가

**예외(exception)**는 프로그램의 정상 실행 흐름을 계속하기 어려운 비정상 상황을 언어와 런타임이 구조화된 객체·값·제어 흐름으로 표현한 것이다. 파일 없음, 숫자 변환 실패, 배열 범위 초과, 네트워크 시간 초과, 업무 규칙 위반 등이 예외로 표현될 수 있다.

모든 잘못을 예외로 잡을 수 있는 것은 아니다.

- 구문 오류나 정적 자료형 오류는 보통 실행 전에 컴파일러·분석기가 탐지한다.
- 프로세스가 즉시 종료되는 심각한 런타임 장애는 일반 예외 처리로 복구하지 못할 수 있다.
- 논리 오류는 예외 없이 잘못된 결과를 낼 수 있다.
- 사용자의 예상 가능한 선택 오류는 반환 결과나 검증 메시지가 더 적합할 수 있다.

따라서 예외 처리문을 추가했다고 프로그램 정확성이 자동으로 보장되지는 않는다.

### 1.2 오류 코드와 예외

오류 코드는 호출자가 매번 반환값을 검사해야 하고 정상 결과와 실패 정보를 같은 경로로 전달한다. 예외는 실패를 정상 반환과 분리하고 호출 스택의 상위 처리 지점까지 전파할 수 있다.

| 방식 | 장점 | 위험 |
|---|---|---|
| 오류 코드·결과형 | 예상 가능한 실패를 명시적으로 계약화, 제어 흐름이 보임 | 검사 누락, 정상값과 혼동 가능 |
| 예외 | 정상 흐름과 분리, 스택을 따라 전파, 풍부한 원인 정보 | 과도한 사용, 처리 위치 불명확, 숨은 제어 흐름 |

둘 중 하나가 항상 우월한 것은 아니다. 언어 관례, 실패의 예상 가능성, 호출 경계, 복구 책임과 성능을 기준으로 선택한다. 예를 들어 사용자 검색 결과 없음은 정상적인 빈 결과일 수 있지만 저장장치 장애는 예외적 실패다.

## 2. 예외 처리의 기본 구조

### 2.1 탐지·발생·전파·처리

예외 흐름은 다음 단계로 이해한다.

1. 코드나 런타임이 비정상 조건을 탐지한다.
2. 예외를 발생(throw, raise 등)시킨다.
3. 현재 위치에 맞는 처리기가 없으면 호출 스택 위로 전파한다.
4. 일치하는 처리기가 예외를 잡아 복구·변환·기록·종료를 결정한다.
5. 성공·실패와 관계없이 필요한 자원을 정리한다.

일반적인 의사 코드는 다음과 같다.

```text
TRY
    resource = OPEN_RESOURCE()
    data = READ_AND_VALIDATE(resource)
    RETURN transform(data)
CATCH ExpectedFormatError AS error
    THROW DomainInputError("입력 형식이 올바르지 않음", cause=error)
CATCH TemporaryIOError AS error
    RECORD retryable failure safely
    THROW error
FINALLY
    CLOSE resource if it was opened
END
```

키워드 이름과 `finally` 제공 여부는 언어마다 다르다. 공통 목적은 처리 가능한 예외만 의미 있게 다루고 자원 정리를 보장하는 것이다.

### 2.2 try–catch–finally

- `try`: 예외가 발생할 수 있는 최소 범위의 작업
- `catch`/`except`: 특정 예외 유형이나 조건을 처리
- `finally`: 정상 종료, 예외, 중간 반환 여부와 관계없이 수행할 정리

`try` 범위를 함수 전체로 지나치게 넓히면 어느 문장이 실패했는지와 어떤 상태까지 변경되었는지 알기 어렵다. 반대로 너무 작은 범위마다 같은 예외를 잡고 다시 던지면 코드가 장황해진다. 복구 책임과 자원 경계에 맞춰 범위를 정한다.

### 2.3 구체적인 예외부터 처리한다

상속 구조가 있는 예외 언어에서 상위 예외를 먼저 잡으면 뒤의 구체적인 처리기가 도달 불가능해지거나 의도한 복구가 실행되지 않을 수 있다.

```text
잘못된 순서 후보:
    catch Exception
    catch FileNotFound

적절한 순서:
    catch FileNotFound
    catch PermissionDenied
    catch IOProblem
    catch Exception  // 최상위 경계에서만 신중히 사용
```

언어가 컴파일 시 도달 불가능 처리를 거부할 수도 있고, 허용해도 일반 처리기가 먼저 소비할 수 있다.

### 2.4 예외 전파와 재발생

현재 함수가 복구 방법을 모르면 예외를 상위로 전파한다. 정보를 추가하기 위해 다른 예외로 변환할 때 원인 체인(cause)을 보존하면 최초 실패 위치와 업무 맥락을 함께 볼 수 있다.

```text
catch LowLevelDatabaseError as cause:
    throw OrderSaveError(order_id, cause)
```

새 예외를 만들면서 원인을 버리거나 단순 문자열만 남기면 스택과 진단 정보가 끊긴다. 반대로 내부 테이블명, SQL 전문, 개인정보를 사용자 메시지에 그대로 노출해서도 안 된다. 외부에는 안전한 오류 코드·메시지, 운영 로그에는 추적 ID와 필요한 진단을 남긴다.

## 3. 안전한 예외 처리 원칙

### 3.1 처리할 수 있을 때만 잡는다

다음 중 하나를 할 책임이 있는 경계에서 잡는다.

- 대체 값을 사용해 정상적으로 복구
- 제한된 재시도 수행
- 하위 예외를 업무 의미의 상위 예외로 변환
- 트랜잭션 롤백과 자원 정리
- 사용자·프로토콜용 오류 응답 생성
- 프로세스 최상위에서 안전하게 기록하고 종료

아무 동작 없이 예외를 삼키는 빈 처리기는 실패를 성공처럼 보이게 한다.

```text
catch Exception:
    pass  // 원인과 실패 상태가 사라짐
```

로그만 남기고 정상값을 반환하는 것도 실제 복구가 아니면 같은 문제다.

### 3.2 자원 해제를 구조로 보장한다

파일, 소켓, DB 연결, 잠금은 예외 경로에서도 해제해야 한다. `finally`, 범위 기반 자원 관리, `with`/`using`/try-with-resources처럼 언어가 제공하는 구조를 우선한다.

```text
WITH open_file(path) AS file
    return parse(file)
END WITH  // 성공·실패 모두 닫힘
```

정리 도중 새 예외가 발생하면 원래 예외를 가릴 수 있다. 자원 관리 구조가 원인 보존을 어떻게 처리하는지 이해하고, 정리 실패도 필요한 경우 별도로 기록한다.

### 3.3 트랜잭션과 상태를 되돌린다

여러 변경 중 일부가 수행된 뒤 예외가 나면 프로그램 메모리와 외부 자원이 불일치할 수 있다. 데이터베이스 트랜잭션, 임시 파일 교체, 보상 동작 등으로 원자성을 설계한다.

```text
BEGIN TRANSACTION
TRY
    decrease_inventory()
    create_order()
    record_history()
    COMMIT
CATCH
    ROLLBACK
    RETHROW
END
```

예외를 잡았다는 사실만으로 롤백이 자동 수행되는지 여부는 프레임워크·DBMS에 따라 다르다. 트랜잭션 경계와 예외 전파 정책을 확인한다.

### 3.4 재시도는 제한·멱등성·원인을 본다

시간 초과나 일시적인 연결 실패는 재시도 가능할 수 있지만 입력 오류, 권한 없음, 유일성 위반을 반복해도 해결되지 않는다.

- 재시도 가능한 오류를 분류한다.
- 최대 횟수와 전체 시간 제한을 둔다.
- 지수 백오프와 임의 지연으로 동시 폭주를 줄인다.
- 같은 요청을 다시 실행해도 중복 결제가 되지 않도록 멱등성을 설계한다.
- 최종 실패를 숨기지 않고 호출자에게 전달한다.

네트워크 시간 초과는 서버가 작업을 수행하지 않았다는 뜻이 아니다. 응답만 잃었을 수 있으므로 무조건 재요청하면 중복 처리가 생긴다.

### 3.5 단언과 예외를 구분한다

단언(assertion)은 개발 중 “이 상태는 내부 논리상 반드시 참이어야 한다”는 불변조건을 확인하는 용도다. 외부 입력 검증이나 운영 복구를 단언에만 맡기면 실행 설정에 따라 비활성화되거나 사용자에게 부적절한 실패가 될 수 있다. 외부 계약 위반은 명시적 검증과 적합한 오류·예외로 처리한다.

## 4. 예외 유형 설계와 언어 차이

### 4.1 검사 예외와 비검사 예외

일부 언어는 호출자가 선언하거나 처리해야 하는 검사 예외(checked exception)와 그렇지 않은 비검사 예외를 구분한다. 다른 언어는 이 구분을 강제하지 않는다.

- 검사 예외는 복구 가능 실패를 호출 계약에 드러낼 수 있다.
- 너무 많은 검사 예외는 상위 계층에 기계적 전달 코드를 늘릴 수 있다.
- 비검사 예외도 문서화와 경계 처리가 필요하다.

이 구분을 모든 언어의 공통 규칙으로 일반화하지 않는다.

### 4.2 업무 예외와 기술 예외

| 유형 | 예시 | 일반적 처리 위치 |
|---|---|---|
| 입력·검증 | 형식 오류, 범위 위반 | 사용자/API 경계에서 안전한 메시지 |
| 업무 규칙 | 잔액 부족, 상태 전이 불가 | 서비스 계층에서 업무 코드로 변환 |
| 기술·인프라 | DB 연결, 저장공간, 네트워크 | 제한 재시도·운영 기록·상위 전파 |
| 프로그래밍 결함 | NULL 오용, 불가능한 분기 | 숨기지 말고 실패시켜 수정 |

모든 예외를 하나의 `ApplicationError`로만 바꾸면 원인별 복구가 어려워지고, 너무 세분화하면 계약이 복잡해진다. 호출자가 다르게 대응해야 하는지를 기준으로 유형을 나눈다.

### 4.3 예외 안전성 수준

연산 실패 후 객체·데이터 상태를 어떻게 보장할지 생각한다.

- 실패해도 자원 누수와 불변조건 위반이 없어야 하는 기본 보장
- 실패하면 상태가 호출 전과 같은 강한 보장
- 특정 연산은 실패하지 않는다고 계약하는 무실패 보장

모든 연산에 가장 강한 보장을 적용할 필요는 없지만, 부분 변경을 허용하는지와 호출자가 복구할 방법을 명확히 해야 한다.

## 5. 프로토타입의 개념

### 5.1 함수 원형

**프로토타입(function prototype)**은 함수의 이름, 반환 자료형, 매개변수의 개수·순서·자료형을 구현 전에 선언하여 호출 계약을 알리는 것이다. C 계열 문맥에서 대표적으로 사용한다.

```c
double calculate_average(const int values[], size_t count);
```

이 선언을 통해 컴파일러는 다음 호출에서 인수 개수와 자료형, 반환값 사용을 검사할 수 있다.

```c
int samples[] = {10, 20, 30};
double result = calculate_average(samples, 3);
```

함수 정의는 실제 본문을 가진다.

```c
double calculate_average(const int values[], size_t count) {
    long sum = 0;
    for (size_t i = 0; i < count; ++i) {
        sum += values[i];
    }
    return count == 0 ? 0.0 : (double)sum / count;
}
```

선언과 정의의 시그니처가 일치해야 한다. 위 예제에서 빈 입력을 0.0으로 처리하는 정책이 올바른지는 별도 요구사항 문제이며, 프로토타입 자체가 업무 규칙을 설명하지는 않는다.

### 5.2 프로토타입의 목적

- 함수 정의보다 앞에서 안전하게 호출할 수 있다.
- 인수 개수·순서·자료형과 반환형 불일치를 컴파일 단계에서 찾는다.
- 호출자와 구현을 분리해 별도 컴파일을 지원한다.
- 헤더 파일로 여러 소스 파일에 공통 인터페이스를 제공한다.
- 라이브러리의 공개 API와 내부 구현을 구분한다.

프로토타입은 코드 실행 예시용 “시제품(prototype)”이나 JavaScript의 프로토타입 체인과 같은 말이 아니다. 문맥을 보고 구분한다.

### 5.3 선언과 정의

**선언(declaration)**은 이름과 자료형 정보를 컴파일러에 알리고, **정의(definition)**는 함수 본문이나 저장 공간을 실제로 제공한다. 함수 정의도 선언 역할을 할 수 있지만, 다른 파일의 호출자가 정의를 보기 전에 계약을 알아야 하면 별도 프로토타입이 필요하다.

```c
// math_util.h: 공개 선언
#ifndef MATH_UTIL_H
#define MATH_UTIL_H

double calculate_average(const int values[], size_t count);

#endif
```

```c
// math_util.c: 구현
#include "math_util.h"

double calculate_average(const int values[], size_t count) {
    /* implementation */
}
```

구현 파일도 자신의 헤더를 포함하면 선언과 정의가 달라졌을 때 컴파일러가 불일치를 찾는 데 도움이 된다.

### 5.4 매개변수 이름과 자료형

C의 함수 프로토타입에서는 매개변수 이름을 생략할 수 있어도, 의미 있는 이름을 문서화에 쓰면 호출 계약을 이해하기 쉽다. 다만 배열 매개변수 표기는 함수 매개변수 문맥에서 포인터로 조정되는 등 언어 규칙이 있으므로, 배열 길이가 자동으로 전달된다고 착각하지 않는다. 위 예제처럼 포인터/배열과 원소 수를 함께 계약한다.

```c
void process();       // C 문맥에서 매개변수 정보가 명확하지 않을 수 있음
void process(void);   // 매개변수가 없음을 명시
```

정확한 차이는 언어 표준과 컴파일 모드에 따라 확인한다. 시험에서는 프로토타입이 매개변수와 반환형 검사에 쓰인다는 핵심을 우선한다.

### 5.5 값·포인터·const 계약

프로토타입은 전달 방식과 변경 가능성도 드러낸다.

```c
int parse_number(const char *text, int *out_value);
```

- `text`가 가리키는 문자를 함수가 변경하지 않겠다는 의도를 `const`로 표현한다.
- 파싱 성공 여부를 반환값으로, 결과 숫자를 출력 포인터로 전달할 수 있다.
- `out_value`가 NULL일 수 있는지, 실패 시 값이 보존되는지는 문서·검증이 추가로 필요하다.

자료형 선언만으로 모든 의미가 표현되는 것은 아니다. 소유권, 수명, NULL 허용, 단위, 오류 계약을 함께 문서화하고 테스트한다.

### 5.6 가변 인수와 위험

가변 인수 함수는 호출 인수 개수와 자료형 검사가 제한될 수 있다. 형식 문자열과 실제 인수가 다르면 잘못된 메모리 접근이나 보안 문제가 생길 수 있다. 가능하면 자료형 안전한 대안을 사용하고, 정적 분석과 컴파일러 경고를 활성화한다.

## 6. 프로토타입 적용 절차와 판단 기준

1. 함수의 한 가지 책임과 호출 목적을 정의한다.
2. 입력, 출력, 실패 조건을 명세한다.
3. 안정적인 이름과 반환형을 고른다.
4. 매개변수 순서·자료형·수정 가능성·필수 여부를 정한다.
5. 공개 선언은 헤더에, 내부 전용 선언은 구현 범위에 둔다.
6. 구현 파일에서 같은 선언을 포함해 정의와 일치시킨다.
7. 정상·경계·NULL·잘못된 크기와 실패 경로를 테스트한다.
8. 공개 시그니처 변경이 모든 호출자와 바이너리 호환성에 주는 영향을 확인한다.

매개변수가 너무 많고 불리언 플래그가 연속되면 호출자가 순서를 혼동하기 쉽다. 의미 있는 구조체·옵션 객체로 묶거나 책임을 나누는 설계를 검토한다.

```c
// 의미를 읽기 어려운 호출 후보
create_report(data, 1, 0, 1, 30);

// 개념적 개선
struct ReportOptions options = {
    .include_summary = true,
    .include_detail = false,
    .max_rows = 30
};
create_report(data, &options);
```

구체적인 문법은 언어에 따라 다르지만 호출 계약을 명확하게 만든다는 판단은 공통이다.

## 7. 예외 처리와 프로토타입을 연결한다

함수 인터페이스는 성공 값뿐 아니라 실패도 계약해야 한다. C처럼 언어 차원의 예외가 없는 환경에서는 반환 코드, 출력 매개변수, 오류 상태를 설계한다. 예외를 제공하는 언어에서는 어떤 예외가 발생할 수 있고 호출자가 무엇을 복구할지 문서화한다.

| 계약 질문 | 오류 코드 방식 | 예외 방식 |
|---|---|---|
| 성공 결과 | 반환값 또는 출력 매개변수 | 정상 반환값 |
| 실패 구분 | 코드·결과형 | 예외 유형·속성 |
| 자원 정리 | 모든 반환 경로에서 명시 | finally/자원 관리 구조 |
| 호출자 의무 | 반환 코드 검사 | 처리하거나 전파 |
| 원인 보존 | 별도 오류 구조 필요 | 원인 체인 활용 가능 |

프로토타입의 반환형이 `int`라는 사실만으로 0과 음수의 의미를 알 수 없다. 성공·실패 코드, 출력값 유효 조건, 스레드 안전성, 소유권을 함께 정의해야 실제 계약이 된다.

## 8. 테스트와 디버깅 체크리스트

### 8.1 예외 처리 테스트

- 정상 입력에서 예외가 발생하지 않고 올바른 결과를 내는가?
- 각 예상 예외가 정확한 조건에서 발생하는가?
- 더 구체적인 처리기가 선택되는가?
- 예외 후 파일·연결·잠금이 정리되는가?
- 부분 변경이 롤백되거나 문서화된 상태로 남는가?
- 원인 체인과 추적 ID가 보존되는가?
- 사용자 메시지에 내부 비밀이 노출되지 않는가?
- 재시도가 최대 횟수와 멱등성 조건을 지키는가?

### 8.2 프로토타입 검사

- 선언과 정의의 이름·반환형·매개변수형이 일치하는가?
- 호출 전에 적절한 선언이 보이는가?
- 헤더 중복 포함을 안전하게 처리하는가?
- 배열·버퍼 길이와 소유권을 계약했는가?
- `const`와 출력 매개변수 의도가 맞는가?
- 공개 API 변경 시 모든 호출자를 다시 빌드·테스트했는가?
- 컴파일러 경고를 무시하지 않았는가?

## 9. 시험 함정

- 예외를 잡기만 하면 오류가 해결된다고 본다.
- 모든 예외를 빈 처리기로 삼켜 정상값을 반환한다.
- 상위 예외를 먼저 잡아 구체적 처리기를 가린다.
- `finally`가 정상 종료 때는 실행되지 않는다고 본다.
- 시간 초과는 작업 미수행을 의미하므로 무조건 재시도해도 된다고 본다.
- 새 예외로 변환하면서 원래 원인과 스택을 버린다.
- 단언을 외부 입력 검증과 운영 복구의 유일한 수단으로 쓴다.
- 함수 프로토타입을 함수 본문이 있는 정의와 항상 동일하다고 본다.
- 프로토타입이 있으면 배열 길이·소유권·NULL 의미도 자동 전달된다고 본다.
- 함수 원형, 시제품, 프로토타입 기반 객체 상속을 문맥 없이 같은 개념으로 본다.

## 10. 확인 문제

### 문제 1

상위 예외 유형 처리기를 구체적인 하위 예외 처리기보다 먼저 두면 생길 수 있는 문제는 무엇인가?

### 문제 2

네트워크 시간 초과가 발생한 결제 요청을 무조건 재시도하면 안 되는 이유와 필요한 방어 조건을 설명하라.

### 문제 3

함수 프로토타입의 주된 목적을 두 가지 적어라.

### 문제 4

선언과 정의의 차이를 설명하고, 헤더의 프로토타입과 구현 파일의 함수 정의가 달라지지 않게 하는 방법을 적어라.

### 문제 5

다음 중 예외 처리 원칙으로 가장 부적절한 것은 무엇인가?

1. 복구 책임이 있는 경계에서 구체적인 예외를 처리한다.
2. 자원 관리 구조로 성공·실패 경로의 해제를 보장한다.
3. 원인을 알 수 없도록 모든 예외를 같은 정상값으로 바꾼다.
4. 예외 변환 시 원인 체인과 안전한 업무 맥락을 보존한다.

## 정답과 해설

1. **정답:** 상위 처리기가 하위 예외까지 먼저 잡아 버려 구체적인 복구·메시지·재시도 정책이 실행되지 않거나 뒤 처리기가 도달 불가능해질 수 있다.
2. **정답:** 서버가 처리를 완료했지만 응답만 잃었을 수 있어 같은 요청이 중복 결제될 수 있다. 재시도 가능 오류 분류, 제한 횟수·백오프와 함께 요청 키 등 멱등성 보장이 필요하다.
3. **정답:** 호출 전에 함수의 이름·반환형·매개변수 계약을 알리고, 컴파일러가 인수 개수·순서·자료형과 반환값 사용의 불일치를 검사하게 한다. 별도 컴파일과 공개 API 분리에도 쓰인다.
4. **정답:** 선언은 이름과 자료형 계약을 알리고 정의는 실제 함수 본문을 제공한다. 구현 파일이 공개 헤더를 직접 포함하게 하고 경고를 오류로 다루어 시그니처 불일치를 빌드 단계에서 찾는다.
5. **정답: 3번.** 모든 실패를 같은 정상값으로 바꾸면 호출자는 실패를 구분·복구할 수 없고 결함과 장애가 숨는다.

## 11. 최종 요약

- **예외 처리**는 비정상 조건을 탐지·발생·전파·처리하고 성공·실패 경로의 자원을 정리하는 구조다.
- 처리할 수 있는 구체적 예외만 적합한 경계에서 잡고, 복구하지 못하면 원인을 보존해 상위로 전파한다. 빈 처리기와 중복 로그로 오류를 숨기지 않는다.
- `finally`나 범위 기반 자원 관리로 파일·연결·잠금을 정리하고, 부분 변경은 트랜잭션·보상으로 일관성을 지킨다.
- 재시도는 일시 오류, 제한 횟수, 백오프, 멱등성 조건을 갖춰야 한다. 시간 초과가 미처리를 보장하지는 않는다.
- **프로토타입**은 함수 이름, 반환형, 매개변수의 개수·순서·자료형을 구현 전에 선언하는 함수 원형이다.
- 선언과 정의를 구분하고, 공개 헤더를 구현도 포함해 시그니처 일치를 검사한다. 자료형 외의 NULL, 길이, 소유권, 오류 의미도 계약해야 한다.
- 함수 프로토타입과 예외·오류 반환 설계는 호출자와 구현 사이의 성공·실패 계약이라는 한 흐름으로 검토한다.
