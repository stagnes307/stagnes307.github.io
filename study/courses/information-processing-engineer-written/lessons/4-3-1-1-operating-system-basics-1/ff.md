# 4-3-1-1. 운영체제 종류 · 메모리 관리 · 프로세스 스케쥴링

> **출제 범위 기준**: 이 레슨은 정보처리기사 필기 `프로그래밍 언어 활용 > 응용 SW 기초 기술 활용 > 운영체제 기초 활용`의 **운영체제 종류**, **메모리 관리**, **프로세스 스케쥴링**을 다룬다. 다음 레슨의 환경변수·셸 스크립트와는 분리하고, 특정 운영체제 명령보다 운영체제가 자원을 배분하는 공통 원리와 스케줄링 계산 기준에 집중한다.

운영체제는 사용자와 하드웨어 사이에서 CPU, 메모리, 저장장치, 입출력장치를 관리하고 프로그램이 안전하게 실행될 공통 환경을 제공한다. 시험에서는 운영체제의 분류 이름만 외우는 것보다 “어떤 작업 목표 때문에 등장했는가”, “메모리 주소가 어떻게 변환되는가”, “각 스케줄링 정책이 누구에게 유리하거나 불리한가”를 연결해야 한다.

## 1. 운영체제의 역할과 기본 구조

### 1.1 핵심 목적

운영체제의 목표는 다음 네 관점으로 정리할 수 있다.

- **편리성**: 응용 프로그램이 복잡한 하드웨어 차이를 직접 처리하지 않도록 추상화한다.
- **효율성**: 한정된 CPU·메모리·입출력장치의 유휴 시간을 줄이고 처리량을 높인다.
- **공정성**: 여러 사용자와 프로세스가 자원을 독점하지 않도록 정책에 따라 배분한다.
- **보호와 신뢰성**: 사용자 프로그램의 오류가 커널이나 다른 프로세스를 침범하지 않도록 격리하고 복구한다.

처리량만 높이면 대화형 작업의 응답 시간이 나빠질 수 있고, 모든 작업에 같은 시간을 주면 긴급한 실시간 작업의 기한을 놓칠 수 있다. 따라서 운영체제 정책은 시스템 목적에 맞는 지표 사이의 절충이다.

### 1.2 커널과 시스템 호출

**커널(kernel)**은 프로세스·메모리·파일·장치·보호를 담당하는 운영체제의 핵심 부분이다. 응용 프로그램은 하드웨어를 임의로 조작하지 않고 **시스템 호출(system call)**을 통해 커널에 서비스를 요청한다.

```text
사용자 프로그램
  └─ 라이브러리/API
       └─ 시스템 호출 경계
            └─ 커널: 스케줄러·메모리·파일·장치 관리
                 └─ 하드웨어
```

일반 명령을 실행하는 **사용자 모드**와 특권 명령을 실행할 수 있는 **커널 모드**를 구분한다. 시스템 호출, 인터럽트, 예외가 발생하면 통제된 절차로 커널에 진입하고 처리가 끝나면 사용자 모드로 돌아간다. 단순히 “API를 호출하면 항상 새 프로세스가 생긴다”거나 “모드 전환은 곧 문맥 교환이다”라고 보지 않는다. 같은 프로세스 안에서 모드만 전환될 수도 있다.

## 2. 운영체제 종류

운영체제 종류는 서로 완전히 배타적인 제품 분류가 아니다. 한 현대 운영체제가 다중 사용자·시분할·다중 처리·분산 기능을 함께 제공할 수 있다. 분류 기준과 목적을 먼저 확인한다.

### 2.1 처리 방식에 따른 분류

| 종류 | 핵심 방식 | 적합한 상황 | 주의할 점 |
|---|---|---|---|
| 일괄 처리(batch processing) | 작업을 모아 순서대로 처리 | 급여 계산, 정기 집계처럼 즉시 상호작용이 적은 대량 작업 | 개별 작업의 대기·응답 시간이 길 수 있음 |
| 다중 프로그래밍(multiprogramming) | 메모리에 여러 작업을 두고 한 작업이 I/O를 기다리면 다른 작업 실행 | CPU 유휴 시간 감소와 이용률 향상 | 메모리 보호와 작업 선택 정책 필요 |
| 시분할(time sharing) | 짧은 시간 할당량을 번갈아 주어 여러 사용자가 동시에 쓰는 듯 제공 | 터미널·대화형 서비스 | 문맥 교환 비용, 응답 시간 관리 필요 |
| 실시간 처리(real-time) | 정해진 시간 제약 안에 결과를 제공 | 제어·의료·통신 등 기한이 중요한 작업 | 평균 속도보다 최악 실행 시간과 기한 보장이 중요 |
| 다중 처리(multiprocessing) | 둘 이상의 CPU/코어로 작업을 병렬 처리 | 처리량·가용성 향상 | 동기화·캐시 일관성·병렬화 비용 고려 |

**다중 프로그래밍**은 한 CPU가 여러 작업 사이를 전환해 CPU 이용률을 높이는 개념이고, **다중 처리**는 실제로 둘 이상의 처리 장치를 활용하는 개념이다. **멀티태스킹**은 사용 관점에서 여러 작업을 번갈아 또는 병렬로 수행하는 넓은 표현이며, 단일 코어에서는 매우 빠른 전환 때문에 동시에 보일 수 있다.

### 2.2 실시간 운영체제

- **경성 실시간(hard real-time)**: 기한을 넘기면 시스템 실패로 간주될 수 있다. 최악 실행 시간과 스케줄 가능성을 엄격히 분석한다.
- **연성 실시간(soft real-time)**: 기한 초과가 품질 저하를 만들지만 곧바로 치명적 실패를 뜻하지는 않는다.

실시간은 단순히 “매우 빠름”이 아니다. 평균 1ms지만 가끔 1초가 걸리는 시스템보다, 언제나 10ms 안에 끝나는 시스템이 20ms 기한 업무에는 더 적합할 수 있다. 핵심은 **예측 가능성과 기한 충족**이다.

### 2.3 사용 환경에 따른 분류

- **분산 운영체제**: 네트워크로 연결된 여러 컴퓨터의 자원을 협력시켜 사용자에게 통합된 환경을 제공한다.
- **네트워크 운영체제**: 파일·프린터·인증 등 네트워크 서비스를 제공하며, 사용자가 개별 시스템의 존재를 비교적 명확히 인식할 수 있다.
- **임베디드 운영체제**: 특정 장치 목적에 맞춰 작은 자원, 낮은 전력, 높은 신뢰성과 때로는 실시간성을 중시한다.
- **모바일 운영체제**: 터치·센서·무선 통신·앱 격리·배터리 관리 같은 이동 장치 요구를 지원한다.

분산 운영체제와 네트워크 운영체제를 “네트워크를 사용하느냐”로 구분하면 부족하다. 자원과 서비스가 하나의 시스템처럼 얼마나 투명하게 통합되는지가 주요 차이다.

### 2.4 커널 구성 관점

| 구조 | 설명 | 대표 장단점 |
|---|---|---|
| 단일형(monolithic) | 주요 운영체제 서비스를 큰 커널 공간에서 실행 | 호출이 빠를 수 있으나 결합도와 장애 영향이 커질 수 있음 |
| 계층형(layered) | 기능을 계층으로 나누고 인접 계층 인터페이스로 구성 | 이해·검증이 쉬우나 계층 통과 비용과 경계 설계 필요 |
| 마이크로커널 | 최소 기능만 커널에 두고 파일·장치 등 서비스를 사용자 공간 서버로 분리 | 격리·확장성이 좋지만 메시지 전달·전환 비용 가능 |
| 모듈형 | 핵심 커널에 필요한 기능을 동적으로 추가·제거 | 성능과 확장성의 균형, 모듈 인터페이스와 신뢰 관리 필요 |

실제 운영체제는 여러 구조를 혼합하므로 제품 이름 하나를 오직 한 구조로 과도하게 단정하지 않는다.

## 3. 메모리 관리의 기초

### 3.1 논리 주소와 물리 주소

CPU가 프로세스 관점에서 생성하는 주소를 **논리 주소(가상 주소)**, 실제 주기억장치 위치를 **물리 주소**라고 한다. 메모리 관리 장치(MMU)가 페이지 테이블 같은 자료구조를 참고해 주소를 변환한다.

```text
CPU의 가상 주소
  → MMU와 변환 캐시(TLB)
  → 페이지 테이블 확인
  → 물리 주소
  → 주기억장치 접근
```

각 프로세스에 독립된 주소 공간을 제공하면 같은 가상 주소라도 다른 물리 프레임에 연결할 수 있다. 이는 재배치와 보호를 쉽게 한다. **TLB(Translation Lookaside Buffer)**는 최근 주소 변환 결과를 저장하는 고속 캐시이며, 일반 데이터 캐시와 역할이 다르다.

### 3.2 연속 메모리 할당

프로세스를 하나의 연속된 주기억장치 영역에 배치하는 방식이다.

- **고정 분할**: 미리 정한 크기의 구역에 작업을 배치한다. 구현은 단순하지만 작업보다 분할이 커 남는 **내부 단편화**가 생길 수 있다.
- **가변 분할**: 작업 크기에 맞춰 동적으로 영역을 만든다. 사용·반납이 반복되면 작은 빈 공간이 흩어지는 **외부 단편화**가 생길 수 있다.

가변 분할의 빈 공간 선택 방식은 다음과 같다.

| 방식 | 선택 기준 | 일반적 특징 |
|---|---|---|
| 최초 적합(first fit) | 처음 만난 충분한 공간 | 검색이 빠르지만 앞부분에 작은 구멍이 쌓일 수 있음 |
| 최적 적합(best fit) | 들어갈 수 있는 가장 작은 공간 | 큰 공간을 보존하려 하지만 매우 작은 잔여 공간이 늘 수 있음 |
| 최악 적합(worst fit) | 가장 큰 공간 | 큰 잔여 공간을 남기려 하지만 큰 블록을 빠르게 소모할 수 있음 |
| 순환 적합(next fit) | 직전 검색 위치부터 최초 적합 | 앞부분 집중을 줄이나 전체 결과는 부하에 따라 달라짐 |

**압축(compaction)**은 흩어진 사용 영역을 이동시켜 외부 단편화를 큰 연속 공간으로 모으는 방법이다. 이동 비용과 재배치 지원이 필요하다. 페이징은 물리 메모리를 고정 크기 프레임으로 나눠 연속 할당의 외부 단편화를 피한다.

### 3.3 페이징

가상 주소 공간을 같은 크기의 **페이지**, 물리 메모리를 같은 크기의 **프레임**으로 나눈다. 페이지 테이블은 각 가상 페이지가 어느 물리 프레임에 있는지 기록한다.

```text
가상 주소 = 페이지 번호 p + 페이지 안 변위 d
페이지 테이블[p] = 프레임 번호 f
물리 주소 = 프레임 번호 f + 같은 변위 d
```

페이지 크기가 4KiB이고 가상 주소가 13,500이라면 페이지 번호는 `13500 // 4096 = 3`, 변위는 `13500 % 4096 = 1212`이다. 페이지 3이 프레임 8에 있다면 물리 주소는 `8 × 4096 + 1212 = 33,980`이다.

페이징은 외부 단편화를 줄이지만 마지막 페이지에 사용되지 않는 공간이 생기는 내부 단편화 가능성이 있다. 페이지가 작으면 내부 낭비는 줄 수 있지만 페이지 테이블 항목과 관리 횟수가 늘고, 크면 반대 효과가 생긴다.

### 3.4 세그먼테이션

프로그램을 코드·데이터·스택처럼 의미가 있는 가변 크기의 **세그먼트**로 나눈다. 논리 주소는 세그먼트 번호와 변위로 구성되고, 세그먼트 테이블에는 기준 주소와 한계 길이가 저장된다.

세그먼테이션은 논리 단위별 보호·공유에 적합하지만 가변 크기이므로 외부 단편화가 생길 수 있다. 페이징과 세그먼테이션을 결합해 논리 세그먼트를 다시 페이지로 나누는 구성도 가능하다.

| 구분 | 페이징 | 세그먼테이션 |
|---|---|---|
| 분할 크기 | 고정 크기 | 의미에 따른 가변 크기 |
| 사용자 인식 | 보통 투명한 물리 관리 단위 | 코드·데이터 등 논리 단위를 반영 |
| 대표 단편화 | 내부 단편화 | 외부 단편화 |
| 주소 구성 | 페이지 번호 + 변위 | 세그먼트 번호 + 변위 |

## 4. 가상 메모리와 요구 페이징

**가상 메모리**는 실제 주기억장치보다 큰 주소 공간을 프로세스에 제공하고, 당장 필요한 부분만 메모리에 올려 실행하도록 하는 기법이다. 프로그램 전체를 항상 적재할 필요가 없으므로 더 많은 프로세스를 실행할 수 있지만, 보조기억장치 접근이 잦아지면 성능이 급격히 낮아진다.

### 4.1 페이지 부재 처리

요구한 페이지가 주기억장치에 없을 때 **페이지 부재(page fault)**가 발생한다.

1. 하드웨어가 페이지 부재 예외를 발생시켜 커널로 제어를 넘긴다.
2. 운영체제는 주소가 유효한 접근인지 검사한다. 잘못된 주소라면 프로세스에 오류를 전달한다.
3. 빈 프레임을 찾고, 없으면 교체할 희생 페이지를 선택한다.
4. 희생 페이지가 수정되었다면 보조기억장치에 기록한다.
5. 필요한 페이지를 프레임으로 읽고 페이지 테이블·TLB 정보를 갱신한다.
6. 중단된 명령을 다시 실행한다.

페이지 부재는 정상적인 가상 메모리 동작일 수 있다. 반면 유효하지 않은 주소 접근으로 발생하는 보호 오류와 같은 의미는 아니다.

### 4.2 페이지 교체 알고리즘

| 알고리즘 | 선택 원리 | 특징 |
|---|---|---|
| OPT(최적) | 앞으로 가장 오랫동안 사용하지 않을 페이지 교체 | 이론적 최소 부재, 미래 참조를 알아야 해 실제 구현 기준보다 비교용 |
| FIFO | 가장 먼저 들어온 페이지 교체 | 단순하지만 프레임 증가 시 부재가 늘 수 있는 Belady 이상 가능 |
| LRU | 가장 오랫동안 사용하지 않은 페이지 교체 | 지역성을 활용하지만 정확한 최근 사용 추적 비용 필요 |
| LFU | 참조 횟수가 가장 적은 페이지 교체 | 오래 있었던 과거 인기 페이지가 남을 수 있어 시간 감쇠 등 보완 필요 |
| NUR/NRU | 참조 비트와 수정 비트로 최근 사용 가능성이 낮은 페이지 선택 | 적은 하드웨어 정보로 LRU에 근사 |
| Clock(Second Chance) | FIFO 순환 포인터와 참조 비트로 한 번 더 기회 제공 | 구현 비용과 성능의 균형, LRU 근사 |

참조열 `1 2 3 1 4 2`와 빈 프레임 3개를 FIFO로 처리하면 처음 `1,2,3`에서 3번 부재가 발생한다. 다음 `1`은 적중한다. `4`가 오면 가장 먼저 적재된 `1`을 교체하고, 마지막 `2`는 남아 있으므로 적중한다. 총 부재는 4번이다. 교체 순서는 “가장 오래 참조하지 않은 것”이 아니라 “가장 먼저 들어온 것”이라는 점이 FIFO와 LRU의 차이다.

### 4.3 지역성, 스래싱, 작업 집합

- **시간 지역성**: 최근 사용한 데이터·명령을 가까운 미래에 다시 사용할 가능성이 높다.
- **공간 지역성**: 사용한 주소 주변을 곧 참조할 가능성이 높다.

프로세스 수를 지나치게 늘려 각 프로세스가 자주 쓰는 페이지를 유지할 프레임이 부족해지면 페이지 부재와 교체만 반복하는 **스래싱(thrashing)**이 발생한다. 이때 CPU 이용률이 낮다고 다중 프로그래밍 정도를 더 높이면 오히려 악화될 수 있다.

**작업 집합(working set)**은 일정 시간 창에서 프로세스가 실제 참조한 페이지 집합이다. 작업 집합을 유지할 충분한 프레임을 주거나 페이지 부재율을 관찰해 프레임을 조절한다. 전체 요구 프레임이 물리 메모리보다 크면 일부 프로세스를 일시 중지하는 방식도 검토한다.

## 5. 프로세스와 스케줄링의 기반

### 5.1 프로그램, 프로세스, 스레드

- **프로그램**: 저장장치에 있는 수동적인 명령·데이터 집합
- **프로세스**: 프로그램이 실행되며 CPU·주소 공간·파일 같은 자원을 가진 작업 단위
- **스레드**: 프로세스 안에서 CPU를 배정받는 실행 흐름. 같은 프로세스의 코드·데이터·열린 자원을 공유하지만 각자 레지스터와 스택을 가진다.

운영체제는 **PCB(Process Control Block)**에 프로세스 식별자, 상태, 프로그램 카운터, 레지스터, 스케줄링 정보, 메모리·입출력 정보를 저장한다. 실행 프로세스를 바꿀 때 현재 문맥을 PCB 등에 저장하고 다음 문맥을 복원하는 **문맥 교환(context switch)**이 발생한다. 문맥 교환 자체는 사용자 업무를 처리하지 않는 관리 비용이므로 지나치게 잦으면 처리량이 줄 수 있다.

### 5.2 프로세스 상태

```text
생성(new) → 준비(ready) → 실행(running) → 종료(terminated)
                    ↑       │
                    └─ 대기(waiting/blocked) ← I/O 요청·이벤트 대기
```

- 준비 → 실행: 디스패처가 CPU를 배정한다.
- 실행 → 준비: 시간 할당량 만료나 더 높은 우선순위 작업 도착으로 선점된다.
- 실행 → 대기: I/O나 이벤트를 요청해 스스로 CPU를 사용할 수 없게 된다.
- 대기 → 준비: I/O·이벤트가 완료되어 다시 CPU를 기다린다.

I/O를 요청한 프로세스는 보통 곧바로 준비 상태가 아니라 대기 상태로 이동한다. I/O 완료 뒤 준비 큐에 들어가며, 즉시 실행되는지는 스케줄링 정책에 달렸다.

### 5.3 스케줄러 구분

| 구분 | 역할 | 호출 빈도 |
|---|---|---|
| 장기 스케줄러 | 어떤 작업을 시스템에 받아들여 준비 상태로 만들지 결정 | 상대적으로 낮음 |
| 중기 스케줄러 | 메모리 압박 등을 위해 프로세스를 일시 중지·재개(스와핑) | 필요 시 |
| 단기 스케줄러 | 준비 큐에서 다음 CPU 실행 프로세스를 선택 | 매우 높음 |

**디스패처**는 단기 스케줄러가 고른 프로세스에 실제로 CPU 제어를 넘기며, 문맥 교환·모드 전환·실행 위치 이동을 수행한다. 선택 정책과 전달 기능을 구분한다.

## 6. 프로세스 스케쥴링 기준

커리큘럼 표기인 **프로세스 스케쥴링**은 일반적으로 프로세스 스케줄링이라고도 쓴다. 평가 지표를 정확히 계산해야 알고리즘을 비교할 수 있다.

| 지표 | 정의 | 일반 목표 |
|---|---|---|
| 도착 시간 | 프로세스가 준비 큐에 들어온 시각 | 입력 조건 |
| 실행 시간(burst time) | CPU가 실제로 필요한 시간 | 입력 조건 |
| 완료 시간 | 실행을 모두 끝낸 시각 | 작게 |
| 반환 시간(turnaround) | 완료 시간 − 도착 시간 | 작게 |
| 대기 시간 | 반환 시간 − CPU 실행 시간 | 작게 |
| 응답 시간 | 최초 CPU 시작 시간 − 도착 시간 | 대화형에서 작게 |
| 처리량 | 단위 시간당 완료 프로세스 수 | 크게 |
| CPU 이용률 | 전체 시간 중 CPU가 유용한 일을 한 비율 | 크게 |

반환 시간과 응답 시간을 혼동하지 않는다. 선점형 시스템에서 프로세스가 빨리 한 번 실행됐어도 여러 번 밀려 늦게 완료될 수 있으므로 응답은 짧고 반환은 길 수 있다.

### 6.1 비선점과 선점

- **비선점(non-preemptive)**: 실행 프로세스가 종료하거나 대기 상태로 갈 때까지 CPU를 자발적으로 놓도록 한다. 구현과 동기화가 비교적 단순하지만 긴 작업이 짧은 작업을 오래 기다리게 할 수 있다.
- **선점(preemptive)**: 시간 할당량 만료나 우선순위 변화 때 운영체제가 CPU를 회수할 수 있다. 응답성과 긴급 작업 처리가 좋아질 수 있으나 문맥 교환과 공유 자원 동기화 비용이 늘어난다.

알고리즘 이름만으로 판단하지 말고 선점형 변형인지 확인한다. SJF는 보통 비선점형, SRTF는 남은 시간이 더 짧은 작업이 도착하면 선점하는 형태다. 우선순위 스케줄링은 선점형과 비선점형 모두 가능하다.

## 7. 대표 CPU 스케줄링 알고리즘

### 7.1 FCFS

**FCFS(First Come First Served)**는 준비 큐 도착 순서대로 실행하는 비선점 방식이다. 단순하고 먼저 온 작업을 앞세우지만, 긴 CPU 작업 뒤에서 짧은 작업들이 기다리는 **호위 효과(convoy effect)**가 생길 수 있다.

### 7.2 SJF와 SRTF

**SJF(Shortest Job First)**는 예상 CPU 실행 시간이 가장 짧은 작업을 먼저 고른다. 모든 작업이 동시에 준비되고 실행 시간을 정확히 안다는 조건에서 평균 대기 시간을 최소화할 수 있다. 현실에서는 다음 CPU 버스트를 예측해야 하고 긴 작업이 계속 밀리는 기아 문제가 있다.

**SRTF(Shortest Remaining Time First)**는 SJF의 선점형으로, 새 작업의 실행 시간이 현재 작업의 남은 시간보다 짧으면 선점한다.

### 7.3 우선순위 스케줄링

가장 높은 우선순위 작업부터 실행한다. 숫자가 작을수록 높은지 큰수록 높은지는 시스템 정의를 확인해야 한다. 낮은 우선순위 작업이 계속 밀리는 **기아(starvation)**를 줄이기 위해 오래 기다린 작업의 우선순위를 점차 높이는 **에이징(aging)**을 사용할 수 있다.

우선순위 역전은 낮은 우선순위 작업이 가진 잠금을 높은 우선순위 작업이 기다리고, 중간 우선순위 작업이 낮은 작업을 선점하면서 높은 작업까지 지연시키는 현상이다. 우선순위 상속 같은 동기화 정책으로 완화할 수 있다.

### 7.4 Round Robin

**RR(Round Robin)**은 준비 큐를 순환하며 각 프로세스에 **시간 할당량(time quantum)**만큼 CPU를 주는 선점 방식이다. 대화형 시스템에서 공정한 첫 응답을 제공하기 쉽다.

- 할당량이 너무 크면 FCFS에 가까워져 응답성이 낮아질 수 있다.
- 할당량이 너무 작으면 문맥 교환이 지나치게 잦아져 유효 처리 시간이 줄어든다.
- 프로세스가 할당량 전에 I/O를 요청하거나 끝나면 남은 시간을 억지로 사용하지 않고 CPU를 반납한다.

### 7.5 HRN

**HRN(Highest Response-ratio Next)**은 비선점 방식으로 다음 응답률이 가장 높은 작업을 고른다.

```text
응답률 = (대기 시간 + 실행 시간) / 실행 시간
       = 1 + 대기 시간 / 실행 시간
```

짧은 작업을 우대하면서도 오래 기다릴수록 응답률이 올라가 긴 작업의 기아를 완화한다. 예를 들어 대기 6, 실행 2인 A의 응답률은 4이고, 대기 5, 실행 5인 B는 2이므로 A를 먼저 선택한다.

### 7.6 다단계 큐와 다단계 피드백 큐

- **다단계 큐(MLQ)**: 시스템·대화형·일괄 작업처럼 준비 큐를 등급별로 고정 분리하고 큐 사이 및 큐 내부 정책을 둔다. 프로세스가 보통 다른 큐로 이동하지 않는다.
- **다단계 피드백 큐(MLFQ)**: 실행 행동과 대기 시간에 따라 프로세스가 큐 사이를 이동한다. 짧은 대화형 작업은 높은 큐에서 빠르게 처리하고 CPU를 오래 쓰는 작업은 낮은 큐로 내릴 수 있다.

MLFQ는 작업 길이를 미리 정확히 몰라도 행동으로 추정할 수 있지만, 큐 수·할당량·승격·강등 규칙이 복잡하고 낮은 큐 기아를 막는 주기적 우선순위 상향이 필요하다.

## 8. 스케줄링 계산 예제

세 프로세스가 모두 시각 0에 도착하고 CPU 실행 시간이 `P1=6`, `P2=2`, `P3=4`라고 하자. 문맥 교환 시간은 무시한다.

### 8.1 FCFS: 입력 순서 P1, P2, P3

```text
시간 0        6   8       12
     |   P1   | P2|   P3   |
```

| 프로세스 | 완료 | 반환 | 대기 |
|---|---:|---:|---:|
| P1 | 6 | 6 | 0 |
| P2 | 8 | 8 | 6 |
| P3 | 12 | 12 | 8 |

평균 대기 시간은 `(0+6+8)/3 = 14/3 ≈ 4.67`이다.

### 8.2 SJF: P2, P3, P1

```text
시간 0   2       6          12
     | P2|   P3   |    P1     |
```

대기 시간은 각각 `P2=0`, `P3=2`, `P1=6`이고 평균은 `8/3 ≈ 2.67`이다. 이 조건에서는 FCFS보다 평균 대기가 짧다. 하지만 실제 도착 시간이 다르면 시각별 준비 큐에 아직 도착하지 않은 프로세스를 선택할 수 없다.

### 8.3 RR, 시간 할당량 2

```text
0-2 P1 | 2-4 P2(완료) | 4-6 P3 | 6-8 P1
8-10 P3(완료) | 10-12 P1(완료)
```

완료 시간은 `P2=4`, `P3=10`, `P1=12`이다. 모두 시각 0 도착이므로 반환 시간도 같고, 대기 시간은 반환 시간에서 실행 시간을 뺀 `P2=2`, `P3=6`, `P1=6`이다. P2가 일찍 응답·완료하지만 문맥 교환 횟수는 FCFS보다 많다.

계산 문제에서는 다음 순서를 지킨다.

1. 도착 시간과 현재 준비 큐를 시간축에 표시한다.
2. 선점 여부, 우선순위 숫자 방향, 시간 할당량을 확인한다.
3. 간트 차트에 실제 실행 구간을 그린다.
4. 각 완료 시간과 최초 시작 시간을 읽는다.
5. 공식으로 반환·대기·응답 시간을 계산한다.

## 9. 통합 판단 시나리오

### 시나리오 A: 대화형 업무가 배치 뒤에서 멈춘다

긴 배치 하나와 짧은 사용자 요청들이 FCFS 큐에 함께 있고, 긴 배치가 먼저 도착했다. CPU가 긴 작업에 묶여 짧은 요청의 응답이 나빠진다. RR이나 적절한 우선순위·다단계 피드백 큐를 검토하되, 할당량을 너무 작게 잡아 문맥 교환이 폭증하지 않는지 측정한다.

### 시나리오 B: CPU 이용률은 낮고 디스크 활동만 높다

프로세스를 더 많이 투입하기 전에 페이지 부재율과 작업 집합을 확인한다. 프레임 부족으로 스래싱이 발생했다면 다중 프로그래밍 정도를 낮추거나 메모리를 확충하고, 프로세스별 프레임 배분과 접근 지역성을 개선한다.

### 시나리오 C: 제어 작업의 평균 시간은 빠르지만 가끔 기한을 넘긴다

일반 시분할의 평균 응답만으로 실시간 요구를 만족했다고 볼 수 없다. 최악 실행 시간, 인터럽트 지연, 우선순위 역전, 스케줄 가능성과 자원 잠금 상한을 분석한다. 경성인지 연성인지 기한 실패의 결과도 명확히 한다.

### 시나리오 D: 메모리 총 여유는 있지만 큰 작업을 연속 배치할 수 없다

가변 연속 할당에서 빈 공간 합계는 충분하나 흩어져 있다면 외부 단편화다. 압축 가능성과 비용을 검토하거나 페이징 방식으로 연속 물리 배치 요구를 없앤다. 마지막 페이지 내부의 남는 공간 문제와 혼동하지 않는다.

## 10. 자주 틀리는 포인트

1. **다중 프로그래밍과 다중 처리는 같다?** 아니다. 전자는 여러 작업을 메모리에 두고 CPU 이용률을 높이는 방식이고, 후자는 둘 이상의 처리 장치를 활용한다.
2. **실시간 운영체제는 평균 처리 속도가 가장 빠르다?** 핵심은 정해진 기한 안의 예측 가능한 완료다.
3. **페이징은 모든 단편화를 없앤다?** 외부 단편화는 피하지만 마지막 페이지의 내부 단편화가 생길 수 있다.
4. **세그먼테이션은 고정 크기다?** 코드·데이터 같은 의미 단위의 가변 크기 분할이다.
5. **페이지 부재는 항상 불법 접근이다?** 유효한 페이지가 아직 메모리에 없어도 정상적으로 발생할 수 있다.
6. **OPT는 실제 시스템이 미래를 알아 구현하는 알고리즘이다?** 보통 다른 알고리즘 성능을 비교하는 이론적 기준이다.
7. **프레임을 늘리면 FIFO 부재는 항상 줄어든다?** Belady 이상 때문에 증가할 수 있다.
8. **CPU 이용률이 낮으면 프로세스를 무조건 더 넣는다?** 스래싱이면 페이지 부재만 늘어 악화될 수 있다.
9. **대기 시간은 완료 시간과 같다?** `완료−도착−실행`이며, 반환 시간에서 실행 시간을 뺀다.
10. **SJF는 긴 작업의 기아가 없다?** 짧은 작업이 계속 도착하면 긴 작업이 밀릴 수 있다.
11. **RR 시간 할당량은 작을수록 무조건 좋다?** 응답성은 좋아질 수 있지만 문맥 교환 비용이 커진다.
12. **우선순위 숫자가 항상 작을수록 높다?** 문제나 시스템 정의를 확인해야 한다.
13. **응답 시간과 반환 시간은 같다?** 응답은 최초 실행까지, 반환은 전체 완료까지다.
14. **I/O 요청 프로세스는 바로 준비 상태가 된다?** I/O 완료 전에는 대기 상태다.

## 11. 확인 문제

### 문제 1

다중 프로그래밍과 다중 처리의 차이를 CPU 수와 목적 관점에서 설명하라.

### 문제 2

가변 분할에서 총 300MiB의 빈 공간이 여러 곳에 흩어져 있지만 120MiB 연속 요청을 배치하지 못했다. 어떤 단편화이며 가능한 대응은 무엇인가?

### 문제 3

페이지 크기가 1,024바이트이고 가상 주소가 3,500일 때 페이지 번호와 변위를 구하라.

### 문제 4

FIFO와 LRU가 교체 대상을 고르는 기준을 각각 쓰고, 미래 참조가 필요한 알고리즘의 이름을 쓰라.

### 문제 5

프로세스의 도착 시간이 2, 최초 CPU 시작이 5, 완료가 14, CPU 실행 시간 합계가 7이다. 응답·반환·대기 시간을 구하라.

### 문제 6

RR에서 시간 할당량을 지나치게 작게 했을 때 생기는 주된 비용은 무엇인가?

### 문제 7

우선순위 스케줄링에서 낮은 우선순위 프로세스가 무기한 기다리는 문제와 대표 완화 기법을 쓰라.

### 문제 8

스래싱 상태에서 CPU 이용률만 보고 다중 프로그래밍 정도를 높이면 왜 문제가 악화되는가?

## 12. 정답과 해설

### 정답 1

다중 프로그래밍은 한 CPU라도 여러 작업을 메모리에 두고 I/O 대기 중 다른 작업을 실행해 CPU 이용률을 높인다. 다중 처리는 둘 이상의 CPU나 코어가 실제 작업을 병렬 처리하도록 구성해 처리량·가용성을 높인다.

### 정답 2

빈 공간의 합계는 충분하지만 연속 공간이 없어 생기는 **외부 단편화**다. 사용 영역을 이동할 수 있다면 압축으로 큰 연속 공간을 만들거나, 페이징을 사용해 프로세스의 물리적 연속 배치 요구를 없앨 수 있다.

### 정답 3

`3500 // 1024 = 3`, `3500 % 1024 = 428`이므로 페이지 번호 3, 변위 428이다.

### 정답 4

FIFO는 가장 먼저 메모리에 들어온 페이지, LRU는 가장 오랫동안 참조되지 않은 페이지를 고른다. 미래에 가장 늦게 쓰일 페이지를 선택하는 것은 OPT다.

### 정답 5

응답 시간은 `5−2=3`, 반환 시간은 `14−2=12`, 대기 시간은 `12−7=5`다.

### 정답 6

프로세스 사이 문맥 교환이 지나치게 자주 발생해 레지스터·주소 공간 전환 등 관리 비용이 커지고 실제 작업 처리량이 감소한다.

### 정답 7

문제는 **기아**이고, 오래 기다린 프로세스의 우선순위를 점차 올리는 **에이징**으로 완화할 수 있다.

### 정답 8

프로세스별 작업 집합을 유지할 프레임이 더 부족해져 페이지 부재와 디스크 교체가 늘어난다. CPU는 페이지를 기다리느라 더 놀게 되므로 다중 프로그래밍 정도를 낮추거나 프레임을 확보해야 한다.

## 13. 핵심 요약

- 운영체제는 하드웨어를 추상화하고 CPU·메모리·입출력 자원을 효율적이고 안전하게 관리한다.
- 일괄 처리는 대량 작업, 시분할은 대화형 응답, 실시간 처리는 예측 가능한 기한 충족을 중시한다.
- 다중 프로그래밍은 CPU 유휴 감소, 다중 처리는 여러 처리 장치의 병렬 실행이 핵심이다.
- 논리 주소는 MMU와 페이지·세그먼트 테이블을 통해 물리 주소로 변환된다.
- 페이징은 고정 크기로 외부 단편화를 피하지만 내부 단편화가, 세그먼테이션은 가변 논리 단위라 외부 단편화가 생길 수 있다.
- 요구 페이징의 빈번한 부재와 프레임 부족은 스래싱을 일으키며 지역성·작업 집합 관점으로 진단한다.
- FCFS는 단순하지만 호위 효과, SJF/SRTF는 짧은 작업 우대와 기아, RR은 응답성과 문맥 교환의 절충이 핵심이다.
- 우선순위 기아는 에이징으로 완화하며 HRN은 대기와 실행 시간을 함께 반영한다.
- 계산 문제는 간트 차트를 먼저 그리고 `반환=완료−도착`, `대기=반환−실행`, `응답=최초 시작−도착`을 적용한다.
