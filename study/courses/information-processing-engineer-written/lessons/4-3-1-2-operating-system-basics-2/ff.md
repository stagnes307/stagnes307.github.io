# 4-3-1-2. 환경변수 · shell script

> **출제 범위 기준**: 이 레슨은 정보처리기사 필기 `프로그래밍 언어 활용 > 응용 SW 기초 기술 활용 > 운영체제 기초 활용`의 **환경변수**, **shell script**를 다룬다. 앞 레슨의 운영체제·메모리·프로세스 스케줄링 이론은 전제로 삼고, 다음 네트워크 레슨의 프로토콜·계층 내용은 다루지 않는다. 예시는 POSIX 계열 셸을 중심으로 하되 운영체제에 독립적인 구성·자동화 판단 원리를 함께 설명한다.

환경변수는 실행 환경의 설정값을 프로세스에 전달하는 표준 수단이고, 셸 스크립트는 운영체제 명령을 순서·조건·반복으로 묶어 재현 가능한 작업으로 만든다. 둘을 제대로 사용하면 배포·빌드·백업·점검을 자동화할 수 있지만, 인용·오류 처리·비밀정보·실행 권한을 잘못 다루면 수동 명령보다 더 넓은 피해를 낼 수 있다.

---

## 1. 셸과 명령 실행 환경

### 1.1 셸의 역할

**셸(shell)**은 사용자의 명령을 해석해 프로그램을 실행하고, 입출력 연결·변수 치환·파이프·조건·반복 같은 기능을 제공하는 명령 해석기다. 셸 자체는 운영체제 커널과 같지 않다.

```text
사용자 또는 스크립트
  → 셸: 구문 분석·확장·입출력 연결
  → 시스템 호출을 사용하는 명령/프로그램
  → 운영체제 커널
  → 하드웨어와 자원
```

대화형 셸에서는 사용자가 프롬프트에 한 줄씩 입력한다. 비대화형 셸에서는 파일에 적힌 명령을 순서대로 해석한다. 같은 명령도 어떤 셸이 해석하는지에 따라 문법과 확장 규칙이 달라질 수 있으므로 `sh`, `bash`, `zsh`, PowerShell, `cmd.exe`를 무조건 같은 문법으로 보지 않는다.

### 1.2 내부 명령과 외부 명령

- **내부 명령(builtin)**: `cd`, 변수 설정처럼 셸 프로세스 안에서 처리되는 명령이다. 현재 셸의 작업 디렉터리를 바꾸려면 셸 자신이 수행해야 한다.
- **외부 명령**: 실행 파일을 찾아 새 프로세스에서 수행하는 프로그램이다.
- **함수·별칭**: 셸 환경에 등록된 사용자 정의 명령 또는 치환 규칙이다.

어떤 이름을 실행할 때 별칭·함수·내부 명령·실행 파일 중 무엇이 선택되는지는 셸 규칙에 달려 있다. 신뢰할 수 없는 디렉터리를 검색 경로 앞에 두면 의도한 프로그램 대신 같은 이름의 악성 파일이 실행될 수 있다.

## 2. 환경변수의 개념

### 2.1 셸 변수와 환경변수

셸 변수는 현재 셸이 관리하는 이름–값이고, **환경변수(environment variable)**는 프로세스 실행 환경에 포함되어 자식 프로세스에 전달될 수 있는 이름–값이다.

```sh
# 현재 셸 변수 생성
APP_MODE=development

# 자식 프로세스 환경으로 내보내기
export APP_MODE

# 한 명령에만 임시 환경 제공
APP_MODE=test ./run-tests.sh
```

`APP_MODE=development`만 한 값은 현재 셸의 변수지만 일반적으로 `export` 전에는 새 외부 프로그램의 환경에 포함되지 않는다. `export APP_MODE=development`처럼 한 번에 설정할 수도 있다.

### 2.2 프로세스 상속 방향

부모 프로세스가 자식을 시작할 때 환경의 복사본을 전달한다. 자식이 자기 환경변수를 바꿔도 이미 실행 중인 부모의 환경으로 역전파되지는 않는다.

```text
로그인 환경
  └─ 부모 셸: APP_MODE=prod
       ├─ 자식 A: APP_MODE=prod → 자식 안에서 test로 변경
       └─ 자식 B: 여전히 부모가 전달한 prod
```

따라서 스크립트를 별도 프로세스로 실행한 뒤 그 안에서 `cd`하거나 변수를 바꿔도 호출한 셸이 그대로인 것이 보통이다. 현재 셸에 파일 내용을 읽히는 `.` 또는 `source`는 별도 실행과 효과가 다르며, 신뢰할 수 있는 파일에만 사용한다.

### 2.3 이름과 값의 특성

환경변수는 보통 문자열로 전달된다. 숫자·불리언·목록도 프로그램이 문자열을 해석하는 규칙이 필요하다.

- `PORT=8080`: 프로그램이 정수 범위인지 검증해야 한다.
- `DEBUG=false`: 문자열이 존재한다는 이유만으로 참으로 해석하지 않도록 규칙을 정한다.
- `FEATURES=a,b,c`: 쉼표가 값 자체에 포함될 수 있는지 형식을 정의한다.
- 변수가 **없음**, 빈 문자열, 기본값은 서로 다른 상태일 수 있다.

이름의 대소문자 구분, 영구 저장 위치, 사용자/시스템 범위, 경로 구분자는 운영체제와 셸에 따라 다르다. 이식 가능한 스크립트에서는 지원 환경을 명시하고 값 형식을 검증한다.

## 3. 주요 환경변수와 검색 경로

| 변수 예 | 역할 | 주의점 |
|---|---|---|
| `PATH` | 명령 이름으로 실행 파일을 찾을 디렉터리 순서 | 앞쪽 디렉터리가 우선, 빈 항목·상대 경로·쓰기 가능한 경로 위험 |
| `HOME` | POSIX 계열 사용자 홈 디렉터리 | 문자열 결합보다 플랫폼 경로 API 권장 |
| `USER`/`LOGNAME` | 사용자 이름 정보 | 인증·권한 판단의 신뢰 근거로 단독 사용 금지 |
| `SHELL` | 로그인 셸 경로 정보 | 현재 스크립트 해석기가 반드시 이 값과 같지는 않음 |
| `LANG`, `LC_*` | 언어·지역·문자·정렬 형식 | 숫자·날짜·정렬·명령 출력 파싱에 영향 |
| `TMPDIR` | 임시 파일 기본 위치 후보 | 파일명 충돌·권한·심볼릭 링크 공격 방지 필요 |
| `PWD` | 현재 작업 디렉터리 표현 | 실제 경로와 심볼릭 링크 표현 차이 가능 |

### 3.1 PATH 검색

명령에 `/` 같은 경로 구분자가 없으면 셸은 보통 `PATH`의 디렉터리를 앞에서부터 검색한다.

```sh
PATH="/opt/myapp/bin:$PATH"
export PATH
```

이 구성은 사용자 프로그램을 우선 찾도록 한다. 하지만 현재 디렉터리 `.`이나 누구나 쓸 수 있는 디렉터리를 앞에 두면 시스템 명령과 같은 이름의 파일이 가로챌 수 있다. 운영 스크립트는 핵심 명령의 절대 경로를 사용하거나 시작 시 안전한 `PATH`를 명시하고, 실행 대상과 소유권을 확인할 수 있다.

`PATH`는 라이브러리 검색 경로와 같지 않다. 실행 파일, 동적 라이브러리, 언어 패키지, 설정 파일은 각각 다른 검색 규칙을 가질 수 있다.

### 3.2 설정 우선순위

응용 프로그램은 흔히 다음과 같은 우선순위를 정하지만 절대 표준은 아니다.

```text
명령행 인자 > 환경변수 > 프로젝트 설정 파일 > 사용자 설정 > 내장 기본값
```

어떤 값이 최종 적용됐는지 로그나 진단 명령으로 확인할 수 있게 하고, 비밀값 자체는 출력하지 않는다. 개발·테스트·운영에서 같은 변수 이름을 쓰더라도 허용 범위와 기본값을 환경별로 검증한다.

### 3.3 비밀정보와 환경변수

환경변수는 소스 코드에 비밀을 넣는 것보다 분리에는 도움이 되지만 그 자체가 비밀 저장소는 아니다. 프로세스 진단, 오류 보고, 자식 프로세스, 로그, 빌드 산출물에 노출될 수 있다.

- 저장소와 스크립트에 실제 비밀번호·토큰을 하드코딩하지 않는다.
- 전용 비밀 관리 시스템이나 권한이 제한된 파일·프로세스 주입을 사용한다.
- 필요하지 않은 자식에게 비밀 환경을 전달하지 않는다.
- 진단 시 `env` 전체를 무심코 로그에 남기지 않는다.
- 비밀을 명령행 인자로 넘기면 프로세스 목록에 보일 수 있으므로 도구별 안전 입력 방식을 확인한다.

## 4. 변수 확장과 인용

셸은 명령을 실행하기 전에 변수·명령·파일 이름 패턴 등을 확장한다. 안전한 스크립트의 핵심은 문자열과 인자 경계를 보존하는 것이다.

### 4.1 기본 확장

```sh
name="study"
printf '%s\n' "$name"

# 이름 경계를 중괄호로 명확히 함
file="${name}_report.txt"
```

`echo`는 구현별 옵션·이스케이프 해석 차이가 있어 정확한 형식 출력에는 `printf`가 더 예측 가능하다.

### 4.2 작은따옴표, 큰따옴표, 무인용

| 형태 | 일반 의미 |
|---|---|
| `'literal $name'` | 내부를 문자 그대로 취급, 변수 확장 안 함 |
| `"value: $name"` | 변수 확장하되 결과를 한 인자로 보존 |
| `$name` | 확장 후 단어 분리·파일명 패턴 확장이 일어날 수 있음 |

```sh
target="Study Materials"
rm -- "$target/report.tmp"
```

`"$target"`처럼 인용하지 않으면 공백에서 여러 인자로 나뉠 수 있다. 파일명이 `-`로 시작할 가능성이 있으면 지원하는 명령에서 `--`로 옵션의 끝을 표시한다. 단, 모든 명령이 `--`를 지원하는 것은 아니므로 사양을 확인한다.

### 4.3 기본값과 필수값

POSIX 셸의 매개변수 확장으로 누락을 명시적으로 처리할 수 있다.

```sh
# unset 또는 빈 값이면 기본값 사용
mode=${APP_MODE:-development}

# unset 또는 빈 값이면 메시지와 함께 중단
: "${OUTPUT_DIR:?OUTPUT_DIR is required}"
```

기본값을 무조건 두면 운영 설정 누락이 개발 기본값으로 조용히 실행될 수 있다. 안전에 중요한 값은 필수로 검증하고, 편의 설정만 명확한 기본값을 둔다.

## 5. shell script의 구성과 실행

### 5.1 기본 파일

```sh
#!/bin/sh

set -eu

input=${1:?usage: report.sh INPUT_FILE}
printf 'processing: %s\n' "$input"
```

첫 줄의 **셔뱅(shebang)**은 파일을 직접 실행할 때 사용할 해석기를 지정한다. `/bin/sh` 문법으로 작성했다면 특정 Bash 전용 배열·조건 문법을 섞지 않는다. Bash 기능이 필요하면 지원 환경과 해석기를 명확히 지정한다.

실행 방식은 의미가 다를 수 있다.

```sh
chmod u+x report.sh   # 실행 권한 부여
./report.sh data.csv  # 셔뱅에 따라 직접 실행
sh report.sh data.csv # sh가 파일을 해석; 셔뱅 선택을 우회할 수 있음
. ./settings.sh       # 현재 셸에서 읽음; 변수·디렉터리 변경이 남음
```

셸 파일의 확장자는 실행에 필수 조건이 아니다. 실행 권한, 셔뱅, 호출 방식이 중요하다.

### 5.2 위치 매개변수

| 표현 | 의미 |
|---|---|
| `$0` | 스크립트 또는 호출 이름 |
| `$1`, `$2` | 첫째, 둘째 인자 |
| `$#` | 인자 개수 |
| `"$@"` | 각 인자를 원래 경계대로 전달 |
| `"$*"` | 모든 인자를 하나의 문자열처럼 결합 |
| `$?` | 직전 명령의 종료 상태 |
| `$$` | 현재 셸 프로세스 ID |

다른 명령이나 함수에 받은 인자를 그대로 넘길 때는 보통 `"$@"`가 맞다.

```sh
run_tool() {
  printf 'argument count: %s\n' "$#"
  tool-command "$@"
}
```

인자가 `"first value"`, `"second value"` 두 개라면 `"$@"`는 두 인자를 유지한다. 무인용 `$*`나 `$@`는 공백과 패턴 때문에 경계를 잃을 수 있다.

### 5.3 종료 상태

유닉스 계열 명령은 관례적으로 성공 시 0, 실패 시 0이 아닌 종료 상태를 반환한다.

```sh
if validate_config "$config"; then
  printf '%s\n' 'configuration is valid'
else
  status=$?
  printf 'validation failed: %s\n' "$status" >&2
  exit "$status"
fi
```

표준 출력은 정상 결과, 표준 오류는 진단 메시지에 사용한다. 스크립트가 오류를 출력하고도 마지막 명령이 성공해 0으로 끝나지 않도록 의미 있는 종료 상태를 반환한다.

`set -e`는 단순한 “모든 오류에서 무조건 중단” 스위치가 아니다. 조건식·파이프라인·서브셸 등 문맥에 따라 동작이 다를 수 있다. 중요한 실패는 `if ! command; then ...; fi`처럼 의도를 명시하고, 테스트로 확인한다. `set -u`는 설정되지 않은 변수 사용을 오류로 처리하지만 선택 변수에는 기본값 처리가 필요하다.

## 6. 입출력 재지정과 파이프

프로세스는 일반적으로 표준 입력(0), 표준 출력(1), 표준 오류(2)를 사용한다.

```sh
command < input.txt       # 표준 입력을 파일에서
command > output.txt      # 표준 출력을 덮어쓰기
command >> output.txt     # 표준 출력을 이어쓰기
command 2> error.log      # 표준 오류를 파일로
command > all.log 2>&1    # 현재 표준 출력 대상으로 표준 오류도 연결
producer | consumer       # 앞 명령의 표준 출력을 뒤 명령의 표준 입력으로
```

재지정은 왼쪽에서 오른쪽으로 적용되므로 순서가 중요하다. `2>&1 >file`은 먼저 표준 오류를 당시 표준 출력에 연결한 뒤 표준 출력만 파일로 바꾸므로 두 스트림이 모두 파일로 가지 않을 수 있다.

### 6.1 파이프라인의 의미

```sh
generate_report | compress_output > report.gz
```

파이프는 프로그램끼리 중간 파일 없이 스트림을 연결한다. 그러나 기본 셸에서는 파이프라인 전체 종료 상태가 마지막 명령의 상태일 수 있어 앞 명령 실패가 가려질 수 있다. 사용하는 셸의 `pipefail` 지원 여부를 확인하거나 각 단계 결과를 별도로 검증한다.

명령 출력 한 줄을 프로그램 논리로 파싱할 때 로캘·공백·오류 메시지 변경에 취약할 수 있다. 가능하면 구조화 출력 옵션이나 전용 API를 사용하고 `LANG` 같은 환경 영향을 통제한다.

## 7. 조건, 반복, 함수

### 7.1 조건문

```sh
if [ -f "$input" ]; then
  printf 'regular file: %s\n' "$input"
elif [ -d "$input" ]; then
  printf 'directory: %s\n' "$input"
else
  printf 'not found: %s\n' "$input" >&2
  exit 2
fi
```

`[`는 셸 문법처럼 보이지만 인자를 받는 명령이므로 공백이 필요하다. 문자열 비교에는 `=`, 숫자 비교에는 `-eq`, `-lt`, `-gt` 등을 구분한다.

```sh
case ${APP_MODE:-} in
  development|test) debug=true ;;
  production)       debug=false ;;
  *) printf '%s\n' 'invalid APP_MODE' >&2; exit 2 ;;
esac
```

여러 허용 문자열을 분기할 때 `case`가 읽기 쉽고 누락을 줄일 수 있다.

### 7.2 반복문

```sh
for file in "$@"; do
  [ -f "$file" ] || {
    printf 'skip non-file: %s\n' "$file" >&2
    continue
  }
  process_file "$file" || exit 1
done
```

`for file in $(find ...)`처럼 명령 치환 결과를 공백으로 나누면 공백·줄바꿈이 있는 파일명을 망가뜨린다. 파일 목록을 전달할 때는 도구가 제공하는 NUL 구분 방식이나 셸별 안전 배열 기능 등 입력 계약에 맞는 방법을 사용한다.

```sh
attempt=1
while [ "$attempt" -le 3 ]; do
  if fetch_data; then
    break
  fi
  attempt=$((attempt + 1))
done
```

재시도에는 최대 횟수, 대기·백오프, 재시도 가능한 오류 구분이 필요하다. 결제·삭제처럼 부작용이 있는 명령은 멱등성이나 중복 방지 키 없이 무조건 재시도하지 않는다.

### 7.3 함수와 반환

```sh
require_file() {
  path=$1
  if [ ! -r "$path" ]; then
    printf 'not readable: %s\n' "$path" >&2
    return 1
  fi
}

require_file "$input" || exit 2
```

셸 함수의 `return`은 보통 작은 정수 종료 상태를 돌려주며 임의 문자열 반환 기능이 아니다. 데이터는 표준 출력으로 내보내 캡처하거나 호출자가 지정한 파일·변수 규칙을 사용하되, 진단 메시지와 정상 데이터를 섞지 않는다.

## 8. 안전하고 재현 가능한 자동화 절차

### 8.1 입력 검증

1. 필수 환경변수와 인자 존재를 확인한다.
2. 숫자 범위, 허용 문자열, 경로 유형을 검증한다.
3. 경로가 기대한 기준 디렉터리 안인지 정규화해 확인한다.
4. 파일 소유권·권한·심볼릭 링크 조건을 위험도에 맞춰 점검한다.
5. 명령 문자열을 조립해 다시 평가하는 `eval`을 피하고 인자를 분리해 전달한다.

사용자 입력을 다음처럼 명령 문자열에 합치면 명령 구분자나 치환 문법이 실행될 수 있다.

```sh
# 위험한 설계 예: 실제로 사용하지 말 것
eval "tool --name $user_input"

# 인자 경계를 보존
tool --name "$user_input"
```

### 8.2 중간 결과와 원자적 반영

파일을 바로 덮어쓰다가 실패하면 불완전한 결과가 남을 수 있다.

```sh
tmp=$(mktemp) || exit 1
cleanup() { rm -f -- "$tmp"; }
trap cleanup EXIT HUP INT TERM

generate_config > "$tmp" || exit 1
validate_config "$tmp" || exit 1
mv -- "$tmp" "$output" || exit 1
trap - EXIT HUP INT TERM
```

실제 원자성은 임시 파일과 대상이 같은 파일시스템인지, `mv`가 기존 파일을 어떻게 처리하는지, 권한·소유권을 보존해야 하는지에 달려 있다. 중요한 파일은 백업과 복구 절차도 둔다.

### 8.3 권한 최소화

- 전체 스크립트를 관리자 권한으로 실행하기보다 필요한 작은 단계만 승격한다.
- 쓰기 대상 경로와 실행 파일을 명시적으로 제한한다.
- 임시 파일은 예측 가능한 이름 대신 안전한 생성 도구를 사용한다.
- 로그·산출물의 기본 권한을 확인하고 민감정보가 있다면 더 제한한다.
- 다운로드한 스크립트를 검토 없이 파이프로 셸에 바로 넘기지 않는다.

### 8.4 관찰 가능성과 건식 실행

운영 자동화는 무엇을 할지 미리 보여주는 `--dry-run`, 단계별 로그, 시작·종료 시각, 대상 수, 오류 원인을 제공하면 안전하다. 다만 디버그 추적 `set -x`는 확장된 토큰·비밀번호를 로그에 노출할 수 있으므로 비밀을 다루는 구간에서는 사용하지 않거나 마스킹한다.

## 9. 실전 예제: 입력 디렉터리 점검

다음은 입력 디렉터리의 `.csv` 파일을 검사해 개수만 보고하는 POSIX `sh` 예시다. 파일 내용을 수정하지 않는다.

```sh
#!/bin/sh
set -u

usage() {
  printf 'usage: %s DIRECTORY\n' "$0" >&2
}

[ "$#" -eq 1 ] || {
  usage
  exit 2
}

input_dir=$1
[ -d "$input_dir" ] || {
  printf 'not a directory: %s\n' "$input_dir" >&2
  exit 2
}

count=0
for file in "$input_dir"/*.csv; do
  # 패턴과 일치하는 파일이 없으면 패턴 문자열 자체가 남을 수 있다.
  [ -f "$file" ] || continue
  [ -r "$file" ] || {
    printf 'not readable: %s\n' "$file" >&2
    exit 1
  }
  count=$((count + 1))
done

printf 'csv files: %s\n' "$count"
```

검토 포인트는 다음과 같다.

- 인자 개수를 먼저 검사한다.
- 경로 변수를 항상 큰따옴표로 감싼다.
- 글로브가 일치하지 않을 때의 동작을 고려한다.
- 사용자 입력을 `eval`하지 않는다.
- 정상 결과와 오류를 다른 스트림으로 보낸다.
- 사용법 오류와 실행 오류에 서로 의미 있는 종료 상태를 준다.

디렉터리를 재귀 순회하거나 줄바꿈이 든 파일명까지 처리해야 한다면 단순 `for` 글로브만 확장하지 말고, 대상 플랫폼의 안전한 파일 순회 인터페이스와 NUL 구분을 사용한다.

## 10. 환경별 차이와 이식성

### 10.1 POSIX 셸과 PowerShell 비교

| 목적 | POSIX 셸 예 | PowerShell 예 |
|---|---|---|
| 환경변수 읽기 | `printf '%s\n' "$PATH"` | `$env:PATH` |
| 현재 프로세스 환경 설정 | `export APP_MODE=test` | `$env:APP_MODE = 'test'` |
| 명령 성공 판단 | 종료 상태 0 여부 | `$?`, `$LASTEXITCODE`, 예외 규칙 구분 |
| 파이프 | 주로 텍스트 바이트 스트림 | 주로 객체 파이프라인, 외부 명령은 텍스트 경계 |
| 경로 구분 | 일반적으로 `/`, PATH 항목 `:` | Windows에서 `\` 또는 `/`, PATH 항목 `;` |

PowerShell 파이프는 내부 명령 사이에서 객체를 전달할 수 있어 속성 기반 처리가 가능하다. 외부 프로그램 경계에서는 다시 문자열·바이트와 종료 코드 규칙을 고려해야 한다. POSIX 셸 코드를 파일 확장자만 바꿔 PowerShell에서 실행할 수는 없다.

### 10.2 이식성을 높이는 원칙

- 요구 셸과 최소 버전을 문서화한다.
- 특정 셸 기능을 쓰면 셔뱅과 검사 도구 설정을 맞춘다.
- 운영체제별 경로·인코딩·줄바꿈·명령 옵션 차이를 테스트한다.
- 사람용 명령 출력 파싱보다 구조화된 인터페이스를 우선한다.
- `LANG=C`처럼 로캘을 고정하면 파싱은 안정될 수 있지만 사용자 문자 데이터 처리 요구를 해치지 않는지 확인한다.
- 임시 디렉터리, 홈, 실행 파일 위치를 하드코딩하지 않고 플랫폼 API·검증된 환경값을 사용한다.

## 11. 자주 틀리는 포인트

1. **셸은 커널이다?** 셸은 명령 해석기이며 시스템 호출로 커널 서비스를 이용한다.
2. **셸 변수는 자동으로 모든 자식에 전달된다?** 환경으로 내보낸 값만 자식 실행 환경에 포함되는 것이 일반적이다.
3. **자식이 바꾼 환경변수는 부모에 반영된다?** 환경은 부모에서 자식 방향으로 복사되며 역전파되지 않는다.
4. **환경변수 값에는 숫자형이 저장된다?** 프로세스 환경은 보통 문자열이며 응용 프로그램이 형식과 범위를 해석한다.
5. **PATH의 현재 디렉터리를 맨 앞에 두면 편리하기만 하다?** 같은 이름의 악성 실행 파일이 우선될 수 있다.
6. **환경변수는 안전한 비밀 저장소다?** 로그·진단·자식 프로세스로 노출될 수 있어 별도 비밀 관리가 필요하다.
7. **`$var`와 `"$var"`는 항상 같다?** 무인용 확장은 단어 분리와 파일명 패턴 확장으로 인자 수가 달라질 수 있다.
8. **`"$*"`는 여러 인자를 그대로 전달한다?** 하나로 결합될 수 있으므로 보통 `"$@"`가 인자 경계를 보존한다.
9. **0이 오류 종료 상태다?** 유닉스 계열 관례에서는 0이 성공, 0이 아닌 값이 실패다.
10. **`set -e`면 모든 실패가 완벽히 처리된다?** 문맥별 예외가 있어 중요한 실패는 명시적으로 검사해야 한다.
11. **`>`는 파일 뒤에 추가한다?** 덮어쓰고, `>>`가 이어쓴다.
12. **파이프라인 성공은 모든 단계 성공을 뜻한다?** 셸 설정에 따라 마지막 명령 상태만 보일 수 있다.
13. **스크립트를 실행하면 그 안의 `cd`가 부모 셸에도 남는다?** 별도 프로세스라면 보통 남지 않는다.
14. **명령 문자열을 `eval`하면 인용 문제가 해결된다?** 입력이 코드로 재해석되어 명령 주입 위험을 만든다.

## 13. 정답과 해설

### 정답 1

셸 변수는 현재 셸이 관리하는 값이다. `export` 등으로 환경에 포함된 변수는 새 자식 프로세스를 시작할 때 전달될 수 있다. 단순 셸 변수는 일반적으로 외부 자식 프로그램에 자동 전달되지 않는다.

### 정답 2

프로세스 환경은 부모가 자식을 만들 때 복사되어 전달된다. 자식은 자신의 복사본을 바꿀 뿐 이미 실행 중인 부모 환경을 직접 수정하지 않는다.

### 정답 3

공격자가 시스템 명령과 같은 이름의 실행 파일을 그 디렉터리에 두면 PATH 검색에서 먼저 선택되어 의도하지 않은 코드가 실행될 수 있다. 안전한 검색 경로와 절대 경로·권한 검증을 사용한다.

### 정답 4

`command "$file"`처럼 변수 확장을 큰따옴표로 감싸 한 인자 경계를 보존한다. 대상 명령이 지원하고 파일명이 옵션처럼 보일 수 있다면 `command -- "$file"`도 검토한다.

### 정답 5

`"$@"`를 사용한다. 각 위치 인자를 별개의 인자로 보존한다. `"$*"`는 구분 문자를 사이에 두고 하나의 값처럼 결합된다.

### 정답 6

먼저 표준 출력을 `result.log`로 연결하고, 표준 오류를 현재 표준 출력의 대상과 같은 곳에 연결한다. 결과적으로 두 스트림이 파일로 간다. 재지정은 왼쪽에서 오른쪽으로 적용된다.

### 정답 7

관례적으로 0은 성공, 0이 아닌 값은 실패나 다른 상태를 뜻한다. 정상 결과는 표준 출력, 진단·오류 메시지는 표준 오류로 보내 파이프와 로그에서 구분할 수 있게 한다.

### 정답 8

환경변수는 프로세스 진단·로그·자식 환경·오류 보고에 노출될 수 있다. 전용 비밀 관리 시스템으로 실행 시 필요한 프로세스에만 주입하고, 전체 환경 출력과 디버그 추적을 피하며, 최소 권한·짧은 수명 토큰을 사용한다.

## 14. 핵심 요약

- 셸은 사용자 명령과 스크립트를 해석해 프로그램 실행·입출력 연결·변수 확장을 제공하며 커널과는 다르다.
- 환경변수는 문자열 기반 프로세스 환경으로 부모에서 자식 방향으로 전달되고, 자식의 변경은 부모로 자동 역전파되지 않는다.
- `PATH`는 순서대로 실행 파일을 검색하므로 신뢰할 수 없는 디렉터리·현재 디렉터리·쓰기 권한을 주의한다.
- 환경변수는 설정 분리에 유용하지만 완전한 비밀 저장소가 아니므로 전용 관리·최소 전달·로그 차단이 필요하다.
- 변수와 경로는 기본적으로 큰따옴표로 감싸 인자 경계를 보존하고, 여러 인자를 그대로 전달할 때 `"$@"`를 사용한다.
- 셔뱅은 직접 실행할 해석기를 지정하며 실제 문법과 호출 방식이 일치해야 한다.
- 성공은 보통 종료 상태 0이며, 표준 출력·표준 오류·재지정·파이프의 연결 순서와 실패 전파를 구분한다.
- 조건·반복·함수는 입력 검증, 최대 재시도, 의미 있는 종료 코드와 함께 사용한다.
- 자동화는 최소 권한, 안전한 임시 파일, 원자적 반영, 건식 실행, 비밀을 제외한 관찰 가능성을 갖춰야 한다.
