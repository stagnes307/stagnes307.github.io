# 5-2-2-1. SW 구축 관리

## 출제범위와 학습 목표

이 레슨의 정확한 출제범위는 **IT 신기술 및 SW 개발 트렌드 정보**와 **SW개발보안 정책**이다. 최신 제품명이나 일시적인 인기 순위를 외우기보다 클라우드 네이티브, 서비스 분리, 자동화, 선언적 인프라, API·이벤트, 인공지능 보조 개발 같은 흐름의 목적과 도입 조건을 이해하고, 보안 정책을 요구·설계·구현·시험·배포와 공급망 관리에 연결하는 능력을 기른다.

학습 후에는 다음을 할 수 있어야 한다.

- 주요 SW 개발 트렌드를 해결하려는 문제와 함께 설명한다.
- 단일 구조와 분산 구조, 가상머신과 컨테이너, 수동·자동 배포를 비교한다.
- 유행성보다 업무 적합성, 복잡도, 운영 역량, 보안과 총비용으로 도입을 판단한다.
- SW개발보안 정책의 목적, 범위, 역할, 통제와 예외 절차를 구성한다.
- 개발 파이프라인에서 코드·의존성·비밀·산출물의 신뢰를 통제한다.

## 1. SW 구축 관리의 의미

SW 구축 관리는 요구사항을 충족하는 소프트웨어를 설계·구현·시험하고, 재현 가능한 산출물로 만들어 안전하게 배포·운영하도록 통제하는 활동이다. 새 기술 도입 자체가 목표가 아니라 업무 가치, 품질, 보안, 운영성과 지속 가능한 변경 능력을 확보하는 것이 목적이다.

SW 구축 관리의 핵심 질문은 다음과 같다.

- 어떤 구조가 현재 업무와 예상 변화에 적합한가?
- 개발부터 운영까지 같은 산출물과 설정을 재현할 수 있는가?
- 변경이 작고 자주 일어나도 품질 게이트를 유지할 수 있는가?
- 외부 패키지와 빌드 도구를 신뢰할 근거가 있는가?
- 장애와 보안 사고가 발생했을 때 영향 범위와 복구 경로가 명확한가?

## 2. IT 신기술 및 SW 개발 트렌드 정보

**IT 신기술 및 SW 개발 트렌드 정보**는 특정 도구보다 기술 흐름이 해결하려는 문제, 얻는 효과, 새로 생기는 위험을 함께 학습한다.

### 2.1 클라우드 네이티브

클라우드의 자동 확장, 탄력적 자원, 관리형 서비스와 자동화된 배포를 활용할 수 있도록 애플리케이션을 설계·운영하는 접근이다. 단순히 기존 프로그램을 클라우드 서버로 옮기는 것과 다르다.

주요 방향:

- 상태를 외부 저장소와 명시적으로 관리
- 자동 배포와 구성 분리
- 장애를 전제로 한 복구와 관측
- 수평 확장 가능한 단위와 느슨한 결합

모든 시스템을 클라우드 네이티브로 바꿀 필요는 없다. 데이터 위치 규제, 지연, 기존 장비 의존, 예측 가능한 고정 부하와 조직 운영 역량을 평가한다.

### 2.2 마이크로서비스

업무 능력을 작은 독립 서비스로 나누고 각각 개발·배포·확장할 수 있게 하는 구조다.

장점:

- 서비스별 독립 변경과 배포
- 부하가 큰 기능만 선택적으로 확장
- 팀별 책임과 장애 경계 설정

위험:

- 원격 호출, 시간 초과, 재시도와 부분 실패
- 분산 데이터 일관성과 거래 추적
- 서비스 발견, 인증, 로그·지표 통합
- 배포 단위와 운영 대상 증가

서비스 수가 많을수록 현대적이라는 판단은 틀리다. 업무 경계가 불명확하거나 운영 자동화가 부족하면 분산 복잡도가 이점보다 커질 수 있다. 변경 독립성과 팀 경계가 실제로 필요한지 본다.

### 2.3 컨테이너와 오케스트레이션

컨테이너는 애플리케이션과 필요한 사용자 공간 의존성을 격리된 실행 단위로 패키징한다. 가상머신은 일반적으로 하드웨어 가상화 위에서 각 게스트 운영체제를 실행하는 반면, 컨테이너는 호스트 커널을 공유하는 방식으로 설명할 수 있다.

| 구분 | 가상머신 | 컨테이너 |
|---|---|---|
| 격리 단위 | 게스트 운영체제를 포함한 가상 시스템 | 프로세스와 사용자 공간 |
| 이미지 | 상대적으로 큼 | 상대적으로 작고 시작이 빠를 수 있음 |
| 커널 | 게스트별 커널 | 호스트 커널 공유 |
| 주의 | 자원·이미지 관리 | 커널 공유 위험, 이미지·권한·비밀 관리 |

오케스트레이션은 많은 컨테이너의 배치, 상태 유지, 확장, 네트워크와 업데이트를 자동화한다. 자동 복구 기능이 애플리케이션의 데이터 일관성과 업무 복구를 자동 보장하는 것은 아니다.

### 2.4 서버리스·관리형 실행

개발자가 서버 단위의 용량과 운영을 직접 관리하는 부담을 줄이고 함수나 서비스 단위로 코드를 실행하는 접근이다. 이벤트 기반 처리와 변동 부하에 유리할 수 있다. 실행 시간·상태·네트워크·관측·이식성 제약, 지연과 비용 구조를 대표 부하로 확인한다.

“서버리스”는 물리 서버가 없다는 뜻이 아니라 사용자가 서버 운영의 많은 부분을 제공자에게 위임한다는 뜻이다.

### 2.5 DevOps와 CI/CD

DevOps는 개발과 운영 사이의 협업, 자동화, 측정과 피드백을 통해 변경을 빠르고 안정적으로 전달하려는 문화·실천의 묶음이다. 특정 도구 하나가 아니다.

- 지속적 통합: 변경을 자주 통합하고 빌드·시험하여 문제를 빨리 발견
- 지속적 전달: 배포 가능한 상태를 유지하고 운영 반영은 승인 가능
- 지속적 배포: 통과한 변경이 자동으로 운영에 반영되는 운영 방식

전달과 배포의 구분은 교재에 따라 번역 표현이 다를 수 있다. 시험 지문에서 운영 반영의 자동 여부를 확인한다.

### 2.6 Infrastructure as Code와 선언적 관리

인프라와 환경 구성을 코드 형태로 버전 관리하고 검토·자동화하여 환경 차이와 수작업 오류를 줄인다. 원하는 상태를 선언하고 실제 상태와 맞추는 방식도 포함할 수 있다.

장점은 재현성, 변경 추적, 자동 복구이고 위험은 잘못된 정의의 대규모 확산, 비밀 노출, 권한 과다와 실제 상태의 무단 변경이다. 코드 검토, 정책 검사, 단계 반영, 상태 보호와 되돌리기가 필요하다.

### 2.7 API 우선·이벤트 기반

API 우선 접근은 구현 전에 소비자와 제공자 사이의 계약을 명확히 하고 독립 개발과 검증을 돕는다. 이벤트 기반 구조는 상태 변화나 사건을 발행하고 구독자가 비동기로 처리하여 결합을 낮춘다.

이벤트 방식에서는 중복 전달, 순서 역전, 지연, 재처리, 실패 메시지와 추적을 설계해야 한다. “메시지가 한 번만 전달된다”는 가정에 의존하지 말고 업무 멱등성과 중복 처리 전략을 둔다.

### 2.8 관측 가능성과 운영 피드백

로그, 지표, 추적 정보를 연결하여 시스템 내부 상태와 요청 경로를 추론한다. 분산 구조에서는 서비스별 로그만으로 전체 원인을 찾기 어렵기 때문에 공통 요청 식별자, 시각 동기화, 구조화된 상태 정보와 민감정보 보호가 중요하다.

### 2.9 인공지능 보조 개발

코드 제안, 시험 후보, 문서화와 분석에 인공지능을 보조적으로 활용할 수 있다. 생산성 이점과 함께 잘못된 코드, 학습·입력 데이터의 기밀성, 라이선스·출처, 편향, 책임과 검토 문제가 있다.

도입 원칙:

- 승인된 데이터와 도구 경계 사용
- 생성 결과를 사람이 이해하고 검토
- 보안·품질 시험을 동일하게 적용
- 중요 결정과 변경 근거를 추적
- 기밀·개인정보 입력 통제

## 3. 트렌드 도입 판단 기준

| 기준 | 질문 |
|---|---|
| 업무 적합성 | 실제 변경·확장·지연 문제를 해결하는가 |
| 복잡도 | 새 분산·자동화 복잡도를 감당할 수 있는가 |
| 팀 역량 | 설계, 운영, 장애 분석 경험과 학습 계획이 있는가 |
| 품질 | 성능, 가용성, 보안, 데이터 일관성 목표를 만족하는가 |
| 운영성 | 로그·지표·추적, 백업·복구, 비상 접근이 준비되는가 |
| 상호운용성 | 기존 시스템·표준·데이터와 연결 가능한가 |
| 지속성 | 지원, 문서, 인력과 변경 정책이 업무 수명에 맞는가 |
| 종속·철수 | 특정 환경 의존과 이전 비용을 통제할 수 있는가 |
| 총비용 | 개발뿐 아니라 교육, 운영, 관측, 보안 비용을 포함했는가 |

도입은 “전면 적용 또는 미적용”만 있는 것이 아니다. 위험이 작은 기능으로 기술 검증을 하고, 측정 결과가 기준을 만족할 때 단계적으로 확대할 수 있다.

## 4. SW개발보안 정책

**SW개발보안 정책**은 소프트웨어의 요구·설계·구현·시험·배포·유지보수 전 과정에서 보안 위험을 줄이기 위한 조직의 원칙, 역할, 의무 통제와 예외 절차다. 정책은 “보안을 고려한다”라는 선언보다 누가 무엇을 어떤 기준으로 확인하고 실패 시 어떻게 처리하는지를 정해야 한다.

### 4.1 정책과 하위 문서

| 문서 수준 | 역할 | 예 |
|---|---|---|
| 정책 | 조직의 의무와 방향, 책임 | 모든 운영 배포는 보안 게이트를 통과 |
| 표준 | 일관된 필수 기준 | 인증, 암호, 로그, 의존성 관리 기준 |
| 절차 | 수행 순서와 승인 흐름 | 취약점 접수·수정·예외 승인 절차 |
| 지침 | 구체적 권고와 구현 예 | 안전한 API, 오류 처리 가이드 |

정책은 안정적으로 유지하고, 빠르게 변하는 기술 세부는 표준·지침에서 갱신하는 방식이 관리에 유리하다.

### 4.2 정책의 핵심 구성

- 목적과 적용 대상 시스템·조직·외부 공급자
- 자산·데이터 분류와 위험 평가 원칙
- 역할과 책임, 승인 권한과 독립 검토 조건
- 보안 요구사항 정의와 위협 분석
- 안전한 설계·코딩 기준과 금지 항목
- 코드 검토, 정적·동적·구성·침투 시험
- 외부 구성요소와 공급망·라이선스 관리
- 비밀·키·개발 데이터와 환경 접근 통제
- 결함 심각도, 수정 기한, 배포 차단 기준
- 예외 신청, 위험 수용, 만료와 재검토
- 교육, 측정, 감사, 사고 피드백과 정책 개선

구체적인 입력값 취약점과 방어 코딩은 뒤 보안 설계 레슨에서 다룬다. 여기서는 정책이 그런 활동을 의무화하고 증거를 관리하는 구조를 이해한다.

## 5. 역할과 책임

- 경영·정책 책임자: 위험 수용 범위와 조직 정책 승인
- 프로젝트 책임자: 일정·자원과 보안 활동 통합
- 보안 담당자: 위협·통제 자문, 중요 결과 검토
- 개발자: 안전한 설계·코딩, 결함 수정과 단위 검증
- 검토·시험 담당자: 독립성 수준에 맞는 보안 검증
- 운영 담당자: 안전한 설정, 비밀, 감시·대응과 패치
- 공급자: 계약된 보안 기준, 구성요소 정보와 결함 통보
- 데이터 소유자: 데이터 분류와 사용·보존·노출 승인

보안팀만 보안을 책임진다는 구조는 적절하지 않다. 각 생명주기 역할이 자신의 산출물 보안을 책임지고 보안 전문가는 기준과 고위험 판단을 지원한다.

## 6. 개발 파이프라인 보안

    변경 제안
       │
       ▼
    코드 검토 ── 실패 → 수정
       │
       ▼
    빌드·단위 시험
       │
       ├─ 소스·의존성·비밀·구성 검사
       ▼
    서명·식별된 배포 산출물
       │
       ▼
    시험 환경 보안·업무 검증
       │
       ▼
    승인 게이트 → 단계 배포 → 감시·복구

핵심 통제:

- 빌드는 승인된 소스와 잠긴 의존성 기준에서 재현한다.
- 빌드 서비스 계정은 최소 권한을 갖고 비밀을 소스에 저장하지 않는다.
- 외부 패키지의 출처, 버전, 무결성과 알려진 위험을 추적한다.
- 생성 산출물에 고유 식별자와 소스·빌드 정보의 연결을 남긴다.
- 시험을 우회한 수동 산출물이 운영에 들어가지 않게 한다.
- 배포는 소규모부터 상태를 확인하며 실패 시 중단·복구한다.

구성요소 목록은 사용 중인 외부·내부 구성요소를 추적해 취약점 영향과 교체 대상을 찾는 데 도움이 된다. 목록만 만들고 갱신하지 않으면 실제 배포물과 달라질 수 있으므로 빌드 결과와 연결한다.

## 7. 보안 정책 적용 절차

1. **범위·자산 식별**: 시스템, 데이터, 사용자, 외부 연계와 공급자를 파악한다.
2. **위험·의무 분석**: 공격 가능성, 영향, 법·계약·조직 기준을 확인한다.
3. **보안 요구 도출**: 인증, 권한, 데이터 보호, 로그, 가용성과 공급망 요구를 명확히 한다.
4. **활동·게이트 배치**: 설계 검토, 코드 검사, 시험, 승인과 배포 차단 기준을 단계에 넣는다.
5. **역할·도구 준비**: 책임자, 교육, 자동화 도구와 수동 검토 절차를 마련한다.
6. **개발·검증 수행**: 위험이 큰 변경부터 깊게 확인하고 결과를 추적한다.
7. **결함·예외 처리**: 심각도와 영향에 따라 수정, 보완 통제, 위험 수용과 만료를 결정한다.
8. **배포·운영 감시**: 승인 산출물만 배포하고 이상, 취약점, 구성 변경을 관찰한다.
9. **사고·지표 피드백**: 반복 결함과 우회 원인을 분석해 정책·교육·자동화를 개선한다.

### 예외 관리

예외에는 대상, 위반 기준, 업무 이유, 위험·영향, 보완 통제, 책임 있는 승인자, 유효기간, 해소 계획을 기록한다. 예외는 영구 면제가 아니며 만료 시 재검토한다. 일정 압박만으로 고위험 결함을 묵인해서는 안 된다.

## 8. 구체 예시

### 상황

외부 파트너 주문을 받는 API를 새로 구축한다. 팀은 컨테이너와 자동 배포를 도입하려 한다.

### 트렌드 적용 판단

- 서비스가 독립 확장될 필요가 있는지 실제 부하와 변경 주기로 확인한다.
- 컨테이너 이미지의 최소 구성, 실행 권한과 갱신 절차를 정의한다.
- 자동 배포 전에 계약 시험과 보안 검사를 게이트로 둔다.
- 분산 추적 식별자로 파트너 요청과 내부 처리를 연결한다.
- 재시도 시 주문 중복 생성이 없도록 업무 키와 멱등 처리를 설계한다.

### 정책 적용

1. 파트너 인증과 허용 권한, 데이터 분류를 요구사항에 넣는다.
2. 위협 분석에서 위조 요청, 재전송, 과다 호출, 민감정보 로그를 검토한다.
3. 소스·외부 패키지·컨테이너 구성과 비밀 노출을 검사한다.
4. 배포 산출물을 실행한 소스 변경과 연결한다.
5. 소규모 트래픽에 먼저 배포하고 오류·지연·거부율을 감시한다.
6. 기준을 넘으면 자동 확대를 중단하고 이전 산출물로 복구한다.

자동화는 배포 횟수를 늘릴 수 있지만 보안 책임을 없애지 않는다. 빠른 피드백과 재현 가능한 증거가 있을 때 속도와 안전을 함께 높일 수 있다.

## 9. 자주 틀리는 포인트

1. **DevOps를 도구 이름이나 개발팀의 운영 겸임으로만 이해**: 협업·자동화·측정·피드백 문화와 실천이다.
2. **지속적 전달과 지속적 배포를 동일시**: 운영 반영의 자동 여부를 지문에서 확인한다.
3. **컨테이너를 가상머신과 완전히 같은 격리로 판단**: 일반적으로 호스트 커널을 공유한다.
4. **마이크로서비스는 작을수록 좋다고 생각**: 업무 경계와 독립 변경 가치를 기준으로 나눈다.
5. **서버리스에는 서버가 없다고 이해**: 운영 책임의 많은 부분을 제공자에게 위임하는 모델이다.
6. **IaC가 수작업 오류를 모두 제거한다고 생각**: 잘못된 코드가 대규모로 재현될 수 있다.
7. **SW개발보안 정책을 안전한 코딩 목록만으로 한정**: 역할, 요구, 시험, 공급망, 배포, 예외·사고 피드백까지 포함한다.
8. **보안 검사를 마지막 단계에서만 수행**: 초기 요구와 설계부터 단계별 게이트로 배치한다.
9. **자동 검사 PASS를 무결점으로 해석**: 도구 범위 밖의 업무·설계 결함과 오탐·미탐을 검토한다.
10. **예외 승인을 영구 면제로 사용**: 보완 통제, 만료와 해소 계획이 필요하다.

## 11. 정답과 해설

### 정답 1

단순 이전은 기존 구조를 다른 서버 환경으로 옮기는 데 그칠 수 있다. 클라우드 네이티브는 탄력 자원, 자동 배포, 외부 상태, 장애 복구와 관측을 활용하도록 구조와 운영을 설계한다.

### 정답 2

이점은 독립 변경·배포, 선택 확장, 팀 책임 경계다. 위험은 원격 호출과 부분 실패, 분산 데이터 일관성, 서비스 발견·관측, 운영 대상 증가 등이다.

### 정답 3

가상머신은 일반적으로 게스트 운영체제와 커널을 포함한 가상 시스템 단위로 격리하고, 컨테이너는 호스트 커널을 공유하면서 프로세스와 사용자 공간을 격리한다.

### 정답 4

DevOps는 개발·운영 협업과 자동화·피드백의 넓은 문화·실천이고, CI/CD는 변경 통합, 시험, 전달·배포를 자동화하는 대표 실천이다.

### 정답 5

중복 전달, 순서 역전, 지연, 처리 실패, 재시도 폭증, 실패 메시지 누적과 전체 요청 추적 중 네 가지다.

### 정답 6

목적·범위, 역할·책임, 보안 요구·위협 분석, 설계·코딩 기준, 검토·시험, 공급망·비밀 관리, 결함·예외, 교육·측정·사고 피드백 중 다섯 가지다.

### 정답 7

승인된 원천 사용, 의존성 출처·버전·무결성 추적, 구성요소 목록, 빌드 계정 최소 권한, 비밀 분리, 산출물과 소스 연결, 취약점 대응 중 네 가지다.

### 정답 8

대상, 위반 기준, 업무 이유, 위험·영향, 보완 통제, 승인자, 유효기간, 해소 계획 중 다섯 가지다.

### 정답 9

제안에 오류·취약점·라이선스·기밀성 문제가 있을 수 있고 책임은 개발 조직에 남기 때문이다. 승인된 경계에서 사용하고 사람이 이해·검토하며 동일한 보안·품질 시험을 적용한다.

## 핵심 요약

- **IT 신기술 및 SW 개발 트렌드 정보**는 클라우드 네이티브, 마이크로서비스, 컨테이너, 관리형 실행, DevOps·CI/CD, IaC, API·이벤트와 관측 같은 변화 방향으로 학습한다.
- 새 기술은 업무 문제, 팀 역량, 분산 복잡도, 품질·보안, 운영성과 총비용을 기준으로 단계 도입한다.
- **SW개발보안 정책**은 생명주기 전반의 원칙, 역할, 필수 통제, 결함·예외와 개선 책임을 정한다.
- 정책은 요구·위협 분석, 안전한 설계·구현, 코드·의존성·비밀 검사, 승인 산출물 배포와 운영 피드백으로 이어져야 한다.
- 자동화는 검토를 없애는 수단이 아니라 빠르고 재현 가능한 검증·증거를 만드는 수단이다.
- 최신 제품보다 안정된 기술 목적과 도입 조건, 공급망 신뢰와 복구 가능성을 중심으로 판단한다.
