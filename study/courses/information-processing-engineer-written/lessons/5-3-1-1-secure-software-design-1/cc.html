01

출제범위와 학습 목표

이 레슨의 정확한 출제범위는 Secure SDLC(Software Development Life Cycle)와 입력데이터 검증 및 표현이다. 보안을 개발 완료 후 시험 한 번으로 확인하지 않고 요구·설계·구현·시험·배포·운영·폐기 전 과정에 통합하는 원리와, 신뢰 경계를 넘는 입력을 정규화·검증하고 사용 맥락에 맞게 안전하게 표현하는 방법을 익힌다. 인증·접근제어, 에러·세션, 암호 알고리즘은 뒤 레슨의 주범위이므로 여기서는 상세 구현으로 확장하지 않는다.

학습 후에는 다음을 할 수 있어야 한다.

  • 일반 SDLC와 Secure SDLC의 활동 차이를 단계별로 설명한다.
  • 자산·위협·공격 표면·오용 사례를 이용해 보안 요구를 도출한다.
  • 입력의 신뢰 경계, 정규화, 형식·범위·업무 규칙 검증을 설계한다.
  • SQL·명령·경로·웹 출력 등 사용 맥락별 안전한 처리 원칙을 적용한다.
  • 클라이언트 검증과 서버 검증, 입력 검증과 출력 인코딩을 구분한다.
02

1. Secure SDLC의 의미

Secure SDLC(Software Development Life Cycle)는 소프트웨어 생명주기의 각 단계에 보안 활동, 책임, 산출물과 품질 게이트를 포함해 취약점을 조기에 예방·발견·대응하는 개발 체계다. 별도의 보안 단계를 마지막에 붙이는 것이 아니라 기존 요구분석·설계·구현·시험·배포와 운영 활동에 위험 기반 통제를 통합한다.

왜 필요한가?

  • 설계 결함은 코딩 규칙 검사만으로 찾기 어렵다.
  • 개발 후반에 발견한 구조 결함은 수정 비용과 일정 영향이 크다.
  • 외부 패키지, 빌드·배포와 운영 설정도 공격 표면이다.
  • 위협과 기술은 운영 중 변하므로 지속적인 취약점 대응이 필요하다.
  • 법·계약·데이터 보호 요구를 개발 증거와 연결해야 한다.

“초기에 보안을 한다”는 shift-left 관점은 중요하지만 운영 감시와 사고 피드백을 없애는 뜻은 아니다. 초기 예방과 운영 중 지속 검증을 함께 수행한다.

03

2. Secure SDLC의 기본 원칙

2. Secure SDLC의 기본 원칙 · 학습 표 1
원칙적용 의미
위험 기반자산 가치, 노출, 가능성과 영향에 따라 검토 깊이를 정한다.
안전한 기본값별도 설정이 없어도 최소 기능·접근만 허용한다.
최소 권한·기능서비스가 필요한 자원만 사용하고 불필요한 공격 표면을 줄인다.
심층 방어입력 검증, 안전한 API, 출력 인코딩과 감시처럼 다른 실패를 다루는 통제를 겹친다.
안전한 실패검증·정책 확인 실패가 민감 기능 허용으로 이어지지 않게 한다.
추적·반복 가능성요구, 위협, 통제, 코드와 시험 결과를 연결하고 같은 검사를 재현한다.

모든 기능을 같은 깊이로 검사하는 것이 위험 기반은 아니다. 결제·개인정보·관리 기능처럼 영향이 큰 범위에 더 깊은 위협 분석과 독립 검증을 배치한다.

04

3. Secure SDLC 단계별 활동

3. Secure SDLC 단계별 활동 · 학습 표 2
단계핵심 활동과 증거
준비·교육정책, 역할별 교육, 승인 도구·빌드 기준, 심각도·예외·배포 차단 기준을 확정한다.
요구사항자산·민감 데이터와 신뢰 경계를 식별하고 보안 요구, 오용 사례, 인수 기준을 만든다.
설계데이터 흐름과 공격 표면을 모델링하고 위협, 입력·출력 책임, 통제 실패를 검토한다.
구현안전한 코딩, 승인 API, 코드·정적 분석, 비밀 분리와 의존성 출처 추적을 수행한다.
검증보안 요구, 경계·오용, 동적·침투 관점, 구성·공급망과 수정 회귀를 시험한다.
배포승인 소스에서 재현한 산출물, 안전 설정, 무결성, 복구와 잔여 위험을 확인한다.
운영·폐기취약점·이상을 감시하고 패치·사고를 기준에 피드백하며 데이터·비밀·계정을 안전하게 제거한다.

“시스템은 안전해야 한다”는 검증하기 어렵다. “정의되지 않은 상태 코드는 거부한다”처럼 관찰 가능한 요구로 바꾼다. 자동 분석은 업무·구조 결함을 모두 찾지 못하므로 사람 검토와 동적 시험을 조합하고, 운영 문제가 개발 기준으로 돌아와야 생명주기가 순환한다.

05

4. 대표 Secure SDLC 접근

시험에서는 특정 접근의 세부 버전보다 강조점을 구분한다.

4.1 Microsoft SDL 계열 관점

교육, 보안 요구, 위협 모델링, 안전한 구현, 검증, 릴리스와 사고 대응을 조직 개발 절차에 통합하는 접근으로 알려져 있다. 필수 활동과 릴리스 기준, 보안 대응을 체계화한다.

4.2 CLASP 관점

역할과 활동, 산출물 중심으로 보안 활동을 기존 개발 프로세스에 통합할 수 있도록 제시하는 경량·적응형 접근으로 알려져 있다. 프로젝트가 필요한 활동을 선택해 적용하는 관점이 중요하다.

4.3 Seven Touchpoints 관점

보안 요구, 오용 사례, 아키텍처 위험 분석, 코드 검토, 위험 기반 시험, 침투 시험과 운영 피드백처럼 효과가 큰 보안 활동을 개발 과정에 접점으로 배치하는 관점이다.

모델 이름을 도구나 취약점 분류와 혼동하지 않는다. 세부 단계와 명칭은 자료의 판에 따라 달라질 수 있으므로 문제에서 제시한 정의를 우선한다.

5. Secure SDLC 텍스트 도식

자산·의무 │ ▼ 보안 요구 ── 오용 사례 │ ▼ 구조·데이터 흐름 ── 위협 모델 │ ▼ 안전한 구현 ── 코드·의존성 검토 │ ▼ 보안 시험 ── 결함 수정·회귀 │ ▼ 릴리스 게이트 ── 운영 감시 ▲ │ └──── 사고·취약점 피드백 ────┘

각 화살표에는 요구 ID, 위협 ID, 통제, 코드와 시험 결과의 추적 관계가 있어야 한다.

07

6. 입력데이터 검증 및 표현

입력데이터 검증 및 표현은 외부 또는 신뢰도가 낮은 출처에서 들어온 데이터를 정해진 문법과 업무 규칙으로 확인하고, SQL·명령·경로·HTML 등 사용되는 문맥에서 데이터가 제어 구문으로 해석되지 않도록 안전하게 표현하는 보안 설계 영역이다.

입력 출처:

  • 화면 폼, URL 경로와 질의 문자열
  • HTTP 헤더·쿠키와 요청 본문
  • 파일 업로드와 파일명
  • 메시지 큐·이벤트와 외부 API
  • 데이터베이스의 기존 값
  • 환경 변수, 설정, 명령행
  • 장치·센서와 외부 공급 데이터

내부 데이터베이스에 저장되었다는 이유로 신뢰하지 않는다. 과거에 검증되지 않았거나 다른 문맥에서 위험한 값일 수 있다.

08

7. 안전한 입력 처리 순서

원시 입력 │ ▼ 크기·구조 제한 │ ▼ 합의된 디코딩·정규화 │ ▼ 형식·자료형·길이·범위 검증 │ ▼ 업무 상태·관계 검증 │ ▼ 내부의 명확한 자료형으로 변환 │ ▼ 안전한 API로 사용 │ ▼ 출력 문맥에 맞는 인코딩

정규화 전에 검증한 문자열이 디코딩 후 다른 위험한 표현으로 바뀌면 우회가 가능하다. 반대로 여러 번 디코딩하면 원래 데이터 의미가 달라질 수 있다. 시스템이 실제 사용할 단일 표현을 정하고 그 표현을 검증한다.

09

8. 검증 원칙

8.1 서버 측 검증

클라이언트 검증은 사용자의 빠른 피드백에 유용하지만 공격자가 요청을 직접 만들어 우회할 수 있다. 신뢰 경계 안의 서버 또는 최종 처리 구성요소가 반드시 검증한다. 여러 서비스가 있다면 경계별 책임과 내부 계약을 명확히 한다.

8.2 허용 목록

가능하면 알려진 정상 형태를 허용한다.

  • 자료형: 정수, 날짜, 열거형으로 변환 가능한가?
  • 길이: 업무상 최소·최대 안인가?
  • 범위: 수량·날짜가 허용 범위인가?
  • 문자 집합: 식별자에 허용한 문자만 있는가?
  • 열거 값: 승인된 상태·종류 중 하나인가?
  • 구조: 예상 필드와 중첩 깊이, 배열 크기를 만족하는가?

금지 목록은 알려진 위험 문자열을 막는 보조 수단일 수 있지만 우회 표현을 모두 나열하기 어렵다.

8.3 문법과 업무 규칙 분리

“수량이 정수”는 문법 검증이고 “재고와 주문 한도 안”은 업무 규칙 검증이다. 둘 다 필요하다. 문법상 유효한 음수나 지나치게 먼 날짜가 업무상 허용되지 않을 수 있다.

8.4 전체 요청과 교차 필드 검증

각 필드가 개별적으로 유효해도 시작일이 종료일보다 늦거나 할인 금액이 주문액을 넘을 수 있다. 필드 간 관계와 현재 업무 상태를 검증한다.

8.5 크기와 복잡도 제한

너무 긴 문자열, 거대한 배열, 깊은 중첩과 압축 해제 후 폭증하는 입력은 자원을 고갈시킬 수 있다. 원시 크기뿐 아니라 파싱 후 항목 수와 처리 비용을 제한한다.

8.6 거부와 기록

유효하지 않은 입력은 안전하게 거부하고 내부 상세를 과도하게 노출하지 않는다. 어떤 규칙이 실패했는지 운영자가 추적할 식별자와 최소 정보를 남기되, 비밀·개인정보와 공격 문자열 전체를 로그에 그대로 복제하지 않는다.

10

9. 사용 문맥별 안전한 표현

입력 검증만으로 주입 공격을 모두 막을 수 없다. 데이터가 전달되는 해석기에서 명령과 데이터가 분리되도록 안전한 API를 쓰고, 출력은 목적 문맥에 맞게 인코딩한다.

9. 사용 문맥별 안전한 표현 · 학습 표 3
문맥안전한 처리피할 방식
SQL값은 매개변수 바인딩하고 열·정렬 같은 구조는 서버 허용 목록에서 선택입력을 SQL 문자열에 연결
OS 명령가능한 경우 전용 API를 쓰고, 필요하면 실행 파일 고정·구조화 인수·최소 권한 적용입력을 셸 명령 문자열에 결합
웹 출력원래 값을 보존하고 HTML 본문·속성·URL 등 실제 출력 문맥에서 인코딩입력 시 일괄 치환하거나 한 인코딩을 모든 문맥에 사용
파일 경로서버 내부 ID, 기준 디렉터리와 정규 경로 비교, 심볼릭 링크 경계·최소 권한 적용특정 상위 경로 문자열만 삭제
파일 업로드수·크기·실제 내용 검사, 서버 생성 이름, 실행 불가 격리 저장과 악성 콘텐츠 검사확장자와 요청 콘텐츠 유형만 신뢰
URL·외부 요청허용 목적지 ID를 실제 주소에 매핑하고 스킴·호스트·포트·주소 해석을 제한사용자 URL과 단순 접두사 비교
구조화 문서허용 필드·유형, 전체 크기·깊이·배열 수, 외부 자원 참조와 중복 키 정책 설정파서 기본값으로 모든 기능 허용

SQL의 안전한 개념은 다음처럼 구조와 값을 분리하는 것이다.

sql = "SELECT name FROM member WHERE id = :id" execute(sql, bind = { id: validatedId })

파일 이름과 URL도 검증된 문자열을 그대로 쓰기보다 서버가 가진 허용 대상에 매핑한다. 사용자 표현을 금지 목록으로 일부 삭제하는 방식은 다른 인코딩이나 구분자로 우회될 수 있다.

11

10. 입력 검증과 출력 인코딩 비교

10. 입력 검증과 출력 인코딩 비교 · 학습 표 4
구분입력 검증출력 인코딩
질문이 값이 허용된 데이터인가이 데이터를 현재 문맥에서 어떻게 표현할까
시점신뢰 경계 진입과 사용 전출력·해석기 전달 직전
기준자료형, 길이, 범위, 구조, 업무 규칙HTML, 속성, URL 등 목적 문맥
실패거부·보류·안전한 오류데이터가 명령으로 해석되지 않게 표현
주의금지 목록만 의존하지 않음하나의 인코딩을 모든 문맥에 쓰지 않음

검증과 인코딩은 대체 관계가 아니다. 허용되지 않은 수량을 HTML 인코딩해도 업무상 유효해지지 않고, 정상 이름도 인코딩 없이 HTML에 넣으면 위험할 수 있다.

12

11. 적용 절차와 판단 기준

  1. 입력 지점 목록화: 화면, API, 파일, 메시지, 설정과 저장 데이터의 출처를 찾는다.
  2. 신뢰 경계·최종 사용처 연결: 입력이 어떤 구성요소와 해석기를 거치는지 데이터 흐름으로 나타낸다.
  3. 문법·업무 규칙 정의: 자료형, 길이, 범위, 문자, 열거, 교차 필드와 상태 규칙을 명시한다.
  4. 정규화 책임 결정: 인코딩·대소문자·경로·유니코드 표현을 어느 한 단계에서 표준화할지 정한다.
  5. 안전한 API 선택: 매개변수화, 구조화 인수, 안전한 템플릿과 서버 생성 식별자를 적용한다.
  6. 출력 문맥 식별: HTML, 속성, URL, 문서 등 실제 문맥별 인코딩을 적용한다.
  7. 경계 시험: 최소·최대, NULL, 다국어, 중복 키, 깊은 구조, 우회 표현과 비정상 순서를 시험한다.
  8. 자동·수동 검토: 정적 분석과 코드 검토로 문자열 결합·우회 API를 찾고 동적 시험으로 실제 해석을 확인한다.
  9. 운영 피드백: 반복 거부, 새로운 우회와 사고를 규칙·시험에 반영한다.

판단 기준:

  • 검증이 최종 신뢰 경계의 서버에서 수행되는가?
  • 허용 규칙이 업무 정의와 일치하고 예외가 명확한가?
  • 정규화 전후의 표현 우회가 없는가?
  • 명령 구조와 데이터가 안전한 API에서 분리되는가?
  • 출력 인코딩이 실제 문맥과 일치하는가?
  • 크기·중첩·횟수로 자원 고갈을 통제하는가?
  • 검증 실패가 민감정보를 노출하지 않고 추적 가능한가?
  • 같은 규칙이 모든 입력 경로에 적용되는가?

12. 구체 예시

상황

상품 검색 API는 검색어, 정렬 기준, 페이지 크기를 받고 결과 이름을 웹 화면에 표시한다.

취약한 설계

  • 검색어를 SQL 문자열에 연결한다.
  • 정렬 열을 요청 문자열 그대로 붙인다.
  • 페이지 크기를 숫자로만 변환하고 상한을 두지 않는다.
  • 상품명을 HTML에 그대로 출력한다.
  • 브라우저 검증만 있고 서버 검증이 없다.

안전한 설계

  1. 서버에서 검색어의 자료형과 최대 길이를 확인한다.
  2. 페이지 크기를 정수로 변환하고 업무상 허용 범위로 제한한다.
  3. 정렬 기준은 price, name, newest 같은 외부 선택값을 서버 내부의 승인된 열 표현에 매핑한다.
  4. 검색 조건 값은 매개변수로 바인딩한다.
  5. 결과 상품명은 원본 의미를 유지해 저장하고 HTML 본문에 출력할 때 문맥 인코딩한다.
  6. 요청 전체 크기와 호출 비용을 제한한다.
  7. 정상·최대 길이·다국어·인용 문자·알 수 없는 정렬값·과도한 페이지 크기를 시험한다.

이 설계에서 입력 허용 목록과 SQL 매개변수화, 출력 인코딩은 서로 다른 방어 역할을 한다. 어느 하나만으로 나머지를 생략하지 않는다.

14

13. 자주 틀리는 포인트

  1. Secure SDLC를 마지막 침투 시험으로 이해: 요구부터 운영·폐기까지 단계별 활동이다.
  2. shift-left가 운영 보안을 대체한다고 생각: 운영 취약점·사고 피드백이 다시 개발로 돌아와야 한다.
  3. 모든 프로젝트에 같은 보안 활동 깊이 적용: 자산·노출·영향을 기준으로 우선순위를 정한다.
  4. 클라이언트 검증만 신뢰: 요청을 직접 만들어 우회할 수 있어 서버 검증이 필요하다.
  5. 금지 문자열 목록으로 모든 공격을 차단: 알려진 정상 문법을 허용하는 방식이 우선이다.
  6. 입력 검증과 출력 인코딩을 동일시: 허용 여부 판단과 문맥 표현은 목적·시점이 다르다.
  7. SQL 특수 문자를 제거하면 안전하다고 생각: 매개변수화로 명령 구조와 값을 분리한다.
  8. HTML 인코딩 하나를 URL·스크립트·속성에 재사용: 실제 출력 문맥별 규칙이 다르다.
  9. 파일 확장자와 요청 콘텐츠 유형을 신뢰: 서버가 내용·크기·저장 위치를 통제한다.
  10. 내부 DB 값은 신뢰된다고 가정: 저장된 공격 문자열이 다른 문맥에서 실행될 수 있다.
  11. 정규화를 여러 단계에서 반복: 실제 사용할 단일 표현과 책임 단계를 정한다.

15. 정답과 해설

정답 1

Secure SDLC는 요구의 자산·보안 기준, 설계 위협 모델, 안전한 구현, 보안 시험, 배포 기준과 운영 피드백을 전체 생명주기에 통합한다. 마지막 시험만으로 설계 결함과 운영·공급망 위험을 충분히 다룰 수 없다.

정답 2

요구에서는 자산·오용 사례, 설계에서는 위협·신뢰 경계, 구현에서는 안전한 코딩·검토, 검증에서는 위험 기반 보안 시험, 배포·운영에서는 승인 산출물·감시·패치와 사고 피드백을 수행한다.

정답 3

보안 활동을 소프트웨어 생명주기에 체계적으로 배치하여 취약점을 조기에 줄이고, 검증·릴리스·대응까지 지속 관리하는 공통 목적이 있다.

정답 4

공격자는 브라우저 화면과 스크립트를 거치지 않고 요청을 직접 만들어 전송할 수 있기 때문이다. 최종 처리 서버가 같은 규칙을 강제해야 한다.

정답 5

자료형, 길이, 값 범위, 허용 문자, 열거 값, 구조·필드, 중첩 깊이·배열 크기, 교차 필드와 업무 상태 중 여섯 가지다.

정답 6

입력 검증은 값이 허용된 데이터인지 신뢰 경계에서 판단한다. 출력 인코딩은 허용된 데이터를 HTML·URL 등 실제 문맥에서 명령이 아닌 데이터로 안전하게 표현한다.

정답 7

SQL 문장 구조는 미리 고정되고 입력은 별도 데이터 값으로 전달되어 입력 문자가 SQL 구문으로 해석되는 것을 막기 때문이다.

정답 8

서버 생성 내부 파일명, 기준 디렉터리와 정규 경로 비교, 허용 파일 집합, 심볼릭 링크 경계 확인, 파일 계정 최소 권한 중 네 가지다.

정답 9

확장자와 요청의 콘텐츠 유형은 공격자가 바꿀 수 있다. 실제 내용과 크기를 확인하고 서버 생성 이름, 실행 불가 격리 영역, 최소 권한과 악성 콘텐츠 검사를 적용한다.

정답 10

허용 필드·자료형 검증, 전체 크기, 중첩 깊이와 배열 수 제한, 외부 자원 참조 비활성화, 중복 키 정책, 필요한 기능만 명시적 허용 중 네 가지다.

핵심 요약

  • Secure SDLC(Software Development Life Cycle)는 요구, 위협 설계, 안전한 구현, 검증, 릴리스, 운영·폐기의 보안 활동과 증거를 연결한다.
  • 보안은 위험 기반, 안전한 기본값, 최소 권한·기능, 심층 방어, 안전한 실패와 추적성 원칙으로 적용한다.
  • 입력데이터 검증 및 표현은 신뢰 경계에서 입력을 정규화·검증하고, 안전한 API와 출력 문맥별 인코딩으로 명령과 데이터를 분리한다.
  • 클라이언트 검증은 사용성 보조이며 서버 검증을 대신하지 못한다. 허용 목록, 자료형·길이·범위·구조와 업무 규칙을 함께 적용한다.
  • SQL은 매개변수화, 명령은 구조화 인수, 경로는 기준 디렉터리와 서버 식별자, 웹 출력은 실제 문맥 인코딩을 사용한다.
  • 자동 검사 하나에 의존하지 말고 코드 검토, 경계·오용 시험, 운영 피드백으로 규칙과 Secure SDLC를 지속 개선한다.
