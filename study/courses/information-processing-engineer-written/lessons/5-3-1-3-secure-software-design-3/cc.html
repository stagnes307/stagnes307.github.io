01

출제범위와 학습 목표

이 레슨은 실패 상황에서도 정보 노출과 데이터 불일치를 막는 에러처리, 인증된 사용자 상태를 안전하게 유지·종료하는 세션통제를 다룬다. 학습 후에는 오류의 탐지–분류–복구–기록–응답 흐름을 설계하고, 세션 식별자의 생성·전달·갱신·만료·폐기 정책과 위험 기반 재인증 기준을 설명할 수 있어야 한다.

앞 레슨의 인증·접근제어·기밀성, 다음 구현 레슨의 암호 알고리즘과 코드오류는 필요한 연결만 한다. 공격 절차나 우회 기법이 아니라 오류와 세션 문제를 예방·탐지·대응하는 설계 원리에 집중한다.

02

에러와 예외의 의미

에러는 프로그램이 기대한 처리를 완료하지 못하는 상태를 넓게 가리킨다. 예외는 언어 또는 실행환경이 비정상 상황을 전달하는 한 메커니즘이다. 모든 실패가 예외로만 표현되는 것은 아니며 반환 상태, 오류 코드, 검증 결과로 전달될 수 있다.

오류를 다음처럼 구분하면 대응이 명확해진다.

  • 입력·업무 오류: 필수값 누락, 범위 위반, 허용되지 않는 상태 전이
  • 인증·인가 오류: 인증 정보 부재, 권한 부족, 정책 거부
  • 자원 오류: 파일 부재, 저장 공간 부족, 연결 시간 초과
  • 데이터 오류: 제약조건 위반, 일관되지 않은 상태, 변환 실패
  • 프로그래밍 오류: NULL 참조, 잘못된 인덱스, 불가능해야 할 분기
  • 시스템 오류: 프로세스 자원 고갈, 하위 서비스 장애

사용자가 고칠 수 있는 입력 오류와 운영자가 대응해야 할 시스템 오류를 같은 메시지와 재시도 정책으로 처리하지 않는다. 실패 원인을 숨기지 않되 공개 범위에 맞춰 표현한다.

03

안전한 에러처리 목표

에러처리의 목표는 단순히 프로그램이 종료되지 않게 하는 것이 아니다.

  1. 잘못된 상태가 확정되지 않도록 한다.
  2. 파일·연결·잠금 같은 자원을 확실히 정리한다.
  3. 호출자가 재시도·수정·중단을 판단할 수 있게 한다.
  4. 사용자에게 내부 구조와 민감정보를 노출하지 않는다.
  5. 운영자가 원인을 추적할 충분한 진단 정보를 남긴다.
  6. 정상과 실패를 상태 코드와 결과 계약에서 구분한다.

예외를 모두 잡아 성공값 0이나 빈 목록을 반환하면 정상적으로 결과가 없는 상황과 실패를 구분하지 못한다. 시스템은 조용해 보이지만 데이터 누락이 쌓일 수 있다.

04

오류 처리 경계

오류는 책임 있는 계층에서 처리한다. 입력 계층은 형식 오류를 업무용 오류로 변환하고, 업무 계층은 상태 전이 실패와 트랜잭션 경계를 관리하며, 기반 계층은 구체 연결 오류를 의미 있는 상위 오류로 전달한다.

낮은 계층이 사용자 화면 문구까지 결정하면 재사용이 어렵고 내부 정보가 노출될 수 있다. 반대로 모든 오류를 최상위까지 원형 그대로 올리면 기술 세부와 비밀이 응답에 섞인다. 각 경계에서 필요한 문맥을 추가하되 원래 원인을 진단용으로 보존한다.

외부 요청 ↓ 형식 검증 실패 → 안전한 입력 오류 업무 처리 ↓ 규칙 위반 → 업무 상태 오류 저장·외부 연동 ↓ 기술 실패 → 분류된 기반 오류 최상위 처리기 → 트랜잭션 정리 확인 → 내부 로그와 상관 식별자 → 외부에는 안정된 코드와 최소 메시지

포괄 오류 처리기는 예상하지 못한 실패의 마지막 안전망이지, 모든 세부 오류를 무시하는 수단이 아니다.

05

Fail Safe와 Fail Secure

Fail Safe는 실패했을 때 사람과 시스템의 피해를 최소화하는 안전한 상태로 가는 개념이다. 보안 관점의 Fail Secure는 보안 통제가 정상 작동하지 않을 때 접근을 허용하지 않고 보호 상태를 유지하는 데 초점을 둔다.

권한 정책 저장소를 읽지 못했을 때 “확인할 수 없으니 허용”하면 안 된다. 결제 상태 저장이 불확실한데 성공 응답을 보내 재시도를 유도하는 것도 위험하다. 결과를 확정할 수 없다면 미완료 또는 확인 필요 상태로 두고 중복 방지 식별자로 안전하게 조회·재처리한다.

가용성 때문에 무조건 차단할 수 없는 안전 시스템도 있을 수 있으므로 위험 분석과 업무 연속성 정책에 따라 별도 안전 모드를 설계한다. 중요한 것은 실패 동작을 우연에 맡기지 않고 요구사항으로 정하는 것이다.

06

정보 노출 방지

외부 오류 메시지에 스택 추적, 내부 파일 경로, 데이터베이스 질의, 테이블명, 구성값, 라이브러리 버전, 사용자 존재 여부를 불필요하게 포함하지 않는다. 공격자에게 구조를 알려 줄 뿐 아니라 개인정보와 비밀이 노출될 수 있다.

사용자 응답은 안정적인 오류 코드, 이해 가능한 최소 메시지, 안전한 상관 식별자와 필요한 수정 필드 정도를 제공한다. 내부 로그에는 더 자세한 오류 유형, 호출 위치, 하위 원인, 환경 식별자를 접근 통제하에 기록한다.

개발환경의 상세 오류 화면이 운영에 켜지지 않도록 환경 설정을 검증한다. 단순히 화면 CSS로 숨기는 것이 아니라 서버가 상세 내용을 전송하지 않아야 한다.

07

로그와 오류 응답의 분리

오류 응답은 API 소비자와의 계약이고, 로그는 운영 진단 기록이다. 사용자에게 “오류가 발생했습니다”만 보여 주더라도 운영 로그에는 어떤 요청 흐름에서 어떤 원인이 발생했는지 식별할 정보가 있어야 한다.

로그 권장 항목은 사건 시각, 서비스·버전, 요청 상관 식별자, 인증된 주체의 안전한 식별자, 오류 분류, 처리 단계, 결과다. 비밀번호, 세션 토큰, 전체 요청 본문, 불필요한 개인정보는 남기지 않는다.

동일 오류가 대량 반복될 때 로그 폭주로 저장 공간이 고갈되지 않도록 집계·속도 제한과 경보를 둔다. 그러나 증거를 전부 버려 발생 규모를 알 수 없게 해서는 안 된다.

08

트랜잭션과 자원 정리

여러 변경이 하나의 업무 단위라면 일부 실패 시 전체가 일관된 상태가 되도록 롤백한다. 오류를 잡은 뒤 계속 진행하기 전에 이미 확정된 부분과 되돌린 부분을 확인한다. 외부 시스템 호출은 데이터베이스 롤백만으로 되돌아오지 않을 수 있어 보상과 중복 방지 설계가 필요하다.

파일, 네트워크 연결, 데이터베이스 연결, 잠금은 정상·실패 모든 경로에서 정리한다. 언어의 자동 자원 관리 구문을 사용하면 빠뜨릴 가능성을 줄인다. 정리 자체가 실패할 수 있으므로 원래 오류를 덮어쓰지 않고 두 정보를 모두 진단 가능하게 한다.

안전한 의사코드는 다음 흐름을 갖는다.

function process(request): correlationId = newCorrelationId() try: command = validateAndMap(request) result = transactionallyExecute(command) return success(minimize(result), correlationId) catch KnownBusinessError as error: logExpected(error.category, correlationId) return safeBusinessError(error.publicCode, correlationId) catch UnexpectedError as error: logRestrictedDetails(error, correlationId) return genericServerError(correlationId) finally: closeOwnedResources()

실제 문법은 언어마다 다르지만 알려진 오류를 구체적으로 처리하고, 예상 밖 오류는 상세를 노출하지 않으며, 자원을 항상 정리한다는 원리는 공통이다.

09

재시도 판단

재시도는 모든 오류의 해결책이 아니다. 일시적인 연결 실패나 교착 해제처럼 다시 시도해 성공할 가능성이 있는 오류와, 입력 형식 오류·권한 부족·스키마 불일치처럼 그대로 반복해도 실패할 오류를 구분한다.

재시도에는 최대 횟수, 점진적 대기, 무작위 분산, 전체 시간 제한을 둔다. 많은 클라이언트가 동시에 즉시 재시도하면 장애를 악화한다. 상태 변경 요청은 멱등성 키나 업무 유일성으로 중복 효과를 막는다.

하위 서비스가 계속 실패하면 회로 차단과 같은 방식으로 잠시 호출을 제한하고 회복 상태를 확인할 수 있다. 정확한 기준은 서비스 수준과 위험에 맞춰 설정한다.

10

세션의 개념

세션(Session)은 여러 요청 사이에서 인증된 사용자와 작업 상태를 연결하는 논리적 대화 단위다. HTTP처럼 요청 자체가 독립적인 환경에서는 서버 저장소나 보호된 토큰을 사용해 로그인 상태를 이어 갈 수 있다.

세션 식별자는 세션을 찾는 열쇠다. 식별자 자체에 비밀번호를 담지 않더라도 탈취되면 사용자를 대신할 수 있으므로 인증 비밀처럼 보호한다. 충분히 예측하기 어렵게 생성하고 URL이나 로그에 노출하지 않으며 안전한 전송 경로만 사용한다.

세션 저장 방식은 서버 상태형과 토큰 기반으로 구분해 볼 수 있다.

  • 서버 상태형은 식별자가 서버 저장소의 세션 상태를 가리킨다. 즉시 폐기와 중앙 통제가 쉽지만 저장소 확장과 가용성을 설계해야 한다.
  • 보호된 토큰은 일부 상태와 유효기간을 담아 서버가 검증할 수 있다. 분산 처리에 유리할 수 있지만 발급 후 즉시 폐기, 권한 변경 반영, 크기와 키 관리가 복잡하다.

두 방식 모두 안전한 서명·보호, 만료, 재발급, 수신자·발급자 확인이 필요하다. 토큰 내용을 읽을 수 없다고 자동으로 안전하거나, 서명되었다고 기밀성이 생기는 것은 아니다.

11

세션통제의 생명주기

세션통제는 생성부터 종료까지 다음 단계로 설계한다.

  1. 인증 성공 후 새 세션을 만든다.
  2. 인증 전 임시 상태가 있었다면 인증 후 식별자를 새로 발급한다.
  3. 세션에는 필요한 최소 주체·인증 강도·생성·최근 활동 정보를 연결한다.
  4. 매 요청에서 유효기간, 폐기 여부, 권한과 위험 조건을 확인한다.
  5. 중요 작업 전에 필요하면 재인증 또는 추가 인증을 요구한다.
  6. 일정 미사용 시간과 절대 최대 수명에 따라 만료한다.
  7. 로그아웃, 비밀번호 변경, 계정 정지, 위험 탐지 시 폐기한다.
  8. 종료 후 식별자와 서버 상태를 다시 사용할 수 없게 한다.

로그인 직전과 직후 같은 식별자를 계속 사용하면 공격자가 미리 정한 식별자가 인증 상태로 승격되는 세션 고정 위험이 생길 수 있다. 인증 수준이 올라갈 때 식별자를 회전한다.

12

세션 식별자 전달 보호

브라우저 쿠키를 사용한다면 보안 통신에서만 전송, 클라이언트 스크립트 접근 제한, 교차 사이트 전송 범위 제한, 경로·도메인 최소화 같은 속성을 위험에 맞게 설정한다. 구체 속성 조합은 애플리케이션 흐름과 최신 브라우저 정책을 따른다.

세션 식별자를 URL 질의에 넣으면 브라우저 기록, 참조 정보, 로그, 화면 공유를 통해 노출될 수 있다. 응답 본문이나 오류에 다시 출력하지 않는다. 전송 중 보호와 서버 인증이 없으면 네트워크에서 세션이 노출되거나 잘못된 서버에 전송될 수 있다.

토큰을 브라우저 저장소에 둘 때 스크립트 침해와 지속성 위험을 고려한다. 하나의 저장 방식이 모든 위협에 최선은 아니므로 클라이언트 구조, 교차 출처 요청, 스크립트 실행 위험과 폐기 요구를 함께 본다.

13

시간 제한과 동시 세션

미사용 시간 제한은 마지막 활동 후 일정 시간 요청이 없으면 만료한다. 절대 시간 제한은 계속 사용 중이어도 세션의 최대 수명을 제한한다. 둘을 함께 사용하면 방치 세션과 장기 탈취 위험을 줄일 수 있다.

모든 요청이 민감 세션 수명을 무한히 연장하게 하지 않는다. 배경 자동 요청이 사용자 활동처럼 간주되면 미사용 만료가 작동하지 않을 수 있다. 최근 인증 시각과 최근 활동 시각을 구분한다.

동시 세션을 허용할지 제한할지는 업무 위험과 사용성을 고려한다. 새 로그인 때 기존 세션 알림, 장치 목록과 원격 종료 기능을 제공할 수 있다. IP 주소가 바뀌었다는 이유만으로 무조건 종료하면 이동망 사용자를 방해할 수 있으므로 여러 신호로 위험을 평가한다.

14

로그아웃과 강제 폐기

로그아웃은 클라이언트 화면을 로그인 페이지로 보내는 것만이 아니다. 서버 세션을 제거하거나 토큰의 갱신 권한을 폐기하고, 클라이언트 보관 식별자를 지워야 한다. 뒤로 가기 캐시에 민감 화면이 남는 문제도 응답 캐시 정책으로 고려한다.

비밀번호 변경, 계정 잠금, 권한 축소, 기기 분실, 사고 대응 시 기존 세션을 전체 또는 선택적으로 종료할 수 있어야 한다. 토큰 기반 설계에서는 짧은 수명, 세션 버전, 폐기 목록, 갱신 토큰 통제 같은 전략을 위험에 맞게 조합한다.

세션 폐기 저장소 장애 시 기존 토큰을 계속 허용할지에 대한 Fail Secure 정책을 정한다. 고위험 관리 기능과 일반 조회가 같은 결정을 가질 필요는 없다.

15

세션과 요청 위조 방어

브라우저가 세션 쿠키를 자동 첨부하면 사용자가 의도하지 않은 출처에서 상태 변경 요청이 유도될 수 있다. 상태 변경에는 안전한 요청 방식, 위조 방지 토큰, 출처 검증, 적절한 쿠키 정책을 적용한다.

세션이 유효하다는 사실만으로 요청 의도를 확인한 것이 아니다. 결제·권한 변경처럼 중요한 작업은 현재 사용자에게 대상과 효과를 명확히 보여 주고 최근 인증 또는 추가 확인을 요구할 수 있다.

조회 요청이 서버 상태를 변경하도록 만들면 외부 링크나 미리 불러오기 때문에 의도치 않은 실행이 생길 수 있다. 요청 방법의 안전성과 멱등성 의미를 지킨다.

16

세션 이상 탐지와 대응

탐지 신호에는 짧은 시간의 비정상 지역 변화, 새 장치, 과도한 실패, 동시에 먼 위치에서 사용, 권한 변경 직후 중요 작업, 비정상 요청 속도가 있다. 단일 신호만으로 공격이라고 단정하면 오탐이 많다.

위험 점수에 따라 추가 인증, 특정 작업 제한, 세션 회전, 사용자 알림, 강제 종료를 적용한다. 탐지에는 개인정보 최소화와 보존 정책을 함께 적용한다.

사고가 의심되면 관련 세션을 폐기하고 인증 요소와 비밀을 교체하며 로그를 보존해 영향 범위를 조사한다. 단순 로그아웃만으로 이미 변경된 데이터가 복구되는 것은 아니므로 업무별 대응 절차가 필요하다.

17

방어 중심 예시: 계정 설정 변경

설정 변경 요청 → 세션 식별자 안전 수신 → 서명·저장 상태·만료·폐기 확인 → 현재 계정과 요청 대상 일치 확인 → 최근 강한 인증 여부 확인 → 변경 전 기존 연락처로 통지 → 업무 변경과 감사 기록 → 세션 회전 또는 위험에 따른 기존 세션 정리

사용자가 이메일 주소를 바꾸는 작업은 탈취자가 계정 복구 채널을 장악할 수 있는 중요 작업이다. 세션이 단순히 유효한지만 보지 않고 최근 인증과 알림을 추가한다. 오류 응답에는 기존 이메일 전체나 내부 정책 상세를 노출하지 않는다.

18

설계·구현 절차와 판단 기준

  1. 실패 유형과 사용자·데이터·가용성 영향을 분류한다.
  2. 계층별 처리 책임과 외부 오류 계약을 정한다.
  3. 트랜잭션, 보상, 자원 정리, 재시도 가능성을 설계한다.
  4. 내부 로그와 외부 응답의 정보 수준을 분리한다.
  5. 세션 저장·전달 방식과 신뢰 경계를 선택한다.
  6. 식별자 생성·회전, 미사용·절대 만료, 로그아웃·강제 폐기를 설계한다.
  7. 중요 작업 재인증과 요청 위조 방어, 이상 탐지를 정한다.
  8. 정상·오류·시간 초과·중복·로그아웃·권한 변경 시나리오를 시험한다.
  9. 로그의 민감정보, 세션 누수, 실패 시 허용 여부를 검토한다.
  10. 운영 경보와 사고 시 전체 세션 폐기·복구 절차를 훈련한다.

판단 기준은 오류가 일관성을 해치지 않는가, 외부 정보가 최소인가, 운영자가 원인을 추적할 수 있는가, 세션이 예측·재사용·과도하게 지속되지 않는가, 종료가 실제로 강제되는가, 통제가 사용성과 가용성 위험에 비례하는가다.

19

자주 틀리는 포인트

  • 예외를 잡았다는 사실만으로 트랜잭션과 자원이 자동 정리된다고 보지 않는다.
  • 모든 오류를 빈 결과나 성공 코드로 바꾸면 실패와 정상 없음이 구분되지 않는다.
  • 외부에는 최소 메시지를, 내부에는 접근 통제된 진단을 남긴다.
  • 상세 오류 화면을 CSS로 숨겨도 서버가 내용을 보내면 정보 노출이다.
  • 동일 요청 재시도에는 일시 오류 판단과 중복 효과 방지가 함께 필요하다.
  • 세션 식별자는 사용자 비밀번호를 담지 않아도 인증 비밀처럼 보호한다.
  • 로그인 전후에 같은 식별자를 유지하지 않고 인증 수준 상승 시 회전한다.
  • 미사용 시간 제한과 절대 수명은 서로 다른 목적이다.
  • 로그아웃 화면 이동만으로 서버 세션이 폐기되는 것은 아니다.
  • 서명된 토큰은 변조 방지를 제공할 수 있지만 내용 기밀성을 자동 제공하지 않는다.
  • 세션 쿠키가 자동 전송되면 요청 위조 위험을 별도로 고려한다.
  • IP 변경 하나만으로 탈취를 확정하지 않고 여러 신호와 사용성을 본다.

확인 문제

  1. 입력 오류, 업무 오류, 자원 오류, 프로그래밍 오류를 예와 함께 구분하라.
  2. 안전한 에러처리의 목표를 네 가지 이상 쓰라.
  3. 외부 오류 응답과 내부 오류 로그에 담을 정보가 달라야 하는 이유는 무엇인가?
  4. 일시 오류와 영구 오류의 재시도 정책을 비교하라.
  5. 서버 상태형 세션과 보호된 토큰 방식의 장단점을 설명하라.
  6. 인증 성공 뒤 세션 식별자를 회전해야 하는 이유는 무엇인가?
  7. 미사용 시간 제한과 절대 시간 제한을 비교하라.
  8. 로그아웃 때 서버와 클라이언트에서 수행할 일을 쓰라.
  9. 세션이 유효해도 중요 작업에 재인증이 필요할 수 있는 이유는 무엇인가?
  10. 세션 이상 탐지 뒤 가능한 단계적 대응을 쓰라.
21

정답과 해설

  1. 잘못된 날짜 형식은 입력 오류, 이미 취소된 주문의 재취소는 업무 오류, 저장 공간 부족은 자원 오류, 불가능한 NULL 참조는 프로그래밍 오류다. 분류에 따라 사용자 수정·재시도·운영 대응이 달라진다.
  2. 일관성 보존, 자원 정리, 의미 있는 실패 전달, 정보 노출 방지, 운영 진단, 정상·실패 상태 구분이 목표다.
  3. 외부 소비자에게 내부 구조와 비밀을 노출하지 않으면서도 운영자는 원인을 조사해야 하기 때문이다. 상관 식별자로 두 기록을 연결한다.
  4. 일시 오류는 제한 횟수와 지연, 멱등성 보호 아래 재시도할 수 있다. 잘못된 입력·권한 부족 같은 영구 오류는 원인이 바뀌기 전 반복하지 않는다.
  5. 서버 상태형은 즉시 폐기와 중앙 통제가 쉽지만 저장소 확장이 필요하다. 보호된 토큰은 분산 검증에 유리할 수 있지만 즉시 폐기와 권한 변경 반영, 키 관리가 복잡하다.
  6. 공격자가 인증 전에 알게 된 식별자가 인증된 세션으로 그대로 승격되는 고정 위험을 줄이기 위해서다.
  7. 미사용 제한은 활동이 없는 기간을, 절대 제한은 활동 여부와 무관한 최대 수명을 제한한다. 둘을 함께 적용할 수 있다.
  8. 서버 세션 또는 갱신 권한을 폐기하고 클라이언트 식별자를 제거하며 민감 응답의 캐시 정책을 적용한다.
  9. 세션이 오래되었거나 탈취되었을 수 있고, 결제·권한·복구 채널 변경은 영향이 커 현재 사용자의 의도를 더 강하게 확인해야 하기 때문이다.
  10. 위험 신호에 따라 추가 인증, 민감 작업 제한, 세션 회전, 사용자 알림, 선택 또는 전체 강제 종료를 수행하고 영향과 변경 기록을 조사한다.
22

핵심 요약

  • 에러처리는 탐지, 분류, 일관성 복구, 자원 정리, 안전한 응답, 제한된 로그와 재시도 판단의 전체 흐름이다.
  • 오류를 성공으로 숨기지 않고 외부 계약과 내부 진단을 분리하며 실패 시 안전한 상태를 유지한다.
  • 세션통제는 식별자의 안전한 생성·전달·회전, 요청별 검증, 미사용·절대 만료, 로그아웃·강제 폐기를 포함한다.
  • 인증과 권한 수준이 올라갈 때 세션을 회전하고 중요한 작업에는 최근 재인증을 요구할 수 있다.
  • 브라우저의 자동 인증 전송에는 요청 위조 방어를 적용하고 위험 신호에는 단계적으로 대응한다.
  • 공격 절차를 재현하기보다 세션 누출·고정·과도한 지속을 막고 탐지·폐기·복구가 가능한지를 검증한다.
