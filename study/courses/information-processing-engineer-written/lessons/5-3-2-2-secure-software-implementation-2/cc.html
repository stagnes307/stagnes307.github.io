01

출제범위와 학습 목표

이 레슨은 민감한 상태와 구현 세부를 안전한 경계 안에 감추는 캡슐화, 라이브러리·운영체제·서비스 인터페이스의 계약을 잘못 이해해 생기는 API 오용을 다룬다. 학습 후에는 정보 은닉, 최소 인터페이스, 불변식 보호와 민감정보 노출 방지를 설명하고, API의 사전조건·반환값·자원 소유권·보안 기본값·수명·동시성 계약을 검토해 오용을 예방할 수 있어야 한다.

앞 레슨의 암호 알고리즘과 메모리·산술 코드오류를 반복하지 않는다. 이 레슨은 구현 경계와 API 사용 방식에 집중한다. 실제 침해에 악용되는 호출법 대신 안전한 래퍼, 검증, 오류 확인, 코드 검토와 시험 절차를 다룬다.

02

캡슐화의 개념

캡슐화(Encapsulation)는 관련 데이터와 그 데이터를 다루는 행동을 하나의 단위로 묶고 외부가 내부 표현을 임의로 변경하지 못하게 접근을 통제하는 원리다. 정보 은닉은 변경 가능하거나 민감한 내부 세부를 공개 계약 뒤에 숨겨 영향과 노출을 줄인다.

계좌 객체가 잔액 필드를 공개하면 외부 코드가 검증 없이 음수나 임의 값으로 바꿀 수 있다. 잔액을 비공개로 두고 deposit과 withdraw 같은 업무 메서드가 금액·상태·권한 규칙을 확인하면 불변식을 한곳에서 지킬 수 있다.

필드를 비공개로 선언한 뒤 아무 값이나 받는 공개 setter를 제공하면 문법적으로는 감쌌지만 의미 있는 캡슐화는 약하다. 외부에 필요한 행위만 제공하고 객체가 유효한 상태 전이를 책임져야 한다.

03

추상화 경계와 최소 인터페이스

공개 인터페이스는 소비자가 알아야 할 안정적인 계약만 보여 주고 내부 자료 구조, 저장 위치, 보안 정책 구현은 숨긴다. 공개 항목이 많을수록 호환성 유지와 권한 검토 범위가 넓어진다.

최소 인터페이스는 기능을 못 쓰게 하는 것이 아니라 목적에 필요한 가장 좁은 동작을 제공하는 것이다. 전체 사용자 객체를 반환하기보다 표시 이름만 필요한 기능에는 그 값만 반환한다. 임의 SQL 실행 기능보다 “주문 조회” 같은 제한된 업무 연산을 제공한다.

내부 메서드와 디버그 기능이 외부 라우팅, 원격 호출, 플러그인 경계로 우연히 노출되지 않게 한다. 문서에 없다는 사실은 접근통제가 아니다. 빌드·배포 결과에서 실제 공개 표면을 자동 검사할 수 있다.

04

불변식 보호

불변식은 객체가 유효한 동안 항상 만족해야 하는 규칙이다. 주문 총액은 항목 합계와 일치하고, 승인된 주문은 임의 수정되지 않으며, 기간의 종료일은 시작일보다 빠르지 않아야 한다.

생성자나 팩터리에서 필요한 값을 모두 검증해 유효한 객체만 만든다. 외부가 변경 가능한 목록을 넘겼다면 내부에서 방어적 복사하거나 불변 뷰를 사용해 생성 후 몰래 바뀌지 않게 한다.

반환할 때도 내부의 변경 가능한 컬렉션 참조를 그대로 주면 외부가 객체 메서드를 거치지 않고 상태를 바꿀 수 있다. 읽기 전용 표현, 복사본, 제한된 반복자를 제공한다. 다만 대용량 복사의 비용과 수명 요구를 함께 판단한다.

동시 실행에서는 메서드 하나가 불변식을 확인하고 변경하는 전체 과정이 원자적이어야 할 수 있다. 필드가 비공개라는 사실만으로 스레드 안전성이 생기는 것은 아니다.

05

민감정보 캡슐화

비밀번호, 암호 키, 인증 토큰, 개인정보 객체는 평문 문자열로 여러 계층에 전달하지 않는다. 사용 목적이 제한된 타입과 서비스를 만들고 원문 접근 지점을 최소화한다.

예를 들어 비밀번호 검증 서비스는 비밀번호 해시값을 외부에 반환하지 않고 verify라는 동작만 제공한다. 키 관리 서비스는 키 원문을 장기 반환하기보다 승인된 암호 연산을 제한된 권한으로 수행하게 할 수 있다.

객체의 자동 문자열 변환, 디버그 출력, 직렬화 기능이 모든 필드를 포함하면 로그와 오류에 비밀이 노출될 수 있다. 민감 타입의 출력은 마스킹하고 기본 직렬화 대상에서 제외한다.

개인정보를 담은 객체가 캐시, 임시 파일, 충돌 보고서로 복제되는지도 살핀다. 캡슐화 경계는 클래스 접근 지정자뿐 아니라 프로세스·서비스·저장소 경계까지 확장된다.

06

모듈과 계층 캡슐화

모듈은 공개 API와 내부 구현을 구분한다. 데이터 접근 모듈은 저장소의 구체 질의와 자격 증명을 감추고, 업무 계층에는 도메인 의미의 조회·저장 계약을 제공한다. 표현 계층이 데이터베이스 연결을 직접 가져가면 권한과 트랜잭션 규칙이 흩어진다.

서비스 경계에서는 내부 오류, 데이터베이스 키, 관리자 필드를 외부 응답 모델과 분리한다. 내부 객체를 그대로 JSON으로 자동 직렬화하면 나중에 추가한 민감 필드가 예기치 않게 외부에 나갈 수 있다. 허용한 필드만 명시적으로 변환한다.

플러그인이나 확장 코드에는 전체 애플리케이션 객체 대신 필요한 기능만 가진 제한된 역량 객체를 제공한다. 내부 참조 하나로 파일·네트워크·권한 기능 전체에 접근하게 하지 않는다.

07

API 오용의 개념

API(Application Programming Interface)는 함수, 클래스, 운영체제 호출, 원격 서비스가 제공하는 사용 계약이다. API 오용은 문법상 호출이 가능하더라도 전제조건, 순서, 반환값, 보안 옵션, 자원 수명과 실패 의미를 잘못 적용하는 것이다.

오용은 개발자 실수만의 문제가 아니다. 안전한 사용법이 지나치게 복잡하고 위험한 기본값이 쉬운 API 설계는 오용 가능성을 높인다. 안전한 API는 잘못된 상태를 타입과 구조로 표현하기 어렵게 하고, 위험한 기능에는 명시적인 선택과 검증을 요구한다.

09

보안 API 오용

암호 API에서 알고리즘 이름만 선택하고 키·nonce·인증 태그 처리와 검증 실패를 무시하면 안전하지 않다. 낮은 수준 구성요소를 직접 조합하기보다 목적에 맞는 고수준 승인 API를 사용한다.

인증서 검증 오류를 시험 편의로 무시하거나 모든 대상 이름을 허용하는 설정은 운영에서 상대 인증을 무력화한다. 시험 환경도 별도 신뢰 저장소를 사용하고 우회 플래그가 운영 빌드에 포함되지 않게 검사한다.

난수가 필요한 보안 값에 일반 시뮬레이션용 난수 API를 사용하지 않는다. 용도 이름이 비슷해도 예측 불가능성 계약이 다르다. 검증된 보안 난수원을 사용한다.

권한 API에서 “실행 가능”만 확인하고 대상 객체 소유 관계를 빠뜨리거나, 관리 API의 넓은 권한을 일반 요청 경로에서 공유하지 않는다.

10

문자열·경로·명령 API 오용

구조화된 값을 문자열로 이어 붙여 SQL, 운영체제 명령, 경로, URL을 만들면 데이터가 제어 구조로 해석될 수 있다. 각 문맥의 구조화 API를 사용한다.

  • 데이터베이스 값은 매개변수화된 질의로 전달한다.
  • 프로세스 실행은 명령 문자열보다 실행 파일과 인수 배열을 구분한다.
  • 파일 경로는 경로 결합과 정규화 API를 사용하고 최종 허용 루트를 확인한다.
  • URL은 구성 요소별 인코딩과 허용 프로토콜·대상을 적용한다.

한 문맥의 이스케이프를 다른 문맥에 재사용하지 않는다. HTML 인코딩이 SQL 매개변수화를 대신하지 못하고, URL 인코딩이 파일 경로 허용 검사를 대신하지 못한다.

구조 요소인 정렬 열이나 파일 종류는 외부 문자열을 그대로 넣지 않고 서버가 정의한 허용값을 실제 내부 값으로 매핑한다.

11

시간·경계·단위 API 오용

시간 API는 시간대, 달력, 일광 절약, 윤초 처리, 단조 시계와 실제 시각의 차이를 고려한다. 경과 시간 측정에는 시스템 시각 변경의 영향을 덜 받는 단조 시계를 사용하고, 업무 시각에는 명시적 시간대와 표준 표현을 사용한다.

기간 인수가 초인지 밀리초인지 혼동하면 지나치게 짧은 만료나 긴 대기가 생긴다. Duration 같은 단위 타입이나 변수 이름으로 구분한다.

길이 API도 문자 수, 코드 단위 수, 바이트 수가 다를 수 있다. 버퍼 할당과 네트워크 길이는 바이트, 사용자 표시 제한은 문자 단위 요구를 명확히 한다.

인덱스가 끝 위치를 포함하는지 제외하는지, 최대 길이가 실제 데이터만인지 종료 표시까지 포함하는지 문서를 확인한다. 경계값 0, 1, 최대, 최대+1을 시험한다.

12

자원·수명 API 오용

파일·연결·응답 본문 같은 자원은 성공과 실패 모든 경로에서 닫는다. 자동 자원 관리 구문을 사용하고 함수가 자원을 소유하는지 빌리는지 이름과 타입으로 명시한다.

비동기 API는 호출이 반환되었다고 작업이 끝난 것이 아닐 수 있다. 완료 신호를 기다리고, 취소·시간 제한·부분 결과의 의미를 처리한다. 함수 지역 버퍼를 비동기 작업에 넘긴 뒤 수명이 끝나는 오류를 피한다.

콜백을 등록하면 해제 시점과 중복 호출 가능성, 어느 실행 문맥에서 호출되는지 확인한다. 객체가 이미 종료된 뒤 콜백이 도착할 수 있으므로 상태를 안전하게 검증한다.

연결 풀에서 빌린 연결은 물리 연결을 종료하는 것과 풀에 반환하는 의미가 다를 수 있다. 라이브러리 계약에 따라 반납하고 세션 상태·트랜잭션을 다음 사용자에게 누출하지 않게 초기화한다.

13

반환값과 실패 계약

API 호출 뒤 결과를 확인하지 않으면 다음 단계가 잘못된 전제에서 실행된다. 파일 쓰기가 일부만 성공했거나 접근통제 API가 오류를 반환했는데 참으로 취급하면 데이터 손상과 권한 문제가 생긴다.

특별한 숫자 하나로 실패를 표현하는 API에서는 정상값과 겹치지 않는지, 별도 오류 정보를 언제 읽어야 하는지 확인한다. 최신 고수준 API가 명시적인 결과 타입을 제공한다면 활용한다.

result = accessPolicy.evaluate(actor, action, resource) switch result.kind: case ALLOW: performAuthorizedAction() case DENY: recordPolicyDenial(result.reasonCode) return safeDenied() case ERROR: recordInternalFailure(result.diagnosticId) return failSecure()

오류를 DENY와 구분해 내부 진단하되 외부에는 불필요한 정책 세부를 노출하지 않는다. ERROR를 ALLOW로 해석하지 않는 것이 핵심이다.

14

안전한 래퍼와 어댑터

조직에서 반복 사용하는 위험한 API는 얇은 래퍼로 안전한 설정과 검증을 중앙화할 수 있다. 예를 들어 외부 요청 클라이언트 래퍼가 허용 프로토콜, 시간 제한, 응답 크기, 인증서 검증, 추적 식별자를 기본 적용한다.

래퍼는 모든 하위 기능을 그대로 다시 노출하지 않고 승인된 사용 사례만 제공한다. 위험한 원시 API 접근을 코드 검색·정적 분석 규칙으로 제한한다. 다만 래퍼 자체가 최신 하위 라이브러리와 호환되는지 유지보수해야 한다.

어댑터는 외부 라이브러리 모델을 내부 계약으로 변환해 교체와 시험을 쉽게 한다. 외부 예외·오류 코드를 내부 분류로 매핑하되 원인 진단 정보를 보존한다.

15

API 문서와 코드 검토

API 사용 전 확인 항목은 다음과 같다.

  1. 입력 타입, 허용 범위, 단위, NULL 가능성
  2. 반환값과 오류 전달 방식
  3. 호출 전후 상태와 올바른 호출 순서
  4. 자원 소유권·수명과 정리 책임
  5. 동시 호출 안전성과 재진입 가능성
  6. 보안 기본값과 반드시 켜야 할 검증
  7. 버전별 폐기·변경 사항과 호환 범위
  8. 성능·크기 제한과 부분 처리 가능성

코드 검토에서는 호출 한 줄만 보지 말고 값이 어디서 왔고 결과가 어디로 가는지 데이터 흐름을 본다. 실패 분기가 실제로 시험되는지, 운영 설정이 안전한지 확인한다.

16

방어 중심 예시: 외부 문서 가져오기

function fetchApprovedDocument(requestedId): document = catalog.findVisibleTo(currentUser, requestedId) if document is absent: return safeNotFound()

response = approvedHttpClient.get( destination=document.registeredLocation, timeout=SHORTPOLICYTIMEOUT, maximumBytes=DOCUMENT_LIMIT ) if response.failed: auditExternalFailure(response.diagnosticId) return temporaryFailure() if not allowedContentType(response.contentType): return validationFailure() return parseAsDataOnly(response.body)

사용자가 임의 URL을 직접 전달하지 않고 승인 카탈로그의 목적지만 사용한다. 클라이언트 래퍼가 상대 인증, 허용 프로토콜, 리다이렉트, 시간·크기를 통제한다고 계약한다. 응답은 코드로 실행하지 않고 자료 형식으로 검증한다.

17

설계·구현 절차와 판단 기준

  1. 보호할 상태와 불변식, 민감 필드를 식별한다.
  2. 공개해야 할 최소 행위와 내부 구현을 구분한다.
  3. 생성·변경 메서드에서 유효 상태만 만들도록 한다.
  4. 변경 가능한 입력·반환 객체의 복사와 소유권을 정한다.
  5. 사용하는 API의 전제·결과·수명·동시성·보안 옵션을 문서로 확인한다.
  6. 위험한 저수준 API를 안전한 래퍼와 정적 분석 규칙으로 제한한다.
  7. 오류·부분 성공·시간 초과·최대 크기·동시 종료를 시험한다.
  8. 자동 직렬화·로그·디버그 출력에서 민감정보 노출을 검사한다.
  9. 라이브러리 버전 변경 때 계약과 안전 기본값의 변화를 재검토한다.

판단 기준은 외부가 불변식을 우회할 수 없는가, 민감정보 접근이 최소인가, 잘못된 API 사용을 타입·구조로 어렵게 했는가, 모든 반환과 정리 책임을 처리했는가, 위험한 기본값이 운영에 남지 않는가다.

18

자주 틀리는 포인트

  • 캡슐화는 단순히 필드를 비공개로 선언하는 것보다 상태와 행위·불변식을 함께 통제하는 개념이다.
  • 모든 필드에 공개 setter를 두면 내부 상태가 사실상 외부에서 조립될 수 있다.
  • 내부 컬렉션의 변경 가능한 참조를 반환하면 메서드 밖에서 불변식이 깨질 수 있다.
  • 자동 문자열 변환과 직렬화가 민감 필드를 노출할 수 있다.
  • API 호출이 문법적으로 성공해도 반환 상태를 무시하면 오용이다.
  • 안전하지 않은 기본값을 그대로 쓰고 호출자 교육만으로 해결하지 않는다.
  • HTML 이스케이프와 SQL 매개변수화처럼 문맥별 방어를 혼용하지 않는다.
  • 시간의 초·밀리초, 문자열의 문자·바이트 단위를 구분한다.
  • 비동기 함수 반환은 작업 완료와 같지 않을 수 있다.
  • 자원 소유자와 빌린 사용자를 구분해 누수와 이중 정리를 막는다.
  • 인증서 검증 오류를 무시하는 시험 설정이 운영에 들어가면 상대 인증이 무력화된다.
  • 오래된 API는 동작한다고 안전한 것이 아니며 폐기 공지와 대체 기능을 확인한다.
19

확인 문제

  1. 캡슐화와 정보 은닉의 목적을 계좌 객체 예로 설명하라.
  2. 비공개 필드에 단순 공개 setter를 모두 제공하는 방식의 한계는 무엇인가?
  3. 변경 가능한 컬렉션을 입력받거나 반환할 때 방어적 복사가 필요한 이유를 쓰라.
  4. API 오용의 대표 유형을 네 가지 이상 쓰라.
  5. 암호·인증서 API에서 안전한 기본값과 검증 실패 처리가 중요한 이유는 무엇인가?
  6. 문자열 결합 대신 문맥별 구조화 API를 사용해야 하는 사례를 세 가지 쓰라.
  7. 자원 소유권과 비동기 작업 수명을 명시해야 하는 이유는 무엇인가?
  8. 반환값의 DENY와 ERROR를 구분하면서도 Fail Secure를 지키는 방법을 설명하라.
  9. 안전한 래퍼가 저수준 API 오용을 줄이는 원리를 쓰라.
  10. 캡슐화와 API 사용을 코드 검토할 때 확인할 항목을 다섯 가지 쓰라.
20

정답과 해설

  1. 잔액을 외부가 직접 바꾸지 못하게 하고 입금·출금 메서드가 금액과 잔액 규칙을 지키게 한다. 관련 상태와 행동을 묶고 내부 표현을 숨겨 불변식을 보호한다.
  2. 외부가 임의 순서와 값으로 필드를 설정해 유효하지 않은 중간·최종 상태를 만들 수 있어 의미 있는 행위 경계를 제공하지 못한다.
  3. 외부가 객체 메서드를 거치지 않고 공유 컬렉션을 바꿔 내부 상태와 불변식을 깨뜨릴 수 있기 때문이다. 불변 뷰나 소유권 이전도 대안이다.
  4. 반환값 무시, 호출 순서 오류, 자원 소유권 혼동, 위험한 기본값, 단위 혼동, 권한 과다, 폐기 API, 동시성 계약 위반 등이 있다.
  5. 암호 안전성은 키·nonce·인증 검증을 포함한 구성에 달려 있고, 인증서 검증 실패를 허용하면 잘못된 상대와 보호된 것처럼 통신할 수 있기 때문이다.
  6. SQL은 매개변수화, 프로세스 실행은 실행 파일과 인수 배열, 경로는 결합·정규화 후 허용 루트 확인, URL은 구성 요소 API와 허용 대상을 사용한다.
  7. 누가 언제 닫고 데이터가 언제까지 유효한지 불명확하면 누수, 이중 해제, 해제 후 사용과 완료 전 버퍼 소멸이 생긴다.
  8. 내부 감사와 경보를 위해 정책 거부와 시스템 오류를 구분하되 둘 다 외부 작업은 허용하지 않는다. 오류에는 안전한 일반 응답을 반환한다.
  9. 승인된 옵션, 제한, 시간 초과, 검증을 중앙에서 기본 적용하고 위험한 기능을 공개하지 않아 각 호출자가 세부 설정을 빠뜨리기 어렵게 한다.
  10. 공개 표면, 불변식 우회, 민감정보 출력, API 입력·결과·오류, 수명·소유권, 동시성, 안전 기본값, 버전 변경을 확인한다.
21

핵심 요약

  • 캡슐화는 상태와 행동을 묶고 최소 공개 인터페이스로 불변식과 민감정보를 보호한다.
  • 비공개 필드만으로 끝내지 않고 생성·변경·반환 경계에서 유효 상태와 소유권을 통제한다.
  • API 오용은 반환값, 호출 순서, 자원 수명, 단위, 보안 설정, 동시성 계약을 잘못 적용할 때 발생한다.
  • 문맥별 구조화 API, 승인된 고수준 기능, 안전한 래퍼와 어댑터를 사용해 위험한 선택을 줄인다.
  • 오류와 부분 성공을 반드시 확인하고 DENY와 ERROR 모두 외부 작업을 허용하지 않는 Fail Secure를 지킨다.
  • 코드 검토와 경계·시간 초과·동시성 시험, 버전 변경 검증으로 캡슐화와 API 계약이 실제로 유지되는지 확인한다.
