“별도 프로세스로 비동기 처리했습니다”라는 문장이 어렵다면, 먼저 컴퓨터가 무엇을 실행하고 어디에 값을 적는지부터 보면 됩니다. 이 장에서는 코드 한 줄에서 시작해 프로그램·프로세스·스레드·메모리를 차례로 연결합니다. 마지막에는 같은 이름의 진행률 변수가 왜 서로 다른 값을 가질 수 있는지 설명할 수 있게 됩니다.

1-1. 컴퓨터는 명령을 실행하고 값을 바꾼다

통근버스 배정을 종이에 한다고 생각해 봅시다. 담당자는 근무자 명단을 읽고, 버스에 이름을 적고, 정원을 넘었는지 확인합니다. 컴퓨터에도 처리할 재료와 처리 순서가 필요합니다. 데이터는 직원 번호, 출근 시각, 버스 정원처럼 프로그램이 다루는 값입니다. 명령은 값을 읽기, 더하기, 비교하기, 저장하기처럼 수행할 일을 표현합니다. 코드는 이런 명령을 사람이 정한 프로그래밍 언어로 적은 것입니다.

컴퓨터가 문장의 업무 의미를 스스로 이해한다고 생각하면 오류를 찾기 어렵습니다. 직원 세 명을 버스 두 대에 적었다는 사실만으로 누락과 중복이 없는지는 알 수 없습니다. 누락을 찾을 명령과 중복을 찾을 명령을 별도로 적어야 합니다. “계산이 끝났다”와 “업무 규칙을 지켰다”는 그래서 다른 주장입니다. 뒤에서 생성기와 검사기를 나누는 이유도 이 차이에서 출발합니다.

이 책의 공통 예시는 2026년 7월 20일의 가상 배정입니다. E1·E2·E3은 근무하고 E4는 휴무입니다. E1·E2는 S1 정류장, E3은 S2 정류장에서 타며 버스 정원은 두 명입니다. E1 같은 표시는 사람을 구별하는 식별자입니다. 이름이 같은 사람이 있어도 식별자는 서로 달라야 대상을 정확히 셀 수 있습니다. 이 숫자와 시각은 학습을 위한 가정이며 실제 서비스 요구를 뜻하지 않습니다.

명령은 실행한 순서에 영향을 받습니다. “정원이 넘는지 확인한 뒤 배정”과 “모두 배정한 뒤 정원 확인”은 중간에 남는 값이 다릅니다. 두 순서가 같은 최종 결과를 만들 수도 있지만, 중간에 프로그램이 끝나거나 오류가 생기면 차이가 드러납니다. 코드를 이해한다는 것은 단어의 뜻뿐 아니라 값이 언제 생기고 언제 바뀌는지 따라가는 일입니다.

1-2. 변수는 값을 가리키는 이름, 함수는 다시 부를 수 있는 처리다

변수는 프로그램이 값을 찾을 때 쓰는 이름입니다. 다음 Python 코드는 capacity라는 이름으로 정원 2를 사용하고, assigned라는 이름으로 배정 인원 0을 사용합니다. =는 여기서 수학의 “두 식이 같다”가 아니라 오른쪽 값을 왼쪽 이름으로 사용하게 하는 대입입니다. 그다음 줄에서는 현재 배정 인원에 1을 더해 새 값으로 대입합니다.

capacity = 2
assigned = 0
assigned = assigned + 1
print(assigned)

위 코드를 순서대로 읽으면 assigned는 0에서 1로 바뀌고, print는 그 값을 화면에 표시합니다. 화면에 1을 출력하는 것과 파일에 1을 저장하는 것은 다른 일입니다. 다음 실행에서도 1을 읽고 싶다면 저장과 불러오기에 해당하는 명령이 필요합니다. 변수 자체가 과거 실행의 값을 기억해 주지는 않습니다.

조건문은 조건에 따라 다른 명령을 실행합니다. if assigned < capacity:는 배정 인원이 정원보다 작을 때만 아래의 일을 하라는 뜻입니다. 반복문은 명단의 각 직원을 차례로 처리하는 식으로 같은 구조를 반복합니다. 함수는 이름을 붙여 다시 사용할 수 있게 묶은 처리입니다. 함수를 정의하는 일과 그 함수를 호출해 실행하는 일은 구분해야 합니다.

def has_seat(assigned, capacity):
    return assigned < capacity

available = has_seat(1, 2)

has_seat는 빈자리가 있는지 묻는 함수입니다. 괄호 안의 1과 2는 함수에 전달하는 입력값이고, return 뒤의 비교 결과는 함수를 부른 쪽에 돌려주는 반환값입니다. 이 호출의 결과는 참입니다. 그러나 이 함수는 사람을 실제로 배정하지도, 두 요청이 동시에 마지막 자리를 차지하는 문제를 막지도 않습니다. 이름보다 함수 안에서 실행하는 명령을 확인해야 합니다.

1-3. 프로그램 파일과 실행 중 메모리는 다르다

프로그램은 컴퓨터가 실행할 수 있도록 준비한 명령과 데이터의 묶음입니다. plan.py라는 파일에 코드를 저장했다면 그 파일은 프로그램의 일부입니다. 이 파일명은 설명을 위한 예시이며 교재의 실제 내려받기 파일을 가리키지 않습니다. 파일이 폴더에 있다는 사실은 현재 배정 계산이 실행 중이라는 뜻이 아닙니다. 종이에 조리법이 있다고 지금 음식이 만들어지고 있지는 않은 것과 같습니다.

메모리는 실행 중 필요한 명령과 값을 올려 두는 작업 공간입니다. 저장장치는 파일을 보관하는 SSD 같은 장치입니다. 종이를 보관하는 서랍과 작업 중 펼쳐 놓는 책상을 구분하면 이해하기 쉽습니다. 다만 실제 컴퓨터는 운영체제가 여러 방법으로 저장장치와 메모리를 함께 관리하므로, 이 비유를 물리 구조의 완전한 설명으로 외우지는 마세요.

운영체제는 Windows나 Linux처럼 프로그램 실행, 메모리, 파일과 장치를 관리하는 소프트웨어입니다. 사용자가 프로그램을 실행하면 운영체제와 실행 환경이 필요한 자원을 준비합니다. Python에서는 Python 실행기가 코드를 읽고 처리하는 역할을 합니다. CPU는 명령을 실제로 수행하는 장치이고, 코어는 그 안의 실행 자원을 설명할 때 쓰는 단위입니다. 코어 수가 많아도 작업을 나누지 못하거나 다른 곳에서 기다리면 자동으로 빨라지지는 않습니다.

실행 중인 progress = 60이 일반 변수라면 “현재 작업 공간에 진행률 60이 있다”는 뜻입니다. 프로그램이 끝난 뒤 새로 실행했을 때 이전 진행률을 다시 읽으려면 파일이나 데이터베이스에 남긴 기록이 필요합니다. 데이터베이스(DB)는 정한 구조와 규칙에 따라 데이터를 저장하고 조회하는 시스템입니다. 파일에 기록하는 SQLite도 DB의 한 종류입니다. 저장했다고 말할 때에는 무엇을 어디에 언제 기록했는지까지 확인해야 합니다.

1-4. 프로세스는 실행 중인 프로그램의 한 인스턴스다

프로세스는 프로그램을 실행 중인 하나의 단위입니다. 인스턴스는 같은 설계에서 실제로 만들어진 개별 대상을 뜻합니다. 같은 프로그램을 두 번 실행하면 코드 파일은 같아도 실행 상태는 두 개일 수 있습니다. 두 계산 담당자가 같은 설명서를 읽지만 각자 자기 책상을 쓰는 상황에 가깝습니다. 운영체제는 프로세스를 구별하는 번호인 PID를 관리합니다.

요청을 받는 서버와 계산을 맡은 작업자를 별도 프로세스로 둘 수 있습니다. 서버는 다른 프로그램의 요청을 받아 처리하는 역할이고, 뒤에서 다룰 Worker는 맡겨진 작업을 수행하는 역할의 이름입니다. Worker라고 이름 붙인 함수가 반드시 새 프로세스에서 실행되는 것은 아닙니다. 함수 호출인지, 스레드 시작인지, 프로세스 시작인지 실제 실행 코드를 봐야 합니다.

서버 프로세스의 status와 Worker 프로세스의 status는 이름이 같아도 같은 저장 위치가 아닐 수 있습니다. Worker가 자기 일반 변수를 완료로 바꾸었다고 서버 변수도 바뀌지는 않습니다. 주소 공간은 프로세스가 자기 명령과 값에 접근하는 범위를 이해하는 기본 개념입니다. 프로세스마다 일반적인 메모리 접근 범위가 나뉘어 있어 다른 프로세스와 값을 주고받으려면 명시적인 방법이 필요합니다.

그렇다고 별도 프로세스가 모든 자원을 완전히 분리한다는 뜻은 아닙니다. 두 프로세스가 같은 DB 파일을 열거나 같은 네트워크 서비스를 사용할 수도 있습니다. Worker가 죽어도 서버가 계속 응답할 수 있다는 장점과, DB에 남은 작업을 누가 정리하는가라는 문제를 함께 생각해야 합니다. 실행 경계를 나누는 것과 업무를 복구하는 것은 서로 다른 설계입니다.

1-5. 스레드는 한 프로세스 안에서 진행하는 실행 흐름이다

스레드는 프로세스 안에서 명령을 따라 진행하는 실행 흐름입니다. 같은 사무실에서 두 담당자가 각자 일을 진행하지만 같은 게시판을 읽고 고칠 수 있다고 생각해 봅시다. 같은 프로세스의 스레드는 보통 객체와 자원을 공유할 수 있습니다. 객체는 숫자, 직원 목록, 사전처럼 프로그램이 다루는 값의 개별 대상을 가리키는 말입니다. Python의 {"count": 0}도 객체입니다.

공유는 편리하지만 순서 문제가 생깁니다. 버스 자리가 하나 남았을 때 담당자 A와 B가 모두 빈자리 1을 읽었다고 합시다. A는 E2를, B는 E3을 배정하면 같은 마지막 자리를 두 사람이 사용하게 됩니다. 두 흐름의 읽기와 쓰기 순서에 따라 결과가 달라지는 문제를 경쟁 상태라고 부릅니다. “한 프로세스니까 안전하다”는 설명은 공유 값을 누가 어떤 규칙으로 바꾸는지 빠뜨립니다.

잠금은 특정 구간을 한 번에 하나의 실행 흐름만 처리하게 만드는 도구입니다. 빈자리 확인과 배정을 같은 보호 구간으로 묶는 식으로 사용할 수 있습니다. 다만 메모리 잠금을 하나 두었다고 별도 프로세스나 다른 서버의 요청까지 모두 막는다고 가정해서는 안 됩니다. 도구마다 보호하는 범위가 다르므로 뒤의 DB와 확정 경계에서 다시 확인합니다.

이 장에서는 스레드 수를 늘리면 계산이 빨라지는지까지 판단하지 않습니다. 기다리는 일이 많은지, CPU 계산이 많은지, 어떤 언어 실행기를 쓰는지에 따라 결과가 달라집니다. 지금 필요한 첫 구분은 실행 흐름이 같은 프로세스 안에 있는가, 어떤 값을 공유하는가입니다. 동시성·병렬성·비동기는 이 바탕 위에서 7장에서 정리합니다.

1-6. 값을 전달하는 일과 오래 남기는 일도 구분한다

별도 프로세스끼리는 메시지, 공유 메모리, DB 같은 방법으로 통신할 수 있습니다. 메시지는 다른 실행 주체에게 보내는 값이고, 큐는 값을 넣고 꺼내는 통로를 표현하는 자료구조입니다. “계산을 마쳤다”는 메시지를 보냈다는 사실과 “재시작 뒤에도 완료 기록을 읽을 수 있다”는 사실은 다릅니다. 큐의 종류와 저장 방식에 따라 남는 기록이 달라집니다.

영속성은 실행이 끝난 뒤에도 필요한 기록을 다시 읽을 수 있는 성질입니다. 일반 변수만 사용하면 새 프로세스에서 과거 값을 자동 복구할 수 없습니다. 파일 DB에 기록했다면 새 연결로 다시 읽는 시험이 첫 근거가 됩니다. 전원 차단까지 견디는가, DB 파일을 다른 호스트로 옮겨도 되는가는 별도의 조건과 시험이 필요합니다. 작은 성공 사례를 모든 장애의 안전성으로 넓히지 않는 습관을 들이세요.

보충 파일 examples/ch01.py는 한 프로세스의 스레드가 count를 0에서 1로 바꾼 뒤, spawn 방식으로 만든 자식 프로세스가 자기 값을 99로 바꾸고 큐로 보내는 작은 실험입니다. spawn은 새 Python 실행기를 시작하는 방식입니다. join()은 여기서 시작한 실행 흐름의 종료를 기다리는 호출입니다. 기다렸다고 두 프로세스의 일반 메모리가 합쳐지는 것은 아닙니다.

"""Process memory versus thread memory. Run as a file (Windows spawn)."""
import json
import multiprocessing
import threading

STATE = {"count": 0}


def child(queue):
    STATE["count"] = 99
    queue.put(STATE["count"])


def thread_work():
    STATE["count"] += 1


def main():
    thread = threading.Thread(target=thread_work)
    thread.start()
    thread.join()
    after_thread = STATE["count"]
    ctx = multiprocessing.get_context("spawn")
    queue = ctx.Queue()
    process = ctx.Process(target=child, args=(queue,))
    process.start()
    try:
        child_count = queue.get(timeout=10)
        process.join(timeout=10)
        assert not process.is_alive(), "child did not exit"
        assert process.exitcode == 0
        assert (after_thread, child_count, STATE["count"]) == (1, 99, 1)
    finally:
        if process.is_alive():
            process.terminate()
            process.join()
        queue.close()
        queue.join_thread()
    print(json.dumps({"parent_after_thread": after_thread,
                      "child": child_count, "parent_after_process": STATE["count"]}))


if __name__ == "__main__":
    main()

2-1. 화면, 요청 서버, 계산은 서로 다른 역할이다

브라우저는 Chrome이나 Edge처럼 웹페이지를 보여 주고 사용자 입력을 받는 프로그램입니다. 사용자가 날짜를 고른 뒤 생성 버튼을 누르면 브라우저의 코드가 그 선택을 서버에 전달할 수 있습니다. 브라우저 화면은 요청을 보내는 쪽이고 서버는 요청을 받는 쪽입니다. 실제 배정 계산은 요청을 받은 서버 안에서 할 수도 있고, 다른 Worker에 맡길 수도 있습니다.

식당으로 비유하면 화면은 주문표를 쓰는 자리, 요청 서버는 주문을 접수하는 창구, Worker는 조리를 맡은 주방에 가깝습니다. 주문번호를 받았다는 사실과 음식이 완성되었다는 사실은 다릅니다. 이 비유는 역할을 구별하기 위한 것입니다. 실제 프로그램에서는 서버와 Worker가 같은 프로세스의 함수일 수도 있으므로 그림의 상자 개수만으로 프로세스 수를 결정하면 안 됩니다.

요청은 상대 프로그램에게 어떤 처리를 부탁하는 메시지이고, 응답은 그 요청을 받은 쪽이 돌려주는 메시지입니다. 브라우저는 응답을 읽어 화면을 바꿉니다. 화면의 “작업 중” 문구는 브라우저가 보관한 값일 수 있고, DB의 작업 상태는 서버가 기록한 값입니다. 둘이 항상 같은 시점에 바뀌지는 않기 때문에 상태를 어디에서 읽었는지 확인해야 합니다.

여기서는 운영자가 2026년 7월 20일의 배정을 요청한다고 합시다. 서버는 날짜와 적용된 입력 버전을 확인하고, 작업 식별자를 만든 뒤, 계산을 맡깁니다. 사용자는 작업 식별자로 진행 상태를 조회합니다. 이 흐름은 교재의 가상 설계입니다. 실제 API가 이런 순서와 저장 방식을 갖는지는 해당 프로젝트의 요청 처리 코드와 기록을 봐야 합니다.

2-2. API는 프로그램끼리 주고받는 약속이다

인터페이스는 한 대상이 다른 대상에게 기능을 제공하는 접점입니다. API는 프로그램이 다른 프로그램의 기능을 호출할 때 사용하는 인터페이스를 뜻합니다. 웹에서는 어떤 주소로 어떤 값을 보내고, 성공하거나 실패했을 때 무엇을 받는지를 정합니다. 버튼이 사람의 접점이라면 API는 프로그램의 접점이라고 이해할 수 있습니다.

HTTP는 웹에서 요청과 응답을 주고받을 때 쓰는 통신 규약입니다. URL은 요청할 자원의 위치를 나타내며, 메서드는 요청의 의미를 표현합니다. GET은 정보를 조회할 때, POST는 서버에 처리를 요청할 때 자주 사용합니다. 메서드 이름만 정했다고 권한·중복 처리·저장이 자동 구현되는 것은 아닙니다.

요청에는 추가 정보를 담는 헤더와 업무 값을 담는 본문이 있을 수 있습니다. JSON은 이름과 값을 묶어 표현하는 텍스트 형식입니다. 다음은 프로젝트에 대입할 API 모양의 예시이며, 이 주소로 실제 교재 서버가 운영된다는 뜻은 아닙니다. dataset_version은 계산에 사용할 입력 묶음의 판을 가리킵니다.

약속에는 필드 이름뿐 아니라 값의 의미가 들어가야 합니다. 날짜가 빠지면 거절하는지, 존재하지 않는 입력 버전을 보내면 어떻게 되는지, 결과는 어디서 조회하는지를 함께 정합니다. 이처럼 입출력과 동작 의미를 합친 약속을 여기서는 API 계약이라고 부릅니다. “요청이 성공한다”보다 “어떤 요청에 무엇을 약속하는가”가 더 구체적인 설명입니다.

2-3. 202는 접수, 배정 성공은 검증과 확정 뒤의 일이다

HTTP 응답에는 세 자리의 상태 코드가 들어갑니다. 202는 요청이 처리 대상으로 받아들여졌지만 처리가 아직 끝나지 않았을 수 있음을 나타냅니다. 이 가상 설계에서는 작업 J7을 접수했다는 뜻으로 사용합니다. 그것만으로 E1·E2·E3이 모두 배정되었거나 결과가 DB에 확정되었다고 말할 수 없습니다. 요청의 접수와 업무 완료를 분리하는 첫 이유입니다.

다음 조회가 200으로 응답해도 본문의 작업 상태를 읽어야 합니다. GET /jobs/J7이 {"status": "RUNNING"}을 돌려주면 조회 요청은 정상 처리했지만 배정 계산은 진행 중입니다. 반대로 계산이 실패한 작업을 조회해서 200과 실패 상태를 받을 수도 있습니다. HTTP 요청의 처리 결과와 그 요청이 가리키는 업무 작업의 결과는 서로 다른 층위입니다.

작업 상태는 접수·실행·검증·성공·실패처럼 업무 진행을 표현한 기록입니다. QUEUED는 대기 중, RUNNING은 실행 중이라는 뜻으로 쓸 수 있습니다. 정확한 상태 이름과 전이는 프로젝트마다 다릅니다. 이 책에서는 개념을 설명하기 위해 이름을 고정하지만 실제 답변에서는 자기 코드에 있는 상태만 말해야 합니다.

배정 성공을 판정하려면 생성한 후보가 대상·정원·시간 규칙을 통과했는지, 확정 조건을 만족하는지, 공개 결과가 저장되었는지를 연결해야 합니다. Worker가 “계산 완료”라고 로그를 남긴 직후 저장에 실패할 수도 있습니다. 따라서 사용자에게 성공을 표시하는 지점은 계산 함수가 반환한 순간과 같다고 자동 가정하지 않습니다.

네트워크 응답을 기다리다 시간제한이 걸렸을 때도 마찬가지입니다. 브라우저가 응답을 못 받았을 뿐 서버에는 작업이 남아 있을 수 있습니다. 같은 요청을 다시 보내면 중복 작업을 만들 수 있으므로 기존 작업 식별자나 재시도 식별 규칙을 확인해야 합니다. 실패를 자세히 구분하는 이유는 이름을 늘리려는 것이 아니라, 다음 행동이 달라지기 때문입니다.

2-4. 요구사항을 관찰 가능한 완료 조건으로 바꾼다

요구사항은 사용자가 시스템에 바라는 기능과 지켜야 할 조건입니다. “근무자 전원을 배정한다”는 요구는 출발점이지만 아직 확인 방법이 부족합니다. 어느 날짜의 누가 근무자인지, 출근만인지 퇴근도 포함하는지, 중복은 허용하는지를 더 정해야 합니다. 모호한 문장은 구현한 뒤에도 각자 다른 성공을 주장하게 만듭니다.

이 책의 가정에서는 E1·E2·E3이 2026년 7월 20일에 근무하고 E4는 휴무입니다. 완료 조건을 “해당 날짜의 각 근무자가 출근과 퇴근에 각각 한 번 배정되고, 휴무자는 배정되지 않으며, 각 운행의 정원과 시각 조건을 지킨다”로 바꿀 수 있습니다. 인수 조건은 이런 식으로 기능을 받아들일 수 있는지 확인하는 구체적인 기준입니다.

원하는 출력의 행 수만 세면 충분하지 않습니다. 출근 세 행에 E1·E1·E2가 들어 있다면 수는 세 명처럼 보여도 E3은 빠졌습니다. 사람과 방향과 날짜를 함께 식별해 횟수를 세어야 합니다. “대상 세 명”이라는 문장을 어떤 입력에서 만들고, 결과의 무엇과 비교하는지까지 정하면 검증기가 해야 할 일이 분명해집니다.

“잘못된 데이터셋은 적용하지 않는다”도 관찰로 바꿀 수 있습니다. 적용 전 입력 버전과 기존 결과를 기록하고, 없는 직원 번호를 참조하는 입력을 적용해 봅니다. 오류 메시지뿐 아니라 적용 뒤 입력 버전과 기존 결과가 보존되는지 다시 조회합니다. 오류를 보여 준 뒤 현재 데이터를 일부 지워 버리는 구현은 이 완료 조건을 만족하지 않습니다.

구현 순서도 이 기준에서 정할 수 있습니다. 예쁜 진행률 화면보다 누락 없는 대상 선정과 잘못된 입력의 적용 차단이 먼저 필요할 수 있습니다. 반대로 과제 요구에 로그인이나 재시작 보존이 필수라면 이를 나중 문제로 빼서는 안 됩니다. 기능을 줄일 때는 무엇을 제외했는지 밝히고, 필수 요구를 생략한 것을 단순한 구현이라고 포장하지 않습니다.

2-5. 인증은 누구인지, 인가는 무엇을 허용할지 확인한다

인증은 요청한 사람이 누구인지 확인하는 일입니다. 인가는 확인한 사람이 이 요청을 수행하거나 이 자료를 읽어도 되는지 판단하는 일입니다. 사원증으로 신원을 확인하는 것과 다른 부서의 명단을 열 수 있는지 정하는 것은 다른 질문입니다. 로그인에 성공했다는 사실만으로 모든 직원의 계획을 볼 권한이 생기지는 않습니다.

가상 서비스에서는 운영자가 입력 적용과 계획 생성을 요청하고, 구성원은 자기 계획을 읽는다고 합시다. E1이 주소의 직원 번호를 E2로 바꾸어 조회할 수 있다면 버튼을 숨겨도 보호가 되지 않습니다. 서버가 요청자의 신원과 조회 대상 E2의 관계를 검사해야 합니다. 화면은 사용 편의를 제공하고, 요청을 허용하는 최종 판단은 실제 서버 처리 경로에서 확인합니다.

401은 유효한 인증 정보가 필요한 경우에 쓰이고, 403은 요청을 이해했지만 수행을 허용하지 않는 경우에 쓰입니다. 실제 서비스는 자원 존재를 드러내지 않으려고 다른 응답 정책을 선택할 수도 있습니다. 초보 단계에서는 숫자를 암기하기보다 신원 확인과 권한 판단을 분리하고, 서버가 어느 코드에서 거절하는지 찾는 것이 먼저입니다.

인증과 업무 검증도 서로 대신하지 못합니다. 운영자가 보낸 CSV라도 없는 직원을 참조할 수 있고, 형식이 맞는 계획이라도 다른 사람에게 공개하면 안 될 수 있습니다. 계층은 역할에 따라 나눈 처리 부분을 뜻합니다. 요청 계층의 권한 검사, 입력 계층의 데이터 검사, 결과 계층의 공개 범위를 각각 연결해야 전체 설명이 됩니다.

2-6. 제3자가 따라갈 수 있도록 요구와 근거를 연결한다

추적성은 요구가 설계·코드·검사와 어떻게 이어지는지 앞뒤로 찾을 수 있는 성질입니다. “전원 배정”이라는 요구에서 대상 선정 함수와 결과 횟수 검사를 찾고, 검사 실패에서 어떤 요구를 어겼는지 돌아갈 수 있으면 좋습니다. 파일을 많이 만드는 것보다 각 파일이 어떤 주장을 뒷받침하는지 연결하는 것이 중요합니다.

프로젝트에 대입할 요구와 확인 항목의 예시
요구관찰할 것추가로 확인할 경계
근무자 전원 배정날짜·방향·직원별 기대 횟수와 결과 횟수대상 명단이 원본 근무표에서 나왔는가
잘못된 입력 적용 차단오류와 적용 전후 버전·결과실제 적용 경로가 검증을 호출하는가

표의 오른쪽 질문은 함정이 아니라 주장의 범위를 좁혀 주는 장치입니다. 검사 함수만 따로 실행했다면 그 함수의 동작을 확인한 것입니다. 실제 API가 그 함수를 호출하는지까지 확인하지 않았다면 요청 경로 전체를 검증했다고 말하지 않습니다. 화면이 아직 없다면 서버 경로까지 완료한 사실과 화면 미구현을 함께 설명할 수 있습니다.

근거를 남길 때에는 코드 버전, 실행 명령, 입력 조건, 기대 결과, 실제 결과를 묶습니다. 서로 다른 버전에서 나온 코드와 출력을 섞으면 재현이 어렵습니다. 명령이 실제 저장소에 존재하는 파일을 실행하는지도 확인해야 합니다. 교재에 그럴듯한 파일명을 써 두는 것과 실제 프로젝트에서 같은 명령으로 실행하는 것은 다른 일입니다.

"""Real loopback HTTP; fixture tokens, not production authentication."""
import json
import threading
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from urllib.error import HTTPError
from urllib.request import Request, urlopen

IDENTITIES = {"member-demo": ("member", "E1"), "admin-demo": ("admin", None)}
JOBS = {}
LOCK = threading.Lock()


class Handler(BaseHTTPRequestHandler):
    def log_message(self, *args):
        pass

    def handle_request(self):
        identity = IDENTITIES.get(self.headers.get("Authorization", "").removeprefix("Bearer "))
        status, body = 401, {"error": "authentication required"}
        if identity:
            role, owner = identity
            if self.command == "POST" and self.path == "/generate":
                if role == "admin":
                    with LOCK:
                        job_id = "J" + str(len(JOBS) + 1)
                        JOBS[job_id] = {"job_id": job_id, "status": "QUEUED"}
                        status, body = 202, JOBS[job_id].copy()
                else:
                    status, body = 403, {"error": "admin required"}
            elif self.command == "GET" and self.path.startswith("/jobs/"):
                with LOCK:
                    job = JOBS.get(self.path.split("/")[-1])
                    status, body = ((200, job.copy()) if role == "admin" and job
                                    else (403, {"error": "not allowed"}))
            elif self.command == "GET" and self.path.startswith("/plans/"):
                target = self.path.split("/")[-1]
                status, body = ((200, {"emp_id": target}) if role == "admin" or owner == target
                                else (403, {"error": "not your resource"}))
            else:
                status, body = 404, {"error": "not found"}
        self.send_response(status)
        self.send_header("Content-Type", "application/json")
        if status == 401:
            self.send_header("WWW-Authenticate", 'Bearer realm="demo"')
        self.end_headers()
        self.wfile.write(json.dumps(body).encode())

    do_GET = handle_request
    do_POST = handle_request


def main():
    server = ThreadingHTTPServer(("127.0.0.1", 0), Handler)
    thread = threading.Thread(target=server.serve_forever, daemon=True)
    thread.start()
    def request(path, token="", method="GET"):
        req = Request(f"http://127.0.0.1:{server.server_port}{path}", method=method,
                      headers={"Authorization": "Bearer " + token})
        try:
            with urlopen(req, timeout=5) as response:
                return response.status, json.load(response)
        except HTTPError as error:
            return error.code, json.load(error)
    try:
        assert request("/plans/E1")[0] == 401
        assert request("/plans/E1", "member-demo")[0] == 200
        assert request("/plans/E2", "member-demo")[0] == 403
        assert request("/generate", "member-demo", "POST")[0] == 403
        code, body = request("/generate", "admin-demo", "POST")
        assert code == 202 and body["status"] == "QUEUED"
        assert request("/jobs/" + body["job_id"], "admin-demo") == (200, body)
        assert request("/jobs/" + body["job_id"], "member-demo")[0] == 403
        print(json.dumps({"own": 200, "other": 403, "generate": code, "job_state": body["status"]}))
    finally:
        server.shutdown()
        server.server_close()
        thread.join(timeout=5)


if __name__ == "__main__":
    main()

"""A small executable requirements-to-test trace, not an understanding grader."""
import json


def within_capacity(count, capacity):
    return 0 <= count <= capacity


def targets(rows):
    return {row["id"] for row in rows if row["status"] == "WORK"}


def same_version(candidate, current):
    return candidate == current


def test_capacity():
    assert within_capacity(45, 45)
    assert not within_capacity(46, 45)


def test_off():
    assert targets([{"id": "E1", "status": "WORK"}, {"id": "E2", "status": "OFF"}]) == {"E1"}


def test_version():
    assert same_version(2, 2)
    assert not same_version(1, 2)


def main():
    trace = {"R-CAP": (within_capacity, test_capacity),
             "R-OFF": (targets, test_off), "R-VER": (same_version, test_version)}
    for requirement, (implementation, test) in trace.items():
        assert callable(implementation), requirement
        test()
    print(json.dumps({"mapped_requirements": sorted(trace), "tests_passed": len(trace),
                      "atomic_publication_proven": False}))


if __name__ == "__main__":
    main()

3-1. 선택은 대상을 정하고, 검증은 조건을 묻고, 적용은 현재 상태를 바꾼다

데이터셋은 한 작업에 함께 사용하는 데이터 묶음입니다. 직원 정보만으로 배정할 수는 없습니다. 어느 날 근무하는지, 어디서 타는지, 이동에 몇 분 걸리는지 등을 함께 연결해야 합니다. 이 책에서는 사업장, 근무 유형, 직원, 근무표, 정류장, 이동시간, 승차 수요라는 일곱 종류의 자료를 예로 듭니다. 실제 프로젝트의 파일 수와 열 이름은 해당 요구에서 따로 확인해야 합니다.

선택은 사용할 묶음을 지목하는 일입니다. 7월 자료 A와 8월 자료 B 중 A를 골랐다고 해서 A 안의 날짜와 직원 번호가 올바른지는 아직 모릅니다. 검증은 정한 조건을 만족하는지 확인하는 일입니다. 적용은 검사한 묶음을 현재 작업에 사용할 입력으로 등록하는 일입니다. 선택은 식별, 검증은 판정, 적용은 상태 변경이라고 먼저 구분하세요.

가령 현재 입력이 v7인데 다른 묶음 B를 선택했다고 합시다. 선택 화면에 B가 보이는 순간 현재 입력까지 바꿀 필요는 없습니다. B에 없는 직원 번호가 발견되면 적용을 거절하고 v7을 유지할 수 있습니다. 반대로 선택과 동시에 현재 데이터를 덮어쓰면 오류를 알아낸 뒤 원래 입력을 복구해야 합니다. 처리 단계의 구분은 실패했을 때 무엇이 남는지와 연결됩니다.

여기서 v7은 설명을 위한 버전입니다. 버전은 서로 다른 입력의 판을 구별하는 표시입니다. 파일 이름이 같아도 내용이 바뀌면 같은 입력이라고 단정하기 어렵습니다. “어느 자료를 검사했고 어느 자료를 적용했는가”를 이어 줄 식별 정보가 있어야 오래된 검사 결과를 새 내용에 잘못 붙이지 않을 수 있습니다.

3-2. 읽히는 자료라고 업무에 맞는 자료는 아니다

CSV는 행과 열의 값을 쉼표 등의 구분자로 표현하는 텍스트 형식입니다. 첫 행의 열 이름을 헤더라고 부릅니다. emp_id,site_id라는 헤더 아래에 E1,ICN이 있다면 직원 E1의 사업장이 ICN이라는 모양으로 읽을 수 있습니다. 값 안에 쉼표가 있으면 따옴표 처리도 필요하므로 문자열을 무조건 쉼표로 자르는 방법은 안전하지 않습니다.

텍스트를 구조화된 값으로 읽는 일을 파싱이라고 합니다. CSV 파서가 성공했다는 것은 우선 그 형식대로 읽었다는 뜻입니다. 2026-02-30이라는 텍스트도 한 칸의 문자열로는 읽힐 수 있습니다. 실제 날짜인지 확인하려면 별도의 날짜 규칙이 필요합니다. “파일을 열었다”, “열을 나눴다”, “값이 업무에 맞다”를 같은 검사로 취급하지 마세요.

타입은 숫자, 문자열, 날짜처럼 값을 어떤 종류로 다루는지 나타냅니다. 키는 행이나 대상을 구별하는 값이고, 참조는 다른 자료의 키를 가리키는 관계입니다. 근무표의 E1이 직원 자료에 존재하는지 확인하는 것이 참조 검사입니다. 날짜와 직원의 조합이 하나여야 한다면 두 값을 묶은 키의 중복도 따로 검사해야 합니다.

각 종류를 전부 검사해도 계획이 반드시 존재하는 것은 아닙니다. 직원과 정류장이 모두 존재하지만 시간이 너무 짧아 출근시킬 수 없을 수 있습니다. 데이터가 읽을 수 있고 내부적으로 일관된다는 판단과, 주어진 자원으로 조건을 만족하는 배정이 가능하다는 판단은 다릅니다. 뒤의 생성과 결과 검증에서 다시 이어 볼 경계입니다.

3-3. 실제 ch04.py가 가진 검사와 빠진 검사를 펼쳐 본다

examples/ch04.py는 이 장의 실제 보충 파일입니다. DATA라는 사전에 일곱 CSV 모양의 문자열을 넣었습니다. 실제 폴더를 검색하거나 사용자가 파일을 선택하는 화면을 구현한 것은 아닙니다. 함수 validate(files)는 이 문자열 묶음을 받아 일부 조건을 검사하고, 읽은 표를 반환합니다. 이 예제는 공통 사례의 네 사람보다 더 작은 E1 한 명의 자료를 사용합니다.

“코드가 검사하도록 작성돼 있다”와 “특정 잘못된 입력을 넣어 거절을 확인했다”도 구분합니다. 이 파일의 main()은 정상 묶음, 따옴표 안의 쉼표, 없는 직원 참조의 적용 거절, 내용이 바뀐 뒤 옛 해시를 사용한 적용 거절을 확인하도록 작성되어 있습니다. 중복 헤더와 모든 잘못된 숫자의 경우까지 각각 실행해 검사하는 것은 아닙니다.

단언은 프로그램이 기대한 조건이 참인지 확인하는 명령입니다. Python의 assert가 해당합니다. 검사 프로그램이 정상 종료한 사실은 그 실행 경로의 단언 조건이 통과했다는 근거입니다. 코드에 등장한 모든 조건과 실제 업무의 모든 규칙이 완전히 증명되었다는 뜻은 아닙니다. 제3자에게 보여 줄 때는 실행한 입력과 단언 조건을 함께 가리켜야 합니다.

3-4. 위임했다는 말에는 실제 호출 경로와 책임이 필요하다

위임은 내가 맡은 일의 일부를 다른 구성요소가 수행하도록 맡기는 것입니다. CSV의 따옴표와 구분자를 해석하는 일을 Python의 csv.DictReader에 맡기는 것이 예입니다. 이 도구가 쉼표가 든 정류장 이름을 읽어 줄 수 있어도 그 정류장 ID가 다른 표에 존재하는지는 알지 못합니다. 형식 해석의 위임을 업무 검증의 위임으로 넓히면 빈칸이 생깁니다.

DB의 고유 제약이나 외래 키 제약으로 일부 규칙을 강제할 수도 있습니다. 외래 키 제약은 다른 표에 없는 식별자를 참조하지 못하게 하는 조건입니다. 제약은 저장하거나 계산할 때 지켜야 할 조건입니다. 예를 들어 같은 직원 번호를 두 번 저장하지 못하게 하는 고유 제약은 중복 방지 책임의 일부를 DB에 맡깁니다. 그러나 ch04.py에는 그런 DB가 없습니다. 실제 프로젝트에 해당 제약이 있는지, 활성화되었는지, 적용 요청이 그 테이블을 사용하는지 확인한 뒤 위임했다고 말해야 합니다.

“다른 팀에서 할 예정”과 “다른 계층이 실제로 수행”은 다릅니다. 요청 계층이 직원 참조를 검사한다고 들었어도 실제 적용 경로가 그 검사를 거치지 않을 수 있습니다. 어디에서 호출하고 오류를 어떻게 전달받는지를 연결해야 합니다. 호출이 없으면 설계 문서에 적힌 책임일 뿐 실행된 검사라는 근거는 부족합니다.

자기 구현을 정리할 때에는 각 규칙을 직접 구현, 실제 위임, 미구현, 아직 미확인으로 표시하세요. 미구현은 요구를 알고 있지만 검사 코드가 없다는 뜻이고, 미확인은 코드나 실행 근거를 아직 확인하지 못했다는 뜻입니다. 두 말을 구분하면 모르는 부분을 숨기지 않으면서 다음에 무엇을 찾아야 하는지도 분명해집니다.

3-5. 검증한 고정본을 적용해야 검사와 결과가 이어진다

자료 A를 검사한 뒤 사용자가 같은 이름의 파일을 B 내용으로 바꾸었다고 합시다. 적용 함수가 파일을 다시 읽어 B를 사용하면 A의 검사 통과 기록으로 B를 적용한 셈이 됩니다. 검사와 사용 사이에 내용이 바뀌는 문제가 생긴 것입니다. 검사한 대상을 고정하고 적용까지 같은 내용을 전달해야 하는 이유입니다.

스냅샷은 특정 시점의 내용을 고정해 다루는 복사본입니다. 이 예제에서는 사전을 복사하고 값으로 든 문자열을 사용합니다. 문자열은 내용을 제자리에서 바꿀 수 없는 값이므로 이 작은 모형에서는 같은 입력을 유지하는 데 도움이 됩니다. 사전 안에 계속 바뀌는 목록이나 객체가 들어 있다면 겉 사전만 복사했다고 내부까지 고정되었다고 말할 수 없습니다.

해시는 내용을 정해진 계산으로 짧은 값에 대응시킨 것입니다. fingerprint(files)는 입력 사전을 일정한 순서의 JSON으로 표현하고 SHA-256 해시를 계산합니다. 여기서는 파일 이름이 아니라 내용 묶음의 차이를 감지하는 데 사용합니다. 해시가 있다는 사실만으로 올바른 데이터이거나 믿을 수 있는 사용자가 만든 자료라는 뜻은 아닙니다. 내용 동일성 확인과 업무 규칙 판정은 별개입니다.

apply(state, files, expected_hash)는 받은 묶음을 복사해 다시 검증하고, 해시가 기대값과 같을 때만 현재 메모리 상태를 갱신합니다. state는 현재 값을 모아 둔 사전입니다. 예제의 잘못된 참조와 해시 불일치 경로에서는 갱신 전에 예외가 발생하므로 이전 상태가 유지됩니다. 예외는 정상 흐름으로 계속 진행할 수 없음을 알리는 프로그램의 신호입니다.

이것은 단일 프로그램 안의 작은 실험입니다. 여러 요청이 동시에 적용하거나 중간에 프로세스가 죽는 상황의 원자성까지 제공하지 않습니다. 원자성은 관련 변경을 전부 반영하거나 전부 반영하지 않도록 묶는 성질입니다. 실제 파일 DB의 입력 적용에서는 버전 비교와 트랜잭션 같은 저장 규칙이 더 필요하며 9장에서 다룹니다.

3-6. 제3자는 파일·명령·입력 전후 상태를 함께 본다

이 보충 예제를 확인할 실제 명령은 다음과 같습니다. 교재에서 받은 examples 폴더의 상위 위치에서 실행합니다. 파일 하나만 내려받았다면 그 파일이 있는 폴더에서 python ch04.py로 실행합니다. 사용 중인 Python 버전과 실행한 파일이 교재의 실행 기록과 같은지도 확인하면 재현의 조건을 맞출 수 있습니다.

"""Seven tiny fictional CSVs; reduced columns, not the actual exam dataset."""
import csv
import hashlib
import io
import json

DATA = {
    "sites": "site_id\nICN\n",
    "shifts": "shift_code,site_id\nA,ICN\n",
    "employees": "emp_id,site_id,shift_code\nE1,ICN,A\n",
    "work_schedule": "date,emp_id,status\n2026-07-20,E1,WORK\n",
    "stops": 'stop_id,name\nS1,"중앙, 정류장"\n',
    "travel_times": "from_id,to_id,minutes\nS1,ICN,12\n",
    "ridership": "date,stop_id,boardings\n2026-07-20,S1,1\n",
}
REQUIRED = {name: set(next(csv.reader(io.StringIO(text)))) for name, text in DATA.items()}


def validate(files):
    if set(files) != set(REQUIRED):
        raise ValueError("exactly seven named CSVs required")
    tables = {}
    for name, text in files.items():
        reader = csv.DictReader(io.StringIO(text))
        if len(reader.fieldnames or []) != len(set(reader.fieldnames or [])) or not REQUIRED[name] <= set(reader.fieldnames or []):
            raise ValueError(name + ": header")
        rows = list(reader)
        if any(None in row or any(value is None or not value.strip() for value in row.values()) for row in rows):
            raise ValueError(name + ": empty/extra cells")
        tables[name] = rows
    sites = {r["site_id"] for r in tables["sites"]}
    shifts = {r["shift_code"]: r["site_id"] for r in tables["shifts"]}
    employees = {r["emp_id"]: r for r in tables["employees"]}
    if len(employees) != len(tables["employees"]):
        raise ValueError("employees: duplicate")
    for row in employees.values():
        if row["site_id"] not in sites or shifts.get(row["shift_code"]) != row["site_id"]:
            raise ValueError("employees: reference")
    for row in tables["work_schedule"]:
        if row["emp_id"] not in employees or row["status"] not in {"WORK", "OFF"}:
            raise ValueError("work_schedule: reference/status")
    nodes = sites | {r["stop_id"] for r in tables["stops"]}
    for row in tables["travel_times"]:
        if row["from_id"] not in nodes or row["to_id"] not in nodes or int(row["minutes"]) <= 0:
            raise ValueError("travel_times: reference/minutes")
    return tables


def fingerprint(files):
    return hashlib.sha256(json.dumps(files, sort_keys=True, ensure_ascii=False).encode()).hexdigest()


def apply(state, files, expected_hash):
    snapshot = dict(files)
    tables = validate(snapshot)  # no state mutation before validation succeeds
    if fingerprint(snapshot) != expected_hash:
        raise ValueError("validated input changed")
    state.update(input_hash=expected_hash, tables=tables)
    # This in-memory demonstration preserves the prior plan; production uses a transaction.


def main():
    snapshot = dict(DATA)  # strings are immutable; keep this exact input for use.
    validated = validate(snapshot)
    state = {"input_hash": fingerprint(snapshot), "plan": "previous-success"}
    apply(state, snapshot, fingerprint(snapshot))
    before = dict(state)
    broken = dict(snapshot)
    broken["work_schedule"] = broken["work_schedule"].replace("E1", "UNKNOWN")
    try:
        apply(state, broken, fingerprint(broken))
        raise AssertionError("invalid input accepted")
    except ValueError:
        pass
    assert state == before
    changed = dict(snapshot)
    changed["stops"] = changed["stops"].replace("중앙", "서쪽")
    try:
        apply(state, changed, fingerprint(snapshot))
        raise AssertionError("changed snapshot accepted")
    except ValueError:
        pass
    assert state == before
    assert validated["stops"][0]["name"] == "중앙, 정류장"
    print(json.dumps({"csv_count": len(snapshot), "quoted_comma": True,
                      "invalid_reference_rejected": True, "changed_input_rejected": True,
                      "old_state_preserved": state == before}))


if __name__ == "__main__":
    main()

4-1. 작업, 후보, 공식 결과는 서로 다른 질문에 답한다

작업(job)은 사용자의 요청 한 건을 처리하기 위해 기록한 실행 단위입니다. J7이라는 작업은 “7월 20일, 입력 버전 v7로 배정을 만들어 달라”는 의도를 가리킬 수 있습니다. 작업은 아직 계산 전에도 존재합니다. 생성 시각, 진행 상태, 사용한 입력 버전, 실패 이유 같은 정보를 기록하면 요청이 끊어진 뒤에도 무엇을 하던 중이었는지 찾는 데 도움이 됩니다.

후보(candidate)는 생성기가 만들어 검사에 내놓은 결과입니다. 이 책의 생성기(Creator)는 조건에 맞는 배정을 찾아 후보를 만드는 역할입니다. 후보를 만들었다는 것은 확인할 대상이 생겼다는 뜻이지 모든 규칙을 통과했다는 뜻은 아닙니다. 임시 후보를 뜻하는 temp라는 이름을 쓸 수도 있지만, 이름보다 아직 공개 전이라는 역할을 확인하세요.

검사기(Validator)는 주어진 후보를 원본 입력과 규칙에 대조하는 역할입니다. E1·E2·E3을 각각 배정했는지, E4를 넣지 않았는지, 정원과 시각을 지켰는지 확인합니다. 검증 보고서는 어느 후보를 어떤 기준으로 검사해 무엇이 통과하거나 위반했는지 담은 기록입니다. 보고서가 없는 단순한 성공 표시만으로는 실패 원인을 따라가기 어렵습니다.

확정 결과(final)는 검증과 공개 조건을 만족해 사용자에게 공식 결과로 제공하는 배정입니다. 작업 J7은 실행을 추적하고, 후보 C7은 계산 내용을 담고, 결과 F7은 공개할 대상을 가리킵니다. 셋의 식별자가 다른 이유는 맡은 질문이 다르기 때문입니다. “작업은 실패했지만 이전 공식 결과는 남아 있다”는 상황도 이렇게 구분하면 모순이 아닙니다.

첫째, 운영자가 이미 검증해 적용한 입력 v7에서 2026년 7월 20일을 선택합니다. 이 입력에는 E1·E2·E3의 근무와 E4의 휴무가 있습니다. 화면에 표시된 날짜만 믿지 않고 서버가 요청 날짜와 사용할 입력을 확인합니다. 긴 계산 중 원본 자료가 바뀌어도 어떤 내용으로 계산했는지 알 수 있도록 입력 고정본을 연결합니다.

둘째, 작업 관리가 J7을 기록하고 대기 상태로 둡니다. 실제 비동기 설계라면 작업 접수를 응답하고 계산을 Worker에 맡길 수 있습니다. 반대로 같은 요청 안에서 계산을 끝내고 응답하는 동기 설계도 가능합니다. 여기서는 가상 흐름의 책임을 설명하는 것이므로, 두 구조가 모두 구현되어 있다는 뜻은 아닙니다. 어느 구조든 작업 접수와 공식 결과의 의미를 구분할 수 있어야 합니다.

셋째, 생성기가 근무자 세 명을 대상으로 후보 C7을 만듭니다. 출근에는 S1에서 E1·E2가 탄 버스가 08:20에 출발해 08:40에 ICN에 도착합니다. S2에서는 E3이 08:30에 출발해 08:40에 도착합니다. 퇴근에는 두 버스가 ICN에서 18:10에 출발해 S1에 18:35, S2에 18:25 도착합니다. 버스 정원 두 명, 근무 09:00~18:00, 출근 도착 08:40까지·퇴근 출발 18:10 이후라는 교재 가정을 사용한 값입니다.

넷째, 검사기가 C7을 고정된 v7 입력과 대조합니다. 출근과 퇴근에 E1·E2·E3이 각각 한 번 있는지, E4가 없는지, 승차 인원과 방향별 이동시간이 맞는지 다시 확인합니다. S1→ICN은 20분이지만 ICN→S1은 25분입니다. 출근 계산을 그대로 뒤집어 퇴근도 20분이라고 가정하면 잘못된 결과를 놓칠 수 있습니다.

다섯째, 확정 저장이 검증한 후보와 지금 공개할 후보가 같은지, 사용할 입력 버전이 여전히 허용되는지, 이 실행에 공개 권한이 남아 있는지 확인합니다. 조건을 만족하면 C7을 결과 F7로 기록하고 J7의 완료 상태를 함께 일관되게 남깁니다. 실제 DB에서 이를 안전하게 묶는 방법은 9장의 주제입니다. 여섯째, 화면은 J7 상태와 F7을 조회해 새 공식 결과를 보여 줍니다.

4-4. 기록 사이의 연결이 있어야 “이 결과”를 설명할 수 있다

연결 정보는 어떤 입력·작업·후보·검사·결과가 서로 이어지는지 식별하는 값입니다. 예를 들어 보고서가 “통과”만 적고 후보 ID나 내용 식별 정보를 담지 않으면 C7을 검사했는지 C8을 검사했는지 알기 어렵습니다. 작업 ID가 같아도 재시도마다 후보가 바뀔 수 있으므로 작업 ID 하나만으로 충분한지도 확인해야 합니다.

가상의 기록 사슬을 입력 v7 → 작업 J7 → 후보 C7 → 보고서 R7 → 결과 F7로 써 볼 수 있습니다. 여기의 이름은 설명용이며 실제 교재에 이런 DB 테이블이 운영되는 것은 아닙니다. 개인 프로젝트에서는 각 화살표를 어떤 열이나 파일 내용으로 연결하는지 찾습니다. “파일이 있다”보다 “그 파일이 어떤 입력과 시도의 결과인가”를 확인해야 합니다.

실행 시도는 한 작업을 실제로 계산하는 개별 실행을 뜻합니다. Worker가 죽어 같은 J7을 다시 수행했다면 작업은 같아도 첫 시도와 두 번째 시도는 다릅니다. 첫 시도가 뒤늦게 돌아와 새 결과를 덮어쓰면 곤란하므로, 실행 시도를 구별하고 오래된 실행의 확정 권한을 막는 설계가 필요할 수 있습니다. 재시도와 안전한 확정을 나누는 이유입니다.

검증이 끝난 뒤 후보 내용을 고친 경우에도 연결이 끊어집니다. 정원 두 명을 검사한 뒤 E3을 같은 버스에 추가했다면 앞의 통과 결과는 바뀐 후보를 증명하지 않습니다. 검증 뒤 수정하지 못하게 다루거나, 내용이 달라지면 다시 검사하도록 해야 합니다. 후보 동일성은 단지 보기 좋은 ID를 붙이는 문제가 아니라 무엇을 검사했는지 유지하는 문제입니다.

4-5. 실패한 작업과 보존한 이전 결과를 함께 보여 준다

이미 성공한 결과 F6가 있는 상태에서 새 작업 J7을 시작했다고 합시다. C7에서 E3이 빠져 검증에 실패했다면 J7은 실패 기록과 위반 이유를 남길 수 있습니다. 그러나 C7을 새 공식 결과로 공개하면 안 됩니다. F6를 보존하는 것과 J7의 실패를 숨기는 것은 다릅니다. 사용자는 새 요청이 실패했다는 사실과 현재 표시하는 결과가 이전 성공본이라는 사실을 모두 알아야 합니다.

입력 v8을 새로 적용했다면 F6가 남아 있다는 사실만으로 v8의 최신 결과라고 표시할 수도 없습니다. 과거 이력으로 보관하는 정책과 현재 입력에 맞는 결과로 제공하는 정책을 구분해야 합니다. 이 책의 가상 설명에서는 이전 성공본을 지우지 않고 그 입력 버전을 함께 표시합니다. 실제 프로젝트의 화면 정책은 요구사항과 결과 조회 코드를 통해 확인합니다.

Worker가 후보를 만들던 중 죽었을 때 후보 파일이 일부 남아 있을 수도 있고 아무 후보도 없을 수도 있습니다. 메모리에만 있던 후보는 프로세스와 함께 사라질 수 있습니다. 작업이 DB에 RUNNING으로 남았다고 해서 지금도 계산 중이라는 뜻은 아닐 수 있습니다. 이 상태를 누가 감지하고 처리하는지는 별도 책임입니다. 이 장의 정상 흐름만으로 자동 복구를 약속하지 않습니다.

실패를 확인하려면 J7의 상태, 입력 버전, 후보 식별자, 위반 보고서, final 식별자를 각각 봅니다. 모든 실패를 “오류 발생” 한 줄로만 남기면 입력 문제인지 계산 중단인지 확정 거절인지 판단하기 어렵습니다. 반대로 사용자에게 내부 기록을 전부 노출할 필요는 없습니다. 운영자가 확인할 진단 정보와 사용자가 볼 결과를 역할에 맞게 구분할 수 있습니다.

4-6. 책임을 분리한 코드와 강제하는 저장 경계는 다르다

examples/ch05.py는 입력, 후보, 생성, 검증, 저장소를 작은 Python 코드로 나눈 보충 자료입니다. Input은 버전과 직원 묶음을, Candidate는 버전과 배정 묶음을 담습니다. create()는 받은 직원을 그대로 후보로 옮깁니다. 이 예제에는 정류장, 버스, 날짜, 출근·퇴근 시각 계산이 없습니다. 공통 배정 사례의 전체 구현이 아니라 책임을 읽는 모형입니다.

validate()는 버전이 같은지, 직원 집합이 같은지, 중복이 없는지 확인합니다. Repository.publish()는 저장소의 현재 버전과 후보 버전이 같을 때 후보를 final에 넣습니다. 저장소(Repository)는 데이터 저장과 조회를 맡기는 코드의 역할 이름입니다. 이 파일에서는 실제 파일 DB가 아닌 메모리 객체입니다.

중요한 빈칸도 있습니다. 이 publish() 자체는 후보가 검증을 통과했는지 검사하지 않습니다. main()에서 검증 함수를 호출하는 순서는 보이지만, 다른 호출자가 검증을 생략하고 저장소를 부르지 못하게 강제하는 완성된 경계는 아닙니다. “검증 함수를 만들었다”와 “검증 없는 공개 경로를 막았다”는 다른 주장입니다. 실제 설계를 설명할 때 꼭 구별해야 합니다.

예제는 입력 버전을 2로 바꾼 뒤 버전 1 후보의 공개가 거절되는지, 중복된 직원 후보가 검증에서 거절되는지 확인하도록 작성되어 있습니다. 데이터 묶음은 변경을 제한하는 형태로 만들지만 그것이 DB 트랜잭션이나 여러 프로세스의 경쟁 제어를 대신하지 않습니다. 하나의 호출 흐름에서 통과한 조건을 서비스 전체 보장으로 확대하지 않는 연습입니다.

실제 확정 경계에서는 검증 근거, 후보 내용, 입력 버전, 실행 시도, 현재 작업 상태를 어디에서 함께 확인하는지 찾아야 합니다. 파일을 여러 개로 나누었다는 설명보다 “검증 결과와 후보가 같은지 이 지점에서 확인하고, 조건을 만족할 때만 공식 결과를 바꾼다”는 설명이 책임을 더 잘 보여 줍니다.

"""Responsibility boundaries in a single-thread in-memory model."""
import json
from dataclasses import dataclass, FrozenInstanceError


@dataclass(frozen=True)
class Input:
    version: int
    workers: tuple[str, ...]


@dataclass(frozen=True)
class Candidate:
    version: int
    assignments: tuple[str, ...]


def create(snapshot):
    return Candidate(snapshot.version, snapshot.workers)


def validate(snapshot, plan):
    return (plan.version == snapshot.version
            and set(plan.assignments) == set(snapshot.workers)
            and len(plan.assignments) == len(set(plan.assignments)))


class Repository:
    def __init__(self):
        self.version, self.final = 1, None

    def publish(self, plan):
        if plan.version != self.version:
            return False
        self.final = plan
        return True


def main():
    snapshot = Input(1, ("E1", "E2"))
    plan = create(snapshot)
    assert validate(snapshot, plan)
    repository = Repository()
    repository.version = 2
    assert not repository.publish(plan)
    assert repository.final is None
    try:
        snapshot.version = 3
        raise AssertionError("frozen field changed")
    except FrozenInstanceError:
        pass
    assert not validate(snapshot, Candidate(1, ("E1", "E1")))
    print(json.dumps({"candidate_valid": True, "stale_publication_rejected": True,
                      "repository_scope": "single-thread-memory"}))


if __name__ == "__main__":
    main()

5-1. 답을 만드는 일과 답을 확인하는 일

누군가 여행 일정을 짰다고 생각해 봅시다. 만드는 사람은 목적지와 시간을 조합해 일정을 찾습니다. 확인하는 사람은 완성된 일정에서 기차가 출발하기 전에 역에 도착하는지, 같은 시간에 다른 도시에 있지는 않은지 살펴봅니다. 좋은 일정을 찾아내는 절차와 이미 만들어진 일정의 모순을 찾는 절차는 다를 수 있습니다.

이 책에서 Creator는 입력과 규칙을 받아 배정 후보를 만드는 생성기입니다. Validator는 원본 입력·규칙·후보를 대조해 위반 목록을 만드는 검사기입니다. 앞 장의 candidate는 이 둘 사이를 오가는 임시 계획입니다. final은 필요한 검사를 통과하고 확정 조건까지 충족해 사용자에게 공개한 결과입니다. 생성기는 “어떤 답을 만들까”, 검사기는 “이 답이 조건을 지켰나”라는 질문을 맡습니다.

근무자 E1·E2·E3를 출근과 퇴근에 배정하는 예를 떠올려 보세요. 생성기는 E1과 E2를 S1 노선에, E3를 S2 노선에 넣을 수 있습니다. 검사기는 근무표에서 대상 세 명을 다시 구해 각각 양방향 한 번씩 등장하는지 셉니다. 생성기가 스스로 적은 “전원 배정 완료” 문장만 읽고 끝내면 검사기의 역할을 한 것이 아닙니다.

역할 분리는 같은 파일 안의 함수 두 개로도 시작할 수 있습니다. 별도 파일이나 프로세스가 반드시 필요한 것은 아닙니다. 중요한 것은 생성 함수의 어떤 결과를 검사 함수에 주고, 검사 실패를 어떻게 전달하며, 누가 최종 공개를 허용하는지가 분명한가입니다. 검사기가 후보를 몰래 고치면 그 변경에 대한 검사도 다시 필요합니다.

5-2. 검사기에 무엇을 넘겨야 할까

입출력 계약은 한 역할이 어떤 자료를 받고 어떤 결과를 돌려주는지 정한 약속입니다. 생성기에 근무표·정류장·이동시간·정원·시간 조건을 주고 후보를 받았다면, 검사기에도 그 후보의 의미를 판단할 근거가 있어야 합니다. 직원 이름만 주고 날짜나 방향을 빼면 출근 누락과 다른 날의 배정을 구별할 수 없습니다.

입력과 규칙에는 버전도 연결합니다. 버전은 어느 시점의 내용을 사용했는지 구별하는 표지입니다. 생성기는 근무표 v7을 썼는데 검사기는 v8을 읽었다면 같은 직원을 대상으로 이야기하고 있는지부터 알 수 없습니다. 후보·입력·규칙의 연결을 고정해야 검사 통과라는 말에 구체적인 대상이 생깁니다.

5-3. 동시에 시작해도 되는 일과 기다려야 하는 일

의존성은 어떤 일이 다른 일의 결과를 필요로 하는 관계입니다. 식탁을 닦는 일과 접시를 준비하는 일은 겹칠 수 있지만, 접시에 담긴 음식의 양을 확인하려면 먼저 음식이 담겨 있어야 합니다. 같은 완성 후보의 최종 검사도 생성이 끝나기를 기다립니다. 두 역할을 별도 프로세스로 옮겨도 필요한 입력이 저절로 생기지는 않습니다.

이런 순서를 화살표로 그린 뒤 앞선 작업을 끝낸 것부터 배치하는 방법을 위상 순서라고 합니다. 어려운 이름을 외우기보다 “아직 없는 자료를 읽지 않게 순서를 정한다”고 이해하세요. 준비된 작업을 찾는 도구와 실제로 여러 일을 실행하는 장치는 다릅니다. 작업 목록만 나열했다고 병렬 실행한 것은 아닙니다.

5-4. 조각마다 통과해도 합치면 틀릴 수 있다

생성을 두 조각으로 나눠 보겠습니다. 첫 조각은 출근 대상 E1을 한 번 배정하고, 둘째 조각도 E1을 한 번 배정했습니다. 각 조각 안에서 중복을 검사하면 둘 다 통과합니다. 그러나 전체 대상이 E1·E2라면 합친 결과는 E1 두 번, E2 영 번입니다. 조각 내부의 성공을 전체 성공으로 바꿔 말할 수 없습니다.

지역 검사는 한 조각 안의 조건을, 전역 검사는 합친 전체의 조건을 확인합니다. 노선마다 정원을 지켰더라도 같은 차량을 같은 시간에 서로 다른 노선에 넣었을 수 있습니다. 사업장별로 따로 만들었더라도 다른 사업장 근무자를 빠뜨렸을 수 있습니다. 무엇을 나누었고 어떤 자원을 함께 쓰는지 살펴야 합니다.

생성된 조각을 차례로 넘겨 즉시 검사하는 방식을 만들 수도 있습니다. 이처럼 단계의 출력이 다음 단계로 흘러가는 구조를 파이프라인이라고 합니다. 다만 중간에 아직 E3의 조각이 오지 않았다고 바로 “E3 누락”을 최종 판정하면 안 됩니다. 조각이 모두 왔음을 알리는 완료 조건과 마지막 전역 검사가 필요합니다.

초보 단계에서는 입력을 고정하고, 완성 후보를 한 번 넘기고, 전체를 검사하는 흐름부터 이해하는 편이 좋습니다. 그 뒤 실제 자료가 커서 메모리나 시간이 문제일 때 조각 처리의 이득을 따져 볼 수 있습니다. 단순한 흐름도 모든 요구를 지켜야 하며, 복잡한 흐름도 전체 검사를 생략할 이유가 되지는 않습니다.

5-5. 독립 검사는 다른 파일 이름에서 생기지 않는다

생성기와 검사기가 모두 잘못된 근무자 목록을 읽으면 같은 오류를 놓칠 수 있습니다. 예를 들어 공통 함수가 OFF 직원 E4를 WORK로 골랐고, 두 역할 모두 그 목록을 정답으로 믿었다면 결과가 일치해도 실제 요구는 어겼습니다. 독립 검사란 생성기의 자체 판정만 되풀이하지 않고 원본과 규칙에서 결과의 조건을 다시 확인하는 것입니다.

코드를 모두 두 번 작성해야 한다는 뜻은 아닙니다. 문자 인코딩, 즉 문자를 바이트로 표현하는 방식이나 날짜 자료형을 읽는 공통 도구를 사용할 수 있습니다. 다만 누가 대상인지, 배정 횟수가 몇 번인지, 노선 시각이 조건을 만족하는지 같은 핵심 판정을 생성기의 탐색 내부 상태에만 의존하지 않게 합니다. 공통 코드에서 틀릴 수 있는 부분에는 별도의 작은 정답 사례를 붙일 수 있습니다.

검사기를 확인할 때는 정상 후보 하나만 보여 주지 않습니다. E1을 지운 후보, E1을 두 번 넣은 후보, OFF인 E4를 넣은 후보, 정원보다 한 명 많이 태운 후보를 만들어 각각 거절하는지 확인합니다. 정상 결과를 일부러 바꾸는 이런 검사를 여기서는 변이 검사라고 부릅니다. 무엇을 틀리게 했는지 우리가 아는 사례로 검사기의 반응을 보는 것입니다.

또한 검사한 뒤 후보가 바뀌지 않아야 합니다. 검사 시점에는 E1·E2였는데 저장 직전에 E3를 추가하면 통과 기록은 현재 후보의 근거가 아닙니다. 변경 불가능한 복사본을 넘기거나 내용 식별값을 연결하고, 확정할 때 동일성을 확인하는 방법을 생각할 수 있습니다. 자세한 DB 확정 조건은 9장에서 다룹니다.

5-6. AI 작성자·검토자와 계획 생성기·검사기

“Creator와 Validator를 나눴다”는 말을 AI 협업에서도 쓰곤 합니다. 이때 작성자는 코드를 제안하고 검토자는 요구 누락이나 버그 가능성을 찾습니다. 여기까지 설명한 계획 생성기·계획 검사기와는 검사 대상이 다릅니다. 코드를 읽는 AI 검토와 실제 계획의 배정 횟수를 계산하는 프로그램 검사를 구별해서 말해야 합니다.

AI 검토가 도움이 되더라도 “문제가 없어 보인다”는 문장은 실행 결과가 아닙니다. 같은 AI가 역할만 바꿔 검토했다면 독립된 외부 사람이 확인했다고 표현할 수도 없습니다. 검토 대상 파일이나 코드 버전, 지적한 내용, 실제 수정, 실행한 명령과 출력을 연결하면 무엇을 확인했는지 설명할 수 있습니다.

계획 Validator를 나눈 장점은 생성 전략을 바꾸어도 같은 기준으로 후보를 확인하기 쉽다는 점입니다. 대가도 있습니다. 후보를 전달하고 조건을 다시 계산하는 비용이 들며, 두 역할이 같은 규칙 버전을 사용하도록 관리해야 합니다. “분리했으니 안전하다”보다 “어떤 오류를 별도 계산으로 잡고 어떤 공통 오류는 남는가”까지 설명하면 설계 판단이 드러납니다.

여러 정류장에서 타고 내리는 노선에서는 전체 승차 인원과 최대 탑승 인원이 다를 수 있습니다. A에서 2명이 타고 B에서 1명이 내린 뒤 C에서 1명이 탄다면 누적 승차는 3명이지만 동시에 탄 사람은 최대 2명입니다. 규칙이 구간별 탑승량을 제한한다면 인접 구간마다 남아 있는 사람을 세어야 합니다. 반대로 업무 요구가 노선 전체의 배정 수를 제한한다면 그 조건도 따릅니다.

6-4. 시간은 방향과 날짜를 붙여 계산한다

출근은 09:00보다 20분 이른 08:40까지 도착해야 합니다. S1에서 20분 걸리므로 늦어도 08:20에 출발합니다. S2는 10분이므로 08:30에 출발할 수 있습니다. 퇴근은 18:00에서 10분 뒤인 18:10 이후 출발합니다. ICN에서 S1은 25분이므로 18:35 도착, S2는 15분이므로 18:25 도착입니다.

출근의 “도착”과 퇴근의 “출발”은 서로 다른 사건입니다. 퇴근 도착이 18:20이라고만 보고 합격시키면 실제 출발이 근무 종료 전이었을 수 있습니다. 어떤 시각을 검사하는지 필드의 의미를 정해야 합니다. 후보에 arrival과 departure라는 이름이 있다고 각각의 계산까지 올바른 것은 아닙니다.

왕복 이동시간도 같다고 가정하지 않습니다. S1 → ICN은 20분이지만 ICN → S1은 25분입니다. 길의 방향, 교통 조건, 제공된 표의 의미가 다를 수 있습니다. 필요한 이동 구간이 입력에 없을 때 이를 0분으로 처리하면 이동할 수 없는 계획을 빠른 계획으로 만들 위험이 있습니다. 누락 데이터를 오류로 볼지 별도 경로로 계산할지는 요구와 설계에 명시합니다.

자정을 넘는 경우에는 날짜와 시각을 결합한 시점으로 계산합니다. 예를 들어 근무 시작이 7월 21일 00:10이면 20분 전은 7월 20일 23:50입니다. 시각 문자열만 비교하면 전날이라는 관계를 잃습니다. 너무 이른 도착이나 지나치게 늦은 퇴근을 허용할지도 업무 시간 창으로 정해야 합니다. 이번 공통 사례는 하루 주간 근무이고, 자정 사례는 별도 확장 설명입니다.

6-5. 유효한 계획 중 무엇을 더 좋다고 할까

알고리즘은 입력에서 결과를 얻기 위한 절차입니다. 모든 대상을 먼저 배정한 뒤 가능한 노선을 합치거나, 후보들을 만들어 조건을 검사하고 비용을 비교할 수 있습니다. 어떤 방식을 택하든 정한 제약을 지켜야 합니다. 빠른 계산이라는 이유로 누락을 허용했다면 같은 문제를 해결했다고 볼 수 없습니다.

목적함수는 유효한 계획 사이에서 좋고 나쁨을 수치로 비교하는 기준입니다. 차량 수, 총 운행시간, 최대 대기시간 등이 될 수 있습니다. 차량 수만 줄이면 일부 근무자가 아주 일찍 출발할 수 있고, 대기시간만 줄이면 차량이 늘어날 수 있습니다. 서로 다른 목적의 손실을 먼저 정해야 개선이라는 말을 해석할 수 있습니다.

반드시 지켜야 하는 조건을 하드 제약, 만족할수록 좋지만 위반에 비용을 부여할 수 있는 선호를 소프트 제약이라고 부르기도 합니다. “정원 초과 금지”라는 필수 요구를 벌점만 주는 선호로 바꾸면, 비용이 더 싸다는 이유로 초과 승차를 선택할 수 있습니다. 계산기의 성공과 요구 충족은 이때 갈라집니다.

비교에는 같은 기준이 필요합니다. 입력·근무일·정원·시간 여유·목적을 고정한 뒤 기존 유효 계획과 새 유효 계획을 비교합니다. 한 명을 누락해 운행시간이 줄었다면 품질 개선이라고 보고하지 않습니다. 먼저 유효성, 그다음 목적값, 마지막으로 계산 시간과 자원 사용을 확인하는 순서가 도움이 됩니다.

6-6. 최적이라는 말에는 조사한 범위가 필요하다

최적해는 정한 모형에서 가능한 해 가운데 목적값이 가장 좋은 해입니다. 좋은 해 하나를 찾았다는 사실만으로 최적임을 알 수는 없습니다. 작은 후보 공간을 전부 살펴보는 완전 탐색은 최적성을 확인하는 한 방법입니다. 그러나 후보 수가 늘면 조사량이 매우 빠르게 커질 수 있습니다.

보충 자료 examples/ch07.py는 별도의 작은 덮기 모형을 사용합니다. A는 E1·E2를 비용 5로, B는 E3를 비용 4로, C는 세 명을 비용 12로 덮습니다. 이 모형에서는 C도 유효하고 A+B도 유효하며, 전체 조합을 조사해 비용 9인 A+B를 찾습니다. 비용은 추상적인 점수이며 운행 분이나 차량 수가 아닙니다.

이 보충 모형에는 정원 2명, 출근·퇴근, 정류장, 시각 조건이 없습니다. 따라서 공통 통근 사례에서 C에 세 명을 태워도 된다는 뜻이 아닙니다. 서로 다른 모형의 수치를 합쳐 읽지 마세요. 예제가 확인한 것은 작은 후보 공간에서 유효성과 비용 개선이 다르다는 점입니다. 출력도 전체 버스 문제의 최적성을 증명하지 않았다고 구별합니다.

실제 탐색이 시간제한에 걸렸다면 무엇을 찾았는지 먼저 말합니다. 유효한 후보가 있으면 “조건을 지키는 후보를 찾았고 최적성은 미확인”일 수 있습니다. 후보를 못 찾았다고 해가 존재하지 않는다는 증명이 되지는 않습니다. 사용한 도구의 종료 상태와 뜻을 확인하고, 중간 후보를 공개하려면 그 후보도 독립 검사와 확정 조건을 통과해야 합니다.

6-7. 검사기를 어떤 반례로 확인할까

"""Exhaustive oracle for one tiny covering model, not a full bus optimizer."""
import itertools
import json

TARGET = {"E1", "E2", "E3"}
ROUTES = {"A": ({"E1", "E2"}, 5), "B": ({"E3"}, 4), "C": (TARGET, 12)}


def feasible(names):
    occurrences = [emp for name in names for emp in ROUTES[name][0]]
    return len(occurrences) == len(set(occurrences)) and set(occurrences) == TARGET


def cost(names):
    return sum(ROUTES[name][1] for name in names)


def main():
    baseline = ("C",)
    assert feasible(baseline)
    choices = [names for size in range(1, 4)
               for names in itertools.combinations(ROUTES, size) if feasible(names)]
    best = min(choices, key=cost)
    assert best == ("A", "B") and cost(best) == 9
    assert cost(baseline) == 12
    assert not feasible(("A",)) and not feasible(("A", "C"))
    print(json.dumps({"baseline_cost": 12, "tiny_model_optimum": 9,
                      "improvement_fraction": (12 - 9) / 12,
                      "global_bus_optimality_proven": False}))


if __name__ == "__main__":
    main()

"""Independent miniature plan checker plus deliberate mutations; not real CSV schema."""
from collections import Counter
from datetime import datetime, timedelta
import json


def check(plan, capacity=45):
    expected = Counter((emp, direction) for emp in ('E1', 'E2') for direction in ('IN', 'OUT'))
    actual = Counter((emp, trip['direction']) for trip in plan for emp in trip['people'])
    errors = []
    if actual != expected:
        errors.append('coverage')
    start = datetime.fromisoformat('2026-07-21T00:10')
    end = datetime.fromisoformat('2026-07-21T08:10')
    for trip in plan:
        if len(trip['people']) > capacity:
            errors.append('capacity')
        moment = datetime.fromisoformat(trip['time'])
        if trip['direction'] == 'IN' and not start - timedelta(hours=12) <= moment <= start - timedelta(minutes=20):
            errors.append('arrival')
        if trip['direction'] == 'OUT' and not end + timedelta(minutes=10) <= moment <= end + timedelta(hours=12):
            errors.append('departure')
    return sorted(set(errors))


def main():
    good = [{'direction': 'IN', 'people': ['E1', 'E2'], 'time': '2026-07-20T23:50'},
            {'direction': 'OUT', 'people': ['E1', 'E2'], 'time': '2026-07-21T08:20'}]
    assert not check(good)
    missing = [dict(trip, people=list(trip['people'])) for trip in good]
    missing[0]['people'] = ['E1']
    assert check(missing) == ['coverage']
    late = [dict(trip) for trip in good]
    late[0]['time'] = '2026-07-21T00:00'
    assert check(late) == ['arrival']
    duplicate = [dict(trip, people=list(trip['people'])) for trip in good]
    duplicate[0]['people'].append('E1')
    assert check(duplicate) == ['coverage']
    off = [dict(trip, people=list(trip['people'])) for trip in good]
    off[0]['people'].append('OFF1')
    assert check(off) == ['coverage']
    early = [dict(trip) for trip in good]
    early[1]['time'] = '2026-07-21T08:19'
    assert check(early) == ['departure']
    too_early = [dict(trip) for trip in good]
    too_early[0]['time'] = '2026-07-20T12:09'
    assert check(too_early) == ['arrival']
    too_late = [dict(trip) for trip in good]
    too_late[1]['time'] = '2026-07-21T20:11'
    assert check(too_late) == ['departure']
    # Candidate metadata cannot override the independently supplied capacity.
    forged = [dict(trip, capacity=999) for trip in good]
    assert check(forged, capacity=1) == ['capacity']
    assert check(good, capacity=1) == ['capacity']
    print(json.dumps({'valid_pass': True, 'mutations_detected': ['missing', 'duplicate', 'off', 'arrival', 'departure', 'capacity', 'arrival-too-early', 'departure-too-late', 'forged-capacity'],
                      'midnight_checked': True, 'route_travel_times_checked': False}))


if __name__ == '__main__':
    main()

7-1. 한 사람이 번갈아 일하는 것과 두 사람이 함께 일하는 것

물을 끓이는 동안 채소를 썰면 두 요리가 진행 중입니다. 요리사는 한 명이지만 물이 끓기를 기다리는 시간을 활용합니다. 두 요리사가 각자 채소를 썰면 같은 순간 두 손질이 실제로 진행됩니다. 어느 경우든 여러 일이 끝나기를 기다리지만, 동시에 사용한 실행 자원은 다릅니다.

동시성은 여러 작업의 진행을 겹쳐 다루는 구조를 말합니다. 한 작업이 끝나기 전에 다른 작업도 시작해 진행할 수 있습니다. 병렬성은 여러 계산이 같은 순간 실제로 실행되는 성질입니다. 한 CPU 코어가 실행 흐름을 번갈아 처리하면 동시성을 구현할 수 있지만 두 계산이 같은 순간 실행됐다는 뜻은 아닙니다.

프로세스나 스레드는 실행을 구성하는 단위이고, 동시성과 병렬성은 실행이 이루어지는 방식에 관한 질문입니다. 프로세스를 두 개 만들었더라도 한쪽이 다른 결과를 기다리거나 CPU 자원이 부족하면 병렬 이득이 작을 수 있습니다. 반대로 한 프로세스 안의 스레드도 환경과 작업 특성에 따라 병렬 실행에 관여할 수 있습니다. 이름만으로 실제 속도를 결정하지 않습니다.

먼저 “A가 끝나기 전에 B도 진행 중인가”, 다음으로 “CPU 계산이 같은 순간 여러 자원에서 실행되는가”를 따로 물어 보세요. 실행 사건의 순서와 사용 자원을 분리하면 화면의 동시 진행 표시만 보고 성능을 판단하는 실수를 줄일 수 있습니다.

7-2. 누가 무엇의 완료를 기다리는가

가상 배정 서비스에서 서버가 계산·검사·저장을 마친 뒤 최종 계획을 응답하면 업무 완료를 한 요청 안에서 기다리는 흐름입니다. 반면 작업 J1을 기록한 뒤 “접수됐다”는 응답을 보내고 나중에 J1을 조회하게 하면 업무의 시작과 완료가 분리됩니다. 두 번째 구조에서 응답이 빨라졌다고 계산 시간이 줄었다고 말할 수는 없습니다. 기다리는 위치가 바뀐 것일 수도 있습니다.

7-3. async와 await를 일의 양보로 이해하기

Python의 코루틴은 진행을 멈추었다가 다시 이어갈 수 있는 작업을 표현합니다. async def로 정의한 함수를 호출하면 코루틴 객체가 만들어집니다. 호출한 사실만으로 별도 프로세스나 스레드가 생기지 않습니다. await로 실행을 이어 가거나 태스크로 등록하는 등 실제 실행 흐름에 연결해야 합니다.

태스크는 코루틴을 실행하도록 관리하는 단위이고, 이벤트 루프는 진행 가능한 태스크와 대기 중인 태스크를 관리하는 실행 장치입니다. 한 태스크가 아직 준비되지 않은 결과를 기다리며 자리를 양보하면 다른 태스크를 진행할 수 있습니다. 계산을 다른 곳으로 순간이동시키는 장치라기보다, 대기 중인 시간을 활용하는 규칙으로 이해하세요.

await가 쓰인 모든 줄에서 반드시 오래 멈추는 것은 아닙니다. 기다리는 결과가 이미 준비됐다면 바로 이어갈 수 있습니다. 반대로 비동기 함수 안에 오래 걸리는 일반 계산이나 실행 흐름을 붙잡는 파일·네트워크 호출이 있으면 다른 태스크도 지연될 수 있습니다. 이처럼 자리를 잡고 반환하지 않는 호출을 블로킹 호출이라고 합니다.

예를 들어 배정 후보를 수백만 번 비교하는 반복문을 async def generate() 안에 넣어도, 그 계산이 저절로 다른 CPU 코어로 옮겨 가지 않습니다. 같은 이벤트 루프에서 오래 자리를 차지하면 상태 조회 같은 다른 요청까지 늦어질 수 있습니다. 함수 선언보다 실제로 어디서 계산하고 어디서 기다리는지 따라가야 합니다.

7-4. CPU 계산과 입출력 대기를 구별하기

CPU는 프로그램의 명령을 실행하는 장치이고, 코어는 계산을 수행하는 실행 자원입니다. 숫자 조합을 많이 비교하는 배정 탐색은 CPU 계산의 비중이 클 수 있습니다. 파일이나 네트워크 응답을 기다리는 작업은 입출력 대기의 비중이 클 수 있습니다. 실제 요청에는 두 종류가 섞이므로 구간을 나누어 관찰합니다.

입출력 대기가 긴 요청 여러 개는 기다리는 시간을 겹쳐 처리하는 이득을 얻을 수 있습니다. 하지만 외부 서비스가 초당 요청 수를 제한하거나 DB 연결 수가 부족하면 무작정 동시 작업을 늘릴 수 없습니다. CPU 계산이 긴 경우에는 실행 자원을 더 쓰는 방법을 검토하지만, 전달 비용과 메모리 사용도 함께 봐야 합니다.

CPython은 Python을 실행하는 대표 구현입니다. 이 책의 Python 3.11 일반적인 CPython 환경에는 GIL이라는 Python 실행기 내부의 잠금이 있어 순수 Python 코드를 여러 스레드가 같은 순간 실행하는 데 제한이 있습니다. 따라서 순수 Python CPU 계산에 스레드만 늘렸다고 여러 코어의 가속을 주장하면 안 됩니다. 입출력 대기와 잠금을 해제하는 확장 라이브러리의 동작은 다를 수 있습니다.

이 설명을 모든 Python 구현과 모든 버전에 그대로 적용하지도 않습니다. 실행 환경과 라이브러리의 보장을 확인해야 합니다. 별도 프로세스는 다른 실행기와 메모리 공간을 사용하지만, 큰 근무표를 전달하고 결과를 되돌리는 비용이 듭니다. 작업이 짧으면 새 프로세스를 시작하는 시간이 절약한 계산보다 클 수도 있습니다.

스레드에 일을 맡기는 구조에서는 실행 흐름을 나누고 같은 프로세스의 객체를 공유할 수 있습니다. 자료 전달이 편할 수 있지만 공유 상태를 동시에 고치는 순서를 관리해야 합니다. 프로세스 자체가 종료되면 그 안의 스레드도 함께 영향을 받습니다. “진행률 변수를 공유한다”와 “서버 재시작 뒤에도 남는다”는 다른 성질입니다.

7-6. 기다림을 옮겨도 남는 문제

비동기 처리와 역할 분리는 계획의 정확성을 대신하지 않습니다. 같은 후보를 생성 중인데 최종 검사기가 중간 배열을 읽으면 아직 오지 않은 직원을 누락으로 볼 수 있습니다. 5장에서 정리한 의존 순서를 지켜 완성 후보를 검사하고, 부분 처리를 사용했다면 마지막 전역 검사를 해야 합니다.

업무 비동기에서는 응답을 못 받은 사용자가 같은 버튼을 다시 누를 수도 있습니다. 작업은 이미 기록됐는데 응답만 유실됐을 수 있기 때문입니다. 같은 요청을 식별할 규칙과 상태 조회가 필요합니다. 대기 시간이 끝났다는 사실도 계산이나 DB 쓰기가 취소됐다는 뜻은 아닙니다. 이 차이는 9·10장의 중복 요청과 실패 처리로 이어집니다.

실행 중인 태스크는 영구 작업 기록이 아닙니다. 서버가 재시작하면 메모리 상태가 사라질 수 있습니다. 별도 프로세스도 작업을 기억하고 회수하는 정책을 자동으로 주지 않습니다. “누가 언제까지 맡았는가”, “현재 공개 결과는 무엇인가”를 저장하고 조회하는 경로가 있어야 장애 뒤 상태를 설명할 수 있습니다.

성능은 같은 입력·규칙·정확성 조건에서 실제 경과 시간을 재어 비교합니다. 계산 시간, 대기 시간, 검사 시간, 확정 시간을 나누면 병목이 보입니다. 화면 도식에서 막대가 짧아진 것은 설명이며 측정값이 아닙니다. 작업 수를 늘리면서 검사를 껐다면 동일한 작업의 속도를 비교한 것도 아닙니다.

"""Concurrent coroutine waiting; no claim of CPU parallelism or speedup."""
import asyncio
import json
import os


async def main():
    started = asyncio.Queue()
    release = asyncio.Event()
    trace = []
    pids = set()

    async def work(name):
        pids.add(os.getpid())
        trace.append((name, "start"))
        await started.put(name)
        await release.wait()
        trace.append((name, "end"))
        return name

    tasks = [asyncio.create_task(work(name)) for name in ("A", "B")]
    names = [await started.get(), await started.get()]
    assert sorted(names) == ["A", "B"]
    assert all(stage == "start" for _, stage in trace)
    release.set()
    result = await asyncio.gather(*tasks)
    assert sorted(result) == ["A", "B"]
    assert len(pids) == 1
    print(json.dumps({"started_before_release": sorted(names),
                      "completed": sorted(result), "one_process": len(pids) == 1}))


if __name__ == "__main__":
    asyncio.run(asyncio.wait_for(main(), timeout=10))

8-1. 주문표를 보관하는 곳과 요리하는 사람

식당에서 주문표를 쌓아 두는 곳과 실제로 요리하는 사람은 다릅니다. 주문표가 있어도 요리사가 가져가지 않으면 음식이 나오지 않습니다. 요리사가 별도 방에서 일해도 주문표를 잃어버리면 무엇을 해야 했는지 알 수 없습니다. 프로그램도 “일을 기억하는 장치”와 “일을 수행하는 실행자”를 나누어 봅니다.

큐는 처리할 항목을 넣고 꺼내는 자료구조나 서비스입니다. 일을 넣는 쪽을 생산자, 꺼내는 쪽을 소비자라고 부릅니다. Worker는 맡은 일을 실제로 수행하는 역할입니다. 요청 서버가 배정 작업을 등록하고 계산 프로세스가 꺼내 수행한다면, 전자는 생산자이고 후자는 소비자 역할을 합니다.

단순 큐는 먼저 들어온 항목을 먼저 꺼내지만 업무 시스템에는 우선순위나 재전달이 있을 수 있습니다. 꺼낸 순서가 완료 순서와 같다고도 할 수 없습니다. 먼저 시작한 큰 작업보다 나중에 시작한 작은 작업이 먼저 끝날 수 있습니다. 사용자에게는 줄의 위치와 작업 상태를 구분해 보여 주어야 합니다.

Worker라는 파일명이나 함수명만으로 별도 프로세스가 되는 것은 아닙니다. 같은 함수 호출일 수도, 스레드일 수도, 별도 실행 프로그램일 수도 있습니다. 실제 시작 코드와 실행 프로세스를 확인해야 요청 서버와 계산이 어떤 실패를 공유하는지 설명할 수 있습니다.

8-2. 메모리 큐와 기록이 남는 작업 큐

메모리에만 둔 대기 목록은 실행 프로세스가 사라지면 함께 잃을 수 있습니다. 영속성은 실행이 끝난 뒤에도 필요한 값을 다시 읽을 수 있게 보관하는 성질입니다. 작업을 받았다고 사용자에게 알렸다면, 요구에 따라 재시작 뒤에도 그 작업을 찾아야 할 수 있습니다. 그때는 파일 DB나 적절한 저장 설정을 가진 작업 서비스가 필요합니다.

Queue라는 이름이 같아도 확인할 범위는 다르다
도구의 예주로 잇는 경계별도로 확인할 점
queue.Queue한 프로세스의 스레드 사이프로세스 종료 뒤 작업 보존
multiprocessing.Queue서로 다른 프로세스 사이미완료 작업의 영구 보관·회수
파일 SQLite의 작업 테이블같은 파일에 접근하는 실행자 사이선점·상태 전이·장애 뒤 재처리
외부 메시지 서비스여러 실행자·서버 사이저장·확인 응답·재전달의 계약과 설정

프로세스 사이에 값을 전달할 수 있다는 사실은 값을 영구 보관한다는 뜻이 아닙니다. 반대로 DB에 작업 행을 저장했어도 실제 실행자가 가져가거나 실패를 회수하는 코드는 별도로 필요합니다. 통신, 보관, 실행, 복구는 연결돼 있지만 같은 기능은 아닙니다.

단일 서버의 작은 서비스에서는 DB 작업 테이블을 큐처럼 사용할 수 있습니다. 입력 버전과 상태를 한 저장소에서 연결하기 쉬운 장점이 있습니다. 다만 같은 로컬 파일을 여러 서버에서 쓰는 구조로 저절로 확장되지는 않습니다. 작업량과 장애 요구가 커지면 저장소의 지원 범위와 운영 방법을 다시 판단해야 합니다.

8-3. 접수했다는 말을 하기 전에 무엇을 기록할까

가상 흐름에서 사용자는 입력 v7으로 계획 생성을 요청합니다. 요청 서버는 요청 권한과 기본 조건을 확인하고 작업 J7을 만듭니다. 작업에는 업무용 식별자인 job_id, 사용할 입력 버전, 상태, 필요하다면 실행 시도 번호를 연결합니다. 이 항목들은 이론 설명을 위한 설계 예시이며 현재 교재가 하나의 통합 서버로 제공하는 API는 아닙니다.

처음 상태를 QUEUED, 즉 대기 중이라고 부르겠습니다. DB 저장을 확정한 뒤 작업 ID로 접수 응답을 보냅니다. DB 변경을 확정하는 것을 커밋이라고 합니다. 메모리에 잠깐 적은 뒤 “저장 완료”라고 응답하거나, 아직 실패할 수 있는 DB 기록 전에 재시작 보존을 약속하면 실제 상태와 사용자 안내가 어긋납니다.

접수 응답 뒤 사용자는 J7을 조회합니다. 대기·실행·검증 실패·성공 같은 상태를 읽고, 성공일 때 어떤 확정 결과를 볼 수 있는지 확인합니다. 진행률 60%는 사용자를 돕는 표시이지만 완료의 근거가 아닙니다. 단계별 비중을 임의로 정한 값일 수도 있고 갱신이 멈췄을 수도 있습니다.

작업의 수명과 요청 연결의 수명도 다릅니다. 브라우저를 닫거나 요청 응답을 기다리다 시간이 끝나도 J7이 실행 중일 수 있습니다. 사용자가 다시 접속했을 때 같은 작업을 찾을 식별자가 필요합니다. 그래서 운영체제의 PID를 업무 작업 ID 대신 쓰지 않습니다. 프로세스는 끝나고 번호가 재사용될 수 있지만 작업 기록은 계속 조회해야 하기 때문입니다.

8-4. 두 Worker가 같은 일을 가져가지 않게 하기

선점은 여기서 대기 중인 작업을 한 실행자가 자신이 맡을 작업으로 확보하는 일을 뜻합니다. Worker A와 B가 둘 다 “J7은 대기 중”이라는 값을 읽고 각자 계산을 시작하면 같은 일을 두 번 수행할 수 있습니다. 읽기와 맡기기를 아무 규칙 없이 떨어뜨려 놓은 것이 원인입니다.

한 가지 방법은 “대기 행을 찾고, 여전히 대기 상태일 때 실행 중으로 바꾼다”를 짧은 DB 트랜잭션으로 묶는 것입니다. 트랜잭션은 정한 변경 묶음을 하나의 확정 경계로 다루는 도구입니다. 상태를 QUEUED → RUNNING으로 바꾸고 실제로 한 행이 바뀌었는지 확인합니다. 다른 실행자가 이미 가져갔다면 자신도 가져갔다고 가정하지 않습니다.

긴 배정 계산을 선점 트랜잭션 안에서 모두 수행하는 것은 피할 이유가 있습니다. 다른 작업이 필요한 DB 쓰기를 오래 기다릴 수 있기 때문입니다. 짧게 맡기기를 확정하고 계산은 그 경계 밖에서 수행한 뒤, 마지막 저장 때 현재 권한을 다시 확인하는 구조를 생각할 수 있습니다. 계산을 바깥으로 옮긴 만큼 그 사이의 상태 변화에 대응해야 합니다.

선점 성공은 업무 성공이 아닙니다. RUNNING은 어떤 실행자가 맡았다는 기록입니다. 생성·검사·확정이 남아 있습니다. 선점 직후 Worker가 사라지면 결과 없이 RUNNING만 남을 수 있습니다. 이 사실이 선점과 복구를 별도 질문으로 다뤄야 하는 이유입니다.

8-5. 계산과 검사를 마쳤어도 확정 조건을 확인한다

Worker가 가상의 정상 후보를 만들면 Validator가 원본 입력과 규칙에 맞춰 검사합니다. 통과한 후보도 즉시 누구나 덮어쓸 수 있게 저장하지 않습니다. 계산 중 새 입력 v8이 적용됐거나, 취소·재시도로 다른 실행 시도가 유효해졌을 수 있습니다. 후보가 자기 입력에 맞는 것과 지금 공개할 권한이 있는 것은 다른 조건입니다.

확정 경계에서는 입력 버전, 현재 작업 상태, 실행 시도 번호, 검사한 후보의 동일성 등을 확인할 수 있습니다. 충족할 때 결과 공개와 성공 상태를 함께 확정해야 사용자가 “성공인데 결과 없음” 같은 어긋난 상태를 읽을 가능성을 줄일 수 있습니다. 구체적인 DB 조건부 갱신은 9장에서 차근차근 다룹니다.

검증 실패라면 어떤 규칙을 어겼는지 진단하고 새 후보를 공식 결과로 바꾸지 않습니다. 이전 성공 결과가 있다면 이 가상 설계에서는 보존합니다. 다만 이전 결과가 현재 입력과 다른 버전일 수 있으므로 사용자에게 결과의 기준 버전을 표시해야 합니다. 이전 계획이 남아 있다는 사실과 새 생성이 성공했다는 안내를 섞지 않습니다.

자동 재시도도 모든 실패에 맞는 해결책은 아닙니다. 없는 직원 ID를 참조하는 입력은 같은 내용으로 반복해도 보통 해결되지 않습니다. 일시적인 실행 장애는 재시도할 수 있지만 횟수·대기·오래된 실행의 확정 차단을 정해야 합니다. 실패 종류와 재시도 효과를 함께 설명할 수 있어야 합니다.

8-6. Worker가 사라졌을 때 회수는 누가 할까

RUNNING이라는 글자는 Worker의 현재 생존을 보증하지 않습니다. 마지막 기록 이후 프로세스가 종료됐을 수 있습니다. heartbeat는 실행자가 살아서 일하고 있음을 주기적으로 알리는 신호입니다. 임대는 일정 기간 동안 작업을 맡을 권한을 주는 방식입니다. 관리자는 신호와 만료 조건을 보고 작업을 다시 대기로 돌리거나 실패 처리할 수 있습니다.

오랫동안 신호가 없다고 옛 Worker가 확실히 사라졌다고 단정할 수도 없습니다. 일시 정지나 통신 지연 뒤 돌아올 수 있습니다. 회수 후 새 실행에 시도 번호를 주고, 옛 번호의 결과 확정을 거절하는 조건이 필요합니다. 그렇지 않으면 새 결과가 저장된 뒤 옛 계산이 덮어쓸 수 있습니다. 회수와 오래된 실행 차단은 한 쌍으로 생각합니다.

외부 메시지 서비스에서 쓰는 확인 응답, 또는 ack도 어느 단계의 확인인지 중요합니다. 메시지를 받자마자 완료 확인을 보내고 계산 중 죽으면 다시 전달받지 못할 수 있습니다. 결과 저장 뒤 확인하면, 저장은 됐지만 확인 응답이 유실돼 다시 받을 수 있습니다. 따라서 전달과 실행을 항상 한 번으로 만들었다고 가정하기보다 중복 실행 시 확정이 안전한지 확인합니다.

작업이 너무 많이 쌓이는 문제도 남습니다. Worker를 늘리면 CPU·메모리·DB 경쟁이 커질 수 있고, 대기열만 늘리면 사용자의 결과 대기가 길어집니다. 대기 작업 수와 최대 동시 실행 수를 제한하고 실제 대기·계산·검증·확정 시간을 관찰해야 합니다. 큐를 두었다는 사실만으로 처리 용량이 늘지는 않습니다.

8-7. 보충 예제에서 실행한 것과 설명한 것

examples/ch10.py는 임시 폴더에 파일 SQLite DB를 만들고 대기 작업 하나를 넣습니다. spawn 방식으로 별도 Python 프로세스 두 개를 시작합니다. 각 Worker는 BEGIN IMMEDIATE로 짧은 선점 트랜잭션을 열고 대기 작업을 RUNNING으로 바꿉니다. 한 실행자가 맡은 뒤 다른 실행자는 그 작업을 다시 대기 작업으로 가져가지 않습니다.

일을 가져간 프로세스는 fictional-plan이라는 고정 문자열과 자기 PID를 저장하고 상태를 SUCCEEDED로 바꿉니다. 부모는 자식 종료 코드, 저장된 PID가 부모와 다른지, 최종 행이 하나인지, 다시 가져갈 대기 작업이 없는지를 확인합니다. 책의 예제 폴더에서 python examples/ch10.py로 실행할 수 있습니다.

여기에는 실제 Creator·Validator 호출, 근무자 배정, 임대·heartbeat·자동 회수가 없습니다. 출력의 recovery_after_claim_tested: false는 선점 뒤 죽음의 복구를 확인하지 않았다는 뜻입니다. SUCCEEDED도 이 작은 실험의 고정 결과 저장 상태이며 실제 계획이 유효하다는 판정이 아닙니다. 임시 DB는 실험 종료 뒤 정리되므로 사용자에게 영구 결과 파일을 남기는 예제도 아닙니다.

자신의 프로젝트에서는 작업 등록 경로, 선점 코드, 프로세스 시작점, 상태 조회, 확정 조건, 회수 관리자를 찾아 하나씩 연결합니다. 존재하지 않는 회수 기능은 “설계상 필요하지만 현재 미구현”이라고 말합니다. 별도 프로세스를 만들었다는 증거와 장애 뒤 사용자가 결과를 확인할 수 있다는 증거는 따로 제시해야 합니다.

"""Persistent claim + real spawned worker. Fictional miniature queue, no lease recovery."""
import json
import multiprocessing as mp
import os
import sqlite3
import tempfile
from pathlib import Path


def claim(path):
    db = sqlite3.connect(path, isolation_level=None, timeout=5)
    try:
        db.execute('BEGIN IMMEDIATE')
        row = db.execute("SELECT id FROM jobs WHERE status='QUEUED' ORDER BY id LIMIT 1").fetchone()
        if not row:
            db.execute('COMMIT')
            return None
        assert db.execute("UPDATE jobs SET status='RUNNING' WHERE id=? AND status='QUEUED'", row).rowcount == 1
        db.execute('COMMIT')
        return row[0]
    finally:
        db.close()


def worker(path):
    job = claim(path)
    if job is None:
        return
    db = sqlite3.connect(path)
    try:
        with db:
            db.execute("UPDATE jobs SET status='SUCCEEDED', result=?, pid=? WHERE id=? AND status='RUNNING'",
                       ('fictional-plan', os.getpid(), job))
    finally:
        db.close()


def main():
    with tempfile.TemporaryDirectory() as temp:
        path = str(Path(temp) / 'jobs.db')
        db = sqlite3.connect(path)
        db.execute('CREATE TABLE jobs(id INTEGER PRIMARY KEY, status TEXT, result TEXT, pid INTEGER)')
        db.execute("INSERT INTO jobs VALUES(1,'QUEUED',NULL,NULL)")
        db.commit()
        db.close()
        processes = [mp.get_context('spawn').Process(target=worker, args=(path,)) for _ in range(2)]
        try:
            for p in processes:
                p.start()
            for p in processes:
                p.join(15)
                assert p.exitcode == 0
            db = sqlite3.connect(path)
            try:
                status, result, pid = db.execute('SELECT status,result,pid FROM jobs').fetchone()
                assert (status, result) == ('SUCCEEDED', 'fictional-plan')
                assert pid != os.getpid()
                assert claim(path) is None
            finally:
                db.close()
        finally:
            for p in processes:
                if p.is_alive():
                    p.terminate()
                    p.join()
    print(json.dumps({'workers': 2, 'final_rows': 1, 'separate_pid': True,
                      'recovery_after_claim_tested': False}))


if __name__ == '__main__':
    main()

9-1. DB는 기록을 관리하고, 트랜잭션은 변경을 묶는다

DB는 데이터베이스의 줄임말이며, 데이터를 저장하고 정해진 조건으로 찾고 바꾸는 시스템입니다. 파일에 저장하는 DB는 나중에 다시 펼칠 수 있는 기록장에 비유할 수 있습니다. 다만 메모리 전용 DB는 프로세스 종료 뒤 남지 않으므로 실제 저장 방식도 확인해야 합니다. 테이블은 같은 모양의 기록을 모아 둔 표입니다. 작업 표에는 작업 번호, 입력 버전, 상태를 한 행에 기록할 수 있습니다. 여기서 행은 작업 한 건에 해당합니다. SQL은 이런 표를 조회하거나 바꾸는 데 사용하는 언어입니다.

하지만 DB를 쓴다고 모든 기록이 저절로 함께 바뀌지는 않습니다. 새 계획은 저장했는데 작업 상태를 성공으로 바꾸기 전에 프로그램이 죽으면, 화면에는 실행 중으로 보이면서 결과만 바뀔 수 있습니다. 반대로 상태만 성공이고 결과가 없다면 사용자는 무엇을 믿어야 할까요? 서로 맞아야 하는 변경을 하나의 묶음으로 다루어야 합니다.

트랜잭션은 관련된 DB 작업을 하나의 성공 또는 실패 단위로 다루는 경계입니다. 은행에서 A의 돈을 줄이고 B의 돈을 늘리는 두 변경이 함께 확정되어야 하는 것과 비슷합니다. 커밋은 변경을 확정하는 일이고, 롤백은 아직 확정하지 않은 묶음의 변경을 되돌리는 일입니다. “후보를 공식 결과로 저장하기”와 “해당 작업을 성공으로 표시하기”가 같은 경계에 있어야 둘 사이의 모순을 줄일 수 있습니다.

이 비유에도 범위가 있습니다. DB 트랜잭션이 이메일 발송이나 이미 외부 업체에 전송한 명령까지 되돌려 주지는 않습니다. 먼저 무엇이 같은 DB 안의 변경이고 무엇이 밖에서 일어나는 효과인지 구분해야 합니다. 하나의 함수에 적혀 있다는 사실도 같은 트랜잭션이라는 증거가 되지 않습니다.

9-2. 긴 계산보다 짧은 확정 경계가 중요한 이유

배정 생성에 30초가 걸린다고 가정해 봅시다. 이 시간 내내 DB를 바꾸는 권한을 잡고 있으면 다른 요청의 데이터 적용이나 상태 변경이 기다릴 수 있습니다. 잠금은 여러 실행이 같은 자료를 바꾸려 할 때 허용 순서를 조정하는 수단입니다. 잠금은 필요한 충돌을 막지만, 오래 유지하면 기다리는 시간도 길어질 수 있습니다.

이 책의 설명용 설계는 입력을 고정해 읽고, 그 입력으로 계산하고 검사한 뒤, 짧은 트랜잭션에서 확정 조건을 다시 확인합니다. 책상에서 초안을 작성하는 동안 금고 문을 계속 붙잡지 않고, 마지막으로 서류를 넣는 순간에 필요한 확인을 모으는 셈입니다. 다만 입력을 읽는 시점에 정한 기준이 최종 공개 순간에도 맞는지 다시 검사해야 합니다.

  1. 적용된 입력 v7을 읽어 이번 작업이 사용할 고정본을 만든다.
  2. DB 쓰기 경계 밖에서 후보를 계산하고, 같은 고정본과 규칙으로 검사한다.
  3. 확정 트랜잭션을 열고 현재 입력 버전과 작업의 실행 권한을 확인한다.
  4. 조건이 맞을 때 결과와 성공 상태를 함께 기록하고 커밋한다.
  5. 조건이 달라졌다면 확정을 거절하고 기존 공식 결과를 보존한다.

이 순서는 설계 원리입니다. 실제 프로그램이 이 흐름을 구현했는지는 호출 경로와 SQL을 읽고, 실패 전후의 기록을 확인해야 알 수 있습니다. 모든 계산에 짧은 트랜잭션 구조가 자동으로 적합한 것도 아닙니다. 요구하는 일관성과 사용 중인 DB의 동작에 맞춰 읽기와 쓰기의 경계를 정해야 합니다.

9-3. 입력 버전은 “어느 문제를 풀었는가”를 나타낸다

버전은 바뀐 자료를 구별하기 위해 붙이는 표시입니다. 오전의 근무표 v7에는 E1·E2·E3가 근무자로 적혀 있었는데, 생성 중에 E3가 휴무로 바뀐 v8이 적용됐다고 해 봅시다. v7을 기준으로 만든 후보는 v7의 규칙을 완벽하게 지켰더라도 v8의 공식 결과로 쓰기에는 맞지 않을 수 있습니다. 계산 오류와 입력이 오래된 문제는 서로 다릅니다.

따라서 후보에는 자신이 사용한 입력 버전이 연결되어야 합니다. 마지막 공개 시점에 후보의 v7과 현재 적용 버전 v8을 비교해, 현재 입력으로 다시 만들어야 하는지 판단합니다. 이 책의 기본 설계는 서로 다르면 현재 결과로 확정하지 않는 쪽입니다. 과거 입력의 결과를 이력으로 보관하는 정책은 별도로 정할 수 있지만, 이력을 최신 결과처럼 표시해서는 안 됩니다.

해시는 데이터 내용을 바탕으로 만든 지문과 같은 값입니다. 검증한 파일 내용이 이후 바뀌었는지 비교하는 데 쓸 수 있습니다. 버전이 “자료의 몇 번째 상태인가”에 가깝다면 해시는 “같은 내용인가”를 확인하는 단서입니다. 해시가 같다는 이유만으로 데이터가 업무적으로 올바르다는 결론은 나오지 않습니다. 잘못된 파일도 지문을 가질 수 있기 때문입니다.

입력 버전만 기록하고 실제 생성기가 그 입력을 읽었는지 확인하지 않으면 연결이 끊깁니다. 기록된 v7과 계산에 사용한 파일이 v8일 수도 있습니다. 버전 표기, 고정본을 전달하는 경로, 검사기가 사용한 입력, 확정된 결과의 연결을 함께 따라가야 합니다.

9-4. 시도 번호는 “지금 확정할 권한이 있는 실행인가”를 나타낸다

같은 입력에서도 오래된 실행이 생길 수 있습니다. 작업 J1의 첫 Worker가 멈춘 것처럼 보여 두 번째 Worker에게 일을 다시 맡겼다고 합시다. 잠시 뒤 첫 Worker도 돌아와 결과를 저장하려 합니다. 두 실행 모두 입력 v7을 썼으므로 입력 버전 비교만으로는 어느 쪽을 막아야 할지 알 수 없습니다.

시도 번호는 같은 업무를 다시 실행할 때 현재 유효한 실행을 구별하는 번호입니다. 코드에서는 세대, epoch, attempt 같은 이름을 쓰기도 합니다. 이번 장에서는 이해를 돕기 위해 “확정권의 차례표”라고 생각해 봅시다. 처음에는 시도 1에 권한을 주고 다시 맡길 때 시도 2로 바꾸면, 시도 1은 뒤늦게 계산을 끝내도 공식 결과를 덮어쓸 수 없어야 합니다.

이런 차단을 펜싱이라고 부릅니다. 울타리처럼 오래된 실행의 쓰기를 막는다는 뜻입니다. 핵심은 Worker가 스스로 “나는 최신이다”라고 말하는 데 있지 않습니다. 최종 저장 경계에서 현재 시도 번호와 후보가 가진 시도 번호를 비교해야 합니다. 현재 상태가 여전히 실행 중인지도 함께 확인해야 취소 후 완료나 같은 후보의 반복 확정을 막을 수 있습니다.

즉 확정 조건은 적어도 세 질문으로 나누어 볼 수 있습니다. 같은 입력의 결과인가, 현재 유효한 시도가 만든 것인가, 아직 확정이 허용되는 상태인가? 번호를 비교하는 순간과 실제 저장 사이가 다시 벌어지면 틈이 생기므로, 조건 검사와 변경을 같은 트랜잭션이나 조건부 변경에 모읍니다.

9-5. 중복 요청과 중복 실행은 비슷해 보여도 다르다

생성 버튼을 눌렀는데 응답이 오지 않아 다시 누른 상황을 생각해 봅시다. 첫 요청이 서버에 도착하지 않았을 수도 있고, 이미 접수됐지만 응답만 사라졌을 수도 있습니다. 사용자의 의도는 한 번인데 요청은 두 번 보일 수 있습니다. 멱등성은 같은 의도를 반복했을 때 추가 효과가 생기지 않도록 다루는 성질을 말합니다.

설명용 설계에서는 사용자와 요청 키를 묶어 동일한 업무를 식별합니다. 같은 사용자·같은 키·같은 내용이면 기존 작업 번호를 돌려줍니다. 같은 키에 다른 내용이 오면 충돌로 거절합니다. 키만 같다고 다른 근무일이나 다른 설정을 조용히 같은 요청으로 취급하면 사용자의 새 의도를 잃을 수 있습니다.

요청 중복 제거는 Worker가 실제로 한 번만 실행된다는 보장과 다릅니다. 재시도 때문에 계산은 두 번 할 수 있어도 최종 저장은 한 번만 허용할 수 있습니다. 반대로 DB 결과는 한 번 저장했는데 이메일이나 외부 결제는 두 번 수행될 수도 있습니다. “멱등 키를 넣었으니 모든 효과가 정확히 한 번이다”라고 말하면 확인 범위보다 주장이 넓어집니다.

외부 효과까지 다룰 때는 DB에 전송할 일을 함께 남긴 뒤 전달하는 방식 등이 필요할 수 있습니다. 이를 깊게 구현하는 일은 이 입문서의 중심에서 벗어나므로, 여기서는 DB 안의 확정과 밖의 효과가 서로 다른 경계라는 점을 기억하면 충분합니다. 무엇을 중복으로 보며, 어디서 막았는지 구체적으로 설명하세요.

9-6. 작은 예제에서 확인할 수 있는 것

보충 파일 examples/ch08.py는 파일 SQLite에서 참조가 잘못된 행을 넣다가 롤백한 뒤 계획 행이 0개인지 확인합니다. 이어서 버전 1일 때만 바꾸는 조건부 변경을 두 번 수행해, 처음에는 1행이 바뀌고 오래된 조건의 두 번째 변경은 0행인지 검사합니다. 연결을 닫고 새로 열어 버전 2가 남아 있는지도 확인합니다. 이것은 재연결 후 보존과 순차 조건부 변경의 근거이며 동시 작성자나 전원 차단 시험은 아닙니다.

examples/ch11.py는 별도의 메모리 SQLite에서 요청 중복 제거와 조건부 확정을 확인합니다. 출력의 job_rows: 1은 같은 요청이 한 행으로 남았다는 뜻입니다. stale_input_rows: 0과 stale_worker_rows: 0은 오래된 입력과 시도의 변경이 거절됐다는 뜻입니다. 올바른 첫 확정은 accepted_rows: 1, 같은 조건의 반복 확정은 repeat_publication_rows: 0입니다.

두 파일은 서로 다른 작은 실험입니다. 하나의 배정 서버가 이 둘을 연달아 호출한다는 뜻은 아닙니다. 특히 ch11.py의 validated-candidate는 검사기를 실제 호출해 얻은 계획이 아니라 교육용 문자열입니다. 이 파일만으로 배정 규칙을 검사했다고 말할 수 없습니다. 파일과 실행 기록을 함께 볼 때 이 구분이 중요합니다.

"""Rollback, file persistence and optimistic version check, sequentially exercised."""
import json
import sqlite3
import tempfile
from pathlib import Path


def main():
    with tempfile.TemporaryDirectory() as temp:
        path = Path(temp) / "sample.db"
        db = sqlite3.connect(path, isolation_level=None)
        db.execute("PRAGMA foreign_keys=ON")
        assert db.execute("PRAGMA foreign_keys").fetchone()[0] == 1
        db.executescript("""
          CREATE TABLE input(id INTEGER PRIMARY KEY, version INTEGER NOT NULL);
          CREATE TABLE plan(id INTEGER PRIMARY KEY, input_id INTEGER REFERENCES input(id));
          INSERT INTO input VALUES(1,1);
        """)
        db.execute("BEGIN IMMEDIATE")
        try:
            db.execute("INSERT INTO plan VALUES(1,1)")
            db.execute("INSERT INTO plan VALUES(2,999)")
            raise AssertionError("foreign key accepted")
        except sqlite3.IntegrityError:
            db.execute("ROLLBACK")
        assert db.execute("SELECT COUNT(*) FROM plan").fetchone()[0] == 0
        first = db.execute("UPDATE input SET version=2 WHERE id=1 AND version=1").rowcount
        stale = db.execute("UPDATE input SET version=3 WHERE id=1 AND version=1").rowcount
        assert (first, stale) == (1, 0)
        db.close()
        reopened = sqlite3.connect(path)
        try:
            assert reopened.execute("SELECT version FROM input WHERE id=1").fetchone()[0] == 2
        finally:
            reopened.close()
    print(json.dumps({"rollback_rows": 0, "accepted_update": first,
                      "stale_update": stale, "reopened_version": 2,
                      "simultaneous_writers_tested": False}))


if __name__ == "__main__":
    main()

"""Request deduplication and fenced publication inside one SQLite transaction."""
import json
import sqlite3


def main():
    db = sqlite3.connect(':memory:', isolation_level=None)
    db.executescript('''CREATE TABLE jobs(id INTEGER PRIMARY KEY, owner TEXT, key TEXT,
        body TEXT, epoch INTEGER, UNIQUE(owner,key));
        CREATE TABLE current(id INTEGER PRIMARY KEY, version INTEGER, epoch INTEGER, result TEXT, status TEXT);
        INSERT INTO current VALUES(1,2,3,'old-success','RUNNING');''')

    def accept(key, body):
        db.execute('INSERT OR IGNORE INTO jobs(owner,key,body,epoch) VALUES(?,?,?,?)', ('admin', key, body, 3))
        row = db.execute('SELECT id,body FROM jobs WHERE owner=? AND key=?', ('admin', key)).fetchone()
        if row[1] != body:
            raise ValueError('same key with different request')
        return row[0]

    def publish(version, epoch, result):
        db.execute('BEGIN IMMEDIATE')
        try:
            changed = db.execute("UPDATE current SET result=?,status='PUBLISHED' WHERE id=1 AND version=? AND epoch=? AND status='RUNNING'",
                                 (result, version, epoch)).rowcount
            db.execute('COMMIT')
            return changed
        except BaseException:
            db.execute('ROLLBACK')
            raise

    assert accept('K1', 'v2') == accept('K1', 'v2')
    try:
        accept('K1', 'v1')
        raise AssertionError('conflict accepted')
    except ValueError:
        pass
    assert publish(1, 3, 'stale-input') == 0
    assert publish(2, 2, 'stale-worker') == 0
    assert db.execute('SELECT result FROM current').fetchone()[0] == 'old-success'
    assert publish(2, 3, 'validated-candidate') == 1
    assert publish(2, 3, 'second-publication') == 0
    assert db.execute('SELECT result FROM current').fetchone()[0] == 'validated-candidate'
    assert db.execute('SELECT COUNT(*) FROM jobs').fetchone()[0] == 1
    db.close()
    print(json.dumps({'job_rows': 1, 'stale_input_rows': 0, 'stale_worker_rows': 0,
                      'accepted_rows': 1, 'repeat_publication_rows': 0, 'external_effects_tested': False}))


if __name__ == '__main__':
    main()

10-1. 먼저 정상 흐름을 느리게 따라간다

이번 사례의 날짜는 2026년 7월 20일입니다. E1·E2·E3는 근무하고 E4는 휴무입니다. E1·E2는 S1, E3는 S2에서 탑승하고 버스 정원은 2명입니다. 근무는 09:00부터 18:00까지이며, 설명용 규칙은 출근 08:40까지 사업장 도착, 퇴근 18:10 이후 사업장 출발입니다. 이 값들은 개념을 배우기 위한 가정입니다.

S1에서 사업장 ICN까지 20분, S2에서는 10분이 걸린다고 두면 출근 버스는 각각 08:20과 08:30에 출발해 08:40에 도착할 수 있습니다. 퇴근은 방향이 바뀝니다. ICN에서 S1은 25분, S2는 15분이므로 18:10에 출발하면 각각 18:35와 18:25에 도착합니다. 같은 길도 방향별 시간이 같다고 단정하지 않습니다.

설명용 서비스는 적용된 입력을 고정하고 작업을 접수합니다. Worker가 작업을 맡아 후보를 만들면 Validator가 근무자별 출근·퇴근 각 1회, 휴무자 0회, 정원, 시간을 확인합니다. 근무자 세 명이 두 방향으로 한 번씩 배정되므로 사람·방향 배정 수는 총 6개입니다. 통과한 동일 후보만 확정 조건을 거쳐 공식 결과가 됩니다. 여기까지가 우리가 기대하는 정상 순서입니다.

실제 교재 보충 예제들은 이 전체 서비스를 구현한 프로그램이 아닙니다. 지금은 이 순서를 사고의 지도처럼 사용합니다. 장애를 설명할 때는 먼저 자신이 구현한 지도에서 요청, 입력, 후보, 검사, DB 확정의 위치를 찾아야 합니다.

10-2. 시간제한에는 서로 다른 두 질문이 있다

시간제한 또는 timeout은 정한 시간 안에 어떤 일을 끝내거나 기다리겠다는 제한입니다. 그런데 “무엇의 시간인가”가 빠지면 뜻이 모호해집니다. 브라우저가 응답을 5초 기다리는 제한과, 계산기가 탐색을 30초 수행하는 제한은 다른 사건입니다.

요청 대기 시간제한에 걸렸다는 것은 기다리던 쪽이 제때 답을 얻지 못했다는 뜻입니다. 요청이 도착하지 않았을 수도 있지만, 서버가 일을 끝내고 응답만 전달하지 못했을 수도 있습니다. 별도 Worker가 계산 중일 수도 있습니다. 화면에 오류가 보였다는 사실만으로 계산 실패나 DB 롤백을 단정하지 말고, 이미 받은 작업 번호가 있다면 그 번호로 상태를 다시 조회해야 합니다.

계산 시간제한은 탐색이나 최적화에 허용한 시간이 끝난 경우입니다. 이때 후보가 전혀 없을 수도 있고, 규칙을 지키는 후보는 있지만 최적이라는 증거가 없을 수도 있습니다. “유효한 후보를 검사한 뒤 제한 종료 결과로 제공할지”는 서비스 계약에서 정해야 합니다. 최적성을 증명하지 못한 후보를 최적해로 표시해서는 안 됩니다.

부분 후보에 E1·E2만 있고 E3가 빠져 있다면 계산이 오래 걸렸다는 사정으로 정상 계획이 되지는 않습니다. 이 책의 기본 설명은 전체 제약을 통과하지 못한 후보를 새 공식 결과로 공개하지 않는 것입니다. 계산 제한의 종료 상태, 후보 유무, 독립 검사 결과를 각각 기록해야 이유를 설명할 수 있습니다.

10-3. Worker가 죽으면 누가 그 사실을 발견하는가

Worker는 일을 맡아 계산하는 역할입니다. 별도 프로세스로 실행했더라도 언제나 끝까지 살아 있다는 보장은 없습니다. 작업을 실행 중으로 바꾼 직후 종료됐다면 DB에는 실행 중이라는 기록만 남을 수 있습니다. 프로그램이 사라졌는데 상태가 자동으로 실패로 바뀐다고 가정하면 복구 설계의 빈칸을 놓치게 됩니다.

하트비트는 Worker가 살아서 진행 중임을 주기적으로 남기는 신호입니다. 임대는 일을 맡을 권한에 유효 시간을 두는 방식입니다. 정한 시간이 지나도록 갱신이 없으면 다른 실행이 회수할 수 있게 설계합니다. 하지만 신호가 늦다는 사실만으로 Worker의 죽음을 완벽하게 알 수는 없습니다. 잠시 느려진 Worker가 나중에 돌아올 가능성도 고려해야 합니다.

그래서 회수와 함께 앞 장의 시도 번호가 필요합니다. 새 Worker에게 다시 맡길 때 유효한 시도를 바꾸고, 옛 Worker가 돌아와도 확정하지 못하게 합니다. “실행 중이 오래됐으니 다시 실행한다”만 구현하면 두 실행이 결과를 놓고 경쟁할 수 있습니다. 복구는 다시 시작하는 기능과 오래된 실행을 막는 기능을 함께 다루어야 합니다.

보충 예제 ch10.py에는 이런 자동 회수가 없습니다. 따라서 그 예제를 기준으로 가장 분명한 취약점을 말한다면 “선점 후 Worker가 죽으면 실행 중 상태가 남고 자동 복구되지 않는다”입니다. 설명용 하트비트 설계를 배웠다는 이유로 현재 코드에도 구현되어 있다고 말하면 안 됩니다.

10-4. 검증 실패는 계산 실패와 다른 기록을 남긴다

Creator가 후보를 끝까지 만들었어도 Validator가 E3의 누락을 발견할 수 있습니다. 이 경우 프로그램은 계산을 수행했고 후보도 있지만, 업무 규칙을 만족하지 못한 것입니다. 실패 이유를 남기려면 “검증 실패”와 “계산 중 예외”를 구분하는 편이 좋습니다. 진단은 무엇이 잘못됐는지 조사할 수 있게 남기는 정보입니다.

예를 들어 “2026-07-20, E3, OUT, 기대 1회, 실제 0회”라는 진단은 단순한 실패 문자열보다 유용합니다. 사용자는 다시 시도할지 판단할 수 있고, 개발자는 생성기와 검사기의 기준이 맞는지 비교할 수 있습니다. 개인 정보가 포함된 입력 전체를 무조건 로그에 넣는 대신 필요한 식별자와 위반 규칙을 정해 남깁니다.

검증에 실패한 후보를 조사 목적으로 보관할 수는 있습니다. 그러나 임시 후보와 공개 결과는 구별되어야 합니다. 이전에 성공한 공식 결과 F3가 있다면 새 후보의 실패 때문에 F3를 덮어쓰지 않습니다. 첫 실행이라 이전 성공 결과가 없다면 “이전 결과”를 보여 줄 수도 없으므로, 사용 가능한 결과 없음과 실패 원인을 안내해야 합니다.

또한 이전 결과를 남긴다는 것과 현재 입력에도 맞는 결과라고 표시한다는 것은 다릅니다. 입력이 바뀐 뒤 남은 과거 결과에는 입력 버전과 생성 시각을 붙여야 합니다. 사용자가 오래된 계획을 최신 계획으로 오해하면 저장을 보존한 의도와 사용자 안전이 어긋납니다.

10-7. 취약한 지점은 중단 위치와 증거로 설명한다

“Worker가 취약합니다”라는 말만으로는 개선할 곳을 알기 어렵습니다. “선점 직후 종료되면 상태가 실행 중으로 남는데 회수 담당이 없어 사용자가 계속 기다립니다”처럼 위치, 남은 기록, 사용자 영향을 함께 말해야 합니다. 그러면 개선 방향도 임대·감시·수동 재처리 정책처럼 구체화됩니다.

복구 기능이 있어도 최신 실행만 확정하는 조건이 없다면 재실행 뒤 옛 결과가 덮어쓸 수 있습니다. 검사기가 생성기와 같은 잘못된 계산을 그대로 재사용한다면 둘 다 통과하는 오류가 남을 수 있습니다. 가장 취약한 지점은 실제 코드에서 어떤 보장이 빠졌는지에 따라 달라집니다. 유행하는 기술 이름으로 미리 정하지 마세요.

장애 시험은 중단 지점과 기대 상태를 정한 뒤 수행해야 설명이 됩니다. “프로세스를 종료해 봤다”보다 “선점 직후 종료했고, 새 연결로 실행 중 잔존을 확인했다. 회수는 미구현이다”가 더 정확합니다. 다음 장에서는 다른 사람이 이 설명을 따라 확인할 수 있게 증거를 묶는 방법을 배웁니다.

"""A timed-out waiter does not stop the running thread; a fence blocks publication."""
from concurrent.futures import ThreadPoolExecutor, TimeoutError
import json
import threading


def main():
    started, release, finished = threading.Event(), threading.Event(), threading.Event()
    lock = threading.Lock()
    state = {'epoch': 1, 'status': 'RUNNING', 'final': 'old-success'}

    def work(epoch):
        started.set()
        if not release.wait(5):
            raise RuntimeError('test release missing')
        with lock:
            if state['epoch'] == epoch and state['status'] == 'RUNNING':
                state.update(status='SUCCEEDED', final='new-plan')
        finished.set()
        return 'calculated'

    with ThreadPoolExecutor(max_workers=1) as pool:
        future = pool.submit(work, 1)
        assert started.wait(5)
        try:
            future.result(timeout=.01)
            raise AssertionError('expected timeout')
        except TimeoutError:
            pass
        assert not future.cancel()  # already running
        with lock:
            state.update(epoch=2, status='CANCELLED')
        release.set()
        assert future.result(timeout=5) == 'calculated'
        assert finished.is_set()
        assert state == {'epoch': 2, 'status': 'CANCELLED', 'final': 'old-success'}
    print(json.dumps({'waiter_timed_out': True, 'calculation_finished': True,
                      'cancelled_publication_blocked': True, 'previous_final_preserved': True}))


if __name__ == '__main__':
    main()

11-1. 주장을 먼저 작게 나누면 필요한 증거가 보인다

“이 서비스는 안전합니다”는 범위가 너무 넓습니다. 잘못된 입력을 거절한다는 뜻인지, 중복 배정을 막는다는 뜻인지, Worker가 죽어도 복구된다는 뜻인지 알 수 없습니다. 먼저 관찰할 수 있는 작은 문장으로 바꿉니다. 예를 들어 “없는 직원 ID를 참조하는 데이터를 적용하면 오류가 나고 이전 입력이 바뀌지 않는다”는 어떤 입력과 전후 상태를 볼지 정할 수 있는 주장입니다.

증거는 그 주장을 뒷받침하는 관찰과 기록입니다. 코드가 존재한다는 것, 테스트가 실행됐다는 것, 기대 결과와 같았다는 것은 서로 다른 단계입니다. 파일에서 검사 함수를 찾았더라도 실제 요청 경로가 그 함수를 호출하지 않을 수 있습니다. 테스트 명령을 적었어도 실행하지 않았다면 결과의 근거는 아닙니다.

확인할 것은 네 묶음입니다. 어떤 코드와 입력을 썼는가, 어떤 명령을 실행했는가, 무엇을 기대했는가, 실제로 무엇을 관찰했는가? 여기에 확인하지 않은 범위를 붙이면 설명의 경계가 분명해집니다. “정상 입력 1개와 잘못된 참조 1개를 검사했지만 날짜 오류와 실제 DB 장애는 확인하지 않았다”처럼 좁게 말해도 충분히 유용합니다.

서로 다른 증거를 하나로 합쳐 더 큰 성공으로 만들지 않는 것도 중요합니다. 스레드 실험, DB 실험, 계획 검사기 실험이 각각 통과했다고 해서 세 개를 연결한 전체 서버가 통과한 것은 아닙니다. 연결 자체에도 입력 전달 오류나 호출 누락이 있을 수 있습니다.

11-2. 파일을 볼 때는 이름보다 호출과 조건을 본다

파일 이름이 validator.py라고 해서 올바른 검증기가 되는 것은 아닙니다. 그 안에서 무엇을 입력으로 받고, 어떤 규칙을 확인하고, 위반을 어떻게 반환하는지 읽어야 합니다. 생성기가 남긴 “성공” 값을 그대로 읽어 승인한다면 생성 결과를 독립적으로 검사했다고 보기 어렵습니다.

호출 경로는 한 동작이 어떤 함수들을 거쳐 진행되는지 나타내는 순서입니다. “적용” 버튼에서 시작해 서버의 요청 처리, 데이터 검증 함수, 저장 함수로 이어지는 길을 따라갑니다. 검사 함수 자체가 옳더라도 저장 함수가 다른 길에서 무조건 실행된다면 적용 전 검사가 빠질 수 있습니다.

이 책에서 실제로 열어 볼 파일은 examples/ch04.py의 validate와 apply, examples/ch13.py의 check입니다. ch04.py에서는 apply가 같은 고정본을 검증한 뒤 해시를 비교하고 메모리 상태를 바꾸는지 확인합니다. ch13.py에서는 후보의 사람·방향별 횟수를 기대 횟수와 비교하고 정원과 시간 조건을 확인하는지 읽습니다.

이 파일들에는 실제 웹서비스의 데이터셋 선택 화면이나 전체 배정 생성기가 없습니다. 개인 프로젝트를 점검할 때 찾을 파일 이름은 달라질 수 있습니다. dataset_service.py, worker.py, plan_repository.py 같은 이름은 역할을 설명하기 위한 예시일 뿐, 이 교재가 제공하는 실제 서비스 파일이 아닙니다. 내 저장소에서 실제 경로와 함수 이름으로 바꾸어 적어야 합니다.

11-3. 제3자가 실행할 명령에는 시작 위치와 기대 결과가 필요하다

명령 한 줄만 보내면 상대는 어디에서 실행해야 하는지 모를 수 있습니다. 보충 자료의 폴더를 내려받았다면 examples 폴더가 보이는 위치에서 다음 명령을 실행합니다. Python 3.11 이상을 기준으로 하며 이 작은 예제들은 외부 패키지를 요구하지 않습니다. 파일 하나만 받았다면 그 파일이 있는 폴더에서 파일 이름만 지정합니다.

python examples/ch04.py
python examples/ch13.py

ch04.py는 일곱 종류의 축소 가상 CSV를 사용합니다. 출력에서 잘못된 직원 참조를 거절했는지, 검증 후 내용이 바뀐 입력을 거절했는지, 이전 메모리 상태를 보존했는지 봅니다. ch13.py는 별도의 두 직원·야간 근무 사례입니다. 이 책 본문의 세 근무자·주간 사례를 실행한 결과가 아닙니다. 출력은 정상 후보 통과와 누락·중복·휴무자·시간·정원 등을 일부러 바꾼 아홉 가지 변이 감지를 보여 줍니다.

종료 코드는 실행한 프로그램이 어떻게 끝났는지 알리는 숫자입니다. 보통 0은 정상 종료를 뜻하지만, 무엇을 실제로 검사했는지는 코드 안의 조건과 출력에서 읽어야 합니다. 아무것도 검사하지 않는 프로그램도 0으로 끝날 수 있기 때문입니다. 기대한 거절 조건과 전후 상태가 코드에 포함되어 있는지 함께 확인하세요.

Windows PowerShell에서는 명령 직후 $LASTEXITCODE로 직전 프로그램의 종료 코드를 볼 수 있습니다. 이 값이 0이어도 화면에서 출력 일부를 복사하는 것만으로 전체 실행 맥락이 보존되지는 않습니다. 실행 시각, Python 버전, 코드 버전, 입력과 설정을 기록해 다른 사람이 같은 조건을 준비할 수 있게 합니다.

11-4. 상태는 결과 화면뿐 아니라 저장 위치를 나누어 확인한다

오류 메시지를 봤다는 것과 이전 데이터가 보존됐다는 것은 같은 관찰이 아닙니다. 잘못된 데이터를 적용하기 전 입력 버전 v7과 공식 결과 F3를 읽어 둡니다. 실패를 일으킨 뒤 다시 읽어 v7과 F3가 그대로인지 비교해야 보존을 확인할 수 있습니다. 실제 DB를 쓰는 서비스라면 새 연결로 읽는 확인도 유용합니다. 실행 중인 객체의 오래된 값을 보고 DB가 보존됐다고 착각하는 일을 줄일 수 있습니다.

작업과 결과의 상태도 나누어 봅니다. 작업 J1이 검증 실패라고 기록됐어도 공식 결과 F3는 성공 이력으로 남을 수 있습니다. “현재 작업 실패”와 “사용 가능한 이전 결과 존재”는 함께 성립합니다. 후보 C1이 보관돼 있다면 왜 공개되지 않았는지 위반 보고서와 연결되어야 합니다.

11-5. 실행 기록과 파일 해시를 함께 읽는다

교재의 verification.json은 보충 예제의 실행 기록을 모은 자료입니다. 명령, 실행 환경, 종료 코드, 표준 출력, 코드 해시를 대조해 읽습니다. 표준 출력은 프로그램이 일반 결과를 내보내는 통로이고, 표준 오류는 오류나 진단을 내보내는 통로입니다. 어느 한쪽이 비어 있다고 모든 장애가 없었다고 결론내릴 수는 없습니다.

SHA-256은 파일 내용의 지문을 계산하는 한 방식입니다. 내려받은 코드의 해시가 실행 기록의 코드 해시와 다르면, 그 기록이 지금 파일을 실행한 결과인지 다시 확인해야 합니다. 해시가 맞더라도 입력과 환경이 달라지면 결과가 달라질 수 있으므로 이것 하나가 모든 재현 조건을 대신하지는 않습니다.

ch04.py의 파일 지문을 계산하는 실제 명령
python -c "import hashlib; from pathlib import Path; print(hashlib.sha256(Path('examples/ch04.py').read_bytes()).hexdigest())"

examples 폴더가 보이는 위치에서 실행합니다. 출력값을 해당 예제의 실행 기록에 있는 코드 SHA-256과 비교합니다. 이것은 파일 내용의 동일성 확인이며 코드가 옳다는 검사와는 별개입니다.

특히 기록의 확인 범위를 읽으세요. ch10.py의 정상 완료 기록에는 장애 후 자동 회수를 확인하지 않았다는 표시가 있습니다. ch13.py는 실제 방향별 경로 이동시간을 계산하지 않습니다. ch14.py는 근거 없는 완료 주장을 걸러 내는 교육용 목록 실험입니다. 그 안에 “통과”라고 적힌 자료도 실제 운영 서비스의 인증서가 아닙니다.

독립적인 사람이 다시 실행해 같은 관찰을 얻는 일은 신뢰를 높입니다. 다만 같은 입력 몇 개가 통과했다는 사실이 가능한 모든 입력의 정확성을 증명하지는 않습니다. 무엇을 바꾸어도 지켜져야 할 규칙을 찾고 그 규칙을 깨는 예를 더해 가는 방식으로 확인 범위를 넓힙니다.

11-6. 반례를 만들어 검사가 실제로 거절하는지 본다

정상 입력만 넣으면 검사기가 늘 “통과”라고 답해도 성공처럼 보입니다. 그래서 반례, 즉 주장이 성립하지 않는 상황을 의도적으로 만듭니다. 정상 후보에서 E3의 퇴근 배정을 지우고, E1을 한 번 더 넣고, 휴무자 E4를 추가하고, 정원을 줄여 봅니다. 위반이 생겼을 때 예상한 이유로 거절하는지 확인해야 합니다.

이처럼 자료의 한 부분을 의도적으로 바꾼 것을 여기서는 변이라고 부릅니다. 한 번에 여러 부분을 바꾸면 어느 규칙이 실패를 잡았는지 알기 어려우므로 처음에는 한 조건씩 바꿉니다. 잘못된 후보가 거절됐어도 이유가 예상과 다르면 다른 결함에 가려졌을 가능성을 살펴봅니다.

오류 입력, 오류 후보, 장애는 확인 대상이 다릅니다. 없는 직원 ID를 넣는 것은 입력 검증 시험이고, E3가 빠진 계획을 넣는 것은 결과 검증 시험입니다. Worker를 선점 직후 종료하는 것은 복구 시험입니다. 입력 시험을 많이 했다는 이유로 Worker 장애를 확인했다고 말하지 않습니다.

성능과 품질도 별도입니다. 빨리 끝났다고 근무자 전원이 배정됐다는 보장은 없습니다. 버스 수가 줄었더라도 한 사람이 빠져 줄어든 것이라면 개선으로 셀 수 없습니다. 동일한 입력과 조건에서 먼저 유효성을 확인하고, 그다음 차량 수·소요 시간·계산 시간 등의 지표를 비교합니다. 작은 교재 예제를 실제 규모의 성능 측정으로 확대하지 마세요.

11-7. 구현 설명과 취약점 보고에 쓸 수 있는 양식

다음 양식은 자신의 프로젝트에 대입하기 위한 예시입니다. 빈칸을 실제로 확인한 내용으로 채우고, 해당하지 않는 항목은 이유를 적습니다. 특히 완료 여부를 “구현함”, “다른 계층이 담당”, “미구현”, “실행 미확인”으로 나누면 함수의 존재와 실제 보장을 혼동하는 일을 줄일 수 있습니다.

"""Independent miniature plan checker plus deliberate mutations; not real CSV schema."""
from collections import Counter
from datetime import datetime, timedelta
import json


def check(plan, capacity=45):
    expected = Counter((emp, direction) for emp in ('E1', 'E2') for direction in ('IN', 'OUT'))
    actual = Counter((emp, trip['direction']) for trip in plan for emp in trip['people'])
    errors = []
    if actual != expected:
        errors.append('coverage')
    start = datetime.fromisoformat('2026-07-21T00:10')
    end = datetime.fromisoformat('2026-07-21T08:10')
    for trip in plan:
        if len(trip['people']) > capacity:
            errors.append('capacity')
        moment = datetime.fromisoformat(trip['time'])
        if trip['direction'] == 'IN' and not start - timedelta(hours=12) <= moment <= start - timedelta(minutes=20):
            errors.append('arrival')
        if trip['direction'] == 'OUT' and not end + timedelta(minutes=10) <= moment <= end + timedelta(hours=12):
            errors.append('departure')
    return sorted(set(errors))


def main():
    good = [{'direction': 'IN', 'people': ['E1', 'E2'], 'time': '2026-07-20T23:50'},
            {'direction': 'OUT', 'people': ['E1', 'E2'], 'time': '2026-07-21T08:20'}]
    assert not check(good)
    missing = [dict(trip, people=list(trip['people'])) for trip in good]
    missing[0]['people'] = ['E1']
    assert check(missing) == ['coverage']
    late = [dict(trip) for trip in good]
    late[0]['time'] = '2026-07-21T00:00'
    assert check(late) == ['arrival']
    duplicate = [dict(trip, people=list(trip['people'])) for trip in good]
    duplicate[0]['people'].append('E1')
    assert check(duplicate) == ['coverage']
    off = [dict(trip, people=list(trip['people'])) for trip in good]
    off[0]['people'].append('OFF1')
    assert check(off) == ['coverage']
    early = [dict(trip) for trip in good]
    early[1]['time'] = '2026-07-21T08:19'
    assert check(early) == ['departure']
    too_early = [dict(trip) for trip in good]
    too_early[0]['time'] = '2026-07-20T12:09'
    assert check(too_early) == ['arrival']
    too_late = [dict(trip) for trip in good]
    too_late[1]['time'] = '2026-07-21T20:11'
    assert check(too_late) == ['departure']
    # Candidate metadata cannot override the independently supplied capacity.
    forged = [dict(trip, capacity=999) for trip in good]
    assert check(forged, capacity=1) == ['capacity']
    assert check(good, capacity=1) == ['capacity']

                      'midnight_checked': True, 'route_travel_times_checked': False}))

    main()

Creator는 제약을 만족하는 후보를 찾고, Validator는 주어진 후보를 입력과 규칙에 대조합니다. 역할 분리는 “무엇을 책임지는가”의 문제입니다. 병렬 처리는 “어떤 일을 동시에 실행할 수 있는가”의 문제입니다. 프로세스 분리는 “어떤 실행·메모리 경계에서 동작하는가”의 문제입니다. 서로 연결될 수 있지만 같은 말은 아닙니다.

설명용 설계를 기준으로 한 답변 예시

“같은 완성 후보의 최종 검증은 생성이 끝난 뒤 수행합니다. 입력 파일별 기본 검사처럼 독립적인 일은 겹쳐 처리할 수 있지만, 교차 참조 검사나 합친 계획의 전역 검사는 필요한 자료가 모인 뒤 해야 합니다. 부분 계획이 각각 정원을 지켜도 합칠 때 한 직원이 중복될 수 있기 때문입니다.”

“비동기는 호출한 쪽이 완료까지 붙잡혀 기다리지 않도록 흐름을 구성하는 방식이고, 별도 프로세스는 실행 인스턴스와 일반 메모리의 경계를 나누는 방식입니다. async 함수 선언만으로 별도 프로세스가 생기지 않습니다. 실제 프로세스 시작 코드, PID, 통신 경로와 저장 상태를 보아야 합니다.”

독립 검증에서는 생성기가 잘했다고 말한 값만 믿지 않습니다. 원본 근무표에서 날짜·방향별 대상과 기대 횟수를 만들고 후보의 횟수와 비교합니다. E1·E2·E3는 출근·퇴근 각 1회, E4는 0회인지 보고, 정원과 실제 시간 조건도 확인합니다. 집합에 세 사람이 모두 있다고 끝내지 말고 한 사람이 두 번 들어간 경우를 검사해야 합니다.

교재의 ch06.py는 의존 관계와 지역 성공·전역 실패를 설명하는 작은 실험이며 실제 병렬 실행기는 아닙니다. ch09.py는 같은 프로세스의 코루틴들이 대기를 겹치는 순서를 확인합니다. ch10.py는 별도 프로세스 두 개의 선점과 정상 완료를 확인하지만 결과는 교육용 문자열이고 생성기·검사기를 연결하지 않습니다. 이 세 사실을 합쳐 “병렬 배정 서버가 완성됐다”고 말하지 않습니다.

추가 질문으로 답변을 다듬기

부분 검사가 통과한 뒤 후보를 수정하면? 두 후보 작업이 같은 객체를 바꾸면? CPU 계산을 async 함수 안에서 오래 수행하면? 프로세스 둘이 같은 DB 파일을 바꾸면? “역할·의존 순서·실행 자원·상태 공유” 중 어느 축의 문제인지 먼저 분류하면 답을 정리하기 쉽습니다.

12-4. 질문 3: 정상 처리와 실패 뒤 사용자의 결과는 무엇인가

질문: 근무자 전원이 정상 배정되는 흐름을 설명해 주세요. 생성 도중 시간제한, Worker 사망, 검증 실패가 발생하면 사용자에게 어떤 결과가 남나요? 이 설계의 가장 취약한 지점은 어디인가요?

가상 서비스의 흐름을 설명하는 답변 예시

“검증해 적용한 입력의 고정본과 설정으로 작업을 접수합니다. Worker는 작업을 선점해 후보를 만들고, Validator가 날짜·출퇴근별 누락·중복·휴무자·정원·시간을 확인합니다. 본문 사례는 세 근무자가 두 방향으로 한 번씩 배정되어 총 6개의 사람·방향 배정이 있어야 합니다. 통과한 동일 후보만 입력 버전·시도 번호·작업 상태를 비교한 뒤 공식 결과로 확정합니다.”

“요청을 기다리던 시간이 끝났다면 계산이 멈췄다고 단정하지 않고 작업 번호로 상태와 결과를 조회합니다. 계산 자체가 제한 종료됐다면 유효 후보가 있는지와 독립 검사 결과를 보고 정한 정책에 따라 처리합니다. 불완전 후보를 정상 계획으로 내보내지는 않습니다.”

“Worker가 선점 후 죽으면 회수가 없는 구현에서는 실행 중 상태가 남을 수 있습니다. 검증 실패는 새 후보를 공식 결과로 바꾸지 않고 위반 진단과 작업 실패를 기록하는 설계를 사용합니다. 이전 성공 결과가 있다면 보존하되 입력 버전이 다르면 과거 결과임을 표시합니다. 첫 실행이라면 결과 없음이 남습니다.”

마지막 취약점 답변은 실제 구현에 맞춰 선택해야 합니다. 교재 ch10.py만 기준으로 말하면 선점 후 자동 회수가 없다는 점이 분명한 공백입니다. 실제 프로젝트에 회수가 있다면 임대 만료 뒤 옛 Worker가 확정할 수 있는지, 검증한 후보와 저장한 후보가 같은지, 공식 결과와 성공 상태가 함께 커밋되는지 다음 경계를 봅니다.

개선 방향에는 비용도 붙입니다. 하트비트와 회수 기능은 중단 작업을 발견하고 다시 맡길 수 있게 하지만 느린 작업을 죽은 작업으로 오판할 수 있어 시도 번호와 확정 차단이 필요합니다. 긴 계산을 요청에서 떼면 응답 대기는 줄일 수 있지만 상태 저장·조회·복구 책임은 늘어납니다. 장점만 나열하는 대신 그 선택으로 새로 관리해야 할 일을 말하세요.

추가 질문으로 답변을 다듬기

커밋은 성공했는데 응답만 사라지면? 새 입력 v8을 적용했는데 v7 Worker가 끝나면? 취소를 기록한 뒤 계산이 완료되면? 이전 결과가 아예 없으면? 각 경우에 작업 기록·후보·공식 결과·사용자 표시를 따로 설명해 보세요.

12-5. 부족한 답변을 근거 있는 문장으로 바꾼다

말의 범위를 줄이면 설명이 더 정확해진다
부족한 답변바꿔 말할 방향
비동기라서 프로세스가 따로 돕니다.완료를 기다리는 흐름과 실행 프로세스를 구분하고 실제 시작 코드·PID를 확인합니다.
Creator와 Validator는 무조건 병렬입니다.같은 완성 후보에는 선행 의존이 있고 독립 입력 검사 등만 겹칠 수 있습니다.
일곱 CSV를 읽으므로 검증은 끝났습니다.형식·타입·참조·업무 규칙별 구현과 미구현을 나누어 말합니다.
시간 초과면 작업이 실패한 겁니다.대기 종료인지 계산 제한인지 구분하고 작업·확정 상태를 조회합니다.
DB와 큐가 있으니 죽어도 복구됩니다.선점 후 잔존 상태, 감지·회수 정책, 재시도와 옛 실행 차단 근거를 확인합니다.
테스트가 통과했으니 모두 안전합니다.시험한 입력·변이·장애와 아직 확인하지 않은 경계를 제시합니다.

답변을 짧게 만들기 위해 한계를 빼는 대신, 질문에 필요한 한계를 한 문장으로 붙입니다. “파일 DB 재연결은 확인했지만 프로세스 강제 종료 복구는 확인하지 않았습니다” 정도면 무엇을 믿을 수 있는지 분명해집니다. 모르는 부분을 기술 이름으로 덮는 것보다 확인할 다음 행동을 제시하는 편이 낫습니다.

12-6. 내 구현으로 바꾸어 말하는 연습

실제 프로젝트가 있다면 종이에 화살표 다섯 개를 그립니다. 입력 선택 → 검증·적용 → 생성 → 결과 검증 → 확정입니다. 각 화살표 아래 실제 파일과 함수, 읽는 입력 버전, 바꾸는 상태를 적습니다. 별도 Worker가 없다면 있는 것처럼 그리지 말고 같은 요청 안의 함수 호출로 표시합니다.

그다음 첫 화살표에서 실패했을 때, Worker가 일을 맡자마자 죽었을 때, 검증 직후 확정 전에 입력이 바뀌었을 때를 대입합니다. 관찰한 값은 실선으로, 아직 설계만 한 대응은 점선으로 표시해 보세요. 구현과 가정이 섞인 지점이 눈에 들어올 것입니다.

다른 계층에 맡긴 일도 연결합니다. UI가 선택을 제한해도 서버가 임의 ID 요청을 거절하는지, DB가 참조 제약을 가진다면 그 기능이 활성화됐는지, 생성기가 검사기를 실제로 호출하는지 확인합니다. 위임은 “누군가 해 줄 것이다”가 아니라 “이 경계에서 이 계약으로 연결된다”는 설명이어야 합니다.

마지막으로 명령을 받는 제3자를 생각합니다. 빈 환경에서 시작 위치와 필요한 설정을 알 수 있는가, 정상·오류 사례를 실행할 수 있는가, 기대 상태와 미구현 범위를 읽을 수 있는가를 봅니다. 이 교재의 파일명은 작은 예제를 위한 것이므로 자신의 저장소 이름으로 반드시 바꾸어야 합니다.

12-7. 두 분 설명을 준비하는 방법

먼저 30초 동안 요청부터 공식 결과까지 정상 흐름을 말합니다. 다음 30초에는 Creator·Validator의 역할과 실행 순서, 비동기와 프로세스의 차이를 설명합니다. 그다음 30초에는 하나의 장애를 골라 남는 작업·후보·공식 결과를 말합니다. 마지막 30초에는 실제 파일·명령·상태와 가장 약한 경계, 확인하지 않은 부분을 붙입니다. 이것은 연습을 위한 시간 배분입니다.

녹음해서 들으며 “값은 어디에 남지?”, “누가 호출하지?”, “실패 뒤 무엇이 유지되지?”라는 빈틈을 찾습니다. 한 요청의 흐름을 끝까지 설명해 보고 막히는 장으로 돌아가세요.

자가 점검은 다섯 가지로 마칩니다. 용어를 구분했는가, 흐름의 주체와 순서가 맞는가, 실패 뒤 남는 상태를 말했는가, 실제 근거를 제시했는가, 선택의 비용과 미확인을 밝혔는가? 답변이 막히는 부분이 다음에 읽을 장입니다. 읽음 표시를 모두 채우는 것보다 질문 하나를 내 말로 끝까지 설명할 수 있는지가 학습 목표입니다.

세 질문에 내 말로 답하기

1. 데이터셋 선택·검증·적용에서 구현·위임·미구현을 나누고, 제3자가 확인할 파일·명령·상태를 설명하세요. 실제 프로젝트가 없다면 교재 보충 예제의 범위로 답하세요.

답변 점검

세 동작이 구분되는지, 구체 규칙과 실제 apply 호출이 연결되는지, 전후 상태를 확인하는지 봅니다. ch04.py가 모든 일곱 파일의 업무 규칙이나 DB 원자성까지 구현했다고 확대하지 않습니다. 결과 검증은 ch13.py의 별도 범위로 설명합니다.

2. Creator·Validator의 역할, 같은 후보의 의존 순서, 병렬 가능한 작업, 비동기와 별도 프로세스의 차이를 하나의 흐름으로 설명하세요.

답변 점검

역할 분리·실행 순서·실행 자원을 섞지 않았는지 확인합니다. 같은 후보의 최종 검증은 생성 완료 뒤이며 부분 검사 후에는 전역 검사가 필요할 수 있습니다. 실제 프로세스 여부는 시작 코드·PID·통신과 저장 경로의 근거로 말합니다.

3. 정상 전원 배정과 시간제한·Worker 사망·검증 실패 뒤의 사용자 결과를 설명하고 가장 취약한 경계와 근거를 제시하세요.

답변 점검

대기 시간제한과 계산 제한을 구분하고, 실행 중 잔존·회수·옛 실행 차단을 살펴야 합니다. 이전 성공 결과가 있는지와 현재 입력 버전도 확인합니다. 취약점은 실제 구현 근거로 고르고, 교재가 실제 제출 서비스의 장애 복구를 인증한 것처럼 답하지 않습니다.
