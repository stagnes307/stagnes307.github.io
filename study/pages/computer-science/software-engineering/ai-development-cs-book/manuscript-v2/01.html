“별도 프로세스로 비동기 처리했습니다”라는 문장이 어렵다면, 먼저 컴퓨터가 무엇을 실행하고 어디에 값을 적는지부터 보면 됩니다. 이 장에서는 코드 한 줄에서 시작해 프로그램·프로세스·스레드·메모리를 차례로 연결합니다. 마지막에는 같은 이름의 진행률 변수가 왜 서로 다른 값을 가질 수 있는지 설명할 수 있게 됩니다.

1-1. 컴퓨터는 명령을 실행하고 값을 바꾼다

통근버스 배정을 종이에 한다고 생각해 봅시다. 담당자는 근무자 명단을 읽고, 버스에 이름을 적고, 정원을 넘었는지 확인합니다. 컴퓨터에도 처리할 재료와 처리 순서가 필요합니다. 데이터는 직원 번호, 출근 시각, 버스 정원처럼 프로그램이 다루는 값입니다. 명령은 값을 읽기, 더하기, 비교하기, 저장하기처럼 수행할 일을 표현합니다. 코드는 이런 명령을 사람이 정한 프로그래밍 언어로 적은 것입니다.

컴퓨터가 문장의 업무 의미를 스스로 이해한다고 생각하면 오류를 찾기 어렵습니다. 직원 세 명을 버스 두 대에 적었다는 사실만으로 누락과 중복이 없는지는 알 수 없습니다. 누락을 찾을 명령과 중복을 찾을 명령을 별도로 적어야 합니다. “계산이 끝났다”와 “업무 규칙을 지켰다”는 그래서 다른 주장입니다. 뒤에서 생성기와 검사기를 나누는 이유도 이 차이에서 출발합니다.

이 책의 공통 예시는 2026년 7월 20일의 가상 배정입니다. E1·E2·E3은 근무하고 E4는 휴무입니다. E1·E2는 S1 정류장, E3은 S2 정류장에서 타며 버스 정원은 두 명입니다. E1 같은 표시는 사람을 구별하는 식별자입니다. 이름이 같은 사람이 있어도 식별자는 서로 달라야 대상을 정확히 셀 수 있습니다. 이 숫자와 시각은 학습을 위한 가정이며 실제 서비스 요구를 뜻하지 않습니다.

명령은 실행한 순서에 영향을 받습니다. “정원이 넘는지 확인한 뒤 배정”과 “모두 배정한 뒤 정원 확인”은 중간에 남는 값이 다릅니다. 두 순서가 같은 최종 결과를 만들 수도 있지만, 중간에 프로그램이 끝나거나 오류가 생기면 차이가 드러납니다. 코드를 이해한다는 것은 단어의 뜻뿐 아니라 값이 언제 생기고 언제 바뀌는지 따라가는 일입니다.

1-2. 변수는 값을 가리키는 이름, 함수는 다시 부를 수 있는 처리다

변수는 프로그램이 값을 찾을 때 쓰는 이름입니다. 다음 Python 코드는 capacity라는 이름으로 정원 2를 사용하고, assigned라는 이름으로 배정 인원 0을 사용합니다. =는 여기서 수학의 “두 식이 같다”가 아니라 오른쪽 값을 왼쪽 이름으로 사용하게 하는 대입입니다. 그다음 줄에서는 현재 배정 인원에 1을 더해 새 값으로 대입합니다.

capacity = 2
assigned = 0
assigned = assigned + 1
print(assigned)

위 코드를 순서대로 읽으면 assigned는 0에서 1로 바뀌고, print는 그 값을 화면에 표시합니다. 화면에 1을 출력하는 것과 파일에 1을 저장하는 것은 다른 일입니다. 다음 실행에서도 1을 읽고 싶다면 저장과 불러오기에 해당하는 명령이 필요합니다. 변수 자체가 과거 실행의 값을 기억해 주지는 않습니다.

조건문은 조건에 따라 다른 명령을 실행합니다. if assigned < capacity:는 배정 인원이 정원보다 작을 때만 아래의 일을 하라는 뜻입니다. 반복문은 명단의 각 직원을 차례로 처리하는 식으로 같은 구조를 반복합니다. 함수는 이름을 붙여 다시 사용할 수 있게 묶은 처리입니다. 함수를 정의하는 일과 그 함수를 호출해 실행하는 일은 구분해야 합니다.

def has_seat(assigned, capacity):
    return assigned < capacity

available = has_seat(1, 2)

has_seat는 빈자리가 있는지 묻는 함수입니다. 괄호 안의 1과 2는 함수에 전달하는 입력값이고, return 뒤의 비교 결과는 함수를 부른 쪽에 돌려주는 반환값입니다. 이 호출의 결과는 참입니다. 그러나 이 함수는 사람을 실제로 배정하지도, 두 요청이 동시에 마지막 자리를 차지하는 문제를 막지도 않습니다. 이름보다 함수 안에서 실행하는 명령을 확인해야 합니다.

1-3. 프로그램 파일과 실행 중 메모리는 다르다

프로그램은 컴퓨터가 실행할 수 있도록 준비한 명령과 데이터의 묶음입니다. plan.py라는 파일에 코드를 저장했다면 그 파일은 프로그램의 일부입니다. 이 파일명은 설명을 위한 예시이며 교재의 실제 내려받기 파일을 가리키지 않습니다. 파일이 폴더에 있다는 사실은 현재 배정 계산이 실행 중이라는 뜻이 아닙니다. 종이에 조리법이 있다고 지금 음식이 만들어지고 있지는 않은 것과 같습니다.

메모리는 실행 중 필요한 명령과 값을 올려 두는 작업 공간입니다. 저장장치는 파일을 보관하는 SSD 같은 장치입니다. 종이를 보관하는 서랍과 작업 중 펼쳐 놓는 책상을 구분하면 이해하기 쉽습니다. 다만 실제 컴퓨터는 운영체제가 여러 방법으로 저장장치와 메모리를 함께 관리하므로, 이 비유를 물리 구조의 완전한 설명으로 외우지는 마세요.

운영체제는 Windows나 Linux처럼 프로그램 실행, 메모리, 파일과 장치를 관리하는 소프트웨어입니다. 사용자가 프로그램을 실행하면 운영체제와 실행 환경이 필요한 자원을 준비합니다. Python에서는 Python 실행기가 코드를 읽고 처리하는 역할을 합니다. CPU는 명령을 실제로 수행하는 장치이고, 코어는 그 안의 실행 자원을 설명할 때 쓰는 단위입니다. 코어 수가 많아도 작업을 나누지 못하거나 다른 곳에서 기다리면 자동으로 빨라지지는 않습니다.

실행 중인 progress = 60이 일반 변수라면 “현재 작업 공간에 진행률 60이 있다”는 뜻입니다. 프로그램이 끝난 뒤 새로 실행했을 때 이전 진행률을 다시 읽으려면 파일이나 데이터베이스에 남긴 기록이 필요합니다. 데이터베이스(DB)는 정한 구조와 규칙에 따라 데이터를 저장하고 조회하는 시스템입니다. 파일에 기록하는 SQLite도 DB의 한 종류입니다. 저장했다고 말할 때에는 무엇을 어디에 언제 기록했는지까지 확인해야 합니다.

1-4. 프로세스는 실행 중인 프로그램의 한 인스턴스다

프로세스는 프로그램을 실행 중인 하나의 단위입니다. 인스턴스는 같은 설계에서 실제로 만들어진 개별 대상을 뜻합니다. 같은 프로그램을 두 번 실행하면 코드 파일은 같아도 실행 상태는 두 개일 수 있습니다. 두 계산 담당자가 같은 설명서를 읽지만 각자 자기 책상을 쓰는 상황에 가깝습니다. 운영체제는 프로세스를 구별하는 번호인 PID를 관리합니다.

요청을 받는 서버와 계산을 맡은 작업자를 별도 프로세스로 둘 수 있습니다. 서버는 다른 프로그램의 요청을 받아 처리하는 역할이고, 뒤에서 다룰 Worker는 맡겨진 작업을 수행하는 역할의 이름입니다. Worker라고 이름 붙인 함수가 반드시 새 프로세스에서 실행되는 것은 아닙니다. 함수 호출인지, 스레드 시작인지, 프로세스 시작인지 실제 실행 코드를 봐야 합니다.

서버 프로세스의 status와 Worker 프로세스의 status는 이름이 같아도 같은 저장 위치가 아닐 수 있습니다. Worker가 자기 일반 변수를 완료로 바꾸었다고 서버 변수도 바뀌지는 않습니다. 주소 공간은 프로세스가 자기 명령과 값에 접근하는 범위를 이해하는 기본 개념입니다. 프로세스마다 일반적인 메모리 접근 범위가 나뉘어 있어 다른 프로세스와 값을 주고받으려면 명시적인 방법이 필요합니다.

그렇다고 별도 프로세스가 모든 자원을 완전히 분리한다는 뜻은 아닙니다. 두 프로세스가 같은 DB 파일을 열거나 같은 네트워크 서비스를 사용할 수도 있습니다. Worker가 죽어도 서버가 계속 응답할 수 있다는 장점과, DB에 남은 작업을 누가 정리하는가라는 문제를 함께 생각해야 합니다. 실행 경계를 나누는 것과 업무를 복구하는 것은 서로 다른 설계입니다.

1-5. 스레드는 한 프로세스 안에서 진행하는 실행 흐름이다

스레드는 프로세스 안에서 명령을 따라 진행하는 실행 흐름입니다. 같은 사무실에서 두 담당자가 각자 일을 진행하지만 같은 게시판을 읽고 고칠 수 있다고 생각해 봅시다. 같은 프로세스의 스레드는 보통 객체와 자원을 공유할 수 있습니다. 객체는 숫자, 직원 목록, 사전처럼 프로그램이 다루는 값의 개별 대상을 가리키는 말입니다. Python의 {"count": 0}도 객체입니다.

공유는 편리하지만 순서 문제가 생깁니다. 버스 자리가 하나 남았을 때 담당자 A와 B가 모두 빈자리 1을 읽었다고 합시다. A는 E2를, B는 E3을 배정하면 같은 마지막 자리를 두 사람이 사용하게 됩니다. 두 흐름의 읽기와 쓰기 순서에 따라 결과가 달라지는 문제를 경쟁 상태라고 부릅니다. “한 프로세스니까 안전하다”는 설명은 공유 값을 누가 어떤 규칙으로 바꾸는지 빠뜨립니다.

잠금은 특정 구간을 한 번에 하나의 실행 흐름만 처리하게 만드는 도구입니다. 빈자리 확인과 배정을 같은 보호 구간으로 묶는 식으로 사용할 수 있습니다. 다만 메모리 잠금을 하나 두었다고 별도 프로세스나 다른 서버의 요청까지 모두 막는다고 가정해서는 안 됩니다. 도구마다 보호하는 범위가 다르므로 뒤의 DB와 확정 경계에서 다시 확인합니다.

이 장에서는 스레드 수를 늘리면 계산이 빨라지는지까지 판단하지 않습니다. 기다리는 일이 많은지, CPU 계산이 많은지, 어떤 언어 실행기를 쓰는지에 따라 결과가 달라집니다. 지금 필요한 첫 구분은 실행 흐름이 같은 프로세스 안에 있는가, 어떤 값을 공유하는가입니다. 동시성·병렬성·비동기는 이 바탕 위에서 7장에서 정리합니다.

1-6. 값을 전달하는 일과 오래 남기는 일도 구분한다

별도 프로세스끼리는 메시지, 공유 메모리, DB 같은 방법으로 통신할 수 있습니다. 메시지는 다른 실행 주체에게 보내는 값이고, 큐는 값을 넣고 꺼내는 통로를 표현하는 자료구조입니다. “계산을 마쳤다”는 메시지를 보냈다는 사실과 “재시작 뒤에도 완료 기록을 읽을 수 있다”는 사실은 다릅니다. 큐의 종류와 저장 방식에 따라 남는 기록이 달라집니다.

영속성은 실행이 끝난 뒤에도 필요한 기록을 다시 읽을 수 있는 성질입니다. 일반 변수만 사용하면 새 프로세스에서 과거 값을 자동 복구할 수 없습니다. 파일 DB에 기록했다면 새 연결로 다시 읽는 시험이 첫 근거가 됩니다. 전원 차단까지 견디는가, DB 파일을 다른 호스트로 옮겨도 되는가는 별도의 조건과 시험이 필요합니다. 작은 성공 사례를 모든 장애의 안전성으로 넓히지 않는 습관을 들이세요.

보충 파일 examples/ch01.py는 한 프로세스의 스레드가 count를 0에서 1로 바꾼 뒤, spawn 방식으로 만든 자식 프로세스가 자기 값을 99로 바꾸고 큐로 보내는 작은 실험입니다. spawn은 새 Python 실행기를 시작하는 방식입니다. join()은 여기서 시작한 실행 흐름의 종료를 기다리는 호출입니다. 기다렸다고 두 프로세스의 일반 메모리가 합쳐지는 것은 아닙니다.

파일을 실행하면 스레드 뒤 부모 값 1, 자식이 보낸 값 99, 자식 종료 뒤 부모 값 1을 확인합니다. 부모가 메시지 99를 받았다는 것과 부모의 count가 99라는 것은 다른 관찰입니다. 이 실험은 통근 계획 생성, DB 저장, Worker 사망 뒤 자동 복구를 구현하지 않습니다. 프로세스와 변수의 경계를 확인하는 보충 자료로 읽으면 됩니다.

python examples/ch01.py

답변 후 해설 확인

Worker가 바꾼 값과 서버가 읽는 값의 저장 위치부터 찾습니다. 서로 다른 일반 변수인지, 같은 DB의 같은 작업 행인지, 통신 메시지를 실제로 처리했는지 확인합니다. 프로세스 분리 외에도 오래된 조회값이나 잘못된 작업 식별자일 수 있으므로 원인을 이름만 보고 단정하지 않습니다.

답변 후 해설 확인

공유 자리 수의 읽기·쓰기와 보호 규칙을 확인하지 않아 안전성을 판단할 수 없습니다. 작업 특성과 실행 환경, 측정 결과가 없어 속도 향상도 단정할 수 없습니다. 실행 흐름 수, 정확성, 성능은 각각 다른 근거가 필요합니다.
