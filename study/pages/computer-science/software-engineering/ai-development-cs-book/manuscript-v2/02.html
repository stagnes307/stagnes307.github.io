화면에서 “생성”을 눌렀는데 서버는 202를 돌려주고, 화면에는 계속 “작업 중”이 보입니다. 이 숫자는 무엇을 약속한 것일까요? 이 장에서는 사용자 행동이 요청과 응답으로 바뀌는 과정을 따라가고, 기능을 만들었다는 주장에 어떤 완료 조건과 권한 검사가 필요한지 배웁니다.

2-1. 화면, 요청 서버, 계산은 서로 다른 역할이다

브라우저는 Chrome이나 Edge처럼 웹페이지를 보여 주고 사용자 입력을 받는 프로그램입니다. 사용자가 날짜를 고른 뒤 생성 버튼을 누르면 브라우저의 코드가 그 선택을 서버에 전달할 수 있습니다. 브라우저 화면은 요청을 보내는 쪽이고 서버는 요청을 받는 쪽입니다. 실제 배정 계산은 요청을 받은 서버 안에서 할 수도 있고, 다른 Worker에 맡길 수도 있습니다.

식당으로 비유하면 화면은 주문표를 쓰는 자리, 요청 서버는 주문을 접수하는 창구, Worker는 조리를 맡은 주방에 가깝습니다. 주문번호를 받았다는 사실과 음식이 완성되었다는 사실은 다릅니다. 이 비유는 역할을 구별하기 위한 것입니다. 실제 프로그램에서는 서버와 Worker가 같은 프로세스의 함수일 수도 있으므로 그림의 상자 개수만으로 프로세스 수를 결정하면 안 됩니다.

요청은 상대 프로그램에게 어떤 처리를 부탁하는 메시지이고, 응답은 그 요청을 받은 쪽이 돌려주는 메시지입니다. 브라우저는 응답을 읽어 화면을 바꿉니다. 화면의 “작업 중” 문구는 브라우저가 보관한 값일 수 있고, DB의 작업 상태는 서버가 기록한 값입니다. 둘이 항상 같은 시점에 바뀌지는 않기 때문에 상태를 어디에서 읽었는지 확인해야 합니다.

여기서는 운영자가 2026년 7월 20일의 배정을 요청한다고 합시다. 서버는 날짜와 적용된 입력 버전을 확인하고, 작업 식별자를 만든 뒤, 계산을 맡깁니다. 사용자는 작업 식별자로 진행 상태를 조회합니다. 이 흐름은 교재의 가상 설계입니다. 실제 API가 이런 순서와 저장 방식을 갖는지는 해당 프로젝트의 요청 처리 코드와 기록을 봐야 합니다.

2-2. API는 프로그램끼리 주고받는 약속이다

인터페이스는 한 대상이 다른 대상에게 기능을 제공하는 접점입니다. API는 프로그램이 다른 프로그램의 기능을 호출할 때 사용하는 인터페이스를 뜻합니다. 웹에서는 어떤 주소로 어떤 값을 보내고, 성공하거나 실패했을 때 무엇을 받는지를 정합니다. 버튼이 사람의 접점이라면 API는 프로그램의 접점이라고 이해할 수 있습니다.

HTTP는 웹에서 요청과 응답을 주고받을 때 쓰는 통신 규약입니다. URL은 요청할 자원의 위치를 나타내며, 메서드는 요청의 의미를 표현합니다. GET은 정보를 조회할 때, POST는 서버에 처리를 요청할 때 자주 사용합니다. 메서드 이름만 정했다고 권한·중복 처리·저장이 자동 구현되는 것은 아닙니다.

요청에는 추가 정보를 담는 헤더와 업무 값을 담는 본문이 있을 수 있습니다. JSON은 이름과 값을 묶어 표현하는 텍스트 형식입니다. 다음은 프로젝트에 대입할 API 모양의 예시이며, 이 주소로 실제 교재 서버가 운영된다는 뜻은 아닙니다. dataset_version은 계산에 사용할 입력 묶음의 판을 가리킵니다.

POST /generate
{"date": "2026-07-20", "dataset_version": 7}

202 Accepted
{"job_id": "J7", "status": "QUEUED"}

약속에는 필드 이름뿐 아니라 값의 의미가 들어가야 합니다. 날짜가 빠지면 거절하는지, 존재하지 않는 입력 버전을 보내면 어떻게 되는지, 결과는 어디서 조회하는지를 함께 정합니다. 이처럼 입출력과 동작 의미를 합친 약속을 여기서는 API 계약이라고 부릅니다. “요청이 성공한다”보다 “어떤 요청에 무엇을 약속하는가”가 더 구체적인 설명입니다.

2-3. 202는 접수, 배정 성공은 검증과 확정 뒤의 일이다

HTTP 응답에는 세 자리의 상태 코드가 들어갑니다. 202는 요청이 처리 대상으로 받아들여졌지만 처리가 아직 끝나지 않았을 수 있음을 나타냅니다. 이 가상 설계에서는 작업 J7을 접수했다는 뜻으로 사용합니다. 그것만으로 E1·E2·E3이 모두 배정되었거나 결과가 DB에 확정되었다고 말할 수 없습니다. 요청의 접수와 업무 완료를 분리하는 첫 이유입니다.

다음 조회가 200으로 응답해도 본문의 작업 상태를 읽어야 합니다. GET /jobs/J7이 {"status": "RUNNING"}을 돌려주면 조회 요청은 정상 처리했지만 배정 계산은 진행 중입니다. 반대로 계산이 실패한 작업을 조회해서 200과 실패 상태를 받을 수도 있습니다. HTTP 요청의 처리 결과와 그 요청이 가리키는 업무 작업의 결과는 서로 다른 층위입니다.

작업 상태는 접수·실행·검증·성공·실패처럼 업무 진행을 표현한 기록입니다. QUEUED는 대기 중, RUNNING은 실행 중이라는 뜻으로 쓸 수 있습니다. 정확한 상태 이름과 전이는 프로젝트마다 다릅니다. 이 책에서는 개념을 설명하기 위해 이름을 고정하지만 실제 답변에서는 자기 코드에 있는 상태만 말해야 합니다.

배정 성공을 판정하려면 생성한 후보가 대상·정원·시간 규칙을 통과했는지, 확정 조건을 만족하는지, 공개 결과가 저장되었는지를 연결해야 합니다. Worker가 “계산 완료”라고 로그를 남긴 직후 저장에 실패할 수도 있습니다. 따라서 사용자에게 성공을 표시하는 지점은 계산 함수가 반환한 순간과 같다고 자동 가정하지 않습니다.

네트워크 응답을 기다리다 시간제한이 걸렸을 때도 마찬가지입니다. 브라우저가 응답을 못 받았을 뿐 서버에는 작업이 남아 있을 수 있습니다. 같은 요청을 다시 보내면 중복 작업을 만들 수 있으므로 기존 작업 식별자나 재시도 식별 규칙을 확인해야 합니다. 실패를 자세히 구분하는 이유는 이름을 늘리려는 것이 아니라, 다음 행동이 달라지기 때문입니다.

2-4. 요구사항을 관찰 가능한 완료 조건으로 바꾼다

요구사항은 사용자가 시스템에 바라는 기능과 지켜야 할 조건입니다. “근무자 전원을 배정한다”는 요구는 출발점이지만 아직 확인 방법이 부족합니다. 어느 날짜의 누가 근무자인지, 출근만인지 퇴근도 포함하는지, 중복은 허용하는지를 더 정해야 합니다. 모호한 문장은 구현한 뒤에도 각자 다른 성공을 주장하게 만듭니다.

이 책의 가정에서는 E1·E2·E3이 2026년 7월 20일에 근무하고 E4는 휴무입니다. 완료 조건을 “해당 날짜의 각 근무자가 출근과 퇴근에 각각 한 번 배정되고, 휴무자는 배정되지 않으며, 각 운행의 정원과 시각 조건을 지킨다”로 바꿀 수 있습니다. 인수 조건은 이런 식으로 기능을 받아들일 수 있는지 확인하는 구체적인 기준입니다.

원하는 출력의 행 수만 세면 충분하지 않습니다. 출근 세 행에 E1·E1·E2가 들어 있다면 수는 세 명처럼 보여도 E3은 빠졌습니다. 사람과 방향과 날짜를 함께 식별해 횟수를 세어야 합니다. “대상 세 명”이라는 문장을 어떤 입력에서 만들고, 결과의 무엇과 비교하는지까지 정하면 검증기가 해야 할 일이 분명해집니다.

“잘못된 데이터셋은 적용하지 않는다”도 관찰로 바꿀 수 있습니다. 적용 전 입력 버전과 기존 결과를 기록하고, 없는 직원 번호를 참조하는 입력을 적용해 봅니다. 오류 메시지뿐 아니라 적용 뒤 입력 버전과 기존 결과가 보존되는지 다시 조회합니다. 오류를 보여 준 뒤 현재 데이터를 일부 지워 버리는 구현은 이 완료 조건을 만족하지 않습니다.

구현 순서도 이 기준에서 정할 수 있습니다. 예쁜 진행률 화면보다 누락 없는 대상 선정과 잘못된 입력의 적용 차단이 먼저 필요할 수 있습니다. 반대로 과제 요구에 로그인이나 재시작 보존이 필수라면 이를 나중 문제로 빼서는 안 됩니다. 기능을 줄일 때는 무엇을 제외했는지 밝히고, 필수 요구를 생략한 것을 단순한 구현이라고 포장하지 않습니다.

2-5. 인증은 누구인지, 인가는 무엇을 허용할지 확인한다

인증은 요청한 사람이 누구인지 확인하는 일입니다. 인가는 확인한 사람이 이 요청을 수행하거나 이 자료를 읽어도 되는지 판단하는 일입니다. 사원증으로 신원을 확인하는 것과 다른 부서의 명단을 열 수 있는지 정하는 것은 다른 질문입니다. 로그인에 성공했다는 사실만으로 모든 직원의 계획을 볼 권한이 생기지는 않습니다.

가상 서비스에서는 운영자가 입력 적용과 계획 생성을 요청하고, 구성원은 자기 계획을 읽는다고 합시다. E1이 주소의 직원 번호를 E2로 바꾸어 조회할 수 있다면 버튼을 숨겨도 보호가 되지 않습니다. 서버가 요청자의 신원과 조회 대상 E2의 관계를 검사해야 합니다. 화면은 사용 편의를 제공하고, 요청을 허용하는 최종 판단은 실제 서버 처리 경로에서 확인합니다.

401은 유효한 인증 정보가 필요한 경우에 쓰이고, 403은 요청을 이해했지만 수행을 허용하지 않는 경우에 쓰입니다. 실제 서비스는 자원 존재를 드러내지 않으려고 다른 응답 정책을 선택할 수도 있습니다. 초보 단계에서는 숫자를 암기하기보다 신원 확인과 권한 판단을 분리하고, 서버가 어느 코드에서 거절하는지 찾는 것이 먼저입니다.

인증과 업무 검증도 서로 대신하지 못합니다. 운영자가 보낸 CSV라도 없는 직원을 참조할 수 있고, 형식이 맞는 계획이라도 다른 사람에게 공개하면 안 될 수 있습니다. 계층은 역할에 따라 나눈 처리 부분을 뜻합니다. 요청 계층의 권한 검사, 입력 계층의 데이터 검사, 결과 계층의 공개 범위를 각각 연결해야 전체 설명이 됩니다.

2-6. 제3자가 따라갈 수 있도록 요구와 근거를 연결한다

추적성은 요구가 설계·코드·검사와 어떻게 이어지는지 앞뒤로 찾을 수 있는 성질입니다. “전원 배정”이라는 요구에서 대상 선정 함수와 결과 횟수 검사를 찾고, 검사 실패에서 어떤 요구를 어겼는지 돌아갈 수 있으면 좋습니다. 파일을 많이 만드는 것보다 각 파일이 어떤 주장을 뒷받침하는지 연결하는 것이 중요합니다.

프로젝트에 대입할 요구와 확인 항목의 예시
요구관찰할 것추가로 확인할 경계
근무자 전원 배정날짜·방향·직원별 기대 횟수와 결과 횟수대상 명단이 원본 근무표에서 나왔는가
잘못된 입력 적용 차단오류와 적용 전후 버전·결과실제 적용 경로가 검증을 호출하는가
자기 계획만 조회E1의 E2 조회 거절화면 외 직접 요청도 거절하는가
재시작 후 상태 조회프로그램 재실행 후 같은 작업 조회DB 파일과 저장 위치가 유지되는가

표의 오른쪽 질문은 함정이 아니라 주장의 범위를 좁혀 주는 장치입니다. 검사 함수만 따로 실행했다면 그 함수의 동작을 확인한 것입니다. 실제 API가 그 함수를 호출하는지까지 확인하지 않았다면 요청 경로 전체를 검증했다고 말하지 않습니다. 화면이 아직 없다면 서버 경로까지 완료한 사실과 화면 미구현을 함께 설명할 수 있습니다.

근거를 남길 때에는 코드 버전, 실행 명령, 입력 조건, 기대 결과, 실제 결과를 묶습니다. 서로 다른 버전에서 나온 코드와 출력을 섞으면 재현이 어렵습니다. 명령이 실제 저장소에 존재하는 파일을 실행하는지도 확인해야 합니다. 교재에 그럴듯한 파일명을 써 두는 것과 실제 프로젝트에서 같은 명령으로 실행하는 것은 다른 일입니다.

2-7. 보충 예제는 어떤 약속까지만 확인하는가

examples/ch02.py는 컴퓨터 내부의 HTTP 통신으로 권한과 접수를 확인하는 실제 보충 파일입니다. 실행하면 임시 주소와 포트로 서버를 열고, 구성원의 자기 계획 조회 허용과 타인 조회 거절, 구성원의 생성 거절, 운영자의 작업 접수와 조회를 검사한 뒤 서버를 닫습니다. 포트는 같은 컴퓨터의 네트워크 통신을 구별하는 번호입니다.

이 예제의 member-demo와 admin-demo는 미리 정한 교육용 신원 표시입니다. 실제 로그인, 비밀번호 확인, 토큰 발급·만료·서명 검증을 구현한 것이 아닙니다. 작업은 메모리의 JOBS에 접수되며 Worker가 실행하거나 DB에 영구 저장하지 않습니다. 프로그램이 끝나면 같은 작업을 다시 조회할 수 있다는 보장도 없습니다.

따라서 이 파일을 보여 주며 말할 수 있는 범위는 “권한에 따른 요청 처리와 실제 HTTP 작업 접수·조회를 확인했다”입니다. “전원 배정과 장애 복구까지 검증했다”로 넓힐 수는 없습니다. 기능의 앞부분을 정확히 설명하는 연습이 되어야 뒤의 계산과 저장도 같은 방식으로 연결할 수 있습니다.
