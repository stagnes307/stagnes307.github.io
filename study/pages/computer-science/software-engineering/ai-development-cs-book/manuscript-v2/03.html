데이터셋을 골랐다는 것, 읽을 수 있다는 것, 업무 규칙에 맞다는 것, 현재 입력으로 적용했다는 것은 각각 다릅니다. 이 장에서는 네 사건을 나누고, 실제 보충 코드가 검사하는 규칙과 아직 없는 규칙을 표로 확인합니다. “검증을 구현했습니다”라는 말을 파일·함수·검사 결과로 풀어 말하는 연습입니다.

3-1. 선택은 대상을 정하고, 검증은 조건을 묻고, 적용은 현재 상태를 바꾼다

데이터셋은 한 작업에 함께 사용하는 데이터 묶음입니다. 직원 정보만으로 배정할 수는 없습니다. 어느 날 근무하는지, 어디서 타는지, 이동에 몇 분 걸리는지 등을 함께 연결해야 합니다. 이 책에서는 사업장, 근무 유형, 직원, 근무표, 정류장, 이동시간, 승차 수요라는 일곱 종류의 자료를 예로 듭니다. 실제 프로젝트의 파일 수와 열 이름은 해당 요구에서 따로 확인해야 합니다.

선택은 사용할 묶음을 지목하는 일입니다. 7월 자료 A와 8월 자료 B 중 A를 골랐다고 해서 A 안의 날짜와 직원 번호가 올바른지는 아직 모릅니다. 검증은 정한 조건을 만족하는지 확인하는 일입니다. 적용은 검사한 묶음을 현재 작업에 사용할 입력으로 등록하는 일입니다. 선택은 식별, 검증은 판정, 적용은 상태 변경이라고 먼저 구분하세요.

가령 현재 입력이 v7인데 다른 묶음 B를 선택했다고 합시다. 선택 화면에 B가 보이는 순간 현재 입력까지 바꿀 필요는 없습니다. B에 없는 직원 번호가 발견되면 적용을 거절하고 v7을 유지할 수 있습니다. 반대로 선택과 동시에 현재 데이터를 덮어쓰면 오류를 알아낸 뒤 원래 입력을 복구해야 합니다. 처리 단계의 구분은 실패했을 때 무엇이 남는지와 연결됩니다.

여기서 v7은 설명을 위한 버전입니다. 버전은 서로 다른 입력의 판을 구별하는 표시입니다. 파일 이름이 같아도 내용이 바뀌면 같은 입력이라고 단정하기 어렵습니다. “어느 자료를 검사했고 어느 자료를 적용했는가”를 이어 줄 식별 정보가 있어야 오래된 검사 결과를 새 내용에 잘못 붙이지 않을 수 있습니다.

3-2. 읽히는 자료라고 업무에 맞는 자료는 아니다

CSV는 행과 열의 값을 쉼표 등의 구분자로 표현하는 텍스트 형식입니다. 첫 행의 열 이름을 헤더라고 부릅니다. emp_id,site_id라는 헤더 아래에 E1,ICN이 있다면 직원 E1의 사업장이 ICN이라는 모양으로 읽을 수 있습니다. 값 안에 쉼표가 있으면 따옴표 처리도 필요하므로 문자열을 무조건 쉼표로 자르는 방법은 안전하지 않습니다.

텍스트를 구조화된 값으로 읽는 일을 파싱이라고 합니다. CSV 파서가 성공했다는 것은 우선 그 형식대로 읽었다는 뜻입니다. 2026-02-30이라는 텍스트도 한 칸의 문자열로는 읽힐 수 있습니다. 실제 날짜인지 확인하려면 별도의 날짜 규칙이 필요합니다. “파일을 열었다”, “열을 나눴다”, “값이 업무에 맞다”를 같은 검사로 취급하지 마세요.

타입은 숫자, 문자열, 날짜처럼 값을 어떤 종류로 다루는지 나타냅니다. 키는 행이나 대상을 구별하는 값이고, 참조는 다른 자료의 키를 가리키는 관계입니다. 근무표의 E1이 직원 자료에 존재하는지 확인하는 것이 참조 검사입니다. 날짜와 직원의 조합이 하나여야 한다면 두 값을 묶은 키의 중복도 따로 검사해야 합니다.

각 종류를 전부 검사해도 계획이 반드시 존재하는 것은 아닙니다. 직원과 정류장이 모두 존재하지만 시간이 너무 짧아 출근시킬 수 없을 수 있습니다. 데이터가 읽을 수 있고 내부적으로 일관된다는 판단과, 주어진 자원으로 조건을 만족하는 배정이 가능하다는 판단은 다릅니다. 뒤의 생성과 결과 검증에서 다시 이어 볼 경계입니다.

3-3. 실제 ch04.py가 가진 검사와 빠진 검사를 펼쳐 본다

examples/ch04.py는 이 장의 실제 보충 파일입니다. DATA라는 사전에 일곱 CSV 모양의 문자열을 넣었습니다. 실제 폴더를 검색하거나 사용자가 파일을 선택하는 화면을 구현한 것은 아닙니다. 함수 validate(files)는 이 문자열 묶음을 받아 일부 조건을 검사하고, 읽은 표를 반환합니다. 이 예제는 공통 사례의 네 사람보다 더 작은 E1 한 명의 자료를 사용합니다.

실제 보충 코드의 구현 범위 — 전체 서비스 규칙 목록이 아님

“코드가 검사하도록 작성돼 있다”와 “특정 잘못된 입력을 넣어 거절을 확인했다”도 구분합니다. 이 파일의 main()은 정상 묶음, 따옴표 안의 쉼표, 없는 직원 참조의 적용 거절, 내용이 바뀐 뒤 옛 해시를 사용한 적용 거절을 확인하도록 작성되어 있습니다. 중복 헤더와 모든 잘못된 숫자의 경우까지 각각 실행해 검사하는 것은 아닙니다.

단언은 프로그램이 기대한 조건이 참인지 확인하는 명령입니다. Python의 assert가 해당합니다. 검사 프로그램이 정상 종료한 사실은 그 실행 경로의 단언 조건이 통과했다는 근거입니다. 코드에 등장한 모든 조건과 실제 업무의 모든 규칙이 완전히 증명되었다는 뜻은 아닙니다. 제3자에게 보여 줄 때는 실행한 입력과 단언 조건을 함께 가리켜야 합니다.

3-4. 위임했다는 말에는 실제 호출 경로와 책임이 필요하다

위임은 내가 맡은 일의 일부를 다른 구성요소가 수행하도록 맡기는 것입니다. CSV의 따옴표와 구분자를 해석하는 일을 Python의 csv.DictReader에 맡기는 것이 예입니다. 이 도구가 쉼표가 든 정류장 이름을 읽어 줄 수 있어도 그 정류장 ID가 다른 표에 존재하는지는 알지 못합니다. 형식 해석의 위임을 업무 검증의 위임으로 넓히면 빈칸이 생깁니다.

DB의 고유 제약이나 외래 키 제약으로 일부 규칙을 강제할 수도 있습니다. 외래 키 제약은 다른 표에 없는 식별자를 참조하지 못하게 하는 조건입니다. 제약은 저장하거나 계산할 때 지켜야 할 조건입니다. 예를 들어 같은 직원 번호를 두 번 저장하지 못하게 하는 고유 제약은 중복 방지 책임의 일부를 DB에 맡깁니다. 그러나 ch04.py에는 그런 DB가 없습니다. 실제 프로젝트에 해당 제약이 있는지, 활성화되었는지, 적용 요청이 그 테이블을 사용하는지 확인한 뒤 위임했다고 말해야 합니다.

“다른 팀에서 할 예정”과 “다른 계층이 실제로 수행”은 다릅니다. 요청 계층이 직원 참조를 검사한다고 들었어도 실제 적용 경로가 그 검사를 거치지 않을 수 있습니다. 어디에서 호출하고 오류를 어떻게 전달받는지를 연결해야 합니다. 호출이 없으면 설계 문서에 적힌 책임일 뿐 실행된 검사라는 근거는 부족합니다.

자기 구현을 정리할 때에는 각 규칙을 직접 구현, 실제 위임, 미구현, 아직 미확인으로 표시하세요. 미구현은 요구를 알고 있지만 검사 코드가 없다는 뜻이고, 미확인은 코드나 실행 근거를 아직 확인하지 못했다는 뜻입니다. 두 말을 구분하면 모르는 부분을 숨기지 않으면서 다음에 무엇을 찾아야 하는지도 분명해집니다.

3-5. 검증한 고정본을 적용해야 검사와 결과가 이어진다

자료 A를 검사한 뒤 사용자가 같은 이름의 파일을 B 내용으로 바꾸었다고 합시다. 적용 함수가 파일을 다시 읽어 B를 사용하면 A의 검사 통과 기록으로 B를 적용한 셈이 됩니다. 검사와 사용 사이에 내용이 바뀌는 문제가 생긴 것입니다. 검사한 대상을 고정하고 적용까지 같은 내용을 전달해야 하는 이유입니다.

스냅샷은 특정 시점의 내용을 고정해 다루는 복사본입니다. 이 예제에서는 사전을 복사하고 값으로 든 문자열을 사용합니다. 문자열은 내용을 제자리에서 바꿀 수 없는 값이므로 이 작은 모형에서는 같은 입력을 유지하는 데 도움이 됩니다. 사전 안에 계속 바뀌는 목록이나 객체가 들어 있다면 겉 사전만 복사했다고 내부까지 고정되었다고 말할 수 없습니다.

해시는 내용을 정해진 계산으로 짧은 값에 대응시킨 것입니다. fingerprint(files)는 입력 사전을 일정한 순서의 JSON으로 표현하고 SHA-256 해시를 계산합니다. 여기서는 파일 이름이 아니라 내용 묶음의 차이를 감지하는 데 사용합니다. 해시가 있다는 사실만으로 올바른 데이터이거나 믿을 수 있는 사용자가 만든 자료라는 뜻은 아닙니다. 내용 동일성 확인과 업무 규칙 판정은 별개입니다.

apply(state, files, expected_hash)는 받은 묶음을 복사해 다시 검증하고, 해시가 기대값과 같을 때만 현재 메모리 상태를 갱신합니다. state는 현재 값을 모아 둔 사전입니다. 예제의 잘못된 참조와 해시 불일치 경로에서는 갱신 전에 예외가 발생하므로 이전 상태가 유지됩니다. 예외는 정상 흐름으로 계속 진행할 수 없음을 알리는 프로그램의 신호입니다.

이것은 단일 프로그램 안의 작은 실험입니다. 여러 요청이 동시에 적용하거나 중간에 프로세스가 죽는 상황의 원자성까지 제공하지 않습니다. 원자성은 관련 변경을 전부 반영하거나 전부 반영하지 않도록 묶는 성질입니다. 실제 파일 DB의 입력 적용에서는 버전 비교와 트랜잭션 같은 저장 규칙이 더 필요하며 9장에서 다룹니다.

3-6. 제3자는 파일·명령·입력 전후 상태를 함께 본다

이 보충 예제를 확인할 실제 명령은 다음과 같습니다. 교재에서 받은 examples 폴더의 상위 위치에서 실행합니다. 파일 하나만 내려받았다면 그 파일이 있는 폴더에서 python ch04.py로 실행합니다. 사용 중인 Python 버전과 실행한 파일이 교재의 실행 기록과 같은지도 확인하면 재현의 조건을 맞출 수 있습니다.

python examples/ch04.py

확인할 코드 위치는 DATA, validate(), fingerprint(), apply(), main()입니다. 먼저 실제 입력이 문자열 일곱 묶음임을 보고, 검사 함수를 읽고, 적용 전에 검증과 해시 비교가 호출되는지 따라갑니다. 마지막으로 main()의 잘못된 입력 적용 뒤 state == before 단언을 봅니다. 오류를 잡았다는 출력과 이전 값이 유지되었다는 조건을 연결하는 방식입니다.

여기서 이전 계획은 previous-success라는 문자열 표식일 뿐 실제 근무자 배정표가 아닙니다. 이 예제의 보존 결과로 모든 업무 데이터나 파일 DB의 장애 보존을 주장할 수는 없습니다. 데이터셋 선택 화면, 실제 파일 읽기, 저장소 트랜잭션은 이 파일에 없습니다. 이 경계를 정확히 말하는 것이 “무엇을 구현하지 않았는가”에 답하는 방법입니다.

개인 프로젝트에서는 같은 방식으로 실제 입력 위치, 검증 함수, 적용 호출 경로, 저장 코드, 실패 검사와 결과 조회를 연결하세요. 명령과 파일명은 그 저장소에서 확인한 것으로 채웁니다. 입력 버전과 결과 ID를 적용 전후에 새로 조회하면, 화면만 보고 판단할 때 놓칠 수 있는 부분 변경을 찾는 데 도움이 됩니다.
