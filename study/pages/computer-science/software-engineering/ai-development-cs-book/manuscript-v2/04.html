한 요청이 끝까지 지나가는 길을 먼저 그려 봅시다. 적용한 입력을 고정하고, 작업을 기록하고, 배정 후보를 만들고, 규칙을 검사하고, 조건이 맞을 때 공식 결과로 공개합니다. 이 장의 핵심은 이름을 외우는 것이 아니라 각 기록을 누가 바꿀 수 있고 어디에서 공개를 결정하는지 설명하는 것입니다.

4-1. 작업, 후보, 공식 결과는 서로 다른 질문에 답한다

작업(job)은 사용자의 요청 한 건을 처리하기 위해 기록한 실행 단위입니다. J7이라는 작업은 “7월 20일, 입력 버전 v7로 배정을 만들어 달라”는 의도를 가리킬 수 있습니다. 작업은 아직 계산 전에도 존재합니다. 생성 시각, 진행 상태, 사용한 입력 버전, 실패 이유 같은 정보를 기록하면 요청이 끊어진 뒤에도 무엇을 하던 중이었는지 찾는 데 도움이 됩니다.

후보(candidate)는 생성기가 만들어 검사에 내놓은 결과입니다. 이 책의 생성기(Creator)는 조건에 맞는 배정을 찾아 후보를 만드는 역할입니다. 후보를 만들었다는 것은 확인할 대상이 생겼다는 뜻이지 모든 규칙을 통과했다는 뜻은 아닙니다. 임시 후보를 뜻하는 temp라는 이름을 쓸 수도 있지만, 이름보다 아직 공개 전이라는 역할을 확인하세요.

검사기(Validator)는 주어진 후보를 원본 입력과 규칙에 대조하는 역할입니다. E1·E2·E3을 각각 배정했는지, E4를 넣지 않았는지, 정원과 시각을 지켰는지 확인합니다. 검증 보고서는 어느 후보를 어떤 기준으로 검사해 무엇이 통과하거나 위반했는지 담은 기록입니다. 보고서가 없는 단순한 성공 표시만으로는 실패 원인을 따라가기 어렵습니다.

확정 결과(final)는 검증과 공개 조건을 만족해 사용자에게 공식 결과로 제공하는 배정입니다. 작업 J7은 실행을 추적하고, 후보 C7은 계산 내용을 담고, 결과 F7은 공개할 대상을 가리킵니다. 셋의 식별자가 다른 이유는 맡은 질문이 다르기 때문입니다. “작업은 실패했지만 이전 공식 결과는 남아 있다”는 상황도 이렇게 구분하면 모순이 아닙니다.

4-2. 소유권은 누가 변경을 결정하는가라는 뜻이다

이 장의 소유권은 데이터를 누가 구입했는가라는 뜻이 아닙니다. 어떤 구성요소가 해당 상태의 변경 규칙을 책임지고 허용하는가를 뜻합니다. 작업 상태를 바꾸는 곳이 여기저기 흩어져 있으면 한 코드는 성공, 다른 코드는 취소를 기록할 수 있습니다. 책임을 모으면 어떤 조건에서 전이가 허용되는지 찾기 쉬워집니다.

구성요소는 역할에 따라 나눈 프로그램의 부분입니다. 요청 처리, 입력 관리, 작업 관리, 생성, 검증, 확정 저장을 나눌 수 있습니다. 이 구분은 논리적인 역할 구분입니다. 파일 여섯 개로 나누거나 프로세스 여섯 개를 만들라는 지시가 아닙니다. 하나의 파일 안에서도 함수를 나누어 책임을 구분할 수 있고, 파일이 여러 개여도 같은 DB를 제멋대로 고치면 책임은 흐릴 수 있습니다.

4-3. 정상 흐름을 입력부터 한 단계씩 따라간다

첫째, 운영자가 이미 검증해 적용한 입력 v7에서 2026년 7월 20일을 선택합니다. 이 입력에는 E1·E2·E3의 근무와 E4의 휴무가 있습니다. 화면에 표시된 날짜만 믿지 않고 서버가 요청 날짜와 사용할 입력을 확인합니다. 긴 계산 중 원본 자료가 바뀌어도 어떤 내용으로 계산했는지 알 수 있도록 입력 고정본을 연결합니다.

둘째, 작업 관리가 J7을 기록하고 대기 상태로 둡니다. 실제 비동기 설계라면 작업 접수를 응답하고 계산을 Worker에 맡길 수 있습니다. 반대로 같은 요청 안에서 계산을 끝내고 응답하는 동기 설계도 가능합니다. 여기서는 가상 흐름의 책임을 설명하는 것이므로, 두 구조가 모두 구현되어 있다는 뜻은 아닙니다. 어느 구조든 작업 접수와 공식 결과의 의미를 구분할 수 있어야 합니다.

셋째, 생성기가 근무자 세 명을 대상으로 후보 C7을 만듭니다. 출근에는 S1에서 E1·E2가 탄 버스가 08:20에 출발해 08:40에 ICN에 도착합니다. S2에서는 E3이 08:30에 출발해 08:40에 도착합니다. 퇴근에는 두 버스가 ICN에서 18:10에 출발해 S1에 18:35, S2에 18:25 도착합니다. 버스 정원 두 명, 근무 09:00~18:00, 출근 도착 08:40까지·퇴근 출발 18:10 이후라는 교재 가정을 사용한 값입니다.

넷째, 검사기가 C7을 고정된 v7 입력과 대조합니다. 출근과 퇴근에 E1·E2·E3이 각각 한 번 있는지, E4가 없는지, 승차 인원과 방향별 이동시간이 맞는지 다시 확인합니다. S1→ICN은 20분이지만 ICN→S1은 25분입니다. 출근 계산을 그대로 뒤집어 퇴근도 20분이라고 가정하면 잘못된 결과를 놓칠 수 있습니다.

다섯째, 확정 저장이 검증한 후보와 지금 공개할 후보가 같은지, 사용할 입력 버전이 여전히 허용되는지, 이 실행에 공개 권한이 남아 있는지 확인합니다. 조건을 만족하면 C7을 결과 F7로 기록하고 J7의 완료 상태를 함께 일관되게 남깁니다. 실제 DB에서 이를 안전하게 묶는 방법은 9장의 주제입니다. 여섯째, 화면은 J7 상태와 F7을 조회해 새 공식 결과를 보여 줍니다.

4-4. 기록 사이의 연결이 있어야 “이 결과”를 설명할 수 있다

연결 정보는 어떤 입력·작업·후보·검사·결과가 서로 이어지는지 식별하는 값입니다. 예를 들어 보고서가 “통과”만 적고 후보 ID나 내용 식별 정보를 담지 않으면 C7을 검사했는지 C8을 검사했는지 알기 어렵습니다. 작업 ID가 같아도 재시도마다 후보가 바뀔 수 있으므로 작업 ID 하나만으로 충분한지도 확인해야 합니다.

가상의 기록 사슬을 입력 v7 → 작업 J7 → 후보 C7 → 보고서 R7 → 결과 F7로 써 볼 수 있습니다. 여기의 이름은 설명용이며 실제 교재에 이런 DB 테이블이 운영되는 것은 아닙니다. 개인 프로젝트에서는 각 화살표를 어떤 열이나 파일 내용으로 연결하는지 찾습니다. “파일이 있다”보다 “그 파일이 어떤 입력과 시도의 결과인가”를 확인해야 합니다.

실행 시도는 한 작업을 실제로 계산하는 개별 실행을 뜻합니다. Worker가 죽어 같은 J7을 다시 수행했다면 작업은 같아도 첫 시도와 두 번째 시도는 다릅니다. 첫 시도가 뒤늦게 돌아와 새 결과를 덮어쓰면 곤란하므로, 실행 시도를 구별하고 오래된 실행의 확정 권한을 막는 설계가 필요할 수 있습니다. 재시도와 안전한 확정을 나누는 이유입니다.

검증이 끝난 뒤 후보 내용을 고친 경우에도 연결이 끊어집니다. 정원 두 명을 검사한 뒤 E3을 같은 버스에 추가했다면 앞의 통과 결과는 바뀐 후보를 증명하지 않습니다. 검증 뒤 수정하지 못하게 다루거나, 내용이 달라지면 다시 검사하도록 해야 합니다. 후보 동일성은 단지 보기 좋은 ID를 붙이는 문제가 아니라 무엇을 검사했는지 유지하는 문제입니다.

4-5. 실패한 작업과 보존한 이전 결과를 함께 보여 준다

이미 성공한 결과 F6가 있는 상태에서 새 작업 J7을 시작했다고 합시다. C7에서 E3이 빠져 검증에 실패했다면 J7은 실패 기록과 위반 이유를 남길 수 있습니다. 그러나 C7을 새 공식 결과로 공개하면 안 됩니다. F6를 보존하는 것과 J7의 실패를 숨기는 것은 다릅니다. 사용자는 새 요청이 실패했다는 사실과 현재 표시하는 결과가 이전 성공본이라는 사실을 모두 알아야 합니다.

입력 v8을 새로 적용했다면 F6가 남아 있다는 사실만으로 v8의 최신 결과라고 표시할 수도 없습니다. 과거 이력으로 보관하는 정책과 현재 입력에 맞는 결과로 제공하는 정책을 구분해야 합니다. 이 책의 가상 설명에서는 이전 성공본을 지우지 않고 그 입력 버전을 함께 표시합니다. 실제 프로젝트의 화면 정책은 요구사항과 결과 조회 코드를 통해 확인합니다.

Worker가 후보를 만들던 중 죽었을 때 후보 파일이 일부 남아 있을 수도 있고 아무 후보도 없을 수도 있습니다. 메모리에만 있던 후보는 프로세스와 함께 사라질 수 있습니다. 작업이 DB에 RUNNING으로 남았다고 해서 지금도 계산 중이라는 뜻은 아닐 수 있습니다. 이 상태를 누가 감지하고 처리하는지는 별도 책임입니다. 이 장의 정상 흐름만으로 자동 복구를 약속하지 않습니다.

실패를 확인하려면 J7의 상태, 입력 버전, 후보 식별자, 위반 보고서, final 식별자를 각각 봅니다. 모든 실패를 “오류 발생” 한 줄로만 남기면 입력 문제인지 계산 중단인지 확정 거절인지 판단하기 어렵습니다. 반대로 사용자에게 내부 기록을 전부 노출할 필요는 없습니다. 운영자가 확인할 진단 정보와 사용자가 볼 결과를 역할에 맞게 구분할 수 있습니다.

4-6. 책임을 분리한 코드와 강제하는 저장 경계는 다르다

examples/ch05.py는 입력, 후보, 생성, 검증, 저장소를 작은 Python 코드로 나눈 보충 자료입니다. Input은 버전과 직원 묶음을, Candidate는 버전과 배정 묶음을 담습니다. create()는 받은 직원을 그대로 후보로 옮깁니다. 이 예제에는 정류장, 버스, 날짜, 출근·퇴근 시각 계산이 없습니다. 공통 배정 사례의 전체 구현이 아니라 책임을 읽는 모형입니다.

python examples/ch05.py

validate()는 버전이 같은지, 직원 집합이 같은지, 중복이 없는지 확인합니다. Repository.publish()는 저장소의 현재 버전과 후보 버전이 같을 때 후보를 final에 넣습니다. 저장소(Repository)는 데이터 저장과 조회를 맡기는 코드의 역할 이름입니다. 이 파일에서는 실제 파일 DB가 아닌 메모리 객체입니다.

중요한 빈칸도 있습니다. 이 publish() 자체는 후보가 검증을 통과했는지 검사하지 않습니다. main()에서 검증 함수를 호출하는 순서는 보이지만, 다른 호출자가 검증을 생략하고 저장소를 부르지 못하게 강제하는 완성된 경계는 아닙니다. “검증 함수를 만들었다”와 “검증 없는 공개 경로를 막았다”는 다른 주장입니다. 실제 설계를 설명할 때 꼭 구별해야 합니다.

예제는 입력 버전을 2로 바꾼 뒤 버전 1 후보의 공개가 거절되는지, 중복된 직원 후보가 검증에서 거절되는지 확인하도록 작성되어 있습니다. 데이터 묶음은 변경을 제한하는 형태로 만들지만 그것이 DB 트랜잭션이나 여러 프로세스의 경쟁 제어를 대신하지 않습니다. 하나의 호출 흐름에서 통과한 조건을 서비스 전체 보장으로 확대하지 않는 연습입니다.

실제 확정 경계에서는 검증 근거, 후보 내용, 입력 버전, 실행 시도, 현재 작업 상태를 어디에서 함께 확인하는지 찾아야 합니다. 파일을 여러 개로 나누었다는 설명보다 “검증 결과와 후보가 같은지 이 지점에서 확인하고, 조건을 만족할 때만 공식 결과를 바꾼다”는 설명이 책임을 더 잘 보여 줍니다.

입력 관리가 검증된 v7을 고정하고, 작업 관리가 J7을 접수하고, 생성기가 C7을 만들고, 검사기가 v7과 C7을 대조해 R7을 만들고, 확정 저장이 현재 조건을 확인해 F7과 완료를 기록하며, 요청·화면 계층이 J7과 F7을 조회합니다. 이는 가상 계약이므로 실제 구현에서는 해당 함수·파일·저장 기록으로 대입해야 합니다.
