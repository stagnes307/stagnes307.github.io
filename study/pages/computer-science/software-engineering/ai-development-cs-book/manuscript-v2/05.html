계획을 만드는 사람과 계획을 검사하는 사람을 나누면 무엇이 좋아질까요? 둘을 동시에 일하게 하면 더 빨라질까요? 답하려면 이름보다 각 역할이 받아야 하는 자료와 일이 끝나는 순서를 봐야 합니다. 이번 장에서는 가상 통근 배정 계획 하나를 끝까지 따라가며 역할 분리, 독립 검사, 병렬 처리의 관계를 배웁니다.

5-1. 답을 만드는 일과 답을 확인하는 일

누군가 여행 일정을 짰다고 생각해 봅시다. 만드는 사람은 목적지와 시간을 조합해 일정을 찾습니다. 확인하는 사람은 완성된 일정에서 기차가 출발하기 전에 역에 도착하는지, 같은 시간에 다른 도시에 있지는 않은지 살펴봅니다. 좋은 일정을 찾아내는 절차와 이미 만들어진 일정의 모순을 찾는 절차는 다를 수 있습니다.

이 책에서 Creator는 입력과 규칙을 받아 배정 후보를 만드는 생성기입니다. Validator는 원본 입력·규칙·후보를 대조해 위반 목록을 만드는 검사기입니다. 앞 장의 candidate는 이 둘 사이를 오가는 임시 계획입니다. final은 필요한 검사를 통과하고 확정 조건까지 충족해 사용자에게 공개한 결과입니다. 생성기는 “어떤 답을 만들까”, 검사기는 “이 답이 조건을 지켰나”라는 질문을 맡습니다.

근무자 E1·E2·E3를 출근과 퇴근에 배정하는 예를 떠올려 보세요. 생성기는 E1과 E2를 S1 노선에, E3를 S2 노선에 넣을 수 있습니다. 검사기는 근무표에서 대상 세 명을 다시 구해 각각 양방향 한 번씩 등장하는지 셉니다. 생성기가 스스로 적은 “전원 배정 완료” 문장만 읽고 끝내면 검사기의 역할을 한 것이 아닙니다.

역할 분리는 같은 파일 안의 함수 두 개로도 시작할 수 있습니다. 별도 파일이나 프로세스가 반드시 필요한 것은 아닙니다. 중요한 것은 생성 함수의 어떤 결과를 검사 함수에 주고, 검사 실패를 어떻게 전달하며, 누가 최종 공개를 허용하는지가 분명한가입니다. 검사기가 후보를 몰래 고치면 그 변경에 대한 검사도 다시 필요합니다.

5-2. 검사기에 무엇을 넘겨야 할까

입출력 계약은 한 역할이 어떤 자료를 받고 어떤 결과를 돌려주는지 정한 약속입니다. 생성기에 근무표·정류장·이동시간·정원·시간 조건을 주고 후보를 받았다면, 검사기에도 그 후보의 의미를 판단할 근거가 있어야 합니다. 직원 이름만 주고 날짜나 방향을 빼면 출근 누락과 다른 날의 배정을 구별할 수 없습니다.

가상 계획 검사에 필요한 세 묶음
묶음담긴 내용필요한 이유
고정한 원본 입력근무일·직원·WORK/OFF·정류장·방향별 이동시간누가 어떤 이동을 해야 하는지 다시 계산
신뢰한 규칙정원 2명, 출근 도착 08:40까지, 퇴근 출발 18:10 이후후보 스스로 합격 기준을 바꾸지 못하게 함
검사할 후보실제 배정 인원·방향·정류장·운행 시각주장 대신 구체적인 결과를 대조

후보가 자기 안에 capacity: 999라고 적었다고 해서 정원을 999명으로 바꾸면 안 됩니다. 정원은 신뢰할 수 있는 요청 설정이나 업무 규칙에서 가져옵니다. 마찬가지로 후보의 valid: true는 생성기의 주장일 뿐, 검사 결과를 대신하지 않습니다. “누가 기준을 결정했는가”를 확인하면 검사기가 순환해서 자신을 믿는 오류를 찾을 수 있습니다.

입력과 규칙에는 버전도 연결합니다. 버전은 어느 시점의 내용을 사용했는지 구별하는 표지입니다. 생성기는 근무표 v7을 썼는데 검사기는 v8을 읽었다면 같은 직원을 대상으로 이야기하고 있는지부터 알 수 없습니다. 후보·입력·규칙의 연결을 고정해야 검사 통과라는 말에 구체적인 대상이 생깁니다.

5-3. 동시에 시작해도 되는 일과 기다려야 하는 일

의존성은 어떤 일이 다른 일의 결과를 필요로 하는 관계입니다. 식탁을 닦는 일과 접시를 준비하는 일은 겹칠 수 있지만, 접시에 담긴 음식의 양을 확인하려면 먼저 음식이 담겨 있어야 합니다. 같은 완성 후보의 최종 검사도 생성이 끝나기를 기다립니다. 두 역할을 별도 프로세스로 옮겨도 필요한 입력이 저절로 생기지는 않습니다.

데이터 의존성을 따라 정한 실행 순서
단계겹칠 수 있는가다음 단계의 조건
직원 파일 기본 검사 / 이동시간 파일 기본 검사서로의 결과가 필요 없다면 가능두 검사 결과가 모두 준비됨
파일 사이 참조 확인앞의 결과를 기다림생성에 필요한 입력 검증 완료
같은 후보 생성 / 최종 검사완성본 기준으로는 순서가 필요후보 완성·고정 후 검사 시작
확정 결과 공개검사 통과만으로 즉시 허용하지 않음현재 입력 버전·작업 권한도 확인

후보 A가 완성됐다면 A를 검사하는 동안 후보 B를 탐색하는 구조는 가능합니다. 이때 A와 B는 서로 다른 후보이며, 각각 어떤 입력으로 만들어졌는지 구별해야 합니다. 같은 후보 목록을 계속 고치면서 한쪽에서는 읽고 있다면 “A를 검사했다”는 말 자체가 불명확해집니다. 시간이 겹쳤다는 사실보다 무엇을 읽었는지가 먼저입니다.

이런 순서를 화살표로 그린 뒤 앞선 작업을 끝낸 것부터 배치하는 방법을 위상 순서라고 합니다. 어려운 이름을 외우기보다 “아직 없는 자료를 읽지 않게 순서를 정한다”고 이해하세요. 준비된 작업을 찾는 도구와 실제로 여러 일을 실행하는 장치는 다릅니다. 작업 목록만 나열했다고 병렬 실행한 것은 아닙니다.

5-4. 조각마다 통과해도 합치면 틀릴 수 있다

생성을 두 조각으로 나눠 보겠습니다. 첫 조각은 출근 대상 E1을 한 번 배정하고, 둘째 조각도 E1을 한 번 배정했습니다. 각 조각 안에서 중복을 검사하면 둘 다 통과합니다. 그러나 전체 대상이 E1·E2라면 합친 결과는 E1 두 번, E2 영 번입니다. 조각 내부의 성공을 전체 성공으로 바꿔 말할 수 없습니다.

지역 검사는 한 조각 안의 조건을, 전역 검사는 합친 전체의 조건을 확인합니다. 노선마다 정원을 지켰더라도 같은 차량을 같은 시간에 서로 다른 노선에 넣었을 수 있습니다. 사업장별로 따로 만들었더라도 다른 사업장 근무자를 빠뜨렸을 수 있습니다. 무엇을 나누었고 어떤 자원을 함께 쓰는지 살펴야 합니다.

생성된 조각을 차례로 넘겨 즉시 검사하는 방식을 만들 수도 있습니다. 이처럼 단계의 출력이 다음 단계로 흘러가는 구조를 파이프라인이라고 합니다. 다만 중간에 아직 E3의 조각이 오지 않았다고 바로 “E3 누락”을 최종 판정하면 안 됩니다. 조각이 모두 왔음을 알리는 완료 조건과 마지막 전역 검사가 필요합니다.

초보 단계에서는 입력을 고정하고, 완성 후보를 한 번 넘기고, 전체를 검사하는 흐름부터 이해하는 편이 좋습니다. 그 뒤 실제 자료가 커서 메모리나 시간이 문제일 때 조각 처리의 이득을 따져 볼 수 있습니다. 단순한 흐름도 모든 요구를 지켜야 하며, 복잡한 흐름도 전체 검사를 생략할 이유가 되지는 않습니다.

5-5. 독립 검사는 다른 파일 이름에서 생기지 않는다

생성기와 검사기가 모두 잘못된 근무자 목록을 읽으면 같은 오류를 놓칠 수 있습니다. 예를 들어 공통 함수가 OFF 직원 E4를 WORK로 골랐고, 두 역할 모두 그 목록을 정답으로 믿었다면 결과가 일치해도 실제 요구는 어겼습니다. 독립 검사란 생성기의 자체 판정만 되풀이하지 않고 원본과 규칙에서 결과의 조건을 다시 확인하는 것입니다.

코드를 모두 두 번 작성해야 한다는 뜻은 아닙니다. 문자 인코딩, 즉 문자를 바이트로 표현하는 방식이나 날짜 자료형을 읽는 공통 도구를 사용할 수 있습니다. 다만 누가 대상인지, 배정 횟수가 몇 번인지, 노선 시각이 조건을 만족하는지 같은 핵심 판정을 생성기의 탐색 내부 상태에만 의존하지 않게 합니다. 공통 코드에서 틀릴 수 있는 부분에는 별도의 작은 정답 사례를 붙일 수 있습니다.

검사기를 확인할 때는 정상 후보 하나만 보여 주지 않습니다. E1을 지운 후보, E1을 두 번 넣은 후보, OFF인 E4를 넣은 후보, 정원보다 한 명 많이 태운 후보를 만들어 각각 거절하는지 확인합니다. 정상 결과를 일부러 바꾸는 이런 검사를 여기서는 변이 검사라고 부릅니다. 무엇을 틀리게 했는지 우리가 아는 사례로 검사기의 반응을 보는 것입니다.

또한 검사한 뒤 후보가 바뀌지 않아야 합니다. 검사 시점에는 E1·E2였는데 저장 직전에 E3를 추가하면 통과 기록은 현재 후보의 근거가 아닙니다. 변경 불가능한 복사본을 넘기거나 내용 식별값을 연결하고, 확정할 때 동일성을 확인하는 방법을 생각할 수 있습니다. 자세한 DB 확정 조건은 9장에서 다룹니다.

5-6. AI 작성자·검토자와 계획 생성기·검사기

“Creator와 Validator를 나눴다”는 말을 AI 협업에서도 쓰곤 합니다. 이때 작성자는 코드를 제안하고 검토자는 요구 누락이나 버그 가능성을 찾습니다. 여기까지 설명한 계획 생성기·계획 검사기와는 검사 대상이 다릅니다. 코드를 읽는 AI 검토와 실제 계획의 배정 횟수를 계산하는 프로그램 검사를 구별해서 말해야 합니다.

AI 검토가 도움이 되더라도 “문제가 없어 보인다”는 문장은 실행 결과가 아닙니다. 같은 AI가 역할만 바꿔 검토했다면 독립된 외부 사람이 확인했다고 표현할 수도 없습니다. 검토 대상 파일이나 코드 버전, 지적한 내용, 실제 수정, 실행한 명령과 출력을 연결하면 무엇을 확인했는지 설명할 수 있습니다.

계획 Validator를 나눈 장점은 생성 전략을 바꾸어도 같은 기준으로 후보를 확인하기 쉽다는 점입니다. 대가도 있습니다. 후보를 전달하고 조건을 다시 계산하는 비용이 들며, 두 역할이 같은 규칙 버전을 사용하도록 관리해야 합니다. “분리했으니 안전하다”보다 “어떤 오류를 별도 계산으로 잡고 어떤 공통 오류는 남는가”까지 설명하면 설계 판단이 드러납니다.

5-7. 이 책에서 직접 확인할 수 있는 범위

보충 자료 examples/ch06.py는 선행 작업의 순서와 지역 검사만으로 놓치는 전역 오류를 보여 주는 독립 실험입니다. 책의 예제 폴더에서 python examples/ch06.py로 실행할 수 있습니다. 첫 준비 목록은 employees와 travel이고, 그 뒤 create → validate → publish 순서를 확인합니다. 두 조각에 E1이 각각 들어 있을 때 지역 검사는 통과하고 전체 검사는 실패하는지도 확인합니다.

이 코드의 TopologicalSorter는 준비된 작업을 알려 주는 도구입니다. 예제가 실제 직원 CSV를 읽거나 생성기와 검사기를 병렬 실행하는 것은 아닙니다. 출력의 local_pass_global_fail은 그 작은 반례를 확인했다는 뜻입니다. 전체 통근 서비스, Worker 복구, 실제 후보의 모든 규칙을 검사했다는 뜻으로 넓히면 안 됩니다.

자신의 구현에서는 생성기 시작점, 완성 후보가 만들어지는 지점, 검사기 호출, 실패 시 반환, 최종 저장 경로를 차례로 찾습니다. “검사 함수가 존재한다”에서 멈추지 말고 실제 생성 요청이 그 함수를 호출하는지 확인하세요. 검증한 후보와 저장한 후보가 같은지도 추적해야 합니다.

5-8. 내 말로 설명하기

질문 1. “Creator와 Validator를 병렬로 실행했다”는 말을 들었습니다. 무엇을 먼저 확인해야 할까요?

해설 확인

같은 후보의 최종 검사를 뜻하는지, 독립 입력 검사나 서로 다른 후보의 처리를 뜻하는지 확인합니다. 같은 후보라면 완성·고정 시점과 검사 시작의 선후 관계가 필요합니다. 실제 실행 경계와 병합 후 전역 검사도 확인해야 합니다.

질문 2. 두 조각이 각각 E1을 한 번 배정했고 각 조각의 중복 검사는 통과했습니다. 전체도 통과했다고 할 수 있을까요?

해설 확인

그럴 수 없습니다. 전체에서 E1이 두 번이고 다른 대상이 누락됐을 수 있습니다. 원본 근무표의 날짜·직원·방향별 기대 횟수와 병합된 후보의 실제 횟수를 비교해야 합니다.

질문 3. 생성기는 성공이라고 했고 AI 검토도 통과했습니다. 어떤 근거를 더 보여 주겠습니까?

해설 확인

같은 입력·규칙 버전과 고정 후보를 사용한 독립 검사 결과, 일부러 망가뜨린 후보의 거절 결과, 검사 후 같은 후보만 확정하는 경로를 제시합니다. 실제 실행한 파일·명령·출력과 아직 확인하지 않은 범위를 함께 말합니다.
