서버가 바로 응답하면 계산도 끝난 걸까요? async라고 쓰면 다른 프로세스가 계산할까요? 이런 질문은 서로 다른 기준을 한 단어로 묶을 때 어려워집니다. 이번 장에서는 작업이 겹치는 방식, 계산을 실행하는 자원, 호출자가 기다리는 방식을 나누어 같은 요청을 다시 살펴봅니다.

7-1. 한 사람이 번갈아 일하는 것과 두 사람이 함께 일하는 것

물을 끓이는 동안 채소를 썰면 두 요리가 진행 중입니다. 요리사는 한 명이지만 물이 끓기를 기다리는 시간을 활용합니다. 두 요리사가 각자 채소를 썰면 같은 순간 두 손질이 실제로 진행됩니다. 어느 경우든 여러 일이 끝나기를 기다리지만, 동시에 사용한 실행 자원은 다릅니다.

동시성은 여러 작업의 진행을 겹쳐 다루는 구조를 말합니다. 한 작업이 끝나기 전에 다른 작업도 시작해 진행할 수 있습니다. 병렬성은 여러 계산이 같은 순간 실제로 실행되는 성질입니다. 한 CPU 코어가 실행 흐름을 번갈아 처리하면 동시성을 구현할 수 있지만 두 계산이 같은 순간 실행됐다는 뜻은 아닙니다.

프로세스나 스레드는 실행을 구성하는 단위이고, 동시성과 병렬성은 실행이 이루어지는 방식에 관한 질문입니다. 프로세스를 두 개 만들었더라도 한쪽이 다른 결과를 기다리거나 CPU 자원이 부족하면 병렬 이득이 작을 수 있습니다. 반대로 한 프로세스 안의 스레드도 환경과 작업 특성에 따라 병렬 실행에 관여할 수 있습니다. 이름만으로 실제 속도를 결정하지 않습니다.

먼저 “A가 끝나기 전에 B도 진행 중인가”, 다음으로 “CPU 계산이 같은 순간 여러 자원에서 실행되는가”를 따로 물어 보세요. 실행 사건의 순서와 사용 자원을 분리하면 화면의 동시 진행 표시만 보고 성능을 판단하는 실수를 줄일 수 있습니다.

7-2. 누가 무엇의 완료를 기다리는가

동기 처리는 호출한 작업의 완료가 돌아와야 호출 흐름이 다음으로 이어지는 방식입니다. 비동기 처리는 시작과 완료를 분리해 완료를 나중에 받거나 확인하는 방식입니다. 단어의 범위가 중요합니다. 브라우저가 생성 결과를 기다리는지, 서버의 함수가 파일 읽기를 기다리는지, 작업 ID를 받은 사용자가 나중에 결과를 조회하는지를 붙여 설명해야 합니다.

가상 배정 서비스에서 서버가 계산·검사·저장을 마친 뒤 최종 계획을 응답하면 업무 완료를 한 요청 안에서 기다리는 흐름입니다. 반면 작업 J1을 기록한 뒤 “접수됐다”는 응답을 보내고 나중에 J1을 조회하게 하면 업무의 시작과 완료가 분리됩니다. 두 번째 구조에서 응답이 빨라졌다고 계산 시간이 줄었다고 말할 수는 없습니다. 기다리는 위치가 바뀐 것일 수도 있습니다.

별도 프로세스를 시작하고 바로 종료를 기다리면 호출자는 여전히 기다립니다. 반대로 같은 프로세스에 작업을 남기고 HTTP 응답만 먼저 보낼 수도 있습니다. 그래서 “별도 프로세스 비동기 처리”라는 설명은 두 선택을 함께 했다는 말이어야 합니다. 실제 시작 코드와 응답 시점을 각각 확인합니다.

7-3. async와 await를 일의 양보로 이해하기

Python의 코루틴은 진행을 멈추었다가 다시 이어갈 수 있는 작업을 표현합니다. async def로 정의한 함수를 호출하면 코루틴 객체가 만들어집니다. 호출한 사실만으로 별도 프로세스나 스레드가 생기지 않습니다. await로 실행을 이어 가거나 태스크로 등록하는 등 실제 실행 흐름에 연결해야 합니다.

태스크는 코루틴을 실행하도록 관리하는 단위이고, 이벤트 루프는 진행 가능한 태스크와 대기 중인 태스크를 관리하는 실행 장치입니다. 한 태스크가 아직 준비되지 않은 결과를 기다리며 자리를 양보하면 다른 태스크를 진행할 수 있습니다. 계산을 다른 곳으로 순간이동시키는 장치라기보다, 대기 중인 시간을 활용하는 규칙으로 이해하세요.

await가 쓰인 모든 줄에서 반드시 오래 멈추는 것은 아닙니다. 기다리는 결과가 이미 준비됐다면 바로 이어갈 수 있습니다. 반대로 비동기 함수 안에 오래 걸리는 일반 계산이나 실행 흐름을 붙잡는 파일·네트워크 호출이 있으면 다른 태스크도 지연될 수 있습니다. 이처럼 자리를 잡고 반환하지 않는 호출을 블로킹 호출이라고 합니다.

예를 들어 배정 후보를 수백만 번 비교하는 반복문을 async def generate() 안에 넣어도, 그 계산이 저절로 다른 CPU 코어로 옮겨 가지 않습니다. 같은 이벤트 루프에서 오래 자리를 차지하면 상태 조회 같은 다른 요청까지 늦어질 수 있습니다. 함수 선언보다 실제로 어디서 계산하고 어디서 기다리는지 따라가야 합니다.

7-4. CPU 계산과 입출력 대기를 구별하기

CPU는 프로그램의 명령을 실행하는 장치이고, 코어는 계산을 수행하는 실행 자원입니다. 숫자 조합을 많이 비교하는 배정 탐색은 CPU 계산의 비중이 클 수 있습니다. 파일이나 네트워크 응답을 기다리는 작업은 입출력 대기의 비중이 클 수 있습니다. 실제 요청에는 두 종류가 섞이므로 구간을 나누어 관찰합니다.

입출력 대기가 긴 요청 여러 개는 기다리는 시간을 겹쳐 처리하는 이득을 얻을 수 있습니다. 하지만 외부 서비스가 초당 요청 수를 제한하거나 DB 연결 수가 부족하면 무작정 동시 작업을 늘릴 수 없습니다. CPU 계산이 긴 경우에는 실행 자원을 더 쓰는 방법을 검토하지만, 전달 비용과 메모리 사용도 함께 봐야 합니다.

CPython은 Python을 실행하는 대표 구현입니다. 이 책의 Python 3.11 일반적인 CPython 환경에는 GIL이라는 Python 실행기 내부의 잠금이 있어 순수 Python 코드를 여러 스레드가 같은 순간 실행하는 데 제한이 있습니다. 따라서 순수 Python CPU 계산에 스레드만 늘렸다고 여러 코어의 가속을 주장하면 안 됩니다. 입출력 대기와 잠금을 해제하는 확장 라이브러리의 동작은 다를 수 있습니다.

이 설명을 모든 Python 구현과 모든 버전에 그대로 적용하지도 않습니다. 실행 환경과 라이브러리의 보장을 확인해야 합니다. 별도 프로세스는 다른 실행기와 메모리 공간을 사용하지만, 큰 근무표를 전달하고 결과를 되돌리는 비용이 듭니다. 작업이 짧으면 새 프로세스를 시작하는 시간이 절약한 계산보다 클 수도 있습니다.

7-5. 같은 요청을 세 가지 실행 방식으로 그리기

동기 흐름에서는 요청을 받은 실행자가 입력을 읽고 생성·검사·확정까지 수행합니다. 연결이 단순해 순서를 설명하기 쉽지만 계산이 길면 그 실행자가 오래 붙잡힙니다. 다만 동기 함수 하나가 있다는 사실만으로 서버 전체가 한 번에 한 요청만 처리한다고 단정할 수는 없습니다. 서버가 실행자를 몇 개 두는지는 별도 설정입니다.

스레드에 일을 맡기는 구조에서는 실행 흐름을 나누고 같은 프로세스의 객체를 공유할 수 있습니다. 자료 전달이 편할 수 있지만 공유 상태를 동시에 고치는 순서를 관리해야 합니다. 프로세스 자체가 종료되면 그 안의 스레드도 함께 영향을 받습니다. “진행률 변수를 공유한다”와 “서버 재시작 뒤에도 남는다”는 다른 성질입니다.

별도 프로세스의 Worker에 맡기면 요청 서버와 계산의 일반 메모리 상태가 분리됩니다. 입력과 결과를 큐·파일·DB 같은 명시적 경로로 전달해야 합니다. 요청 서버가 접수 응답을 먼저 보내고 DB의 작업 상태를 조회하게 만들 수 있지만, 이는 프로세스 시작에 더해 작업 기록과 조회 경로까지 설계한 결과입니다.

7-6. 기다림을 옮겨도 남는 문제

비동기 처리와 역할 분리는 계획의 정확성을 대신하지 않습니다. 같은 후보를 생성 중인데 최종 검사기가 중간 배열을 읽으면 아직 오지 않은 직원을 누락으로 볼 수 있습니다. 5장에서 정리한 의존 순서를 지켜 완성 후보를 검사하고, 부분 처리를 사용했다면 마지막 전역 검사를 해야 합니다.

업무 비동기에서는 응답을 못 받은 사용자가 같은 버튼을 다시 누를 수도 있습니다. 작업은 이미 기록됐는데 응답만 유실됐을 수 있기 때문입니다. 같은 요청을 식별할 규칙과 상태 조회가 필요합니다. 대기 시간이 끝났다는 사실도 계산이나 DB 쓰기가 취소됐다는 뜻은 아닙니다. 이 차이는 9·10장의 중복 요청과 실패 처리로 이어집니다.

실행 중인 태스크는 영구 작업 기록이 아닙니다. 서버가 재시작하면 메모리 상태가 사라질 수 있습니다. 별도 프로세스도 작업을 기억하고 회수하는 정책을 자동으로 주지 않습니다. “누가 언제까지 맡았는가”, “현재 공개 결과는 무엇인가”를 저장하고 조회하는 경로가 있어야 장애 뒤 상태를 설명할 수 있습니다.

성능은 같은 입력·규칙·정확성 조건에서 실제 경과 시간을 재어 비교합니다. 계산 시간, 대기 시간, 검사 시간, 확정 시간을 나누면 병목이 보입니다. 화면 도식에서 막대가 짧아진 것은 설명이며 측정값이 아닙니다. 작업 수를 늘리면서 검사를 껐다면 동일한 작업의 속도를 비교한 것도 아닙니다.

7-7. 이 책의 비동기 실험은 무엇을 보여 주나

보충 자료 examples/ch09.py는 같은 프로세스 안의 코루틴 두 개를 태스크로 실행합니다. A와 B는 각각 시작을 알린 뒤 같은 이벤트가 열리기를 기다립니다. 주 흐름은 두 시작을 모두 확인하고 나서 이벤트를 엽니다. 따라서 어느 것도 끝나기 전에 두 태스크가 모두 시작됐다는 사실을 확인할 수 있습니다.

책의 예제 폴더에서 python examples/ch09.py를 실행하면 시작한 이름과 완료한 이름, 하나의 프로세스였는지를 확인하는 결과를 얻습니다. 여기의 Queue와 Event는 한 이벤트 루프 안에서 쓰는 asyncio 도구입니다. 프로세스 사이의 통신 큐나 재시작 뒤 남는 작업 큐와 같은 도구가 아닙니다.

이 실험에는 실제 배정 탐색이나 속도 비교가 없습니다. 두 태스크의 대기가 겹쳤다는 사실에서 CPU 병렬성, 가속, 재시작 복구를 추론하지 않습니다. 자신의 구현에서는 실행 프로세스, 태스크를 만든 코드, 입력 전달, 실제 양보 지점, 결과 저장 경로를 함께 확인해야 합니다. 이 기준으로 보면 “async를 썼다”는 한 줄 설명을 구체적인 흐름으로 바꿀 수 있습니다.

7-8. 내 말로 설명하기

질문 1. async 함수 안에서 오래 걸리는 배정 계산을 실행했습니다. 별도 프로세스로 계산한 것일까요?

해설 확인

함수 선언만으로는 아닙니다. 실제 프로세스 시작이나 실행기에 위임하는 코드와 PID를 확인해야 합니다. 같은 이벤트 루프에서 긴 계산을 하면 다른 태스크의 진행을 지연시킬 수 있습니다.

질문 2. 별도 프로세스를 시작한 뒤 바로 종료까지 기다렸습니다. 프로세스 분리와 비동기를 어떻게 설명할까요?

해설 확인

실행 경계는 분리했지만 호출 흐름은 그 완료를 기다립니다. 업무 접수 응답을 먼저 주는 비동기 구조인지와는 다른 질문입니다. 누가 무엇을 기다리는지 범위를 붙여 말합니다.

질문 3. 응답은 빨라졌지만 결과가 나오는 시간은 그대로입니다. 개선됐다고 말할 수 있는 범위는 어디까지인가요?

해설 확인

접수 응답 시간이나 요청 자원 점유가 개선됐을 수 있습니다. 계산 성능이 빨라졌다고 말하려면 같은 조건의 생성·검사·확정 시간을 측정해야 합니다. 접수와 업무 완료를 구분해 보고합니다.
