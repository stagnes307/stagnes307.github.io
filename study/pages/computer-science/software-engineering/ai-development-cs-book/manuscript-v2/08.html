계산을 다른 프로세스에 맡긴 뒤 요청 서버가 응답했다고 생각해 봅시다. 맡긴 일을 누가 기억하고, 두 Worker가 같은 일을 가져가면 어떻게 되며, 작업자가 중간에 사라지면 무엇이 남을까요? 큐와 Worker는 이런 질문을 나누어 생각하기 위한 장치입니다. 이번 장에서는 접수와 완료 사이의 기록을 따라갑니다.

8-1. 주문표를 보관하는 곳과 요리하는 사람

식당에서 주문표를 쌓아 두는 곳과 실제로 요리하는 사람은 다릅니다. 주문표가 있어도 요리사가 가져가지 않으면 음식이 나오지 않습니다. 요리사가 별도 방에서 일해도 주문표를 잃어버리면 무엇을 해야 했는지 알 수 없습니다. 프로그램도 “일을 기억하는 장치”와 “일을 수행하는 실행자”를 나누어 봅니다.

큐는 처리할 항목을 넣고 꺼내는 자료구조나 서비스입니다. 일을 넣는 쪽을 생산자, 꺼내는 쪽을 소비자라고 부릅니다. Worker는 맡은 일을 실제로 수행하는 역할입니다. 요청 서버가 배정 작업을 등록하고 계산 프로세스가 꺼내 수행한다면, 전자는 생산자이고 후자는 소비자 역할을 합니다.

단순 큐는 먼저 들어온 항목을 먼저 꺼내지만 업무 시스템에는 우선순위나 재전달이 있을 수 있습니다. 꺼낸 순서가 완료 순서와 같다고도 할 수 없습니다. 먼저 시작한 큰 작업보다 나중에 시작한 작은 작업이 먼저 끝날 수 있습니다. 사용자에게는 줄의 위치와 작업 상태를 구분해 보여 주어야 합니다.

Worker라는 파일명이나 함수명만으로 별도 프로세스가 되는 것은 아닙니다. 같은 함수 호출일 수도, 스레드일 수도, 별도 실행 프로그램일 수도 있습니다. 실제 시작 코드와 실행 프로세스를 확인해야 요청 서버와 계산이 어떤 실패를 공유하는지 설명할 수 있습니다.

8-2. 메모리 큐와 기록이 남는 작업 큐

메모리에만 둔 대기 목록은 실행 프로세스가 사라지면 함께 잃을 수 있습니다. 영속성은 실행이 끝난 뒤에도 필요한 값을 다시 읽을 수 있게 보관하는 성질입니다. 작업을 받았다고 사용자에게 알렸다면, 요구에 따라 재시작 뒤에도 그 작업을 찾아야 할 수 있습니다. 그때는 파일 DB나 적절한 저장 설정을 가진 작업 서비스가 필요합니다.

Queue라는 이름이 같아도 확인할 범위는 다르다
도구의 예주로 잇는 경계별도로 확인할 점
queue.Queue한 프로세스의 스레드 사이프로세스 종료 뒤 작업 보존
multiprocessing.Queue서로 다른 프로세스 사이미완료 작업의 영구 보관·회수
파일 SQLite의 작업 테이블같은 파일에 접근하는 실행자 사이선점·상태 전이·장애 뒤 재처리
외부 메시지 서비스여러 실행자·서버 사이저장·확인 응답·재전달의 계약과 설정

프로세스 사이에 값을 전달할 수 있다는 사실은 값을 영구 보관한다는 뜻이 아닙니다. 반대로 DB에 작업 행을 저장했어도 실제 실행자가 가져가거나 실패를 회수하는 코드는 별도로 필요합니다. 통신, 보관, 실행, 복구는 연결돼 있지만 같은 기능은 아닙니다.

단일 서버의 작은 서비스에서는 DB 작업 테이블을 큐처럼 사용할 수 있습니다. 입력 버전과 상태를 한 저장소에서 연결하기 쉬운 장점이 있습니다. 다만 같은 로컬 파일을 여러 서버에서 쓰는 구조로 저절로 확장되지는 않습니다. 작업량과 장애 요구가 커지면 저장소의 지원 범위와 운영 방법을 다시 판단해야 합니다.

8-3. 접수했다는 말을 하기 전에 무엇을 기록할까

가상 흐름에서 사용자는 입력 v7으로 계획 생성을 요청합니다. 요청 서버는 요청 권한과 기본 조건을 확인하고 작업 J7을 만듭니다. 작업에는 업무용 식별자인 job_id, 사용할 입력 버전, 상태, 필요하다면 실행 시도 번호를 연결합니다. 이 항목들은 이론 설명을 위한 설계 예시이며 현재 교재가 하나의 통합 서버로 제공하는 API는 아닙니다.

처음 상태를 QUEUED, 즉 대기 중이라고 부르겠습니다. DB 저장을 확정한 뒤 작업 ID로 접수 응답을 보냅니다. DB 변경을 확정하는 것을 커밋이라고 합니다. 메모리에 잠깐 적은 뒤 “저장 완료”라고 응답하거나, 아직 실패할 수 있는 DB 기록 전에 재시작 보존을 약속하면 실제 상태와 사용자 안내가 어긋납니다.

접수 응답 뒤 사용자는 J7을 조회합니다. 대기·실행·검증 실패·성공 같은 상태를 읽고, 성공일 때 어떤 확정 결과를 볼 수 있는지 확인합니다. 진행률 60%는 사용자를 돕는 표시이지만 완료의 근거가 아닙니다. 단계별 비중을 임의로 정한 값일 수도 있고 갱신이 멈췄을 수도 있습니다.

작업의 수명과 요청 연결의 수명도 다릅니다. 브라우저를 닫거나 요청 응답을 기다리다 시간이 끝나도 J7이 실행 중일 수 있습니다. 사용자가 다시 접속했을 때 같은 작업을 찾을 식별자가 필요합니다. 그래서 운영체제의 PID를 업무 작업 ID 대신 쓰지 않습니다. 프로세스는 끝나고 번호가 재사용될 수 있지만 작업 기록은 계속 조회해야 하기 때문입니다.

8-4. 두 Worker가 같은 일을 가져가지 않게 하기

선점은 여기서 대기 중인 작업을 한 실행자가 자신이 맡을 작업으로 확보하는 일을 뜻합니다. Worker A와 B가 둘 다 “J7은 대기 중”이라는 값을 읽고 각자 계산을 시작하면 같은 일을 두 번 수행할 수 있습니다. 읽기와 맡기기를 아무 규칙 없이 떨어뜨려 놓은 것이 원인입니다.

한 가지 방법은 “대기 행을 찾고, 여전히 대기 상태일 때 실행 중으로 바꾼다”를 짧은 DB 트랜잭션으로 묶는 것입니다. 트랜잭션은 정한 변경 묶음을 하나의 확정 경계로 다루는 도구입니다. 상태를 QUEUED → RUNNING으로 바꾸고 실제로 한 행이 바뀌었는지 확인합니다. 다른 실행자가 이미 가져갔다면 자신도 가져갔다고 가정하지 않습니다.

긴 배정 계산을 선점 트랜잭션 안에서 모두 수행하는 것은 피할 이유가 있습니다. 다른 작업이 필요한 DB 쓰기를 오래 기다릴 수 있기 때문입니다. 짧게 맡기기를 확정하고 계산은 그 경계 밖에서 수행한 뒤, 마지막 저장 때 현재 권한을 다시 확인하는 구조를 생각할 수 있습니다. 계산을 바깥으로 옮긴 만큼 그 사이의 상태 변화에 대응해야 합니다.

선점 성공은 업무 성공이 아닙니다. RUNNING은 어떤 실행자가 맡았다는 기록입니다. 생성·검사·확정이 남아 있습니다. 선점 직후 Worker가 사라지면 결과 없이 RUNNING만 남을 수 있습니다. 이 사실이 선점과 복구를 별도 질문으로 다뤄야 하는 이유입니다.

8-5. 계산과 검사를 마쳤어도 확정 조건을 확인한다

Worker가 가상의 정상 후보를 만들면 Validator가 원본 입력과 규칙에 맞춰 검사합니다. 통과한 후보도 즉시 누구나 덮어쓸 수 있게 저장하지 않습니다. 계산 중 새 입력 v8이 적용됐거나, 취소·재시도로 다른 실행 시도가 유효해졌을 수 있습니다. 후보가 자기 입력에 맞는 것과 지금 공개할 권한이 있는 것은 다른 조건입니다.

확정 경계에서는 입력 버전, 현재 작업 상태, 실행 시도 번호, 검사한 후보의 동일성 등을 확인할 수 있습니다. 충족할 때 결과 공개와 성공 상태를 함께 확정해야 사용자가 “성공인데 결과 없음” 같은 어긋난 상태를 읽을 가능성을 줄일 수 있습니다. 구체적인 DB 조건부 갱신은 9장에서 차근차근 다룹니다.

검증 실패라면 어떤 규칙을 어겼는지 진단하고 새 후보를 공식 결과로 바꾸지 않습니다. 이전 성공 결과가 있다면 이 가상 설계에서는 보존합니다. 다만 이전 결과가 현재 입력과 다른 버전일 수 있으므로 사용자에게 결과의 기준 버전을 표시해야 합니다. 이전 계획이 남아 있다는 사실과 새 생성이 성공했다는 안내를 섞지 않습니다.

자동 재시도도 모든 실패에 맞는 해결책은 아닙니다. 없는 직원 ID를 참조하는 입력은 같은 내용으로 반복해도 보통 해결되지 않습니다. 일시적인 실행 장애는 재시도할 수 있지만 횟수·대기·오래된 실행의 확정 차단을 정해야 합니다. 실패 종류와 재시도 효과를 함께 설명할 수 있어야 합니다.

8-6. Worker가 사라졌을 때 회수는 누가 할까

RUNNING이라는 글자는 Worker의 현재 생존을 보증하지 않습니다. 마지막 기록 이후 프로세스가 종료됐을 수 있습니다. heartbeat는 실행자가 살아서 일하고 있음을 주기적으로 알리는 신호입니다. 임대는 일정 기간 동안 작업을 맡을 권한을 주는 방식입니다. 관리자는 신호와 만료 조건을 보고 작업을 다시 대기로 돌리거나 실패 처리할 수 있습니다.

오랫동안 신호가 없다고 옛 Worker가 확실히 사라졌다고 단정할 수도 없습니다. 일시 정지나 통신 지연 뒤 돌아올 수 있습니다. 회수 후 새 실행에 시도 번호를 주고, 옛 번호의 결과 확정을 거절하는 조건이 필요합니다. 그렇지 않으면 새 결과가 저장된 뒤 옛 계산이 덮어쓸 수 있습니다. 회수와 오래된 실행 차단은 한 쌍으로 생각합니다.

외부 메시지 서비스에서 쓰는 확인 응답, 또는 ack도 어느 단계의 확인인지 중요합니다. 메시지를 받자마자 완료 확인을 보내고 계산 중 죽으면 다시 전달받지 못할 수 있습니다. 결과 저장 뒤 확인하면, 저장은 됐지만 확인 응답이 유실돼 다시 받을 수 있습니다. 따라서 전달과 실행을 항상 한 번으로 만들었다고 가정하기보다 중복 실행 시 확정이 안전한지 확인합니다.

작업이 너무 많이 쌓이는 문제도 남습니다. Worker를 늘리면 CPU·메모리·DB 경쟁이 커질 수 있고, 대기열만 늘리면 사용자의 결과 대기가 길어집니다. 대기 작업 수와 최대 동시 실행 수를 제한하고 실제 대기·계산·검증·확정 시간을 관찰해야 합니다. 큐를 두었다는 사실만으로 처리 용량이 늘지는 않습니다.

8-7. 보충 예제에서 실행한 것과 설명한 것

examples/ch10.py는 임시 폴더에 파일 SQLite DB를 만들고 대기 작업 하나를 넣습니다. spawn 방식으로 별도 Python 프로세스 두 개를 시작합니다. 각 Worker는 BEGIN IMMEDIATE로 짧은 선점 트랜잭션을 열고 대기 작업을 RUNNING으로 바꿉니다. 한 실행자가 맡은 뒤 다른 실행자는 그 작업을 다시 대기 작업으로 가져가지 않습니다.

일을 가져간 프로세스는 fictional-plan이라는 고정 문자열과 자기 PID를 저장하고 상태를 SUCCEEDED로 바꿉니다. 부모는 자식 종료 코드, 저장된 PID가 부모와 다른지, 최종 행이 하나인지, 다시 가져갈 대기 작업이 없는지를 확인합니다. 책의 예제 폴더에서 python examples/ch10.py로 실행할 수 있습니다.

여기에는 실제 Creator·Validator 호출, 근무자 배정, 임대·heartbeat·자동 회수가 없습니다. 출력의 recovery_after_claim_tested: false는 선점 뒤 죽음의 복구를 확인하지 않았다는 뜻입니다. SUCCEEDED도 이 작은 실험의 고정 결과 저장 상태이며 실제 계획이 유효하다는 판정이 아닙니다. 임시 DB는 실험 종료 뒤 정리되므로 사용자에게 영구 결과 파일을 남기는 예제도 아닙니다.

자신의 프로젝트에서는 작업 등록 경로, 선점 코드, 프로세스 시작점, 상태 조회, 확정 조건, 회수 관리자를 찾아 하나씩 연결합니다. 존재하지 않는 회수 기능은 “설계상 필요하지만 현재 미구현”이라고 말합니다. 별도 프로세스를 만들었다는 증거와 장애 뒤 사용자가 결과를 확인할 수 있다는 증거는 따로 제시해야 합니다.
