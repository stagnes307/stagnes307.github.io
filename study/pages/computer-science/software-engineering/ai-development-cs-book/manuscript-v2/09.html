계산이 맞았다고 해서 그 결과를 지금 공개해도 되는 것은 아닙니다. 계산하는 동안 입력이 바뀌었거나, 취소한 작업이 뒤늦게 끝났을 수 있습니다. 이번 장은 “좋은 후보를 만들기” 다음에 남는 일, 즉 현재의 올바른 결과만 안전하게 확정하는 방법을 설명합니다.

9-1. DB는 기록을 관리하고, 트랜잭션은 변경을 묶는다

DB는 데이터베이스의 줄임말이며, 데이터를 저장하고 정해진 조건으로 찾고 바꾸는 시스템입니다. 파일에 저장하는 DB는 나중에 다시 펼칠 수 있는 기록장에 비유할 수 있습니다. 다만 메모리 전용 DB는 프로세스 종료 뒤 남지 않으므로 실제 저장 방식도 확인해야 합니다. 테이블은 같은 모양의 기록을 모아 둔 표입니다. 작업 표에는 작업 번호, 입력 버전, 상태를 한 행에 기록할 수 있습니다. 여기서 행은 작업 한 건에 해당합니다. SQL은 이런 표를 조회하거나 바꾸는 데 사용하는 언어입니다.

하지만 DB를 쓴다고 모든 기록이 저절로 함께 바뀌지는 않습니다. 새 계획은 저장했는데 작업 상태를 성공으로 바꾸기 전에 프로그램이 죽으면, 화면에는 실행 중으로 보이면서 결과만 바뀔 수 있습니다. 반대로 상태만 성공이고 결과가 없다면 사용자는 무엇을 믿어야 할까요? 서로 맞아야 하는 변경을 하나의 묶음으로 다루어야 합니다.

트랜잭션은 관련된 DB 작업을 하나의 성공 또는 실패 단위로 다루는 경계입니다. 은행에서 A의 돈을 줄이고 B의 돈을 늘리는 두 변경이 함께 확정되어야 하는 것과 비슷합니다. 커밋은 변경을 확정하는 일이고, 롤백은 아직 확정하지 않은 묶음의 변경을 되돌리는 일입니다. “후보를 공식 결과로 저장하기”와 “해당 작업을 성공으로 표시하기”가 같은 경계에 있어야 둘 사이의 모순을 줄일 수 있습니다.

이 비유에도 범위가 있습니다. DB 트랜잭션이 이메일 발송이나 이미 외부 업체에 전송한 명령까지 되돌려 주지는 않습니다. 먼저 무엇이 같은 DB 안의 변경이고 무엇이 밖에서 일어나는 효과인지 구분해야 합니다. 하나의 함수에 적혀 있다는 사실도 같은 트랜잭션이라는 증거가 되지 않습니다.

9-2. 긴 계산보다 짧은 확정 경계가 중요한 이유

배정 생성에 30초가 걸린다고 가정해 봅시다. 이 시간 내내 DB를 바꾸는 권한을 잡고 있으면 다른 요청의 데이터 적용이나 상태 변경이 기다릴 수 있습니다. 잠금은 여러 실행이 같은 자료를 바꾸려 할 때 허용 순서를 조정하는 수단입니다. 잠금은 필요한 충돌을 막지만, 오래 유지하면 기다리는 시간도 길어질 수 있습니다.

이 책의 설명용 설계는 입력을 고정해 읽고, 그 입력으로 계산하고 검사한 뒤, 짧은 트랜잭션에서 확정 조건을 다시 확인합니다. 책상에서 초안을 작성하는 동안 금고 문을 계속 붙잡지 않고, 마지막으로 서류를 넣는 순간에 필요한 확인을 모으는 셈입니다. 다만 입력을 읽는 시점에 정한 기준이 최종 공개 순간에도 맞는지 다시 검사해야 합니다.

  1. 적용된 입력 v7을 읽어 이번 작업이 사용할 고정본을 만든다.
  2. DB 쓰기 경계 밖에서 후보를 계산하고, 같은 고정본과 규칙으로 검사한다.
  3. 확정 트랜잭션을 열고 현재 입력 버전과 작업의 실행 권한을 확인한다.
  4. 조건이 맞을 때 결과와 성공 상태를 함께 기록하고 커밋한다.
  5. 조건이 달라졌다면 확정을 거절하고 기존 공식 결과를 보존한다.

이 순서는 설계 원리입니다. 실제 프로그램이 이 흐름을 구현했는지는 호출 경로와 SQL을 읽고, 실패 전후의 기록을 확인해야 알 수 있습니다. 모든 계산에 짧은 트랜잭션 구조가 자동으로 적합한 것도 아닙니다. 요구하는 일관성과 사용 중인 DB의 동작에 맞춰 읽기와 쓰기의 경계를 정해야 합니다.

9-3. 입력 버전은 “어느 문제를 풀었는가”를 나타낸다

버전은 바뀐 자료를 구별하기 위해 붙이는 표시입니다. 오전의 근무표 v7에는 E1·E2·E3가 근무자로 적혀 있었는데, 생성 중에 E3가 휴무로 바뀐 v8이 적용됐다고 해 봅시다. v7을 기준으로 만든 후보는 v7의 규칙을 완벽하게 지켰더라도 v8의 공식 결과로 쓰기에는 맞지 않을 수 있습니다. 계산 오류와 입력이 오래된 문제는 서로 다릅니다.

따라서 후보에는 자신이 사용한 입력 버전이 연결되어야 합니다. 마지막 공개 시점에 후보의 v7과 현재 적용 버전 v8을 비교해, 현재 입력으로 다시 만들어야 하는지 판단합니다. 이 책의 기본 설계는 서로 다르면 현재 결과로 확정하지 않는 쪽입니다. 과거 입력의 결과를 이력으로 보관하는 정책은 별도로 정할 수 있지만, 이력을 최신 결과처럼 표시해서는 안 됩니다.

해시는 데이터 내용을 바탕으로 만든 지문과 같은 값입니다. 검증한 파일 내용이 이후 바뀌었는지 비교하는 데 쓸 수 있습니다. 버전이 “자료의 몇 번째 상태인가”에 가깝다면 해시는 “같은 내용인가”를 확인하는 단서입니다. 해시가 같다는 이유만으로 데이터가 업무적으로 올바르다는 결론은 나오지 않습니다. 잘못된 파일도 지문을 가질 수 있기 때문입니다.

입력 버전만 기록하고 실제 생성기가 그 입력을 읽었는지 확인하지 않으면 연결이 끊깁니다. 기록된 v7과 계산에 사용한 파일이 v8일 수도 있습니다. 버전 표기, 고정본을 전달하는 경로, 검사기가 사용한 입력, 확정된 결과의 연결을 함께 따라가야 합니다.

9-4. 시도 번호는 “지금 확정할 권한이 있는 실행인가”를 나타낸다

같은 입력에서도 오래된 실행이 생길 수 있습니다. 작업 J1의 첫 Worker가 멈춘 것처럼 보여 두 번째 Worker에게 일을 다시 맡겼다고 합시다. 잠시 뒤 첫 Worker도 돌아와 결과를 저장하려 합니다. 두 실행 모두 입력 v7을 썼으므로 입력 버전 비교만으로는 어느 쪽을 막아야 할지 알 수 없습니다.

시도 번호는 같은 업무를 다시 실행할 때 현재 유효한 실행을 구별하는 번호입니다. 코드에서는 세대, epoch, attempt 같은 이름을 쓰기도 합니다. 이번 장에서는 이해를 돕기 위해 “확정권의 차례표”라고 생각해 봅시다. 처음에는 시도 1에 권한을 주고 다시 맡길 때 시도 2로 바꾸면, 시도 1은 뒤늦게 계산을 끝내도 공식 결과를 덮어쓸 수 없어야 합니다.

이런 차단을 펜싱이라고 부릅니다. 울타리처럼 오래된 실행의 쓰기를 막는다는 뜻입니다. 핵심은 Worker가 스스로 “나는 최신이다”라고 말하는 데 있지 않습니다. 최종 저장 경계에서 현재 시도 번호와 후보가 가진 시도 번호를 비교해야 합니다. 현재 상태가 여전히 실행 중인지도 함께 확인해야 취소 후 완료나 같은 후보의 반복 확정을 막을 수 있습니다.

즉 확정 조건은 적어도 세 질문으로 나누어 볼 수 있습니다. 같은 입력의 결과인가, 현재 유효한 시도가 만든 것인가, 아직 확정이 허용되는 상태인가? 번호를 비교하는 순간과 실제 저장 사이가 다시 벌어지면 틈이 생기므로, 조건 검사와 변경을 같은 트랜잭션이나 조건부 변경에 모읍니다.

9-5. 중복 요청과 중복 실행은 비슷해 보여도 다르다

생성 버튼을 눌렀는데 응답이 오지 않아 다시 누른 상황을 생각해 봅시다. 첫 요청이 서버에 도착하지 않았을 수도 있고, 이미 접수됐지만 응답만 사라졌을 수도 있습니다. 사용자의 의도는 한 번인데 요청은 두 번 보일 수 있습니다. 멱등성은 같은 의도를 반복했을 때 추가 효과가 생기지 않도록 다루는 성질을 말합니다.

설명용 설계에서는 사용자와 요청 키를 묶어 동일한 업무를 식별합니다. 같은 사용자·같은 키·같은 내용이면 기존 작업 번호를 돌려줍니다. 같은 키에 다른 내용이 오면 충돌로 거절합니다. 키만 같다고 다른 근무일이나 다른 설정을 조용히 같은 요청으로 취급하면 사용자의 새 의도를 잃을 수 있습니다.

요청 중복 제거는 Worker가 실제로 한 번만 실행된다는 보장과 다릅니다. 재시도 때문에 계산은 두 번 할 수 있어도 최종 저장은 한 번만 허용할 수 있습니다. 반대로 DB 결과는 한 번 저장했는데 이메일이나 외부 결제는 두 번 수행될 수도 있습니다. “멱등 키를 넣었으니 모든 효과가 정확히 한 번이다”라고 말하면 확인 범위보다 주장이 넓어집니다.

외부 효과까지 다룰 때는 DB에 전송할 일을 함께 남긴 뒤 전달하는 방식 등이 필요할 수 있습니다. 이를 깊게 구현하는 일은 이 입문서의 중심에서 벗어나므로, 여기서는 DB 안의 확정과 밖의 효과가 서로 다른 경계라는 점을 기억하면 충분합니다. 무엇을 중복으로 보며, 어디서 막았는지 구체적으로 설명하세요.

9-6. 작은 예제에서 확인할 수 있는 것

보충 파일 examples/ch08.py는 파일 SQLite에서 참조가 잘못된 행을 넣다가 롤백한 뒤 계획 행이 0개인지 확인합니다. 이어서 버전 1일 때만 바꾸는 조건부 변경을 두 번 수행해, 처음에는 1행이 바뀌고 오래된 조건의 두 번째 변경은 0행인지 검사합니다. 연결을 닫고 새로 열어 버전 2가 남아 있는지도 확인합니다. 이것은 재연결 후 보존과 순차 조건부 변경의 근거이며 동시 작성자나 전원 차단 시험은 아닙니다.

examples/ch11.py는 별도의 메모리 SQLite에서 요청 중복 제거와 조건부 확정을 확인합니다. 출력의 job_rows: 1은 같은 요청이 한 행으로 남았다는 뜻입니다. stale_input_rows: 0과 stale_worker_rows: 0은 오래된 입력과 시도의 변경이 거절됐다는 뜻입니다. 올바른 첫 확정은 accepted_rows: 1, 같은 조건의 반복 확정은 repeat_publication_rows: 0입니다.

두 파일은 서로 다른 작은 실험입니다. 하나의 배정 서버가 이 둘을 연달아 호출한다는 뜻은 아닙니다. 특히 ch11.py의 validated-candidate는 검사기를 실제 호출해 얻은 계획이 아니라 교육용 문자열입니다. 이 파일만으로 배정 규칙을 검사했다고 말할 수 없습니다. 파일과 실행 기록을 함께 볼 때 이 구분이 중요합니다.

선택해서 실행하기
python examples/ch08.py
python examples/ch11.py

교재 보충 자료 폴더에서 실행하는 실제 명령입니다. 각 예제는 자기 DB를 만들고 확인한 뒤 정리합니다. 실행 후 운영 서비스의 DB가 생긴다고 기대하지 마세요.

9-7. 안전 장치를 설명할 때는 비용과 빈틈도 함께 말한다

버전 확인으로 오래된 후보를 거절하면 계산한 시간을 버릴 수 있습니다. 긴 계산 중 입력을 자주 바꾸는 서비스라면 재생성 비용을 어떻게 감당할지 정해야 합니다. 하나의 DB에 쓰기를 모으면 단순하지만 동시에 처리할 수 있는 변경량에 한계가 있을 수 있습니다. 별도 프로세스를 늘린다고 이 DB의 쓰기 경계가 사라지지는 않습니다.

가장 먼저 찾을 취약점은 이름이 아니라 우회 경로입니다. 정상 경로에서는 조건부 확정을 쓰는데 다른 관리 함수가 결과를 무조건 저장한다면 울타리가 뚫립니다. 또한 최신 시도 번호를 누가 바꾸고, 취소와 재시도가 어떤 상태에서 허용되는지 불명확하면 조건식을 적어도 전체 규칙은 흔들립니다.

4장에서 본 ch05.py도 이 관점으로 다시 읽을 수 있습니다. 정상 호출 순서에서는 검사 뒤에 공개하지만, publish 함수 자체가 검사를 강제하는 구조는 아닙니다. 다른 호출자가 검사를 건너뛸 수 있는 작은 모형의 빈칸입니다. ch11.py 역시 배정 검사 결과를 스스로 증명하지 않습니다. 버전·시도·상태 조건을 지키는 실험과, 동일한 후보가 실제 배정 검사를 통과했는지 확인하는 책임을 함께 연결해야 전체 확정을 설명할 수 있습니다.

좋은 설명은 “DB로 안전하게 처리했습니다”에서 끝나지 않습니다. “입력 버전·시도 번호·실행 상태가 맞을 때만 같은 트랜잭션에서 공개하고, 변경 행 수가 0이면 거절로 처리합니다. 외부 전송 효과와 실제 동시 요청은 아직 확인하지 않았습니다”처럼 경계와 근거를 붙입니다. 다음 장에서는 바로 그 경계 사이에서 작업이 끊겼을 때 무엇이 남는지 살펴봅니다.

2. 새 결과를 저장한 뒤 작업 상태를 성공으로 바꾸기 전에 서버가 죽으면 어떤 모순이 생길까요?

해설

결과는 새 값인데 상태는 실행 중일 수 있습니다. 사용자 조회와 복구 판단이 어긋나므로 두 변경을 같은 트랜잭션으로 묶는 설계를 검토합니다. 실제로 함께 커밋되는지는 코드와 중단 시험으로 확인해야 합니다.

3. ch11.py가 성공했다는 근거로 “배정 검증과 Worker 장애 복구를 모두 확인했다”고 말해도 될까요?

해설

이 예제는 요청 중복 제거와 입력·시도·상태 조건부 확정의 작은 DB 실험입니다. 실제 배정 검사기나 Worker 장애 복구를 연결하지 않습니다. 근거가 있는 조건부 변경만 설명하고 나머지는 별도 확인 대상으로 남깁니다.
