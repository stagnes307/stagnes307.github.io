설명을 들은 사람이 같은 결론에 도달하려면 따라갈 수 있는 근거가 있어야 합니다. “검증했습니다”라는 말에 파일, 실행 명령, 기대 결과, 실제 기록이 붙으면 다른 사람이 확인할 수 있는 설명이 됩니다. 이번 장은 구현한 것과 아직 모르는 것을 정확하게 보여 주는 방법을 다룹니다.

11-1. 주장을 먼저 작게 나누면 필요한 증거가 보인다

“이 서비스는 안전합니다”는 범위가 너무 넓습니다. 잘못된 입력을 거절한다는 뜻인지, 중복 배정을 막는다는 뜻인지, Worker가 죽어도 복구된다는 뜻인지 알 수 없습니다. 먼저 관찰할 수 있는 작은 문장으로 바꿉니다. 예를 들어 “없는 직원 ID를 참조하는 데이터를 적용하면 오류가 나고 이전 입력이 바뀌지 않는다”는 어떤 입력과 전후 상태를 볼지 정할 수 있는 주장입니다.

증거는 그 주장을 뒷받침하는 관찰과 기록입니다. 코드가 존재한다는 것, 테스트가 실행됐다는 것, 기대 결과와 같았다는 것은 서로 다른 단계입니다. 파일에서 검사 함수를 찾았더라도 실제 요청 경로가 그 함수를 호출하지 않을 수 있습니다. 테스트 명령을 적었어도 실행하지 않았다면 결과의 근거는 아닙니다.

확인할 것은 네 묶음입니다. 어떤 코드와 입력을 썼는가, 어떤 명령을 실행했는가, 무엇을 기대했는가, 실제로 무엇을 관찰했는가? 여기에 확인하지 않은 범위를 붙이면 설명의 경계가 분명해집니다. “정상 입력 1개와 잘못된 참조 1개를 검사했지만 날짜 오류와 실제 DB 장애는 확인하지 않았다”처럼 좁게 말해도 충분히 유용합니다.

서로 다른 증거를 하나로 합쳐 더 큰 성공으로 만들지 않는 것도 중요합니다. 스레드 실험, DB 실험, 계획 검사기 실험이 각각 통과했다고 해서 세 개를 연결한 전체 서버가 통과한 것은 아닙니다. 연결 자체에도 입력 전달 오류나 호출 누락이 있을 수 있습니다.

11-2. 파일을 볼 때는 이름보다 호출과 조건을 본다

파일 이름이 validator.py라고 해서 올바른 검증기가 되는 것은 아닙니다. 그 안에서 무엇을 입력으로 받고, 어떤 규칙을 확인하고, 위반을 어떻게 반환하는지 읽어야 합니다. 생성기가 남긴 “성공” 값을 그대로 읽어 승인한다면 생성 결과를 독립적으로 검사했다고 보기 어렵습니다.

호출 경로는 한 동작이 어떤 함수들을 거쳐 진행되는지 나타내는 순서입니다. “적용” 버튼에서 시작해 서버의 요청 처리, 데이터 검증 함수, 저장 함수로 이어지는 길을 따라갑니다. 검사 함수 자체가 옳더라도 저장 함수가 다른 길에서 무조건 실행된다면 적용 전 검사가 빠질 수 있습니다.

이 책에서 실제로 열어 볼 파일은 examples/ch04.py의 validate와 apply, examples/ch13.py의 check입니다. ch04.py에서는 apply가 같은 고정본을 검증한 뒤 해시를 비교하고 메모리 상태를 바꾸는지 확인합니다. ch13.py에서는 후보의 사람·방향별 횟수를 기대 횟수와 비교하고 정원과 시간 조건을 확인하는지 읽습니다.

이 파일들에는 실제 웹서비스의 데이터셋 선택 화면이나 전체 배정 생성기가 없습니다. 개인 프로젝트를 점검할 때 찾을 파일 이름은 달라질 수 있습니다. dataset_service.py, worker.py, plan_repository.py 같은 이름은 역할을 설명하기 위한 예시일 뿐, 이 교재가 제공하는 실제 서비스 파일이 아닙니다. 내 저장소에서 실제 경로와 함수 이름으로 바꾸어 적어야 합니다.

11-3. 제3자가 실행할 명령에는 시작 위치와 기대 결과가 필요하다

명령 한 줄만 보내면 상대는 어디에서 실행해야 하는지 모를 수 있습니다. 보충 자료의 폴더를 내려받았다면 examples 폴더가 보이는 위치에서 다음 명령을 실행합니다. Python 3.11 이상을 기준으로 하며 이 작은 예제들은 외부 패키지를 요구하지 않습니다. 파일 하나만 받았다면 그 파일이 있는 폴더에서 파일 이름만 지정합니다.

python examples/ch04.py
python examples/ch13.py

ch04.py는 일곱 종류의 축소 가상 CSV를 사용합니다. 출력에서 잘못된 직원 참조를 거절했는지, 검증 후 내용이 바뀐 입력을 거절했는지, 이전 메모리 상태를 보존했는지 봅니다. ch13.py는 별도의 두 직원·야간 근무 사례입니다. 이 책 본문의 세 근무자·주간 사례를 실행한 결과가 아닙니다. 출력은 정상 후보 통과와 누락·중복·휴무자·시간·정원 등을 일부러 바꾼 아홉 가지 변이 감지를 보여 줍니다.

종료 코드는 실행한 프로그램이 어떻게 끝났는지 알리는 숫자입니다. 보통 0은 정상 종료를 뜻하지만, 무엇을 실제로 검사했는지는 코드 안의 조건과 출력에서 읽어야 합니다. 아무것도 검사하지 않는 프로그램도 0으로 끝날 수 있기 때문입니다. 기대한 거절 조건과 전후 상태가 코드에 포함되어 있는지 함께 확인하세요.

Windows PowerShell에서는 명령 직후 $LASTEXITCODE로 직전 프로그램의 종료 코드를 볼 수 있습니다. 이 값이 0이어도 화면에서 출력 일부를 복사하는 것만으로 전체 실행 맥락이 보존되지는 않습니다. 실행 시각, Python 버전, 코드 버전, 입력과 설정을 기록해 다른 사람이 같은 조건을 준비할 수 있게 합니다.

11-4. 상태는 결과 화면뿐 아니라 저장 위치를 나누어 확인한다

오류 메시지를 봤다는 것과 이전 데이터가 보존됐다는 것은 같은 관찰이 아닙니다. 잘못된 데이터를 적용하기 전 입력 버전 v7과 공식 결과 F3를 읽어 둡니다. 실패를 일으킨 뒤 다시 읽어 v7과 F3가 그대로인지 비교해야 보존을 확인할 수 있습니다. 실제 DB를 쓰는 서비스라면 새 연결로 읽는 확인도 유용합니다. 실행 중인 객체의 오래된 값을 보고 DB가 보존됐다고 착각하는 일을 줄일 수 있습니다.

작업과 결과의 상태도 나누어 봅니다. 작업 J1이 검증 실패라고 기록됐어도 공식 결과 F3는 성공 이력으로 남을 수 있습니다. “현재 작업 실패”와 “사용 가능한 이전 결과 존재”는 함께 성립합니다. 후보 C1이 보관돼 있다면 왜 공개되지 않았는지 위반 보고서와 연결되어야 합니다.

확인 대상과 물어볼 질문
대상확인할 값판단할 수 있는 것

이 표의 항목은 개인 프로젝트에 대입할 점검 항목입니다. 교재의 모든 작은 예제에 이 상태들이 전부 구현되어 있다는 뜻은 아닙니다. 기록이 없다면 로그 문장을 추측해 채우지 말고 “현재 저장하지 않아 확인할 수 없음”이라고 적습니다. 그 빈칸 자체가 관측 기능을 보완할 근거가 됩니다.

11-5. 실행 기록과 파일 해시를 함께 읽는다

교재의 verification.json은 보충 예제의 실행 기록을 모은 자료입니다. 명령, 실행 환경, 종료 코드, 표준 출력, 코드 해시를 대조해 읽습니다. 표준 출력은 프로그램이 일반 결과를 내보내는 통로이고, 표준 오류는 오류나 진단을 내보내는 통로입니다. 어느 한쪽이 비어 있다고 모든 장애가 없었다고 결론내릴 수는 없습니다.

SHA-256은 파일 내용의 지문을 계산하는 한 방식입니다. 내려받은 코드의 해시가 실행 기록의 코드 해시와 다르면, 그 기록이 지금 파일을 실행한 결과인지 다시 확인해야 합니다. 해시가 맞더라도 입력과 환경이 달라지면 결과가 달라질 수 있으므로 이것 하나가 모든 재현 조건을 대신하지는 않습니다.

ch04.py의 파일 지문을 계산하는 실제 명령
python -c "import hashlib; from pathlib import Path; print(hashlib.sha256(Path('examples/ch04.py').read_bytes()).hexdigest())"

examples 폴더가 보이는 위치에서 실행합니다. 출력값을 해당 예제의 실행 기록에 있는 코드 SHA-256과 비교합니다. 이것은 파일 내용의 동일성 확인이며 코드가 옳다는 검사와는 별개입니다.

특히 기록의 확인 범위를 읽으세요. ch10.py의 정상 완료 기록에는 장애 후 자동 회수를 확인하지 않았다는 표시가 있습니다. ch13.py는 실제 방향별 경로 이동시간을 계산하지 않습니다. ch14.py는 근거 없는 완료 주장을 걸러 내는 교육용 목록 실험입니다. 그 안에 “통과”라고 적힌 자료도 실제 운영 서비스의 인증서가 아닙니다.

독립적인 사람이 다시 실행해 같은 관찰을 얻는 일은 신뢰를 높입니다. 다만 같은 입력 몇 개가 통과했다는 사실이 가능한 모든 입력의 정확성을 증명하지는 않습니다. 무엇을 바꾸어도 지켜져야 할 규칙을 찾고 그 규칙을 깨는 예를 더해 가는 방식으로 확인 범위를 넓힙니다.

11-6. 반례를 만들어 검사가 실제로 거절하는지 본다

정상 입력만 넣으면 검사기가 늘 “통과”라고 답해도 성공처럼 보입니다. 그래서 반례, 즉 주장이 성립하지 않는 상황을 의도적으로 만듭니다. 정상 후보에서 E3의 퇴근 배정을 지우고, E1을 한 번 더 넣고, 휴무자 E4를 추가하고, 정원을 줄여 봅니다. 위반이 생겼을 때 예상한 이유로 거절하는지 확인해야 합니다.

이처럼 자료의 한 부분을 의도적으로 바꾼 것을 여기서는 변이라고 부릅니다. 한 번에 여러 부분을 바꾸면 어느 규칙이 실패를 잡았는지 알기 어려우므로 처음에는 한 조건씩 바꿉니다. 잘못된 후보가 거절됐어도 이유가 예상과 다르면 다른 결함에 가려졌을 가능성을 살펴봅니다.

오류 입력, 오류 후보, 장애는 확인 대상이 다릅니다. 없는 직원 ID를 넣는 것은 입력 검증 시험이고, E3가 빠진 계획을 넣는 것은 결과 검증 시험입니다. Worker를 선점 직후 종료하는 것은 복구 시험입니다. 입력 시험을 많이 했다는 이유로 Worker 장애를 확인했다고 말하지 않습니다.

성능과 품질도 별도입니다. 빨리 끝났다고 근무자 전원이 배정됐다는 보장은 없습니다. 버스 수가 줄었더라도 한 사람이 빠져 줄어든 것이라면 개선으로 셀 수 없습니다. 동일한 입력과 조건에서 먼저 유효성을 확인하고, 그다음 차량 수·소요 시간·계산 시간 등의 지표를 비교합니다. 작은 교재 예제를 실제 규모의 성능 측정으로 확대하지 마세요.

11-7. 구현 설명과 취약점 보고에 쓸 수 있는 양식

다음 양식은 자신의 프로젝트에 대입하기 위한 예시입니다. 빈칸을 실제로 확인한 내용으로 채우고, 해당하지 않는 항목은 이유를 적습니다. 특히 완료 여부를 “구현함”, “다른 계층이 담당”, “미구현”, “실행 미확인”으로 나누면 함수의 존재와 실제 보장을 혼동하는 일을 줄일 수 있습니다.

내 프로젝트의 근거를 채우는 양식
항목직접 채울 내용

취약점은 “어느 경계에서”, “무엇이 보장되지 않아”, “누가 어떤 불편이나 잘못된 결과를 겪는가”로 작성합니다. 예를 들어 선점 후 회수가 없으면 작업이 영원히 실행 중으로 남을 수 있습니다. 여기에 해당 코드와 재현 기록이 붙으면 개선 우선순위를 논의할 수 있습니다.

하나의 기록으로 결론이 나지 않을 때는 불확실성을 숨기지 않습니다. 요청 경로를 읽었지만 실제 HTTP 호출은 실행하지 않았을 수도 있습니다. 그 경우 코드상 연결 확인과 실행 검증을 나누어 적으면 됩니다. 다음 장에서는 이 근거들을 길게 나열하는 대신 질문에 맞게 묶어 말하는 연습을 합니다.

1. “잘못된 데이터를 거절했다”는 화면 캡처가 있습니다. 이전 입력과 공식 결과까지 보존됐다고 말하려면 무엇이 더 필요할까요?

해설

적용 전후 입력 버전·내용과 공식 결과 식별자·내용을 비교해야 합니다. 실제 DB라면 새 연결의 조회도 확인합니다. 오류 응답은 거절 표현의 근거이고, 상태 보존은 별도 관찰이 필요합니다.

2. ch13.py가 정상 종료했습니다. 본문의 세 근무자 사례와 실제 노선 이동시간을 검증했다고 말할 수 있을까요?

해설

아닙니다. 그 파일은 두 직원의 야간 사례로 횟수·정원·시간과 아홉 변이를 검사합니다. 본문 사례 및 실제 경로 계산은 별도입니다. 코드와 출력의 확인 범위를 먼저 읽어야 합니다.

3. 정상·입력 오류·후보 오류 시험이 모두 통과했습니다. 가장 약한 부분을 찾으려면 어떤 질문을 더 할 수 있을까요?

해설

선점 직후 종료, 커밋 직후 응답 유실, 입력 교체, 옛 Worker의 늦은 저장 같은 경계를 묻습니다. 이미 확인한 시험 수보다 아직 끊어 보지 않은 경계와 실제 사용자 영향을 살펴야 합니다.
