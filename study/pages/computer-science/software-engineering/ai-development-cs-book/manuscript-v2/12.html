이제 용어를 하나씩 정의하는 단계를 지나, 요청 하나가 어디를 거쳐 어떤 결과를 남기는지 연결해 봅시다. 목표는 멋진 설계 이름을 많이 말하는 것이 아니라 내가 한 일, 하지 않은 일, 확인한 근거를 질문에 맞게 설명하는 것입니다. 이 장의 답변은 가상 사례와 교재 보충 예제를 기준으로 하므로 실제 프로젝트에 맞게 바꾸어야 합니다.

12-1. 답변은 개념·순서·실패·근거·한계를 연결한다

“비동기, 프로세스, 검증기, 트랜잭션을 사용했습니다”라는 목록만으로 실제 동작을 그리기는 어렵습니다. 먼저 실행 구조, 업무 규칙, 실패 뒤 결과 중 무엇을 묻는지 나누고 질문에 맞는 흐름부터 설명합니다.

답변을 만드는 데 쓸 수 있는 순서는 다섯 가지입니다. 첫째, 필요한 개념을 한 문장으로 구분합니다. 둘째, 실제 흐름을 입력에서 결과까지 따라갑니다. 셋째, 한 지점에서 실패하면 무엇이 남는지 말합니다. 넷째, 이를 확인할 파일·명령·상태를 제시합니다. 다섯째, 구현하지 않았거나 확인하지 않은 범위와 선택의 비용을 밝힙니다.

이는 자가 점검용이며 공식 채점표는 아닙니다. “DB를 썼다” 뒤에 무엇을 함께 확정하는지, “검증했다” 뒤에 어떤 규칙과 반례를 확인했는지가 따라오는지 보세요.

아래 질문의 예시를 외우기보다 실제 파일과 관찰을 연결하세요. 코드가 없는 부분은 설계 설명으로 구분합니다.

12-2. 질문 1: 데이터셋 선택·검증·적용에서 무엇을 구현했는가

질문: 데이터셋 선택·검증·적용에서 실제로 구현하고 검증한 규칙은 무엇인가요? 구현하지 않았거나 다른 계층에 맡긴 것은 무엇인가요? 잘못된 데이터와 계산 결과를 제3자가 확인하려면 어떤 파일, 명령, 상태를 보면 되나요?

먼저 세 동작을 나눕니다. 선택은 사용할 자료를 지정하는 일, 검증은 자료가 정한 규칙을 만족하는지 확인하는 일, 적용은 그 자료를 이후 작업의 기준으로 바꾸는 일입니다. 자료를 읽거나 화면에서 선택했다고 검증·적용까지 끝난 것은 아닙니다. 검증한 고정본과 적용한 내용이 같아야 한다는 연결도 필요합니다.

교재 보충 예제를 기준으로 한 답변 예시

“ch04.py는 일곱 이름의 축소 CSV 묶음을 받습니다. 필수 열과 중복 헤더, 빈 셀과 초과 셀, 직원 ID 중복, 일부 참조 관계, WORK/OFF 상태, 이동시간의 양수를 검사합니다. apply는 같은 고정본을 다시 검증하고 내용 해시를 확인한 뒤 메모리 상태를 바꿉니다. 잘못된 직원 참조와 해시가 달라진 자료의 적용을 실제로 호출해 거절하고 이전 상태를 비교합니다.”

“다만 날짜 실재성, 모든 표의 업무 키 중복, 수요표의 모든 교차 규칙, DB 장애 중 원자적 적용은 이 예제에 없습니다. 데이터셋 선택 화면과 서버 API도 구현하지 않습니다. 제3자는 examples/ch04.py의 validate·apply·main과 실행 기록을 확인하고 python examples/ch04.py로 같은 작은 실험을 재현할 수 있습니다.”

“다른 계층에 맡겼다”는 설명에는 담당자만 적지 말고 연결을 붙입니다. 예를 들어 실제 서버가 인증·인가를 담당한다고 말하려면 요청마다 권한을 확인하는 경로가 있어야 합니다. DB가 참조 무결성, 즉 참조 대상이 실제로 존재하도록 유지하는 규칙을 담당한다고 말하려면 실제 제약과 활성 설정, 위반 시 동작을 확인해야 합니다. 다른 계층 이름을 말하는 것만으로 그 책임이 이행되지는 않습니다.

계산 결과 확인은 입력 검증과 별도입니다. 보충 ch13.py는 두 직원의 야간 사례에서 누락·중복·휴무자·정원·시간과 변이를 검사합니다. 이것은 본문의 세 근무자 전체 서비스나 실제 노선 계산을 실행한 증거가 아닙니다. 개인 프로젝트에서는 입력 규칙표와 출력 규칙표를 각각 실제 파일·테스트·전후 상태에 연결해 답합니다.

12-3. 질문 2: Creator·Validator의 병렬 처리와 별도 프로세스는 어떻게 다른가

질문: Creator와 Validator는 왜 나누었고 무엇을 병렬로 처리하나요? 별도 프로세스와 비동기 처리는 어떤 차이가 있나요? 최종 플랜이 올바른지는 어떻게 판단하나요?

Creator는 제약을 만족하는 후보를 찾고, Validator는 주어진 후보를 입력과 규칙에 대조합니다. 역할 분리는 “무엇을 책임지는가”의 문제입니다. 병렬 처리는 “어떤 일을 동시에 실행할 수 있는가”의 문제입니다. 프로세스 분리는 “어떤 실행·메모리 경계에서 동작하는가”의 문제입니다. 서로 연결될 수 있지만 같은 말은 아닙니다.

설명용 설계를 기준으로 한 답변 예시

“같은 완성 후보의 최종 검증은 생성이 끝난 뒤 수행합니다. 입력 파일별 기본 검사처럼 독립적인 일은 겹쳐 처리할 수 있지만, 교차 참조 검사나 합친 계획의 전역 검사는 필요한 자료가 모인 뒤 해야 합니다. 부분 계획이 각각 정원을 지켜도 합칠 때 한 직원이 중복될 수 있기 때문입니다.”

“비동기는 호출한 쪽이 완료까지 붙잡혀 기다리지 않도록 흐름을 구성하는 방식이고, 별도 프로세스는 실행 인스턴스와 일반 메모리의 경계를 나누는 방식입니다. async 함수 선언만으로 별도 프로세스가 생기지 않습니다. 실제 프로세스 시작 코드, PID, 통신 경로와 저장 상태를 보아야 합니다.”

독립 검증에서는 생성기가 잘했다고 말한 값만 믿지 않습니다. 원본 근무표에서 날짜·방향별 대상과 기대 횟수를 만들고 후보의 횟수와 비교합니다. E1·E2·E3는 출근·퇴근 각 1회, E4는 0회인지 보고, 정원과 실제 시간 조건도 확인합니다. 집합에 세 사람이 모두 있다고 끝내지 말고 한 사람이 두 번 들어간 경우를 검사해야 합니다.

교재의 ch06.py는 의존 관계와 지역 성공·전역 실패를 설명하는 작은 실험이며 실제 병렬 실행기는 아닙니다. ch09.py는 같은 프로세스의 코루틴들이 대기를 겹치는 순서를 확인합니다. ch10.py는 별도 프로세스 두 개의 선점과 정상 완료를 확인하지만 결과는 교육용 문자열이고 생성기·검사기를 연결하지 않습니다. 이 세 사실을 합쳐 “병렬 배정 서버가 완성됐다”고 말하지 않습니다.

12-4. 질문 3: 정상 처리와 실패 뒤 사용자의 결과는 무엇인가

질문: 근무자 전원이 정상 배정되는 흐름을 설명해 주세요. 생성 도중 시간제한, Worker 사망, 검증 실패가 발생하면 사용자에게 어떤 결과가 남나요? 이 설계의 가장 취약한 지점은 어디인가요?

가상 서비스의 흐름을 설명하는 답변 예시

“검증해 적용한 입력의 고정본과 설정으로 작업을 접수합니다. Worker는 작업을 선점해 후보를 만들고, Validator가 날짜·출퇴근별 누락·중복·휴무자·정원·시간을 확인합니다. 본문 사례는 세 근무자가 두 방향으로 한 번씩 배정되어 총 6개의 사람·방향 배정이 있어야 합니다. 통과한 동일 후보만 입력 버전·시도 번호·작업 상태를 비교한 뒤 공식 결과로 확정합니다.”

“요청을 기다리던 시간이 끝났다면 계산이 멈췄다고 단정하지 않고 작업 번호로 상태와 결과를 조회합니다. 계산 자체가 제한 종료됐다면 유효 후보가 있는지와 독립 검사 결과를 보고 정한 정책에 따라 처리합니다. 불완전 후보를 정상 계획으로 내보내지는 않습니다.”

“Worker가 선점 후 죽으면 회수가 없는 구현에서는 실행 중 상태가 남을 수 있습니다. 검증 실패는 새 후보를 공식 결과로 바꾸지 않고 위반 진단과 작업 실패를 기록하는 설계를 사용합니다. 이전 성공 결과가 있다면 보존하되 입력 버전이 다르면 과거 결과임을 표시합니다. 첫 실행이라면 결과 없음이 남습니다.”

마지막 취약점 답변은 실제 구현에 맞춰 선택해야 합니다. 교재 ch10.py만 기준으로 말하면 선점 후 자동 회수가 없다는 점이 분명한 공백입니다. 실제 프로젝트에 회수가 있다면 임대 만료 뒤 옛 Worker가 확정할 수 있는지, 검증한 후보와 저장한 후보가 같은지, 공식 결과와 성공 상태가 함께 커밋되는지 다음 경계를 봅니다.

개선 방향에는 비용도 붙입니다. 하트비트와 회수 기능은 중단 작업을 발견하고 다시 맡길 수 있게 하지만 느린 작업을 죽은 작업으로 오판할 수 있어 시도 번호와 확정 차단이 필요합니다. 긴 계산을 요청에서 떼면 응답 대기는 줄일 수 있지만 상태 저장·조회·복구 책임은 늘어납니다. 장점만 나열하는 대신 그 선택으로 새로 관리해야 할 일을 말하세요.

12-5. 부족한 답변을 근거 있는 문장으로 바꾼다

말의 범위를 줄이면 설명이 더 정확해진다
부족한 답변바꿔 말할 방향
비동기라서 프로세스가 따로 돕니다.완료를 기다리는 흐름과 실행 프로세스를 구분하고 실제 시작 코드·PID를 확인합니다.
Creator와 Validator는 무조건 병렬입니다.같은 완성 후보에는 선행 의존이 있고 독립 입력 검사 등만 겹칠 수 있습니다.
일곱 CSV를 읽으므로 검증은 끝났습니다.형식·타입·참조·업무 규칙별 구현과 미구현을 나누어 말합니다.
시간 초과면 작업이 실패한 겁니다.대기 종료인지 계산 제한인지 구분하고 작업·확정 상태를 조회합니다.
DB와 큐가 있으니 죽어도 복구됩니다.선점 후 잔존 상태, 감지·회수 정책, 재시도와 옛 실행 차단 근거를 확인합니다.
테스트가 통과했으니 모두 안전합니다.시험한 입력·변이·장애와 아직 확인하지 않은 경계를 제시합니다.

답변을 짧게 만들기 위해 한계를 빼는 대신, 질문에 필요한 한계를 한 문장으로 붙입니다. “파일 DB 재연결은 확인했지만 프로세스 강제 종료 복구는 확인하지 않았습니다” 정도면 무엇을 믿을 수 있는지 분명해집니다. 모르는 부분을 기술 이름으로 덮는 것보다 확인할 다음 행동을 제시하는 편이 낫습니다.

12-6. 내 구현으로 바꾸어 말하는 연습

실제 프로젝트가 있다면 종이에 화살표 다섯 개를 그립니다. 입력 선택 → 검증·적용 → 생성 → 결과 검증 → 확정입니다. 각 화살표 아래 실제 파일과 함수, 읽는 입력 버전, 바꾸는 상태를 적습니다. 별도 Worker가 없다면 있는 것처럼 그리지 말고 같은 요청 안의 함수 호출로 표시합니다.

그다음 첫 화살표에서 실패했을 때, Worker가 일을 맡자마자 죽었을 때, 검증 직후 확정 전에 입력이 바뀌었을 때를 대입합니다. 관찰한 값은 실선으로, 아직 설계만 한 대응은 점선으로 표시해 보세요. 구현과 가정이 섞인 지점이 눈에 들어올 것입니다.

다른 계층에 맡긴 일도 연결합니다. UI가 선택을 제한해도 서버가 임의 ID 요청을 거절하는지, DB가 참조 제약을 가진다면 그 기능이 활성화됐는지, 생성기가 검사기를 실제로 호출하는지 확인합니다. 위임은 “누군가 해 줄 것이다”가 아니라 “이 경계에서 이 계약으로 연결된다”는 설명이어야 합니다.

마지막으로 명령을 받는 제3자를 생각합니다. 빈 환경에서 시작 위치와 필요한 설정을 알 수 있는가, 정상·오류 사례를 실행할 수 있는가, 기대 상태와 미구현 범위를 읽을 수 있는가를 봅니다. 이 교재의 파일명은 작은 예제를 위한 것이므로 자신의 저장소 이름으로 반드시 바꾸어야 합니다.

12-7. 두 분 설명을 준비하는 방법

먼저 30초 동안 요청부터 공식 결과까지 정상 흐름을 말합니다. 다음 30초에는 Creator·Validator의 역할과 실행 순서, 비동기와 프로세스의 차이를 설명합니다. 그다음 30초에는 하나의 장애를 골라 남는 작업·후보·공식 결과를 말합니다. 마지막 30초에는 실제 파일·명령·상태와 가장 약한 경계, 확인하지 않은 부분을 붙입니다. 이것은 연습을 위한 시간 배분입니다.

녹음해서 들으며 “값은 어디에 남지?”, “누가 호출하지?”, “실패 뒤 무엇이 유지되지?”라는 빈틈을 찾습니다. 한 요청의 흐름을 끝까지 설명해 보고 막히는 장으로 돌아가세요.

자가 점검은 다섯 가지로 마칩니다. 용어를 구분했는가, 흐름의 주체와 순서가 맞는가, 실패 뒤 남는 상태를 말했는가, 실제 근거를 제시했는가, 선택의 비용과 미확인을 밝혔는가? 답변이 막히는 부분이 다음에 읽을 장입니다. 읽음 표시를 모두 채우는 것보다 질문 하나를 내 말로 끝까지 설명할 수 있는지가 학습 목표입니다.

세 질문에 내 말로 답하기

1. 데이터셋 선택·검증·적용에서 구현·위임·미구현을 나누고, 제3자가 확인할 파일·명령·상태를 설명하세요. 실제 프로젝트가 없다면 교재 보충 예제의 범위로 답하세요.

답변 점검

세 동작이 구분되는지, 구체 규칙과 실제 apply 호출이 연결되는지, 전후 상태를 확인하는지 봅니다. ch04.py가 모든 일곱 파일의 업무 규칙이나 DB 원자성까지 구현했다고 확대하지 않습니다. 결과 검증은 ch13.py의 별도 범위로 설명합니다.

2. Creator·Validator의 역할, 같은 후보의 의존 순서, 병렬 가능한 작업, 비동기와 별도 프로세스의 차이를 하나의 흐름으로 설명하세요.

답변 점검

역할 분리·실행 순서·실행 자원을 섞지 않았는지 확인합니다. 같은 후보의 최종 검증은 생성 완료 뒤이며 부분 검사 후에는 전역 검사가 필요할 수 있습니다. 실제 프로세스 여부는 시작 코드·PID·통신과 저장 경로의 근거로 말합니다.

3. 정상 전원 배정과 시간제한·Worker 사망·검증 실패 뒤의 사용자 결과를 설명하고 가장 취약한 경계와 근거를 제시하세요.

답변 점검

대기 시간제한과 계산 제한을 구분하고, 실행 중 잔존·회수·옛 실행 차단을 살펴야 합니다. 이전 성공 결과가 있는지와 현재 입력 버전도 확인합니다. 취약점은 실제 구현 근거로 고르고, 교재가 실제 제출 서비스의 장애 복구를 인증한 것처럼 답하지 않습니다.
