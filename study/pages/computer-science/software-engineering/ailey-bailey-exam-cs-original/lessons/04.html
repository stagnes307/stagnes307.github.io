오늘은 웹서비스가 사용자를 어떻게 구분하고, 그 사용자가 무엇을 할 수 있는지 어떻게 결정하는지 배울 거야.

통근버스 서비스를 떠올려 보자. 구성원은 자신의 출퇴근 노선과 거주지를 확인할 수 있어야 하고, 운영자는 전체 노선과 데이터셋을 관리할 수 있어야 해.

그런데 이런 일이 일어나면 어떨까?

구성원 A가 정상적으로 로그인했어. 자기 노선을 조회하다가 요청 주소에 들어 있는 직원 ID를 다른 사람의 ID로 바꿨지. 서버는 A가 로그인했다는 사실만 확인하고, 다른 구성원의 노선과 거주지를 그대로 돌려줬어.

비밀번호도 맞았고, 로그인도 성공했으며, 서버는 정상적으로 200 OK를 반환했어. 프로그램에 오류가 난 것도 아니야.

그런데 이 서비스는 보안에 실패했어.

왜 그럴까?

이 질문에 답하려면 사용자를 알아보는 일과 사용자에게 권한을 주는 일은 서로 다른 판단이라는 사실을 이해해야 해.

오늘 수업의 핵심은 이 두 판단이 매 HTTP 요청에서 어떻게 이루어지는지, 그리고 서버가 그 판단을 유지하고 검증하기 위해 어떤 정보를 관리하는지야.

🧱 1. HTTP는 요청을 기억하지 않는다. 그렇다면 서버는 어떻게 같은 사람을 알아볼까?

1-1. HTTP 요청에는 원래 '로그인한 사람'이라는 보장이 없다

먼저 선수 개념부터 짧게 복원하자.

브라우저에서 통근버스 조회 버튼을 누르면 대략 다음 과정이 일어나.

  1. 브라우저가 서버 주소와 경로를 결정한다.
  2. GET /api/my-route?date=2026-07-20 같은 HTTP 요청을 전송한다.
  3. 서버가 요청을 해석하고 필요한 데이터를 조회한다.
  4. 서버가 HTTP 상태 코드와 응답 데이터를 반환한다.
  5. 브라우저가 데이터를 화면에 표시한다.

여기서 중요한 건 HTTP는 기본적으로 무상태(stateless) 프로토콜이라는 점이야.

무상태라는 말은 서버 프로그램이 절대로 메모리를 가질 수 없다는 뜻이 아니야. 각각의 HTTP 요청이 프로토콜 차원에서 이전 요청의 로그인 사실이나 사용자 정보를 자동으로 계승하지 않는다는 뜻이지.

예를 들어 같은 브라우저가 다음 요청을 순서대로 보냈다고 하자.

서버는 단순히 같은 IP 주소에서 요청이 왔다는 이유로 같은 사용자라고 판단할 수 없어. 사무실에서는 여러 직원이 하나의 공인 IP를 공유할 수 있고, 같은 사람도 네트워크가 바뀌면 다른 IP를 사용할 수 있으니까.

브라우저가 로그인 화면에서 /home으로 이동했다는 사실만으로도 사용자를 증명할 수 없어. 주소는 직접 입력할 수 있기 때문이야.

따라서 서버에는 다음 두 가지가 필요해.

  • 처음 로그인할 때 사용자 신원을 확인하는 방법
  • 이후 요청에서 이미 확인된 신원과 현재 요청을 연결하는 방법

첫 번째가 인증(Authentication), 두 번째를 지속적으로 가능하게 하는 체계가 세션 관리(Session Management)야.

그리고 확인된 사용자가 요청한 작업을 실제로 허용할지는 별도의 인가(Authorization) 문제야.

1-2. 인증과 인가는 서로 다른 질문이다

출입증을 예로 들어 보자.

공장 출입구에서 직원증을 확인해 이 사람이 실제 직원 A임을 확인하는 건 인증과 비슷해. 하지만 직원이라고 해서 모든 제조 설비의 설정값을 변경할 수 있는 것은 아니지. 설비별 접근 권한을 확인하는 건 인가에 해당해.

웹서비스도 마찬가지야.

구분 인증(Authentication) 인가(Authorization)
핵심 질문 누구인가? 이 작업을 해도 되는가?
판단 근거 비밀번호, 세션, 토큰 등 역할, 소유 관계, 정책, 자원 상태
성공 결과 요청자의 신원을 신뢰할 수 있음 해당 요청을 수행하도록 허용
실패 예 로그인하지 않은 사람 로그인한 구성원이 운영자 작업 요청
통근버스 사례 E00001로 로그인했는가 E00002의 거주지를 읽을 수 있는가

인증은 인가의 재료를 제공하지만 인가 결론 자체를 대신하지는 않아.

이 차이를 이해하면 앞서 본 사고가 명확해져.

구성원 A가 로그인에 성공했다면 인증은 성공한 것이야. 그러나 A가 다른 구성원 B의 정보를 요청했을 때 B의 자원을 읽을 권리가 있는지 확인하지 않았다면 인가가 빠진 것이지.

이 문제는 서버가 사용자 신원을 아예 모르는 경우보다 발견하기 어려울 수 있어. 정상 로그인 사용자만 접근하는 화면에서 발생하기 때문이야.

🔑 2. 로그인은 비밀번호를 매번 보내는 과정이 아니다

2-1. 비밀번호는 어떻게 사용자 신원을 증명할까?

통근버스 서비스에 직원 계정이 등록되어 있다고 하자.

아래 계정과 값은 수업용 가상 예시야. 실제 시험에 제공된 CSV 행이나 응시자가 작성한 계정 데이터는 아니야.

users
--------------------------------------
user_id       employee_id   role
u-101         E00001        MEMBER
u-900         null          OPERATOR

실제 시험 지시문에는 서비스 내부 로그인과 운영자·구성원 두 역할이 명시되어 있어. 사내 SSO 연동은 요구하지 않아. 다만 계정 테이블이나 로그인 세부 구현 방식은 특정하지 않았어.

로그인 요청은 예를 들어 다음처럼 전송할 수 있어.

POST /api/login
Content-Type: application/json

{
  "username": "employee01",
  "password": "사용자가_입력한_비밀번호"
}

서버는 제출한 비밀번호가 등록된 계정의 비밀번호와 일치하는지 검증해야 해.

그런데 여기서 중요한 질문이 생겨.

서버는 사용자 비밀번호를 어떻게 보관해야 할까?

가장 단순한 방법은 데이터베이스에 원래 비밀번호를 그대로 저장하는 거야.

username       password
employee01     example-password

하지만 DB를 읽을 수 있게 된 공격자나 과도한 권한을 가진 운영자가 모든 사용자의 비밀번호를 그대로 볼 수 있게 돼. 사용자가 다른 서비스에도 같은 비밀번호를 사용했다면 피해는 더 커질 수 있어.

그래서 비밀번호는 일반적으로 복원 가능한 원문 대신 비밀번호 해시(password hash)를 저장해.

2-2. 해시는 암호화해서 숨기는 것과 다르다

암호화는 보통 적절한 복호화 키가 있으면 다시 원문으로 되돌릴 수 있게 설계해.

반면 비밀번호 해싱은 원래 비밀번호를 복원해서 비교하는 방식이 아니야. 입력된 비밀번호를 동일한 검증 절차에 넣어 저장된 값과 일치하는지 확인하지.

여기서 알아둘 개념은 세 가지야.

해시 함수는 입력값으로부터 정해진 형태의 출력값을 계산하는 함수야. 일반적인 암호학적 해시 함수는 원문을 역으로 구하기 어렵도록 설계돼. 다만 짧고 흔한 비밀번호는 공격자가 후보를 반복 대입하는 방식으로 알아낼 수 있으므로 해시 함수만 쓴다고 충분한 건 아니야.

Salt(솔트)는 비밀번호마다 새로 만드는 무작위 값이야. 두 사용자가 같은 비밀번호를 써도 서로 다른 검증 결과가 저장되게 해. Salt는 숨겨야 하는 비밀키가 아니고, 보통 해시와 함께 저장해.

느린 비밀번호 해싱 알고리즘은 공격자가 대량의 비밀번호 후보를 빠르게 시험하지 못하도록 비용을 높여. 대표적으로 Argon2id, scrypt, bcrypt 같은 방식이 있어. 반대로 단순 SHA-256을 비밀번호에 한 번 적용하는 건 일반적으로 적절한 비밀번호 저장 방식이 아니야.

이 구조에서도 비밀번호가 약하거나 공격자가 충분한 자원을 확보하면 추측 공격이 가능해. 그래서 안전한 저장뿐 아니라 로그인 시도 제한과 충분히 강한 비밀번호 정책도 필요하지.

2-3. 로그인 성공 후 왜 비밀번호를 계속 보내지 않을까?

이론적으로는 API 요청마다 비밀번호를 보내 서버가 계속 확인하게 만들 수도 있어.

하지만 이 방법에는 문제가 있어.

비밀번호라는 장기 비밀을 계속 전송·처리해야 하고, 요청을 처리하는 여러 코드와 로그 경로에서 노출될 가능성이 커져. 특정 기기의 로그인만 취소하기도 어렵고, 사용자 경험도 불편해.

그래서 일반적인 웹서비스는 다음처럼 동작해.

  1. 로그인 시 비밀번호를 검증한다.
  2. 검증이 성공하면 서버가 별도의 로그인 증명 수단을 발급한다.
  3. 이후 요청은 비밀번호 대신 그 증명 수단을 전달한다.
  4. 서버는 증명 수단의 유효성을 확인해 사용자를 식별한다.

이때 사용하는 대표적인 방식이 서버 측 세션과 세션 쿠키야.

여기서 발급되는 값은 일종의 임시 출입증이라고 생각하면 돼. 비밀번호 자체는 아니지만, 탈취당하면 다른 사람이 사용자의 권한으로 요청할 수 있으므로 똑같이 민감하게 보호해야 해.

🍪 3. 세션과 쿠키: 브라우저는 출입증을 가지고, 서버는 그 출입증을 확인한다

3-1. 세션은 무엇이고, 쿠키는 무엇일까?

두 개념을 처음에는 하나로 착각하기 쉬워.

서버가 로그인 정보를 기억하게 해주는 걸 모두 쿠키라고 부르기도 하고, 브라우저에 저장된 쿠키를 세션이라고 부르기도 해.

하지만 두 개념은 다르지.

세션(Session)은 여러 요청을 하나의 사용자 상호작용 흐름으로 연결해 관리하는 논리적 상태 또는 그 관리 체계야.

쿠키(Cookie)는 서버가 브라우저에 저장하도록 지시할 수 있는 작은 데이터이고, 브라우저는 쿠키의 적용 조건에 맞는 이후 요청에 그 데이터를 자동으로 첨부해.

즉, 세션은 무엇을 기억하고 연결할 것인가의 문제이고, 쿠키는 그 연결에 필요한 값을 어떻게 전달할 것인가의 문제야.

가장 이해하기 쉬운 구조는 서버가 세션 상태를 저장하고, 브라우저에는 무작위 세션 식별자만 보관하는 방식이야.

실제 구현에서 세션 저장소는 서버 메모리일 수도 있고 SQLite의 테이블일 수도 있어.

예를 들어 SQLite에는 다음과 같은 정보가 존재할 수 있지.

session_id_hash user_id expires_at revoked_at
해시된 증명값 A u-101 만료 시각 NULL
해시된 증명값 B u-900 만료 시각 폐기 시각

이 표는 수업용 설계 예시야.

실제 세션 증명값은 충분히 긴 암호학적 무작위 값으로 생성해야 해. 세션 ID를 E00001처럼 예측 가능한 직원 번호로 만드는 건 위험해. 공격자가 다른 직원 번호를 추측해 인증을 우회할 가능성이 생기니까.

세션 저장소에는 원문 증명값 대신 해시된 검증값을 저장하는 설계도 가능해. 이렇게 하면 세션 테이블만 읽힌 경우 원문 세션 증명값이 그대로 노출되는 위험을 줄일 수 있어. 단, 세션 해싱이 이미 탈취된 쿠키를 무효화해 주는 건 아니야.

3-2. 로그인부터 첫 번째 노선 조회까지 실제 순서를 따라가자

서버가 어떻게 행동하는지 단계마다 나눠 볼게.

① 사용자가 아이디와 비밀번호를 전송한다

POST /api/login
Content-Type: application/json

{
  "username": "employee01",
  "password": "..."
}

비밀번호는 HTTPS 연결을 통해 전송해야 해. 해시 저장을 사용하더라도 로그인 순간의 원문 비밀번호는 서버에 전달되어 검증에 사용되므로 전송 경로 보호가 필요하지.

② 서버가 사용자 기록을 조회하고 비밀번호를 검증한다

서버는 계정을 조회하고 해당 계정에 등록된 비밀번호 해시를 사용해 입력값을 검증해.

실패하면 로그인 요청을 거부해. 아이디가 존재하는지 여부를 응답 메시지로 지나치게 자세히 드러내지 않는 것도 중요해.

③ 검증이 성공하면 새로운 세션을 발급한다

서버는 암호학적으로 안전한 난수 생성기를 사용해서 예측하기 어려운 세션 증명값을 만들고, 사용자와 연결해 저장해.

이때 이전에 사용하던 세션 ID를 그대로 로그인 상태로 승격시키면 안 돼. 공격자가 미리 알고 있던 세션 ID를 피해자가 로그인하도록 유도하는 세션 고정(Session Fixation) 공격을 방지하려면 인증 전후의 세션 ID를 새로 발급하는 것이 중요해.

④ 응답에 Set-Cookie를 포함한다

HTTP/1.1 200 OK
Set-Cookie: __Host-sid=<random-secret>;
            Path=/; Secure; HttpOnly;
            SameSite=Lax
Content-Type: application/json

{"authenticated": true}

이 예시에서 <random-secret>은 임의의 문자열을 뜻하는 설명용 표시야. 실제 HTTP 헤더는 보통 한 줄로 전송돼.

__Host- 접두사를 사용하는 쿠키는 브라우저가 요구하는 조건을 만족해야 해. Secure가 필요하고, Path=/이어야 하며 Domain 속성이 없어야 하지. 이런 조건은 쿠키가 다른 하위 도메인에 의해 잘못 설정되는 위험을 줄여 줘.

⑤ 브라우저가 쿠키를 저장하고 다음 요청에 자동으로 첨부한다

GET /api/my-route?date=2026-07-20
Cookie: __Host-sid=<random-secret>

여기서 사용자는 비밀번호를 다시 입력하지 않았어.

브라우저가 해당 쿠키를 저장하고 있다가 요청 주소와 쿠키 조건에 맞게 첨부했기 때문이야.

⑥ 서버가 쿠키 속 세션 증명값을 검증한다

서버는 이 세션 증명값이 발급된 것인지, 폐기되지 않았는지, 만료되지 않았는지 확인해.

유효하다면 연결된 사용자 u-101을 알아낼 수 있어.

그렇지만 아직 노선을 반환할 수 있는 건 아니야.

이제 요청한 노선이 정말 u-101에게 허용되는 자원인지 확인해야 하기 때문이지.

⑦ 인가가 성공하면 노선을 조회해 반환한다

서버가 확인한 사용자 정보에서 직원 ID를 얻고 그 직원에게 연결된 노선을 조회해.

이 순서가 중요해.

안전한 방향

유효한 세션
    ↓
서버가 사용자 식별
    ↓
서버가 연결된 employee_id 확인
    ↓
그 직원의 운행 배정만 조회
    ↓
응답

반대로 브라우저가 보낸 직원 번호를 그대로 믿고 조회하면, 로그인은 정상이어도 개인정보가 노출될 수 있어.

3-3. 쿠키는 자동으로 붙지만, 모든 요청에 붙는 건 아니다

쿠키는 브라우저에 저장된다고 해서 인터넷의 모든 사이트에 무조건 보내지는 건 아니야.

어떤 요청에 쿠키가 포함될지는 쿠키의 도메인, 경로, Secure, SameSite, 만료 상태, 그리고 브라우저 정책에 영향을 받아.

또한 쿠키는 인증을 위한 기능만 있는 게 아니야. 언어 설정이나 화면 환경설정 저장에도 쓸 수 있어.

따라서 쿠키가 존재한다 = 로그인했다라는 식으로 판단해서는 안 돼.

서버가 그 쿠키의 값을 검증하고, 인증에 사용할 수 있는 유효한 증명값이라는 것을 확인해야 로그인 상태로 취급할 수 있어.

⏳ 4. 만료와 로그아웃: 출입증을 없애는 것과 출입 권한을 없애는 것은 다르다

세션에 만료를 두는 이유는 뭘까?

공격자가 세션 증명값을 탈취했다고 상상해 보자. 만료도 폐기도 없는 세션이라면 공격자는 사용자의 비밀번호를 몰라도 오래도록 그 사람인 척할 수 있어.

그래서 서버는 세션이 언제까지 유효한지 관리해야 해.

4-1. 두 종류의 만료 시간을 이해하자

절대 만료(Absolute Timeout)는 세션을 발급한 뒤 일정 시간이 지나면 사용자 활동과 관계없이 세션을 끝내는 거야.

유휴 만료(Idle Timeout)는 마지막으로 인정된 활동에서 일정 시간 동안 활동이 없으면 세션을 끝내는 방식이지.

두 방식을 조합할 수 있어. 유휴 만료가 활동에 따라 연장되더라도 절대 만료를 넘어서지는 않게 하는 거지.

중요한 것은 브라우저 화면에 표시된 타이머만 믿어서는 안 된다는 점이야.

서버가 실제 요청을 처리할 때 만료 여부를 검사해야 해. 브라우저의 JavaScript는 사용자가 수정하거나 중단할 수 있으니까.

또한 쿠키의 Max-Age나 Expires와 서버 세션의 만료는 같은 것이 아니야.

쿠키가 아직 브라우저에 있어도 서버 세션이 만료되었다면 요청은 인증 실패로 처리돼야 해.

4-2. 로그아웃은 UI에서 로그인 표시를 없애는 일이 아니다

다음 구현을 생각해 보자.

// 잘못된 로그아웃의 예
function logout() {
  localStorage.removeItem("loggedIn");
  showLoginPage();
}

이 코드는 화면 상태를 바꿀 수는 있어.

하지만 서버에 유효한 세션이 그대로 남아 있다면 어떨까?

공격자가 이전에 탈취한 세션 쿠키를 가지고 있다면 서버에 요청을 계속 보낼 수 있겠지.

서버 입장에서는 그 세션이 로그아웃되었다는 사실을 알지 못하니까.

세션 기반 로그아웃에서는 다음 과정이 필요해.

  1. 서버가 로그아웃 요청을 받는다.
  2. 요청을 보낸 세션을 식별한다.
  3. 서버 저장소에서 해당 세션을 삭제하거나 폐기 상태로 전환한다.
  4. 브라우저에 쿠키 제거 지시를 보낸다.
  5. 같은 세션 증명값으로 다시 요청해도 서버가 거부한다.

핵심은 마지막 단계야.

쿠키를 삭제하는 것은 브라우저 쪽 정리이고, 서버 세션을 폐기하는 것은 인증 효력 자체를 없애는 것이야.

둘 다 필요하지만 서로 대신하지는 못해.

여기서 또 하나의 질문이 나와.

로그아웃 요청은 서버에 도착했는데 쿠키 삭제 응답이 네트워크 장애로 브라우저에 도착하지 못했다면?

서버가 세션 폐기를 성공적으로 저장했다면, 브라우저에 낡은 쿠키가 남아 있어도 그 쿠키로 다시 인증받을 수 없어야 해.

반대 상황에서는 위험이 달라져. 브라우저의 쿠키만 삭제하고 서버 세션은 폐기하지 않았다면 탈취된 사본이 여전히 유효할 수 있거든.

이렇게 어떤 상태를 보안 판단의 최종 근거로 삼을 것인지 구분하는 사고가 중요해.

🚧 5. 로그인한 구성원도 다른 구성원의 데이터를 볼 수 없는 이유

이제 수업의 중심으로 들어가 보자.

시험 지시문에서 운영자와 구성원에게 요구한 기능은 다음과 같아.

운영자는 데이터셋 선택·적용, 운영 조건 변경, 노선 생성 실행, 전체 노선 조회를 수행해. 구성원은 날짜를 선택해 자신의 노선을 조회하지.

실제 시험은 이 두 역할을 요구하지만, 특정 API 경로나 인가 구현 방식을 강제하지 않았어.

우리는 이해를 돕기 위해 가상의 API 설계를 사용하자.

5-1. 첫 번째 인가: 역할(Role)에 따라 기능을 제한한다

역할 기반 접근 제어를 RBAC(Role-Based Access Control)이라고 불러.

예를 들어 다음과 같은 규칙을 만들 수 있어.

API · 가상 설계 구성원 운영자
GET /api/my-route 허용 별도 정책 필요
GET /api/routes 거부 허용
POST /api/datasets/apply 거부 허용
POST /api/plans/generate 거부 허용
GET /api/my-profile 허용 별도 정책 필요

여기서 운영자에게 모든 API를 자동으로 허용하지 않았다는 걸 봐.

운영자 권한이 있다는 이유만으로 구성원 개인 계정의 모든 자원에 접근할 필요가 있는 건 아니야. 업무상 정말 필요한 권한만 부여하는 걸 최소 권한(Least Privilege) 원칙이라고 해.

또한 역할이 정의되지 않았거나 인가 규칙이 빠진 API는 기본적으로 거부하도록 설계하는 게 좋아. 이를 기본 거부(Deny by Default)라고 하지.

역할 검사는 이렇게 이루어져.

POST /api/plans/generate
         ↓
세션 검증
         ↓
현재 사용자 = u-101
         ↓
서버가 역할 확인: MEMBER
         ↓
이 API는 OPERATOR 필요
         ↓
403 Forbidden

이 설계에서는 요청 본문에 다음 정보가 있더라도 믿지 않아.

{
  "role": "OPERATOR",
  "capacity": 45
}

왜냐하면 요청 본문은 브라우저를 사용하는 사람이 직접 바꿀 수 있기 때문이야.

누군가 요청에 자신의 역할이 운영자라고 썼다는 사실은 운영자라는 증거가 아니야.

서버는 로그인에서 확인한 신원과 서버가 신뢰할 수 있는 역할 정보를 사용해야 해.

5-2. 두 번째 인가: 같은 역할이라도 누구의 자원인지 검사한다

여기서 RBAC만으로 해결되지 않는 문제가 있어.

구성원 A와 구성원 B가 모두 MEMBER 역할을 가지고 있다고 하자.

역할 검사만 한다면 A와 B는 둘 다 구성원 조회 API를 호출할 수 있어.

하지만 A가 B의 개인정보까지 읽을 수 있어야 할까?

아니지.

역할을 검사하는 것만으로는 충분하지 않아. 요청한 자원이 누구에게 속하고, 현재 사용자가 그 자원을 읽을 권리가 있는지를 확인해야 해.

이걸 자원별 인가 또는 객체 수준 인가(Object-Level Authorization)라고 해.

이를 수식처럼 표현하면 다음과 같아.

Allow(u, a, r)

이 식은 사용자 u가 자원 r에 대해 작업 a를 할 수 있는지 결정한다는 뜻이야.

  • u: 로그인한 사용자
  • a: 조회, 수정, 삭제, 생성 등의 행위
  • r: 특정 구성원, 노선, 운영 계획 등의 자원

실제로는 사용자 역할뿐 아니라 자원의 소유 관계, 소속 조직, 운영 정책, 자원의 현재 상태 등이 판단에 참여할 수 있어.

예를 들어 MEMBER 역할을 가졌다는 것은 자신의 노선을 조회할 수 있는 종류의 작업에 대한 권한일 뿐, 모든 구성원 노선을 조회할 권한은 아니야.

5-3. 직원 ID를 바꾸는 공격은 어디서 발생할까?

이제 의도적으로 취약한 API를 만들었다고 가정해 보자.

GET /api/employees/E00001/route?date=2026-07-20
Cookie: __Host-sid=<valid-session>

서버가 세션을 검증하고 A가 로그인한 것을 확인해.

그런 다음 URL에 있는 E00001을 그대로 사용해 DB에서 결과를 조회한다고 하자.

# 잘못된 설계 예시 (의사코드)
user = require_login(request)

emp_id = request.path["emp_id"]

route = database.get_route(emp_id, date)

return route

여기에는 로그인 여부 확인은 있지만 요청 사용자와 자원 소유자를 비교하는 코드가 없어.

따라서 A는 주소를 다음처럼 바꿀 수 있어.

GET /api/employees/E00002/route?date=2026-07-20
Cookie: __Host-sid=<valid-session>

서버가 여전히 E00002의 데이터를 반환한다면 다른 구성원의 정보에 접근하는 데 성공한 거야.

이런 취약성을 IDOR(Insecure Direct Object Reference)라고 불러. 직접 참조할 수 있는 객체 식별자를 바꾸어 권한 없는 객체에 접근하는 문제지.

IDOR는 단순히 직원 번호가 연속되어서 생기는 문제가 아니야. 번호를 UUID처럼 무작위로 바꿔도 다른 사람의 식별자를 알게 되었을 때 같은 문제가 발생할 수 있어.

근본 원인은 서버의 자원별 인가 누락이야.

5-4. 안전한 조회는 요청자 신원을 서버가 직접 연결한다

본인 노선 조회라면 가장 단순한 방법은 브라우저가 직원 ID를 선택하지 않게 하는 거야.

GET /api/my-route?date=2026-07-20

서버는 다음 과정을 수행하지.

# 안전한 설계 방향을 보여 주는 의사코드

user = require_authenticated_user(request)

if user.role != "MEMBER":
    raise Forbidden()

employee_id = user.employee_id

route = database.get_route(
    employee_id=employee_id,
    work_date=request.query["date"]
)

return route

핵심은 직원 번호를 request의 조작 가능한 필드에서 얻지 않고, 서버에서 인증한 user로부터 얻는다는 거야.

이 설계는 본인 조회의 공격 표면을 줄여 줘.

물론 서버 내부에서 user.employee_id가 정확하게 연결되어 있어야 하고, 다른 조회 API나 결과 내보내기 API에도 별도의 인가 검사가 필요해.

경로에 직원 ID를 포함하는 API가 반드시 잘못된 것은 아니야. 운영자가 특정 구성원을 조회해야 하는 업무가 있을 수도 있지.

그런 경우 서버가 요청자와 대상 직원의 관계를 확인한 뒤 허용해야 해.

# 자원 소유 관계를 확인하는 의사코드

actor = require_authenticated_user(request)
target_emp_id = request.path["emp_id"]

if actor.role == "MEMBER":
    if actor.employee_id != target_emp_id:
        raise Forbidden()

elif actor.role == "OPERATOR":
    if not policy.can_view_employee(actor, target_emp_id):
        raise Forbidden()

else:
    raise Forbidden()

return database.get_route(target_emp_id, date)

운영자에게 어떤 구성원 데이터까지 열람 권한을 줄지는 업무 정책으로 결정해야 해. 실제 시험 지시문이 운영자에게 모든 개인 거주지의 무제한 열람을 명령한 것은 아니야.

이때 반드시 구분할 점은 브라우저에 있는 role이나 employee_id 표시값은 서버가 신뢰할 권한의 근거가 될 수 없다는 사실이야.

서버의 세션과 신뢰할 수 있는 사용자 기록, 그리고 검증된 자원 관계를 근거로 판단해야 하지.

🛡️ 6. 서버가 책임져야 할 권한과 화면이 책임져야 할 권한은 다르다

6-1. 운영자 버튼을 숨기면 구성원의 조작을 막을 수 있을까?

다음 프런트엔드 코드를 보자.

if (currentUser.role === "OPERATOR") {
  showGeneratePlanButton();
} else {
  hideGeneratePlanButton();
}

구성원이 로그인하면 운영 계획 생성 버튼이 보이지 않아.

그렇다면 구성원은 노선 생성을 실행할 수 없게 된 걸까?

아니야.

브라우저가 보내는 HTTP 요청은 화면 버튼을 누르는 것 말고도 여러 방식으로 생성할 수 있어. 개발자 도구, HTTP 클라이언트, 스크립트를 통해 API를 직접 호출할 수도 있지.

예를 들어 구성원이 다음 요청을 보냈다고 하자.

POST /api/plans/generate
Cookie: __Host-sid=<member-session>
Content-Type: application/json

{
  "capacity": 45,
  "arrival_buffer_minutes": 20
}

운영자 버튼이 화면에 없더라도 서버 엔드포인트가 존재한다면 요청은 도착할 수 있어.

따라서 UI 숨김은 사용자 경험을 위한 기능 제어이지 신뢰할 수 있는 보안 경계가 아니야.

프런트엔드는 사용자가 조작할 수 있는 영역이야. JavaScript 변수도 수정할 수 있고, 네트워크 요청도 새로 만들 수 있어.

반면 서버는 데이터베이스에 실제 변경을 반영하는 위치에 있어.

그래서 서버는 외부에서 들어오는 사용자 식별자, 역할 주장, 요청 파라미터를 모두 신뢰할 수 없는 입력으로 취급해야 해.

단, 서버 측 구현이라고 무조건 안전한 건 아니야. 서버가 클라이언트가 전달한 role을 그대로 사용한다면 단순히 검사 위치만 서버로 옮겼을 뿐이거든.

중요한 것은 서버에서 신뢰할 수 있는 근거를 사용하여 인가 결정을 내리는 것이야.

6-2. 권한 검사는 실제 업무 수행보다 먼저 있어야 한다

운영자가 데이터셋을 적용하는 요청을 생각해 보자.

취약한 순서:

요청 수신
    ↓
데이터셋을 DB에 적용
    ↓
사용자 역할 확인
    ↓
구성원이므로 403 반환

이렇게 구현하면 응답은 403 Forbidden이지만 이미 데이터가 바뀌었어.

즉, 사용자에게는 실패했다고 말하면서 실제 시스템 상태는 변경한 거야.

안전한 기본 순서는 다음과 같아.

요청 수신
    ↓
사용자 인증
    ↓
작업 권한 확인
    ↓
입력값 검증
    ↓
데이터 조회·변경
    ↓
결과 저장
    ↓
응답

특히 중요한 작업은 검사를 통과한 뒤 실제 변경이 확정되기 전까지 권한이 바뀔 가능성도 생각해야 해.

예를 들어 노선 생성을 요청한 운영자가 작업 대기 중에 권한을 박탈당한 경우를 가정해 보자. 언제의 권한을 기준으로 작업 시작과 최종 확정을 허용할지 정책이 필요해.

기본 원칙은 요청을 접수하는 순간의 인가를 검증하고, 오래 대기하는 작업이나 중요한 최종 확정에서는 필요에 따라 권한을 다시 확인하는 거야.

이것은 단순한 UI 문제가 아니라 작업의 수명주기와 권한 변경 시점 사이에서 어떤 보장을 제공할지의 문제지.

🚦 7. 401과 403: 두 실패가 같은 것이 아닌 이유

HTTP 응답 상태 코드도 구분해야 해.

401 Unauthorized는 현재 요청에서 유효한 인증 자격을 확인할 수 없다는 뜻으로 사용해. 이름에는 Unauthorized가 들어가지만 실무적으로는 인증 문제를 표현하는 상태 코드야.

403 Forbidden은 서버가 요청을 이해했지만 해당 접근을 허용하지 않는다는 뜻이야. 유효하게 인증된 사용자에게 권한이 없는 경우가 대표적이지. 인증 없이도 정책상 거부하는 경우에 403을 사용할 수 있으므로 반드시 로그인이 성공했다는 뜻은 아니야.

상황 일반적 응답 이유
세션 없이 내 노선 조회 401 유효한 인증 없음
만료된 세션으로 내 노선 조회 401 인증 자격이 더 이상 유효하지 않음
구성원이 노선 생성 실행 403 필요한 역할이 없음
구성원이 타인 노선 조회 403 또는 404 자원별 인가 거부, 필요시 존재 여부 보호
운영자가 정상적으로 노선 생성 요청 성공 또는 작업 접수 상태 인증·인가를 통과한 뒤 별도 검증과 실행 필요

존재 자체가 민감한 자원에 대해서는 타인의 자원이 실제 존재하는지 알려주지 않도록 404 Not Found를 반환하기도 해. 이 경우에도 내부적으로 인가 판단은 수행해야 하고, 자원을 숨기는 것만으로 인가가 해결되는 건 아니야.

또한 웹사이트에서 401을 받았을 때 로그인 화면으로 이동시키는 것은 브라우저 애플리케이션의 처리 방식일 수 있어. API가 401을 돌려주는 것과 화면을 로그인 페이지로 전환하는 것은 다른 계층의 행동이야.

실패 응답이 올바른 상태를 뜻하지는 않는다

보안 테스트에서 403이라는 코드만 확인하고 끝내면 안 되는 이유가 있어.

권한 없는 사용자가 데이터셋 적용을 호출했을 때 403을 받았더라도 DB가 변경되었다면 여전히 실패한 구현이야.

따라서 권한 거부를 테스트할 때는 두 가지를 동시에 확인해야 해.

  • 응답: 요청이 거부되었는가?
  • 서버 상태: 거부된 요청으로 보호 자원이 조회되거나 변경되지 않았는가?

조회 요청에서는 응답 내용과 정보 노출을 확인하고, 변경 요청에서는 변경 전후 DB 상태까지 확인해야 하지.

🌐 8. 쿠키가 안전하게 저장되어도 다른 공격이 가능하다

지금까지는 사용자가 직접 직원 ID나 역할을 바꾸는 경우를 봤어.

하지만 공격자가 사용자의 브라우저를 이용하거나, 브라우저에서 실행되는 스크립트를 악용하는 경우도 있어.

대표적으로 CSRF와 XSS가 있지.

둘은 이름이 비슷해 보여도 공격의 출발점이 달라.

8-1. CSRF: 로그인한 사람의 브라우저가 원하지 않는 요청을 보내게 한다

CSRF(Cross-Site Request Forgery)는 사용자가 인증된 사이트에 대해 공격자가 의도한 요청을 보내도록 유도하는 공격이야.

상황을 하나 만들어 보자.

운영자가 통근버스 서비스에 로그인해 있어. 브라우저에는 유효한 세션 쿠키가 저장돼 있지.

그런데 운영자가 공격자가 만든 다른 웹페이지를 방문했다고 하자.

공격 페이지가 특정 조건에서 통근버스 서버의 데이터셋 적용 엔드포인트에 요청을 보내도록 만들었다면 무슨 일이 일어날까?

브라우저는 쿠키 정책에 따라 해당 서비스의 세션 쿠키를 자동으로 전송할 수 있어.

그러면 서버 입장에서는 유효한 운영자 세션이 첨부된 요청을 받게 되지.

하지만 그 요청이 정말 운영자의 의도에 따라 발생했다는 뜻은 아니야.

CSRF의 본질은 서버가 이 요청을 보낸 브라우저가 인증된 사용자 것인지는 확인했지만, 그 사용자가 해당 변경을 의도했는지는 구분하지 못하는 데 있어.

그래서 인증과 인가를 제대로 구현해도 CSRF 방어가 별도로 필요할 수 있어.

대표적인 방어 방법은 다음과 같아.

  • 상태를 변경하는 요청에 CSRF 토큰을 요구하고 서버에서 검증한다.
  • Origin 등의 요청 출처 정보를 검사한다.
  • 세션 쿠키에 적절한 SameSite 정책을 적용한다.
  • 조회용 GET 요청이 서버 상태를 변경하지 않도록 설계한다.
  • 필요한 경우 사용자 재인증 등 추가 확인을 수행한다.

CSRF 토큰은 공격자가 단순히 다른 사이트에서 요청을 만들어 보내는 것만으로는 유효한 값을 얻거나 위조하기 어렵도록 설계된 값이야. 세션에 연결된 동기화 토큰이나 적절하게 서명된 이중 제출 패턴 등이 사용돼.

다만 SameSite만 설정하면 모든 환경에서 CSRF가 사라진다고 보면 안 돼. SameSite는 같은 site에 속하는 다른 출처를 모두 동일하게 차단하는 정책이 아니며, 배포 도메인과 엔드포인트 구성에 따라 한계가 있어.

8-2. XSS: 공격자가 웹사이트 안에서 스크립트를 실행하게 한다

XSS(Cross-Site Scripting)는 신뢰할 수 없는 데이터가 웹페이지에서 실행 가능한 코드로 해석되도록 만드는 공격이야.

통근버스 서비스의 운영자가 입력할 수 있는 정류장 설명 필드가 있다고 가정하자.

정류장 설명은 본래 단순 텍스트여야 해.

그런데 서버가 이 값을 아무 처리 없이 HTML에 삽입하고 브라우저가 이를 코드로 해석한다면, 공격자가 의도한 스크립트가 서비스의 출처에서 실행될 위험이 있어.

XSS와 CSRF의 차이를 정확히 보자.

구분 CSRF XSS
공격의 출발점 외부 요청을 유도 신뢰할 수 없는 내용을 코드로 실행
주로 악용하는 것 브라우저의 자동 인증 정보 첨부 웹사이트 출처에서 실행되는 스크립트
발생 가능한 피해 사용자 의도 없는 상태 변경 데이터 읽기·변경, 인증된 요청 실행
주요 방어 CSRF 토큰, 출처 검사, SameSite 출력 인코딩, 안전한 DOM API, 입력 처리, CSP

XSS를 막으려면 사용자에게서 받은 문자열을 HTML 코드가 아니라 텍스트로 다뤄야 해.

예를 들어 JavaScript에서 textContent로 일반 텍스트를 넣는 방식이, 검증되지 않은 문자열을 innerHTML에 그대로 넣는 것보다 안전해.

단, 문맥에 맞는 출력 인코딩이 중요해. HTML 본문, HTML 속성, JavaScript 문자열, URL에는 서로 다른 처리 기준이 필요하거든. 일부 HTML을 허용해야 한다면 검증된 HTML 정화(sanitization) 도구를 사용해야 해.

8-3. 쿠키의 보안 속성은 각각 다른 위험을 줄인다

여기서 Secure, HttpOnly, SameSite를 정확히 이해하자.

속성 하는 일 하지 못하는 일
Secure 브라우저가 쿠키를 HTTPS 연결에서만 전송하도록 제한 악성 스크립트 실행 자체 방지
HttpOnly JavaScript에서 쿠키 값을 직접 읽는 것을 제한 같은 출처에서 실행된 악성 스크립트의 인증된 요청 방지
SameSite 사이트 간 요청에서 쿠키 전송을 조건에 따라 제한 모든 CSRF와 XSS를 완전히 차단
Path 쿠키가 전송되는 URL 경로 범위 지정 신뢰할 수 있는 보안 격리 경계 제공
Domain 쿠키를 전송할 도메인 범위 지정 서버의 자원별 인가 수행
Max-Age / Expires 브라우저가 쿠키를 보관할 기간 설정 서버의 세션을 자동으로 확실히 폐기

특히 HttpOnly를 오해하면 안 돼.

공격자가 XSS로 스크립트를 실행하더라도 HttpOnly 쿠키의 값을 document.cookie로 직접 읽는 것은 제한돼.

하지만 그 스크립트가 해당 사이트의 출처에서 실행되고 있다면, 사용자의 세션을 이용한 요청을 보낼 수 있는 경우가 있어.

따라서 HttpOnly는 쿠키 값 탈취 경로를 줄여 주지만 XSS에 대한 완전한 방어책은 아니야.

또 하나 중요한 점은 SameSite의 기본적인 목적이 쿠키가 언제 첨부되는지를 제어하는 것이라는 사실이야. SameSite=Strict는 더 제한적이지만 정상적인 외부 링크 진입에서도 사용자 경험에 영향을 줄 수 있어. Lax는 일정한 최상위 탐색 요청을 허용하는 등 더 유연한 정책이고, None은 Secure를 동반해야 해.

어떤 속성을 사용할지는 보안 요구와 로그인 동선, 서비스 도메인 구성에 따라 결정해야 하지.

🔀 9. CORS는 권한 관리가 아니다

이 부분은 API를 개발할 때 특히 자주 헷갈려.

CORS를 이해하려면 먼저 Origin(출처)이 무엇인지 알아야 해.

브라우저에서 출처는 일반적으로 다음 세 요소의 조합이야.

Origin = (Scheme, Host, Port)

예를 들어 다음 두 주소는 서로 다른 출처야.

http://localhost:3000   → 프런트엔드
http://localhost:8000   → API 서버

호스트와 프로토콜이 같더라도 포트 번호가 다르므로 출처가 달라.

브라우저는 기본적으로 스크립트가 다른 출처의 응답을 읽는 데 제한을 둬. 이것이 동일 출처 정책(Same-Origin Policy)의 핵심적인 부분이야.

CORS(Cross-Origin Resource Sharing)는 서버가 응답 헤더를 통해 다른 출처의 브라우저 스크립트에 특정 교차 출처 접근을 허용할 수 있게 해주는 메커니즘이야.

예를 들어 다음 헤더를 사용할 수 있어.

Access-Control-Allow-Origin: http://localhost:3000
Access-Control-Allow-Credentials: true

이 설정은 허용된 프런트엔드 출처에서 자격 증명을 포함한 교차 출처 요청을 처리할 수 있도록 하는 설정의 일부야. 브라우저 측에서도 fetch의 credentials 설정 등 필요한 조건을 충족해야 하고, 쿠키의 SameSite 정책도 별도로 적용돼.

그런데 왜 CORS가 인가가 아닐까?

CORS는 기본적으로 브라우저가 어떤 교차 출처 요청과 응답 접근을 허용할지에 관한 정책이기 때문이야.

서버가 요청자를 업무상 운영자로 인정할지와는 별개의 문제지.

서버가 CORS를 올바르게 제한해 두었다고 하자.

그런데 API에서 운영자 권한 검사를 누락했어.

이때 별도의 HTTP 클라이언트가 운영자 API를 직접 호출하면 브라우저의 CORS 정책은 그 요청을 막는 보안 장벽이 되지 않아.

반대로 CORS 설정이 지나치게 넓더라도 서버가 모든 요청에서 강한 인증과 인가를 수행한다면, CORS 설정 자체가 모든 사용자를 운영자로 만드는 것은 아니야. 물론 과도한 CORS 허용은 특히 쿠키 인증이나 민감한 API와 결합될 때 실제 보안 문제를 초래할 수 있어.

여기서 반드시 기억해야 할 차이는 다음과 같아.

CORS는 웹페이지의 출처 간 접근을 제어한다. 인가는 사용자나 서비스가 특정 자원에 수행할 작업을 제어한다.

또한 CORS 실패가 곧 서버에서 요청이 실행되지 않았다는 뜻도 아니야. 일부 교차 출처 요청에서는 브라우저가 사전 요청(Preflight)을 수행하지만 모든 요청이 사전 요청을 거치는 것은 아니며, 응답을 읽지 못하더라도 서버에서 이미 작업이 수행된 경우가 있을 수 있어.

그래서 CORS를 CSRF 방어와 혼동해서도 안 돼.

지금까지 배운 내용을 하나의 실제적인 요청 흐름에 연결해 보자.

여기서부터는 단일 서버와 SQLite를 사용하는 가상 참조 설계야.

시험 원문에 등장하는 역할과 업무 요구사항을 기반으로 하지만, 실제 CSV 행이나 응시자의 제출 코드는 제공되지 않았으므로 이것을 시험 당시의 구현이나 실행 결과로 취급하면 안 돼.

10-1. 먼저 DB에서 어떤 정보를 관리해야 하는가?

시험 데이터에는 employees.csv의 구성원 정보와 work_schedule.csv의 날짜별 근무 상태가 존재해.

하지만 employees.csv에 구성원 정보가 있다고 해서 그 데이터가 곧 로그인 계정 테이블이 되는 건 아니야.

직원 데이터와 로그인 신원을 분리할 수 있어.

이 구조를 통해 세 가지 연결 관계가 만들어져.

첫째, sessions.user_id는 어떤 로그인 계정에 속한 세션인지 알려줘.

둘째, users.employee_id는 로그인 계정과 실제 구성원 업무 기록을 연결해. 구성원 계정은 대응하는 직원 ID가 필요하지만, 운영자 계정은 정책에 따라 직원 ID가 없을 수도 있지.

셋째, assignments.emp_id는 어떤 구성원이 어떤 날짜의 어느 노선에 배정되었는지 알려줘.

따라서 구성원이 자신의 노선을 조회할 때는 다음 경로를 따라가는 거야.

세션 증명값
   ↓
sessions.user_id
   ↓
users.employee_id
   ↓
assignments.emp_id
   ↓
해당 날짜의 배정 및 노선 정보

이때 employee_id는 브라우저가 새로 주장한 값이 아니라 인증된 계정에 저장된 관계를 통해 얻은 값이야.

10-2. 서버가 요청을 처리하는 책임을 분리해 보자

다음은 특정 프레임워크에 의존하지 않는 의사코드야. 실행 가능한 완성 프로그램이 아니라 요청 처리 순서를 설명하기 위한 코드지.

def get_my_route(request):
    # 1. 인증: 현재 요청의 세션을 검증
    actor = authenticate_session(request)

    if actor is None:
        return response(401, {"error": "UNAUTHENTICATED"})

    # 2. 역할 검사
    if actor.role != "MEMBER":
        return response(403, {"error": "FORBIDDEN"})

    # 3. 서버에 저장된 사용자-직원 연결 확인
    employee_id = actor.employee_id

    if employee_id is None:
        return response(403, {"error": "NO_EMPLOYEE_LINK"})

    # 4. 입력값 검증
    date = parse_work_date(request.query.get("date"))

    if date is None:
        return response(400, {"error": "INVALID_DATE"})

    # 5. 자원 범위를 본인으로 제한해 조회
    route = db.get_assignment_and_route(
        employee_id=employee_id,
        work_date=date
    )

    # 6. 응답
    if route is None:
        return response(404, {"error": "ROUTE_NOT_FOUND"})

    return response(200, route)

여기서 authenticate_session()은 단순히 쿠키 문자열이 있는지만 확인하는 함수가 아니야.

세션 증명값을 검증하고, 만료·폐기 여부를 확인하고, 연결된 사용자 계정의 유효성까지 판단해야 해. 역할은 서버가 신뢰할 수 있는 기록에서 읽거나, 무효화와 갱신 정책을 갖춘 캐시에서 확인할 수 있어.

이 코드에는 중요한 설계 의도가 하나 있어.

자원 조회 전에 인가 범위를 결정하고, DB 조회 자체를 허용된 자원으로 제한한다는 것이야.

반대로 모든 구성원의 배정 정보를 조회한 뒤 프런트엔드에서 자신의 행만 필터링한다면 이미 서버가 불필요한 개인정보를 전달했을 수 있어.

서버 내부에서도 필요한 최소한의 데이터를 읽는 편이 좋아.

10-3. SQL에서도 본인 자원 범위를 표현할 수 있다

가상으로 설계한 assignments 테이블을 사용해 조회한다고 하자.

SELECT
    a.work_date,
    a.direction,
    a.route_id,
    a.board_stop,
    a.alight_stop
FROM assignments AS a
WHERE a.emp_id = :authenticated_employee_id
  AND a.work_date = :requested_date;

핵심은 :authenticated_employee_id에 어떤 값을 넣는가야.

서버가 검증한 세션에서 얻은 직원 ID를 넣으면 본인 데이터 조회로 범위를 제한할 수 있어.

반대로 브라우저가 보내온 직원 ID를 그대로 넣고 소유 관계를 검사하지 않으면 취약해질 수 있지.

:로 시작하는 값은 SQL 파라미터를 나타내는 설명용 표현이야. 실제 DB 라이브러리에서는 지원하는 파라미터 바인딩 방식을 사용해야 하고, 문자열을 이어 붙여 SQL을 조립하는 방식은 SQL 삽입 공격의 위험을 만들 수 있어.

이 조회가 개인정보 보호를 완성하는 것은 아니야. 같은 직원 ID를 사용하는 다른 API, 전체 조회, 결과 내보내기, 검색 기능 등에서도 각각 접근 권한을 확인해야 해.

특히 통근버스 서비스는 다음 항목이 연결될 수 있어.

  • 직원별 거주지 좌표
  • 날짜별 출퇴근 노선
  • 사업장과 근무시간대
  • 노선별 배정자 정보
  • 전체 운영 계획 내보내기

따라서 운영자 전체 노선 화면에 필요한 정보와 구성원 개인 화면에 필요한 정보가 다르다면 응답의 필드 수준에서도 최소 정보 제공 원칙을 적용해야 해.

예를 들어 구성원 화면에서 자신의 거주지는 표시할 필요가 있어도, 다른 탑승자의 상세 거주지까지 응답할 필요는 없을 수 있지.

10-4. 날짜별 노선 조회에서 인증과 업무 판단은 다른 단계다

여기까지 이해했다면 중요한 경계가 하나 더 보여야 해.

구성원이 로그인했고, 자신의 노선을 조회하는 것도 허용되었다고 하자.

그렇다고 해당 날짜에 노선이 반드시 존재하는 것은 아니야.

시험에서는 work_schedule.csv의 WORK와 OFF가 날짜별 배정 여부를 결정해.

따라서 서버는 해당 날짜의 근무 상태, 유효한 생성 결과, 배정 존재 여부를 업무 규칙에 따라 처리해야 해.

인증: E00001이 맞는가?
    ↓
인가: E00001의 노선을 읽을 권한이 있는가?
    ↓
업무 판단: 선택 날짜에 WORK인가?
    ↓
데이터 판단: 적용된 운영 계획에 배정이 존재하는가?
    ↓
응답

로그인 성공과 날짜별 노선 존재 여부는 서로 다른 개념이야.

휴무일에 노선이 없다고 해서 401이나 403이 되는 것은 아니지. 해당 요청에서 인증과 인가는 유효할 수 있고, 데이터가 없거나 해당 날짜에 배정 대상이 아니라는 업무상 결과를 돌려주면 돼.

이런 구분은 오류 설계를 더 명확하게 만들어 줘.

🏗️ 11. 단일 서버·SQLite에서 세션을 어디에 보관할 것인가?

사용자의 규모와 운영 환경에 따라 세션 저장 방식의 성질이 달라져.

여기서는 한 대의 서버 프로세스와 SQLite부터 생각해 보자.

11-1. 서버 메모리에만 세션을 두는 경우

가장 단순한 구현은 다음과 비슷해.

sessions = {}

sessions["random-session-id"] = {
    "user_id": "u-101",
    "expires_at": "..."
}

요청이 들어오면 sessions 딕셔너리를 조회하는 방식이지.

이 구조는 간단하고 세션 조회가 빨라.

하지만 서버 프로세스가 종료되면 어떻게 될까?

딕셔너리는 프로세스 메모리에 있으므로 별도 영속화가 없다면 사라져. 서버가 재시작되면 사용자는 다시 로그인해야 할 수 있어.

또한 같은 서버 컴퓨터에서도 프로세스가 둘이라면 보통 각 프로세스의 메모리는 분리돼 있어. A 프로세스에서 만든 세션을 B 프로세스가 자동으로 알 수는 없어.

이 구조는 서버가 하나이고 재시작 시 모든 로그인 상태가 사라져도 괜찮은 작은 실습에는 사용할 수 있지만, 여러 프로세스로 확장할 때 구조적 한계가 있어.

11-2. SQLite에 세션을 저장하는 경우

세션 상태를 SQLite에 저장한다면 서버 프로세스가 종료되어도 세션 기록은 DB 파일에 남아 있을 수 있어.

서버가 재시작한 뒤 같은 DB를 사용하고 해당 세션이 여전히 유효하다면 기존 쿠키로 다시 인증될 수 있지.

여기서는 브라우저의 쿠키 지속 여부도 함께 영향을 미쳐.

또한 로그아웃할 때 SQLite에서 세션을 폐기하면 이후 조회 요청에도 그 폐기 상태를 반영할 수 있어.

다만 SQLite에 저장한다고 해서 모든 문제가 자동으로 해결되는 건 아니야.

DB 파일이 사라지거나, 컨테이너의 비영속 파일시스템에만 보관되거나, 세션 조회 코드에서 만료를 검사하지 않으면 의도한 보장을 얻지 못할 수 있어.

방식 프로세스 재시작 서로 다른 프로세스 주요 부담
프로세스 메모리 일반적으로 세션 소실 별도 공유 불가 재로그인, 프로세스별 상태
동일한 SQLite DB 세션 기록 유지 가능 같은 DB에 접근하면 공유 가능 파일·잠금·DB 가용성 관리
공용 세션 저장소 영속화 설정 등에 따름 여러 서버에서 공유 가능 별도 인프라와 운영 복잡성

이 비교는 일반적인 서버 측 세션 구조에 대한 설명이야. 실제 사용한 라이브러리나 배포 방식에 따라 세부 동작은 달라질 수 있어.

11-3. 별도 WORKER가 생기면 무엇이 달라질까?

시험 복기에는 별도 프로세스 비동기 처리와 WORKER 종료 같은 질문이 등장해. 다만 이것이 모든 응시자에게 요구된 강제 구현이라는 뜻은 아니야.

가상으로 노선 생성 작업을 웹 서버와 별도 WORKER 프로세스로 나누었다고 해 보자.

이 상황에서 운영자가 노선 생성을 요청하면 웹 서버는 요청자의 인증과 인가를 확인한 뒤 작업을 기록하고 WORKER에게 계산을 맡길 수 있어.

WORKER는 브라우저의 세션 쿠키가 필요하지 않을 수 있어. 이미 허가되어 등록된 작업의 ID와 계산 조건을 받아 실행할 수 있기 때문이야.

하지만 이때도 누가 작업을 요청했는지, 어떤 조건으로 실행되는지, 권한이 중간에 바뀌었을 때 어떻게 할 것인지 같은 정책은 명확해야 해.

그리고 WORKER가 계산을 수행한다는 사실과 사용자가 그 계산 결과를 조회할 권한이 있다는 사실은 별개의 판단이야.

예를 들어 구성원은 다른 사람이 생성한 작업의 중간 결과나 전체 배정 내역을 마음대로 볼 수 없어야 할 수 있지.

11-4. 여러 서버에서는 무엇을 추가로 고려해야 할까?

이제 웹 서버가 두 대 있다고 해 보자.

서버 A에서 로그인하고 서버 B로 요청이 전달되었을 때, 서버 B도 같은 세션을 검증할 수 있어야 해.

이를 위해 공용 저장소를 쓰거나, 로드밸런서에서 같은 사용자 요청을 특정 서버로 보내는 스티키 세션(Sticky Session) 같은 방식을 활용할 수 있어.

그러나 스티키 세션은 해당 서버가 죽었을 때의 세션 지속성 문제를 해결하지 못해.

또한 여러 서버에서 DB에 있는 역할 정보를 캐시하는 경우 권한 변경이 다른 서버에 언제 반영되는지도 중요해.

운영자 권한을 박탈했는데 한 서버의 캐시에 예전 역할이 남아 있다면 그 서버에서는 계속 운영자 요청을 허용할 수 있기 때문이지.

따라서 여러 서버 환경에서는 세션 공유뿐 아니라 권한 변경 반영, 폐기 상태 일관성, 캐시 무효화도 설계 대상이 돼.

11-5. JWT 같은 토큰을 사용하면 세션 저장소가 없어질까?

여기서 토큰을 함께 이해해 보자.

토큰(Token)은 일반적으로 어떤 인증이나 접근 권한을 증명하는 데 사용하는 값을 가리키는 넓은 표현이야.

우리가 앞에서 사용한 무작위 세션 ID도 인증 증명값이라는 점에서 토큰의 일종으로 볼 수 있어.

실무에서는 토큰이라는 말을 JWT 같은 서명된 자격 증명에 대해 사용하는 경우가 많아.

JWT(JSON Web Token)는 보통 헤더, 페이로드, 서명의 세 부분으로 구성돼. 서명된 JWT를 사용하는 서버는 토큰의 서명을 검증하고 발급자, 대상 서비스, 만료 시간 등의 조건을 확인해 사용할 수 있지.

하지만 JWT를 사용한다는 것과 반드시 서버에 상태가 없다는 것은 같은 말이 아니야.

예를 들어 서버가 JWT 폐기 목록을 관리하거나 사용자별 토큰 버전을 확인한다면 그 검증을 위한 상태가 필요해.

반대로 서버가 토큰 서명과 만료만 검증하는 설계라면 빠르게 여러 서버에서 처리할 수 있지만, 발급된 토큰의 즉각적인 로그아웃이나 권한 박탈을 반영하기가 상대적으로 어려워질 수 있어.

비교 서버 측 세션 + 쿠키 자체 검증형 JWT
서버가 확인하는 것 저장소의 세션 기록과 사용자 상태 서명·클레임·현재 정책
즉시 폐기 서버 세션을 삭제·폐기하면 가능 별도 폐기 전략이 필요할 수 있음
다중 서버 세션 저장소 공유 또는 조정 필요 검증 키 공유와 정책 일관성 필요
주요 위험 세션 ID 탈취, 저장소 장애 토큰 탈취, 긴 만료, 검증 오류, 폐기 지연
장점 폐기와 상태 관리가 직관적 분산 환경에서 검증을 단순화할 수 있음
부담 저장소 운영과 조회 키 관리, 토큰 수명, 폐기·권한 변경 정책

여기서도 토큰이 존재한다는 사실은 어떤 업무를 수행할 수 있는지의 최종 판단이 아니야.

서버가 토큰의 진위와 유효성을 검증한 다음, 요청한 자원과 작업이 허용되는지 판단해야 해.

또 JWT에 역할 정보가 들어 있다면 그 역할이 언제 발급된 것인지, 이후 권한 변경을 어떻게 반영할지도 생각해야 하지.

통근버스 시험의 단일 서버·SQLite 기본 설계에서는 서버 측 세션 방식이 충분히 합리적인 선택이 될 수 있어. 다만 이것이 시험에서 강제된 기술 선택이라는 뜻은 아니야.

🔬 12. 보안은 코드가 있어 보인다는 이유로 검증되지 않는다

지금까지의 설명을 실제 구현 검증에 연결해 보자.

시험 복기에는 구현한 기능 중 무엇을 실제로 검증했고, 무엇을 검증하지 않았는지 설명해야 했다는 내용이 있어.

인증·인가에서도 같은 태도가 필요해.

AI가 인증 미들웨어를 작성했고, 로그인 화면이 정상적으로 나타났다고 해서 모든 보안 요구가 충족된 것은 아니야.

권한 있는 요청은 성공하고, 권한 없는 요청은 실제로 실패하는지를 각각 확인해야 해.

12-1. 정상 경로와 공격 경로를 함께 테스트해야 한다

가상 서버의 API가 다음과 같다고 하자.

POST /api/login
POST /api/logout

GET  /api/my-route
GET  /api/routes

POST /api/datasets/apply
POST /api/plans/generate

다음은 구현 시 검증해야 할 대표 시나리오야.

테스트 기대되는 결과 추가 확인
올바른 계정 로그인 로그인 성공 세션 발급
틀린 비밀번호 로그인 거부 세션 발급되지 않음
비로그인 상태 노선 조회 401 개인정보 없음
만료 세션으로 조회 401 만료 세션 거부
구성원 자신의 노선 조회 정상 응답 해당 직원 데이터만 포함
구성원의 타인 노선 조회 403/404 타인 정보 없음
구성원의 노선 생성 요청 403 작업 생성·DB 변경 없음
운영자의 노선 생성 요청 허용 후 실행/접수 조건 및 업무 검증 수행
로그아웃 후 옛 세션 재사용 401 폐기된 세션 재사용 불가
구성원 요청에 role=OPERATOR 삽입 권한 상승 불가 서버 역할 기준 유지

이 표는 테스트 설계이며, 실제 시험에서 이 테스트들이 실행되었다는 기록은 아니야.

특히 타인 자원 접근 테스트에서는 자기 데이터만 조회되는지 확인하는 것보다, 다른 사람의 데이터가 절대 반환되지 않는지 확인하는 게 중요해.

또한 로그아웃은 화면이 로그인 페이지로 돌아갔는지 보는 것만으로 부족해. 이전 세션 증명값을 저장해 두었다가 로그아웃 이후 다시 요청했을 때 서버가 거부하는지 확인해야 하지.

12-2. 간단한 통합 테스트는 어떤 형태일까?

다음은 가상의 Python 테스트 클라이언트를 사용하는 의사코드야. client, create_test_app, read_database_state 등은 프로젝트에 맞게 구현해야 해.

def test_member_cannot_generate_plan():
    app = create_test_app()
    client = app.test_client()

    # 구성원으로 로그인
    login_as(client, username="employee01")

    before = read_database_state(app)

    response = client.post(
        "/api/plans/generate",
        json={"capacity": 45}
    )

    after = read_database_state(app)

    assert response.status_code == 403
    assert after == before

이 테스트가 확인하려는 것은 단순히 403 반환이 아니야.

권한 없는 요청으로 업무 상태가 변경되지 않았다는 사실까지 확인하려는 거지.

다만 실제 DB 전체 상태를 단순 비교하는 것이 항상 적절하지는 않아. 거부 요청에 대한 감사 로그는 정상적으로 추가될 수 있기 때문이야.

따라서 실무에서는 노선 계획, 작업 생성 기록, 데이터셋 적용 버전 등 변경이 금지되어야 할 업무 상태를 정확히 선택해서 비교하는 게 좋아.

타인 조회의 경우에는 다음 구조를 사용할 수 있어.

def test_member_cannot_read_another_employee():
    app = create_test_app()
    client = app.test_client()

    login_as(client, username="employee01")

    response = client.get(
        "/api/employees/E00002/route"
        "?date=2026-07-20"
    )

    assert response.status_code in (403, 404)
    assert b"E00002-private-data" not in response.data

물론 테스트에서 사용하는 비밀 데이터 식별자는 실제 테스트 데이터에 맞춰 구성해야 해. 여기서는 허용되지 않은 데이터가 응답에 포함되지 않아야 한다는 검증 의도만 보여 주는 거야.

12-3. 반드시 구분해야 할 검증 수준

실제로 단위 테스트만 통과했다면 그 범위만 검증한 거야.

실제 브라우저에서 HTTPS 쿠키 동작을 확인하지 않았다면, 해당 항목은 미검증이라고 설명해야 해.

시험 지시문도 실제 배포는 요구하지 않았어. 따라서 운영 환경을 고려한 설계를 설명할 수는 있지만, 배포하지 않은 환경에서 보안이 검증되었다고 주장해서는 안 돼.

⚖️ 13. 어떤 설계를 선택하면 무엇을 얻고 무엇을 잃을까?

보안 설계는 단순히 더 많은 기능을 넣는 경쟁이 아니야.

특정 구조를 선택하면 어떤 위험을 줄이고, 대신 어떤 복잡성과 제약을 받아들이는지를 설명할 수 있어야 해.

선택 A. 서버 측 세션을 SQLite에 보관한다

장점은 세션 폐기와 만료 판단이 명확하고, 현재 유효한 로그인 상태를 서버가 관리할 수 있다는 점이야.

반면 세션 조회에 DB 접근이 필요하고, SQLite 파일과 DB 가용성에 의존해. 프로세스가 여러 개라면 같은 저장소를 사용하는지 확인해야 하지.

선택 B. JWT를 발급하고 자체 검증한다

검증할 때 매번 세션 DB를 조회하지 않는 구성을 만들 수 있다는 장점이 있어.

하지만 장기간 유효한 JWT를 발급하면 도중에 권한을 회수하기 어려울 수 있어. 즉시 로그아웃을 엄격하게 요구한다면 별도 상태 관리나 짧은 만료 등 추가 정책이 필요해.

선택 C. 화면에서 역할별 기능을 숨긴다

사용자가 자신의 역할에 맞지 않는 메뉴를 혼동하지 않으므로 사용성은 좋아져.

하지만 직접 API를 호출하는 공격을 막을 수 없으므로 서버 인가를 대신할 수 없어.

선택 D. 본인 조회를 /api/my-route로 제한한다

브라우저에서 직원 ID를 조작하는 대표적인 공격 경로를 줄여 줘. 서버에서 사용자-직원 연결을 이용한다는 구조도 명확하지.

반면 운영자가 특정 구성원 자원을 조회해야 하는 기능은 별도 API와 정책이 필요할 수 있어.

선택 E. 로그인·세션 기능을 자체 개발한다

요구사항을 세밀하게 조정할 수 있어.

하지만 세션 난수 생성, 해시 검증, 로그인 시도 제한, 쿠키, 만료, 로그아웃, CSRF 방어 등 여러 보안 기능을 정확히 구현해야 하므로 실수 가능성이 커져.

따라서 일반적으로는 검증된 프레임워크의 인증·세션 기능을 활용하고, 업무별 인가 규칙을 명시적으로 구현하는 편이 유리해.

단, 라이브러리를 사용하더라도 그 설정이 어떤 보장을 제공하는지 검토해야 해. 프레임워크가 알아서 모든 자원별 인가를 수행해 주는 것은 아니니까.

🧠 14. 한 번의 요청에 모든 개념을 합쳐 보자

이제 처음에 제시한 사고로 돌아가 보자.

구성원 A가 정상 로그인했고, 다른 구성원 B의 직원 ID를 URL에 넣어 조회를 시도하는 상황이야.

정상적인 서버라면 다음을 구분해야 해.

이 수업 전체를 한 문장으로 정리하면 다음과 같아.

인증은 요청자의 신원을 확인하고, 세션은 그 신원을 후속 요청과 연결하며, 인가는 확인된 요청자가 특정 자원에 특정 작업을 수행할 수 있는지를 서버에서 판단한다.

쿠키는 그 연결을 위한 증명값을 전달할 수 있고, 토큰 역시 검증을 거쳐야 해. CORS는 출처 간 브라우저 접근에 관한 정책이지 업무 권한을 의미하지 않아. UI 숨김은 사용성에 도움을 주지만 보안 경계를 제공하지 않아.

또한 인증·인가가 있더라도 CSRF·XSS 같은 공격을 별도로 고려해야 해.
