읽기 약속: 이 문서는 읽고 보관할 수 있는 일반 Markdown 원본이다. 이전의 표시 오류 응답을 재구성한 것이 아니라 새로 집필한 수업이다. 학습 이미지 생성 모드는 꺼져 있으며, 복잡한 화면 위젯 대신 텍스트 도식·표·코드로 개념을 표현한다. 저장은 별도의 학습 진행상태 패킷을 만드는 명령이며, 이 Markdown 파일을 저장하는 일과 다르다.

근거의 경계: 시험 원문 EXAM_ORIGINAL_COMBINED.txt는 업로드 없는 준비 데이터셋 선택·검증·적용, CSV 7종, 필수 열·존재하지 않는 ID·형식 오류의 실제 검증, 실패 시 기존 데이터와 생성 결과 유지, 새 데이터 적용 후 재계산 전의 결과 오인 방지, 변경된 근무·휴무 반영을 요구한다. EXAM_RECOLLECTION.txt는 응시자가 기억한 추궁 질문이며 공식 평가 기준이 아니다. 원본에는 45석, 출근 20분 전 도착, 퇴근 10분 후 출발, travel_times.csv 사용 등이 명시된다. 실제 CSV 행, 응시 제출 코드, 실제 실행 로그는 주어지지 않았다. 아래 E001, S1/S2, 시각, 결과, SQL은 모두 가상·미실행 교육 예제다. 특정 프레임워크·테이블·WORKER 구성을 시험이 강제한 것은 아니다.

신뢰의 경계: 후보 파일에서 공식 결과까지

입력의 내용이 고정되고, 검증되고, 확정되는 각각의 순간을 구별한다.

🧭 1. '선택했다'와 '적용됐다'는 전혀 다른 말이야

작은 가게의 가격표를 생각해 보자. 직원이 새 가격표를 책상 위에 올려놓는 것과 그 가격표가 계산대의 공식 가격이 되는 것은 다르지. 계산대가 새 가격표를 사용하려면 우선 숫자와 상품 연결을 확인해야 하고, 그 다음 어느 가격표를 공식 기준으로 삼을지 변경해야 해. 이 비유의 한계는 파일은 사람 손으로만 바뀌지 않고 다른 프로세스가 순식간에 수정할 수 있다는 점이야.

통근버스 운영자 화면에 candidate-B가 있다고 하자. 기존 S1으로 만든 노선 R1이 서비스되고 있어. 운영자가 B를 선택했다는 것은 검사할 대상을 지정했다는 뜻이지, 기존 운영 상태를 바꾸라는 승인이 아니야. 검증은 그 후보의 실제 데이터가 계약을 만족하는지 알아보는 판단이야. 적용은 이후 새 계산에서 사용할 공식 입력을 변경하는, 영속적으로 기록해야 하는 사건이야. 그리고 재계산/결과 확정은 새 공식 입력으로 결과를 만들어 검증한 뒤 사용자에게 제공하는 별도의 사건이야.

사건 입력 후보 상태 공식 입력 결과 R1
시작 없음 S1 S1 기준 CURRENT
B 선택 SELECTED S1 그대로 CURRENT
B 검사 중 VALIDATING S1 그대로 CURRENT
B 검증 통과 VALID S1 그대로 CURRENT
B 적용 커밋 APPLIED S2 보존되나 STALE
S2 계산·검증·확정 APPLIED S2 과거 결과로 보존, 새 R2가 CURRENT
B 검증 실패 INVALID S1 유지 R1 CURRENT 유지

상태 명칭은 가상 설계야. 중요한 건 각 열이 서로 다른 질문에 답한다는 사실이지. VALID는 '이 후보를 검사해 통과했다'이고 APPLIED는 '지금 공식 기준으로 삼는다'야. 하나의 status 값으로 모든 의미를 억지로 표현하면, 적용됐지만 결과가 아직 없는 중간 상태를 정확히 표현하기 어려워.

운영자가 후보 B 선택
        │ 공식 입력 S1 그대로
        ▼
B의 불변 입력 확보 ──► B 검증 ── 실패 ──► 오류 보고 / S1·R1 유지
                           │
                          통과
                           ▼
                   공식 입력 포인터 S2로 변경
                           │ 기존 R1은 STALE
                           ▼
                S2 기준 새 job 생성·계산
                           ▼
                결과 규칙·현재성 검증
                           ▼
                   R2를 CURRENT로 확정

데이터를 적용하는 것과 결과를 생성하는 것을 구분하면 왜 'S2 적용 성공, 재계산 실패'라는 상태가 가능한지도 이해돼. 입력 기준은 S2로 바뀌었지만 아직 적합한 새 노선은 없을 수 있어. 이때 R1을 S2 결과로 위장하지 않는 것이 중요해.

🧱 2. CSV 일곱 개는 왜 함께 고정해야 할까?

시험의 입력은 sites.csv(사업장), shifts.csv(근무시간대), employees.csv(구성원), work_schedule.csv(날짜별 근무·휴무), stops.csv(정류장 후보), travel_times.csv(방향별 이동시간), ridership.csv(과거 승하차 실적)의 일곱 파일 한 묶음이야. 외부 지도 API의 이동시간으로 임의 대체하는 것도 원문 요구와 맞지 않아.

예를 들어 아래 세 행은 모두 가상 값이야.

# employees.csv 일부라고 가정
emp_id,site_id,shift_code
E001,ICN,ICN_A

# shifts.csv 일부라고 가정
shift_code,site_id,start_time,end_time
ICN_A,ICN,06:00,14:00

# work_schedule.csv 일부라고 가정
work_date,emp_id,shift_code,work_status
2026-07-20,E001,ICN_A,WORK

이제 shifts.csv에서 ICN_A가 삭제됐다면? 각각의 CSV는 잘 파싱될 수 있지만 구성원이 참조하는 근무시간대가 사라졌어. 반대로 work_status=BROKEN이라면 참조는 연결돼도 업무적으로 허용된 상태(WORK/OFF)가 아니지.

  • 형식 검증은 파일을 기대한 구조로 읽을 수 있는지 확인해. 필수 열, 숫자, 날짜 문자열의 실제 유효성 등을 살핀다. 2026-02-30처럼 모양만 날짜인 값은 달력상 날짜가 아니야.
  • 참조 검증은 ID 연결의 존재와 일관성을 확인해. emp_id가 구성원 목록에 있는지, shift_code가 근무시간대에 있는지 등이야.
  • 업무 규칙 검증은 읽히고 연결된 값이 운영상 허용되는지 판단해. 이동시간은 음수가 될 수 없고, 날짜별 근무 대상과 휴무자를 바르게 구별해야 하지. 실제 날짜 범위·중복 행·근무표 완전성도 계약에 따라 검사해야 해.

여기서 입력 검증과 결과 검증을 섞지 말자. 입력 OFF는 유효한 값일 수 있어. 그런데 Creator가 그 구성원을 출근 노선에 배정했다면 잘못된 것은 입력이 아니라 계산 결과야. 시험 원문에 따르면 그 근무일의 근무자는 각 방향 정확히 한 번 배정되어야 하고 휴무자는 배정하지 않아야 해. 과거 승차율로 좌석 확보 대상을 줄여서도 안 되지.

일곱 CSV의 일관성은 파일 각각 정상이냐보다 강한 조건이야. A 시점의 employees.csv와 B 시점의 work_schedule.csv를 섞으면 두 파일 각각의 구조가 정상이어도 없는 구성원을 참조하거나 변경된 근무 상태가 반영되지 않을 수 있어.

⏳ 3. 검증이 끝났는데도 왜 위험할까? TOCTOU

이제 시간을 실제로 따라가 보자. 서버가 파일 경로 prepared/B/work_schedule.csv를 열어 WORK를 검사했어. 2초 뒤 다른 프로그램이 그 경로의 내용만 BROKEN으로 교체했어. 적용 과정에서 서버가 그 경로를 다시 읽는다면 검사했던 WORK와 사용한 BROKEN은 서로 달라.

시간         검사기                 파일 경로                 적용기
10:00:00     WORK 읽고 검증 ───────► [WORK]
10:00:01                            [BROKEN] ◄── 다른 작업이 내용 교체
10:00:02                                                    [BROKEN] 다시 읽어 적용

결론: 검사한 바이트 ≠ 적용한 바이트

이것이 TOCTOU(Time of Check to Time of Use)야. '검사 시점'과 '사용 시점' 사이에 보호하려던 대상의 상태가 달라지는 경쟁이지. 적용 직전에 한 번 더 검사하자는 제안은 약해. 재검증이 끝나고 사용하는 사이에 또 바뀔 수 있기 때문이야. 심지어 파일을 읽고 난 뒤 같은 경로를 다시 여는 코드라면 재검사도 경로 변경을 막지 못해.

해결의 방향은 시간을 0초로 줄이는 게 아니라 검사한 대상과 사용하는 대상을 동일하게 만드는 것이야. 그 목적에 쓰는 중요한 도구가 불변 스냅샷이지.

📸 4. 불변 스냅샷: '같은 파일명'이 아니라 '같은 내용'

스냅샷은 일정한 시점의 입력 내용을 따로 고정한 사본이야. 불변(immutable)은 확정 후 사본의 내용을 수정하지 않는다는 운영 규칙이지. 원본 B를 수정해도 S2가 변하지 않는다면 검사기와 계산기는 안전하게 S2만 볼 수 있어.

수정될 수 있는 B 폴더
        │
        ├── [일곱 CSV를 일관되게 확보] ──► 불변 스냅샷 S2
        │                                  ├── 내용 해시 H2
        │                                  ├── 입력 검증보고서 V2
        │                                  └── 이후 계산 job의 입력
        └── 이후 B 폴더 수정 ───────────────X S2에는 영향 없어야 함

다만 복사가 완료된 뒤 불변이라는 것과 복사 중 일곱 파일이 같은 버전이었다는 건 달라. 예컨대 10:00에 employees.csv를 복사하고 10:01에 근무표 생성기가 일곱 파일을 새 버전으로 고치기 시작했으며 10:02에 work_schedule.csv를 복사했다면, S2는 영원히 바뀌지 않는 잘못 섞인 사본일 수 있어.

방법은 몇 가지야. (1) 준비 도중 쓰는 draft/와 완료 후 공개하는 ready/를 분리하고, 완료된 묶음은 수정 금지로 만드는 방법. (2) 원본 작성자와 읽는 사람이 합의한 잠금·버전 규칙을 사용하는 방법. (3) 일관된 DB 읽기 스냅샷에서 일곱 자료를 함께 추출하는 방법. 완성된 폴더를 원자적으로 이름 바꾸는 것은 공개 시점의 경로 전환을 도울 수 있지만, 그 전에 일곱 파일이 일관되게 준비되지 않았다면 해결이 아니야. 폴더의 원자적 전환도 파일시스템과 배포 조건에 의존하지.

한 가지 가상 SQLite 구현에서는 각 원본 CSV 행을 snapshot_id가 붙은 레코드로 DB에 적재할 수 있어. 원본 바이트도 보관하면 이후 파싱 오류를 재현하기 좋아. 다만 데이터 테이블에 행만 보존하는 방식은 인코딩, 열 순서, 원본의 불필요한 공백 등 파일 원형을 완전히 복원하지 못할 수 있어. 어떤 수준의 재현성이 필요한지 결정해야 해.

🔏 5. 파일명, 해시, 스냅샷 ID, 버전, 적용 세대는 서로 무엇이 다를까?

'버전'이라는 단어를 다섯 가지 의미로 쓰면 반드시 혼동이 생겨. 차이를 분리해 보자.

식별자 실제로 답하는 질문 이것만으로 증명 못 하는 것
파일명 work_schedule.csv 어디에 접근할까? 그곳 내용이 안 변했다는 사실
후보 이름 B 또는 표시 버전 v2 사람이 어느 후보로 부를까? 바이트/내용 동일성
내용 해시 H2 정해진 방식으로 표현한 바이트가 같은가? 업무 규칙 준수, DB 원자성
불변 snapshot_id=S2 저장소가 어떤 고정 입력 묶음을 가리키나? 불변성 규칙이 실제 강제되는지
적용 세대 generation=8 공식 입력 상태가 몇 번째 전환 상태인가? 그 자체로 입력 내용을 알 수 있는지
validator_version=V3 어떤 검증 규칙으로 판단했나? 다른 버전 규칙의 통과 여부
conditions_version=C4 계산 조건의 어느 변경 상태인가? 결과 자체가 맞는지

해시 함수 SHA-256은 주어진 바이트를 고정 길이 값으로 바꿔. 같은 바이트는 같은 해시를 만들어. 아주 드물지만 해시 충돌 가능성은 수학적으로 존재하므로 동일성의 절대적인 논리 증명과 동일시하면 안 돼. 정상적인 파일 무결성 확인에서 SHA-256은 강한 도구지만, 원본이 틀리면 그 틀린 원본에도 지문이 생겨.

예를 들어 work_status=BROKEN 파일을 해시한 뒤 1주일 후 똑같은 해시를 얻었어도 여전히 업무상 잘못된 값이야. 그리고 해시가 같아도 적용 중 DB 작업이 절반만 수행되는 것을 막지는 못해. 원자성은 나중에 배울 트랜잭션 책임이야.

일곱 파일 전체 해시를 만들 때는 파일 이름 → 파일 크기/바이트 또는 파일별 해시를 일정한 순서와 모호하지 않은 인코딩으로 직렬화한 manifest를 사용하면 좋아. 파일 하나의 해시로 전체 데이터셋을 대표하면 나머지 여섯 파일을 놓치게 돼. 원본 바이트 기준인지 파싱·정규화된 행 기준인지도 정해야 해. 두 CSV가 열 순서만 다르면 의미는 같을 수 있지만 원본 바이트 해시는 다르지. 반대로 정규화 과정이 서로 다른 의미를 잘못 합칠 수도 있으므로 정규화 규칙 버전까지 기록하면 재현성이 좋아져.

같은 내용 다시 적용 — 왜 세대 번호가 필요할까?

현재 S1 / 세대 7에서 S2 / 세대 8로 바꾸고, 운영자가 S1로 되돌리기를 하면 S1 / 세대 9가 돼. 처음 S1과 마지막 S1의 내용은 같아도 중간에 상태 변화가 있었어. 오래된 job이 현재 snapshot_id=S1만 확인하면 자기가 시작했던 세대 7과 현재 세대 9를 구별하지 못하지. 이것을 ABA 문제와 연결해 생각할 수 있어.

그런데 운영자가 이미 S1이 적용된 상황에서 다시 S1을 누른 경우는 정책 선택이 필요해. 완전한 무변경(no-op)으로 취급해 세대를 그대로 둘 수도 있고, 감사상 새로운 적용 사건으로 기록해 세대를 올릴 수도 있어. 전자는 불필요한 재계산을 줄이지만 재적용 행위가 현재성 변경으로 보이지 않아. 후자는 명시적 재적용을 새 상태로 인식하지만 같은 내용의 계산까지 STALE로 만들 수 있어. '같은 내용이면 항상 세대 증가'도 '절대 증가 안 함'도 보편적인 정답은 아니야. 무엇을 새 운영 사건으로 정의할지 먼저 정해야 해. 어느 경우든 단순히 문자열 v2가 같다는 이유로 판단해서는 안 돼.

📑 6. 검증보고서는 '누가 무엇을 믿었는지'를 남기는 증거야

VALID=true 한 줄은 부족해. 검증보고서는 특정 스냅샷, 내용 해시, 검증 규칙 버전, 시각, 세부 실패 위치를 묶어야 해. 이 보고서는 검증 결과이지 실제 적용 기록은 아니야. 가상 예시는 아래와 같아.

{
  "report_id": "VR-002",
  "snapshot_id": "S2",
  "dataset_hash": "<실제로 계산한 SHA-256이 들어갈 자리>",
  "validator_version": "input-v3",
  "status": "INVALID",
  "errors": [{
    "file": "work_schedule.csv",
    "row": 28,
    "column": "emp_id",
    "code": "UNKNOWN_EMPLOYEE",
    "message": "해당 구성원 ID를 찾을 수 없음"
  }]
}

이것은 실제 시험 데이터 28행의 오류가 아니라 가상 행이야. 검증기가 처리 중 종료됐다면 INVALID(규칙 위반 확인)과 ERROR 또는 INCOMPLETE(판정 자체 미완료)를 구분해야 해. 실패한 검증보고서는 운영자가 오류를 고칠 때 유용하므로 남길 수 있지만, 그 스냅샷의 공식 적용을 허가해서는 안 돼. 검증 로직이 input-v3에서 input-v4로 바뀌었다면 과거의 성공이 새 규칙의 성공을 의미하지 않는다는 점도 명시해야 하지.

🗃️ 7. 적용 포인터 — 데이터 보존과 현재 상태를 분리하기

이제 S1과 S2가 모두 수정되지 않는다고 가정해 보자. S1 행을 삭제하고 S2 행으로 덮어쓰면 어제의 노선 R1이 어떤 근무표에서 계산됐는지 추적하기 어려워져. 그래서 스냅샷은 남겨두고 현재 적용 포인터 하나를 바꾸는 방식을 택할 수 있어.

                     [active_state]
                snapshot_id=S2, generation=8
                           │
                           ▼
 [스냅샷 S1: 보존]      [스냅샷 S2: 현재 입력]
          │                      │
 [과거 결과 R1: S1]      [재계산 결과 R2: S2]

여기서 active_state는 '새 계산의 기본 입력이 어느 스냅샷인가?'에 답하는 권위 있는 DB 기록이야. 스냅샷과 별도로 존재해야 해. 과거 결과 R1도 source_snapshot_id=S1로 연결해서 보존해. 보존이 무기한 삭제 금지라는 뜻은 아니야. 추후 보관·폐기 정책이 필요하지만, 참조 중인 스냅샷을 먼저 지우면 재현성을 잃으므로 주의해야 해.

특히 과거 결과의 VALID 여부와 현재 결과의 CURRENT 여부를 나눠야 해. R1은 S1에 대해 규칙을 지키는 VALID 결과일 수 있어도 현재 입력 S2에 대한 CURRENT 결과는 아니야. 이 상태를 STALE이라고 표시할 수 있지.

🔐 8. 적용 트랜잭션 — '전체 성공 또는 전체 실패'가 필요한 경계

SQLite에 포인터와 적용 세대를 저장한다고 해 보자. S2를 적용하면서 active_snapshot_id=S2, generation=8, 기존 현재 결과의 CURRENT 해제라는 세 변경이 필요해. 첫 번째만 성공하고 프로그램이 죽으면 DB가 모순될 수 있어. 여기서 트랜잭션은 관련 DB 변경을 하나의 확정 단위로 묶는 장치야.

적용 전:     S1 / 세대 7 / 현재 결과 R1
BEGIN
  보고서·스냅샷·현재 세대 확인
  포인터 S2로 변경
  세대 8로 증가
  R1을 현재 결과로 제공하지 않도록 변경
COMMIT ──► S2 / 세대 8 / 새 결과 없음(STALE R1 보존)

중간 실패 + ROLLBACK ──► S1 / 세대 7 / R1 CURRENT 그대로

원자성은 COMMIT이 성공했다면 모든 관련 DB 변경이 한 단위로 확정되고, 커밋하지 못한 변경은 철회된다는 뜻이야. 격리성은 동시에 진행 중인 트랜잭션들이 서로의 미완성 변경을 임의로 보지 않도록 조정한다는 뜻이지. 지속성은 정상적인 DB·저장장치 보장 아래 커밋된 변경이 재시작 후에도 남는 성질이야. 흔히 원자성·일관성·격리성·지속성을 ACID라고 부르는데, DB가 업무 규칙 자체를 알아서 검사해 주는 것은 아니야.

가상 SQLite SQL을 보자. 다음은 실행하지 않은 구조 예시이고, 전체 스키마·권한 처리·오류 처리·보고서 유효성 검사까지 구현한 완성 프로그램은 아니야.

BEGIN IMMEDIATE;

-- 애플리케이션은 이 트랜잭션에서 S2의 불변성,
-- 검증 통과 보고서, 규칙 버전, 사용자 권한을 확인해야 한다.

UPDATE active_state
SET snapshot_id = :new_snapshot,
    generation = generation + 1,
    current_result_id = NULL
WHERE id = 1
  AND generation = :expected_generation;

-- 변경 행 수가 정확히 1이 아닐 경우 ROLLBACK;
-- 관련 DB 변경이 모두 끝난 경우에만 COMMIT;
COMMIT;

여기서 :expected_generation=7인데 다른 요청이 이미 세대 8로 적용했다면 UPDATE 대상은 0행이야. 이를 조건부 갱신 또는 Compare-and-Swap(CAS)에 가까운 패턴이라고 불러. '내가 본 상태가 여전히 맞으면 바꾼다'는 뜻이야. 조건 검사와 변경이 한 SQL 갱신 안에 들어 있으므로 검사 후 변경 사이에 다른 요청이 끼어드는 문제를 줄여 줘. 0행을 성공으로 잘못 처리하지 않아야 하고, 앞뒤의 관련 검사는 같은 트랜잭션 안에서 해야 해.

SQLite는 보통 동시 쓰기 트랜잭션을 한 번에 하나씩 처리해. WAL 모드라도 단일 작성자라는 제약은 남아 있어. 그래서 파일 읽기·검증·노선 최적화까지 긴 쓰기 트랜잭션으로 묶으면 잠금 대기와 지연이 커질 수 있어. 오래 걸리는 준비/계산은 트랜잭션 밖, 원자적 공개는 짧은 트랜잭션 안이라는 분리가 합리적이야.

단, 트랜잭션은 SQLite DB 내부 상태에 대한 보장이야. DB 외부 파일의 수정, 브라우저 표시, 외부 API 호출을 자동으로 되돌리지는 않아. 스냅샷 파일을 DB 밖에 둔다면 파일 완성·영속화·DB 포인터 확정의 순서를 별도로 설계해야 해. 포인터가 아직 완성되지 않은 파일을 가리키면 안 되지.

두 운영자의 경쟁

10:00  운영자 갑, 을 모두 현재 세대 7을 봄
10:01  갑: S2 적용, 기대 세대 7 → COMMIT, 현재 세대 8
10:02  을: S3 적용, 기대 세대 7 → 조건부 갱신 0행
10:03  을 화면: '현재 상태가 변경됨. 다시 확인 필요'

을의 요청을 자동으로 현재 세대 8에 맞춰 무조건 재시도하면 갑이 선택한 S2를 몰래 덮어쓸 수 있어. '경쟁을 발견했다'는 사실은 에러 복구와 다르며, 운영자 의사결정이 필요할 수 있어.

응답 유실의 반례

DB에는 S2 적용 COMMIT이 성공했지만 브라우저로 돌아가는 성공 응답이 사라질 수 있어. 사용자가 다시 누르면 같은 의도의 적용이 두 번 처리될 수 있지. 서버 응답 실패 = DB 변경 실패가 아니야. 현재 상태를 조회해 사실을 확인하거나 요청 ID를 저장해 중복을 인식하는 설계가 필요해. 이 주제는 멱등성과 연결되지만 여기서는 '커밋과 응답은 별개의 사건'이라는 인과만 기억하자.

🕒 9. 정상·실패 적용 시간표 — 어떤 상태가 살아남는가?

정상 적용: 모든 수치·식별자는 가상

시간 발생 사건 공식 입력 CURRENT 결과 과거 기록
10:00 기존 운영 S1, 세대 7 R1(S1) S1 보존
10:01 B 선택 S1, 세대 7 R1 선택 사실
10:02 일곱 CSV를 S2로 확보 S1, 세대 7 R1 S2 후보
10:03 S2 검증 통과 S1, 세대 7 R1 S2·보고서
10:04 적용 COMMIT S2, 세대 8 없음 R1은 STALE로 보존
10:05 S2 계산 job 생성 S2, 세대 8 없음 RUNNING job
10:08 R2 검증·현재성 확인·COMMIT S2, 세대 8 R2(S2) R1 보존

입력 검증 실패: S2에서 없는 emp_id 참조가 확인되면 INVALID 보고서는 남기되 포인터 변경은 하지 않아. S1 / 세대 7 / R1 CURRENT가 그대로야. 사용자에게는 어느 파일·행·열·규칙이 왜 실패했는지 알려 줄 수 있어.

적용 도중 실패: 포인터를 바꾼 SQL 뒤 다른 관련 SQL이 실패하고 전체 트랜잭션을 ROLLBACK하면 S1 / 세대 7 / R1 CURRENT가 그대로야. 다만 검증보고서가 이미 별도 트랜잭션으로 저장돼 있었다면 보고서 자체는 남을 수 있어. 이건 모순이 아니야. 검증 이력과 적용 상태는 별개니까.

정상 적용 후 계산 실패: S2 / 세대 8의 적용은 유지되고, R1은 S1의 과거 결과로 남아. S2에 대한 CURRENT 결과는 없다고 표시해야 해. '입력 적용'과 '계산 결과 확정'을 분리한 설계에서는 계산 실패가 앞선 적용까지 자동 취소하지 않아. 입력과 결과를 함께 전환해야 하는 강한 업무 요구라면 다른 배포/확정 정책을 택할 수 있지만, 시험 원문은 적용 후 재계산 전의 중간 상태를 구분하라고 했어.

🧮 10. Creator의 입력 고정과 '늦게 끝난 계산'의 위험

시험 복기에 등장하는 Creator/Validator의 정확한 출제 의미는 불확실해. 여기서는 Creator=노선 생성 컴포넌트, Validator=결과 검증 컴포넌트라는 가상 소프트웨어 설계 의미로 사용해. AI가 코드를 만드는 역할과 동일시하지 않을 거야.

한 번 노선 생성 버튼을 누르면 Creator는 막연히 '현재 데이터'를 계속 재조회하면 안 돼. 계산 도중 현재 데이터가 바뀌면 앞 절의 파일 TOCTOU와 비슷한 혼합 입력 위험이 생기거든. job을 만드는 순간 다음 정보를 고정해야 해.

{
  "job_id": "J17",
  "input_snapshot_id": "S1",
  "input_dataset_hash": "H1",
  "input_generation": 7,
  "period": {"start_date":"2026-07-20", "end_date":"2026-07-24"},
  "capacity": 45,
  "arrival_buffer_minutes": 20,
  "algorithm_version": "route-a1",
  "status": "RUNNING"
}

이 JSON은 가상·미실행 예시야. 시험 원문의 기본 45석, 20분 조건을 사용했지만 선택 기간과 ID는 임의로 정했어. 원문에서는 출근·퇴근 시각과 수요 판정도 중요하므로, 최종 생성기는 검증된 travel_times.csv, 근무표, shift 정보를 함께 참조해야 해. capacity나 arrival_buffer_minutes가 화면에서 바뀌더라도 이미 시작한 J17의 계산 조건은 변하지 않아야 재현할 수 있어.

두 번째 TOCTOU: 계산 완료와 결과 확정 사이

시간   Creator(J17)                         공식 상태
11:00  S1, 세대 7, 정원 45로 시작          S1, 세대 7
11:01  계산 수행 중                         운영자가 S2 적용
11:02  계속 S1의 불변 입력으로 계산         S2, 세대 8
11:05  R17 완성, S1 기준 규칙 검사 통과      S2, 세대 8
11:06  결과 확정 트랜잭션: 7 == 8 ? NO     현재 결과 포인터 변경 금지

R17이 원래 입력 S1에 대해 완벽할 수도 있어. 그러나 현재 운영 입력 S2에 대한 결과는 아니야. 규칙에 맞음(VALID)과 지금 보여도 됨(CURRENT)은 다른 판단이지.

위험한 코드는 if current_generation == 7을 트랜잭션 밖에서 확인하고 시간이 지난 뒤 current_result_id=R17을 기록하는 거야. 중간에 S2가 적용되면 확인한 상태가 이미 낡아. 그러니 결과 확정의 현재성 비교와 포인터 변경을 같은 짧은 DB 트랜잭션에 넣어야 해.

-- 개념 예시: 결과 검증이 이미 끝났고 R17 후보가 저장됐다고 가정
BEGIN IMMEDIATE;

UPDATE active_state
SET current_result_id = :candidate_result_id
WHERE id = 1
  AND snapshot_id = :source_snapshot_id
  AND generation = :source_generation
  AND conditions_version = :source_conditions_version;

-- 변경 행 수 1 + 결과 자체가 VALID/완성 상태인지 같은 트랜잭션에서 확인되어야 확정
-- 0행이면 현재 입력 또는 조건이 변경된 것: 후보는 보존 가능, CURRENT로는 확정 불가
COMMIT;

이 SQL은 구현 전체가 아니야. 특히 검증 완료 결과만 확정하는 규칙, 결과 소유권, 세대/조건 버전이 실제 어떤 테이블에서 관리되는지, 0행 처리, 트랜잭션 실패 처리를 보강해야 안전해. conditions_version 외에 기간·정원·도착 여유의 정확한 값 또는 불변 조건 스냅샷을 job과 결과에 연결해야 해. 조건 버전만 같고 내용이 수정 가능한 구조라면 또 같은 문제가 생겨.

정상 계산과 실패 계산을 대비하자

상황 J17의 입력 최종 확정 시 공식 입력 처리
변경 없음 S1·세대 7·조건 C3 S1·세대 7·C3 규칙 검증 통과 시 CURRENT 가능
데이터 변경 S1·세대 7·C3 S2·세대 8·C3 오래된 후보, CURRENT 거부
조건 변경 S1·세대 7·C3 S1·세대 7·C4 정원/기간/여유 불일치, CURRENT 거부
다시 S1 적용 S1·세대 7·C3 S1·세대 9·C3 내용 동일해도 세대 불일치, 기본 정책상 거부
결과 검증 실패 S1·세대 7·C3 S1·세대 7·C3 규칙 위반 후보, CURRENT 거부

여기에는 선택의 대가가 있어. 세대가 달라졌다는 이유로 오래된 계산을 거부하면 사실상 여전히 쓸 수 있는 결과까지 폐기할 수 있어. 반대로 세대 조건을 약화하면 의도하지 않은 되돌리기나 중간 운영 변경을 놓칠 수 있지. 엄격한 현재성 정책과 내용·조건 동등성을 인정하는 재사용 정책 중 무엇을 쓸지는 업무의 안전성과 비용을 고려해 결정해야 해. 초보 구현에는 우선 엄격한 세대 비교가 이해하고 증명하기 쉬워.

🖥️ 11. STALE 결과가 사라지는 것은 아니야 — 저장과 조회의 차이

R1을 삭제하지 않고 보존하되 새 적용 직후에는 '현재 노선' 화면에서 보여 주지 않거나 명확히 이전 데이터 기준이라고 표시해야 해. 예를 들어 운영자 화면에는 적용 S2 / 새 계산 대기 / 과거 R1(S1) 열람 가능이라고 표시할 수 있어. 반면 구성원에게 지금 이용할 노선을 보여 주는 화면은 새 결과가 확정되지 않았다면 재계산 중 또는 유효한 최신 노선 없음이라고 표시하는 편이 안전할 수 있어.

DB의 역사 기록: S1 ─ R1(VALID for S1)
                S2 ─ R2(아직 없음)

현재 적용: S2
현재 노선 조회: R1을 S2의 노선인 척 반환하지 않음
과거 이력 조회: R1을 'S1 기준'으로 명시하여 열람 가능

STALE은 계산이 틀렸다는 말(INVALID)이 아니라 현재 기준과 연결이 끊어졌다는 말이야. 새 결과 R2가 생겼다고 R1이 나중에 자동으로 오류가 되는 것도 아니지.

DB는 맞아도 캐시와 브라우저는 틀릴 수 있다

캐시는 예전에 계산한 응답을 잠깐 저장해 빠르게 반환하는 공간이야. 캐시 키가 routes:2026-07-20뿐이라면 S1과 S2의 해당 날짜 결과가 같은 칸을 차지할 수 있어. routes:g8:C3:2026-07-20처럼 입력 세대와 조건 버전을 포함하면 섞일 위험을 줄일 수 있지. 하지만 현재 세대 자체를 오래 캐시하거나, 캐시를 무효화하지 않으면 여전히 문제야.

브라우저에서도 순서 역전이 가능해. S1 노선을 조회한 요청 A가 느리게 도착하고, S2 현재 상태를 조회한 요청 B가 먼저 도착할 수 있어. 화면이 '나중에 도착한 응답이 언제나 최신'이라고 판단하면 S2를 표시했다가 다시 S1을 표시하는 오류가 생겨. 응답에 스냅샷/세대/조건 정보를 포함하고 화면이 현재 기준과 비교하도록 하면 도움 돼. 하지만 UI만 막는 것은 충분하지 않아. 서버 API에서도 현재 결과 조건을 강제해야 해.

🏗️ 12. 단일 서버·SQLite와 별도 WORKER·여러 서버의 보장 차이

단일 서버·단일 프로세스 + SQLite: 구조가 단순해. 스냅샷·검증보고서·적용 포인터·job·결과를 같은 DB에 저장하면 재시작 후에도 확인하기 좋아. 그렇다고 경쟁이 없는 것은 아니야. 같은 서버의 두 HTTP 요청이나 비동기 작업도 겹칠 수 있어. 전역 변수 하나에만 적용 세대를 넣으면 서버 재시작 때 사라지고 DB와 불일치할 수 있어.

웹 서버 + 별도 WORKER 프로세스 + SQLite: 긴 노선 계산을 웹 요청 처리에서 분리할 수 있어. 하지만 프로세스 간 메모리를 공유한다고 가정하면 안 돼. 웹 서버가 job의 고정 입력을 DB에 기록하고 WORKER는 그 job을 읽어야 해. WORKER가 종료돼도 DB의 RUNNING 기록을 어떻게 복구할지 설계해야 하지. 또한 여러 프로세스가 SQLite에 쓸 때 잠금 경합이 늘 수 있어. 원자적 포인터 변경과 세대 비교는 계속 DB에서 해야 해.

여러 서버 + 공유 DB: 서버 A와 B는 각자의 메모리와 캐시를 가져. A가 S2를 적용한 뒤에도 B의 캐시는 S1을 오래 보관할 수 있어. 그래서 공유된 권위 있는 상태 저장소와 조건부 갱신, 캐시 무효화/버전 키가 필요해. SQLite WAL 데이터베이스를 서로 다른 호스트에서 하나의 네트워크 파일처럼 공유하는 것은 일반적인 다중 서버 해법이 아니야. 그 경우 중앙 DB(예: PostgreSQL)나 별도의 메시지/작업 인프라를 고려할 수 있지만, 시험에서 요구한 스택은 아니야.

구성 이점 추가 손실·위험 여전히 필요한 보장
단일 프로세스·SQLite 적은 구성요소, 단순 디버깅 긴 계산이 요청 처리에 영향, 잠금 불변 입력, 짧은 커밋, 세대 비교
별도 WORKER·SQLite 계산과 웹 응답 분리 프로세스 종료·작업 인계·DB 경합 job에 입력 고정, 복구, 확정 CAS
여러 서버·중앙 DB 처리량 확대 가능 분산 캐시·중복 실행·운영 복잡성 공유 권위 저장소, 동시성 제어

여러 서버를 쓴다고 자동으로 신뢰성이 올라가지는 않아. 프로세스를 늘리면 계산은 확장하기 쉬워져도 현재 상태를 정확히 합의해야 하는 일이 더 어려워져. 반대로 단일 서버라고 자동으로 모든 결과가 일관된 것도 아니고.

⚖️ 13. 설계 대안마다 얻는 것과 잃는 것

선택 얻는 것 잃는 것/주의할 것

불변 스냅샷 + 포인터 과거 입력 보존·검증 대상 고정 저장 공간, 보관/폐기 정책

좋은 설계는 안전장치를 많이 붙이는 설계가 아니야. 어떤 문제가 생기면 무엇이 깨지고, 그 깨짐을 어떤 경계에서 막는지 설명 가능한 설계야.

🔍 14. '실제로 검증했다'고 말하려면 어떤 증거가 있어야 할까?

아래는 제안 테스트 시나리오이며 미실행이야. 테스트 코드나 실행 로그가 제공되지 않았으므로 통과했다고 주장할 수 없어.

재현 행동 확인해야 하는 DB·API·UI 증거
필수 열 없는 CSV 후보 검증 오류 보고서에 파일/열, 적용 포인터와 세대 불변
존재하지 않는 emp_id 입력 참조 오류 코드, 기존 노선 그대로 CURRENT
검증 후 원본 폴더 내용 수정 검증한 불변 스냅샷 해시와 실제 사용 입력이 동일
일곱 CSV 복사 중 원본 변경 혼합 사본을 공개하지 않는지, 원본 일관성 보호 방식 확인
적용 트랜잭션 중 강제 오류 포인터·세대·현재 결과 상태가 함께 롤백되는지
세대 7의 두 적용 요청 경쟁 하나만 성공, 다른 요청은 충돌로 보고되는지
S1 job 실행 중 S2 적용 S1 후보가 S2 CURRENT를 덮지 못하는지
S2 적용 후 새 계산 실패 S2는 적용 상태, R1은 과거 결과로 보존, 현재 결과 없음
같은 S1 재적용 정의한 no-op/새 적용 정책과 세대 변화 일치
오래된 API 응답이 나중 도착 화면이 이전 노선을 현재 결과로 다시 표시하지 않는지
서버 재시작 포인터·스냅샷·보고서·job·결과가 복원되는지

시험 복기 질문이 요구하는 자세는 여기에서 나와. 'AI가 테스트가 성공했다고 말했다'는 보고는 독립적인 증거가 아니야. 제3자가 어떤 입력을 바꿨고, 어떤 API나 명령을 실행했고, 어떤 DB 행과 화면 상태를 비교했는지 확인할 수 있어야 하지. 실제 코드가 없으므로 여기서는 검증 계획과 검증 성과를 분명하게 구분해 둔다.

🧠 15. 내 말로 설명하기 — 원인을 짚는 질문

이 질문들은 이 수업에서 배운 개념을 자기 언어로 연결하기 위한 것이야. 지금 정답을 외우기보다 시간 순서와 실패 원인을 설명해 봐.

질문 1. 운영자가 B를 선택하고 검증에 성공했어. 왜 아직 공식 입력은 S1이어야 할까? '선택', '검증', '적용' 각각이 DB에서 무엇을 바꾸는지 말해 봐.

질문 2. work_schedule.csv가 검증 당시와 적용 당시 같은 이름이었어. 왜 이것만으로 안전하지 않을까? 적용 직전 재검증도 만능이 아닌 이유를 설명해 봐.

질문 3. S2의 해시가 검증 때와 적용 때 같아. 그런데 적용 SQL 세 개 중 두 번째에서 장애가 생겼어. 해시로 원자성을 보장할 수 있을까? 어떤 도구가 필요하고 왜일까?

질문 4. '일곱 파일을 복사했고 복사본을 수정하지 않았다'는 개발자의 주장만으로 일관된 스냅샷이라고 할 수 있을까? 복사 도중의 반례를 만들어 봐.

질문 5. S1→S2→S1으로 재적용했어. 마지막 S1의 내용은 처음과 같아. 그런데 왜 세대를 비교하면 도움이 될까? 같은 S1을 다시 적용할 때 세대를 올리는 정책과 안 올리는 정책의 손실도 비교해 봐.

질문 6. Creator가 세대 7과 정원 45로 계산을 시작했고, 완료 전 데이터 세대가 8, 정원이 40으로 바뀌었어. 결과가 정원 45 기준 검증에 통과했어도 왜 현재 노선으로 확정하면 안 될까? 어디에서 무엇을 비교해야 할까?

질문 7. S2 적용은 COMMIT했지만 새 노선 계산이 실패했어. DB에서 S1과 R1을 삭제해야 할까? 운영자 화면과 구성원 화면에 무엇을 다르게 보여 주어야 할까?

질문 8. 웹 서버와 WORKER를 분리하면 왜 전역 변수의 현재 버전만으로는 부족할까? 서버가 여러 대가 되면 무엇이 한층 더 어려워질까?

Bailey의 한마디: “해시가 같으니 안전하다고? 정확히 무엇이 같고, 어느 순간까지 같으며, DB의 몇 가지 변경이 같이 성공했다는 증거는 어디 있지?”

Ailey의 연결: 해시는 내용 비교를, 스냅샷은 입력 고정을, 검증보고서는 규칙 판정의 근거를, 포인터와 세대는 현재 운영 기준을, 트랜잭션은 원자적 확정을, 결과의 입력 메타데이터는 계산의 출처를 맡아. 각 장치가 다른 질문에 대답하기 때문에 함께 필요한 거야.
