🧭 1. 사용자가 요청을 보냈는데, 왜 결과를 기다리지 않아도 될까?

통근버스 운영자가 화면의 ‘노선 생성’ 버튼을 누른다고 생각해 보자. 서버는 그날 근무하는 구성원을 골라 정류장에 배정하고, 버스 정원과 도착 시간을 지키는 노선을 찾고, 결과가 규칙을 지켰는지 검사해야 한다. 계산이 2초 만에 끝날 수도 있지만, 조건이 복잡하면 2분 이상 걸릴 수도 있다.

가장 단순한 구현은 브라우저 요청 한 번 안에서 모든 일을 하는 것이다.

시간 →
브라우저 ─ POST /plans/generate ─→ 웹 서버 ─ 계산 ─ 검증 ─ DB 저장 ─→ HTTP 200 + 결과
          │                                                   │
          └──────────── 브라우저가 이 요청의 응답을 기다림 ───────┘

여기서 브라우저가 ‘기다린다’는 말은 반드시 CPU를 계속 쓰며 멈춰 있다는 뜻은 아니다. 네트워크 응답이 돌아오기를 기다리는 논리적 상태라는 뜻이다. 웹 서버가 비동기 프레임워크를 써도, 이 HTTP 요청의 최종 결과가 생성 완료에 의존한다면 응답과 긴 계산은 여전히 한 묶음이다. 네트워크 연결이 끊기거나 프록시의 시간 제한에 걸리면, 서버 쪽 계산이 끝났는지 브라우저는 알기 어렵다. 연결이 끊겼다고 계산이 자동 취소되는 것도 아니다.

그렇다면 ‘버튼 누르기’와 ‘계산 끝나기’를 분리해 보자.

[운영자 브라우저]  POST /jobs
       │
       ▼
[웹 서버: 접수] ── 데이터·조건의 참조를 담은 job 기록 ──▶ [DB]
       │                                             │
       └── HTTP 202 + job_id ◀─────────────────────────┘
                                                       │
                                             [WORKER가 작업 획득]
                                                       │
                                            계산 → 검증 → 결과 확정
                                                       │
[브라우저] ── GET /jobs/{id} ────────────────────────────┘
              상태/진행률/완료 결과의 위치를 조회

202 Accepted는 ‘요청을 받아 처리 대상으로 삼았다’는 뜻이지 ‘노선이 완성됐다’는 뜻이 아니야. 사용자는 접수 번호인 job_id로 진행 상황을 조회한다. 중요한 질문은 그다음이다. ‘받아 두었다’는 사실이 어디에 남아 있는가? 웹 서버의 메모리에만 있으면 프로세스가 죽는 순간 사라질 수 있다. DB에 커밋했으면 서버 프로세스가 바뀌어도 그 사실을 다시 읽을 수 있다. 비동기란 이 차이를 대신 보장해 주는 주문이 아니다.

선수 개념을 지금 필요한 만큼만 다시 세우기

  • 동시성(concurrency): 작업 A와 B가 시간상 겹쳐 진행될 수 있게 조정하는 성질. CPU 하나에서 번갈아 실행될 수도 있다.
  • 병렬성(parallelism): 둘 이상의 CPU 코어/실행 자원에서 실제로 동시에 계산하는 것. WORKER 두 개라고 무조건 병렬 성능이 나오는 것은 아니다.
  • 비동기(asynchrony): 요청자가 특정 일이 끝날 때까지 자신의 다음 진행을 반드시 막아 두지 않는 인터페이스/실행 방식. 비동기 API를 호출했다는 이유로 작업 기록이 영속화되지는 않는다.
  • 프로세스(process): 운영체제가 관리하는 실행 단위. 별도 프로세스는 웹 서버와 메모리·실패 경계를 분리할 수 있지만, 같은 디스크·DB·CPU를 공유할 수 있다.
  • 트랜잭션(transaction): DB 변경을 한 묶음으로 확정하거나 취소하는 경계. COMMIT하기 전 변경은 다른 연결에서 보이지 않을 수 있으며 종료 시 롤백된다.

이 구분을 놓치면 ‘별도 프로세스로 돌리니 안전하다’ 또는 ‘async 함수이니 요청이 끊겨도 복구된다’는 잘못된 결론으로 뛰기 쉽다.

작업 실행의 세 가지 경계 — 접수, 실행 권한, 최종 공개

🧩 2. 생산자·큐·소비자·WORKER·프로세스는 같은 말이 아니다

택배를 떠올리면 관계를 먼저 볼 수 있다. 고객의 발송 요청을 접수한 직원은 생산자, 맡길 물건의 순서를 적는 목록은 대기열, 목록에서 일을 가져가는 주체는 소비자, 실제로 분류·배송 일을 수행하는 것은 WORKER, 직원들이 사용하는 물리적 사무실 하나는 프로세스에 비유할 수 있다. 이 비유의 경계는 분명하다. 소프트웨어에서는 소비자와 WORKER가 같은 함수일 수 있고, 한 프로세스 안에 여러 WORKER 실행 단위가 들어갈 수도 있다.

개념 맡은 역할 반드시 독립 프로세스인가? 가진다고 착각하기 쉬운 보장
작업 생산자(producer) 새로운 일을 정의·접수하고 큐/DB에 알림 아니오. 웹 핸들러일 수 있음 ‘보냈으니 저장됐겠지’
대기열(queue) 지금 실행 가능한 일의 순서와 대기를 표현 아니오. 메모리·DB·브로커 등 여러 구현 ‘넣었으니 영원히 남겠지’
소비자(consumer) 대기 중인 메시지/작업을 받아 옴 아니오. WORKER 내부 동작일 수 있음 ‘받았으니 끝났겠지’
WORKER 계산·검증·결과 확정 등 실제 일을 수행하는 실행 주체 아니오. 스레드·태스크·프로세스 가능 ‘한 번만 실행되겠지’
별도 프로세스 웹 서버와 분리된 메모리·종료 단위 정의상 별도의 OS 프로세스 ‘분리됐으니 복구도 되겠지’
브로커(broker) 메시지 수신·보관·전달·재전달을 담당하는 서비스 대개 별도 서비스 ‘브로커가 DB 결과까지 책임지겠지’

WORKER는 일하는 역할이고 프로세스는 그 역할을 담는 실행 경계다. 다음 두 구현은 둘 다 ‘WORKER가 있다’고 말할 수 있다.

구조 A: 한 프로세스
┌──────────────────── web-server process ────────────────────┐
│ HTTP handler → in-memory Queue → background worker thread │
└────────────────────────────────────────────────────────────┘
                  서버 프로세스가 죽으면 둘 다 영향

구조 B: 프로세스 분리
┌── web process ──┐        ┌── worker process ────────┐
│ HTTP handler    │        │ poll/claim → compute     │
└──────┬──────────┘        └──────────┬───────────────┘
       └────────────── shared DB ────┘
  웹 프로세스 종료 ≠ WORKER 즉시 종료
  단, DB·디스크·호스트가 고장 나면 둘 다 영향

구조 B도 WORKER를 누가 시작하고, 죽으면 누가 다시 시작하는지 없으면 자동 복구되지 않는다. 개발 중 셸에서 수동으로 시작했다면 셸 종료와 함께 죽을 수 있다. 운영에서는 supervisor, 컨테이너 재시작 정책, 오케스트레이터 등 별도의 재기동 장치가 필요하다. 그것이 재기동에 성공해도 어떤 미완료 작업을 다시 실행할지는 작업 저장 모델이 결정한다.

무엇이 ‘큐’인가: 저장 위치와 수명

             전원/프로세스 재시작 후 다시 찾을 수 있는가?
메모리 Queue       ─── 대체로 아니오 (해당 프로세스와 함께 소멸)
DB jobs 테이블     ─── 예, 커밋된 기록이고 DB 저장소가 유지되면
외부 메시지 브로커   ─── 설정·내구성·확인 절차에 따라 달라짐

                  ┌──── Web 서버의 RAM ────┐
request ────────▶ │ deque / asyncio.Queue │ ──▶ worker
                  └───────────────────────┘
                                  VS
request ────────▶ [SQLite jobs 테이블 COMMIT] ◀── claim/poll ── worker
                                  VS
request ────────▶ [broker persistent message] ── deliver ── worker

메모리 큐는 처리 속도가 빠르고 구성이 간단하다. 하지만 프로세스 메모리의 수명을 벗어날 수 없다. DB 기반 job은 큐를 별도로 두지 않아도 status='queued'인 행 전체가 논리적인 대기열이 된다. 이 경우 DB는 상태의 원본(source of truth)이고, WORKER는 조건에 맞는 행을 찾아 선점한다. 브로커를 추가하면 전달 기능이 전문화되지만, DB에 기록한 업무 상태와 브로커 메시지 두 저장소 사이에 새로운 불일치 문제가 생긴다.

세 가지 ‘수명’은 별도로 보자

  1. HTTP 요청의 수명: 브라우저가 보낸 요청에서 응답이 끝날 때까지.
  2. job 기록의 수명: 접수된 작업의 상태가 조회·감사에 필요한 동안.
  3. WORKER 실행의 수명: 실제 계산을 수행하는 프로세스/태스크가 살아 있는 동안.

긴 작업을 HTTP 요청 바깥으로 빼는 목적은 이 셋이 반드시 같은 순간에 시작·끝나지 않게 하는 것이다. 대신 서로를 연결할 작업 ID, 상태, 선점 권한, 결과 참조가 필요해진다.

🧾 3. 접수는 언제 ‘정말 접수’가 되는가: 커밋·202·작업 ID

운영자가 기간, 정원, 도착 여유 시간을 바꿔 다시 계산을 누른다고 하자. 여기서 POST /jobs는 두 가지 일을 구별해야 한다. 첫째, 요청이 유효한지, 둘째, 나중에 실행할 일이 지속적으로 기록됐는지이다. 계산 자체의 성공 여부는 아직 알 수 없다.

잘못된 사건 순서: 응답부터 보내기

T1  Web: job_id J-101을 메모리에서 생성
T2  Web: HTTP 202 {job_id:J-101} 전송
T3  Web: DB INSERT 시도
T4  Web: 프로세스 강제 종료 → DB INSERT 없음
T5  Client: GET /jobs/J-101 → 404

사용자가 정상 접수로 이해할 수 있는 응답을 받았는데, 서버에는 그 사실이 없다. 그러니 202를 보낼 기준은 계산 시작이 아니라 ‘접수 기록의 성공적인 커밋’으로 잡자.

더 안전한 사건 순서: 커밋 뒤 202

T1  인증/인가 및 요청 형식 확인
T2  적용 데이터셋의 정확한 버전과 조건을 고정해 job_id 생성
T3  DB BEGIN
T4  jobs에 (J-101, queued, dataset_version=V7, params=...) INSERT
T5  DB COMMIT 성공
T6  HTTP 202 Accepted
    Location: /jobs/J-101
    body: {"job_id":"J-101", "status":"queued"}
T7  WORKER가 J-101을 발견해 선점 (T6보다 앞설 수도 있다)

T5와 T6의 순서가 결정적인 이유는, 클라이언트가 응답을 확인한 뒤 조회할 근거가 DB에 남아 있기 때문이다. 단, COMMIT 뒤 서버가 죽어서 202 응답이 유실되면 DB에는 job이 있는데 클라이언트는 접수 여부를 모르는 반대 상황이 발생한다. 재전송을 무조건 새 작업으로 처리하면 중복 접수가 일어난다. 클라이언트가 생성한 요청 식별자(idempotency key)를 유일 제약조건으로 묶거나, 기존 job을 검색해 동일한 접수 사실을 돌려주는 방식이 필요하다. 이 수업에서는 중복의 핵심만 설명하며 멱등성의 일반 설계는 별도 주제에서 깊이 다룬다.

job_id는 계산 결과의 ID와 다르다

job_id는 한 번의 작업 시도/요청을 추적하는 식별자다. plan_id는 검증을 통과해 확정된 운영 계획의 식별자일 수 있다. J-101이 실패했다면 plan_id는 없어야 한다. 새로운 조건으로 재계산한 J-102가 같은 노선 모양을 만들더라도 별개의 작업 이력일 수 있다.

데이터셋 이름만 저장하면 부족하다

운영자가 dataset=default로 접수한 뒤 다른 데이터셋을 적용할 수 있다. WORKER가 나중에 ‘현재 default’를 읽으면 접수 때와 다른 입력으로 계산한다. 그러므로 job에는 변경되지 않는 dataset version 또는 스냅샷 참조, 요청 조건, 알고리즘 버전(재현이 필요하다면), 생성 시각을 보관한다. 입력을 원본에서 다시 읽더라도 특정 버전을 지목해야 한다. ‘데이터가 DB에 있다’와 ‘어떤 버전이 계산에 사용됐는지 추적된다’는 다른 보장이다.

시험 근거와 설계의 구분: 과제 원문은 준비된 CSV 7종을 선택·검증·적용하고, 데이터/생성 결과를 DB에 저장해 재시작 후에도 유지하며, 변경 데이터를 반영해 재계산하라고 요구한다. POST /jobs, 202, job_id, 버전 컬럼은 이를 구현하는 가능한 설계이지 원문의 강제 API 명세는 아니다.

10:00:03                                    UPDATE J-101 SET running
10:00:04   노선 계산 시작                    노선 계산 시작

두 WORKER 모두 조회 당시에는 queued를 보았다. 먼저 읽었다는 사실은 처리 권한을 독점했다는 뜻이 아니다. 선점은 ‘내가 이 상태를 바꿀 자격이 아직 남아 있는가’를 DB가 한 순간에 판정하도록 해야 한다. 이를 원자적 선점(atomic claim)이라고 한다.

SQLite 단일 서버의 한 가지 선점 방법

-- 가상 예시: SQLite 3.35+의 RETURNING을 가정한다.
-- 연결별 busy_timeout 설정, 예외 처리, 스키마·인덱스는 별도 필요.
BEGIN IMMEDIATE;

UPDATE jobs
SET status       = 'running',
    owner_id     = :worker_id,
    attempt      = attempt + 1,
    claim_token  = claim_token + 1,
    lease_until  = :lease_deadline,
    started_at   = COALESCE(started_at, :now)
WHERE job_id = (
    SELECT job_id
    FROM jobs
    WHERE status = 'queued'
       OR (status = 'running' AND lease_until < :now)
    ORDER BY created_at, job_id
    LIMIT 1
)
AND (
    status = 'queued'
    OR (status = 'running' AND lease_until < :now)
)
RETURNING job_id, owner_id, attempt, claim_token,
          dataset_version, params_json;

COMMIT;

읽기와 상태 변경의 경쟁을 하나의 쓰기 트랜잭션으로 묶는다. BEGIN IMMEDIATE는 SQLite에서 쓰기 트랜잭션을 시작하면서 쓰기 예약을 확보하므로, 같은 DB 파일에 접근하는 다른 쓰기 트랜잭션이 동시에 선점 변경을 커밋할 수 없다. 둘째 WORKER는 잠깐 기다리거나 SQLITE_BUSY를 만나고, 다시 시도하면 이미 바뀐 상태를 본다. RETURNING에서 행이 없으면 선점 성공으로 간주하지 않는다. 데이터베이스의 실제 잠금과 격리, 예외 처리에 의존하므로 단순한 SELECT 후 무조건 UPDATE 두 문장과 같지 않다.

SQLite에서는 일반적으로 한 번에 한 writer만 진행한다. 따라서 오래 걸리는 계산 동안 트랜잭션을 열어 놓으면 다른 접수·상태 갱신도 막힐 수 있다. 올바른 실행은 짧은 트랜잭션으로 선점 → 커밋 → 트랜잭션 밖에서 계산 → 짧은 트랜잭션으로 확정이다.

[짧게 DB 잠금]            [긴 시간 계산, DB write lock 없음]      [짧게 DB 잠금]
 BEGIN → claim → COMMIT ──▶ route algorithm ──▶ validate ────────▶ finalize → COMMIT

왜 claim_token이 필요한가

owner_id=W-A만 기록하면 A가 뒤늦게 돌아와 여전히 ‘내 작업’이라고 착각할 수 있다. 새 WORKER가 선점할 때 claim_token을 증가시키면, 지금 권한을 가진 실행 세대(generation)를 구분할 수 있다. 결과 확정 시 WHERE job_id=? AND owner_id=? AND claim_token=? AND status='running' AND lease_until >= :now AND cancel_requested_at IS NULL을 확인해야 한다. 이 조건만으로도 충분하지 않다. 최종 공개 포인터를 바꿀 때는 job이 참조한 입력 스냅샷의 dataset_version·params_json과 현재 활성 데이터셋·생성 요청 세대(generation_revision)가 일치하는지도 같은 확정 트랜잭션 안에서 검사한다. 이미 다른 데이터셋이나 조건으로 새 생성 요청이 접수됐다면 이전 job은 성공 기록으로 보관할 수 있어도 현재 계획을 덮어써서는 안 된다. 임대 기한이 지났다면 아직 다른 WORKER가 재선점하지 않았더라도 확정은 거절한다. 임대가 권한인 이상 만료 이후의 이전 token은 최신으로 남아 있어도 유효하지 않다. 이 숫자를 fencing token이라고 부르는 설계도 있다. 다만 DB 최종 확정만 방어한다. 외부 파일을 덮거나 외부 API를 호출하는 부작용까지 저절로 차단하는 것은 아니다. 그런 자원도 토큰을 검사하거나 별도 안전 장치가 필요하다.

일의 단위와 병렬 계산은 다르다

WORKER A가 J-101, B가 J-102를 각각 선점하면 두 작업을 병렬로 수행할 수 있다. 하지만 SQLite 쓰기 작업은 직렬화될 수 있고, CPU 코어 한 개면 계산 자체도 경쟁한다. WORKER가 많을수록 좋은 것이 아니라 자원 한계와 DB 경합을 함께 본다.

하나의 작업에서 계산은 겹쳐도 유효한 최종 공개 권한은 겹치지 않게 만든다

⏳ 5. 살아 있는지 알 수 없을 때: 임대·heartbeat·죽음 감지

작업을 running으로 바꿨는데 WORKER가 전원 문제로 사라졌다고 하자. running을 영원히 잠가 두면 작업은 재개되지 않는다. 그렇다고 ‘5초 동안 응답 없음 = 죽음’이라고 확정하면, 단지 계산이 늦거나 네트워크가 지연된 살아 있는 WORKER를 중복 실행시킬 수 있다. 분산 시스템에서 침묵만 보고 죽음을 확실하게 증명하기 어렵다.

이를 위해 임대(lease)를 사용한다. 임대는 ‘지금부터 언제까지 이 작업을 처리할 권리를 가진 것으로 간주한다’는 만료 가능한 권한이다. lease_until과 claim_token은 DB에 저장한다. WORKER가 주기적으로 heartbeat를 갱신해 기한을 연장한다.

시간(예시; UTC 기준으로 통일했다고 가정)
10:00:00  A: J-101 선점, token=5, lease_until=10:00:30
10:00:10  A: heartbeat 성공 → lease_until=10:00:40
10:00:20  A: CPU 계산 중 일시 정지/네트워크 지연
10:00:41  B: DB에서 lease 만료 발견 → J-101 재선점, token=6
10:00:42  B: 계산 시작
10:00:45  A: 다시 진행. 실제로 죽은 것이 아님!
10:00:46  A: token=5로 확정 시도 → 조건부 UPDATE 0행 → 확정 거절
10:00:48  B: token=6으로 검증 후 정상 확정 가능

이 시간선은 ‘임대 만료 = 이전 WORKER가 죽었다’를 의미하지 않는다는 반례다. 임대는 소유권 회수를 위한 운영 규칙이지, 물리적 사망 판정이 아니야. 그래서 임대와 token 검증이 함께 필요하다.

heartbeat에도 경쟁 조건이 있다

heartbeat는 다음 조건처럼 현재 소유자와 토큰이 일치하고 만료 전에만 연장하는 편이 안전하다.

UPDATE jobs
SET lease_until = :new_deadline,
    heartbeat_at = :now
WHERE job_id = :job_id
  AND owner_id = :worker_id
  AND claim_token = :claim_token
  AND status = 'running'  -- 검증 중에도 DB 상태는 running
  AND cancel_requested_at IS NULL
  AND lease_until >= :now;

갱신된 행이 0개라면 WORKER는 권한을 더 이상 갖지 못한 것으로 간주하고 최종 확정을 멈춰야 한다. 시계 기준을 섞으면 오판하기 쉬우므로, 예시 설계에서는 DB 측 시각을 한 기준으로 사용하거나 시스템 간 시계를 엄격하게 관리한다. 임대 길이가 너무 짧으면 느린 계산을 중복 실행한다. 너무 길면 진짜 죽은 WORKER의 복구가 늦어진다. heartbeat를 별도 스레드로 보내더라도 프로세스 정지·DB 장애·네트워크 분할이 발생할 수 있다.

세 가지 실패를 구별해 보자

사건 관찰되는 현상 지금 말할 수 있는 것 아직 단정할 수 없는 것
WORKER 프로세스 종료 heartbeat 중단, 임대 만료 새 선점 후보가 됨 이전 계산이 어디까지 실행됐는지
긴 계산/일시 정지 heartbeat 지연, 나중에 복귀 기존 임대가 유효하지 않을 수 있음 이전 WORKER가 영원히 종료됐는지
DB 연결 단절 heartbeat/확정 실패 DB에서 현재 권한 확인 필요 계산 메모리 상태의 정확성

중요한 결론은 실패 감지와 실패 복구가 같은 것이 아니다. 만료된 작업을 다시 조회·선점할 로직, 재시도 상한, 비정상 반복 작업 격리, 결과 확정의 토큰 검증이 함께 있어야 복구 절차가 닫힌다.

🏗️ 6. 계산 중 결과와 사용자에게 보이는 확정 결과를 분리하기

시험의 통근버스 노선은 예쁜 경로 하나만 생성해서는 끝나지 않는다. 과제 원문의 기준으로 예를 들면, 근무자 전원에 대해 각 근무일 출근·퇴근 배정이 정확히 하나씩 있어야 하고, 차량 정원을 넘으면 안 되며, 출근 도착은 적용 도착 여유 이상 빨라야 하고, 퇴근 출발은 근무 종료 10분 후 이후여야 한다. 인접 정류장 간 소요 시간은 travel_times.csv의 방향별 값을 만족해야 한다. 검증 결과는 적용 데이터셋 버전과 적용 조건에 매여 있다.

계산 중 일부 노선이 생성됐다고 곧바로 최종 plans에 덮어쓰면 어떤 일이 생길까? 20개 근무일 중 12일째에 WORKER가 죽었을 때 구성원은 부분적으로 완성된 계획을 정상 결과인 줄 볼 수 있다. 따라서 결과 상태의 소유권을 나누자.

jobs (업무 상태)
 J-101: queued → running [계산 → 검증(progress phase)] → succeeded / failed
                           │
                           ▼
job_attempts / temp_results (임시, 작업 시도에 귀속)
 J-101 / token=5 : 생성 중인 계산 산출물, 정상 공개 금지
                           │
                 [독립 Validator가 전체 검사]
                           │ PASS
                           ▼
plans + plan_routes + plan_assignments (확정, 사용자가 읽을 자료)
  └── active_plan_pointer를 검증된 계획으로 교체

이 설계에서 validating은 DB에 영속 저장하는 jobs.status가 아니라 running 동안의 검증 진행 단계(progress phase)다. 화면이나 로그에서는 ‘검증 중’으로 표현할 수 있지만, 영속 작업 상태는 계속 running이며 임대 갱신·재선점·재시작 복구 대상에도 동일하게 포함된다. 검증 단계에서 WORKER가 종료되어도 lease 만료 후 다시 선점할 수 있다. 상태 이름보다 중요한 것은 다음 불변식이다.

유효한 결과로 공개되는 것은 한 번의 검증을 모두 통과한 확정 계획뿐이며, 이전 유효 계획은 새 작업이 완료되기 전까지 보존된다.

Creator(업무 계획 생성기)가 계산한 임시 결과를 Validator(업무 규칙 검증기)가 독립적으로 검사한다는 뜻이다. 원문 복기에는 Creator/Validator라는 단어가 있었지만 그것이 이 업무 컴포넌트인지 AI 작성·검토 역할인지 확정되지 않았다. 여기에서는 업무 생성기/검증기라는 가상 설계를 채택한다. Validator가 Creator와 같은 버그를 공유하지 않도록 구현 경로, 검사 기준, 경계 사례를 분리하는 것이 중요하다.

최종 확정은 다시 짧은 DB 트랜잭션으로

T1  A의 claim_token=5 확인
T2  A가 임시 결과 생성 완료, Validator PASS
T3  DB BEGIN IMMEDIATE
T4  jobs: J-101이 여전히 owner=A, token=5, status=running이고
    lease_until >= DB 기준 현재 시각이며 취소 요청이 없는지 확인
T5  plans와 관계 데이터의 확정 기록을 삽입/연결
T6  job의 dataset_version·params_json·generation_revision을 현재 활성
    데이터셋·계산 조건·최신 생성 요청 세대와 비교해 일치할 때만
    active_plan_pointer를 갱신(경쟁 갱신은 조건부 갱신으로 차단)
T7  jobs: succeeded, result_plan_id=... 로 변경
T8  COMMIT
T9  브라우저 조회 시 새 계획 표시

T4~T7은 가능한 한 하나의 DB 트랜잭션이어야 한다. T4의 lease 유효성은 재선점 여부와 무관하게 검사한다. 만료 시각이 지났다면 아직 재선점자가 없어도 현재 시도는 공개할 수 없고, 다음 WORKER가 새 토큰으로 선점해 다시 수행해야 한다. 취소는 cancel_requested_at IS NULL인 경우만 확정을 허용하는 정책을 가정한다. 입력 비교의 범위는 접수 때 고정한 입력 스냅샷·계산 파라미터·생성 요청 세대와 현재 공개 대상의 활성 데이터셋·조건·최신 세대다. 이전 버전의 작업을 기록상 완료 처리하는 정책은 별도일 수 있지만, 오래된 결과를 현재 활성 계획으로 게시하는 것은 거절한다. 이 예시에서는 그런 작업을 failed와 STALE_INPUT 사유로 종결하고 포인터는 그대로 두는 정책을 택한다. 이런 확인과 포인터 갱신을 트랜잭션 밖에서 따로 수행하면 그 사이 데이터셋 적용·새 요청·취소가 끼어들 수 있다. 만약 결과를 먼저 커밋하고 job 상태 변경 전에 죽으면 ‘결과는 있는데 job은 running’ 상태가 된다. 별도의 복구 설계를 하지 않는 한 사용자는 무엇이 끝났는지 판단하기 어렵다. 반대로 job을 succeeded로 먼저 커밋하고 실제 결과 저장이 실패하면 ‘완료라고 하는데 결과가 없다’. 확정 데이터와 완료 상태가 일치하도록 원자적 커밋하는 이유다.

주의: 데이터가 너무 커서 모든 최종 행을 한 트랜잭션에 삽입하기 어렵다면, plan_id에 staging 표시를 두고 앞서 일부를 적재한 뒤 마지막 짧은 트랜잭션에서 validated/published로 바꾸는 방식도 가능하다. 그 경우 조회 경로가 staging을 절대로 정상 계획으로 노출하지 않는다는 조건이 추가된다. 외부 파일 내보내기나 외부 API는 SQLite 트랜잭션 하나로 함께 롤백할 수 없으므로 별도 원자성 전략이 필요하다.

검증 성공, 확정 트랜잭션 전 종료 재시도·복구 대상 유효 후보는 있을 수 있음 기존 계획 그대로
확정 COMMIT 후 응답 유실 succeeded 정리 가능 새 계획 공개됨, job 조회로 확인

‘기존 계획 그대로’는 새 작업 실패가 기존 정상 계획을 교체하지 않도록 설계한 경우의 보장이다. 원문은 검증 실패 데이터셋 적용 시 기존 데이터/생성 결과 유지와, 새 데이터 적용 후 재계산 전에는 기존 결과를 새 데이터 결과로 보이지 않게 하도록 요구한다. 구현은 활성 데이터 버전과 결과 버전을 검사하여 구분해야 한다. 즉, 이전 계획을 DB에 보존할 수 있어도 현재 활성 데이터셋에 맞는 최신 계획이라고 표시하면 안 된다.

✉️ 7. 브로커를 붙이면 새로 생기는 문제: 두 종류의 ‘확인’

단일 서버와 SQLite만으로 jobs 테이블을 폴링하는 구조에서는 브로커 메시지 자체가 없다. 따라서 publisher confirm과 consumer ack는 그 구조의 필수 절차가 아니다. 대신 SQLite의 COMMIT, claim, 결과 확정이 접수·실행 권한을 관리한다. 외부 브로커를 추가했을 때만 메시지 전달 확인의 의미를 별도로 배워야 한다.

producer (웹/API) ── publish ──▶ broker ── deliver ──▶ consumer (WORKER)
                     ◀── confirm ──          ── ack ──▶
                     ↑                      ↑
             publisher confirm        consumer acknowledgement
             브로커가 publish를        소비자가 처리 완료를
             책임졌다는 방향의 확인    브로커에 알리는 방향의 확인

publisher confirm은 브로커가 발행 메시지에 대해 책임을 인수했다는 확인이다. consumer ack는 소비자 측이 메시지 처리의 성공 기준을 충족했다고 브로커에 알리는 확인이다. 서로 다른 전달 구간에 존재하며, 어느 하나도 업무 DB에 검증된 최종 노선이 저장됐다는 사실을 단독 보증하지 않는다. RabbitMQ 문서 역시 이 둘이 독립적인 메커니즘임을 설명한다. 출처: RabbitMQ: Consumer Acknowledgements and Publisher Confirms.

실패 사례 A: DB에는 job이 있지만 브로커에는 메시지가 없다

T1  Web: DB jobs에 J-101 INSERT + COMMIT
T2  Web: broker.publish(J-101) 직전 프로세스 종료
T3  broker: J-101 메시지 없음
T4  WORKER: 대기만 하고 job은 영원히 queued

이는 두 시스템(DB와 브로커) 중 하나에만 기록이 남는 dual-write 문제다. DB COMMIT와 브로커 publish는 보통 같은 원자적 트랜잭션에 속하지 않는다. 발행 순서를 반대로 바꾸면 ‘브로커에는 메시지가 있는데 DB에는 job이 없음’이라는 대칭적인 문제가 생긴다.

이를 줄이는 대표적인 방법은 transactional outbox다.

              [하나의 DB 트랜잭션]
WEB ──▶ INSERT jobs(J-101) + INSERT outbox(event=JobReady,J-101)
                              COMMIT
                                 │
                  relay가 미발행 outbox 탐색
                                 │
                       broker publish + confirm
                                 │
                     outbox sent 표시/재시도

접수와 ‘발행해야 할 사실’이 함께 커밋되므로 접수됐는데 발행 예정 기록이 없는 틈을 막는다. 하지만 relay가 publish 성공 후 confirm 수신 전에 죽으면 같은 이벤트를 다시 발행할 수 있다. 따라서 outbox는 ‘중복 없이 정확히 한 번 전송’을 보장하는 기술이 아니다. 소비자는 같은 job_id에 대한 중복 메시지를 받아도 DB에서 선점에 성공한 실행만 진행해야 한다.

또 하나, 브로커가 publish를 confirm했다고 해서 반드시 WORKER가 실제 업무를 끝낸 것은 아니다. 브로커의 라우팅, 큐 내구성, 메시지 지속성, 클러스터 설정까지 확인해야 하며, 잘못된 라우팅은 confirm 하나로 해결되지 않는다. 제품별 의미는 공식 문서를 보아야 한다.

실패 사례 B: ACK를 너무 일찍 보내면 일을 잃는다

T1  broker → W-A: J-101 전달
T2  W-A → broker: ack (즉시)
T3  broker: 해당 전달 처리 완료로 기록/삭제 가능
T4  W-A: 계산 시작 전 종료
T5  broker: 재전달 근거가 사라짐

ack는 ‘메시지 받았습니다’가 아니라 설계에 따라 업무 처리를 맡아 안전한 상태로 만들었습니다라는 책임 선언으로 잡는 편이 안전하다. DB 기반 job이 별도로 살아 있고 복구 스캐너가 있다면 job을 통해 재시도할 수도 있지만, 브로커만 믿었다면 손실이다.

실패 사례 C: DB 확정 뒤 ACK가 유실되면 같은 메시지가 돌아온다

T1  broker → W-A: J-101 전달 (미확인)
T2  W-A: 계산 + 검증
T3  W-A: DB에 plan 확정 및 job succeeded COMMIT
T4  W-A: broker로 ack 전송 시도
T5  네트워크 단절: broker는 ack를 수신하지 못함
T6  broker: 연결 단절 감지 후 J-101 재전달
T7  W-B: J-101 수신, DB 조회 → 이미 succeeded → 재실행 없이 ack

T3의 데이터 확정은 성공했지만 T5의 메시지 제거는 실패했다. DB 커밋과 브로커 ACK는 원자적으로 묶여 있지 않다. 여기서 ‘적어도 한 번(at-least-once) 전달’은 메시지가 한 번 이상 도착할 수 있다는 의미이며, ‘업무 효과가 정확히 한 번’이라는 뜻은 아니다. RabbitMQ의 미확인 전달은 연결 종료 시 재대기할 수 있으며, SQS에서도 visibility timeout으로 메시지가 다시 나타날 수 있다. 제품별 정책과 내구성 조건 아래 이해해야 한다. 출처: RabbitMQ Reliability Guide, AWS SQS Visibility Timeout.

‘커밋 전 ACK’, ‘커밋 후 ACK’의 선택 손실

순서 종료가 끼어들면 얻는 것 잃는 것/필요한 보완
ACK → 결과 COMMIT ACK 후 종료 시 결과 누락 중복 전달 감소 작업 손실 위험, 별도 복구 장치 필요
결과 COMMIT → ACK COMMIT 후 종료 시 중복 전달 완료 결과 보존 우선 중복을 식별·무해화해야 함

따라서 신뢰성이 중요한 업무에서는 대개 결과를 안전하게 확정한 뒤 ACK하고, 반복 전달을 견디도록 설계한다. succeeded이면 아무것도 하지 않는 것만으로 충분한지는 결과 외부 발송, 이메일, 파일 쓰기 같은 부작용이 있는지에 달려 있다. ‘정확히 한 번 실행’과 ‘최종 확정 상태가 하나’는 다르다. 전자는 재시도 시스템에서 쉽게 보장할 수 없지만, 후자는 DB 제약과 조건부 확정으로 접근 가능하다.

🚦 8. 줄이 길어질 때: 백프레셔·동시 실행 수·대기 시간

WORKER가 아무리 안전하게 일을 재시도해도 요청 유입이 처리 능력을 넘으면 대기열은 계속 길어진다. 이를 이해하려면 계산식보다 일이 들어오는 속도와 나가는 속도를 먼저 보자.

요청 유입: 평균 분당 12개
          ┌──────────────────┐
12 jobs/min ──▶ [ Q Q Q Q Q Q ... ] ──▶ WORKER 2개 × 4 jobs/min = 8 jobs/min
          └──────────────────┘
                         ▲
               매분 평균 4개씩 밀림

이 수치는 설명용 가상 수치다. 유입 λ=12 jobs/min, 처리 μ=8 jobs/min이면, 단순한 평균 모형에서 대기 작업 수는 매분 약 4개씩 증가한다. 더 많은 WORKER를 만든다고 무조건 해결되지 않는다. CPU가 포화되거나 SQLite 쓰기 잠금으로 처리 시간이 늘어나면 WORKER당 처리량이 하락할 수 있다.

백프레셔(backpressure)는 ‘입력을 늦추거나 거절하라’는 신호

  • 동시 실행 제한: 예를 들어 노선 생성은 한 번에 2개까지만 실행한다. CPU와 DB를 보호하지만 대기 시간은 늘어난다.
  • 대기열 길이 제한: 대기 작업이 일정 개수를 넘으면 신규 접수를 거절하거나, Retry-After 같은 신호와 함께 나중에 재시도하도록 안내한다. 429/503 중 선택은 API 정책에 따른다.
  • 중복 요청 합치기: 동일한 데이터 버전·조건으로 진행 중인 작업이 있다면 기존 job을 돌려줄 수 있다. 단, 재계산 의도와 권한 범위를 명확히 확인해야 한다.
  • 우선순위·예약: 긴 작업이 짧은 작업을 전부 막지 않게 작업 종류를 나눌 수 있다. 대신 어떤 사용자는 더 오래 기다릴 수 있다.
  • 소비 속도 조절: 브로커의 prefetch나 WORKER의 semaphore로 한 번에 점유하는 작업 수를 제한한다. 점유 수를 늘릴수록 메모리·부하가 커질 수 있다.

무엇을 측정해야 병목을 찾을 수 있을까?

시간선: created_at → claimed_at → computation_done_at → committed_at
queue_wait:     created_at ──▶ claimed_at
execution_time:             claimed_at ──▶ committed_at
end_to_end:    created_at ─────────────────▶ committed_at

정확한 구간 정의:
queue_wait      = claimed_at - created_at
execution_time  = committed_at - claimed_at
end_to_end      = committed_at - created_at

queue_wait가 길고 실행 시간이 일정하다면 대기열·WORKER 수·우선순위가 문제일 가능성이 있다. execution_time이 점점 길어지면 알고리즘, CPU, DB 경합, 입력 규모, 외부 자원 등을 조사해야 한다. 성공 건만 평균을 내면 만료·실패한 장기 작업이 통계에서 사라진다. 그러므로 대기 중 작업 수, 가장 오래된 대기 작업의 나이, 실행 중 수, 만료된 lease 수, 재시도 횟수, 실패율, 성공/실패 각각의 지연 분포를 함께 본다. 평균뿐 아니라 p50/p95/p99 같은 분위수도 유용하다.

참고로 안정적인 정상 상태에서 평균 작업 수 L, 도착률 λ, 평균 체류 시간 W에는 Little의 법칙 L = λW가 적용된다. 이것은 안정적 장기 평균과 측정 범위가 맞을 때의 관계다. 유입이 처리량보다 계속 많아 큐가 무한히 커지는 상황에서는 안정 상태로 간주하여 목표 대기 시간을 역산하면 안 된다.

백프레셔의 손실도 설명해야 한다

동시 실행을 1개로 제한하면 DB 경합은 줄지만 대기 시간이 커진다. 10개로 늘리면 병렬성이 좋아질 가능성은 있지만 메모리와 CPU가 포화되고 각 작업이 더 느려질 수 있다. 신규 접수를 거부하면 시스템은 보호되지만 사용자에게 작업이 보장되지 않는다. 안전성·지연·처리량은 한 번에 모두 최대화할 수 없다.

🛠️ 9. 단일 서버·SQLite에서 출발하는 최소한의 실행 설계

이번에는 개념을 작동 가능한 설계 흐름으로 연결하자. 단, 아래는 검증하지 않은 개념 예제다. 웹 프레임워크, 인증, 예외 처리, 실제 CSV 파싱, Validator, 마이그레이션, 작업 재기동, 파일 권한 등은 생략되어 있으며 제출 가능한 완성 코드가 아니다.

스키마의 의도부터

-- 교육용 구조 발췌. 실제 운영에서는 CHECK, FK, 인덱스,
-- 실패 메시지 길이, retention, migration 등을 추가해야 한다.
CREATE TABLE jobs (
    job_id           TEXT PRIMARY KEY,
    request_key      TEXT UNIQUE,
    status           TEXT NOT NULL CHECK (
        status IN ('queued','running','succeeded','failed')
    ),
    dataset_version  TEXT NOT NULL,
    params_json      TEXT NOT NULL,
    generation_revision INTEGER NOT NULL, -- 공개 대상의 요청 세대
    cancel_requested_at TEXT,            -- 취소 요청을 지원하는 경우의 가드
    created_at       TEXT NOT NULL,
    started_at       TEXT,
    owner_id         TEXT,
    attempt          INTEGER NOT NULL DEFAULT 0,
    claim_token      INTEGER NOT NULL DEFAULT 0,
    lease_until      TEXT,
    heartbeat_at     TEXT,
    result_plan_id   TEXT,
    error_code       TEXT
);

CREATE INDEX idx_jobs_claim ON jobs(status, created_at, lease_until);

-- 확정 계획의 공개 여부를 따로 나타내는 개념 구조
CREATE TABLE plans (
    plan_id          TEXT PRIMARY KEY,
    source_job_id    TEXT NOT NULL UNIQUE REFERENCES jobs(job_id),
    dataset_version  TEXT NOT NULL,
    params_json      TEXT NOT NULL,
    visibility       TEXT NOT NULL CHECK (visibility IN ('staging','published'))
);

validating은 별도 저장 상태가 아니므로 스키마의 상태 목록에 없다. generation_revision은 새 생성 요청이나 활성 조건 변경 시 증가하는 현재 공개 대상 세대와 대조하는 값이며, 그 세대를 관리하는 별도 활성 설정 레코드와 조건부 갱신은 이 발췌 스키마에서 생략했다. cancel_requested_at은 선택적 취소 요청을 받는 경우의 가드이고, 취소 API 자체는 이 예제에 구현되어 있지 않다. request_key UNIQUE는 동일 클라이언트 요청의 재접수 문제를 다루는 한 장치다. claim_token은 이전 WORKER가 늦게 확정하는 문제를 방어한다. source_job_id UNIQUE는 한 job에서 여러 최종 계획 레코드가 생기는 문제를 제한한다. 세 장치가 서로 다른 중복 문제를 막는다는 사실이 중요하다.

WORKER의 흐름을 의사코드로

# 교육용 의사코드: 실제로 실행·검증되지 않았음.
# DB 트랜잭션과 시간 기준은 각 함수 안에서 별도 구현한다고 가정.

def worker_loop(worker_id):
    while service_is_running():
        claim = atomic_claim_one_job(worker_id)
        if claim is None:
            sleep_with_jitter()
            continue

        job_id = claim.job_id
        token = claim.claim_token
        try:
            # 데이터 버전과 조건은 접수 당시 고정된 스냅샷을 사용한다.
            inputs = load_immutable_input(claim.dataset_version)
            candidate = create_routes(inputs, claim.params)

            # heartbeat 갱신에 실패하면 이 실행은 확정 권한을 잃는다.
            assert_still_owner(job_id, worker_id, token)
            validation = validate_all_rules(candidate, inputs, claim.params)
            if not validation.ok:
                conditional_mark_failed(job_id, worker_id, token,
                                        validation.errors)
                continue

            # 핵심: 권한 확인, 확정 데이터, succeeded 상태를 한 트랜잭션으로.
            committed = conditional_publish_plan_and_finish(
                job_id=job_id,
                worker_id=worker_id,
                token=token,
                candidate=candidate,
                validation=validation,
            )
            if not committed:
                # 예전 실행이 선점을 잃었을 수 있으므로 결과 공개 금지.
                discard_unpublished_candidate(candidate)
        except TransientFailure:
            # 단순 재시도 가능 판단은 오류 유형과 시도 상한 정책에 따름.
            record_if_still_owner_and_schedule_retry(job_id, worker_id, token)
        except Exception as exc:
            # 실제 구현에서는 예외 범주·보안·오류 노출 정책을 구분.
            conditional_mark_failed(job_id, worker_id, token,
                                    safe_error_summary(exc))

이 의사코드에서 assert_still_owner는 편의를 위한 중간 검사일 뿐 최종 안전장치가 아니다. 검증 중에도 jobs.status는 running으로 유지되어 heartbeat와 lease 만료 복구가 동일하게 적용된다. 검사 직후 임대가 만료될 수 있으니 마지막 확정 트랜잭션에서도 owner·token·running 상태·유효 lease·취소 요청 부재를 다시 검증해야 한다. conditional_publish_plan_and_finish는 같은 트랜잭션 안에서 현재 활성 데이터셋·계산 조건·generation_revision과 job의 스냅샷이 일치하는지도 확인한 후에만 공개 포인터를 바꾼다. 임대 만료 시각만 지났고 새 WORKER가 선점하지 않은 경우에도 이 호출은 확정을 거절한다. 또한 장기 계산 중 heartbeat를 어떻게 지속할지, 얼마나 재시도할지, 프로세스를 누가 재시작할지는 이 코드를 감싼 실행 환경의 책임이다.

실제 구현 시 나눠서 검증할 불변식

  1. 접수: 202를 반환한 작업은 같은 DB 저장소에서 GET /jobs/{id}로 조회 가능해야 한다.
  2. 선점: 두 WORKER가 경쟁해도 같은 job에서 동일 시점에 유효한 claim token은 하나다. 임대 만료 후 중복 계산이 존재할 수 있다는 것은 별개다.
  3. 권한: 현재 claim token을 잃었거나 lease가 만료된 실행은 (재선점 전이어도) job/최종 결과를 확정하지 못한다. 취소 요청이 있거나 현재 공개 대상의 데이터셋·계산 조건·요청 세대가 달라도 활성 계획을 교체하지 못한다.
  4. 공개: 검증에 실패했거나 확정되지 않은 후보 결과가 정상 계획 조회·JSON 내보내기에 나타나지 않는다.
  5. 상태: succeeded라면 그 job이 참조하는 확정 plan이 존재하며 필요한 데이터/조건 버전이 맞는다.
  6. 복구: 재시작 후 queued 및 만료된 running을 스캔해 재시도하거나 제한 사유와 함께 실패 처리한다. 검증 도중에도 DB 상태는 running이므로 같은 스캔 경로로 복구된다. 자동 복구는 이 로직과 재기동 설정을 실장한 후에만 주장할 수 있다.
  7. 자원: 최대 동시 작업 수와 큐 적체를 측정할 수 있다.

🌐 10. 프로세스를 분리하고 서버가 여러 대가 되면 무엇이 달라지나

설계에 ‘WORKER’가 등장하는 것과 별도 프로세스로 실행되는 것은 다른 결정이다. 각각의 단계를 구분하자.

구성 요청 실패·메모리 작업의 영속 저장 동시 선점 운영 비용/한계
한 웹 프로세스 + 메모리 큐 웹 프로세스 종료 시 큐/WORKER 함께 위험 기본 없음 같은 프로세스 안에서도 조정 필요 가장 간단하지만 복구 근거 부족
한 웹 프로세스 + SQLite jobs + 내부 WORKER 웹 서버 재시작 시 실행 중 계산 소실 DB 파일 유지 시 job 보존 DB 조건부 변경 가능 재기동 및 임대 복구 로직 필요
웹 프로세스와 WORKER 프로세스 분리 + SQLite 웹만 죽어도 WORKER 계속 계산 가능 DB 파일이 공통·지속일 때 보존 SQLite 쓰기 직렬화 이용 프로세스 관리·DB 잠금·파일 접근 관리
여러 서버 + 공유 DB/브로커 한 서버 장애에 대한 가용성 확장 가능 공유 저장소의 구성에 의존 모든 WORKER가 같은 권위 저장소에서 claim해야 함 네트워크 장애·중복·분산 운영 복잡도 상승

특히 서버 A의 로컬 SQLite 파일과 서버 B의 로컬 SQLite 파일은 같은 DB가 아니다. 각자 J-101을 선점했다고 믿어도 서로의 상태를 보지 못한다. SQLite 파일을 네트워크 파일시스템으로 공유하는 것은 잠금·일관성·운영 제약 때문에 무비판적으로 권장할 수 없다. 여러 서버에서 공동 선점이 중요하면 일반적으로 네트워크 DBMS나 신뢰할 수 있는 브로커, 공유 영속 저장소를 검토한다. 그 선택에도 장애·중복 대응은 남는다.

여러 서버를 구성해도 ‘브로커가 있으니 정확히 한 번만 실행된다’고 할 수 없다. 네트워크는 성공 메시지가 돌아오는 순간 끊길 수 있고, 임대가 만료되면 기존 WORKER와 새 WORKER가 잠시 동시에 계산할 수 있다. 운영자가 정말 설명해야 할 보장은 결과 확정의 단일성, 상태의 내구성, 중복 처리에 대한 안전성, 실패 후 복구 경로다.

단일 서버에선 무엇을 우선할까?

시험 과제의 ‘기술 스택 자유’, ‘3시간’, ‘DB 재시작 후 유지’, ‘배포 고려’ 조건을 감안할 때, SQLite jobs 테이블 + 별도 WORKER 프로세스 또는 명확한 복구 가능한 백그라운드 실행기는 학습용 기준안으로 설명하기 좋다. 하지만 시험에 강제된 구조는 아니며 간단한 동기 처리도 요구된 기능과 시간/응답 한계를 충족한다면 가능하다. 설계 선택을 방어할 때는 ‘큐를 썼다’가 아니라 왜 HTTP 응답과 긴 계산을 분리했는지, 접수 사실을 어디에 남겼는지, 장애 시 무엇을 다시 시작하는지를 근거로 말해야 한다.

⚖️ 12. 같은 요구를 만족하는 설계 두 개: 무엇을 포기하는가

선택 A — SQLite job polling: WEB은 접수 정보를 커밋하고, WORKER는 주기적으로 작업을 찾아 조건부 선점한다. 코드 경로와 저장소가 적어 이해·검증하기 쉽다. 반면 polling 주기만큼 접수 후 시작이 지연되고, SQLite의 동시 쓰기 한계와 프로세스 재기동 문제가 있다. 장애 복구를 위해 lease, 상태 전이, 재시도 스캐너가 여전히 필요하다.

선택 B — SQLite job + broker/outbox: WEB은 DB와 outbox를 함께 기록하고, relay가 브로커로 발행하며, WORKER가 메시지를 받아 claim한다. 대기 전달과 WORKER 확장, backpressure 제어의 선택지가 많아진다. 대신 outbox relay, publisher confirm, consumer ack, 브로커 설정, DB↔메시지 중복 처리 등 실패 경계가 늘어난다. 추가된 인프라가 복잡성을 없애지 않고 다른 종류로 옮긴다.

선택 기준은 ‘마이크로서비스가 좋아 보인다’가 아니라 다음 질문이다. 접수량은 어느 정도인가? 계산은 얼마나 오래 걸리고 CPU를 얼마나 쓰나? 사용자가 대기할 수 있는 시간은? 서버 재시작 후 작업 손실을 허용할 수 있나? 여러 서버에서 같은 job을 잡을 가능성이 있는가? 운영자가 브로커까지 관찰·복구할 역량이 있는가? 시험에서는 이 질문을 주어진 시간과 필수 요구사항에 맞춰 좁혀야 한다.

이 강좌에서는 답안을 아직 채점하지 않는다. 답을 제출하면 먼저 어떤 보장을 말했는지 확인하고, 단정이 과한 부분을 반례로 점검할 수 있다. 본문의 가상 코드를 실제 실행했다고 가정하지 않는다.

🧷 14. 마지막 연결: 한 줄 상태 변화가 실제로 뜻하는 것

운영자의 요청을 받아 jobs에 queued를 커밋한다는 것은 ‘해야 할 일이 기록됐다’는 약속이다. WORKER가 원자적으로 running을 선점한다는 것은 ‘이번 실행에 임시 처리 권한이 있다’는 뜻이다. heartbeat로 lease를 연장한다는 것은 ‘그 권한이 아직 유효하다고 갱신했다’는 뜻이지 프로세스의 무조건적 생존 증명이 아니다. WORKER가 계산과 검증 뒤 토큰을 다시 확인해 결과와 성공 상태를 한 번에 커밋한다는 것은 ‘이 계획을 사용자에게 공개할 근거가 완성됐다’는 뜻이다. 브로커를 쓴 경우 마지막 ack는 ‘이 메시지를 다시 보낼 필요가 없다고 소비자가 알렸다’는 별도의 전달 관계다.

이 다섯 문장을 한 사건 순서로 붙이면, 웹 응답이 끊기고 WORKER가 죽고 메시지가 중복되어도 어떤 작업이 남아 있고 무엇을 다시 시도하며 어떤 결과를 보이면 안 되는지 설명할 수 있다. 실패를 없애는 설계가 아니라, 실패가 발생해도 잘못된 최종 결과를 확정하지 않도록 만드는 설계다.
