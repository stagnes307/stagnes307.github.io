🧭 0. 오늘 이해할 현상: 성공했는데 또 눌러야 한다면?

운영자가 웹 화면의 노선 생성 버튼을 누른다. 서버는 계산 작업을 받아 저장하고, WORKER가 근무자 배정과 시간표를 계산한다. 실제 시험의 서비스는 정류장을 고르고, 근무자를 배정하고, 노선·시간표를 만들며, 바뀐 데이터셋이나 운영 조건으로 재계산해야 한다. 검증 실패한 데이터셋은 적용하지 않고 기존 데이터와 생성 결과를 유지해야 하며, 적용 후 아직 재계산하지 않은 옛 결과를 새 데이터의 결과로 표시하면 안 된다. 이것이 이번 설계가 지켜야 할 업무상 불변 조건이다.

이제 웹 요청 하나가 아래처럼 흘렀다고 상상하자.

[운영자 브라우저]        [웹 서버]                  [SQLite]           [WORKER]
   생성 클릭 ──────────▶  작업 접수 ──────────────▶ job J41 저장
                          202 Accepted ◀──────────┘
   X 응답이 도중에 끊김
   '안 된 건가?' ─ 재시도 ─▶  ???

브라우저는 응답을 못 받았지만 서버는 이미 일을 접수했다. 브라우저의 입장에서 두 세계를 구분할 수 없다.

  • 세계 A: 요청이 서버에 도달하기 전에 사라졌다. 재시도가 필요하다.
  • 세계 B: 서버가 접수·커밋했지만 응답만 사라졌다. 같은 일을 새로 만들면 중복된다.

브라우저는 관측한 정보가 같으므로 둘 중 무엇이 사실인지 알 수 없다. 타임아웃은 실패의 증거가 아니라 결과를 모른다는 증거다. 이 불확실성이 재시도 설계의 출발점이야.

0-1. 하나의 요청에 여러 종류의 '한 번'이 있다

물음 '한 번'의 단위 잘못 섞으면 생기는 오류
사용자가 같은 의도로 버튼을 두 번 눌렀는가? 논리적 요청(intent) 같은 계획 생성 작업이 두 개 생김
WORKER가 계산 함수를 몇 번 실행했는가? 실행 시도(attempt) 재시도를 전부 막아 작업 복구 실패
DB가 성공 상태를 몇 번 기록했는가? 확정(commit) 옛 실행이 새 결과를 덮어씀
사용자에게 결과를 몇 번 알렸는가? 전달(delivery) 결과는 한 개여도 알림이 여러 번 감
구성원 화면에 어느 결과가 보이는가? 공개된 현재 버전(pointer) 데이터셋과 맞지 않는 계획을 보여 줌

핵심 구분: 재시도를 허용하면서도 “최종으로 인정되는 효과”만 한 번이 되게 할 수 있다. 멱등성은 계산이 한 번만 실행된다는 약속이 아니다. 재시도된 동일 논리적 요청의 외부 관찰 가능한 효과를 되풀이해 만들지 않는 약속이다. 이 약속의 대상, 범위, 기간을 명시해야만 의미가 있다.

0-2. 선수 개념을 짧게 다시 연결하자

트랜잭션은 DB에 변경 여러 개를 묶어 전부 커밋하거나 전부 롤백하도록 하는 경계다. 커밋 전에 다른 접속이 볼 수 없는 변경과 커밋 뒤 영속적으로 인정된 변경을 구분한다. 격리와 경쟁 갱신은 두 접속이 같은 값을 보거나 바꾸려 할 때의 규칙이다. SQLite는 같은 DB 파일에 대한 쓰기를 한 시점에 하나씩 직렬화한다. 하지만 쓰기 직렬화가 업무 규칙 자체를 보장하지는 않는다. UPDATE ... WHERE 상태/세대 조건과 고유제약 같은 규칙이 필요하다.

큐는 “해야 할 일”을 잠시 쌓아 두는 곳이다. WORKER는 큐나 DB에서 작업을 가져가 수행하는 프로그램·프로세스다. 임대(lease)는 특정 WORKER에게 일정 기간 작업을 처리할 권한을 준다는 기록이며, ack(전달 확인)는 큐에 “받은 일을 처리했다”고 통보하는 신호다. ack는 DB 커밋과 다른 사건이다. 서로 다른 시스템에서는 하나의 보통 SQL 트랜잭션으로 묶이지 않는다.

🔁 1. 멱등성: 요청을 복사하는 것과 의도를 복사하는 것은 다르다

1-1. 왜 서버가 자동으로 알아차리지 못할까?

두 번의 POST /jobs 요청이 있다. 본문이 똑같다고 해서 반드시 같은 의도인 것은 아니다. 운영자가 같은 날짜를 대상으로 새로운 최적화 실험을 별도로 수행하려는 것일 수도 있고, 통신 장애로 같은 버튼 클릭을 재전송했을 수도 있다. 본문 비교만으로는 의도를 알 수 없다.

그래서 요청자가 “이 요청은 지난번 그 요청과 같은 의도다”라는 표시를 붙인다. 예를 들면 HTTP 헤더의 Idempotency-Key: 5f2a...다. 키는 사용자가 접근 가능한 화면이나 계정과 연결된 요청자 범위 안에서 의미를 갖는다.

[운영자 A] -- 같은 의도 --▶ (scope=A, key=K7, fingerprint=H1) ──▶ job J41
             재전송 ─────▶ (scope=A, key=K7, fingerprint=H1) ──▶ job J41을 재조회
             내용 변경 ──▶ (scope=A, key=K7, fingerprint=H2) ──▶ 409 Conflict

[운영자 B] -- 다른 의도 --▶ (scope=B, key=K7, fingerprint=H1) ──▶ 별개 요청 가능

같은 문자열 K7이라도 다른 요청자라면 충돌할 필요가 없다. 실제 범위는 tenant_id, 인증된 actor_id, API 작업 종류 등으로 정한다. 브라우저가 헤더에 적은 임의의 사용자 ID를 믿지 않고 인증된 주체에서 범위를 계산해야 한다. 권한 검사는 멱등성 기록의 조회에도 적용해야 한다.

1-2. 같은 키·다른 본문을 왜 조용히 받아들이면 안 될까?

첫 요청은 capacity=45였는데 재시도에서 capacity=30으로 바뀌었다고 하자. 서버가 같은 키라서 옛 결과를 준다면 사용자는 30석 계획을 요구하고 45석 계획을 받는다. 반대로 새 요청으로 취급하면 멱등성이 깨진다. 그래서 같은 범위+키인데 의미 있는 본문이 다르면 충돌을 알려 준다. 예제에서는 HTTP 409 Conflict를 선택한다. 특정 HTTP 상태 코드가 유일한 정답은 아니지만 계약상 명확히 정해야 한다.

본문 비교는 JSON 문자열의 공백 순서가 아니라 정규화한 업무 입력으로 한다. 예컨대 다음 항목을 묶어 fingerprint를 생성한다.

{
  "operation": "generate_routes",
  "dataset_version": 12,
  "period_start": "2026-07-20",
  "period_end": "2026-08-14",
  "capacity": 45,
  "arrival_margin_min": 20,
  "algorithm_version": "v3"
}

가상 예시. 날짜·기본값은 시험 자료에 등장하지만 dataset_version=12, algorithm_version=v3는 설계 설명용이다. JSON 키 순서·숫자 표기·기본값 채우기 규칙을 정한 뒤 정규화된 바이트에 SHA-256 등을 적용할 수 있다. 해시는 “같은 의미의 요청”을 스스로 이해하지 않는다. 어떤 필드를 입력 의미로 삼을지가 먼저다. 인가·공격 방지 목적의 민감한 값은 노출하지 않는다. 해시 충돌 가능성은 극히 낮아도 논리적으로 영(0)은 아니며, 높은 보증이 필요하면 정규화 본문도 별도 보관·비교한다.

1-3. DB의 고유제약이 꼭 필요한 이유

다음 둘은 중복 차단을 보장하지 않는다.

T1: 서버 A가 'K7 없네?' 조회
T2: 서버 B가 'K7 없네?' 조회
T3: 서버 A가 job J41 INSERT
T4: 서버 B가 job J42 INSERT

조회하고 나중에 넣는 두 단계 사이에 경쟁이 생긴다. 단일 프로세스에서도 동시에 들어온 요청은 서로 다른 스레드/접속을 통할 수 있다. 애플리케이션의 if not exists는 설명하기 쉽지만 최후의 심판이 될 수 없다. DB가 UNIQUE(scope, key)를 갖고 원자적 삽입을 판단해야 한다.

가상 SQLite 스키마 — 핵심 규칙을 분리해서 보기

PRAGMA foreign_keys = ON;  -- 사용하는 각 연결에서 활성화 여부 확인

CREATE TABLE request_keys (
  scope          TEXT NOT NULL,
  request_key    TEXT NOT NULL,
  request_hash   TEXT NOT NULL,
  job_id         TEXT NOT NULL UNIQUE,
  created_at_ms  INTEGER NOT NULL,
  expires_at_ms  INTEGER NOT NULL,
  PRIMARY KEY (scope, request_key)
);

CREATE TABLE jobs (
  job_id              TEXT PRIMARY KEY,
  state               TEXT NOT NULL
                        CHECK (state IN ('QUEUED','RUNNING','SUCCEEDED','FAILED')),
  input_version       INTEGER NOT NULL,
  input_fingerprint   TEXT NOT NULL,
  algorithm_version   TEXT NOT NULL,
  attempt_no          INTEGER NOT NULL DEFAULT 0,
  fence_token         INTEGER NOT NULL DEFAULT 0,
  lease_until_ms      INTEGER,
  result_id           TEXT,
  CHECK (attempt_no >= 0),
  CHECK (fence_token >= 0)
);

위 표는 교재용 일부 스키마다. 생성 순서상 request_keys.job_id의 외래키나 만료된 키 이력의 정책, 권한 스키마, 감사 필드는 생략했다. 그대로 복사해 완성된 보안·운영 코드를 얻는다는 뜻은 아니다. 실서비스에선 트랜잭션 안에서 키 예약과 job 삽입을 함께 커밋하고, UNIQUE 충돌 시 기존 행의 해시를 비교해 기존 job을 돌려줄지 충돌을 반환할지 결정해야 한다.

실행 흐름은 이렇게 된다.

요청 (scope, K, body)
     │
     ▼
인가 확인 + 업무 입력 정규화 + H(body) 계산
     │
     ▼
BEGIN IMMEDIATE  [쓰기 권한 확보/직렬화 시작]
     │
     ├─ request_keys (scope, K)가 이미 있나?
     │    ├─ 있음, H 동일 ─▶ 기존 job_id 조회 → COMMIT → 기존 상태 반환
     │    └─ 있음, H 다름 ─▶ ROLLBACK → 409 충돌
     │
     └─ 없음 ─▶ 새 job 생성 + 키 연결 + COMMIT → 새 job_id 반환

여기서 BEGIN IMMEDIATE는 SQLite의 쓰기 트랜잭션을 일찍 잡아 경합을 단순하게 설명하려는 선택이다. 모든 DB나 모든 호출이 이 방식이어야 한다는 뜻은 아니다. SQLITE_BUSY 대기/재시도, 커넥션 설정, 예외 처리까지 고려해야 한다. 더 일반적인 방법은 원자적 INSERT ... ON CONFLICT ...와 고유제약을 사용하고 충돌을 조회하는 것이다. SQLite UPSERT는 UNIQUE/PRIMARY KEY 충돌에 반응하며 어떤 오류든 자동으로 고쳐 주는 장치가 아니다.

1-4. 멱등 키는 영원히 기억할 수 있나?

메모리와 저장 용량은 유한하다. 요청 키를 영원히 저장하면 테이블이 계속 커진다. 그러나 24시간 뒤 키를 잊었다면, 25시간 후 같은 키가 도착할 때 새 요청으로 취급될 수 있다. 따라서 “멱등성 보장”은 반드시 보존 기간과 후속 정책을 포함한다.

정책 장점 손실·위험
키 이력 7일 보존(가상 예) 구현 단순, 저장 비용 제한 7일 이후 지연 요청을 새 의도로 처리할 수 있음
작업이 유지되는 동안 요청 키 보존 같은 job으로 재조회 용이 오래 살아 있는 작업에 이력 비용 발생
완료 후도 영구 tombstone 보존 아주 늦은 중복도 식별 가능 저장량·개인정보 보유·키 재사용 문제
만료 후 키 재사용 거부/별도 nonce 정책 오인 재실행 감소 클라이언트가 새 요청 키를 발급해야 함

tombstone은 본문이나 결과를 모두 저장하지 않고 “과거 이 키를 쓴 적이 있다”는 최소 흔적을 남기는 방식이다. 단, 어떤 입력과 연결됐는지 검증해야 할 정책에는 해시 등도 필요하다. 오래된 작업·외부 효과의 수명보다 키 보존을 짧게 잡으면 보호가 끊어진다. 키 보존 종료와 결과·감사 기록 삭제는 독립된 정책일 수 있다.

Ailey: “사용자에게 보이는 성공 응답을 두 번 만들지 않는 것보다 더 중요한 건, 같은 의도를 가리키는 job_id를 계속 찾게 하는 거야. 중복 요청은 실패시키는 게 아니라 같은 작업을 가리키게 하는 쪽이 자연스럽지.”

🧾 2. 네 가지 식별자: job ID, 요청 키, 시도 번호, 입력 버전

같은 숫자처럼 보이지만 서로 다른 질문에 답한다.

값 누가 정하는가 무엇을 식별하는가 언제 바뀌는가
요청 키 K7 요청자 사용자가 한 번 의도한 명령 새 논리 요청에만 새 키
job ID J41 서버 저장·조회할 작업 기록 같은 논리 요청의 재전송이면 그대로
attempt_no 1→2→3 실행 조정자 동일 job을 몇 번째 실행했는가 임대 회수와 새 실행 때 증가
input_version 12 데이터 관리 계층 어떤 적용된 데이터셋/설정 스냅샷에 대해 계산하는가 데이터셋 적용 또는 입력 버전 변경 시 새 버전

여기서 입력 버전은 한 정수만으로 모든 입력을 자동 식별하지 않는다. 실제로는 데이터셋 버전 + 조건값 + 알고리즘 버전 + 정규화된 입력 해시로 계산을 재현 가능하게 해야 한다. 운영자가 데이터셋을 바꿨는데 job은 옛 스냅샷을 읽었다면, 이 job이 무엇을 계산했는지 알 수 있어야 한다. 스냅샷 방식은 동일 입력 복제·콘텐츠 해시·불변 테이블 등 여러 선택이 있으며, 버전 번호만 붙인 뒤 원본을 제자리 수정하면 재현성이 사라진다.

2-1. 차이를 시간선으로 그려 보자

시간 ───────────────────────────────────────────────────────────────▶

운영자 의도 I1     [K7] ──────┬── HTTP 재시도 ──┬── 상태 재조회
                            │                 │
서버 작업                      └────── J41 ──────┘
                                            │
WORKER 실행                            attempt 1 ──(임대 만료)
                                            │
                                            └── attempt 2 ──(성공 확정)

읽은 입력                         dataset v12 + 조건 C + 알고리즘 v3

새로운 운영 의도 I2  [K8] ─────────────────────▶ 새 job J42 (v13일 수 있음)

왜 4개를 합쳐서 하나의 ID로 만들지 않을까? 동일 job을 여러 번 시도할 수 있고, 동일 입력으로 의도적으로 두 번 실험할 수도 있기 때문이다. 입력 버전이 같다고 요청이 같은 것은 아니고, 시도가 새로 생겼다고 사용자 요청이 새로 생긴 것도 아니다.

2-2. “입력이 바뀌었을 때 기존 성공 결과”를 어떻게 다룰까?

예를 들어 현재 적용 데이터셋이 v12이고 J41이 v12의 계획을 성공으로 확정했다. 운영자가 v13을 검증하고 적용했다. J41의 성공이 거짓이 되는 건 아니다. “v12에서 성공”은 역사적 사실이다. 하지만 현재 적용 데이터셋 v13의 계획으로 표시해서는 안 된다.

[현재 적용 입력] v13
       │
       ├── [이전 결과 R41] input=v12, state=SUCCEEDED → 보관 가능, 현재 표시 금지
       │
       └── [현재 결과 포인터] NULL / NOT_READY → 재계산 필요 표시

여기서 “성공 작업 이력”과 “현재 공개 가능한 계획”은 서로 다른 상태다. 이 구별이 마지막 원자적 확정의 출발점이다.

⏳ 3. 재시도와 임대: 멈춘 작업을 살리되, 살아 돌아온 옛 WORKER를 믿지 않는다

3-1. 왜 타임아웃만으로는 WORKER가 죽었다고 할 수 없을까?

WORKER A가 J41을 가져와 계산하다가 GC 정지, OS 일시 정지, DB 잠금 대기 또는 네트워크 지연으로 멈춘 듯 보인다. 관리자는 임대 시간이 만료되어 WORKER B에 다시 맡긴다. 그런데 A가 나중에 깨어나면 둘 다 같은 job의 결과를 저장하려 할 수 있다.

시간  A (옛 실행)                 DB/조정자                  B (새 실행)
 t0   J41 임대 획득  ◀──────────── attempt=1, fence=1
 t1   계산 시작
 t2   멈춤 ...........
 t3                               lease 만료
 t4                               attempt=2, fence=2 ──────────▶ J41 실행
 t5   깨어나서 결과 저장 요구 ──▶ [fence=1?]  거절!
 t6                                                         결과 제출(fence=2)
 t7                               조건 확인 + COMMIT ──────────▶ 성공

임대 만료는 옛 프로그램을 죽이는 물리적 장치가 아니다. 그 프로그램이 일을 계속할 수도 있다. 임대는 “지금 누가 저장해도 되는지”를 알려 주는 계약이고, 계약이 실제 보호가 되려면 저장 시점에 검증되어야 한다.

3-2. 펜싱(fencing): 더 이상 권한 없는 실행의 쓰기를 가로막는다

fence_token은 작업의 소유권을 넘길 때 단조 증가하는 세대 번호(epoch)다. A는 1, B는 2를 받는다. A가 늦게 왔다면 “나는 1번 세대다”라고 스스로 밝히고, 결과를 받는 DB는 현재 세대가 2임을 확인해 거절한다.

단순한 파이썬 비교는 불충분하다.

# 위험한 구조: 읽기와 쓰기가 분리돼 있음 (설명용 의사코드)
if db.get_fence(job_id) == my_fence:
    # 바로 이 사이에 다른 WORKER가 lease 회수할 수 있다.
    db.save_result(job_id, result)

검사와 상태 변경이 하나의 DB 원자적 동작에 실려야 한다.

-- 가상 확정 조건의 핵심 형태: UPDATE 자체가 판단한다.
UPDATE jobs
SET state = 'SUCCEEDED', result_id = :result_id,
    lease_until_ms = NULL
WHERE job_id = :job_id
  AND state = 'RUNNING'
  AND attempt_no = :attempt_no
  AND fence_token = :fence_token
  AND lease_until_ms > :db_now_ms;
-- 변경된 행 수가 정확히 1이어야 현재 실행의 확정 권한이 있음을 뜻한다.

주의할 점: 이 UPDATE 하나로 결과 데이터 전체와 공개 포인터까지 원자적으로 저장된 것은 아니다. 그 일은 다음 절의 같은 트랜잭션 안에서 함께 해야 한다. 또한 :db_now_ms를 한 요청 안의 일관된 시간 기준으로 계산해야 한다. SQLite에서 CURRENT_TIMESTAMP와 밀리초 필드의 형식을 맞추지 않고 비교하면 틀린다. 서로 다른 서버의 클록에 기대면 오차 문제가 생기므로 가능하면 DB 시각 또는 일관된 기준과 여유를 설계한다.

3-3. 펜싱 번호와 시도 번호는 같은가?

단순한 구현에서는 임대 소유권을 넘길 때 attempt_no를 1씩 올리고 그것을 펜싱 번호로 사용해도 된다. 그러나 시도 번호는 로그용 식별, 펜싱은 권한 비교에 사용하는 단조 증가 세대라는 개념적 책임이 다르다. 예를 들어 재개·재시도 카운트 조정이나 다른 자원까지 함께 보호하는 설계에서는 별도 토큰이 유리하다. 핵심은 변수 이름이 아니라 모든 실제 쓰기 경계가 현재 세대를 확인하는가다.

3-4. 임대 갱신과 회수도 원자적이어야 한다

WORKER는 계산이 길어지면 heartbeat로 임대를 연장한다. 그러나 이미 회수된 작업이 “시간만 연장”할 수 있으면 펜싱이 무너진다.

UPDATE jobs
SET lease_until_ms = :new_deadline_ms
WHERE job_id = :job_id
  AND state = 'RUNNING'
  AND attempt_no = :attempt_no
  AND fence_token = :fence_token
  AND lease_until_ms > :db_now_ms;

여기서도 변경 행이 0이면 자기 소유가 아니므로 연장 중단, 후보 폐기, 결과 확정 금지다. 임대 회수 때는 조정자가 트랜잭션 안에서 기존 작업의 상태·만료를 확인하고 세대를 증가시켜 새 소유자로 바꾼다. 새 소유자가 이미 확정된 작업을 다시 집지 않도록 state='RUNNING'/QUEUED 조건이 중요하다.

장애 반례: fence_token이 DB job에만 있고, 결과 파일은 모든 WORKER가 current_result.json에 마음대로 덮어쓰게 하면? DB 펜싱은 지켜져도 파일은 옛 실행이 덮을 수 있다. DB 밖의 쓰기에는 (1) 세대 조건을 이해하는 저장소, 또는 (2) 실행마다 다른 불변 경로에 먼저 쓰고 DB의 유효 포인터만 원자적으로 이동하는 방식이 필요하다. 객체 저장소의 조건부 쓰기가 가능하면 그 계약을 명시하고, 외부 저장소가 조건을 지원하지 않는다면 DB가 공개하는 포인터만 신뢰하도록 설계해야 한다.

3-5. 반복 확정은 같은 시도여도 차단되어야 한다

WORKER B가 유효한 fence=2로 성공을 커밋했다. 직후 함수가 재호출되거나 응답이 유실되어 같은 attempt 2가 성공 확정을 다시 호출한다면? 펜싱 비교만 하고 state 조건이 없으면 두 번째 호출도 “현재 세대”로 보일 수 있다.

따라서 안전한 확정의 문장은 다음 세 조건을 함께 만족해야 한다.

  1. 이 job이 아직 확정 가능한 상태인가? — state='RUNNING'.
  2. 이 실행이 현재 권한자인가? — attempt_no와 fence_token 일치, 임대 유효.
  3. 확정할 증거가 이 입력과 후보에 묶여 있는가? — 입력 버전·후보 해시·검증 보고서 일치.

첫 번째는 동일 시도 반복, 두 번째는 과거 시도 지연, 세 번째는 엉뚱한 결과 연결을 차단한다. 하나라도 빠지면 다른 종류의 사고가 난다.

🧪 4. 후보·검증 보고서·최종 결과: 무엇을 성공이라고 부를 수 있을까?

실제 시험은 제공된 CSV 7종으로 정류장 선정·구성원 배정·노선·시간표를 만들고, EXPORT_SCHEMA.md의 JSON 형식으로 내보내야 했다. 기본 정원 45석, 출근 근무 시작 20분 전 도착, 퇴근 근무 종료 10분 이후 출발, 평일 근무일별 WORK 구성원 양방향 정확히 한 번 배정, OFF 제외, 방향별 travel_times.csv의 시간 준수 등이 요구됐다. 과거 탑승 실적이 낮다고 좌석 확보 대상을 줄일 수 없다.

4-1. 후보를 만드는 일과 승인하는 일을 구분하자

생성기(Creator)가 한 결과 후보를 만들었다고 해서 공개할 자격을 얻는 것은 아니다. 검증기(Validator)가 그 후보, 그 입력, 그 규칙을 독립적으로 검사해야 한다. 여기의 Creator/Validator는 업무상 계획 생성기와 계획 검증기를 말한다. 시험 복기에 등장한 같은 용어가 AI 코딩 에이전트의 역할을 가리켰는지는 확인되지 않았다.

                         변경 불가능한 입력 snapshot v12
                                      │
                      ┌───────────────┴───────────────┐
                      ▼                               ▼
                 [Creator]                      [Validator]
                후보 C77 생성                    입력 규칙 획득
                      │                               ▲
                      ▼                               │
            canonical result bytes                    │
                      │                               │
                      ▼                               │
                SHA-256 = HC77 ────────────────────────┘
                      │                               │
                      ▼                               ▼
                [후보 저장]                 [보고서 V77 저장]
                 job=J41                        input=v12
                 input=v12                      candidate_hash=HC77
                 candidate_hash=HC77           ruleset_version=R5
                                               pass=true / 검사 상세
                      └───────────────┬───────────────┘
                                      ▼
                         [조건부 최종 확정 트랜잭션]
                                      ▼
                         final result F77 + 공개 포인터

모든 ID와 버전 값은 가상이다. 중요한 화살표는 V77.candidate_hash == C77.candidate_hash이고, 둘 다 input_version == job.input_version이어야 한다는 점이다. 보고서에 “통과”만 적혀 있고 무엇을 통과시켰는지 빠지면 다른 후보를 확정할 수 있다.

4-2. 해시 하나만으로 모든 검증이 끝나지 않는다

해시는 바이트 동일성을 확인한다. 후보 JSON이 두 번 직렬화될 때 키 순서가 다르면 해시가 달라질 수 있으므로 canonical JSON이나 불변 저장 바이트를 기준으로 해야 한다. 해시가 같아도 업무 규칙을 지켰다는 뜻은 아니다. “이 파일을 검사했다”와 “이 파일이 안전하다”는 서로 다르다.

검증보고서에는 적어도 검사 대상과 검사 결과의 연결을 남겨야 한다.

{
  "report_id": "V77",
  "job_id": "J41",
  "input_version": 12,
  "input_fingerprint": "sha256:...input...",
  "candidate_hash": "sha256:...candidate...",
  "validator_version": "validator-r5",
  "passed": true,
  "checks": {
    "schema": "PASS",
    "work_off_membership": "PASS",
    "one_assignment_per_direction": "PASS",
    "capacity_by_segment": "PASS",
    "arrival_departure_margins": "PASS",
    "directed_travel_times": "PASS",
    "route_references": "PASS"
  }
}

가상 보고서다. PASS 표시는 실제 데이터에서 측정되었다는 주장이 아니다. 최종 구현에서는 검사별 위반 건수·대상 행 식별자·적용 파라미터·검증기 버전·로그 위치 등 재현 가능한 정보를 남기는 편이 좋다. 검증기가 생성기가 만든 요약 숫자만 믿으면 “독립”이 아니다. 원본 근무표·정류장·소요시간 및 실제 생성된 전체 assignments/routes를 다시 읽어 검사해야 한다.

4-3. 검증 시점과 확정 시점이 다르면 무엇이 변할 수 있을까?

10:00에 후보 C77을 검증했는데 10:01에 파일을 다른 내용으로 덮어 쓰고 10:02에 passed=true인 보고서만 읽어 확정한다면? 이것이 검증 시점과 사용 시점의 차이(TOCTOU)다. 그래서 후보를 불변 객체로 저장하거나, 확정할 바로 그 바이트의 해시를 다시 확인해야 한다. DB에 저장된 후보·보고서·최종 결과의 참조 무결성도 함께 지켜야 한다. 외부 파일·객체 저장소에 대한 검증은 DB 트랜잭션만으로 원자적으로 지킬 수 없으므로 불변 경로와 해시·보관 정책이 별도로 필요하다.

Ailey: “검증 보고서가 passed=true라고 해도, 보고서가 붙은 후보가 확정할 후보와 같다는 연결고리가 없으면 승인 도장이 다른 종이에 찍힌 셈이야.”

✅ 5. 안전한 확정: 결과 저장·성공 상태·공개 포인터가 하나의 사건이 되게 한다

5-1. 세 번 저장하면 왜 위험할까?

WORKER가 후보를 검증했다고 가정하자. 다음 순서로 각각 독립적으로 저장하면?

T1: final_results에 결과 F77 INSERT     [성공]
T2: jobs.state='SUCCEEDED' UPDATE      [성공]
T3: current_plan.pointer=F77 UPDATE   [실패: 프로세스 종료]

DB에는 성공 작업이 있지만 공개 화면은 옛 계획을 가리킨다. 다른 순서였다면 더 위험하다. 공개 포인터를 먼저 바꾸고 결과 본문 저장에 실패하면, 사용자가 아직 존재하지 않는 계획을 보게 된다. 필요한 것은 결과·상태·포인터를 같은 SQLite 트랜잭션에서 성공시키거나 전부 무효화하는 것이다.

5-2. 하지만 “새 결과가 무조건 현재 계획”은 아니다

두 작업이 있을 수 있다.

  • J41: 현재 입력 v12로 시작한 장시간 작업.
  • J42: 운영자가 v13을 적용한 뒤 새 조건으로 시작한 작업.

J41이 늦게 끝났다는 이유로 v13 화면에 J41을 공개해서는 안 된다. J41은 자기 입력에 대한 성공 이력이 될 수 있지만, 현재 포인터의 주인이 될 조건은 다르다.

가상 설계에서 현재 포인터는 다음을 지닌다고 하자.

plan_head
  plan_scope = (site / period / 기타 업무상 하나의 현재 계획 범위)
  active_input_version = 13
  desired_job_id = J42
  published_result_id = NULL
  published_input_version = NULL

plan_scope가 무엇인지(사업장별인지, 기간별인지)는 서비스가 정해야 한다. 위 설계에서는 현재 입력 버전 + 최신 확정 대상 job 둘 다 일치해야만 공개 포인터를 교체한다. 이 정책을 “최신 의도 우선”이라고 부르자. 다른 정책(시작 시점 우선, 운영자 승인 후 공개)도 가능하지만 반드시 명시해야 한다.

5-3. 원자적 확정의 가상 의사 SQL

아래는 SQLite 안에 후보와 보고서가 불변 레코드로 이미 저장돼 있다는 전제에서, 의미를 드러내기 위해 단순화한 의사 SQL/애플리케이션 순서다. 실행해 검증한 완성 코드가 아니다. SQLite 문법·오류 처리·행 수 확인·스키마 제약·시각 표현·권한 확인을 실제 앱에서 구현해야 한다.

BEGIN IMMEDIATE;

-- ① 앱은 같은 트랜잭션에서 jobs, candidates, validation_reports를 읽어 비교한다.
--    J41의 현재 attempt/fence, 상태 RUNNING, 유효한 임대 확인.
--    job.input_version = candidate.input_version = report.input_version
--    job.input_fingerprint = candidate.input_fingerprint = report.input_fingerprint
--    candidate.hash = report.candidate_hash
--    report.passed = 1 및 필요한 checks 전체 통과 확인.
--    후보·보고서 불변성/참조 제약 확인. 불일치면 ROLLBACK.

-- ② 최종 결과 삽입은 job 하나당 하나로 제한한다.
INSERT INTO final_results(result_id, job_id, input_version, candidate_hash, payload)
VALUES (:result_id, :job_id, :input_version, :candidate_hash, :canonical_payload);
-- final_results.job_id에는 UNIQUE 제약이 있다고 가정.

-- ③ 실행 소유권과 상태가 유효할 때에만 성공으로 전이한다.
UPDATE jobs
SET state = 'SUCCEEDED', result_id = :result_id, lease_until_ms = NULL
WHERE job_id = :job_id
  AND state = 'RUNNING'
  AND attempt_no = :attempt_no
  AND fence_token = :fence_token
  AND lease_until_ms > :db_now_ms;
-- affected_rows != 1 이면 ROLLBACK. final_results INSERT도 함께 되돌아간다.

-- ④ '현재 대상'인 경우에만 공개 포인터를 원자적으로 교체한다.
UPDATE plan_head
SET published_result_id = :result_id,
    published_input_version = :input_version
WHERE plan_scope = :plan_scope
  AND active_input_version = :input_version
  AND desired_job_id = :job_id;
-- 변경 0건은 '확정 성공이지만 현재 공개 대상 아님' 정책에서 허용 가능.
-- 현재 공개가 필수인 명령이라면 0건을 실패로 취급하고 롤백해야 함.

-- ⑤ (외부 이벤트가 필요하다면) 같은 트랜잭션에서 outbox 행 INSERT.
COMMIT;

선택의 핵심: UPDATE plan_head의 변경 0건을 어떻게 처리할지 비즈니스 계약으로 정해야 한다. 여기서는 오래된 작업도 SUCCEEDED 이력으로 보관하지만 공개하지 않는다. 또는 “현재성이 없으면 SUPERSEDED 상태로 종료”하도록 모델링할 수도 있다. 어느 쪽이든 SUCCEEDED가 계산/검증 성공인지 현재 공개 성공인지 정확히 정의해야 한다. 위 최소 상태 목록에는 SUPERSEDED가 없으므로 그 선택을 할 경우 스키마를 확장해야 한다.

5-4. 같은 트랜잭션이 제공하는 보장과 제공하지 않는 보장

                          ┌──── SQLite transaction ────────────────────┐
  candidate C77, V77 ───▶ │ INSERT final F77                              │
  job J41/fence2 ───────▶ │ UPDATE job SUCCEEDED (조건부, 1행)             │
  현재 입력/대상 ───────▶ │ UPDATE visible pointer (조건부)              │
                          │ INSERT outbox event (선택)                  │
                          └─────────────── COMMIT or ROLLBACK ─────────┘
                                           │
                          한 DB에서 함께 확정됨 / 함께 취소됨
                                           │
                          X HTTP 응답 전송이나 외부 큐 ack까지는 불포함

SQLite의 트랜잭션은 이 한 DB 안의 변경을 원자적으로 다룬다. 외부 파일 쓰기, 이메일, 브로커 publish, 다른 서버의 별도 DB는 같은 로컬 트랜잭션의 보호를 받지 않는다. 또한 코드가 트랜잭션을 열어도 후보 검증을 10분간 DB 쓰기 잠금을 쥔 채 수행하면 다른 작업을 지연시킨다. 무거운 계산/독립 검증은 밖에서, 마지막 짧은 참조·상태 확인과 확정만 트랜잭션 안에서 수행하는 구조가 보통 유리하다. 단 후보/보고서는 그 사이 변경될 수 없도록 불변이어야 한다.

5-5. 결과의 공개는 읽는 쪽에서도 지켜야 한다

구성원 화면은 job.state='SUCCEEDED'인 최신 행을 무조건 골라 보여 주면 안 된다. plan_head.published_result_id와 active_input_version, 결과의 input_version을 함께 확인해야 한다. 새 데이터셋을 적용할 때는 새 적용 버전과 현재 계획의 유효성 처리를 원자적으로 갱신한다. 즉 옛 결과를 새 입력의 결과처럼 읽지 못하도록 포인터를 무효화하거나 유효 버전 비교로 가린다.

예를 들어 아래 읽기 규칙을 둘 수 있다.

SELECT f.payload
FROM plan_head h
JOIN final_results f ON f.result_id = h.published_result_id
WHERE h.plan_scope = :scope
  AND h.published_input_version = h.active_input_version
  AND f.input_version = h.active_input_version;

이 SELECT는 설명용이다. 실제로는 적용된 조건 버전/기간 범위도 포함해야 한다. 반환 행이 없으면 “아직 현재 데이터의 결과가 없음: 재계산 필요”로 보여 주어야 한다. 이전 결과를 숨기거나 “이전 데이터 기준”으로 명확히 따로 보여 주는 것은 UI 정책이다.

📬 6. 커밋했는데 응답이나 ack가 사라진다면?

6-1. 커밋 뒤 HTTP 응답 유실

WORKER / API                    SQLite                      브라우저
   성공 확정 요청 ───────────────▶ COMMIT 완료
   200/201 응답 전송 ──────────────────────────────X  네트워크 유실
                                            화면에는 타임아웃

확정이 일어났다는 사실과 클라이언트가 그 사실을 안다는 사실은 다르다. 서버가 응답을 보냈다는 로그조차 브라우저의 수신 증거가 아니다. 사용자가 같은 요청 키로 다시 물으면 request_keys에서 기존 J41을 찾고, 그 상태를 재조회해 SUCCEEDED와 result_id를 알려 준다. 새로운 job을 만들거나 같은 결과를 다시 공개하려고 하면 안 된다.

권장되는 API 경험(가상):

POST /jobs
Idempotency-Key: K7
Content-Type: application/json

{"dataset_version":12,"capacity":45,"arrival_margin_min":20,"period_start":"2026-07-20","period_end":"2026-08-14"}

첫 접수 응답을 202 Accepted + Location: /jobs/J41로 줄 수 있고, 같은 키·같은 본문 재요청에는 J41의 현재 상태와 위치를 반환한다. 완료된 작업이면 GET /jobs/J41에 state=SUCCEEDED, result_id=F77를 담는다. REST의 특정 상태 코드 선택보다 중요한 것은 반복 호출의 의미를 문서화하는 일이다.

6-2. 큐의 ack 유실

외부 큐를 쓰는 경우는 순서가 하나 더 추가된다.

[Broker] -- J41 전달 --> [WORKER]
                            │
                            ├── SQLite에서 결과·성공 상태 COMMIT
                            │
                            └── Broker에 ack 전송 ──X

Broker: 'ack 못 받음' → J41 재전달
새 WORKER: DB의 J41 상태 SUCCEEDED 확인 → 계산/확정 생략 → ack

이때 ack를 먼저 보내고 DB에 커밋하지 않으면 작업을 잃을 수 있다. broker는 처리 완료로 간주했지만 DB에는 결과가 없을 수 있다. 보통은 DB 확정이 먼저, ack는 그 뒤다. 그 결과 중복 전달은 생길 수 있으므로 DB의 상태 조건과 멱등 처리가 필수다. 특정 브로커의 가시성 제한·ack 계약은 제품마다 다르므로 실제 구현 시 문서를 확인한다.

6-3. 무한 재시도도 안전하지 않다

모든 실패를 즉시 반복하면 DB를 더 압박하거나 비용을 폭증시킨다. 실패를 나누어야 한다.

실패 종류 해석 합리적인 다음 행동
일시적 DB busy / 네트워크 끊김 결과 미확정일 수도, 이미 확정됐을 수도 있음 상태 재조회 후 제한된 재시도, 지수 백오프와 지터
후보 검증 실패 같은 입력·같은 알고리즘이면 또 실패할 가능성 높음 오류 보고·수정 대기, 무조건 재실행 금지
요청 키 본문 충돌 다른 의도가 같은 키를 사용 409 반환, 새로운 의도에는 새 키
lease 상실 / fence 불일치 이 WORKER는 더 이상 권한 없음 저장 중지, 후보 폐기, 현재 job 상태 재조회
완전하지 않은 외부 전달 ack/publish의 결과를 모름 안정적 메시지 ID로 재전달·중복 제거
장기간 반복 장애 자동 복구 한계 초과 재시도 상한, FAILED/보류, 운영자 확인 및 재구동 정책

재시도는 속도를 높이는 기능이 아니라 일시적 불확실성을 안전하게 다시 관측·처리하는 기능이다. 지수 백오프는 예컨대 1초, 2초, 4초처럼 대기 시간을 늘리고, 지터는 여러 WORKER가 동시에 몰려드는 일을 줄인다. 횟수·대기 상한은 작업 비용과 장애 복구 목표에 따라 정한다.

🔀 7. DB와 외부 큐를 함께 쓰면 왜 '이중 쓰기'가 문제가 될까?

웹 서버가 작업을 접수할 때, jobs는 SQLite에 넣고 큐에는 J41 메시지를 보내야 한다. 서로 다른 두 시스템에는 두 번의 쓰기가 필요하다.

7-1. 순서를 바꿔도 틈은 남는다

DB 먼저

1. SQLite에 J41 저장 / COMMIT ── 성공
2. 외부 Broker에 J41 publish ─── X 실패
⇒ DB에는 QUEUED인데 아무 WORKER도 모름: 유령 대기 작업

큐 먼저

1. Broker에 J41 publish ─────── 성공
2. SQLite에 J41 저장 / COMMIT ─ X 실패
⇒ WORKER가 아직 존재하지 않는 job을 처리할 수 있음

트랜잭션 두 개를 각각 성공시키는 것만으로 둘을 함께 원자화할 수 없다. 같은 DB 안에서 처리할 때는 DB 테이블을 큐로 삼아 하나의 트랜잭션 경계를 사용할 수 있지만, 외부 브로커를 도입하면 새로운 조정 문제가 생긴다.

7-2. Transactional outbox는 '메시지를 보내겠다는 사실'을 DB에 먼저 저장한다

아웃박스(outbox)는 보내야 할 이벤트를 저장하는 DB 테이블이다. 업무 변경과 outbox 삽입은 같은 DB 트랜잭션으로 묶는다. 나중에 relay(발행기)가 미발행 행을 읽어 broker에 보낸다.

   API: POST /jobs (K7)
             │
             ▼
  ┌── SQLite TRANSACTION ─────────────────────────┐
  │ jobs: J41 QUEUED INSERT                       │
  │ request_keys: (A,K7) → J41 INSERT             │
  │ outbox: EVT-901 'JobQueued(J41)' INSERT       │
  └───────────────────── COMMIT ───────────────────┘
             │
             ▼
       Outbox relay (별도 루프/프로세스)
             │ read EVT-901
             ▼
       Broker publish EVT-901 ─────────▶ WORKER/Consumer
             │                              │
             └── outbox SENT 기록           └── 중복 메시지 차단 후 처리

이 방식이 보장하는 것은 업무 상태가 커밋됐는데 '보낼 메시지' 기록이 아예 없는 상태를 없앤다는 것이다. 단, relay가 계속 실행되고 broker가 회복한다는 가정 아래에 결국 전달을 시도할 기회가 남는다는 뜻이지, 무조건 즉시 전달된다는 뜻은 아니다.

7-3. relay도 중복 publish할 수 있다

T0 relay: EVT-901 읽음
T1 relay: Broker publish 성공
T2 relay: 'SENT'로 마킹하기 직전 프로세스 종료
T3 새 relay: EVT-901이 아직 미발행으로 보임
T4 새 relay: Broker에 EVT-901 다시 publish

아웃박스만 붙이면 유실 가능성이 줄어들지만 중복 가능성은 남는다. 그래서 outbox의 짝은 수신자 멱등 처리(inbox / processed_messages)다.

CREATE TABLE processed_messages (
  consumer_id TEXT NOT NULL,
  event_id    TEXT NOT NULL,
  processed_at_ms INTEGER NOT NULL,
  PRIMARY KEY (consumer_id, event_id)
);

수신자가 메시지 EVT-901을 받으면 하나의 DB 트랜잭션 안에서 (consumer_id, event_id)를 기록하고 해당 업무 변경을 한다. 이미 고유키가 존재한다면 그 메시지가 이전에 성공 처리되었다는 정책에 따라 업무 변경을 반복하지 않고 ack한다. 반대로 기록만 먼저 커밋하고 업무 변경을 나중에 별도 트랜잭션에서 하면, 중간 장애에서 처리한 척하게 되므로 잘못이다.

수신자 트랜잭션의 올바른 묶음:

BEGIN
  INSERT processed_messages(consumer, event) -- 중복이면 기존 처리 확인
  실제 소비자의 DB 변경
COMMIT
→ broker ack

다만 외부 이메일 발송, 타 회사 API 호출 등 수신자 DB 밖의 부작용은 이 트랜잭션만으로 딱 한 번 보장할 수 없다. 외부 API가 멱등 키를 지원하면 동일 event ID를 전달하고, 그렇지 않으면 중복 가능성과 보상/대사(reconciliation) 정책을 명시해야 한다. 물리적으로 같은 이메일이 한 번만 발송되었는지, 모든 장애에서 단정할 수 없다.

7-4. outbox와 job 큐는 같은 것인가?

아니야. job은 수행할 업무 자체, outbox는 외부 시스템에 알릴 사건을 기록한다. JobQueued 이벤트가 job의 생성 사실을 알리고, PlanPublished 이벤트가 최종 결과의 공개 사실을 알릴 수 있다. 동일 DB로 처리하는 단일 서버에서는 jobs 테이블의 QUEUED 행 자체가 영속적인 작업 대기열이 될 수 있다. 이 경우 job 접수에 외부 outbox가 반드시 필요한 것은 아니다. 외부 브로커나 다른 서비스를 추가할 때 outbox의 이점이 커진다.

최종 확정과 outbox의 연결도 중요하다. 결과 F77의 성공·공개 포인터 변경과 PlanPublished(F77) outbox 행을 함께 커밋하면, 공개되지도 않은 결과를 발표하거나 공개한 사실을 발행할 기록 없이 잃는 틈을 줄인다. 단 위 절의 정책처럼 옛 job이 성공했으나 공개되지 않았다면 PlanPublished를 발행하면 안 된다. 이벤트 이름과 발생 조건은 실제 업무 상태와 일치해야 한다.

🏗️ 8. 세 환경에서 어떤 보장이 실제로 달라지는가

8-1. 단일 서버 + SQLite + 같은 프로세스의 WORKER

가장 단순한 시작점은 SQLite jobs를 작업 대기열로 사용하고, 애플리케이션 안에 하나의 실행 루프를 두는 것이다. 웹 요청은 job을 커밋하고 곧바로 응답한다. 백그라운드 루프는 QUEUED를 찾아 임대하고 계산·검증·확정한다. 핵심 상태는 전부 DB에 저장한다.

장점: 외부 브로커 이중 쓰기 없음, 구성 단순, 시험 시 구현·설명 비용이 낮다.
한계: 프로세스가 중단되면 루프도 멈춘다. 재시작 시 DB에서 미완료 job을 찾아 복구해야 한다. 웹 서버 프로세스가 여러 개 뜨면 “루프 하나”라는 가정이 깨진다. SQLite는 한 번에 쓰기 연결 하나만 허용하므로 여러 계산 결과를 동시에 짧게 저장하는 건 가능해도 긴 쓰기 트랜잭션은 병목이 된다. 프로세스 내부 메모리 큐만 쓰면 재시작 시 대기 작업을 잃는다.

8-2. 같은 호스트 별도 WORKER 프로세스 + SQLite

웹 프로세스와 계산 프로세스를 분리하면 계산 중 웹 응답이 막히는 일을 줄일 수 있다. 둘이 같은 DB 파일에 접근한다면 상태·고유제약·펜싱 조건은 여전히 공유된다. 그러나 서로 다른 프로세스의 메모리는 다르므로 파이썬 전역 변수나 뮤텍스는 공유 락이 아니다. 임대·상태는 DB에 있어야 한다.

장점: 계산 실패가 웹 서버를 직접 죽일 위험 감소, 재시작/감시 분리.
한계: 별도 실행·감시·로그·종료 신호 처리 비용. 같은 DB에서 쓰기 경쟁은 남는다. SQLite WAL을 쓴다면 프로세스들이 같은 호스트의 적절한 로컬 파일시스템을 공유해야 하며, 네트워크 파일시스템을 통한 다중 호스트 WAL 공유는 지원 방식이 아니다.

8-3. 여러 웹 서버·여러 WORKER + 외부 DB/브로커

여러 서버에서는 API가 어떤 서버에 도착할지, 어떤 WORKER가 작업을 재수신할지 예측할 수 없다. 메모리 락이나 서버별 임의 파일로 중복 차단을 하면 보장이 분열된다. 모든 실행자가 공유하는 권위 있는 DB/조정 서비스, 원자적 비교 후 갱신, 임대 세대, outbox/consumer 멱등성이 더 중요해진다.

장점: 처리량·장애 격리·수평 확장 선택지가 커진다.
한계: 서버 간 클록·네트워크 분할·브로커 중복·운영 관측과 복구·비용 복잡성. 일반적인 SQLite WAL 파일을 네트워크 공유로 여러 호스트에 올리는 것은 권장 설계가 아니다. 이 규모에서는 PostgreSQL과 외부 큐 등 다른 선택을 검토할 수 있지만, 특정 기술 선택은 시험의 필수 요구사항이 아니었다.

설계 요청 중복 방지 옛 WORKER 차단 외부 메시지 내구성 운영 비용
단일 프로세스·DB job 큐 UNIQUE + 트랜잭션 재시작/재진입까지 대비한 상태·fence 외부 메시지가 없다면 해당 없음 낮음
별도 프로세스·공유 SQLite 동일한 DB 제약 필수적으로 DB 상태·fence 확인 외부 브로커 없으면 DB 큐로 처리 중간
다중 서버·외부 브로커 공유 DB UNIQUE + API 계약 분산 실행 전부에서 원자적 fence outbox + 중복 수신 차단 + relay 감시 높음

이 표의 “방지”는 구현과 운용이 계약을 지켰을 때 특정 범위에서 성립한다는 뜻이지 절대적인 실행 exactly-once 보증이 아니다.

9-2. 몇 개를 세어야 '정상'이라고 할 수 있나?

가상 운영 점검 SQL의 방향은 다음과 같다. 스키마에 맞는 실제 쿼리는 별도 구현해야 한다.

-- 한 job에 최종 결과가 두 개 생기지 않았는가?
SELECT job_id, COUNT(*)
FROM final_results
GROUP BY job_id
HAVING COUNT(*) > 1;

-- 성공이라고 하는데 최종 결과 참조가 없는가?
SELECT job_id FROM jobs
WHERE state = 'SUCCEEDED' AND result_id IS NULL;

-- 공개 중인 결과가 현재 적용 입력과 맞지 않는가?
SELECT plan_scope FROM plan_head
WHERE published_result_id IS NOT NULL
  AND published_input_version <> active_input_version;

-- 임대가 오래 만료됐는데 RUNNING으로 방치된 작업은?
SELECT job_id FROM jobs
WHERE state = 'RUNNING' AND lease_until_ms <= :now_ms;

-- 발행되지 않은 outbox가 쌓이고 있는가?
SELECT COUNT(*) FROM outbox WHERE published_at_ms IS NULL;

모든 결과가 0이라고 규칙 위반이 전혀 없다는 충분조건은 아니다. 예를 들어 “45석 이하”는 최종 내보내기 JSON과 적용된 차량 정원으로 별도 검증해야 하고, 근무자별 양방향 정확히 한 번 및 travel_times.csv의 방향별 소요시간도 실제 행을 읽어 검사해야 한다. 또 공개 포인터 값이 잘못 삭제된 결과를 가리키는지, outbox relay가 장시간 멈췄는지, 보존 만료가 늦은 중복 요청보다 짧은지 등을 추가로 봐야 한다.

9-3. 무엇을 로그에 남겨야 추궁에 답할 수 있을까?

작업 하나의 추적에서 최소한 다음 관계가 이어져야 한다.

request scope + key → job_id → input_version/fingerprint
                                 │
                                 ├─ attempt_no / fence / worker / lease
                                 ├─ candidate_id + candidate_hash
                                 ├─ validation_report_id + validator_version + pass/fail
                                 ├─ final_result_id + commit time
                                 ├─ published? + plan_scope + pointer version
                                 └─ event_id + outbox status + consumer dedup status

사용자/구성원의 개인정보를 해시나 로그에 무심코 넣는다고 익명화되는 것은 아니다. 접근 통제, 개인정보 최소화, 보존·삭제 정책이 필요하다. 로그만 있고 DB 상태가 없다면 로그의 순서·완전성 문제로 진실을 단정하기 어렵다. DB의 권위 있는 상태와 연관 ID로 추적해야 한다.

⚖️ 10. 실무 설계의 손실: 보호 장치를 더할수록 무엇이 비싸질까?

멱등 키는 기록량과 보존 정책을 요구한다. 불변 입력 스냅샷은 저장 공간을 사용한다. 임대는 만료·연장·회수 정책과 stale worker 테스트가 필요하다. 펜싱 조건은 모든 결과 쓰기 경계에 삽입해야 하므로 코드 경로가 길어진다. 검증 보고서는 CPU와 I/O를 늘리지만 독립성·설명 가능성을 높인다. 원자적 결과 확정은 스키마와 트랜잭션 경계 설계가 필요하다. outbox는 relay, backlog 모니터링, 이벤트 ID, 수신자 멱등 테이블까지 운영해야 한다.

어디까지 선택할지는 실패가 발생했을 때 손실되는 것과 보호 장치 유지 비용을 비교해서 결정한다.

질문 최소 구현 선택의 이점 포기하는 보장 / 후속 과제
외부 브로커 없이 DB 큐 사용? 이중 쓰기 제거, 배포 구성 단순 DB 큐 처리량/폴링 지연, 프로세스 복구 구현
임대·펜싱 구현? 죽은 듯 보이는 작업을 회수하면서 옛 확정 거절 heartbeat·세대 관리·테스트 비용
계산 결과는 DB에 저장? 최종 원자적 커밋이 쉬움 DB 용량·쓰기 압력 증가
후보는 DB 밖 불변 객체? 큰 파일 처리와 저장 확장 파일 내구성·해시·고아 객체 정리 필요
outbox까지 구현? DB 변경과 이벤트 발행 의도를 함께 기록 relay·중복 수신 차단·운영 감시 필수
입력 변경 후 자동 재계산? 사용자 편의 반복 job 비용·기존 실행 취소/선점 정책 복잡

단일 서버·SQLite로 시험 수준의 서비스 설명을 준비할 때는 DB 기반 job 접수 + 고유제약 + 명시적 상태 전이 + 결과 확정 트랜잭션 + 입력 버전별 공개 관리가 우선순위가 높다. 계산이 길고 프로세스 중단·재시도를 다뤄야 한다면 임대·펜싱이 필요해진다. 외부 큐와 다른 서비스가 없다면 outbox는 필수 구현이라고 주장하면 안 된다. 그런 경우 왜 지금은 채택하지 않았으며 어떤 조건에서 도입할지 설명하는 편이 설계적으로 더 정확하다.

10-1. '정확히 한 번'을 주장할 때 반드시 목적어를 붙인다

  • 정확히 한 번 요청을 수신: 네트워크 중복/재전달까지 포함하면 일반적으로 이런 보장을 단정하지 않는다.
  • 정확히 한 번 계산 함수 실행: 프로세스 중단·재시도가 있는 환경에서는 목표로 삼기 어렵다.
  • 한 job에 최종 DB 결과 최대 한 개: UNIQUE(job_id), 상태 조건, 원자적 확정으로 강하게 보장하도록 설계할 수 있다.
  • 하나의 현재 계획 포인터만 유효: DB가 권위 있는 포인터를 소유하고 버전 조건을 원자적으로 검사하면 보장 범위를 정의할 수 있다.
  • 이벤트를 소비해 업무 변경을 한 번만 커밋: 수신자 DB의 processed_messages와 업무 변경을 함께 트랜잭션 처리한다는 조건에서 가능하다.
  • 외부 메시지·이메일이 물리적으로 딱 한 번 전달: 일반 outbox + at-least-once 전달만으로는 보장되지 않는다.

이 차이를 설명하는 사람은 “우리는 exactly-once입니다”라는 말보다 어떤 효과가, 어느 시스템에서, 어떤 키와 기간 안에서, 어떤 장애까지 견디는가를 분명히 말한다.

🧠 11. 하나의 사건을 처음부터 끝까지 설명해 보자

이 절은 지금까지의 조각을 한 번에 연결한 가상 완성 사건이다.

  1. 운영자 A는 적용 데이터 v12, 기간, 정원 45, 도착 여유 20분을 선택하고 생성 버튼을 누른다. 브라우저는 이 한 의도에 대한 키 K7을 만든다. 새로운 의도를 시작할 때만 새 키를 만든다.
  2. API는 인증된 A의 범위에서 K7과 정규화 본문 해시 H1을 구한다. SQLite 쓰기 트랜잭션에서 키와 J41을 함께 저장한다. 외부 브로커를 쓴다면 JobQueued(J41)도 outbox에 함께 기록한다. 브로커를 쓰지 않으면 DB의 QUEUED 자체가 대기열이다.
  3. 서버는 응답을 보내지만 네트워크에서 사라진다. 사용자가 다시 누르면 같은 K7, H1으로 재조회하여 J41을 받는다. J42가 생기지 않는다.
  4. WORKER A는 J41을 임대해 attempt 1/fence 1로 계산을 시작한다. 그 뒤 일시 정지해 임대가 만료된다. 회수자는 원자적 상태 변경으로 attempt 2/fence 2를 발급한다.
  5. WORKER B가 입력 v12의 불변 스냅샷으로 C77을 계산한다. 독립 Validator가 EXPORT_SCHEMA.md와 업무 규칙에 따라 같은 입력과 후보를 재검사하고 보고서 V77에 후보 해시·입력 해시·검증기 버전·검사 결과를 남긴다.
  6. A가 뒤늦게 복귀하여 옛 토큰으로 결과를 확정하려 하지만 SQLite의 조건부 UPDATE가 0행이므로 거절된다. A의 임시 후보는 최종 공개되지 않는다.
  7. B는 같은 SQLite 트랜잭션 안에서 C77/V77 연결 및 현재 fence/상태를 확인하고, F77 저장 + J41 성공 전이 + 현재 입력과 대상 job 일치 시 공개 포인터 변경을 커밋한다. 외부 이벤트가 필요하면 PlanPublished(F77) outbox도 함께 저장한다.
  8. 바로 뒤 B의 ack가 끊겨 큐가 J41을 다시 전달한다. 새 WORKER는 J41이 SUCCEEDED임을 보고 확정을 반복하지 않고 ack한다.
  9. outbox relay가 이벤트를 발행했으나 SENT 기록 전 종료될 수 있다. 같은 event_id가 다시 오면 수신자는 processed_messages 고유키로 자신의 DB 효과를 중복하지 않는다.
  10. 운영자가 이제 v13 데이터셋을 검증·적용하면 현재 입력 포인터가 갱신되고 v12 결과는 이력으로 남더라도 현재 계획 화면에서는 사라지거나 구버전으로 표시된다. 새 계산 J42가 완료·검증되기 전에는 v13 계획이 존재한다고 주장하지 않는다.

이 전체 흐름을 “한 번 실행”이라고 요약하면 틀린다. 실제로는 HTTP 요청도 여러 번, WORKER 계산도 여러 번, 큐 전달도 여러 번 일어났다. 한 번만 일어났다고 약속한 것은 J41의 유효한 최종 DB 확정과 그 정책에 맞는 공개 효과다.

🧷 13. 구분을 남기는 끝맺음

이 강좌를 관통하는 한 문장은 “재시도는 반복되어도, 권위 있는 상태의 전이는 조건부로 한 번만 인정한다”야. 요청자는 키로 의도를 식별하고, DB는 고유제약으로 접수를 묶고, 조정자는 시도와 임대 세대를 바꾸고, WORKER는 후보를 계산하고, 검증기는 특정 입력과 후보를 확인하고, 최종 트랜잭션은 지금도 권한이 있는 실행인지와 이 보고서가 이 후보를 통과시켰는지를 검증한 뒤 저장·상태·공개를 묶는다. 외부 큐가 있으면 outbox는 발송할 의도를 DB 커밋에 붙이고 수신자 중복 차단은 전달이 여러 번 이루어지는 현실을 받아들인다.

시험에서는 “우리 서비스가 절대 중복 실행하지 않는다”고 말하기보다, “요청 중복은 이 키와 고유제약으로, 오래된 실행은 이 펜싱 조건으로, 같은 실행의 중복 확정은 이 상태 조건으로, 결과-검증 불일치는 이 해시 연결로, DB 내부 부분 성공은 이 트랜잭션으로 막는다. 다만 외부 브로커의 중복 전달은 막지 않고 수신자에서 멱등 처리한다”라고 말할 수 있어야 해. 실제 제출 코드가 없으므로 여기의 설계가 구현되어 있다고 주장하지 않으며, 실제 프로젝트에서는 코드·DDL·동시성 테스트·로그를 대조해야 한다.
