🧭 0. 하나의 사고에서 시작하자 — “시간 초과됐는데 결과가 생겼습니다”

통근버스 웹서비스의 운영자가 ‘노선 생성’을 누른다. 화면에는 회전하는 표시가 뜬다. 30초 뒤 브라우저가 “시간 초과”라고 말한다. 운영자는 실패한 줄 알고 한 번 더 누른다. 그런데 첫 번째 계산은 서버에서 계속 실행 중이고, 두 번째 계산도 시작됐다. 잠시 후 먼저 끝난 결과가 저장된다. 더 늦게 끝난 다른 결과가 다시 덮어쓴다. 운영자가 확인한 결과는 어떤 데이터셋과 어떤 조건으로 계산됐을까?

이 이야기는 버스 노선 자체보다 결과의 소유권과 공개 권한에 관한 이야기야. 화면은 보지 못했어도 서버는 일을 하고 있을 수 있어. 서버의 함수가 끝나도 데이터베이스에 결과가 없을 수 있고, DB에 결과가 남아도 화면이 그 사실을 모를 수 있어. 반대로 DB에 임시 결과가 있다는 사실만으로 구성원에게 노선을 보여 주면 안 돼.

여기서 수업 전체를 관통하는 한 문장을 먼저 놓을게.

어떤 일이 ‘멈췄다’는 사실과, 어떤 결과가 ‘정식으로 유효하다’는 사실은 서로 다른 차원이다.

예를 들어 운영자는 재계산을 취소할 수 있지만, 취소 전에 이미 확정된 이전 운행 계획은 남아 있어야 한다. 새로운 계산을 시작했다는 이유만으로 검증 완료된 이전 결과를 삭제할 이유도 없어. 다만 데이터셋이나 운영 조건이 바뀌었다면 이전 결과는 남아 있더라도 현재 조건에 대한 결과로는 표시하지 않아야 해. 이 두 가지를 같은 ‘삭제’ 버튼으로 해결하려 하면 정상 결과를 없애거나, 반대로 잘못된 결과를 공개하기 쉬워진다.

이 수업에서 ‘사실’과 ‘설계 예시’를 구별하는 약속

시험 원문인 EXAM_ORIGINAL_COMBINED.txt에는 CSV 7종을 선택·검증·적용하고, 근무일별 통근버스 노선을 생성하며, 잘못된 데이터셋을 적용하지 않고 기존 데이터와 생성 결과를 유지하고, 재시작 뒤에도 DB에 데이터를 보존하라는 요구가 있다. 생성·검증·저장 흐름, 시간 제한, WORKER 종료와 취약 지점은 EXAM_RECOLLECTION.txt에 사용자의 복기 질문으로 남아 있다. 이것은 실제 제출 코드나 실행 로그가 아니다.

시험 원문은 특정 프레임워크, SQLite, 별도 WORKER, 아래 상태 이름을 필수로 지정하지 않는다. 이 강좌는 설명을 위해 ‘단일 서버 + SQLite + 별도 프로세스로 실행할 수 있는 생성 작업’을 가상 설계로 채택한다. 실제 CSV 행과 응시자의 제출 소스 코드가 제공되지 않았으므로, 아래의 데이터 값·job ID·시간·예시 SQL·예상 로그는 모두 가상 사례 또는 미실행 설계 코드로 표기한다. 원본의 규칙과 혼동하지 마.

원문에서 특히 중요한 사실은 다음과 같다. 버스 기본 정원은 45명이고, 근무일에 근무하는 모든 구성원을 출퇴근 각각 정확히 한 번씩 배정하며, 출근은 근무 시작 20분 전까지 도착하고 퇴근은 근무 종료 10분 후 이후 출발해야 한다. 구간별 이동시간은 travel_times.csv에서 가져와야 하며, 선택한 기간·정원·도착 여유 시간을 바꾼 재계산도 검증해야 한다. 따라서 ‘계산 완료’가 ‘제약 만족’을 의미하지 않는다.

🔎 1. 먼저 자르는 다섯 개의 사건: 기다림, 계산, 실행 주체, 확정, 공개

1-1. 화면은 서버의 머릿속을 볼 수 없다

사용자가 버튼을 누르면 웹 브라우저는 서버에 HTTP 요청을 보낸다. 서버는 요청을 받은 뒤 작업을 처리하고 응답한다. 응답이 돌아오기 전 브라우저는 보통 ‘처리 중’으로 표시한다. 이때 브라우저가 기다림을 포기했다면 확인할 수 있는 것은 응답을 제시간에 받지 못했다는 사실뿐이다. 서버에서 계산이 멈췄는지, 결과가 DB에 저장됐는지는 아직 모른다.

시간 →
브라우저         | 요청 보냄 ───── 기다림 ──── 30초 경과! ── timeout 표시
HTTP 연결       | ─────────────────────────── 끊김 / 응답 포기
웹 서버         | 요청 수신 ─ 작업 접수 ───────────── 상태 조회 가능
생성 계산       |                 계산 시작 ──────────────────── 계산 계속 ── 끝
SQLite          | job 기록 ────────── temp 기록 ───────── 검증 ── 확정
공개 결과       | 기존 계획 유지 ─────────────────────────────── 새 계획으로 변경

주의: 각 줄은 서로 연결돼 있지만 동시에 자동 중단되는 하나의 줄이 아니다.

30초짜리 timeout이 있더라도 어느 계층의 시간 제한인지 말해야 해. 브라우저의 요청 대기 제한, 리버스 프록시의 응답 제한, 서버 코드의 대기 제한, 계산 자체의 수행 시간 제한, WORKER 임대(lease) 시간 제한은 목적과 결과가 다르다.

사건 직접 변화하는 것 자동으로 보장하지 않는 것 확인할 위치
요청 대기 timeout 호출자가 결과를 기다리지 않음 서버 계산 종료, DB 롤백, 실패 확정 HTTP/프록시 로그, job ID 상태
협력적 계산 중단 계산이 취소 신호를 확인하고 안전한 지점에서 종료 이미 커밋한 DB 변경 되돌리기 WORKER 로그, 체크포인트
Task/Future 취소 요청 실행 모델에 맞는 취소 요청/대기 작업 취소 시도 현재 실행 중인 모든 코드 즉시 정지 태스크 상태, 실제 함수 종료 기록
프로세스 강제 종료 운영체제가 프로세스 실행을 중단 임시 파일 자동 삭제, 완료 메시지 전송, finally 실행 프로세스 종료 코드, 재기동 시 DB
결과 공개 차단 조회 API가 미확정 결과를 숨김 계산 중단, 저장 공간 정리 조회 쿼리, 공개 포인터, 버전 조건

다섯 번째가 특히 중요하다. 프로세스를 굳이 죽이지 않아도 결과를 공개하지 않을 수 있고, 프로세스가 죽었더라도 이전에 공개된 안전한 결과는 계속 제공할 수 있다. 실행 제어와 노출 제어를 분리한 덕분이야.

1-2. 시간 제한은 ‘단순 경고’가 아니라 계약이다

‘30초 제한’이 무엇을 제한하는지 명시하지 않으면 같은 숫자를 두고 서로 다른 말을 하게 된다.

  1. 응답 대기 상한: 사용자는 30초만 기다린다. 이후 202 Accepted를 받은 작업 ID로 상태를 조회하거나, timeout 후 별도 상태 조회를 한다.
  2. 작업 수행 상한: 해당 시도(attempt)는 지정된 마감 시각을 넘으면 더는 계산을 진행하지 말라는 정책을 갖는다. 실행 코드는 주기적으로 마감 시각을 확인해야 한다.
  3. 실행 소유권 상한(임대): 어떤 WORKER가 독점적으로 확정할 권한을 갖는 시간이 제한된다. 임대가 만료되어 다른 WORKER가 소유권을 얻으면 이전 WORKER는 결과를 확정할 수 없어야 한다.
  4. 전체 서비스 목표: 사용자가 누른 순간부터 결과가 공개되기까지의 시간 목표. 이 목표 위반과 작업의 유효성은 별도다.

마감시각을 저장할 때는 벽시계 시각(복구·관측에 필요)과 프로세스 내부 경과시간 측정용 단조시계(monotonic clock)의 목적이 다르다는 점도 알아 둬. 시스템 시계가 보정되면 벽시계의 ‘30초 전’ 계산은 흔들릴 수 있지만, 여러 재시작에 걸친 DB 임대 만료는 저장된 UTC 시각 등 공유 가능한 시간 기준으로 판단해야 한다. 여러 서버에서는 시계 오차까지 고려한다.

1-3. ‘실패’라는 말은 결과를 못 받은 사람과 작업 자신에게 다르다

클라이언트 timeout = 응답 결과를 알 수 없음(unknown)일 수 있다. 작업 실패 = 더는 실행하지 않거나 성공 조건을 만족하지 못함을 확정한 상태다. 저장 실패 = 트랜잭션이 확정되지 않음일 수 있다. 사용자에게 FAILED를 표시하려면 확인 가능한 근거가 필요하다. 응답을 못 받았다는 이유만으로 job을 FAILED로 바꾸면 나중에 실제 성공한 결과와 충돌한다.

Ailey: 결과를 못 들었다는 것과 실패했다는 건 같지 않아. 상대가 전화를 안 받는다고 해서 약속이 취소됐다고 결론 내릴 수 없는 것과 비슷해. 단, 이 비유와 달리 소프트웨어는 DB의 커밋 흔적과 고유 ID를 통해 사후 확인하도록 설계할 수 있어.

🧱 2. WORKER가 무엇을 소유하는지부터 그려 보자

2-1. 작업의 네 가지 물건: job, attempt, temp, final

사용자가 한 번 노선 생성을 요청한 논리적 작업을 job이라고 부르자. 그 일을 실제로 한 번 계산하려는 실행을 attempt라고 부른다. temp는 계산 과정의 후보 결과이고, final은 검증과 원자적 확정을 통과한 결과다. job과 attempt가 일대일이라는 보장은 없다. 작업을 재시도하면 같은 job에 여러 attempt가 생긴다.

                         한 번의 운영자 의도
                     job J-104 (dataset D7, rule R3)
                                  │
             ┌────────────────────┴────────────────────┐
             ▼                                         ▼
     attempt A1 (epoch=8)                      attempt A2 (epoch=9)
     계산하다 중단됨                           새 WORKER가 재시도
             │                                         │
             ▼                                         ▼
       temp A1의 일부                              temp A2 완성
       공개 금지                                    독립 검증 통과
             │                                         │
             └───────── 확정 권한 없음                ▼
                                                 final P-88
                                                      │
                                             공개 포인터 갱신
                                                      │
                                            구성원 조회 API 노출

이 도식의 epoch는 시도 번호처럼 계속 증가하는 펜싱 토큰(fencing token)이다. 뒤에서 설명하지만 ‘누가 지금 확정할 수 있는지’를 DB가 판정하는 재료다. 임시 결과가 남았다고 해서 그 시도가 살아 있거나 확정 권한이 있는 것은 아니야.

2-2. 저장 장소를 따져야 잔존 상태를 예측할 수 있다

대상 설명과 소유자 프로세스가 죽으면? 공개 조건
브라우저 로딩 상태 브라우저 메모리 화면 새로고침/종료 시 사라짐 없음, 사용자 피드백일 뿐
Python 지역 변수에 있는 후보 경로 작업 실행 프로세스 메모리 사라짐 절대 직접 공개하지 않음
jobs/attempts 행 SQLite 파일의 커밋된 데이터 DB 파일이 보존되면 남음 운영자 상태 API에만 필요한 범위 공개
temp_routes, temp_assignments SQLite의 임시 의미상 스테이징 테이블 커밋돼 있으면 남음. SQL의 세션별 TEMP TABLE과는 다름 최종 사용자에게 공개 금지
별도 JSON 임시 파일 파일시스템 삭제 코드가 실행되지 않으면 남을 수 있음 공개 금지, 디렉터리 관리 필요
final_plans, final_routes, final_assignments 검증 후 확정된 결과 커밋 완료라면 DB에 남음 포인터·버전·상태 조건을 만족할 때만 공개
active_plan 공개 포인터 어떤 결과가 현재 선택된 결과인지 가리키는 DB 행 트랜잭션으로 기록했으면 남음 조회 시 포인터의 유효성 재검사

주의: temp를 Python 변수로만 유지하면 재시작 뒤 흔적이 없으므로 복구할 수 없다. temp를 DB의 일반 테이블에 커밋하면 복구 가능하지만 불완전 데이터를 청소하고 공개를 차단할 책임이 생긴다. SQLite CREATE TEMP TABLE은 연결별 임시 저장이라는 별개 개념이다. 이름이 같아서 혼동하지 말자.

2-3. 원본 요구에 대응시키기

통근버스 예시에서 job은 어느 적용 데이터셋 버전, 어느 날짜 구간, 좌석 정원, 도착 여유 시간을 기준으로 계산하는지 고정해야 한다. 다른 데이터셋을 적용하거나 조건을 바꾸면 기존 job 결과가 그 조건에 맞는 결과인 양 노출되면 안 된다. final 안에는 출퇴근 운행과 배정 모두가 함께 있어야 한다. 운행만 20개 저장되고 구성원 배정은 60%만 저장된 상태를 보여 준다면, 겉으로는 성공처럼 보여도 모든 근무자를 배정해야 한다는 시험 조건에 반한다.

가상 예시로 dataset_version = 'D7', settings_version = 'R3', job_id = 'J-104'라 부르자. 이 ID는 실제 CSV에 있던 값이 아니야. 2026-07-20~2026-08-14라는 원본 제공 기간을 쓸 수 있지만, 특정 근무자 수나 정류장 배정 결과를 여기서 실제 산출했다고 주장하지 않는다.

🔄 3. 상태 머신은 예쁜 진행 표시가 아니라 약속 위반을 막는 울타리다

3-1. 상태는 왜 필요한가

함수가 실행되면 ‘진행 중’, 반환하면 ‘완료’라고만 적는 설계는 다음 경우를 구분하지 못해. 결과 계산은 끝났지만 검증 중일 수 있다. 사용자가 취소를 요청했으나 실제 작업이 계속 실행 중일 수 있다. 검증은 통과했지만 최종 커밋은 실패했을 수 있다. 서버가 죽어 마지막으로 남긴 RUNNING 기록만 존재할 수 있다.

그래서 상태를 임의의 라벨이 아니라 허용된 전이와 조건을 갖춘 상태 머신으로 쓴다. 이 강좌에서의 예시는 다음과 같다.

                 생성 요청
                    │
                    ▼
                 QUEUED ───── 취소 승인 ──────────────> CANCELLED
                    │ 선점(claim)
                    ▼
                 RUNNING ───── 계산 예외/예산 소진 ───> FAILED
                    │  │
       취소 요청 ────┘  │ 후보 결과 생성
           │           ▼
           ▼       VALIDATING ── 검증 실패 ──────────> FAILED
    CANCEL_REQUESTED   │  │
           │           │  └── 취소 요청 ──────────> CANCEL_REQUESTED
           │           │ 검증 통과 + 권한 재확인 + 원자적 확정
           │           ▼
           │       SUCCEEDED
           │
           └── 실행 중단 확인 + 정리/확정 차단 ───────> CANCELLED

추가 경로: RUNNING / VALIDATING에서 lease 만료 → 만료 판정 후
재시도 예산이 있으면 새 attempt로 QUEUED 또는 재선점,
없으면 FAILED. 기존 attempt의 늦은 확정은 거부한다.

QUEUED, RUNNING, VALIDATING, SUCCEEDED, FAILED, CANCEL_REQUESTED, CANCELLED는 학습용 상태 이름의 한 예시야. 실무에서는 RETRY_WAIT, RECOVERING, UNKNOWN 등을 추가할 수 있지만, 상태가 많아진다고 안전해지는 것은 아니다. 각 전이에 선행 조건이 있고, 그 조건을 DB에서 원자적으로 검사해야 안전해져.

3-2. 전이와 권한을 분리한 표

현재 사건 다음 반드시 지켜야 할 조건
QUEUED WORKER가 선점 RUNNING 한 번에 단 하나의 유효 epoch·lease를 부여
QUEUED 사용자가 취소 CANCELLED 아직 실행되지 않은 상태에서 원자적으로 변경
RUNNING 취소 클릭 CANCEL_REQUESTED 클릭 응답은 ‘요청 접수’, ‘종료 완료’가 아님
RUNNING 후보 저장 완료 VALIDATING 후보는 아직 공개 불가
VALIDATING 검증 실패 FAILED 또는 재시도 결정 실패 원인을 기록, 기존 공개 계획 유지
RUNNING/VALIDATING 취소 확인 CANCELLED 같은 epoch의 확정을 금지하고 정리 여부 기록
VALIDATING 검증 통과 및 확정 SUCCEEDED 상태·epoch·lease·취소·입력 버전 확인과 final+pointer 변경을 한 트랜잭션으로
RUNNING/VALIDATING lease 만료 새 attempt 또는 최종 FAILED 이전 WORKER가 살아 있더라도 확정 권한을 잃게 함
SUCCEEDED 늦게 온 취소 요청 그대로 SUCCEEDED 커밋을 과거로 되돌릴 수 없음; 별도 ‘결과 철회’ 작업 필요

‘취소’를 누르는 순간에 이미 확정이 끝났다면 어떻게 될까? 확정 트랜잭션이 먼저 성공했다면 SUCCEEDED가 정답이고, 반대로 취소 상태 변경이 먼저 커밋됐다면 확정을 막아야 해. 두 작업이 동시에 일어나도 DB 커밋 순서에 따라 단 하나의 승자가 정해져야 한다.

3-3. 상태와 사실을 같은 것으로 착각하지 않기

RUNNING이라고 DB에 쓰여 있어도 실제 프로세스는 죽었을 수 있다. CANCEL_REQUESTED라고 쓰여 있어도 WORKER가 아직 신호를 확인하지 않았을 수 있다. SUCCEEDED는 ‘알고리즘이 올바르다’의 증거가 아니다. 독립 검증이 어떤 입력 버전과 어떤 규칙으로 수행됐는지, 그리고 그 근거가 기록됐는지를 확인해야 한다.

따라서 job.status는 최종 진실 그 자체가 아니라, 서비스가 관리하는 내구성 있는 상태 기록이야. 이 기록의 정확성을 위해 상태 전이마다 조건부 UPDATE와 트랜잭션을 사용한다.

⏱️ 4. timeout과 취소의 내부: ‘기다림을 끊는 코드’는 계산을 끊는 코드가 아니다

4-1. Future.result(timeout=...)가 실제 하는 일

Python의 concurrent.futures에서 future.result(timeout=30)은 결과를 최대 30초 기다린다는 뜻이다. 30초가 지나면 기다리는 쪽에서 TimeoutError가 발생한다. 제출된 함수가 실행 중이면 그 함수는 보통 계속 실행한다. 그리고 future.cancel()은 아직 실행 시작 전인 작업을 취소할 수 있지만, 이미 실행 중이라면 False를 반환하고 실행을 끝내지 못한다. 이 차이는 Python 공식 문서에도 명시돼 있다.

# 교육용 개념 예시 — 실제 시험 코드도 아니고 실행 검증한 예제도 아님
from concurrent.futures import ThreadPoolExecutor, TimeoutError
import time

def expensive_calculation():
    time.sleep(60)          # 계산 대신 긴 작업을 흉내 낸 것
    return 'candidate'

pool = ThreadPoolExecutor(max_workers=1)
future = pool.submit(expensive_calculation)
try:
    result = future.result(timeout=1)
except TimeoutError:
    print('기다림만 1초 후 종료')
    print('cancel accepted?', future.cancel())  # 이미 실행 중이라면 False 가능
# 여기서 함수가 자동으로 멈췄다고 결론 내리지 않는다.
# 실제 예제라면 executor 종료/리소스 관리를 별도로 설계한다.

위 코드를 ‘timeout을 걸었으니 서버 자원도 1초만 쓴다’고 설명하면 틀렸어. 스레드가 계속 일할 수 있기 때문이야. 그리고 WORKER라는 이름을 붙였다고 별도 프로세스라는 뜻도 아니다. 하나의 웹 프로세스 안에서 스레드로 작업한다면, 웹 프로세스를 죽일 때 작업도 함께 죽을 수 있다.

4-2. asyncio.Task.cancel()은 강제 정지 버튼이 아니다

비동기 함수(coroutine)는 await 등에서 실행을 다른 작업에 양보한다. task.cancel()은 다음 적절한 실행 지점에서 CancelledError를 전달하도록 요청한다. 취소를 받은 함수가 finally를 실행하고 빠져나올 수 있지만, 이를 잡아 무시하거나, 긴 동기 CPU 계산이 await 없이 이벤트 루프를 붙잡고 있으면 취소 반영이 지연될 수 있다. 더구나 asyncio 태스크 안에서 별도 스레드·프로세스에 계산을 위임했다면 바깥 태스크의 취소가 외부 실행 자체를 종료한다는 보장은 없다.

# 개념 코드 — 실행 미검증, 실제 서비스 도입 전 버전별 확인 필요
import asyncio

async def simulate_work():
    try:
        for _ in range(100):
            await asyncio.sleep(0.1)  # 취소가 반영될 기회
    except asyncio.CancelledError:
        # 연결·임시 자원 정리를 시도한 뒤 취소를 다시 전달
        raise
    finally:
        # 정상 반환이나 예외로 파이썬 제어 흐름이 이곳에 도달하면 실행
        print('cleanup attempted')

async def caller():
    task = asyncio.create_task(simulate_work())
    await asyncio.sleep(0.2)
    task.cancel()
    try:
        await task
    except asyncio.CancelledError:
        print('task ended by cancellation')

이 예시에서 중요한 것은 task.cancel() 다음 줄에 곧바로 ‘취소 완료’라고 기록하지 않고 태스크가 실제로 종료됐는지 기다리고 확인한다는 점이야. 다만 서비스 전체 안전성은 이 함수의 finally가 아니라 DB의 확정 차단 규칙에서 나온다.

4-3. CPU 연산에는 협력적 취소 지점이 필요하다

버스 노선 탐색이 수천 개 조합을 검토한다면 매 반복마다 DB를 조회하는 것은 비싸다. 반대로 단 한 번도 취소를 확인하지 않으면 취소 요청 이후에도 오래 CPU를 쓸 수 있어. 그래서 반복 단위, 묶음 처리 단위, 단계 전환 지점에 협력적 점검을 둔다.

[계산 1묶음] → [취소/마감 점검] → [계산 1묶음] → [취소/마감 점검]
                     │                              │
              취소 발견: 중단                 살아 있음: 다음 묶음
              temp 공개 안 함

점검 주기를 줄이면 중단 응답성이 높아지지만 DB 조회·분기 비용이 증가한다. 늘리면 처리량이 좋아질 수 있지만 취소 이후의 낭비가 커진다. 중단 요청의 빠른 반영과 계산 효율 사이에는 비용 교환이 존재한다. 요청을 확인했다는 로그만으로 취소 완료가 증명되지 않는 것도 기억해.

4-4. 협력적 취소와 강제 종료의 차이

항목 협력적 취소 프로세스 종료 신호 / 강제 종료
누가 멈추나 프로그램이 안전 지점에서 스스로 멈춤 운영체제 또는 관리자가 프로세스에 신호·종료 적용
중간 정리 코드가 실행될 기회가 있다 종료 방식에 따라 정리 기회가 없을 수 있다
응답성 점검 주기와 막힌 호출에 의존 강제 종료는 보통 더 직접적이나 OS·하위 작업 차이 있음
DB 트랜잭션 코드가 명시적으로 롤백 가능 미커밋 트랜잭션은 DB 복구 규칙에 맡겨야 함
temp 파일 코드가 삭제할 수 있음 남을 수 있으므로 재시작 청소가 필요

POSIX 계열에서 SIGTERM은 처리 가능한 종료 신호인 반면 SIGKILL은 프로세스가 처리하지 못한다. Windows는 종료 API와 신호 의미가 다르다. 어떤 환경이든 ‘강제로 죽여도 finally가 반드시 실행된다’고 설명해서는 안 된다. 또한 종료한 PID가 자식 프로세스나 GPU 작업·외부 서비스까지 모두 멈췄는지도 별도로 확인해야 한다.

4-5. finally의 유용함과 한계

finally는 Python의 정상적인 제어 흐름에서 함수가 빠져나갈 때 자원을 정리하려고 사용한다. 파일 핸들 닫기나 스레드 내 상태 되돌리기처럼 중요한 구문이지. 하지만 전원 차단, SIGKILL, 런타임 중단, 프로세스 크래시 등에서는 그 코드가 수행될 기회조차 없을 수 있다. finally 안에서 DB를 업데이트하려다가 네트워크 또는 디스크 오류로 실패할 수도 있어. 그래서 설계할 때는 다음처럼 두 층으로 생각해야 한다.

  • 정상적 중단 시도: finally가 할 수 있는 정리를 최대한 한다.
  • 비정상 중단 이후에도 성립해야 할 불변식: 정리가 한 줄도 실행되지 않았더라도 미검증 결과가 공개되지 않아야 하고, 다른 시도가 재개할 수 있어야 한다.

🧪 5. 다섯 개의 장애 장면을 같은 눈금으로 추적한다

이 절의 시나리오는 모두 가상 구현 사례다. 원본 시험 자료에서 확인되는 운영 요구를 반영했지만 실제 응시자의 제출 시스템이나 CSV 행을 실행·관찰한 결과는 아니다.

먼저 공통 초기 조건을 정한다. final P-70은 앞선 데이터셋·조건으로 검증돼 공개된 기존 계획이고, 새 job J-104는 D7/R3 입력으로 계산하려 한다. temp는 attempt별 커밋된 후보 행으로, 그 자체는 사용자 조회에서 보이지 않는다. active_plan 포인터는 버전 범위를 가진다고 가정한다. 표의 final은 저장된 최종 결과와 그중 현재 공개되는 결과를 구별해서 적는다.

T3–T4 VALIDATING A1 후보 있음 P-88 미공개, 이전 P-70은 저장돼 있음
T6–T7 SUCCEEDED 정리 전에는 남아도 무방 P-88 커밋/포인터 변경; 현재 조건 일치 시 공개

T6이 핵심이다. 먼저 SUCCEEDED를 커밋하고 나중에 노선 테이블에 내용을 넣으면 중간에 읽은 사용자는 비어 있는 성공을 볼 수 있다. final 결과, 현재 포인터, 성공 상태를 하나의 원자적 트랜잭션으로 바꾼다는 것이 이 가상 설계의 확정 원칙이다.

5-2. 검증 실패: 계산된 결과는 존재하지만 운영 계획은 존재하지 않는다

T0~T3  후보 계산과 temp(A1) 저장까지 정상
T4     검증기가 한 근무자의 출근 배정 누락을 발견(가상 오류)
T5     validation_error 기록, job FAILED
T6     temp 격리 또는 정책에 따라 나중에 삭제
시점 job temp final / 사용자 공개
실패 직후 FAILED + 오류 근거 A1 후보는 디버깅 용도로 남을 수 있음 새 P-88 없음, P-70은 보존
정리 이후 FAILED 삭제돼도 실패 근거/요약은 보존 이전 검증 완료 계획 이외에는 노출 없음

원본 시험 요구에서는 근무자 전원에 대한 좌석과 배정이 필수다. 누락자가 하나라도 있으면 ‘대부분 맞았다’고 결과를 내보내서는 안 된다. 오류 메시지에는 job_id, 데이터 버전, 규칙 코드, 위반 건수, 재현 가능한 검증 방법을 포함할 수 있다. 다만 사용자 개인정보나 전체 원본 입력을 불필요하게 로그에 복사하지 않도록 주의한다.

5-3. 선점 직후 죽음: RUNNING은 살아 있다는 증거가 아니다

T0 job J-104 = QUEUED
T1 W1이 DB에 RUNNING/attempt A1/epoch 8/lease_until 커밋
T2 W1 프로세스가 생성기를 실행하기 전에 강제 종료
T3 DB에는 RUNNING이 남음, temp 없음, final 없음
T4 다른 실행 주체의 복구 검사: lease 만료 확인
T5 재시도 예산 확인, 새 attempt A2/epoch 9 선점
T6 A2 계산/검증/확정
시점 job temp final / 사용자 공개
T2 직후 RUNNING, 하지만 W1은 죽음 없음 기존 P-70만 존재
T3 복구 전 겉보기에 영구 진행 중 없음 새 결과 없음
T5 복구 후 새 시도 RUNNING A2가 생성할 예정 기존 결과 유지, 새 결과는 아직 미공개

복구 실행자 자체가 없다면 T4는 일어나지 않는다. 단일 프로세스 웹 서버의 시작 코드에서 스캔할 수도 있고 별도 WORKER의 시작·주기적 스캔에서 수행할 수도 있다. 어느 방식이든 ‘누가 언제 만료 작업을 검색하는가’가 적혀 있어야 해. 단순히 TTL 숫자를 DB에 적는 것만으로 복구가 자동 실행되지는 않는다.

5-4. 저장 중 죽음: ‘몇 행까지 썼나’보다 ‘어느 트랜잭션까지 커밋했나’

두 설계를 나눠 보자. A안은 final_routes에 행을 하나씩 자동 커밋한다. 첫 운행 10개가 들어간 뒤 프로세스가 죽으면 10개가 남을 수 있다. 만약 조회 API가 그 테이블을 그대로 읽는다면 불완전한 노선을 구성원에게 보여 주는 결함이 생긴다.

B안은 temp를 별도로 관리하고, 검증 후 최종 결과·포인터·job 성공 변경을 하나의 트랜잭션에 넣는다. 그 트랜잭션 도중 프로세스가 죽었다면 SQLite의 트랜잭션 복구는 전부 보이거나 전부 보이지 않는 상태를 목표로 한다. 따라서 커밋 전 중단이라면 기존 포인터를 유지하고, 커밋 완료라면 새 포인터까지 일관되게 보인다. 이는 정상적인 SQLite 트랜잭션·저장소 설정과 파일 보존을 전제로 하며, DB 외부 파일·외부 API까지 자동으로 원자화하는 것은 아니다.

위험한 A안
final_routes: R1 [COMMIT] → R2 [COMMIT] → R3 [COMMIT] → 💥
조회: R1,R2,R3만 있는 '반쪽 결과'를 볼 위험

안전한 B안
임시 작업: temp_A1 (여러 번 커밋 가능, 공개 금지)
최종 확정: BEGIN → final 전체 삽입 → pointer 변경 → job 성공 → COMMIT
                     ├──── 💥 COMMIT 전: 새 확정 전체가 보이지 않음
                     └──── 💥 COMMIT 후: 새 확정 전체가 보임
장애 지점 job temp final / 공개
temp 저장 트랜잭션 중 사망 마지막 커밋된 상태 마지막 커밋 분량까지만 남음 새 final 없음
검증 통과 후 확정 트랜잭션 중 사망, 커밋 전 이전 상태(VALIDATING 등) 커밋된 temp는 남음 새 final/포인터 변경이 보이지 않음
확정 커밋 뒤 사망 SUCCEEDED 남을 수 있음 새 final과 pointer가 함께 남음

SQLite에서 한 트랜잭션에 모든 final 레코드를 넣으면 락 유지 시간이 길어질 수 있다. 이때는 보이지 않는 버전의 final을 여러 트랜잭션에 미리 저장하고, 모든 검사 이후 짧은 포인터 활성화 트랜잭션으로 공개하는 대안도 있다. 그러나 이 방식에서는 준비 중인 버전을 읽지 못하게 하는 조건과 정리 정책이 더욱 중요해진다. ‘여러 번 써도 안전하다’는 말은 공개 포인터가 가리키기 전에는 읽히지 않는다는 전제가 있어야 한다.

5-5. 커밋 성공 후 응답 전 죽음: 가장 쉽게 ‘실패’라고 거짓말하는 지점

T0~T5  정상 계산과 검증
T6     SQLite COMMIT 성공 → P-88, SUCCEEDED, pointer 모두 DB에 저장
T7     응답 HTTP 200을 보내기 직전 서버/연결 종료
T8     브라우저는 timeout 또는 연결 오류를 봄
T9     운영자가 같은 요청을 다시 보냄
관찰자 알고 있는 것 아직 모르는 것
브라우저 응답을 받지 못했다 COMMIT이 성공했는지
DB J-104가 SUCCEEDED, P-88과 pointer가 있다 클라이언트가 메시지를 읽었는지
새 요청 처리기 job ID 또는 멱등성 키로 J-104를 조회할 수 있음 키가 없다면 이전 요청과 동일한 의도인지

정답은 T8에서 ‘실패했으니 다시 처음부터 계산’이 아니야. 먼저 같은 idempotency key/job ID로 DB를 조회해서 이미 성공했는지 확인해야 해. 같은 의도라면 성공한 J-104 결과를 재전달할 수 있다. 클라이언트가 HTTP 응답을 반드시 받도록 만들 수는 없지만, 반복 요청이 같은 효과를 내도록 만들 수는 있어.

다섯 시나리오를 한 장으로 합친 잔존 상태 지도

장면 job에 남는 기록 temp에 남는 것 final에 남는 것 현재 사용자에게 새 계획을 보여도 되나?
정상 완료 SUCCEEDED 있을 수 있으나 비공개 새 결과와 포인터가 함께 커밋 예, 현재 입력/조건과 일치하면
검증 실패 FAILED + 위반 근거 후보가 격리돼 남을 수 있음 기존 성공 결과만 아니오, 실패 후보는 금지
선점 직후 죽음 만료된 RUNNING 없음 기존 성공 결과만 아니오, 복구 후 다시 판단
확정 저장 중 죽음 최종 커밋 전 상태 또는 SUCCEEDED 마지막 커밋 상태 전부 없음 또는 전부 있음 커밋/포인터/버전 확인 후에만
커밋 후 응답 전 죽음 SUCCEEDED 있을 수 있음 새 결과 커밋됨 예, 상태 재조회로 확인

여기서 ‘기존 결과 유지’와 ‘현재 결과로 노출’은 구분한다. 원본 시험은 다른 데이터셋 적용 후 재계산 전에는 기존 계산 결과를 새 데이터의 결과처럼 보여 주지 말라고 요구한다. 따라서 이전 P-70이 DB에 남아도 D7/R3 조건의 결과로는 사용하지 않는다.

🧯 6. 왜 ‘죽었는지 확인’만으로는 재시도가 안전해지지 않을까

6-1. 선점, 임대, 심장박동의 관계

claim(선점)은 ‘이 작업은 지금 내가 맡는다’는 권한 획득이다. lease(임대)는 그 권한의 유효 시간을 정한다. WORKER는 살아 있는 동안 heartbeat(갱신 신호)를 통해 임대를 갱신한다. 시간 초과 뒤 새 WORKER가 작업을 이어받을 수 있다. 다만 만료됐다고 이전 WORKER가 정말 죽었다는 뜻은 아니다. 잠시 멈췄거나, GC 중이거나, CPU를 과도하게 사용하거나, DB 접근만 끊긴 상태일 수 있다.

시각           00      10      20      30      40
W1 (epoch 8)   선점 ── heartbeat ── [장시간 멈춤] ────── 다시 깨어남!
DB lease       유효 ── 유효 ──────── 만료
W2 (epoch 9)                          새 선점 ─── 계산 ── 확정
W1의 늦은 결과                                           └─ 확정 거절!

                           왜 거절하나?
           W1이 가진 epoch=8 < DB의 현재 epoch=9

W1이 다시 살아나 내 계산은 맞아라고 주장할 수 있어. 실제로 계산이 맞더라도 최신 데이터셋·조건에 대한 유효한 확정 권한을 잃었기 때문에 결과를 공개하면 안 된다. 이를 막는 수단이 펜싱(fencing)이야.

6-2. 펜싱은 ‘락을 믿는다’가 아니라 ‘저장 순간에 권한을 검사한다’

단순히 lease_until만 두고 W2를 시작하면 W1도 뒤늦게 결과를 저장할 수 있어. epoch를 단조 증가시키고, 저장 트랜잭션에서 jobs.current_epoch == my_epoch인지 확인하면 이전 시도를 막을 수 있다. 비교만 하고 나중에 별도 트랜잭션으로 저장하면 검사 직후 W2가 선점하는 경합이 생기므로 같은 DB 트랜잭션 안에서 검사와 확정이 이루어져야 한다.

가상 예시로 다음 불변식을 두자.

최종 결과를 공개하는 트랜잭션은 job.status == VALIDATING, job.current_epoch == attempt.epoch, job.cancel_requested == false, lease가 유효하고 입력 버전이 확정 대상과 맞을 때에만 커밋할 수 있다.

SQLite의 BEGIN IMMEDIATE처럼 쓰기 트랜잭션을 먼저 획득하는 방식으로 비교와 변경을 직렬화할 수 있다. 그런데 DB에서만 펜싱을 검사하면 DB 밖의 전송 메일, 파일 이동, 외부 API 쓰기까지 막지 못한다. 외부 대상도 펜싱 토큰을 검증하거나 멱등성 키·outbox 소비 규칙을 사용해야 한다. 또 W1이 이미 외부에 부작용을 일으킨 뒤라면 나중의 펜싱은 그것을 과거로 돌릴 수 없어.

6-3. 멱등성과 펜싱은 서로 다른 공격을 막는다

  • 멱등성(idempotency): 같은 운영자 요청이 여러 번 전달되어도 같은 논리적 작업과 효과를 얻도록 한다. 예: 같은 요청 키로 동일 job을 재조회한다.
  • 펜싱(fencing): 같은 job에 대해 서로 다른 시도가 겹쳐도 오래된 실행 주체가 최신 결과를 확정하지 못하도록 한다. 예: epoch 8의 COMMIT은 epoch 9 선점 이후 거절한다.
  • 원자적 확정(atomic publication): 결과와 공개 상태가 찢어져 보이지 않게 한다.
  • outbox: DB 커밋과 외부 알림이 서로 별개의 시스템일 때, 커밋과 함께 ‘보낼 사건’을 기록하고 나중에 안전하게 전달할 수 있게 한다. 전송은 중복될 수 있으므로 수신자 멱등성도 필요하다.

세 개를 섞어 ‘재시도하면 한 번만 실행된다’고 주장하면 안 돼. 실제 계산이 여러 번 일어나더라도 최종 공개 효과는 유일하게 만들 수 있어. 이것이 흔히 추구하는 실용적인 보장이야. exactly once execution과 effectively once effect는 다르다.

6-4. 재시도 예산 없이는 정상 서비스도 죽을 수 있다

재시도는 무조건 좋은 일이 아니야. 잘못된 CSV 참조, 불가능한 좌석 제약, 코드 버그 같은 결정적 실패를 계속 재시도하면 DB 부하와 CPU 사용량만 늘어. 일시적 DB 잠금이나 순간적인 프로세스 종료는 재시도가 의미 있을 수 있어. 실패를 분류하고 max_attempts, 총 경과시간 상한, 간격 증가(backoff), 약간의 무작위 지연(jitter), 운영자 개입 기준을 정해야 한다.

실패 유형 바로 재시도? 이유
CSV 필수 열 누락·참조 무결성 오류 보통 아니오 입력이 바뀌지 않으면 결과도 같음
검증기가 제약 위반 발견 보통 아니오; 생성 알고리즘 수정 필요 같은 결정적 계산 반복은 무의미
짧은 SQLite 잠금 경합 제한적 재시도 가능 시간이 지나면 해결될 수 있음
WORKER 프로세스 우발 종료 재시도 예산 내에서 가능 새로운 시도가 완주할 수 있음
외부 비가역 작업 이미 수행 여부 불명 곧바로 재호출 금지 부작용 중복 위험, 먼저 상태 대조

지나친 재시도는 장애 상황의 자원을 더욱 압박한다. 반대로 재시도 예산이 너무 적으면 일시적 문제에도 작업이 빨리 포기된다. 요구하는 복구 속도와 부하, 오류 유형에 따라 선택의 손실을 설명해야 해.

request_key는 운영자가 한 번 누른 요청의 동일 의도 식별자로 취급한다. 입력 데이터, 조건, 작업 범위가 다른 요청을 같은 키로 재사용해서는 안 된다. 기존 키에 다른 입력 지문이 들어오면 409 Conflict 같은 충돌 정책을 검토할 수 있다. 키가 언제 생성되고 얼마나 보관되는지도 계약에 포함된다. 또 final_plans가 실제 운행과 배정의 완전성을 자동으로 증명하는 것은 아니며, 검증기와 세부 DB 제약이 필요하다.

7-2. 선점은 ‘읽고 나중에 쓰기’로 하면 위험하다

두 WORKER가 동시에 QUEUED를 읽고 각자 일을 시작할 수 있어. 따라서 선점은 조건부 변경으로 해야 한다. 예를 들어 트랜잭션 안에서 status='QUEUED', cancel_requested=0인 경우에만 RUNNING으로 바꾸고 current_epoch를 증가시킨다. 변경 행 수가 1인지 확인해야 해. BEGIN IMMEDIATE를 사용하면 SQLite에서 쓰기 트랜잭션 시작 단계의 충돌을 조절할 수 있어.

# 의사 코드 — SQL 트랜잭션과 예외 처리를 보여 주는 설계 예시
# 실제 sqlite3 실행기·busy_timeout·시간 처리·동시성 테스트는 별도 필요

def claim_job(db, job_id, worker_id, now_utc, lease_end_utc):
    db.execute('BEGIN IMMEDIATE')
    try:
        changed = db.execute('''
            UPDATE jobs
               SET status='RUNNING',
                   current_epoch=current_epoch+1,
                   attempt_count=attempt_count+1,
                   lease_until=?, updated_at=?
             WHERE job_id=? AND status='QUEUED' AND cancel_requested=0
        ''', (lease_end_utc, now_utc, job_id)).rowcount
        if changed != 1:
            db.rollback()
            return None
        epoch = db.execute(
            'SELECT current_epoch FROM jobs WHERE job_id=?', (job_id,)
        ).fetchone()[0]
        db.execute('''
            INSERT INTO attempts(job_id,epoch,worker_id,started_at)
            VALUES(?,?,?,?)
        ''', (job_id, epoch, worker_id, now_utc))
        db.commit()
        return epoch
    except BaseException:
        db.rollback()
        raise

이것은 QUEUED 선점 경로만 보여 준다. 만료된 RUNNING을 다시 선점하는 로직은 별도 조건부 전이로 작성해야 한다. 재선점 시에도 epoch를 올리고 새 임대와 시도를 기록해야 하며, 기존 WORKER의 갱신과 충돌하지 않게 해야 한다.

7-3. 확정은 ‘검증 후 한 번 더 권한 검사’가 필요하다

생성 결과는 오래 걸려 나온다. 검증 중에도 사용자가 취소할 수 있고, lease가 만료되며, 데이터셋이 바뀔 수 있다. 따라서 검증이 끝났다고 단순 INSERT로 확정해서는 안 된다. 아래는 검증기가 별도 계산 결과를 이미 확인했고 그 검증 내용이 immutable staging snapshot/해시로 연결되었다는 전제의 의사 코드다.

# 의사 코드 — 실행 미검증, 실제 사용 전 SQL·트랜잭션·입력 불변성 점검 필요

def publish_plan(db, job_id, my_epoch, expected_input, expected_settings,
                 plan_id, verified_digest, now_utc):
    db.execute('BEGIN IMMEDIATE')
    try:
        row = db.execute('''
            SELECT status, current_epoch, cancel_requested, lease_until,
                   input_version, settings_fingerprint
              FROM jobs WHERE job_id=?
        ''', (job_id,)).fetchone()
        if row is None:
            raise RuntimeError('job missing')
        status, epoch, cancel, lease_end, inp, cfg = row
        if not (status == 'VALIDATING' and epoch == my_epoch
                and cancel == 0 and lease_end > now_utc
                and inp == expected_input and cfg == expected_settings):
            raise RuntimeError('stale/expired/cancelled attempt')

        # 중요: 공개 범위의 현재 적용 데이터/조건과도 비교해야 함.
        # 이 예시는 그 테이블과 검사 쿼리의 상세를 생략함.
        assert_active_input_and_settings_match(db, inp, cfg)
        assert_staging_digest_still_matches(db, job_id, my_epoch, verified_digest)

        # 검증된 staging snapshot으로부터 전체 확정 레코드를 같은 트랜잭션에 생성
        insert_final_plan_and_all_rows(db, plan_id, job_id, inp, cfg, verified_digest)
        update_active_pointer(db, plan_id, inp, cfg)
        db.execute('''
            UPDATE jobs SET status='SUCCEEDED', final_plan_id=?, updated_at=?
             WHERE job_id=? AND status='VALIDATING' AND current_epoch=?
               AND cancel_requested=0
        ''', (plan_id, now_utc, job_id, my_epoch))
        # 실제 구현은 위 UPDATE의 rowcount == 1도 확인해야 함.
        db.commit()
    except BaseException:
        db.rollback()
        raise

이 코드는 ‘복사해서 실행하면 끝나는 완성 코드’가 아니야. 예컨대 lease_end > now_utc는 UTC ISO8601 정규화처럼 비교 가능한 저장 형식을 전제한다. verified_digest는 내용 검증 없이 문자열만 저장하면 아무 안전성도 주지 못한다. assert_active_input_and_settings_match를 생략하면 오래된 데이터 기준 결과가 최신 포인터가 될 수 있다. 한 트랜잭션에서 모두 삽입할 때의 잠금 시간도 측정해야 한다.

7-4. 공개 API의 마지막 방어선

운영자 job 상태 API는 RUNNING, FAILED, 검증 오류를 보여 줄 수 있어. 그러나 구성원 노선 조회와 JSON 내보내기는 오직 현재 적용 데이터 버전 및 요청 조건에 맞고, 검증 후 확정된 plan만 읽어야 한다.

-- 공개 대상 선택의 원리를 보여 주는 개념 쿼리(컬럼·테이블 보완 필요)
SELECT p.plan_id
  FROM active_plan AS a
  JOIN final_plans AS p ON p.plan_id = a.plan_id
  JOIN jobs AS j ON j.job_id = p.job_id
 WHERE a.scope_id = :scope
   AND a.input_version = :current_input_version
   AND a.settings_fingerprint = :current_settings
   AND p.input_version = a.input_version
   AND p.settings_fingerprint = a.settings_fingerprint
   AND j.status = 'SUCCEEDED';

한 요청에서 공개 포인터와 계획의 여러 행을 따로 조회하면 중간에 다른 트랜잭션이 포인터를 바꿀 수 있다. 동일한 읽기 트랜잭션/스냅샷에서 메타데이터와 실제 운행·배정을 함께 조회하도록 하자. 버전 일치 실패 시 ‘현재 조건에 맞는 계획 없음, 재계산 필요’라고 말한다. 이는 결과를 삭제한다는 뜻이 아니다.

7-5. SQLite에서 주의할 현실적 경계

SQLite는 작은 서비스의 트랜잭션과 내구성 있는 저장에 유용하지만, 한 시점에 쓰기 작업이 직렬화된다는 운영상 특성이 있어. 오래 걸리는 계산 내내 쓰기 트랜잭션을 붙잡으면 다른 상태 업데이트나 조회와 충돌하기 쉽다. 계산은 가급적 DB 트랜잭션 밖에서 수행하고, temp 쓰기와 final 확정은 적절한 작은 트랜잭션으로 분리한다. WAL 모드를 사용해도 ‘여러 쓰기 트랜잭션이 무제한 병렬’이 되는 건 아니다. busy_timeout, 외래키 활성화, 적절한 동기화 설정, DB 파일을 보존하는 볼륨, 마이그레이션과 백업 정책이 중요하다.

SQLite의 원자적 커밋은 동일 DB 트랜잭션의 일관성을 말한다. 데이터베이스 파일이 컨테이너의 일시적 파일시스템에 있고 재생성 때 삭제된다면, 트랜잭션이 아무리 정확해도 데이터가 남지 않는다. 또한 결과 JSON을 DB 밖 파일로 쓰고 DB 포인터만 커밋하면 둘은 자동 원자적으로 묶이지 않는다. 파일 방식은 임시 파일 작성 → flush/fsync 고려 → 같은 파일시스템 내 원자적 이름 교체 → DB 참조 순서 같은 별도 설계가 필요하고, 파일/DB 간 장애 구간을 완전히 없애기 어렵다.

🔁 8. 복구란 ‘다시 시작하기’가 아니라 미완료 작업의 의미를 재판정하는 것이다

8-1. 재시작 시 가장 먼저 확인할 세 가지

서버가 켜질 때 해야 할 일은 무조건 jobs를 삭제하고 초기 데이터를 다시 넣는 일이 아니야. 이미 존재하는 운영 기록을 읽어서 아직 처리할 작업과 만료된 시도를 재판정하는 것이 복구다.

[서비스 시작]
      │
      ▼
DB 파일 열기/스키마 존재 확인 ─ 없으면 최초 초기화 경로
      │ 존재
      ▼
무결성·마이그레이션 검사 → 공개 포인터와 final 일치 확인
      │
      ▼
QUEUED / CANCEL_REQUESTED / 만료된 RUNNING·VALIDATING 찾기
      │
      ├── QUEUED               → 처리 주체에 재전달
      ├── CANCEL_REQUESTED     → 실행/확정 여부 조사 후 안전하게 종결
      ├── lease 만료           → 새 epoch, 예산 내 재시도 또는 FAILED
      ├── SUCCEEDED           → final/포인터 검증 후 그대로 보존

여기서 ‘만료’를 판단할 때 단지 updated_at이 오래됐다는 이유만으로 실패 처리하면, 오래 걸리지만 정상 작동 중인 작업을 오인할 수 있다. 명확한 lease와 갱신 프로토콜이 필요하다. 애초에 lease가 없는 간단한 단일 프로세스라면 프로세스 생존 상태와 작업 재시작 정책을 이용한 보수적인 복구가 대안이지만, 여러 프로세스가 생기면 같은 방식을 그대로 확장할 수 없다.

8-3. 재기동 복구의 경쟁 조건

서버가 두 번 시작되거나 WORKER가 둘이면, 두 복구 실행자가 동시에 만료 job을 발견할 수 있다. 그래서 복구 스캔에서 ‘발견’과 ‘선점’을 별개로 처리한다. 발견은 중복될 수 있지만, 실제 재선점은 조건부 UPDATE로 한 명만 성공해야 한다. 취소 요청과 재선점도 경쟁하므로 취소 플래그와 epoch 조건을 함께 확인한다.

🧰 9. 별도 WORKER가 없어도 설계는 가능한가

원본 시험은 별도 프로세스를 필수로 지정하지 않는다. ‘WORKER가 종료되면?’이라는 복기 질문만으로 사용자 제출물에 별도 WORKER가 있었다고 결론 내릴 수도 없어. 구현 선택을 구분해 보자.

구조 계산을 누가 수행하나 timeout/취소 능력 프로세스 종료 시 적합한 조건과 포기하는 것
동기식 HTTP 처리 웹 요청 처리 스레드/프로세스 요청 대기 timeout은 계산 중단과 다름 웹 프로세스와 계산이 함께 중단될 수 있음 매우 짧은 계산에 단순; 긴 요청·재시작 복구 취약
웹 프로세스 내부 백그라운드 태스크/스레드 같은 프로세스의 실행 단위 협력적 취소 가능; 스레드 강제 종료 어렵다 웹 재시작에 휘말림 빠른 프로토타입; 내구 큐·복구 루프 별도 구현 필요
웹 서버가 자식 프로세스 실행 별도 자식 PID 신호·종료·시간 상한 제어 가능 부모/자식 관계와 고아 프로세스 관리 필요 CPU 작업 격리; 실행 관리·로그·IPC 복잡
상주 별도 WORKER + DB 큐 전용 프로세스가 DB 작업 선점 lease·epoch·협력 취소·재시도 구현 가능 다른 WORKER/재시작이 복구 복구와 확장성 개선; 운영 비용 증가
여러 서버 + 공유 DB/큐 여러 서버와 WORKER 분산 경합·중복 실행·시계 오차 대처 필요 한 서버 장애에서 다른 서버가 계속할 수 있음 가용성 증가 가능; 공유 스토리지·펜싱·외부 부작용 관리 강화

9-1. ‘별도 WORKER 없음’의 정직한 답변

‘제가 만든 시스템은 별도 WORKER가 아니라 HTTP 요청 내부에서 생성기를 동기적으로 호출합니다. 따라서 요청이 끊겨도 계산이 자동 중단된다고 보장할 수 없고, 서버 프로세스가 종료되면 실행 중 계산 상태는 사라질 수 있습니다. DB에 최종 커밋한 결과는 보존되지만, 메모리에만 있던 후보는 복구할 수 없습니다. 현재 구현에서 중단 복구는 충분히 검증되지 않았고, 개선한다면 DB 기반 job 상태·임대·재시도·확정 포인터를 도입하겠습니다.’

이런 설명은 별도 WORKER를 ‘있었던 것처럼’ 꾸며 내는 것보다 정확해. 단, 실제 자신의 코드에서 무엇이 구현됐는지 확인한 뒤 그 부분만 구현 사실로 말해야 한다. 위 문장은 가상 구현의 방어 답변 예시다.

9-2. 단일 서버에서도 ‘동시 실행’은 생긴다

서버가 한 대라고 해서 요청이 한 번에 하나만 오는 것은 아니야. 같은 사용자가 두 번 누르거나, 브라우저가 재전송하거나, 두 브라우저가 동시에 접속하거나, 웹 서버가 스레드 여러 개를 사용할 수 있다. 따라서 SQLite 단일 서버에서도 멱등성 키와 조건부 전이, 원자적 확정이 의미 있다. ‘서버가 하나니까 경쟁 조건은 없다’는 주장은 틀리다.

9-3. 여러 서버에서 약해지는 가정

한 컴퓨터의 프로세스 메모리에 저장한 is_cancelled 변수는 다른 서버에서 보이지 않는다. 한 서버의 로컬 SQLite 파일은 다른 서버의 같은 데이터가 아니야. 공유 파일시스템 위 SQLite의 잠금·장애 의미는 배포 구성에 민감하므로, 여러 서버가 동시에 쓰는 일반적인 분산 서비스에서는 서버형 DB나 적절한 공유 데이터 저장소를 검토하는 편이 낫다. 여러 서버의 시계 오차, 네트워크 단절, 동일 작업 중복 실행이 생긴다면 lease만으로 ‘오직 한 실행’은 보장하지 못한다. 늦게 돌아온 시도의 확정을 거절하는 펜싱이 중요해진다.

🧾 10. outbox와 ‘알림은 보냈지만 DB에는 없다’ 문제

이 수업의 중심은 노선 확정이지만, 면접에서 ‘완료되면 운영자에게 알림도 보낸다면?’이라는 추궁을 받을 수 있어. 트랜잭션 안에서 DB 결과를 커밋하고, 그 다음 외부 메일을 전송한다고 하자.

문제 A: 메일 먼저 발송 → DB 커밋 실패
사용자에게 '완료' 알림 도착, 실제 확정 결과 없음

문제 B: DB 먼저 커밋 → 메일 발송 전 프로세스 종료
결과는 존재하지만 완료 알림 없음

둘을 해결하려고 DB 트랜잭션을 연 채 외부 메일을 보내도, 메일 시스템은 SQLite의 COMMIT/ROLLBACK에 참여하지 않아서 한 번에 확정할 수 없어. outbox 패턴은 final + SUCCEEDED + outbox_event를 같은 DB 트랜잭션에서 커밋한다. 별도 발송 주체가 아직 보내지 않은 이벤트를 읽고 전송한다. 보내고 난 뒤 ‘전송 완료’를 표시하기 전에 죽으면 중복 발송할 수 있으므로 수신자·이벤트 고유 키를 통해 중복을 처리해야 한다.

이 시험의 노선 JSON 다운로드가 DB 상태를 읽어 즉시 내려주는 구조라면 외부 알림용 outbox는 반드시 필요하지 않을 수 있다. 원본 시험이 outbox를 요구했다고 말하지 말자. 여기서는 DB를 벗어난 부작용이 생길 때 원자성의 경계가 어디인지 설명하기 위한 연결 개념이다.

🔬 11. ‘복구된다’를 증명하려면 어디를 강제로 끊고 무엇을 확인할까

11-1. 실행 보고서보다 중요한 관찰 가능한 증거

AI가 ‘에러 처리를 구현했다’고 말해도 그것만으로 확인된 것은 없어. 적어도 코드 경로, 상태 변경, DB 잔존 데이터, 사용자 조회 결과, 재시작 후 상태를 나란히 확인해야 해. 특히 실패 시점을 임의로 만들 수 있는 장애 주입(fault injection)이 유용하다. 이는 테스트용 플래그로 특정 단계에서 예외를 내거나 자식 WORKER 프로세스를 종료하는 방식일 수 있다. 운영 환경에 무분별한 강제 종료 코드를 남겨 두어서는 안 된다.

11-3. 눈으로 확인할 수 있는 SQL 점검 예시

-- 미실행 점검 쿼리. 실제 테이블·컬럼명에 맞춰 수정한다.
SELECT job_id, status, current_epoch, cancel_requested,
       attempt_count, lease_until, final_plan_id, last_error_code
  FROM jobs ORDER BY created_at DESC;

SELECT job_id, epoch, worker_id, started_at, ended_at, stop_reason
  FROM attempts WHERE job_id = :job_id ORDER BY epoch;

SELECT job_id, epoch, COUNT(*) AS staged_routes
  FROM staging_routes WHERE job_id = :job_id GROUP BY job_id, epoch;

SELECT p.plan_id, p.job_id, j.status, p.input_version, p.settings_fingerprint
  FROM final_plans p JOIN jobs j ON j.job_id = p.job_id
 WHERE p.job_id = :job_id;

SELECT * FROM active_plan WHERE scope_id = :scope_id;

이것만으로 좌석·이동시간·배정 제약까지 검증되지는 않아. 별도로 확정 JSON이 실제 적용된 근무표와 전체 조건을 충족하는지 독립 검증해야 해. 예를 들면 날짜별 WORK 구성원과 두 방향 배정 집합을 비교하고, 각 운행의 최대 구간 탑승 수를 재계산하며, travel_times.csv를 기준으로 인접 정차 시각 차이를 확인한다. 외부 지도 API 결과를 대신 사용하면 원본 과제의 이동시간 검증 기준과 어긋난다.

11-4. 시험 응답에서 구분할 네 가지 주장

  1. 설계했다: 도식과 코드 초안이 존재한다.
  2. 구현했다: 실행 경로에 실제 코드가 들어 있다.
  3. 테스트했다: 어떤 입력·장애 지점·명령으로 무엇을 관찰했는지 증거가 있다.
  4. 보장한다: 테스트 범위를 넘어 어떤 환경·실패 모델에서 불변식이 성립하는지 논리와 저장소 계약을 설명할 수 있다.

예컨대 try/finally만 넣었다면 ‘정상 제어 흐름에서 정리를 시도한다’는 주장을 뒷받침할 수 있어도, ‘프로세스를 강제 종료해도 항상 임시 파일이 삭제된다’는 주장을 뒷받침할 수 없어.

마지막 인과 고리

서비스가 안전하게 ‘멈춘다’는 것은 계산을 즉시 죽이는 마술이 아니다. 요청의 기다림을 제한하고 → 실제 계산의 중단 가능 지점을 설계하고 → 취소 요청이 확정과 경쟁할 때 단일 승자를 정하고 → 프로세스가 죽어도 DB에 남은 증거로 복구하고 → 재시도하는 오래된 시도의 확정을 막고 → 끝내 검증된 버전의 결과만 공개하는 것이야. 이 고리를 설명할 수 있다면 ‘30초 timeout을 넣었습니다’보다 훨씬 정확하게 자신의 시스템을 설명할 수 있어.
