🧩 1. 네 질문은 사실 하나의 질문이다: 무엇을 믿어도 되는가?

운영자가 화면에서 ‘노선 생성’을 눌렀다고 상상해 보자. 화면에 ‘완료’가 떴다. 이제 그 노선을 구성원에게 보여 줘도 될까? 아직은 알 수 없다. 버튼 클릭은 요청이 접수되었다는 뜻일 수 있고, 계산이 끝났다는 뜻일 수 있고, 계산된 결과가 제약을 통과했다는 뜻일 수도 있다. 세 사건은 서로 다르다.

통근버스 서비스의 최종 약속은 특정 색의 화면이나 특정 알고리즘 이름이 아니다. 해당 기간에 실제 근무하는 모든 사람에게 출근과 퇴근 운행이 각각 한 번 배정되고, 모든 운행이 정원과 시간 조건을 만족하며, 현재 적용된 데이터와 운영 조건에 대응하는 결과만 조회·내보내기된다는 것이다. 이 약속은 어느 한 컴포넌트의 ‘성공’ 로그보다 크다.

[시험 원문]은 평일 근무일별 생성, 기본 45석, 출근 시작 20분 전 도착, 퇴근 종료 10분 후 출발, 이동시간의 travel_times.csv 사용, 데이터셋 7종의 선택·검증·적용, 입력 오류 시 기존 데이터와 결과 유지, 두 역할의 접근 분리, JSON 내보내기, DB 지속성·재시작·Dockerfile·헬스체크 등을 요구한다. 기술 스택은 자유이며 특정 프레임워크, WORKER 구조, 생성기/검증기 분리를 강제했다고 확인되는 것은 아니다.

[복기]의 네 질문을 이 약속에 대입하면 다음과 같이 읽힌다.

📝 2. 먼저 PRD에서 ‘좋은 계획’과 ‘반드시 지켜야 할 약속’을 분리하자

왜 바로 코드를 쓰면 서로 다른 정답을 만들까?

가령 개발자는 ‘과거 통근버스 이용자가 60%이니 1,500명 중 900석만 마련하자’고 생각할 수 있다. 비용을 줄이는 데는 그럴듯하다. 그러나 [시험 원문]은 과거 이용률로 배정 인원을 줄이지 말고 당일 근무자 전원의 좌석을 확보하라고 정했다. 겉으로 좋은 최적화가 문제의 정의를 어긴 것이다.

PRD(Product Requirements Document)는 “무엇을 왜 만들어야 하며 무엇을 만족해야 완료인가”를 합의하는 문서다. 여기서 핵심은 문서 제목보다 의사결정의 출처를 보존하는 것이다. 설명 가능한 서비스에는 적어도 다음 세 층이 필요하다.

  • 업무 사실·제약: 원문에 확정된 사실. 예: 평일 근무자 양방향 정확히 한 번 배정, 45석 기본값, 방향별 소요시간.
  • 해석이 필요한 조건: 원문만으로 단일 해석이 어려운 부분. 예: 동률인 정류장 후보를 어떤 원칙으로 선호할지, 이용 편의 기준에서 최대 허용 접근거리의 업무 의미. 업무 DM 담당자에게 질문하고 답을 기록할 영역이다.
  • 구현 선택: SQLite를 쓸지, 계산을 백그라운드에 둘지, 어떤 휴리스틱을 적용할지. 담당자가 정답을 대신 주는 층이 아니라 개발자가 비용과 위험을 책임지는 층이다.

아래는 확인과 가정을 섞지 않기 위한 작은 PRD 조각이다.

ID 요구/결정 출처·상태 인수 조건(관찰 가능한 결과) 추적할 구현/검사
R-01 근무자에게 출근·퇴근 각각 한 번 배정 시험 원문 선택한 각 평일에 WORK인 사람의 각 방향 배정 수가 정확히 1, OFF는 0 일정 조인·배정 UNIQUE·독립 집합 비교
R-02 차량별 구간별 정원 준수 시험 원문 모든 운행의 매 구간 탑승 인원 ≤ 적용된 정원 구간별 승하차 누적 검사
R-03 시간표가 방향별 이동시간 및 근무시간 준수 시험 원문 정류장 일시 증가, 각 이동 ≥ CSV의 방향별 분, 출근/퇴근 시각 조건 통과 Validator의 시간 계산
R-04 7개 CSV 묶음이 유효할 때만 적용 시험 원문 하나라도 오류면 적용 버전/결과 불변, 사용자에게 구체 오류 데이터셋 검증·적용 트랜잭션
R-05 품질 개선 기준 수립 시험 원문 + 설계 결정 필요 유효한 해끼리 기준선 대비 지표 보고, 제약 위반은 탈락 목적함수·기준선·품질 실험
D-01 최단 정류장 접근거리 우선 가상 선택, 담당자 확인 전 평균/상위 분위 거리 측정 및 선택 이유 기록 거리 계산·편의 지표
D-02 별도 WORKER 사용 가상 구현 선택 요청 수락 후 상태 조회, 장애 시 복구 규약 확인 job 처리·lease/timeout 검사

인수 조건은 ‘성능 좋게’ 같은 소망이 아니라, 어떤 입력을 주었을 때 어떤 관찰로 합격/불합격을 결정하는가를 말한다. “PRD를 작성했다”는 말만으로 요구사항 검증이 끝나지 않는다. 요구 ID가 코드 경로와 테스트 증거까지 이어져야 요구 추적성(traceability)이 생긴다.

원문 문장(R-01) ──► PRD/인수조건 ──► 계산 모듈 ──► 독립 검증 규칙
       │                  │                  │                  │
       └──► 담당자 확인 기록          └────► 결함/테스트 ID ────► 증거

끊긴 화살표가 있으면 “요구했으나 구현/검증 위치를 모르는 상태”다.

담당자에게 무엇을 물어야 하나?

“어떤 DB를 쓰면 좋을까요?”는 업무 담당자가 답할 질문이 아니다. 대신 “도보 접근 편의는 평균 거리보다 최장 거리의 제한을 더 중시하나요? 특정 직군·시간대의 배차 우선순위가 있나요?”처럼 운영 의미가 결과를 바꾸는 질문을 해야 한다. 답이 없다면 ‘담당자 확인’이라고 적지 말고 미확인 가정으로 표시한다. 정답이 확정되지 않은 품질 목표는 실험 가능한 가정으로 취급하되, 명시된 정원·시간 제약을 완화하지 않는다.

첫 번째 잘못된 대답

“PRD가 있으니 요구는 모두 검증됐습니다.”

베일리: “문서가 한 사람을 버스에 태워 주나? OFF인 사람이 배정된 결과를 내보내도 PRD 파일이 있으면 통과인가?”

아니지. 문서는 약속의 출처, 프로그램은 약속의 수행, 테스트/증거는 약속의 확인이다. 세 층을 구분해야 다음 질문에서 ‘무엇을 실제로 확인했는가’를 답할 수 있다.

🧱 3. 입력 검증: ‘CSV가 읽힌다’와 ‘계획에 써도 된다’의 거리

왜 검증은 한 번의 if가 아닐까?

입력은 파일 하나가 아니라 서로 참조하는 일곱 파일이다. 예를 들어 work_schedule.csv의 emp_id가 employees.csv에 없으면 날짜 형식은 맞아도 업무적으로 계산할 사람이 없다. travel_times.csv에 필요한 방향의 시간이 없으면 노선 시간표 계산이 막힌다. 근무시간대는 존재해도 그 직원의 소속 사업장과 맞지 않으면 잘못된 배정이 나올 수 있다.

검증을 세 문으로 나눠 보자.

문 질문 통과해도 남는 위험
1. 형식·스키마 CSV 파싱, 필수 열, 타입, 날짜/시각, 숫자 범위, 중복 키가 적절한가? 존재하지 않는 ID 참조는 여전히 가능
2. 참조·관계 emp_id, site_id, shift_code, stop_id가 올바른 테이블과 연결되는가? 필요한 방향별 travel time이 있는가? 근무자 전원 배정 같은 업무 규칙은 아직 미검증
3. 업무·계획 가능성 날짜별 WORK/OFF, 기간, 시간대 정합성과 노선 가능성을 판단할 수 있는가? 실제 생성 결과가 모든 제약을 만족하는지는 별도 검사 필요

검증 책임도 둘로 나뉜다. 애플리케이션은 ‘어떤 파일의 어떤 행이 왜 잘못됐는지’ 사용자에게 설명하고 여러 파일 사이의 의미를 검사한다. DB 제약은 저장된 관계가 위반되지 않도록 2차로 보호한다. NOT NULL, UNIQUE, FOREIGN KEY, CHECK를 쓰더라도 외래키 활성화와 스키마 적합성을 확인해야 하며, 복잡한 ‘해당 근무일의 전원 배정’은 단순 단일 행 CHECK만으로 충분하지 않다.

[준비된 7개 CSV 묶음 A] ── 읽기/파싱 ──► [필수 열/형식]
                                              │
                                              ▼
                                     [ID 참조/관계]
                                              │
                                              ▼
                                     [업무 조건/완전성]
                                       │            │
                                     실패           통과
                                       │            │
                         [행/열/사유 진단]       [새 버전 후보]
                                       │            │
                           기존 적용 유지        ▼
                                           [적용 트랜잭션]
                                                  │
                                        dataset_version + 1
                                                  │
                                    과거 결과는 새 결과로 표시 금지

‘유효성 검증’과 ‘적용’ 사이에 데이터가 바뀌면?

이것이 검사 시점과 사용 시점의 차이(TOCTOU)다. 7개 CSV를 검증한 뒤 다른 파일을 다시 읽어 적용한다면, 검증한 바이트와 사용한 바이트가 다를 수 있다. 한 가지 설계는 준비된 CSV의 바이트를 읽어 스냅샷을 고정하고, 파일별 해시와 묶음 버전 ID를 기록한 다음, 그 스냅샷으로만 검증·적용하는 것이다. 해시는 ‘같은 내용인지 비교하는 식별 정보’이지, 데이터의 업무적 정당성을 보증하는 마법이 아니다.

다음은 독립 감사가 가능한 가상 검증 기록 형식이다. 실제 시험에서 작성된 파일이 아니다.

{
  "dataset_candidate": "candidate-B",
  "files_expected": 7,
  "manifest_sha256": "<실제 해시를 계산한 경우에만 기록>",
  "status": "REJECTED",
  "errors": [
    {"file": "work_schedule.csv", "row": 42,
     "column": "emp_id", "code": "UNKNOWN_EMPLOYEE",
     "message": "employees.csv에 존재하지 않는 참조"}
  ],
  "applied_version_before": 12,
  "applied_version_after": 12
}

행 42와 버전 12는 예시 수치다. 실제 CSV에서 발견했다는 뜻이 아니다.

범위 밖과 다른 계층을 어떻게 정직하게 말할까?

  • 실제로 검사한 범위: 코드와 테스트가 확인되어야만 ‘검사했다’라고 말한다. 예시로 스키마/참조 검사를 설계할 수는 있지만 실제 구현을 단정하면 안 된다.
  • 계산 뒤 검사할 범위: 입력 정합성이 통과해도 route_id별 승차/하차 순서, 정원, 도착 시각, 날짜별 정확히 한 번 배정은 결과 Validator의 몫이다.
  • DB의 책임: 기본키·외래키·유일성 등 저장 무결성을 보조하되, 의미 검증의 전부는 아니다.
  • 제외된 범위: [시험 원문]의 실제 지도 API, GPS, SSO, 실제 배포, 운행 비용/단가 산정 등은 별도 요구가 아니었다. ‘미구현’과 ‘원래 범위 밖’은 구분해야 한다.
  • 확인 불가: 제출 코드가 없으므로 특정 규칙을 실제 구현하거나 특정 오류를 재현했다고 말할 근거가 없다.

제3자가 볼 파일·명령·상태는 무엇인가?

검증 결과가 “제 노트북에서는 됐어요”에 머무르면 재현이 불가능하다. 시험 제출물에서 확인되는 파일 이름인 HOW_TO_RUN.md, AI_COLLABORATION.md, Dockerfile, .env.example, 원본 README.md의 보존과 입력 데이터 생성/보관 방법은 확인 대상이다. 아래 명령은 실행 가능한 형태를 가정해 설계한 인터페이스 예시일 뿐, 실제 제출물에 존재한다고 확인되지 않았다.

# [설계 예시 — 구현된 경우에만 유효] 제3자 재현 경로
python -m app.validate_dataset --dataset data/candidates/bad_case --json reports/input.json
python -m app.generate --dataset-version 12 --capacity 45 --arrival-buffer 20
python -m app.validate_plan --plan reports/plan.json --dataset-version 12 \
  --capacity 45 --arrival-buffer 20
python -m pytest tests/test_dataset_validation.py tests/test_plan_invariants.py

제3자는 출력 메시지만 보지 말고 다음을 연쇄 대조한다. 입력 묶음 해시 → 적용 버전 → job의 고정 조건 → 검증 보고서 → final의 입력 버전/조건 → 내보낸 JSON → 재실행한 독립 검사 결과. 파일 경로나 명령은 구현마다 다르므로 실제 HOW_TO_RUN.md에 있는 경로를 우선한다. DB를 열어야 하는 경우에도 실제 스키마를 먼저 확인하고 예시 테이블 이름을 그대로 존재한다고 가정하지 않는다.

🚌 4. 정상 실행: ‘근무자 전원’이라는 말의 수학적 의미

근무자와 배정 결과를 서로 다른 집합으로 보자

하루 d의 근무표에서 WORK인 사람의 집합을 W(d)라 하자. 출근 배정의 사람 목록을 A_in(d), 퇴근 배정 목록을 A_out(d)라 하자. 단순히 개수가 같다는 이유로 전원 배정이라고 하면 안 된다. A가 두 번 배정되고 B가 빠져도 총행 수는 같을 수 있기 때문이다.

충족해야 할 것은 집합 동일성과 중복 없음이다. 각 emp_id, work_date, direction 조합이 정확히 한 번 나타나고, 두 방향 모두 배정된 사람의 집합이 W(d)와 같아야 한다. 휴무자 OFF는 양쪽 집합에서 빠져야 한다. 운행의 shift_code와 직원 근무시간대, 사업장도 일치해야 한다.

실제 계획의 정원은 각 운행 구간별 탑승 인원으로 검사한다. 예컨대 첫 정류장에서 30명 탑승, 두 번째에서 20명 추가 탑승하면 그 구간에는 50명이 타므로 45석 위반이다. 총 승차자가 50명이라는 사실만으로 모든 구간이 위반인지는 알 수 없지만, 출근 운행처럼 중간 하차가 없다면 총 승차자가 상한이 된다. 반대로 일반적인 승하차가 섞인 노선에는 구간 누적 계산이 필요하다.

[가상 근무일 d / WORK: E01 E02 E03 / OFF: E04]
                  │
                  ├────► 출근 배정: E01 E02 E03 (각 1회)
                  └────► 퇴근 배정: E01 E02 E03 (각 1회)

잘못된 예: 출근 [E01, E01, E03] = 3행
          근무 인원도 3명 → 행 수는 일치! 그러나 E02 누락, E01 중복.

정류장 S1 ──(30명)──► S2 ──(50명)──► 사업장
                              ↑ 45석 초과: 해당 구간 불합격

시간 규칙은 방향과 기준일까지 확인해야 한다. travel_times.csv의 A→B와 B→A 값은 다를 수 있다. site에 출근하는 운행은 근무 시작보다 적용된 여유(기본 20분)만큼 빨리 도착하고, 퇴근 운행은 근무 종료 10분 후 이후 출발해야 한다. [내보내기 규격]은 비정상 날짜의 운행을 막기 위해 출근 도착은 근무 시작 전 12시간 이내, 퇴근 출발은 종료 후 12시간 이내의 범위를 추가로 명시한다. 정차 시각은 KST ISO 형식의 분 단위이고 각 인접 구간은 travel time 이상이어야 한다.

정상 흐름을 사건별로 쪼개기

T0  운영자 인증/권한 확인
T1  요청 수신: 기간, capacity, arrival_buffer, dataset_version, 요청 ID
T2  입력 버전/조건의 사전 검사; job 생성(QUEUED)
T3  Creator가 같은 버전의 7개 입력으로 후보 정류장 → 배정 → 노선 → 시간표 생성
T4  staging에 결과 저장, job=VALIDATING
T5  Validator가 독립적으로 원문·EXPORT_SCHEMA 규칙을 검사
T6  [트랜잭션] 결과가 생성된 데이터 버전·조건이 여전히 공개 대상인지 재확인
T7  [같은 트랜잭션] final에 기록 + active_plan_id를 새 결과로 교체 + job=SUCCEEDED
T8  조회 API와 내보내기는 active_plan_id의 결과만 제공

T3은 노선 최적화가 쉬워서 짧은 단계라는 뜻이 아니다. 정류장 선택, 구성원 배정, 정차 순서, 시간표가 서로 영향을 주기 때문에 해를 찾기 어렵다. 어떤 정류장을 열면 사람의 접근거리는 짧아지지만 차량 운행시간이 길어질 수 있다. Creator는 일단 조건을 만족하는 해를 찾고 품질을 개선하는 역할이며, 그것이 불가능하면 ‘실패/불가능’이라고 보고해야 한다. 성공 플래그만으로 유효성이 입증되지 않는다.

🧨 5. timeout·WORKER 종료·검증 실패: 화면은 무엇을 보여 줘야 할까?

타임아웃은 ‘계산이 중단됐다’와 다르다

사용자가 30초 동안 응답을 못 받아 HTTP 타임아웃을 겪었다고 하자. 그때 백그라운드 계산은 계속 진행 중일 수 있다. 브라우저가 요청을 포기하는 것은 서버 프로세스를 종료시키는 명령이 아니다. 반대로 운영자가 취소 버튼을 눌렀다고 해도 그것이 실제 계산 중지와 확정 금지를 구현했다는 증거는 아니다.

서버 응답 타임아웃, 작업 실행 제한시간, 사용자 취소, 프로세스 강제 종료는 서로 다른 사건이다. 각각 DB에 어떤 상태가 남는지 합의해야 한다.

사건 즉시 알 수 있는 것 유지해야 할 가시적 결과 별도 확인할 경합
HTTP 요청 타임아웃 클라이언트는 완료 응답을 받지 못함 기존 active final 유지, job 조회 가능 실제로는 커밋되었을 수 있음
작업 시간 초과 작업이 기한 내 끝나지 못함 이전 final 유지; job TIMEOUT/FAILED는 정책에 따름 기한 지난 실행이 뒤늦게 저장 시도
사용자 취소 요청 취소 의사가 기록됨 기존 final 유지; 확정 전 취소 의사 재확인 취소와 성공 확정의 순서
WORKER 종료 그 프로세스의 메모리 계산이 사라짐 DB의 job/staging/이전 final은 저장 방식에 따라 남음 죽은 WORKER의 lease 만료와 재실행
Validator 실패 생성된 결과가 규칙을 못 지킴 실패 보고서 보관, 이전 active final 유지 staging을 final로 잘못 공개하는 경로
커밋 직후 응답 유실 사용자에게는 성공 여부 불명 실제 성공 시 새 final은 존재 재시도로 중복 job/중복 공개

왜 job, temp, final을 나눌까?

job은 “요청과 진행 상태의 장부”다. temp 또는 staging은 “검증 전의 후보”다. final은 “검증을 통과하고 공개 대상으로 확정된 결과”다. 데이터가 셋 다 DB에 있더라도 읽을 자격이 다르다. 후보 결과를 구성원 화면에서 조회한다면, DB 저장에는 성공했지만 서비스는 틀렸다.

[기존 공개 계획 P17] ───────────────────────────────┐
                                                     │ 사용자 조회
새 job J18: QUEUED → RUNNING → VALIDATING           │
                          │                          │
                   staging S18                      │
                    ├─ FAIL ──► FAILED ──────────────┤ P17 유지
                    └─ PASS ──► 원자적 교체 ──► [P18]┘ 공개 포인터 변경

핵심: staging S18의 존재 ≠ P18이 공개 가능한 상태

상태 머신이 필요한 이유

“상태 문자열을 하나 둔다”가 전부가 아니다. 상태마다 허용되는 다음 상태를 정해 불법적인 되돌림을 막는다. 예컨대 이미 CANCELLED인 job의 늦은 WORKER가 SUCCEEDED로 덮어쓰면 취소 약속을 어긴다.

QUEUED → RUNNING → VALIDATING → SUCCEEDED
    │        │           │
    └────────┴───────────┴──► FAILED / CANCELLED / TIMED_OUT

(설계 정책에 따라 일부 전이는 다를 수 있음)
복구 시 RUNNING/VALIDATING + 만료된 lease → RETRY_QUEUED 또는 FAILED
SUCCEEDED / CANCELLED는 자동으로 RUNNING으로 되돌리지 않음

단일 서버라도 재시도가 있으면 옛 시도와 새 시도가 겹친다. 그래서 멱등성 키는 같은 의도/같은 요청을 중복 생성하지 않게 하고, fencing token(펜싱 토큰)은 오래된 실행 주체가 뒤늦게 결과를 확정하지 못하도록 한다. 멱등성은 요청 중복을 통제하고 펜싱은 실행 주체의 권한을 통제하므로 둘을 서로 대체할 수 없다.

가상 예: J18의 시도 A가 lease=7을 얻어 계산하던 중 멈췄다. 만료 뒤 시도 B가 lease=8을 얻었다. A가 갑자기 돌아와서 final을 쓰려 할 때 jobs.fence_token=7이라고만 주장하면 거절해야 한다. DB 안의 현재 토큰 8과 비교해 원자적으로 갱신해야 한다. 단순히 토큰을 읽은 뒤 몇 초 뒤에 쓰면 사이에 다시 변경되는 경합이 남는다.

가장 작은 안전한 확정 구간

-- [설계 예시 / 실제 스키마 아님]
BEGIN IMMEDIATE;
-- 현재 job의 lease/fence, 취소 여부, dataset version, 운영 조건 버전을 확인한다.
-- staging의 검증 통과 보고와 입력 해시를 확인한다.
-- 조건이 하나라도 틀리면 ROLLBACK하고 공개 포인터를 건드리지 않는다.
INSERT INTO final_plans (...) SELECT ... FROM staging_plans WHERE job_id = :job_id;
UPDATE active_plans SET plan_id = :new_plan_id
 WHERE scope_key = :scope_key AND version = :expected_active_version;
-- 바뀐 행 수가 정확히 1인지 확인한다. 0이면 경쟁 변경으로 실패 처리한다.
UPDATE jobs SET status = 'SUCCEEDED' WHERE id = :job_id AND fence_token = :token;
-- 이 UPDATE도 정확히 1행이어야 한다. 모든 사전 조건을 트랜잭션 안에서 보장.
COMMIT;

이 코드는 의사 SQL이다. (...)와 스키마, 예외 처리, 트랜잭션 오류 복구, UPDATE 결과 검사 구현이 생략되어 있어 그대로 실행 가능한 완성 코드는 아니다. 원칙은 하나라도 조건이 어긋나면 최종 결과와 공개 포인터 변경 전체를 롤백한다는 것이다. SQLite는 한 DB 파일 안의 트랜잭션에 원자적 커밋을 제공하지만, DB 트랜잭션이 별도 파일시스템 기록이나 외부 메시지 발송까지 자동으로 원자화하지는 않는다. 또한 SQLite는 동시에 하나의 writer만 허용하므로 계산 전체에 긴 쓰기 트랜잭션을 잡지 말고, 계산은 밖에서 진행하고 짧은 확정 트랜잭션만 사용한다.

outbox는 여기서 왜 나오나?

final을 확정한 직후 ‘완료 알림’을 외부 큐에 전송한다고 하자. DB commit은 성공하고 메시지 전송 전에 프로세스가 죽을 수 있다. 그러면 계획은 성공했으나 알림이 없다. 반대로 알림을 먼저 보내면 실제로는 롤백됐는데 완료 안내가 갈 수 있다. outbox는 확정 트랜잭션 안에 보낼 이벤트 레코드도 같은 DB에 기록하고, 별도 전달자가 나중에 전송하도록 하는 패턴이다. 이벤트 발송은 중복될 수 있으므로 수신 측의 멱등 처리도 필요하다. 시험에서 반드시 outbox를 구현하라는 요구였다는 뜻이 아니다. 외부 비동기 알림/큐가 붙을 때 생기는 경계 문제를 설명하기 위한 심화 연결이다.

두 가지 현실적인 기본안

설계 가장 단순한 단일 서버·SQLite 별도 WORKER 프로세스
요청 처리 동기 생성으로 응답까지 계산하거나, 서버 내부 작업 처리 API는 job 접수 후 worker가 비동기 실행
장점 구성 단순·추적 쉬움 긴 작업 중 API 응답성 향상, 계산 격리
대가 요청 타임아웃·응답성 문제, 재시작 시 실행 중 작업 손실 job/lease/재시도/상태 복구/배포·관측 복잡도 증가
반드시 지켜야 할 보장 검증 전 결과 비공개, 실패 시 이전 final 보존 같은 보장 + 오래된 worker 확정 차단

별도 프로세스 = 자동 복구가 아니다. 공유 DB에 job 상태를 저장하고, 재시작 시 만료된 작업을 탐지하고, 원자적 소유권 획득/펜싱/재시도를 구현하지 않으면 오히려 취약점이 늘어난다. 여러 서버로 확장한다면 로컬 메모리 락은 서버 간 공유되지 않으므로 DB의 원자적 조건부 갱신이나 외부 조정 장치가 더 중요해진다. 공유 SQLite 파일의 접근 방식과 스토리지 특성도 검토해야 한다. SQLite WAL을 모든 네트워크 파일시스템에서 무조건 공유 가능하다고 가정하지 않는다.

🔎 6. AI가 ‘성공’이라 했을 때, 정확성과 품질은 누가 증명하나?

같은 목적함수를 한 번 더 돌리면 독립 검사일까?

Creator와 Validator가 같은 함수 is_valid()를 호출하면 둘 다 똑같은 버그를 공유할 수 있다. 분리의 핵심은 프로세스 수나 파일 수 자체가 아니라 실패를 독립적으로 발견할 수 있는 관점이다. Creator는 해를 구성하고, Validator는 해를 반박하려고 검증한다. Validator는 원본 입력과 요구조건에서 기대 집합을 다시 만들고 결과 JSON을 읽어 제약을 처음부터 확인해야 한다.

예를 들어 Creator는 노선에 E01, E02, E03을 추가하고 assigned_count=3을 기록했다. Validator가 그 저장된 숫자만 믿으면 중복 배정을 못 잡는다. 독립 Validator는 원본 근무표의 WORK 집합, 실제 assignments의 (사람, 날짜, 방향) 수, 경로 내부의 정류장 순서, 매 구간 좌석 점유, 방향별 travel time을 자기 계산으로 도출한다.

정확성, 품질, 규모를 별개로 보자

차원 본질 관찰/검증 통과해도 말할 수 없는 것
정확성(feasibility) 불변식 위반이 없는가? 모든 날짜·근무자·방향·구간·시각 검사 가장 효율적인 노선인지는 모름
품질(objective quality) 유효한 해들 중 얼마나 나은가? 차량 운행 횟수, 총 이동분, 평균/상위 분위 접근거리, 최장 이동시간, 편의 형평성 선택한 지표 외의 공정함·비용까지 보장하지 않음
규모·성능(scale) 입력이 커져도 제시간에 안정적으로 끝나는가? 1.5k→3k→6k 가상 규모에서 시간·메모리·쿼리·재시도·오류율 규모가 달라도 반드시 동일 품질이라는 뜻은 아님

품질 점수를 다음처럼 설계할 수 있다. 이것은 가상 선택이며 원문이 강제한 공식이 아니다.

먼저: 모든 강제 제약을 만족하는 해만 후보로 남긴다.
그다음: 품질 점수 = α × 총 운행시간 + β × 구성원 접근거리 합
                   + γ × 상위 5% 접근거리 + δ × 차량 운행 수
조건: 지표 단위/정규화/가중치의 합의가 필요하다.

왜 ‘먼저 제약 통과’일까? 가중합만 쓰면 차량을 한 대 줄이는 점수가 45석 위반을 상쇄하는 오류가 생길 수 있기 때문이다. 필수 조건은 패널티로 흥정할 수 없는 제약, 선택적 편의는 목적함수로 분리하는 설계가 안전하다. 최적화가 정확히 전역최적을 찾았는지(최적해 보장)와 개선된 휴리스틱 해를 찾았는지는 별개다. 보장 증명이 없다면 ‘최적화했다’는 말을 기준선 대비 개선의 의미로 한정한다.

강한 반례 다섯 개

  1. 중복이 누락을 가리는 경우: 총 배정 행 수는 근무자 수와 같지만 한 명은 빠지고 다른 한 명은 두 번. → 집합 비교 + 유일성 검사.
  2. 여러 정류장에서 정원을 초과하는 경우: 첫 구간 30명, 다음 구간 50명. → 차량 단위·구간 단위 최대 승객 검사.
  3. 방향을 뒤집은 이동시간: A→B는 12분, B→A는 20분인데 퇴근에도 12분 적용. → 방향별 인접 노드 시간을 재계산.
  4. 데이터셋 적용 뒤 낡은 결과 노출: B를 적용했지만 활성 플랜은 A의 것. → plan.dataset_version == current_applied_version 아니면 새 데이터의 결과로 표시하지 않음. 정책상 이전 결과를 역사적 자료로 보관할 수는 있음.
  5. 조건 변경 미반영: 차량 정원 45→30으로 바꾸었지만 이전 계획을 그대로 내보냄. → 검증자는 출력 JSON이 자체 주장하는 조건이 아니라 운영자가 적용한 조건으로 재검증.

독립 검사기의 사고 순서

# [설계 예시 / 의사코드. 실제 CSV/JSON에서 미실행]
def validate_plan(dataset, plan, requested_period, capacity, arrival_buffer):
    errors = []

    # 7. 발견한 위반을 행·날짜·운행 ID·규칙 ID로 반환

위 코드는 구현 논리를 보여 주는 뼈대다. return []이 실제 유효하다는 뜻이 아니고, 함수가 실제로 위 주석의 로직을 수행하지도 않는다. 이 차이를 구별하는 게 바로 독립 확인이다.

규모 또는 운영 조건이 바뀔 때 더 봐야 할 것

  • 정원 45→30: 필요한 차량 수가 늘 가능성이 크다. 날짜·shift·방향별 재배정, 구간 정원, 운영시간을 다시 검사한다. 반드시 차량 수가 늘어난다고 단정하지는 않는다.
  • 도착 여유 20→35분: 출근 목표 도착이 더 빨라진다. 시간표를 새로 계산하고 조건을 기준으로 다시 검사한다. 퇴근의 10분 규칙과 혼동하지 않는다.
  • 근무/휴무 변경: 변경된 사람만 덧붙이는 방식은 기존 경로와 정원의 전체 최적성을 무너뜨릴 수 있다. 현재 적용 버전의 기간 전체를 다시 평가해야 한다.
  • 규모 증가: 시간복잡도뿐 아니라 DB 쓰기 경합, 메모리·CPU, 작업 대기 시간, timeout, 복구 소요, 휴리스틱 품질 저하를 함께 측정한다.
  • 입력의 지리적 분포 변화: 총 인원 수가 같아도 거주 분포가 달라지면 기존 정류장 선정이 부적절할 수 있다. 결과가 우연히 같다는 이유로 재계산 실패라고 단정하지 않는다.

측정할 때는 입력 버전·기간·정원·여유시간·알고리즘 버전·시드·기계 사양을 같이 보관해야 비교가 가능하다. 예를 들어 time_total=12s만 있으면 규모, 데이터 편차, warm cache, 재시도 여부를 알 수 없다. p50/p95 처리 시간, 실패율, 작업 단계별 소요, peak RSS, DB 잠금 대기 등으로 쪼개는 이유는 느리다는 사실을 고칠 수 있는 원인으로 바꾸기 위해서다.

⚙️ 8. Creator/Validator 병렬 추궁: 병렬로 돌린다고 더 정확해질까?

먼저 두 의미를 분리하자

[복기]에서는 다른 응시자가 “Creator와 Validator 병렬 처리” 관련 질문을 받았다는 전달만 있다. 정확한 질문 및 용어가 서비스의 생성기/검증기인지, AI 코딩 에이전트의 작성/검토 역할인지는 확인되지 않았다. 아래에서는 두 경우를 분리한다.

① 서비스의 Creator/Validator: Validator는 생성된 결과가 있어야 그 결과를 검사할 수 있다. 따라서 동일 결과에 대한 최종 검증은 생성 뒤에 수행해야 한다. 다만 Creator가 날짜/shift별 독립 후보를 생산하고 그 조각을 Validator가 앞서 완료된 것부터 검사하는 파이프라인 병행은 가능하다. 조각마다 통과했어도 전체 인원의 중복/누락, 전 기간 일관성, 활성 버전 등 전역 검사는 최종 집계 뒤 반드시 다시 해야 한다.

시간 ───────────────────────────────────────────────────────►
Creator:   [7/20 후보] [7/21 후보] [7/22 후보] [전체 합치기]
Validator:           [7/20 검사] [7/21 검사] [7/22 검사] [전역 검사]
Finalizer:                                               [한 번 확정]

검사 시작을 앞당길 수는 있지만, 최종 확정은 마지막 전역 PASS 이후.

② AI 코딩 작업의 Creator/Validator: 한 AI가 API 코드를 작성하고 다른 AI가 요구사항에 따라 테스트/코드 리뷰를 병렬로 준비할 수 있다. 단, 작성 중인 코드를 기준으로 ‘테스트 통과’를 선언하면 안 된다. 둘이 파일을 동시에 수정하면 충돌한다. 작업물 버전/커밋 해시를 고정해 평가하고, Validator가 Creator에게서 복사한 가정만 확인하는 일이 없도록 PRD 원문을 별도로 준다. “AI가 검증했다”는 말은 검증 도구의 실제 실행과 관찰된 출력이 있어야만 성립한다.

순차·동시·병렬·비동기의 정확한 차이

  • 순차(sequential): A가 끝난 다음 B 시작. 의존성 이해와 디버깅이 쉽지만 대기 시간이 길 수 있다.
  • 동시성(concurrency): 여러 작업이 진행 중인 구조. 한 코어에서 번갈아 실행해도 동시성이 있다.
  • 병렬성(parallelism): 같은 순간 실제로 여러 계산이 실행된다. 코어/프로세스 등 실행 자원이 필요하다.
  • 비동기(asynchronous): 작업을 시작하고 완료를 기다리는 동안 요청 처리 주체가 다른 일을 할 수 있는 제어 흐름이다. 여러 CPU 코어에서 계산한다고 보장하지 않는다.

예: API가 job을 DB에 만들고 HTTP 202 Accepted와 job_id를 반환하면, 결과가 완료된 것은 아니다. 다른 프로세스가 계산을 수행할 수 있다. 또한 async def로 CPU 집약 노선 계산을 바로 실행한다고 해서 자동으로 별도 코어에 분산되는 것도 아니다. CPU 점유가 크다면 별도 프로세스·작업 큐 또는 적절한 실행기 선택이 필요하지만 그 비용(직렬화, 배포, 관측, 취소와 복구, DB 경합)을 지불해야 한다.

오래된 fence=21의 확정은 거절. 메모리에만 둔 중간 결과는 사라짐.

가장 중요한 반례: 두 WORKER가 동시에 QUEUED job을 보고 둘 다 ‘내 작업’이라고 판단하면 같은 노선을 두 번 계산한다. 먼저 읽고 나중에 쓰는 비원자적 claim이 원인이다. 단일 SQLite DB의 짧은 트랜잭션 안에서 한 작업만 상태·lease를 획득하도록 조건부 UPDATE를 사용하고 결과 행 수를 확인한다. 복구와 중복 방지에 필요한 건 “WORKER 2개”라는 설정이 아니라 하나의 권위 있는 상태 저장소와 원자적 전이다.

🧠 10. 네 축을 다시 하나로 연결해 설명해 보자

질문 ① ‘무엇을 실제로 검증했고, 안 한 것은 무엇인가?’

이 질문의 출발점은 검증 함수의 이름이 아니다. 검증의 대상이 무엇인지부터 밝히는 것이다. 입력 스키마를 검사했는지, 일곱 파일의 참조를 검사했는지, 날짜별 업무 조건을 검사했는지, 생성 결과를 검사했는지 순서대로 구분한다. 그다음 코드·명령·리포트·DB 버전이 있는 것만 ‘실제로 확인했다’고 말한다. DB 제약은 저장 무결성, Validator는 출력 계획의 전역 규칙, 독립 실행은 최종 근거라는 책임 차이를 지킨다. 실제 코드가 없으면 특정 구현의 검증 범위는 미확인이다.

틀리기 쉬운 말: “CSV 7개가 열리면 전부 검증했습니다.” → 행은 파싱돼도 없는 직원 참조, 누락된 방향의 이동시간, 배정 누락이 남는다.

추궁: “유효한 CSV를 적용하기 직전 파일을 바꾸면?”, “검증 실패한 데이터셋 뒤 기존 결과와 활성 데이터가 각각 어떤 버전인가?”, “제3자가 동일한 오류를 확인할 수 있는 단일 명령이 있나?”

질문 ② ‘정상 배정부터 실패 뒤 잔존까지?’

먼저 날짜별 WORK 집합을 만들고 출퇴근 각각 정확히 한 번 배정되도록 생성한다. 생성된 후보를 staging에 둔 뒤 독립 규칙을 통과한 것만 final로 확정한다. HTTP timeout은 작업 중단 보장이 아니고, WORKER 종료는 메모리 작업을 잃지만 DB에 커밋된 job/staging/final의 운명은 저장 경계에 달려 있다. Validator 실패 시 기존 final을 유지하는 설계가 중요하다. 가장 취약한 점을 하나 고른다면 ‘검증 통과 여부·현재 버전·현재 실행 주체를 같은 확정 경계에서 재확인하지 않은 채 공개 포인터를 변경하는 지점’이다. 다만 실제 시스템의 최약점은 코드·장애 실험 없이 확정할 수 없으므로 이는 가상 설계의 우선 위험 가설이다.

틀리기 쉬운 말: “timeout이면 자동 롤백됩니다.” → timeout이 이미 커밋된 DB 작업을 되돌리지는 않는다. 요청의 연결과 DB 트랜잭션의 경계가 다르다.

추궁: “커밋 후 응답만 유실되면 재시도는?”, “취소 직후 늦은 WORKER가 성공을 쓰면?”, “staging이 디스크에 남아 있으면 사용자에게 보이나?”

질문 ③ ‘AI 보고 없이 정확성과 품질을 어떻게 확인하나?’

AI의 설명과 앱의 자체 성공 플래그는 증거 후보일 뿐이다. 원본 근무표로 근무 집합을 재구성하고, 실제 JSON에서 중복/누락·구간 정원·방향별 이동시간·근무 시간·기간/조건 일치 여부를 다시 계산한다. 정확성을 통과한 해끼리 차량 수, 총 운행시간, 접근거리와 편의 형평성 같은 품질 지표를 비교한다. 규모가 커지면 시간·메모리·대기·실패율과 품질 변화도 잰다. 최적해 보장은 별도 증명이 필요하다.

틀리기 쉬운 말: “배정률이 100%고 AI가 최적화했다고 하니 완성입니다.” → 중복 배정으로 숫자를 부풀릴 수 있고, 전체 제약 및 품질 비교가 빠져 있다.

추궁: “정원을 줄였는데 경로가 같으면 버그인가?”, “품질 목표를 위해 도착 20분 규칙을 깨도 되나?”, “Validator도 Creator와 같은 버그를 복사했다면?”

질문 ④ ‘버튼에서 저장까지 책임과 소유자는?’

UI는 요청 의도를 보내고 API는 인가·요청 계약을 검사하며 job 관리자에게 접수를 맡긴다. Creator는 고정된 입력 버전과 조건으로 staging 후보를 만든다. Validator는 독립 계산으로 위반을 찾는다. Finalizer는 검증과 동시성 조건을 짧은 DB 트랜잭션 안에서 재확인해 final과 active pointer를 함께 확정한다. 조회와 내보내기는 공개된 final만 읽는다. 생성·검증 분리의 이유는 작동 성공과 규칙 준수를 같은 코드의 자기보고로 판단하지 않기 위해서다.

틀리기 쉬운 말: “컴포넌트가 나뉘었으니 데이터도 안전합니다.” → 실제 접근 경계가 없으면 Creator도 final을 덮어쓸 수 있다.

추궁: “어느 지점에서 확정이 되나?”, “SQLite 트랜잭션 밖의 파일을 동시에 바꾸면?”, “별도 프로세스 두 개가 같은 job을 가져가면 누가 소유자인가?”

PRD·병렬·별도 프로세스까지 한 문장 사슬로

업무의 약속은 PRD/인수 조건으로 추적하고 → 입력과 운영 조건을 버전으로 고정하고 → Creator가 후보를 만들고 → 독립 Validator가 반례를 검사하고 → Finalizer가 현재성·소유권·검증 통과를 한 번에 확인하고 → 공개 결과만 읽게 만들며 → timeout·중단·재시도 뒤에도 같은 약속을 유지하는지 실험으로 증명한다. 병렬 처리와 별도 프로세스는 이 사슬을 빠르게 하거나 격리할 수 있지만, 원래 없던 상태 소유권·중복 실행·복구 문제도 추가한다.
