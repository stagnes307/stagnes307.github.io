대주제 1. 실행과 웹의 기초 / 중주제 1-1. 실행 원리 / 소주제 1-1-1

Ailey: 오늘은 네가 작성한 코드가 실제 컴퓨터 안에서 어떻게 실행되는지, 그리고 그 실행이 멈췄을 때 무엇이 사라지고 무엇이 남는지 끝까지 따라가 볼 거야.

예를 들어 통근버스 노선 생성 버튼을 눌렀다고 해보자. 화면에는 '노선 생성 중'이라고 표시되고, 서버는 1,500명의 데이터를 읽어서 노선을 계산하기 시작해. 몇 초 후 계산이 끝나면 결과를 보여주겠지.

그런데 계산 도중 서버를 종료하면 어떻게 될까?

  • 계산 중이던 노선은 어디에 있었을까?
  • 계산을 수행하던 WORKER만 종료하면 웹 서버도 죽을까?
  • 생성 도중 임시로 만든 결과와 이전에 성공했던 노선은 같이 사라질까?
  • SQLite에 저장했다고 해서 서버 재시작 후 반드시 다시 읽을 수 있을까?

이 질문에 답하려면 프로그램 → CPU와 운영체제 → 프로세스 → 메모리 → 함수 호출 → 스레드 → 프로세스 간 통신 → 저장소를 하나의 연결된 원리로 이해해야 해.

오늘의 목표는 용어를 외우는 게 아니라 실행 중인 데이터가 누구의 소유이고, 어느 사건까지 살아남을 수 있는지 인과관계로 설명하는 것이야.

이번 수업의 전체 경로

01 코드 파일(저장된 명령) → 02 CPU·OS(실행과 자원 관리) → 03 프로세스(독립된 실행 환경) → 04 메모리(실행 중인 상태) → 05 스레드(실행 흐름과 경쟁) → 06 DB·디스크(실행 이후의 상태)

실행 구조를 이해한 다음, 통근버스 WORKER 종료와 기존 성공 결과 보존을 이 흐름에 대입한다.

이 수업의 기술 원리는 운영체제의 가상화·동시성·영속성을 다루는 Operating Systems: Three Easy Pieces와도 연결돼. 시험 관련 사실은 제공된 원본 지시문과 복기 자료를 따르고, 별도로 만든 코드와 수치는 가상 예제로 표시할게.

🖥️ 1. 코드 파일은 왜 스스로 실행되지 않을까?

1-1-1-1. 코드와 실행은 서로 다른 사건이다

가장 작은 프로그램부터 보자.

price = 1000
quantity = 3

total = price * quantity

print(total)

우리는 이 코드를 읽는 순간 3000이 나온다는 걸 예상할 수 있어.

하지만 example.py라는 파일에 이 내용을 저장했다는 사실만으로 컴퓨터가 3000을 계산한 건 아니야.

파일은 디스크나 SSD에 기록된 바이트들의 집합일 뿐이거든.

파일이 저장되었을 때와 실행되었을 때를 구분해 보자.

01강 비교와 확인
구분 파일로 존재할 때 실행할 때
코드 저장장치에 기록됨 실행 환경에서 처리됨
변수 price 코드 속 이름과 값의 표현 실행 중 실제 객체와 참조가 형성됨
계산 아직 수행하지 않음 CPU가 계산에 필요한 명령 수행
출력 없음 표준 출력에 3000 기록
종료 후 코드 파일은 남음 일반적인 실행 상태는 사라짐

여기서 첫 번째 핵심 구분이 나와.

코드는 앞으로 어떤 일을 하라는 기술이고, 실행은 그 일을 컴퓨터가 실제로 수행하는 사건이야.

그리고 컴퓨터에는 코드를 실행할 물리적인 장치와, 그 장치를 여러 프로그램에 나누어 주는 관리자가 필요해.

1-1-1-2. CPU는 무엇을 할까?

CPU는 Central Processing Unit, 즉 중앙처리장치야.

CPU는 기계어 명령을 읽고 수행하는 장치야. 간단히 말하면 다음 일을 반복하지.

  1. 다음에 수행할 명령을 가져온다.
  2. 명령의 의미를 해석한다.
  3. 레지스터를 이용해 계산하거나 메모리에 접근한다.
  4. 다음에 실행할 명령 위치를 결정한다.

레지스터는 CPU 내부에 있는 아주 빠른 소규모 저장 공간이야. 현재 계산에 필요한 숫자나 주소 등을 담아.

예를 들어 CPU 수준에서 두 숫자를 더한다면 개념적으로 이런 동작을 수행할 수 있어.

메모리에서 값 10 읽기
메모리에서 값 20 읽기
CPU 내부에서 10 + 20 계산
결과 30을 저장할 위치에 쓰기

실제 CPU 명령어는 기계 종류와 컴파일러에 따라 달라. Python의 price * quantity 한 줄도 CPython 인터프리터의 여러 명령과 내부 처리 과정을 거쳐 실행돼.

이 차이가 중요해. 고급 언어의 한 줄이 CPU 명령어 한 개라는 뜻은 아니야.

CPU는 계산을 수행할 수 있지만, 스스로 어떤 Python 파일을 실행할지 결정하거나 프로그램에 메모리를 마음대로 배분해 주는 것은 아니야.

그 역할에 운영체제가 등장해.

1-1-1-3. 운영체제는 왜 필요할까?

네 컴퓨터에 브라우저, 메신저, VS Code, Python 서버가 동시에 열려 있다고 해보자.

모두 CPU와 메모리를 필요로 해. 그런데 각 프로그램이 자기 마음대로 물리 메모리를 쓰거나 다른 프로그램의 실행 상태를 덮어쓸 수 있다면 시스템은 금방 불안정해지겠지.

운영체제(OS)는 이런 자원들을 관리하고 보호해.

대표적으로 다음 일을 맡아.

  • CPU 스케줄링: 어떤 실행 흐름에 언제 CPU 실행 기회를 줄지 결정한다.
  • 메모리 관리: 각 프로세스에 주소 공간을 제공하고 메모리 접근을 보호한다.
  • 프로세스 관리: 프로세스 생성·종료와 자원 정리를 관리한다.
  • 입출력 관리: 파일, 디스크, 네트워크 등 장치를 사용할 수 있도록 인터페이스를 제공한다.

여기서 운영체제 전체가 모든 순간 CPU에서 실행되는 건 아니야. 사용자 프로그램이 실행되다가 시스템 호출이나 인터럽트 등을 통해 커널 기능을 사용하지.

커널은 운영체제의 핵심 부분으로, 하드웨어 접근과 중요한 자원 관리를 담당해.

1-1-1-4. Python 파일을 실행할 때 일어나는 일

터미널에서 다음 명령을 입력했다고 해보자.

python example.py

흐름을 순서대로 따라가면 다음과 같아.

  1. 사용자가 python example.py 명령을 입력한다.
  2. 운영체제가 실행 환경을 준비하며 프로세스를 생성한다.
  3. Python 인터프리터가 파일을 읽고 코드를 처리한다.
  4. CPU가 명령을 수행하고 객체 생성·계산·출력이 이루어진다.
  5. 프로세스가 종료되면 실행 자원을 정리한다.

좀 더 정확하게 말해볼게.

운영체제는 Python 인터프리터 실행 파일을 실행할 프로세스를 준비해. Python 인터프리터는 example.py를 읽고, 일반적인 CPython에서는 소스를 바이트코드로 컴파일한 다음 가상 머신에서 실행해.

CPU가 직접 이해하는 것은 Python 바이트코드가 아니라, 인터프리터와 관련 실행 코드의 기계어 명령이야.

그 과정에서 price, quantity, total에 해당하는 실행 상태가 메모리에 생기고, 출력이 이루어져.

마지막으로 Python 실행이 끝나면 프로세스가 종료되고 운영체제가 자원을 회수해.

그런데 example.py 파일이 자동으로 삭제되지는 않아.

왜일까?

코드 파일을 저장해 둔 저장장치의 수명과, 그 코드를 실행하는 프로세스의 수명이 다르기 때문이야.

이제 그 프로세스가 정확히 무엇인지 살펴보자.

🏭 2. 프로그램과 프로세스는 무엇이 다를까?

1-1-1-5. 하나의 프로그램이 여러 번 실행될 수 있다

python이라는 인터프리터 실행 파일이 컴퓨터에 있다고 해보자.

터미널 창 두 개에서 다음 명령을 각각 입력해.

python server.py

python worker.py

둘 다 Python이라는 프로그램을 이용하지만 실행된 결과는 서로 다른 프로세스야.

하나는 웹 서버 작업을 하고, 다른 하나는 노선 계산 작업을 수행할 수 있어.

프로세스 A: server.py, PID 2101 (가상), 자기 메모리, 자기 실행 상태.

프로세스 B: worker.py, PID 2102 (가상), 자기 메모리, 자기 실행 상태.

두 프로세스가 같은 Python 인터프리터를 사용한다고 해서 변수와 객체를 자동 공유하지는 않는다. PID 값은 설명용이다.

프로그램은 주로 실행 가능한 코드와 그에 필요한 정적인 자료를 말해.

프로세스는 그 프로그램이 실행되는 동안 운영체제가 관리하는 실행 환경과 자원의 단위야.

프로세스를 구성하는 대표적인 요소를 살펴보자.

01강 비교와 확인
구성 요소 의미
PID 운영체제가 프로세스를 식별하기 위한 번호
가상 주소 공간 프로세스가 사용하는 메모리 주소 체계
실행 스레드 실제 명령 실행을 진행하는 흐름
열린 파일 프로세스가 사용할 수 있는 파일 핸들 등의 자원
네트워크 소켓 다른 프로그램과 통신할 때 사용하는 자원
실행 상태 실행 가능, 대기, 종료 등의 관리 상태

프로세스와 프로그램이 다른 이유는 간단해.

같은 계산기를 두 번 실행하면 계산기 프로그램 파일이 두 개 생기는 것이 아니라, 서로 다른 계산 상태를 가진 실행 인스턴스가 두 개 생기기 때문이야.

다만 운영체제가 모든 물리적 자원을 무조건 별도로 복제하는 것은 아니야. 읽기 전용 프로그램 코드 페이지를 여러 프로세스가 공유하거나, 명시적으로 공유 메모리를 설정할 수도 있어.

프로세스 격리는 서로 다른 실행 상태를 기본적으로 보호한다는 의미이지, 물리적으로 모든 것이 완전히 분리된다는 의미는 아니야.

1-1-1-6. 프로세스가 동시에 실행된다는 말의 정확한 뜻

CPU가 실행 가능한 스레드 하나만 처리할 수 있는 상황을 가정해 보자.

웹 서버와 계산기가 모두 실행 중이어도, 한순간에 CPU에서 실행되는 것은 하나의 스레드일 수 있어.

운영체제는 다음처럼 실행 기회를 번갈아 줄 수 있지.

가상의 단일 CPU 실행 흐름: 웹 서버와 계산 프로세스가 CPU 실행 기회를 시간순으로 번갈아 받는다. 설명용 시간 조각은 0ms, 2ms, 4ms, 6ms, 8ms, 10ms이며 실제 실행 순서와 길이는 고정되지 않는다.

이처럼 여러 작업을 번갈아 진행하는 것을 동시성(concurrency)의 한 형태라고 해.

반면 CPU 코어가 여러 개이고 서로 다른 스레드가 실제로 같은 순간 실행된다면 병렬성(parallelism)이야.

운영체제는 실행을 중단했던 스레드가 다시 이어서 실행할 수 있도록 필요한 CPU 상태를 보관하고 복원해. 이를 문맥 전환(context switch)이라고 해.

CPU가 실제 명령을 수행 중인 스레드가 있는 반면, 어떤 스레드는 디스크 응답이나 작업 도착을 기다리느라 실행할 필요가 없을 수도 있어.

따라서 '프로세스가 살아 있다'는 말과 '지금 CPU를 사용하고 있다'는 말도 달라.

이 차이는 서버가 멈춘 것처럼 보이지만 실제로는 DB 잠금을 기다리고 있는 상황을 이해할 때 중요해.

🧩 3. 메모리는 무엇을 저장하며, 변수는 어디에 있을까?

1-1-1-7. 실행 도중에는 상태를 둘 공간이 필요하다

이번에는 통근버스 문제를 축소한 가상 사례를 사용할게.

employees = [
    {"id": "E001", "working": True},
    {"id": "E002", "working": False},
    {"id": "E003", "working": True},
]

working = [
    e for e in employees if e["working"]
]

print(len(working))  # 2

이 코드를 실행하면 구성원 3명의 정보가 메모리에 올라와 처리되고, 그중 근무자 두 명이 선택돼.

하지만 여기서 메모리에 저장된다는 말을 좀 더 정확하게 살펴보자.

컴퓨터의 주기억장치인 RAM은 실행 중인 프로그램의 코드와 데이터 등을 보관하는 장치야.

CPU가 계산을 수행하려면 필요한 값에 접근할 수 있어야 해. Python 프로그램에서 리스트와 딕셔너리 등의 객체는 일반적으로 프로세스의 메모리에 생성돼.

따라서 이 예제의 employees는 단순히 숫자나 문자 세 개가 들어 있는 작은 상자가 아니야. 여러 객체를 가리키는 참조들의 구조를 포함해.

1-1-1-8. 변수와 객체는 같은 것이 아니다

변수는 값을 참조하기 위한 이름이고, 객체는 실제 데이터와 동작상의 특성을 가진 대상이야.

다음 코드를 보자.

a = {"route": "R01"}

b = a
b["route"] = "R02"

print(a["route"])  # R02

왜 a를 수정하지 않았는데 a["route"]도 바뀌었을까?

b = a가 딕셔너리 전체를 복사한 것이 아니라 동일한 딕셔너리 객체를 참조하게 만들었기 때문이야.

참조 관계: 변수 이름 a와 b가 하나의 딕셔너리 객체 route: R02를 참조한다. Python 참조의 개념도이며 객체의 실제 메모리 배치를 나타내지는 않는다.

통근버스 계산에서 이 현상은 아주 중요해.

예를 들어 previous_plan이라는 변수와 new_plan이라는 변수가 동일한 리스트를 참조하고 있다고 해보자.

새로운 노선을 생성하기 위해 new_plan을 직접 수정하면 이전 계획까지 변경될 수 있어.

이건 DB에 저장되지 않았더라도 프로그램의 메모리 안에서 발생할 수 있는 오류야.

서로 다른 변수라는 사실만으로 데이터가 분리되는 건 아니라는 뜻이지.

반면 다음처럼 복사하면 이야기가 달라져.

import copy

new_plan = copy.deepcopy(previous_plan)

deepcopy는 일반적인 내장 컨테이너의 중첩된 변경 가능 객체까지 복사하려고 시도해. 다만 임의의 사용자 정의 객체나 외부 자원에서는 복사 동작과 의미에 제약이 있을 수 있어.

변수를 분리했는가가 아니라, 수정하는 객체가 실제로 분리되었는가를 확인해야 해.

1-1-1-9. 프로세스의 가상 주소 공간

그런데 CPU가 여러 프로세스의 메모리를 읽고 쓰려면 주소가 필요하겠지?

RAM의 실제 위치와 프로그램이 사용하는 주소는 일반적으로 일대일로 고정되어 있지 않아.

현대 운영체제는 보통 각 프로세스에 가상 주소 공간(virtual address space)을 제공해.

프로그램은 자기 주소 공간 안에서 특정 주소에 접근하는 것처럼 동작하지만, 운영체제와 하드웨어의 메모리 관리 장치(MMU)가 해당 가상 주소를 물리 메모리와 연결해.

가상 주소 공간 도식: 프로세스 A와 B는 모두 0x1000 같은 가상 주소를 사용하더라도 각각 물리 페이지 X와 Y로 연결될 수 있다. 실제 매핑과 페이지 공유 방식은 달라질 수 있다.

이 구조에는 두 가지 중요한 효과가 있어.

첫째, 프로그램은 실제 RAM의 물리적인 배치를 일일이 알지 않아도 돼.

둘째, 한 프로세스가 다른 프로세스의 메모리를 허가 없이 접근하지 못하도록 보호할 수 있어.

하지만 가상 주소 공간이 독립적이라고 해서 모든 메모리가 반드시 RAM에 존재하는 건 아니야.

일부 페이지는 필요할 때 불러오거나 다른 저장장치로 이동할 수 있어. 사용하지 않는 주소 영역을 예약만 해둘 수도 있고, 두 프로세스가 특정 물리 페이지를 의도적으로 공유할 수도 있지.

그래서 가상 주소 공간의 크기, 실제 RAM 사용량, 디스크 사용량은 각각 다른 개념이야.

1-1-1-10. 스택과 힙은 왜 구분할까?

프로세스의 메모리를 설명할 때 스택(stack)과 힙(heap)이 자주 등장해.

전형적인 네이티브 프로그램에서는 코드·정적 데이터·힙·스택 등이 서로 다른 용도로 사용돼. 다만 실제 주소 배치와 Python 객체의 저장 방식은 단순한 교과서 그림보다 복잡해.

한 프로세스의 가상 주소 공간 — 개념적 구역: 스택(함수 호출·실행 문맥), 사용·예약되지 않은 영역, 힙(동적 할당 데이터), 정적 데이터 등, 실행 코드.

스택

함수가 호출되었다가 돌아오는 실행 순서를 관리하는 데 쓰여.

힙

실행 도중 크기와 수명이 유동적인 데이터를 동적으로 할당하는 데 쓰여.

이 그림은 구역의 역할을 강조한 단순화다. 모든 운영체제·런타임의 실제 배치가 이 형태인 것은 아니다.

이제 스택이 필요한 이유를 함수 호출을 통해 이해해 보자.

📚 4. 함수를 호출하면 메모리에서는 무슨 일이 일어날까?

1-1-1-11. 함수는 현재 작업을 잠시 다른 작업으로 옮기는 구조다

다음 코드를 보자.

def calculate_seats(workers):
    return workers * 2

def create_plan():
    workers = 90
    seats = calculate_seats(workers)
    return seats

result = create_plan()
print(result)

출력은 180이야. 이 값은 실제 노선 계산 규칙이 아니라 함수 호출 설명용 가상 숫자야.

CPU 입장에서는 create_plan()을 실행하다가 calculate_seats()로 이동하고, 다시 돌아와야 해.

여기서 문제가 생겨.

calculate_seats()를 끝낸 다음 정확히 어디로 돌아와야 할까?

호출 이전의 함수는 어떤 지역 상태를 유지해야 할까?

이런 실행 문맥을 관리하기 위해 호출 스택이 사용돼.

함수 호출 스택 탐색: 모듈 실행 → create_plan() 호출 → calculate_seats() 호출 → calculate_seats() 반환 → create_plan() 반환. 프레임이 호출 순서대로 추가되고 반환될 때 제거된다.

보이는 각 호출 단계를 스택 프레임(stack frame)이라고 불러.

프레임에는 호출 정보, 지역 변수와 관련된 실행 문맥 등이 포함돼. 함수가 반환되면 해당 호출 프레임은 제거돼.

단, Python의 구현 세부사항을 엄밀히 구분해야 해.

CPython의 Python 함수 실행 프레임을 일반적인 C 언어의 기계 스택 프레임과 완전히 동일시하면 안 돼. Python 프레임은 인터프리터가 관리하는 구조를 갖고 있고, Python 객체들은 일반적으로 힙에 있어.

여기서 반드시 이해해야 할 건 물리적인 바이트 배치가 아니라 함수 호출에 따른 실행 문맥의 수명이야.

1-1-1-12. 함수가 끝나도 객체가 살아남을 수 있다

다음 코드를 보자.

def make_route():
    route = ["S01", "S02", "ICN"]
    return route

saved_route = make_route()

print(saved_route)

make_route() 호출은 끝났어. 그런데 리스트는 남아 있지?

왜일까?

함수 호출 프레임이 끝나도, 반환된 리스트 객체를 saved_route가 계속 참조하기 때문이야.

반대로 어떤 객체도 더 이상 참조하지 않는다면 그 객체는 나중에 메모리에서 회수될 수 있어.

CPython에서는 참조 카운트와 순환 참조를 처리하기 위한 가비지 컬렉터 등이 메모리 관리에 관여해. 정확한 회수 시점을 모든 Python 구현에서 동일하게 가정하면 안 돼.

여기서 중요한 결론이 나와.

함수의 종료, 객체의 소멸, 프로세스의 종료는 세 가지 서로 다른 사건이야.

함수가 끝나도 객체가 남을 수 있고, 프로세스가 살아 있어도 특정 객체는 없어질 수 있어. 하지만 프로세스가 끝나면 그 프로세스가 독점하던 일반적인 메모리 상태는 더 이상 유지되지 않아.

1-1-1-13. 큰 데이터를 처리하면 무슨 일이 일어날까?

실제 시험의 구성원은 1,500명이지만, 원리를 이해하기 위해 훨씬 큰 가상 예를 생각해 보자.

노선 계산기가 10만 개의 후보 노선을 만들고, 후보 하나의 관련 메모리가 평균 2 KiB라고 가정하자.

그러면 후보 데이터만 대략 다음 공간을 사용해.

[ 100{,}000 \times 2\ \text{KiB} =195.3\ \text{MiB} ]

이는 객체 자체와 관련 메모리가 후보당 평균 2 KiB라는 가정 아래의 계산이야. Python 컨테이너 오버헤드나 추가 참조, 중복 객체 등에 따라 실제 사용량은 달라져.

이 후보를 여러 번 복사하거나, 여러 요청이 동시에 같은 계산을 한다면 메모리 부담은 커질 수 있어.

메모리가 부족해지면 운영체제와 실행 환경에 따라 할당 실패, 성능 저하, 프로세스 강제 종료 등이 발생할 수 있어.

따라서 노선 계산이 진행된다는 사실만으로 정상적으로 끝난다는 보장은 없어.

그리고 메모리 안에 계산 결과가 만들어졌다는 사실도 그 결과가 안전하게 저장되었다는 뜻은 아니야.

이 구분을 놓치면 WORKER 종료 후의 결과 보존을 제대로 설명할 수 없어.

🧵 5. 스레드는 왜 필요하고, 프로세스와 어떻게 다를까?

1-1-1-14. 한 프로세스에도 여러 실행 흐름이 있을 수 있다

프로세스는 실행에 필요한 자원과 주소 공간을 제공하는 단위라고 했지.

그런데 하나의 프로세스 안에서 여러 일을 진행하고 싶을 수도 있어.

예를 들어 웹 서버가 다음 작업들을 수행한다고 해보자.

  • 요청 A: 운영자의 노선 생성 요청 처리
  • 요청 B: 구성원의 기존 노선 조회
  • 요청 C: 관리자의 작업 상태 조회

서버가 요청 A의 긴 계산을 끝낼 때까지 다른 요청을 전혀 처리하지 않는 구조라면 사용자는 불편하겠지.

이 문제를 처리하는 여러 방법 중 하나가 스레드(thread)야.

스레드는 프로세스 안에서 명령을 실행하는 하나의 흐름이야.

한 프로세스는 하나 이상의 스레드를 가질 수 있고, 스레드마다 자기 실행 위치와 호출 스택을 가져.

반면 같은 프로세스 안에 속한 스레드들은 일반적으로 해당 프로세스의 주소 공간과 여러 자원을 공유해.

스레드 공유 메모리 도식: 하나의 웹 서버 프로세스에서 스레드 A(요청 처리), B(상태 조회), C(로그 처리)가 각자의 호출 스택을 갖고 공통 힙 객체·전역 상태·코드에 접근한다. 접근 가능하다는 것과 안전하다는 것은 다르다.

여기서 스레드가 실행 흐름을 여러 개 제공한다는 말은, 무조건 CPU 계산을 세 배 빠르게 한다는 뜻이 아니야.

같은 프로세스에 스레드가 여러 개 있어도 CPU 코어와 스케줄링 제약을 받아.

특히 일반적인 GIL 기반 CPython에서는 한 인터프리터의 Python 바이트코드 실행이 GIL에 의해 제한될 수 있어. Python 버전·빌드·확장 모듈에 따라 구체적인 실행 특성은 달라지며, 입출력을 기다리는 작업에는 스레드가 유용할 수 있어.

따라서 CPU를 많이 사용하는 노선 최적화 계산을 스레드로 옮겼다는 사실만으로 여러 코어를 활용해 더 빨라진다고 보장할 수 없어.

1-1-1-15. 스레드가 메모리를 공유하면 왜 위험할까?

다음 코드는 동시성 오류의 원리를 보여주는 의사코드야.

공유 변수 counter = 0

스레드 A:
    기존 값 읽기
    1 증가
    결과 저장

스레드 B:
    기존 값 읽기
    1 증가
    결과 저장

A와 B가 모두 값을 1씩 증가시키면 결과가 2여야 할 것 같지?

그런데 내부 동작이 서로 겹치면 예상과 다른 결과가 나올 수 있어.

두 스레드가 같은 값을 읽는 실행 순서

01강 비교와 확인
순서 스레드 A 스레드 B 공유 값
1 A가 0 읽음 — 0
2 — B가 0 읽음 0
3 A가 1 저장 — 1
4 — B가 1 저장 1

두 번 증가시키려 했는데 최종 값은 1이야. 두 스레드가 같은 오래된 값을 기반으로 결과를 덮어썼기 때문이지.

이처럼 실행 순서에 따라 결과가 잘못되는 현상을 경쟁 상태(race condition)라고 해.

정확히는 여러 실행 흐름이 공유 상태에 접근하고, 그중 적어도 하나가 상태를 수정하며, 필요한 동기화가 부족해 실행 순서가 결과에 영향을 미치는 상황을 말해.

여기서 중요한 개념 하나를 더 배워보자.

원자성(atomicity)은 하나의 동작이 다른 실행 흐름에 의해 중간 상태가 관찰되거나 끼어들 수 없는 단위로 수행되는 성질이야.

counter += 1은 코드상 한 줄이지만 모든 언어와 모든 상황에서 원자적이라고 가정하면 안 돼.

공유 상태를 안전하게 변경하려면 잠금(lock), 원자적 연산, 메시지 전달, DB 트랜잭션 등 상황에 적합한 동기화 수단이 필요해.

단, 잠금을 사용한다고 모든 문제가 자동으로 사라지는 건 아니야. 어느 데이터와 연산 범위를 함께 보호할지 잘못 정하면 일부 경쟁이 남아 있을 수 있어.

즉, 경쟁은 메모리 공유 때문에 발생하기도 하고, 서로 다른 실행 흐름이 하나의 논리적 자원(DB의 현재 결과 등)을 변경하려 할 때도 발생해.

이를 해결하는 버전 확인, 원자적 결과 확정, 트랜잭션 등은 후속 소주제에서 상세히 배울 내용이지만, 지금은 이 원인까지 연결하면 충분해.

🔌 6. 서로 다른 프로세스는 어떻게 정보를 주고받을까?

1-1-1-17. 프로세스가 분리되면 변수도 분리된다

이제 서버와 WORKER를 별도의 프로세스로 실행한다고 가정해 보자.

서버 프로세스의 Python 코드에서 다음 변수를 만든다고 해보자.

job_status = {
    "job_17": "RUNNING"
}

다른 프로세스인 WORKER에서 같은 이름의 변수를 선언한다고 해도, 그 변수가 서버 메모리의 job_status와 자동으로 연결되지는 않아.

서로 다른 프로세스는 기본적으로 독립적인 주소 공간을 가지기 때문이야.

그렇다면 웹 서버가 WORKER에게 'job_17을 계산해'라고 전달하려면 무엇이 필요할까?

두 실행 환경 사이에 정보를 전달하는 별도의 통로가 필요해.

이를 프로세스 간 통신(IPC, Inter-Process Communication)이라고 해.

대표적인 수단에는 파이프, 소켓, 공유 메모리 등이 있어. 파일이나 DB, 메시지 큐도 프로세스 간 데이터를 교환하는 데 활용할 수 있지.

1-1-1-18. WORKER와 웹 서버의 역할을 분리해 보자

통근버스 예제를 생각해 보자.

웹 서버가 버튼 클릭을 받고, 별도 WORKER가 계산을 진행해.

가상 아키텍처: 웹 서버 프로세스(작업 요청 생성·서버 독립 메모리) ↔ IPC ↔ WORKER 프로세스(노선 계산·WORKER 독립 메모리). 두 프로세스가 SQLite DB 파일(작업 기록·확정된 노선·입력 데이터)에 접근한다. 이 그림만으로 동시 접근 안전성이나 장애 복구가 보장되는 것은 아니다.

구체적인 순서를 만들어 볼게.

  1. 서버가 운영자의 노선 생성 요청을 받는다.
  2. 서버가 DB에 작업 job_17을 생성하고 PENDING으로 기록한다.
  3. WORKER가 DB를 조회해 처리할 작업을 찾는다.
  4. WORKER가 작업 정보를 읽고 필요한 CSV 기반 데이터를 가져온다.
  5. WORKER의 메모리 안에서 노선을 계산한다.
  6. 계산 결과를 검증하고, 성공 결과를 DB에 저장한다.
  7. 서버가 DB의 상태와 결과를 조회해 사용자에게 보여준다.

이는 사용자에게 제공된 실제 제출 코드의 동작을 복원한 게 아니라, 설명을 위해 설계한 가상의 단일 서버·SQLite 구현 흐름이야.

특히 3단계에서 WORKER가 DB 작업을 가져오는 방식은 여러 가능한 IPC 설계 중 하나야.

프로세스들이 파일을 공유한다고 해서 서로의 메모리까지 공유하는 것은 아니야.

또한 DB 작업 테이블을 이용하려면 작업 중복 획득 방지, 실패 후 재처리, 원자적 작업 확보 등의 추가 설계가 필요해.

1-1-1-19. 별도 WORKER를 두면 무엇이 좋아질까?

별도 프로세스를 두는 이유를 단순히 '속도가 빨라지기 때문'이라고 설명하면 부정확해.

주요 장점은 역할과 장애 영향을 분리할 수 있다는 것이야.

노선 계산에 시간이 많이 걸리더라도 웹 서버는 상태 조회 등의 요청을 계속 처리하도록 설계할 수 있어.

WORKER만 종료되더라도 웹 서버 프로세스는 살아남을 수 있어.

또 CPython 환경에서는 CPU 중심 계산을 별도 프로세스로 분리함으로써 독립적인 Python 실행 환경에서 병렬 처리를 구성할 수 있어.

하지만 추가적인 비용도 있어.

  • WORKER를 별도로 실행하고 관리해야 해.
  • 프로세스 사이에 데이터를 전달해야 해.
  • 동일한 데이터를 각 프로세스 메모리에 중복 적재할 수 있어.
  • 작업이 중단되었을 때 이를 발견하고 복구하는 규칙이 필요해.
  • 한 WORKER가 처리할 작업을 다른 WORKER가 중복 처리하지 않도록 해야 해.

그리고 중요한 반례가 하나 있어.

WORKER가 별도 프로세스라고 해서 언제나 웹 서버 전체가 안정적으로 살아남는 것은 아니야.

예를 들어 둘이 같은 컨테이너에 있고 컨테이너가 종료되거나, 전체 시스템의 메모리가 부족해지거나, 공통 DB에 장애가 생기면 둘 다 영향을 받을 수 있어.

프로세스 격리는 장애 전파를 줄이는 수단이지, 완전한 장애 독립성을 보장하는 마법은 아니야.

💾 7. 메모리에 저장한 것과 DB에 저장한 것은 왜 다를까?

1-1-1-20. RAM과 SSD는 서로 다른 수명을 가진다

앞에서 사용한 current_plan 변수를 다시 생각해 보자.

current_plan = {
    "route_id": "R01",
    "capacity": 45
}

이 변수와 관련 객체는 실행 중인 Python 프로세스의 메모리에 있어.

따라서 프로세스가 정상적으로 종료하거나 강제 종료되면 해당 프로세스의 일반적인 메모리 상태는 사라져.

하지만 SSD에 있는 SQLite DB 파일은 보통 프로세스가 종료되어도 그대로 남아 있어.

왜 그럴까?

RAM은 전원이 공급되는 동안 동작 상태를 유지하는 휘발성 메모리고, SSD는 전원이 끊겨도 저장된 데이터를 유지하도록 만들어진 비휘발성 저장장치이기 때문이야.

단, SSD에 파일이 존재한다는 사실만으로 모든 장애에서 데이터가 절대 손실되지 않는다는 뜻은 아니야. 저장 완료 시점, 파일시스템과 장치의 내구성, DB의 동기화 설정, 장애 유형 등에 따라 실제 보장 범위는 달라져.

1-1-1-21. 변수 값을 DB에 저장한다는 것은 무엇을 의미할까?

Python의 current_plan 딕셔너리가 그대로 SSD 안으로 이동한다고 생각하기 쉬워.

실제로는 프로그램이 값을 DB가 이해하는 형태로 변환해서 저장 요청을 해야 해.

예를 들어 SQLite 테이블이 다음과 같다고 해보자.

CREATE TABLE plans (
    plan_id TEXT PRIMARY KEY,
    capacity INTEGER NOT NULL,
    status TEXT NOT NULL
);

Python 코드에서 다음 SQL을 실행할 수 있어.

import sqlite3

conn = sqlite3.connect("bus.db")

conn.execute(
    """
    INSERT INTO plans (plan_id, capacity, status)
    VALUES (?, ?, ?)
    """,
    ("R01", 45, "SUCCESS")
)

conn.commit()
conn.close()

이 코드는 bus.db라는 SQLite DB 파일에 행을 저장하도록 요청해.

commit()은 현재 트랜잭션의 변경 내용을 확정하는 동작이야.

일반적인 SQLite의 정상적인 설정과 저장 환경에서는 트랜잭션 커밋이 완료되면 이후 프로세스가 다시 DB 파일을 열어 해당 데이터를 조회할 수 있어.

다만 코드가 실행되었다는 사실만으로 커밋 성공 여부나 디스크 장애 상황까지 검증한 것은 아니야.

여기에선 실제 코드를 실행하지 않았으므로 이것은 설명용 코드야.

1-1-1-22. 프로세스가 종료되어도 DB가 남는 이유

다음 두 상황을 비교해 보자.

A. 메모리만 사용: 계산 → Python 변수 → 프로세스 종료 → 해당 상태 소멸.

B. DB 커밋 완료: 계산 → DB 저장 → 프로세스 종료 → DB 기록은 유지 가능.

오른쪽의 보존은 DB 파일이 영속적인 위치에 있고, 트랜잭션이 성공적으로 커밋되었으며, 저장장치 장애 등 별도 문제가 없다는 전제에 따른다.

여기서 영속성(persistence)이라는 용어를 이해할 수 있어.

영속성은 프로그램의 한 번 실행이 끝나더라도 필요한 데이터가 계속 존재하도록 보관하는 성질이야.

DB만 영속성을 제공하는 것은 아니야. 일반 파일도 영속적으로 저장할 수 있어.

DB는 단순한 파일 저장에 더해 검색, 제약조건, 트랜잭션, 동시 접근 관리 등 데이터를 체계적으로 다루는 기능을 제공하는 거야.

1-1-1-23. SQLite의 메모리와 디스크를 혼동하면 안 된다

SQLite를 사용한다고 해서 항상 DB 파일이 디스크에 저장되는 것은 아니야.

예를 들어 다음 코드는 메모리 DB를 생성해.

conn = sqlite3.connect(":memory:")

연결이 닫히고 해당 메모리 DB가 없어지면 그 데이터는 보존되지 않아. 별도 공유 메모리 DB 설정도 있지만 일반적인 파일 영속성과는 구분해야 해.

또 다음 두 저장 경로를 비교해 보자.

/app/bus.db
/data/bus.db

경로가 다르다고 해서 어느 쪽이 반드시 영속적이라고 결정할 수는 없어.

일반적인 Docker 환경에서는 컨테이너 내부 쓰기 계층에 저장한 파일이 동일 컨테이너의 프로세스 재시작 동안은 남을 수 있지만, 컨테이너를 삭제하고 다시 만들 때 사라질 수 있어.

반면 지속성 있는 볼륨이나 적절한 호스트 바인드 마운트에 저장하면 컨테이너 수명을 넘어 데이터를 유지하도록 구성할 수 있지.

서버 재시작 후 데이터가 남는다는 요구를 검증하려면, 무엇을 재시작하고 무엇을 삭제하는지까지 구분해야 해.

이것은 원본 시험에서 DB 영속성과 Dockerfile을 요구한 이유를 이해하는 데 직접 연결돼.

1-1-1-25. 정상적인 노선 생성 시나리오

아래의 가상 시스템은 하나의 서버 컴퓨터, 하나의 파일 기반 SQLite DB, 하나의 웹 서버 프로세스, 하나의 별도 WORKER 프로세스를 사용해.

운영자의 버튼 클릭부터 결과 확정까지

  1. 운영자 — 노선 생성 버튼 클릭: 브라우저가 서버로 요청 전송.
  2. 웹 서버 — 작업 기록 생성: DB에 PENDING 커밋.
  3. WORKER — 대기 작업 확보: 작업 데이터를 읽어 계산 시작.
  4. WORKER 메모리 — 후보 노선 생성: 임시 객체가 생성·변경됨.
  5. 검증 로직 — 규칙 충족 검사: 정원·배정·시간표 등 확인.
  6. SQLite — 결과 확정 트랜잭션: 성공 결과와 상태를 일관되게 커밋.
  7. 웹 서버 — DB에서 결과 조회: 최종 결과를 화면에 표시.

가상 설계 흐름. 5단계 검증과 6단계 저장을 어떻게 구현하느냐에 따라 실제 보장 수준이 달라진다.

이 흐름에서 누가 무엇을 소유하는지 구분해 볼게.

브라우저는 버튼과 화면 상태를 가지고 있어. 브라우저의 '생성 중' 표시는 실제 WORKER가 반드시 실행 중이라는 증거가 아니야.

웹 서버는 사용자의 요청을 받아 작업을 등록하고 결과를 조회해. 서버의 메모리에 작업 상태를 캐싱할 수는 있지만, 그 캐시가 진실의 유일한 근거가 되어서는 안 돼.

WORKER는 노선 계산을 실행해. 계산 중간에 생성한 후보 노선 객체들은 주로 해당 WORKER 메모리에 있을 수 있어.

SQLite는 커밋된 작업 기록과 최종 결과를 프로세스 실행 수명과 독립적으로 유지하는 역할을 해.

검증 로직은 계산된 결과가 요구사항을 충족하는지 판단해. 같은 WORKER 안에서 함수로 실행할 수도 있고 별도의 프로세스로 구성할 수도 있어.

여기서 구성요소의 책임과 물리적 실행 위치는 반드시 같은 개념이 아니라는 점이 중요해.

예를 들어 '계산기'와 '검증기'가 서로 다른 모듈이라도 둘 다 같은 Python 프로세스에서 실행될 수 있어.

반대로 동일한 계산 모듈을 여러 WORKER 프로세스에서 각각 실행할 수도 있지.

1-1-1-26. 별도 WORKER가 죽으면 정확히 어떤 일이 일어날까?

첫 번째 상황에서는 메모리의 임시 결과가 사라져. 하지만 DB에 이전 성공 결과가 저장돼 있었다면 함께 삭제될 이유는 없어.

두 번째 상황에서는 DB 트랜잭션이 중요해져. 정상적으로 SQLite의 트랜잭션을 사용했고, 새로운 결과 저장이 하나의 원자적 트랜잭션 안에 있다면 커밋되지 않은 변경은 롤백돼야 해.

단, 프로그램이 이미 별도 트랜잭션에서 일부 결과를 커밋했다면 이야기가 달라져. 따라서 단순히 SQLite를 사용했다는 사실만으로 전체 생성 결과의 원자성이 확보되는 것은 아니야.

세 번째 상황에서는 계산과 저장은 성공했는데, WORKER가 웹 서버에 완료 사실을 알리기 전에 종료될 수 있어.

웹 서버는 응답을 못 받았기 때문에 실패라고 생각할 수 있지만 DB에는 성공 결과가 있을 수 있지.

그래서 성공 여부를 메시지 수신 여부만으로 판단하면 안 돼.

커밋된 DB 상태를 조회하고, 재시도 요청이 왔을 때 이미 확정된 결과를 중복 생성하지 않도록 설계해야 해.

이것이 작업 상태 관리와 멱등성 설계가 필요한 이유야.

1-1-1-27. WORKER가 죽었다고 작업 상태가 자동으로 FAILED가 될까?

아니야.

이것은 특히 자주 혼동하는 부분이야.

WORKER 메모리에 작업 상태가 다음처럼 있었다고 해보자.

status = "RUNNING"

그리고 WORKER가 강제 종료됐어.

그 변수를 FAILED로 바꾸는 Python 코드는 더 이상 실행되지 못해.

DB에 RUNNING 상태를 미리 저장해 두었다면 DB에는 여전히 RUNNING이 남을 수 있어.

따라서 시스템에 별도의 감지·복구 로직이 없다면 화면에서는 실제로 종료된 작업을 계속 실행 중으로 표시할 수도 있어.

이 문제를 해결하려면 작업 상태만이 아니라 마지막 진행 시각, 소유 WORKER, 실행 제한시간 또는 임대 만료 시각 등으로 중단된 작업을 판별할 수 있어야 해.

예를 들어 다음과 같은 가상 작업 기록을 생각해 보자.

job_id        job_17
status        RUNNING
worker_id     worker_1
heartbeat_at  10:05:00

10:10이 되었는데 WORKER가 살아 있는지 확인되지 않고 heartbeat 갱신도 없다면, 복구 로직이 작업을 재확인할 수 있어.

하지만 heartbeat가 늦다는 사실만으로 WORKER가 반드시 죽었다고 확정할 수는 없어. 일시적인 지연이나 멈춤도 가능하니까.

그래서 감지 이후의 작업 소유권 회수와 결과 확정 경쟁까지 고려해야 해.

작업을 중단된 것으로 감지하는 것과 안전하게 재실행하는 것은 별개의 문제라는 뜻이야.

1-1-1-28. 사용자에게 보이는 결과는 어떻게 설계해야 할까?

메모리와 DB의 원리를 응용하면 다음 원칙을 만들 수 있어.

생성 중에는 현재 작업 상태를 표시하고, 이전 결과가 있다면 그 결과가 이전 데이터셋의 것임을 명확하게 표시해야 해.

새로운 계산이 성공하고 검증과 DB 커밋이 완료되기 전까지는 새 결과를 확정된 계획으로 표시하지 않아야 해.

새 계산이 실패하면 실패 사실과 원인을 보여주되, 기존 성공 결과를 무조건 삭제하지 않아야 해.

그리고 기존 결과가 남아 있더라도 현재 적용 데이터셋과 맞지 않는다면 새 데이터에 대한 유효한 계획으로 제시하면 안 돼.

여기서 핵심은 다음 세 가지 사실을 분리하는 거야.

  • 존재: 데이터가 메모리나 DB에 있는가?
  • 완료: 계산과 검증, 결과 확정이 성공했는가?
  • 유효성: 그 결과가 현재 요청한 데이터셋과 조건에 대응하는가?

셋 중 하나만 참이라고 해서 나머지 둘도 참이 되는 것은 아니야.

⚙️ 9. 실제 코드의 실행 순서로 소유권을 확인해 보자

지금까지는 개념과 그림으로 설명했어. 이번에는 코드 몇 줄을 실행 흐름에 대응시켜 볼게.

다음은 실제 제출 코드가 아니라 별도 WORKER의 메모리 상태와 SQLite 저장을 설명하기 위한 가상 Python 코드야.

1-1-1-29. 메모리에서 계산한 결과는 아직 확정 결과가 아니다

import sqlite3

def calculate_routes(dataset):
    # 설명용: 실제 노선 최적화 아님
    return {
        "dataset": dataset,
        "routes": [
            {"id": "R01", "capacity": 45}
        ]
    }

def run_job():
    # 1. 입력 데이터 준비
    dataset = "dataset_v2"

    # 2. WORKER 메모리에서 계산
    candidate = calculate_routes(dataset)

    # 3. 계산 결과 검증 (예제용 최소 조건)
    if not candidate["routes"]:
        raise ValueError("생성된 노선이 없습니다.")

    # 4. DB 저장
    conn = sqlite3.connect("bus.db")

    try:
        with conn:
            conn.execute(
                """
                INSERT INTO plans
                    (plan_id, capacity, status)
                VALUES (?, ?, ?)
                """,
                ("R01", 45, "SUCCESS")
            )
    finally:
        conn.close()

run_job()

위 코드가 실행된다고 가정하고, 각 시점에서 결과가 어디에 있는지 보자.

시점 메모리 DB 종료되면?
calculate_routes() 전 입력 정보 기존 데이터 새 계산 결과 없음
candidate 생성 직후 새 노선 객체 새 결과 없음 계산 결과 소실

커밋 완료 후 객체가 남아 있을 수 있음 새 행 확정 정상 저장 환경에서 결과 보존

여기서 with conn: 블록을 정상적으로 벗어나면 SQLite 트랜잭션이 커밋되고, 예외가 발생하면 롤백되는 방식으로 동작해. 다만 이 동작은 Python sqlite3의 트랜잭션 설정에도 영향을 받아.

주의할 점은 이 코드가 시험 요구사항을 충족하는 완성 구현이 아니라는 것이야.

실제 노선 계산도 없고, 전체 근무자 배정도 없고, 출퇴근 시간표 검증도 없어. 작업 상태 관리, 데이터셋 버전 관리, 기존 결과 보호, 재시도 중복 방지도 없어.

반례 C. DB에 SUCCESS가 있으므로 새 데이터셋에 적합하다?

반례 D. WORKER가 죽었으니 DB 상태가 FAILED일 것이다?

자동으로 그렇게 되지는 않아.

종료된 WORKER는 더 이상 상태 갱신 코드를 실행하지 못할 수 있어. 따라서 DB에는 RUNNING이 남아 있을 수 있어.

별도의 모니터링과 복구 로직이 필요해.

반례 E. DB 커밋을 했으니 모든 장애에서 데이터가 절대 안전하다?

DB 커밋은 중요한 영속성 경계지만, 어떤 장애에서도 절대적인 보장을 한다는 뜻은 아니야.

🧭 13. 이번 소주제에서 얻어야 하는 가장 중요한 이해

이 수업의 중심에는 하나의 질문이 있었어.

코드로 계산한 데이터는 언제 생기고, 누가 소유하며, 언제까지 남아 있는가?

코드는 저장된 명령이고, 프로세스는 실행 환경이며, 스레드는 그 안에서 명령을 수행하는 흐름이야.

프로세스의 메모리에는 실행 중 필요한 객체와 상태가 존재해. 같은 프로세스의 스레드는 이러한 상태에 함께 접근할 수 있어서 동기화가 필요할 수 있어.

별도 프로세스는 기본적으로 서로 다른 메모리 공간을 가지므로 통신 수단이 필요해.

그리고 프로세스가 종료되어도 데이터를 유지하려면 파일이나 DB 등의 영속 저장소가 필요하지.

통근버스 서비스를 설명한다면 다음처럼 이야기할 수 있어.

운영자가 노선 생성을 요청하면 서버가 작업을 등록하고 WORKER가 계산을 실행할 수 있습니다. WORKER는 입력 데이터로부터 메모리 내에 임시 노선 후보를 생성합니다. 이 후보는 아직 확정된 결과가 아닙니다.

계산이 검증을 통과하고 SQLite 트랜잭션이 성공적으로 커밋되면, 결과는 WORKER 프로세스의 수명과 독립적으로 유지될 수 있습니다. 계산 중 WORKER가 종료되면 메모리의 임시 객체는 사라지지만 기존에 커밋된 성공 결과까지 자동으로 삭제되지는 않습니다.

다만 실제 작업 상태가 DB에 올바르게 반영되었는지, 새 결과가 현재 적용 데이터셋과 조건에 대응하는지는 별도로 확인해야 합니다. WORKER의 종료 여부와 결과의 유효성은 DB에 데이터가 존재한다는 사실만으로 결정되지 않습니다.

이 설명은 특정 구현의 검증 결과가 아니라, 오늘 학습한 원리로부터 도출할 수 있는 설계 설명이야.

제공된 시험 복기에서 기억한 질문들도 바로 이런 관계를 추궁하고 있어. 특히 WORKER 종료 시의 상태, 진행 중 작업과 임시 결과의 소유자, 기존 성공 결과와 DB의 관계를 구분할 수 있어야 해.

이제 네가 실제 코드를 보게 되면 단지 worker.py가 있다는 이유로 별도 프로세스라고 판단하지 말고, 어떻게 실행되며 어느 메모리를 사용하고, 어느 시점에 어떤 DB 트랜잭션을 커밋하는지를 확인해야 해.

그 차이를 설명할 수 있는 것이 이 소주제의 학습 목표야.
