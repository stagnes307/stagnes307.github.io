🧱 1. 컴퓨터는 무엇을 실제로 실행할까?

프로그램은 저장된 설명서이고, 프로세스는 실행 중인 실체야

Python으로 다음과 같은 프로그램을 작성했다고 생각해 보자.

def create_routes():
    # 통근버스 노선 계산
    ...

def get_my_route():
    # 구성원의 노선 조회
    ...

이 코드를 파일에 저장했다고 해서 컴퓨터가 노선을 계산하고 있는 건 아니야. 파일은 어디까지나 실행할 일을 적어 둔 프로그램이지.

Python 인터프리터가 프로그램을 실행하면 운영체제는 그 실행을 관리하기 위한 자원을 준비해. 이렇게 실행 중인 프로그램의 독립적인 실행 단위를 프로세스(Process)라고 해.

프로세스에는 실행할 코드 외에도 계산 중인 값, 메모리 공간, 열린 파일과 네트워크 연결 같은 자원이 관계돼.

그런데 프로세스 내부에서도 여러 실행 흐름을 만들 수 있어. 이것이 스레드(Thread)야.

프로세스와 스레드의 관계 — 개념도

두 스레드는 같은 프로세스의 메모리 공간을 공유할 수 있어. 하지만 실행 위치와 호출 스택은 각자 가져.

여기서 메모리는 중요한 역할을 해.

  • 프로세스는 일반적으로 다른 프로세스와 분리된 가상 주소 공간을 가져.
  • 스레드는 같은 프로세스의 메모리를 공유하므로 같은 객체를 읽고 수정할 수 있어.
  • 각 스레드의 호출 스택에는 현재 어느 함수를 실행 중인지, 함수의 지역 상태가 무엇인지 등이 관리돼.

메모리를 공유하는 덕분에 스레드는 데이터를 주고받기 편하지만, 동시에 수정하면 충돌할 수도 있어. 반면 별도 프로세스는 메모리 격리가 강한 대신 데이터를 교환하려면 별도 통신 방법이 필요하지.

단, 프로세스가 분리되어 있다고 모든 자원이 격리되는 것은 아니야. 두 프로세스가 같은 SQLite 파일을 열 수도 있고, 같은 네트워크 서비스에 접근할 수도 있어.

CPU는 코드를 실행하지만, 대기하는 작업까지 계속 계산하지는 않아

CPU는 프로그램 명령을 수행하는 하드웨어야. CPU 안에는 여러 코어가 있을 수 있고, 각 코어가 실행 자원을 제공해.

여기서 중요한 상황을 하나 보자.

웹 서버가 DB에서 노선 정보를 조회했다고 해 보자. DB에서 답이 돌아오기까지 100밀리초가 걸린다면 그 100밀리초 내내 CPU가 노선 조회 결과를 계산하고 있는 걸까?

그렇지 않아. 상당 시간은 디스크, DB 연결, 운영체제 또는 다른 장치에서 결과가 준비되기를 기다리는 시간일 수 있어.

이때 스레드는 대기 상태에 들어갈 수 있고, 운영체제는 CPU를 다른 실행 흐름에 배정할 수 있어.

바로 이 CPU 실행 시간과 대기 시간이 다르다는 사실이 동시성을 이해하는 출발점이야.

⏱️ 2. 동시에 진행된다는 것은 동시에 계산한다는 뜻일까?

두 작업을 준비해 보자.

  • 작업 A: 통근버스 노선을 계산한다.
  • 작업 B: 구성원이 자기 노선을 조회한다.

먼저 CPU 실행 자원이 하나뿐인 상황을 가정할게.

첫 번째 시간표: 작업을 순서대로 끝내는 경우

시간표 A · 순차 실행 (가상 시간)

설명을 위한 예시: A 300ms, B 50ms. B는 A가 끝난 뒤 시작해 350ms에 완료돼.

이 방식은 이해하기 쉬워. 작업 A를 시작하고 끝내고, 그다음 B를 실행하면 돼.

문제는 A가 오래 걸릴 때야. B가 단순 조회 요청이어도 앞에 있는 작업이 끝나지 않으면 기다려야 해.

두 번째 시간표: 작업을 번갈아 진행하는 경우

운영체제가 CPU 실행 시간을 나누거나 작업이 스스로 제어권을 양보한다면 작업이 번갈아 진행될 수 있어.

시간표 B · 동시성, 단일 실행 자원

개념적 예시. A를 잠시 중단하고 B를 처리한 뒤 A를 이어서 실행할 수 있어. 한순간에 실행되는 작업은 하나야.

이때 우리는 A와 B가 동시성(Concurrency)을 가진다고 말할 수 있어.

동시성은 여러 작업의 진행 기간이 겹치도록 실행을 조직하는 성질이야. 반드시 같은 순간에 두 작업의 명령을 실행할 필요는 없어.

CPU가 매우 빠르게 바뀌어 가며 실행하기 때문에 사람에게는 여러 일이 동시에 이루어지는 것처럼 보일 수 있지.

여기서 오해하면 안 되는 게 있어. CPU를 번갈아 사용하는 데는 작업 전환 비용이 발생할 수 있어. 따라서 동시성은 반드시 전체 작업을 더 빨리 끝내기 위한 기술은 아니야. 다른 작업이 오래 기다리지 않게 하거나, 대기 중인 자원을 활용하는 것이 중요한 목적일 수 있어.

세 번째 시간표: 정말 같은 순간에 계산하는 경우

이제 CPU 실행 자원 두 개를 사용할 수 있다고 해 보자.

시간표 C · 병렬성, 두 실행 자원

작업 A와 B가 겹치는 구간에 서로 다른 코어에서 실제 명령을 실행하는 예시야. B는 A의 완료를 기다릴 필요가 없어.

이것이 병렬성(Parallelism)이야.

동시성과 병렬성의 차이는 작업 진행 기간을 보는지, 실제 실행 자원을 보는지에 있어.

병렬 실행은 동시성의 한 구현 방식일 수 있지만, 동시성이 곧 병렬성은 아니야.

또 하나 주의할 점이 있어. 프로세스 두 개를 만들었다고 무조건 병렬 실행되는 것은 아니야. 실제 코어 배정, 사용 가능한 CPU 수, 운영체제 스케줄링, 실행 환경의 제한에 따라 달라져.

둘을 구별하는 가장 유용한 질문

작업 A를 실행하는 동안 B가 중간에 진행할 수 있다면 동시성 관점에서 의미가 있어. 하지만 실제 같은 순간에 서로 다른 계산 자원이 A와 B의 명령을 수행해야 병렬성의 증거가 돼.

그래서 실행 로그에서 A의 시작 시각과 B의 시작 시각이 겹쳤다고 해서 실제 병렬 계산을 증명할 수는 없어. 실행 시작부터 끝까지에는 기다리는 시간도 포함되기 때문이야.

🔄 3. 비동기는 CPU보다 '호출자가 기다리는 방법'에 관한 개념이야

앞에서는 CPU가 어떤 작업을 실행하는지 관찰했어. 이제 시선을 옮겨 보자.

웹 서비스에서 운영자가 '노선 생성' 버튼을 누르면 브라우저가 서버에 요청을 보내. 서버는 노선 생성 함수를 호출할 거야.

여기서 호출자(Caller)란 다른 함수나 작업을 시작하도록 요청한 쪽이야. 어떤 함수가 다른 함수를 호출할 수도 있고, 웹 요청을 보낸 서버 코드가 DB 작업의 호출자가 될 수도 있어.

동기: 결과를 받아야 다음 단계로 진행할 수 있는 관계

result = create_routes()
save_result(result)

이 코드는 create_routes()의 결과를 받은 다음 save_result()를 실행해.

create_routes()가 10초 걸린다면 해당 실행 흐름은 그 결과 없이 다음 줄로 넘어갈 수 없어.

이러한 관계를 동기(Synchronous)라고 설명할 수 있어. 호출자는 호출한 작업의 완료와 자신의 다음 동작을 맞춰 진행해.

여기서 한 가지를 구분해야 해. 동기 호출이라고 해서 CPU가 반드시 10초 내내 계산하는 것은 아니야. 그동안 호출 스레드가 DB나 외부 장치의 응답을 기다릴 수도 있지.

비동기: 작업을 시작한 뒤 완료를 나중에 확인할 수 있는 관계

이번에는 실행 구조를 바꿔 볼게.

job_id = submit_route_job()

# 계산 결과를 기다리지 않고 다른 일을 진행
show_job_status(job_id)

submit_route_job()이 실제 계산을 끝낼 때까지 기다리지 않고 작업 접수 정보인 job_id를 돌려준다고 가정한 예시야.

호출자는 '노선 생성 완료'를 기다리지 않고 다음 동작으로 진행할 수 있어. 계산은 다른 실행 주체가 맡아 계속 진행하고, 나중에 상태를 확인하거나 완료 통지를 받으면 돼.

이것이 비동기(Asynchronous)의 핵심이야.

비동기는 일이 자동으로 빨라진다는 뜻이 아니라, 호출자와 작업 완료 시점을 분리할 수 있다는 뜻이야.
같은 작업, 서로 다른 호출 구조
동기 호출
비동기 접수

설명용 순서도. 왼쪽은 계산이 끝난 뒤 호출자가 진행해. 오른쪽은 작업을 접수한 뒤 호출자가 다른 일을 할 수 있어.

그런데 여기에는 함정이 하나 있어.

job_id = submit_route_job()
while not is_finished(job_id):
    pass

작업을 비동기로 접수했지만 호출자가 곧바로 반복문에서 완료 여부만 계속 확인한다면 어떨까?

작업 시작 방식은 비동기여도 호출자는 실질적으로 다음 유용한 일을 진행하지 못해. 게다가 이 반복문은 CPU를 계속 소비할 수 있어.

따라서 비동기 구조의 유용성을 판단하려면 단순히 '나중에 결과를 받는다'는 사실뿐 아니라 기다리는 동안 어떤 실행 자원을 해방하고, 어떤 다른 일을 진행할 수 있는가까지 봐야 해.

🚦 4. 동기·비동기와 블로킹·논블로킹은 왜 다른 말일까?

이제 하나 더 구분할 필요가 있어.

우리가 대기한다는 말을 쓰고 있지만, '결과를 기다리는 관계'와 '실행 흐름이 실제로 멈추는 상태'는 서로 다른 관점이야.

블로킹(Blocking)은 어떤 작업이 완료되거나 필요한 조건이 만족될 때까지 호출 실행 흐름이 계속 진행하지 못하는 상황을 뜻해.

논블로킹(Non-blocking)은 요청한 작업이 아직 완료되지 않았더라도 해당 호출에서 제어권을 반환해 호출 흐름이 계속 진행할 수 있게 하는 성질이야.

예를 들어 네트워크에서 데이터를 읽는 상황을 생각해 보자.

  • 블로킹 읽기: 아직 데이터가 없으면 스레드가 데이터 도착을 기다려.
  • 논블로킹 읽기: 데이터가 준비되지 않았으면 곧바로 '지금은 읽을 수 없음' 상태를 반환할 수 있어.

이제 두 축을 결합하면 네 가지 상황이 생겨.

이 표는 두 축이 독립적이라는 것을 보여 주기 위한 개념적 분류야. 실제 API에서는 '동기/비동기'를 호출 자체의 반환 시점으로 정의하기도 하므로, 분류할 때 어떤 호출과 전체 작업 흐름을 기준으로 삼았는지 밝혀야 해.

특히 await가 포함된 코드를 무조건 블로킹이라고 판단하면 안 돼.

await를 수행하면 해당 코루틴은 결과가 준비될 때까지 진행을 멈출 수 있어. 하지만 적절한 비동기 작업을 기다리는 동안 이벤트 루프 스레드는 다른 작업을 실행할 수 있지.

즉,

  • 현재 코루틴은 결과가 필요하므로 잠시 중단된다.
  • 이벤트 루프 전체가 반드시 멈추는 것은 아니다.
  • 운영체제 스레드가 멈춘 것과 코루틴이 중단된 것은 다르다.

🧮 5. CPU 중심 작업과 입출력 중심 작업은 왜 다르게 다룰까?

지금까지는 작업을 하나의 상자로 표현했어. 하지만 실제 작업 안에는 계산과 대기가 섞여 있어.

CPU 중심 작업

CPU 중심 작업(CPU-bound)은 실행 시간 중 실제 계산에 쓰는 CPU 시간이 큰 작업이야.

통근버스 노선 서비스라면 다음 과정이 여기에 해당할 가능성이 있어.

정류장 후보의 조합을 비교하고, 구성원을 배정하고, 차량 정원과 시간을 계산하고, 여러 대안의 품질 점수를 비교하는 과정이지.

예를 들어 1,500명의 구성원을 여러 정류장 후보에 배정하는 최적화 알고리즘이 복잡하다면, CPU는 반복해서 후보를 평가해야 할 수 있어.

이런 작업에서 스레드를 단순히 늘리는 것만으로 계산 시간이 줄어들지는 않아. CPU 실행 자원이 부족하거나 Python 실행 환경의 제약이 있다면 오히려 스레드 전환과 동기화 비용이 늘어날 수 있어.

입출력 중심 작업

입출력 중심 작업(I/O-bound)은 외부 시스템이나 장치의 응답을 기다리는 시간이 큰 작업이야.

통근버스 서비스에서는 다음 상황이 가능해.

  • SQLite에서 저장된 노선을 읽어 오는 작업
  • 브라우저에 HTTP 응답을 전송하는 작업
  • 별도 WORKER로부터 작업 완료 메시지를 기다리는 작업
  • 파일에서 CSV 데이터를 읽는 작업

다만 'DB 작업은 언제나 I/O 중심'이라고 단정하면 안 돼. 복잡한 DB 쿼리는 계산 비용이 클 수도 있고, 캐시에 들어 있는 자료는 디스크 대기 없이 처리될 수도 있어.

계산과 대기를 구분해 보자

같은 100ms 작업 안에서도 자원 사용은 달라질 수 있어

비율은 원리를 보여 주기 위한 가정이며 실제 노선 서비스의 측정값이 아니야.

위에서 CPU 중심 작업은 계산 시간이 길고, I/O 중심 작업은 기다리는 시간이 길어.

입출력 중심 작업을 처리할 때는 기다리는 동안 다른 요청을 진행하도록 구성하는 것이 유리할 수 있어. 반면 CPU 중심 작업은 실제 계산을 서로 다른 코어에서 실행할 수 있는지가 중요해.

🔁 6. 이벤트 루프는 한 스레드에서 어떻게 여러 요청을 다룰까?

이제 웹 프레임워크에서 자주 나오는 async, await, event loop를 연결해 보자.

여러 작업이 대기할 때 누가 다음 작업을 고를까?

웹 서버에 요청 세 개가 도착했다고 가정해 볼게.

A는 구성원 노선을 DB에서 읽고, B는 작업 상태를 조회하고, C는 노선 생성 작업을 접수해.

세 요청이 모두 다른 시스템의 응답을 기다리는 순간이 있다면, 한 요청이 기다린다고 전체 스레드가 멈춰 있을 필요는 없어.

이러한 작업의 실행과 재개를 관리하는 것이 이벤트 루프(Event Loop)야.

이벤트 루프는 실행 가능한 작업을 진행하고, I/O 작업의 완료 같은 이벤트가 발생하면 기다리던 작업을 다시 실행하도록 스케줄링해.

하나의 이벤트 루프에서 세 작업이 번갈아 실행되는 모습

개념도. 세 작업을 동시에 CPU에서 실행한다는 의미가 아니라, 실행 가능한 작업 사이에서 제어권을 넘긴다는 뜻이야.

실제 이벤트 루프는 운영체제의 I/O 준비 상태 통지, 콜백, 타이머, 실행 준비 큐 등을 활용할 수 있어. 여기서 콜백(Callback)은 '어떤 일이 발생하면 실행하도록 등록한 함수'야.

다만 이벤트 루프가 알아서 모든 오래 걸리는 일을 중단시키지는 못해. 코드가 제어권을 양보할 수 있는 지점에 도달해야 다른 작업이 진행될 수 있어. 이것이 협력적 스케줄링의 핵심이야.

코루틴은 실행을 잠시 중단했다가 이어갈 수 있는 함수야

일반 함수는 호출되면 실행해서 값을 반환해. 코루틴(Coroutine)은 실행 상태를 보존한 채 중단되었다가 재개될 수 있는 실행 구조야.

Python에서는 async def로 코루틴 함수를 정의할 수 있어.

import asyncio

async def read_route():
    print("조회 시작")
    await asyncio.sleep(2)
    print("조회 완료")
    return {"route_id": "R-001"}

이 코드의 asyncio.sleep(2)는 실제 DB 조회가 아니야. 비동기 대기를 관찰하기 위한 가상 예제야.

우선 await에서 중요한 것은 '2초 쉬어라'가 아니라 '이 작업은 지금 진행할 수 없으니 제어권을 양보할 수 있다'는 점이야.

단, 코루틴에 await가 있다고 언제나 제어권을 양보하는 것은 아니야. 기다리는 대상이 즉시 완료된다면 중단하지 않고 계속 실행할 수 있어.

await를 쓴다고 두 작업이 자동으로 겹치는 것은 아니야

다음 코드를 보자.

async def main():
    a = await read_route()
    b = await read_route()

이 경우 첫 조회가 완료된 뒤 두 번째 조회를 시작해. 두 호출을 순서대로 기다리고 있기 때문이야.

반면 다음처럼 각각을 Task로 예약하면 두 작업을 겹쳐 진행할 기회를 만들 수 있어.

async def main():
    task_a = asyncio.create_task(read_route())
    task_b = asyncio.create_task(read_route())

    a = await task_a
    b = await task_b

여기서 Task는 이벤트 루프가 코루틴을 실행하도록 스케줄링하고 그 완료·오류·취소 상태를 관리하는 객체야.

create_task()는 코루틴을 실행 대상으로 예약해. 이후 await task_a는 A의 결과가 필요하다고 표시하고, A가 아직 완료되지 않았다면 호출 코루틴이 제어권을 양보할 수 있어. 그사이 이벤트 루프는 B를 실행할 수 있지.

Python 공식 문서도 코루틴 호출 자체가 실행을 예약하지 않는다는 점과 Task를 사용해 동시 실행을 스케줄링한다는 점을 구별해 설명하고 있어.

그렇다면 왜 await만 붙이면 해결된다는 설명이 위험할까?

다음 코드를 살펴보자.

async def create_routes():
    total = 0
    for i in range(100_000_000):
        total += i * i
    return total

async def handle_request():
    result = await create_routes()
    return result

코드에는 async와 await가 있어. 하지만 create_routes() 안의 계산 반복문에는 제어권을 양보하는 대기 지점이 없어.

따라서 일반적인 단일 이벤트 루프 스레드에서 이 코루틴을 실행하면 계산이 끝날 때까지 다른 코루틴이 실행될 기회를 얻지 못할 수 있어.

이것이 async def는 CPU 계산을 자동으로 다른 스레드나 프로세스로 옮기지 않는다는 중요한 반례야.

비슷하게 비동기 함수 내부에서 동기 time.sleep(2)를 직접 호출하면 해당 이벤트 루프 스레드가 블로킹될 수 있어. 반면 await asyncio.sleep(2)는 타이머 대기 동안 다른 Task의 실행을 허용하지.

입출력 호출도 마찬가지야. 동기 SQLite 호출을 단순히 async def 안에 넣었다고 자동으로 비동기 DB 호출이 되는 것은 아니야. 필요하다면 전용 스레드, 스레드 풀 또는 적절한 비동기 인터페이스를 사용해야 해.

그렇다고 await를 자주 추가하기만 하면 CPU 중심 문제가 해결되는 것도 아니야. CPU 작업이 제어권을 양보하도록 나누면 응답성은 개선할 수 있어도 CPU 계산 자체가 병렬화되는 것은 아니야.

🧵 7. 스레드와 프로세스는 어떤 문제를 해결할까?

이제 이벤트 루프와는 다른 방법으로 실행 흐름을 분리해 보자.

스레드: 같은 프로세스 안에서 실행 흐름을 늘린다

웹 서버 프로세스에 두 개의 스레드가 있다고 가정하자.

하나는 구성원의 DB 조회를 처리하고, 다른 하나는 외부 시스템의 응답을 기다려.

스레드는 같은 프로세스의 메모리를 공유하지만 운영체제에 의해 서로 다른 실행 흐름으로 스케줄링될 수 있어.

스레드는 동기적인 입출력 함수를 처리할 때도 유용해. 한 스레드가 블로킹 I/O로 기다리더라도 다른 스레드는 실행될 수 있으니까.

하지만 메모리를 공유하기 때문에 문제가 생길 수 있어.

# 두 스레드가 공유한다고 가정
job_status = {"status": "RUNNING"}

스레드 A가 상태를 SUCCEEDED로 바꾸고, 스레드 B가 동시에 다른 필드를 수정한다고 해 보자.

단순한 변수 하나보다 여러 필드를 함께 갱신하는 경우가 특히 위험해. 읽는 시점에 따라 상태와 결과가 서로 맞지 않을 수도 있어.

이 문제를 다루기 위해 락(Lock) 같은 동기화 수단이 필요해.

락은 임계 구역(Critical Section), 즉 동시에 실행되면 데이터가 손상되거나 규칙이 깨질 수 있는 코드 구간에 여러 실행 흐름이 함부로 들어오지 못하게 해.

그러나 락을 남용하면 작업들이 서로를 기다리느라 동시성의 이점이 사라질 수 있어.

프로세스: 별도 메모리 공간과 실행 환경으로 분리한다

이번에는 노선 계산을 별도 프로세스에서 실행한다고 해 보자.

웹 서버 프로세스
  ├─ 운영자 요청 접수
  ├─ 구성원 조회 응답
  └─ 작업 상태 저장
            │
            ▼
       별도 WORKER 프로세스
            ├─ 입력 데이터 조회
            ├─ 노선 계산
            └─ 검증 결과 기록

별도 프로세스는 각자 독립적인 메모리 공간을 가지므로, 웹 서버의 Python 객체를 WORKER가 일반 변수처럼 직접 읽고 쓰지는 못해.

그래서 둘 사이에 정보를 전달할 방법이 필요해. 예를 들면 데이터베이스, 프로세스 간 큐, 파이프, 소켓 등이 있어.

이 분리가 중요한 이유는 두 가지야.

첫째, 웹 서버가 긴 계산을 직접 수행하지 않도록 할 수 있어. 둘째, 별도 프로세스를 다른 CPU 코어에서 실행하도록 운영체제가 배정할 수 있어.

하지만 분리만으로 장애 격리와 복구가 완성되지는 않아. WORKER가 계산 도중 종료될 수 있고, 작업을 재시작할 때 중복 실행이 발생할 수도 있으며, 데이터 전달과 직렬화에도 비용이 들어.

여기서 직렬화(Serialization)는 프로그램 내부의 객체를 JSON이나 바이트처럼 전달·저장 가능한 표현으로 변환하는 과정이야.

Python 코드를 학습할 때 자주 나오는 문장이 있어.

"Python은 GIL 때문에 스레드로 병렬 처리를 못 한다."

이 문장은 너무 넓게 일반화한 설명이야.

GIL이 무엇을 보호하는가?

일반적인 GIL 활성화 CPython에서는 여러 스레드가 같은 인터프리터의 Python 객체와 내부 상태를 다룰 때 충돌하지 않도록 전역 인터프리터 락(Global Interpreter Lock)을 사용해.

그 결과 보통 하나의 CPython 인터프리터에서 한순간에 Python 코드를 실행할 수 있는 스레드가 제한돼.

따라서 순수 Python 계산을 여러 스레드로 분할해도, GIL이 켜진 일반적인 CPython 환경에서는 여러 코어에서 해당 Python 계산을 동시에 실행하는 성능 향상을 기대하기 어려워.

그러나 입출력 대기 중에는 GIL을 해제할 수 있고, 일부 C 확장 라이브러리는 GIL을 해제한 상태에서 실제 병렬 계산을 수행할 수 있어.

왜 Python 버전과 구현체를 확인해야 할까?

CPython 3.13부터는 GIL을 비활성화할 수 있는 별도의 free-threaded build를 지원하기 시작했어. 이 빌드에서는 적절한 조건에서 여러 스레드의 실제 병렬 실행이 가능해.

다만 빌드 종류, 실행 시점의 GIL 활성화 상태, 확장 모듈 호환성에 따라 결과가 달라져. 따라서 버전 번호만 보고 실제 병렬성을 단정할 수는 없어.

import sys
import sysconfig

이 코드 역시 여기서 실행한 결과를 제시하는 것은 아니야. 설치된 Python의 특성을 확인하는 방법을 보여 주는 것이고, 실제 CPU 병렬성까지 입증하려면 작업 실행 중 코어 사용과 수행 시간을 별도로 측정해야 해.

GIL이 없더라도 데이터 경쟁이 사라지는 것은 아니야. 공유 데이터가 안전하게 변경되도록 락이나 다른 동기화 방법을 설계해야 한다는 사실은 그대로 남아.

🚌 9. 통근버스 서비스에서는 어떤 실행을 겹칠 수 있을까?

이제 지금까지 배운 개념을 시험 사례에 연결해 보자.

제공된 시험 원문은 데이터셋 선택·검증·적용, 노선 생성과 재계산, 구성원별 노선 조회, 결과 내보내기를 요구해. 별도 WORKER나 특정 비동기 라이브러리를 반드시 쓰라는 요구사항은 아니야.

또한 복기 자료에서는 생성 중 시간 제한, WORKER 종료, 검증 실패 시 남는 상태와 Creator·Validator 분리 이유가 질문으로 등장해.

여기서부터는 단일 웹 서버 + SQLite + 별도 계산 WORKER를 선택했다고 가정하는 설계 사례야. 실제 제출 코드를 확인한 결과는 아니야.

운영자가 생성 버튼을 누른 뒤의 실행 흐름

가상 구현의 작업 흐름과 소유권

설명용 설계. Validator는 WORKER 내부에서 호출하거나 별도 실행 단위로 만들 수 있어. 위 그림의 분리는 논리적 책임이며 반드시 별도 프로세스라는 뜻은 아니야.

전체 흐름을 시간에 따라 보면 다음과 같아.

  1. 운영자가 생성 요청을 보내면 서버는 적용 중인 데이터 버전과 계산 조건을 확인해.
  2. 서버는 SQLite 트랜잭션으로 작업을 QUEUED 상태로 기록하고, 작업 ID를 반환해. 이 설계에서는 SQLite의 작업 테이블 자체를 큐로 사용해.
  3. WORKER가 작업을 가져와 RUNNING으로 변경하고, 고정된 입력 조건으로 Creator를 실행해.
  4. Creator가 정류장·배정·시간표의 임시 후보 결과를 생성해.
  5. Validator가 후보 결과를 독립적으로 검사하고, 통과한 결과만 최종 확정 절차로 보내.
  6. 서버는 구성원 조회와 작업 상태 조회를 계속 처리하고, 브라우저는 별도 요청으로 QUEUED, RUNNING, SUCCEEDED, FAILED 등의 상태를 확인해.

이 구조에서는 브라우저가 최초 요청의 응답을 기다리는 시간이 전체 노선 계산 시간과 같을 필요가 없어.

하지만 서버가 단순히 async def generate() 안에서 Creator의 거대한 계산 반복문을 직접 호출했다면 상황은 달라져. 이벤트 루프가 막혀 조회 응답이 지연될 수 있지.

그렇다고 별도 WORKER를 사용한다고 자동으로 모든 조회가 빨라지는 것도 아니야. CPU 코어가 부족하거나 SQLite 쓰기 락 경합이 심하면 조회 역시 영향을 받을 수 있어.

Creator와 Validator는 어느 부분을 병렬 처리할 수 있을까?

여기서 가장 중요한 것은 데이터 의존성(Data Dependency)이야.

작업 B가 작업 A의 출력을 반드시 필요로 한다면, B의 해당 부분은 A의 출력이 준비되기 전에는 정확하게 수행할 수 없어.

계산 의존성 그래프

가상 구조. 독립적인 후보 A와 B는 생성·검증을 겹쳐 진행할 수 있지만, 최종 비교는 필요한 검증 결과를 확보한 뒤 수행해야 해.

여기서 구분해야 하는 경우가 세 가지 있어.

첫째, 같은 후보에 대한 생성과 최종 검증.

Creator가 아직 후보를 완성하지 않았는데 Validator가 완성된 후보처럼 검증하면 안 돼. 일부 정류장만 배정된 중간 결과에 대해 '전원 배정'을 검사하면 당연히 실패할 테니까.

따라서 하나의 최종 후보를 검증할 때는 생성 완료라는 선행 조건이 필요해.

둘째, 서로 독립적인 후보를 여러 개 생성하는 경우.

후보 A와 B가 독립적이라면 별도 프로세스에서 동시에 계산할 수 있어. A가 먼저 완성되면 A의 Validator가 시작될 수 있고, B는 그동안 계속 계산할 수 있지.

단, 두 후보가 같은 수정 가능한 자료를 공유하거나 서로의 탐색 상태에 의존한다면 독립적이라고 볼 수 없어.

셋째, 생성 도중 일부 규칙을 검사하는 경우.

예를 들어 Creator가 버스 한 대의 배정을 완성할 때마다 차량 정원 초과를 검사하는 것은 가능해. 그러나 이 부분 검사만으로 전체 근무일의 전원 배정까지 검증했다고 주장하면 안 돼.

이 차이를 설명할 때는 '검증기가 병렬 실행된다'고만 말하지 말고, 어떤 데이터가 언제 완성되고, 무엇이 독립적으로 검사 가능한지를 밝혀야 해.

복기 자료의 Creator·Validator라는 표현은 두 의미가 모두 가능해.

  • 업무상의 Creator·Validator: 노선 계획을 생성하고 그 결과를 검증하는 컴포넌트
  • AI 개발 과정의 Creator·Validator: 코드를 작성하는 에이전트와 그 코드를 검토하는 에이전트

후자의 경우에도 검토 대상 코드가 아직 작성되지 않았다면 그 코드의 최종 검증은 불가능해. 하지만 요구사항 분석, 검사 기준 작성, 테스트 데이터 설계처럼 작성 결과에 의존하지 않는 준비 작업은 겹칠 수 있지.

데이터가 바뀌는 순간에는 무엇이 더 필요할까?

가상 상황을 보자.

  • 10:00:00 — 작업 A가 데이터 버전 7로 계산 시작
  • 10:00:03 — 운영자가 데이터 버전 8 적용
  • 10:00:05 — 작업 A의 계산 완료
  • 10:00:06 — A 결과를 최신 결과로 저장하려고 시도

A가 생성한 결과가 내부 규칙을 모두 만족해도, 현재 적용 데이터 버전 8의 결과는 아니야.

이때 단순히 'Validator 성공'이라는 이유만으로 최신 결과에 덮어쓰면 데이터 적용 이후의 결과 표시가 잘못돼.

따라서 작업에는 입력 버전과 계산 조건을 기록하고, 최종 결과 확정 시점에 현재 적용 데이터와의 관계를 확인해야 해. 예를 들어 확정 트랜잭션 안에서 현재 버전이 작업의 입력 버전과 같은지 비교하고, 다르면 최신 결과로 게시하지 않는 방법이 있어.

이것은 CPU 병렬성 문제가 아니라 실행 순서가 겹치면서 발생하는 상태 정합성 문제야.

🗄️ 10. 같은 프로세스와 별도 프로세스, 여러 서버에서 무엇이 달라질까?

여러 작업이 겹치기 시작하면 '누가 어떤 데이터를 동시에 수정할 수 있는가'라는 문제가 생겨.

여기서는 단일 서버와 SQLite를 기본으로 보자.

같은 프로세스의 여러 스레드

같은 프로세스 안의 스레드들이 하나의 Python 딕셔너리를 공유한다면 threading.Lock 같은 락으로 접근을 조정할 수 있어.

하지만 이 락은 일반적으로 해당 프로세스 내부의 스레드 사이에서만 의미가 있어. 별도 프로세스의 WORKER가 같은 딕셔너리나 Python 락을 공유하는 것은 아니지.

또한 스레드 락만으로 SQLite 트랜잭션의 일관성이나 서버 재시작 이후의 상태 보존이 해결되는 것도 아니야.

같은 서버의 별도 프로세스

웹 서버와 WORKER가 별도 프로세스이고 같은 SQLite DB 파일을 사용한다면, 서로의 Python 변수는 분리돼 있어도 SQLite의 트랜잭션과 파일 잠금 메커니즘을 통해 DB 접근을 조정할 수 있어.

SQLite의 WAL(Write-Ahead Logging) 모드에서는 일반적으로 읽기와 쓰기가 겹쳐 진행될 수 있어. 그러나 동시에 활성화할 수 있는 쓰기 트랜잭션은 기본적으로 하나라는 제약이 남아. WAL이 쓰기 작업을 무제한 병렬화해 주지는 않아.

따라서 여러 WORKER가 결과를 동시에 저장하려 하면 잠금 대기가 발생할 수 있어.

작업을 안전하게 가져오는 과정에도 주의해야 해.

WORKER A: QUEUED 작업 발견
WORKER B: 같은 QUEUED 작업 발견
WORKER A: 작업 시작
WORKER B: 같은 작업 시작

단순히 SELECT로 대기 작업을 읽은 뒤 별도의 UPDATE를 수행하면 이런 경쟁 상태(Race Condition)가 발생할 수 있어.

이를 방지하려면 작업 획득을 적절한 트랜잭션에서 조건부로 처리하고, 하나의 WORKER만 작업 소유권을 획득하도록 설계해야 해.

반대로 SQLite 파일을 네트워크 파일시스템에 놓고 여러 서버가 WAL 모드로 공유하도록 만드는 것도 SQLite가 지원하는 일반적인 WAL 운영 방식이 아니야.

여러 서버로 확장하려면 일반적으로 네트워크 DB나 별도 작업 큐 등 서버 사이에서 상태를 일관되게 조정할 수 있는 구조를 고려해야 해.

여기서 중요한 것은 시스템 규모가 커질수록 동시성이란 단순 실행 문제가 아니라 공유 상태와 소유권의 문제가 된다는 거야.

브라우저가 비동기로 요청했다는 사실은 이 문제를 해결해 주지 않아. 비동기는 호출자가 기다리지 않게 하는 실행 방식이지, 작업을 영원히 살아 있게 해 주는 보장이 아니기 때문이야.

처음에 작업을 메모리 큐에만 저장했다면 웹 서버가 재시작될 때 접수된 작업 자체가 사라질 수 있어.

반면 작업 정보를 SQLite에 저장했다면 서버 재시작 이후에도 작업 상태를 확인할 수 있어. 다만 저장했다는 것만으로 재시도 로직이 생기는 것은 아니야.

예를 들어 WORKER가 주기적으로 마지막 생존 시각을 기록하고, 일정 기간 갱신되지 않은 작업을 복구 대상으로 식별하는 방법이 있어.

이 경우에도 단순히 오래된 작업을 재실행하면 문제가 생길 수 있어. 기존 WORKER가 종료된 것이 아니라 느려진 것뿐이라면 같은 작업을 두 번 실행할 수 있기 때문이야.

따라서 작업 재시도와 최종 확정에는 작업 ID, 실행 시도 번호, 작업 소유권, 조건부 상태 갱신 같은 추가 설계가 필요해.

타임아웃은 작업 종료를 보장할까?

서버가 10초 뒤 HTTP 응답을 포기했다고 가정해 보자.

HTTP 요청에 타임아웃이 발생했다고 해서 별도 WORKER 프로세스가 자동으로 종료되지는 않아. 작업은 계속 계산 중일 수 있어.

마찬가지로 Python의 코루틴 취소 요청도 별도 프로세스의 계산을 반드시 중단시키는 것은 아니야.

타임아웃, 취소 요청, 실제 프로세스 종료, DB 트랜잭션 롤백은 각각 다른 사건이야.

그 차이를 이해하면 '시간 제한이 발생했을 때 사용자에게 무엇이 남는가?'라는 질문에 단순히 '실패 메시지를 보여 줍니다'보다 훨씬 정확하게 답할 수 있어.

검증 실패 시 무엇을 보존해야 할까?

제공된 시험 원문에서는 데이터셋 검증에 실패했을 때 기존 적용 데이터와 생성 결과를 유지하도록 요구하고 있어.

노선 생성 결과도 비슷하게 확정 전 상태를 분리해서 설계할 수 있어.

작업 접수 → 계산 중 → 임시 결과 생성
                              │
                              ▼
                          Validator
                         /         \
                       통과        실패
                        │            │

                        │            │
                        ▼            ▼

위 구조는 하나의 가능한 설계야.

중요한 점은 Creator가 계산을 완료했다고 해서 곧바로 최종 결과를 게시하지 않는다는 것이지.

작업 결과가 규칙을 만족하는지 검증하고, 적용 데이터 버전과 계산 조건이 일치하는지 확인한 다음, 확정 과정이 원자적으로 처리되도록 해야 해.

여기서 원자적(Atomic)이란 관련된 DB 변경이 일부만 확정되는 상태를 피하도록 하나의 트랜잭션으로 묶는 성질이야.

가령 새 결과를 최신으로 지정하면서 이전 최신 결과를 해제하는 과정이 있다면, 두 변경 사이에 서버가 종료되어도 DB가 잘못된 중간 상태로 확정되지 않도록 해야 해.

이것은 비동기와 병렬성이 해결하는 문제가 아니라 트랜잭션과 상태 관리가 해결하는 문제야.

운영자가 노선 생성을 시작했는데 구성원의 노선 조회는 왜 계속 가능할까?

가능한 설명은 다음과 같아.

웹 서버는 노선 생성 요청을 받아 작업을 DB에 기록한 뒤, 계산이 끝날 때까지 HTTP 요청을 붙잡아 두지 않고 작업 ID를 반환해. 이 구조는 호출자 관점에서 비동기적이야.

별도 WORKER는 그 작업을 수행하고, 웹 서버는 다른 요청을 처리할 수 있어. 두 작업이 진행 기간을 겹치므로 동시성이 있어.

웹 서버와 WORKER가 다른 CPU 코어에서 실제 계산 명령을 동시에 수행한다면 병렬성도 있어. 하지만 같은 코어에서 번갈아 실행된다면 동시성은 있어도 그 순간의 병렬성은 없어.

반대로 웹 서버가 단일 이벤트 루프에서 CPU 중심 계산을 직접 오래 실행해 다른 요청을 처리하지 못한다면, 함수 선언에 async가 붙어 있더라도 기대한 응답성을 얻지 못할 수 있어.
