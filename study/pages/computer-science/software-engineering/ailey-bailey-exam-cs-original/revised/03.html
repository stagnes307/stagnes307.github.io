🚌 1. 버튼을 눌렀는데, 실제로 무엇이 움직였을까?

통근버스 노선을 만드는 웹 서비스가 있다고 생각해 보자.

운영자가 브라우저를 열고 데이터셋 dataset-B를 선택했어. 화면에는 다음과 같은 버튼이 있어.

통근버스 운영 관리 · 학습용 가상 화면

이 선택 화면은 브라우저 안의 설명용 모의 동작이야. 버튼을 눌러 요청값을 볼 수 있지만 실제 HTTP 서버나 DB를 바꾸지는 않아. 서버 요청의 실행 근거는 아래 별도 보충 실험에서 확인해.

이 화면은 실제 서버와 연결되지 않은 학습용 시뮬레이션이야. DB는 변경되지 않아.

이 버튼을 누르는 순간 데이터베이스가 자동으로 바뀌는 걸까?

아니야. 버튼은 브라우저 안에 있는 화면 요소일 뿐이야. SQLite 데이터베이스는 서버가 실행되는 환경에 있고, 브라우저는 그 데이터베이스의 내용을 마음대로 변경할 수 없어.

따라서 화면에 보이는 사용자 의도를 서버에 전달하는 과정이 필요해.

이것이 오늘 수업의 출발점이야.

그림 1. 요청과 응답이 통과하는 세 영역

세 영역은 논리적인 역할 구분이야. 개발 중에는 브라우저와 서버가 같은 컴퓨터에서 실행될 수도 있어.

여기서 처음으로 중요한 차이를 발견할 수 있어.

브라우저가 무언가를 요청했다는 사실과 서버가 실제로 변경을 완료했다는 사실은 다르다.

요청이 서버에 도착하지 않을 수도 있고, 도착했지만 거절당할 수도 있고, 서버가 처리한 결과를 브라우저가 전달받지 못할 수도 있어.

이 차이를 이해해야 API, 오류 처리, 재시도, 작업 상태 조회가 왜 필요한지 설명할 수 있어.

시험 자료에서 확인되는 사실과 오늘의 가상 설계

원문 과제에서는 운영자가 CSV 7종으로 구성된 준비된 데이터셋을 선택·검증·적용하고, 노선 생성과 재계산을 수행해야 해. 잘못된 데이터셋은 적용하지 않고 기존 데이터와 생성 결과를 유지해야 하며, 적용 이후 재계산하기 전의 결과를 새 데이터로 만든 것처럼 표시해서도 안 돼.

결과는 SQLite 같은 DB에 저장할 수 있고, 재시작 후에도 남아야 해. JSON 내보내기 형식은 별도의 EXPORT_SCHEMA.md에 명시되어 있어.

반면 오늘 등장할 /api/datasets, /api/jobs 같은 URL, 작업 ID, API 응답 형태, 예시 데이터는 원리를 설명하기 위해 새로 만든 가상 설계야. 실제 시험에 특정 경로·프레임워크·비동기 구현이 강제되었다는 뜻은 아니야. 제출 코드와 실제 CSV 행이 없으므로 실제 실행 결과 역시 확정하지 않을 거야.

🖥️ 2. 클라이언트와 서버는 무엇이고, 왜 나누어 놓을까?

하나의 프로그램이 모든 일을 처리하지 않는 이유

먼저 웹 서비스가 아닌 일반적인 계산기 프로그램을 생각해 봐.

사용자가 숫자 3과 5를 입력하고 더하기 버튼을 누르면 프로그램은 자신의 메모리에서 계산하고 8을 표시할 수 있어. 반드시 네트워크가 필요하지는 않아.

하지만 통근버스 서비스는 상황이 달라.

운영자는 데이터셋을 적용하고 노선을 생성해야 하고, 구성원은 자신에게 배정된 노선을 조회해야 해. 여러 사람이 같은 운영 데이터와 생성 결과를 일관되게 사용해야 하지.

각자의 브라우저에 별개의 데이터를 저장한다면 어떤 일이 생길까?

운영자 브라우저에서는 B 데이터셋이 적용되었는데, 구성원 브라우저는 A 데이터셋 기준 노선을 보여 줄 수도 있어. 운영자의 노트북을 껐을 때 중요한 데이터가 사라질 위험도 있어.

따라서 공통으로 관리할 데이터를 서버 쪽에 두는 구조를 선택할 수 있어.

이때 역할을 다음처럼 나눠.

여기서 클라이언트(Client)는 서비스를 이용하기 위해 요청을 보내는 쪽, 서버(Server)는 그 요청을 받아 기능을 제공하는 쪽이야.

이름이 아니라 관계로 이해하면 돼. 브라우저가 서버에 요청하는 상황에서는 브라우저가 클라이언트지만, 우리 서버가 다른 외부 서비스에 요청한다면 그 순간 우리 서버도 클라이언트 역할을 할 수 있어.

서버라는 말의 두 가지 뜻

초보자가 자주 혼동하는 부분이 있어.

서버는 컴퓨터를 뜻하기도 하고, 그 컴퓨터에서 요청을 처리하는 프로그램을 뜻하기도 해.

예를 들어 개발용 노트북에서 웹 서버 프로그램을 실행했다고 하자.

그 컴퓨터는 여전히 한 대야. 하지만 운영체제는 브라우저 프로그램과 서버 프로그램을 각각 실행할 수 있어.

운영체제가 실행 중인 프로그램의 단위를 프로세스(Process)라고 불러.

  • 브라우저 프로세스는 화면과 사용자 상호작용을 담당해.
  • 서버 프로세스는 요청을 받고 코드를 실행해.
  • 서버 프로세스는 SQLite 데이터베이스 파일을 열어 읽거나 쓸 수 있어.

이때 프로세스는 자기 실행 상태와 메모리 공간을 갖기 때문에 브라우저의 JavaScript 변수가 서버의 Python 변수나 SQLite 행이 되는 건 아니야.

selectedDataset = "dataset-B"라는 브라우저 변수는 서버가 직접 읽는 것이 아니라 요청에 실어 전달해야 해.

같은 컴퓨터여도 왜 네트워크 요청을 사용할까?

개발할 때는 브라우저에서 http://localhost:8000을 열기도 해.

localhost는 지금 사용 중인 컴퓨터 자신을 가리키는 이름이야. 뒤의 8000은 어떤 서버 프로그램과 통신할지를 구분하는 포트 번호야.

하나의 컴퓨터에 여러 프로그램이 동시에 실행되더라도, 포트를 기준으로 요청을 받아야 하는 프로그램을 찾아갈 수 있는 거지.

인터넷을 거치지 않더라도 클라이언트와 서버라는 경계는 존재해.

서버를 다른 컴퓨터로 옮겨도 브라우저가 같은 방식으로 요청하도록 만드는 것이 웹 구조의 중요한 장점이야.

🌐 3. HTTP는 두 프로그램이 이해하는 공통 언어야

네트워크 연결과 HTTP는 같은 것이 아니야

사람 두 명이 멀리 떨어져 있다고 상상해 보자.

전화망에 연결되어야 말을 전할 수 있고, 연결된 다음에는 어떤 말을 하는지에 관한 규칙이 필요하겠지.

웹에서도 비슷한 구분이 있어.

네트워크는 데이터를 다른 컴퓨터로 전달하는 기반이고, HTTP는 그 데이터를 어떤 요청과 어떤 응답으로 해석할 것인지 정하는 통신 규약이야.

HTTP는 Hypertext Transfer Protocol의 약자지만, HTML 문서뿐 아니라 JSON, 이미지, 파일 같은 여러 형태의 데이터를 전달할 수 있어.

브라우저에서 사용자가 버튼을 누르면 JavaScript 코드가 HTTP 요청을 만들 수 있어. 서버는 그 요청을 해석해서 HTTP 응답으로 돌려줘.

실제 네트워크에서는 IP 주소, 포트, TCP 또는 HTTP/3에서 사용하는 QUIC, TLS 같은 요소들이 관여해. 그러나 지금은 다음 구분만 확실히 잡으면 돼.

  • 네트워크 전달: 데이터를 상대 프로그램까지 운반하는 문제
  • HTTP: 전달된 메시지가 어떤 기능 요청이고 어떤 결과를 뜻하는지 해석하는 문제
  • API 계약: 우리 서비스에서 어떤 요청에 어떤 응답을 주기로 했는지 정하는 문제

HTTP/1.1, HTTP/2, HTTP/3는 전송과 표현 방식에 차이가 있지만, 요청 메서드와 응답 상태코드 같은 핵심 의미는 공유해. 오늘은 사람이 눈으로 읽기 쉬운 HTTP/1.1 형태로 설명할게.

그런데 URL만으로는 서버가 무엇을 해야 하는지 충분하지 않을 수 있어.

예를 들어 같은 데이터셋 주소를 사용하더라도 조회하는 것과 삭제하는 것은 다른 일이야.

이 차이를 HTTP 메서드가 나타내.

GET과 POST가 왜 구분될까?

GET은 자원의 표현을 조회하는 데 사용하는 메서드야. 원칙적으로 GET 요청은 읽기 목적이어야 하고, 호출 자체가 업무 데이터를 변경하도록 설계하면 안 돼.

POST는 서버에 데이터를 보내 처리하도록 요청할 때 많이 사용해. 데이터셋 적용, 노선 생성 시작 같은 동작에 사용할 수 있어.

다른 메서드도 있어.

메서드일반적인 의미가상 통근버스 예시

하지만 메서드 이름을 붙인다고 서버가 자동으로 올바르게 동작하는 것은 아니야.

서버 개발자가 GET /api/delete-all을 호출하면 모든 결과를 삭제하도록 구현하는 것도 기술적으로 가능해. 다만 HTTP 의미에 어긋나고, 브라우저나 캐시, 자동 조회 시스템 때문에 의도하지 않은 변경이 생길 수 있는 위험한 설계야.

즉, HTTP 메서드는 행동의 의미를 표현하는 약속이고, 실제로 그 약속을 지키도록 구현해야 하는 책임은 서버에 있어.

📤 4. 실제 HTTP 요청을 한 줄씩 읽어 보자

운영자가 dataset-B를 검증하려고 해.

다음은 가상 API 설계야.

POST /api/datasets/dataset-B/validate HTTP/1.1
Host: localhost:8000
Content-Type: application/json
Accept: application/json

{
  "strict": true
}

이 요청은 네 가지 부분으로 읽을 수 있어.

첫째, 요청 시작 줄

POST /api/datasets/dataset-B/validate HTTP/1.1

POST는 작업을 요청한다는 뜻이고, 뒤의 경로는 검증할 데이터셋을 나타내. HTTP/1.1은 이 예시 메시지가 따르는 HTTP 버전이야.

중요한 것은 /validate라는 단어 자체가 특별한 HTTP 명령은 아니라는 점이야. 서버 개발자가 그 경로와 기능의 대응 관계를 정해 놓았기 때문에 의미가 생기는 거야.

둘째, Host 헤더

Host: localhost:8000

HTTP/1.1에서 어느 호스트를 대상으로 하는 요청인지 알려 줘.

셋째, Content-Type과 Accept 헤더

Content-Type: application/json은 내가 보내는 본문의 형식이 JSON이라는 뜻이야.

Accept: application/json은 나는 JSON 형태의 응답을 받을 수 있다는 뜻이고.

둘은 방향이 달라.

브라우저가 JSON을 보낸다고 해서 서버 응답도 반드시 JSON이어야 하는 것은 아니야. 다만 우리 API 계약에서 응답도 JSON으로 정하면 클라이언트가 일관되게 처리할 수 있어.

넷째, 요청 본문(Body)

{
  "strict": true
}

본문은 서버에 전달할 실제 데이터야.

strict라는 속성은 이번 가상 설계에서 검증 강도를 나타낸다고 정한 거야. 시험 원문에서 필수로 정한 필드는 아니야.

true는 JSON의 불리언 값이야. 문자열 "true"와 다르다는 점도 중요해.

본문은 항상 필요한 건 아니야. 단순 GET 조회에서는 보통 URL 경로나 쿼리로 필요한 정보를 전달해.

브라우저 JavaScript로 보내면?

async function validateDataset(datasetId) {
  const response = await fetch(
    `/api/datasets/${encodeURIComponent(datasetId)}/validate`,
    {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        "Accept": "application/json"
      },
      body: JSON.stringify({ strict: true })
    }
  );

  const result = await response.json();
  return { httpStatus: response.status, result };
}

여기서 fetch()는 브라우저가 HTTP 요청을 시작하도록 제공하는 기능이야.

JSON.stringify()는 JavaScript 객체를 JSON 문자열로 변환해. 반대로 response.json()은 응답 본문을 읽고 JSON으로 해석하는 작업이야.

그리고 await는 해당 비동기 작업의 결과를 기다리면서 이 함수의 나머지 실행을 일시 중단한다는 뜻이지, 브라우저 전체가 멈춘다는 뜻이 아니야.

한 가지 주의: fetch()는 서버에서 400이나 500을 반환했다고 해서 자동으로 예외를 던지는 것이 아니야. HTTP 오류 응답도 수신했다면 정상적으로 Response 객체를 받을 수 있어. response.ok나 response.status를 직접 확인해야 해. 반면 네트워크 실패나 일부 요청 중단은 예외로 처리돼.

이 구분을 모르면 서버가 400으로 잘못된 데이터셋을 거절했는데도 프런트엔드가 검증 성공으로 표시하는 버그를 만들 수 있어.

📥 5. 서버는 무엇을 보고, 어떻게 응답을 만들까?

서버에 HTTP 요청이 도착했다고 가정해 보자.

서버는 단순히 JSON을 받아서 똑같이 돌려주는 기계가 아니야. 요청이 허용되는지 판단하고, 필요한 코드를 실행하고, 결과를 응답으로 표현해야 해.

그 과정을 조금 더 자세히 보자.

그림 3. 서버 내부의 요청 처리 경로

① HTTP 요청 수신
POST /api/datasets/.../validate
↓
② 라우팅 · 요청 해석

↓

↓

실제 구현에서는 단계가 더 세분화되거나 일부가 합쳐질 수 있어. 여기서는 각 단계의 책임을 이해하기 위한 논리적 구조로 그렸어.

라우팅은 무엇일까?

서버는 많은 종류의 요청을 받을 수 있어.

  • /api/datasets는 준비된 데이터셋 목록 조회
  • /api/datasets/dataset-B/validate는 특정 데이터셋 검증
  • /api/jobs/J-001은 특정 생성 작업 상태 조회

요청의 경로와 메서드를 살펴 어떤 코드가 담당할지 결정하는 과정을 라우팅(Routing)이라고 불러.

라우터가 해당 경로를 알지 못한다면 보통 404 Not Found를 반환할 수 있어. 경로는 있지만 그 경로에서 POST가 허용되지 않는다면 405 Method Not Allowed가 적절할 수 있어.

그다음 서버는 요청값을 해석하고 검사해.

예를 들어 운영자만 데이터셋을 적용할 수 있도록 설계했다면, 이 요청을 보낸 사용자가 누구인지와 그 사용자에게 적용 권한이 있는지도 확인해야 해.

검증이 성공했을 때의 HTTP 응답

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store

{
  "datasetId": "dataset-B",
  "valid": true,
  "errors": [],
  "applied": false
}

응답도 세 부분으로 나뉘어.

첫 줄은 상태 줄(Status Line)이야. 200 OK는 이번 HTTP 요청이 성공적으로 처리되었다는 뜻이야.

그다음 헤더에는 응답 본문의 데이터 형식과 캐시 정책 같은 정보가 들어가.

마지막 본문은 실제 결과를 알려 줘. 이 예시에서는 다음 네 가지 사실을 표현하고 있어.

datasetId는 검증한 대상이고, valid는 검증 결과야. errors는 발견된 오류 목록, applied는 실제 적용 여부를 나타내.

여기서 가장 중요한 것은 valid: true와 applied: false가 함께 존재할 수 있다는 사실이야.

검증에 성공했다는 것은 새 데이터셋을 사용할 수 있는 조건을 만족한다는 뜻이지, 반드시 현재 사용 데이터로 교체되었다는 뜻이 아니야.

이 둘을 구분하지 않으면 검증 버튼을 누르기만 했는데 운영 데이터가 바뀌는 잘못된 프로그램이 만들어질 수도 있어.

상태코드는 어떤 정보를 주는 걸까?

HTTP 상태코드는 가장 먼저 요청 처리의 큰 결과를 알려 주는 숫자야.

03강 비교와 확인
범위뜻대표적인 해석
1xx정보처리가 계속되는 중간 응답
2xx성공요청이 HTTP 의미상 성공
3xx리다이렉션다른 위치나 추가 동작 필요
4xx클라이언트 측 오류요청이 잘못되었거나 수행할 수 없음
5xx서버 측 오류서버가 요청 처리에 실패

4xx를 받았다고 항상 사용자가 실수했다는 뜻은 아니고, 5xx를 받았다고 반드시 데이터가 변경되지 않았다는 뜻도 아니야. 상태코드는 요청 처리 결과의 분류이지, 내부에서 일어난 모든 사건의 완벽한 기록이 아니거든.

HTTP의 표준 의미는 RFC 9110에 정의되어 있어.

📄 6. JSON은 데이터의 모양이고, 스키마는 허용되는 모양에 대한 규칙이야

통근버스 서비스는 다양한 데이터를 다뤄.

직원 ID, 날짜, 근무 상태, 차량 정원, 도착 여유 시간 같은 값들이 필요하지.

이런 값을 어떤 형식으로 주고받을까?

대표적인 방법이 JSON(JavaScript Object Notation)이야.

JSON을 구성하는 것들

{
  "datasetId": "dataset-B",
  "valid": true,
  "errorCount": 0,
  "workDates": ["2026-07-20", "2026-07-21"],
  "settings": {
    "capacity": 45,
    "arrivalBufferMinutes": 20
  }
}

이 데이터에는 여러 종류의 값이 있어.

  • "dataset-B"는 문자열이야.
  • true는 참 또는 거짓을 표현하는 불리언 값이야.
  • 0, 45, 20은 숫자야.
  • workDates는 순서가 있는 배열이야.
  • settings는 다른 값들을 묶은 객체야.

JSON에는 이 밖에도 null이 있어. 이는 값이 없거나 비어 있음을 나타내지만, 어떤 의미인지는 API 계약에서 정해야 해.

예를 들어 다음 세 경우는 같지 않아.

{"jobId": null}
{"jobId": ""}
{}

첫째는 jobId 속성이 존재하고 값은 null이야. 둘째는 빈 문자열이고, 셋째는 속성 자체가 없어.

서버가 셋을 똑같이 취급해도 되는지는 JSON이 정해 주지 않아. 우리 서비스의 데이터 규칙이 정해야 해.

JSON 문법에 맞는다고 올바른 요청일까?

다음 요청을 봐.

{
  "capacity": "forty-five",
  "arrivalBufferMinutes": -20
}

문법적으로는 완전한 JSON이야.

하지만 차량 정원은 숫자여야 할 텐데 문자열이 들어왔고, 도착 여유 시간에 음수가 들어왔어.

여기서 첫 번째 중요한 구분이 생겨.

JSON을 파싱할 수 있는가와 업무에서 사용할 수 있는 값인가는 다른 문제야.

JSON 파싱은 메시지를 자료구조로 읽어 내는 작업이야. 스키마 검증은 그 자료구조가 정해진 모양과 조건을 만족하는지 확인하는 작업이고.

스키마(Schema)는 데이터의 구조와 허용되는 값을 정의하는 규칙이야. 예를 들어 API 요청에 다음과 같은 계약을 정할 수 있어.

03강 비교와 확인
필드타입필수 여부추가 조건
startDate문자열필수YYYY-MM-DD 형식의 실제 날짜
endDate문자열필수시작일보다 빠르지 않음
capacity정수필수1 이상
arrivalBufferMinutes정수필수0 이상

여기서 capacity가 정수라는 조건만으로는 -500이 거부되지 않아. 정수이기 때문이야.

따라서 타입 검사에 더해 값의 범위도 확인해야 해.

그리고 startDate가 2026-02-30이라면 문자열 형식은 날짜처럼 보이지만 실제 날짜가 아니야. 날짜 자체의 유효성도 검사해야 하지.

마지막으로 시작일과 종료일이 각각 올바른 날짜라도 종료일이 시작일보다 빠르다면 기간으로는 잘못되었어.

이것은 필드 하나만 보는 검사가 아니라 여러 필드 사이의 관계를 보는 검사야.

이 차이를 알아야 서버 오류 메시지도 구체적으로 설계할 수 있어.

🤝 7. API 계약은 왜 필요할까?

이제 브라우저와 서버를 서로 다른 개발자가 만들었다고 생각해 보자.

프런트엔드 개발자는 서버가 이런 응답을 줄 거라고 예상했어.

{
  "valid": true
}

그런데 서버 개발자는 다음처럼 만들었어.

{
  "is_valid": true
}

두 응답 모두 올바른 JSON이야.

HTTP 상태코드도 둘 다 200 OK일 수 있어.

하지만 프런트엔드가 result.valid를 읽도록 작성되어 있다면 두 번째 응답에서는 값이 존재하지 않아. JavaScript에서는 이런 접근의 결과가 undefined가 될 수 있지.

양쪽 프로그램이 서로 다른 약속을 사용했기 때문에 고장 난 거야.

API(Application Programming Interface)는 프로그램끼리 기능이나 데이터를 이용할 수 있도록 제공하는 접점이야.

그리고 API 계약(API Contract)은 그 접점에서 무엇을 요청하고 무엇을 돌려줄지에 관한 구체적인 약속이야.

계약에는 단순히 URL이나 필드 이름만 들어가는 것이 아니야.

서버가 어떤 상태에서 요청을 받아들이고, 어떤 조건에서 거절하며, 성공 응답이 업무상 어디까지 보장하는지도 포함해야 해.

데이터셋 적용 API의 계약을 직접 설계해 보자

다음은 가상 계약이야.

데이터셋 적용 · 가상 계약 v1

POST /api/datasets/{datasetId}/apply

사전조건

요청자는 운영자여야 하며 데이터셋이 준비되어 있어야 해.

성공조건

서버는 대상 데이터셋을 검증하고, 적용할 수 있을 때 현재 데이터셋을 전환해. 이 가상 계약에서는 데이터셋 전환이 DB에 확정된 후에만 200을 반환하기로 해.

실패조건

검증이 실패하면 현재 적용 데이터셋과 기존 생성 결과를 변경하지 않아.

응답에 반드시 포함할 정보

적용된 데이터셋 ID, 데이터 버전, 재계산 필요 여부, 오류가 있다면 오류 목록.

이 계약의 핵심은 200을 반환하는 기준이야.

서버가 단순히 "이 요청을 이해했다"는 이유로 200을 반환하면 안 돼. 우리 계약에서 200을 적용 완료라고 정의했기 때문에 실제 적용이 확정된 뒤에만 성공 응답을 만들어야 해.

반대로 처리 중이라는 사실만 확인했다면 완료를 약속해서는 안 돼.

적용 성공과 노선 생성 성공도 구분해야 해

데이터셋 B를 적용했다고 해서 B로 만든 노선이 자동으로 존재하는 것은 아니야.

시험 원문은 오히려 이 상태를 정확히 구분하라고 요구해.

가상으로 다음과 같은 응답을 설계할 수 있어.

HTTP/1.1 200 OK
Content-Type: application/json

{
  "activeDatasetId": "dataset-B",
  "datasetVersion": 8,
  "applied": true,
  "recalculationRequired": true,
  "currentPlan": null
}

이 응답은 B가 적용되었다는 사실을 보여 주지만, B에 대한 노선 생성이 완료되었다고 말하지 않아.

currentPlan: null은 이 계약에서 새로운 데이터셋에 대응하는 현재 사용 가능한 계획이 없다는 의미로 정한 것이야.

서버는 기존 계획 A를 기록으로 보존할 수 있어. 다만 B로 계산된 계획처럼 표시해서는 안 돼.

데이터셋과 생성 결과가 서로 어느 버전에 속하는지 연결해야 하는 이유도 바로 여기에 있어.

오류를 하나의 문자열로 끝내면 무엇이 부족할까?

다음 응답을 보자.

{
  "error": "invalid data"
}

무언가 잘못되었다는 사실은 알 수 있어. 하지만 어떤 파일의 어느 부분이 왜 잘못됐는지 모르겠지.

조금 더 설명 가능한 계약을 만들어 보자.

HTTP/1.1 422 Unprocessable Content
Content-Type: application/json

{
  "code": "DATASET_VALIDATION_FAILED",
  "message": "데이터셋 검증에 실패했습니다.",
  "datasetId": "dataset-invalid",
  "errors": [
    {
      "file": "work_schedule.csv",
      "row": 18,
      "field": "emp_id",
      "code": "UNKNOWN_REFERENCE",
      "message": "구성원 목록에 없는 ID입니다.",
      "value": "E99999"
    }
  ],
  "applied": false
}

여기서 422는 요청의 문법은 이해했지만 그 내용이 유효하지 않아 처리할 수 없다는 의미로 사용할 수 있어.

단, 여러 파일로 이루어진 데이터셋에서 발견한 오류를 400으로 할지 422로 할지는 API 설계에서 명시해야 해. 모든 상황에 단 하나의 정답이 정해진 것은 아니야.

구조화된 오류에는 장점이 있어.

화면은 message를 사용자에게 보여 줄 수 있고, 개발자는 code, file, row, field를 사용해 실제 원인을 추적할 수 있어.

단, 위의 18행과 E99999는 설명용 가상 값이야. 제공 자료에 실제로 그 오류가 있었다는 뜻은 아니야.

입력 오류와 업무 오류는 다를까?

둘을 같은 것으로 취급하면 원인 분석이 어려워져.

예를 들어 capacity: "abc"는 입력 타입 오류야. 서버는 차량 정원이 무엇인지 계산할 수도 없어.

반면 정원 45와 날짜 2026-07-20은 입력 형식상 올바를 수 있어. 그러나 선택한 데이터셋에서 특정 직원의 근무 기록이 누락되어 계획을 생성할 수 없다면, 이것은 데이터 완전성 또는 업무 규칙 문제야.

또 하나의 예를 들어 보자.

서버는 노선 생성 요청의 형식도 확인했고, 실제 계산도 시작했어. 그런데 주어진 정류장 후보지와 운행 제약으로는 모든 근무자를 정해진 시간까지 운송할 수 없다는 결론을 얻었어.

이 경우 입력 JSON은 올바르지만 요청한 업무 결과를 만들어 낼 수 없는 상태인 거야.

이런 오류는 단순한 JSON 파싱 실패와 다르게 표현해야 해. 원인이 어디에 있는지에 따라 사용자가 해야 할 일도 다르기 때문이지.

🚦 8. 200, 201, 202: 모두 성공인데 무엇이 다를까?

이번 수업에서 가장 중요한 부분 중 하나야.

서버가 노선 생성 요청을 받았다고 해 보자.

생성에는 데이터 검증, 직원 배정, 정류장 선정, 경로 계산, 시간표 생성, 최종 검증, DB 저장 같은 작업이 필요할 수 있어.

그런데 HTTP 요청을 받았다는 사실만으로 이 과정이 끝난 것은 아니야.

HTTP 성공 상태코드 가운데 200, 201, 202는 서로 다른 상황을 표현할 수 있어.

200OK요청이 성공했어
201Created새 자원을 만들었어
202Accepted처리를 접수했어

HTTP 표준 의미에 따른 구분이야. 실제 업무상 무엇이 완료되었는지는 해당 API 계약까지 함께 읽어야 해.

200 OK — 요청의 목적이 성공한 상태

운영자가 데이터셋 적용을 요청했고, 서버가 검증과 DB 전환까지 마쳤다고 하자.

앞에서 정한 계약에서는 다음 응답을 사용할 수 있어.

HTTP/1.1 200 OK
Content-Type: application/json
{
  "activeDatasetId": "dataset-B",
  "applied": true
}

이 가상 API에서 200은 데이터셋 적용이 끝났다는 의미야.

하지만 200이 언제나 "서버 내부의 모든 후속 작업 완료"를 의미하는 것은 아니야. 예를 들어 단순 작업 상태 조회 GET 요청에 200이 왔다면, 상태 조회가 성공했다는 뜻이지 그 작업이 완료되었다는 뜻이 아니야.

201 Created — 새로운 자원이 생성된 상태

이번에는 서버가 새로운 운영 계획을 계산하고 DB에 저장했어.

그 결과 새 계획 ID P-104가 만들어졌다고 해 보자.

HTTP/1.1 201 Created
Location: /api/plans/P-104
Content-Type: application/json

{
  "planId": "P-104",
  "status": "COMPLETED",
  "datasetId": "dataset-B"
}

여기서는 새로운 운영 계획 자원이 만들어졌기 때문에 201을 사용할 수 있어.

Location 헤더는 생성된 자원을 찾아갈 주소를 나타내는 데 사용돼.

다만 주의할 점이 있어. 201은 새 자원이 생성되었다는 의미지, 언제나 노선 최적화 계산까지 끝났다는 의미는 아니야.

예를 들어 생성 작업을 추적하는 job 자원만 새로 만들어졌다면, 계약에 따라 201 Created로 새 작업 자원의 생성을 알릴 수도 있어. 이때 실제 노선 계획은 아직 없을 수 있지.

그러니까 상태코드와 함께 무엇이 생성된 자원인가를 확인해야 해.

202 Accepted — 요청은 받아들였지만 완료되지 않은 상태

이제 노선 생성에 시간이 오래 걸린다고 생각해 보자.

서버는 요청을 받아 작업 기록을 만들고, 실제 노선 생성은 이어서 수행하도록 설계할 수 있어.

이때 응답은 다음과 같을 수 있어.

HTTP/1.1 202 Accepted
Location: /api/jobs/J-104
Content-Type: application/json

{
  "jobId": "J-104",
  "status": "QUEUED",
  "statusUrl": "/api/jobs/J-104"
}

이 응답에서 확실하게 말할 수 있는 것은 서버가 노선 생성 요청을 처리 대상으로 접수했다는 사실이야.

실제 계산은 시작하지 않았을 수도 있고, 시작했지만 완료되지 않았을 수도 있어. 나중에 실패할 수도 있지.

HTTP 표준에서도 202는 최종 처리 결과를 보장하지 않는 응답이야.

같은 200인데 왜 하나는 완료이고 다른 하나는 진행 중일까?

다음 두 요청을 비교해 보자.

POST /api/datasets/dataset-B/apply
GET /api/jobs/J-104

첫 번째의 200은 우리가 정한 계약에서 데이터셋 적용 성공을 나타내.

하지만 두 번째의 200은 작업 상태를 성공적으로 읽었다는 의미야.

그 본문은 이렇게 생길 수 있어.

{
  "jobId": "J-104",
  "status": "RUNNING"
}

여기서 200과 RUNNING은 모순이 아니야.

HTTP 요청 자체의 상태와 장시간 실행되는 업무 작업의 상태는 서로 다른 층에 있기 때문이야.

접수한 작업과 완성된 노선을 따로 찾아보자

Ailey 상태 코드가 여럿 나왔지만 처음에는 한 요청만 따라가도 돼. 서버 한곳에서 처리하더라도 요청을 받은 사실과 배정 결과가 저장된 사실을 나누는 거야.

Bailey 작업 조회가 200이면 성공이라고? 조회한 본문이 RUNNING이라면 무엇이 성공했는지 정확히 붙여 말해야지.

먼저 손으로 예상하기

  1. 운영자의 생성 요청이 작업 번호와 202를 받는다.
  2. 같은 작업을 조회하니 요청은 200이고 본문의 작업 상태는 RUNNING이다.
  3. 공식 계획이 있는지와 업무 성공 상태는 따로 확인한다.

위 두 응답만으로 확실히 말할 수 있는 것과 아직 알 수 없는 것을 적어 봐. 실제 내 코드에 작업 조회가 없다면 그 한계도 써 봐.

예상을 적은 뒤 Ailey의 해설 보기

이 예시 계약에서는 요청을 접수했고 작업 상태 조회를 정상 처리했다는 것까지 알 수 있어. 전원 배정·결과 검사·DB 확정은 아직 근거가 없어. 실제 보충 HTTP 실험도 고정 신원으로 권한과 작업 접수·조회만 확인하고, 생성 완료나 DB 영속성을 구현하지 않아.

내 것으로 바꾸기: 내 API 주소, 보낸 값, 받은 상태 코드와 본문, 최종 결과를 찾는 명령으로 바꿔 말해 봐.

실제 예제 파일·명령·확인 범위

ch02.py 내려받기 · 실행 기록과 한계

통합편의 examples 폴더가 보이는 위치에서 Python 3.11 이상으로 실행해. 파일 하나만 받았다면 그 폴더에서 파일 이름을 지정하면 돼.

python examples/ch02.py

ch02.py는 실제 로컬 HTTP 요청으로 고정 신원의 조회·생성 권한과 메모리 작업 접수·조회를 확인한다. 로그인·영속 큐·노선 생성 완료는 구현하지 않는다.

실행 기록의 해당 예제 ID에서 명령·입력·종료 코드·출력·소스 해시와 미검증을 함께 확인해. 예제가 실제 제출물이나 원문 전체 스키마를 검증했다는 뜻은 아니야.

처음 읽을 때는 위의 사건 순서를 설명해 보고 다음 본문으로 이어가. 아래의 ‘더 깊이 읽기’는 필요한 때 펼쳐도 돼. 원문 설명·그림·코드는 그 안에도 남아 있어.

⏳ 9. 오래 걸리는 작업은 왜 작업 ID를 사용할까?

작업 ID(Job ID)는 서버에 접수된 특정 작업을 다시 식별하기 위한 이름이야.

노선 생성처럼 시간이 오래 걸리는 기능에서는 이 식별자가 매우 유용해.

작업 ID가 없다면

운영자가 노선 생성 버튼을 눌러서 40초가 지났다고 생각해 보자.

브라우저 화면에는 로딩 표시만 있어.

그런데 브라우저가 요청 시간을 초과했다고 판단해.

운영자는 어떤 상황인지 알 수 있을까?

계산이 시작되지 않았는지, 90% 진행되었는지, 이미 저장까지 완료했는데 응답만 전달되지 않았는지 구분하기 어려워.

작업 ID를 사용하면 서버가 작업 기록을 남기고 브라우저가 그 기록을 조회할 수 있어.

접수부터 완료까지의 시간 순서

그림 5. 작업 ID를 사용하는 노선 생성 시퀀스

  1. ① 브라우저 → 서버
    POST 생성 요청
  2. ② 서버 → SQLite
    작업 기록 저장
  3. ③ 서버 → 브라우저
    202 + J-104
  4. ④ 서버 → SQLite
    계산 결과 저장
  5. ⑤ 브라우저 → 서버
    GET /jobs/J-104
  6. ⑥ 서버 → SQLite
    상태 읽기
  7. ⑦ 서버 → 브라우저
    200 COMPLETED

설명용으로 일부 단계만 표시했어. 실제 서버에서는 작업이 진행 중일 때 여러 번 조회할 수 있고, 실패 상태로 종료될 수도 있어.

여기서 중요한 점은 작업 접수 기록과 최종 결과를 구분해 저장한다는 거야.

SQLite를 이용한 단일 서버라면 가상으로 다음과 같은 테이블을 만들 수 있어.

jobs 테이블은 작업의 ID, 입력 데이터셋 버전, 실행 조건, 상태, 오류 정보를 저장해.

plans 테이블은 최종 검증을 통과하고 확정된 운영 계획을 저장해.

이 둘이 같은 데이터가 아닌 이유는 간단해.

생성 작업이 실패했을 때도 jobs에는 실패 사실이 남아야 하지만, plans에는 잘못된 최종 결과를 남겨서는 안 되기 때문이야.

작업 상태는 어떤 순서로 변할까?

그림 6. 가상 작업 상태 전이

COMPLETED와 FAILED는 이 예시의 종료 상태.

QUEUED는 접수되었지만 아직 실행하지 않은 상태, RUNNING은 실행 중인 상태야.

COMPLETED는 계약에서 정한 성공 조건을 모두 만족한 상태이고, FAILED는 성공 조건을 달성하지 못하고 끝난 상태야.

이것을 상태 머신(State Machine)이라고 해. 가능한 상태들과 그 상태 사이에서 허용되는 이동을 정한 모델이지.

상태 머신은 서버가 임의의 모순된 상태를 만들지 않도록 도와줘.

예를 들어 FAILED로 종료된 작업이 아무런 재시도 기록이나 새로운 실행 절차 없이 갑자기 RUNNING으로 바뀐다면 원인을 추적하기 어려울 수 있어.

단일 서버에서도 비동기 작업을 만들 수 있을까?

가능해.

예를 들어 한 서버 프로세스가 HTTP 요청을 받아 SQLite에 작업을 접수하고, 같은 프로그램의 별도 실행 흐름에서 계산하도록 구현할 수 있어.

다만 별도 실행 흐름이 있다고 해서 프로세스가 죽어도 작업이 계속되는 것은 아니야.

서버 프로세스가 종료되면 그 안의 실행 흐름도 종료될 수 있어. SQLite에 RUNNING이라는 기록은 남아도 실제 계산은 멈춰 있을 수 있지.

따라서 재시작 시 미완료 작업을 식별하고 어떻게 처리할지 정해야 해.

별도 WORKER 프로세스와 작업 큐는 이런 문제를 다루는 다른 구조이지만, 오늘은 작업을 접수하는 HTTP 요청과 실제 계산 실행의 생명주기가 다를 수 있다는 점까지만 이해하면 돼.

프런트엔드는 완료를 어떻게 확인할까?

가장 단순한 방법은 일정한 간격으로 상태를 다시 조회하는 것이야.

이를 폴링(Polling)이라고 해.

예를 들어 2초마다 다음 요청을 보낼 수 있어.

GET /api/jobs/J-104 HTTP/1.1
Host: localhost:8000
Accept: application/json

처음에는 다음 응답이 올 수 있어.

{
  "jobId": "J-104",
  "status": "RUNNING",
  "planId": null
}

나중에는 이렇게 바뀔 수 있겠지.

{
  "jobId": "J-104",
  "status": "COMPLETED",
  "planId": "P-104"
}

중요한 것은 서버가 이미 반환한 202 응답을 뒤늦게 200으로 바꾸는 것이 아니라, 새로운 GET 요청을 보내 새로운 상태를 읽는다는 사실이야.

또 COMPLETED가 되었다고 작업 조회 응답에 전체 노선 계획을 반드시 포함할 필요는 없어. planId를 받아 별도 계획 조회 API로 최종 결과를 가져오도록 만들 수 있지.

이렇게 역할을 분리하면 작업 상태와 최종 데이터가 서로 다른 목적에 맞게 관리돼.

⚠️ 10. 요청 시간이 초과되면 서버 작업도 실패한 걸까?

이제 실제 장애 상황으로 가 보자.

운영자가 노선 생성 버튼을 눌렀어. 그런데 30초 뒤 브라우저에 다음 메시지가 표시돼.

요청 시간이 초과되었습니다.

운영자는 다시 버튼을 눌러도 될까?

바로 대답하기 전에 요청과 응답의 경로를 생각해야 해.

시간 초과(Timeout)는 정해진 시간 안에 기대한 결과를 받지 못했다는 관찰이지, 서버가 어떤 일을 했는지에 관한 완전한 증거가 아니야.

같은 타임아웃, 서로 다른 실제 상황

그림 7. 브라우저에서 똑같이 시간 초과로 보일 수 있는 경우

상황 A · 서버에 도착하지 않음

요청이 연결 문제로 서버에 전달되지 않았어.

작업이 접수되지 않았을 수 있어.

상황 B · 서버에서 계산 중

서버는 요청을 받았고 계산을 수행하고 있지만 응답이 늦어.

작업은 아직 진행 중일 수 있어.

상황 C · 처리 완료, 응답 유실

서버는 결과를 DB에 저장했지만 응답이 브라우저까지 전달되지 않았어.

작업은 이미 완료되었을 수 있어.

운영자 화면에서는 세 경우가 똑같이 보일 수 있어.

그런데 서버 내부의 실제 상태는 완전히 다르지.

이 때문에 HTTP 요청이 타임아웃되었다는 사실만으로 노선 생성이 취소되었다고 판단하면 안 돼.

브라우저의 AbortController로 요청을 중단하더라도 서버 계산이 자동으로 취소된다는 보장은 없어. 클라이언트 측 요청 중단과 서버 측 작업 취소는 별개로 설계해야 해.

다시 누르면 무엇이 위험할까?

운영자가 재요청하면 서버는 같은 노선 생성을 두 번 시작할 수 있어.

첫 번째 작업 J-104가 이미 결과를 저장했는데, 두 번째 작업 J-105도 실행된다면 다음 문제가 생길 수 있지.

  • 계산 자원을 불필요하게 두 번 사용해.
  • 같은 입력으로 여러 계획을 생성할 수 있어.
  • 두 작업 중 어느 결과가 현재 계획인지 혼동할 수 있어.
  • 실행 도중 데이터셋이 바뀌었다면 서로 다른 입력으로 계산한 결과가 경쟁할 수도 있어.

여기서 등장하는 개념이 멱등성(Idempotency)이야.

쉽게 말하면 같은 효과를 의도하는 요청을 여러 번 보내더라도 업무상 결과가 중복으로 발생하지 않도록 하는 성질이야.

구현 방법 중 하나는 클라이언트가 요청마다 고유한 재시도 식별자를 보내는 것이야.

POST /api/jobs HTTP/1.1
Idempotency-Key: req-20261031-001
Content-Type: application/json

서버는 이 키와 요청 내용을 연결해 기록할 수 있어. 같은 키와 같은 요청이 다시 오면 새 작업을 무조건 만들지 않고 기존 작업의 식별자와 상태를 돌려주도록 설계할 수 있지.

다만 키만 추가하면 자동으로 안전해지는 것은 아니야. 서버가 실제로 중복을 감지하고, 같은 키에 서로 다른 요청 내용이 왔을 때 어떻게 처리할지 정하고, 기록을 충분히 지속해야 해.

또 요청에 식별자가 없거나 서버가 접수 기록을 남기기 전에 실패했다면 작업 ID를 알 수 없는 상황이 생길 수 있어.

멱등성과 재시도의 자세한 구현은 별도 주제에서 다룰 수 있지만, 오늘 반드시 기억해야 할 인과관계는 이것이야.

타임아웃은 결과를 알 수 없게 만들고, 그 불확실성 때문에 무작정 재요청하는 행동이 위험해질 수 있어.

응답이 유실되면 어떻게 확인할까?

이미 작업 ID가 알려져 있다면 그 ID로 상태를 조회하면 돼.

작업 ID를 아직 받지 못했다면 서버는 멱등성 키나 별도의 요청 식별자로 기존 접수 기록을 찾아줄 수 있도록 설계할 수 있어.

그런 장치가 없다면 브라우저만으로 작업이 실행되었는지 정확히 판단하기 어려울 수 있어.

이것은 브라우저의 문제가 아니라 분산된 두 프로그램 사이의 관찰 한계야.

🧩 11. 인증·인가·트랜잭션은 이 흐름 어디에 들어갈까?

지금까지는 브라우저가 올바른 요청을 보낸다고 가정했어.

하지만 실제 웹 서비스에서는 서버가 누가 요청했는지, 그 사람이 이 기능을 실행할 수 있는지, 변경 도중 실패하면 어떤 상태가 남아야 하는지까지 판단해야 해.

이 세 문제는 서로 다르기 때문에 분리해서 이해해야 해.

인증 — 요청한 사람이 누구인지 확인하기

인증(Authentication)은 사용자가 주장하는 신원을 확인하는 절차야.

통근버스 시험에는 운영자와 구성원 두 역할이 있고, 서비스 내부 로그인을 구현해야 한다는 요구가 있어.

운영자가 로그인하면 서버는 이후 요청에서 어떤 사용자가 요청하는지 식별할 수 있어야 해.

로그인 후에는 세션 쿠키나 토큰 같은 방법으로 인증 상태를 전달할 수 있어. 구체적인 방법은 선택한 기술 스택에 따라 달라져.

중요한 점은 로그인 화면을 통과했다는 사실만으로 어떤 API든 실행할 수 있게 되는 것은 아니라는 것이야.

인가 — 그 사용자가 이 행동을 해도 되는지 확인하기

인가(Authorization)는 인증된 사용자가 특정 기능이나 데이터에 접근할 권한이 있는지를 판단하는 절차야.

시험 원문의 역할 구분을 생각해 보자.

운영자는 데이터셋 적용과 노선 생성을 수행할 수 있지만, 구성원은 자기 노선을 조회하는 역할이야.

그런데 구성원이 개발자 도구나 직접 만든 HTTP 요청으로 데이터셋 적용 API를 호출하면 어떻게 해야 할까?

브라우저에서 적용 버튼을 숨겨 놓는 것만으로는 충분하지 않아.

사용자는 브라우저 화면을 거치지 않고 서버에 직접 요청을 보낼 수도 있거든.

따라서 서버가 적용 API 자체에서 요청자의 역할을 검사해야 해. 권한이 없다면 보통 403 Forbidden 응답이 적절해.

반대로 인증 정보가 없거나 유효한 인증을 제공하지 않았다면 401 Unauthorized를 사용할 수 있어. 이름 때문에 헷갈릴 수 있지만, 401은 HTTP에서 인증이 필요하다는 의미로 사용돼.

구성원이 다른 구성원 ID를 URL에 넣어 다른 사람의 노선을 조회하는 상황도 생각할 수 있어. 서버는 자기 정보만 조회할 수 있다는 규칙이 있다면, 요청 URL에 적힌 ID만 믿지 말고 인증된 사용자와 조회 대상의 관계를 검사해야 해.

트랜잭션 — 여러 변경을 하나의 확정 단위로 묶기

데이터셋 적용 기능을 생각해 보자.

서버는 현재 데이터셋 ID를 B로 바꾸고, 데이터 버전을 기록하고, 기존 결과를 현재 결과로 보이지 않도록 해야 해.

그런데 첫 번째 변경만 성공한 다음 서버가 종료되면 어떻게 될까?

DB에는 현재 데이터셋이 B라고 적혀 있지만 화면은 A의 노선 결과를 현재 결과처럼 보여 줄 수 있어.

이런 상태를 막기 위해 DB의 여러 변경을 하나의 논리적 단위로 처리할 수 있어. 이것을 트랜잭션(Transaction)이라고 해.

SQLite에서는 다음과 같은 흐름을 생각할 수 있어.

BEGIN;

-- 현재 데이터셋 버전 전환
-- 결과의 현재 표시 상태 갱신
-- 필요한 적용 이력 기록

COMMIT;

트랜잭션 중 문제가 발생하면 성공을 확정하지 않고 ROLLBACK으로 이전 상태로 되돌리는 방식을 사용할 수 있어.

여기서 원자성(Atomicity)은 한 트랜잭션에 속한 변경들이 전체적으로 확정되거나 전체적으로 취소되도록 하는 성질이야.

단, SQLite 트랜잭션이 CSV 파일 자체의 변경, 서버 외부 서비스 호출, 브라우저 화면 갱신까지 모두 원자적으로 묶어 주는 것은 아니야. 트랜잭션으로 보호되는 DB 변경 범위를 정확히 알아야 해.

그리고 트랜잭션이 성공했어도 브라우저가 성공 응답을 받지 못할 수 있다는 점은 여전히 남아.

그래서 트랜잭션과 재요청 안전성은 서로 다른 문제인 거야.

🛣️ 12. 통근버스 서비스 전체를 하나의 API 흐름으로 연결해 보자

이제 앞에서 배운 내용을 실제 서비스 흐름에 적용해 보자.

아래 예시는 단일 웹 서버 + SQLite + 서버 내부 작업 실행 흐름을 전제로 한 가상 아키텍처야.

사용자 화면과 API 경로는 자유롭게 설계할 수 있지만, 시험 원문의 업무 규칙을 충족해야 한다는 조건은 그대로 유지할게.

단계 1. 준비된 데이터셋 목록 조회

운영자가 화면을 열면 브라우저는 데이터셋 목록을 요청해.

GET /api/datasets HTTP/1.1
Accept: application/json

서버는 준비된 데이터셋과 현재 적용된 데이터셋을 조회해 응답해.

{
  "datasets": [
    {"id": "dataset-A", "name": "기본 데이터셋"},
    {"id": "dataset-B", "name": "변경 데이터셋"}
  ],
  "activeDatasetId": "dataset-A"
}

이 단계의 목적은 조회야. 서버는 브라우저가 화면에 표시할 정보를 제공해.

단계 2. 새 데이터셋 검증

운영자가 B를 선택하고 검증 버튼을 눌러.

서버는 B를 구성하는 CSV 7종을 실제로 읽어 필수 열, 값의 형식, 참조 관계, 필요한 업무상 조건을 검사해.

여기서 중요한 점은 오류 결과가 미리 고정된 문자열이어서는 안 된다는 거야.

실제 CSV 행이 바뀌면 검증 결과도 달라져야 해.

예를 들어 work_schedule.csv의 한 직원 참조가 잘못되었다면 그 행을 찾아 오류로 보고해야 하고, 그 오류를 수정했다면 같은 위치의 오류는 사라져야 하지.

검증 과정에서 사용하는 CSV 목록은 다음과 같아.

03강 비교와 확인
파일검증을 생각할 때의 핵심 질문
sites.csv사업장 ID와 위치 정보가 유효한가?
shifts.csv근무시간대가 유효한 사업장을 참조하는가?
employees.csv직원 ID와 사업장·근무시간대 참조가 유효한가?
work_schedule.csv직원·근무일·근무 상태가 유효한가?
stops.csv후보 정류장 ID와 위치 정보가 유효한가?
travel_times.csv출발·도착 지점 참조와 소요시간 값이 유효한가?
ridership.csv정류장 참조, 방향, 승하차 집계 값이 유효한가?

이 표는 검증 설계의 출발점이지, 실제 구현과 검증 완료의 증거는 아니야.

단계 3. 검증 성공 후 적용

검증이 성공하면 운영자가 적용을 요청해.

POST /api/datasets/dataset-B/apply HTTP/1.1

서버는 검증했던 데이터가 적용 시점에도 같은 내용인지 확인할 필요가 있어.

왜냐하면 검증 후 적용 전에 데이터가 변경될 수 있기 때문이야.

이때 검증된 데이터의 버전이나 해시를 적용 요청에 포함하도록 설계할 수 있어.

예를 들어 expectedVersion: 7을 보냈는데 적용 시점의 데이터 버전이 이미 8이라면, 이전 검증 결과만 믿고 적용해서는 안 되겠지.

이와 같은 경쟁 상태에 대비하는 더 자세한 동시성 제어는 다른 소주제에서 배울 수 있어.

적용이 확정되면 새 데이터셋이 현재 입력으로 지정되고, 기존 노선 계획과 새 데이터셋의 관계를 잘못 표시하지 않도록 상태가 갱신돼야 해.

단계 4. 노선 생성 요청

운영자는 기간, 차량 정원, 도착 여유 시간을 선택하고 노선 생성 버튼을 눌러.

POST /api/jobs HTTP/1.1
Content-Type: application/json
Accept: application/json
Idempotency-Key: generate-B-001

{
  "type": "GENERATE_ROUTES",
  "datasetVersion": 8,
  "startDate": "2026-07-20",
  "endDate": "2026-08-14",
  "capacity": 45,
  "arrivalBufferMinutes": 20
}

서버는 이 요청을 해석하고 입력값을 검사한 후, 해당 데이터셋과 조건으로 계획을 생성하는 작업을 접수할 수 있어.

이 설계에서는 요청을 접수하고 작업 ID를 반환하는 형태를 선택할게.

HTTP/1.1 202 Accepted
Location: /api/jobs/J-104
{
  "jobId": "J-104",
  "status": "QUEUED"
}

여기까지는 노선 생성이 완료된 것이 아니야.

서버 내부에서는 입력 데이터와 실행 조건을 기준으로 정류장 선정, 구성원 배정, 노선과 시간표 계산을 수행해야 해.

생성기가 결과 후보를 만들면 검증기가 그 후보가 운영 규칙을 지키는지 검사하는 구조를 선택할 수도 있어.

검증에서 실패하면 최종 계획으로 확정하지 않아야 해.

단계 5. 생성 작업 조회

브라우저는 J-104의 상태를 조회해.

GET /api/jobs/J-104 HTTP/1.1

서버는 SQLite에 기록된 상태를 확인해 QUEUED, RUNNING, COMPLETED, FAILED 등의 결과를 돌려줘.

작업이 완료되었다고 보고하려면 이 가상 계약에서 정한 성공조건을 충족해야 해.

예를 들어 계산은 끝났지만 운영 규칙 검증을 통과하지 못했다면 COMPLETED가 아니라 실패로 처리하는 것이 타당해.

또 결과가 메모리에만 있고 DB 확정이 끝나지 않았다면, DB 저장까지 요구하는 계약에서 완료라고 보고할 수 없어.

단계 6. 최종 계획 조회와 JSON 내보내기

작업이 완료되면 브라우저는 생성된 계획을 조회할 수 있어.

내보내기 API는 예를 들어 다음과 같이 설계할 수 있어.

GET /api/plans/P-104/export HTTP/1.1
Accept: application/json

응답에서는 다음과 같은 헤더를 사용할 수 있어.

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Disposition: attachment; filename="plan-P-104.json"

그리고 본문에는 EXPORT_SCHEMA.md에서 요구하는 JSON 형식의 운영 계획이 들어가야 해.

여기서 Content-Disposition: attachment는 브라우저가 응답 내용을 다운로드 파일로 취급하도록 유도하는 헤더야. 그러나 일반적인 브라우저 다운로드는 브라우저 환경과 설정에 따라 파일 처리 방식이 달라질 수 있어.

시험에서는 파일 탐색기나 저장 위치 선택창을 열지 않도록 요구하므로, 이 헤더만 붙였다는 사실로 시험 조건 충족을 확정하면 안 돼. 실제 응시 환경에서 파일 선택·저장창이 열리지 않는 내보내기 동작을 확인해야 해.

또 JSON 내보내기는 단순한 문자열 출력이 아니야.

원문 형식에 따르면 period, routes, assignments가 있어야 하고, 각 노선의 정차 순서와 시각, 직원 배정 관계 등이 정해진 규칙을 따라야 해.

가령 stops[].seq는 1부터 연속해야 하고, 정차 시각은 증가해야 하며, 인접 지점의 소요시간은 travel_times.csv 값을 충족해야 해.

즉, JSON이 문법적으로 올바른 것만으로는 운영 계획의 유효성을 입증할 수 없어.

단계 7. 구성원이 자신의 노선을 조회

이제 구성원이 로그인해서 날짜를 선택했다고 생각해 보자.

GET /api/my-routes?date=2026-07-20 HTTP/1.1
Accept: application/json

이 가상 API에서 서버는 인증된 구성원의 신원을 확인하고, 지정 날짜에 그 사람이 근무자인지와 어느 노선에 배정되었는지 조회해.

화면은 노선, 탑승 정류장, 출발 시각 등을 표시할 수 있어.

현재 시각에 따른 버스 위치는 제공된 노선 시간표를 이용해 추정하는 기능이야. 시험 원문에는 실제 GPS 연동이 범위에 포함되지 않으므로, 화면에서 표현하는 위치가 실시간 GPS 측정값인 것처럼 설명하면 안 돼.

이제 운영자 요청부터 구성원 조회까지가 하나의 흐름으로 연결됐어.

🔍 13. API 계약이 실제로 지켜지는지는 어떻게 확인할까?

API 문서를 작성했다고 해서 API가 올바르게 구현되었다는 뜻은 아니야.

문서에 valid: true를 반환한다고 적어 놓아도 실제 서버가 is_valid를 반환한다면 계약이 깨진 상태야.

따라서 API 계약은 문서로 정의하고, 요청을 보내 실제 응답을 검사하고, 업무 상태까지 확인해야 해.

계약 문서에 무엇을 적을까?

API 하나마다 최소한 다음 내용을 정리해야 해.

요청자허용 역할과 인증 조건
입력경로·쿼리·헤더·본문과 타입

이 내용을 Markdown 문서로 적을 수도 있고, OpenAPI 같은 기계가 읽을 수 있는 API 명세 형식을 사용할 수도 있어.

OpenAPI에서는 메서드, 경로, 요청 본문, 응답 코드, JSON 스키마 등을 구조적으로 표현할 수 있어. 도구를 이용하면 문서 생성이나 자동 계약 검사에도 활용할 수 있지.

다만 API 명세 파일이 있다는 사실만으로 서버가 그 명세를 지킨다는 보장은 없어.

검사 1. 정상적인 요청을 보내기

가장 기초적인 검사는 유효한 입력에 올바른 상태코드와 응답 구조가 나오는지 확인하는 거야.

예를 들어 서버가 실행 중이라면 터미널에서 다음과 같은 요청을 보낼 수 있어.

curl -i \
  -X POST http://localhost:8000/api/datasets/dataset-B/validate \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{"strict":true}'

curl은 HTTP 요청을 직접 보내고 응답을 확인할 수 있는 도구야.

-i를 사용하면 응답 헤더와 본문을 함께 볼 수 있어.

위 명령은 가상 API가 실제로 구현되어 있을 때 사용할 수 있는 예시일 뿐, 현재 시험 제출물에 대해 실행한 기록은 아니야. 인증이 필요하도록 구현했다면 그에 맞는 인증 정보도 포함해야 해.

검사 2. 잘못된 입력을 보내기

정상 경로만 확인하면 부족해.

예를 들어 다음 값들을 차례로 검사할 수 있어.

03강 비교와 확인
요청 상황기대하는 판단
capacity: "abc"타입이 잘못되었으므로 거절
시작일이 종료일보다 늦음기간 관계 위반으로 거절
존재하지 않는 직원 참조데이터셋 검증 실패
구성원이 데이터셋 적용 호출권한 부족으로 거절
완료되지 않은 작업의 결과 조회계약에 정의된 미완료 처리

어떤 오류에 400, 403, 409, 422 등을 배정할지는 구체적인 계약에 맞게 정의하고 검사해야 해.

여기서 특히 중요한 검증은 오류가 발생했을 때 무엇이 변경되지 않았는지 확인하는 것이야.

데이터셋 적용 요청이 실패했다면 오류 메시지가 화면에 보이는 것뿐 아니라, SQLite의 현재 적용 데이터셋 ID도 이전 값을 유지하는지 확인해야 해.

서버가 422를 보냈다고 해서 DB가 실제로 변경되지 않았다는 사실이 저절로 증명되는 건 아니니까.

검사 3. HTTP 응답과 DB 상태를 비교하기

예를 들어 데이터셋 적용 API가 200을 반환했어.

브라우저에는 B가 적용되었다고 표시돼.

그런데 SQLite에서 현재 적용 버전을 조회하면 여전히 A가 남아 있다면 어떻게 될까?

이것은 화면이나 응답 형식의 문제가 아니라 계약에서 약속한 상태 변경이 실제로 수행되지 않은 문제야.

따라서 검증은 적어도 세 가지 관찰을 연결해야 해.

세 관찰 결과가 서로 충돌한다면, 어느 지점에서 계약이 깨졌는지 추적해야 해.

검사 4. 응답 시간 초과와 재요청을 검사하기

정상 입력과 잘못된 입력을 모두 검사했다고 해도 통신 장애 상황은 남아 있어.

예를 들어 서버가 DB에 작업을 접수한 직후 응답이 끊기면 어떻게 되는지 검사할 수 있어.

이때 확인해야 하는 것은 단순히 에러 메시지가 출력되느냐가 아니야.

같은 요청을 다시 보냈을 때 작업이 중복 생성되는지, 기존 작업을 조회할 수 있는지, 확정되지 않은 결과가 현재 결과로 표시되지 않는지를 확인해야 해.

실제 검증에서는 인위적으로 응답을 끊거나 처리 지연을 주는 방식이 필요할 수 있어.

다만 여기서는 그런 실험을 실행하지 않았어. 시험 제출 코드가 제공되지 않았기 때문에 어떤 조건이 실제로 통과했는지 주장할 수 없어.

검사 5. 최종 JSON을 독립적으로 확인하기

마지막으로 내보낸 JSON을 읽고 원문 EXPORT_SCHEMA.md와 비교하는 별도 검증 절차가 필요해.

예를 들어 응답에 routes가 존재하는지만 보면 충분하지 않아.

선택된 기간의 근무자가 각 방향에 정확히 한 번 배정되었는지, 휴무자가 배정되지 않았는지, 정차 시각과 이동시간이 맞는지, 차량 정원이 지켜졌는지 확인해야 해.

또 경로를 생성한 코드와 동일한 잘못된 계산을 검증기가 반복한다면 둘 다 같은 오류를 놓칠 수 있어.

그래서 최종 결과를 독립적인 입력·규칙 검증으로 살펴보는 것이 중요해.

이것은 단순한 API 계약 검사를 넘어 업무 결과 자체의 타당성을 확인하는 단계야.

🧪 14. 정상 사례와 실패 사례를 나란히 추적해 보자

지금까지 배운 내용을 단편적으로 기억하지 말고, 실제로 어떤 상태 변화가 일어나는지 비교해 보자.

아래는 모두 설명을 위해 설정한 시나리오야.

상황별 서버 동작 추적 · 학습 시뮬레이션

정상: 검증 후 적용

  1. 요청 — 운영자가 dataset-B 적용 요청
  2. 검증 — CSV 7종 검증 통과
  3. DB — 현재 데이터셋 버전을 B로 확정
  4. 응답 — 200 OK, applied: true
  5. 화면 — B 적용 표시, 재계산 필요 표시

실패: 잘못된 직원 참조

  1. 요청 — dataset-invalid 적용 요청
  2. 검증 — 없는 emp_id 참조 발견
  3. DB — 적용 변경을 확정하지 않음
  4. 응답 — 422, 오류 위치와 코드 전달
  5. 화면 — 오류 표시, 기존 A 유지

불확실: 응답 유실

  1. 요청 — 노선 생성 POST 전송
  2. 서버 — 요청 접수, J-104 기록
  3. 네트워크 — 202 응답이 브라우저에 도착하지 못함
  4. 화면 — 네트워크 오류 또는 시간 초과
  5. 확인 — 요청 식별자로 작업 조회 필요

비동기: 최종 계산 실패

  1. 요청 — POST 생성 → 202 Accepted
  2. 실행 — 작업 J-104 실행 시작
  3. 검증 — 생성 결과가 제약 위반
  4. DB — 작업 FAILED 기록, 계획 미확정
  5. 조회 — GET /jobs/J-104 → 200 + FAILED

네 가지 시나리오는 가상 설계의 기대 동작을 보여 주며, 실제 실행·검증 결과가 아니야.

여기서 특히 네 번째 사례를 살펴봐.

노선 생성 POST 요청은 202 Accepted로 성공했지만, 작업 자체는 나중에 FAILED가 되었어.

이것은 잘못된 HTTP 사용이 아니야.

오히려 202가 의미하는 접수와 최종 작업 완료를 정확하게 분리했기 때문에 표현할 수 있는 상황이야.

서버가 작업 상태 조회 요청에 200 OK를 돌려주면서 본문에 "status": "FAILED"를 담는 것도 마찬가지야.

실패한 작업을 성공적으로 조회한 것이기 때문이지.

이 둘을 혼동하면 UI에서 response.ok가 참이라는 이유만으로 "노선 생성 완료"를 띄우는 문제가 생겨.

이제 조금 더 까다로운 질문을 해 볼게. 답을 먼저 제시하면서 어떤 사고가 필요한지 살펴보자.

반례 A. 서버가 200을 보냈다면 DB 저장도 성공했다고 봐도 될까?

그렇게 단정할 수 없어.

HTTP 200은 해당 요청의 성공을 나타내지만, 성공의 업무상 의미는 API 계약에 달려 있어.

만약 데이터셋 적용 API에서 DB 커밋 완료를 200의 조건으로 정했다면, 올바른 구현은 커밋 성공을 확인한 뒤 200을 반환해야 해.

하지만 버그 때문에 커밋 전에 200을 만들어 전송하거나, DB 저장 예외를 무시해 버리는 구현도 가능하지.

따라서 계약에 적힌 내용과 실제 구현의 상태 변경 순서를 비교하고, DB에 남은 결과로 확인해야 해.

반례 B. 입력값이 올바르면 노선 생성도 성공해야 할까?

아니야.

입력 형식이 올바르더라도 실제 데이터를 바탕으로 모든 제약을 만족하는 해를 찾지 못할 수 있어.

예를 들어 노선 시간표가 이동시간이나 도착 여유 제약을 위반한다면 최종 결과를 확정해서는 안 돼.

이때 문제는 JSON 입력 형식이 아니라 계산 결과의 유효성이야.

노선 생성기가 어떤 경로를 만들었다는 사실과 그 경로가 업무 규칙을 만족한다는 사실은 서로 다른 주장이지.

반례 C. 요청이 취소되면 서버 작업도 취소되는 걸까?

반드시 그렇지는 않아.

브라우저가 네트워크 요청을 중단하더라도 서버는 이미 계산을 시작했을 수 있어.

서버 작업까지 취소하려면 별도의 취소 API나 실행 흐름에 대한 취소 신호를 설계해야 할 수 있어.

그리고 취소 요청을 받았다고 이미 확정된 DB 변경이 자동으로 되돌아가는 것도 아니야.

취소가 가능한 시점과 범위를 계약으로 정해야 해.

반례 D. 검증을 통과한 데이터셋이라면 언제든 안전하게 적용할 수 있을까?

아니야.

검증 시점과 적용 시점 사이에 데이터가 바뀔 수 있어.

검증 당시에는 직원 E00001이 존재했는데 적용 전에 employees.csv에서 삭제되었다고 생각해 보자.

서버가 예전 검증 결과만 믿고 현재 데이터를 적용하면 존재하지 않는 직원 참조를 포함할 수 있어.

그래서 데이터 버전 비교나 적용 시점의 재검증이 필요해.

반례 E. JSON 스키마가 맞으면 내보낸 계획도 맞을까?

아니야.

스키마는 필드의 존재, 타입, 값 범위, 일부 구조적 제약을 검사하는 데 유용해.

하지만 직원이 해당 날짜에 근무하는지, 운행의 중간 구간에 정원을 초과했는지, 출근 도착 시간이 실제 근무 시작보다 충분히 빠른지 등은 데이터 간 관계와 업무 규칙을 확인해야 해.

문법이 맞는 JSON과 운영할 수 있는 통근버스 계획은 다른 것이야.

🎓 16. 이해 확인 — 직접 설명할 수 있는가?

여기까지 읽었다면 외워야 할 단어보다 설명할 수 있어야 하는 인과관계가 중요해.

아래 질문은 오늘 수업에서 배운 원리를 스스로 재구성하기 위한 확인 질문이야. 정답을 미리 외우는 대신 버튼에서 DB까지 어떤 사건이 일어나는지 머릿속에 그려 보면서 답해 봐.

운영자가 데이터셋 적용 버튼을 눌렀어. 버튼 클릭부터 화면에 '적용 완료'가 표시될 때까지, 브라우저·HTTP·서버·SQLite의 역할을 순서대로 설명해 봐.

핵심 구분: 요청을 보낸 사실과 DB에 적용된 사실의 차이

노선 생성 API가 202 Accepted와 작업 ID를 반환했어. 이것이 왜 노선 생성 성공의 증거가 아닌지, 이후 무엇을 조회해야 하는지 설명해 봐.

핵심 구분: HTTP 요청 상태와 작업 상태의 구분

데이터셋 검증 API가 200과 valid: true를 반환했어. 그런데 화면에 즉시 새 데이터셋 노선이 표시된다면 어떤 문제가 있을까?

핵심 구분: 검증·적용·재계산의 서로 다른 상태

브라우저가 생성 요청에서 타임아웃을 만났어. 다시 요청할 때 발생할 수 있는 두 가지 위험과 이를 줄이는 방법을 설명해 봐.

핵심 구분: 결과 불확실성, 작업 ID, 재요청 안전성

내보낸 JSON은 스키마 검사를 통과했지만 휴무자가 노선에 배정되어 있어. 어떤 검사는 통과했고 어떤 검사는 실패한 것일까?

핵심 구분: 구조 검증과 업무 규칙 검증의 차이

이 화면은 자동 AI 채점을 하지 않아. 답변은 이 브라우저에 보관하며, 원한다면 복사해서 별도의 대화에서 검토를 요청할 수 있어. 복사만으로 대화에 전송되지는 않아.

이 질문들에서 반복해서 등장하는 구분을 연결해 보자.

버튼 클릭은 사용자 의도의 시작이고, HTTP 요청은 그 의도를 서버에 전달하는 수단이야. 서버의 응답은 요청 처리에 대해 서버가 한 주장이지.

그리고 그 주장이 정확한지는 실제 DB 상태, 작업 상태, 결과 데이터와 비교해 확인해야 해.

통근버스 서비스에서는 검증과 적용, 생성 접수와 생성 완료, JSON 문법과 업무 규칙 준수라는 서로 다른 단계가 존재해.

이 단계들을 한 덩어리의 "성공"으로 이해하지 않는 것이 정확한 시스템 설명의 출발점이야.

📚 근거와 검증 경계

오늘 수업은 시험 원문에 나타난 통근버스 업무 요구를 사례의 기준으로 삼고, HTTP 자체의 일반 원리는 표준 문서로 보완했어.

  • 시험 원문: EXAM_ORIGINAL_COMBINED.txt — CSV 7종, 운영자·구성원 역할, 데이터셋 검증·적용, 노선 생성, EXPORT_SCHEMA.md의 JSON 규칙
  • 시험 복기: EXAM_RECOLLECTION.txt — 데이터 검증 범위, 시간 초과·WORKER 종료, 결과 검증, 작업 상태와 컴포넌트 책임에 관한 기억
  • HTTP 학습 근거: MDN HTTP 개요 및 RFC 9110 HTTP Semantics

API 경로, 요청·응답 JSON, 작업 테이블과 상태 전이는 설명을 위한 제안 설계야. 실제 제출 코드, CSV 행, 서버 실행 결과가 제공되지 않았으므로 구현 성공 여부는 판정하지 않았어.

통합 웹교재 안내: 본문과 새 자기 설명 연습을 같은 흐름으로 읽으면 돼. 답변은 이 브라우저에 보관하고 필요한 내용은 통합편의 백업으로 따로 남겨. 목차와 이어 읽기로 다른 강에 갈 수 있어. “저장” 채팅 명령·복원 패킷·학습 이미지 생성·AI 채점은 이 웹페이지의 기능이 아니야.
