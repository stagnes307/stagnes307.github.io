노선은 누가 만들고, 누가 검사하며, 누가 공식 결과로 인정할까?

운영자는 '노선 생성' 버튼 하나를 누른다. 하지만 그 버튼 뒤에는 요청을 접수하는 역할, 계산하는 역할, 검사하는 역할, 데이터를 보관하는 역할, 그리고 이제 구성원에게 보여 줘도 된다고 결정하는 역할이 있어.

이번 수업에서는 이 역할들이 실제로 어떻게 연결되고, 중간에 서버가 죽거나 다른 운영자가 설정을 바꿀 때 무엇이 살아남아야 하는지 하나의 이야기로 끝까지 추적할 거야.

먼저 이번 수업의 근거를 구분하자

[시험 원문] 통근버스 정류장 선정, 구성원 배정, 노선·시간표 생성, 7종 CSV 데이터셋 선택·검증·적용, 운영 규칙 준수, DB 저장, 재시작 후 유지, 역할별 조회가 요구됐어. 기술 스택과 DB 종류는 자유였어.

[시험 복기] 버튼부터 저장까지 거치는 컴포넌트와 job·temp·final 소유자, 생성기와 검증기 분리 이유, 시간 제한과 WORKER 종료 시 동작 등을 설명하는 질문이 기억되어 있어. 공식 채점표나 정확한 질문 전문은 아니야.

[교육용 가상 설계] 이 수업에서 사용하는 API 주소, 테이블, job ID, 시간표, Service·Creator·Validator·Repository 코드 구조는 이해를 위한 설계안이야. 실제 응시 제출 코드가 없으므로 구현·실행·검증이 완료됐다고 주장하지 않을게.

통합 웹교재 안내: 본문과 새 자기 설명 연습을 같은 흐름으로 읽으면 돼. 답변은 이 브라우저에 보관하고 필요한 내용은 통합편의 백업으로 따로 남겨. 목차와 이어 읽기로 다른 강에 갈 수 있어. “저장” 채팅 명령·복원 패킷·학습 이미지 생성·AI 채점은 이 웹페이지의 기능이 아니야.

🧭 1. 먼저 생각해 보자 — 계산을 끝낸 것과 저장을 끝낸 것은 같은 일일까?

운영자가 통근버스 노선 생성을 실행했어.

여기서 '계산 성공'이라는 사실만으로 결과를 공식 DB에 저장하면 어떻게 될까?

구성원은 존재해서는 안 되는 노선을 조회하게 돼.

반대로 모든 운영 규칙을 지킨 후보가 나왔다고 해 보자. 이번에는 공식 DB에 저장하는 도중 서버가 종료됐어. 노선 18개 중 11개만 저장되었다면 구성원은 불완전한 계획을 읽을 수 있겠지.

이 두 사고를 막으려면 다음 세 사건을 서로 구분해야 해.

이 세 사건을 하나로 취급하지 않도록 책임과 데이터를 분리하는 것이 이번 수업의 출발점이야.

🌐 2. 버튼에서 서버까지 — 요청은 무엇이고 어디서 실행될까?

컴포넌트를 배우기 전에 가장 먼저 알아야 할 개념이 있어.

브라우저와 서버는 같은 프로그램이 아니라는 점이야.

2-1. 브라우저가 하는 일과 서버가 하는 일

운영자가 웹페이지에서 생성 버튼을 누르면 브라우저 안의 JavaScript가 실행될 수 있어. 이 코드는 화면의 날짜와 차량 정원 등의 입력값을 모아 서버로 요청을 보내지.

브라우저는 사용자 PC에서 실행되고, 서버는 요청을 받아 처리하는 프로그램이야.

두 프로그램은 보통 네트워크를 통해 HTTP라는 통신 규칙으로 메시지를 주고받아.

브라우저가 요청했다고 해서 서버가 반드시 성공하는 것은 아니야.

서버가 요청을 받기 전에 네트워크가 끊길 수 있고, 서버가 처리하는 도중 오류가 발생할 수도 있어. 반대로 서버는 저장에 성공했는데 성공 응답만 브라우저에 전달되지 않을 수도 있지.

이 구분은 나중에 중복 요청과 job 재시도를 이해할 때 중요해져.

2-2. HTTP와 API의 차이

HTTP는 메시지를 주고받는 방식에 대한 규칙이야.

API는 외부에서 프로그램 기능을 호출하는 약속이야. 웹서비스에서는 주로 어떤 URL과 HTTP 메서드를 사용할지, 어떤 데이터를 받고 어떤 결과를 돌려줄지 정해.

가상의 요청을 보자.

POST /api/plans/generate
Content-Type: application/json

{
  "period_start": "2026-07-20",
  "period_end": "2026-07-24",
  "capacity": 45,
  "arrival_buffer_minutes": 20
}

POST는 여기서 새로운 생성 작업을 요청하는 데 사용한 HTTP 메서드야.

/api/plans/generate는 우리가 설계한 URL이고, { ... } 안의 JSON은 요청 본문이야. 정원 45석과 여유 시간 20분이라는 입력이 전달되지.

이 요청은 '이 조건으로 작업을 시작해 달라'는 뜻이지, '반드시 계획이 생성될 것이다'라는 보장은 아니야.

2-3. 로그인 상태와 권한 확인은 왜 API에서 다시 할까?

운영자 화면에는 생성 버튼이 있고, 구성원 화면에는 없다고 해 보자.

구성원이 직접 HTTP 요청을 만들어 같은 API를 호출한다면 어떻게 될까?

서버가 권한을 확인하지 않으면 화면에 버튼이 없더라도 생성할 수 있어.

따라서 API 요청을 처리하는 서버는 세션이나 인증 정보에서 사용자를 식별하고, 이 사용자가 운영자인지 확인해야 해.

  • 인증(authentication): 누구인지 확인한다.
  • 인가(authorization): 그 사람이 이 작업을 해도 되는지 확인한다.
  • 세션(session): 여러 요청에 걸쳐 로그인한 사용자를 연결하는 수단이다.

브라우저가 보낸 "role": "admin" 같은 글자를 그대로 믿어서는 안 돼. 서버가 신뢰하는 인증·세션 정보로 권한을 판단해야 하지.

여기서 하나 더 구분하자.

요청자가 운영자라는 사실은 요청을 받아도 되는 이유일 뿐, 그 운영자가 잘못된 노선을 최종 저장하도록 강제할 권한이 있다는 뜻은 아니야.

운영자의 권한과 운영 규칙 검증은 서로 다른 보호 장치야.

🏛️ 3. 다섯 컴포넌트의 책임은 왜 분리할까?

이제 서버 안으로 들어가 보자.

처음에는 서버가 하나의 프로그램처럼 보일 거야. 실제로 단일 Python 프로그램 파일로도 웹서비스를 만들 수 있어.

하지만 하나의 함수가 요청 접수, 데이터 조회, 노선 계산, 검증, 저장, 오류 표시까지 모두 처리하면 문제가 생겼을 때 어느 부분을 고쳐야 하는지 찾기 어려워져.

더 위험한 건 한 부분이 다른 부분의 책임을 마음대로 침범할 수 있다는 점이야.

그래서 논리적인 역할을 구분해.

3-1. API — 외부 세계의 요청을 받아들이는 문지기

API 계층은 HTTP 요청을 이해해.

예를 들어 날짜 형식이 잘못됐는지, 필수 필드가 빠졌는지, 로그인한 사람이 운영자인지를 확인하고, 내부 프로그램이 사용할 수 있는 형태로 명령을 만들어.

API는 계산이 실패했을 때 적절한 HTTP 응답을 돌려주는 책임도 있어.

하지만 API가 노선 최적화 알고리즘까지 알아야 할 필요는 없어.

왜냐하면 나중에 HTTP가 아닌 다른 방식으로 같은 노선 생성 기능을 실행할 수도 있기 때문이야. 예를 들어 WORKER가 DB에서 작업을 읽어 실행한다면 HTTP 요청 자체가 없을 수 있지.

API에 업무 계산 전체를 묶어 두면 이때 코드를 재사용하기가 어려워져.

따라서 API는 요청의 형태와 접근 권한을 다루는 역할로 생각하자.

3-2. Application Service — 하나의 업무를 끝까지 조정하는 책임자

Application Service는 API에서 받은 '노선 생성'이라는 명령을 실제 업무 절차로 바꿔.

이번 작업을 진행하려면 무엇부터 해야 할까?

먼저 어떤 데이터셋과 조건으로 계산할지 결정해야 해. 그다음 작업 이력을 남기고, 생성기를 실행하고, 검증기로 결과를 확인한 뒤, 최종적으로 확정해야겠지.

Application Service는 이 전체 순서를 알고 있어.

예를 들어 다음과 같은 의사코드를 상상할 수 있어.

def generate_plan(command):
    job = register_job_with_frozen_input(command)

    candidate = creator.create(job.input_snapshot)
    save_temporary_candidate(job.id, candidate)

    report = validator.check(
        candidate,
        job.input_snapshot
    )

    if not report.valid:
        mark_job_failed(job.id, report)
        return job.id

    publish_if_still_allowed(job.id, candidate, report)
    return job.id

이 코드는 실제로 실행하거나 검증한 구현이 아니라 전체 책임을 설명하는 의사코드야. 예외, 재시도, 취소, 동시성 처리도 아직 생략되어 있어.

Service가 직접 노선을 계산하지 않는 이유는 명확해. 노선 알고리즘이 달라져도 작업 접수·검증·확정 순서는 유지할 수 있도록 하기 위해서야.

반대로 Creator가 어떻게 계산했는지는 Service가 전혀 알 필요 없다는 말도 아니야. Service는 Creator의 입력·출력 계약과 실패 의미를 알아야 해. 다만 계산의 세부 구현까지 책임질 필요는 없다는 뜻이지.

3-3. Creator — 조건을 만족할 후보를 찾는 계산자

Creator는 계획을 만들어 내는 컴포넌트야.

통근버스 서비스에서는 다음 정보를 받아 계산할 수 있어.

  • 어느 날짜에 누가 근무하는가?
  • 어느 사업장과 근무조에 속하는가?
  • 선택 가능한 정류장은 어디인가?
  • 정류장 사이의 이동 시간은 얼마인가?
  • 차량 정원과 도착 여유 시간은 얼마인가?

이 정보로 정류장을 선정하고, 구성원을 배정하고, 운행 순서와 시간표를 계산해.

하지만 Creator의 결과는 어디까지나 후보(candidate)야.

Creator가 규칙을 지키도록 계산했다고 해서 결과가 실제로 모든 규칙을 만족한다는 것은 아니거든.

알고리즘에 버그가 있거나, 입력의 일부를 잘못 해석했거나, 특정한 예외를 놓쳤을 수 있어.

3-4. Validator — 생성된 후보를 다시 의심하는 검사자

Validator는 Creator가 반환한 후보가 실제 운영 규칙을 만족하는지 확인해.

원문 기준으로는 근무자 전원의 출퇴근 배정, 휴무자 제외, 구간별 정원, 방향별 이동 시간, 시간표, 사업장·근무조 일치 등을 검사해야 해.

여기서 두 개념을 구별하자.

생성기는 답을 찾으려는 역할이고, 검증기는 그 답이 유효한지 확인하는 역할이야.

예를 들어 Creator가 후보를 만들 때 travel_times.csv의 A→B 이동 시간을 사용했다고 주장해도, Validator는 후보의 연속 정차 지점과 시간을 직접 비교해야 해.

Creator가 이용한 중간 계산값을 무조건 믿어서는 안 되겠지.

그렇다고 생성기와 검증기가 아무 코드도 공유하면 안 된다는 뜻은 아니야. 공통 입력 형식이나 데이터 파싱 규칙은 공유할 수도 있어. 다만 검증해야 할 오류를 함께 만들어 내는 계산 경로를 그대로 재사용하는 것은 위험해.

Validator의 결과도 아직 final은 아니야. 검증이 끝난 뒤 저장이 실패할 수 있으니까.

3-5. Repository — 데이터가 어디에 어떻게 저장되는지 책임진다

Repository는 데이터 접근을 담당하는 인터페이스야.

Service가 작업을 등록해야 한다면 jobs 테이블에 어떤 SQL을 실행할지 알 필요 없이 Repository에 요청할 수 있어.

job_repo.create(job)
job_repo.mark_failed(job_id, error)
plan_repo.publish(plan)

Repository의 핵심 가치는 DB 접근을 한곳에 모으고, 저장 형식과 트랜잭션 구현을 관리하기 쉽게 만드는 데 있어.

다만 여기서 중요한 구분이 하나 있어.

저장할 기술적 능력과 저장을 허가할 업무적 권한은 달라.

Repository는 final 테이블에 SQL을 실행할 수 있지만, 검증 실패 후보를 공식 결과로 인정해도 되는지는 Application Service의 정책과 DB 제약조건이 함께 통제해야 해.

이것을 책임 경계라고 불러.

🗄️ 4. job·temp·final — 세 가지 기록은 서로 다른 질문에 답한다

이제 이번 수업의 핵심인 상태 소유권을 살펴보자.

사용자가 노선 생성 버튼을 누른 순간부터 시스템에는 서로 다른 종류의 정보가 생겨.

하나는 '무슨 작업을 하고 있는지'이고, 다른 하나는 '무엇을 계산했는지'이며, 마지막 하나는 '무엇을 공식적으로 사용할 수 있는지'야.

4-1. job: 작업 요청과 실행 상태의 진실

job은 작업 자체에 대한 기록이야.

예를 들어 이런 정보가 있을 수 있어.

{
  "job_id": "J104",
  "status": "RUNNING",
  "dataset_version": 7,
  "capacity": 45,
  "arrival_buffer": 20,
  "attempt": 1,
  "cancel_requested": false
}

job에는 어떤 입력으로 요청했는지, 현재 실행 중인지, 몇 번째 실행 시도인지, 취소 요청이 있었는지 등을 기록할 수 있어.

여기서 중요한 건 job이 노선이 아니라는 사실이야.

생성에 실패해도 job은 존재할 수 있어. 오히려 실패했기 때문에 이 기록이 필요하지.

운영자는 이 작업의 상태를 확인해서 '왜 실패했는지', '다시 실행해야 하는지', '이미 성공했는지'를 판단할 수 있어.

Application Service가 job의 업무 상태 변경을 결정하고, Repository가 DB에 기록하도록 설계할 수 있어.

4-2. temp: 계산됐지만 아직 공개할 수 없는 후보

temp는 임시 결과야.

Creator가 노선 18개를 계산했다면 노선 정보, 배정 정보, 정차 시각 등 후보 데이터를 임시로 보관할 수 있어.

그런데 temp라는 이름 때문에 무조건 RAM 메모리에 있어야 한다고 생각하면 안 돼.

메모리 temp

계산 과정에서 빠르게 다룰 수 있지만 프로세스가 종료되면 일반적으로 사라져. 중간 후보를 복구하려면 다시 계산해야 할 수 있어.

DB temp

SQLite의 일반 영속 테이블에 저장하면 커밋된 후보가 재시작 이후에도 남을 수 있어. 단, 일부만 작성했는지 구분해야 해.

여기서 말하는 DB temp는 candidate_routes 같은 일반 영속 테이블을 의미해. SQLite의 특별한 TEMP TABLE과는 달라. SQLite TEMP 테이블은 DB 연결 수명에 종속될 수 있으므로 장기 복구 기록용으로 혼동해서 사용하면 안 돼.

temp의 핵심은 저장 위치가 아니라 아직 검증되고 확정되지 않았다는 지위야.

Creator는 후보를 작성할 수 있어도 이를 구성원에게 공개할 권한은 없어야 해.

final은 검증을 통과하고 DB의 확정 절차까지 완료된 계획이야.

이전 계획을 보존한다면 final 데이터에는 여러 버전이 있을 수 있어.

다만 DB가 권위 있는 기록이어도, 실행 중인 프로세스가 실제로 살아 있는지는 별도 문제야. DB에 RUNNING이라고 남아 있다고 해서 지금도 CPU가 일을 하고 있다는 증거는 아니거든.

🔄 5. 정상 실행: J104라는 작업을 처음부터 끝까지 추적하자

이제 모든 개념을 하나의 사례에 연결해 보자.

가상의 운영자 A가 2026년 7월 20일부터 24일까지의 통근버스 계획을 생성한다고 하자.

조건은 데이터셋 버전 7, 정원 45석, 출근 도착 여유 20분이야.

이 숫자와 ID는 교육용이지만, 적용해야 하는 규칙의 종류는 시험 원문을 따르고 있어.

5-1. 시간 흐름 전체

각 단계는 단순히 다음 함수로 넘어가는 게 아니야. 어느 순간부터 무엇이 DB에 사실로 남는지가 달라져.

5-2. 입력 고정이 먼저 필요한 이유

입력을 고정한다는 건 '나중에 변경되지 않을 조건을 정의한다'는 뜻이야.

여기에는 적어도 두 종류의 입력이 있어.

하나는 데이터셋이고, 다른 하나는 운영자가 선택한 계획 조건이야.

데이터셋에는 구성원, 근무표, 정류장 후보, 이동 시간 등이 포함돼. 계획 조건에는 기간, 정원, 출근 여유 시간이 포함되지.

Service가 J104를 등록할 때 다음처럼 고정했다고 해 보자.

job_id               J104
dataset_version      7
period               2026-07-20 ~ 2026-07-24
capacity             45
arrival_buffer       20
algorithm_version    creator-v1
status               PENDING

이때 '데이터셋 버전 7'이 정말 불변이어야 해. 같은 버전 번호를 가진 CSV 내용이 도중에 수정될 수 있다면 숫자만 기록해서는 입력 고정을 보장할 수 없지.

안전한 방법으로는 검증·적용된 데이터셋을 불변 스냅샷으로 보관하고 그 버전 ID를 참조하거나, 작업에 필요한 실제 입력 복사본과 해시를 보존하는 방식이 있어.

해시는 내용에서 계산한 식별값이야. 내용을 변경하면 일반적으로 해시도 달라지므로 나중에 입력이 일치하는지 점검하는 데 사용할 수 있어. 단, 해시만 남기고 원본을 잃어버리면 입력을 재현할 수는 없어.

5-3. job 등록에는 짧은 트랜잭션을 사용한다

트랜잭션(transaction)은 관련 DB 변경을 하나의 작업 단위로 묶는 방법이야.

초기 등록 단계에서는 다음을 한 묶음으로 처리할 수 있어.

  • 현재 활성 데이터셋 버전 확인
  • 실행 옵션과 데이터셋 참조 기록
  • 새 job 생성
  • PENDING 상태 기록

이 중 job만 생성되고 실행 조건이 기록되지 않으면, 재시작 이후 어떤 데이터로 계산해야 할지 알 수 없어.

그래서 처음부터 재현 가능한 작업 기록을 만드는 거야.

여기서 트랜잭션을 열어 둔 채 노선 전체를 계산하지는 않는 것이 좋아. 생성에 수십 초나 몇 분이 걸리면 DB의 쓰기 잠금을 오래 점유할 수 있고, 다른 작업과 충돌하기 쉬워져.

기본 설계에서는 짧은 등록 트랜잭션 → 트랜잭션 밖에서 계산 → 짧은 확정 트랜잭션으로 나누는 것이 합리적이야.

5-4. Creator와 temp

Creator가 입력을 읽어 후보 C1을 만들었다고 가정해 보자.

후보에는 단순히 노선 수만 있는 게 아니야. 실제로 검증하려면 각 날짜, 출근·퇴근 방향, 버스 운행별 정류장 순서, 시각, 구성원 배정까지 있어야 해.

temp를 DB에 저장한다면 J104에 연결해야 하지.

candidate_id    C1
job_id          J104
attempt         1
dataset_version 7
candidate_state COMPLETE

여기서 COMPLETE는 후보 작성이 끝났다는 뜻이지, 검증을 통과했다는 뜻은 아니야.

만약 Creator가 18개 노선 중 10개만 저장하고 종료됐다면, 후보 C1을 COMPLETE로 취급해서는 안 되겠지.

따라서 후보 저장을 하나의 트랜잭션으로 처리하거나, 부분 작성된 후보와 완료된 후보를 구별할 수 있어야 해.

5-5. Validator가 확인하는 사실

Validator는 C1과 J104의 고정 조건을 받아 검사해.

예를 들어 어떤 날짜의 구성원 E00001이 WORK라면 출근과 퇴근 각각 하나의 유효한 배정이 있어야 해. OFF라면 그 날짜에 배정되면 안 돼.

운행의 연속 정차 지점 A와 B 사이 시간이 15분으로 계산됐다면, 입력된 방향별 travel_times.csv의 A→B 값 이상인지 비교해야 해. B→A의 값을 대신 사용하는 것은 올바르지 않아.

또한 정원은 평균 탑승 인원이 아니라 실제 구간별 동시 탑승 인원을 기준으로 확인해야 해.

이렇게 Validator가 결과를 다시 계산해 확인해야 할 항목을 정해 놓으면, Creator가 잘못된 결과를 반환했을 때 final로 넘어가는 것을 차단할 수 있어.

5-6. 최종 확정 전에는 한 번 더 확인한다

많이 놓치는 단계가 바로 여기야.

Validator가 C1에 대해 valid = true를 반환했다고 해 보자.

그런데 검증 중 운영자 B가 새로운 데이터셋을 적용했어. 또는 J104가 취소 요청을 받았어. 또는 J104의 첫 번째 실행이 멈춘 줄 알고 두 번째 시도를 시작했어.

그렇다면 첫 번째 실행의 C1을 그대로 final에 확정해도 될까?

그건 서비스가 채택한 충돌·취소 정책에 따라 달라져.

이번 수업에서는 다음 정책을 기본안으로 삼을게.

현재 적용된 데이터셋과 맞지 않거나, 유효한 최신 실행 시도가 아니거나, 취소된 작업이라면 현재 계획으로 발행하지 않는다.

이 판단은 검증이 끝난 시점의 기억에 의존해서는 안 돼. 확정하는 DB 트랜잭션 안에서 최신 상태를 확인해야 해.

5-7. final 저장과 활성 포인터를 함께 확정한다

최종 확정 트랜잭션에서는 새 계획의 노선·배정·시간표가 모두 저장되고, 현재 공개 계획을 가리키는 포인터가 갱신되며, job이 성공 상태가 되어야 해.

이때 일부만 성공한 상태가 외부에 보이지 않도록 해야 하지.

SQLite는 명시적 트랜잭션의 커밋과 롤백을 지원하고, BEGIN IMMEDIATE처럼 쓰기 트랜잭션을 시작하는 방법도 제공해. 다만 DB 오류가 발생했을 때 트랜잭션의 구체적인 상태를 확인하고 적절히 롤백하는 처리가 필요해.

이 설계에서 최종 커밋이 성공해야 비로소 '생성이 완료됐다'고 할 수 있어.

5-8. 조회도 공개 정책의 일부다

구성원이 자신의 노선을 조회할 때는 어느 테이블을 읽을까?

임시 후보가 아니라 final이야.

또 final 가운데 아무 버전이나 읽으면 안 돼. 현재 활성 계획이 무엇인지, 그 계획이 현재 데이터셋에 대응하는지, 요청한 날짜와 구성원에게 해당하는지 확인해야 해.

조회 역시 서버의 책임이야.

사용자가 요청 URL에 다른 사람의 구성원 ID를 적었다고 해서 그 사람의 거주지와 노선을 그대로 반환하면 안 돼. 인증된 구성원의 ID를 기준으로 조회 범위를 제한해야 하지.

한 서버에서도 작업표·메모리 초안·DB 확정본을 나눌 수 있어

Ailey 컴포넌트 표를 전부 외우기보다 별도 Worker가 없는 서버 한곳을 먼저 그려 보자. 함수가 차례로 호출되어도 초안을 만드는 일과 공개를 허락하는 일은 달라.

7-1. 검증에 실패한 후보는 어떻게 될까?

Validator가 정원 위반을 발견하면 Service는 J104를 실패 상태로 기록할 수 있어.

이때 temp를 무조건 삭제할 필요는 없어. 실패 후보를 보관하면 어떤 노선에서 몇 명이 초과했는지 분석하기 좋거든.

다만 장기간 보관하면 저장 공간이 증가하고 개인정보가 남는다는 부담이 있어. 그래서 접근 권한과 보관 기간을 정해야 해.

진단을 위한 보존과 공식 공개는 완전히 다른 일이야.

7-2. 확정 직전에 서버가 종료되면?

중요한 것은 커밋이 일어났는지야.

커밋되지 않은 트랜잭션의 변경은 정상적인 복구 절차에서 공식 확정 상태로 남아서는 안 돼.

그러므로 확정 로직을 한 트랜잭션 안에 묶었다면, 일부 노선만 활성 계획으로 표시되는 상태를 방지할 수 있어.

단, DB에 저장한 파일이 아니라 외부 JSON 파일을 별도로 기록했다면 그 파일은 SQLite 트랜잭션의 보호를 받지 않아. 이 차이 때문에 공식 계획의 진실은 DB에 두고, 내보내기 JSON은 확정된 DB 상태에서 생성하는 편이 단순해.

7-3. DB 커밋 후 HTTP 응답이 사라지면?

운영자 브라우저에는 실패처럼 보일 수 있지만 DB에는 이미 성공한 계획이 있을 수 있어.

그래서 브라우저의 응답 실패를 곧바로 계산 실패라고 표시하면 안 돼.

작업 ID나 요청의 고유 식별자를 이용해 서버에 상태를 다시 조회할 수 있어야 해.

재시도 시에는 같은 요청이 새로운 계획을 중복 생성하지 않도록 멱등성 정책이 필요해. 여기서 핵심은 같은 요청을 여러 번 전달하더라도 의도하지 않은 중복 확정이 일어나지 않도록 하는 것이야.

7-4. 시간 제한은 취소와 같은 뜻일까?

아니야.

브라우저가 30초 동안 응답을 기다리다 포기해도 서버 계산은 계속될 수 있어.

HTTP 연결이 끊어졌다는 사실과 작업을 중단하라는 명령은 다르거든.

작업을 실제로 취소하려면 Service나 WORKER가 취소 상태를 확인하고, 결과 확정도 차단해야 해.

특히 계산이 끝나고 검증까지 통과한 직후에 취소가 들어올 수 있기 때문에 확정 직전의 취소 확인이 중요해져.

8-1. 데이터셋 버전 경쟁

J104가 데이터셋 버전 7로 계산을 시작했어.

Creator가 계산하는 동안 다른 운영자가 버전 8을 적용했다고 해 보자.

서비스 정책은 두 가지 방향으로 만들 수 있어.

첫 번째는 현재 활성 데이터셋이 달라졌다면 기존 job의 현재 계획 발행을 거부하는 거야. 이번 수업의 기본 정책이지.

두 번째는 버전 7의 결과를 과거 계획으로 보존하되, 버전 8의 공식 계획으로 표시하지 않는 방식이야.

어느 쪽이든 버전 7로 계산한 결과를 버전 8로 계산했다고 거짓 주장하면 안 돼.

이런 문제를 검증 시점과 사용 시점 사이의 경쟁, 즉 TOCTOU(Time-of-check to time-of-use)의 한 형태로 이해할 수 있어.

8-2. 실행 시도(attempt) 경쟁

이번에는 데이터셋이 바뀌지 않았다고 해 보자.

J104의 첫 번째 실행 시도가 너무 오래 걸렸어. 시스템이 중단됐다고 판단해서 두 번째 실행 시도를 시작했지.

그런데 첫 번째 실행이 실제로는 살아 있었고 뒤늦게 검증을 마쳤다면?

08강 비교와 확인
시도 1늦게 계산 완료 · 검증 통과
시도 2현재 유효한 실행 시도로 등록됨
문제시도 1이 뒤늦게 final을 덮어쓸 수 있음

여기서 attempt = 2가 현재 유효한 시도라면, attempt = 1의 확정을 거부해야 해.

이를 구현할 때 실행 세대 번호나 토큰을 사용할 수 있어. 새 시도에 더 큰 세대 번호를 부여하고, 확정 트랜잭션에서 DB의 최신 세대 번호와 정확히 일치하는지 확인하는 거지.

이런 방식을 fencing token이라고 부르기도 해.

핵심은 오래된 실행자에게서 확정 권한을 회수하는 것이야. 프로세스가 늦게 끝났다는 이유만으로 이미 회수된 권한을 다시 주어서는 안 돼.

단순히 WORKER의 메모리에서 is_current = True를 확인하는 건 충분하지 않아. 실제 권위를 가진 DB에서 최신 시도를 확인해야 해.

8-3. 취소 경쟁

운영자가 취소를 눌렀다고 해 보자.

Service가 job의 취소 요청을 DB에 기록했는데, Creator는 아직 계산 중이라 이를 모를 수 있어.

계산 결과가 완성되면 Validator가 통과를 반환할 수도 있겠지.

그렇다면 취소 요청이 있는 job을 확정해도 될까?

기본 정책에서는 안 돼.

계산 중 주기적으로 취소 상태를 확인하는 것도 좋지만, 그것만으로 충분하지 않아. 마지막 확인 직후 취소가 들어올 수 있거든.

그래서 확정 트랜잭션에서 다시 취소 여부를 확인해야 해.

다만 취소와 확정이 거의 동시에 발생한다면 순서를 명확히 정의해야 해.

예를 들어 DB에서 확정이 먼저 성공했다면 그 후의 취소 요청으로 이미 발행된 계획을 취소했다고 표시하면 안 돼. 반대로 취소가 먼저 커밋됐다면 이후 확정은 거부해야 하지.

이런 순서 규칙이 있어야 사용자가 본 상태와 DB 상태가 모순되지 않아.

8-4. 최종 확정은 단순한 INSERT가 아니다

이제 확정 로직을 개념적으로 표현해 보자.

def publish(job_id, candidate_id, attempt):
    with db.transaction():
        job = db.get_job_for_update_or_cas(job_id)
        active_dataset = db.get_active_dataset()

        assert job.attempt == attempt
        assert job.status == "VALIDATING"
        assert not job.cancel_requested
        assert job.dataset_version == active_dataset.version
        assert candidate_belongs_to_job(candidate_id, job_id, attempt)
        assert candidate_is_complete(candidate_id)
        assert validated_candidate_is_unchanged(candidate_id)

        plan_id = db.insert_final_from_candidate(candidate_id)
        db.update_active_plan(plan_id)
        db.mark_job_succeeded(job_id, plan_id)

이 코드는 개념용 의사코드야. 그대로 실행되는 완전한 SQLite 구현은 아니야. 특히 SQLite에는 일반적인 SELECT ... FOR UPDATE 문법이 없으므로, BEGIN IMMEDIATE나 조건부 UPDATE와 행 수 확인 등의 방식으로 경쟁을 통제해야 해.

assert도 실제 서비스의 오류 처리 방식으로 그대로 권장하는 건 아니야. 실제 구현에서는 조건 미충족을 명시적인 업무 오류로 처리하고 롤백해야 하지.

또 검증 이후 temp가 수정될 수 있다면 '검증 성공' 기록만 믿을 수 없어. 검증된 정확한 후보와 확정할 후보가 동일한지 확인해야 해. 예를 들어 후보를 변경 불가능하게 만들거나, 검증한 후보 해시와 확정 대상을 연결할 수 있어.

최종 확정에서 확인하는 것은 네 가지 종류의 일치야.

  1. 입력 일치: 이 후보가 만들어진 데이터와 조건이 유효한가?
  2. 실행 주체 일치: 지금 확정하려는 시도가 현재 허가된 시도인가?
  3. 상태 일치: 취소·실패·이미 완료된 작업은 아닌가?
  4. 후보 일치: 검증한 바로 그 결과를 확정하는가?

이 확인과 final 저장·활성 포인터 변경이 경쟁 중에도 안전해야 해.

8-5. 공개 경쟁: 두 job이 모두 유효하면?

운영자 A와 B가 같은 데이터셋 버전으로 각각 노선을 생성했다고 하자. 두 계획이 모두 규칙을 통과했을 수 있어.

그런데 둘 다 '현재 공개 계획'이 되려고 한다면?

이때는 어떤 것이 최신인지에 대한 정책이 필요해.

예를 들어 Service가 작업을 접수할 때 공개 대상의 active_plan_revision을 함께 기록하고, 확정할 때 그 값이 그대로인지 비교할 수 있어.

이를 낙관적 동시성 제어(optimistic concurrency control)라고 부를 수 있어. 상태가 안 바뀌었을 것으로 기대하되 실제 변경 직전에 비교하는 거야.

버전이 이미 바뀌었다면 이전 계획을 덮어쓰지 않고 충돌을 반환하거나 다시 검토하게 할 수 있어.

이때 주의할 점은 dataset_version과 active_plan_revision이 서로 다르다는 거야.

데이터셋은 같아도 계획을 새로 발행할 수 있기 때문에, 입력 버전 확인만으로 공개 계획 경쟁을 모두 막을 수는 없어.

🧩 9. 생성기와 검증기를 분리한다고 모든 오류가 사라질까?

이제 생성과 검증 분리의 이유를 더 깊이 생각해 보자.

Creator가 다음과 같은 잘못된 코드를 썼다고 가정하자.

travel_minutes = travel_times[(to_stop, from_stop)]

실제로 필요한 것은 (from_stop, to_stop)인데 반대로 읽은 거야.

시험 원문에서는 A→B와 B→A 소요시간이 다를 수 있다고 명시돼 있어.

그런데 Validator도 Creator가 사용한 travel_minutes 값을 그대로 받아 검사한다면?

Creator가 잘못 계산한 시간이 실제 입력과 일치한다고 착각할 수 있어.

이런 상황에서는 모듈을 둘로 나눴다는 사실만으로 독립 검증이 되지 않아.

검증기는 후보 결과를 원본 규칙과 독립적으로 대조해야 해.

검사 대상과 생성 방법을 구분하자

생성기의 질문

어떻게 정류장을 묶고 구성원을 배정해야 노선의 품질이 좋아질까?

탐색 · 휴리스틱 · 최적화 · 후보 구성

검증기의 질문

이 후보에서 모든 WORK 구성원이 배정됐고, 정원과 이동 시간과 근무 규칙을 지켰는가?

제약조건 검사 · 누락·중복 확인 · 위반 보고

생성기는 좋은 후보를 찾아야 하고, 검증기는 잘못된 후보를 놓치지 않아야 해.

둘의 목표가 다르기 때문에 구현도 달라질 수 있어.

하지만 독립 검증에도 한계는 있어.

Creator와 Validator 모두 잘못된 CSV를 같은 방식으로 해석한다면 공통 오류가 남을 수 있어. 둘이 같은 잘못된 업무 규칙을 적용해도 마찬가지야.

따라서 입력 데이터 자체의 검증과, 담당자에게 확인해야 할 업무 의미의 검증도 중요해.

또 규칙 준수와 계획 품질은 서로 달라.

모든 구성원을 정원 이내에 배정했더라도 운행이 지나치게 많거나 구성원의 이동이 불편하면 좋은 최적화 결과라고 말하기 어려워.

반대로 총 운행 횟수가 적다고 해도 정원을 초과하거나 휴무자를 배정하면 유효한 계획이 아니지.

이번 수업에서 Validator가 보증하는 것은 정의된 필수 규칙의 준수야. 최적화 품질은 별도의 지표와 비교 기준으로 평가해야 해.

⚙️ 10. 별도 WORKER가 없어도 이 구조를 구현할 수 있을까?

가능해. 그리고 그 사실이 중요해.

API, Service, Creator, Validator, Repository를 논리적으로 분리하는 것과 프로세스를 분리하는 것은 다른 결정이야.

10-1. 모듈 분리

Python에서 파일을 다음과 같이 나눴다고 생각해 보자.

app/
  api.py
  application_service.py
  creator.py
  validator.py
  repository.py
  database.py

이것은 코드의 책임을 나눈 거야.

한 Python 서버 프로세스에서 전부 실행해도 돼.

API가 Service 함수를 호출하고, Service가 Creator 함수를 호출하며, Validator를 거쳐 Repository로 저장할 수 있어.

이 구조에서는 별도 프로세스나 작업 큐가 필요하지 않을 수 있어.

10-2. 동기 방식의 단일 서버 MVP

가장 단순한 흐름은 다음과 같아.

동기 방식 — HTTP 응답 전에 계산까지 수행
HTTP 요청
↓
API → Service → Creator → Validator → Repository
↓
확정 결과 HTTP 응답

이 구현의 장점은 단순성이야.

다만 노선 계산이 오래 걸리면 해당 요청이 오랫동안 끝나지 않아. 웹 서버의 실행 구조에 따라 다른 요청의 처리 자원을 점유할 수도 있지.

HTTP 요청이 시간 제한을 초과하거나 클라이언트가 연결을 끊었을 때 작업이 어떻게 되는지도 명확히 정해야 해.

중요한 점은 동기 방식이라고 job 기록이 불필요한 것은 아니라는 것이야. 작업 이력과 실패 원인, 중복 요청을 추적할 필요가 있다면 단일 프로세스에서도 job을 DB에 저장할 가치가 있어.

10-3. 같은 프로세스 안의 비동기 작업

HTTP 요청을 받은 뒤 job ID를 먼저 반환하고, 같은 프로세스 안에서 작업을 이어서 실행하는 방식도 있어.

이렇게 하면 브라우저는 상태 조회를 통해 진행 상황을 확인할 수 있지.

그러나 서버 프로세스가 종료되면 내부 실행 작업도 함께 사라질 수 있어. job을 DB에 저장했더라도 자동으로 다시 실행되지는 않아.

또 이벤트 루프에서 CPU 계산을 그대로 오래 수행하면 다른 비동기 요청의 진행을 막을 수 있어.

따라서 HTTP에 빨리 응답한다는 사실과 계산이 별도 프로세스로 격리됐다는 사실은 달라.

10-4. 별도 WORKER 프로세스

WORKER는 등록된 작업을 가져와 실제 계산을 수행하는 실행자야.

API 프로세스가 job을 등록하고, WORKER가 대기 중인 job을 선택해 Creator와 Validator를 실행할 수 있어.

두 번째 구조에서는 프로세스 사이의 통신이 필요해.

공유 DB의 job을 조회하는 방식이나 별도 작업 큐를 사용할 수 있어.

큐(queue)는 처리할 작업을 대기시키는 구조야. 보통 먼저 등록한 작업을 먼저 처리하는 방식이지만, 우선순위나 재시도 정책에 따라 순서는 달라질 수 있어.

SQLite jobs 테이블을 간단한 대기열처럼 사용할 수도 있어. 그러나 여러 WORKER가 동시에 같은 PENDING job을 읽으면 둘 다 실행할 위험이 있으므로, 작업을 가져가는 행위 자체를 조건부 갱신 등의 원자적 연산으로 만들어야 해.

그리고 WORKER가 작업을 가져간 뒤 사라졌다면, 남은 job을 누가 언제 회수할지도 정해야 해.

10-5. 각 방식에서 얻는 것과 잃는 것

08강 비교와 확인
구조얻는 것감수하는 손실

같은 프로세스 내부 비동기빠른 응답, job 상태 조회프로세스 종료에 취약, 작업 회수 구현 필요

중요한 건 WORKER가 있느냐 없느냐보다 선택한 구조에서 실제로 어떤 보장이 있는지 정확하게 설명하는 것이야.

10-6. 단일 서버와 여러 서버의 '진실'은 달라질까?

단일 서버에서 SQLite 파일 하나를 사용한다면 job과 final을 같은 DB에 보관하는 것이 자연스러워.

그러나 여러 서버가 각각 로컬 plans.db를 가진다면 서버 A와 B가 서로 다른 활성 계획을 읽을 수 있어.

이 경우에는 두 서버가 공유하는 권위 있는 저장소가 필요해.

SQLite 파일을 네트워크 공유 드라이브에 올리는 것만으로 모든 분산 문제가 해결되는 것도 아니야. 파일 잠금과 네트워크 파일시스템의 특성, 동시 쓰기, 장애 복구를 별도로 고려해야 해.

SQLite는 한 DB에 대한 쓰기 트랜잭션이 직렬화되는 특성을 갖고 있어. 단일 서버에서 간결한 구현을 선택할 수 있다는 장점이 있지만, 여러 서버·다수 WORKER의 높은 동시 쓰기 요구를 그대로 충족하는 범용 분산 DB라고 생각하면 안 돼.

여러 서버 환경에서는 공용 DB와 작업 큐, 소유권 임대, 세대 번호, 모니터링을 갖춘 구조를 검토할 수 있어. 하지만 이번 시험의 단일 서버 MVP를 이해하는 데 그 모든 것을 먼저 구현할 필요는 없어.

🛡️ 11. 컴포넌트를 나눴는데도 우회 저장이 가능하다면?

여기까지 Service가 최종 확정을 담당하고 Creator는 후보만 만든다고 했어.

그런데 실제 코드에서 Creator가 DB 연결을 직접 열 수 있다면 다음과 같은 코드를 작성할 수도 있겠지.

def create_routes(input_data):
    candidate = calculate_routes(input_data)

    # 위험한 우회 경로
    db.insert_into_final(candidate)

    return candidate

그러면 Service에서 아무리 Validator를 호출해도 소용이 없어. 검증하기 전에 이미 공식 결과가 저장됐으니까.

문제의 핵심은 검증기를 만들어 놓았다는 사실이 아니라, 검증을 거치지 않고 공개되는 경로가 존재하느냐야.

검증과 확정 정책이 우회됨

이 문제를 줄이려면 적어도 코드 구조에서 공식 발행 경로를 한곳으로 모아야 해.

Creator에는 검증 전 후보를 작성할 수 있는 인터페이스만 제공하고, final 발행은 Service가 사용하는 제한된 Repository 기능으로 모을 수 있어.

하지만 여기에도 한계가 있어.

같은 프로세스의 모든 코드가 SQLite 파일에 직접 접근할 수 있다면, Python 모듈을 나누는 것만으로 보안 경계를 강제할 수는 없어. 개발자가 다른 곳에서 DB에 직접 쓰는 코드를 넣을 수 있기 때문이야.

그러므로 소유권 통제에는 수준이 있어.

  • 설계 규칙: 어떤 컴포넌트가 무엇을 변경할지 명확히 한다.
  • 코드 구조: 공식 발행 함수를 한곳으로 모으고 호출 경로를 제한한다.
  • DB 제약: 기본키·외래키·고유 조건·트랜잭션 등으로 잘못된 저장을 줄인다.
  • 독립 검증: 생성 코드와 별도로 실제 결과를 검사한다.
  • 운영 권한: 별도 DB 사용자·권한 체계를 지원하는 환경에서는 물리적 쓰기 권한도 분리할 수 있다.

SQLite에서 코드 모듈별로 서로 다른 DB 계정 권한을 주는 방식은 일반적인 서버형 DB처럼 제공되지 않아. 따라서 단일 SQLite MVP에서는 구조적 통제와 테스트, 트랜잭션 및 DB 제약을 조합하는 것이 현실적이야.

그리고 DB 제약조건만으로 복잡한 노선 최적화 규칙을 전부 표현할 수도 없어. 예를 들어 구간별 탑승 인원이나 모든 근무자의 정확한 배정 검사는 여러 행을 함께 봐야 하므로 별도 검증 로직이 필요할 수 있지.

소유권은 이름표가 아니라 변경 경로를 통제하는 규칙이라는 점을 기억하자.

🔎 12. 내가 만들었다면 무엇으로 실제 동작을 확인할까?

설계가 그럴듯하다고 해서 시스템이 그 설계대로 동작한다는 증거는 아니야.

실제로 구현한 서비스라면 다음의 세 층을 나누어 검증하는 게 좋아.

첫째, 컴포넌트의 책임이 지켜지는가?

Creator가 반환한 후보를 Validator에 전달하기 전에 final에 저장하는 경로가 없는지 살펴봐야 해.

API가 권한 검증 없이 Service를 호출하는 곳은 없는지, 구성원 조회에서 temp를 읽는 곳은 없는지도 확인하지.

이것은 코드 구조를 검토하는 검사야.

둘째, 상태 변경이 실제 DB에 남는가?

job을 등록한 뒤 서버를 종료하고 재시작해 보자.

DB에 등록된 job이 남는지, 중단된 상태를 처리하는지, 이전 final이 훼손되지 않았는지 확인해야 해.

또한 final 저장 중 예외를 인위적으로 일으켜, 일부 노선만 공식 결과로 남지 않는지 확인할 수 있어.

이것은 저장과 복구 동작을 검사하는 방법이야.

셋째, 동시 요청과 실패가 의도한 순서로 처리되는가?

가령 J104가 검증을 끝내기 직전에 데이터셋 버전을 바꿔 보자.

J104가 예전 버전 결과를 현재 계획으로 발행하지 않는지 확인해야 해.

취소와 확정이 경쟁하는 상황, 오래된 실행 시도가 뒤늦게 종료되는 상황, 확정 성공 후 응답이 소실되는 상황도 각각 재현할 가치가 있어.

이것은 상태 경쟁과 확정 조건을 검증하는 방법이야.

이 표는 실제로 시험 제출물을 검사한 결과가 아니라, 구현을 검증할 때 필요한 증거의 설계야.

실제 코드를 작성했다면 실행 로그, DB 레코드, 테스트 결과, API 응답을 함께 확보해야 해. AI 코딩 도구가 '테스트 완료'라고 보고했다는 사실만으로 검증이 끝난 것은 아니야.

🧠 13. 이제 하나의 원리로 다시 연결해 보자

앞에서 익힌 모든 개념을 묶어 보자.

운영자가 버튼을 누른다는 것은 시스템에 업무를 실행해 달라는 요청을 하는 거야.

HTTP는 그 요청을 서버에 전달하고, API는 요청자와 입력을 확인해.

Application Service는 이 요청을 하나의 작업으로 등록하고 입력을 고정해. 그 기록이 job이야.

Creator는 그 입력으로 후보를 계산해. 그 후보가 temp야.

Validator는 그 후보가 운영 규칙을 만족하는지 별도로 확인하지.

마지막으로 Service는 검증 결과뿐 아니라 최신 데이터셋 버전, 현재 실행 시도, 취소 상태, 후보의 동일성, 다른 계획과의 확정 경쟁을 확인해.

조건이 맞으면 Repository를 통해 final과 공개 상태를 하나의 트랜잭션으로 확정해.

구성원 조회는 이 공개된 final만 사용해.

이 세 경계를 섞으면 위험이 생겨.

요청자가 운영자라는 이유로 잘못된 결과를 저장하면 요청 경계와 검증 경계를 혼동한 거야.

Creator가 후보를 만들었다는 이유로 이를 공식 계획으로 저장하면 계산과 확정 경계를 혼동한 거야.

Validator가 통과시켰다는 이유로 버전과 취소 여부를 확인하지 않으면 검증 시점의 사실과 확정 시점의 사실을 혼동한 거지.

이번 수업에서 얻어야 할 이해는 이거야.

시스템의 안전성은 컴포넌트가 몇 개로 나뉘어 있는지가 아니라, 상태를 바꿀 권한이 어디에 있고 그 권한을 행사하기 전에 무엇을 확인하는지에 달려 있어.

아래 질문은 지금 점수를 매기는 시험이 아니라, 수업의 핵심 인과관계를 자신의 언어로 연결하는 확인 지점이야.

① job과 final은 왜 다른가?

노선 생성이 실패했는데도 기존 구성원이 정상적으로 노선을 조회할 수 있는 상황을 job과 final의 차이로 설명해 봐.

② 검증을 통과했는데 왜 저장을 거부하는가?

J104가 버전 7로 계산하고 검증을 통과했지만, 확정 직전 버전 8이 적용됐다면 어떤 선택이 가능하고 왜 현재 계획으로 발행하면 위험할까?

③ WORKER가 죽었는데 DB에는 RUNNING이 남는 이유는?

프로세스 메모리와 SQLite에 커밋된 기록의 차이를 사용해 설명해 봐.

④ 생성기와 검증기를 나눴는데도 버그를 놓치는 경우는?

Creator와 Validator가 같은 잘못된 이동 시간 계산 함수를 사용할 때 어떤 문제가 생길까?

통합편 답변 안내: 위 네 칸은 이 브라우저에 보관되는 자기 설명 공간이야. 이 HTML은 AI 채점·ChatGPT 전송·공식 점수 계산을 하지 않아. 다른 기기와 자동 동기화하지 않으므로 필요한 내용은 백업하거나 직접 복사해 보관해.

Bailey라면 마지막으로 이렇게 물을 거야.

"Creator와 Validator를 완벽하게 나눴다고 했지? 그런데 Creator가 final 테이블에 직접 INSERT할 수 있다면, 네가 만든 분리는 실제로 무엇을 보장하지?"

이 질문에 계산 책임의 분리와 최종 상태 변경 권한의 통제는 다르다는 관계를 설명할 수 있다면, 이번 수업에서 가장 어려운 구분 중 하나를 이해한 거야.

참고 근거와 범위
