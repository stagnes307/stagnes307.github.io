🧱 1. 왜 '만드는 사람'과 '확인하는 사람'을 나눌까?

종이에 통근버스 노선을 그렸다고 생각하자. 정류장 A, B에서 직원을 태우고 사업장 C로 가는 경로를 적었다. 누군가 “좋아요, 완성입니다”라고 답했다. 그런데 정류장에 50명이 타야 하는데 버스는 45석뿐이고, 사업장 도착 시각은 근무 시작보다 10분 빠를 뿐이라면 어떨까? 경로가 존재한다는 사실과 경로가 요구를 충족한다는 사실은 다르다.

이 차이가 오늘의 시작점이야. Creator(생성기)는 수많은 후보 중 그럴듯하고 효율적인 답을 찾는 역할을 맡는다. Validator(검증기)는 이미 주어진 후보를 원본 요구와 입력에 대조해서 허용 가능한 답인지 판정하는 역할을 맡는다. 전자는 탐색의 문제, 후자는 판정의 문제다.

그렇다고 검증이 언제나 계산상 쉽다는 뜻은 아니야. 예컨대 단순 좌석 수 세기는 빠르지만 복잡한 전역 자원 제약을 증명하려면 비용이 클 수 있어. 핵심은 목적과 출력의 차이야. Creator가 “이 계획이 좋아 보인다”를 반환한다면, Validator는 “해당 입력·규칙·시점에 대해 무엇을 확인했고 어디서 위반했는가”를 반환해야 해.

도식 읽기: 오른쪽 검증기가 Creator의 말을 받아 적는 게 아니라, 별도로 받은 원본 입력과 규칙을 기준으로 후보 P를 검사해야 한다. 화살표가 하나 더 있는 이유가 바로 이 점이야.

생성 안에 이미 검사가 있는데 왜 또 검증할까?

Creator도 경로를 만들면서 정원을 확인할 수 있어. 실제로 그래야 불필요한 후보를 줄인다. 하지만 생성 도중 사용하는 검사는 대체로 탐색을 안내하는 내부 제약 검사이고, 최종 Validator는 반환된 산출물 전체가 실제 계약을 만족하는지 보는 판정 경계야.

예를 들어 생성기가 정류장별 합계는 확인했는데 특정 구성원을 두 노선에 중복 배정했을 수 있다. 내부 코드에 capacity <= 45 검사가 있었다는 사실만으로 중복 배정이 없다는 결론은 나오지 않아. 생성기의 코드가 올바르게 의도되었다는 것과 실제 결과가 올바르다는 것도 다르지.

핵심 문장: 생성기는 정답 후보를 만드는 주체이고, 검증기는 그 후보를 사용해도 되는지 결정할 증거를 만드는 주체다. 이 둘의 기능을 분리하는 이유는 탐색의 자유와 판정의 신뢰를 동시에 확보하기 위해서야.

🪜 2. 통근버스 계획을 컴퓨터는 어떤 순서로 처리할까?

시험 지시문이 요구한 실제 업무 흐름은 세 단계다. ① 후보 중 정류장 선택, ② 근무자 정류장 배정, ③ 정류장을 잇는 운행 노선과 시간표 생성. 모든 단계가 완료되었다고 해서 자동으로 올바른 결과가 되는 것은 아니므로 마지막에 전체 계획의 계약을 다시 확인해야 해.

이 수업에서 쓰는 구체적 입력과 규칙

원 시험의 입력 묶음은 sites.csv, shifts.csv, employees.csv, work_schedule.csv, stops.csv, travel_times.csv, ridership.csv의 7종이야. 기본 차량 정원은 45석, 출근은 근무 시작 최소 20분 전 도착, 퇴근은 근무 종료 10분 이후 출발이야. 선택한 평일 근무일의 실제 WORK 직원은 각 방향에 정확히 한 번 배정하고 OFF 직원은 배정하지 않아. 특정 정류장에서 타는 승객 수만이 아니라 모든 이동 구간의 실제 탑승 인원이 정원을 넘지 않아야 하지. 두 지점 사이 시간은 오직 travel_times.csv에서 읽고, A→B와 B→A를 다른 값으로 다룰 수 있어야 한다.

ridership.csv는 과거 탑승 실적이지, 현재 근무자의 좌석을 줄여도 좋다는 허가가 아니야. 평균 탑승률이 60%라고 해서 오늘의 WORK 직원 100명 중 60명만 배정하면 요구를 위반하는 거야. 또한 파일에 등록된 후보지 이외의 임의 지점을 새 정류장으로 만들어서는 안 돼.

🔍 3. '검증기를 분리했다'는 말은 정확히 어디까지 맞을까?

컴포넌트를 두 파일로 나누는 것만으로 서로 독립이라고 할 수는 없어. 다음 세 층위를 차례로 구분하자.

첫째: 역할 독립 — 서로 다른 질문을 묻는다

Creator: “어떻게 하면 모든 직원에게 운행을 제공하면서 운행 횟수와 이동시간을 줄일 수 있지?”

Validator: “이 특정 결과가 이 버전의 직원·근무표·교통시간·운영 규칙을 전부 지키는가?”

역할을 분리했다면 Creator는 탐색 방법을 바꾸어도 결과 계약을 그대로 지켜야 하고, Validator는 생성기가 어떤 알고리즘을 썼는지 몰라도 산출물을 검증할 수 있어야 해. 이런 성질을 블랙박스 검증 가능성이라고 생각하면 이해가 쉽다.

둘째: 자료 독립 — 생성기의 자기 주장 대신 원본을 본다

나쁜 검증:

# 가상 의사코드: 실제 시험 제출 코드 아님
result = creator.generate(input_data)
if result["creator_says_valid"]:
    publish(result)

검증기가 Creator가 설정한 creator_says_valid 플래그만 확인한다면, 생성기 오류와 함께 틀릴 수 있어. 더 나은 형태는 다음과 같아.

# 가상 의사코드: 라이브러리·DB 함수는 설명을 위한 추상 이름
candidate = creator.generate(frozen_input, frozen_rules)
report = validator.validate(
    original_input=frozen_input,
    rules=frozen_rules,
    candidate=candidate,
)
if report.ok:
    finalize_exact_candidate(candidate, report)

이때 frozen_input은 생성 시 사용한 완전한 데이터 묶음의 불변 스냅샷을 뜻해. 코드에서 같은 변수를 전달하는 것만으로 진짜 불변이 보장되지는 않아. 메모리 객체를 누군가 수정할 수 있다면 깊은 복사, 불변 자료구조, DB 스냅샷 또는 내용 해시 등 추가 통제가 필요해.

셋째: 구현 독립 — 공통 오류가 함께 전파되는 정도를 낮춘다

Creator와 Validator가 동일한 잘못된 파서를 쓰면 어떨까? work_status를 OFF인데도 WORK로 읽는다든지, travel_times.csv의 방향을 뒤집는 버그가 있다고 해 보자. 생성 결과도 틀리고 검증 기준도 똑같이 틀려서 검증 통과라는 그럴듯한 허위 안전감을 만들 수 있어. 이를 공통 원인 오류(common-mode failure)라고 부른다.

하지만 “모든 코드를 무조건 두 벌 작성”도 좋은 답은 아니야. 독립 파서를 별도로 만드는 것은 개발·유지보수 비용을 늘리고, 서로 다른 파서가 다른 뜻으로 해석하는 오류를 새로 만들 수도 있어. 선택지는 층위별로 달라.

09강 비교와 확인
전략 얻는 것 치르는 비용·남는 위험
동일 파서 + 동일 검증 헬퍼 재사용 구현량·계약 불일치 감소 헬퍼 버그가 생성·검증에 동시에 반영

단일 서버에선 대개 입력 스키마는 일관되게 정규화하되, 결정적인 업무 불변식은 생성기의 내부 상태를 신뢰하지 않고 독립 경로에서 계산하는 균형이 실용적이야. 중요한 경계값은 원본 CSV나 기준 fixture에서 별도로 계산한 기대값과도 대조해. 독립은 '공통 코드가 0줄'이라는 절대 명제가 아니라 같은 버그가 두 쪽을 동시에 통과할 확률과 영향을 의식적으로 줄이는 설계야.

파서를 공유한 채 '독립 검증'이라고 말해도 될까?

범위를 붙이면 돼. “생성 알고리즘과 규칙 검사 루틴은 분리했지만 CSV 해석기는 공유한다. 그래서 파서 버그는 공통 위험이고, 원본 데이터의 경계 사례 테스트로 보완한다.” 이게 “완전히 독립”이라는 과장보다 훨씬 정확해.

🧬 4. 후보가 완성된 뒤 정말 그 후보를 검증했는가?

여기서 초보자가 가장 자주 놓치는 것은 시간이야. Validator가 옳게 검사하더라도, 검사한 대상과 저장한 대상이 다르면 의미가 없어.

입력 버전과 규칙 버전이 필요한 이유

오전 9시에 운영자가 데이터셋 D1을 적용하고 정원 45, 여유 20분으로 생성 요청을 했다고 하자. 생성이 1분 걸리는 동안 다른 운영자가 D2를 적용하거나 정원을 40으로 바꿨다. 생성기는 D1/45/20으로 만들었는데 검증기는 '현재 화면의 값'인 D2/40/20으로 검사한다면, 동일한 계획에 대해 서로 다른 기준을 쓰는 셈이야.

그래서 한 작업에는 최소한 다음 식별 정보가 필요해.

job J-104
 ├─ dataset_version = D1
 ├─ dataset_content_hash = H(D1의 실제 CSV 7종 내용)
 ├─ rules_version = R3
 ├─ parameters = {period, capacity=45, arrival_margin=20}
 ├─ candidate_id = C-7
 └─ candidate_content_hash = H(C-7의 실제 내용)

버전 이름만 있으면 D1이라는 이름 아래 파일이 바뀌는 것을 탐지하지 못할 수 있어. 내용 해시는 바이트 내용이 바뀌었는지 식별하는 수단이지만, 그 자체가 업무 규칙 통과 증명은 아니다. 실제 구현에서는 파일 순서·인코딩·줄바꿈·정렬 등 무엇을 해시하는지 정해 일관되게 적용해야 해. 보안 위협 모델이 있으면 약한 체크섬 대신 충돌에 강한 해시를 쓰고, 누가 스냅샷을 수정할 수 있는지도 통제해야 한다.

완료 후보의 정확한 의미

생성기가 스트리밍으로 100개 노선 중 70개를 먼저 만들었다고 하자. 이 70개는 부분 후보일 수는 있지만, 완료 계획은 아니야. 같은 날짜·방향의 나머지 30개가 없으면 모든 근무자 정확히 한 번 배정 같은 전역 조건을 결정할 수 없거든. candidate.status = COMPLETE는 단순히 프로세스가 종료됐다는 뜻이 아니라, 출력 목록과 메타데이터가 더는 변경되지 않는 확정 스냅샷이어야 해.

시각   생성기                 검증기                  공개 결과
T0     C 초안 생성 시작      입력 형식 검사 가능      기존 final F0
T1     C 일부 노선 작성      부분 로컬 검사 가능      기존 final F0
T2     C 완성·봉인           정확한 C 해시 확인       기존 final F0
T3     C 변경 금지           C 전체 규칙 검증         기존 final F0
T4     결과 전달 대기        C 통과 보고 기록         기존 final F0
T5     ─                     ─                       C를 final F1로 확정

검사 후 C가 수정된다면 T3의 통과 판정은 새 버전 C′에는 적용되지 않아. 이 문제는 TOCTOU(Time of Check to Time of Use, 확인 시점과 사용 시점의 차이)야. 막는 방법은 후보를 봉인한 뒤 수정 불가로 만들고, 검증 보고서에 후보 해시를 기록하며, 확정 트랜잭션에서 동일 후보·동일 입력/규칙 버전을 재확인하는 것. 유효한 오래된 계획이 새로 적용한 데이터의 최신 계획인 것처럼 표시되지 않도록 활성 버전 포인터도 신중히 관리해야 해.

해시는 만능 봉인이 아니다

해시는 일치성 검사의 재료이지 자동 잠금장치가 아니야. 생성기가 후보를 바꿀 수 있는 공유 테이블이라면, 검증 직후부터 저장 직전 사이에 변경이 생긴다. 같은 트랜잭션의 적절한 격리·잠금 또는 불변 저장소를 이용해야 하고, 확정 단계가 검증 당시의 버전·내용 식별자를 비교해야 해. 더구나 서로 같은 버그로 만든 잘못된 결과와 검증 보고서는 서로 해시가 완벽히 일치할 수 있다. 동일성과 정당성은 다른 속성이야.

🕸️ 5. 병렬 처리 여부는 '두 개의 이름'이 아니라 의존 그래프가 결정한다

이제 선수 개념을 다시 잡아 보자. 동시성(concurrency)은 여러 작업이 겹쳐 진행되는 구조이고, 병렬성(parallelism)은 실제로 같은 시간에 별도 실행 자원에서 여러 계산이 수행되는 상태야. 비동기(asynchrony)는 시작한 작업이 끝날 때까지 호출자가 계속 붙잡혀 기다리지 않도록 결과 통지를 나중에 받는 인터페이스 방식이지. 셋은 서로 겹칠 수 있어도 동일하지 않아.

예를 들어 서버가 노선 생성을 Job으로 접수하고 HTTP 202 Accepted를 반환한 뒤 상태 조회 URL을 제공하면 비동기 요청 처리야. 하지만 서버 내부 생성기와 검증기가 순서대로 실행돼도 비동기일 수 있어. 반대로 같은 프로세스에서 입력 데이터의 서로 독립적인 두 검사를 병렬로 해도 최종 HTTP 응답은 동기적으로 기다릴 수 있지.

DAG: 누가 누구의 결과를 기다려야 하는가

DAG(Directed Acyclic Graph, 방향이 있고 순환이 없는 그래프)는 작업 간 필수 선후 관계를 그린 그림이야. A → B는 B가 A의 결과를 필요로 한다는 뜻이지, 단지 B가 'A 다음 줄에 코딩되어 있다'는 뜻이 아니야.

                     [원본 입력 스냅샷 I]
                      /      |       \
                     ▼       ▼        ▼
               [형식 검사] [참조 검사] [규칙/기간 검사]
                     \       |        /
                      └──────┼───────┘
                             ▼
                        [입력 합격]
                             │
                             ▼
                    [Creator 계획 생성]
                             │
                             ▼
                   [후보 C 완료·불변]
                      /      |       \
                     ▼       ▼        ▼
                  [좌석]  [시간표]   [배정 검사]
                      \      |       /
                       └─────┼──────┘
                             ▼
                     [전역 일관성 검사]
                             │
                             ▼
                       [확정 트랜잭션]

핵심: 후보 C 완료 이전에도 수행 가능한 것은 후보가 필요 없는 입력 검사야. 후보 내용이 필요한 'C의 최종 좌석 검사'는 C 생성 완료 후에야 시작 가능해. 좌석·시간표·배정 검사는 같은 불변 후보를 읽는다면 병렬화할 수 있지만, 전역 합격 결정은 세 검사가 모두 끝나고 서로의 결과를 종합한 다음 해야 해.

'Creator/Validator 병렬'이라는 표현이 무조건 틀렸을까?

아니야. 무엇을 병렬로 했는지 물어봐야 해. (1) 입력 검사와 후보 생성 준비, (2) Creator가 진행 중에 완료된 부분을 Validator가 임시 확인하는 파이프라인, (3) 완성 후보에 대해 좌석·시간·중복 검사를 병렬 수행하는 건 가능해. 그러나 (4) 아직 존재하지 않는 완성 후보를 '완성 후보'인 양 최종 검증하는 건 논리적으로 불가능하지. 중요한 것은 병렬 실행 여부가 아니라 검증 결과가 무엇을 보증하는가야.

파이프라인의 시간 이익과 필수 최종 장벽

시간 ─────────────────────────────────────────────────────────▶

                                                              │
                                                      [최종 승인/거부]

부분 검사로 일찍 오류를 찾고 생성 작업을 중단할 수 있으므로 시간·자원을 아낄 수 있어. 다만 병렬 읽기와 생성기 쓰기가 같은 데이터에 충돌하지 않도록 완료된 조각의 불변 스냅샷을 넘겨야 하고, 각 조각이 충분하다고 선언할 기준도 필요해. 최종 단계에서는 모든 조각이 하나의 일관된 후보에 속하는지 합쳐 확인해야 해.

Validator가 Creator와 분리되어 있어도 검사 내용이 빈약하면 도움이 안 돼. 최소한 입력 집합에서 기대되는 대상을 독립적으로 만들고, 후보의 실제 노선·배정을 계산해서 비교해야 해. 예컨대 “Creator가 만든 전체 인원이 100명”이라는 수를 믿지 말고, work_schedule.csv에서 그 날짜 WORK인 직원이 누구인지 다시 구해야 한다는 뜻이지.

① 대상 집합: 누구를 몇 번 태워야 하나?

주어진 날짜 d, 방향 q에 대해 원본 근무표의 WORK 직원 집합을 W(d)라고 하자. 내보낸 결과에서 해당 날짜·방향에 직원 e가 배정된 횟수를 count(d,q,e)라고 하자. 그러면 필수 조건은 이렇게 말할 수 있어.

  • e ∈ W(d)라면 count(d,q,e) = 1
  • e ∉ W(d)라면 count(d,q,e) = 0
  • q는 출근(to_work)과 퇴근(to_home) 각각에 대해 확인한다.

'총 근무자 100명이고 배정도 100건'이라는 총합 일치는 충분하지 않아. A가 두 번, B가 0번이어도 총합은 100일 수 있거든. 그래서 반드시 직원별 키와 횟수를 대조해야 해.

② 각 배정은 실제 노선에 말이 되게 연결되어 있나?

배정의 route_id가 같은 날짜의 실존 노선을 가리키는지, 직원·노선의 shift_code가 맞는지, 출근 하차점 및 퇴근 승차점이 해당 직원의 사업장인지 확인해야 해. 승차와 하차 지점은 같은 노선의 stops 배열에 있어야 하고, 승차 순번은 하차 순번보다 작아야 해. route_id는 같은 근무일 안에서 고유해야 하므로, 단순히 이름이 보이는 노선 하나를 연결하는 것으로 끝나면 안 돼.

③ 정원은 '노선 총배정 수'보다 구간별 점유로 생각한다

출근 노선이 A → B → 사업장 순서라면 A에서 30명이 타고 B에서 20명이 타는 경우 사업장 도착 직전 50명이 되므로 정원 45를 초과해. 반면 중간 하차가 허용되는 일반 노선은 총 탑승 인원이 50명이라도 구간별 동시 점유가 45명 이하일 수 있어. 따라서 내보내기 형식의 실제 승하차 순서를 따라 정차 지점마다 인원 변화를 누적하는 구간 점유 검사가 일반적으로 안전해.

가상 운행: A ───▶ B ───▶ ICN
처음 점유        0
A: 30명 탑승   30 / 45   통과
B: 20명 탑승   50 / 45   실패  ← 이 구간에서 초과
ICN: 50명 하차  0

출근/퇴근 규칙에서 종점·시점 사업장은 구분하고, 입력에 없는 임의 승하차를 만들어서는 안 돼.

④ 시간은 방향과 날짜를 함께 검증한다

가상 입력에서 A→B=12분, B→A=19분이라고 하자. 출근 A 07:00 → B 07:08인 계획은 8분밖에 걸리지 않았으므로 A→B 기준으로 실패야. 반대로 이동 방향이 B→A라면 19분을 써야 해. 한 파일에 두 값이 모두 존재하더라도 방향을 무시하고 min(12,19)를 쓰면 안 되지.

또 시험 내보내기 형식에는 실제 정차 시각이 한국 시간 오프셋을 포함한 일시로 들어가야 해. 인접 정차 시각이 증가하고 그 차이가 이동시간 이상인지 확인한다. 출근 종점은 근무 시작보다 적용한 도착 여유 시간만큼 일찍, 퇴근 시점은 근무 종료 10분 후 이후여야 해. 시험의 내보내기 검증 규칙에는 출근 도착이 근무 시작 전 12시간 이내, 퇴근 출발이 근무 종료 후 12시간 이내라는 추가 제한도 있어. 자정 전후 근무시간대에서는 HH:MM 문자열만 비교하면 날짜를 틀리기 쉬워 실제 일시로 복원한 뒤 비교해야 해.

🛠️ 8. 가상 구현으로 확인하는 불변식과 실패 원인

아래 코드는 실제 CSV 스키마 전체를 구현한 완성 프로그램이 아닌 교육용 Python 예시야. work_status 기준으로 누락·중복·휴무자 오배정을 잡는 핵심 원리를 보여 준다. 파일 경로, API, DB 저장, 시간 검사는 생략되었으며 이 대화에서 실행 테스트하지 않았다.

from collections import Counter


def validate_assignments(work_rows, assignment_rows, work_date, direction):
    """교육용 부분 검사: 날짜/방향/직원별 정확히 한 번만 확인."""
    expected = {
        row["emp_id"]
        for row in work_rows
        if row["work_date"] == work_date
        and row["work_status"] == "WORK"
    }

    assigned = [
        row["emp_id"]
        for row in assignment_rows
        if row["work_date"] == work_date
        and row["direction"] == direction
    ]
    counts = Counter(assigned)

    missing = sorted(expected - counts.keys())
    duplicate = sorted(emp for emp, n in counts.items() if n > 1)
    unexpected = sorted(counts.keys() - expected)

    return {
        "ok": not (missing or duplicate or unexpected),
        "missing": missing,
        "duplicate": duplicate,
        "unexpected": unexpected,
    }

가상 입력 WORK={E101,E102,E103}, 배정 E101,E102,E102라면 기대 출력은 missing=[E103], duplicate=[E102], unexpected=[]야. 이 사례의 중복은 Counter가 보존하지만, set만 비교하면 중복 횟수가 사라져. 자료구조 선택이 검증 가능한 속성을 바꾼다는 점을 이해해.

그러나 이 함수 하나로 최종 Validator가 완성된 것은 아니야. work_schedule.csv에 같은 직원·날짜가 중복으로 존재하거나 참조 ID가 잘못된 입력부터 먼저 검사해야 하고, 나머지 정원·시간·노선 참조·기간·시각 제한도 따로 확인해야 해. 위 함수가 통과했다고 해서 결과 전체를 안전하다고 판정할 수 없어.

🔐 9. SQLite에서 검증 통과 결과를 어떻게 안전하게 공개할까?

단일 서버·SQLite를 기준으로 생각하자. 서버 재시작 후에도 jobs, 후보, final이 남으려면 필요한 상태는 DB 등 지속 저장소에 기록해야 해. 이 수업에선 이해를 위해 SQLite 테이블을 개념적으로 jobs, candidate_plans, validation_reports, final_plans, active_plan으로 나눌게. 시험에서 이 테이블 구성을 지정한 것은 아니다.

핵심은 SQL 문법의 양이 아니라 확정의 경계야. 검증된 후보 C와 그 보고서 V가 같은 입력·규칙 버전·후보 해시를 가리키는지 확인한 뒤, 새 final 기록과 active_plan 포인터 변경을 하나의 트랜잭션으로 묶는다. 중간에 오류가 나면 둘 다 롤백되어 이전 계획을 가리켜야 해.

처음 상태: active_plan ──▶ F0 (이전의 정상 결과)

J-104가 생성한 C1 검증 실패:
    temp C1 ──▶ FAILED
    active_plan ──▶ F0   (유지)

J-105가 생성한 C2 검증 통과:
    [트랜잭션 BEGIN]
       C2·검증보고서·버전 정합성 확인
       final F1 기록
       active_plan ──▶ F1 갱신
    [COMMIT]

실패하여 ROLLBACK 시:
    active_plan ──▶ F0   (그대로)

SQLite는 단일 DB 파일을 사용하는 구성에 적합하고 트랜잭션을 지원해. 다만 BEGIN만 쓴다고 모든 경쟁 상태가 사라지는 건 아니야. SQLite의 동시 쓰기 제약과 트랜잭션 시작 방식, 충돌 재시도 정책을 알아야 하고, 동일 요청이 중복 제출된 경우의 멱등성도 별도 고려가 필요해. 예를 들어 작업이 확정된 직후 HTTP 응답이 끊기면 브라우저는 실패로 보아 재시도할 수 있지만 DB에는 이미 새 계획이 저장되어 있을 수 있지. 이때 요청 식별자와 상태 조회로 “이미 확정된 동일 작업”을 구별하지 않으면 중복 생성될 수 있어.

'검증 시점'과 '공개 시점'의 틈은 어떻게 막아야 하지?

검증 리포트에 후보 해시가 들어 있어도 검증 이후 후보가 변경된다면 문제가 남아. 가장 간단한 원칙은 검증 대상으로 삼은 후보를 불변 객체로 취급하고, 확정 트랜잭션 안에서 그 식별자·해시와 리포트가 일치할 때만 공개하는 거야. 운영자가 그 사이 새 데이터셋을 적용한 경우에는 “예전 데이터에 대한 계획을 완료된 이력으로 저장할 수 있는가?”와 “현재 적용 데이터의 활성 계획으로 보여 줄 수 있는가?”를 구분해야 해. 현재 데이터와 달라졌다면 일반적으로 활성 결과의 버전 일치 여부를 다시 요구하거나 재계산 필요 상태로 보여 줘야 하지.

별도 프로세스와 여러 서버에서는 무엇이 달라질까?

09강 비교와 확인
배치 쉬워지는 것 추가로 의식할 문제
단일 서버 프로세스 + SQLite 구성 단순, 로컬 함수 호출, 작은 배포 범위 같은 프로세스 종료 시 실행 중 작업도 중단, 장시간 계산이 요청을 막지 않게 처리
API와 Worker 별도 프로세스 + 공유 SQLite 계산과 HTTP 처리 분리, Worker 재시작 독립 프로세스 간 작업 인수·상태 통지·리스/재시도, 중복 실행 방지
여러 서버 + 공용 DB/큐 처리량·가용성 확장 가능 중복 작업 인수, 분산 잠금/리스, 네트워크 실패, 인스턴스 간 파일·상태 공유

단일 프로세스의 Python 객체에 락을 걸어도 다른 프로세스나 다른 서버에는 그 락이 전파되지 않아. 여러 Worker가 같은 Job을 잡지 않도록 DB의 원자적 상태 변경, 적절한 리스(lease)와 재시도 정책 등 공유된 조정 장치가 필요해. 특히 SQLite 파일을 여러 서버의 일반 네트워크 파일시스템에서 무작정 함께 쓰는 구조는 권장하기 어렵고, 운영 구성의 요구가 커지면 서버형 DB와 작업 큐를 검토해야 해. 이와 별도로 검증이 생성에 의존한다는 논리는 서버 수가 늘어도 변하지 않아.

TIMEOUT, 종료, 검증 실패를 같은 '실패'로 취급해도 될까?

셋 모두 final 공개를 막아야 한다는 공통점은 있지만 원인이 달라. TIMEOUT은 정해진 시간 내 후보 완성·검증을 못 했다는 뜻일 수 있고, WORKER_CRASHED는 실행 주체가 사라진 경우야. FAILED_VALIDATION은 완성 후보를 검사했더니 규칙 위반이 관찰된 경우지. 재시도할 때 동일 입력으로 계산을 다시 할지, 알고리즘을 수정할지, 잘못된 입력을 교정할지가 다르기 때문에 상태를 구분해야 해. 어느 경우든 미검증 temp를 final처럼 노출하지 않는 것이 중심 원칙이야.

🤖 10. 'Creator/Validator'가 AI 작성자·검토자일 때는 다른 문제다

여기서 이름이 같아 헷갈리는 두 번째 층위가 등장해. 시험 복기에는 다른 응시자에게 “Creator와 Validator 병렬 처리”에 관한 질문이 있었다고 전해지지만, 그 표현이 실제 서비스의 계획 생성/검증 컴포넌트를 뜻했는지, AI 코딩 도구의 작성/검토 역할을 뜻했는지는 확인되지 않았다. 따라서 아래를 구분해야 해.

09강 비교와 확인
구분 계획 Creator/Validator AI 작성자/검토자
다루는 대상 근무자 배정·운행 노선·시간표 코드, 설계 문서, 테스트 초안, 설명
Creator의 산출물 계획 후보 데이터 프로그램·PRD·코드 패치
Validator/Reviewer의 판단 원본 CSV와 운영 규칙 대조 요구사항 충족·결함 가능성 검토
신뢰 근거 독립 불변식 계산 및 결과 대조 테스트, 실제 실행 결과, 정적 분석, 독립 근거
큰 착각 '생성기가 맞다고 했으니 맞다' 'AI가 두 역할을 연기했으니 독립이다'

한 AI에게 “이제부터 Validator 역할이 되어 네 코드의 오류를 찾아”라고 시키는 것은 검토 관점을 추가하는 방법이지, 독립적인 사실 검증이 자동으로 이루어졌다는 증명은 아니야. 동일 모델은 같은 잘못된 전제, 잘못 읽은 요구사항, 같은 생략을 반복할 수 있어. 다른 모델을 쓴다고 해도 둘 다 잘못된 시험 지시문 요약을 입력받았다면 독립 판단이 깨진다.

AI 리뷰와 실제 검증의 차이

AI 작성자: “정원을 검사하는 코드를 만들었습니다.”
AI 검토자: “if passengers <= capacity가 있으니 괜찮습니다.”
실제 검증: “passengers는 어떤 구간을 나타내고, 중간 정차마다 어떻게 변하며, 근무자 전원이 정확히 한 번 포함되었는가? 이를 실패 fixture에 넣으면 어떤 결과가 나오는가?”

두 번째 문장은 코드 존재를 확인했을 뿐, 대상을 제대로 계산하는지 아직 검증하지 않았어. 외부 기준은 실행한 테스트 결과, 경계 입력의 기대값, 원본 요구사항과 구현 함수의 대응표, DB 상태, 실제 내보내기 JSON을 비교하는 데서 생겨. AI 리뷰는 그 확인을 도울 수 있지만 실행되지 않은 테스트를 통과했다고 주장해서는 안 돼.

AI 역할을 나눌 때 실용적인 절차

  1. 작성자에게 작업 범위를 분명히 준다. 예: “가상 테스트 데이터 생성과 운행 계획 알고리즘 구현. 정원·기간 제약을 만족하고 반환 데이터 계약을 지켜라.”
  2. 검토자에게 작성자의 자체 요약만 주지 않는다. 가능하면 원본 시험 지시문·원본 스키마·코드 diff·실제 테스트 로그를 제공한다.
  3. 검토자가 독립 기대값을 만들게 한다. 예: 특정 날짜 WORK 집합에서 예상 배정 키를 계산하게 하고 실제 출력과 대조한다.
  4. 실패 입력을 고정한다. 중복 배정·휴무자 포함·방향 뒤바뀐 이동시간·45석 초과·시간 경계값·계획 날짜 누락을 각각 깨뜨려야 한다.
  5. 실행 관찰과 AI 의견을 구분한다. 실행 로그와 입력 파일·검증 결과가 없다면 “검토상 의심 없음”이라고만 말할 수 있고 “실제 검증 완료”라고 말하면 안 된다.

AI 작성자와 검토자가 동시에 서로 다른 모듈을 리뷰할 수는 있어. 하지만 검토에 필요한 코드가 아직 작성되지 않았다면 완료된 코드의 최종 리뷰는 불가능해. 여기서도 같은 DAG 원리가 작동하지.

🧷 12. 마지막으로, 시험의 어떤 질문까지 설명할 수 있나?

시험 복기에는 “생성기를 검증기와 분리한 이유”, “운영자가 생성 버튼을 누른 때부터 저장까지의 책임과 상태 소유자”, “AI의 실행 보고와 별도로 검증한 근거”, “시간 제한·Worker 종료·검증 실패 후 남는 결과” 같은 질문이 있었다고 기록되어 있어. 여기에 답한다면 다음처럼 흐름과 한계를 함께 말할 수 있어.

“API는 작업을 접수하고 입력 데이터셋·규칙·설정을 특정 버전으로 고정합니다. Creator는 그 스냅샷으로 후보 노선과 배정을 만듭니다. Validator는 Creator의 성공 플래그를 신뢰하지 않고 원본 WORK 명단, 정류장, 방향별 이동시간, 정원, 시각과 완성된 후보 전체를 대조합니다. 동일 직원의 날짜·방향별 정확히 한 번 배정은 전역으로 확인합니다. 검증된 후보와 보고서의 해시·버전이 맞을 때만 DB 트랜잭션으로 최종 결과를 공개합니다. 검사 실패나 중단이 나면 이전 정상 결과를 유지합니다. 단, 제가 실제로 구현하거나 실행한 범위가 어디까지인지는 코드와 테스트 로그를 확인해야 말할 수 있습니다.”

이 설명은 권장 아키텍처를 설명하는 가상의 답변 틀이야. 실제 응시자가 구현했다고 확인된 기능에 대한 진술은 아니야. 채점자가 “실제로는 어떤 파일을 보면 됩니까?”라고 물으면 함수 위치, 검증 테스트명, 실행 명령, 실패 fixture, DB/JSON 결과까지 근거로 제시해야 해. 제공된 자료에는 제출 코드와 실제 CSV 행이 없으므로 이 수업에서 그러한 실증을 만들어 낼 수는 없어.

내 말로 설명해 볼 질문 — 답을 먼저 외우지 말기

아래는 수업을 읽은 뒤 자신의 설명을 구성하기 위한 성찰 질문이야. 현재 점수나 숙달 수준을 측정한 정식 진단이 아니며, 질문에 답했다는 사실만으로 합격·숙달을 판정하지 않는다. 답은 이 페이지를 가리면서 문장으로 구성해 봐.

  1. 역할의 차이: Creator가 45석 검사를 이미 수행해도 Validator를 별도로 둘 이유를 “다른 질문을 한다”는 관점에서 설명할 수 있을까?
  2. 독립성의 범위: Creator와 Validator가 같은 CSV 파서를 쓰지만 서로 다른 규칙 검사 코드를 쓴다. 이 구조를 어디까지 '독립 검증'이라고 부를 수 있고, 어느 오류에 취약할까?
  3. 의존성의 증명: 생성 10초, 검증 3초라고 하자. 완성 후보 검증을 생성 시작 시점과 동시에 시작할 수 없다는 이유를 단순한 '코딩 순서' 말고 필요한 데이터의 관점에서 설명해 봐.
  4. 반례 찾기: 날짜별 두 로컬 검사가 각각 통과했는데 직원 E102가 출근 노선 둘에 배정되었다. 어떤 집합·키·카운트를 만들어야 이를 찾을 수 있을까?
  5. 입력 버전: 생성에 D1·정원 45가 사용되었으나 검증 시 현재 선택값이 D2·정원 40이라면 어느 입력을 기준으로 무슨 검증을 해야 하고, 활성 결과 공개는 어떻게 판단해야 할까?
  6. TOCTOU: 검증은 후보 해시 H1을 통과시켰지만 확정 직전에 후보 내용이 H2로 바뀌었다. 무슨 보장이 깨졌고, 이를 막는 경계는 어디일까?
  7. 실패 보존: 검증 중 위반이 나오거나 Worker가 종료되었을 때 job, temp, final 각각에 어떤 상태가 남아야 할까?
  8. AI 역할: 같은 모델이 작성자와 검토자를 번갈아 수행해 “모두 문제없다”고 보고했다. 독립 사실 확인이라고 부르기 위해 어떤 별도 자료·테스트가 필요할까?
  9. 선택의 손실: 독립 Validator를 제거해 구현 시간을 줄이는 대신 무엇을 위험에 노출시키는지 구체적인 실패 경로로 말해 봐.
  10. 범위 구별: 차량 BUS-01의 시간대 중복 사용을 검사하는 건 왜 타당한 확장 예시이면서도 제공 JSON의 필수 검증 규칙이라고 단정할 수 없을까?

통합편의 답변은 이 브라우저에 보관돼. 다른 기기와 자동 동기화하지 않으며 자동 AI 채점이나 대화 전송도 하지 않아. 필요한 답변은 백업하거나 직접 복사해 보관해.

📎 근거와 예시의 경계

  • 시험 원문 자료: EXAM_ORIGINAL_COMBINED.txt — 운영 규칙, CSV 7종, 데이터 관리, 검증 실패 시 기존 결과 유지, EXPORT_SCHEMA.md의 기간·노선·배정 검증 조건. 실제 데이터 행과 코드가 아니라 지시문 및 스키마 설명이다.
  • 시험 복기 자료: EXAM_RECOLLECTION.txt — 질문 유형에 관한 기억. 공식 평가표가 아니며 Creator/Validator 표현의 정확한 의미는 불확실하다.
  • 외부 개념 참고: Google OR-Tools, Vehicle Routing / Dimensions — 용량·이동시간 등 노선 제약이 별도 차원으로 모델링되는 일반적인 배경. 이것이 시험에서 OR-Tools를 사용하라고 지정한 근거는 아니다.
