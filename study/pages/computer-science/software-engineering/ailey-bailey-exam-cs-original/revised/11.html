🧱 1. 화면의 객체와 DB의 행: 무엇을 ‘하나’라고 셀 것인가?

1-1. 먼저 기억 속의 목록을 그려 보자

운영자가 노선 계획을 만든 프로그램이 이런 Python 값을 들고 있다고 상상해 봐.

# [가상 예시] 파이썬 메모리의 객체. DB가 아니다.
plan = {
    "date": "2026-07-20",
    "routes": [
        {"route_id": "R01", "site_id": "ICN", "capacity": 45}
    ],
    "assignments": [
        {"emp_id": "E001", "route_id": "R01", "direction": "to_work"}
    ]
}

여기서 routes는 목록이고 그 안의 {...}는 하나의 운행을 나타내는 객체야. assignments의 객체는 구성원 한 명의 배정을 나타내지. 객체에 필드를 더하고 프로그램 안에서 검색할 수 있지만, 프로그램이 죽으면 해당 프로세스의 메모리에 있던 객체는 없어져. 같은 이름의 변수를 다시 선언해도 예전 운행이 돌아오지는 않아.

DB에서는 반복되는 종류의 사실을 테이블(table) 로 분리하고, 같은 종류의 기록 하나를 행(row) 으로, 그 기록의 성질을 열(column) 로 표현할 수 있어. 예를 들어:

[가상 테이블: route_runs]
┌────────┬────────────┬─────────┬───────────┐
│ run_id │ work_date  │ site_id │ capacity  │ ← 열 이름 = 어떤 속성을 기록하나
├────────┼────────────┼─────────┼───────────┤
│ R01    │ 2026-07-20 │ ICN     │ 45        │ ← 행 1 = 운행 하나
│ R02    │ 2026-07-20 │ ICN     │ 45        │ ← 행 2 = 다른 운행
└────────┴────────────┴─────────┴───────────┘

테이블은 단순한 Excel 시트와 닮았지만 같지 않아. 일반적인 스프레드시트는 사용자가 셀에 임의의 값을 적을 수 있지만, 관계형 DB는 데이터 형식과 제약, 여러 테이블 사이의 연결 규칙을 선언하고 이를 DB 엔진에 맡길 수 있어. 또 SQL의 테이블을 사용할 때 행의 물리적 저장 순서는 결과 순서의 보장이 아니야. ORDER BY 없는 SELECT에서 “먼저 넣은 행이 먼저 나올 것”이라고 믿으면 안 돼.

1-2. ‘행 하나’의 단위를 잘못 정하면 생기는 비용

employees에는 구성원 한 명당 한 행이 자연스러워 보이지? 그런데 work_schedule은 다르다. 같은 직원이 월요일에 근무하고 화요일에 쉬면, 직원 한 명의 ‘근무표 행’은 하나가 아니라 날짜마다 하나야. emp_id만으로 근무표를 식별하려 하면 4주 기록을 넣을 수 없어.

11강 비교와 확인
테이블 후보 한 행이 뜻하는 사실 잘못 잡은 단위의 결과
employees 구성원 한 명의 기본 정보 같은 직원을 중복 등록
work_schedule 구성원 × 날짜의 근무 상태 여러 날짜가 서로 덮어쓰기 됨
travel_times 출발 지점 × 도착 지점의 방향별 시간 A→B와 B→A를 같은 것으로 오인
route_runs 한 날짜·방향에 실제로 계획한 버스 운행 한 건 같은 경로의 버스 두 대를 한 행으로 합침
assignments 구성원 × 날짜 × 방향의 한 번 배정 출근/퇴근 배정이 서로 덮어쓰기 됨

마지막 두 테이블은 [가상 설계]다. 시험 원문의 JSON 내보내기 구조가 운행 하나와 배정 하나의 의미를 제공하므로 여기에서 저장 모델로 옮겨 생각한 것이지, 원문에 실제 DB 테이블명이 지정된 것은 아니야.

1-3. 데이터셋 버전은 ‘행의 출처’를 바꾼다

선수 주제를 아직 정확히 설명하기 어렵더라도, 최소한 이 구별은 필요해. 데이터셋(dataset) 은 7개 입력 CSV의 논리적 묶음, 버전(version) 은 어느 묶음을 기준으로 계산했는지의 식별, 스냅샷(snapshot) 은 특정 시점에 사용한 입력의 고정된 모습이야. employees에 E001만 있다고 해서 이 직원의 좌표가 모든 버전에서 같다는 뜻은 아니지. 따라서 과거 결과를 재현해야 한다면 데이터 행이 어떤 dataset_id에 속했는지도 중요해.

[가상 개념도]
DSET-1 ── 직원 E001의 과거 좌표 ──┐
                                   ├─ 각 버전을 분리해서 보존
DSET-2 ── 직원 E001의 변경 좌표 ──┘
                  │
                  ▼
             생성 결과 RUN-22
             source_dataset = DSET-2

같은 테이블을 통째로 덮는 단순 구현도 가능하지만, 이전 버전의 정확한 입력과 결과를 잃을 수 있다. 반대로 버전별 입력을 모두 보관하면 저장 공간·마이그레이션·조회 조건이 복잡해진다. 무엇을 더 보장하려고 복잡도를 감수하는지가 설계의 핵심이야.

🔑 2. 키는 무엇을 구분하고, 제약조건은 무엇을 막는가?

2-1. 이름이 같아도 다른 사람일 수 있다 — 기본키

김OO라는 이름만으로 직원을 찾으면 동명이인을 구분하기 어려워. 정류장 이름도 바뀔 수 있어. 그래서 DB에서는 기록을 안정적으로 구별하는 값이 필요하고, 이를 기본키(primary key, PK) 라고 해.

[가상 테이블: employees]
emp_id (PK) | site_id | dept
------------+---------+----------
E001        | ICN     | 연구
E002        | BND     | 사무

emp_id=E001을 기본키로 선언했다면 같은 테이블에 E001이 두 행 들어가는 걸 DB가 막는다. 단, SQLite의 일반 rowid 테이블에서는 TEXT PRIMARY KEY만으로 NULL까지 금지된다고 단정할 수 없어. 이 예시의 sites.site_id와 employees.emp_id처럼 식별자가 반드시 있어야 한다면 TEXT NOT NULL PRIMARY KEY로 선언해야 해. SQLite의 INTEGER PRIMARY KEY, WITHOUT ROWID 테이블, STRICT 테이블 등은 이 NULL 예외의 적용 범위가 달라. 복합 기본키도 일반 rowid 테이블에서 해당 열에 NOT NULL을 쓰지 않으면 이 예외를 검토해야 한다. 기본키는 한 행을 식별한다는 약속이지, 값이 업무적으로 옳다는 인증서가 아니야. 실제로 직원 E001이 어느 사업장에 다녀야 하는지는 이 기본키만으로 증명할 수 없어.

기본키에는 하나의 열뿐 아니라 여러 열을 묶은 복합키(composite key) 도 있어. work_schedule의 (dataset_id, work_date, emp_id)는 입력 버전별로 같은 날짜·직원 조합을 한 번만 허용한다는 좋은 예시야. 데이터셋 구별 없이 (work_date, emp_id)만 유일하게 만들면 과거·현재 버전의 동일 근무표를 동시에 보관할 수 없겠지.

2-2. 직원의 site_id는 새 사업장을 만들지 않는다 — 외래키

employees.site_id='ICN'은 문자열이야. 그 문자열이 실제 사업장 테이블에 존재하는지는 별도의 문제지. 외래키(foreign key, FK) 는 다른 테이블의 유효한 키를 가리키도록 연결을 제한하는 장치야.

[가상 관계 도식]
┌──────────────────┐           ┌─────────────────────┐
│ sites            │           │ employees           │
│ PK: site_id      │◀──────────│ FK: site_id         │
│ ICN              │  참조     │ E001 → ICN          │
│ BND              │           │ E002 → BND          │
└──────────────────┘           └─────────────────────┘

E003 → XYZ : sites에 XYZ가 없다면 외래키 위반

SQLite에서는 이 선언이 실제로 강제되려면 각 연결(connection)에서 PRAGMA foreign_keys = ON을 설정해야 해. SQL 파일에 REFERENCES만 썼다고 모든 연결에서 자동으로 보장된다고 가정하면 위험해. 또한 외래키를 켜는 위치가 중요해. 이미 시작한 트랜잭션 중에 켜려 해도 설정이 바뀌지 않아. [SQLite 공식 문서 1, 2]

외래키는 “그 사업장 ID가 존재한다”를 확인할 뿐, “그 직원이 정말 그 사업장에 근무한다”는 업무 진실까지 확인하지는 못해. 존재의 정합성과 의미의 정확성을 분리하자.

2-3. 기본키와 고유 제약은 비슷하지만 역할이 다르다

기본키는 대표 식별자야. 고유 제약(UNIQUE) 은 대표 식별자가 아닌 다른 조합의 중복까지 금지할 때 쓴다. 예를 들어 assignments의 내부 PK가 자동 정수 assignment_id여도 (generation_id, work_date, direction, emp_id)에 UNIQUE를 걸면 한 생성 결과 안에서 같은 직원이 같은 날 같은 방향으로 두 번 배정되는 일을 DB 수준에서 막아.

하지만 UNIQUE는 “누구나 반드시 배정되어야 한다”까지 보장하지 않아. 중복 금지와 누락 금지는 서로 다른 검증이야. E002가 누락되어도 다른 행들의 유일성은 지켜질 수 있지.

2-4. NULL은 빈 문자열이나 0이 아니라 ‘값이 없음’이다

NULL은 아직 값이 없거나 알려지지 않았다는 상태를 표현해. ''(빈 문자열)은 길이가 0인 텍스트, 0은 정수 값, NULL은 둘과 달라.

-- [가상 조회] 값이 없는 행을 찾는 방식
SELECT emp_id FROM employees WHERE home_lat IS NULL;
-- 다음 구문은 NULL 비교에서 기대한 결과를 내지 못한다.
SELECT emp_id FROM employees WHERE home_lat = NULL;

SQL은 NULL 때문에 참/거짓 외에 UNKNOWN을 다루는 세 값 논리를 사용해. NULL = NULL도 TRUE가 아니야. 일반적인 SQL WHERE는 조건이 TRUE인 행만 남기므로 UNKNOWN인 행은 결과에서 빠진다. SQLite에서는 UNIQUE 대상에 NULL이 여러 개 들어갈 수 있으므로, 반드시 존재해야 하는 값에는 별도로 NOT NULL을 선언해야 해. 일반 rowid 테이블의 TEXT PRIMARY KEY도 예외적으로 NULL을 허용할 수 있으니, PRIMARY KEY라는 표기만 보고 비NULL을 보장한다고 생각하지 말자. 그 때문에 UNIQUE(email) 하나만으로 “이메일이 비어 있지 않고 모두 서로 다른 사람”을 보장한다고 말하면 틀려.

2-5. 자료형은 값의 모양과 가능한 연산을 정한다

날짜를 '2026-07-20' 같은 텍스트로 넣어도 될까? SQLite에는 독립적인 DATE 저장 클래스가 없고 날짜·시간을 관례적으로 TEXT/INTEGER/REAL 등으로 표현할 수 있어. ISO YYYY-MM-DD를 일관되게 저장하면 날짜 문자열의 사전식 정렬이 날짜 순서와 일치하는 장점이 있어. 그러나 잘못된 문자열 '2026-99-88'이 자동으로 업무 날짜 검증을 통과하는 건 아니야. CHECK, 애플리케이션 파싱, 날짜 범위 검사 등이 필요해.

SQLite의 일반 테이블은 타입 친화성(type affinity) 으로 인해 선언한 열의 타입과 다른 값을 일부 받아들일 수 있어. 엄격한 유형 검사가 필요하면 STRICT 테이블 지원과 실행 버전, 제약 설계를 검토해야 해. 여기서는 초보자가 결과를 예측하기 쉽도록 INTEGER, TEXT, REAL에 더해 NOT NULL, CHECK를 함께 사용한다. 좌표는 보통 수치로 다루지만, 그 수치가 대한민국의 실제 좌표인지까지 자료형만으로 알 수 있는 것은 아니야.

개념 막아 주는 것 못 막는 것
PK 동일 행 식별자의 중복 실제 업무상 잘못된 ID 배정
FK 존재하지 않는 부모 키 참조 지리·근무표 의미의 오류
UNIQUE 지정된 키 조합의 중복 빠진 직원의 누락 배정

2-6. 여러 테이블이 엮이는 업무 규칙은 남는다

[시험 근거] 근무자는 각 근무일에 출근과 퇴근 노선에 각각 정확히 한 번 배정되어야 하고, 휴무자는 배정하지 않는다. 버스 정원, 도착 여유, 이동 시간, 운행 방향도 맞아야 해. 이 규칙은 하나의 assignments 행만 보면 판별하기 어렵다. work_schedule, route_runs, route_stops, travel_times를 함께 봐야 하기 때문이지.

따라서 역할을 나누자. DB 제약은 강력하고 재사용 가능한 국소 불변식(존재, 중복, NULL, 간단한 범위)을 지키고, 애플리케이션 검증은 여러 행·여러 테이블의 도메인 규칙을 검사한다. 둘을 경쟁 관계로 보지 말자. 애플리케이션만 믿으면 다른 코드 경로가 DB를 망가뜨릴 수 있고, DB 제약만 믿으면 잘못된 버스 운행을 정상이라고 통과시킬 수 있어.

🗺️ 3. 인덱스는 데이터의 주인이 아니라 ‘찾아가는 길’이다

더 알고 싶다면 · 찾기 성능과 인덱스

직원 1,500명의 출근 배정을 화면에서 찾아야 한다고 해 보자. assignments가 수만 행이라면 DB는 특정 emp_id를 찾기 위해 테이블의 많은 행을 살펴볼 수도 있어. 이를 테이블 스캔이라고 해. 자주 검색하는 값에 인덱스(index) 를 만들면, DB는 별도의 탐색 구조를 사용해 필요한 행을 빠르게 찾는 실행 계획을 선택할 수 있어.

[개념 모형 — 실제 SQLite 내부 자료구조의 완전한 그림은 아님]
인덱스: (emp_id, work_date) → 해당 행 위치를 찾는 통로

E001 ─┬─ 07-20 ──► assignment 행 A
      └─ 07-21 ──► assignment 행 C
E002 ─── 07-20 ──► assignment 행 B

인덱스 없이: 많은 행을 열어 확인할 수 있음
인덱스 사용: 정렬된 탐색 구조에서 후보를 좁힌 뒤 행을 읽음

-- [가상 설계]
CREATE INDEX idx_assignment_member_day
ON assignments (emp_id, work_date);

선택의 손실도 분명해. 인덱스는 저장 공간을 쓰고, INSERT·UPDATE·DELETE가 발생할 때 같이 갱신해야 하므로 쓰기 비용을 늘린다. emp_id, work_date 순서로 만든 복합 인덱스가 work_date만으로 검색할 때 동일하게 최적이라는 보장도 없다. 데이터 규모가 작을 때는 스캔이 더 간단하고 빠를 수도 있어. 성능을 논하려면 EXPLAIN QUERY PLAN 같은 도구로 실행 계획을 보아야지, “인덱스 있음=항상 빠름”이라고 말하면 안 돼.

EXPLAIN QUERY PLAN
SELECT run_id FROM assignments
WHERE emp_id = 'E001' AND work_date = '2026-07-20';

이 명령은 실행 계획을 관찰하는 도구이지 결과의 업무 정확성을 검사하는 도구가 아니야. 유니크 제약은 보통 내부 인덱스를 활용하지만, 일반 조회 성능용 인덱스와 “중복을 막는 제약”의 목적을 혼동하지 말자.

🧪 4. 이제 SQLite를 실제로 읽을 수 있는 SQL 언어로 연결하자

Ailey: 여기서부터는 같은 말을 데이터베이스가 이해할 수 있게 만들어 보자. SQL은 “어떤 자료를 원하고 무엇을 바꾸려는지”를 선언하는 언어야. Python의 리스트 반복문처럼 각 행을 한 줄씩 조작하는 방법을 직접 작성하지 않아도, DB 엔진이 적합한 접근 방법을 고른다.

4-1. 가상 SQLite 스키마: 최소한의 식별·관계·배정

아래 코드는 설명용 부분 스키마야. CSV 7종 전체를 로드하거나 실제 시험의 모든 검증을 구현하는 완성 서비스가 아니다. 특히 경로 정차 순서·시간 검증, 좌표의 의미, 재계산 동시성, 비밀번호 관리 등은 별도 구현이 필요해.

-- [가상 설계] SQLite에 연결한 뒤, 트랜잭션 시작 전에 연결별 설정
PRAGMA foreign_keys = ON;

CREATE TABLE IF NOT EXISTS sites (
    site_id TEXT NOT NULL PRIMARY KEY,
    name TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS employees (
    emp_id TEXT NOT NULL PRIMARY KEY,
    site_id TEXT NOT NULL REFERENCES sites(site_id),
    dept TEXT NOT NULL,
    home_lat REAL,
    home_lon REAL,
    CHECK (home_lat IS NULL OR (home_lat BETWEEN -90 AND 90)),
    CHECK (home_lon IS NULL OR (home_lon BETWEEN -180 AND 180))
);

CREATE TABLE IF NOT EXISTS work_schedule (
    dataset_id TEXT NOT NULL,
    work_date TEXT NOT NULL,
    emp_id TEXT NOT NULL REFERENCES employees(emp_id),
    shift_code TEXT NOT NULL,
    work_status TEXT NOT NULL CHECK (work_status IN ('WORK', 'OFF')),
    PRIMARY KEY (dataset_id, work_date, emp_id)
);

CREATE TABLE IF NOT EXISTS route_runs (
    generation_id TEXT NOT NULL,
    run_id TEXT NOT NULL,
    work_date TEXT NOT NULL,
    direction TEXT NOT NULL CHECK (direction IN ('to_work', 'to_home')),
    site_id TEXT NOT NULL REFERENCES sites(site_id),
    capacity INTEGER NOT NULL CHECK (capacity > 0),
    PRIMARY KEY (generation_id, run_id)
);

CREATE TABLE IF NOT EXISTS assignments (
    assignment_id INTEGER PRIMARY KEY,
    generation_id TEXT NOT NULL,
    work_date TEXT NOT NULL,
    direction TEXT NOT NULL CHECK (direction IN ('to_work', 'to_home')),
    emp_id TEXT NOT NULL REFERENCES employees(emp_id),
    run_id TEXT NOT NULL,
    FOREIGN KEY (generation_id, run_id)
        REFERENCES route_runs(generation_id, run_id),
    UNIQUE (generation_id, work_date, direction, emp_id)
);

CREATE INDEX IF NOT EXISTS idx_assignments_lookup
ON assignments(emp_id, work_date);

이 스키마의 의도적 한계: assignments.work_date가 참조된 route_runs.work_date와 같고 방향도 동일하다는 제약은 현재 DDL만으로 강제하지 않는다. 또한 employees를 버전별로 저장하지 않으면서 근무표에만 dataset_id를 둔 예시이므로, 실제로 서로 다른 7종 CSV 스냅샷을 완전히 격리하는 설계로는 부족하다. 전체 버전 분리가 필요하면 각 입력 엔터티의 키에 dataset_id를 포함하고 복합 FK를 정합하게 연결하거나, 버전별 입력을 불변 저장하는 별도 모델을 설계해야 한다. 코드를 읽으며 이 결함을 찾아내는 것 자체가 수업의 목적이다.

4-2. INSERT — 아직 없던 사실을 기록한다

-- [가상 데이터: 실제 제공 CSV 행이 아님]
INSERT INTO sites (site_id, name)
VALUES ('ICN', '가상 이천 사업장');

INSERT INTO employees (emp_id, site_id, dept, home_lat, home_lon)
VALUES ('E001', 'ICN', '연구', 37.20, 127.40);

INSERT INTO work_schedule
(dataset_id, work_date, emp_id, shift_code, work_status)
VALUES ('DSET-2', '2026-07-20', 'E001', 'ICN_A', 'WORK');

INSERT는 열 목록과 값 목록을 대응시켜 새 행을 넣어. 위 순서가 중요한 까닭은 FK가 켜져 있다면 부모 sites가 먼저 있어야 직원이 ICN을 참조할 수 있기 때문이야. 부모가 없으면 참조 무결성 위반이다. 단, 연속 INSERT의 원자적 성공을 보장하려면 적절한 트랜잭션 안에서 처리해야 해. 세 문장을 따로 자동 커밋하다가 마지막만 실패하면 앞의 두 행은 남을 수 있거든.

4-3. SELECT — 저장된 사실에서 원하는 부분을 읽는다

SELECT e.emp_id, s.work_date, s.work_status
FROM employees AS e
JOIN work_schedule AS s ON s.emp_id = e.emp_id
WHERE s.dataset_id = 'DSET-2'
  AND s.work_date = '2026-07-20'
  AND s.work_status = 'WORK'
ORDER BY e.emp_id;

FROM은 읽을 테이블, JOIN ... ON은 두 테이블을 연결하는 조건, WHERE는 반환할 행의 조건, SELECT는 보여 줄 열, ORDER BY는 결과 순서를 정해. 사용자가 “오늘 일하는 직원 목록”을 조회할 때의 출발점이지. 하지만 위 SQL은 employees가 한 버전의 직원 정보만 표현한다는 가상 스키마의 제한을 그대로 안고 있어.

조건의 차이를 눈으로 확인해 보자.

조건 의미 위험

4-4. UPDATE — 기존 사실의 일부를 바꾼다

-- [가상 예시] 의도한 버전·날짜·직원의 상태만 변경
UPDATE work_schedule
SET work_status = 'OFF'
WHERE dataset_id = 'DSET-2'
  AND work_date = '2026-07-20'
  AND emp_id = 'E001';

UPDATE는 기존 행을 수정해. WHERE를 빼면 테이블의 모든 행에 적용될 수 있어. 조건을 잘못 쓰면 아무 행도 수정되지 않을 수도 있어. “문장이 성공했다”와 “원한 행 하나를 수정했다”는 서로 다르지. 수정 후 영향받은 행 수(rowcount 등)를 확인하거나 기대했던 상태를 다시 조회하는 이유야.

실서비스에서는 이미 승인·적용된 데이터셋을 직접 UPDATE하기보다 새 데이터셋 버전을 생성·검증한 뒤 적용 포인터를 전환하는 설계가 더 적절할 수 있어. 직접 수정은 간단하지만 과거 계산의 입력 재현성을 훼손할 수 있다.

4-5. DELETE — 조건에 맞는 행을 지운다

DELETE FROM work_schedule
WHERE dataset_id = 'DSET-2'
  AND work_date = '2026-07-20'
  AND emp_id = 'E001';

DELETE는 행을 삭제해. 역시 WHERE가 없다면 모든 행이 대상이 될 수 있어. 삭제가 무서운 또 한 가지 이유는 다른 테이블이 해당 행을 참조할 수 있기 때문이야. 기본적인 FK는 부모 삭제를 제한할 수 있고, ON DELETE CASCADE를 설정하면 자식 행이 연쇄 삭제될 수 있어. CASCADE는 편리하지만 의도치 않은 대량 삭제의 피해가 커질 수 있으므로 “관계가 있으니 무조건 CASCADE” 는 좋은 원칙이 아니야.

4-6. 파라미터 바인딩 — 값과 SQL 문법을 분리한다

사용자가 구성원 검색창에 'E001'을 적었다고 해 보자. 아래처럼 문자열을 이어 붙이는 것은 위험해.

# [금지할 패턴] SQL 문장에 사용자 값을 직접 끼워 넣음
sql = "SELECT * FROM employees WHERE emp_id = '" + user_input + "'"

입력값에 따옴표나 SQL 연산자가 들어가면 사용자가 제공한 데이터가 SQL의 문법으로 해석될 수 있다. 이를 SQL 인젝션 위험이라고 해. 바인딩을 쓰면 SQL 템플릿과 값이 분리되어 DB가 입력값을 값으로 취급한다.

# [가상 예시] Python 표준 sqlite3
import sqlite3

con = sqlite3.connect("/app/data/shuttle.db")
con.execute("PRAGMA foreign_keys = ON")
user_input = "E001"  # 실제 서비스에서는 요청 입력을 검증해서 전달
rows = con.execute(
    "SELECT emp_id, site_id FROM employees WHERE emp_id = ?",
    (user_input,)
).fetchall()
con.close()

?는 그 자리에 올 값의 자리표시자이고, (user_input,)은 한 원소짜리 튜플이야. 바인딩은 테이블명·열 이름 같은 SQL 식별자를 대체하는 일반적인 방법이 아니다. 사용자가 ORDER BY 열을 고르게 하려면 서버의 허용 목록에서 정해진 SQL 조각을 선택해야 해. 바인딩으로 입력값이 SQL 문법이 되는 위험을 줄였다고 해도 접근 권한까지 생기지는 않는다. 다른 직원의 배정을 조회할 수 있는지는 로그인 사용자의 인가 규칙이 따로 검사해야 하지. [SQLite 공식 문서: https://www.sqlite.org/lang_expr.html]

[조회 요청의 단계]
브라우저: E001 검색
   ↓
서버: 요청자 신원·조회 권한 확인
   ↓
서버: SQL 템플릿과 파라미터 값 준비
   ↓
SQLite 연결: SQL 실행·행 반환
   ↓
서버: 결과를 응답 형식으로 변환
   ↓
브라우저: 화면 갱신

화면에 값이 나왔다는 사실만으로 해당 값이 DB에 저장되었다는 사실이나 재시작 복구가 증명되지 않아.

🧬 5. SQL에서 디스크까지: 어디에서 확정되는가?

SQLite는 별도의 데이터베이스 서버 프로세스를 반드시 요구하지 않아. 보통 웹 서버 프로세스에 포함된 SQLite 라이브러리가 DB 파일을 읽고 쓰지. 그렇다고 연결이 필요 없는 것은 아니야. DB 연결(connection) 은 어떤 DB를 대상으로 SQL을 실행하고, 연결별 제약 설정과 트랜잭션을 어떻게 다룰지를 정하는 통로야.

[가상 단일 서버와 파일 SQLite]
┌──────────┐ HTTP ┌──────────────────────────┐
│ 브라우저  │ ───► │ 웹 서버 프로세스          │
│ 생성 클릭 │      │ 요청/권한/업무 규칙 처리  │
└──────────┘      └────────────┬─────────────┘
                               │ 연결 C1
                               ▼
                    ┌──────────────────────┐
                    │ SQLite 라이브러리     │
                    │ SQL·제약·트랜잭션    │
                    └──────────┬───────────┘
                               │ 파일 입출력
                               ▼
                    /app/data/shuttle.db

5-1. 연결을 닫으면 데이터도 사라질까?

연결 객체는 사라져도 파일 DB에 커밋된 내용은 정상적이고 지속적인 저장 매체에 남을 수 있어. 앱이 재시작되면 새로운 연결을 열어 같은 경로를 다시 조회해야 해. 상대 경로 data/shuttle.db는 실행 위치에 따라 다른 파일을 의미할 수 있어.

서버 1: 현재 폴더 /app  → data/shuttle.db = /app/data/shuttle.db
서버 2: 현재 폴더 /tmp  → data/shuttle.db = /tmp/data/shuttle.db

이름은 같지만 두 개의 다른 DB일 수 있다.

5-2. COMMIT은 ‘SQL 실행’과 어떻게 다를까?

트랜잭션(transaction) 은 여러 변경을 하나의 확정 단위로 묶는 장치야. BEGIN으로 시작해 여러 행을 수정하고 COMMIT으로 확정하거나, 실패하면 ROLLBACK으로 그 트랜잭션의 변경을 되돌릴 수 있어. [SQLite 트랜잭션: https://www.sqlite.org/lang_transaction.html]

[가상 입력 데이터 적용]
BEGIN
 ├─ sites 입력            성공
 ├─ shifts 입력           성공
 ├─ employees 입력        성공
 ├─ work_schedule 입력    외래키 오류!
 └─ ROLLBACK              ← 묶인 변경을 확정하지 않음

반대로 각각 자동 커밋하여 앞의 세 테이블을 저장했다면 마지막 입력에 오류가 발생해도 앞의 변경이 남을 수 있지. 7개 CSV가 함께 적용되거나 함께 거부되어야 한다는 업무 요구를 어떤 경계로 구현했는지가 중요해. 다만 큰 CSV를 파싱하고 노선을 계산하는 오래 걸리는 작업 전체에 DB 잠금을 걸 필요는 없어. 입력 검증과 계산은 별도의 후보 상태에서 수행하고, 최종 결과 확정에 필요한 변경만 짧은 트랜잭션으로 묶는 방식을 고려할 수 있어. 그 사이 데이터가 변경되지 않았는지는 버전 비교나 스냅샷으로 확인해야 하고.

5-3. 원자성이 닿지 않는 곳

DB 트랜잭션의 원자성은 해당 트랜잭션 안의 DB 작업에 대한 보장이야. DB 커밋과 HTTP 응답 도착, 외부 JSON 파일 쓰기, worker 메모리 계산, 다른 DB 시스템의 트랜잭션이 자동으로 하나로 묶이는 건 아니야.

예를 들어 COMMIT은 성공했지만 서버가 브라우저에 성공 응답을 보내기 전에 종료되었다고 하자. DB에는 결과가 남아 있지만 브라우저는 실패로 볼 수 있지. 사용자가 같은 생성 요청을 재전송하면 중복 실행을 막는 요청 식별자·멱등성 정책이 필요할 수 있어. “DB 성공”과 “사용자가 성공을 알았음”은 다른 사건이다.

⏳ 6. 네 종류의 수명: 메모리 객체·메모리 DB·파일 DB·컨테이너

6-1. 메모리 DB도 DB지만 지속적인 파일은 아니다

Python 딕셔너리는 객체일 뿐이고 SQL·키 제약은 제공하지 않아. SQLite :memory:는 SQL과 제약을 사용할 수 있는 진짜 관계형 DB지만 일반적으로 특정 연결이 유지되는 동안만 존재해. sqlite3.connect(':memory:')를 두 번 호출하면 기본적으로 서로 별개의 DB를 만든다.

# [가상 예시] 실행했다고 주장하지 않음
import sqlite3
c1 = sqlite3.connect(':memory:')
c1.execute('CREATE TABLE t (v INTEGER)')
c1.execute('INSERT INTO t VALUES (42)')
c1.commit()
c2 = sqlite3.connect(':memory:')
# c2.execute('SELECT * FROM t') → 보통 no such table: t
c1.close()
c2.close()

일부 SQLite 공유 메모리 URI 설정 같은 예외가 있지만, 기본값을 이해할 때는 연결별 메모리 DB라고 생각하면 돼.

11강 비교와 확인
저장 대상 연결 종료 프로세스 종료 컨테이너 제거·재생성
Python 딕셔너리 DB 연결과 무관 값 사라짐 값 사라짐
일반 SQLite :memory: 해당 메모리 DB 소멸 소멸 소멸
호스트에 둔 SQLite 파일 DB 커밋된 행 유지 가능 유지 가능 호스트 파일 경로가 보존되면 유지
컨테이너 내부 writable layer 파일 유지 가능 같은 컨테이너 재시작 시 유지 가능 해당 계층 제거 시 소실
영속 볼륨의 파일 DB 유지 가능 유지 가능 같은 볼륨 연결 시 유지 가능

‘유지 가능’은 정상적인 파일·장치·권한·마운트·커밋 조건에서의 뜻이야. 파일 삭제·손상이나 잘못된 경로·권한까지 자동으로 해결한다는 뜻이 아니다.

6-2. 커밋은 저장 위치를 영속 볼륨으로 바꾸지 않는다

커밋은 DB 내부 변경의 확정 시점이지, 파일 시스템의 어느 위치에 저장하라는 명령이 아니야. 파일이 컨테이너의 사라지는 쓰기 계층에 있으면 커밋되어도 컨테이너 교체 후 잃을 수 있어. 반대로 볼륨을 붙여도 :memory:를 선택했다면 파일 DB로 자동 변경되지 않지. 저장 형식·확정 시점·매체 수명은 서로 독립적인 선택이다.

🏗️ 7. 빈 DB 초기화와 마이그레이션은 왜 별개의 작업인가?

처음 서비스가 켜졌을 때 DB 파일이 없으면 SQLite가 파일을 생성할 수 있지만 업무 테이블, 관리자 계정, 초기 데이터셋은 알아서 만들지 않아. 앱의 부팅 절차가 구조를 갖추어야 해.

[가상 부팅 순서]
환경변수 읽고 필수 값 검사
          ↓
DB 파일 경로 및 디렉터리 권한 확인
          ↓
DB 연결 + 연결별 PRAGMA foreign_keys=ON
          ↓
스키마 버전 확인 ──┬─ 새 DB → 테이블·인덱스 생성
                  ├─ 구 DB → 마이그레이션 실행
                  └─ 현 DB → 변경 불필요
          ↓
초기 계정·설정·데이터의 존재 확인 및 중복 방지
          ↓
서비스 준비 상태 판정 → 요청 접수

스키마(schema) 는 테이블 열·키·제약·인덱스의 구조를 뜻해. CREATE TABLE IF NOT EXISTS는 테이블이 없을 때 만들지만 기존 테이블이 최신 모양인지 자동으로 수정하지 않아. 예를 들어 버전 1에 없던 job_type을 버전 2에서 추가하려면 실제로 구조 변경을 실행해야 해. 이것이 마이그레이션(migration) 이다.

-- [가상 마이그레이션] 실제 테이블 구조와 기존 버전을 확인한 후 시행
ALTER TABLE employees ADD COLUMN job_type TEXT;
PRAGMA user_version = 2;

user_version은 개발자가 사용할 수 있는 버전 표식이지 마이그레이션 실행기 자체는 아니야. 변경이 정상적으로 끝난 후 버전을 올려야 하며, 이미 버전 2라면 무작정 재실행하지 않아야 해. 이행 중 중단되거나 과거 데이터가 새 제약을 어기면 실패가 날 수 있으므로 변경 전 백업, 실패 복구, 데이터 이행 검증이 필요해. 빠른 초기화 스크립트는 간단하지만 기존 데이터 보존·업그레이드에는 약하고, 버전별 마이그레이션은 안전한 변경 이력을 제공하는 대신 관리 비용을 요구해.

초기 데이터를 매번 INSERT하는 것 역시 위험해. 재시작할 때마다 중복 레코드나 기존 사용자 설정 덮어쓰기 사고가 날 수 있어. “없을 때만 초기화하고 이미 있으면 보존”해야 하지만, 무조건 INSERT OR REPLACE도 자식 참조·연관 데이터를 건드릴 수 있으니 의미를 확인해야 해.

🔐 8. 환경변수로 설정을 빼야 하는 이유와 그 한계

[시험 근거] 원문은 DB 접속 정보, 초기 계정 비밀번호, 포트 등 설정·비밀값을 환경변수로 주입하고 .env.example을 제공할 것을 요구했다. 아래는 [가상 설계]이며 실제 비밀이 아니다.

# .env.example: 이 값들은 설명용 예제다.
APP_PORT=8000
DB_PATH=/app/data/shuttle.db
INITIAL_ADMIN_USERNAME=admin
INITIAL_ADMIN_PASSWORD=CHANGE_BEFORE_USE

환경변수는 같은 코드를 다른 환경에서 실행하면서 DB 경로와 포트를 바꿀 수 있게 해 줘. 소스 코드에 비밀번호를 고정하지 않는 데도 도움이 되지만 환경변수가 저절로 암호화되거나 유출 방지되는 것은 아니다. 초기 비밀번호는 안전한 해시 방식으로 저장하고, 실제 값은 Git 커밋·로그·공개 예제 파일에 기록하지 않아야 해. 운영자·구성원 인증과 인가 정책은 환경변수만으로 구현되지 않아.

# [가상 예시] 잘못된 배포 설정을 조기에 드러내기
from pathlib import Path
import os

raw = os.environ.get('DB_PATH')
if not raw:
    raise RuntimeError('DB_PATH 환경변수가 필요합니다')
path = Path(raw)
if not path.is_absolute():
    raise RuntimeError('운영용 DB_PATH는 절대 경로로 지정하세요')

환경변수가 없을 때 조용히 현재 작업 폴더에 새 DB를 만들면 앱이 정상 시작해도 과거 데이터가 사라진 것처럼 보일 수 있어. 실패를 즉시 알리는 선택은 초기 설정 편의성을 일부 잃는 대신, 잘못된 DB를 사용한 사고를 빨리 발견하게 한다.

🐳 9. Docker 볼륨은 컨테이너보다 오래 사는 저장 공간이다

파일 DB를 /app/data/shuttle.db에 두었다고 하자. 컨테이너가 재시작하는 것과 컨테이너 자체를 삭제·교체하는 것은 다르다. 컨테이너의 writable layer에 쓴 파일은 해당 컨테이너가 사라질 때 함께 잃을 수 있어. 그래서 데이터 디렉터리를 볼륨(volume) 과 연결하는 설계가 필요하다. [Docker Storage: https://docs.docker.com/engine/storage/], [Docker Volumes: https://docs.docker.com/engine/storage/volumes/]

9-1. WAL 모드에서는 왜 단일 파일 복사가 조심스러울까?

SQLite는 WAL(Write-Ahead Logging) 모드에서 기본 DB 파일 외에 -wal, -shm 보조 파일을 사용할 수 있어. 확정된 변경 일부가 메인 DB 파일로 체크포인트되기 전에 WAL에 존재할 수 있지. 운영 중 메인 shuttle.db 파일 하나만 무작정 복사하면 일관된 백업이 아닐 수 있어. SQLite 온라인 백업 API나 일관성 있는 스냅샷 절차를 사용해야 한다. [SQLite WAL: https://www.sqlite.org/wal.html]

10-1. ‘검증한 데이터셋을 적용한다’는 말이 무엇을 요구하나?

[시험 근거] 잘못된 데이터셋은 적용하지 않고 기존 데이터와 결과를 유지해야 한다. 또한 새 데이터셋 적용 뒤 재계산 전의 기존 결과를 새 데이터의 결과처럼 보여 주면 안 된다. 그러므로 단순히 current_dataset_id만 바꾸고 화면에서 마지막 결과를 그대로 노출하면 요구를 어길 수 있어.

DSET-1 적용 → 결과 G1 생성 완료
                  ↓
            G1.source = DSET-1
                  ↓
DSET-2 검증 완료 → 적용
                  ↓
현재 입력 = DSET-2
현재 입력과 일치하는 확정 결과 = 없음
과거 G1 = 보존 가능하지만 DSET-1의 결과라고 명확히 표시
                  ↓

                  ↓
            G2.source = DSET-2

입력 버전과 결과 출처가 연결되어 있어야 과거 결과가 새 결과로 위장하지 않아. 이를 테이블의 FK와 버전 필드, 현재 결과 포인터, 조회 조건으로 구현할 수 있지만 어느 한 가지 필드를 더한 것만으로 완성되지는 않아. 업데이트 타이밍과 재조회 동작도 함께 설계해야 해.

10-2. 생성 도중 서버가 죽으면 DB가 자동 복구할까?

아니. DB에 RUNNING이라는 작업 기록을 남겨도 재시작 후 상태를 검사하고 해당 작업을 실패·재시도 대기 등으로 조정하는 코드는 별도로 필요해. 중간 계산이 오직 worker 메모리에 있다면 그 계산은 소실돼. 최종 결과 포인터가 검증·커밋된 결과만 가리키도록 하면 적어도 미완성 중간 결과를 현재 결과로 노출하는 피해는 줄일 수 있어. 이 과정의 상세 상태 머신과 재시도는 별도 소주제의 영역이야.

🧨 11. 실패 반례: DB가 있다는데도 틀린 여덟 장면

반례 A — 없는 사업장 ID를 넣었다

E003.site_id='XYZ'이고 sites에 XYZ가 없다. FK가 선언되었고 현재 연결에서 활성화됐다면 거절할 수 있어. FK가 꺼져 있으면 삽입이 진행될 수 있다. 확인할 것은 PRAGMA foreign_keys;와 PRAGMA foreign_key_check;, 그리고 입력 검증 오류 메시지야. FK의 손실은 데이터 입력 순서와 이행 과정이 더 엄격해진다는 점이지.

반례 B — 직원이 두 번 배정되거나 한 번도 배정되지 않았다

UNIQUE는 동일 직원·날짜·방향의 중복은 막지만 근무자 전체가 빠짐없이 배정됐는지는 말해 주지 않아. 근무표의 WORK 집합과 배정 집합을 비교하고, OFF가 들어오지 않았는지 검사해야 해. [시험 근거] 근무일의 근무자는 출퇴근 각 한 번씩 배정되고 휴무자는 배정하지 않아야 했다.

반례 C — 일곱 CSV 중 여섯 번째가 실패했다

앞의 다섯 개가 이미 커밋됐다면 부분 상태가 남을 수 있어. 모든 변경을 하나의 트랜잭션으로 묶고 실패 시 ROLLBACK했다면 해당 트랜잭션의 변경을 취소할 수 있지. 실제로 검증하려면 일부러 FK 위반 데이터를 넣고 전후 DB 행 수, 현재 버전 포인터와 이전 결과를 비교해야 해.

반례 D — 결과 저장 뒤 HTTP 응답 직전에 서버가 죽었다

DB에 결과가 있어도 사용자에게는 실패가 표시될 수 있어. 재요청이 중복 실행되지 않게 요청 ID와 상태 조회·멱등성 규칙이 필요할 수 있어. 여기서 DB는 커밋의 사실을 가질 뿐, 사용자가 응답을 받았는지 알지는 못해.

반례 E — 볼륨은 있었지만 DB 경로를 잘못 잡았다

/app/data에 볼륨을 연결하고 실제 연결은 /tmp/shuttle.db였다. 컨테이너 재생성 후 사라진다. 확인은 실제 PRAGMA database_list로 열린 DB의 위치를 살피고, 새 컨테이너에서 같은 볼륨으로 조회하는 방식이야. 파일 이름을 눈으로 보는 것만으로는 부족해.

반례 F — 정원은 45석인데 46명을 태운다

[시험 근거] 기본 정원은 45석이고 입석이 없어. 여기서 46명은 가상 반례 수치야. PK·FK·COMMIT이 모두 정상이어도 구간별 탑승 인원이 초과될 수 있어. 정차 순서대로 승하차를 누적하여 각 구간의 승객 수를 검사해야 해. DB 제약만으로 모든 시간표·정원·근무 상태 규칙이 검증되지는 않는다.

반례 G — DB와 JSON 내보내기의 결과가 다르다

DB의 최신 결과는 G2인데 파일 내보내기 코드가 G1을 읽었다면 운영자가 잘못된 JSON을 받을 수 있어. generation_id, source_dataset_id로 DB와 출력의 출처를 연결하고, 제공된 EXPORT_SCHEMA.md에 따라 결과를 독립적으로 검사해야 해.

반례 H — 커밋된 DB가 저장장치 고장으로 사라졌다

파일 DB에 커밋되어 있었더라도 그 파일이 유일한 사본이었다면 복원이 어려워. 다른 위치의 백업과 실제 복원 실험이 필요해. PRAGMA integrity_check는 파일 구조 확인에 유용하지만 정원·시간표와 같은 비즈니스 규칙을 대신 검사하지 않는다.

🛠️ 12. 직접 확인하는 최소 실험: ‘실행하지 않은 코드’와 ‘검증된 동작’을 나누자

아래 코드는 학습자가 격리된 환경에서 실험할 수 있도록 작성한 가상 예시다. 작성 과정에서 이 코드들을 실제 실행했다는 주장은 하지 않는다. 실험의 예상 결과와 실제 관찰 결과는 구분해야 해. 개인 데이터나 기존 시험 DB에 덮어쓰지 않도록 임시 경로를 사용하자.

실험 1 — 파일 DB의 커밋된 행을 새 연결에서 읽기

from contextlib import closing
from pathlib import Path
from tempfile import TemporaryDirectory
import sqlite3

with TemporaryDirectory() as folder:
    db_path = Path(folder) / 'demo.db'
    with closing(sqlite3.connect(db_path)) as conn:
        # closing은 이 블록이 끝날 때 연결을 닫는다.
        with conn:  # 연결의 트랜잭션 컨텍스트: 정상 종료 시 커밋, 예외 시 롤백
            conn.execute('CREATE TABLE notes (id INTEGER PRIMARY KEY, text TEXT NOT NULL)')
            conn.execute('INSERT INTO notes(text) VALUES (?)', ('기록 A',))
    with closing(sqlite3.connect(db_path)) as new_conn:
        print(new_conn.execute('SELECT id, text FROM notes').fetchall())
# 두 연결이 모두 닫힌 뒤 TemporaryDirectory가 정리된다.

예상 관찰: [(1, '기록 A')]처럼 새 연결에서도 커밋된 기록을 조회할 수 있다. Python의 with sqlite3.connect(...) as conn:는 연결 자체의 수명 관리가 아니라 트랜잭션 컨텍스트 관리다. 블록을 벗어날 때 열린 트랜잭션을 커밋하거나 예외 시 롤백하지만, 연결을 닫지는 않는다. 따라서 여기서는 contextlib.closing(...)으로 쓰기 연결과 읽기 연결을 각각 닫은 다음 임시 디렉터리를 삭제하도록 했다. 사용자가 Windows Python에서 이전 예제를 실행했을 때 출력은 [(1, '기록 A')]였으나, 열린 DB 파일 연결 때문에 디렉터리 정리 시 PermissionError: [WinError 32]가 발생했다고 보고했다. 이는 학습자의 별도 임시 실험 관찰이며 원래 시험 실행 결과가 아니다. 임시 디렉터리는 with TemporaryDirectory()가 끝나면 삭제되므로, 이것은 연결 수명의 차이를 관찰하는 실험이지 영구 보존을 약속하는 실험이 아니다.

실험 2 — 메모리 DB의 연결 경계 확인

import sqlite3
c1 = sqlite3.connect(':memory:')
c1.execute('CREATE TABLE t (v INTEGER)')
c1.execute('INSERT INTO t VALUES (1)')
c1.commit()
c2 = sqlite3.connect(':memory:')
try:
    print(c2.execute('SELECT * FROM t').fetchall())
except sqlite3.OperationalError as e:
    print(type(e).__name__, str(e))
finally:
    c1.close()
    c2.close()

예상 관찰: 보통 no such table: t가 나온다. c1과 c2가 각각 다른 메모리 DB이기 때문이야.

실험 3 — 트랜잭션 롤백의 범위

import sqlite3
con = sqlite3.connect(':memory:')
con.execute('CREATE TABLE sites (site_id TEXT PRIMARY KEY)')
con.commit()
try:
    con.execute('BEGIN')
    con.execute('INSERT INTO sites VALUES (?)', ('ICN',))
    con.execute('INSERT INTO sites VALUES (?)', ('ICN',))  # PK 중복
    con.commit()
except sqlite3.IntegrityError:
    con.rollback()
print(con.execute('SELECT COUNT(*) FROM sites').fetchone())
con.close()

예상 관찰: fetchone()은 조회 결과의 행 하나를 튜플로 반환하므로 실제 print(...) 출력 형태는 (0,)야. 괄호 안의 0은 COUNT(*)가 반환한 행 개수 0이고, 쉼표는 원소가 하나인 Python 튜플의 표기야. 학습자가 Windows Python에서 (0,)을 관찰했다고 보고한 것은 별도 임시 실험 결과이며 원래 시험 결과가 아니다. 첫 번째 INSERT는 실행됐지만 두 번째 실패에 따라 트랜잭션을 명시적으로 롤백했기 때문이지. 한 문장이 실패했다고 모든 드라이버·모든 오류에서 트랜잭션 전체가 자동으로 롤백된다고 가정해서는 안 돼.

실험 4 — 인덱스를 쓰는지 계획 살펴보기

EXPLAIN QUERY PLAN
SELECT assignment_id FROM assignments
WHERE emp_id = 'E001' AND work_date = '2026-07-20';

관찰할 것은 계획에 SCAN이 나오는지 인덱스를 이용한 SEARCH가 나오는지야. 실제 데이터 크기·통계·SQLite 버전과 쿼리에 따라 달라진다. 이 SQL 한 번을 적은 것만으로 실제 서비스가 빨라졌다고 검증한 것은 아니다.

실험 5 — 서비스 재시작을 검증하기 위한 절차

  1. 입력 데이터셋의 ID와 생성 결과 ID를 확인한다.
  2. 새 DB 연결을 통해 현재 적용 데이터셋과 결과의 행 수를 읽는다.
  3. 서버 프로세스를 실제 종료하고 다시 실행한다.
  4. 프로그램이 연 DB의 정확한 위치를 기록하고 비교한다.
  5. 새 HTTP 요청으로 동일 ID의 데이터를 조회한다.
  6. 컨테이너 배포를 주장한다면 삭제·재생성 후 동일 볼륨에서 다시 조회한다.
  7. 저장 결과를 원문의 내보내기 규칙에 따라 독립적으로 검증한다.

1~2만 성공했다고 3~7을 완료했다고 말하면 안 돼. 새 연결 성공과 서버 재시작 성공은 다른 수준의 증거야.

단일 프로세스에서는 같은 메모리 객체를 함수 간 공유할 수 있지만 별도 worker 프로세스는 동일한 Python 변수를 자동 공유하지 않아. 같은 파일 SQLite를 별개의 연결로 열고 상태를 기록·조회할 수는 있어. 다만 동시에 쓰는 상황에서는 SQLite의 잠금과 SQLITE_BUSY 등 오류를 고려해야 한다. busy_timeout, 짧은 트랜잭션, 재시도 범위, 작업 상태 기록이 중요해져.

[하나의 서버 프로세스]
웹 서버 P1 ── 메모리 객체
          └─ SQLite 연결 C1 → 로컬 파일 DB

[웹 서버와 worker 분리]
웹 서버 P1 ── 연결 C1 ─┐
                        ├── 같은 로컬 파일 DB
worker P2 ─── 연결 C2 ─┘
(메모리 변수는 공유되지 않음)

[서로 다른 서버 호스트]
서버 A → /app/data/shuttle.db (A의 로컬 파일)
서버 B → /app/data/shuttle.db (B의 로컬 파일)
(이름이 같아도 동일한 DB라는 보장 없음)

여러 서버가 각자 로컬 파일을 사용하면 사용자가 어느 서버에 접속했는지에 따라 다른 데이터가 보일 수 있어. 단순히 SQLite 파일을 네트워크 공유 폴더에 두는 것도 파일 잠금과 네트워크 파일 시스템 특성을 고려해야 해서 항상 안전한 해결책은 아니야. 여러 서버의 동시 쓰기·가용성이 중요해지면 PostgreSQL 같은 공용 서버형 DB와 작업 큐를 검토할 수 있지만, 대신 네트워크 장애·운영 복잡도·서비스 간 일관성 문제를 새로 떠안게 된다.

11강 비교와 확인
관점 단일 프로세스 SQLite 별도 worker + SQLite 여러 서버
메모리 상태 공유 프로세스 안에서 가능 자동 공유 안 됨 자동 공유 안 됨
DB 상태 공유 연결로 가능 같은 파일을 연결해 가능 공용 DB/분산 저장 설계가 필요
쓰기 충돌 연결 간 가능 프로세스 간도 가능 네트워크 및 DB 설계가 관건
재시작 후 복구 파일·연결·조회 구현 필요 추가로 작업 소유권·복구 필요 추가로 노드 간 일관성 필요
얻는 이점/손실 단순하지만 확장 한계 작업 격리 대신 조정 비용 확장성 대신 복잡도

단일 서버에서 맞는 설명을 여러 서버에 그대로 확대하면 안 돼. SQLite를 선택했다는 사실은 잘못이 아니라 어떤 조건에서 어떤 보장을 얻고 어디에서 경계가 끝나는지를 말할 수 있는지가 중요해.

🛡️ 14. 백업은 재시작 영속성과 다른 약속이다

더 알고 싶다면 · 백업과 복원

정상적인 서버 재시작 후 기록이 남는 것과 DB 파일이 손상된 뒤 복원할 수 있는 것은 다른 문제야. 전자는 프로세스보다 오래 사는 파일 저장이, 후자는 독립적인 복구 사본이 필요해.

원본 DB ── 일관성 있는 백업 작업 ──► 별도 위치의 백업본
   │                                   │
   └── 서비스 운영                     ├─ 접근 권한 관리
                                       ├─ 백업 시점 기록
                                       └─ 별도 경로로 복원
                                               │
                                               ▼
                                      DB 새 연결·행 조회
                                      integrity_check
                                      foreign_key_check
                                      업무 규칙·출처 검증

Python sqlite3.Connection.backup() 같은 API는 실행 중인 SQLite의 일관성 있는 백업을 만드는 데 유용해. 복원 뒤 PRAGMA integrity_check;는 DB 구조의 무결성 검사에 도움을 주지만 모든 외래키의 의미나 노선의 정원 규칙까지 확인해 주지는 않아. FK 상태는 PRAGMA foreign_key_check;, 노선 준수는 별도의 업무 검증기로 살펴야 해. [SQLite 온라인 백업: https://www.sqlite.org/backup.html]

백업 이후 새로 커밋된 작업은 장애 시 잃을 수 있어. RPO는 허용 가능한 데이터 손실 시점 범위, RTO는 목표 복구 시간을 설명할 때 쓰는 운영 용어야. 이 수업에서 실제 시험의 필수 설정값이었다는 뜻은 아니야. 자주 백업하면 손실 구간을 줄이는 데 도움이 되지만 비용이 늘고, 보관 기간·보안·복원 훈련도 필요해. 백업 파일 자체가 있다는 사실만으로 복구 성공을 선언하면 안 된다.

Ailey: 이제 “통근버스 결과를 DB에 넣는다”를 한 번 풀어 쓰자. 먼저 한 행이 무엇을 뜻하는지 정한다. 직원 한 명과 직원의 하루 근무표는 다르고, 버스 한 번의 운행과 그 버스에 배정된 직원 한 명도 다르다. PK는 행을 식별하고, FK는 행이 유효한 다른 행을 가리키도록 제한하며, UNIQUE는 같은 방향의 중복 배정을 막을 수 있어. 그러나 누락된 직원이나 시간표의 이동 시간 위반은 그런 국소 제약만으로 잡을 수 없어.

🗣️ 16. 내 말로 설명하기: 무엇이 확인됐고 무엇이 아직 가설인가?

다음은 정답을 암기하는 단답형 시험이 아니라 설명 연습을 위한 열린 질문이야. 이 글을 읽었다는 사실만으로 답할 수 있다고 판단하지 않는다. 실제로 답안을 제출하고 평가받는 단계는 원본 Ailey & Bailey의 외부 교육 자료 기반 문항·피드백 절차에 따라 따로 수행한다. 여기서는 질문마다 답에 포함되어야 할 구별의 축만 제시할게.

1. 행을 어떻게 구분할까?

“직원 테이블에는 emp_id가 PK인데, 근무표 테이블에 emp_id만 PK로 쓰면 왜 안 되나요? 같은 날짜를 서로 다른 데이터셋 버전에서 보관하려면요?”

설명의 축: 행의 단위 → 날짜·직원 조합 → 버전 구분 → 복합키.

2. FK가 검증했다는 말을 어디까지 믿을까?

“employees.site_id가 외래키 검사를 통과했으면 그 직원의 통근버스 노선도 올바르다는 뜻인가요?”

설명의 축: 참조 대상 존재 → 실제 근무 사업장의 진실 → 근무/휴무와 배정 → 시간·정원.

3. NULL을 어떻게 생각할까?

“휴대전화 열에 UNIQUE를 걸었는데 전화번호가 없는 직원 둘을 등록할 수 있나요? 빈 문자열 둘이면 어떤가요?”

설명의 축: NULL과 ''의 차이, UNIQUE와 NOT NULL의 역할.

4. ?가 해 주는 것과 못 하는 것은?

“사용자 입력을 SQL 문자열에 더하는 대신 바인딩하면 무엇이 달라지나요? 바인딩만 하면 타인의 배정을 조회할 권한도 막을 수 있나요?”

설명의 축: SQL 문법/데이터의 분리, 인젝션, 인가의 별도 책임.

5. 한 데이터셋 안에서 오류가 나면 무엇이 남는가?

“7개 CSV 입력 중 마지막 파일에서 FK 오류가 발생했다고 합시다. 앞의 여섯 CSV는 DB에 남을 수도 있나요?”

설명의 축: 트랜잭션 경계, 기존 커밋 유무, ROLLBACK, 적용 포인터 보존.

6. COMMIT과 재시작의 차이는?

“커밋에 성공했습니다. 서버를 재시작한 후 DB 파일이 여전히 있다고 합니다. 그런데 화면에는 빈 노선이 나옵니다. 어떤 순서로 점검하겠어요?”

설명의 축: 같은 파일 경로, 연결, 현재 버전, 결과 ID, SELECT, 캐시 및 화면 변환.

7. worker를 별도 프로세스로 만들면?

“웹 서버가 메모리 변수에 결과를 넣고 worker가 읽도록 했습니다. 어떤 가정이 틀렸고 어떤 지속 가능한 공유 방법이 있나요?”

설명의 축: 프로세스 격리, DB 공유, 파일 경로, 연결별 PRAGMA, 잠금.

8. Docker 볼륨과 백업은 왜 다른가?

“볼륨을 설정했으니 언제든 장애 복구가 가능하다는 주장이 왜 틀렸나요?”

설명의 축: 컨테이너 수명, 볼륨 삭제·호스트 장애, 독립 백업, 복원 검증.

9. 새 데이터셋은 적용됐는데 노선은 옛것이라면?

“DSET-1 결과 G1이 있는 상태에서 DSET-2를 적용했습니다. 재계산 전까지 G1을 DSET-2의 결과라고 보여 주면 안 되는 이유는?”

설명의 축: 입력 스냅샷, 결과의 출처, 유효성, 포인터 전환과 조회.

10. 선택의 손실을 어떻게 방어할까?

“왜 단일 서버·SQLite를 출발점으로 썼고, 언제 여러 서버나 서버형 DB를 검토해야 하며 그때 새로 생기는 책임은 무엇인가요?”

설명의 축: 단순성, 동시 쓰기, 파일 위치, 분산 일관성, 운영 비용.

자기 점검법: 각 답에서 “그렇다”나 “안 된다”로 끝내지 말고 원인 → 실행 순서 → 예상되는 실패 → 확인할 증거 → 선택의 비용을 붙여 봐. 가령 “파일 DB라서 재시작해도 남습니다” 대신 “서버 메모리와 파일 수명이 다르고, 커밋된 파일이 보존된 매체에 있으며, 재시작한 새 연결이 같은 파일을 열어 조회해야 합니다”라고 말할 수 있어야 해. 그래도 실제 이해 성취는 후속 답변과 실행 관찰 없이는 판정하지 않는다.
