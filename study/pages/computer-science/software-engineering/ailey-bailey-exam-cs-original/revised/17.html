🧭 1. 검사한다는 것은 ‘돌아간다’가 아니라 ‘틀릴 방법을 구분한다’는 뜻이야

웹 서비스는 사용자 화면 하나가 아니야. 브라우저의 요청, 서버의 권한 확인, DB에서 꺼낸 입력, 계산기, 독립 규칙 검사, 결과 확정, 재시작 후 조회가 이어진 하나의 사건 사슬이야. 중간에서 하나가 잘못돼도 맨 마지막 버튼은 초록색일 수 있어. 예컨대 생성 API가 HTTP 200을 돌려주면서 실은 어제 계획을 보여 준다면 화면의 ‘성공’은 오늘 계획의 정당성을 입증하지 못해.

여기서 검사(test)는 미리 정한 자극을 가했을 때 시스템이 실제로 무엇을 하는지 관찰하고, 기대한 성질과 비교하는 일이야. 검증(validation)은 특히 ‘이 계획이 업무 제약을 지키는가’를 판정하는 일이야. 용어는 팀에 따라 넓게 쓰이지만, 이 수업에선 ‘테스트는 행동의 증거를 모으는 방법’, ‘계획 검증은 그중 업무 규칙을 판정하는 활동’로 구분할게.

검사에는 늘 네 조각이 필요해.

  1. 초기 상태: DB가 비었는지, 과거 확정 계획이 있는지, 적용 중인 입력 버전은 무엇인지.
  2. 자극: 버튼, HTTP 요청, 데이터 변경, 프로세스 종료, 시간 제한, 재시작.
  3. 관측점: 응답뿐 아니라 DB 행, 로그, 내보내기 JSON, 화면, 재시작 후 조회.
  4. 판정 기준(oracle): 관측 결과를 맞음·틀림으로 구분하는 독립적인 규칙.

오라클(oracle)이란 ‘정답을 알려 주는 기준’을 말해. 정답 노선이 딱 하나가 아닐 때는 더 중요해. 두 계획이 정류장 방문 순서부터 달라도 각각 모든 근무자를 배정하고, 좌석과 시간 제약을 지키면 둘 다 유효할 수 있어. 따라서 ‘지난번 JSON과 글자 단위로 똑같은가’보다 ‘독립적인 제약 검사를 통과하는가’를 먼저 보아야 해. 그 뒤에야 어느 쪽이 더 편리한지 품질을 비교할 수 있어.

이 그림의 202 Accepted와 작업 레코드/비동기 처리 방식은 예시 설계이지 시험의 필수 스택이 아니야. 단일 서버에서 동기 실행할 수도 있어. 핵심은 요청이 도착함, 계산이 끝남, 규칙을 통과함, 확정 저장됨, 다른 사용자가 조회할 수 있음이 서로 다른 사실이라는 점이야.

선수 개념을 확인하며 복원하기

프로세스가 종료되면 그 프로세스가 가진 RAM의 지역 변수와 진행 중 계산은 일반적으로 사라져. 반면, 이미 커밋된 DB 변경은 영속 저장소가 정상 동작한다는 전제에서 남도록 설계돼. timeout은 약속한 시간을 넘겼다는 판단이고, cancel은 중단 의사를 전달하는 동작이야. 시간 초과 응답이 나왔다고 작업이 실제로 멈췄다고 결론낼 수 없고, 취소 신호가 전달됐다고 이미 확정된 결과가 자동으로 취소되는 것도 아니야. 이 세 가지를 섞으면 장애 테스트가 틀린 대상을 관찰해.

가령 요청자가 20초 기다리다 연결을 끊었어도 서버의 계산은 30초 뒤 계속 DB에 저장할 수 있어. 따라서 클라이언트의 실패와 서버의 확정 실패는 다른 상태야. 반대로 프로세스가 죽어도 예전 확정 결과는 남길 수 있지. 이 차이를 실제로 검사하려면 HTTP 응답, 작업 상태, 확정본을 각기 관찰해야 해.

🔬 2. 단위·통합·전체 사용자 흐름·독립 계획 검사·장애 주입은 서로 다른 질문이야

‘테스트를 100개 만들었다’는 말에는 어떤 위험을 다뤘는지 정보가 거의 없어. 작은 함수를 100번 검사해도 DB가 잘못 연결되어 있으면 서비스는 실패할 수 있고, 화면을 한 번 끝까지 클릭해도 희귀한 시간 경계 오류를 놓칠 수 있거든.

‘독립 계획 검사’는 별도의 테스트 단계이자 산출물 검사 방식이므로, 단위·통합·E2E와 완전히 같은 축에 놓이는 분류는 아니야. 단위 검사로 구현할 수도 있고 별도 프로그램으로 내보내기 JSON에 대해 실행할 수도 있어. ‘장애 주입’도 층위라기보다 자극의 종류야. 통합 또는 E2E와 함께 실행할 수 있어. 서로 다른 축임을 알아야 테스트 설계표가 의미 있어져.

같은 오류를 검사층별로 보면 무엇이 달라질까

상황: 출근 버스의 두 지점 이동 시간이 원본 travel_times.csv에서 12분인데 생성기가 8분 간격으로 시각을 기록했다고 가정하자.

  • 단위: actual_delta >= required_minutes라는 비교 함수에 (8, 12)를 넣어 False가 나오는지 확인한다.
  • 통합: 서버가 적용된 입력 버전에서 올바른 방향 A→B의 12분을 읽는지 확인한다. B→A가 9분이라면 방향 혼동도 탐지한다.
  • 전체 사용자 흐름: 생성 버튼을 누른 뒤 실패 이유를 운영자가 볼 수 있고 이전 계획을 계속 조회할 수 있는지 확인한다.
  • 독립 검사: 생성기 내부 계산에 의존하지 않고 적용 CSV와 내보낸 JSON을 연결해 8분이 부족함을 찾아낸다.
  • 장애 주입: 오류를 찾아내는 중에 검증 프로세스가 죽을 때도 잘못된 후보가 확정되지 않는지 본다.

이 예시의 12·8·9분은 실제 CSV 값이 아니야. 여기에서 중요한 건 같은 결함을 서로 다른 관찰 경계에서 발견한다는 사실이야.

UI 전체 검사는 실제 경험에 가깝지만 느리고 화면 요소 변경에 취약할 수 있어. 단위 검사는 빠르지만 실제 연결 실패를 감추기 쉬워. 그러므로 검사 수를 균등하게 늘리는 문제가 아니라, 위험마다 어떤 증거 조합이 필요한지 결정해야 해. 이 대비는 Martin Fowler의 The Practical Test Pyramid가 설명하는 범위와 제한에도 부합해. [외부 참고 1]

실제 시험 원문은 ① 정류장 선정, ② 구성원 배정, ③ 노선·시간표 생성과 7종 CSV를 요구해. 45석 기본 정원, 출근 20분 전 도착, 퇴근 10분 후 출발, 평일 근무일별 근무자 전원 양방향 배정, travel_times.csv 기준 계산, 운영자·구성원 역할, 파일 업로드 없는 데이터셋 선택·검증·적용, 그래프 화면, JSON 내보내기, DB 영속화, 헬스체크와 빈 DB 초기화, Dockerfile, 실행 문서도 포함돼. 기술 스택은 자유이며 SQLite, 작업 테이블, 독립 검증 프로세스는 여기서 선택한 교육용 구현안이야. DB가 무엇을 소유해야 할까? 예를 들어 적용 입력 버전, 현재 확정 실행 ID, 작업 상태, 검증 결과, 최종 노선과 배정은 재시작 뒤에도 의미가 있어야 하므로 DB에 남기는 선택이 자연스러워. 생성기 함수 내부 리스트인 임시 후보는 계산 도중만 필요할 수 있지만, 실패 분석·프로세스 분리·재시도에는 임시 파일이나 DB staging table로 남기는 편이 유리할 때가 있어. 저장을 선택하면 추가 I/O와 정리 정책이 생겨.

핵심 불변조건은 두 가지로 요약할 수 있어.

불변조건 A: 검증되지 않은 계획은 current_run_id가 될 수 없다.
불변조건 B: 실패한 후보나 잘못된 입력 때문에 이미 확정된 정상 계획이 사라지지 않는다.

다만 입력이 새 버전으로 적용됐는데 옛 계획이 남아 있는 것은 별도 의미야. 기존 확정 계획을 기록으로 보존하는 것은 가능하지만, 화면에서 이를 새 입력에 대한 현재 유효 계획처럼 표시하면 안 돼. 이를 구분하려면 current_dataset_version과 각 run.dataset_version을 비교해 ‘재계산 필요’ 상태를 보여야 해.

업무 규칙을 오라클로 옮기는 순서

계획을 판정하려면 먼저 파일 형식만 볼 수는 없어. 최소한 다음 순서로 확인해야 해.

  1. 계약·참조: 기간 안의 평일인지, route_id가 같은 날짜에 유일한지, 지점과 구성원·시간대 ID가 실제 입력에 있는지, stops[].seq가 1부터 끊기지 않는지.
  2. 노선 구조: 출근은 해당 사업장에서 끝나고 퇴근은 시작하는지, 한 운행에 지점 최소 2개인지, 다른 사업장을 경유하지 않는지.
  3. 시각: 한국시간 오프셋 형식과 시간 증가, 인접 지점 사이의 실제 간격 ≥ 방향별 CSV 소요시간, 출근 시작 전 설정된 여유 시간, 퇴근 종료 10분 이후 출발 및 원문 지정 12시간 범위.
  4. 배정: WORK만, 각 근무일·방향당 정확히 한 번, 해당 직원의 사업장/시간대 일치, 탑승 지점이 하차보다 앞서는지.
  5. 용량: 버스 한 대 한 번 운행의 각 이동 구간에 남아 있는 승객 수 ≤ 적용 정원. 전체 운행 배정 수만으로 판단하면 중간 승하차 때문에 오판할 수 있어.
  6. 범위·입력 일치: 평가에 사용한 기간·정원·도착 여유·적용 CSV 버전이 실제 생성 조건과 같은지. 출력 JSON이 자기 자신에게 적어 놓은 ‘정원’만 믿으면 안 돼.

원문에 사용된 ridership.csv의 과거 실제 탑승 수는 좌석 배정 대상자를 줄이는 근거가 아니야. 전체 좌석 확보 대상은 그 날짜 work_schedule.csv에서 WORK인 사람이야. 이 차이를 잊으면 ‘승객 수가 적어서 최적’이라는 가짜 성공이 생겨.

🧱 4. 빈 DB에서 재시작 조회까지: 하나의 증거 사슬을 세워 보자

테스트의 목적은 코드 라인 하나를 지나갔다는 보고가 아니라, 사용자가 밟는 업무가 서로 일관된 상태 전이를 보이는지 입증하는 거야. 단일 서버·SQLite 기준으로 아래는 실제로 실행할 수 있도록 설계한 시나리오 순서야. 특정 라우트 경로나 테이블 이름은 예시로 설정했어.

먼저 증거가 남는 실험실을 만든다

테스트가 시작할 때마다 같은 DB를 재사용하면 어제 남은 확정 계획 때문에 오늘의 결함을 놓쳐. tempfile로 시험 전용 DB 경로를 만들고, 새 서버 프로세스에 DATABASE_URL 또는 앱이 사용하는 환경변수를 전달한 뒤 스키마 생성과 seed를 실행해야 해. 테스트에서 기대하는 ‘빈 DB’는 테이블도 없고 이전 작업도 없는 새 파일이야. 첫 부팅에 스키마·초기 로그인 계정·준비된 데이터셋 목록이 필요한 경우 이를 반복 가능하게 만드는 과정이 초기화/마이그레이션이야.

동시에 재현을 위해 최소한 다음을 증거 묶음으로 보관해.

17강 비교와 확인

모든 행에 실제 명령, 실행 시각, 종료코드, 기대와 실제 관측이 붙어야 재현 가능한 증거가 돼. HTTP 상태뿐 아니라 DB 상태의 불변 여부를 비교해야 해. 권한 검사에서 403이 나왔어도 부작용으로 작업이 만들어졌다면 실패야.

단계 3의 ‘적용 실패’는 어떻게 원자성을 검사하나

초기 상태가 입력 버전 v1, 확정 결과 r7이라고 가정하자. 운영자가 새 후보 v2를 선택했는데 work_schedule.csv에 존재하지 않는 emp_id가 있어. 기대되는 진행은 다음과 같아.

시간 ─────────────────────────────────────────────────────►
DB        current_dataset=v1      current_dataset=v1
          current_run=r7           current_run=r7
화면      'v2 검증 시작'          '참조 오류: emp_id ...'
후보      v2 (미적용)            v2 (거절/진단 기록 가능)

오류 메시지가 보인다고 끝이 아니야. 버전과 확정 결과가 실제로 그대로인지 DB에서 비교해야 해. 입력을 테이블 7개에 순서대로 지운 뒤 다시 적재하면 4번째 CSV에서 오류가 났을 때 앞의 3개만 새 입력일 수 있어. 안전한 방식은 후보 스테이징에 모두 적재→전체 검증→한 트랜잭션에서 활성 버전 포인터 교체야. 또는 신규 버전 데이터를 한 번에 커밋해도 돼. DB 트랜잭션 범위 밖의 파일 변경은 SQLite의 롤백 대상이 아니므로 파일까지 얽히면 별도의 임시 파일·원자적 교체 전략이 필요해.

단계 5의 ‘생성 성공’은 어느 시점인가

시간  시작    입력 고정      후보 작성      후보 검증       DB COMMIT       조회
      │          │              │              │               │            │
      ▼          ▼              ▼              ▼               ▼            ▼
상태  QUEUED → RUNNING ─────► VALIDATING ───► COMMITTING ──► SUCCEEDED
                         후보는 아직 공개 금지          그 후 공개 가능

다른 흐름: 검증 실패 ──► FAILED (이전 current_run 유지)
다른 흐름: timeout ──► 중단/격리 확인 ──► FAILED 또는 재시도 대기

SUCCEEDED를 찍는 기준을 계산 종료로 잡으면 저장 실패에도 성공으로 보일 수 있어. 대신 검증 결과와 확정 결과가 같은 입력 버전·후보 해시로 묶이고, DB 커밋 뒤에야 성공으로 관찰되도록 설계해. 작업 레코드의 성공 표시와 확정 포인터 갱신도 가능한 한 같은 DB 트랜잭션으로 다루는 게 유리해.

재시작 검증은 무엇을 종료해야 의미 있나

브라우저 새로고침은 서버 재시작이 아니야. ‘재시작 후에도 남는다’를 증명하려면 서버 프로세스 PID가 바뀌었음을 기록하고, 기존에 쓰던 같은 영속 DB 파일/볼륨을 재사용해 조회해야 해. 테스트가 재시작할 때 새 임시 DB를 만들었다면 복구 테스트가 아니라 초기화 테스트가 돼. 반대로 개발용 서버의 자동 리로드가 부모 프로세스·자식 프로세스를 섞어 관리하면 무엇을 죽였는지 불명확해질 수 있으니 PID·시작 시간·컨테이너 ID를 남겨.

재현 가능한 최소 절차(가상 명령 예시)

# 이 명령은 특정 프로젝트에서 실행 검증된 명령이 아니다.
# 아래의 ./app, /health, /api/...는 예시 인터페이스이다.
export DATABASE_URL="sqlite:////tmp/bus-test-case-001.sqlite3"

# 로그인과 API 호출은 프로젝트 계약에 맞게 수행한다.
# 성공 결과 기록 후 서버 PID에 TERM 또는 강제 종료를 주고,
# 동일 DB 경로를 가리켜 다시 서버를 실행한다.

시험 원문은 특정 URL·Python 모듈·환경변수 이름을 요구하지 않았어. 이 코드는 절차를 읽는 참고이며 현재 환경에서 서비스에 접속하거나 실행하지 않았어.

💥 5. 실패를 ‘일으켜 보는’ 이유는 오류 화면이 아니라 금지 상태를 찾기 위해서야

정상 경로는 고속도로를 달리는 차량 사진 한 장과 비슷해. 차량이 브레이크 고장에 어떻게 반응할지는 모르는 거지. 장애 주입(fault injection)은 네트워크 차단·예외 발생·프로세스 강제 종료·시간 제한처럼 의도적으로 실패 조건을 만들고 시스템 경계를 관찰하는 검사야. 무작정 죽이는 것이 아니라 실패 위치와 기대 불변조건을 먼저 정해야 해.

장애의 시점을 분리하면 왜 정확해질까

여기서는 ‘재시도를 하지 말라’보다 ‘같은 요청을 식별하라’가 더 강한 설계야. 예시로 idempotency_key를 운영자·작업 의미·입력 버전·조건과 연관시켜 저장해 두면 같은 키의 재요청에서 기존 결과를 재조회할 수 있어. 단, 같은 키를 다른 조건으로 재사용하는 것은 거부해야 해. 키가 같다는 사실만으로 후보가 동일하거나 DB가 정상이라는 것도 아니므로 commit 기록을 조회해 확인해야 해.

프로세스 종료 vs timeout vs cancel: 실패 신호의 의미

  • 시간 초과: 관찰자가 정한 데드라인을 넘었다는 사실. 서버 요청이 타임아웃됐어도 계산 프로세스가 살아 있을 수 있어.
  • 취소: 어떤 주체가 ‘그만하라’고 요청. 작업이 신호를 확인하거나 강제 종료될 때까지 실제 중단은 보장되지 않아.
  • 강제 종료: 대상 프로세스가 실제로 사라지는 것. DB가 이미 커밋했는지까지 알려 주진 않아.
  • 서버 재시작: 메모리 내 큐·락·진행률이 사라질 수 있어. DB에 남은 RUNNING을 재분류할 규칙이 필요해.

한 프로세스만 쓰는 설계에서는 서버와 생성기가 함께 죽기 쉽고, 요청 중 강제종료를 테스트하면 서버도 다운돼. 생성기를 별도 자식 프로세스로 빼면 계산만 강제 종료하고 API가 생존하는 구조를 시험하기 쉬워지지만, PID 기록, 프로세스 간 메시지 전달, 중복 실행·정리 정책이 더 필요해. 어느 쪽이든 작업 상태의 최종 진실을 RAM 변수만으로 정의하지 않는 것이 복구의 출발점이야.

왜 장애 주입에 ‘고장 위치 식별 도구’가 필요할까

time.sleep(1)을 넣고 적당한 순간 kill하면 실패 위치가 매번 달라질 수 있어. 더 재현 가능한 방식은 예시처럼 코드 경계에 테스트 전용 failpoint를 둬서 정확한 순간에 멈추게 하는 거야. 운영 모드에선 꺼야 하고 비밀 키나 임의 명령으로 외부 사용자에게 열어 두면 안 돼.

# 교육용 의사 코드: 실제 제출 코드 아님, 실행 확인하지 않음.
def promote_candidate(job, candidate):
    assert candidate.input_hash == job.input_hash
    verdict = independent_validate(candidate, job.applied_inputs)
    if not verdict.ok:
        record_failure(job, verdict)
        return

    failpoint("after_validation_before_commit")  # 테스트 환경 전용
    with sqlite_transaction() as tx:
        # DB에 현재 입력 버전·작업 소유권이 여전히 유효한지도 검사한다.
        tx.assert_active_version(job.input_version)
        tx.assert_attempt_is_owner(job.id, job.attempt_id)
        tx.insert_confirmed_run(candidate, verdict)
        tx.set_current_run(candidate.id)
        tx.mark_job_succeeded(job.id)
    failpoint("after_commit_before_response")

여기서 assert는 Python 내장 assert를 DB 검증 대용으로 쓰라는 의미가 아니야. 의사 코드의 tx.assert_*는 DB 안에서 조건을 확인하고 불일치 시 트랜잭션을 중단하는 명시적 검증 동작을 뜻해. 실제 구현은 예외 처리와 잠금/조건부 UPDATE, 트랜잭션 설정을 정확히 설계해야 해. assert 문은 실행 옵션에 따라 제거될 수 있으므로 업무 규칙 검증에 의존하면 안 돼.

liveness와 readiness가 다른 이유

  • Liveness: 서버 프로세스가 살아 있고 최소한 응답할 수 있는지. 계속 실패하면 재시작 대상으로 볼 수 있어.
  • Readiness: 지금 사용자 요청을 제대로 처리할 준비가 됐는지. DB 접속·필수 스키마 상태 등 실제 의존성을 가볍게 확인할 수 있어.
  • 업무 정확성: 45석·시간표·전원 배정이 지켜지는지. 헬스 200은 이 질문에 답하지 않아.

DB가 잠깐 느려졌다는 이유로 liveness까지 503을 반환하면 재시작이 폭주할 수 있어. 반대로 readiness를 단순히 return 200으로 만들면 실제로는 DB가 준비되지 않았는데 트래픽을 받게 돼. 헬스는 범위를 좁게 정의하고 응답 의미를 문서화해야 해.

무엇을 남기면 서로 연결되는가

가장 먼저 구별할 ID는 다음이야.

  • job_id: 사용자가 요청한 업무 단위. 한 번의 생성 요구 자체를 식별.
  • input_version 및 input_hash: 어떤 적용 데이터와 조건으로 작업했는지. 원본 7종 파일의 정규화된 목록 + 파일별 바이트 해시 또는 불변 데이터 스냅샷을 연결해야 함.
  • attempt_id: 같은 job의 몇 번째 실제 계산 시도인지. 재시도 횟수가 바뀌어도 job은 동일할 수 있음.
  • candidate_hash: 생성기가 낸 후보 결과를 직렬화한 바이트의 해시. 독립 검증과 확정이 같은 후보를 다루는지 연결.
  • run_id: 확정되어 조회와 내보내기의 기준이 되는 계획 버전.
  • trace_id/span_id: 웹 요청과 내부 작업·단계 간 경로를 잇는 표식.

주의할 점: JSON 객체는 키 순서·공백·숫자 표현에 따라 내용은 같아도 바이트가 달라질 수 있어. 해시 비교를 안정적으로 하려면 직렬화 규칙(canonicalization)을 정하거나 해시 대상의 원본 바이트를 그대로 보존해야 해. input_hash에 CSV 내용만 넣고 차량 정원·날짜 범위·여유 시간을 누락하면 동일 입력이라는 오판이 생길 수 있어. 데이터 해시와 실행 파라미터 해시를 별도로 두거나 하나의 명시적 작업 fingerprint로 묶는 편이 명료해.

위 값들은 모두 형식만 보여 주는 가상 로그야. 예시의 첫 행은 명령 문자열을 기록하고 있지만, 실제 환경에서는 비밀값을 포함하는 명령 인자/환경변수는 마스킹해야 해. ‘종료코드 2’의 의미 역시 프로젝트에서 문서화하지 않으면 알 수 없어. 로그가 남는 것 자체가 종료를 확인했다는 뜻은 아니므로, 부모 프로세스가 자식의 종료코드를 wait/communicate 등으로 회수한 시점을 따로 기록해야 해.

기록하지 않으면 구분할 수 없는 다섯 가지

  1. 계산 도중 중단: 시작 로그만 있고 종료코드 없음. 부모가 죽었다면 기록 자체가 불가능할 수 있음.
  2. 정상 종료하지만 잘못된 후보: 프로세스 종료코드 0, 독립 검증 실패.
  3. 검증은 성공하지만 확정 실패: validator ok=true, DB commit 예외.
  4. 확정 성공하지만 응답 실패: DB current run 변경됨, HTTP 연결 종료.
  5. 재시작 후 복구: 이전 attempt에 종료 이벤트 없음, 재기동의 reconciliation 이벤트와 새 attempt 기록 존재.

이 구분이 바로 ‘실행 기록을 남긴다’의 실질적인 의미야. 한 줄의 Generation complete로는 다섯 경우를 판별할 수 없어.

     t0               t1                 t2                 t3              t4             t5          t6         t7
     └─ 접수·생성 지연 ┘└──── 실제 큐 대기 ──┘└──── 입력 로드 ────┘└── 계산 ─────┘└── 검증 ───┘└─ 확정 ──┘└─ 가시화 ─┘

접수·작업 생성 지연 = t1 - t0  (클릭 → 서버 접수·job QUEUED 영속 기록)
실제 큐 대기       = t2 - t1  (job QUEUED 생성 → worker claim)
입력 로드          = t3 - t2
계산              = t4 - t3
검증              = t5 - t4
확정              = t6 - t5
최종 가시화        = t7 - t6
전체 체감 시간     = t7 - t0  (위 구간의 합, 구간이 겹치지 않는 단순 순차 모델)

worker claim은 워커가 대기 작업의 소유권을 확보하고 실행을 시작하도록 상태를 바꾸는 사건이야. 단일 서버에서 요청을 받은 즉시 동기 계산한다면 영속 QUEUED 상태나 실제 큐가 없을 수 있으므로 큐 대기 시간을 측정했다고 쓰지 않고, 해당 설계에는 없는 구간으로 표시해야 해. t0는 브라우저 시계, t1 이후는 서버·워커 시계일 수 있어. 따라서 위 차이는 개념상 분해식이고, 실제 측정에는 기준 시계를 맞추거나 브라우저 구간과 서버 내부 구간을 별도로 계측해야 해. 여러 프로세스의 단조 시계 절대값을 그대로 빼서는 안 돼.

각 프로세스 내부의 구간 길이는 단조 시계(monotonic clock)로 재는 게 안전해. 벽시계 시각은 로그 사건을 사람이 읽는 데 좋지만 NTP 보정이나 시간 변경으로 구간 측정이 왜곡될 수 있어. 프로세스 사이의 큐 대기는 공유 DB에 기록된 queued_at과 claimed_at 등 같은 기준의 타임스탬프로 추정하되 시계 오차·DB 기록 지연을 고려해야 해. 정밀 계측이 필요하면 동일 시계 영역의 계측 또는 명시적인 분산 추적 측정 설계를 적용해야 해.

평균만으로 왜 부족할까

다섯 작업이 각각 1, 1, 1, 1, 16초 걸렸다고 가정하자. 평균은 4초지만 다섯 번째 운영자는 16초를 기다렸어. 평균이 낮아도 긴 꼬리 지연이 사용자에게 큰 영향을 줘. p50(중앙값), p95, p99는 지연 분포에서 느린 쪽을 보여 주는 분위수야. 표본이 5개면 p95·p99의 추정이 불안정하므로 표본 수와 측정 구간을 함께 적어야 해. 또한 성공 작업 시간과 실패 작업 시간을 구분해야 해. 즉시 오류를 반환하는 작업이 많아져 평균 처리시간이 줄었다면 서비스가 빨라졌다고 자랑할 수 없지.

Google SRE의 관측 개념에서는 지연(latency), 트래픽(traffic), 오류(errors), 포화(saturation)를 네 가지 핵심 신호로 강조해. 이 수업의 작업형 서비스로 옮기면 ‘요청 수/분’, ‘성공·실패별 소요시간’, ‘업무 오류율’, ‘동시 작업·큐·CPU·메모리·DB 잠금 대기’가 해당돼. [외부 참고 3]

메모리도 하나의 값이 아니야

  • RSS: 프로세스가 점유한 물리 메모리의 대략적인 크기. 공유 페이지 등이 포함될 수 있고 운영체제별 측정 차이가 있어.
  • peak RSS: 한 작업 중 최고 RSS. 순간 폭증 후 종료되면 마지막 RSS보다 이 수치가 중요해.
  • Python 힙 추적 같은 도구는 특정 할당의 증가 원인을 찾을 수 있지만 전체 프로세스 메모리와 일치하지 않아.
  • 전체 시스템 메모리: 웹 서버·워커·SQLite 페이지 캐시 등 여러 프로세스와 OS 캐시가 합쳐져, 한 워커 RSS만으로 서버 용량을 판단할 수 없어.

단위 검사가 쉽게 알아내는 오류: 구간별 정원

한 노선의 정류장마다 사람이 타고 내리면 버스의 탑승 인원은 움직여. 마지막에 30명이 내렸다고 해서 중간에 50명이 탄 적이 없다고 할 수 없어.

# 가상 예시. 각 정류장에 도착한 뒤 먼저 하차, 그다음 승차한다고 가정.
def capacity_violations(events, seats):
    on_board = 0
    errors = []
    for seq, alight, board in events:
        on_board -= alight
        if on_board < 0:
            errors.append((seq, "negative_on_board"))
        on_board += board
        if on_board > seats:
            errors.append((seq, "over_capacity"))
    return errors

# 가상 값: 첫 정류장 40명 승차, 다음 정류장 10명 하차·16명 승차.
# 두 번째 지점 이후 46명 → 45석 위반.
assert capacity_violations([(1, 0, 40), (2, 10, 16)], 45) == [
    (2, "over_capacity")
]

이 함수 검사가 통과해도 실제 배정 테이블에서 승차·하차를 올바르게 모으는지, 정류장 순서가 맞는지는 몰라. 또한 노선의 시발점이 차량 공차라는 가정과 하차/승차 순서, 동일 지점에서 하차 후 승차 허용 여부가 실제 요구에 어떻게 맞는지 확인해야 해. 함수 하나의 성공이 전체 계획 성공이 아닌 이유야.

# 자식 프로세스 워커를 실행하는 방식의 가상 예시.
import subprocess
import time

def utf8_size(value):
    # text=True의 정상 경로는 str, TimeoutExpired의 출력은 bytes일 수 있다.
    # 두 경로 모두 UTF-8 바이트 길이라는 동일한 정의를 사용한다.
    if value is None:
        return 0
    if isinstance(value, bytes):
        return len(value)
    return len(value.encode("utf-8"))

def run_worker(command, timeout_s):
    started = time.monotonic()
    timed_out = False
    try:
        p = subprocess.run(
            command, capture_output=True, text=True, encoding="utf-8",
            timeout=timeout_s, check=False,
        )
        code, out, err = p.returncode, p.stdout, p.stderr
    except subprocess.TimeoutExpired as exc:
        timed_out = True
        # 타임아웃 예외만으로 실제 종료코드를 회수하지 못했다.
        code, out, err = None, exc.stdout, exc.stderr
    return {
        "elapsed_s": time.monotonic() - started,
        "timed_out": timed_out,
        "exit_code": code,
        "stdout_bytes": utf8_size(out),
        "stderr_bytes": utf8_size(err),
    }

이 코드가 관찰하는 것은 명령의 종료 상태지 결과의 업무적 타당성이 아니야. 정상 경로의 text=True 출력은 문자열이므로 len(str)는 문자 수이고, 여기서는 encode("utf-8")의 길이를 세어 stdout_bytes·stderr_bytes를 UTF-8 바이트 수로 통일했어. TimeoutExpired에 담긴 출력은 text=True를 사용했더라도 bytes일 수 있어 바이트 그대로 길이를 세어. 다만 정상 경로를 UTF-8로 디코딩한 후 재인코딩한 길이와 원시 출력 바이트의 길이가 항상 같다고 주장할 수는 없어(잘못된 인코딩·디코딩 오류 등). 이 예시는 유효한 UTF-8 출력 전제의 교육용 코드이며, 원시 바이트 수가 반드시 필요하면 처음부터 바이너리 캡처로 계측해야 해. 또 exit_code=None은 실제 종료코드를 회수했다는 뜻이 아니라 관측값이 없다는 뜻이야. subprocess.run은 직접 자식에 대한 타임아웃 처리를 수행하지만, 손자 프로세스를 포함한 프로세스 트리 전체 정리까지 보장하진 않아. capture_output=True는 큰 로그를 메모리에 쌓을 수 있으므로 대규모 출력은 파일 또는 스트리밍으로 제한해야 해.

SQLite가 보장하는 것과 애플리케이션이 보장해야 하는 것

SQLite 트랜잭션은 단일 DB의 다중 변경을 원자적으로 커밋하도록 설계돼. 그러나 ‘검증한 후보가 현재 입력 버전과 맞다’는 업무 조건을 자동으로 알아주진 않아. 이를 애플리케이션이 조건부 UPDATE나 트랜잭션 안의 검증으로 지켜야 해. 또한 SQLite는 한 순간에 쓰기 수행자가 하나인 모델이어서, 여러 워커가 커밋을 경쟁하면 지연이나 busy 오류를 다루어야 해. WAL 모드는 읽기와 쓰기의 동시성을 개선할 수 있지만 동시 쓰기 무제한을 의미하지 않고 네트워크 파일시스템에서 여러 호스트가 공유할 분산 DB로 쓰는 방식은 적합하지 않아. [외부 참고 4·5]

별도 프로세스·다중 서버에서는 보장이 어떻게 달라지나

 [SQLite 파일]                         [공유 작업 저장소]

단일 워커이면 동일 작업이 동시에 실행될 위험을 상대적으로 줄일 수 있지만 서버가 죽으면 작업도 멈춰. 여러 워커는 처리량/장애 격리를 개선할 수 있어도 동일 job을 둘이 잡는 경쟁이 발생할 수 있지. 여러 서버에선 RAM 락은 서버별로 따로 존재하므로 전역 보장이 되지 않아. DB에 저장되는 작업 소유권, lease 만료, 조건부 상태 전이, idempotency key, 유일 제약조건 등이 필요해.

lease는 ‘정해진 시간 동안 특정 워커에게 이 작업의 소유권을 준다’는 식의 임시 소유권이야. 워커가 멈추면 기한이 지난 뒤 다른 워커가 가져갈 수 있어. 그러나 첫 워커가 단지 느렸는데 lease가 만료되면 둘 다 실행 중일 수 있다는 위험이 있어. 따라서 lease만으로 중복 확정을 막지 말고, 현재 소유 attempt인지 DB에서 다시 비교하고 확정 결과에 유일 조건·조건부 갱신을 두어야 해. 이는 구현 세부가 아니라 ‘누가 최종 상태를 바꿀 권리가 있는가’라는 일관성 문제야.

🧯 10. 그럴듯하지만 틀린 주장 여섯 개를 분해해 보자

“테스트 120개 통과했으니 정확해.”

그 120개가 모두 format_time() 같은 단위 검사라면 실제 근무자 전원이 배정되었는지에 대한 증거는 없어. 무엇을 검사했는지, 어떤 반례를 넣었는지, 어느 관측점에서 확인했는지가 중요해. 또한 검사 코드가 잘못된 오라클을 갖고 있으면 120개 모두 같은 오류를 승인할 수 있어.

“AI 에이전트가 All tests passed라고 했어.”

그 문장은 실행했다는 주장이지 실행 환경·명령·종료코드·검사 보고서·DB 상태를 대신하지 않아. 실제 터미널 이력의 명령과 출력, 테스트 결과물, 실패 시 재현 절차, 독립 검증 결과를 연결해야 해. AI가 작성한 검증기가 AI가 만든 생성기와 같은 규칙 오류를 공유할 수도 있어. AI 협업 자체가 불가능하다는 뜻이 아니라, 주장과 증거의 책임을 분리하자는 거야.

“평균 2초니까 성능 문제 없어.”

실패는 0.1초, 성공은 20초인 서비스가 실패를 많이 반환하면 평균이 낮아질 수 있어. 큐가 길어지는 순간 사용자 체감은 크게 변하고 p95 또는 최악의 기다림은 평균에 드러나지 않아. 성공/실패별 지연, 큐 대기, 입력 규모, 동시성, 표본 수를 붙여야 해.

“서버가 재시작됐고 헬스 200이야. 복구됐어.”

프로세스가 살아 있음을 확인한 것뿐이야. DB의 입력 버전, 미완료 작업, 확정 run, 해당 직원의 날짜별 조회와 재다운로드까지 확인해야 복구의 범위를 말할 수 있어.

“생성기와 검증기가 둘 다 OK래.”

검증기가 생성기의 대상 목록을 그대로 신뢰해도 그럴 수 있어. 생성기가 1,500명 중 100명을 빼고 검증기까지 1,400명을 전체로 오해하면 둘 다 통과해. 근무표에서 독립적으로 기대 대상을 다시 만드는 것이 필요해.

“내보낸 JSON이 45석 이하니까 조건은 지켰어.”

출력이 정원을 60으로 적고 그 기준으로 스스로 검사했다면 잘못된 주장이야. 검증자는 외부에서 지정한 정원 45, 적용 데이터와 근무표, 시간 여유 조건을 가져와야 해. 내보내기 대상과 현재 조회 run이 같은지도 확인해야 해.

🧩 11. 실전에서 읽는 하나의 완성 사건: 오류를 발견하고도 계획을 지키는 서비스

다음은 1인 운영자, 단일 서버·SQLite에서 일어난 가상의 전체 사건 기록이야. 숫자와 ID는 시연용으로 만들었고, 실제 시험 실행 결과가 아니야.

상태 0. 처음 DB를 열고 스키마와 테스트 계정을 만든다. 운영자 로그인 후 데이터셋 v1을 적용하고 출근·퇴근 계획 r1을 정상 확정했다고 가정해. r1은 입력 해시 H1, 파라미터 fingerprint P1과 연결돼 있어. 구성원이 조회하면 r1의 자신의 근무일 배정만 보인다.

상태 1. 운영자가 근무표가 바뀐 후보 v2를 선택한다. employees.csv에 없는 E-UNKNOWN이 work_schedule.csv에서 발견돼. 데이터 관리 계층은 ‘참조 무결성 오류’를 반환하고, 현재 입력 v1, current run r1을 유지해. 브라우저에 오류만 표시하고 DB 확인을 건너뛴다면 검사는 아직 미완성이야.

상태 2. 오류를 수정한 v2b가 적용된다. 이때 current input은 v2b, 이전 r1의 input_version은 v1이야. 조회 화면은 ‘새 입력에 대한 재계산 필요’라고 표시하고 r1을 새 계획처럼 보여 주지 않아. 이전 확정 기록 r1은 감사·복원용으로 남길 수 있어.

상태 3. 운영자가 정원 45석, 여유 20분, 선택 기간을 넣어 생성한다. job-27, attempt-1이 생겨. 큐 대기는 200ms, 입력 로드 100ms, 계산 2,000ms라는 가상 측정값이 기록된다. 생성기는 후보 c1을 내고 해시 HC1을 기록해.

상태 4. 독립 검증기가 v2b의 근무표에서 WORK 대상을 다시 구성하고 JSON을 검사한다. 특정 날짜에 한 직원이 퇴근 노선에서 누락되었다고 가정해. 검증기는 ok=false와 날짜·직원·방향·위반 종류를 기록하고 c1을 거절해. job은 FAILED가 되고 r1은 확정 이력에 남지만 v2b의 유효한 현재 계획은 아직 없음으로 표시돼.

상태 5. 구현 오류를 수정한 뒤 새 attempt가 계산해 후보 c2를 만든다. 검증 통과 직후 DB 커밋 전 테스트용 failpoint가 서버 프로세스를 죽여. 재시작해도 c2가 current run이 되어서는 안 돼. RUNNING/COMMITTING으로 남은 작업을 복구 로직이 판별할 때 attempt-2의 종료를 명확히 확정할 수 없으므로 중단 추정/복구 대기 같은 상태를 기록할 수 있어. 이때 재시도 정책에 따라 새로운 attempt가 진행될 수 있지.

상태 6. 새 attempt에서 후보 c3가 검증되고 DB 트랜잭션이 성공한다. current_run=r2, r2.input_version=v2b, r2.candidate_hash=HC3, job SUCCEEDED가 일관되게 기록된다. HTTP 성공 응답이 끊기더라도 재요청 시 동일 작업 키로 r2 확정을 발견할 수 있어야 해.

상태 7. 운영자는 r2에 대한 JSON을 내보내고 그 바이트 그대로 별도 검증기에 입력한다. 분모는 지정 기간의 각 근무일 WORK 집합이고, 정원·도착 여유는 운영자가 지정한 외부 파라미터를 사용해. 독립 보고서와 후보 해시를 저장한다. 마지막으로 서버를 완전히 종료한 뒤 같은 SQLite 파일로 기동해 r2 및 구성원 조회가 여전히 일치하는지 확인한다.

이 사건에서 핵심은 성공이 한 번 나왔다는 게 아니야. 입력 오류 시 보존, 후보 오류 시 확정 금지, 프로세스 종료 시 원자성, 재시도 시 중복 방지, 내보내기 시 독립 판정, 재시작 시 영속성이 각자 다른 증거로 연결된 것이야.

‘가장 취약한 지점’을 답하는 방법

실제 제출 코드를 보지 않았으니 어떤 지점이 실제로 가장 취약했는지는 알 수 없어. 하지만 이 가상 구조에서 우선 의심할 경계는 검증 완료와 DB 확정 사이, 그리고 새 입력 적용과 이전 확정본 노출 사이야. 왜냐하면 둘 모두 화면상 성공/정상으로 보이기 쉬우면서 잘못된 계획이 운영자에게 전달될 수 있는 경계이기 때문이지. 다른 후보 위험으로는 실제 이동시간의 방향 혼동, WORK 기준 누락, 구성원 권한 우회, 재시도 중복 확정이 있어. 의심 우선순위와 실제 발견된 결함을 구분해서 말해야 해.

설명 3 — 반례 설계
가상의 날짜에 출근 120명, 퇴근 118명 배정이 있다고 가정하자. 보고서에 ‘99.17% 배정’이라고 적으면 왜 충분하지 않은가? 원문 업무 규칙과 분모를 연결해 설명해 봐.

설명 4 — 장애 경계
검증 직후 프로세스 종료와 DB 커밋 직후 응답 단절은 어떻게 다른가? 두 경우 각각에서 재기동 후 DB를 확인해야 할 사항을 말해 봐.

설명 5 — 관측 신호
어떤 작업이 평소보다 10배 느리다는 민원을 받았어. 로그·메트릭·트레이스·헬스에서 무엇을 얻고 무엇은 얻지 못하는지, 큐 대기와 계산 시간을 구분하며 설명해 봐.

설명 6 — 독립성
생성기와 독립 검증기가 서로 다른 소스 파일인데도 동시에 같은 오류를 통과시킬 수 있는 사례를 만들고, 입력 근무표·파라미터·해시를 어떻게 검사해야 하는지 제안해 봐.

설명 7 — 설계 손실
단일 서버 SQLite 구현에서 별도 워커 프로세스를 추가할 때 무엇이 쉬워지고 무엇이 어려워지는가? ‘더 안정적이다’라는 표현 없이 소유권·종료·관측·재시도·확정의 언어로 설명해 봐.

설명 8 — 품질과 속도
차량 정원을 45에서 30으로 바꿨더니 계산 시간은 두 배로 증가하고 운행 횟수도 증가했어. 이것이 코드가 느려진 증거인가? 같은 입력·독립 검증·품질 지표·구간별 계측 관점에서 답해 봐.

베일리의 한 번 더 날카로운 질문

“네가 ‘재시작 후 복구했다’고 했지? 그럼 재시작 전에 이미 커밋됐는데 성공 응답만 잃은 작업과, 커밋 자체가 안 된 작업을 네 증거로 어떻게 구별해? 구별할 수 없다면 그건 복구 검증이 아니라 서버가 켜졌다는 관찰일 뿐이야.”

이 질문은 암기 문제가 아니라 정보가 사라지는 경계를 보는 질문이야. 구별하려면 적어도 job_id/attempt_id, 후보 해시와 검증 기록, DB 확정 run 및 현재 포인터, 작업 상태 변경과 커밋의 일관성을 연결해야 해. 저장을 중심으로 진실을 재구성하고, 응답 화면은 그 진실을 조회한 하나의 표현으로 다루는 이유가 여기 있어.
